# 12 任务生命周期｜v14 全景图 SVG 中的 T 模块（节点 18 个）

框标题：T · 任务系统｜先安排，再按渠道执行
框说明：保存未来安排，条件到达后恢复处理，取消时切断后续活动。

## 节点（编号与文档画板一致；措辞为 10/26 最新版，含每个节点两段讲解）
### T01｜把未来安排交给任务系统（蓝底）
- 要点：保留用户原话、对象和时间即时操作与未来安排分流创建回执只确认安排被接住
- 讲解①：用户说“十分钟后关主驾座椅加热”，Planner 应把目标交给任务入口，让后续系统记住时间、对象与动作。此刻不能直接关闭加热；用户如果说“现在关”，则进入即时车控，不需要建立等待中的任务。
- 讲解②：这个入口也可以承接条件、循环和持续跟进诉求。交办后继续看任务是否校验、保存并注册成功，不能仅凭调用受理就认为未来一定执行。用户当前得到的是安排的处理结果，十分钟后的真实车控还要经过另一轮触发与反馈。

### T02｜先辨认用户在新增、修改、取消还是查询（蓝底）
- 要点：结合现有任务理解本轮意图修改和取消先定位原任务查询只读取当前任务视图
- 讲解①：用户说“改成二十分钟后”，任务系统要结合现有安排找到刚才那条提醒，再解释新的规格。“取消刚才那个”进入管理分支；“还有什么提醒”则读取任务视图。几句话可能很短，却分别改变不同事实。
- 讲解②：Planner 负责交办这轮诉求，任务系统负责保存和维护任务。若把查询或取消误解成新增，会让用户越管理任务越多。对象找不到或存在多条候选时，应先澄清关联，不能默认选一条修改，更不能悄悄新建来替代原任务。

### T03｜确认条件能观察、动作能执行（金底）
- 要点：明确对象、条件与结束规则检查信号、工具、开关和配额不具备条件时澄清或说明限制
- 讲解①：创建前先把承诺落到可实现的内容。“到那里提醒我”还缺地点，“宝宝发烧时告诉我”需要可靠体温依据，仅有视觉模型并不足以承担这个目标。系统还要确认动作在当前车型可执行，以及用户指的是谁。
- 讲解②：必要信息齐备后再保存和登记；缺对象就补问，缺能力就说明限制。观察任务并发额度与任务中心总容量是不同检查，不能通过一个就跳过另一个。这样进入等待的安排才有实际证据来源，避免到时才发现根本无法判断条件。

### T04｜登记何时重新唤醒这条任务（蓝底）
- 要点：按时间、状态或视觉目标登记保留规则与原任务的对应关系注册失败时不进入正常等待
- 讲解①：任务系统根据诉求选择相应触发能力。明确时间交到调度，车辆条件交规则判断，视觉任务还要提供可观察目标。“后排宝宝哭了提醒我”必须保留具体位置、对象，以及命中后应该回到哪条任务。
- 讲解②：规则登记成功后才能继续等待。登记失败时，展示与回复不能仍写成安排已生效；修改、停止和失败补偿也要同步维护原规则。触发能力与任务之间的关联尤其重要，否则以后条件到了，系统仍不知道应唤醒哪位用户的哪项安排。

### T05｜先保存整条任务，再登记等待条件（绿底）
- 要点：Task 保存安排与结束策略Run 记录某一次执行保存与规则注册分别返回结果
- 讲解①：自建任务系统先保存 Task，也就是整条长期安排，再登记条件规则。周期按摩会产生多次 Run，每个 Run 单独记录这一次执行；Event 留下状态变化，TaskView 则供查询和展示使用，各自承载不同事实。
- 讲解②：因此保存成功后仍可能注册失败，任务存在不等于已经正常等待。系统需要让这种半完成状态可查询、可解释，并按实际补偿策略处理。验收创建时同时查看保存记录与规则登记结果，不能只凭数据库里有一条任务就向用户报成功。

### T06｜由任务系统持续等待下一次时机（蓝底）
- 要点：等待期间不占用 Planner 推理周期任务按次建立执行记录下电、退出和过期按任务规则处理
- 讲解①：任务注册完成后，等待交给任务系统与触发能力。用户可以继续聊天，Planner 不需要一直推理着数十分钟。周期提醒每到一次时机，再形成一轮执行记录；持续跟进任务则在后续进展出现时继续推进。
- 讲解②：等待期间也会发生下电、退出账号或任务过期。是否保留到下一行程，需要由具体任务的结束规则决定，不能因为存在定时器就默认永久恢复。界面应把当前业务状态说清楚，避免直接照搬一个 waiting 字段，让用户分不清正在创建还是已经等触发。

### T07｜收到触发后检查任务是否仍有效（金底）
- 要点：找到原任务并检查取消与重复原条件由触发器完成判断额外执行约束决定做或跳过
- 讲解①：触发通知到来，任务系统先找到对应任务，检查它是否已关闭、过期或处理过这次通知。用户刚取消了加热关闭安排，晚到的命中就不能重新执行。触发器已经判断原条件，任务层接着检查的是当前任务有效性。
- 讲解②：如果还存在额外执行约束，例如周期按摩这一轮座位无人，可以按规则跳过本次 Run。跳过只说明这一轮没有执行，是否结束整条 Task 还要继续看结束策略。不要重复调用同一个条件判断模型，也不要把一次失败直接改成整条安排结束。

### T08｜把本轮建议与任务执行记录一起交回主链（蓝底）
- 要点：关联 Task、Run 与推荐标识经推荐下发和车端回流输入管理安排 Planner 继续判断
- 讲解①：通用任务允许执行后，任务服务先关联推荐标识、整条 Task 和本次 Run，再经通知通道让客户端回流。服务端据此找回这一轮建议，输入管理决定何时交给 Planner，避免异步任务突然抢占当前用户对话。
- 讲解②：建议只说明该继续办理什么，还没有发生真实动作。Planner 随后规划本轮工具，返回结果再记回原 Run。已接入的 GUI 长任务可由自身执行方推进，不能强制每一个内部步骤都绕回 Planner；但任务归属与最终结果仍要可追踪。

### T09｜用实际工具结果更新本轮执行（绿底）
- 要点：按任务关联收集真实结果成功、失败与跳过分别记录车控受理后继续等状态确认
- 讲解①：Planner 决定本轮动作后，下游工具把真实进展返回，任务系统据此更新这次 Run。座椅控制接口只接受了请求时，应保留等待反馈；确认实际加热状态改变以后，才有依据把这一次关闭动作记为完成。
- 讲解②：结果回写需要独立可追踪，不能只依赖可能丢失的附带异步处理。验收时把工具结果、车辆状态、用户听到的话与卡片状态放在一起看。声音播完只能证明交互输出的一部分，无法代替这轮任务的真实业务结果。

### T10｜本轮结束后决定继续等待还是关闭任务（金底）
- 要点：单次与周期采用不同结束规则失败和跳过是否续跑单独决定终止时同步规则清理与视图
- 讲解①：一次 Run 结束后，任务系统读取整条安排的结束规则。单次关闭加热完成后可以结束目标；每小时按摩则可能继续等下一轮。本轮因无人被跳过，并不足以自动删除整个周期任务，需要按用户设定及场景规则判断。
- 讲解②：完成、取消、过期、失败和车辆下电都可能影响后续，但不同任务的保留策略不必相同。决定终止后清理规则与展示，决定继续后恢复等待。通知发送失败也不能回滚已经保存的任务事实，需把交互失败与业务状态分别记清。

### T11｜把修改和取消落实到原任务（蓝底）
- 要点：修改后重新校验并更新原规则取消要关闭目标与后续活动暂停与恢复按任务类型支持
- 讲解①：用户说“改成二十分钟后”，系统先找到原任务，重校验新的时间和对象，再更新对应规则。“取消刚才那个提醒”则关闭目标并撤销后续触发，不能只从列表删一张卡，更不能顺手新建一条替代任务。
- 讲解②：任务类型决定可用管理操作。我的任务和 AI 服务可以有删除入口，预设场景可以暂停，循环任务的暂停恢复需要单独支持；直接 GUI 任务的在途停止也要核实际能力。管理结果回来后再同步界面，已经发生的车辆动作另行处理。

### T12｜查询任务视图并呈现真实状态（绿底）
- 要点：语音查询返回现有安排任务中心按类别映射展示推送和上电拉取共同同步
- 讲解①：用户问“我还有哪些提醒”，系统读取 TaskView 返回现有状态，不因此新建一次执行。我的任务、AI 服务和预设场景使用各自的展示及管理规则；创建中、运行、暂停和关闭需要用用户能理解的含义表达。
- 讲解②：自建任务中心的容量方案将我的任务分为定时二十、条件二十和长时六，具体启用时按对应类型计数。云端更新推送、上电后拉取用于同步状态；退出账号清理哪些任务也按范围执行，不能把某一类清理扩大成全部安排消失。

### T13｜按项目选择唯一的任务托管方（金底）
- 要点：赛力斯可走自建 Task Service上汽分支可走 Extour Goal同一安排避免两套系统重复接管
- 讲解①：未来诉求进入这里，先确定当前项目由谁托管。赛力斯自建 Task Service 负责自身任务事实和执行轮次；上汽 Extour Goal 分支则由 Extour 保存目标并等待后续条件。两边都可能把执行建议交回 Planner。
- 讲解②：它们的创建卡、取消接口和状态含义分别定义，因此读图时选定一条路线往下走。不能把两套托管系统排成前后必经步骤，也不能向两边重复创建同一提醒。排障先确认任务实际属于谁，才知道应该查询或撤销哪边的目标。

### T14｜把目标与上下文提交给 Extour（蓝底）
- 要点：携带用户目标、上下文和车辆创建处理中保留未完成状态创建结果与未来触发分别回调
- 讲解①：上汽分支把用户原话、相关对话和车辆身份封装后，调用 Extour 的目标创建入口。Extour 接住后保存长期目标并负责后续条件；返回创建处理中，只能说明请求被接收，还不能对用户承诺安排已生效。
- 讲解②：随后分别等待创建成功、创建失败或未来条件触发的回调。成功创建与将来执行之间可能间隔很久，需要保留同一目标关联。静态 Advisor 的主动服务仍有自己的入口，不能因为这里也在跟进未来诉求，就合并成同一个生命周期。

### T15｜用创建结果通知用户安排是否成立（绿底）
- 要点：创建处理中只同步状态成功可直接显示目标卡失败原因回到 Planner 解释
- 讲解①：在采用 Goal 直卡交互的上汽路径中，创建成功可以直接显示目标卡，不必再次让 Planner 播报“已创建”。创建中的状态也不应被播成成功；创建失败则把原因送入推荐回流，让 Planner 告诉用户哪里没有办成。
- 讲解②：创建前可以给必要的处理说明，但卡片出现与用户未来得到服务相隔两段。还需要确认条件规则生效，再在命中时推进真实执行。具体车辆须已接入这套通知方式，不能仅凭有创建字段就认定成功卡、失败回流和后续触发均已可用。

### T16｜让 Extour 触发建议经车端回到主链（蓝底）
- 要点：触发先送推荐卡与关联标识车端回流后进入本轮处理检查旧建议、身份和回流有效性
- 讲解①：Extour 条件命中后先下发推荐执行卡，第一次下行不直接播报动作结果。用户点击携带推荐标识再次上行，服务端取回对应建议，再交输入管理和 Planner。这样回到对话中的内容仍能对应最初的目标。
- 讲解②：这一分支也有无操作自动推进的交互设计，但等待时机与确认规则必须由已接入项目明确，不能扩展成通用授权。采用单槽建议缓存时，后来的建议可能覆盖前一条，不能假定都会排队执行；身份、过期和迟到回流仍需逐次检查。

### T17｜分别记录建议被消费、目标关闭和界面结束（绿底）
- 要点：消费只表示建议进入 Planner关闭目标需调用真实托管接口界面 done 与后台停止分别核实
- 讲解①：Extour 建议被标记 consumed，表示已经送入 Planner 处理，尚未证明用户同意或车辆完成。关闭目标需要相应关闭操作；仅把客户端状态改为 done，可能只改变展示，不能据此认定后台已经停止触发。
- 讲解②：因此查询与管理时要把目标事实、消费回报和界面状态对应起来。部分更新与回报接口仍需明确接入，不能凭状态名相似自动补全。排查“界面结束却又来了建议”，先核真实目标是否关闭，再查旧回调和显示同步。

### T18｜结束任务时撤掉后续规则和观察目标（蓝底）
- 要点：关闭任务并停止后续触发视觉目标列表同步清理迟到结果不得重新推进旧任务
- 讲解①：任务取消或满足结束策略后，要关闭托管目标、清理触发规则，并更新端侧有效视觉目标。已关闭视觉任务的结果晚到时只记录，再补发完整目标列表纠偏。删除卡片如果没有带动这些动作，后台仍可能继续提醒。
- 讲解②：已经发生的车控不会随着任务关闭自动撤回。直接创建的 GUI 在途任务也不能套用普通取消承诺，停止能力需要对应执行方接入。下电、总开关和过期各自按任务类型处理，尚未明确的终止范围不能被一句“都取消了”掩盖。
