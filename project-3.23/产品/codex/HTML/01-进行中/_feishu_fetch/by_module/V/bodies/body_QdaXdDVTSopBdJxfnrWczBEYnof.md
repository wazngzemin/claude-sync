为什么要做豆包汽车</h2><p>我们做豆包汽车，核心是把“用户表达需求”到“需求得到满足”之间的操作成本降下来，而不是让用户多一个聊天入口。上一阶段已经能用大模型增强车辆功能调用，但产品复盘仍指出两个关键瓶颈：多轮任务推进难、对话割裂。单条指令理解得更好，并不等于一个复杂需求能持续办完；增加交互次数也不一定是价值提升，可能是用户不得不反复补充和纠正。这个判断推动项目从在旧语音链路上增加 AI，转向统一对话和任务的座舱助手。<cite type="citation"><a href="https://bytedance.larkoffice.com/docx/XNy1dc03QorjiOxnmC5cZy3fnhc" url-type="1">AI汽车产品 One 进入任务规划；跨步骤的事情根据工具反馈继续推进，不能只生成一段计划就结束；主动服务则要判断有没有价值、时机是否合适以及是否需要确认，不能把“知道用户状态”直接当成“获准替他执行”。端云协同也是为了真实约束，基础离线能力要能兜住可支持的操作，复杂理解可以利用云端，但断网后怎样恢复上下文、怎样解释能力边界都要设计。<cite type="citation"><a Director 承接，不需要先经过主动服务触发器。另一条入口是用户还没有开口，系统收到车况、时间、位置或业务事件，触发器判断条件是否满足并通知 Advisor 先把车外正在下大雨、空调已经最低、这个人不喜欢被直吹这些情境、端状态和记忆组装好，Director 再判断这是复合请求还是隐式需求，像“有点热又有点闷还想听点提神的”这种复合请求，和“我好热”这种要靠上下文推断的隐式需求，才交给它拆成开空调、调风量或座椅通风、放音乐这样一组动作；如果只是白名单里一句话“打开空调”这种明确简单指令，前面离线模型加白名单仲裁就直接快速执行了，不必都走一遍模型。动作拆完由 Agent Server 这个执行适配层去调车控、导航这些工具，工具结果回来 Director 也就是对话推理引擎这一层怎么把话听懂、把事办完，ASR 语音识别是更底层的感知能力，跟我不是并列的两条路线，会议总结、纪要只是另一种应用目标，实时问答和事后记录都建在识别之上，不能说成“我做交互、识别是另一块”。按目标分，一条是实时问答和当场执行，用户说一句直接调车控、导航、放歌，要求当场听懂、当场办对、可打断、执行有反馈，识别错一个字可能直接调错设备，用户当场就发现；另一条是内容记录，把已经发生的话转成文字再提炼成纪要，要求完整、可回溯，错字主要影响事后阅读，而且转写总结同样可以实时做，不能简单按离线和实时把它划成另一块，两条路可以共用识别基座也可以分开建设，取决于团队资源。用一个场景把这一段的交互要求讲透：导航正在播报“前方左转进入丰溪路”，用户不等它说完直接插一句“换条不堵车的”，系统一边播报一边还在听，用户随时能插话，这是我们要验证的全双工交互，本质是同时听说，不用等整句播完再喊唤醒词；设计场景不能代替实车验收结论。这里要把三个容易混的概念放回同一段里：我们当前主链路是级联式，识别、Director 推理、合成播报分段配合，全双工是在这条级联链路上靠边听边播、打断续接做到的，并不等于换成另一种模型；连续对话也不是全双工，它只是答完以后继续监听、允许用户补一句不用重新唤醒；原生语音到语音的端到端方案是另一条技术路线，模型方发布过通用版本，但车机接入状态和排期在我们这里没有证实，不把它和现在的级联划等号。还有一个边界，用户插话导致系统停播，不等于已经发出的车控被取消，打断的是播报，动作是否回滚要看业务设计，会话、任务、播放是三种不同状态，不能把停播理解成撤销。请求也不是都走最重的路，“打开空调”这种明确简单车控在前面离线模型加白名单仲裁就快速执行了，不必都进 Director；“打开空调并讲个笑话”同时包含说和做，才需要 Director 统一理解、分别推进，空调执行成功和笑话播报完成要分别确认，一项完成不代表全部完成；“我有点冷”这种没指定设备和参数的隐式需求，要结合当前车况和已有记忆再决定动作，也进推理。端云上，方案会结合信号来源、资源和离线需求划分：可本地闭环的监听和规则留在端侧，依赖云端能力的判断交给云端；不是所有触发和隐私处理都固定在同一端，这套二代链路现在还在开发联调，先把最小闭环跑通再补离在线配合。识别是整条任务的输入，我在产品上要把交互侧对识别输入质量的要求提清楚，比如车控指令不能认错设备、多人场景分得清谁在说，并按整任务是否办成来提要求，而不是只看识别单字准不准。（参考：<a 唤醒是怎么实现的？</h2><p>唤醒处在这套系统级助手最前端的采集和感知层，产品和供应商算法的分工要先讲清：产品侧定义用哪个唤醒词、在什么环境下响应到什么程度、误响和漏响怎么取舍、体验边界在哪里、拿什么标准验收；唤醒检测模型、回声消除这些算法由外部语音供应商实现和调参，产品不替代算法同学训练模型，也不把供应商实现细节说成自己做的。项目跟踪材料里，这类声学标定预计约两个月，这是历史上按车型给的预计区间，具体周期随车型和交付条件变化，不能当成当前现状，产品侧要据此安排台架与实车验证，而不能只拿模型测试代替整车验收。回声处理是持续辅助唤醒和识别的环节，不把它排成插在两者中间的固定先后台阶。这份方案用“豆包豆包”作为唤醒词，先检测用户是不是在叫它，确认唤醒以后再进入后续语音识别，该方案版本不支持自定义唤醒词，也不支持其他唤醒词，产品方向是用户说不说唤醒词都可以，所以不把选词做成开放配置项。用一个场景把取舍讲透：车正在播导航转向提示，用户同时开口喊“豆包豆包，导航回家”，麦克风里既有用户声音也有车机自己的声音，系统要先分清哪个是人话，再决定要不要醒。唤醒表面是喊一个词，实际要同时平衡两个方向，别漏喊，用户真叫了要及时响应；别误响，没人叫的时候不能自己醒，这对矛盾靠调灵敏度解决不了，抬一点漏喊少了误响就多，压一点反过来，所以要在安静和嘈杂两档环境分别看。PRD 给的是设计目标而不是实测结果，我只提两项：唤醒成功率安静环境目标不低于 98%、嘈杂环境不低于 95%，误唤醒率目标是用户没说唤醒词时不超过 12 小时一次，实车批次有没有达到要以测试记录为准，不把目标念成现状。回声消除与降噪，英文常叫 ECNR，这份 PRD 展开的是其中回声消除这一支，解决车机自己播的东西被麦克风收回去的问题，系统实时采集车内扬声器输出信号把参考音抵消掉，只留下用户指令，避免自己播的声音被当成用户指令，从最小音量到最大音量、音乐导航电话不同类型音频都要工作，不出现明显回声残留；回声处理没把自己的声音清干净，唤醒和识别都会被自己干扰，这也是自唤醒往往先怀疑回声链路、而不是先怀疑识别模型的原因。台架上自己播完语音把自己唤醒这种现象，如果遇到，我的定位方法是先假设回声消除没把自己的声音抵消干净、把自己播的内容收了回来，第二步核环境，先听录音里能不能听到自己播的参考音，再换静音回放看是否复现，最后排查是不是扬声器串到麦克风，把环境问题和产品问题分开定性，不把这个假设说成已经发生的真实案例，也不轻易下“这是 bug”的结论，更不会没核环境就要求改唤醒阈值。（参考：<a href="https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe">车内语音·唤醒与回声消除 PRD</a>；<a 必须说唤醒词吗</h2><p>先说结论：喊一句"豆包豆包"本质是给设备一个明确入口，用户喊出来，设备才判定这句话是说给自己的；免唤醒不是把这个词省掉，而是把入口从"喊词"换成"系统先判断这句话该不该接"，难就难在判断"是不是在跟车说"。这件事发生在语音主链路最前端，也就是麦克风收音之后、真正转写交给对话之前，唤醒词是这一层的显式开关，免唤醒则是把判断该不该接的活往前端拒识里压。为什么还要保留这个入口，因为车里一直在收音，乘客闲聊、放的歌、谁在打电话，如果不设一道确认就全接，误触发一次，用户的感受就是"我没叫你，你怎么自己动了"。用一个贯穿的场景说风险：后排乘客正常聊天，被系统当成指令认领了，这就是免唤醒最典型的误召回，车里比安静房间更保守，路面噪声、多人对话、娱乐声叠在一起，误唤醒会直接打断正在开的车。压风险靠三道闸，而不是一次全开：先看音区，也就是判断这句话从哪个座位来、这个座位有没有人，没人坐的位置不开，从源头上少接一路声音；命中以后也不直接办事，先过拒识，拒识就是判断这句话是不是在跟车说、认不认领、进不进对话历史，分不出来就宁可放过去；涉及需要确认的动作，必须用户明确说出来或者二次确认，免唤醒在这一步不放开。方案上替代代价很清楚：判断不稳就先让唤醒词兜底，而不是开了就全车接话，也通常不是一次全开，先在低风险、说一句就能办成的短指令上试，判断稳了再放开，因为省掉那声喊词省下来的便利，会被误触发赔回去。当前全时免唤醒还在研发验证中、没到上线阈值，拒识的升降级也还没打通，所以我不报一个现网通过率当现状。验收也不报没有确证的数字，而是分安静、嘈杂两档看两件事：真叫了能不能及时响应、没人叫会不会自己醒，再拿乘客闲聊、打电话这类语料过拒识看误召回，高风险动作必须走到确认才算过。（参考：<a href="https://bytedance.larkoffice.com/docx/KSWtdjsmwoJ1TzxcIv4c57vinle?from=lark_search_qa&amp;ccm_open_type=lark_search_qa#Ai29dEcaKofP12x5ZXrc4HSVnNc">多音区全时免唤醒方案</a>）</p><h2>Q10 · 免唤醒还有哪些别的思考</h2><p>结论先说：车里不靠读心，而是用音区、身份、视线这几个辅助信号，把"谁、在哪、说了什么"拼准，让用户不用每次自报家门，辅助信号只备"是谁、在哪"，不替用户猜"要什么"。这几个信号在链路里分两段：音区在最前端收音时就判出来，身份和视线先作为端状态上报给上下文组装，供后面判断建议给谁、结果回给谁，设备能拿到的只有声音从哪来、镜头看到谁、视线朝哪，这些都是旁证，不是想法本身，所以拼准以后还是要等用户把请求说出来。用一个撞车场景讲机制：主驾要求打开同一扇车窗，副驾同时要求关上这扇窗，这才是动作冲突，需要澄清；不同座位分别操作自己那侧的车窗，若权限和车型能力允许，可以独立处理，不能只因为两个人同时说话就认定冲突。处理分两种，内容互补就合并，比如主驾说导航去最近的加油站、副驾说顺便找带充电桩的，合成一条直接找带充电桩的加油站，不打断各自的话；明显冲突就先澄清，问清楚是谁说的、执行哪一条，不默认替人拍板，界面同时把谁在前、谁在后显示出来，让用户看得见采纳了谁。三个辅助信号各管一段：音区靠麦克风阵列判断话从哪个座位来，解决谁在说、结果回给谁，主驾说的回给主驾，不回灌到副驾；身份方案上考虑用人脸识别接出这个人常用的位置和偏好，没注册的乘客按设计降级成通用身份，正常响应车控但不调用车主偏好，声纹还在规划、依赖车企配置界面开发，人脸识别也还在研发验证中没调通，这几项我都不讲成已经上线；视线只做辅助，结合语音判断用户是不是在跟车说、是不是在跟旁边人聊天，看一眼不等于一条指令，人会自然转头看窗外、回头拿东西，单凭视线触发误判太多。方案选择上，辅助信号帮系统少问、少错，真正要办的事还是需要明确请求或确认，按相应入口执行，而不是把旁证当成授权。验收拿多人同时说话的语料看音区分辨准不准、互补有没有合对、冲突有没有先澄清，错把副驾的动作记成车主习惯、把话回灌给另一个座位，都算坏例。（参考：<a 能不能用更隐式的方式交互</h2><p>结论先说：可以，但隐式不是把系统的推测当成用户授权，而是设备先用状态信号把上下文备足，到了该确认的地方再确认，目标是让用户少开口，能由设备读到的状态就不让用户重复说，该用户点头的地方再用最轻的方式确认。这些隐式信号在链路里都是先送到上下文组装这一层当旁证，不直接变成指令。隐式通道大概分三类：一类是设备自己读到的状态信号，比如谁上车、坐哪个位置、是不是在疲劳状态，系统据此把上下文备足，用户不用每次重新交代自己在哪、要什么，设备知道人在哪，结果就回给哪个座位；一类是手势，方案里考虑过对刚提出的建议用确认或拒绝手势这类轻动作，用户不用再开口说"可以"或"不用了"，也不用抬手点屏幕，这块还在待评审阶段，实车效果待验证，我不保证已经落地；一类是视线，只做辅助，结合语音判断用户是不是在跟车说，比如用户转头和旁边人聊天时，系统就不把闲聊接成指令，不能单凭视线发起动作，因为人会转头看窗外、回头拿东西，单凭一个眼神触发误判太多。这些信号最后都要落到一个明确意图上，模糊状态只用来备上下文，不直接生成车控动作。动作处理分三档，和主动服务一致：建议类先递卡片或话术、等用户确认，比如续航不足提醒就近充电，用户点头才办；已经明确授权过的自动化直接执行，也就是用户先前清楚同意过、范围固定的习惯，按约定直接办，不再逐次问；安全通知强提醒，不等确认也要说，比如车辆告警。三档不能混，把建议当授权直接执行，或者把安全告警压成卡片等用户点，都是错的。用车载机器人方案里的落座欢迎这个场景贯穿：主副驾首次落座，机器人给一句欢迎；识别到疲劳状态，给一句放轻的关怀，不替用户改变驾驶行为；泊车成功给一句喝彩，属于事情做完以后的反馈。它的做法是先由落座、状态、完成这些信号触发，再由建议层决定是说出来还是只上卡片，不是传感器一看到人就开始说话，也不把感知直接变成动作。边界是：需要新授权或者信号不确定时才停下来确认，已经授权过的任务按约定直接执行，不必每次都卡一次确认；误把感知当动作、替用户做主，是这一类的主要坏例。（参考：<a · agent 交给软件后端团队是否更划算</h2><p>我的结论是：重复的通用 agent 202607（端云分工）</a>）</p><h2>Q26 · 平台接多家 agent 时，硬件价值在哪</h2><p>硬件这层的价值，是把后面 agent
