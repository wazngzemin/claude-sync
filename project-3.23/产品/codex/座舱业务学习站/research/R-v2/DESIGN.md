# R 章设计（Claude 定稿，Codex 照此写作和画图）

章名：R · 端云采信：一句话该不该接、由谁来办、怎样只办一次

和 V 章的分工：V 章已经把整条链路讲过一遍（判断要不要接、reject 与 unsupported、端云仲裁、回写）。R 章把“一句话进来以后，经过哪几道判断，最后由哪一边生效、怎样保证只办一次”讲深讲透。V 章讲过的入门内容，R 章只用一句话点回，比如“V 章讲过……这里讲它的完整规则”。

## 资料冲突的裁决（写作一律按这里讲，不提有冲突）
- 延时聆听：30 秒。主动服务播报结束后，也进入延时聆听。连续对话时长在部分车型可以设为 30、60 或 90 秒，作为设计选项来讲。
- 最终拒识之后：这句话的上屏文字清空，NLG（自然语言回复）不恢复。被打断的旧播报能不能恢复，看停播的原因：因为流式判断停的，在新话被最终拒识后可以恢复旧播报。
- 本地 1.7B 模型的地位：固定说法（本地干预缓存、正则规则）可以抢跑；车上 1.7B 模型给出的结果，只在断网或超时时兜底。这是后来改定的规则。早期车上模型可以抢跑，但误执行多，所以改成只兜底。讲成“我们为什么改”。
- 计时：云端从正式请求发出算起，3 秒没有返回，判为超时；链路连续 2 秒没有心跳，判为断网。两者是两个独立的触发条件。
- 已经上云、但云端拒识超时：车上 1.7B 模型的结果整体兜底，有把握的 reject 也可以采用。网络正常时，不采用车上的 reject。
- 多人合并的边界：以 Planner 输出第一个字（首 token）为界。之前来的话合并成一轮；之后来的话算打断，旧推理丢弃，已经下发的动作不撤回。
- 迟到的云端结果：不执行，记录为“未采用”，不在屏幕上展示，也不进入对话历史。
- 只办一次：讲成三道防线：同一个 request_id 关联同一轮；先执行的那一边生效，后到的结果不执行；新请求打断旧推理。再讲清还缺哪一道：跨通路的持久幂等键和取消传播。这一条写成“设计上的风险和下一步”，用设计者口吻，不说资料缺失。
- 网络恢复以后：按发生时间补传历史，标记为历史，不当作新指令重办。写成设计要求。
- TTS 缓存：本章只说“常用话术会缓存合成好的音频，命中时可以直接播放”，不写条数。
- 流式拒识的目标：写 90%（当前测试准确率见卡片 1）。

## 大纲与每段必须讲到的事实（数字以 facts.md 和部件卡片为准）

开篇：这一章讲什么，和 Planner 的关系
- 主例接 V 章：“带我去昨天那家游泳馆附近的餐厅”。再加两个 R 章自己的场景：在隧道里断网时说“打开空调”；豆包正在播报时，主驾和副驾同时开口。
- 图位：r-overview（原图）。

一、一句话要过几道门
- 按顺序讲清这几道判断各自决定什么、谁来做、输出什么：提前上云（attend）→ 停播（流式拒识）→ 接不接（云端最终拒识）→ 车上能不能办（固定说法 / FC / unsupported）→ 采用哪一边（端云仲裁）→ 显示什么（上屏）→ 真的执行。
- 核心：每一道门只管自己那件事，前一道通过，不代表后一道也会通过。
- 新图 r2-gates（见下文图设计）。

二、对话状态决定这句话走哪条路
- 讲对话状态机（卡片 9）的各个状态和触发条件；延时聆听 30 秒；全时开关；四音区；唤醒来源（车内、车外）；后仰时的音区修正；语音禁用（OTA 中、蓝牙通话中，等等）。
- 状态不同，入口规则就不同：例如首句豁免只在强聆听时生效。
- 图位：r-states（原图）、r-zones（原图）。

三、该不该接：拒识规则的全貌
- 三种拒识分开讲：流式拒识、云端最终拒识、车上 reject（点回卡片 1、2）。
- 硬规则：唤醒后 5 秒内开口的首句直接召回；单人不拒识；多人时超过 2 个字、句首没叫“豆包”，才请模型判断。
- 车上拒识的原则是高准低召：只拒明确的情况，模糊的交给云端。
- 过拒回捞；看屏幕、单人这些信号会提高召回倾向。
- 生效范围：哪些状态下哪条规则生效。
- 新图 r2-reject-rules。

四、由谁来办：端云采信规则
- 讲端云仲裁（卡片 8）：固定说法抢跑；网络正常时听云端；超时 3 秒；断网 2 秒无心跳；车上已执行的，云端晚到不执行。
- 规则的演变：为什么从“车上模型可以抢跑”改成“只兜底”。原因是误执行，用一个案例讲。
- 本地干预缓存：是正则规则层，不是模型；无上下文的单轮指令才适合放进去。
- 图位：r-adopt（原图）、r-dualrun（原图）；新图 r2-adopt-matrix。

五、断网、弱网和超时
- 讲网络状态判断（卡片 12）；离线时能做什么（离线简单任务、离线 TTS）、不能做什么；弱网时的重试；恢复后补同步；网络提示。
- 新图 r2-network-timeline。

六、只办一次
- 三道防线和一个风险（见上文裁决）；多人合并以首 token 为界；新请求打断旧推理，已经下发的动作不撤回；去重。
- 新图 r2-once-race。

七、屏幕显示要和真正生效的那一边一致
- 讲上屏（卡片 10）；最终显示的文字和实际采用的那一边对应；全时未激活时不逐字上屏；被拒识的话清空；左右胶囊；多屏；工具执行时的等待文案；TTS 播报和屏幕要一致。
- 图位：r-alwayson（原图）；新图 r2-screen-moments。

八、回写：把实际发生的事记下来
- 讲回写（卡片 11）；30 分钟、最多 10 轮；被拒识的话进入情景背景，不进入 Planner 的历史；补同步；端云融合结果埋点（local_cloud_fusion_result），用来追踪最后采用了哪一边。
- 图位：r-sync（原图）。

九、不同车型的设计选项
- 用一张表对比赛力斯、上汽、奇瑞等车型的选项：离线 ASR 芯片（8295 / 8397）、流式拒识跑在车上还是云端 H20、唤醒词（IP / 非 IP）、连续对话时长、音区数（四 / 五 / 六）、纯离线是否支持多人同时说话、声纹的用途。
- 讲成“每种选择的利弊”。

十、怎么评估、怎么排查
- 指标：误拒、误召、端云采信比例、超时率、句准，以及各自的含义和分母。
- 排查顺序：状态 → 拒识 → 采信 → 执行 → 上屏 → 回写。
- 用 2～3 个真实案例演示排查过程。

收尾、附一、附二：按 V-STANDARD 写。

## 新图设计（风格与 V 章 v56-figures 一致：同样的 class 和 CSS 变量，深色、浅色都清楚；每张图节点不超过 9 个；颜色要有含义并配图例）
- r2-gates：从上到下 7 道门，每道门标清“谁来判断 / 输出什么 / 通过后去哪”。右侧并列一个例子：插话“帮我把副驾座椅加热打开”在每道门的结果。
- r2-reject-rules：决策树。顶部“豆包在听到一句话”；第一层判断：是不是唤醒后 5 秒内的首句（是 → 直接召回）；第二层：车上是不是只有一个人（是 → 召回）；第三层：多人，且超过 2 个字、句首没叫豆包 → 交给模型判断（流式 / 最终）；车上 reject 用虚线标“只拒明确的情况”。
- r2-adopt-matrix：一个 3×3 的格子。行是网络状态：正常 / 超时（3 秒无结果）/ 断网（2 秒无心跳）；列是本地结果：固定说法命中 / 1.7B 给出车控候选 / 1.7B 给出 reject 或 unsupported。每格写采用哪一边。
- r2-network-timeline：横向时间线：正常 → 心跳中断 2 秒 → 判为断网、车上兜底 → 网络恢复 → 补同步（标为历史）→ 回到云端为主。
- r2-once-race：两条泳道（车上 / 云端），同一个 request_id。车上先执行“打开空调”，云端结果晚到，标“不执行，记为未采用”。下方再画一条：首 token 前后各来一句新话，分别是合并和打断。
- r2-screen-moments：四个时刻并排：边说边出字（激活态）→ 最终文字按采用的一边刷新 → 被拒识，清空 → 工具执行中显示等待文案。每个时刻画一个小胶囊示意。
