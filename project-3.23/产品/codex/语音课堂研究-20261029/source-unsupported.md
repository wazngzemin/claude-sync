# 【AI汽车\-PRD】车控不支持指令播报和车书打通

## 背景

车载语音助手极大地提升了驾驶中的便利性与安全性，但并非车内的所有功能都支持语音交互。受限于车型配置、系统版本、硬件能力或安全法规，总有部分功能无法通过语音直接控制。

当用户尝试使用语音操作这些“不支持”的功能时，一句简单的“抱歉，我做不到”会中断用户任务，带来挫败感，甚至可能因为用户转而寻求手动操作而引发分心。一个能力强的智能伙伴，不应在能力的边界戛然而止，而应成为一个负责任的向导，帮助用户安全、高效地达成目标。

<div class="callout">

**核心问题**：当用户发出一个车载系统“有此功能，但不支持语音控制”的指令时，我们如何给出清晰、礼貌且具备操作性的回应，引导用户通过物理按键或屏幕菜单完成操作，而不是简单地拒绝？除非功能真没有。

</div>

## 产品目标

设计一套“不支持指令”的播报与引导策略，将一次潜在的失败交互，转变为一次有价值的帮助。

- **清晰，有帮助**：用自然、友善的语言解释“为什么不支持”，并立即提供“下一步该怎么做”。

- **可解释与可信赖 **：通过一致、可靠的反馈，让用户理解系统的能力边界，建立长期信任。用户会明白，即使豆包做不到，但也会尽力提供替代方案。

## 详细产品定义

### 整体的流程

### 不支持的分类

1. 需要对座舱的FC函数列表，标记出哪些支持，哪些不支持。【文档：[【AI汽车主线\-赛力斯】座舱大模型全域FC协议](https://bytedance.larkoffice.com/sheets/Q2d5sizRBhWXN6t859mci6qNnvd?sheet=AayeJY)】

2. 不支持的类型存在「车上没有该功能」和「车上有该功能，但不支持语音控制」两种类型，但标记时不对此做具体分类。

3. A类：车上没有该功能

    1. 描述：由于车型、配置或软件版本原因，车辆确实不具备用户所提及的功能。

    2. 示例：在一个未选装香氛系统的车上，用户说“打开香氛”。

4. B类：车上有该功能，但不支持语音控制

    1. 描述：车辆具备该功能（物理或虚拟），但因安全、架构或权限等原因，未向语音交互开放控制接口。

    2. 示例：“打开双闪”、“调节后视镜”。

### 内容来源

1、为了确保引导的准确性和权威性，所有“不支持语音”指令的替代路径信息，都必须来源于“用户手册”的信息

### 播报策略

1. **统一检索**：将用户不支持的指令函数，在“车辆用户手册”知识库中进行检索，查找相关功能的操作说明。

2. **分支**：

    - **若在车书中找到对应内容**：

        - **判定**：此情况大概率属于 **B类（车上有功能，但语音不支持）**。

        - **回复**：这个后备箱功能不支持语音控制，你可以通过『车书Agent来告诉怎么操作』这个功能。

    - **若在车书中未找到对应内容**：

        - **判定**：此情况大概率属于 **A类（车上没有此功能）**。

        - **~~回复~~**~~：抱歉，车上没有此功能。~~

        - 回复：抱歉，车上没有尾翼这个功能哦。

- 补充：

    - 在回复场景里，需要明确说出，不支持的功能是什么。

        - 示例：后备箱没法用语音控制哦，不过你可以这么操作//抱歉，这车上没有尾翼这个功能哦～

## **典型场景示例**

**示例 0：空调（车有功能，支持语音控制）**

- **Query**：：打开空调

- **Answer**：空调打开了

**示例 1：转向灯 （车有功能，不支持语音控制）**

- **Query**：打开左转向灯。

- **Answer**：左转向灯不支持语音哦。它的控制杆就在方向盘左后方，向下拨动一下就好。

**示例 2：双闪 （车有功能，不支持语音控制）**

- **Query**：打开双闪警示灯。

- **Answer**：“双闪灯请手动开启。紧急按钮就在中控台最显眼的位置，是那个红色的三角标志。

**示例 3：零重力座椅 （车无此功能）**

- **Query**：打开零重力座椅。

- **Answer**：抱歉，车上没有此功能。
