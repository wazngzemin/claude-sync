# 【AI汽车】云端视觉触发器需求文档

<div class="callout">

**视觉类需求前提说明：**

Q：已经提了有很多和视觉相关的需求，他们之间的关系是什么？

A：目前已知和视觉相关的需求包含 

1. VQA 视觉问答，功能定位是对过去式或下发指令那一刻的视觉信息进行询问（前方车辆是什么牌子、旁边那个小区是什么名字），技术方案采取端侧VLM\+图片上传云端VLM配合实现；

2. 影视剧搭子，功能定位是在用户观看电影或电视剧时，豆包作为搭子陪伴用户，解答用户问题（剧里这个人是谁演的）且能对剧情信息进行主动响应，技术方案采取豆包视频通话中的共享屏幕实现；

3. **【本次需求】云端视觉触发器**，功能定位是用户指令需要持续性视觉监测（发现车里有人睡觉就降低媒体音量、后排小孩玩手机你就提醒我），直至该视觉达到要求触发执行/提醒事件，技术方案采纳豆包视频通话能力实现；

**和端侧VLM的关系：**

Q：有些持续性视觉监测（如有人睡着、有人打呼噜）端侧VLM也可以做到，为什么还需要豆包视频通话？

A：端侧VLM只能覆盖被定义的有限集合，且现阶段准确率并不高，豆包视频通话可覆盖场景更多，准确率随豆包主端持续迭代优化，更能满足视觉类触发持续任务的场景。待后续端侧VLM发展到成熟阶段，再考虑二者如何融合。

# 需求概述

根据任务类型，车内任务被划分为：单步任务、条件任务、多步骤任务、持续任务四种分类。其中，持续任务最为特殊，它需要长期保持感知与运行状态，从而持续性为用户提供伴随式服务。

本次需求聚焦于**视觉触发类的持续任务**，如当主驾驾驶疲劳时提醒他，此时需要一个视觉模型持续观测主驾驾驶是否有疲惫现象，在检测到疲惫时通过豆包进行温馨提示；同理如车内有人睡觉时降低媒体音量，当视觉模型检测到车内有人闭眼睡觉时通过豆包控制媒体音量。

迭代后的豆包视频通话具备用户指令下达后的持续性的视觉监测，通过预测每张图片对应的Special Token，\[SILENT\] 表示不做响应，\[SPEAK\] 表示要主动响应。该能力可被赋能于车载视觉触发类的持续任务。

### 语义理解分发

语音助手应具备准确理解用户指令的核心意图，并正确分发给豆包视频通话处理的能力。用户指令需满足以下要求：

- 属于视觉类触发（Advisor判断）

✅ 有人睡觉时、有人上车时、有人抽烟时、有人哭泣时

❌ 十分钟之后（时间触发）、车内温度为25度时（端状态触发）、勇士队赢了时（信息触发）

- 属于持续性任务（Planner判断）

✅ 当有人睡觉时提醒我、有人上车时跟他打招呼、有人抽烟时给车窗开条缝、有人哭泣时安慰他

❌ 前方车辆是什么品牌、我刚路过的桥是什么桥（无需持续性监测，是对过去或发出指令那一刻的视觉信息查询）

### 豆包视频通话

迭代后的豆包视频通话具备用户指令下达后的持续性的视觉监测，和相关产品（@李若瑄）确认后的信息：

- 图片上传频率

    - 用户不说话的时候，之前每2s一帧，最新线上每4s一帧

    - 车载端可定义上传频率，但频率越高，成本越高

- SILENCE输出频率

    - 无规律，模型在图片输入都会判断要不要主动说话

    - 图片上传频率越高，SILENCE输出频率越高

- 任务维持机制

    - 内部不存在任务状态管理，全部靠模型SP和Context信息来理解

    - Context信息包含用户Query、每次模型输出、图片（部分图片会通过策略丢弃）

    - Context window超过24K后，任务会被抛弃，目测24K可以存下40分钟内的所有信息

    - 但模型SP遵循效果有限，40分钟内不一定会主动发起，豆包内部也在优化，短期内想要预期效果，仍需要Advisor持续推进触发

和座舱研发（@张弛）确认后的信息：

- 豆包支持视频通话能力接入，但必须要求通过RTC链路

- RTC链路支持文本\+图片输入，文本输出，但是存在以下弊端：

    - 建联耗时久，慢的时候需要6、7秒

    - 建联后所有query都会进RTC链路，使用RTC链路的ASR能力，无法区分音区

- 近期考虑自研链路，可绕过RTC链路接入豆包视频通话能力，正在做技术可行性调研
