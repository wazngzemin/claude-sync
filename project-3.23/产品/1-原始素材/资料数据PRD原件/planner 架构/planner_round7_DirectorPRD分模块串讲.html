1这份 PRD 整体在写什么

一句话：定义"对话推理引擎（Director）"这个模块在车上该干什么、不该干什么、干得好怎么量。它不是技术方案，是产品需求——回答的是"系统行为应该是什么样"，不是"代码怎么写"。

章节写什么一句话概括
模块综述Director 的定位、输入输出、要解决什么问题对话中枢+推理中枢，治"一锤子买卖"和"割裂没内涵"
链路图Director 在 AI汽车1.0 全链路里的位置前面有 fc模型/拒识仲裁分流，后面有工具执行，旁边有触发器和 advisor
对话需求话术策略：说什么、怎么说说做一致、别废话、[情绪]标签
推理需求任务拆解：结合 context、四种任务类型情景/端状态/记忆/人名/人人对话 五结合
条件任务定时/条件类任务怎么注册和触发=触发器，你的产品的母定义
跟进任务长任务怎么跟踪：goal list + 动态advisor从"单线程响应"到"目标驱动"
冲突处理多任务抢话筒/抢推理怎么办推理阶段合并 + 交互阶段六级策略矩阵
对话节奏什么时候该少说话、不说话"豆包豆包"→沉默，"豆包小公主"→接话
知识管理SP 太胖了怎么瘦身前置筛选模块——按需加载
性能/质量数字目标 + 评测字典首token P50 500ms；推理ACC≥90%；缺失/冗余/错误三 fail

一个 case 走完全链路："我好热"

① 话筒：明骏（主驾）"我好热" → ASR
② 分流：拒识=未拒识；仲裁=不是简单车控指令（无明确动作）→ 不走fc，给Director
③ Director推理（SP注入）：
   情景：车外正下大雨     → 不拆"开窗"
   端状态：空调关、温度非最低 → 可以开空调、可以调低
   记忆：用户不喜欢吹风   → 不拆"大风量对人吹"
   → 输出：{"talk_content":"车里是有点热呢，我来帮你打开空调降降温～",
            "action_list":[开空调, 温度21℃, 风量3档]}
④ 执行：车控执行 → tool_feedback"执行成功"
⑤ 二次推理：总结话术 → "都搞定啦，车里马上就会凉快了"
用户在车上感知到的只有两秒："有点热呢，帮你开空调" → 空调启动 → "搞定啦"。他看不见的是：分流模型放行了它、三条 context 各自否决了一个错误动作。这就是 PRD 说的"对话和推理一体，像人一样沟通"。

4模块① 对话需求：说什么、怎么说（话术策略）

4.1 四条铁律（全部带 bad/good case）

铁律为什么重要PRD 里的 case
别生成无意义响应话术（查询问答/简单车控场景）"我帮你查一下"是纯废话——查完才说的才是人话；还占 TTS 时间query"空调现在是开的吗"：bad"我帮你查一下" → good（查到后）"空调现在是开着的"
响应话术别把做什么介绍得太清楚缓解机械生硬感+防幻觉（说太细=承诺太具体，工具没做到就穿帮）"帮我凉爽放松"：bad 把按摩/通风/氛围灯冰川色/空调15度全念一遍 → good"先把座椅按摩和通风打开，顺便调一下氛围灯和空调"
响应话术和总结话术重复率要低同一句话说两遍是机器人感的最大来源"我好热"：bad 响应"帮你开空调调最低"+总结"空调打开了温度调最低了" → good 响应同上，总结就一句"都搞定啦"
[情绪]标签体系一句话承载语气，下游按标签选播报工具（[唱]→唱歌工具，其他→sami TTS）[用悄悄话说]后排小伙伴睡着了…；[模仿林妹妹的声音说]…；[深情地唱]…

4.2 说做一致：内容一致 + 节奏一致

"工具调用与话术输出严格绑定，确保'说做一致'。"
这是话术的宪法：嘴上说的必须是手上做的，手上做的必须嘴上有交代。说了"帮你开窗"结果 action_list 里没有=说谎；action 里开了座椅加热但嘴上没提=惊吓。节奏一致=别一次性把五步全念完，做一步说一步（家越07版 SP 的示例16彩虹灯"串行节奏"就是这条的兑现）。
车上翻车现场：用户"帮我凉爽一下"，豆包一口气念"我先开按摩开通风氛围灯调冰川色空调15度马上就好"——TTS 念了8秒，车还没动，用户听着像背稿子。改成"先帮你开按摩和通风，顺便调下氛围灯和空调"=边说边做。

4.3 讲话风格（草稿，7种可切换）

方向盘旋钮切换风格，每种风格下有长期且独立的对话记忆——选了"搞笑戏精"并约定自称"豆包小姐"，之后该风格下都说"豆包小姐来咯"。注意：这是草稿状态，07-22 版 SP 里只有"温柔高知女生"一种人设，多风格未落地。

5模块② 推理需求：五结合 + 四种任务类型

5.1 结合 context 推理（PRD 给的全是"不拆解出什么"的减法 case）

结合什么querycontext正确动作（减法）
情景"车里好闷啊"车外正下大雨不拆"开窗"
情景"车里有些热"后排有一位老人一个宝宝不拆"后排大风量"
端状态"车里好热啊"空调已开且温度已最低不拆"开空调/调低温度"
记忆"车里好热啊"用户不喜欢吹风不拆"大风量对人吹"
记忆"去昨天那个烤鸭店"昨天去的是徐汇日月光京典烤鸭直接导航该地址（不用问）
人名改写"给明骏把座椅加热开了"明骏坐副驾tool 下发改写成"打开副驾座椅加热"
人人对话"附近找个评分高点的"晓伟和明骏刚聊完火锅改写成"附近找个评分高点的火锅店"
注意一个反直觉的点：PRD 讲推理质量，用的几乎全是"不做什么"的 case。因为"我好热"的默认拆解（开窗+开空调+大风量）谁都会，真正拉开差距的是用 context 否决掉那些'标准答案'里的错误动作。好的任务拆解=做对加法，更要做对减法。这直接就是评测里"冗余操作/错误操作"两类 fail 的判定依据（§11）。

5.2 四种任务类型（PRD 原版定义 vs SP 演进）

类型定义典型 query拆解要点
即时任务（单/多）一轮 react 内闭环"我好热"/"有点热，空调20度开外循环再放首摇滚"多动作并行；"前挡都是雾"类安全相关的先除雾+外循环+3分钟后关除雾（时间衰减动作带回调）
多步任务串行依赖，前一步结果是后一步输入"去昨天那个游泳馆"/"播放我是歌手第四季夺冠的歌"step1 拿信息（记忆/搜索）→ step2 执行（导航/播放），不能并行
条件任务（含定时）带触发条件，注册后等触发"十分钟后关座椅加热"/"车内超28度让我凉快一下"调条件任务注册工具；先过合理性仲裁5条（见§6）
持续任务一段时间内持续运行，自主决定交互时机"介绍沿途风景"/"扮演猪八戒和我说话"/"跟副驾朋友聊天"可打断可恢复；用户已掌握的功能不再长篇介绍；衔接用户当前话题
示范 case：除雾（PRD 原文级还原）——时间衰减动作的标准处理
query："前挡都是雾，看不清了"
响应话术："车内玻璃是有些起雾[端状态]，我来帮你打开前窗除雾，视野马上清晰[动作]～"
任务拆解：① 开前挡除雾 ② 空调外循环 ③ 三分钟后关闭前挡除雾
总结回复："前窗除雾和外循环开啦，三分钟后会帮你关闭～"
context 减法：外面下大雨→不开窗除雾；已是外循环→不重复开；用户讨厌开窗→不拆开窗
→ 这就是家越07版 SP 示例17"定时自我唤醒"的祖宗：除雾/极速制冷/座椅加热这类'有时间衰减效应'的操作，执行时就要约好回调。

6模块③ 条件任务 = 触发器 你的产品的母 PRD

"对话推理引擎判断是否需要创建条件任务，需要时调用 operate_conditional_task 工具并以自然语言下发（如：车内温度超过30度时打开空调）。工具完成条件的解析和监控，条件达成后通知对话推理引擎。"

6.1 条件合理性仲裁 5 条（Director 的 P1 职责——触发器的准入闸门）

仲裁项不合法 case为什么
① 能否被感知"副驾吃了饭就…" 系统感知不到副驾吃没吃饭
② 具备触发可能性"外界温度超200℃就…"物理不可能
③ 动作符合价值观"把车开到河里"/"播报色情新闻"黄赌毒/损害他人/伤害自己
④ 动作可执行"空调调到50℃"超设备能力（对照家越07边界15.5-30.5℃）
⑤ 条件与动作不矛盾"车内>40℃时空调调到最高"/"检测到尾气污染时开车窗"自相矛盾
车上表现：用户说"世界毁灭时打开空调"→ Director 不调注册工具，聊天回复（"这个条件恐怕等不到啦"）；说"车内温度比较高时开空调"（模糊条件）→ Director 主动明确化为"车内温度超过26度时打开空调"再注册。模糊动作同理："让我凉快一下"→注册时写成"让车内环境凉爽一些"，具体动作等触发后再定。

6.2 触发后的回流（闭环）

用户"十分钟后关座椅加热" → Director 调注册工具 → tool 返回"条件任务已注册"
→ 触发器拆条件（定时器10分钟）→ 到点 → 给 Director 下发：[任务原文]+条件已触发
→ Director 执行关加热并告知用户
注意这个回流设计：触发器自己不动手，它只"叫醒"Director，动作还是 Director 下。这就是为什么后来技术评审把触发器抬成"任务系统承重墙"——它是所有条件/定时/持续任务的闹钟中枢，但执行权始终在 Director。你 7 月评审里"端侧触发器回赛力斯CDC固定闭环"的争论，根子就在这条链路上。

7模块④ 跟进任务 = goal list + 动态advisor 你的另一块地盘

7.1 什么是跟进任务（定义+正负例，考试级重点）

"任务无法在一轮即时连续的 react 中闭环，且被其他任务打断后恢复价值高，需要后续跟进。"
例子判定理由
正例"接下来行程持续介绍沿途风景"跨整段行程，必然被打断（导航播报/新query），恢复价值高
正例"帮我点杯咖啡送到公司"多步+等用户确认，跨轮
负例"氛围灯按彩虹色演示一遍"一轮 react 能闭环，被打断也不可惜
负例"帮我研究大模型领域SKILL"独立执行，不会被别的任务打断

7.2 为什么需要它（PRD 列的 6 个能力缺口）

缺口人话翻译
目标跟踪能力Director 触发靠 user query/advisor，没有长期目标驱动——用户不说就忘了
多线程并行Director 是单线程，同时跟进不了多件事
动态适应目标推进中环境和需求会变，得有人盯着调
统一框架定时/条件/长时任务有共性（要跟进/有触发/有目标），别各搞一套
缓解 Director 依赖Director 要保响应速度，重思考甩给 advisor（性能vs质量的矛盾的分诊处方）
涌现能力职责分散=更少输入和限制，模型反而表现更好

7.3 分工（名词澄清表，全 PRD 最重要的一张表）

8模块⑤ 冲突处理：两套机制，防系统"自我分裂"

8.1 为什么会有冲突（PRD 自陈）

"这些冲突有些存在于推理阶段…有些存在于播报阶段…需要一套机制，避免因为新任务产生导致旧任务被打断，从而产生系统自我分裂的混乱状态。"

四种典型抢道：新 query vs 旧播报（"讲AI新闻"→"车里快热死了"）；advisor建议 vs 用户对话；触发器条件任务 vs 用户对话；系统通知 vs 用户对话（"电机故障请靠边停车"）。

8.2 推理阶段冲突（当前方案，机关在"首token出没出"）

正在进行的阶段新来处理
推理中，首token未出user query / advisor打断当前推理，把新旧输入合并后重新推理（反正还没开口，重新想成本最低）
首token已出 or TTS播报中user query打断，直接进行新 query 推理（用户最大）
首token已出 or 播报中advisor若后续被新 user query 打断→advisor 建议和新 query 合并推理；若没被打断→等播报完，睡眠2s（可配置）再喂给 Director；等待期间同一 advisor 多次建议只处理最新
这张表的精神就一句：用户的话永远可以插队，advisor 的话必须排队。"首token未出"是分水岭——没说出口的想法可以重来，说出去的话泼出去的水。睡眠2s是人性化细节：播报刚停就接话像抢话，停两秒像"想了一下"。

8.3 交互阶段冲突（六级策略 × 优先级矩阵）

策略（新任务优先级低→高）含义
扔弃新任务旧任务继续，新的扔掉
排队旧的完了再上新的
静默执行新任务不需要说话（GUI/生图）→ 后台跑
整合暂停旧推理，query 拼接后新旧一起考虑
插队暂停旧的，先新的，再恢复旧的
停止旧任务抛弃旧的，直接上新的

矩阵的优先级精神（简化）：安全通知 > 导航通知 > 系统消息 > 用户复杂query > 条件任务 > 主动服务。举三格体会：

正在进行新来策略车上表现
豆包在讲AI新闻（主动服务）安全通知"电机故障"插队新闻立刻停，先报故障，报完可以续
安全通知播报中配置类主动服务静默执行别拿任何话打断安全播报，能做的后台做
豆包在讲新闻用户复杂query"车里热死了"插队新闻让路，先解决热，新闻之后恢复
没有这套矩阵的车上乱象：豆包正讲沿途风景，触发器到点"帮你关座椅加热"打断风景；导航播报和豆包同时出声；安全提示被广告式主动服务盖掉。矩阵就是让"谁在什么时候有资格开口"有法可依。

9模块⑥ 对话节奏控制：什么时候该闭嘴

"现阶段 director 的对话体验最大的问题，是在一些需要它'少说话'或'不说话'的场景叽叽喳喳。"
场景策略PRD 示例
用户停顿（喊了唤醒词还在想）"豆包/豆包豆包"等无含义输入→简化回复或不回复（嗯/你说/我在/在呢）；"小豆包/豆包小公主/臭豆包"算有含义，要接话user"豆包豆包"[判停]→doubao[沉默]→user"空气净化开一下"→"搞定！"；user"豆包小公主"→"小公主在呢，怎么啦"

这一章和家越07版 SP 的静默规则（音乐播放成功不说话/录音开启后静默）是同一哲学：会闭嘴的助手才像人。注意"豆包豆包→沉默"这条——它解释了为什么唤醒词是叠词：叠词在口语里几乎只用于唤醒，把'无内容唤醒'和'有内容指令'在文本层面就能分开，模型才能放心沉默。

11.3 三 fail 定义（全 PRD 最有实操价值的一节，你 bug 分诊的祖宗）
