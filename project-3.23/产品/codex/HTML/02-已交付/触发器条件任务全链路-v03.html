条件任务的业务模块责任图

案例：“当座舱实测温度降到 25℃ 时，播放《XX》”。每个节点都写清业务模块、责任、输入和输出。

正确主链是：用户 Query → DT / Planner / Director（同一决策职能）→ 条件任务模块 → Trigger 监听 Context / 端状态 → 条件命中回到条件任务模块 → DT / Planner / Director 再决策 → 音乐能力 → 结果回写。Advisor 只在动作本身是“生成一条建议”时才参与，本案例的播歌主链不经过 Advisor。

你原来 8 步里的关键错位

  • • “DT → Advisor → Director”错了：DT / Planner / Director 是同一决策职能，不是三个串行大脑。
  • • “Advisor 解析条件和动作”错了：普通条件任务由条件任务模块管理。
  • • “Trigger 命中回 Advisor”错了：应回到条件任务，再恢复原目标给决策模块。

Advisor 的正确位置

  • • 播放指定歌曲是确定性动作，不需要 Advisor 二次思考。
  • • 如果用户要“条件成立后给我一条个性化建议”，Advisor 才产生 advice。
  • • Advisor 只给决策模块建议，不直接代替 Trigger，也不直接执行音乐工具。

评审现场可直接问

  • • 条件任务模块这个业务边界，在当前版本由哪个线上模块承接？
  • • Trigger 命中后的回调对象是条件任务还是直接回 Planner？新旧版本如何分界？
  • • 音乐播放成功以哪个回执为准，失败由谁决定重试和结束？
业务模块只负责什么不负责什么证据状态
DT / Planner / Director理解用户目标，判断是否创建条任务；命中后决定本轮行动。不持续监听温度，不自己保存长期任务状态。资料明确
条件任务模块管条件、动作、任务状态、去重、执行轮次和结果收口。不代替 Trigger 判断实时信号，不代替音乐能力播放。业务边界明确，当前线上承接模块待确认
Trigger获取状态、判断条件、防抖频控，命中后发出事件。不理解整个用户目标，不直接决定或执行播歌。资料明确
Context / 端状态供应座舱温度等当前事实和数据时效。不存任务，不做最终行动决策。资料明确
Advisor在需要个性化建议时生成 advice，给决策模块参考。不是普通条件任务的必经环节，不直接播歌。资料明确
音乐能力找歌、播放、返回真实结果。不决定什么时候触发，不管条件任务生命周期。具体工具名和成功回执待对齐
