# V 语音输入与判停

这里采用的语音链路以 300 毫秒的短停顿触发 Soft VAD。车端拿当前文字发起一轮预请求，预处理只完成 LLM 的拒识、意图识别和简单复杂仲裁，不抢跑到函数调用、Director 或对话管理模块；同时继续收音。准备阶段不播正式答案，也不下发车控或导航动作。

停顿达到 500 毫秒时，Hard VAD 让当前音频段收尾，再取得二遍 ASR 的最终文字。300 和 500 毫秒都从停顿开始计算；这两个数描述判停配置，用户等到回答还会经过后续推理与执行。车型采用的实际阈值由对应配置决定。

两条停顿路径会把 300 毫秒和 500 毫秒的识别文字做比对。文字一致时，直接沿用短停顿已经得到的意图进入下游；文字不一致，例如一遍听成“播放音月”、二遍修正为“播放音乐”，就按最终文字重新请求 LLM。若 300 毫秒时判断句意还不完整，例如“我想订一张去……”，则启动语义 VAD，继续等到 1000 毫秒（暂定）；到点后不再判断完整性，直接把结果交给后续 LLM。语义完整性本身的判定方式还要结合供应商输出评测后再定。

语义判停进一步处理“声音停了，但意思还没说全”的情况。例如“我想去……”仍缺目的地，它用于判断是否多等用户一会儿；判断不完整时进入语义 VAD，继续等到 1000 毫秒（暂定）。不同版本对语义判断和计时收尾的配合方式不同，具体延长规则随项目版本配置。

# R 入口与端云采信

唤醒入口有五种来源。标准唤醒说“豆包豆包”，方控 AI 硬按键短按归属主驾，“豆包”后面直接跟有效指令，全时态开关打开时用户直接说出有效指令，主动服务也可以拉起对话。未同意隐私协议、未开启 AI 开关、泊车等禁用场景不支持唤醒，界面用 toast 说明禁用原因，这时候再喊唤醒词也不会进入聆听。拾音默认拉起全车四音区，不会只收当前说话位置；语音唤醒遵循音源定位，硬按键唤醒固定记为主驾。

未唤醒的全时态阶段，ASR 过程文字不上屏，系统判断为有效指令后才把整句上屏；从唤醒到延时聆听期间，ASR 内容才流式上屏并等待拒识结果。TTS 播报结束后进入延时聆听，免唤醒开关打开时计时 30 秒，关闭时计时 60 秒退出并回到静默态。

已经激活的请求在 vad 结束后端云双跑。本地给出 reject 不被采信，要等云端拒识结果；本地给出 functioncall 或 unsupported，同样先等云端判断。TTS 播报过程中，系统用 partial ASR 流式请求本地模型做插话打断判断，确认打断后收音到 vadend，再进入主对话流程。

干预缓存排在本地模型之前。query 先经过离线 ASR，再进入干预模块；命中白名单正则后，直接输出配置好的 functioncall，跳过本地 LLM；未命中才交给本地 LLM 理解。早期版本里的黑名单规则随 0930 仲裁调整取消，当前不再按黑名单拦截。

离线指令缓存遵循三条原则。单轮解析，只看当前这一句，不引用历史对话；上下文无关，“暂停播放”“继续播放”“就选它了”依赖前文对象，不进入缓存；结果唯一，每条指令必须映射到唯一意图和槽位组合，可能歧义的指令回退到其他解析路径。缓存命中目标响应 50 毫秒、准确率 100%；请求超出离线范围时，离线模型输出“其他”。

0930 调整后的仲裁顺序是本地正则缓存优先，其次云端 planner，本地 LLM 只在断网或云端超时作为兜底。正常联网时，本地模型即使先返回 functioncall 也先保留候选，不抢先执行。早期“本地 LLM 先分流、本地 FC 直接采纳并中断云端”的规则已经废弃，不能再写进当前链路。

本地模型能承接的范围有限。它支持 TTS 流式打断、拒识、简单功能 FC 和少量上下文继承；开放问答、联网搜索、内容生成、复杂导航规划与地点出行推荐、多步工具编排与长任务、依赖大量端状态、事件和长期记忆的判断都超出本地范围，需要整段上云交给云端处理。

断网时本地三类结果分别处理。本地 functioncall 和 reject 直接采纳；本地判定为 unsupported_cloud 的有效诉求，播报“网络异常，请稍后再试”，单次唤醒周期内同类网络异常的 NLG 只播一次，避免用户连续尝试时反复听到同一句提示。

云端请求超过 3 秒没有返回视为超时。本地已有可执行 functioncall 或 reject 就采纳；本地 unsupported 走异常话术。超时之后云端结果晚到，不再触发执行，也不能补做已经结束的动作。网络格数差不能直接证明业务已经超时，计时起点和停止点以当前配置为准。

本地办理结束后，识别文字、结果类型、函数参数和回复要同步出去。同步字段包括 request_id、session_id、sound_zone、local_asr_text、cloud_asr_text、final_result_type、function_name、function_arguments、nlg 和 timestamp。被本地拒识或不唤醒的轮次也要同步，本地进 context 供后续拒识判定，云端进情景上下文，不进入 Director 的 DT 上下文。

上下文继承分三类。音区继承指主驾打开座椅按摩后，副驾说“我也要”；设备继承指氛围灯调成红色后，用户说“还是绿色吧”；功能继承指风量调大被一句 reject 的闲聊打断后，用户再说“再大一点”。窗口内有明确对象才继承，夹杂新的有效指令时优先上云；中间被拒识的背景语音不清空上一轮有效对象。

本地上下文是公共 Context 的子集，只做类型规则过滤，不做语义检索。窗口保留 30 分钟内最多 10 轮，超出后只保留摘要，可获取云端已经生成的摘要来覆盖端云问答。本地离线 TTS 使用思必驰三方能力，固定文案预置，另有动态 1000 条本地合成音频循环滚动；这套数量与在线缓存 500 条预置、1500 条动态是两套口径，不能互相套用。

一轮语音交互经过四种数据形态，用户音频、ASR 识别文本、待播报文本、TTS 音频。客户端负责采集音频、发起请求、展示回复和上报端状态；豆包云端承接文本对话、环境风控、内容安审和打断判定；AIDV 承接座舱业务处理并统一对接 Speech；Speech 云只由 AIDV 对接，提供 ASR 和 TTS。

上行顺序是客户端经 WebSocket 长链把音频交给 AIDV，AIDV 调 Speech 完成 ASR，文字先回到客户端，客户端再经 HTTP 短链向豆包发起文本对话。下行时 AIDV 调 Speech 合成音频并缓存，AIDV 经豆包把待播报文本和音频标识以 SSE 回给客户端，客户端凭标识经 WebSocket 拉取分片边取边播。

豆包云端的打断判定规则是同一账号、同一会话中后到的 query 打断前面未处理完成的 query；被拒识的 query 不参与打断判定。request_id 是一次端云的唯一凭证，唯一对应一个 question_id；conversation_id 标识会话，chat_id 与 section_id 标识话题多轮。端侧依赖配置表按 channel、channel_app_id、vehicle_type、version 隔离，版本不同即使内容相同也要单独记录。

链路方案有明确的历史取舍。202509 的 RTC 方案因为 S2S 无法被 Director 调度、RTC 建联慢且成本高已经舍弃；202511 只做 AIDV 内部能力迭代；202607 当前采用文本链路。手机豆包 IM 新链路、音视频新链路和自建 QUIC 链路在本项目暂不跟进，讲解时不能把规划方向写成已上线能力。

# M 输入管理

输入管理是 Director 前置模块，只组织有效输入的打断、排队和合并。它不调用模型，不判断最终意图，不合成音频，不操作播放器，也不回滚已经执行的 Tool。首期接入四类来源，用户 Query、有效 advice、触发 DT 推理的有效 Event、同步 Tool Feedback；独立异步 callback 与持久结果回流本期不接入。

输入先带固定的合并属性。主动消息、有效 Event 和用户 Query 属于 mergeable，可以出队合批；Tool feedback 属于 isolated，保守单独交给 Director，避免不同工具结果被错误拼到一批。这个属性在接入时确定，不由输入管理临时判断，也不由模型当场改判。订座、停车、外卖这类长程 tool 或 agent feedback 单独处理；生图、AI light 等 AIGC 走独立界面 push，没有语音播报，不进入 DT。

每条输入用来源身份找回归属。用户 Query 用 request_id，新链路准入前置条件是 request_id 非空，不满足该条件的旧渠道走旧链路，不以空 ID 准入；Task Service 的一次运行用 task_run_id；云端异步 feedback 用 tool_call_id；简单车控异步结果沿用原 request_id。

接入决策先看前台处于哪一种状态。IDLE 表示没在推理也没有 TTS，P0 直接 DISPATCH，mergeable 和 isolated 的 P1 各自 DISPATCH。PROCESSING 表示 Director 已经启动但还没有首 token，旧 Input 仍可重放时 P0 走 INTERRUPT 加 MERGE 加 DISPATCH；已经越过 Tool 重放边界时，INTERRUPT 加 DISPATCH，旧 Input 只作为中断上下文；P1 一律 QUEUE。

RESPONDING 表示已经输出或正在播报。P0 由客户端先停播，再 INTERRUPT 加 DISPATCH，已播部分、未播部分和原 Input 一起带入中断上下文；P1 继续 QUEUE，其中 mergeable 出队合批，isolated 单独成条。状态不同，补话能不能和旧请求合并的答案也不同。

能否重放在 Tool 放行那一刻锁定。新执行开始时默认可重放；一旦 Tool call 被放行，下发前在同一原子操作内校验 OutputPermit、CommittedOutputExecutionID 并确认未撤销，登记 tool_call_id 后置为不可重放。此后旧 Input 不能整体重推，只能作为中断上下文；重试复用同一个 tool_call_id。这样设计是为了避免车控、下单这类带副作用的动作被重复提交。

排队中的主动建议按轮次收敛。同一个 advisor 排队期间多条 advice 只保留最新一条；advice 带有有效时间，超时丢弃并通知 advisor。技术方案本期不引入 Input Manager 自己的业务 TTL，TaskRun 的 DeadlineAt 仍由 Task Service 管理，两条时效口径不能混为一谈。

每次新执行都有自己的 DirectorExecutionID。首次推理、ToolFeedback 续轮、打断重算、故障恢复重跑都发新 ID；同一次重传、同一候选预跑转发布复用原 ID。新链路里 TaskRoundID 等于 DirectorExecutionID。ActiveComputeExecutionID 管候选，CommittedOutputExecutionID 管正式输出，二者可以不同，但同属一套 ID 体系，发布前只校验相等，不比大小。

一轮执行有五类结束路径，每一类都必须能推进 waiting 或回到 IDLE，分别是静默、纯 Tool call、首 token 前失败、有展示文本但无 TTS、有 TTS。TTS 事件本身不形成 Input，也不进入 waiting 队列。缺少结束路径的轮次会一直等待一个根本不会出现的播完事件。

播放终态的权威来源是客户端上报。FINISHED 需要已经看到 TaskRoundEnd，并且全部 Provider 解码队列和播放器尾部耗尽；ABORTED 表示这一轮声音永久停止，同一 TaskRound 不可恢复。HTTP 或 WS 断开、网络尾包、估算时长都不能伪造 FINISHED。超时兜底按显式终态、总时长加播放时长动态超时、hard_deadline 可用性兜底的顺序推进，超时状态记为 FINISH_UNCONFIRMED 或 PLAYBACK_STATUS_TIMEOUT，不伪装成正常 FINISHED。

被打断的信息按新输入是否被拒识分流。新 user input 未被拒识时，被打断信息作为 last_talk_content 随 Query 进入中断上下文；新输入被拒识时，旧内容作为独立 Event 重新准入生成新执行。中断上下文不参与排队，也不再触发旧 Tool。

多音区迁移后，每个音区先成为独立 Input，由 Input Manager 决定本轮处理哪些，多音区模块只组装已经选中的 Input。旧的 SetSoundZoneMerge Redis 1 分钟窗口、QueryVersion、AdvisorVersion 和 ShouldBreak 不再决定准入。

实例失联后，owner lease 到期由恢复流程接管。可重放的输入才重跑；不可重放的 Input 以“实例失联且不可重放”结束，等待已发 Tool feedback 或新 Query 收尾。已经受理的工具真实结果不会因为旧执行失效而丢弃。

客户端本地接管时携带原 request_id 上报已完成，结束对应 Input 并让它对应的云端执行失效，其他等待中的输入继续保留。Redis 原子登记失败在有限重试后 fail-closed，禁止绕过 Input Manager 直接调用 Director。

# C Context 上下文

Context 筛选经历过两代做法。早期 V1 用写入、粗筛、精筛三步式，由单一模型统一过滤各来源，为控制速度只输出 5 个结果，靠前的数据更容易被放行，各来源效果此消彼长；设计目标 P90 800 毫秒，实际 P90 达到 1.2 秒，端状态筛选需要两次模型调用是主要瓶颈。当前 V2 取消统一精筛，把筛选权下放给各来源，拆成预注入和动态检索两阶段。预注入并行取用户画像、由标签模型算标签后按标签召回记忆，覆盖约 80% 常用请求；剩余约 20% 复杂请求由 Director 判断信息不足时再动态检索兜底，V2 的 P90 为 564 毫秒。后续规划是新增 profile 模块、解决跨来源冲突，并推动业务方接入结构化数据、废弃非结构化返回。

# D Planner / Director

“十分钟后关座椅加热”属于定时任务，跨出当前即时交互。Director 把时间、对象和动作交给任务系统，任务系统保存安排并注册触发器，到时间后再把任务建议送回。模型只在收到输入时推理，等待和持续检查由任务系统承担。

任务按 PRD 分为即时任务（单任务、多任务）、定时任务（单次、循环）、条件任务（单次、循环）和持续任务；“先查地址再导航”这类多步推进，基于模型 ReAct 特性呈现出多步任务特征，在评测案例中单独观察，不改变上面四类归属。

注册条件任务前，Director 还要做合理性仲裁，依次检查条件能否被系统感知、是否具备触发可能性、动作是否符合价值观、动作是否可执行、条件与动作之间是否矛盾。感知不到的内容、不可能触发的条件、伤害性动作以及条件和动作互相冲突的安排，不注册为任务，直接用对话回复说明。

talk_content 的情绪写在句首方括号标签里，例如[开心地说]、[疑惑地问]，也可以标注[模仿孙悟空说]、[用四川话说]、[唱]，一轮可以带多个标签；正文只能使用文字和必要标点，不能出现 emoji、表格或列表，表情另由 emoji_id 控制。

# E 工具执行与回流

执行层选定实现时，按 agent_id、租户和环境找到当前渠道已发布、已启用且有权调用的版本，草稿配置可以覆盖发布配置。工具发现前先做用户权限预检查；管理表里曾经出现过这个名字，不等于当前车型和环境有可用实现。找不到实现就返回明确不可用，不能换一个不相关工具冒充完成。SP 和 UP 由 Agent 内部自行从 Fornax 获取，不由调用方传入。

动作真正发出前还要确认当前候选仍然有效，并取得输入管理给出的发布许可。用户已经打断替换旧轮时，旧候选不能因为迟到算完就再发出车控。已经发出的调用继续保留，真实结果返回后写回对应目标，新执行不会抹掉已经发生的车辆变化。

同批反馈以本轮 action_list 为基准收集，每一项都要带回成功、失败、受理、处理中或未确认状态。一项已经完成不能覆盖另一项仍在等待的结果。is_finish 只表示这一段 Agent 响应流结束，不能替代车窗关闭、订单确认或用户付款这类业务终态。

普通同步反馈延续当前 Director 的 ReAct 目标，完整批次取得续轮准入后再调用 Director。订座、停车、外卖这类长程反馈按各自任务独立跟踪；独立异步 callback 与持久结果回流首期不新建输入，后续接入时再定义结果身份、查询时机和交互方式。

车控沿三段推进。先把用户表达整理成设备、座位、动作和数值等语义参数，再按车型配置校验能力范围，最后由车企把约定语义转换成 ZoneAPI 或 SOA 真实接口。车型不支持时在第二段返回能力限制，不会进入车辆接口。增量控制的幂等边界按各工具合同确定，重试复用同一调用身份；结果不明时不把重新发送当成无害确认，避免“再降一点”被执行两次。

音乐解析可能用到歌名、序号、歌手、专辑、歌词、榜单、标签和媒体类型等参数。选源先看端上当前可用信源，再结合用户指定或记忆偏好、版权覆盖、登录与会员条件，多个来源都满足时才比较音质。未登录先引导登录，超时不自动重复调用。搜索返回候选只说明找到了曲目，目标播放器真正开始播放之后，才能把结果说成正在播放。

GUI 长任务的新建、补充和取消共用同一个任务身份。new_task 建立任务，add_info 把用户回答送回仍在等待的任务，delete_task 请求终止。已经终止的任务不能靠 add_info 复活，用户重新办理时需要重新 new_task。停止界面操作和撤销外部订单是两件事，已经形成的订单按实际返回说明。

每类工具的重试、取消和副作用边界写在各自合同里。导航、支付、车控和内容生成重复调用的成本不同，不能假设所有工具遵守同一个重试策略；取消推理也不能代替下游已经发出的取消操作。

# DR 司机 Agent：把导航、临停与泊车串成专项任务

分工边界来自各自掌握的信息。Director 掌握多轮对话、候选澄清和用户最新改口，专项层只管导航与停泊车之间的依赖关系，ADC 掌握道路、车况和可安全执行条件。总对话模型不直接判断实时转向、制动和避障，安全动作必须留在车辆侧。

“导航回家并激活智驾”按先导航、后激活的串行顺序处理，而不是两个工具同时下发。目的地还没定时激活智驾，车辆可能朝错误路线进入辅助驾驶；先取得导航成功反馈，再调用 auto_drive，可以把激活建立在明确路线之上。

无图分支要先承认服务范围收缩。目的地没有泊车地图时，系统无法保证车位级泊入，只能询问“无法直达车位，是否要激活智驾前往目的地”。用户同意后目标从车位到车位退化为前往该地点，到导航终点由下游能力靠边停或提示接管；用户拒绝则取消任务，后续回复沿新目标说明进度。

单泊车场景的园区选择受当前方案限制。SLS 首期有导航时使用导航终点园区，无导航时使用当前位置园区；有导航时不在任意途经点承接泊车。途经点泊入属于 OTA 规划能力，本期不下发。单泊车没有地图时，智驾支持并允许漫游找车位才进入漫游；不支持直接返回失败，不向用户承诺自动找位。

加点和设属性必须分两步，因为导航 App 先要有这个路线点，临停属性才有挂载对象。跳过加点直接设属性，系统无法把“靠边停”对应到 A 点。加点失败时不能宣称临停已设置；属性设置失败时，已成功添加的路线点仍然保留，后续只补未完成的停靠要求。

路线与属性的保留规则随操作类型变化。增加途经点保留原有临停属性；只更换路线选项不改途经点，属性同样保留；车辆经过 A 后，A 的途经与临停记录随进度删除；结束本次导航或以重新算路方式修改目的地，会清空这一轮临停与途经列表。

语音激活智驾必须二次确认，原因是激活涉及车辆安全接管。确认卡展示期间还没有取得用户授权，卡片超时、被新卡片替代或用户取消，都不生成同意。控制请求交给 ADC 后，还要再判断当前路况和车况是否允许激活，回复只能依据这份真实激活结果。

先取消旧任务再发新安排，是为了避免两份冲突目标同时存在。旧负二层充电车位泊入未确认撤销时，直接下发路边停车，车辆可能同时收到两个停靠目标。取消失败、超时或结果未确认，新临停暂停发布，专项层把当前状态和失败原因交回 Director，旧任务继续保持有效。

# O 播报、展示与真实结果

选在线还是离线合成有明确条件。网络正常且没有大量波动时走在线；无网、波动大或速度差、本次在线 ASR 异常、未登录豆包账号时走离线。系统警告提示场景强制离线；上下文里有特殊播报风格要求（例如四川话、悄悄话）时强制在线。

缓存只保存在线合成结果。预置缓存提前合成高频文案，上限 500 条（暂定）；动态缓存首次合成并播放完成后入库，上限 1500 条（暂定），超出后刷新替换。命中要求待合成文本和声音配置完全一致。

播报分 P0 到 P5 六个等级，具体模块归属由车企音频管理定义；高优先级可以打断低优先级，低优先级请求遇到高优先级正在播报时被拒绝。只有豆包内部语音交互需要联动动效，导航等其他业务不要求同一套动效。

## 节点 V4 与识别并行观察人声和停顿

VAD 是语音活动检测，观察用户是否仍在发声、停顿持续多久。ASR 一边写文字，VAD 一边给出停顿信号。用户说“我想去……”后停一下，系统虽然已有文字，仍不能据此判断意思已经完整。

本图中的 300 毫秒和 500 毫秒都从同一次停顿开始计算，不能相加成 800 毫秒，也不从开口第一个字起计。短停顿去 V5 提前准备，较长停顿去 V7 收尾；句意不完整时由 V10 进入语义 VAD，继续等到 1000 毫秒（暂定）。

## 节点 V6 提前准备背景，保留正式执行的门槛

预请求利用用户停顿提前处理允许的准备，预处理只完成 LLM 的拒识、意图识别和简单复杂仲裁，不抢跑到函数调用、Director 或对话管理模块。它要带上这次输入编号与准备轮次，避免与后来的正式请求混淆。用户仍可继续补话，因此准备不应产生车辆动作或正式回答。

比如先判断这句话属于哪类意图、是否需要拒识，可以减少后续等待；提前开始导航则越过了当前权限。准备阶段也不能误开正式会话、写入正式历史或抢占界面。等最终文字满足复用条件，已支持的准备结果才交给正式业务使用。

## 节点 V7 较长停顿后让当前语音段收尾

本图的 Hard VAD 在停顿达到 500 毫秒时，让当前语音段收尾，接着等待二遍识别给出最终文字。这个时刻表示一段收音结束，用户通常还没有听到回答，也没有得到工具执行结果。

后面仍可能需要识别定稿、正式请求、推理、执行和声音合成。阈值过短会截掉用户的补充，过长又让已经说完的人继续等待。声音停下后若句意仍不完整，还要按语义判停的配合规则处理，不能把收尾直接等同于允许执行。

## 节点 V8 对这一段录音给出最终识别文字

语音段收尾后，二遍 ASR 再处理刚才那段音频，给出正式请求使用的 final。例如一遍听成“播放音月”，二遍可能修正为“播放音乐”。用户无需重说一遍，也没有因此开启第二轮对话。

final 只表示本次识别定稿，仍可能存在错字。300 毫秒与 500 毫秒两段文字一致时沿用短停顿结果，不一致则按最终文字重新请求 LLM。结果为空或失败，则进入 V18；是否允许采用一遍兜底由当前业务规则决定。

## 节点 V10 停顿后判断句意是否完整

“我想订一张去……”后面仍缺目的地。语义判停根据当前文字判断用户是否还需要补充，与声音停顿计时一起决定继续等还是让当前段落收尾。

判断为不完整时启动语义 VAD，继续等到 1000 毫秒（暂定），到点后不再判断完整性，直接把结果交给后续 LLM。计时收尾让已经说完的请求及时进入处理，具体延长方式由对应车型和版本配置，随后最终文字在 V9 检查准备结果能否复用。

## 节点 R1 根据唤醒和接话状态选择入口

唤醒词或按键可以让助手进入聆听，已经激活时还可以继续说话。未激活的免唤醒入口则需要先判断车里这句话是否值得助手接住，例如乘客对朋友聊天不应直接变成新任务。

入口会影响何时上传声音、怎样放行以及哪些音区参与，具体按车辆配置运行。按键属于主驾，也不自然意味着只收主驾声音。确认这次入口以后，R2 再按激活状态分路，同时保留用户这句话的归属。

唤醒入口包含标准唤醒词、方控 AI 硬按键短按、唤醒词后直接跟有效指令、全时态有效指令和主动服务拉起。硬按键归属主驾，语音唤醒遵循音源定位。未同意隐私协议、未开启 AI 开关、泊车等禁用场景不支持唤醒，界面用 toast 说明原因，此时再喊唤醒词也不会进入聆听。

## 节点 R2 激活接话与免唤醒采用不同处理路径

已经唤醒助手时，本地和云端可以并行准备候选，让各自处理支持的内容。未激活时则先用本地流式识别和拒识观察这句话，满足提前放行条件后才把声音交给云端。

因此不能让所有请求都等本地模型处理完再上传，也不能把车里采到的声音全部当成有效 Query。当前开放的音区和持续聆听范围仍由车辆配置决定。分路后还要通过 R3 关联各处结果，确保它们属于同一次输入。

已经激活的请求在 vad 结束后端云双跑，本地 reject 不被采信，要等云端拒识；本地 functioncall 或 unsupported 同样先等云端判断。未激活阶段先用 partial ASR 流式请求本地模型判断 attend，未 attend 时等完整 query 最终判定。

## 节点 R3 让本地、云端与回包认出同一句话

同一句话可能在本地和云端各产生一份文字或动作候选。request_id、会话、音区和时间帮助系统把它们关联起来，并记录最终采用哪一方。端侧与云端编号不同，还需要明确映射关系。

比如本地已经打开空调，几秒后云端才返回开启动作，仍然属于刚才那个请求。后面的采信与防重必须认出这一点，不能把迟到回包当成用户新命令。不同车辆、不同会话的结果也不能仅因文字相同就合并。

request_id 是一次端云唯一凭证，唯一对应一个 question_id；conversation_id 标识会话，chat_id 与 section_id 标识话题多轮。端侧依赖配置表按 channel、channel_app_id、vehicle_type、version 隔离，版本不同即使内容相同也要单独记录。

## 节点 R13 免唤醒时边听边判断是否值得接话

在未激活的免唤醒场景，本地识别与流式拒识一起观察用户的话。出现 attend，表示这句话值得继续让云端接话，可以提前启动音频上传，减少等整句定稿后才开始处理的时间。

一直没有召回时，系统继续听完再看最终结果。若最终判为无关且从未上传，可以安静结束。这条支线使用过程文字，早于正式 Query；提前放行只决定继续处理，最终是否承接仍要由后面的判断完成。

音频状态分三种。已经提前上云后，本地后续 reject 不再终止云端判断；从未上云的 reject 直接丢弃，不唤醒也不上云；本地出 functioncall 或 unsupported 时整段上云，交由云端 ASR、拒识和 planner 处理。三种状态关联同一次输入，不能当成三次独立请求。

## 节点 R15 明确且无需上下文的指令可走缓存

确定性缓存适合单轮、无需历史、意图与参数唯一的指令，例如明确设备的开关要求。命中以后可以跳过本地模型计算，再按实际车型能力把操作交下去，节省一次理解过程。

“暂停”“继续”“就选它”依赖前文对象，不能只因常见就当成同类缓存。否则系统可能对错设备优先执行。没有命中时，本地模型和云端可以并行处理；命中时也仍要经过执行参数校验，不能把匹配成功当成设备成功。

离线指令缓存遵循单轮解析、上下文无关、结果唯一三条原则。暂停播放、继续播放、就选它了依赖前文对象，不进入缓存；超出离线范围的请求输出“其他”。缓存命中目标 50 毫秒、准确率 100%，命中只代表本地解析出指令，车辆是否动作仍以后续车控回包为准。

## 节点 R4 本地模型在支持范围内生成候选

本地模型处理当前车辆已支持的车控、系统或导航基础操作，并承接有限上下文。用户说“再开一点”，需要知道上一轮操作的是哪个窗；中间一句被拒识的闲聊不应让这个有效对象丢失。

联网搜索与复杂多步计划超出本地范围时，要保留不支持的结果。图中的云端优先策略也不允许本地一算好就抢先执行，候选先交 R16 分类，再由 R5 根据断网或超时等条件决定是否采用。

本地模型支持 TTS 流式打断、拒识、简单功能 FC 和少量上下文继承。开放问答、联网搜索、内容生成、复杂导航规划、多步工具编排、依赖大量端状态事件和长期记忆的判断都超出本地范围，需要整段上云。本地上下文是公共 Context 子集，只做类型规则过滤，不做语义检索。

## 节点 R16 分清无关话、操作候选与本地不会

本地结果有三种需要分开的含义。reject 表示这句不应成为助手需求；FC 表示已解析出结构化操作；unsupported 则表示用户确实在求助，但本地能力无法承接，例如需要联网搜索。

三种结果先保存为候选，接下来由采信策略决定如何处理。把 unsupported 当成无关聊天，会让有效需求被静默吞掉；把 FC 当成已经完成，又会提前报喜。分类后继续检查执行权和实际结果，不能只留一个成功或失败标签。

0930 调整后的仲裁顺序是本地正则缓存优先，其次云端 planner，本地 LLM 只在断网或云端超时兜底。正常联网时本地 functioncall 先保留候选，不抢先执行。早期本地 LLM 先分流、本地 FC 直接中断云端的规则已经废弃，当前链路不再沿用。

## 节点 R5 断网或云端超时后检查本地候选

AIVA 9 月策略中，本地模型先返回时保留候选。正常联网继续等待云端；断网或云端超过 3 秒没有返回后，再采用可用的本地结果。干预缓存有独立的优先执行路径。

可执行 FC 交 R6，reject 交 R10 静默结束，unsupported 交 R18 提示网络或能力限制。本地接手后阻止迟到云端重复动作，实际结果随后进入回复和 Context。

断网时本地 functioncall 和 reject 直接采纳，本地 unsupported_cloud 播报网络异常提示，同一唤醒周期内同类异常 NLG 只播一次。云端超过 3 秒未返回视为超时，本地已有可执行候选才接手；超时之后云端结果晚到，不再触发执行。

## 节点 R11 等待云端超过期限后检查本地兜底

云端一直没有返回时，用户不能无限等待。本图这套策略在断网或云端等待超过 3 秒后，解锁本地候选采信。计时从哪里开始、何时停止，应使用当前实际配置；网络格数本身不能证明业务已经超时。

兜底只覆盖这辆车具备的本地能力，无法自动补出联网搜索和复杂任务。接手后还要隔离迟到云端，恢复网络时也不能悄悄补执行旧请求。输入和结果怎样重新同步，需与后面的本地历史回流配合。

兜底只覆盖本车已经开放的本地能力，无法补出联网搜索和复杂任务。恢复网络时不擅自重放已经结束的动作，迟到云端回包按原请求编号隔离。计时起点和停止点以当前配置为准，网络格数差不能直接证明业务超时。

## 节点 R18 本地无法承接时给出受限说明

断网或云端超时后，本地候选若是 unsupported，表示用户确实提出了需求，但此刻没有可完成它的能力。这套本地交互采用网络异常提示，并在同一唤醒周期最多播一次，避免连续尝试时重复打扰。

系统不能用静默拒识代替这次失败，也不能生成没有执行依据的成功答案。网络恢复后是否重新办理、是否需要用户再次发起，必须遵守明确规则；旧动作不可自动补做，当前未完成状态也应保留给后续对话。

本地离线 TTS 使用思必驰三方能力，固定文案预置，另有动态 1000 条本地合成音频循环滚动；这与在线缓存 500 条预置、1500 条动态是两套数量口径，不能互相套用。同一唤醒周期同类网络异常提示只播一次。

## 节点 R17 本地接手后隔离迟到的云端动作

本地因断网或等待超时接手后，旧云端请求仍可能稍后返回。系统要根据同一请求编号和采信记录，阻止这份迟到结果再次执行。只隐藏第二次回复还不够，动作也必须被隔离。

例如“副驾车窗再降一点”若执行两次，实际降幅就超过用户要求。后续核验应看设备到底变化几次，以及历史是否重复记录。迟到结果仍归原请求，不能借新一轮输入身份重新获得执行权。

车窗、座椅这类增量动作一旦重复执行，实际变化会超过用户要求。隔离对象同时包括动作和回复，只隐藏第二次话术仍会留下重复副作用。迟到结果保留原请求归属，不能借新一轮输入身份重新获得执行权。

## 节点 R12 把本地做过的事交给后续上下文

本地处理后，把用户 Query、回复和实际观察结果连同请求编号、音区、函数参数及时间同步出去。下一句“再调低一点”才知道刚才调的是哪一座、哪个设备，以及上次是否成功。

这里接到 C5，让后续云端判断承接本地历史。同步内容必须反映真实状态，不能把已下发写成已完成。本地已经记住与云端已经收到还要分开，离线积压、重复回传和重连补同步都需要保持原请求归属。

同步字段包括 request_id、session_id、sound_zone、local_asr_text、cloud_asr_text、final_result_type、function_name、function_arguments、nlg 和 timestamp。被本地拒识的轮次也要同步，本地进 context 供拒识判定，云端进情景上下文，不进入 DT 上下文。

上下文继承分音区继承、设备继承和功能继承。窗口内有明确对象才继承，夹杂新有效指令优先上云；中间被拒识的背景语音不清空上一轮有效对象。本地窗口保留 30 分钟内最多 10 轮，超出后只保留摘要。

## 节点 M1 接收新输入并保留它来自哪里

输入管理首期方案安排用户、建议和事件，也为完整同步工具反馈取得下一次模型调用的准入。同步反馈延续原 ReAct 目标；独立 callback 与持久结果回流当前尚未接入。

每条输入保留来源、时间、原请求、说话人与音区。“我好热”表达新目标，“建议降温”提供候选服务，“空调调整失败”报告事实。Director 因而能按各自含义处理，而不会把执行反馈重新理解成命令。

首期接入用户 Query、有效 advice、有效 Event 和同步 Tool Feedback 四类来源；独立异步 callback 与持久结果回流本期不接入。主动消息、有效 Event 和用户 Query 为 mergeable，可以出队合批；Tool feedback 为 isolated，保守单独交给 Director，这个属性在接入时确定，不由模型临时改判。

## 节点 M2 分别核对推理、播报和动作当前进度

安排新输入前，系统要同时查看当前模型计算、工具下发和客户端播放状态。模型还没有输出首字，工具也可能已经发布；服务端发送完音频，车里也可能仍未播完。

例如空调已经打开，确认话术尚未响起，此时用户插话不能让系统重算后再开一次。只有把正在算、正在说和已经做分开，后面才知道哪些候选能取消、哪些事实必须保留，以及何时释放新一轮。

前台状态分 IDLE、PROCESSING、RESPONDING。IDLE 直接接入；PROCESSING 还要看旧请求是否仍在可重放边界内；RESPONDING 时 P0 先停播再接入，P1 继续排队。三种状态决定补话能否合并，不能只看模型是否还在生成。

## 节点 M4 补话合并前检查旧动作是否已发出

旧请求还没有调用外部工具时，用户补一句“不辣的”，可以取消旧候选，把这项限制与找餐厅目标一起重新推理。

外部调用已经发出后，原请求仅作为新轮背景保留。后续实际结果继续写回，新一轮根据这些进展判断剩余步骤，避免重放旧目标再次产生相同动作。

新执行开始默认可重放；Tool call 被放行的同一原子操作内校验 OutputPermit、CommittedOutputExecutionID 并确认未撤销，登记 tool_call_id 后置为不可重放。此后旧 Input 只能作为中断上下文，重试复用同一 tool_call_id，避免车控和下单重复提交。

## 节点 M5 用户新话优先，普通建议和事件等待

用户说“退出导航”时要及时处理，普通音乐建议则等待当前对话结束。首期方案用 P0 表示优先用户输入，P1 表示普通建议与事件；高优先任务预留了类别，当时尚无实际场景。

同轮工具结果先汇成完整批次，再经输入管理取得续轮准入，继续原 Director 任务。独立异步 callback 新输入留作后续扩展。

P0 为用户输入加结构预留的高优任务，当前尚无高优实际场景；P1 为主动服务、同步 Tool feedback、有效 Event 和客户端播报状态。同一个 advisor 排队期间多条 advice 只保留最新一条；advice 超时丢弃并通知 advisor，业务 TTL 仍由 Task Service 的 TaskRun DeadlineAt 管理。

## 节点 M9 登记执行身份，分别控制计算与发布

每轮执行登记身份。用户新话接管后，旧轮晚到的文字、声音和新动作在发布前被拦下；已经下发的工具继续返回真实结果，供新一轮判断使用。

完整同步工具批次到齐时，启用预跑就允许下一轮先计算候选。当前播放尚未结束，候选暂不对外发出；播放结束、候选仍有效并满足输出条件后，才释放同一份结果，无需重复请求模型。

候选未发出前收到有效新输入，过时的候选作废，系统把新信息与完整工具事实一起重算。关闭预跑开关时回到串行处理。

每次新执行发 DirectorExecutionID，首次推理、ToolFeedback 续轮、打断重算、故障恢复重跑都是新 ID；同次重传、候选预跑转发布复用原 ID。ActiveComputeExecutionID 管候选，CommittedOutputExecutionID 管正式输出，二者可不同但只校验相等，不比大小。

## 节点 M10 用客户端实际播放更新状态

客户端真正出声时上报 STARTED，播放期间上报 PROGRESS。FINISHED 要等客户端收到本轮音频结束标记，且本地解码与播放队列全部耗尽；它回到 M9 后可释放仍有效的候选，而不会重新触发同一轮推理。

在采用临时暂停的链路中，检测到符合打断条件的人声后先暂停旧播放。新话最终被拒识且本次允许恢复时，继续原播放；确认有效用户插话后，旧播放记为 ABORTED，这个播放实例不能恢复。播放状态直接更新当前交互记录，不进入业务消息等待队列。

FINISHED 需要已经看到 TaskRoundEnd，并且全部 Provider 解码队列与播放器尾部耗尽；ABORTED 永久停止，同一 TaskRound 不可恢复。HTTP 或 WS 断开、网络尾包、估算时长都不能伪造 FINISHED；超时状态记为未确认，不伪装正常播完。

## 节点 M12 恢复执行时先读取已发动作

状态登记失败时按限定范围重试，仍无法确认执行权就停止相应发布。恢复接管前，先读取已有工具调用，已发车控或外部操作不重新执行。

纯工具、静默、仅文本和语音合成失败各有结束路径，完成本轮实际工作后释放交互状态。恢复后的新请求继续使用旧轮真实结果和异常原因。

实例失联 owner lease 到期由恢复流程接管，可重放才重跑；不可重放 Input 以实例失联且不可重放结束，等待已发 Tool feedback 或新 Query 收尾。Redis 原子登记失败有限重试后 fail-closed，禁止绕过 Input Manager 直接调用 Director。

## 节点 C7 推理前注入画像并召回相关记忆

Context 先把已注册用户的语义画像放入常用背景，再根据当前问题召回相关的语义记忆和情景记忆。当前 V2 取消统一精筛，筛选权下放各来源；预注入阶段并行取用户画像，标签模型算出相关标签后按标签召回记忆打分，覆盖约 80% 常用请求。

剩余约 20% 复杂请求由 Director 判断信息不足时再动态检索兜底。“昨天那家游泳馆”如果已经获得明确地址，Director 可以继续导航；仍缺地点或地址时，再通过显式查询补齐。

## 节点 C10 各来源处理质量后汇集并保留未知

身份、状态、记忆和知识各自处理相关性与质量后，在这里汇集。当前 V2 没有再安排一个统一模型替所有来源最终判真；相应来源应保留权限、有效时间和仍然未知的信息。

比如旧偏好写用户不爱开窗，最新明确指令却要求打开，需要 Director 结合当下意图判断。Context 不应在整理时偷偷删除冲突或补出缺失车况。保留这些关系，下一层才能区分历史习惯和当前事实。

## 节点 D6 区分立即执行与未来持续跟进

“现在关加热”交即时车控，“十分钟后关加热”属于定时任务，先解析时间、对象与动作，注册后等待触发。条件任务要先通过合理性仲裁，持续介绍风景还需要跟着后续进展反复处理，不能调用一次就宣布整个目标完成。

任务分为即时（单任务、多任务）、定时（单次、循环）、条件（单次、循环）和持续；先查地址再导航这类多步推进基于 ReAct 特性呈现多步任务特征，在评测案例中单独观察。创建后的触发与执行另有回路，注册成功只能确认安排接住，不能在此刻就说未来加热已经关闭。

## 节点 E2 按当前项目找到已发布可用的实现

同一个工具名在不同车型可能由不同 Agent 或端侧函数承接。执行层要按当前渠道、应用与环境，找到已发布、已启用且有权调用的实现，不能只看管理表里曾经出现过这个名字。

找不到实现就返回明确不可用，不能换一个不相关工具冒充完成。旧名与新名是否映射也需要实际配置，不能凭英文相似就当作同一个功能。实现确认后继续核参数与发布条件，再让动作对外发生。

实现选择按 agent_id、租户和环境定位当前渠道已发布、已启用且有权调用的版本，草稿可以覆盖发布配置。工具发现前先做用户权限预检查。SP 和 UP 由 Agent 内部自行从 Fornax 获取，不由调用方传入。

## 节点 E3 取得发布许可后再发出本轮动作

工具真正发出前，要确认当前候选仍有效，并已取得输入管理给出的输出或动作发布许可。用户已经打断替换旧轮时，旧候选不能因为迟到算完就再偷偷发出车控。

登记调用身份后才对外操作，同批无依赖且不争用资源的动作可以并发，导航互斥等情况则需要分轮。重复请求要认回原调用，不能借重试名义重新提交一项用户没有再次要求的副作用动作。

动作发出前确认候选仍有效并取得发布许可，登记调用身份后再对外操作。已经打断替换的旧轮候选不能迟到补发。重试复用同一调用身份，已经发生的车控或订单外部效果不随旧执行失效而自动撤销。

## 节点 E5 先辨认返回成功究竟成功在哪一阶段

收到成功标记后，先读它证明的业务阶段。任务注册成功说明条件已保存，停车工具拿到二维码说明可以去付款，图片正在生成则还没有作品。不同工具的完成含义不能压成同一个标签。

is_finish 表示这一段 Agent 响应流结束，也不能替代车窗关闭、订单确认或用户付款。回流需要保留受理、进行中、完成与失败原因，让 Director 只承诺当前事实已经支持的结果，再决定是否继续等待或处理。

is_finish 只表示这一段 Agent 响应流结束，不能替代车窗关闭、订单确认或用户付款。受理、处理中、完成和失败原因分别保留，Director 只承诺当前事实已经支持的结果。

## 节点 E7 同一轮工具反馈汇齐后继续判断

本轮同时发出开通风和播放音乐，执行层先汇集两项反馈，再交 Director 统一判断和播报。失败或未确认按该调用的返回规则保留，已经完成的一项不会覆盖另一项的状态。

长任务这一轮可以返回受理或缺少信息，随后继续办理。后续独立进展按对应任务回流，晚到的回包也始终关联原调用。

本轮 action_list 每项都要带回状态，一项完成不能覆盖另一项仍在等待。订座、停车、外卖这类长任务按独立任务跟踪受理和后续回流；普通同步反馈取得续轮准入后回到原 Director 目标。

## 节点 E12 失败时说明停在哪里并谨慎处理后续

工具失败可能来自未接入、权限不足、车辆条件不符或第三方超时，需要返回具体原因。只说网络不好会掩盖真正断点，也让 Director 无法判断能否替代、补问或引导手动完成。

已有车控或订单效果时，应先核实，不能为了尽快给答案就重复执行。对明确不允许重复调用的失败，更要遵守限制。安全可行的后续交 Director 规划，不可恢复则清楚说明，取消声音也不会自动撤回这些业务效果。

失败先区分未接入、权限不足、车型条件不符和第三方超时。已有外部效果先核实再决定是否重试，不允许重复调用的工具按合同停止。取消推理不会自动撤回下游已经发出的车控或订单效果。

## 节点 O13 按网络和话术选择可用语音服务

需要说话时，系统根据网络、登录和话术要求选择语音合成服务。网络正常且无大量波动走在线；无网、波动大或速度差、本次在线 ASR 异常、未登录豆包账号走离线；系统警告场景强制离线，四川话、悄悄话等特殊风格强制在线。

断网却又要求在线专属风格时，需要明确可接受的降级或失败返回，不能悄悄换种声音仍声称完全满足。选定服务后继续检查缓存与合成，再追实际起播。服务已调用成功只说明其中一步，用户可能还没有听到。

## 节点 O14 复用合成音频前核对文本与声音配置

同一句回复如果已经有合适合成音频，缓存可以省掉重复生成。缓存只保存在线合成结果，预置缓存上限 500 条、动态缓存上限 1500 条（数量暂定），超出后刷新替换。命中需要待合成文本和声音配置完全一致。

不能因为文字相同就播放另一种声音，更不能把旧回答的音频误配给当前请求。命中只是性能阶段，后面仍要取得正确音频、按序播放并拿到真实播放状态。它也不会缓存车辆动作结果。

## 节点 O17 申请此刻的发声机会

音频已经生成，也可能暂时无法播放。电话、导航、音乐和助手共享发声资源，播报分 P0 到 P5 六个等级，具体模块归属由车企音频管理定义；高优声音可以抢占，低优内容遇到高优在播会被拒绝。

导航播报与助手说话还有不同的机器人和灯效要求，只有豆包内部语音交互联动动效，不能只要有声音就驱动同一表现。记录时区分没有音频、未获得焦点、主动停止和自然播完。
