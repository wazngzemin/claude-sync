# 业务背景

[事件日志产品需求文档 ](https://bytedance.larkoffice.com/docx/K2ridyWEloBHt8x6uFgcgoK5nZf)

**背景**：在AI汽车1\.0的架构中，对context的依赖非常高。因此我们需要客观、真实地记录log，为其他模块（记忆、always on等）提供原始素材，再加工成context，使得豆包可以更好地服务用户；

**目标**：事件日志旨在客观按时间轴完整记录车辆行驶及停留过程中发生的各类事件及事件与任务的关系，并通过系统性总结为其他模块提供全面、精准的上下文信息；



# 概要设计



- 其他依赖：

    - [产品需求](https://bytedance.larkoffice.com/docx/K2ridyWEloBHt8x6uFgcgoK5nZf#share-OpnidMBq5oLU6txEIRzcrpkbnyg)里的“触发任务ID”、“所属任务ID”字段依赖planner模块提供，本期不做；

    - 端状态和情景描述数据不在事件日志中维护，事件日志查询接口暂不提供该数据的聚合查询功能，需要查询该信息的模块，例如短期记忆，需要根据user\_id\+事件时间从端状态、watcher中按需查询；

    

- 事件日志写入接口设计

    - 考虑因素

        - 支持客户端批量写；批量大小取决于实时性要求，支持单条、多条上传；

        - 单月日志量评估：按5K车辆，周中通勤50，周末自驾游200计算与：（50\*21\+200\*9）\*5000=1400W；

    - 设计方案

        - 接口支持批量写入，限制1000条，数据直接批量入库；

        - 使用分片表，用vehicle\_id 做分片键；

        - 程序生成唯一主键id，使用[字节ID generator](https://bytedance.larkoffice.com/wiki/wikcnbzN06aQPgGJGe4w0GkTBfd) 的NT ID（其他[常见方案](https://bytetech.info/articles/7078938958524055566?searchId=20250913112711491F2AC068338305D4A8#doxcn9AiOYtClWuRiDFK2E4cAdc)），[申请工单](https://bpm.bytedance.net/record/87430489)；



- 事件日志查询接口设计

    - 设计方案

        - 记忆模块根据channel（必填）、vehicle\_id（必填）、时间段、lastMaxEventLogId、limitSize分批查询；

        - 管理页面根据channel（必填）、vehicle\_id（必填）、时间段、page、pageSize分页查询；



# 详细设计

## 数据库设计

事件日志表：

```SQL
create table event_log
(
    `id` bigint unsigned NOT NULL COMMENT '主键ID',
    `channel` varchar(64) DEFAULT '' NOT NULL COMMENT '渠道标识',
    `channel_app_id` int DEFAULT '0' NOT NULL COMMENT '标识来源',
    `vehicle_id` varchar(256) DEFAULT '' NOT NULL COMMENT '车辆ID',
    `account_id` varchar(256) DEFAULT '' NOT NULL COMMENT '车企oem用户ID',
    `login_doubao_uid` bigint unsigned DEFAULT '0' NOT NULL COMMENT '登录的豆包uid',
    `user_in_car` json NULL COMMENT '车里有哪些人',
    `event_time` datetime(3) NOT NULL COMMENT '事件发生的毫秒时间',
    `event_info` varchar(256) DEFAULT '' NOT NULL COMMENT '事件信息',
    `report_cycle_flag` varchar(256) DEFAULT '' NOT NULL comment '原始数据上报周期标识',
    `created_at` datetime NOT NULL DEFAULT *CURRENT_TIMESTAMP *COMMENT '创建时间',
    `updated_at` datetime DEFAULT NULL ON UPDATE *CURRENT_TIMESTAMP *COMMENT '更新时间',
    PRIMARY KEY (`id`),
    INDEX idx_vehicle_id_user_id_event_time (`channel`, `vehicle_id`, `user_id`, `event_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='事件日志表';
```

有需要按照乘客粒度查询时间日志的需求：

```SQL
create table event_log_user_relation
(
    `id` bigint unsigned NOT NULL AUTO_INCREMENT COMMENT '主键ID',
    `channel` varchar(64) NOT NULL COMMENT '渠道标识',
    `channel_app_id` int DEFAULT '0' NOT NULL COMMENT '标识来源',
    `vehicle_id` varchar(256) DEFAULT '' NOT NULL COMMENT '车辆ID',
    `event_log_id` bigint unsigned DEFAULT '0' NOT NULL COMMENT '事件日志id',
    `vehicle_user_id` bigint unsigned DEFAULT '0' NOT NULL COMMENT '汽车用户id',
    `created_at` datetime NOT NULL DEFAULT *CURRENT_TIMESTAMP *COMMENT '创建时间',
    `updated_at` datetime DEFAULT NULL ON UPDATE *CURRENT_TIMESTAMP *COMMENT '更新时间',
    PRIMARY KEY (`id`),
    INDEX idx_vehicle_id_vehicle_user_id_event_log_id (`vehicle_id`, `vehicle_user_id`, `event_log_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci COMMENT='事件日志表与车辆用户关系表';
```

分表设计：

- 新建分片库，事件日志分片表，使用vehicle\_id作为分片键；

- （分片数 = 预计总数据量 / 单表容量）考虑到最长保存半年，*10万车*，日志总量级到16\.8亿，每个分片表1亿条数据；需要16个分片；分片实例数、分片数是整个分片库的配置，需要考虑整体业务量来设计；
