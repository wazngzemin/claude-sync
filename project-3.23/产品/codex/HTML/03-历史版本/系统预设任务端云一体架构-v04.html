00 · SUMMARY

需求摘要：不是做四个孤立 Case，而是建立一套可复用任务框架

四条任务只是第一批实例。真正需要评审的是：一条系统预设任务如何从配置、用户启停、运行判断、交互、执行到反馈形成完整闭环。

PRD主结论

要解决的问题

当前端侧 Trigger 已推进前半段，但触发后的卡片、TTS、二次确认、执行结果和状态回传尚未统一；云端能配置部分规则，端侧仍有大量业务代码。

产品方案

把任务拆成统一积木：任务元数据 + 运行位置 + Trigger + 条件 + 交互 + 动作 + 生命周期 + 反馈 + 发布版本，再按任务特征选择端侧或云端主链路。

本期交付

端云选择规则、两条完整链路、四任务映射、配置平台能力、即时卡片路由、接口产品契约、异常降级、验收与Owner决策表。

不做什么

配置平台不重新实现VUI、Planner或车控；本PRD不替研发确认真实接口名，也不把会议中的候选方案写成已经上线。

系统预设任务的人话定义：这是厂家随车提供的一条长期规则。用户不需要自己创建，只在任务中心决定是否启用；启用后，Trigger继续等待真实业务条件，条件命中才产生一次任务运行事件。

01 · BACKGROUND & OBJECTIVE

背景：现在只有“能触发”，还不是“任务完整可交付”

需求来源于四条赛力斯系统预设任务，以及2026-07-28即时交互卡评审、2026-09-01系统预设任务评审暴露出的公共链路问题。

断点一｜前后半链路断裂

Trigger能判断条件，不等于已经定义触发后如何出卡、播TTS、接受确认、执行车控和展示结果。

断点二｜端云能力分裂

云端可配置部分规则；端侧当前仍依赖研发随车实现。相同任务缺少统一版本、状态和发布治理。

断点三｜同一卡片被当成同一链路

端侧任务应本地闭环；云端任务由Planner理解。若不带业务来源，用户说“好的”时客户端不知道该交给谁。

本需求为什么现在必须做

  • 天气/路况保护研发已经推进，但后续交互尚未闭合，继续单点开发会把公共问题写死在业务代码中。
  • 四个任务同时覆盖固定规则、VLM、DT/VQA、静默执行、卡片确认和端云协同，正好可以验证框架是否完整。
  • 下一阶段需要把TTS、二次确认、点击回调和真实车控结果沉淀成公共能力，否则每新增一个任务都要重新接链路。

02 · OBJECTIVE / SCOPE / VALUE

目标、范围和价值：完整闭环优先于功能堆叠

本期目标是把四条任务放进同一模型，并让每条任务的端云位置、交互方式、执行与反馈都能被明确验收。

KR1｜统一模型四条任务均可用同一Task结构描述，不靠私有字段补洞。
KR2｜闭环完整从任务开启到真实车控回读，每一节点都有输入、输出和Owner。
KR3｜零误执行任务关闭、状态未知、授权过期或复核失败时，不发生真实车控。
KR4｜端云清晰每条任务能说明为什么在端或云，不以“有网/没网”临时乱切。
KR5｜可追踪task_id + event_id + rule_version串起触发、交互、执行和结果。
KR6｜可发布完成配置校验、灰度、回滚、异常、验收和签字门槛。

本期范围

  • 系统预设任务统一模型和端云主链选择。
  • 任务中心有效状态接入端/云Trigger。
  • 触发、条件、去重、冷却和执行前复核。
  • 即时卡、TTS、本地确认、云端确认和语音禁用降级。
  • 四任务规则、动作、回执、异常和验收。
  • 配置发布、日志、Owner和专项决策清单。

非目标

  • 不重做任务中心全部信息架构。
  • 不让配置平台自己渲染卡片或执行车控。
  • 不承诺所有离线卡片都支持大模型泛化。
  • 不把消息盒子当作系统预设任务主链。
  • 不由产品经理代替研发配置生产环境或完成实车验证。
  • 不在接口未评审时锁定本文建议字段名。

03 · TERMINOLOGY

先分清三个平面，再看流程

这是本文为方便评审使用的解释框架，不是飞书原文中的正式模块命名。

展示与操作面

任务中心 / VUI

让用户看见任务、启停任务、点击或语音确认。它只收集操作，不替业务判断真实状态。

配置与判断面

配置平台 / 端云 Trigger

定义规则模板，接收任务有效状态和各种信号，判断是否达到触发条件。

执行与回传面

端侧 Task Manager / 云端 Planner / 车控

完成二次推理或本地闭环，执行真实动作，再把结果和状态回传。

一句话：用户打开任务中心开关，只代表“允许这条任务以后生效”；只有当 Trigger 后续观察到业务条件满足，任务才会真正触发。
范围隔离：新《Task 任务管理设计》明确“静态 Advisor（预设）不属于本方案”。因此本文没有把动态 Task Service 的目标架构直接套在四条系统预设任务上，只引用任务中心通用契约来说明 task_id、event_id 与状态回调语义。

端侧“可见即可说”是什么

把用户说出的按钮文字或预先注册同义词，映射为一次本地按钮点击。例如卡片按钮是“确认调整 / 暂不处理”，可识别“确认、可以、不用、取消”。它快、可离线，但表达范围有限。

云端“泛化能力”是什么

不是卡片UI自己会思考，而是把卡片问题 + 当前选项 + 用户语音交给Planner/选择工具，将“那就帮我调一下”“安全第一，开吧”归一为确认，将“先不用”归一为拒绝。无法明确映射时必须澄清或不执行。

安全边界：泛化理解只负责判断用户选了哪个选项，不直接证明车控可以执行。选择结果仍要带回原event_id，由端侧重新检查任务状态、车辆状态和卡片有效期。

16 · CONFLICTS & GAPS

为什么不能说“所有卡片都走可见即可说”？
端侧 Trigger 卡需要本地可见即可说；云端 Static Advisor 的语音确认要进 Planner / Director，为了避免语义和NLG降级，反而要避免被普通可见即可说抢走；消息盒子手点在本地，泛化语音则拟用动态选择工具。所以客户端必须根据卡片来源路由。
为什么不能说“消息盒子卡已经走 Planner”？
会议确认的只是“外部卡需要语音泛化，手点后要同步 Planner 上下文”。卡片信息是通过事件、Context、模拟Query还是新链路上云，以及最终是否用FC，都留到技术评审收口。
为什么不能说“无卡、无TTS就是端侧任务”？
卡片/TTS决定的是交互方式，端云归属由实时性、信号位置、规则确定性、模型/上下文依赖和安全要求共同决定。儿童锁无卡无TTS，但会议仍出现“云端直接判断”表述；后视镜虽然很像端侧候选，会议并未定部署侧。
