# 模拟 Planner 产品经理独立评审

依据：完整编号正文 source.txt（1—652 行）、原稿图 2 和图 5。以下是模拟角色的评审建议，待确认角色不是已落实的真实负责人。DT、Planner、Director 的命名不能单独证明是不同组件；问题聚焦业务责任与交互状态。

## 1. 图 5 仍把拉卡和执行放在 Director，且存在两条开盖路径

- 原文已写：57—63 行明确模型不直接拉卡，由原业务注册并发起卡片，明确确认后由原业务推动端侧复核与执行；图 2 基本沿用这一责任划分。
- 缺口及位置：388 行图 5 仍写“Director 调用卡片并语音解说”“Director 调用车控开启充电口盖”，其后又画 VUI 卡片“用户正反馈→打开充电口盖”。图文对拉卡方、一次确认后的唯一执行入口不一致；不能因命名不同就认为无冲突。
- 评审提问：“充电口盖这一条最终由哪个业务注册卡片、接收确认并推动执行？图 5 里的 Director 调车控和下方正反馈开盖，是同一次动作还是两次？能否统一成图 2 的唯一业务回调入口？”
- 影响：不同接入方可能分别实现模型工具调用和卡片回调，造成重复开盖请求；或误把模型建议视为已有用户授权。
- 可直接补文：“充电设备识别结果交给充电口盖原业务，由原业务注册并发起 VUI 卡片。模型输出用户选择的语义结果；点击或语音确认均汇入本次业务回调。原业务在授权有效且复核通过后请求端侧执行一次，并根据车辆回读更新结果。图 5 同步删除重复开盖分支，统一采用上述责任划分。”
- 待确认角色：充电口盖原业务产品及研发、Planner 产品及研发、VUI 接入研发。

## 2. “实际展示后才生效”已有原则，缺少云端迟到结果与换卡的判定

- 原文已写：57、61、63、81—82 行已限定实际展示后传入上下文、消失后注销，旧卡不能命中；图 2 有实际展示和未展示/失效分支。不能再概括为“没有上下文生命周期”。
- 缺口及位置：57—63 行、图 2 未说明新卡替换、卡片内容更新、注销与模型回复并发时如何拒绝旧结果。475、477 行的 event_id 关联覆盖业务事件，但不能单凭它识别同一事件内换卡或更新后的询问。
- 评审提问：“开盖卡刚关闭，儿童锁卡刚展示，此时上一轮‘好的’的模型结果才回来，原业务按什么信息判定它属于哪张卡、是否还有效？同一次事件更新了询问内容，旧确认是否还能接受？”
- 影响：可能把旧授权用于当前另一项动作，或在卡片关闭后接受在途确认。
- 可直接补文：“实际展示回执确定本次可交互询问。注入的上下文及返回的语义结果须关联任务、业务事件、本次询问及其版本。关闭、超时、替换或关键内容更新使旧询问失效；业务接收结果时再次核对关联信息、当前有效状态与是否已处理，迟到、旧版本或重复结果不执行。具体字段及同步接口由接入双方确认。”
- 待确认角色：VUI 生命周期负责人、Planner 上下文接入研发、原业务研发。

## 3. 解释和新诉求已有示例，尚未确定返回类型与旧询问去留

- 原文已写：69—82 行已经区分同意、拒绝、解释和新诉求；74 行解释不执行，76 行明确写旧询问规则需与 Planner 确认。
- 缺口及位置：62 行仅“确认、拒绝或其他诉求”，缺少“不明确”的明确处理（图 2 已有不明确）；73—76 行还未落定解释后的有效期是否延长、新诉求是否关闭旧询问，以及新诉求由谁承接。用户说“好，但先别开”这类混合表达也尚无验收口径。
- 评审提问：“‘为什么要打开’解释完是否继续等待原确认，是否续期？‘导航去另一家’是否立即结束开盖询问？‘好，但先别开’能否明确归为不授权，而不是只命中‘好’？”
- 影响：接入方可能把所有其他诉求都结束，也可能继续保留已不合时宜的开盖询问；模型与业务对是否授权产生分歧。
- 可直接补文（建议策略，需会签）：“语义结果至少区分明确确认、拒绝、解释请求、新诉求和无法确定；仅明确针对当前动作的确认可进入执行复核。解释请求保持原询问及原有效期，不自动续期；新诉求转交既有对话链路，同时结束本次预设任务询问；无法确定或包含否定、附加未满足条件时不执行，并按当前询问能力澄清。所有分支仍受原有效期与场景条件约束。”
- 待确认角色：Planner 产品、原业务产品、语音交互产品。

## 4. 点击兼容路线写了互斥，但图 2 和模拟 Query 的约束仍不完整

- 原文已写：60—61 行允许点击直接回业务或显式配置模拟 Query；77—78 行已要求静态 Advisor 兼容路线不得同时端侧再执行一遍。不能重复提成“缺少点击兼容”。
- 缺口及位置：图 2 点击仅画直接回业务，没有体现兼容路径；77—78 行未限定模拟 Query 必须携带本次询问关联、其返回是否仍回原业务，以及连续点击或点击与语音同时确认如何只消费一次。
- 评审提问：“旧链路点击确认生成的模拟 Query，如何保留这是哪一次询问的确认，而非一条新的开盖指令？模拟 Query 与语音确认同时返回时，由谁保证只接受一次？”
- 影响：兼容实现可能绕过当前询问校验，或把点击、语音分别作为两次授权执行。
- 可直接补文：“每张卡片发布时选定唯一点击路线。兼容路线生成的模拟 Query 必须携带本次询问关联与按钮语义，结果回到同一原业务授权入口，并接受与语音相同的有效性及重复处理校验；不得作为无关联的新车控指令执行。原业务对同一次询问只消费一次有效确认。图 2 增补显式兼容分支，具体映射能力在上线前验收。”
- 待确认角色：静态 Advisor 接入研发、Planner 接入研发、VUI 研发、原业务研发。
