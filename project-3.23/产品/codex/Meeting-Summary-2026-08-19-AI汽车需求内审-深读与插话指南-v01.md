## 1. 每个议题在讨论什么

### 1.1 端状态查询工具：从「模型筛选」切到 RAG（吴仁杰）

**背景**：1.6 模型下线，原来「先用小模型筛工具、再查询」的方案要换成 RAG（检索增强，用向量检索匹配查询内容）；赛力斯已上线，上汽在测试。

**会上的关键追问**：
- 张航第一句是「你这个需求是啥」——他不听技术方案，先逼出一句话的变更点。
- 左晨问「为什么用 RAG」——要方案动机。
- 张航追「准确率指标是什么」「不能低于原有模型效果」——量化验收门槛。

**结论（已确认）**：方案通过；吴仁杰补评测结果和预计时间、同步左晨；若 RAG 效果不达标，重新评估，不允许强行切换造成体验退化。

### 1.2 记忆与车机 POI 同步（郝晓伟）

**方案**：用户说「帮我记一下 XX 地址」走高德记忆工具；用户点「设为家/公司/收藏」走导航控制工具——两条语义分开处理，避免协议混乱。

**会上的关键追问**：
- 张航：「是不是只有车主能同步？」「车主没录 FaceID 呢？」——权限主体的边界场景。
- 赵益红：提出赛力斯高德账号自动切换开关的问题（账号切换时高德账号是否同步切换）。
- 徐洋：同一个功能因触发话术不同走了不同工具链路，会造成体验割裂——这是「两个入口、两种行为」的体验一致性问题。

**结论（已确认）**：短期方案通过、可进正式评审；短期方案只活到 915，之后替换成统一的 profile 模块（长期方案）。

### 1.3 赛力斯高德 agent 接入（Jojo）

**背景**：高德 SDK 不支持「指定道路算路、导航中路口控制、道路信息问询」等复杂指令；接高德 agent 能补能力，但性能不达标——算路首 token 平均 7 秒、全链路约 15 秒（理想同方案因此把 8 月 OTA 延到 9 月底）。

**会上的关键追问**：
- 张嘉锋打断：「我想问为什么接」——先对齐价值，再听方案细节。
- 陈敏：「耗时主要在哪个环节」「一定要走 Navi 透传吗」——拆链路找瓶颈、质疑方案前提。

**结论（已确认）**：会上不决策；拉赛力斯 + 高德三方会议，确认赛力斯对性能指标的接受度再定。

### 1.4 POI 搜索策略优化（Jojo）

**规则**：导航/算路状态下默认沿途搜，高速场景优先服务区内最近点；沿途搜无结果兜底为周边搜并明确告知用户；非导航状态默认周边关键字搜；排序对齐高德端侧表现。

**补充**：陈敏补了「POI 详情页场景」——要看用户指代词确定搜索中心点，否则范围跑偏。

**结论（已确认）**：通过，跑量迭代覆盖细分异常场景。

### 1.5 多工具卡片展示方案（苗雪晴）

**两案之争**：
- 方案一：完全流式返回、卡片随工具返回动态拉伸 → 尺寸频繁跳变、前端要适配多套 UI、实现难。
- 方案二：提前按工具类型预判尺寸、初始即按该尺寸加载 → 实现成本低，产问题只在工具失败时出现「空卡」。

**深层争论**：展示顺序要不要严格跟随播报顺序（张嘉锋、张航、陈西钺三人辩论）。张航给出结论性判断：「这代交互做不到 100% 一致」。陈敏建议减少跳变次数。

**结论（已确认）**：暂按方案二推进；与交互团队 April 对齐后再正式落地；先返回先展示、不做强制排序，后续单独优化打断恢复策略。

### 1.6 音乐查播边界（薛灵钥）

**边界规则**：歌名/歌手/专辑/单标签等明确条件直走音乐工具；热点事件、歌词、衍生信息、多标签组合、抽象语义（如「播放天青色等烟雨的歌」）先经联网或模型推理补全意图后再调用音乐工具。

**兜底机制**：director 做一轮校验——音乐工具返回结果与用户核心条件不一致时，再联网推理一遍；二轮仍不一致就终止，不做第三轮。

**留的尾巴**：
- 联网工具输出多首歌时要不要限数量上限？→ 问上汽策略，合理就跟，不合理再评估（薛灵钥）。
- 模型推理 vs 联网工具的边界怎么切？张航的原话是「只能调到一个平衡的状态，不保证直出的一定不走」→ 让明骏实验（晓伟、明骏）。
- 输出典型 case 集给研发做 SP 适配（已在推进）。

**结论（已确认）**：方案通过；可行性评估 + 上限询问两条待办。

### 1.7 车外语音控制智驾（徐汇文）

**场景**：抱小孩/重物时腾不出手掏手机，用语音让车直进直出（前/后移动）挪车取物。

**能力边界（SOP 阶段）**：只支持直进直出；模糊指令 + 0.1 米精度数值指令；单条指令，不支持左右移动、指定车位、组合指令。单次最大 10 米。

**权限**：蓝牙 6 米内的授权账号/车主可操作；声纹沿用现有车外语音统一逻辑（张航在这里追问了注册流程与人的对应关系）。任务执行中新指令目前直接退功能，赛力斯在推变更。

**法规提示**：明年可能有强标要求泊车类必须按住手机/钥匙，功能生命周期最多到明年年底，上线/下架随法规调整。

**张航的追问示例**：「声纹注册流程是什么样」「注册了怎么对应到人」「能向前一直走吗」「端云都会走 director 吗」——把一个「需求很简单」的方案问到了所有接口边界。

**结论（已确认）**：通过，复用现有车内车控工具逻辑适配。

### 1.8 记忆系统隐私策略（郝晓伟）★ 与你之前问题直接相关

**现状（当时线上）**：
- 隔离方式：按「车 + 豆包账号」做上层隔离，再按 FaceID 做筛选。
- 记忆单位 = 在某台车、某个豆包账号下，用户能看到、能召回的全量数据。
- 情景记忆：按用车场景隔离（A 单独用车 / AB 共同用车各自一套），从事件 → 短期 → 长期记忆都有场景隔离。
- 语义记忆：个人偏好/个人信息类，落库直接挂到具体人（FaceID → 昵称）。当时的缺陷：语义记忆没有跟场景绑定，谁说的话都可能被直接记到那个人头上。

**会上定的召回规则（方向已确认）**：
- 白名单标签（饮食偏好、住宿偏好、补能偏好等）：主体在场即可召回，不校验车上其他人。
- 非白名单标签（个人信息、社交关系、情感偏好）：必须主体单人在场，情景记忆按「在场人最小集」召回（AB 共同产生的记忆，AB 都在场才能召回）。
- 白/非白名单分类列表：会后发群里逐项评审，无异议就按此落地。

**会上讨论最深的一段：语义记忆生成原则**。
陈敏举的例子：「我在车上说晓伟喜欢吃苹果，你把这条记在晓伟身上，可晓伟未必真喜欢。」郝晓伟承认「这是当前记忆工具的一个缺陷」。讨论最终收敛为：
- 语义记忆生成必须满足「记忆主体在场 + 主体明确认可」，否则只作为情景记忆留存（「陈敏说过这句话」），不能挂到主体名下。
- 记忆的本质被重新定义：「没有所谓晓伟的记忆，都是豆包的记忆」——豆包对交互事件的认知，不替人打标签。
- 原则：拿不准就不记（「整体原则上要克制一点」）。

**未决/待确认**：
- 他人表述经主体认可后的召回范围（非白名单子集边界）还有一个分歧，后续专题另聊。
- 沉默算不算认可有争议（该场未拍死）。
- 「豆包账号给某人打的标签」的召回与账号切换关系：存在账号下的标签可以召回，账号切换则召回集不同——这块也留给了后续专题。

**回答你之前问的「账号和记忆的关联」**：账号是召回围栏之一。同一台车切换不同豆包账号，能召回的记忆集合不同；FaceID 语义记忆挂在账号下方。会上原话："上层是基于车以及豆包账号做隔离"、"账号切换了肯定不招（回）"。

### 1.9 VLM 长时感知任务链路（丁彬）

**需求**：把「宝宝醒了告诉我」「每隔一段时间告诉我宝宝在干啥」这类持续感知需求，转成端侧 VLM（视觉语言模型）可执行的任务。与 VQA（一次性问答）区分：这类任务要持续观察。

**链路（会上讲的）**：用户 query → Director/TaskService 拆成 VLM 任务 → 通过客户端模块下发到 AI Box（云端不能直连端侧）→ 插入舱内高频 always on 队列（定义 5 秒多，实测上报周期 6–7 秒）→ VLM 持续上报 → 条件满足由触发器判断 → 通知删除插入任务，回到原有预置任务队列。

**会上最关键的追问（张航）**：「哪个模块把 query 转成 VLM 需求？」「照顾后排宝宝不存在触发，VLM 返回的结果就不该过触发器，应该直接返回 advisor —— 但现在的链路是所有 VLM 都过触发器？」
丁彬的答复：过不过触发器由庆磊设计的 TaskService 模块判断——周期类/条件达成类走触发器；持续描述类（照顾宝宝）直接回 advisor。

**边界（会上定的）**：同时插入的长时感知任务 ≤ 3 个（decode 多了影响速度）；用户要求的感知周期最低 30 秒（张航：做不到的要在前期就告诉用户）。

**对标**：seed 的 Omni 视频通话——张航要求 always on 上线后的保底效果至少等同视频通话水平。

**结论（已确认）**：通过，915 落地；三条待办（补种子数据、约庆磊对比方案、研究 Omni）。

## 2. 为什么他们能讨论得这么深？（你问「我怎么不知道」）

不是天赋差，是信息结构差。这场 2.5 小时的会里，深度来自这六样东西：

1. **每个人脑子里有一张「全链路地图」**。
   丁彬刚讲到「task service」，张航立刻能接「那是庆磊设计的那套吗」「长时任务和条件任务都进那个模块吗」——因为这条链路他天天走。你不知道 TaskService 是什么、VLM 任务怎么下发，是因为还没人给你画过这张图（飞书里有庆磊的《[技术方案] Task 任务管理设计》和《【AIVA-视觉感知】TaskService 下发动态感知任务》，去把它读一遍，这张地图就有了）。

2. **带数据、带实验上会**。
   薛灵钥用 fornax 跑了「天青色等烟雨」能不能直接推理；吴仁杰带 RAG 评测准确率；高德 agent 的 7s/15s；always on 实测 6–7s。深度讨论建立在数据和实测上，不是拍脑袋。

3. **用具体场景当证据**。
   陈敏用「晓伟喜欢吃苹果」检验记忆规则；张航用李博暴雨里把车点到面前说明遥控挪车体验；用「杜宸在车上说这不是我家呀」解释地址记忆的边界。抽象问题 5 分钟吵不清，一个具体场景 10 秒让所有人站到同一个画面里。

4. **一套固定的追问链**（see 第三章），每个老手都是按这个模板问的，不是灵感。

5. **敢承认「做不到」和「这是缺陷」**。
   郝晓伟承认「当前语义记忆有缺陷」；张航说「每秒钟播报这种，直接告诉用户做不到」。先承认现状，才可能改对。

6. **有主持人机制**。
   徐洋控范围（不相关的可以不上）、控时长、最后收口（结论发群、明天下午和研发评、把需要的人填表）。没有这个机制，9 个议题聊不完。

## 3. 他们讨论问题的 10 个方法（可直接复用）

1. **先问决策点，再听方案**：「我想问为什么接」——价值没对齐，方案不用展开。（张嘉锋）
2. **先对齐现状，再谈改动**：「现在线上是什么行为？」——不知道现状，方案就是悬空的。
3. **要量化指标、要基线**：「准确率是什么指标？」「不能低于原有方案」。（张航）
4. **补边界场景**：「车主没录 FaceID 呢？」「每秒钟看一下宝宝状态会怎样？」——用极端场景找漏洞。
5. **查链路归属**：「哪个模块承接？」「这块算法谁做？」——问题挂到具体模块和人，才有下一步。
6. **找逻辑矛盾/反例**：「照顾宝宝的 VLM 结果不应该过触发器，但链路里所有的都过？」——用反例逼出设计盲区。（张航）
7. **用用户视角裁判**：规则有分歧时，回到「用户会怎么想」——「你会懵逼的」「爱人沉默了也不能代表默认」。（陈敏）
8. **三段式表达**：现状是什么 → 我建议改成什么 → 兜底是什么。（薛灵钥的查播方案）
9. **结论收口**：每个议题定「通过 / 待办 / 拉会」三选一，指定人和时间；不确定的挂群里确认。
10. **控制讨论范围**：「这只是短期方案，不想做太复杂」——大改动拆出去，本次只评短期。（郝晓伟）

## 4. 你怎么在会上插上嘴

### 4.1 先接受：插不上嘴是「素材差」，不是「嘴笨」

你能听懂别人在说什么，但你的脑子里还没有那张全链路地图、没有实验数据、没有过手过的真实 case——那一刻你没有「可以提出来的东西」。解决办法是先补素材（读文档、跑 case、问 owner），再把开口的动作拆小：**第一次开口不用是观点，可以是提问。提问 > 提建议**。新手最大的坑是急着展示观点（需要背全链路），而提问几乎零风险。

### 4.2 三个零风险的插话入口

1. **澄清式**（最安全）：
   - 「我确认一下，这个需求要解决的其实是 XX 问题，对吗？」
   - 「现在的线上行为是什么？改完之后用户能感觉到什么变化？」
2. **场景式**（用你真实的用户场景补分支）：
   - 「我补一个场景：如果后排有宝宝在睡觉，这个播报会不会吵醒？」
   - 「我补一个场景：用户在地库没信号时，这个链路会怎样？」
3. **边界式**（把极端情况问出来）：
   - 「如果 X 情况发生，会怎样？兜底是什么？」

### 4.3 五个可以直接抄的句式

- 「这块我补一个真实场景……」（把你见过的 case 端上去）
- 「我确认一下我的理解：……对吗？」（对齐认知，暴露信息差也是参与）
- 「这个指标的基线是多少？跟什么对比？」
- 「如果没有 X，兜底是什么？」
- 「今天先定 XX、会后拉群对齐，我理解对吗？」（帮主持人收口，是加分动作）

### 4.4 什么时候开口

- 主讲人停顿、翻页、喝水的时刻（「我这里有 1 个小问题」）。
- 主持人问「大家还有什么问题吗」——这是给你的安全窗口，不要浪费。
- 大领导（张航、张嘉锋、陈敏）问完问题后，你接一句「顺着这个问题，我有个场景」——这时大家的注意力都在「找问题」，你的问题会被认真接住。
- 议题切换时，先说「我最后补一个点」再讲，别在别人讲链路中间打断。

### 4.5 说法上的三层保护

- 对事不对人：说「这个场景等下会不会有问题」而不是「你这个方案有问题」。
- 用疑问句代替否定句：「这里是不是还会出现 XX case？」
- 把问题挂到用户身上：「用户如果……会怎样？」——责任在场景，不在发言人。

### 4.6 会前-会上-会后清单

会前（20 分钟就能做完）：
- 把要评的需求文档过一遍，圈出 3 个不懂的词；不懂就去飞书搜或者提前问 owner。
- 每个议题写一行：「一句话需求 + 现状 + 我能想到的 1 个边界场景」。
- 会前在群里问 owner 一个小问题——既准备了素材，又建立了存在感。

会上：
- 至少问 1 个会前准备好的问题。
- 会议纪要用自己的话记「谁负责、什么时间、什么标准」。

会后（10 分钟）：
- 对着逐字稿复盘：「他们问的哪个问题我本来也能问？为什么没想到？」
- 把没想到的问题抄进自己的「提问清单」，下次直接用。

### 4.7 从这场会里可以立刻拿去用的 7 个问题

1. 这个需求的「决策点」是什么？（先逼一句话）
2. 现在的线上行为是什么？
3. 验收指标是什么、基线是什么？
4. 极端场景是什么？（没登录/没信号/多人/误触发）
5. 这块由哪个模块承接、谁负责？
6. 兜底是什么、不达标怎么办？
7. 今天先定什么，还有什么没定、挂在谁那？
