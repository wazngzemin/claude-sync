# I 插话、打断与恢复

短期方案（2.6 目标阶段）按指令类型决定是否停播。TTS 播报中收到非拒识、又不是简单车控的指令，立刻停止当前播报，等待新一轮结果合成；收到非拒识结果后 1.5 秒（暂定）内仍没有简单车控指令，也立刻打断。判断为拒识就继续讲；非拒识加简单车控只响一声提示音，不打断当前播报。因网络等原因超过 1.5 秒才收到简单车控，此时打断当前播报也可接受。

二月底演示的实验版本采用更激进的开口打断，ASR 识别到两个字以上、确认用户开始讲话就停止 TTS，不先区分拒识还是召回；判断为拒识时用缓存的 pcm 音频续播，判断为召回则等待新一轮 TTS。该版本配有语音打断开关。长期的流式拒识、场景判断和恢复策略仍在方案讨论中。

# W 可见即可说

这套页面操作在语音分流里排在 P1。优先级从高到低依次是用户自定义任务、可见即可说、FAQ、端侧 LLM、云端 LLM。可见即可说只处理围绕界面文字的简单表达，本身不做语义推理；更高优先级的自定义任务先被接走，页面没有命中时才往下考虑 FAQ 和模型理解。

最终语音文字进入匹配服务后，先与当前有效指令比较。直接说按钮名称走精确匹配；模糊匹配允许在前面加“点击”“点一下”“帮我选”“选择”等前缀，句末可以带“吧”“啦”等语气词。需要更强语义理解的即时卡片操作，另走动态工具路径。

局部匹配在候选达到 6 个以上时，要求连续匹配 4 个字以上才认为对应得上。注册方生成指令时先过滤符号和标点；需要操作的元素只扫描最顶层页面，同名按钮要补位置或上下文才能区分。

执行成功、失败和需要播报的内容一起回传给豆包，由豆包统一播报；模拟点击要带页面点击动效。失败按系统提示方式用 toast 展示，失败文案不进入语音播报。

# F 能力准入与 Agent 协议

Agent Server 在链路最底层，只负责单个 Agent 的管理与调用，不承担 Planner 的编排调度。管理面保存 Agent 定义（英文名、中文名、UI 名称、能力描述）、租户实现（channel 与 channel_app_id 隔离，以及 AgentType、IntegrationType、Endpoint、鉴权）、版本环境（草稿、环境绑定、发布、启用禁用）和动态工具信息（Director 可见性、description、param_desc、notice、tips）。运行时按 agent_id、租户和环境选出实现，再做工具发现、准入和用户权限预检查。

这项工具按条件加载。条件引擎用逻辑组合 and/or 加原子条件表达，每个原子条件包含 field_source、field_name、field_type、judgement 和 values；本期 field_source 只支持 param，judgement 支持 exist、not_exist、in、not_in。当前方案检查请求中是否存在 real_time_card 等参数，满足条件后 current_page_specific 才出现在本轮工具说明中；没有有效卡片时，普通对话不会多出这项操作。端状态条件的统一接入属于后续扩展，规划复用 Trigger 服务的判定能力。

模型选中页面操作后，下游返回 select_button，说明选择哪个真实按钮，再通知客户端执行；回包 content_type 为 9 表示透传指令。按钮名称、卡片 ID 和页面有效性共同限定操作对象。它可以理解用户换一种说法，仍只能选择页面实际提供的动作。即时卡片信息未来归入 Context 统一管理。

下游可以分段返回，例如先给歌曲列表，再给完整内容。统一协议用 chat_id（贯穿多轮话题）、question_id（单轮 QA）、conversation_id（会话）、agent_id 和 trace_id（关联一次请求的全部操作）保存关联，把不同提供方的返回整理成同一种结构。is_finish 为 true 的最后一帧必须发出，座舱依赖它做端上发送和历史落表；这一帧才表示本次响应结束。歌曲是否开始播放，仍由业务结果说明。

同一结果可有三个用途。content 给界面呈现，tts_content 供语音链路使用，为 null 时回退到 content，model_content 给 Director 继续总结上下文，另有 reasoning_content 记录思考，command 承载跳转或降级等命令。chunk_type 区分回答与命令，content_type 区分纯文本、卡片 JSON 和透传数据。正常 TTS 播报由 Planner 总结后决定，下游不会各自争相播报。

Agent 无法处理当前请求时，可以返回 Fallback，把原因交回座舱侧重新安排。框架不提供通用的自动重规划，是否换工具、补问或结束仍由 Director 依据真实状态决定。音乐服务没有找到歌，与服务本身不可用，对后续选择的影响不同，因此返回内容要保留具体失败原因和已经完成的部分。

框架还描述了 Redirect，将请求明确转给另一 Agent，跳转最多两次。调用方需要重新检查目标实现、渠道和权限，再继续执行。Fallback 交回决策，Redirect 指定下一站；第三方是否支持该控制方式，要按其接入协议确定。

调用过程中用户打断本次请求，调用方通过 Context 发送 cancel 信号并断开连接，取消信号向下游传播，少数任务允许 WithoutCancel 不向下传播。Agent 需要的 SP 和 UP 由 Agent 内部自行从 Fornax 获取，不再由调用方传入。已经执行的车辆动作则要另走相应操作才能改变。

# T 长期任务与目标管理

创建条件任务前，任务入口还要复核条件和动作本身是否成立。条件要能被现有信号或视觉感知，要具备实际触发的可能；动作要符合安全与价值观，拒绝损害他人、伤害自己或违法的要求；动作要在本车可执行；条件和动作之间也不能互相矛盾，例如高温时要求把空调调到最高、检测到尾气污染时打开车窗。感知不到、不可能触发、无法执行、违背价值观或自相矛盾的安排，Director 不交给任务入口登记，改为对话澄清或直接拒绝，避免先答应一个永远无法判断或不该执行的等待任务。

这条由任务触发的建议，和静态 Advisor 的主动建议一样，都作为 advice 类型进入输入管理，按同一套优先级和排队、合并规则等待交给 Director。两者来源不同：Advisor 建议由顾问判断是否值得服务，任务建议由任务服务按已经登记的目标和本次触发事实生成；任务服务只负责找回原安排、校验有效性和生成本轮 Run，本轮意图判断、话术和工具选择仍归 Director。

# B 信号与当前状态

这些事实进入 Director 时分属不同输入类型：用户请求是 user query，刚发生的变化是 event，工具处理结果是 tool_feedback，主动与任务建议是 advice。输入管理保留类型与来源，Director 才分得清这一轮是在补事实、继续跟进，还是要执行新动作；状态、事件和请求之间不能互相替代。

# A 视觉感知与问图

启动前先检查对应开关、隐私权限、相机和模型资源。这里有三层开关，影响范围不同：AI 总开关关闭后，语音（含离线语音）和豆包 AI 服务整体不可用，各子设置项回到出厂默认，状态上云保存；AlwaysOn 是舱内持续观察的一级开关，下面再分两个子开关，它关闭时依赖常驻观察流的功能停止；AI-Box 关闭后默认同步关闭相关视觉能力。用户主动发起的单次问图和舱内拍照保留各自独立入口，不能因为常驻观察被关就拒绝一次明确的主动提问。

Task Service 接到“帮我照看二排宝宝”后，把任务转为可观察的目标并明确位置，再登记触发规则。创建前先看 AlwaysOn 是否开启：总开关或持续感知未开启时，任务服务查询后直接拒绝创建，而不是先登记再悄悄不运行；同一时刻下发的长时任务不超过 3 个，超过额度同样拒绝创建并把结果返回给发起方。新增、修改或删除目标时，服务端把当前完整目标列表重新发给端侧，VLM 收到的是全量替换后的任务集合，不做增量合并，避免端侧残留已经取消的旧目标。

视觉结果按 task_id 返回，任务服务逐项查找原目标。已经关闭任务的结果只落库、不再转发给触发判断，同时服务端会重发一次当前有效完整列表，清掉端侧残留目标；观察时间与服务端时间相差超过 20 秒的结果只记录、不送触发判断。每条有效结果单独调用一次 TriggerRun，单条失败不影响其他条目；转发结果分为 forwarded、expired、task_closed、forward_failed、task_not_found，返回计数区分 received、forwarded、skipped、failed，异步落库失败不影响本次接口返回。

触发结果按目标走向分成五类：周期汇报由定时器到点触发，把已有观察整理成主动推荐交回 Planner；目标达成即结束，关闭任务、主动推荐一次结果并重发有效列表；持续看护在需要介入时汇报，之后按规则继续观察；关注对象离车等无法继续实现的情况，关闭任务并重发列表；已过期或已关闭的任务同样关闭并重发有效列表。用户取消、目标离车或任务结束时，任务系统都更新完整列表，移除不再需要的观察。

用户问“看看后排孩子在干嘛”，Director 先确定观察对象和视角，再调用问图工具。是否走舱内端侧路径由车型配置判断，赛力斯舱内场景由端侧 AIBox 处理，完成取图和识别后只把文本结果返回云端，舱内图片不上云；端侧识别失败返回兜底话术，不自动 fallback 到云端模型，这是隐私保护下的固定取舍。两条路径共同承担语义理解、槽位提取、指令分发、摄像头控制采集、异常兜底话术和指标埋点，差别只在模型托管位置与结果去向。

舱外、地点或通用识别采用抓拍上传路径。云端发出取图要求，客户端按视角拍摄并返回图片引用；车辆识别交专用接口，其他适用场景由内容定制联网智能体处理。多轮问询时，本轮槽位与上轮一致就复用旧图，不一致才重新取图；舱内目标少，每次请求取新图、不复用。“这/那”等指代词由 Planner 结合上下文和视觉转成方位，转换失败按槽位缺失走正常处理，工程默认取前视摄像头。OMS 策略上后排屏未降下时只取前排 OMS，降下后再取前后排；上汽不支持提前缓存图片，SLS 可按时间戳取最近一张。

Director 接到结果再组织回答，必要时继续询问或调工具。看见充电设施可以支持下一步交互，但打开充电口盖仍需车控执行。无法匹配到已定义功能、也无法聚类到已知意图的请求一律走兜底话术，DNA 与 SLS 两套体系的报错文言不同；LBS 沿途问答结果来自第三方弋途，图片只承担交互展示。相机不可用、看不清或识别失败，本次调用就返回对应情况，让对话有明确结果。

两条路径的展示也不同。赛力斯舱内问图以文本呈现，不展示图片，其他适用上传场景可以图片加文本一起展示，这种体验不一致是端侧隐私取舍下的已知差异。用户主动问了一次，并不会自动创建持续观察任务。

# G 云端触发器

触发器在本轮只依据已经接入的当前状态和观察文字核对登记条件，命中后只把对应出口或建议送回主链，不直接向用户对话。用户偏好、历史背景和最终话术不在触发器这一步形成；任务建议或 Advisor 建议以 advice 类型进入 Director 之后，再由 Director 结合本轮上下文和用户记忆补齐判断与话术。

# S Advisor 主动服务

静态 Advisor 建议与任务系统触发的建议，在输入管理中同属 advice 一类，等待同一套优先级和合并规则；区别在归属：Advisor 建议由顾问基于服务价值生成，任务建议由任务服务按已登记目标和本次触发生成。两类建议都不直接当作用户命令，是否开口、如何确认和本轮动作仍由 Director 结合当前请求与车况决定。

## 节点 I2 按插话场景决定何时先停播

多人场景中，以“豆包”开头能表明是在呼叫助手；未明确呼叫时，由流式拒识判断这段话是否应打断。符合条件就先停下旧声音，让用户说完新话。

2.6 目标阶段的短期规则按指令类型划分，非拒识且非简单车控立刻停播，等待新一轮合成；非拒识后 1.5 秒（暂定）内仍没有简单车控也打断；拒识继续讲；非拒识加简单车控只响一声提示音，不打断。更激进的开口打断实验版本由 I3 单独说明，恢复方式随本车版本配置。

## 节点 I3 实际停止声音，并保存已发生的事

确定打断后，播放层实际停止旧声音，并记录请求编号、中断原因、已说和未说内容。还要保留新旧说话人的身份与音区，否则原本给主驾的回答可能错误接给副驾。

二月底实验版识别到两个字以上、用户开口即停 TTS；拒识时用缓存 pcm 续播，召回时等待新一轮 TTS，该版本配有语音打断开关。假如空调已经打开，只是确认话术没说完，停播不会撤销开启动作。

## 节点 W04 最终文字到来后匹配本次有效界面

用户说按钮名称时，先经过正常语音识别，最终文字到来后才与本次有效界面注册内容匹配。过程文字仍可能改字，因此不能只听到半个按钮名就提前点击。

注册指令集同时作为在线和离线 ASR 的动态热词；免唤醒时走纯离线，唤醒后离在线并行，离线有结果执行离线，离线无结果再等待在线。需要更强语义理解的即时卡片操作，另走动态工具路径，不在本节点的按钮注册范围内。

## 节点 W05 按约定文字规则找候选控件

匹配服务拿最终文字与注册词比较。直接说按钮名称走精确匹配；模糊匹配允许前面加“点击”“点一下”“帮我选”“选择”等前缀，句末可以带“吧”“啦”等语气词。局部匹配在候选达到 6 个以上时，要求连续匹配 4 个字以上。

没有候选时，用户仍可能在问问题或提出车控需求，应回普通入口继续处理。一个候选还要确认控件有效，多个候选则交注册业务选择或消歧。这里产出的是候选关系，尚未证明任何按钮已经被执行。

## 节点 W09 把实际操作结果和可播内容交回

页面业务执行后，把成功、失败和需要播报的内容交回助手。前面的识别、匹配、控件接收即使都成功，服务不可用或目标过期也可能导致最终操作失败，因此需要等这一层的事实。

如果一次操作涉及多项结果，应保留各自完成与失败，不能用一句成功覆盖全部。需要播报的内容交豆包统一播报，失败按系统提示用 toast 展示，失败文案不进入语音播报。接下来由统一输出链处理声音和界面。

## 节点 W10 统一播报并呈现相应界面反馈

页面业务返回可播内容后，交豆包统一合成与播放；界面同时按业务结果展示点击动效、成功状态或失败提示。失败原因需要转成用户能理解的话，例如说明当前按钮已失效，而不是把接口错误直接念出来。

音频已经生成时，电话等高优声音仍可能抢占播放。页面操作的执行结果、界面状态和声音播放各自更新，下一轮对话因此能知道“操作已经成功，但确认声音没有播完”，无需再次点击同一个按钮。

## 节点 F01 分别定义工具做什么与在哪里执行

工具定义告诉模型这个能力做什么，包含标识、中文名和描述；具体实现则说明在哪个项目、通过什么参数与接入点执行。同一种音乐搜索能力可以有多个实现，未必意味着模型看见多个不同工具名。

Agent Server 在管理面保存 Agent 定义、租户实现、版本环境和动态工具信息，运行时按 agent_id、租户和环境选出当前渠道已启用、已发布的实现。只有定义而没有可用接入，用户的需求仍无法落地。

## 节点 F08 补齐单个 Agent 的依赖并选择执行器

Agent Server 先按 Agent ID 读取具体实现配置，再从请求或 Context 准备这个 Agent 声明的依赖。历史、端状态按各自实现传入；长短期记忆的传递方式仍需单独接入。SP 和 UP 由 Agent 内部自行从 Fornax 获取，不再由调用方传入。

准备完成后，按提供方选择执行器，发出本次能力请求。执行器把不同提供方的协议差异整理好，业务后处理再将结果转换为统一返回。Agent Server 只负责单次调用，外层 Director 继续负责这轮目标及其他工具的安排。

## 节点 F09 把流式返回整理成可关联的统一协议

下游流式内容到来时，通用层按 chat_id、question_id、conversation_id、agent_id 和 trace_id 关联这次请求，再整理成统一格式。is_finish 为 true 的最后一帧必须发出，座舱依赖它做端上发送和历史落表，缺少结束信息时不能悄悄当作正常完结。

错误原因与已返回部分也要保存，供后续决定如何处理。即使收到正常终包，车窗是否关闭、订单是否成立仍要看业务内容。协议结束只完成了通信这一层，不能直接向用户宣布所有目标已经达成。

## 节点 F10 分别整理给界面、声音和模型的内容

统一协议后还可能有业务加工。例如音乐返回结构化歌曲列表，界面要保留列表结构，模型则需要能理解的候选事实。content 面向界面，tts_content 提供可播文字、为 null 时回退 content，model_content 供 Director 继续总结上下文。

另有 reasoning_content 记录思考，command 承载跳转或降级命令；chunk_type 区分回答与命令，content_type 区分纯文本、卡片 JSON 和透传数据。三路内容不能一律当成最终回答直接播放，整理之后按各自出口交付。

## 节点 F13 下游无法继续时把原因交回重新规划

Fallback 表示下游无法继续办理，把原因和已有结果交回座舱侧重新安排。框架不提供通用自动重规划，是否换允许的工具、补问或结束，由 Director 依据真实状态决定。比如能力不支持当前要求，回传限制比单纯报一个失败更有助于后续判断。

如果此前已经形成订单或车辆动作，也必须一并说明，避免换工具再做一份相同操作。各 Agent 是否支持这种回退及何时使用，取决于实际接入。回退不是自动重试许可，后续仍要依据真实状态重新规划。

## 节点 F14 下游明确指定下一 Agent 时由调用方转交

Redirect 是下游明确指定下一 Agent 的转交指令，跳转最多两次。调用方取得目标后，按目标实现和权限继续发起请求，同时带上原问题及已发生的业务状态。两者分工不同，Fallback 把问题交回座舱重新安排，Redirect 已经给出下一站。

转交后，原调用还要等待目标 Agent 的实际结果，再向上游说明办理情况。框架定义了这个控制出口，具体第三方是否支持、允许转交到哪些服务，仍由对应接入协议确定。

## 节点 T03 确认条件能观察、动作能执行

创建前先把承诺落到可实现的内容。“到那里提醒我”还缺地点，“宝宝发烧时告诉我”需要可靠体温依据，仅有视觉模型并不足以承担这个目标。系统还要确认动作在当前车型可执行，以及用户指的是谁。

必要信息齐备后再保存和登记；缺对象就补问，缺能力就说明限制。观察任务并发额度与任务中心总容量是不同检查，不能通过一个就跳过另一个。这样进入等待的安排才有实际证据来源，避免到时才发现根本无法判断条件。

条件任务还要再过一轮合法性检查：动作要符合安全与价值观，拒绝损害他人、伤害自己或违法的要求；动作要在本车可执行；条件和动作不能互相矛盾。不满足时不登记等待任务，由 Director 澄清或拒绝。

## 节点 T08 把本轮建议与任务执行记录一起交回主链

通用任务允许执行后，任务服务先关联推荐标识、整条 Task 和本次 Run，再经通知通道让客户端回流。服务端据此找回这一轮建议，输入管理决定何时交给 Planner，避免异步任务突然抢占当前用户对话。

建议只说明该继续办理什么，还没有发生真实动作。Planner 随后规划本轮工具，返回结果再记回原 Run。已接入的 GUI 长任务可由自身执行方推进，不能强制每一个内部步骤都绕回 Planner；但任务归属与最终结果仍要可追踪。

任务触发的建议与静态 Advisor 建议同属 advice 输入类型，经同一输入管理排队合并；任务服务保证归属和本轮 Run，是否开口、说什么、调用什么工具由 Director 决定。

## 节点 G01 登记条件、范围和命中后的接收方

云端触发器接到规则时，先保存要等什么条件、对哪些车辆生效，以及命中后通知谁。用户创建的宝宝提醒需要回原任务，预设舒适场景可能去 Advisor，静默内容则交相应显示业务，接收方不能混用。

绑定关系决定了后续怎样继续。相同一句“条件已成立”，若没有任务或场景身份，就无法判断是谁的安排、该不该执行。登记成功后仍需等待范围与开关检查，再监听相关变化；它此刻尚未触发，也没有替用户完成任何车辆动作。

触发器本轮只使用已接入的当前状态与观察核对登记条件；用户偏好、历史记忆和最终话术，在建议进入 Director 那一轮再由其结合上下文与记忆判断。

## 节点 S06 把需要 Planner 的建议交输入管理

需要 Director 承接的建议进入输入管理。首期方案把 Task Service 主动消息和静态 advice 作为普通优先级输入，空闲时处理，忙时等待，随后按合并属性安排推理。直接去 AI Bar 做界面确认的分支，可以先展示自己的卡片。

用户有效 Query 可以改变当前对话安排，已发出的工具则继续保留真实结果。同一批普通工具反馈汇集后，通过输入管理取得续轮调用；主动建议作为自己的业务输入等待处理。这样新的舒适建议不会把原导航反馈误当成自己已经执行成功的结果。

静态 Advisor 建议与任务系统触发的建议同属 advice 输入类型，按同一套排队与合并规则进入；归属和生命周期分别由顾问与任务服务维护，是否采纳由 Director 决定。

## 节点 A13 下发完整的动态观察目标列表

TaskService 把用户原话改写为可观察目标，并明确“那边的宝宝”所指位置。当前动态观察同时最多承接三条目标，任务标识要唯一；新增、修改或删除后，统一发送完整列表，让端侧准确知道现在该关注哪些事。

关闭持续观察时发送空列表清除已有目标，并告知相关任务终止。重新开启只恢复后续创建权限，不能把用户已经终止的安排自动恢复。超过额度时应给明确创建结果，不能只保存任务却悄悄丢掉对应观察。

AlwaysOn 未开启时任务服务查询后拒绝创建；同一时刻长时任务不超过 3 个，超出拒绝创建并返回明确结果。增删改都由服务端重发完整目标列表，端侧全量替换、不做增量合并。

## 节点 A14 接收动态结果时先查时效与任务状态

动态结果整包到达后，Task Service 按 task_id 逐项查找原任务。观察时间与服务端相差超过二十秒时，只记录、不转发；任务已经关闭时，同样停止转发，并补发当前有效的完整目标列表，移除端侧残留目标。

通过任务和时效检查的条目才分别交 TriggerRun。一条关闭、过期或转发失败，不影响其他有效条目。因此同一包结果可以同时包含成功转发与跳过，处理状态按条目保留。

已关闭任务的结果只落库不转发，并触发重发当前有效完整列表；观察时间与服务端相差超过 20 秒只记录、不送触发判断；每条有效结果单独调用 TriggerRun，单条失败不影响其他条目。

## 节点 A15 赛力斯舱内问图在端侧完成并回文本

赛力斯舱内问图由云端下发问题和相应提示，端侧问图模块直接调用 AIBox 的视觉模型，把文本答案回给 Planner。这里不经 TaskService 托管持续目标，舱内图片也不上云。

用户问后排孩子在做什么时，若相机或端侧模型不可用，必须回真实失败，不能声称已看过，也不会自动改用云端模型兜底。这一规则只描述该舱内路径，舱外或其他渠道应按各自接入选路，避免把隐私与失败行为混为一谈。

舱内端侧 AIBox 只回文本、图片不上云；识别失败返回兜底话术，不自动 fallback 云端模型；舱内画布只展示文本，与其他场景图片加文本的差异是已知隐私取舍。

## 节点 B10 分别理解当前状态、变化事件和用户目标

状态告诉系统当前温度或开关值，事件说明某时发生了开门、点击或停播，用户 Query 则表达希望做什么。它们可以共同进入后续背景，却不能互相替代，否则系统会把一个事实误当新的操作要求。

例如播报被打断是系统事件，随后用户说“先导航”才提出新目标。即使事件使用统一交互输入包装，模型也要按其语义理解。保留输入类型与来源，让 Planner 能准确判断是在补事实、更新进度，还是要重新规划。

进入 Director 的用户请求、事件、工具反馈和建议分别对应 user query、event、tool_feedback、advice 等输入类型；保留类型和来源，才能判断本轮是补事实、更新进度还是重新规划。
