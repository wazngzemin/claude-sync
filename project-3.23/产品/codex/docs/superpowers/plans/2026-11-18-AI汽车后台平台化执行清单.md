### 有车企要开通时怎么走

1. **先定给谁、开哪些功能。** 从交付或项目同学拿到目标车企、申请主体、对应渠道、要开放的模块和所需动作。把查询、配置、管理人员、发布或审批逐项确认。能说明业务场景再选权限。
2. **账号准入走诺亚白名单。** 开白就是让指定账号获得产品入口。在「产品白名单」里找 AI 汽车对应条目，按已确认的对象和有效期发起或跟进申请，审批后查看账号开通情况。文涛确认原「座舱大模型平台」条目属于 ToB。AI 汽车正式条目及真实车企账号的开白记录，用诺亚实际页面核对。 [诺亚白名单手册](https://bytedance.larkoffice.com/wiki/Rm1uwiYnGietgukxBwFcpLCqnyh)
3. **开口之后由研发配客户可用范围。** 方案里，外部主账号的渠道和模块范围由服务端配置。主账号和它的子账号共用这个范围。账号能访问火山后，实际登录人还要申请对应模块的运营角色。首次审批和首位外部管理员授权有各自的步骤。向文涛、兆乾确认这版实际做到了哪些模块和敏感操作，向刘杨确认触发器按单车、渠道以及记录创建人的规则。 [权限管理方案](https://bytedance.larkoffice.com/docx/CX5AdM2VfoBegzxU3ARcA3lDnm5) · [11 月 2 日权限评审逐字稿](https://bytedance.larkoffice.com/docx/Z97idYGySovpXaxgNOgcLViknkS)
4. **从现有需求单收结果。** 问继高或在 Meego 核对当前节点、提测版本及日期、测试负责人、实际结果和卡点。把「车企、渠道、模块、角色、动作、测试结论链接、下次确认时间」记入盘点表或关联需求。不确定的模块粒度请对应研发给当前口径和证据。

## 三 用一条案例定 DT 调试首版

DT 调试服务的是**正在改规则、想重现问题的人**。Planner 负责判断这句话接下来要做什么。系统提示词（SP）给它判断规则，上下文则是这次判断时能看到的车况和对话等信息。现在 Fornax 能调提示词，但有些动态信息需要调试者手填。会上提议先把指定的信息自动带进来，后续再扩到模拟器或其他输入。盘点表现为待设计。 [11 月 11 日逐字稿，01:17–13:30、22:21 起](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh) · [Fornax 提示词开发](https://fornax.bytedance.net/space/7522018773168046082/prompt/develop?page=1&page_size=20&key_word=planner)

1. **找一位实际调过的人演示。** 和明骏、晓伟或正在解 Planner 问题的同学约一条案例。请他跑一遍现在怎么从问题定位到提示词，在哪一步需要手填数据，一次要切哪些页面。请他指出影响最大的那一个卡点。
2. **把案例写成产品验收动作。** 记录项目或车型、输入的一句话或事件、会影响判断的一项车况或变量、现有做法、希望页面展示的输出。比如拿一条已经确认预期的车窗相关案例，用同一句话调试，看到页面取的车窗状态和 Planner 选中的动作，结果可以和预期对上。
3. **和张弛一起框首版。** 建议从一个项目、一个真实案例、一项自动带入的信息开始评估。问清信息来自测试车最近一次上报、模拟器还是调试人员提供的测试值，页面怎么注明来源和有效状态。先让用户看清 Planner 的结果。事件模拟、不同车型切换、模拟器联动及车端实际执行，各自写清在哪一期验证。
4. **把标准化拆成能单独拍板的问题。** 通用提示词放哪维护，车型专属的工具、动态示例和能力边界由谁维护，产品切项目时要看哪份最终版本。让左晨用一个真实车型差异举例，和张弛确认哪些要进首批。能力边界的内容提供者和平台开发负责人分别填清。 [上汽车型能力边界示例](https://bytedance.larkoffice.com/wiki/JFt0waC0XiIElOkSoHocpfHVnTe)

首轮收口需要一页说明，写明实际使用人、一个原始案例、页面输入和输出、首版范围、产品与研发负责人、下一次评审时间。会中可以问：「这个案例现在每次都要手填车况。首版如果只自动带入这一项，再展示实际取值和 Planner 的输出，能不能先解决你最频繁的调试问题？要接哪一个现有工具？」

2. **用同一条请求核对能看到什么。** 打开火山「日志查询」，先选渠道，再用「高级筛选」里的时间和用户 ID 找一个测试样例。只有车辆标识时请兆乾协助定位同一条请求。找到后打开关联的 Fornax Trace（一次请求的执行记录），逐项看原始输入、当时的上下文、Planner 的判断和工具结果，再对照旧 PRD 的展示与筛选清单。回放放在文涛指定的 PPE 预览测试环境查看，走读时记录能否从同一条请求过去、能否播放对应轮次。
3. **对每个缺口写清影响和处理人。** 比如「能听到播报，但看不到触发时车况，无法判断条件在那一刻是否满足」。这时要确认是数据已经有但页面没展示、数据源还缺，还是从列表进详情的入口不顺。先按能否复用现有 Trace 或日志页讨论方案。
4. **把第一版压到实际动作。** 可先讨论「按渠道和时间找到一条请求，点进去看到当时发生了什么，能复制该条关联记录给研发」。数据补齐、音频回放、从途中的某一轮开始播、导出和标注各自看用户是否必需。芮婷的导出与标注是已有使用场景，改数据源或展示形式前请她一起确认。

11 月 17 日周会上，徐洋讲的内部走查工具是**有人主动上报后登记问题**。西钺要的日志查看是**从当时一条实际请求还原现场**。DT 调试则是**主动给定输入和条件，重新跑一次模型判断**。对齐时先问使用者要解决哪一种问题。 [11 月 17 日产品周会，01:23:51–01:25:43](https://bytedance.larkoffice.com/docx/BG24dXxR5oeDt2xjjxzc37b5nih) · [旧版日志需求](https://bytedance.larkoffice.com/wiki/Mw1Bww6rTiV27CkibZkcwdj3nXc) · [日志列表展示维度](https://bytedance.larkoffice.com/wiki/OoagwrefQiBawgkA2mfcpJ9vnBe) · [日志筛选维度](https://bytedance.larkoffice.com/wiki/LtBPwNg4ni5EBHkpVoMcYw5FnZ1)

| 问题 | 火山当前页面看到了什么 | Fornax 的同一条记录有什么 | 回放看到什么 | 缺口影响 | 找谁定 |

| 触发时的车况是否已满足条件（示范） | 记录请求时间、用户输入以及是否有 Trace 链接 | 找到该时刻的输入和条件判断，记哪些字段存在 | 对齐音区及上下行音频。测试入口待就绪时记为待核 | 缺车况时，无法靠音频判断当时条件是否满足 | 西钺定必看字段，兆乾或文涛核已有数据和回放入口 |

查触发器问题时，先顺着「当时的规则 → 端侧有没有得到信号 → 模型怎么判 → 执行谁先谁后」取证。下面这些是排查方向，每一条都要回到同一个案例的记录。

| 候选根因 | 优先取什么证据 |
| --- | --- |
| 规则设计缺陷 | 取当时生效的场景规则和条件，确认该场景边界是否覆盖了用户期望 |
| 端侧资源限制 | 取信号产出状态、端侧处理耗时或资源记录，确认该轮有没有及时得到可用输入 |
| 大模型输出不稳定 | 固定模型版本、提示词和输入，记录多次判断是否一致，以及变化具体出现在哪个输出 |
| 软硬件时序冲突 | 看条件满足、信号到达、工具调用、实际执行各自的时间，对齐在哪一步先后顺序与预期不同 |

跟西钺对齐时可以问：「1 月的目标是出方案还是功能上线？我先跟你和徐洋拿同一条日志走一遍，把现有 Trace 能覆盖的和真的缺的定出来。走完我们再确认我接哪部分以及时间点。」
