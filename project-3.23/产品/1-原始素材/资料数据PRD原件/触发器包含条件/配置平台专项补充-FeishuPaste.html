5.4.1 为什么要做“系统预设任务整体配置框架”专项

本节承接9月1日产品内审02:07—02:17的讨论。本次要评的不是某一个Trigger规则，也不是把四个Case分别再开发一遍，而是：一项系统预设任务能否使用同一套产品框架完成定义、配置、运行、交互、执行和结果收口。

【来源明确】会议暴露的核心问题是：当前大家知道四个任务“想做什么”，却还不能共同回答“下一项新任务怎样接入”。本次专项需要回答：

  1. 一项完整任务由哪些内容组成，产品需要定义到什么程度；
  2. 哪些内容当前能在平台配置，哪些仍要研发单独开发；
  3. 端侧和云端分别支持哪些运行链路，一项任务如何选择；
  4. 卡片、TTS、二次确认、静默执行和防打扰能否被统一表达；
  5. 端云协同时同步什么、谁消费、失败后如何避免重复运行；
  6. 字节和赛力斯分别承接什么，如何避免同一场景重复提醒或重复车控。

四项任务在本次专项中的作用，是验证这套框架是否覆盖高频能力，不是形成四套互不相干的方案。

5.4.2 为什么不能继续按Case零散开发

  • 产品容易漏项：只写“条件＋动作”，会遗漏任务启停、数据时效、二次交互、执行前复核、真实结果和异常退出。
  • 研发会重复接链路：每来一个场景都重新找任务中心、Trigger、VUI、语音、模型和车控对接，成本高且口径不一致。
  • 平台能力容易被误判：会议已经纠正“条件可以配置＝整项任务无需开发”的理解；平台只能使用已经接入的信号、模型、交互和动作。
  • 端云与双边职责容易冲突：没有唯一运行方和主责方时，端侧、云端或字节、赛力斯可能对同一场景各执行一次。

【本稿要求】本期先把任务结构、端云选路、原子能力现状、模块交接和缺口盘清；不要求一次性建设完成统一拖拽式平台，也不能把目标能力写成当前能力。

5.4.3 一项任务从需求到可运行，需要经过六步

步骤产品要做什么各能力方要回答什么完成标准
1. 定义业务场景写清用户为什么需要、何时处理、是否要询问、希望车辆达到什么状态需求是否合理；是否与车企现有功能重复场景、用户价值和范围已会签
2. 拆成可复用能力拆成任务状态、数据、事件、条件、交互、动作、结果和退出每项能力当前是否存在、由谁提供、有什么限制形成原子能力清单，不再只有“条件＋动作”
3. 选择正式运行链路明确端侧、云端或端云协同，并说明为什么所需数据和能力在哪里；网络、时效和安全限制是什么同一次场景只有一个主要判断和建议产生方
4. 完整性检查核对数据、模型、卡片、语音、车控和真实回读均有承接方当前可复用、需要新增或本期不支持缺关键能力时阻止发布，不以“配置已保存”代替可运行
5. 配置或研发交付云端配置已接入能力；端侧按当前方式研发并随版本交付规则怎样生效、适用哪些车型和版本、怎样停止旧版本运行方收到同一份已会签业务定义
6. 联调与验收验证成功、拒绝、关闭、过期、重复和执行失败等场景每一跳输入输出是否正确，车辆是否真实达到目标数据、判断、交互、执行和真实结果证据齐全

5.4.4 当前形态、本期要求与目标形态

阶段云端任务端侧任务产品结论
【来源明确】当前已接入的车辆状态、部分条件、频率和动作可以配置；需要时可进入主动推荐、DT、VQA等已有链路产品先定义规则，端侧研发按需求实现并随车端版本发布；不是整项任务都能直接配置“页面能填条件”不等于信号、卡片、车控和结果链路已经接通
【本稿要求】本期盘清四项任务可复用能力与缺口，补齐云端判断到交互、再到端侧执行的业务交接补齐任务状态、条件、端侧卡、可见即可说、执行与结果回读的业务交接每项能力明确“当前可用／需要新增／本期不支持”
【目标能力】未来从同一份已会签任务定义取得云端运行内容从同一份已会签任务定义取得端侧运行内容同一平台管理任务定义、版本和适用范围；端侧与云端仍按各自正式链路运行
【待确认】建设方式现有配置平台扩展哪些能力、由哪个团队承接任务定义如何同步到端侧、端侧允许配置哪些能力配置平台、端／云Trigger和车端架构共同形成分期方案

目标形态不是“同一任务端云同时判断”，也不是“有网走云端、无网自动切端侧”。每项任务发布前必须确定正式主路径；若支持降级，必须单独定义降级条件和防重复规则。

5.4.7 端云同步必须满足的产品要求

  1. 一项任务只有一份已会签定义。端侧、云端不能各自维护不同的条件、交互和动作口径。
  2. 发布前明确运行位置。标明端侧、云端或端云协同；不能因网络变化让两个Trigger同时产生建议。
  3. 只允许选择已接入能力。缺少信号、模型、卡片或车控时明确提示缺口，不把“保存成功”当成“可运行”。
  4. 真实任务状态必须到达运行方。状态未知、同步失败或启用失败时，不产生新建议和新执行。
  5. 配置变化要有生效边界。新规则、关闭和回退后，旧条件、旧卡和旧用户确认不能继续触发动作。
  6. 端云交接要说明本次建议是否仍有效。云端提出执行请求后，端侧仍用最新任务状态和车况复核。
  7. 真实结果回到原业务。端侧读取车辆实际状态，再给出成功、失败或暂不能确认。
  8. 同一场景只有一个主动执行承接方。字节与赛力斯都具备能力时，发布前必须指定唯一主责。

【待确认】同步协议、底层字段和技术模块由研发方案确定；本PRD要求拍板的是同步对象、业务结果和失败行为。

5.4.8 字节与赛力斯怎样分工

端侧／云端描述能力运行的位置；字节／赛力斯描述谁对业务结果负责，两者不能直接对应。

判断原则产品解释
高实时、硬安全、车辆已有的确定性保护能力先评估由赛力斯车辆系统闭环，避免为接入豆包重复建设
需要语义理解、模型工具、上下文或主动交互价值字节重点承接相应Trigger、模型判断和交互能力
端云协同任务字节可负责建议和交互，赛力斯负责车辆约束、车控和真实状态；每一段仍需唯一主责
任务中心统一管理不等于所有任务都由字节重做；展示管理与实际判断、执行可以由不同业务承接
车辆动作云端结果和用户确认只形成执行申请，端侧最新车况与赛力斯车控限制是最后门槛

【来源明确】会议要求赛力斯先盘点已有和计划建设的主动服务／条件任务，再逐项确定字节参与范围。

【待确认】后视镜自动加热是重点边界Case：若赛力斯已有完整温感／洗车联动，且豆包没有增加新的识别、推理或交互价值，应优先复用车企闭环；若字节参与，必须明确新增价值和唯一主动执行方。
