# 飞书记忆模块全源深读与会议插话指南 v03

> 取证日期：2026-09-14  
> 目标：不是复述一次会议，而是把飞书中的记忆方案、画板、评论、测试记录和原始逐字稿串成一套可理解、可评审、可插话的方法。

## 0. 先说结论

这套车载记忆系统不是一个“用户画像表”，而是一条持续加工链路：

**多源事件 → 事件日志 → 瞬时记忆 → 短期情景记忆 → 长期情景记忆 → 长期语义记忆/用户画像 → 标签检索与排序 → Planner / Director 使用 → 根据反馈更新、降权或删除。**

其中：

- **情景记忆**回答“谁在什么时间、什么场景下经历了什么，系统做了什么，结果怎么样”。
- **语义记忆**回答“这个人长期是什么样、喜欢什么、习惯什么、与谁是什么关系”。
- **账号和车辆**决定数据能不能进入同一个记忆空间；**Face ID**决定空间内“说话的是谁、记忆说的是谁、当时谁在场”，两者不是一回事。
- 评审最难的不是记忆分类，而是四个变量经常被混在一起：**谁说的、说的是谁、存在哪个账号下、以后谁在场能召回。**

## 2. 用一个真实车载场景讲完整链路

场景：A 的豆包账号登录在 Car 1，A 和 B 在车里。B 说“今天有点冷”，A 让豆包给 B 打开座椅加热，B 说“二档正好”。

### 2.1 发生时：先进入事件日志

系统先记录可验证事实：

- 当前车辆是 Car 1；登录的是 A 的豆包账号；在场人员是 A、B。
- B 表达冷；A 发出车控请求；系统把副驾座椅加热设为二档；B 给出正反馈。

事件日志是全量流水账，目的不是直接形成“B 永远喜欢二档”，而是保留原始证据，方便后续追溯。

### 2.2 一段时间内：形成短期情景记忆

系统把相关事件聚成一个完整片段，而不是固定截取几轮对话：

> 晚间，A 与 B 同车；B 表示冷；A 请求打开副驾座椅加热；系统设为二档；B 反馈正好。

短期情景记忆强调 5W1H：谁、何时、何地、发生什么、为什么、结果如何。当前 PRD 明确指出，旧方案“按固定轮数压缩”容易变成流水账，且没有按用车人和用车场景隔离，因此需要优化。

### 2.3 跨天保留：形成长期情景记忆

长期情景记忆保留“有价值的经历”，丢掉不影响后续判断的操作噪声。它仍然保留时间、人物、场景、结果和证据来源，例如：

> B 在冷天乘车时接受了副驾座椅加热二档，并明确给出正反馈。

它不能直接写成“B 喜欢座椅加热二档”，因为一次行为不一定等于稳定偏好。

### 2.4 多次重复后：才可能上升为语义记忆

如果多个独立情景中，B 都在相似条件下选择二档，并且没有反向反馈，系统才有理由总结：

> B 在天气较冷时偏好副驾座椅加热二档。

这就是“从情景记忆总结语义记忆”。当前《记忆系统》把完整能力标记为 **P0，delay**；已完成的是语义用户画像的固定预注入，情景用户画像仍在进行中。

### 2.5 下次使用：先过身份和隐私，再谈召回

下一次用户说“按她习惯的来”，系统不能直接搜全库。它要依次判断：

1. 当前是哪个车辆、登录哪个豆包账号；
2. 说话人是谁，“她”指谁；
3. B 是否在场；
4. 这条记忆属于白名单还是非白名单；
5. 标签命中后，候选记忆的语义相似度、重要性、时效性是否足够；
6. Top N 是否足以支持 Planner 做动作，还是应该向用户澄清。

## 3. 语义记忆与情景记忆到底差在哪

| 对比维度 | 情景记忆 | 语义记忆 |
|---|---|---|
| 核心问题 | 发生过什么 | 这个人长期是什么样 |
| 最小内容 | 人物 + 时间 + 场景 + 行为 + 结果 | 人物 + 稳定事实/偏好/习惯/关系 |
| 证据要求 | 一次完整事件可以成立 | 通常需要明确表达、本人确认或多次行为证据 |
| 与在场人的关系 | 从事件开始就绑定当时的 A/AB/ABC 用车场景 | 绑定具体人物标签，但仍处于车辆 × 豆包账号的上层空间 |
| 更新方式 | 新经历补充、聚类、压缩、降权 | 同类事实覆盖、冲突澄清、周期性总结与遗忘 |
| 典型风险 | 流水账、信息过多、时间字段错位、长期保留价值不足 | 把他人观点写成本人事实、一次行为误判为偏好、不同账号概念混淆 |

最关键的一句：**情景记忆保存证据，语义记忆保存结论。没有可靠证据时，不能把别人对某人的评价直接写成那个人的长期事实。**

## 4. 账号、车辆、Face ID 和记忆是什么关系

### 4.1 一级数据边界：车辆 × 当前登录豆包账号

当前总 PRD 的明确表述是：记忆数据库按“车 & 豆包账号”隔离。换车或换账号，默认不是同一个记忆空间。

因此账号不是一个简单“登录状态”，它决定：

- 哪个豆包实例在积累与用户的共同历史；
- 哪组记忆可被搜索；
- 换账号后哪些记忆天然不可见；
- 删除、授权和记忆开关作用在哪个空间。

### 4.2 Face ID 的作用：空间内识别人，不等于拥有账号

Face ID 负责识别：

- 当前谁在说话；
- 一条语义记忆说的是谁；
- 一条情景记忆发生时谁在车上；
- 召回时哪些人在场。

它不等于“Face ID 属于哪个账号，就自动拥有那个账号的全部记忆”。会上反复争论，正是因为大家把“账号的记忆空间”和“空间里的人物标签”混成了一个概念。

### 4.3 共享乘客是额外同步规则

SLS 文档中的共享乘客有两个维度：

- Face ID 维度：设置为共享乘客后，这台车登录其他账号时也能识别该乘客。
- 记忆维度：主账号登录且共享乘客在车内时，除了生成“Car A × 主账号”的记忆，还可同步生成“Car A × 共享乘客账号”的对应记忆。

这说明“同车出现”并不会自动跨账号共享，必须有明确的共享乘客和同步规则。

### 4.4 当前隐私召回规则

总 PRD v1.8 把隐私分两层：

1. 车辆 × 豆包账号做一级隔离；
2. 在空间内部，按照记忆标签区分敏感与非敏感，并把记忆与当时在场人员绑定。

召回时：

- 白名单记忆：从“询问人的最大集”召回。只要历史场景中包含询问人，就可以作为候选。
- 非白名单记忆：从“当前在场人的最小集”召回。历史场景必须至少包含当前所有在场人，避免当着新乘客暴露只属于原来小圈子的内容。

当前仍有明确缺口：未注册乘客只能按人数判断，无法区分“人数没变但换了一个陌生人”；Face ID 识别期间如果短暂上报车内无人，还可能错误清空对话摘要。

## 5. 8 月 19 日会议真正争论了什么

会议不是在争论“要不要隐私”，这一点很快得到认可。真正没有对齐的是：**第三人描述某人的偏好时，这条信息属于谁的记忆？**

逐字稿中的典型反例是：A 的账号登录，A 说“B 喜欢吃苹果”，B 可能在场、可能确认、也可能不在场。

会上连续追问了这些问题：

1. A 的话是“事实”，还是“A 对 B 的看法”？
2. 如果 B 没确认，能否直接生成“B 喜欢苹果”的语义记忆？
3. 这条信息存于 A 的豆包账号，还是 B 的豆包账号？
4. 存在 A 的账号中但标签指向 B，能不能叫“B 的语义记忆”？
5. 下次 A 问“买 B 爱吃的水果”，B 不在场时能否召回？
6. 如果只进入情景记忆，经过压缩和遗忘后，这个事实会不会丢失？

会议阶段结论必须谨慎区分：

- **已认可：** 车辆 × 豆包账号的一级隔离方向；隐私需要结合车上人员；白名单/非白名单的基本思路有价值。
- **未收敛：** 第三人陈述如何从情景证据上升为语义事实；“某人的语义记忆”到底指数据所有权、记忆主体，还是账号内对该人物的标签。
- **会议现场处理：** 该话题被明确认为需要单独专题继续聊，没有在这次会上完成最终收敛。

## 6. 为什么他们能讨论得深

他们并不是背了更多术语，而是把一个看似合理的规则，连续放进不同状态中验证。

### 6.1 先拆清三个主体

- 说话人：谁提供信息；
- 记忆主体：信息说的是谁；
- 数据拥有者：当前哪个车辆 × 豆包账号空间保存它。

大多数混乱都来自把这三者都叫成“用户”。

### 6.2 追问证据强度

“A 说 B 喜欢苹果”只能证明 A 说过，不能自动证明 B 的真实偏好。只有 B 自己明确表达、B 当场确认，或多个独立行为长期一致，证据才增强。

### 6.3 把规则跑过整个生命周期

他们会连续追问：输入是什么 → 什么时候写入 → 写入哪一层 → 与旧记忆冲突怎么办 → 怎么召回 → 谁能使用 → 反馈后怎么更新 → 多久衰减 → 如何删除。

### 6.4 用反例找边界

不是问“方案对不对”，而是改变一个变量：B 不在场、切换账号、新乘客上车、Face ID 未注册、地址在地图里被修改、三个月后再问。只改一个变量，系统结果如果说不清，规则就还没有闭环。

### 6.5 把跨模块事实源问出来

“家地址”既可存在记忆，也可存在车机地图。短期方案先让记忆语义分流到提槽模块并写入地图；长期方案设想增加统一 Profile 模块，仲裁家、公司、收藏 POI、车牌、通讯录等用户信息。这里的评审重点不是接口，而是：**谁是真实来源、谁负责仲裁、双写冲突时谁覆盖谁。**

### 6.6 用可测指标收尾

测试周会没有只说“效果更好”，而是分层测：

- 打标准确率与召回得分准确率；
- 生成召回率；
- P50 / P90 生成时延；
- badcase 是否属于等级错误、标签有内容但未召回、评判标准不足；
- 改模型后性能提升是否伴随语义/情景效果回退。

6 月 29 日记录中，长期情景记忆打标得分准确率为 87.8%，召回得分准确率为 82.5%；随后要求调整 L0、重审“标签下有内容但未召回”的逻辑，并把全量记忆对比加入复测标准。这种“指标 + 失败样本 + 标准修订”就是深度评审的落点。

## 8. 你在会上怎么插上嘴

你不需要先给答案。先把别人没有说清的变量钉住，就已经是有效发言。

### 8.1 概念边界

> “我先确认一下这里的‘B 的语义记忆’，指的是记忆主体是 B，还是数据存在 B 的账号空间？这两个会影响后面的召回权限。”

### 8.2 事实来源

> “这个偏好是 B 自己明确表达、B 当场确认，还是 A 对 B 的判断？三种证据强度不同，是否应该先进入不同层级？”

### 8.3 写入位置

> “这个 case 最终是进入事件日志、长期情景，还是直接覆盖语义记忆？如果直接升语义，触发阈值和反向证据是什么？”

### 8.4 账号与在场人

> “我补一个切账号反例：同一台车从 A 账号切到 B 账号，Face ID 仍识别出 A、B，这条记忆在哪个空间可见？共享乘客规则是否参与同步？”

### 8.5 隐私异常

> “如果后排未注册乘客人数没变但换了人，当前 Face ID 无法区分。敏感记忆是不是应该默认不主动使用，并记录一次安全降级？”

### 8.6 跨系统事实源

> “家地址同时存在记忆和地图时，谁是 source of truth？用户在地图手动修改后，记忆是覆盖、双写，还是保留版本并澄清？”

### 8.7 评测验收

> “这个方案的收益准备在哪一层验：生成准确率、召回率、P90 时延，还是最终 Planner 使用正确率？如果只看召回，会不会把召回了但不该使用的隐私 badcase 漏掉？”

## 9. 你会前只要准备这一张小抄

遇到任何记忆需求，按下面顺序写 8 行：

1. 用户场景：用户究竟想让系统记住或想起什么；
2. 说话人 / 记忆主体 / 数据拥有者分别是谁；
3. 原始证据来自对话、行为、车况还是其他系统；
4. 应进入事件、情景还是语义层；
5. 写入、冲突、覆盖和遗忘规则；
6. 召回时账号、Face ID、在场人和隐私条件；
7. 下游 Planner 如何使用，错用会造成什么用户伤害；
8. 用什么指标和反例验收。

你只要在会上发现其中一行没人回答，就有一句可以插进去的话。
