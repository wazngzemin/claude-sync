1. 豆包语音联网查询链路总览

核心结论：对“今天金价怎么样？”这类联网查询问题，用户可见链路通常分成两个阶段：搜索中的铺垫话术 与 搜索完成后的总结性话术。从当前 Android 仓库能确认的事实看，客户端主要负责 ASR 结果接入、联网搜索意图透传、FlowIM/Nova 消息接收、搜索 block / 文本消息展示；而“具体文案如何生成、何时返回”主要在服务端 / Director / 搜索编排侧完成。
下面按“用户 query → ASR → Chat 发消息 → FlowIM / 服务端编排 → 铺垫话术 → 总结性话术 → Nova / UI 上屏”的顺序梳理整条链路，便于后续排查“是上游没返回、IM 没到、还是客户端展示慢”。

2. VehicleDialogueManagement 链路拆解（结合端侧离在线仲裁方案）

核心结论：VehicleDialogueManagement 不是一个单纯的“语音回调类”，而是车机端对话内核的总控入口：它负责把 VoiceClient 的 Wakeup / VAD / ASR 事件接入到 DialogueSession，再通过 Interceptor + Session + Platform + Arbitration 这条 handler 链，完成“本地执行 / 远端发送”的分流。结合 wiki《端侧离在线仲裁技术方案》看，当前代码已经落地了“端侧离线 + 云端联网”的双轨设计，但也存在一个明显现实差异：远端发送主链目前仍然直连 NovaAbility.sendTextMsg，并未完全走 IDialogueChannel 抽象。
本节同时对照 wiki 《端侧离在线仲裁技术方案》 的“整体架构 / 业务交互流程”，基于当前仓库最新代码梳理 VehicleDialogueManagement 的真实运行链路，重点回答三个问题：它从哪里被拉起、它如何决定本地还是云端处理、云端结果如何回流到 Nova/TTS/UI。

SessionHandler 先建立 requestId 级别的仲裁缓存：每次请求一进来先创建 TaskResult 放入 NovaTaskCache，再把共享 DialogueContext 挂到 request 上，后续仲裁、本地采纳、云端抢占都围绕这个缓存对象更新。代码见 business/dialogue-management/impl/src/main/java/com/larus/vehicle/dm/impl/handler/SessionHandler.kt:28 与 business/dialogue-management/impl/src/main/java/com/larus/vehicle/dm/impl/cache/NovaTaskCache.kt:20。
DialoguePlatformHandler 负责“包装上下文 + 对接执行层”：它会把 historyCache.fetchAllHistory() 和 vehicleInfo 注入请求，再调用 next.doWork() 交给仲裁器；如果本地结果被采纳，它会走 processInLocal() 触发车控执行；如果要云端处理，它会走 processInRemote()。代码见 business/vehicle/impl/src/main/java/com/larus/vehicle/nova/dialogue/DialoguePlatformHandler.kt:57。
DialogueArbitrationHandler 是“本地 vs 云端”的核心决策器：唤醒态请求会先 processInRemote()，同时启动本地 LLM 推理；非唤醒态则本地优先。如果本地结果命中白名单，就采纳本地；否则转到远端。这里的“已被云端采纳/是否拒识/来自哪一侧”都写回 NovaTaskCache。代码见 business/dialogue-management/impl/src/main/java/com/larus/vehicle/dm/impl/handler/DialogueArbitrationHandler.kt:46。
ExecutionPlugin 是执行层落点：本地执行调用 VehiclePlatform.sendVehicleControl(...)；远端执行理论上可以走 linker.sendMessage(...)，但当前实现中该分支被写成 if (false)，实际固定走 NovaAbility.sendTextMsg(...)。代码见 business/vehicle/impl/src/main/java/com/larus/vehicle/plugin/ExecutionPlugin.kt:95。
云端回流不经过 VehicleDialogueManagement 主循环，而是回到 Nova 宿主：远端文本发出后，后续的 IM/云端消息由 NovaServiceBinder 监听并转换成 NovaData.MessageReceiveData / MessageUpdateData，再交给 NovaAbility.handleNovaData() 做 TTS、状态和 UI 处理。代码见 business/vehicle/impl/src/main/java/com/larus/vehicle/nova/service/NovaServiceBinder.kt:342。

8. 断点判断与根因归类



已确认事实
query 发出、Nova/FlowIM 收发消息都正常，铺垫性话术在 2~3 秒内返回。
铺垫性话术已经在端上展示并播报，不存在“前半段根本没播出来”的问题。
总结性话术真正到达端上后，NovaServiceBinder、MessageTextFloatWindow、AICanvas 都在几十毫秒内完成刷新。
用户感知的“慢 1 分钟”发生在铺垫性话术播报结束与总结性话术开始下发之间。


最终根因
根因已定位为：铺垫性话术端上播报完毕后，没有给服务端上报“播报完毕”状态。服务端因此一直等待该状态，直到接近 1 分钟超时后，才继续下发总结性话术。
所以现象上看起来像“总结性话术云端出得慢”，但更准确地说，是端上缺失播报完成回传，触发了服务端等待超时。


责任边界
不是总结性话术到端后的 UI 渲染问题。
不是单纯的 LLM 或检索首包生成慢。
准确边界应定义为：端上播报状态回传缺失 → 服务端等待播报完成 → 超时后才继续下发总结性话术。

归因口径建议：本次问题应统一表述为：铺垫性话术播报完成后，端上未向服务端回传播报完成状态，导致服务端等待约 1 分钟超时后才下发总结性话术；因此用户感知为总结话术晚到。
