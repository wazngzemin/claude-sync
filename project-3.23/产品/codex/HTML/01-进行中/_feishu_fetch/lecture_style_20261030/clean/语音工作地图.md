# 0. 一页速览

## 0.1 链路一句话

你在车里说「我有点冷」：车端麦克风采集 → 降噪回声消除 → 判断音区（主驾/副驾/二排）→ VAD 判断你说完了没 → 音频上传到座舱云 AIDV → Speech 云把声音转成文字（ASR）→ 拒识模型判断这句话是不是在跟车机说话 → 离在线仲裁决定走端侧还是云端 → 文本请求过豆包云（风控、安审、打断判定）→ AIDV 的 Planner 理解意图、调 Agent 查端状态（空调多少度）→ 生成回复文本 → TTS 合成为「桃子」音色音频 → 客户端拉流播放；如果你中途打断，系统再判断要不要把没说完的话续播。出处：[豆包×AIDV端云链路OnePage](https://bytedance.larkoffice.com/wiki/DBRnwrLFNiPxV5kZZOXcBYxqnCl)、[语音基础体验链路OnePager](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)。

## 0.2 现状最差的三件事（2026-10 口径）

1. **整体慢**：云端全流程 2550ms，「语音识别结束 → 开始播报」3600ms；路测反馈「比上汽慢很多，等 5-6 秒以上」（[服务端AIDV架构梳理](https://bytedance.larkoffice.com/wiki/SwaPwKLkNiKDdekvvp5cWwybntb)、[AIVA高优问题表](https://bytedance.larkoffice.com/wiki/Tp70wuM9YijpZ1kj8pJcgPXKnib)）。
1. **本地对话链路/全时免唤醒通过率 <50%**：提测后未通过，全时免唤醒「不通，拒识升降级也不通」；主交互测试通过率 84%（185 用例 pass126/fail3/block21/NA35）（[AIVA需求管理台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。
1. **离线 ASR 不达标**：思必驰离线句准实测 60.99%（导航场景仅 41.93%），出厂检查点状态 Fail；有网时偶发切到离线 ASR，错得离谱导致后续推理全错（[ASR测试报告](https://bytedance.larkoffice.com/wiki/AeYjwYhOqi3FCYkpbqNc9FFAnsh)、[上汽DNA量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。

# 1. 全链路总览

你会遇到的第一个困惑是：一次语音请求到底过了几台机器、谁在转谁。答案是四方：**客户端（车）、豆包云、座舱云 AIDV、Speech 云**。一次交互经过四种数据形态：用户音频 → ASR 文本 → 待播报文本 → TTS 音频（[端云链路OnePage](https://bytedance.larkoffice.com/wiki/DBRnwrLFNiPxV5kZZOXcBYxqnCl)）。

### 细分① 听谁说、多人分区

<image token="N0uibfqk8oOYfVxCCXbc8FI1neb" width="1200" height="820" align="center"/>

**例子：**主驾说"空调最大"、副驾同时说"有点冷关空调"。**判据（来自多人同时语音交互 PRD）：**先看两条是否都有效 → 再看内容是否冲突，**只有冲突才**由云端反问"同时收到两条指令，请问执行哪个？"并等待乘客选择；不冲突的有效指令可合并执行。**用户结果：**不擅自执行冲突操作、等待乘客选择；选错或没选时的重试动作原文未确认。**边界：**乘客之间聊天（不跟车说话）不回应；有效指令、讲笑话仍应答。来源：[多人同时语音交互PRD](https://bytedance.larkoffice.com/wiki/U4xLwmQNki1Pu5kpyAGcHWtmngf)、[多音区全时免唤醒PRD](https://bytedance.larkoffice.com/wiki/W7kxwMqwmitpjSkv9BAcakO1nSR)。

### 细分② 停顿说完、取字纠错

<image token="BBCjbY0PCoCcYhxioYhcAOVMnvc" width="1200" height="820" align="center"/>

**判据（来自端云链路 OnePager）：**车持续收音，按 VAD 停顿判断你是否说完；流式识别结果出来后还会再过一遍语义。**例子：**"虹煤"被纠成"虹梅"是 PRD 设计中的纠错演示，不是当天实车量产效果。**用户结果：**说完才把完整句子交给后续判断；停顿不够时继续听、不抢答。来源：[OnePager端云链路](https://bytedance.larkoffice.com/docx/Ied8dT6LDoYpPkxauioc3aM4nBx)。

### 细分③ 该不该回应

<image token="RF0sbLIrvof50kxegPxcvVFQnrb" width="1200" height="820" align="center"/>

**判据：**一句话进来，先看它是不是对车说的。**乘客之间闲聊（不跟车说话）→ 不回应**；但**有效请求都接**：你让车讲个笑话、问个问题、下条指令，车都应答。**用户结果：**两人聊天时车不插嘴；你点到它，它就接。**边界：**播报进行中怎么插话、停不停，见细分⑥，本节只判断该不该接。来源：[1.0对话需求](https://bytedance.larkoffice.com/docx/PX9dd8Lk2oQNb1xBeM5c7D3pnUc)、[多人同时语音交互PRD](https://bytedance.larkoffice.com/wiki/U4xLwmQNki1Pu5kpyAGcHWtmngf)。

### 细分④ 无网 / 有网仲裁

<image token="OThnbE9zyo8qF9xyPMycBqJjnUd" width="1200" height="820" align="center"/>

**判据（来自离在线仲裁 PRD）：**先判断有没有网。**无网三层：**本地能理解 → 直接执行；这件事必须联网 → 提示能力限制；连本地都理解不了 → 走离线兜底话术。**有网：**端云并行，结果优先级＝离线白名单 > 在线 > 离线非白名单 > 离线通用兜底——白名单只是"更快"的优先权，**不是**"无网只有白名单能用"。**例子：**"我有点冷"必须先查车况/天气/乘员，不能本地白名单硬开空调。来源：[仲裁PRD（离在线仲裁）](https://bytedance.larkoffice.com/docx/Nvj1dvkl8oOTAhxOjxAc0bn0nS0)、[离线LLM指令解析](https://bytedance.larkoffice.com/wiki/IkRFwEv2biq6igkvlMtcfOiNnjb)。

### 细分⑤ 简单 / 模糊 / 组合执行与反馈

<image token="ELcjbJPF0oQjYhxzsa9clnjpnhd" width="1200" height="820" align="center"/>

**判据：**按指令简单程度分流。命中当前允许的本地快路 / 白名单配置才走本地，不等于所有简单车控都能离线办；**模糊诉求**（如"我有点冷"）必须上云端结合场景理解；**组合指令**（如"打开空调顺便讲个笑话"）由 Planner 拆成多步执行。**用户结果：**成功反馈以服务真实返回、车辆状态真的变化为准，不是"秒办"的口头保证；失败时只提示原则，具体失败话术原文未确认。来源：[1.0对话需求](https://bytedance.larkoffice.com/docx/PX9dd8Lk2oQNb1xBeM5c7D3pnUc)、[仲裁PRD](https://bytedance.larkoffice.com/docx/Nvj1dvkl8oOTAhxOjxAc0bn0nS0)。

### 细分⑥ 播报插话与主动服务

<image token="YUMxbmWI0onpWhxfYK6cuxI7ndc" width="1200" height="820" align="center"/>

**判据：**播报中你开口，先语义判人机还是人人。**人机**→停播、办新事；**人人/拒识**→继续播。**主动提醒**是独立入口，不从"不满足条件"分支接过来；它什么时候能插话、能不能压过播报，原文未确认（TTS 六档优先级仅为参考截图，非量产现状）。**用户结果：**你对车说话车就停；闲聊时车不打断；主动提醒的具体抢占规则待确认。来源：[打断策略PRD](https://bytedance.larkoffice.com/wiki/FLlSwl1GoicNugkWWLCcFxtmnhl)、[离在线车载TTS服务PRD](https://bytedance.larkoffice.com/wiki/KlRgwueVKipbeLkdzkGcO15inKh)。

### 怎么画出上面这六张图

<image token="OCUBbHegOoJ0RoxwSvFc2FwZnNc" width="1200" height="640" align="center"/>

**六步怎么来的（拿多人冲突这条线做示范）：**① 先抄一句真实原文——多人同时语音交互 PRD 里写的"同时收到两条指令，请问执行哪个？"；② 标角色和输入输出——主驾/副驾两条音频进来、云端仲裁出去；③ 拆成真菱形条件——"两条都有效吗？"→"内容冲突吗？"；④ 只有冲突分支才走"反问 + 等待乘客选择"这条线，不冲突走合并；⑤ 用真实 case 走线验证一遍；⑥ 选完之后执行什么，原文没有，就标"原文未确认"，不替它造一个动作。每张细分图都按这六步出，节点分叉数跟着原文走，不强凑四个出口。来源：[多人同时语音交互PRD](https://bytedance.larkoffice.com/wiki/U4xLwmQNki1Pu5kpyAGcHWtmngf)。

# 2. 分环节详解

下面每个环节按统一格式写：它做什么（配一个车里的例子）→ 关键规则和参数 → 指标 → 实现方 → 产品/研发负责人 → 状态排期 → 已知问题和 meego 单 → PRD/方案链接。人名、数字、日期照抄笔记。

## 2.1 唤醒（Wakeup / KWS）

**它做什么**：你说「豆包豆包」把车机叫醒。例子：主驾上车按方向盘按键或直接喊「豆包豆包」，系统在安静、嘈杂环境都要醒。唤醒词固定为「豆包豆包」，不支持自定义；产品终态是「用户说不说唤醒词都可以」（全时免唤醒），唤醒词只是兜底（[车内语音PRD](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）。

**关键规则和参数**：唤醒响应 ≤350ms（用户说完唤醒词到系统给出唤醒事件）；另有方向盘按键唤醒、三方助手（Siri）唤醒互斥。**唤醒抑制是硬伤**：车外人对玻璃喊「豆包豆包」、手机播放含「豆包豆包」的音视频都不应唤醒，PRD 要求弹 Toast「车外人唤醒已抑制」，但原文 callout 写「**唤醒抑制能力，供应商不支持**」（[车内语音PRD·唤醒抑制](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）。

**指标**：安静环境唤醒率 ≥98%、嘈杂 ≥95%；误唤醒 ≤12小时1次（PRD）vs ≤10小时1次（FeatureList）——口径冲突见第 8 章。量产平均耗时 ≤500ms；出厂检查点状态 Block，「唤醒率等待测试结果」，测试 @崔思远（[FeatureList](https://bytedance.larkoffice.com/sheets/PHXzs0YEmhomVQtvpcbcdsXqneg)、[出厂质量检查点](https://bytedance.larkoffice.com/wiki/Ur3Zwu4LMiqatwk4xrScTwYMntV)）。

**实现方/负责人**：实现方 **思必驰**；产品 @左晨；客户端人力 @赵衍 20 人天、服务端/算法 @左晓杰、测试 @林满恕 20 人天。**状态排期**：待优化，S 阀；声学标定关键路径——830 基于 OTS 半工装车型开始标定（1 个月标定+1 个月训练），9/25 功放软件锁定，SLS 要求 2026.11.6 完成声学标定，需求提测 2026.10.30，2026.11.1 合入 SLS 语音包。**已知问题**：唤醒抑制供应商不支持，当前无解；路测「右后首次未唤醒，说豆包豆包多次」（[路测问题](https://bytedance.larkoffice.com/wiki/Tp70wuM9YijpZ1kj8pJcgPXKnib)）。

## 2.2 ECNR（降噪 + 回声消除）

**它做什么**：每个座位的高灵敏度麦克风独立采集+降噪，压掉空调声、轮胎噪声、风雨路噪；回声消除（AEC）实时采集扬声器输出，抵消音乐、导航语音对麦克风的干扰。例子：你在放导航「前方五百米右转」，同时说「把空调调高两度」，系统要从麦克风里把导航声剔掉。参考音暂定 **4 路**；处理时间 ≤50ms；信噪比 ≥20dB（[车内语音PRD·降噪回声消除](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）。

**指标**：本身不设准确率指标，效果靠后续 ASR/唤醒指标体现（[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。**实现方**：思必驰；产品 @左晨；待优化，S 阀，随声学标定 11/6 完成。

## 2.3 音区识别（Sound Zone）

**它做什么**：判断这句话来自哪个座位，5 座车支持 5 音区。例子：副驾说「把我这边车窗关上」，系统要认出是副驾、只动副驾车窗。端侧字段 sound_zone 随请求上送；多模态音区定位用摄像头人体特征+声学特征收窄位置；主驾靠背 >120 度躺平时不能误判成二排左侧。定位误差 ≤±20cm；音区可单独关闭，关闭后弹 Toast「该音区已关闭」（[车内语音PRD·音区识别](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）。

**指标**：安静/中速关窗/高速关窗均 ≥98%（台账）vs 出厂检查点 ≥99%——冲突见第 8 章。**实现方**：思必驰；产品 @左晨；随标定 11/6 完成。**已知问题**：路测「后排右侧说话主驾也上屏了」「豆包错把主驾当副驾」；上汽必解 bug「主驾说的话被识别成主驾+副驾」，已解决（换新版思必驰资源复测，@任少东），meego 7359234801、7359284840（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。

## 2.4 声纹识别（Voiceprint）

**它做什么**：认出说话人是谁。例子：录入声纹后，副驾说话系统叫出「你好晓晓～」；识别为儿童操作车窗时提示无法操作。显性录入连说三次「豆包豆包」；注册上限 **5 个**；特征只存本地。指标：安静 ≥95%、嘈杂 ≥90%（出厂检查点，NA 未测）。**实现方**：火山（云端）；产品 @左晨；**状态**：规划中，DNA1.0（26年8月SOP）否、SLS（26年12月SOP）是，依赖车企配置界面开发（[车内语音PRD·声纹](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)、[FeatureList](https://bytedance.larkoffice.com/sheets/PHXzs0YEmhomVQtvpcbcdsXqneg)）。

## 2.5 车外语音

**它做什么**：你站在车外对车喊「豆包豆包，打开后备箱」，车要醒、要认证你是谁、要执行。当前支持车外四音区定位；能力含车外安全认证、音量调节、开关车门/后备箱、外灯反馈唤醒/聆听/识别/播报状态（[E68车型功能清单](https://bytedance.larkoffice.com/wiki/KqSDwFmXoi8830kmLiScLZUCnGc)）。指标与车内同口径（安静≥98%、中速/高速关窗≥95%、误唤醒≤10h1次）。**实现方**：唤醒 火山+思必驰、降噪/音区 思必驰、识别 火山；产品 @左晨；客户端 @赵衍 10 人天、测试 @林满恕 5 人天。**状态**：规划中；SLS 9.30 提测、10 月合入主线；联调测试未通、提测失败，meego 7356970568（[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。

## 2.6 VAD（语音活动检测：Soft / Hard / 语义，多级 VAD）

**它做什么**：判断你这句话什么时候说完，直接决定延迟和准确率。例子：你说「导航去……」停了一下，Soft VAD 300ms 就抢跑请求云端，Hard VAD 500/600ms 二次确认，语义 VAD 发现你话没说完（「我想订一张去…上海的机票」）就再等你 1000ms。端侧调用思必驰 ASR 接口能力提供 VAD；端侧持续采音、200ms 一帧发云端（[多级VAD技术评审](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)、[多级VAD产品体验PRD](https://bytedance.larkoffice.com/wiki/FzViwCNb2iF43QkB5eDcD3D2nJh)）。

**关键规则**：抢跑范围只做 LLM 的「拒识/意图/简单复杂」预处理，**不抢跑到 FC/Planner/DM**；语义完整性定义暂不自研，先评测思必驰输出再定。预期收益：文本链路整体耗时减少约 200ms。**指标**：不设独立准确率指标（耗时优化项）。**实现方**：火山；服务端人力评估 2.5 人天；meego [6796681344](https://meego.larkoffice.com/telematics/story/detail/6796681344)。**已知问题**：方案一（extra 透传）有两个未解问题——①豆包已是两次请求，第二个会打断第一个，预请求可能没发到 AIDV 就被中断；②端侧「思考中」小云朵会因多次预请求反复横跳（[多级VAD技术评审·存在问题](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)）。

## 2.7 预请求（pre_query / Soft VAD 抢跑）

**它做什么**：Soft VAD 一触发，端侧先抢跑一个前置无状态任务，把拒识/意图/简单复杂仲裁的结果提前算好；正式请求来了如果和预请求一模一样，直接复用，省 ~200ms。例子：Soft 300ms 截到「播放音乐」先跑了一遍拒识，Hard 500ms 确认还是「播放音乐」，就不重算。预请求走 **POST /aidv/v1/pre_query**，**不进正式对话历史**；Redis 缓存 key 为 pre_query:{module}:{channel}:{chat_id}:{request_id}:{round_id}，只缓存 intent_and_refusal，缓存 2min（[多级VAD技术评审·接口与缓存](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)）。

**关键规则（复用条件很苛刻）**：必须 ①requestID 相同 且 ②正式 Query 与前一轮预请求 Query **完全相同**，两条件同时满足才复用，差一个字就正式重算。方案演进：方案二（改豆包文本链路）被否（侵入大、signal 固定=1）；推荐方案三——端侧 ASR 预请求直接 HTTP 对接 AIDV，**预请求流量不过豆包**。实现方火山，端侧对接 @任少东（SectionID）、客户端 @赵衍。**排查信号**：对比同一 request_id 下 round_id 的 Soft 文本与 Hard 文本是否一致、query_type=2 与 1 的 content 是否一致（[链路OnePager·名词表](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

## 2.8 在线 ASR（火山流式 2.0）

**它做什么**：把车端上送的音频实时转成文字，结果流式上屏。例子：「导航去 yunhe」，系统按你所在区域动态加权——在浙江丽水识别成「云和」，在黑龙江大兴安岭识别成「云河」。模型 = 豆包流式语音识别模型 2.0-小时版；热词在建联和上行时注入，**热词不会 100% 生效**（[链路OnePager·当前使用资源](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

**指标**：PRD 要求首字延迟 ≤200ms、尾字 ≤500ms、安静句准 ≥95%/嘈杂 ≥90%；量产按场景拆（车控 95/90、导航媒体 92/88、通讯 94/90、闲聊百科 90/85、车书 92/88）。**实测**（2025/12/25 安静驻车 Pad）：思必驰在线（old 接口）Overall WER 3.39、ACC 79.39%，首字 P50 576ms（明显超 <300ms 预期）；出厂检查点状态 Fail，「最新测试结果 86.99%，未达标，思必驰继续优化」（[ASR测试报告](https://bytedance.larkoffice.com/wiki/AeYjwYhOqi3FCYkpbqNc9FFAnsh)、[出厂检查点](https://bytedance.larkoffice.com/wiki/Ur3Zwu4LMiqatwk4xrScTwYMntV)）。**实现方**：火山；产品 @左晨（AIVA 台账 owner @张嘉锋）；meego [火山ASR FC开关测试](https://meego.larkoffice.com/telematics/story/detail/6892853512)、[RAG+context实验](https://meego.larkoffice.com/telematics/story/detail/7034898018)。

## 2.9 离线 ASR（思必驰 / 豆包离线双方案）

**它做什么**：没网或弱网时兜底。离在线仲裁规则：上屏先流式上离线，最终用在线 ASR 的 final 刷新屏幕；完全无网才全程用离线。双路线：思必驰离线用于 DNA1.0（26年8月SOP）、2B lite；火山（豆包输入法）离线用于 SLS（26年12月SOP）、2B pro——即早期/轻量版走思必驰，SLS/高配切豆包（[FeatureList双行](https://bytedance.larkoffice.com/sheets/PHXzs0YEmhomVQtvpcbcdsXqneg)）。

**实测**：思必驰离线 Overall WER 7.67、**句准严格 60.99%**，导航句准仅 41.93%；豆包复测 Overall WER 1.61、句准 89.81%，但首字 P50 432ms/P90 656ms（准但慢，端侧算力受限）。车控词错例：副驾(负价)、后排(后台)、除雾(储物)、座椅(做一)、ACC(accc)、超充桩(超充装)（[ASR测试报告](https://bytedance.larkoffice.com/wiki/AeYjwYhOqi3FCYkpbqNc9FFAnsh)）。**已知问题**：有网时偶发切到离线 ASR 导致后续推理全错（上汽必解 r5，@刘晓帝）；历史上离线 ASR 出过两次问题（一次交互策略、一次云端鉴权），目前看都已解决（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。产品 @左晨。

## 2.10 二遍 ASR（流式二遍 / 方言二遍）

**它做什么**：一遍追求低延迟、方言弱；二遍在分句后用非流式模型重识别给出 final，侧重高精度，保障方言和强口音。覆盖粤语、上海话、闽南语，及陕西、山西、江淮、四川强口音；粤语 CER 约 7%，二遍整体 CER 稳定 7%~10%。二遍 final 用于正式 Query。实现方火山（字节内部 ASR，推断）；本批资料无独立排期/meego（[车内语音PRD·方言识别](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）。

PRD 要求热词总量至少 3000 个；可见即可说性能 ≤1000ms。详细回流方案在《热词数据回流管理技术方案》——**该文档无权限（3380004）**，冷热处理、回流管线细节未读到，进未读清单（[热词回流方案（无权限）](https://bytedance.larkoffice.com/wiki/IMpVw1X28iDRUnkb7gUc70JYnEc)）。

## 2.12 拒识（AI介入判断 / 非人机拒识）

**它做什么**：判断这句话是不是在跟车机说话。例子：副驾说「等会儿我跟主驾说」、主驾答「好的再开一会儿」——这是人人对话，车机不该插嘴。要在「过拒（该答不答）」和「漏拒（不该答却答）」之间找平衡。对外叫「AI介入判断」，需求管理里叫「非人机拒识」（[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。

**关键规则**：**流式拒识**基于 partial 文本提前打断 TTS，触发前提四条同时满足——①多人场景 ②ASR>2 字 ③ASR 前缀不含「豆包」 ④TTS 正在播放；**最终拒识**基于 final query，用于正式链路与打断恢复。强召回：指令里出现唤醒词及其泛化（如「豆包」）强制召回；强拒识：摄像头识别到某音区用户手持手机打电话，该音区任何指令不响应。单人不拒识：车内单人时 ASR>2 字直接打断 TTS（SingleInterrupt），不做拒识判断。「唤醒后 5s 内同音区首句不拒识」：[Smoke 必过集 20261013 发版子表](https://bytedance.larkoffice.com/wiki/D8Cmwf3UlitqZ5kVwfTcsJ5PnLh)有用例原文（关闭单人不拒识开关和免唤醒后：唤醒 → 5s 内同音区首句「大明你去哪儿玩了昨天」应被召回 → 第二句「拒识的话」被拒识 → 第三句「介绍北京」再召回；结果 Pass）——**用例规格支持，完整实现机制未核验**；同子表「开启免唤醒」用例还确认存在「高相似 query 硬召回逻辑」（低于 3 字不走硬召回、非同音区不走硬召回）。「四合一」对应台账备注「8月底完成流式四合一实验」（CAE-CT-010），推断指流式链路里拒识与意图等模块合一的流式模型（[链路OnePager·名词表/打断场景表](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

**指标**：端云综合拒识准确率目标 **90%**（到 2026-02-06，是年底目标而非现状）；拒识模型输入 3600 token/输出 4，流式拒识 2000/3；拒识全流程 210ms。**实现方**：火山；产品——在线拒识 @张嘉锋、离线拒识 @左晨；PM @李浩然。**状态**：CAE-CT-010 待优化，「主线尚无或不完整，需要评审需求并排期开发」；路测误召回率太高（人人对话被响应、座椅按摩给你打开了）。**已知问题**：meego 7360101634「拒识偶发模型推理超时，正常 query 被误拒识不执行」（已关闭）；拒识 OnePager 本体无权限（[服务端AIDV](https://bytedance.larkoffice.com/wiki/SwaPwKLkNiKDdekvvp5cWwybntb)、[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。

## 2.13 离在线仲裁

**它做什么**：决定这句话走端侧还是云端。例子：车没网了，说「打开空调」走端侧白名单立刻执行；说「我有点冷」（feel 意图）即使端侧能判，也必须等云端——因为云端要按端状态用 Planner 决定是调空调还是反问。规则：无网强离线；网络正常时端云并行，离线命中白名单立刻执行，未命中则等云端，**2 秒内无心跳端侧兜底**；离线理解不了播兜底话术「没有网络时，我只能支持一些基础功能」。白名单入选两条：①无需情景信息即可判断准确意图 ②在线 ASR 识别效果会更好；白名单含通讯录、U 盘/蓝牙音乐、基础控制、地图缩放、倒车影像等（[离在线仲裁PRD](https://bytedance.larkoffice.com/docx/Nvj1dvkl8oOTAhxOjxAc0bn0nS0)）。

**为什么常规车控不进白名单**（PRD 删除线保留的争论）：①要结合多模态做综合理解（大夏天说「打开座椅加热」应反问是否想通风；后排上车说空调调最低要考虑记忆模块里副驾感冒）；②规则穷举不完。**负责人**：PRD @左晨（v0.1 2025-09-15 已评审），研发 @赵衍、测试 @崔思远；2025.11.3 双周报标注已完成（[双周报2025.11.3](https://bytedance.larkoffice.com/wiki/AQEqwvOu2izkzPkrtThcXaDInf0)）。

## 2.14 离线指令解析（含离线拒识、离线缓存）

**它做什么**：没网时本地把指令解析成动作。例子：「导航回家」命中缓存 50ms 内执行。支持范围：车控（空调/座椅/灯光/车窗/雨刮）、系统控制（音量/亮度）、导航、媒体、通讯录、应用开关；不支持实时路况、在线音乐、闲聊。离线指令缓存三原则：单轮解析、上下文无关（「就选它了」不入缓存）、结果唯一。目标：离线响应 ≤200ms、日常场景准确率 ≥95%、缓存命中准确率 100%/响应 50ms。实测离线 LLM（OrinX）准确率 90.42%、P99 427ms（[离线LLM指令解析PRD](https://bytedance.larkoffice.com/docx/YT3pd4wahoa0rZxgZcacoadqnPb)）。产品 @左晨，研发 @张松龙；1 期链路已打通（S03）。

## 2.15 豆包云（入口能力）

**它做什么**：文本对话的入口安检。前置动作：SharkTask（环境风控）、AliceSharkTask（是否封禁）、LocationTask（取地理位置）、UserInputReviewTask（同步安审）；后置：NoBreakAction（判断是否不应被打断）、RiskReplyItemTransformer（响应内容风控）。**打断判定规则**：同一账号同一会话，后到的 query 打断前面未处理完的 query；**车机场景下被拒识的 query 不参与打断判定**（[技术架构](https://bytedance.larkoffice.com/docx/SupzdFrzjoXqhpxiYevcGsO0nXb)、[端云链路OnePage·打断](https://bytedance.larkoffice.com/wiki/DBRnwrLFNiPxV5kZZOXcBYxqnCl)）。实现方豆包云自研。

## 2.16 AIDV 各模块（Gateway / Flow / 句法RAG / 分类拒识 / Planner / Context / Agents / TTS / 触发器 / Frontier / Advisor）

**Gateway**：承接 HTTP/RPC/豆包入口，协议转换、鉴权、路由，10ms。**Flow**：主链路分流，决定走规则快路径、Director、主动链路还是拒识/仲裁，10ms。两条快路径：**句法 RAG**（syntax_match/JSGF 规则匹配，命中跳 Planner，5ms）和**分类拒识**（拒识判定+简单/复杂分类，简单 case 跳 Planner，前置 200ms）。主动回流机制：云端建议经 Frontier 下发车端 → 车端带推荐标识再次请求 AIDV → 恢复建议来源上下文再处理（[服务端AIDV](https://bytedance.larkoffice.com/wiki/SwaPwKLkNiKDdekvvp5cWwybntb)）。

**Context**：端侧上报数据/事件的存储检索。上下文源：aibox 多模态情景、事件日志、短期历史压缩、短/长期情景记忆、长期语义记忆（偏好）、用户画像、端状态、联网基本信息。演进：V1「写入-粗筛-精筛」P90 实际 1.2s；V2「预注入+动态检索」——预注入覆盖约 80% 常规请求，动态检索兜底约 20% 复杂请求，P90 564ms。端云 Context 同步：端侧本地命中后通过 context/sync 上报 Query/Answer/Observation，按 requestID 写历史（[Context OnePage](https://bytedance.larkoffice.com/wiki/OjGMwBX8fiLS0ikDWqVceVjhnPg)）。服务端 @向超然、@高军；产品 @吴仁杰。

**Planner/Director**：任务编排中枢。基于 cloudwego/eino 的 ReAct 图；入口 DoPlan 在 Flow 编排里被**预启动**，句法RAG/简单意图/推荐回流/拒识一旦命中，预启动的 Planner 被直接取消。模型每轮输出严格 JSON（talk_or_not/talk_content/emoji_id/action_list/goal_list_update）。打断：keepCheckShouldBreak 每 100ms 轮询新 query，首 token 前允许打断。TTS 打断续说：优先按逐字打轴 WordTimestamp 切已播/未播，缺打轴按 100ms/字估算，拼成「已播内容（这里被用户打断了，后面没说完：未播内容）」作为下一轮 last_talk_content。基模 2.1-turbo；在研方案：精简 SP（约 5000 token）+ 后训练模型（现 SP 未填变量约 38000 token）。耗时：Director 首字 1300ms、本轮完成 1800ms（[Planner OnePage](https://bytedance.larkoffice.com/wiki/EWziwFVftiGvnlk0FA4cadqonud)）。产品 @郝晓伟，PM @李浩然。

**Agent Server**：注册管理四类 Agent（自建、ToB、豆包/一方、三方）；Executor 类型：AIDV 内置(0)、DPFM 车控(1)、Doubao 内容搜索(2)、Ecology 三方(3)、Offline 端侧离线(4，虚拟 Agent 不进 Planner)、InternalRPC(5)。10ms。下游合作方 Extour：AI Navi 导航、Advisor 建议/目标管理（[服务端AIDV](https://bytedance.larkoffice.com/wiki/SwaPwKLkNiKDdekvvp5cWwybntb)）。

**Frontier**：云端→端侧下发通道，主要下发车控指令、主动推荐的 id 与建议文本，低于 30ms（经验值）。**Advisor/Task Service**：状态感知类主动推荐的建议文本生成、长时任务目标管理；新版 Task Service 当前限定赛力斯。**触发器**见第 3 章专项。

## 2.17 TTS（SAMI 温柔桃子 / 情绪标签 / S2S 唱歌 / tts_audio_id 拉流 / 离线 TTS）

**它做什么**：把 Planner 生成的文本合成声音播给你。例子：Planner 输出「[高兴的说]好嘞，马上给你唱首中文歌。[唱]丑八怪」——方括号是情绪标签，TTS 按它拆段合成；含「唱」就积攒文本改走 S2S 唱歌。音色 Speaker = **zh_female_wenroutaozi_uranus_bigtts**（「温柔桃子」，BigTTS）；App Key jY2ghtW7SIW7XxqU；资源 QPS 50、并发 300。tts_audio_id 拉流：云端生成回复时携带标识下发，端侧经 TTS WSS 独立拉音频分片、边取边播，不等整段合成完（[链路OnePager·TTS处理](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

**离在线 TTS 策略**（PRD v1.3）：在线 = 网络正常且无大量波动；离线 = 无网 OR 网络波动大 OR 在线 ASR 本次异常 OR 未登录豆包账号；明确**不做**在线合成中断后的离线断点续播。缓存仅缓存在线音频：预置 ≤500 条高频文案、动态 ≤1500 条。播报优先级：其他紧急语音1 > 智驾语音 > 主动语音对话 > 紧急语音2/场景对话2 > 场景对话3 > 普通语音——**主动语音对话排第 3 级，高优先级可打断低优先级，你做触发器主动播报要预期自己随时被打断**（[离在线车载TTS PRD](https://bytedance.larkoffice.com/wiki/KlRgwueVKipbeLkdzkGcO15inKh)）。

**指标**：requestId 拉 TTS 首包 P50 70ms/P90 80ms；在线 TTS 情感化合成 avg 300-350ms；离在线 TTS PRD 目标离线缓存 <100ms、离线 TTS <300ms、在线 <500ms。**实现方/负责人**：在线 TTS 火山、产品 @陈西钺；离线 TTS 思必驰、产品 @左晨；TTS 研发 @汪帅。**已知问题**：**离线音色不是桃子**——未找到与桃子相似的发音人，离线（思必驰）与在线（火山）算法提供方不同，音色和离在线切换有重大体验问题；离线桃子音频数据依赖 luyou 提供给思必驰，暂无进展（[主线规划·核心依赖风险](https://bytedance.larkoffice.com/sheets/H1o4sLeJNhVGpJtwEHncJlYLnzh)、[双周报2025.11.3](https://bytedance.larkoffice.com/wiki/AQEqwvOu2izkzPkrtThcXaDInf0)）。

## 2.18 打断恢复

**它做什么**：TTS 播到一半你开口说话，系统智能停播、识别后决定续播还是播新内容。例子：车机正说「……剩下的话是：帮你把座椅调到24度」，你插了一句「先别调」，系统要判断这句是拒识还是召回。SDK 事件级恢复分流：10 种打断事件里只有 3 种要恢复——NotRejectQuery（收到云端未拒识消息）、StreamNotRefusal（流式非拒识停播）、MultiPersonSayStartWithDoubao（多人时以「豆包」开头立即打断）。两种恢复方式：当前 query 最终拒识 → 用 Event 触发恢复上一条未播 pcm（Event 示例：「副驾（小王）和其他人说话，打断了你正在说的话……」）；当前 query 未拒识（Recall）→ Planner 把「新 query + 上一条未播内容」融合生成新 NLG，恢复时结合 TTS 打轴定位未播段（[链路OnePager·打断恢复](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

**版本演进**：2.6 版（非拒识+非简单车控立刻停播，1.5s 窗口）→ 二月底演示实验版（ASR>2 字立即打断，拒识→缓存 pcm 后续播，新增默认关闭的「声学打断」开关）→ 长期 SOP 待定。多人同时交互排队规则：控制+文本排队等控制播完再播文本；文本+文本后面打断前面。**负责人**：打断策略 PRD @左晨，VUI 主交互 @徐洋，PM @李浩然，测试 @熊柳立。**已知问题**（群聊真实反馈）：「TTS 被打断但没有新 query 播出来」——拒识 recall 后研发就触发 NLG 打断，但 Planner 存在 recall 了却判断不输出 NLG（简单指令 talkornot=no）的情况；「豆包豆包」应打断却 Fail（打断测试集）；卡片已有内容被打断后还继续说（[体验优化策略群聊](https://bytedance.larkoffice.com/wiki/AzAxwFNJtiy9Rak1NVgcgD9an7f)、[TTS打断测试集](https://bytedance.larkoffice.com/wiki/BGA5w7AYLiJ0GSkqXyuc05nAnnh)）。

## 2.19 全时免唤醒（always on）

**它做什么**：不喊「豆包豆包」，全车 4 音区随时跟车机说话。例子：主驾说「有点冷」，车机直接响应不用唤醒。开关在系统设置 AI 伙伴（暂定名「陪伴模式」），默认开启；按座椅传感器+Face id 判断位置有人，无人音区不开启。连续对话态：召回后激活 30 秒，30 秒内无效文本退回未激活，任意有效指令重新倒计时。上下文继承：对多轮拒识指令做话题分类总结（8 类话题），每 5 轮一次总结，召回时把前 5 个话题总结作为上文补充。高风险指令二次确认：关 ESP、关自动驾驶、解儿童锁、支付停车费 15 元仅主驾或二次确认（[全时免唤醒PRD](https://bytedance.larkoffice.com/wiki/W7kxwMqwmitpjSkv9BAcakO1nSR)）。

**指标**：固定范围识别准确率 ≥95%；实现方火山，CAE-CT-008，Pre-PC 阀，产品 @左晨。**状态**：待优化，通过率 <50%，「不通，拒识升降级也不通」，1013 已优化合入（[AIVA高优表](https://bytedance.larkoffice.com/wiki/Tp70wuM9YijpZ1kj8pJcgPXKnib)）。

## 2.20 多音区同时交互（4 音区同时说话）

**它做什么**：车里四个人同时跟车机说话。例子：主驾说「打开车窗」、副驾说「我要导航回家」——系统合并成「主驾驶说'打开车窗'，副驾驶说'我要导航回家'」交给 Planner 统一处理。合并上限暂定 4 个，仅合并有效指令；指令冲突（一开窗一关窗）Planner 应优先澄清。指标：2 人字准 ≥93%/句 ≥90%；3 人 88%/85%；4 人 83%/80%。**硬依赖**：高通 8397 及同等级算力芯片，低配车型做不了（[多人同时交互PRD](https://bytedance.larkoffice.com/wiki/U4xLwmQNki1Pu5kpyAGcHWtmngf)、[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。

## 2.21 端云 Context 同步

**它做什么**：端侧本地命中（可见即可说/简单车控）后，要把执行结果、回复话术回传云端，保证端云对话历史一致。例子：副驾在端侧说「打开车窗」本地直接执行了，云端不知道，下一轮多轮对话就接不上。机制：端侧通过 context/sync 上报 Query、Answer、Observation，按 requestID 写历史（[链路OnePager·端云上下文一致](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)）。

触发器的输入是语音链路/端状态的产物，输出大多要回语音链路执行。具体交叉：

1. **输入源**：触发器监测「车辆端状态、视觉感知结果、云端时间计划、推理结果」；其中端状态就是客户端 vehicle_control 上报、经 AIDV 维护的情境数据底座，sls 信号库（vehicle_control_xxxx / navigation_xxxx / media_xxxx）就是可被配置为触发条件的信号白名单（[触发器OnePage](https://bytedance.larkoffice.com/wiki/Xk6xwM3l8iK4oCkXIMlcIo4hnFc)）。

# 4. Badcase 根因四分类

你排查问题时先问：这个 badcase 是哪一类？四类根因——**A 规则设计缺陷 / B 端侧资源限制 / C 大模型输出不稳定 / D 软硬件时序冲突**。每类先讲为什么发生，再给语音链路真实案例（带 meego 单或来源），最后给排查信号。**注意：四个分类只是排查方向，归类不代表每个案例的根因已被证实**；根因未确认的案例，文中以「【已记录现象】…【排查假设】…根因未确认」标出。

## 4.1 A 类：规则设计缺陷

**为什么发生**：规则写得太死、阈值没校准、两个模块的规则没对齐，导致正常用户被错误处理。

- **TTS 被打断但没有新 query 播出来**：拒识 recall 后研发就触发 NLG 打断，但 Planner 存在 recall 了却判断不输出 NLG（简单指令 talkornot=no）——打断规则与 Planner 输出规则没对齐。排查：看打断事件（StreamNotRefusal/NotRejectQuery）后是否有新 TTS requestId；查 Planner 输出的 talk_or_not（[体验优化群聊](https://bytedance.larkoffice.com/wiki/AzAxwFNJtiy9Rak1NVgcgD9an7f)）。
- **抢跑失败/文本不一致重算**：300ms Soft 把「播放音乐」识别成「播放音月」并提前请求 LLM，可能被误拒识，500ms Hard 才纠对。排查：对比同一 request_id 下 round_id 的 Soft 与 Hard 文本（[多级VAD PRD 场景二](https://bytedance.larkoffice.com/wiki/FzViwCNb2iF43QkB5eDcD3D2nJh)）。
- **预请求复用条件过严**：正式 Query 与预请求 Query 必须完全相同才复用，差一个字就重算，200ms 收益拿不到。排查：Redis key pre_query:{module}:{channel}:{chat_id}:{request_id}:{round_id} 是否命中（[多级VAD技术评审](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)）。
- **误唤醒**：「小豆包小豆包」「老豆包老豆包」「打包两个豆包」都能唤醒；主驾说「豆包」后副驾马上说「豆包」也能唤醒（预期不应唤醒）。排查：唤醒日志触发来源标记（[上汽Badcase表](https://bytedance.larkoffice.com/base/ZVlUb9tbcabDDzstcoyc2xAxnKf)）。
- **DM feedback 错误**：吸顶屏实际已成功关闭，仍播报「不能操作」——只发了指令就播报失败，没等车端执行确认。排查：车控执行反馈 VehCtrlRes 是否回传（[AIVA高优表·车控行](https://bytedance.larkoffice.com/wiki/Tp70wuM9YijpZ1kj8pJcgPXKnib)）。
- **触发器被执行策略误拦**：exceed by power count / exceed by exceeds interval。排查：触发记录执行结果字段、上电周期计数、执行间隔（默认 30s）（[触发器OnePage](https://bytedance.larkoffice.com/wiki/Xk6xwM3l8iK4oCkXIMlcIo4hnFc)）。

## 4.2 B 类：端侧资源限制

**为什么发生**：车机芯片算力、内存、SDK 版本、硬件标定周期卡着算法上限，云端再强也落不到端上。

- **豆包离线首字延迟差**：WER 仅 1.61（准）但首字 P50 432ms/P90 656ms（慢），端侧推理算力受限。排查：端侧 ASR 首字 P50/P90、CPU/MEM 占用（[ASR测试报告](https://bytedance.larkoffice.com/wiki/AeYjwYhOqi3FCYkpbqNc9FFAnsh)）。
- **多路同时交互算力依赖**：4 音区同时交互要求高通 8397 及同等级芯片；多人字准随人数下降（两人 93%→三人 88%→四人 83%）。排查：芯片平台型号（[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。
- **没有稳定联调环境**：上汽 8295 台架 10 月底才到；北京 8155 算力不够；只能去上海用 8775（非目标芯片、晚 9 点后才轮到）；思必驰符合预期的 SDK 版本最终 1 月才提供，期间临时用云知声旧 SDK。排查：台架/芯片/SDK 版本记录（[主线规划·依赖风险](https://bytedance.larkoffice.com/sheets/H1o4sLeJNhVGpJtwEHncJlYLnzh)）。
- **离线 TTS 音色问题**：没找到与桃子相似的发音人，离线（思必驰）与在线（火山）提供方不同。排查：播报音色是在线还是离线通道、TTS requestId 来源（[双周报2025.11.3](https://bytedance.larkoffice.com/wiki/AQEqwvOu2izkzPkrtThcXaDInf0)）。
- **声学标定 2 个月硬周期**：唤醒/降噪/音区/离线 ASR 全挂在「8/30 半工装→9/25 功放锁定→11/6 标定」硬件链上。排查：当前半工装还是量产硬件、功放版本（[AIVA需求台账](https://bytedance.larkoffice.com/wiki/EOQQwWRQ3ig56OkuQx4c3qYrnOg)）。

## 4.3 C 类：大模型输出不稳定

**为什么发生**：同一类 query，模型这次答对下次答错；推理超时、拒识波动、工具返回空时不知道怎么续。

- **【已记录现象】偶现拒识模型推理超时，正常 query 被误拒识、不执行**（meego 7360101634，已关闭）。【排查假设】疑似拒识模型或服务耗时超限（原始问题描述写的是「模型或服务超时」，模型与服务未区分）；**根因未确认**，归入 C 类只是排查方向。排查：拒识模型耗时（210ms 基线）是否超时；Fornax trace 看拒识 span；query 是否被误判 rejection=true（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。
- **「只说不做」体验差**：上一轮工具无返回结果后 Director 不知道如何继续，承接「要我导航过去吗」却不执行，左晓杰认为这是当前最突出体验问题。排查：工具返回空时 Director 后续动作；Fornax Trace 里 answer_source 字段（[体验优化群聊](https://bytedance.larkoffice.com/wiki/AzAxwFNJtiy9Rak1NVgcgD9an7f)）。
- **拒识效果波动**：张航反馈「刚才的拒识特别差」；再喊一遍有时 ASR 不好系统招不回来；唤醒词会上屏被当成 query。排查：拒识模型输入文本、流式 partial vs 最终 final 是否一致；按体验时间段回溯日志（[体验优化群聊](https://bytedance.larkoffice.com/wiki/AzAxwFNJtiy9Rak1NVgcgD9an7f)）。
- **ASR 误识别连带错误**：副驾说「没网了」识别成「我累了」，把副驾座椅往后调了。排查：上屏文本与真实意图对比（[路测问题](https://bytedance.larkoffice.com/wiki/Tp70wuM9YijpZ1kj8pJcgPXKnib)）。
- **S2S 联网类 badcase**：纯文本接入的 S2S 对联网意图识别差，Speech 侧新功能不支持文本接入。排查：S2S 走文本还是音频链路（[技术架构·当前链路问题](https://bytedance.larkoffice.com/docx/SupzdFrzjoXqhpxiYevcGsO0nXb)）。

## 4.4 D 类：软硬件时序冲突

**为什么发生**：两个模块各自正确，但在毫秒级的时间窗里没对齐——谁先发、谁后到、谁等谁，差一点就出错。

- **有网时偶发切到离线 ASR**：识别错得离谱，后续推理全错。排查：离在线仲裁日志；有网为何走了离线；ASR 来源标记（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。
- **【已记录现象】车辆网络正常时偶发端云链路异常断开，豆包不回复、无 TTS 播报**（meego 7358394587，已关闭）；另有一例「服务端正常回复但客户端没播放任何信息」（meego 7358795548，已解决）。【排查假设】疑似 WS 长链异常断开或端云时序未对齐；**根因未确认**，归入 D 类只是排查方向。排查：WS 长链连接状态、request_id/round_id 是否对齐、TTS 拉流是否拿到、客户端播放焦点（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。
- **【已记录现象】动态车辆状态下音频分离错误，主驾说话被识别成主驾+副驾**（0715 路试两例：13:42、14:30「我要去上个厕所」；处置=使用新版思必驰新资源复测，已解决，@任少东；meego 7359234801、7359284840）。【排查假设】方向是思必驰音区分离算法模块效果（备注：最新版本测试仍不达标、可能需加工程策略）；**根因未确认**，归入 D 类只是排查方向，需提供实车音频给思必驰系统分析。排查：sound_zone 字段、音区合并 sound_zone_merge（[上汽量产事项](https://bytedance.larkoffice.com/sheets/IElLs7N8yhgXnRt8bmxcRj4dnwd)）。
- **TTS 低概率开头几个字爆破音**（赵衍备注）。排查：TTS 首帧、音频分片边界、传输抖动。
- **预请求被第二次请求打断**：豆包已是两次请求，第二个打断第一个，预请求可能没发到 AIDV 就被中断。排查：AIDV pre_query 接口是否收到完整请求、round_id 是否连续（[多级VAD技术评审](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)）。
- **豆包把自己 TTS 播报的声音再次收录进去**：自唤醒、断断续续（P0）。排查：AEC 参考音路数是否=4、TTS 打轴对齐日志；注意 0520 台架那例是台架没有声学标定/回声消除，属正常（DNA-1188，不需解决）——先分台架还是实车（[上汽Badcase表](https://bytedance.larkoffice.com/base/ZVlUb9tbcabDDzstcoyc2xAxnKf)）。

# 5. 跨团队评审沟通话术

你会遇到的问题：评审会上不敢提问题、提了也被一句「就这样定的」挡回来。方法是**质疑话术 + 举证逻辑（现象 → 数据 → 影响 → 诉求）**，全部用资料里的真实例子。按场景给你。

## 5.1 PRD 评审场景

- **针对「唤醒抑制」**：「PRD 第 X 条要求车外唤醒抑制并弹 Toast，但 callout 里写『唤醒抑制能力，供应商不支持』。现象：车外人对玻璃喊「豆包豆包」现在会唤醒；数据：出厂检查点唤醒抑制成功率要求 ≥95%，供应商不支持意味着这个指标无法验收；影响：PRD 写了做不到的功能，量产时要扯皮。诉求：要么在 PRD 里删掉这条、改成供应商路线图承诺，要么明确降级方案（不弹 Toast，改用视觉反馈）。」（[车内语音PRD·唤醒抑制](https://bytedance.larkoffice.com/docx/NOD0dz79VoonPjxkhbzcf6V2nWe)）
- **针对「离线音色不是桃子」**：「在线 TTS 是温柔桃子，离线 TTS 是思必驰另一个发音人。现象：车没网时说『打开车窗』，播出来的声音突然变了一个人；数据：规划里写『未找到与桃子相似发音人，离在线切换有重大体验问题』；影响：用户在隧道里丢网，体验断裂。诉求：明确离在线音色一致性是哪个版本的验收项，luyou 桃子音频数据给思必驰的时间表谁推动。」（[主线规划·核心依赖风险](https://bytedance.larkoffice.com/sheets/H1o4sLeJNhVGpJtwEHncJlYLnzh)）
- **针对「预请求复用条件」**：「复用要求正式 Query 与预请求 Query 完全相同。现象：用户说『播放音乐』，Soft 截成『播放音月』，Hard 纠回『播放音乐』，差一个字就不能复用，200ms 收益泡汤；数据：方案三改成『最短路径匹配』就是为了提高 Soft 命中率；影响：多级 VAD 省 200ms 的目标在抢跑失败案例上拿不到。诉求：PRD 里把『完全相同』的判定规则改成最短路径匹配的判定，并写清命中率预期。」（[多级VAD PRD](https://bytedance.larkoffice.com/wiki/FzViwCNb2iF43QkB5eDcD3D2nJh)）
- **针对「常规车控不进离线白名单」**：「PRD 删除线写着：大夏天说『打开座椅加热』应反问、副驾感冒时不应被调空调温度。现象：这正是要端侧快速响应的高频车控却被排除白名单；影响：车控车设 1000ms 的目标在复杂场景达不到。诉求：白名单 vs 云端兜底的边界要按车型给出明确清单，不能只停在『规则穷举不完』。」（[离在线仲裁PRD·删除线callout](https://bytedance.larkoffice.com/docx/Nvj1dvkl8oOTAhxOjxAc0bn0nS0)）

## 5.2 技术方案评审场景

- **针对 Hard VAD 口径**：「现行 OnePager 写 Hard VAD 600ms 结束 ASR，多级 VAD PRD 写 Hard 500ms + 语义 VAD 1000ms，PRD 自己注明『暂定，随实车体验后可变更』。现象：两个文档同一参数两个值；数据：VAD 600ms 是时延基线里最前头的固定大头；影响：按 500ms 做的方案上线后到底按哪个生效，没人确认。诉求：当场找算法（@任少东）确认生效值，写进技术方案，更新 OnePager。」（[链路OnePager](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)、[多级VAD PRD](https://bytedance.larkoffice.com/wiki/FzViwCNb2iF43QkB5eDcD3D2nJh)）
- **针对预请求方案一（extra 透传）**：「豆包已是两次请求，第二个会打断第一个，预请求可能没发到 AIDV 就被中断；而且端侧『思考中小云朵』会反复横跳。现象：方案一的两个未解问题在技术评审里摆着；影响：如果按方案一开发，抢跑请求半路被打断，收益归零还增加端侧 UI 抖动。诉求：明确按推荐的方案三（端侧直连 AIDV、预请求不过豆包）排期，方案一的两个问题要么解、要么放弃。」（[多级VAD技术评审·存在问题](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)）
- **针对打断恢复策略**：「拒识 recall 后研发就触发 NLG 打断，但 Planner 存在 recall 了却判断不输出 NLG（talkornot=no）的情况。现象：TTS 被打断了，却没有新内容播出来；影响：用户插了一句话，车机直接沉默，体感像卡了。诉求：打断事件后必须有『新 TTS requestId 或明确静默理由』的契约，写进端云协议。」（[体验优化群聊](https://bytedance.larkoffice.com/wiki/AzAxwFNJtiy9Rak1NVgcgD9an7f)）

# 6. 演进时间线（202509 → 202511 → 202607 → 自建链路）

<whiteboard token="Hk32wc1yVhBiUgbglCUc7UQWnYe"/>

为什么要自建（[自建平台化链路](https://bytedance.larkoffice.com/wiki/DxV9wY7jGiuNSdkg19XcNV8xnAe)）：①车机端用户几乎只有音视频一种用法，却需要车控、POI 导航、S2S 多类 Agent 能力融合；②车机端需要 Planner 调度多个 Agent 并汇总，当前 S2S/视频与主 Bot Agent 能力只能二选一；③RTC 通道要为多音区开多路，成本高。自建技术选型优先 QUIC（李鑫）；排期：vehicle.model.gateway 7PD、vehicle.model.aidv 18PD、vehicle.model.vlm_agent 7PD、端云联调 15PD，总计现有链路能力替换 39PD、链路替换+新增视频能力 46PD。

# 9. 术语表

每个术语一两句白话解释 + 例子。

- **AIDV**：AI Defined Vehicle，AI 汽车；这里指座舱云里的业务编排系统。例子：你说「导航回家」，Planner 就在 AIDV 里。
- **VAD / Soft / Hard / 语义 VAD**：判断用户什么时候说完。Soft 300ms 快速停顿判断、抢跑预请求；Hard 600/500ms 确认说完、触发音频分段；语义 VAD 1000ms 按句子完整性判断。例子：「我想订一张去…」停顿，语义 VAD 知道你没说完。
- **预请求 pre_query**：Soft VAD 后抢跑的前置无状态任务，走 /aidv/v1/pre_query，不进正式对话历史。
- **ASR / 流式 / 二遍**：语音转文字。流式=说话中持续返回 partial；二遍=分句后非流式模型重识别给 final，保障方言。
- **拒识**：判断这句话是不是在跟车机说话。例子：副驾跟主驾聊天，车机不该插嘴。
- **流式拒识 / 最终拒识**：前者基于 partial 提前打断 TTS，后者基于 final query 用于正式链路。
- **离在线仲裁**：决定走端侧还是云端。feel 意图（「我有点冷」）必须等云端。
- **Director / Planner**：同一个东西，任务编排中枢，理解需求、拆任务、调工具、组织回复。
- **Flow / 句法RAG / 分类拒识**：Flow 决定走哪条路；句法RAG 规则匹配命中即跳 Planner；分类拒识把简单 case 直接交 Agent。
- **Context / Memory**：当前场景信息组装（端状态/视觉/基础信息）；Memory=历史与偏好。
- **Agent / FC / Tool**：可被 Director 调用的能力单元；FC=Function Call 函数调用。
- **TTS / 打轴 / tts_audio_id**：文本转语音；打轴=音频与文本逐字对应关系；tts_audio_id=端侧凭标识拉音频流的编号。
- **S2S**：Speech-to-Speech 语音直出（超拟人对话模型）；当前文本接入，唱歌走 S2S。
- **打断恢复**：新 query 打断 TTS 后，判断要不要把没说完的话续播。
- **触发器 Trigger**：判断端状态/视觉/时间/推理条件是否满足，命中自动触发动作（你的模块）。
- **Advisor / Task / Goal**：主动推荐建议文本生成；Task=持续任务，Run=一次执行，Goal=长时目标。
- **Frontier**：云端→端侧下发通道，推车控指令和主动建议。
- **全时免唤醒 always on**：不喊唤醒词，4 音区随时交互。
- **多音区合并**：多人同时说话，合并成「主驾驶说X，副驾驶说Y」交 Planner。
- **sls 信号库**：场景感知状态信号库，触发器可配置的信号白名单（vehicle_control_xxxx / navigation_xxxx / media_xxxx）。
- **Fornax / Argos**：Fornax=Prompt 管理与链路 trace 调试；Argos=服务日志与耗时看板。
- **request_id / round_id**：request_id 是端云一次请求唯一标识；round_id 是同一 request_id 内的轮次，预请求每次递增。
- **ECNR**：降噪（NR）+ 回声消除（AEC/Echo Cancellation）合称。
- **声纹 / FaceID**：声纹=声音识别人是谁；FaceID=驾驶员人脸识别绑定账号。
- **OTS / S阀 / Pre-PC阀 / PC阀**：整车软件里程碑阀点；半工装=硬件位置已不变、用于声学标定的早期样车。
- **WER / ACC / CER**：WER=词错率（越低越好）；ACC/句准=整句准确率；CER=字错误率（方言二遍 7%~10%）。
- **TTFT / TTC**：首字响应耗时 / 本轮输出完成耗时。
- **MOQ / QUIC / Eino / ReAct**：豆包新音视频链路协议；自建链路选的全双工传输协议；字节 Go LLM 编排框架；推理-行动循环。
