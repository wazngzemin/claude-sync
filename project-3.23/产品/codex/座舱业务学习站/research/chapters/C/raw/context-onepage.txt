Context OnePage
背景介绍
Context 模块承担 AI 汽车项目全量上下文信息的管理职能，是决定 AI 智能体验上限的核心能力之一——AI 体验上限一靠模型能力，二靠上下文理解能力，这也是我们与竞品拉开体验差距的关键因素。
过去传统座舱系统是割裂的，AI 仅能感知用户的语音指令，无法知晓用户在车机其他界面的操作、车辆状态变化、舱内人员状态等信息，导致连续对话衔接性差、无法理解上下文场景，显得“很笨”。
Context 模块涵盖情景描述、瞬时记忆、短期记忆、长期情景记忆、长期语义记忆、用户画像、端状态、联网基本信息等核心内容，数据类型覆盖结构化数据、非结构化文本、多模态感知数据等多种形态。为此我们构建了一套公共 Context 服务，实现通用上下文的统一管理与维护，核心功能包含两大维度：
按照标准化结构完成上下文信息的存储、维护与查询，为 Planner、Advisor、Agent 等各类调用方提供高效数据支撑；
在海量繁杂的上下文数据中，精准且快速地定位当前业务场景所需信息，助力系统输出更贴合需求的应答内容。

整体架构
面对体量庞大、类型多样、结构各异的上下文数据，核心挑战是：如何在保证筛选准确率的前提下，最大限度提升检索效率，快速获取与当前场景高度匹配的有效信息。
V1：写入-粗筛-精筛三步式架构
最初设计了一套“写入-粗筛-精筛”三步式架构，覆盖从数据生产到最终消费的全链路：


阶段

作用

写入

对原始数据进行一次提取和锤炼，保证在后续处理流程中可以更好地使用该数据

粗筛

并行地对不同上下文源根据输入条件进行一次筛选，目的是尽可能包含与本次 query 相关的数据

精筛

基于粗筛出来的数据再进行一次更细致的筛选，保证返回的数据可以直接符合上游模块的使用需求

这套方案上线后，从线上数据和评测中发现两类问题：
各源筛选效果难以平衡：集中式架构通过单一模型对各模块筛选的数据统一过滤，为保障速度限制模型输出个数为 5 个，筛选结果存在明显位置偏好——靠前的数据更容易被放行；同一轮评测中，某一个源的准确率提升，势必导致另一个源的准确率降低。
速度不达标：为让 Planner 尽快回复，Context 模块设计目标为 P90 800ms，但实际 P90 耗时达到 1.2s；其中端状态筛选需要调用两次模型，是主要性能瓶颈。
V2（当前方案）：预注入 + 动态检索两阶段架构
针对 Planner 的使用场景，我们设计了全新的上下文管理链路：
链路重构、筛选权下放：重新划分每个上下文源的职责边界，确保各模块数据尽量无重叠；取消统一的精筛模块，将筛选逻辑的控制权完全下放给各个上下文源，由各源独立保障自身的筛选质量，从架构上解决数据源间效果不平衡的问题。
两阶段筛选拆分：将原有单一筛选过程拆分为预注入和动态检索两部分，构建“常用场景快速响应 + 复杂场景兜底覆盖”的分层处理机制。
预注入：进入 Planner 前的 Context 数据不再进行大范围召回，仅提供 Planner 在大多数情况下会用到的常用数据，可覆盖 80% 的常规用户请求，保障核心场景的极致响应速度；
动态检索：进入 Planner 调用逻辑后，由 Planner 判断当前上下文信息是否足以支撑处理用户请求——信息充足则直接回复并结束流程，否则调用检索工具按需精准检索所需数据，兜底覆盖剩余 20% 的复杂请求。
