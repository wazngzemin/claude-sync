00 · 先给你我的真实判断

你现在最缺的，既不是资料，也不是再写一份 Skill

你最缺的是一套“当前真相到执行结果”的闭环：做任务前，系统能取到当前车型、渠道、版本对应的事实；做任务中，每一层留下可查证据；做完后，用评测判定第一次偏离；最后只更新真正出错的那一层。
资料层你已经很多

近 30 天飞书、PRD、会议、Planner SP、114 条动态示例工作簿、74 条当前 prod 实测、Trigger DSL、Task 技术方案和历史评测都在。

真相层仍然分散

动态示例口径在 7 月到 8 月多次变化；上汽和赛力斯信号分开维护；WIP 方案与线上现状容易被混用。

反馈层证据不连续

“没触发”“没参考示例”“导航很慢”经常只有结果，没有同一 case 的分段输入、输出、日志和 Owner。

这篇文章对你的真正价值

作者说“图书馆加图书管理员”“技能文件”“潜空间和确定性空间”。放到你这里，它们分别对应三件很实在的事：

一，Context 和动态检索要找到当前任务真正需要的少量事实。二，A-F 分诊、L0-L6 介入和长时任务排查要写成第二个人也能执行的方法。三，距离、时间、媒体结束、任务状态这些精确条件要交给 Trigger、Task 和工具，不能让模型凭感觉猜。

01 · 先站在你今天的工位旁边看

你当前面对的，不是一个 Planner 问题，是八条系统链同时收口

过去一个月，你的工作已经从“把 Planner 回答修好”扩展成“让 Driver Agent 在车上稳定运行”。下面这些都在你的真实问题线程里，不是我为了套文章临时编出来的。

工作线你当前在处理什么真正卡住的地方文章能提供什么
Planner / Director理解 query、拆任务、调用工具、消费 feedback、给出回复。很多问题被笼统归到模型；输入是否齐全、首次偏离层和修复手段没有统一。把人的分诊判断写成可执行规则，并用 Eval 判卷。
公共 Context管理情景、历史对话、事件日志、端状态、用户记忆、任务状态等 13 类信息。资料多，任务真正该加载哪几条、是否过期、是否属于当前人物和车辆，仍是难点。“正确三本书”和图书管理员。
动态示例给当前 query 检索参考决策，帮助模型少走错路。114 条工作簿与 74 条当前 prod 实测是不同资产；召回、采用、通过和负向影响没有统一观测。把检索结果、模型采用和最终结果分层记录。
Task承接无法在当前轮完成、需要等待、持续或后续管理的任务。WIP 方案、当前实现和车上表现不能混为一谈；TaskSpec、Run 和结束条件缺少 case 级证据。把任务生命周期从自然语言中抽出来，形成可追踪对象。
Trigger / 信号中枢接状态、事件和条件，判断何时激活 Task。上汽与赛力斯信号分开维护；字段、单位、枚举、可订阅性和日志需要按渠道确认。精确条件进入确定性空间。
Advisor / VLM主动建议、视觉观察、语义判断和任务相关感知。历史“动态 Advisor”与较新 Task 方案容易混用；AlwaysOn Context 与动态高频任务是两条不同路径。先区分感知、判断、触发和用户决策，各层各留证据。
工具车控、音乐、导航、记忆、搜索等原子执行。意图边界、前置状态、失败返回、播报责任、测试入口和日志入口仍要统一成契约。确定性动作要有输入、输出和失败分支。
评测和交付动态示例实测、Planner badcase、性能口径、车企版本和演示。单点通过不能证明机制稳定；会议结论经常停在群聊，没有形成当前唯一口径。每次任务结束都回写事实、规则和回归结果。

今天最能说明问题的三条原始 case

到达语义“到了目的地提醒我”

实际被理解成距离目的地 10km 触发。这里可能先错在产品对“到了”没有唯一口径，也可能错在结构化条件。

数字条件“距终点 1km 提醒”

没有触发。这里要看 TaskSpec 是否保留 1000m、渠道距离字段是否上报、Trigger 是否注册并命中。

媒体事件“这首歌唱完就停”

没有执行。这里要先确认媒体结束事件是否存在并可订阅，再看回调和音乐控制工具。

证据边界

“定时触发相对可用，结合端状态的条件触发较差”来自近 3 天飞书原始消息。8 月 14 日或 17 日向 Alex 演示仍是计划，具体日期未锁定。今天相关会议可见日程，但没有可读纪要，因此不能把会议可能讨论的内容写成已拍板结论。

02 · 上一版混淆的关键

你要同时建设三套“脑”，但三套脑不能混成一个文件夹

哪套脑服务谁里面放什么怎样算好边界
车上运行脑司机、乘客和当前一轮 Agent 任务SP、工具、公共 Context、记忆、动态示例、Task、Trigger、VLM 结果。当前任务取到对的信息，能稳定做出动作，延迟与正确率达标。只加载当前任务需要的内容，不能把团队会议和历史争议塞进车上 Context。
团队交付脑你、研发、算法、端侧、车企和评审人当前方案、版本、Owner、接口、真实 payload、日志、评测、决策和未决项。任何人都能回答“现在到底是什么口径”，并能追溯来源。保留公司内部；历史证据与当前结论要分层。
个人职业脑未来的你脱敏后的分诊方法、需求挖掘问题、Eval 设计、会议收口方法和工具使用能力。换到机器人、企业 Agent 或 FDE 场景时，你能复用方法并快速重建行业真值。带走方法，不带走内部 Prompt、日志、客户字段和保密资料。
03 · 先把黑话讲到你能用

这些词第一次出现时，你应该立刻想到哪个工作模块

文章用词一句大白话你工作里的对应物最容易误解的地方
个人 AGI长期读你的资料、按你的规则做事、做完还能留下经验的 AI 工作系统。你的 Codex 工作流、近 30 天飞书上下文、本地产品资料、固定阅读规则和未来的诊断工具。它是作者给工作系统起的大名字，不能据此判断传统意义的 AGI 已被实现。
Context模型在这一轮真正看见的背景。车上的公共 Context 13 类内容；个人工作中是当前问题线程、今日消息、相关 PRD、case 和日志。文件存在硬盘里，不等于已进入 Context；进入 Context 也不等于模型一定正确使用。
正确的三本书做当前任务时，只拿最相关、最新、可信的少量资料。查长时任务时优先拿当前 Task 方案、当前渠道信号、该 case 的完整日志，旧版宏观架构放在后面。重点是选择规则，不是固定只能三份文档。
图书管理员决定什么有效、什么过期、两条冲突听谁、缺证据时怎样标记。车企、车型、环境、版本、来源、Owner、验证状态和冲突记录。它不只做搜索，还要维护当前真相和历史证据。
Skill一类任务的操作说明，写清输入、步骤、分支、输出和验收。A-F 分诊、L0-L6 介入、长时任务证据链、动态示例审查方法。自然语言 Skill 适合编排与判断；精确计算、权限和高风险动作仍需代码与系统保障。
Resolver收到任务后，决定调用哪项能力。在你的产品里，Planner/Director 负责理解和规划，Task 路由与具体服务再承接相应工作。Planner 和 Director 是同一功能的内外名称，不能画成两个串行大脑。
潜空间允许模型根据语义和经验做概率判断的地方。理解“到了提醒我”的用户意图；判断 VLM 描述是否代表宝宝在哭；生成合适话术。概率判断会波动，需要 Eval 和必要的澄清。
确定性空间同样输入应该得到同样结果的规则和程序。10 分钟计时、距离小于等于 1000 米、媒体结束事件、Task 生命周期、工具执行。模型可以生成条件，但条件是否达成要看真实信号和规则。
技能化任务做完后，把有效步骤和新例外写回方法。查完“距终点 1km”后，新增渠道字段、单位、日志入口和一条回归 case。技能化不等于把本次聊天原样存档；必须提炼出下次可执行的变化。
复利第二次处理同类问题时，至少少走一步或多一份可靠证据。下条 Trigger badcase 自动拉齐七段日志；动态示例改动能自动看到召回、采用和负向影响。文件数量增加不算复利。坏规则被反复调用会形成负复利。
04 · 八段逐段陪读

每段都回答五件事：作者说什么、什么意思、前提是什么、落到哪、你要改什么

第一段：作者为什么说“个人 AGI 已经来了”

原文主张：人们还在等待某次 AGI 发布，Garry Tan 认为它已经变成终端窗口、Markdown 文件夹，以及睡眠时跑完的任务。它在个人 Context 中运行，并直接完成工作。
大白话：他想让你停止只用聊天框问问题。模型接上你的资料、工具、定时任务和长期记忆后，就能连续参与真实工作。
隐藏前提

系统拥有正确权限；资料质量可控；任务能够拆清；失败可以发现；关键动作有人验收。少一项，Agent 仍可能很像一个会胡说的实习生。

落到你身上

你已经在同时使用本地资料、飞书消息、文章原文和固定 Skill，这确实比普通聊天更接近“个人工作基础设施”。但它还不会自动知道今天哪个方案已替代旧方案，也不会天然拿到所有不可见的单聊和会议纪要。

落到产品上

Driver Agent 也一样。单有 Seed 模型不够，必须接 SP、公共 Context、工具、Task、Trigger、VLM、日志和 Eval。你的产品本身就是这篇文章观点的量产版考试。

你要改变的决定

以后评估一项 Agent 能力，先问“是否接入了完成任务所需的上下文、工具和反馈”，不要只问“模型能不能理解”。

第二段：为什么同一个模型，有人 2 倍，有人 100 倍

原文主张：效能差距来自 Context、相关性和接入环节。作者用个人代码产出和 YC 创业公司作例子。
大白话：模型像同一个员工。一个人只给一句任务，另一个人给当前资料、可用工具、完成标准和失败后的修正入口，结果当然差很多。
作者说对的

Context 和接入位置确实决定 Agent 能否进入真实工作。你的动态示例“命中但没参考”、事件“概念支持但没有真实 payload”、会议“日程可见但纪要不可读”，都说明信息是否真正进入决策链很关键。

作者说满的

效能还受任务价值、模型、工具可靠性、权限、协作和验收影响。400 倍是个人自述，代码行数也不能等同产品价值。你不应该拿这个数字要求自己。

你的内部证据

一份 SP 优化资料快照记录：全量 SP 约 32,806 tokens，参考示例约 26,164 tokens；优化方案在 PE3-0415 上记录 ACC 88.38%，首包 P50 从 2309ms 降到 998ms，总耗时 P50 从 12231ms 降到 6179ms。这个快照不能直接代表今天线上，但它说明“内容更多”与“效果更好”没有必然关系，选择和压缩同样重要。

你要改变的决定

以后做 Context、SP 或动态示例优化，必须同时看正确率、延迟和负向回归。不要把 token 数、示例数或文档数当成果。

第三段：“正确的三本书”为什么是全文对你最重要的一句

原文主张：知识库价值不在藏书量，关键在当前任务能否选出正确的少量资料。缺少图书管理员，知识库会变成可搜索的垃圾场。
大白话：你有再多资料，只要评审前拿到旧版方案，资料越多反而越危险。
产品对应

公共 Context 资料明确写了 13 类内容，并要求按场景、人物和任务提前过滤。比如点外卖只取相关任务经验；驻车场景不加载行车记忆；不同人物的记忆要防止串用。这就是车上版本的“正确三本书”。

团队对应

当前动态示例口径在 7 月 17 日、7 月 20 日和 8 月 7 日出现不同说法；上汽与赛力斯信号又分开维护。团队需要在页面顶部写当前有效结论，下面保留按时间排列的历史证据，不能让 AI 每次从群聊重新猜。

个人对应

每天读文章前，AI 应先取当前问题线程、今日新增原始消息和最相关产品资料。只有文章没有工作上下文，会产出通用鸡汤；只有工作消息没有原始 PRD，也容易把临时讨论当正式方案。

你要改变的决定

先治理 5 个 P0 线程的当前真相页，不要追求把 `/Users/bytedance/Desktop/3.23` 全部导入一个新知识库。每页只维护：当前结论、适用范围、来源、Owner、未决项和时间线。

第四段：“一个 Skill 就是一名员工”该怎样理解

原文主张：如果一个聪明实习生能根据一页 Markdown 完成任务，Agent 也能执行。作者把 Skill 称作员工，把 Resolver 称作组织架构。
大白话：把脑子里的做法写清楚，让别人或 AI 不需要一直追问你。
你已有的 Skill 原料

6 月 12 日 Planner bug 排查已经形成 A-F 六类和 L0-L6 介入等级。那份 33-case 分析里，D/F 类约 35% 可先从 Planner 责任中剥离，最后真正顽固的模型问题约 3 到 4 条。比例只适用于当时样本，但分诊顺序很有价值。

不能全写成 Skill

通用判断写 Skill；孤立且模型有能力但走错路的 case 放动态示例；多维稳定规则可做场景卡；精确执行、权限和状态更新进入代码、Trigger 或工具。所有东西都塞进 Markdown，会把架构重新搅乱。

聪明实习生测试

如果你把“查一下为什么没触发”交给新人，他会继续问：哪辆车、哪个环境、Task ID 是什么、日志在哪、预计条件是什么。Skill 必须先列这些必要输入，输入不全时要停下并报缺口。

你要改变的决定

第一项资产不能只是一页 `triage.skill.md`。它要连同当前真值、case 账本、Eval、Owner 契约和变更日志一起交付，后文会把文件逐个展开。

第五段：“潜空间和确定性空间”如何直接重画你的产品边界

原文主张：品味、语义和模糊请求交给模型；算术、数据库和大规模精确安排交给代码。
大白话：让模型理解人话，让规则负责数字和状态。模型可以写条件，不能凭想象决定条件已发生。
问题更适合模型判断更适合规则和系统
“到了目的地提醒我”理解用户意图；发现“到了”有多个合理含义；结合产品规则决定是否需要追问。一旦口径确定，用到达事件、距离阈值、导航状态或挡位等真实条件触发。
“宝宝哭了告诉我”VLM 描述画面；语义模型判断“睁眼、有泪、嘴角向下”等描述是否满足哭泣目标。观察周期、任务上限、匹配结果回调、去重、任务结束和通知。
“这首歌唱完就停”理解“这首歌”指当前曲目，“停”指停止或暂停音乐。媒体结束事件、Task 等待、Trigger 命中和音乐控制工具。
“10 分钟后关座椅加热”解析 10 分钟和目标动作。计时、到点回调、座椅状态前置判断、工具执行与关闭 Task。
你要改变的决定

评审一条新场景时，在需求表里强制增加两列：“哪一步允许模型判断”“哪一步必须依赖真实状态或代码”。这两列会比再画一张宏观架构图更能发现风险。

第六段：“一人公司”与你有什么关系

原文主张：一个人加上一组 Skills 和自动任务，可以完成过去由团队完成的工作。
大白话：AI 能帮你承担查资料、整理、生成脚本、跑评测和写初稿，让你把时间留给判断和推动。
适合你的部分

你可以自己做出一个小型 Eval 工具、日志对比脚本、动态示例检查器和会议准备页，不必每次等研发排期。你需要会读 JSON、知道接口输入输出，并能判结果是否可信。

不适合你的部分

量产座舱牵涉端云、车企、隐私、安全、工具 Owner 和实车版本。你无法靠一个人替代全部协作。真正的杠杆是让自己带着更完整证据进入协作，缩短争论时间。

你要改变的决定

短期目标不要写成“成为会单干的全栈工程师”。更准确的目标是：你能独立完成问题建模、证据收集、轻量验证和验收设计，再把需要工程改造的部分准确交给 Owner。

第七段：“第四周飞轮启动”能不能信

原文主张：第一周像玩具，第四周开始复利，第 12 周十几个 Skills 会自动处理例行工作。
大白话：刚开始搭系统很费劲，前几周看不到明显回报；坚持迭代后，同类任务会越来越省力。
可以信的

复利有滞后性。第一版 Skill 常常只是把问题写清；第二、三次真实使用后才知道哪些输入、分支和例外缺失。

不能照搬的

四周和十二周没有普遍数据支撑。你的工作又依赖他人日志、权限和车上环境，速度会受组织链路影响。

你的启动标准

Task 要保存什么你的 case 为什么需要如果缺失会怎样
