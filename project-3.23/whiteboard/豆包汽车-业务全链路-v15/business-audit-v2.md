## 1. P1：语音取消／查询到 T02 后没有对应出口

**12:36 状态：已修复并回读。** 当前增加 T02→T11「取消：定位原任务后管理」、T02→T12「查询：读取 TaskView 返回状态」，构建器增加 T12→E6「仅本次语音查询：任务状态回原工具调用，不等于已执行」。以下为问题形成及修正依据，不代表当前仍断链。

**现存位置：** `parts/async.json` 的 T02（第 89 行起）、T 模块边（第 456 行起）。组合图中 T02 唯一出边为 `T02 → T03：创建/修改`。

用户说“取消刚才的提醒”时，图中会经 `E4 → T01 → T13 → T02`。T02 已明确任务系统判定新增、修改、取消和查询，但取消没有连到 T11，查询也没有回到原工具调用。已有 `U03 → T11` 只能解释用户在任务中心操作；`T06 → T11` 只能解释处于等待中的任务被管理，不能代替这次语音请求的处理出口。

**依据：** [Task 任务管理设计](https://bytedance.larkoffice.com/wiki/B2WYwXFOIigKzbk7aSYcJWmZn2E) 原文 `async/bodies/A02.md:905` 明确由 Spec Builder 判定 `create / update / cancel / query`；第 930–940 行分别返回对应处理结果。查询应返回任务视图，而不是创建、注册规则或只刷新任务中心。

**建议修正：** 给 T02 增加“取消且已定位原任务 → T11”的分支，并为“查询 → 返回现有 TaskView → 原调用反馈”增加明确出口。没有查到任务、对象不唯一或无权限也应返回本次请求的真实结果，不得绕进新建任务。无需新增独立大模块。

**复查用例：** “取消十分钟后关闭加热的提醒”和“我现在有哪些提醒”从语音入口出发，都能沿条件明确的边回到本次交互；前者不重新注册一条任务，后者不产生新任务或取消动作。

## 2. P1：取消链路遗漏直接 GUI 任务的现有能力缺口

**12:36 状态：已修复并回读。** 当前 T11/T18 已明确直接 GUI 不在普通取消覆盖内，GUI 在途停止、多用户、重试和用户取消仍待验；T18→E6 进一步限定有本次管理调用才回失败／取消，自然终止只更新状态。以下保留审阅依据。

**现存位置：** T11 的“取消：停止后续等待及在途执行”；T18 的“停规则、清视觉目标/生态执行”及正文。它们目前没有保留直接创建 GUI 任务不在普通取消覆盖内的例外。

用户说“取消刚才的点单”，不能仅因图上有一条统一取消线，就认为直接 GUI 任务已经支持相同闭环。当前图的表述会把设计中的完整清理责任读成现已覆盖的能力，尤其 T08 正文也提到 GUI 生态任务由 Provider 推进，却没有指明这里的取消缺口。

**依据：** [Task Service OnePager](https://bytedance.larkoffice.com/wiki/A60Zwzy9eiiCtwkY8k2c0LKKnoc) 原文 `async/bodies/A03.md:105` 明确当前普通任务取消链路尚未覆盖直接创建的 GUI 任务；第 119 行仍将正式多用户、并发重试及用户取消列为待验证。早期任务技术设计提出停止生态 Provider 的目标，不足以覆盖这条更明确的现状说明。

**建议修正：** T11/T18 保留完整的取消责任，但加适用范围：“普通规则任务走此取消链；直接 GUI 任务的用户取消当前未被普通链路覆盖，仍需专项验证”。不要只标泛化的“按项目核实”，因为资料已给出具体缺口。已发生的车辆或交易动作不因取消任务自动撤销。

**复查用例：** 普通提醒取消与 GUI 点单取消分开验收。前者验证关闭任务、撤销规则和截断迟到回调；后者先确认是否存在实际取消接口与客户端处理，再验证在途步骤是否停止，不能用卡片消失作成功证据。

## 3. 追加核查：K13 删除分支当前孤立，连接必须保留新需求状态

**12:36 当前观察：** K13 只有 K13→K14→K15，没有进入 K13 的边；K03 仅分流到记录、预取、显式检索和关闭／未授权。根代理拟补入口与反馈是必要的，但不能把新增需求图误画成当前已上线协议。

**直接原文依据：** [记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh) 的 `director/bodies/CbJVw4ACzilvvBkRxkqcQVfAnLh.md:659–668` 明确车主语音删除语义／情景记忆，批量按人、日期或全部删除由 Director 二次确认，语义删除后联动画像。第 635–656 行分别定义历史／摘要逻辑清空与长期库删除，按日期删情景记忆的接口返回删除条数；没有定义所有删除操作统一成功枚举或完整生产协议。

**可补的业务关系：**

- E4→K01：已选择记忆类工具，仍先核可信身份和操作范围。
- K03→K13：明确删除请求、车主身份及删除权限通过；标注「10/19 新需求，发布／工具合同待核」，不当作全车型当前实线能力。
- K13→K14：当前请求范围明确，批量已由 Director 完成二次确认后，才允许执行；未确认时应回 Director 询问，不执行删除。
- K14→E6：实际删除接口结果或失败返回本次调用；不能只确认了用户意图就播“已删除”，也不能把全部存储与画像联动视为一个已经验证的原子动作。

**重要限制：** PRD 第 416–419 行规定关记忆开关停止生产／召回，现有材料没有规定关闭记忆就禁止删除。K03 可复用身份和操作范围核验，但不要增加「先开启记忆，才可删除」这个未经定义的限制。语音删除仍是 10/19 新增需求，与旧工具表“不支持删除”存在版本差异；连接表达的是需求级业务流，不是已部署证明。
