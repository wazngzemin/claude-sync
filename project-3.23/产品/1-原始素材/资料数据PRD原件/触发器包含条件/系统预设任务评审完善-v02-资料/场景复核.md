# V02 场景与测试独立复审

审核文件：`PRD-系统预设任务配置平台与端云交互框架-评审完善-v02.md`。重点核对第1章、5.8/5.9、四项场景新增产品选择、7.5及8.1。仅列4项值得马上修稿的问题，不扩展系统模块。

## 总体判断

V02 已明显补上 V01 欠缺的产品论证：用户收益与动作成功分开；四场景都有推荐意见、代价和验证方法；充电不把设备当意图、天气不外推安全收益、加热不以ON代表视野改善。模块职责没有被新增策略打乱。当前主要剩下“推荐方向与主案例一致”“策略落实到配置和运行状态”“长期授权面对配置变化”三类闭口。

## 需要立即修稿的4项

### 1. 儿童锁推荐 A，但唯一详细案例仍用 B，评审很容易把 B 当本期落地方案

- **严重度：P1（方案表达冲突）。**
- **位置：** 第6.2节行731推荐A类有效变化补查；第8.1行1012同样推荐A；第6.2.1行748却写“假设本次选择切D启动”，步骤2仅非D→D，详细八步都没有演示A最有价值的“进入D后才识别到目标”。
- **问题：** “仅用于比较方案”说明降低误读，但正文花最多篇幅演示的是非推荐方案。读者照着案例开发，仍可能漏掉推荐要覆盖的晚识别。
- **可直接修文：** 将6.2.1标题改为“推荐A类补查＋询问的完整演示（待D06会签）”；案例前置改为“车辆已在D挡，先前目标未明确，随后收到有效后排儿童识别；目标侧锁关闭”。步骤2改为“收到目标成员由未明确/无目标变为有效目标的变化；在非P前提下重新读取成员、后排范围、左右锁及门状态”。其余交互/复核步骤保持。表后用一句比较B：“若只采用切D一次检查，本例不会触发，需求方需接受这一覆盖限制。”
- **注意：** 此修订只是让演示与推荐一致，不把A变成已批准事实；不新增轮询频率，不把UNKNOWN任意变成确定无目标。

### 2. 拒绝／超时后抑制持续场景，仍缺少运行保存与解除的落点

- **严重度：P1（产品策略未完全可执行）。**
- **位置：** 5.9行660建议同一持续场景不立即再问；4.8行404只写“拒绝后是否允许本次停车再次提醒另行会签”；5.4结束后回到等待。尚未明确新事件到来时谁知道这个场景刚被拒绝，也没在字段表中区分“事件去重”和“交互后抑制”。
- **问题：** 去重只挡同一个事件，不能阻止同一持续雨天被新事件再次拉卡。新增策略若只写在体验说明中，业务会消费不到，平台也无法预览有效范围。
- **可直接增加4.8一行：** “回答后抑制｜选择已会签的作用范围：本次停车/同一持续场景；分别配置确认、拒绝、关闭、超时后的处理及解除依据。页面显示策略承接为任务业务；未支持的范围不可选择。建议拒绝/超时后在本次场景内不立即重问，正式解除规则按D11确认。”
- **可直接增加5.9一句：** “任务业务结束询问时保存本次场景与回答后的抑制事实；收到后续候选时，先检查是否仍被抑制，命中则记‘本次不展示’而非再建卡。Trigger的事件去重与该业务抑制分别记录；无需假定Trigger已经能够读取卡片回答。”
- **验收补点：** 同一持续场景发来不同事件关联，第一次已拒绝，后续不得因事件编号不同就绕过抑制；解除后按已会签规则进入下一次服务。

### 3. 首次开启说明补好了，但配置升级后授权范围变化仍没有产品机制

- **严重度：P1（长期许可范围）。**
- **位置：** 5.8行654限定首次开启应明确询问/静默与范围；5.5行611版本变化仅防新条件旧动作混用；4.7允许配置不同交互模式。没有说明同一已开启任务由询问改静默、由单侧改双侧时旧许可还能否使用。
- **问题：** 用户原先开启的是“每次问我”，配置者发布成“自动处理”后，技术版本一致并不能证明用户接受了新的控制方式。这是现有任务配置能力必然面对的行为变化，不宜仅依赖首次文案。
- **建议修文（标本版产品建议，D01/D06/D07按任务会签）：** “配置变更若从询问改为静默、扩大识别对象或控制侧别等用户授权范围，不直接沿用旧范围许可启用新增行为。产品先标记变化及受影响任务实例，状态承接业务和任务中心按已会签方式重新取得该范围确认；没有完成前，维持原已授权范围或暂停新增行为。纯文案修改且不改变意义和范围，不重复要求用户确认。”
- **验收补点：** 原许可仅询问时，将草稿改为静默并发布；未完成新范围确认的实例不能自动动作。这里不要求新增设置页，也不规定存储字段名。

### 4. “业务成功”仍有一处泛称，和新增价值验收的术语容易混淆

- **严重度：P2（术语一致性）。**
- **位置：** 第3.2节点表行205：“真正达到目标才算业务成功”；第7.2行912“真实目标达成”实际只指模式/灯/锁等设备状态。第1章已正确指出车辆动作成功不证明用户价值成立。
- **问题：** 负责人可能再次把图里的业务成功理解为整项用户目标已达成；尤其加热ON与视野改善在前后两种意义下使用“目标”。
- **可直接修文：** 第3.2改为“可信回读达到本次动作目标，才算执行链路完成；服务是否有帮助按第7.5另验”；第7.2层次“真实目标达成”改为“车辆动作目标达成”。其他状态名SUCCESS可保留，只在定义处明确它不是用户价值评分。

## 外部证据不足（不作为本轮继续写长文的理由）

以下内容当前已经正确写为假设/会签，不能靠补文字变成结论：

1. 四项任务在目标车型的实际操作入口、原车自动策略覆盖和用户负担，需B01走查记录。
2. 天气标签到模式/灯光建议的车型适用关系、儿童对象/侧别识别能力、后视镜实际效果，需对应能力和受控场景依据。
3. VUI跨任务准入、当前业务可读的“处理中”事实、旧任务升级的范围确认能力，需真实接入方确认；本稿不能宣称已支持。
4. A/B、低SOC门槛、静默与询问的体验优劣，没有实际样本前只保留推荐及代价，不写胜出比例。

修完上述4项后，场景叙事、配置消费和价值验证能够形成一致的评审主线；不建议再为“显得深入”堆新的模型、用户画像或全局调度模块。
