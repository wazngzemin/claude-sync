产品方案 下次技术评审前

把动态 Advisor 的端状态可用性和失效规则写成一份产品结论

这是同一个产品问题的两面：没有可用端状态，动态 Advisor 无法稳定判断条件；没有生命周期规则，又可能把长期有效任务按七天误删。
现在发生了什么

上汽排查群发现座椅加热只在静态条件中可用，统一端状态表也缺枚举；触发器侧又提出动态 Advisor 场景最长保留七天。

产品要回答什么

哪些车端状态可供动态 Advisor 使用；一次性、短期和长期任务各在什么条件下失效；清理后用户看到什么、能否恢复。

本次交付：一份《动态 Advisor：端状态可用性与生命周期规则》，包含“端状态可用表”和“任务失效规则”两页。
按这个顺序写
  1. 打开统一端状态维护表，为座椅加热等状态标明信号、枚举、数据来源，以及静态条件/动态 Advisor 是否可用。
  2. 把来源不明或当前不可用的状态单独列出，逐项找端侧确认；“正在测试”必须补预计完成时间和验证方式。
  3. 把动态 Advisor 任务分为一次性、短期、长期三类，分别定义结束条件；先不要批准“一律七天删除”。
  4. 为每类补上用户取消、条件长期不满足、车辆下电、系统清理后的用户可见结果和恢复方式。
  5. 用“仍应保留的长期任务”和“已经应该过期的任务”各走查一次，再带到技术评审定稿。
交付对象与来源

交付对象：上汽动态 Advisor 排查群、端状态维护方和触发器研发。来源：8月26日“上汽动态Advisor问题排查”群与“触发器、模拟器及 Advisor 开发沟通”群；目前没有正式截止时间。
