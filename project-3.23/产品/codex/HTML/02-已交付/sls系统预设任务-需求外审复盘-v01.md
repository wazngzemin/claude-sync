## 1. 先给结论

这场会议没有完成“需求外审并形成开发共识”，但完成了“暴露架构缺口并收集部分约束”。所以它不是一场完全没有价值的会，但从外审目标看，结果确实不理想。

真正的问题不是你不会说话，而是你拿着一份还处于方案探索期的内容进入了外审。任务状态、卡片链路、DT 后续承接、执行闭环、端云归属和研发负责人都没有在会前确认。评审者每向下追问一层，你只能现场猜一个模块；下一个人再指出现状不支持，口径就被迫改变。最后，会议从“评需求”变成了“现场发现系统架构”。

05:59 以后，刘杨逐渐接管了问题顺序、场景拆解和会议收口；到 01:01:48，还需要由他提醒“是否还有场景没过”。这说明你丢掉的不只是某一道技术题，而是主持权。恢复主持权的方法不是抢着回答，而是提前准备决策清单，并在未知项出现时立即停车、标记 Owner 和影响。

这次需要改的不是单纯增加更多文字，而是调整工作顺序：

1. 先锁定产品业务闭环。
2. 再与各模块一对一确认现状、边界和负责人。
3. 把已确认结论、产品方案和待确认项分开写。
4. 最后才召开多人外审，会上只处理已经明确列出的决策题。

## 2. 这场会原本应该完成什么

从开场和后续讨论看，本次会议实际上同时装进了四个目标：

- 解释什么是系统预设任务，以及为什么分端侧和云端。
- 评审儿童锁、充电口盖、后视镜加热等具体任务。
- 确认任务中心、Task Service、Trigger、Advisor、DT、即时交互卡和端侧车控之间的链路。
- 讨论现有 Trigger 配置平台需要增加什么能力。

这四个目标不是一个层级的问题。第一个是产品框架，第二个是业务 Case，第三个是系统方案，第四个是平台产品需求。它们放在一场 77 分钟的外审中，而且关键模块又没有预对齐，会议必然不断跳层。

更合适的会议目标应该只有一句：

> 本次先确认“云端系统预设任务”的标准业务闭环和模块边界；具体四个任务只用于验证框架能否承载，不在现场重新发明底层链路。

如果卡片链路、任务状态归属还没确认，这场会应叫“方案对齐会”，不能叫“需求外审”。

## 4. 你个人表现中最影响评审的六个问题

### 4.1 把“没有确认”说成了“我理解应该是”

典型位置是 06:11、15:19、19:52、21:33、28:14、42:18 和 46:30。你不是不知道所有业务，而是没有给信息贴标签。评审人听不出哪句是事实、哪句是建议、哪句只是猜测。

下一次统一使用三种句式：

- **已确认事实**：“这个结论已经和 X 确认，当前能力是……”
- **本次产品方案**：“这里是我提出的产品方案，今天需要大家判断是否可落地……”
- **待确认问题**：“这里我没有证据，不在会上猜；Owner 是 X，结论会阻塞 Y。”

### 4.2 没有守住产品边界，跟着问题不断换模块

充电链路中，“谁决定出卡”先后落到 DT、Trigger、主动推荐和静态 Advisor。模块名变了，但产品需要始终没变：识别结果回来后，必须有一个业务 Owner 判断结果是否有效、决定是否询问用户、消费用户授权并发起执行。

你应该守住的是这条业务不变量，而不是替研发现场选择技术模块：

> 不管底层最后走 Advisor 还是其他通道，产品要求不变：Trigger 只发事件，识别能力只返回结果，系统预设任务业务决定出卡并负责闭环。请研发确认哪个现有模块能承担这个责任；没有就形成新增能力。

### 4.3 用不充分的状态代替业务事件

42:32 用“当前仍在 P 挡”说明结果属于“本次停车”，这在逻辑上不成立。车辆可能 P→D→P，状态相同但已经是另一次停车。类似问题还包括把“RPC 成功”当作动作成功、把“卡片展示”当作用户确认。

以后遇到状态问题，固定问四句：

1. 这是一个持续状态，还是一次状态变化事件？
2. 怎样关联到同一次业务处理？
3. 多久后失效？
4. 最终以哪个真实状态判断成功？

### 4.4 现场为了“简化”删除必要的安全复核

45:52–45:59 因为复核链路不好放，你提出取消二次校验。这个动作会让评审者认为方案由当前模块能力决定，而不是由用户和车辆安全要求决定。

正确说法应该是：

> 执行前复核不能删。现在不确定的是由云端业务还是端侧执行层复核，不是不复核。我们先保留产品门禁，技术 Owner 会后确认落点。

### 4.5 没有在会议结束时完整收口

01:08:37 会议只收出了“找徐洋确认卡片”和“确认出地库”两个 Todo，但实际至少还有任务状态 Owner、云端业务 Owner、DT 后编排、车控回读、默认开关、儿童锁逻辑、平台字段等问题。

任何评审结束前，都要共享屏幕逐项确认：

- 今天确认了什么。
- 哪些没有确认。
- 谁负责给结论。
- 何时给结论。
- 哪些结论不回来，PRD 就不能进入开发。

### 4.6 面对容量风险时过早说“没有问题”

53:42–54:35，刘杨提出大规模车辆同时命中后可能集中调用模型。你用“只有前置条件满足才会调用 VQA”解释过滤逻辑，这个方向没有错，但在没有活跃车辆数、命中率、峰值 QPS、单车频控和降级策略时，不能直接判断“没有问题”。

更稳妥的说法是：

> “容量风险成立。Trigger 前置过滤会降低调用量，但现在没有数据，不能直接判断资源足够。会后我补活跃车辆数、条件命中率、VQA 峰值和失败降级，再请模型侧评估。”

需要客观看：会议暴露出的很多问题，本来就不是产品一个人靠阅读能确认的。

### 6.3 真正阻塞四项任务的是三份公共契约

这场会讨论了很多模块名，但最需要补齐的其实只有三份公共产品契约：

1. **任务开关契约**：任务目录从哪里来；车机的开启/关闭写给谁；按车状态由谁保存；Trigger从哪里读；上电、离线和关闭时怎样恢复或失效。
2. **识别结果与出卡契约**：Trigger发什么事件；DT/VQA返回什么结果；谁等待结果；谁判断结果未过期且属于本次事件；谁决定是否出卡。
3. **用户确认到车辆结果契约**：谁注册卡；展示成功怎样回执；点击和语音回哪里；谁生成执行请求；端侧复核什么；看哪个真实状态算最终成功。

三份契约没有补齐之前，继续给流程图增加模块只会让图更复杂，不会让方案更完整。

## 7. 下一版方案必须先画清的一条主链

下一版不要先堆模块名。先用这一条业务链判断每个模块是否有明确责任：

```text
产品在配置平台定义任务
→ 任务定义发布
→ 任务中心向用户展示任务
→ 用户开启/关闭
→ 任务状态服务保存单车真实状态
→ Cloud Trigger读取任务状态和车辆状态
→ 条件满足后只发一次业务事件
→ 系统预设任务业务接收事件
→ 按需调用 Advisor/DT/VQA 获取进一步判断
→ 业务校验结果属于本次事件且未过期
→ 业务注册并拉起即时交互卡
→ 点击直接返回业务；泛化语音按卡片链路理解
→ 业务获得有效用户确认
→ 端侧执行前重新检查任务和最新车况
→ 调用车控
→ 读取车辆真实状态
→ 业务更新卡片和记录，结束本次
```

这条链中，任何一个箭头答不出“谁给谁、给什么、失败怎么办”，都不能进入多人外审。

## 8. 关键时刻当时应该怎么回答

### 被问“任务开关放在哪里”

> “这里我先区分两个东西。平台保存的是任务定义；用户点开关以后产生的是某辆车的任务实际状态。任务中心负责展示和转发操作，Trigger只读取状态，不应该自己充当状态存储。真实状态由哪个服务承接还没完成会签，这是 P0，今天请晓伟和梦尧确认边界，Owner 没定之前这条链路不进入开发。”

### 被指出儿童锁流程画反

> “对，这张图的分支画反了。正确逻辑是：进入 D 挡、后排有儿童或宠物、儿童锁关闭，才询问是否开启；儿童锁已经开启就结束，不再出卡。我先把这处记为图错，不在错误分支上继续讨论。”

### 被问“Trigger 后谁出卡”

> “产品边界先定：Trigger只负责发现条件成立并发出业务事件，不能直接拉卡。下游必须有系统预设任务业务承接事件、决定是否出卡、消费选择并推进执行。具体复用主动推荐还是新增承接层，需要徐洋和相关研发会签；这不是现场猜一个模块就能定的。”

### 被问“DT 还是 Trigger 决定出卡”

> “都不是。DT/VQA只回答有没有识别到设备；Trigger只回答硬条件是否成立。系统预设任务业务拿到识别结果后，检查结果有效期和本次事件关联，再决定是否询问用户。”

### 被问“怎么判断属于本次停车”

> “仅看当前仍在 P 挡不够，因为可能发生 P→D→P。产品要求必须有关联本次停车或本次触发的标识，并设置有效期；标识由哪个状态能力提供需要研发确认。没有这个能力，旧结果不能继续触发开盖。”

### 被问“新增任务怎么到车上”

> “任务定义来自云端配置，不在端上写死，也不要求一次推给所有车辆。任务中心在车辆下次上电或下一次拉取任务列表时获取最新定义。单车的开启状态另行保存，两者不能混成一次 OTA。”

## 10. 下一次评审前的门禁

下面五项只要有一项没有答案，就不要再次开“需求外审”，最多开小范围方案对齐：

1. **任务状态**：谁保存，Trigger从哪里读，关闭后多久生效。

3. **用户交互**：谁注册卡、点击回哪里、语音回哪里、超时怎么结束。
4. **车辆闭环**：谁复核、谁车控、看哪个真实状态算成功。
5. **配置落点**：每个产品配置项由哪个运行模块消费。
