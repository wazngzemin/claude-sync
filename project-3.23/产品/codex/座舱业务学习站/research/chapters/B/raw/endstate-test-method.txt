基本介绍
收集实车的一些基本信息(比如:空调的状态，轮胎的状态，车速，状态灯....)存入数据库，对外提供查询的接口根据输入的query筛选出相关的状态信息

测试方法
在车辆操作对应的内容（比如：将空调温度调整到24度），或者通过模拟信号(比如：模拟对应的can信号或者根据一些命令修改信号值)
在数据库中查询对应的车辆信息看是否正常落库
注：任何数据以落库为准，数据库数据未正常落库或者数据错误即测试不通过
需要使用到的adb命令如下：
查询客户端上报日志及上报的logid
adb logcat | grep -E --color=always 'on receive report increment|LogInterceptor'
注释：
on receive report increment 是客户端上报端状态信息的关键字
LogInterceptor 是查询各种与云端接口交互时获取对应的logid的关键字
一般logid是跟着上报最近的那个logid如下图

服务端数据库查询
查询链接地址：https://cloud.bytedance.net/rds/detail/db/cn/vehicle_aidv/autoSQL?db_name=vehicle_aidv&region=cn&x-resource-account=public&x-bc-region-id=bytedance&x-bc-vregion=China-North&x-bc-vdc=cn
vehicle_resource_info 表中的信息是当前端状态最新的的信息
vehicle_resource_info_history 表中记录端状态上报的历史信息

根据vehicle_id查询端状态当前信息
select * from vehicle_resource_info WHERE vehicle_id = "1swYTEGdKtqCuXIjORNHaxaqsZI8dURjv6PWtbXkJXo="  ORDER BY resource_id  LIMIT 400;
根据vehicle_id和信号id查询该信号历史上报信息
select * from vehicle_resource_info_history WHERE vehicle_id = "1swYTEGdKtqCuXIjORNHaxaqsZI8dURjv6PWtbXkJXo=" and resource_id = 'vehicle_control_0022' ORDER BY expiration_time DESC LIMIT 450;

端状态上报的一些特殊逻辑
车辆仅首次上电上报时会将该车辆在数据库vehicle_resource_info表中的数据进行清空，重新将新的数据进行落库，这时created_at时间应该都是大于等于该时间，有小于该时间的数据，说明上报是有问题的。
     首次上报还要注意一些状态灯的信息，一些车辆的协议是只有该灯开启状态才会有相关的信息，默认是关闭状             态，那这种情况首次上报的时候是需要将这些默认状态进行上报的
首次上电上报后后面的数据都是进行更新上报

上报数据字段错误

image.png

需求要求字段是switch，上传的字段是mode， 服务端在入库的时候会进行字段校验不通过的不会进行落库
上报的字段值不对导致落库失败
当取值范围是on/off，客户端上传开启/关闭，服务端进行了值校验，校验不通过就不会落库

断网测试方法
车机不开启无线网络和移动网络
操作对应的信号，比如：打开空调，空调温度先调节到26度然后在调节到27度
监测客户端上传日志有重试上报的日志
开启网络
监测客户端上传日志和数据库落库数据
弱网测试
车机通过实地模拟或者软件模拟弱网情况
操作对应的信号，比如：打开空调，空调温度先调节到26度然后在调节到27度
监测客户端上传日志如果接口超时有重试上传日志
解除弱网限制
监测客户端上传日志和数据库落库数据

常见问题分析方式
首次筛选应该筛选确未筛选出相关的端状态
首次筛选端状态是固定一部分内容进行筛选的，内容范围是核心端状态知识梳理，未在范围内未筛选出是正常现象
先查看端状态模型筛选结果，排除模型筛选错误其他都是context服务端的问题
需要二次端状态筛选未进行筛选
这种情况输出planner任务管理的问题，目前二次筛选有planner自己决定是否调用
二次端状态筛选未筛选出相关的数据
image.png

查看planner改写query是否合理，不合理的情况就是planner的bug
planner改写合理模型输出结果不对，筛选模型问题
筛选模型输出正确但context输出结果不对，属于conetxt工程端问题
