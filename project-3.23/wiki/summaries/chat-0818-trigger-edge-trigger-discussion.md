# 8.18 群聊：触发器条件任务重复触发问题

**形式**：飞书群聊（截图转录，约 4 分钟）
**参与人**：施佳杰（动态 Advisor）、王泽民（触发器产品）、郝晓伟

---

## 一、问题现象（施佳杰提出）

用户注册条件任务 **"每次电量小于30%时提醒我"** 后，实际行为是：

- 电量 <30% 的状态会持续 30 分钟～1 小时（用户找充电桩的过程）
- 在这段"条件持续满足"的时间里，触发器**按最小间隔（CD）反复 push** "电量小于30%"给下游
- 一直提醒到条件不再满足为止 → 用户被连续轰炸

## 二、根因

王泽民确认当前实现是**电平触发（level-triggered）**：

> 触发器只判断条件**当前是否满足**，满足就 push 给下游；在条件持续成立的周期内会**多次 push**。

触发器有 CD（冷却时间 / 执行最小间隔，例如续航 <100km 任务的最小间隔为 30 秒），但 **CD 只能降频、不能去重**——它把"每分钟 push 60 次"变成"每 30 秒 push 1 次"，没有解决"一次满足周期内只应触发一次"的问题。

## 三、决议：改为边沿触发（one-shot）

郝晓伟提出、王泽民接受的正确语义：

1. 条件任务应检测**信号跳变沿**（上升沿/下降沿），即"条件从不满足变为满足的那一刻"才 push
2. **一次满足周期内只 push 一次（one-shot）**，之后即使条件持续满足也不再 push
3. 直到条件先变为**不满足**、再重新满足时，才再次 push

**期望行为示例**（郝晓伟原话）：
- 本次开车电量跌破 30% 那一刻 → push 一次 → 之后不再 push
- 用户充电到 50–60%（条件变为不满足）
- 再次开到低于 30% → 再 push 一次

## 五、与 7.10 信号中枢架构的关系

这次定论与 7.10 评审的架构方向**完全一致**：信号中枢把"状态突变检测"独立为**触发事件**层（见 [[signal-hub]]、[[meeting-0710-sls-signal-context-trigger-review]]），本质就是边沿检测。本次讨论相当于把"变更为"的边沿语义**从状态类信号扩展到数值阈值类条件**——"电量<30%"不应理解为持续成立的静态条件，而应理解为"电量下穿 30% 阈值"这一突变瞬间。

对 [[trigger-condition-taxonomy]] 的三种取值判断方式是一个重要澄清：**数值阈值类条件的触发语义 = 阈值穿越边沿，而非阈值区间内的持续满足**。
