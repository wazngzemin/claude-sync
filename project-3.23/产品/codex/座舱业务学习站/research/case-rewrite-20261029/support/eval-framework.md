# 豆包汽车评测体系

# 整体框架

**主观评测贯穿评测全链路**：评测集沉淀典型对话与团队偏好，Rubric 将偏好转化为可复用标准，离线回测验证版本差异，端到端评测补充语音与交互体验，线上监控持续发现真实用户信号，新增问题再回流到 Case、评测集和 Rubric。

**评测集**

</td>
<td>

基础集：覆盖日常用车中的高频需求与高频主观聊天场景

</td>
<td>

样本分布、对话上下文与真实用户使用情况仍有偏差，需要随线上变化持续更新。

</td>
<td>

<tr>
<td>

项目集：围绕项目新增能力与版本变更设计评测样本

</td>
<td>

项目需求变化快，主观体验要求容易停留在“自然”“有温度”等抽象描述。

</td>
<td>

随项目节奏更新样本；对模型、声音、人设或交互策略的变更，补充可观察、可复核的主观体验验收点。

</td>
</tr>

<td>

专家集（挑战集）：覆盖需要推理或复杂交互的高难度任务

</td>
<td>

模型与链路升级后，原有难例可能失去区分度；模糊意图、情绪变化、多人插话等问题也难以用单轮文本复现。

</td>
<td>

随模型能力提升迭代难度，加入多轮分支、情绪转折、多人交互与打断等挑战样本。

</td>
</tr>

<td>

专项集：覆盖安全、信任、人设与重点体验问题

</td>
<td>

专项问题通常低频但影响大，且会以隐性不满、反话或中止对话等方式出现。

</td>
<td>

根据线上问题持续补充安全、信任、人设一致性、冒犯与负面情绪修复等专项样本。

</td>

<tr>
<td>

**主观聊天锚点集：沉淀典型场景、经典对话与偏好答案**

</td>
<td>

主观回答因场景而异，单一通用标准难以覆盖笑话、故事、游戏、情感倾诉等不同类型；单轮样本也无法反映上下文承接与用户反馈。

</td>
<td>

先筛选约 10 个典型 Case 组织组内共评，拉齐“什么是好回答”；再扩展至约 100 个典型 Case，保留完整对话、偏好答案、关键考察点和负面样例，作为自动化评估、回测与端到端评测的共同基准。

</td>
</tr>

<td rowspan="4">

**Rubric**

</td>
<td>

基础需求 Rubric

</td>
<td>

算法训练、测试、评测等环节需要使用一致且可解释的基础标准。

</td>
<td>

统一基础规则，覆盖意图理解、上下文连贯、信息真实性、人设一致、播报流畅与公序良俗等要求，并明确评分尺度与证据要求。参考 [评分标准](https://bytedance.larkoffice.com/wiki/POj4whzWginFzBkomm0cYAFGnQe)。

</td>
</tr>
<tr>
<td>

复杂需求 Rubric

</td>
<td>

复杂需求包含多轮分支，逐轮要求会随对话阶段和用户反馈变化。

</td>
<td>

先通读完整对话，再按轮次设置二元检查点；分别检查开场意图识别、中段承接与调整、收尾时机，避免脱离上下文评分。

</td>
</tr>
<tr>
<td>

**主观需求 Rubric**

</td>
<td>

“自然”“有温度”“像真人”等表述过于抽象，不同场景的好坏标准也不完全相同；自动评分与人工偏好可能不一致。

</td>
<td>

采用“通用原则＋场景细则”：通用原则关注相关与连贯、情绪与情境是否恰当、交流主体感、人设一致及继续聊天意愿；场景细则按笑话、故事、游戏、情感倾诉等类型编写。人工发现遗漏或模型误判时，记录证据并更新 Rubric。详见 [主观对话评测体系](https://bytedance.larkoffice.com/wiki/U2NnwS3SZiQ2yHkzRL3c0IZKnvd)。

</td>
</tr>
<tr>
<td>

**整体体验指标**

</td>
<td>

逐 Query 评分难以识别一段时间内重复话术、表达单一、人设漂移等累计问题。

</td>
<td>

增加跨对话、跨周期指标，重点观察语义与表达丰富度、情感表达丰富度、固定话术重复率、人设一致性及整体继续聊天意愿；明确统计口径后再设置基线和警示线。

</td>
</tr>
<tr>
<td rowspan="2">

**回测**

</td>
<td>

DT 评测

</td>
<td>

真值标注缺少稳定的一致性标准，自动评分也可能偏离人工偏好。

</td>
<td>

以主观聊天锚点集和 Rubric 为真值基础；评测时先通读整段对话，再逐轮打分，并对自动评分结果进行人工抽检，重点复核高分异常、低分异常和版本差异明显的 Case。

</td>
</tr>
<tr>
<td>

**端到端评测**

</td>
<td>

纯文本无法还原车内真实体验，纯人工上车评测又成本高、覆盖有限。

</td>
<td>

在文本 Rubric 外增加非文本标准：语义与情感表达丰富度，语气、音调和停顿是否自然，播报是否符合当前情境，发音是否准确，响应与静默时长是否合理，以及打断、抢话、多人重叠和收尾让位是否得当。人工同时记录 Rubric 未覆盖但明显影响体验的问题，用于后续补充标准。

</td>
</tr>
<tr>
<td rowspan="3">

**线上评测与在线监控**

</td>
<td>

用户反馈与问题挖掘

</td>
<td>

显性上报只能覆盖一部分问题；反话、辱骂、重复追问、催促继续回答、提前结束对话等隐性反馈容易被遗漏，人工逐条复核效率低。

</td>
<td>

统一识别显性与隐性的正负反馈，并保留触发前后的完整对话；建设自动化问题定位与上报工具，将“你让我更生气了”“你在作弊”“继续说”等反馈映射到具体轮次和问题类型。

</td>
</tr>
<tr>
<td>

数据仪表盘

</td>
<td>

缺少能间接反映主观对话质量的稳定指标及统一口径。

</td>
<td>

监控用户显性／隐性正负反馈、主观对话持续时长与轮次、继续聊天率、用户与助手打断次数、重叠说话、长时间沉默、重复提问／催答，以及语义丰富度、人设一致性等整体指标。先观察分布和版本变化，再校准基线与警示线，避免把单一统计值直接当作体验结论。

</td>
</tr>
<tr>
<td>

人工随机抽查

</td>
<td>

自动指标难以覆盖新型问题，也可能误读沉默、打断等事件的真实原因。

</td>
<td>

每周从活跃用户中抽取 10 位进行完整会话复核，结合文本、音频、打断及端状态判断体验；将新问题回填到 Case、Rubric 和监控规则。

</td>
</tr>
<tr>
<td>

**信号发现**

</td>
<td>

通过线上变化识别潜在的主观体验退化

</td>
<td>

单一指标波动难以直接说明体验问题，需要结合场景、版本和完整对话判断。

</td>
<td>

围绕负面反馈上升、正面反馈下降、对话持续度降低、打断或沉默增加、重复话术上升、语义／情感丰富度下降、人设不一致等信号建立基线和警示线；按主观场景类型和模型版本下钻，筛选高价值 Case。

</td>
</tr>
<tr>
<td>

**Case 挖掘与归因**

</td>
<td>

还原问题发生前后的完整体验，并将结论回流到评测资产

</td>
<td>

缺少端状态、语音时序和上下文埋点时，难以区分内容质量、语音交互、工程链路或用户主动打断等不同原因。

</td>
<td>

补齐端状态、完整上下文、ASR／TTS 时序、响应与静默时长、打断方、重叠说话及用户反馈等记录；按内容与 Rubric、语音与交互、工程链路三类归因，并将典型 Case 回流到评测集、Rubric、回测和线上规则。

</td>
</tr>
