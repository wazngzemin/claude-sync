# root-patch 独立复核

复核范围：root-patch.json 的开头、总图解读、复核表、产品经理工具箱、三分钟复述和术语表。对照 baseline-v.json、flow-patch.json、support-patch.json；未修改这些被审核文件。另按父代理指令修改了本人负责的 flow-patch.json 与 flow-ledger.json。

结论：原先“12 步必定串行”“仲裁一定等 DT”“同名 1.7B 必定同一份部署权重”的主要误导已修正。图标记保留，原查询表与术语的信息基本完整。仍建议交付前处理下列 3 项表述一致性问题，并补齐三分钟版的场景分支。

## 本地开始时间与并行关系

总图已明确识别持续出字、判停同时进行，播报中还可做流式拒识；也明确本地不用等云端全部完成。没有再把编号直接写成严格时间顺序，这是通过项。

但“本地不必等云端全部完成”仍可被读成“先等云端定稿，再开始本地”。建议总图或三分钟版补一句即可：“赛力斯已激活时，两套识别同时运行；本地拿自己的识别结果计算候选，不以云端定稿到达为启动条件。”来源是 baseline v39-s3 的激活态两套识别说明和 v39-s4 的“不等云端定稿”。不要进一步推成“本地拿 partial 就可执行”，原资料不支持这一步。

规则与 FC 的精确串并行关系仍留按车型版本核对，root 没有替未确认事项下结论。固定规则抢先、本地兜底不必等 DT、云端超时可能没有云端结果，均已说清。不存在“云端已经返回了但还是等到 3 秒才仲裁”的新误导。

## 三场景能否单独讲通

本次按“游泳馆补餐厅、豆包播报时插话、断网或超时车控”检查。完整章节正文都可找到相应链路；若要求只拿三分钟版就能独立宣讲，后两例还偏抽象。

| 场景 | 已讲通的部分 | 仍建议补的一句 |
|---|---|---|
| 游泳馆补餐厅 | 两档停顿从同一次停顿起算；旧准备不能处理改变后的需求；查到游泳馆再搜周边；导航指令和导航成功分开。 | “查不到昨天的地点，就仍然缺定位依据，不能编一个游泳馆继续搜。”完整第五段已有这一边界，复述版未带出。 |
| 豆包正在播报，主驾要打开副驾座椅加热 | root 说明流式拒识只决定停播，后续执行还需接话与仲裁。 | 加一个具体动作：“介绍餐厅时主驾插入座椅加热请求，先停当前播报、继续收音；正式拒识若不接，座椅加热不会因此被执行。”规则放行与多人模型判断的细节仍留第二段，不必复读。 |
| 断网／超时车控 | root 说明本地候选可用于兜底，且不必等 DT 返回。 | 加“本地也办不了就提示网络异常；本地已执行后，晚到的云端结果不再执行”。这是 support v39-s5 仲裁表的两个必要末端分支，当前复述版都未明确说出。 |

断网和超时应分开讲：断网本身已满足兜底条件，不能在教学故事里再让用户必等 3 秒；“3 秒无返回”用于有网但云端未按时返回的分支。root 当前没有强行要求断网等待，但可在补场景时继续保持这个区别。

## 模型、知识覆盖与篇幅

模型权重判断通过：root 已把 Qwen3 1.7B 限定为基座与规模，保留多任务训练和跨项目对齐的证据，不据此宣称所有项目当前部署同一份权重。流式拒识、最终拒识与 FC 的职责区分可理解；30B 也限定为本章两项规划，没有泛化为所有 30B 都在端侧。

相对 baseline，根补丁没有发现影响业务主线的独有知识被整章删除。原复述末句“家和公司只存豆包记忆”移出复述后，support 的记忆同步专题仍保留方向、项目和待确认状态。原 Input Manager 的“同一时间只处理一件事”改为先后管理，support 已保留线上打断行为与 v0.5 方案差异，未造成解释空缺。

查询表均折叠，正文不再复读全部历史分数。三分钟版的模型训练与权重说明占了一整段，可压成“流式拒识和车控 FC 职责不同，具体模型版本按项目核对”，完整权重说明留紧随其后的展开表；腾出的篇幅用于上面三场景的实际结果与失败分支，宣讲会更完整。

本人的 flow 补丁已按后续指令去掉热词上限、ASR 历史目标、历史耗时与命中率数字的正文复读，原数据仍在就地展开。音区表述已改为人数判断的一项线索，明确结合人脸、座椅压力，避免音区等同人数。
