# I 章真实 badcase 与事故

记录实际问题、讨论中的实测现象；设计示例单列，不计真实案例，未给出的根因与修复不补写。

计数：54 条案例/故障分组登记 = 4 条 BC 现状问题 + 21 条会议登记 + 29 条聊天故障分组；包含相邻一致性问题、汇总现象和工程缺口，**不是 54 个独立 bug 或事故**，无共同 bug ID 的同类表现仅关联。设计风险段与跨检索重复记录均不计数；逐条根因和改法缺证据时写明未给出。

## BC01：旧链路对插话反应慢
- 用户看到了什么：豆包说话时已收到新问题，却要等新问题的 TTS 开始才停旧话，紧急或重要请求不能及时获响应。
- 系统里发生了什么：播报期间持续收音，非简单车控由新一轮 TTS 到达触发打断；简单车控只叮一声、旧播报继续。
- 根因：PRD 描述的旧触发时机晚；未给更细代码根因。
- 怎么改：2.6 提出非拒识且非简单车控立即打断、简单车控结果暂等 1.5 秒；二月底实验版另改为识别超过两个字先停声；均是方案，原文未给验收结果。
- 来源：interrupt-prd.txt:5–13、31–41；真实既有问题描述，非单次事故日志。

## M0813-01：新旧任务回答 BAB / BABA 交错
- 用户看到了什么：导航等场景先听新任务 B，再听旧任务 A，又听 B；一条记录甚至 BABA。
- 系统里发生了什么：新 query 先回应，旧 query 的 feedback 随后触发旧任务结果，新 query 的 feedback 再触发新结果。
- 根因：BAB 是既有输入管理策略与架构问题；BABA 额外交错是否工程 bug 会议未确认。
- 怎么改：根治需调输入管理；当时只能考虑提示词压缩冗余、加强衔接；BABA 单独查 bug，演示前不动。
- 来源：m0813.txt:14–35、46–74，文字记录中的实际路测问题。

## M0813-02：任务被打断后没有回传、没有完成
- 用户看到了什么：插话之后原来的任务没有再给结果或完成反馈。
- 系统里发生了什么：会议只记录“被打断后没有再进行一个回传和完成”，未给任务日志与具体节点。
- 根因：未给出，不能直接写为 Planner 忘记或客户端取消。
- 怎么改：纳入打断专项与量产前必解项讨论，未给已完成修复。
- 来源：m0813.txt:19–20、40–47、73–74。

## M0813-03：旧搜索已失去价值，仍被恢复
- 用户看到了什么：用户从搜幼儿园改为问饭店，或自己打断旧问题后，系统仍把旧答案捞回播报。
- 系统里发生了什么：恢复未正确处理新旧任务的覆盖/补充关系；另有核心内容已播完却恢复后续废话。
- 根因：恢复价值与任务关系判断存在 badcase，不等于所有未播完内容都应恢复。
- 怎么改：按信息查询/控制/多结果搜索判断恢复节点；任务覆盖和补充时识别合并项；当时拟专项优化，未给上线结果。
- 来源：m0813.txt:38、58–74。

## M0813-04：真实路线与历史记录不同步
- 用户看到了什么：查询途经点时被回答半小时前的旧信息；水果店案例历史仍像未完成选点。
- 系统里发生了什么：最近五轮规划与历史对话完成状态、情景记忆内容不一致；纯语音路测同样发生。
- 根因：会议怀疑历史或摘要中的旧内容被参考，不能确定为单一屏幕上报缺失。
- 怎么改：查 log id 与上下文；提出用重要事件穿插对话替换摘要，并校验添加/删除变化，未提供验收。
- 来源：m0813.txt:97–116、148–152；属于历史与结果一致性的相邻案例，未证明由打断引起。

## M0813-05：只问路线时长，导航却被改了
- 用户看到了什么：询问 A 到 B 要多久后，地点进入当前导航途经点，用户需要改回路线。
- 系统里发生了什么：调用 route planning 后反馈“更新路线成功”，实际系统地图发生变化。
- 根因：会议提出查询/执行工具边界和下游 feedback 的疑点，具体工程根因未查定。
- 怎么改：查调用工具、前后台算路逻辑、执行与反馈；讨论查询工具单独设计和重要操作确认，未给修复验收。
- 来源：m0813.txt:128–239；执行结果一致性的相邻案例，未证明由打断引起。

## M0813-06：口头执行结果与实际结果相反
- 用户看到了什么：30 秒切歌被说做不到但仍建任务；加歌单被说已加入却找不到；开窗/氛围灯被说成功却未执行。
- 系统里发生了什么：音乐任务创建与口头能力说明矛盾，部分车控执行链未完成。
- 根因：会议将音乐问题归能力边界；开窗/氛围灯具体原因要求客户端查，未给确定结论。
- 怎么改：按执行记录和反馈排查；未给这几项修复验收。
- 来源：m0813.txt:940–962；结果一致性相邻案例，未证明由打断引起。

## M1013-01：赛力斯多人插话后高频不恢复
- 用户看到了什么：多人对话打断后旧播报不回来，整体体验被报告明显回退。
- 系统里发生了什么：测试已有相关 bug，但会议不能确认是否覆盖了整类问题。
- 根因：未查定；发言明确要求排查链路。
- 怎么改：高优跟进不恢复问题；同时调敏感度，但拒识后的恢复必须独立确保，未给已修复证据。
- 来源：m1013-sls.txt:811–887；赛力斯当时实车版本。

## M1013-02：打断过于敏感
- 用户看到了什么：车上正常体验中豆包频繁被打断。
- 系统里发生了什么：测试侧称有异常打断数据。
- 根因：未给具体模型、阈值或信号根因。

## M1013-04：主副驾连续表达情绪，只回应最后一人

## M1013-07：上游视线信号十次全为 not looking
- 用户看到了什么：视线测试连续给出“未看向”信号；原文未逐条列出用户视线真值，用户端具体误拒表现未给出。

## BC02：取消旧执行后仍产生新输出或落库
- 用户看到了什么：原文概述取消后仍可能有模型文本、工具调用或历史写入，未给单次用户话术或截屏。
- 系统里发生了什么：旧取消依赖本地上下文和轮询，无法保证跨实例出口都停。
- 根因：技术方案指出欠缺原子执行许可和正式输出身份校验。
- 怎么改：Redis 原子许可、每个输出/新工具/派生历史出口复核，Context cancel 仅加快退出；方案未给上线验收。
- 来源：input-tech.txt:34–38、530–536、570–573。

## BC03：端侧已接管但云端继续推理
- 用户看到了什么：有重复处理/反馈风险；本处未给单次是否实际重复播报的证据。
- 系统里发生了什么：端侧召回执行后未及时报告，云端并行链路仍算。
- 根因：接管上报延迟，云端缺请求级终止闭环。
- 怎么改：端携原 request_id 报完成，云端只终止目标输入和关联执行、保留其他等待输入，拒绝重复云端输出。
- 来源：input-tech.txt:176–182、556–558；与 input-prd.txt:638–665 历史端侧接管方案相关，非新增单次事故。
