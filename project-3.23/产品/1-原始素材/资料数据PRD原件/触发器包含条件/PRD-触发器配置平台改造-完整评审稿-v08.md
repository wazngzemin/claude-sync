## 1. 背景与需求

### 1.1 现在遇到什么问题

现有平台能配置场景、条件和动作，但新增任务不再只是“一个状态满足就发一个动作”。儿童锁要判断后排儿童或宠物，充电口盖要把停车前置与下游设备识别分开，闪念要理解已有画面描述并发送一句不打扰用户的文字。继续把这些需求塞进平铺条件，会出现以下问题。

| 实际业务问题 | 现有表达的不足 | 本次需要补什么 |
| --- | --- | --- |
| 后排儿童或宠物，任一种成立才建议开儿童锁 | 不能把两个分支、共同前置、目标锁状态讲成一张可执行关系图 | 条件与推理节点、分支汇合、唯一判断终点 |
| 判断“后排有人睡着”，但收到的是一句描述 | 不能虚构一个“睡着=true”信号；动态任务已收到描述也不等于预配置已接通 | 真实视觉目录、已有描述目标判断、预配置监听入口 |
| 闪念只需要显示固定文字 | 沿带卡推荐链路会引入不需要的 DT、确认按钮和播报 | 普通静默通知动作、Frontier 下发、客户端仲裁 |
| 配完没反应，不知道卡在哪里 | 保存成功、条件命中、频控通过、下游收到、真正展示容易混写 | 当次输入、判断结果、拦截原因和下游反馈分层记录 |
| 修改复杂规则担心影响原任务 | 定义、场景、车辆用户开关和历史记录容易被一起覆盖 | 独立复制、只读定义、新旧切换与用户 OFF 保持 |

10 月 14 日闪念会上明确：一期用已有模型判断目标是否达成，满足后发固定正文；不生成新文案，不带标题、按钮和 TTS。会议同时指出预配置视觉监听与普通通知下发存在接入工作。客户端已有文字容器可以先验证复用，但不能据此认定整条链路已经跑通。

### 1.2 产品是什么、不是什么

**触发器配置平台是供内部产品、业务、研发和测试使用的规则配置与排查后台，不是车主的任务中心，也不是工具编排平台。**它把已接入能力组合成可保存、可运行、可回看的场景。新任务能否只改配置，取决于真实输入、判断方式、动作和组合关系是否均已支持。

一条完整场景包含五部分：

| 组成 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 适用范围 | 这条规则给哪些车使用 | 赛力斯、指定车型与版本、测试车辆、泳道 |
| 启动与判断 | 何时开始检查；检查什么 | 舱内描述更新后，判断是否明确有乘客睡着 |
| 动作 | 满足后交给谁，交什么 | 普通通知正文，或带卡推荐的建议 Query |
| 执行策略 | 允许执行几次，多久再来 | 使用已确认统计范围的次数和最小间隔 |
| 运行证据 | 这次实际发生什么 | 输入、节点三态、频控、发送与展示反馈 |

简单模式用表单表达一条判断；Workflow 用有依赖关系的节点表达判断。两者**不以是否用模型、是否走 DT 区分**：简单模式也可判断已有描述；Workflow 也可以全部是状态比较。两种模式共用场景范围、动作和策略。

VLM 是产生画面观察结果的视觉模型；Caption 是它输出的文字描述。推理节点用已经收到的值或文字判断目标，不临时取图。DT 负责下游决策和工具调用；VQA 是 DT 按需调用的视觉问答能力。Workflow 本期不放 DT、VQA、卡片、用户确认或车控节点。

### 1.3 谁用平台，分别完成什么工作

| 使用方 | 进平台要完成的事 | 不应让其承担的事 |
| --- | --- | --- |
| 产品／业务 | 定义场景、目标、关系、固定正文或建议、策略；检查正反例 | 手写内部信号编码、系统提示词或通知 JSON |
| 配置人员 | 选择合法目录，搭建判断，核对范围，校验保存 | 靠猜测补没有接入的字段或枚举 |
| 研发 | 接入输入、判断、保存、动作与真实反馈；解释能力缺口 | 每新增一句通知都重新开发专用判断链路 |
| 测试 | 用当次定义检查满足、不满足、未知及下游异常 | 用人工模拟成功替代真实联调结果 |

车主仍在车机上开启或关闭自己的任务、回应当次建议。后台规则生效与车主的单任务开关分属不同层级，本次不把两者合并。

### 1.4 为什么现在做、做到什么程度

本期以系统预设任务和闪念一期为实际交付对象。先打通“已有描述 → 目标判断 → 固定普通通知”的最短链路，同时让儿童锁等复杂判断能配置、能解释、能排查。不是先做一套覆盖所有原子能力、端侧脚本、定时编排和车控的通用平台。

完成意味着：真实目录能选、非法配置能拦、目标环境能使用正确规则、运行记录能定位问题、普通通知和带卡建议各自走正确出口。可点击页面、保存回执或模型 PASS 单独出现，均不代表业务完成。

## 2. 目标与价值

### 2.1 给业务、研发和车主带来什么变化

业务可以复用相同输入、节点和动作，修改判断目标或固定文字，而不是为每个新场景重新讨论整条链路。研发能按明确边界接能力，避免 Trigger、DT 和卡片业务互相承接不属于自己的工作。测试能区分规则错误、缺输入、模型不确定、频控和客户端未展示。

车主获得的价值是：该提醒时提醒、不满足时不提醒、不确定时不乱提醒；不因描述反复上报刷屏，也不把闪念变成一次不必要的语音打断。

### 2.2 本期如何判断做对了

| 目标 | 验收证据 |
| --- | --- |
| 场景能准确表达 | 儿童／宠物分支和单视觉闪念分别保存、回读一致，不能只靠截图说明 |
| 能力边界透明 | 未接入输入、目录读取失败、非法比较符均可识别，缺能力不能正式发布 |
| 交互不会丢配置或误提交 | 改渠道／模式／动作有影响提示；错误保留输入并定位；取消不生效 |
| 运行可解释 | 能看到当次输入、节点状态与判断、唯一终点、策略和真实动作结果 |
| 闪念最短链路跑通 | 有真实描述、真实模型判定、Frontier 下发及客户端接收／展示证据 |
| 老规则不被改坏 | 简单、旧定时及既有动作保持原行为；复制和替换不抹掉用户 OFF |

不预设效率提升百分比。上线前记录典型配置的步骤、误填次数和排查耗时，供后续比较；这些数据不作为本期缺省编造的结果。

## 3. 本期范围与边界

### 3.1 保留原四项改造

| 需求 | 具体要求 | 不等于什么 |
| --- | --- | --- |
| 静态条件非必填 | 有合法启动和完整判断语义时可不填静态条件；判断全空仍拦截 | 任意空规则可运行 |
| 复制场景 | 生成独立场景和可编辑的新判断定义，不改原定义 | 复制运行历史、计数、发布状态、单车选择 |
| 指定泳道生效 | 保存、回读与运行均使用真实泳道范围 | 仅列表显示一个泳道标签 |
| 测试／正式筛选 | 与渠道、名称等共同筛选实际环境 | 改筛选条件就迁移部署 |

### 3.2 本次新增在哪里

| 模块 | 页面变化 | 运行或服务变化 |
| --- | --- | --- |
| 场景管理 | 模式、分类、范围和查看／复制入口 | 查询返回真实字段，保留原有分页和筛选 |
| 简单判断 | 元数据级联、视觉目标、依赖说明 | 保留旧判断；接入合法的已有描述判断 |
| Workflow | 画布、两类节点、两层关系、完整校验 | 注册与查询定义，按依赖运行、返回节点结果 |
| VLM 配置 | 来源、可用字段、枚举、文字目标和缺口提示 | 补元数据与预配置监听，不把动态任务转发冒充预配置 |
| 动作 | 普通通知固定正文；带卡建议输入 | 普通通知经 Frontier；带卡沿已有主动推荐链路 |
| 记录 | 当次定义、输入、节点、策略、动作和回执 | 关联场景、定义与一次运行，保存真实证据 |

### 3.3 本期不开放的能力

不新增 Workflow 定时节点、等待节点、时间窗或多轮结果聚合；保留旧定时能力，但不据此开放混合定时画布。不建设端云统一配置、端侧脚本热更新、通用车控画布或完整原子能力管理后台。不新增闪念动态生成正文、小模型或语义匹配降耗。

PHUD 图案与中控文字属于闪念整体业务，但图案映射、复用触发和同步责任未收口。本期不得把中控普通通知跑通写成 PHUD 已同步完成。天气任务的端侧闭环、本地状态保存不在本稿重新指定。

正式权限、发布、停用沿现有平台机制。新草稿、删除恢复和版本回退若无现成能力，需明确一期是否建设；HTML 本地缓存和撤销不代表正式能力。

## 4. 整体逻辑与架构

### 4.1 从配置到车辆端，各模块负责什么

![平台架构与职责](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v07/架构与流程/A1-平台架构.png)

| 层级 | 谁做什么 | 交给下一环的内容 |
| --- | --- | --- |
| 配置后台 | 展示真实目录，引导填写并定位错误 | 场景范围、判断、动作和策略 |
| 配置服务 | 完整校验、保存定义、关联场景、查询回读 | 正式场景与可查询的判断定义 |
| 输入提供方 | 端状态／Context 等提供已接入的值和描述 | 本车、信号、对象、值／文字及可取得的有效性信息 |
| Trigger 判断 | 按启动规则获得本次输入，执行简单或 Workflow 判断 | 满足、不满足、无法判断及原因 |
| 共用策略与动作 | 判断后检查频控与执行锁，调用场景配置的动作 | 固定通知，或下游建议与带卡参数 |
| 下游／客户端 | 受理建议或通知、仲裁、展示和后续业务 | 实际支持的接收、展示或业务回传 |
| 运行记录 | 将真实事件关联到当次定义 | 可定位、不过度推断的历史证据 |

输入“在 Context 中”、Trigger“能收到更新”、目录“可选此能力”是三件事，联调分别核对。只有关联单车任务的规则才检查该任务开关，普通闪念不默认依赖任务中心。任务状态读取失败不冒充关闭或默认开启。

| 来源 | 进入 Trigger 的方式 | 本次配置边界 |
| --- | --- | --- |
| 系统预设场景用既有观察 | 从已接入的端状态／Context 等读取对应值或描述 | 目录必须声明可用来源；预配置 Caption 监听需补接入 |

先选范围和配置模式，再填判断、动作和策略。点击提交先校验全部问题，通过后展示摘要。简单模式保存场景；Workflow 需先注册不可变定义，再与场景关联。保存失败保留编辑内容，提示失败阶段；只完成定义注册不显示整个场景已成功。

保存后回读核对模式、范围、节点／边、参数和策略。发布与车辆采用是下一层事实，按已有机制验收。改旧 Workflow 须复制成新定义；新旧切换、旧规则停用与用户 OFF 保持需一起落实，不能并行跑两份相同提醒。

### 4.4 “启动检查”和“条件满足”不是同一件事

启动输入回答“发生什么更新后开始检查”；条件回答“这次检查能否通过”。挡位从非 P 变为 P 是变化，当前挡位为 P 是状态。一直上报 P 不等于反复停车；缺少上一值时不能编造变化已发生。

| 配置情况 | 开始检查的输入 | 开始后要做的事 |
| --- | --- | --- |
| 简单模式有动态条件 | 动态条件涉及的信号更新 | 检查动态变化及全部附加条件 |
| 简单模式无动态条件 | 现有设计中当前条件涉及的信号更新 | 检查完整当前条件 |
| 单个已有描述目标 | 已配置描述来源更新 | 以本次可用描述判断目标及前置 |
| 多分支 Workflow | 全图输入汇总与唤醒语义需运行方定案 | 按依赖执行图，不能再重复跑旧条件链路 |

页面分别展示“使用的输入”和“实际启动检查的输入”。不能只生成依赖列表就宣称已订阅。儿童任务若只在进入 D 检查，之后新识别儿童是否补提醒必须业务明确，后台不擅自扩大。

使用 workflow_id 的场景只走 Workflow，空值走旧链路。一次新输入建立一次运行，不把上一次节点 PASS 直接带入本次。输入的新鲜度和同次快照边界由接入方确认；定义缓存时长不是画面有效期。

### 4.5 判断如何走到动作

条件节点比较合法字段；推理节点判断已有描述是否达成目标。结果分三态：PASS 满足、REJECT 明确不满足、UNKNOWN 无法判断。缺值、过时、读取失败、模型异常或无法解析不能变成“没有儿童／没有雨”。

Workflow 唯一真实终点给出最终判断；节点不直接发通知。整图收敛后，终点 PASS 再经过共用策略与执行锁，之后才发送 Action。单场景锁不自动解决多场景或一任务多规则重复提醒。

![普通通知与带卡建议出口](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v07/架构与流程/A1b-动作出口.png)

普通通知发固定文字，不进 DT、不等确认；带卡建议交给现有主动推荐链路。儿童锁、后视镜无需额外设备 VQA，不代表 Trigger 自己调车控。充电口盖需要 DT 先查设备再询问；设备结果和确认处理不画回 Trigger 判断图。

## 5. 原型页面与交互要求

### 5.1 页面组织及原型使用方式

沿实际平台保留菜单、渠道和场景管理、新建场景、触发记录。配置页采用五步页内导航：基础与范围 → 判断 → 动作 → 策略 → 校验保存。Workflow 只替换判断区域，闪念复用普通通知动作区，不新建两套后台。

#### 5.5.2 结构化字段怎么配

![S06c 同一乘客的位置与年龄条件，上部](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S06c-结构化VLM位置与年龄字段.png)

| 字段 | 设计值域／比较符 | 页面要求 |
| --- | --- | --- |
| PassengerInfos[].Position | 主驾、副驾、左后、二排中、右后、中控扶手区域；设计比较符为等于 | 定位同一乘客对象；按实际目录显示位置 |
| PassengerInfos[].Gender | 男、女、未知；等于、不等于、包含 | 只提供声明支持的操作；“未知”与字段缺失不同 |

“存在一个后排儿童”必须是**同一个乘客的位置在后排，且年龄属于婴儿／儿童**。不能取主驾的儿童年龄拼接后排成人的位置。后台保存与实际求值都要保留对象关联，只有界面把两行放在一起不算完成。

截图支持 Position 多选，但技术元数据设计仅声明等于。正式页面须使用合法等于组合表达位置备选，并保留同对象约束；若服务暂不能表达，阻止该配置并说明缺口，不能提交未经声明的 in。AgeRange 的集合选择则按目录支持执行。

Context 位置名称与页面中文可能不同，需按协议映射：后方正中对应二排中、副驾后方对应右后、主驾后方对应左后；主驾与副驾对应各自座位。中控扶手等未完整确认的映射继续核对，不能靠文案猜编码。

#### 5.5.3 已有描述推理怎么配

![S07a 输入来源、判断目标与业务描述](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S07a-推理节点输入来源与目标.png)

| 字段 | 配置人员填写什么 | 保存与运行规则 |
| --- | --- | --- |
| 节点名称 | 如“后排宠物判断” | 用于图与记录识别，不代替判断目标 |
| 已收到的推理输入 | 从当前渠道目录选 Objects 描述或指定 Caption | 不手填虚构信号 ID，不串用其他任务／车辆结果 |
| 判断目标 goal | 一次可判断的问题，如是否明确有后排宠物 | 必填；不能混入取图、出卡、执行车控或生成正文 |
| 原始判断描述 original_query | 用业务语言补充目的、对象与边界 | 解释目标，不强制粘贴模型系统提示词；与目标矛盾时提示修正 |
| 输入依赖说明 | 系统随选择生成 | 显示来源及接入状态；不能由用户随意改成“已接通” |

推荐目标：“根据当前舱内物体描述，判断是否明确有位于后排的宠物。”正例描述明确后排有狗；反例明确只有物品且没有动物；画面遮挡、位置不明、无法辨认或描述没提供足够证据，归 UNKNOWN。以上是判断边界和测试样本，不是把“狗”写成关键词硬匹配。

![S07b 缺输入、过时、失败和不可解析的处理](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S07b-推理节点目标与UNKNOWN边界.png)

推理只消费本次已收到的描述。输入未到、不属于该车／来源、超过已确认时效、模型超时、结果矛盾或解析失败，均不允许伪造 PASS。明确未达成是 REJECT，无法确定是 UNKNOWN。技术草案中出现的“包含达成”式匹配不能作为产品验收依据，“未达成”不得误判成“达成”。

模型输出只要求稳定可解析的判断及实际可取得的原因，不新增任意置信度滑杆，不要求保存完整思维过程。输入时间戳、新鲜度阈值和超时由接入方给出，本稿不把历史 10～20 秒估计、定义缓存 5 分钟或动作间隔当作视觉时效。

#### 5.5.4 哪些变化要清理旧值

改信号后清理不兼容字段、比较符和值；改描述来源后标记目标与业务描述需复核，不能保留旧试跑 PASS。若目标可复用，应提示核对而不是无条件删掉人工文字。切渠道重新取目录；取消切换保留旧配置。输入依赖和摘要随实际选择同步，不允许画布、表单、提交内容三份不一致。

### 5.6 Workflow：用判断图表达分支，不把后续业务塞进来

#### 5.6.1 何时用、如何开始搭建

有共同前置、多条替代分支或依赖关系时使用 Workflow；一个视觉目标加一个动作仍可用简单模式。简单与 Workflow 各保留编辑内容，但不承诺自动无损转换。切模式需提示，取消不变；未提交模式不影响现有线上规则。

搭建顺序：增加共同前置 → 增加独立判断分支 → 连接到真实终点 → 设置前驱关系 → 校验 → 核对画布外动作。节点卡片展示类型、名称、关系和关键条件摘要，选中后在属性区编辑；窄屏时属性移至画布下方，不能压缩成不可读侧栏。

#### 5.6.2 两类节点要填什么

![S06 条件节点属性上部，需与下图合看](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S06-条件节点完整属性.png)

![S06b 属性滚动区下部，各条条件分别配置](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S06b-条件节点后续条目.png)

| 节点 | 必填内容 | 允许表达 | 不允许表达 |
| --- | --- | --- | --- |
| 条件节点 | 名称、至少一条合法条件、本节点关系 | 已有状态值比较；合法变化条件按现有能力 | 用不存在的宠物／睡眠布尔标签代替描述 |
| 推理节点 | 名称、合法输入、goal；业务描述按定义要求 | 对本次已有文字判断是否达成 | 调 VQA、生成卡片、控制车辆、等待用户 |

条件字段和枚举复用简单配置，不能另维护一套不一致字典。根节点不需要人工输入前驱；前驱汇合默认 AND，少于两个前驱不开放 OR。节点必须有真实判断，不能仅写“开始”“通过”“结束”充当可运行节点。

#### 5.6.3 两层 AND／OR 分别是什么意思

![S08 前驱任一满足与本节点全部条件是两个独立选择](/Users/bytedance/Desktop/3.23/产品/1-原始素材/资料数据PRD原件/触发器包含条件/图文PRD-v08/原型截图/S08-前驱OR与节点内部AND.png)

“前驱汇合”回答上游怎样才允许本节点开始；“本节点内条件关系”回答本节点自己的条件怎样满足。例如儿童与宠物任一 PASS 后，允许终点检查“目标锁未开”；不是儿童 PASS 就直接执行动作。

| 前驱关系 | 上游情况 | 本节点行为 |
| --- | --- | --- |
| AND 全部 | 全 PASS | 开始自身判断 |
| AND 全部 | 有 REJECT | 不运行，按不满足阻断 |
| AND 全部 | 全部结束、无 REJECT、有 UNKNOWN | 不运行，按无法判断阻断 |
| OR 任一 | 有 PASS | 允许开始自身判断 |
| OR 任一 | 全部结束、无 PASS、有 UNKNOWN | 不运行，按无法判断阻断 |
| OR 任一 | 全 REJECT | 不运行，按不满足阻断 |

OR 允许提前启动后继，但不取消其他分支。按技术设计，整图等待所有节点终态后，取唯一终点有效结果；不是多数投票，也不是收到第一个分支结果就下发动作。慢分支的超时与迟到返回须处理，不能覆盖已终结结果或重复发送。

#### 5.6.4 画布操作和结构校验

| 操作 | 页面反馈 | 校验与保护 |
| --- | --- | --- |
| 加节点 | 增加条件或推理节点，选中打开属性 | 系统管理标识，复制节点须独立，不复用运行结果 |
| 接线 | 从起点到终点，显示方向 | 禁止自连、重复边、无效端点和循环 |
| 删边 | 说明后继依赖变化，立即更新前驱数量 | 剩一个前驱恢复 AND；孤立和多终点重新提示 |
| 删节点 | 提示关联连线会一起删除 | 保留其他节点；不留下指向已删除标识的边 |
| 拖动／缩放／适应 | 只改视图位置 | 不改变判断含义、前驱关系或输入值 |
| 撤销／重做 | 原型图结构可撤销，恢复节点和边关系 | 不承诺所有表单文字由图级撤销恢复；产品界面说明边界 |
| 校验判断图 | 一次列出全部错误，点错误定位 | 保留未提交内容，不因报错清空画布 |

完整图必须满足：每个节点内容合法；全部节点都能到达唯一真实判断终点；无孤立分支、无循环、无空节点、无多终点。空白“汇合”不是第三类节点。前端预校验不能代替服务端注册前完整校验；服务端失败应返回可定位的问题，不生成可用定义 ID。

本期没有时间节点。AND／OR 不能表达“先停车，再持续 10 秒”“过去多帧一直睡着”。若需要持续或多轮判断，作为新增能力另行定义，不用最小触发间隔冒充。

#### 5.6.5 保存与运行状态怎样展示

保存后的 Workflow 定义不可变，查看时只读；修改通过复制新定义完成。场景 ID 表示规则主体，Workflow ID 表示判断定义，Run ID 表示一次运行。复制不带历史、次数或单车开关；是否替换旧场景以及用户状态如何继承，必须在发布前确定。

运行状态与判断结果分栏：等待、可运行、运行中、已完成、异常、未运行，不能统称“失败”。正常执行结束也可能 REJECT 或 UNKNOWN；基础设施异常对应 UNKNOWN；被前驱阻断的节点显示“未运行＋阻断来源”，不伪造自身执行输入与耗时。

当次图以当次定义和输入解释结果，不用最新编辑内容覆盖旧记录。并发数是运行资源约束，当前不新增面向产品的自由调节项；反复点击不应把同次运行变成多次下发。

#### 6.1.1 一期必须覆盖的正反例

| 本次输入或情况 | 判断／处理 |
| --- | --- |
| 明确描述后排乘客正在睡觉，来源正确且有效 | PASS；策略通过才发送固定正文 |
| 明确乘客清醒、在说话，没有睡眠 | REJECT；不发 |
| 只说闭眼，无法确定；画面被遮挡；输入缺失 | UNKNOWN；不发，不写“没人睡觉” |
| 收到别的车辆、别的任务或过时描述 | 不作为本次有效依据，记录具体原因 |
| 一直睡眠，描述反复上报 | 仍按正式频控；不得每次上报都刷屏 |
| 用户正在说话或高优先级内容占用 | 按本版本明确的避让策略处理，不擅自覆盖 |
| 通知等待后乘客已经清醒 | 必须按已确认时效处理过时内容；不能延迟显示旧事实 |
| Frontier 调用成功，但客户端未取得／未展示 | 只记真实阶段，不标最终展示成功 |

会议明确当前仲裁以覆盖为主，排队是后续规划。低优先级、不打断是产品要求；本版本能否排队、等待多久、何时丢弃需客户端与交互侧确认。Trigger 不单独再做一套客户端队列。

#### 6.1.2 闪念具体需要开发什么

预配置规则新增已有视觉描述的监听与取值；复用现有模型目标判断；新增普通通知动作及 Frontier 参数；客户端先验证现有文字容器，满足则复用、不满足列适配；补齐实际可取得回执和联调记录。丁彬负责视觉生产范围确认，不自动负责整个业务判断链路；谢一鸣对接客户端，姜锋提供通知协议，刘杨对齐云端接入，具体新增工作量需团队认领。

景象闪念必须先确认真实描述覆盖，不从“舱外天气描述”直接推导“所有风景可识别”。PHUD 的图案、ID 和时机另行对齐，不把睡眠例子写成已存在 PHUD 场景。

### 6.3 充电口盖：前置判断和设备识别分开

Trigger 配置合法进入 P 的启动及任务许可、SOC、口盖未开等前置。SOC 是电量百分比；技术案例的 ≤20% 为样例，最终阈值由任务需求确定。关系简单可用简单模式，使用 Workflow 也只放前置判断。

前置 PASS 后提交“检查周边充电设备，明确发现再询问是否开盖”的建议。DT 调 VQA，未发现或未知不询问；明确设备后沿既有出卡与确认链路处理。Trigger 不接收设备结果继续编排，不直接开盖。

反例：SOC 缺失不能当 0；一直处于 P 不反复当停车；盖已开不建议；未知设备不能写成已发现；单次拒绝不关闭长期任务。用户回答后车况复核属于下游执行业务，不新建 Trigger 二次校验节点。

### 6.4 后视镜加热：已知天气描述判断，无需新设备 VQA

配置已确认适用车况、真实加热状态与已有舱外天气描述。推理节点判断下雨等业务目标，通过后交给带卡推荐；无需额外设备识别，不等于 Trigger 获得车控工具权限。

天气明确无雨是 REJECT，输入缺失或无法判断是 UNKNOWN；加热状态未取得不能当关闭。技术案例的 P 挡与速度限制仍需解释业务意义，加热状态来源需核对。技术稿已划除的湿度、温差分支不恢复；退出传送带洗车没有已确认信号，不编造条件。缺口未补齐的分支不进入正式发布。

## 7. 核心异常与完成标准

### 7.1 按六层分别验收，不用一个“成功”

| 阶段 | 证明什么 | 不能据此推断 |
| --- | --- | --- |
| 配置保存 | 服务返回成功并回读一致 | 已发布、已被目标车使用 |
| 发布生效 | 目标环境采用正确规则，非目标不运行 | 已命中或已发消息 |
| 判断完成 | 当次输入、节点和最终结果可核对 | 频控或执行锁已放行 |
| 动作发送 | 真实出口调用与返回结果 | 下游已接收或用户已看见 |
| 下游接收 | 有真实受理／客户端接收证据 | 已展示或已执行车控 |
| 展示与后续 | 实际展示、用户选择、车辆状态等真实反馈 | 无回传也可默认成功 |

正式带卡动作的模拟能力以技术方案为准，不能拿本地模拟替代联合联调。普通通知不适用用户确认／车控阶段。无展示回传时明确“未取得反馈”，联调通过客户端日志补证，不伪造埋点已具备。

### 7.2 配置和保存异常

| 问题 | 页面如何提示／恢复 | 验收重点 |
| --- | --- | --- |
| 目录请求失败 | 保留已填项，显示失败和重试 | 不变成暂无数据、不换演示目录 |
| 目录没有能力 | 说明本渠道未开放 | 不允许手写绕过发布校验 |
| 改上级残留旧值 | 清理不兼容项并提示复核 | 提交体与可见内容一致 |
| 同对象关系无法表达 | 指出节点及限制 | 不跨乘客拼接，不提交非法 Position in |
| 图有多处错误 | 一次列出，逐项定位 | 无环、无孤立、唯一真实终点 |
| 定义注册失败 | 不生成可用 ID，保留草稿输入 | 不提交半个图 |
| 定义已注册，场景关联失败 | 分阶段提示，重试避免重复创建 | 不假成功，不破坏原生效场景 |
| 保存后发布失败 | 明确已保存但未发布 | 不把保存按钮结果当运行生效 |

### 7.3 运行、模型与并发异常

| Case | 预期结果 |
| --- | --- |
| 非启动信号更新 | 按已收口启动清单处理，不凭依赖列表随意启动 |
| 有变化条件但缺旧值 | 不编造变化，记录无法判断原因 |
| 信号缺失、来源错误、视觉过时 | 记录具体无效原因，不用缺省 0／OFF 替代 |
| 模型回答“未达成” | 不解析成 PASS；明确负向与不可解析分开 |
| AND 有 REJECT；OR 一个 PASS | 按 5.6 传播；后继仍判断自己 |
| OR 一个 PASS，另一分支慢 | 不取消分支，整图收敛后按终点结果处理 |
| 节点超时后迟到返回 | 不覆盖终态、不重发动作，保留真实迟到记录 |
| 终点 PASS，频控不通过或锁未取得 | 不调用下游，显示策略原因 |
| 多条规则对应同一任务 | 单场景锁不能冒充全任务去重，需单独验证 |
| 修改定义后查询旧运行 | 仍显示当次快照，旧事实不被清空 |

不把历史动态观察任务容量套成 Workflow 节点数；不把单次判断扩写为多轮时间聚合。资源上限、超时、重试和新旧输入并发策略需运行侧明确，页面不能通过任意新增阈值解决。

### 7.4 业务与交互联合验收

儿童同对象正反例、宠物未知和锁已开均覆盖；充电低电边界、缺 SOC、设备无／未知和用户取消均覆盖；后视镜缺天气或加热状态阻断；闪念持续描述、容器占用、过时内容、发送成功但未展示均覆盖。

后台状态、AI 总许可、某车某任务开关和本次确认分开。已有云端设计的“无记录默认开启”必须建立在查询成功确实无记录之上，查询失败不能冒充无记录。普通更新和替换不能抹掉用户 OFF。徐燃的 AI 设置不是单任务状态保存人，本稿不重新指定端侧持久化责任。

每个已通过 Case 保存配置版本、输入样本、节点／策略结果及真实回传证据；被阻塞项写具体能力缺口和责任确认，不用“待联调”概括所有失败。

## 8. 实施顺序与评审待定项

### 8.1 分批做什么

第一批先验证闪念最短链路：确认一条真实舱内描述，预配置接入、模型三态、普通通知协议、Frontier 和客户端展示；同时验证无输入、重复、占用、迟到反例。固定正文可以先于全部 Workflow UI 交付，但优先级和排期由项目确认。
