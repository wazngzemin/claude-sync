### 01:36:10—01:47:50：天气路况保护与端侧二次确认

- 只有无法通过云端继续闭环、又确实需要离线语音确认的少数业务，才单独注册；
- 不计划为可见即可说专门新增小模型做泛化，业务需要补自己的泛化词。

会议同时确认：当前所有即时交互卡并不是已经自动注册了可见即可说。需要该能力的业务必须单独接入。

### 01:47:50—01:52:18：端云切换和离线状态是否让用户感知

张嘉锋继续追问：车辆网络忽有忽无时，是否简单采用“有网 Planner、无网本地”。

徐洋说明不是简单二选一：

- 云端超过约 3 秒未返回时，采用离线结果；
- 离线转在线后，期望重要上下文能够重新同步到云端；
- 但上下文是否重复同步、研发当前如何实现，需要继续确认。

随后讨论用户是否需要明显感知离线状态：

- 张嘉锋担心离线时能力下降，但用户不知道为什么；
- 徐洋、苗雪晴倾向不在 ASR 等交互中强化离线状态，网络图标即可；
- 韩杰认为行业通常尽量通过缓存和兜底，让用户感知保持一致，而不是主动强调没网。

徐洋提到当时端云仲裁优先级：

1. 本地高频缓存；
2. 白名单 Function Call；
3. 云端 Planner；
4. 本地非白名单 Function Call，主要作为断网/超时兜底。

本段结论：

- 暂时维持端云体验尽量一致，不额外强化离线提示；
- 网络图标承担基础网络状态表达；
- 离线转在线的上下文同步机制仍需研发确认；
- 张嘉锋保留“离线能力受损但用户无感”的体验风险，后续观察。

### 01:56:58—02:01:30：任务频控和连续拒绝后的防打扰

陈敏询问系统预设任务多久触发一次，以及用户连续拒绝时有没有防打扰。

当前能力现状：

- 在线任务可以在后台配置一次上电周期执行几次、间隔多久等频控；
- 离线任务当前由产品定义、端侧研发写入代码；
- 长期目标是平台配置后同步到端侧执行；
- 当前没有基于用户连续负反馈的正式防打扰策略。

讨论过三个方向：

1. 连续拒绝多次后自动关闭任务中心开关；
2. 连续拒绝后进入静默期，过一段时间再允许推送；
3. 只限制每个上电周期的推送次数。

陈敏指出，第 3 种只是系统频控，不是根据用户反馈调整；直接自动关闭开关也比较粗糙。

徐洋补充：赛力斯专家任务集可能已经写了“连续拒绝几次后不再推”，这可能会成为验收条件。如果本期没有能力，王泽民必须提前向赛力斯产品澄清。

本段没有确定最终产品方案。明确待办是：

- 核对赛力斯正式验收要求；
- 把“基础频控”和“负反馈防打扰”拆开定义；
- 本期不支持时形成双方确认的范围说明。
