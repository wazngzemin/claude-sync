# 总览

## 模块综述

**对话推理引擎/Director模块**是AI汽车1\.0中的核心模块，是全链路中的对话中枢和推理中枢。

**模块职责：**

1. 与用户交互：负责和用户的响应聊天、话术衔接、话术总结（话术自然简洁、性能佳）

2. 结合context（包括当前情景感知、端状态、用户记忆等）对**用户输入**、**主动服务建议**、**工具返回**进行推理，形成可执行的任务序列，达成 “需求解析 \- 任务规划 \- 执行反馈 \- 动态修正” 的闭环

**模块输入：**

1. user query：（示例）\{\&\#34;query\&\#34;:\&\#34;我好热啊\&\#34;,\&\#34;speaker\_name\&\#34;:\&\#34;晓伟\&\#34;,\&\#34;speaker\_position\&\#34;:\&\#34;主驾\&\#34;\}

2. Advisor input：（示例）\{\&\#34;advisor\&\#34;:\&\#34;晓伟上车了，车内温度比较高，可以调整一下空调温度快速降温\&\#34;\}

3. Tool feedback：（示例）\{\&\#34;tool\_feedback\&\#34;:\&\#34;截至 2025 年 1 月，浙江共有 22 家 5A 级景区。具体如下：……\&\#34;,\&\#34;tool\_name\&\#34;:\&\#34;web\_search\&\#34;\}

**模块输出：**

模块输出包括与用户的对话交互内容以及可执行的任务序列

（示例）

\{

\&\#34;talk\_or\_not\&\#34;:\&\#34;yes\&\#34;,

\&\#34;talk\_content\&\#34;:\&\#34;好啊，我先帮你找个招商银行\&\#34;,

\&\#34;action\_list\&\#34;: \[

\{

\&\#34;action\_id\&\#34;: \&\#34;1\&\#34;,

\&\#34;action\_content\&\#34;: \&\#34;附近的招商银行\&\#34;,

\&\#34;tool\_name\&\#34;: \&\#34;search\_poi\_qa\&\#34;\}\]

\}

**主要解决什么问题：**

1. 对于一些复杂、多步任务，需要用户一直给输入，模型缺失需要的上下文，比如：

    - 口味偏好

    - 冷热偏好

    - 价格偏好

    - ……

2. 很多时候，用户只有一个大目标，没有小目标/明确目标（比如关于具体要做什么的更细化的需求），或者不知道功能怎么用：

    - 想让座舱更舒适，但具体现在应该怎么操作呢？

    - 想在行程途中找一个充电站，但得考虑到达电量、顺路程度、价格、空闲桩，好头疼，怎么办？

    - 这次OTA更新了全域的领航辅助驾驶、还更新了个什么智能光毯，具体该怎么用呢？

3. 检索到想要的东西很费劲：

    - 搜一个我想看的电影，很费劲，用户需要花大把的时间在分类搜索上，能不能结合我的偏好和当前的语音指令把这件事搞定？

    - 搜一个车内乘客都想吃的餐厅，很费劲，能不能把我们的需求都告诉豆包，基于位置，来给我一些最优的推荐？

4. 我讲一句，它应一句，用户的需求被处理成了一锤子买卖，导致需求不闭环

5. 当前的人机互动聊不下去，割裂、没内涵：

    - 不知道舱内外实际发生的情景

    - 不知道车辆实际所处的状态

    - 不知道正在做的事情（任务的进行状态）

    - 触发器的下游包括：

    - 对话推理引擎收到工具返回后，结合context进行二次推理，决策是否需要生成交互内容或任务序列

# 详细需求

## 对话需求

### 话术策略

对话推理引擎在收到user query、advisor input或tool feedback后，需要判断是否需要和用户进行交互，如需要，则生成对话内容。

**重要原则：**

1. 对话内容定义：想和用户说的话，按需生成，不需要和用户交互时可以不生成。

2. 总体要求：

    1. 对话和推理一体，主要目的为：

        1. 解决过去闲聊场景的痛点：

            1. 聊天内容和车辆的情景、状态、任务割裂，没内涵

            2. 不能结合情景做动作（真正的闲聊很少，大部分对话还是和车状态/任务相关，比如我准备接朋友去吃个饭，很容易进入闲聊）

        2. 保持说做一致

            1. 内容上的说做一致

            2. 节奏上的说做一致[\[需求\]【AI汽车\-3月演示】多轮任务 工程逻辑优化（进3月8日版本）](https://meego.larkoffice.com/telematics/story/detail/6859515038)

    2. 快速响应：对话推理引擎需要快速响应用户，性能目标跟随整体要求

    3. 生成的对话内容需要自然（不机械生硬、有过渡）、简洁（不啰嗦、不重复）

3. 策略细节：

    1. 对话内容需要有意义，在端状态查询问答、记忆查询问答、简单联网问答、简单的单指令/多指令车控、单步复杂车控等场景中，无需生成无意义的响应话术：

        - 示例1 query：空调现在是开的吗

        - 示例1 bad case：我帮你查一下

        - 示例1 good case：（查到后）空调现在是开着的

        - 示例2 query：上海上一次人口普查有多少人啊

        - 示例2 bad case：我帮你查一下

        - 示例2 good case：（查到后）根据第七次人口普查结果，上海市常住人口约2487\.09万

    2. 响应话术无需把做什么介绍的清清楚楚（目的：缓解内容机械生硬感和幻觉问题）

        - 示例 query：刚打完球好累好热，帮我凉爽放松一下

        - 示例 bad case：好的，我先帮你把座椅按摩和座椅通风打开，开启全身按摩，然后把氛围灯调成冰川色，空调温度也调到15度，酷爽放松氛围马上就来

        - 示例 good case：好的，我先帮你把座椅按摩和座椅通风打开，顺便调一下氛围灯和空调，酷爽放松氛围马上就来

    3. 响应话术和总结话术的内容重复率低：

        - 示例 query：我好热

        - 示例 bad case：（响应话术）我来帮你把空调打开并把温度调到最低，顺便帮你把座椅按摩也开了；（总结话术）空调已经打开啦，温度也调到最低了，座椅按摩也打开了

        - 示例 good case：（响应话术）我来帮你把空调打开并把温度调到最低，顺便帮你把座椅按摩也开了；（总结话术）都搞定啦

    4. 当需要在说话中带一些语气情绪（比如开心、生气、疑惑、撒娇、冷淡等）时，可以直接在“talk\_content”中的对话内容前加方括号\[\]，例如\[开心地说\]、\[生气地说\]、\[疑惑地问\]、\[撒娇地讲\]、\[冷淡地回应\]，以此来表达相应的情绪。如果需要模仿特定角色、方言或唱歌，也可以在\[\]中注明，如\[模仿孙悟空说\]、\[用四川话说\]、\[唱一下\]。eg：

        - \[模仿林妹妹的声音说\]偏这日子总不遂心，倒教人心头添了几分怅然，连窗边的花都看着蔫蔫的。

        - \[用悄悄话说\]后排的小伙伴睡着了，我们把音乐声调小一点，说话也轻声一些

        - \[生气地说\]这破导航又罢工了，气死我了

        - \[兴奋地说\]哇，我们要去迪士尼做公主吗？

        - \[深情地唱\]我想这样牵着你的手不放开，爱可不可以简简单单，单纯没有伤害\~

    5. 下游根据标签内容来选择播报工具（唱歌工具当前暂无，需求pending）：唱相关的调用唱歌工具，其他情况调用sami tts



### 讲话风格（草稿）

允许用户切换豆包的讲话风格，可选项包括以下七种：

用户可通过方向盘旋钮快速切换豆包的基础讲话风格，在每一种讲话风格下，有**长期且动态的独特对话记忆**。

### 跟进任务

#### **跟进任务的定义**

任务无法在一轮即时连续的react中闭环，且被其他任务打断后恢复价值高，需要后续跟进：

- 正例：

    - 接下来的行程里，你持续给我介绍下沿途的风景

    - 帮我点一杯咖啡送到公司

- 负例：

    - 把氛围灯按照彩虹的颜色给我演示一遍（可以在一轮即时连续的react中闭环，被打断后恢复价值不高）

    - 给我研究一下最近大模型领域的SKILL吧（独立执行，不会被其他任务打断）

#### **体系能提供的能力/解决的问题**

1. 具备目标跟踪能力：目前系统缺乏对于整体目标的管理，对话推理引擎的触发依赖user query和advisor的建议，非长期目标驱动的；

2. 多线程任务并行能力：对话推理引擎为单线程工作模式，整套系统不具备多线程任务并行的能力；

3. 动态适应能力：在目标推进过程中，系统能够适应舱内外环境和用户需求的动态变化；

4. 一套统一的框架，能够兼容之前聊过的“定时任务”、“条件任务”和“长时任务”（这几类任务具有一定的共性：1、需要后续跟进；2、需要触发条件；3、有自己的目标）；

5. 缓解系统对对话推理引擎的依赖：对话推理引擎需要在性能和质量之间找到平衡，兼顾所有的事情有挑战。advisor可以承担更多重思考、实时性要求不高的事情，为整体任务闭环和目标达成负责；

6. 涌现能力：只有在一定程度上将职责分散（分散意味着更少的输入和限制），才能最大化模型的涌现能力，呈现更好的场景。

#### 方案概述

针对以上问题，提出目标和动态advisor的驱动方式。

**期望实现的体验描述：**

- 系统能够快速地响应用户

- 准确理解用户需求，生成动作和目标满足需求

- 对于需要跟进的任务，有一套通用的方法实现目标跟进（包括被打断后能够恢复），目标的闭环率高

**做法：**

- 对话推理引擎和advisors共同维护一套goal list

- knowhow和context注入advisor，advisor去关注目标是否达成（重思考、轻时延）

- 需要和用户交互或者执行动作推动目标时，由advisor将建议给到对话推理引擎

- advisor具备可调用的信息获取类工具，比如联网检索、端状态查询、用户记忆查询等

##### 动态advisor

Q：动态advisor和静态advisor（舒适、内容、出行、情感）的区别

A：静态advisor分别对用车场景中的常态目标负责，可以理解为是永久合同监工；动态advisor由对话推理引擎根据user query或advisor建议来创建，可以理解为是临时合同监工，一般来说有明确的生命周期，并不是一直存在的。

Q：什么情况下会创建动态advisor

A：动态advisor与目标绑定，每创建一个新的目标，就会生成对应的动态advisor，一个目标对应一个动态advisor（基于动态advisor prompt模板）。

Q：目标和动态advisor的创建逻辑

A：目标和动态advisor由**对话推理引擎**根据user query或者advisor建议来创建。一些典型的query包括：接下来的行程帮我介绍沿途的风景、帮我照顾一下二排的宝宝、给我点一杯咖啡送到公司（跟进任务正负例：[元旦后演示冲刺 planner种子数据\&amp;knowhow](https://bytedance.larkoffice.com/wiki/WTPIwriowis0vNkETBfcpyTLnob?sheet=nqFKpP)）

Q：目标和动态advisor的注销逻辑

A：目标和动态advisor的注销逻辑包括：1、动态advisor判断目标达成；2、用户主动取消

Q：动态advisor的生命周期

A：从动态目标创建开始，到目标达成或用户主动终止结束。

##### goal list

Q：goal list的数据结构

A：goal list中存储了现存的目标以及目标的细节和进展，举例如下：

```JSON
[
  {
    "目标": "照顾二排宝宝",
    "目标状态": "进行中",
    "目标细节和进展": "当前宝宝情绪平稳，看起来睡着了，持续监测中"
  },
  {
    "目标": "每5分钟播报一下今天的NBA赛况",

    "目标细节和进展": "已完成咖啡品类选择，等待用户确认杯型"
  }

```

Q：goal list中各个字段的维护原则

A：目标的创建由**对话推理引擎**完成；目标的删除**由对话推理引擎根据用户语义**完成，或者**由动态advisor判断目标完成后**完成。目标状态的更新由动态advisor完成。目标细节和进展的更新由动态advisor完成。

## 冲突处理策略

当前系统中，可能存在多种类型的任务冲突，例如：

- 新的人机对话与正在进行的人机对话播报或任务之间的冲突：“讲下今天的AI新闻”\-\-\-\&gt;“车里快热死了”

- advisor建议和用户人机对话之间的冲突：“讲下今天的AI新闻”\-\-\-\&gt;“advisor：xxx”

- 触发器条件任务和用户人机对话之间的冲突：“讲下今天的AI新闻”\-\-\-\&gt;“\[车外温度超过30度时打开座椅通风\]条件已触发”

- 系统级通知和用户人机对话之间的冲突：“讲下今天的AI新闻”\-\-\-\&gt;“电机故障，请靠边停车”

- ……

这些冲突有些存在于**推理阶段**，比如用户刚讲完话之后立马来一条advisor的建议，这类问题可以在推理阶段避免；有些存在于**播报阶段**，比如豆包已经在播报时来了一条新的用户query，这些必须在播报阶段解决。

针对这些问题，需要有一套机制，避免因为新任务产生，导致旧任务被打断，从而产生系统自我分裂的混乱状态。

> 参考：[全局任务交互管理机制梳理](https://bytedance.larkoffice.com/wiki/QkA9wPqfNiX2j4kRqJicODfcnDd?from=from_copylink)、[planner 任务打断和任务状态管理](https://bytedance.larkoffice.com/wiki/RP4Zws29TiVZTPkBJ2kcrUUQnX1?from=from_copylink)

本小节只讨论交互阶段的冲突，该前提下仅需要和用户交互时才会产生冲突。如果不需要和用户交互，系统仍然可以在后台同时运行多个任务（比如GUI、生图等场景）。



按照新任务优先级由低到高的顺序排列，共有以下几种处理策略：

1. **扔弃新任务**——继续执行旧任务，抛弃新任务

2. **排队**——继续执行旧任务，旧任务执行完后开始新任务

3. **静默执行**——新任务如果不需要和用户交互，可以静默执行

4. **整合**——暂停旧任务的推理，query拼接后综合考虑新任务和旧任务

5. **插队**——暂停执行旧任务，执行完新任务后恢复旧任务

6. **停止旧任务**——抛弃旧任务，开始执行新任务

## 知识管理需求

对话推理引擎中有较多内容在处理具体问题时是冗余的，比如：

- 工具及工具描述

    - 简单查天气的query，把人脸注册的工具给到对话推理引擎显然是冗余项

- 参考示例

    - 目前对话推理引擎有50\+示例注入，有些示例还比较长，处理具体问题时把不相关的示例给到对话推理引擎属于冗余

- knowhow [对话推理引擎/Director knowhow](https://bytedance.larkoffice.com/wiki/GlZhweru4i6naMkbGv4czFeFnGo?from=from_copylink)

    - 对话推理引擎有比较多的knowhow注入，比如下面这些，在不相关的场景中注入这些knowhow也属于冗余

        - 功能knowhow：关于具体功能的使用描述、边界值和步长描述、用户体感描述等

        - 工具knowhow：工具使用知识和技巧

        - 场景knowhow：如果更好地处理某类具体场景（跟参考示例的作用类似）



冗余内容的注入会导致对话推理引擎的性能和推理质量下降，解决方案是需要增加前置筛选模块（角色定位类似端状态筛选、用户记忆筛选等），根据query筛选相关内容然后加载进对话推理引擎。
