# 智能座舱连续情景context

## 背景与问题

为持续增强豆包的“活人感”，一期引入 always\-on 感知。可以把系统的感官分工理解为一句话叙事：**眼睛是 VLM（舱内外视觉描述），耳朵是人人对话与人机对话的全时聆听**。但无论视觉还是听觉，当前都是离散、孤立的点状或切片信息——系统看见乘客刚醒来，却不知道他此前说过精神不佳并休息了一阵；刚刚车里发生激烈争吵，AI 回复时却可能语气不合时宜。

需要把离散的点与切片串联成一个连贯长镜头，让 DT 既知道“现在是什么情况”，也知道“是如何演进到这里的”，从而在理解、指代、语气和主动时机上更像人。具体要回答：

- 当前车内有哪些人、各处于什么状态；

- 当前是否在交谈、车内气氛如何（“聊什么”与“聊得怎样”分开）；

- 关键事情如何演进到当前状态、还有什么没了结；

- 人人对话里出现的需求，是否已向 AI 发起、指令是否真正执行成功；

## 产品目标与成功标准

1. 让 DT 获得**包含时间演进**的座舱完整情景，而不是彼此独立的感知快照。

2. 让 DT 能根据当前气氛、乘员状态、话题延续和需求完成情况，调整理解与表达。

成功的最低闭环：同一段行程内，DT 在指代、话题承接、语气、需求去重等场景能随着情景context的变化而变化。

## 整体方案

由 **上游输入 → 单 Scene Producer → Scene Context 组装 → DT 接入** 四段组成。一期只有**一个** Scene Producer，对本行程内所有新观测做串行增量更新。

> **整体流程（文本版）：** 上游输入（眼睛=VLM / 耳朵=人人对话 / 耳朵=人机对话 / 上一版 Scene Context）→ 单 Scene Producer（串行增量更新，业务输出仅 当前情景 / 情景故事线 / 不确定因素）→ 编排层附加单调版本号、做乐观并发与快照锁定 → 最新已发布 Scene Context 业务体 → DT（读快照，结合当前 Query 与车辆真实任务状态）。

## 输入设计

### 人人对话（耳朵之一）

1. 端侧 always\-on 人人对话数据按三种策略打包上传云端：固定数量（每累计 10 句）、长时间沉默（累计沉默 \&gt; 10s）、有效 query 召回。

2. **每一个上传批次即为一个 ****`new\_observations`**** 微批**；同批内人人、人机、视觉多源观测统一按 `time` 升序排列后再交给 Producer。

3. 端侧上传与云端拒识召回的人人对话，在服务端按时序排列形成人人对话序列。

4. 核心字段参考有效 query，包含说话人、音区等。

### 人机对话（耳朵之二）

1. 作用是为情景补充关键决策信息：人人讨论的某话题/需求，是否已通过人机形成决策并有真实执行结果。

2. 作为情景生产输入，需提供原始 `query`、`query` 对应的 `AI 回复` 以及 `工具执行结果`（如有）。

### VLM 视觉描述（眼睛）

1. 即每一帧舱内外描述 caption。

2. 舱内描述需合并 faceid 结果给出人名，合并策略：

    - faceid 有、vlm 有：合并人名与情景描述；

    - faceid 有、vlm 无：按无 vlm 处理，仅显示位置与人名；

    - faceid 无、vlm 有：该位置有人，乘客身份标记为【未知乘客】，再拼接 vlm 描述；

    - faceid 无、vlm 无：该位置无人。

3. 视觉输入永远只保留最新的一帧。

### 最近的 Scene Context

即最近一次生产的业务体内容，用于对本行程情景做增量更新与进度追踪。

## Scene Producer 工作机制

### 触发策略

1. Producer的情景推理由以下条件触发：

    1. Vlm的caption更新，包含舱内低频、高频和舱外

    2. 人人对话

    3. 人机对话

2. 每次推理触发时，新的输入为当次和上次推理窗口内的所有增量内容。

## Scene Producer 更新机制

### 运行输入与输出

Scene Producer 每轮**唯一输入**为：

```json
{
  "previous_scene_context": { "当前情景":[], "情景故事线":[]},
  "new_observations": []
}
```

### 触发策略

前置条件：车辆使用中（上电状态）

- **输入更新：**当产生新的输入时触发Producer更新场景context。当多个输入源同时触发（推理未完成），则推后至下一次推理。每一次更新都需要合并输入上一次推理间隔内所有积压的输入数据。

- **关键变化：**人员上下车、入睡或醒来、话题明显切换、气氛显著变化、安全风险、人机执行结果返回等，触发及时更新。

- **DT 响应前：**若存在尚未编译的新输入，先更新 Scene Context；若无积压，直接使用最新已发布版本。

### 生命周期规则（情景故事线）

1. **创建和去重：**时间连续、参与者一致、话题或活动相关的新现象，归并到已有同类情景线；确属新事项时才新建“story”。

2. **更新：**持续推进当前`状态`、`进展`，不反复创建同义条目。

3. **话题类未决事项：**作为“storyline”如果没有结束（如路线未决），即使短期无新输入，仍保留为 `active`，不删除。

4. **持续影响事项：**情景结束但仍可能影响后续理解、指代、决策、语气或关怀时（如身体不适），压缩为一句 `进展` 并保留为`active`，不删除。。

5. **删除：**情景结束且没有后续价值时从数组删除。

### 当前情景 更新规则

- 只描述当前仍有效状态；新信息明确改变旧状态时用新状态。

- “没有再次观察到”≠旧状态反面成立；证据不足用 `unknown` 或置空；天气/道路等环境量未收到新观察时沿用上一版。

- 短暂动作结束后不得长期残留为当前状态。

- `车内对话状态`负责“是否在交谈”，`整体氛围` 负责“聊得怎样”，两者独立更新；话题演进归 情景故事线。

- 心理状态或氛围的确定或更新要有足够的证据，单一表情、姿势或音量变化不足以确定心理状态。
