# 背景
AI汽车管理后台 正在面向内部与外部账号提供模拟器、触发器等能力，需要控制账号可用的模块/渠道、用户在模块内的角色，以及敏感操作的审批。
当前问题
|
带来的影响
|
现有模块授权基于 IAM 自定义策略实现，外部账号无法纳入统一授权体系。
|
内外部账号需分别维护模块访问与授权流程，权限口径不统一，运维成本高。
|
缺少权限申请自动流程；缺少完整的渠道管理方案。
|
模块访问人员与管理人员边界不清，权限只能逐个维护。渠道管理通过tcc配置，需要频繁更新。
|
Agent 发布/禁用、动态示例发布等敏感业务操作缺少审批环节，操作权限通过硬编码进行限制，需要优化。
|
敏感操作缺少统一审批工单与执行反馈，审批后的执行结果、失败原因及撤销入口无法追溯，风险不可控。
|
**建设目标：**IAM Action 控制后台接口准入；用站内模块角色统一管理访问权限，以网页工单完成申请、审批、执行和结果查询，让内外账号使用同一套业务流程；。

# 开通账号
**首次开通：**外部账号尚无本模块管理员时，由具备该模块跨账号管理权限的内部 ADMIN 处理首次申请；审批通过仍仅授 OPERATOR，再由内部 ADMIN 在人员管理中任命首位 ADMIN。内部跨账号管理资格不写入目标账号角色、不占目标账号名额；无任何有效审批人时拒绝建单，不免审。
1. 产管平台为外部主账号开白后，服务端手动配置该账号的渠道与模块范围，校验完整性后启用；不写入默认 ADMIN 或 OPERATOR，新增模块也不自动授予角色。
1. 主账号可在控制台创建子账号，并按 IAM 方案配置 AIDV Action 准入。主账号与子账号共用所属主账号当前的渠道、模块范围，子账号不单独维护范围；IAM 准入不等于模块角色授权。
1. 主账号与子账号首次登录均为 role=null：不加载业务数据、隐藏业务导航，仅保留申请模块权限入口；从已开通模块中单选申请，审批通过后授予 OPERATOR。也可由有管理资格的模块管理员直接授权。
1. 获得模块角色后刷新 context，按实际角色展示对应模块及人员管理、审批入口。主账号身份不附带管理权；首位管理员另行任命，不由账号开白或申请审批自动产生。

## 模块权限申请
主账号与子账号均可从未授权页面申请单个模块，也可联系有管理资格的模块管理员直接授权。
无模块角色的主账号与子账号使用同一申请入口和表单，不依赖业务模块访问权限。
页面环节
|
交互规则
|
初次进入
|
外部主账号与子账号尚无任何模块角色时，隐藏整个左侧导航，页面仅显示“暂无模块访问权限”及“申请模块权限”按钮。点击打开统一申请表单，不依赖业务菜单或“我的工单”入口。
|
选择模块
|
申请模块为下拉单选，选项来自 context.modules，即所属主账号已开通的模块范围；主账号与子账号均不按本人现有角色过滤选项，由用户选择目标模块。
|
填写与提交
|
每次申请一个模块，目标角色固定运营，填写申请原因。已有角色、进行中申请或暂不可申请的模块显示状态/原因，避免重复提交；主账号未开通的模块不提供。
|
申请后
|
提交后进入本人工单查看进度，重复申请定位原单。审批授权成功后刷新，开放对应模块内容；也可联系模块管理员直接授权。
|
## 工单管理
**我的工单模块属于公开模块，不受模块权限管控。**
前端拉取审批场景，业务按钮提交时创建工单，通过后才执行业务；普通业务沿用原接口。申请人与审批人通过下列工单页面处理决定及结果。
敏感操作先建单；申请人与审批人在同一个工单入口完成后续处理。
- 我发起的：倒序展示本人工单，支持状态筛选与详情展开。审批中的工单展示“撤销”入口，二次确认后提交，成功显示“已撤销”，刷新列表及 context。若审批先完成，提示“工单已处理，无法撤销”并刷新。
- 待我审批：展示本人当前作为 ADMIN 的账号/模块范围内的工单，含本人发起的工单；新增管理员可处理已有未决定工单，撤权后立即失去该模块审批视角。审批状态中的工单展示同意/拒绝入口，自审也需明确点击。
- 人员信息：始终展示 applicant；尚未审批时 approver=null，不展示审批人；决定后只展示一个实际审批人及审批时间，不展示处理流程。
- 工单状态：0 失败，1 审批中，2 成功，3 已拒绝，4 已撤销；
我发起的工单原型：状态筛选、单模块申请入口、未决定工单的撤销按钮及二次确认；已撤销记录保留。
撤销确认：仅申请人对未决定工单操作。
待我审批：按当前模块管理员资格展示，包含管理员自审发布申请；决定前仅展示申请人，决定后补单个实际审批人，刷新列表与角标。
## 工单状态
审批边界：按目标账号、模块校验当前有效 ADMIN，允许显式自审；外部账号尚无本模块管理员时，由具备该模块跨账号管理权限的内部 ADMIN 处理首次申请。工单为 APPROVING、SUCCESS、REJECTED、FAILED、CANCELLED 五态；仅申请人可撤销尚未产生决定的审批中工单。终态及已同意待结果确认的工单不可撤销；不做多级审批、转交或通用流程编排。

|

审批通过，且业务实际执行成功。

# 人员管理
用户至少具有一个有效模块 ADMIN 时展示人员管理入口，主账号身份本身不展示该入口。外部管理员管理本账号对应模块；具备模块跨账号管理权限的内部管理员可选择目标账号处理初始化，成员来自账号成员体系。
区域
|
展示与交互
|
模块与人员列表
|
选择本人可管理的模块；内部跨账号模块管理员可选择目标账号，外部管理员固定本账号。展示主、子账号用户的实际角色及用量（如 1/5、1/20），无角色不占额。
|
设置模块角色
|
选择目标账号的主账号登录用户或子账号，为当前模块添加角色（默认运营，可选管理员）或调整已有角色；不因主账号身份自动授权。
|
保存与异常
|
提交 account_id、user_id、module_code、role、version，复核目标账号及模块管理资格、账号开通范围和剩余名额；已有管理员时保护最后一名。异常保留输入并刷新用量。
|
变更生效
|
保存后刷新人员列表、名额及 context。管理员直接授权不建审批工单；已有申请后续获批时保留实际角色，不重复占额。
|
人员管理原型：内部模块管理员选择目标账号；主账号示例初始未授权，管理员用量按实际角色计数。列表与添加角色使用同一套主、子账号规则。

## 审批场景与创建工单
**审批场景列表：GET /aidv/web/approval/scenes**，无请求参数。已登录即可查询，返回服务端注册的全部场景元数据；不按是否已有模块角色过滤，实际建单另行鉴权。前端用 scene 匹配业务入口，scene_name 用于表单及工单标题。
```json
{
"data": {
"list": [
{ "scene": "permission_apply", "scene_name": "模块权限申请" },
{ "scene": "trigger_publish", "scene_name": "触发器发布申请" }
]
}
}
```
**创建工单：POST /aidv/web/approval/create-tickets**。前端在需审批的位置直接调用以下契约，不需要额外的审批命中检查接口；scene_name、所属账号与审批人均由后端确定。

## 错误与调用约束
业务查询范围由服务端可信 is_external 生成，客户端条件仅收窄筛选；外部账号限所属主账号，内部账号按既有规则跨账号查看已授权模块业务数据。工单与人员按目标账号/模块管理资格校验：外部 ADMIN 限本账号，内部 ADMIN 须具目标模块跨账号管理权。IAM Action 与站内角色均需满足，主账号身份不能代替角色；写入复核范围、角色、渠道及资源归属，变更后失效缓存。
复用项目现有响应错误封装，具体数字错误码随 IDL 确认；本稿先约定语义。HTTP/接口成功与工单业务成功分开判断，页面以返回工单状态展示业务结果。
语义
|
处理
|
无权限 / 非本账号资源
|
业务读取按 3.2 校验，外部账号不得跨账号；内部账号跨账号可见不自动赋予管理权。审批及人员管理须具有目标账号/模块管理资格，内部跨账号模块 ADMIN 可处理首次申请与首位管理员任命；主账号身份不免鉴权，P1 回调同样适用。
|
资源版本变化 / 人员授权版本冲突
|

|

|

# 上线与验收
## 迁移与上线
1. 核对外部主账号开白及渠道、模块范围，只维护一份主账号范围配置，不初始化默认 ADMIN；新增模块不自动授予角色。存量主、子账号的有效授权按人工确认结果逐模块迁移，不因主账号身份新增角色。后端校验审批场景唯一、名称与执行器齐全，核对角色人数及配额，不自动截断或降级。
1. 先完成账号范围、统一鉴权和人员管理，并配置可处理首次申请的内部跨账号模块 ADMIN，再启用申请与敏感工单。新主、子账号均初始无角色；首次审批通过授 OPERATOR，首位模块 ADMIN 由有资格的内部管理员在人管中另行任命；存量有效角色无需重复申请。
1. 站内授权稳定且无其他依赖后，仅清理退役的 AIDV 模块自定义策略。IAM Action 准入方案确定前，不清理承担接口准入的策略；申请、工单查询等基础接口必须能够进入，避免申请死循环。
本期异常时可暂停新建单与敏感执行，保留网页查询和人工处置，核实在途结果后恢复。授权通过人员管理纠正，已执行操作按场景恢复方案处理。监控覆盖授权失败、越权拒绝、结果待确认与重复决定冲突；

1. 使用 TSP Credentials Provider 动态获取和轮转凭据，再交给火山 Go SDK 完成 OpenAPI 签名。业务代码、普通配置和日志不保存明文 AK/SK；服务端凭据不下发前端。
1. 部署环境须满足 TSP 的 ZTI / IRSA 身份要求；SDK 示例使用服务发现推断运行环境，IAM Region 使用 cn-beijing。分别验证凭据获取、只读查询及授权权限。
## B.2 Go SDK 接入示例
按 [TSP Provider 官方接入说明](https://code.byted.org/security/tsp-creds-provider-go/blob/master/README.md) 整理。替换示例 PSM、火山账号 ID 与 IAM 凭据名；生产服务复用 Provider 和 IAM Client，在服务退出时关闭 Provider。调用方应传入有截止时间的 context，并按所锁定的 SDK 版本联调。
```go
package iamaccess
import (
"context"
"fmt"
tspProvider "code.byted.org/security/tsp-creds-provider-go/provider"
"github.com/volcengine/volcengine-go-sdk/service/iam"
"github.com/volcengine/volcengine-go-sdk/volcengine"
"github.com/volcengine/volcengine-go-sdk/volcengine/credentials"
"github.com/volcengine/volcengine-go-sdk/volcengine/session"
)
// 示例仅查询策略，不创建密钥或执行授权。
func queryPolicies(ctx context.Context) (*iam.ListPoliciesOutput, error) {
provider, err := tspProvider.NewVolcCredentialsProviderSD(
"your.service.psm", "your-volc-account-id",
tspProvider.WithIAMSecret("your-iam-secret-name"),
)
if err != nil {
return nil, fmt.Errorf("init TSP provider: %w", err)
}
defer provider.Close()
cfg := volcengine.NewConfig().
WithRegion("cn-beijing").
WithCredentials(credentials.NewCredentials(provider))
sess, err := session.NewSession(cfg)
if err != nil {
return nil, fmt.Errorf("init IAM session: %w", err)
}
result, err := iam.New(sess).ListPoliciesWithContext(ctx,
&iam.ListPoliciesInput{Scope: volcengine.String("All")})
if err != nil {
return nil, fmt.Errorf("list IAM policies: %w", err)
}
return result, nil
}
```
旧版示例中的静态 AK/SK 及 CreateApiKey 演示不再保留；初始化接口已对齐当前 TSP Provider README，示例仅用于说明接入方式。

## B.4 旧版自动绑定流程（历史参考）
旧版流程：审批同意 → 服务端映射 IAM 用户与目标策略 → 校验归属、用户和策略 → AttachUserPolicy → 按真实执行结果更新工单。该流程不接入当前模块申请；若未来需要将 Action 自动授权纳入审批，再按独立场景设计。
- 只允许后端确认的用户和策略，重复决定不得重复授权；不因主账号登录身份而自动授予 IAM 或模块管理员权限。
- 明确成功才记 SUCCESS；明确业务失败记 FAILED 并展示原因；超时或结果未知保留 APPROVING，先查询实际绑定结果，再决定是否重试。
- IAM Action 准入与站内模块角色分别校验：其中任一层不满足都不能执行业务；申请入口和基础查询的准入需提前打通，避免无权限用户无法申请。
