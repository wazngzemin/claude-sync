## 09｜可见即可说

餐厅候选卡片还停在屏幕上，两家店各带一个“导航”按钮。主驾补一句“第二个”，副驾直接说“导航”。这两句话单独听都没有对象，全靠眼前这张卡片给它们指向。这一章讲可见即可说：用户指着屏幕说的话，怎样被听懂、匹配到已经登记的对象、真的点下去，结果又怎样回到下一轮对话。

传统语音要用户背固定指令、提前配置命令；可见即可说希望屏幕上显示什么，用户说什么就能操作，降低记忆成本。这里先划清两条边界：第一，它不是让视觉模型看图猜按钮长什么样、猜该点哪里；第二，它也不是给模型一个随意操作整块屏幕的权限。只有业务主动登记进名册的元素才支持语音点击，没登记的元素系统不会假装支持。分工上，页面元素解析、指令生成和模拟点击由车企或各业务模块负责，语音识别和指令匹配由字节语音模块负责，依据见[【AI汽车】可见即可说框架需求文档](https://bytedance.larkoffice.com/wiki/AxYjwUI8wiFCXWkdNsDcRae0nCf)。

热词怎样注入在线和离线识别归识别链路章节，普通开放域理解归拒识与 Director 章节，语音合成归播报章节，点击事实怎样写入历史归上下文章节，端侧命中还是进云端归端云采信章节。本章只走可见即可说这条从页面注册到真实点击的快路。

## 卡片出现后，先把可点的对象登记成名册

**W01（页面业务解析当前可交互控件）**是整条快路的起点。它解决的问题是：语音侧不知道屏幕上现在有哪些按钮，必须由最了解界面的一方把可点对象报上来。卡片出现在最上层页面之后，车企或业务方通过无障碍服务界面等技术方式实时扫描当前屏幕，挑出真正能执行点击的可见元素，比如那两家候选店和各自的“导航”按钮，提取它们的显示文字和对应控件对象。解析只针对最顶层页面，弹窗、覆盖层和后台页面不参与；这一步靠的是页面自身提供的控件信息，不是让语音侧用视觉模型去读屏幕猜位置，业务侧自己最清楚哪个元素点下去会发生什么。

为什么不能让视觉模型直接看图猜按钮，有两层原因。一是车机界面控件位置、文字和状态由业务代码维护，模型读图只能得到像素外观，拿不到稳定的控件标识，猜中的位置在页面刷新后就可能失效；二是安全责任无法划分，语音侧直接操作屏幕等于绕过业务自己的校验。因此框架把界面元素解析、指令生成和模拟点击划给车企或各业务模块，语音识别和指令匹配划给字节语音模块，依据见[【AI汽车】可见即可说框架需求文档](https://bytedance.larkoffice.com/wiki/AxYjwUI8wiFCXWkdNsDcRae0nCf)。

名册里的每个对象要先完成登记，进入 **W02（注册可见词、泛化词与控件 ID）**。按钮显示文本直接作为核心指令，用户说“导航”就对应这个“导航”按钮；遇到多个文字相同的控件，比如列表里两个“返回”，名册要补充位置描述，用户说“第二个”才能区分。注册时还要过滤符号、标点等不适合朗读的内容，并按框架配置可识别的泛化表达：前面可以加“点击、点一下、帮我选、选择”等前缀，后面可以带“吧、啦”等语气词。可说名称、允许的说法和一个控件标识绑在一起，形成名称到对象的对应表，注册范围只对应当前页面或卡片。

名册输出的是动态维护的“语音指令到界面元素”映射库，包含热词指令、泛化词指令和对应控件 ID 三类内容；界面切换页面、弹出弹窗时指令库实时更新，保证所见即所说。框架需求规定单页注册词不超过 500 个，这是指定框架的需求上限，不是已经实测过的吞吐能力，也不等于工具数量上限。冲突处理上，同名控件必须补位置或上下文描述，否则“删除”“返回”这类高频词无法区分指向；不做区分就登记，多候选时只能交给业务消歧，语音层不能替用户选。

登记好的有效词再进入 **W03（把有效注册词加入识别热词）**，同时注入在线 ASR（自动语音识别）和离线 ASR，帮助语音识别听清页面上的特殊店名和按钮名；在线与离线的选择策略和免唤醒多音区交互一致，免唤醒走纯离线，唤醒后离在线并行处理，离线有结果执行离线结果，离线无结果等待在线结果。热词随有效页面和卡片更新识别词表。要注意，热词注入成功只提高识别概率，不等于用户这句话最终必然命中按钮；这些热词与人名、地点、媒体、车控等其他热词一起在识别链路处理，交叉口径见[AI 汽车语音基础体验链路 OnePager](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)。

热词分在线和离线两套分别注入，原因是车内网络条件不稳定：唤醒后离在线并行，离线先出结果就先走离线，离线没识别出来再等在线；免唤醒场景没有等待在线的时间窗口，只能依赖离线词表。页面词表随卡片进入和退场同步增删，避免旧店名、旧按钮名长期留在离线词表里挤占识别资源；热词和通用词表冲突时的优先级，归识别链路章节统一处理，本章只保证名册里的有效词被送进词表。

## 等最终文字定稿，再和名册做规则匹配

用户说完，识别链路交出最终输入后进入 **W04（用户 final 到来，带回本次有效界面）**。语音识别是流式出字的，过程中的字一直在变，这一步必须等文字定稿，同时保留本次请求编号、音区和页面上下文；过程文字不能直接拿去模拟点击。为什么必须等定稿，是因为流式中间结果可能把“导航到第二家”识别成半截“导航到第二”，拿中间态去匹配名册，会命中错误对象甚至误点；等 final 同时绑定页面快照，才能保证匹配用的名册和用户看到的界面是同一版。动态卡片也可以登记它当前的可选项，但这份选择器只是当前卡片的名册，不能当成脱离页面、永久有效的本地缓存；具体卡片是否接入，要按车型和发布版本确认【待核】。

文字定稿才进入 **W05（全文、局部或模糊规则产生匹配候选）**。匹配按框架约定的全文精确、局部和模糊规则在名册里比较，不是让模型自由发挥，把意思相近的话都当成按钮。精确匹配直接比对识别文本和核心指令；模糊匹配接受前面列举的点击类前缀和句尾语气词；局部匹配要求 6 个以上词时连续匹配 4 个字以上。匹配结果分零个、一个、多个三种。一个候选直接交后续执行；多个候选先走消歧；一个候选都没有时，这句话回到正常有效 Query 链路继续判断，不能因为没匹配上页面就把用户诉求吞掉，这条出口在 W14 再展开。

规则匹配而不是模型语义匹配，是可见即可说追求快和稳的取舍：页面操作要求对象确定，语义模型在车里可能把“换一首”和“下一首”解释出多个对象，规则比较可控、可回放、可统计；代价是用户必须说名册里有的说法，超出名册的表达就走开放域链路，不在这里硬猜。

## 多个候选先消歧，目标唯一才交给业务

一个候选直接进入执行；多个候选先走 **W06（多个命中：返回全部候选给注册方）**。字节匹配层不擅自挑第一个控件，而是把多个候选标识交回登记业务，由业务按自己掌握的界面信息选择，或按项目约定弹出选择让用户点选。这里不存在“默认点第一个”这条规则，随机选第一个可能造成真实误操作。多候选是否弹窗、弹窗长什么样，由项目合同确认，材料没有给所有车型约定统一形式。业务尚未确定目标时，语音层只能说还没选定，不能把“候选列表已返回”包装成“已经点好了”。

先交回业务消歧而不是语音层排序，是因为业务掌握候选的位置、当前高亮状态和业务优先级，语音匹配层只知道文字相似程度，不知道哪个候选在视觉上离用户最近；把选择权交给业务，才能和用户手动点选的行为保持一致。

目标唯一后进入 **W07（把确定的控件 ID 交回业务执行入口）**。匹配服务输出确定的目标 ID，注册业务接收并对应当前控件。交 ID 之前还有一道有效检查：从用户开口到这一刻，卡片可能已经退场、页面可能已经切换，旧标识不能跨页面继续使用；确认目标仍然有效，才进入执行。这一步只是明确了执行对象，本身还没有点击。有效检查要和 W12 的名册注销联动：页面已经撤掉旧范围，旧标识在校验阶段就应当失效，不能带着过期 ID 进入执行入口。

随后由 **W08（车企或业务方执行模拟点击）**完成动作。控件所属业务用本页面既有的点击执行能力触发对应界面变化或业务请求，字节匹配层交出 ID 并不等于已经替音乐业务播放了歌、替导航业务开始了路线；这里也不是 Director 获得了任意操作整块屏幕的权限，执行能力和责任都在控件所属业务一侧。模拟点击时界面需要给出 UI 点击动效，让用户看到动作确实落在了哪个控件上；执行失败由业务按系统提示方式呈现 toast 短提示。框架定义的模拟操作包括点击、输入、滚动等类型，一期落地以按钮点击为主，输入和滚动能力按各业务接入进度开放。执行入口只接受名册内登记过的控件 ID，语音层不能自行拼接坐标或遍历控件；这样即便匹配环节出现异常，动作也无法落到未授权元素上，形成一道执行侧的兜底约束。

## 点下去之后，等真实回执再反馈

点下去不是结束，而是等回执的开始。**W09（业务返回真实成功、失败与可播内容）**把成功、失败、未完成分开带回，并附上适合统一播报的内容。拿到回执才能分清三段责任：字听错了归识别，匹配错对象归匹配，执行没成归业务。匹配成功不能代替执行回执，业务返回之前不能提前说已经办好。

为什么必须等真实回执，是因为模拟点击发出后，业务内部还可能校验失败、接口超时、控件状态不允许操作；如果语音层在点击请求发出时就播报“搞定了”，界面实际没动，用户会认为语音系统撒谎。框架规定成功播报“好的、搞定了”一类话术，失败播报“抱歉，没执行成功”一类话术，执行结果成功、失败以及需要播报的内容统一传给豆包，由豆包选择播报；失败时界面按系统提示方式呈现 toast 文字，失败文字本身不朗读。

回执之后两条线并行。一条到 **W10（豆包统一播报，界面按交互规则反馈）**，真实结果和可播内容交给统一播报链路选择 TTS（文本转语音合成）路线；页面仍按自己的规则显示成功变化或失败提示。语音反馈和视觉反馈分开收口，是因为不同业务界面的成功动效、失败样式由业务维护，语音话术由统一播报保证一致，两边各自更新自己的状态。

另一条线是把这次点击写进历史，即 **W11（把模拟点击写入历史，给下一轮使用）**。它把这次点击作为已发生事件写进对话历史，注明来源是模拟点击，保留用户原话、目标对象和真实结果，再交给上下文模块衔接最近对话、工具事实和摘要。如果历史里只有一句“第二个”或一句成功话术，下一轮用户说“返回”“再选”时就接不上对象；如果不标注模拟点击来源，模型还可能误认为这是自己通过普通问答或函数调用完成的动作。标注来源之后，下一轮推理能区分这次操作来自页面点击还是本轮模型规划，避免重复执行或错误继承动作。历史记录需要同时保留三层信息：用户原始语音文本、名册匹配到的控件名称和 ID、业务回执里的真实结果；缺了原始原话，模型无法理解“第二个”指的是哪一批候选，缺了控件对象，下一轮“返回”“再选”就没有承接锚点，缺了真实结果，后续问答可能基于一次失败操作继续推演。上下文模块读取这段历史时，按最近对话、工具事实和摘要的顺序衔接，模拟点击事件和普通工具调用事件在格式上区分来源标记。

## 名册跟着页面生命周期更新

整条名册不会在一次点击后永久保留。**W12（卡片退场后注销，页面变化后更新范围）**随页面或卡片变化维护注册范围：卡片进入可见和可操作状态时重新进入解析；卡片退场、切页、手动关闭、超时或被新卡片替换，都要撤掉旧范围、维护新页面词表。旧控件不能跨界面继续被点中。普通页面具体的失效接口仍需按正式实现确认【待核】。读懂这个循环，才能解释用户那句“刚才明明还能点，现在怎么不行了”：先看页面在不在、名册更新了没有，不要一上来判断语音退化。

名册随生命周期注销的必要性，和车机卡片的退出机制直接相关。即时交互卡在 TTS 播报完毕后默认延迟十秒退出，视频正在播放、图片正在加载、用户手动点滑卡片时退出计时顺延；用户上滑 ASR 胶囊也会关闭卡片。卡片一旦退出，旧按钮词就必须从识别名册撤下，否则用户回到其他页面再说旧按钮名，系统仍可能匹配到已经不存在的控件。名册更新要区分进入和退出两个方向：新卡片可见时重新解析并注册新词，旧卡片退场时先注销旧词再注册新词，避免新旧名册短暂并存造成同名冲突；页面跳转打断 TTS、点击卡片内按钮发生页面切换时，同样触发一轮名册重建。普通页面没有统一的卡片生命周期事件，失效接口按各页面实现对接，这也是 W12 标注待核的原因。

## 画板底部的边界与历史口径

**W13（任务中心例外：暂不支持）**标注为已落地：任务中心页面及内部按钮暂不支持可见即可说，该结论经赛力斯任务中心外审确认；多条任务并排时说“第二个”指向不明。可见即可说不是对全车所有页面的承诺，支持范围以按车型、版本维护的清单为准。任务中心不支持语音点屏和 12 章 T21 是同一条规则，多个并排对象缺少唯一位置锚点时，语音层不做猜测。

**W14（零匹配后的开放域拒识）**是 2.6 目标：W05 零候选回到普通语音入口之后，才进入这道判断。它只在沉浸模式关闭时生效，沉浸模式开启时语音助手持续聆听、不做文本拒识。意图清单按提问、陈述、命令指示、社交用语分组，提问类包含获取事实资讯、获取经验知识、获取虚构信息、了解观点评价、了解情绪感受和请求帮助，陈述类包含表达阐述、回答提问、命令指示和社交用语；无上文要求意图明确、语句完整，陈述类只召回情绪和观点评价，有上文时结合相关上下文放宽完整性要求。画板登记为 22 个三级意图，拒识 PRD 表格实际列出 17 个三级意图，清单数量与版本以拒识 PRD 为准【待核】，依据见[【AI汽车0.5】豆包车载版产品需求文档](https://bytedance.larkoffice.com/wiki/DhWHwvmqcixRVEkI9pkce01pnud)。

拒识还有两条回捞规则：语句前面或最后出现配置的唤醒词名称及泛化称呼时直接召回；被拒识后在限定时间内继续说出唤醒词，或表达“我在和你说话呢”“怎么不理我”“没反应”等纠错意图，系统召回上一轮 Query。上下文是否相关，按主体、对象、动作、描述和上文是否一致判断，不相关的插话进入拒识，相关的补充继续承接。

**W15（3 月优先级仅当时设计）**标注为待核。框架文档 3 月版本列出过一套优先级：P0 用户自定义任务、P1 可见即可说、P2 FAQ、P3 端侧 LLM、P4 云端 LLM。这是当时的框架划分，不覆盖 9 月之后的本地兜底改版；生效车型和版本要分列，不能把它画成所有请求必经的漏斗，当前端云采信顺序以端云仲裁章节为准。可见即可说排在 P1，是因为它面向界面文字、只做简单表达、不做推理，追求少推理快响应；这个定位也解释了为什么它不承担开放域理解。

**W16（失败反馈不逐字念）**已落地：失败提示是屏幕上的短提示，系统不机械朗读失败文字；播报是否成功以 W09 回执为准，界面显示成功也不能盖过业务实际失败。失败文字通常包含技术细节或较长提示，逐字朗读体验差，因此只在界面呈现，语音侧使用统一的简短失败话术。

**W17（音区与请求编号留痕）**已落地：谁从哪个座位说的、本次请求编号随注册保留，事后可以回溯说话期间卡片是否发生变更，定位误点时先查这条留痕。多音区场景下，同一时刻可能有多个座位说话，音区和请求编号把每一句输入和当时的名册版本、匹配结果、执行回执串在一起，复盘时才能分清是识别、匹配还是执行环节出的问题。

## 本地闭环、卡片类型与验收要点

按 OnePager 链路，可见即可说或简单车控在端侧本地命中时，可以由端侧直接召回、执行并生成回答，再把 Query、Answer、Observation，即用户提问、系统回答、执行观察结果，经历史同步上报；端侧未命中才进入云端正式链路。对速度和本地可用性要求强、安全相关的场景走这条本地闭环，不往云端 Planner 送；这和普通开放域问题需要云端推理是两条路径，依据见 OnePager 与[【AIVA-PRD】VUI 主交互需求](https://bytedance.larkoffice.com/wiki/FBsrwA734iaFzZkrZExcHHBtn3d)。本地链路输出 reject 拒识或 functioncall 函数调用时驱动状态机流转；本地输出 unsupported 不支持时持续处于思考态等待云端结果，不视作最终结果；赛力斯项目 9 月 30 日更新后，本地大模型输出的拒识和语义结果暂不采纳，状态机以云端为准。

不同卡片接入可见即可说的方式分四类，评审时要先分清属于哪一类。第一类是 Planner 链路推出的卡片，Query 经 Planner 推理并调用工具，结果由 Planner 汇总下发拉起卡片，语音由 Planner 自闭环，手动点击直接执行并作为特殊事件日志上报云端，这类卡片不注册可见即可说词条。第二类是静态 Advisor 主动服务卡片，Advisor 输出建议后由 Planner 继续下发拉起卡片，语音由 Planner 闭环；手动点击因为没有直接执行接口，需要模拟一个 Query 走到云端完成建议到工具的推理转换。第三类是系统通知拉起的增强版卡片，三方直接触达端侧出即时交互卡片，语音由 Planner 动态插入与卡片生命周期绑定的选择工具，用户说“确认、取消”后透传匹配并下发端侧执行指令、更新卡片状态，手动点击有执行接口可直接完成并通过事件日志上报。第四类是端侧自闭环的服务通知，不经过 Planner，端侧直接出卡、离线直接执行，语音靠可见即可说实现。接入方式不同，注册名册和执行回执的来源也就不同。

验收要把注册、识别、匹配、执行、回执几段损失分开统计。注册覆盖与有效性核对已承诺页面和卡片内实际可操作对象是否正确注册，过期标识和未注册按钮单独统计，不把范围扩大到任意屏幕；端到端完成率在有效注册范围内统计最终文字听对、匹配对、执行对象对、真实业务完成且反馈一致的比例；多候选误执行率统计多匹配未完成选择却发生点击、或错误默认第一个的比例，无候选被吞掉单列；过期控件执行率统计卡片退场、切页、手动关闭后仍命中旧名册并产生实际动作的比例，和热词残留率分别检查。这些是建议验收要点，不是已经发布的固定 KPI。

评审时先确认哪些页面、哪类卡片已经支持，屏幕上可见的字是否都在名册里；一个词匹配两个控件时由谁做最终选择也要分清，字节匹配服务和业务执行方责任不同。顺着同一请求编号核对最终文字、匹配对象、业务接收、实际回执和界面反馈，才能证明真实操作完成；再覆盖卡片超时、关闭、替换和切页场景，验证旧名册注销、旧标识不再执行。历史记录还要注明模拟点击来源、记录实际选中对象，并核对框架优先级顺序和当前端云采信策略是不是同一版本。
