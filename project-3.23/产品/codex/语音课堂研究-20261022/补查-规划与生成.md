## 最值得加入课堂的变化

### 1. 先区分“系统正在想”与“工具已经接到命令”

以下可直接作为课堂短节，须保留“拟改造”标签。

**【拟改造：输入管理模块】** 我们拿“打开车窗”这个例子往下走。用户刚说完，豆包可能还没有说出第一个字，但云端已经把开窗命令交给车控工具了。这个时候用户补一句“算了，别开”，不能因为没听见豆包说话，就认定前一轮什么都没做。新方案要先看：旧命令有没有被允许下发。

如果旧命令还没有交给工具，就可以把前后两句话一起重新理解，让 Director，也就是负责理解和规划的模块，按用户最新意思决定怎么做。如果旧命令已经放行，旧请求就只能作为“刚才已经发生了什么”的背景，不能再当作一条待执行指令重新跑一遍。否则，开窗、导航等动作可能重复执行。

这时系统可以停止旧一轮继续说话、继续发新动作，但不能把已经发生的车控当作自动撤销了。已接单的工具仍要把真实结果交回来：究竟成功、失败，还是已经执行一部分。Director 再结合“别开”这句新要求决定后续处理。**停止旧回答、取消尚未下发的新动作、撤回已经执行的动作，是三件不同的事。** 新方案明确不自动回滚工具副作用；是否再发一个反向操作，要看业务能力和新的判断。

画图时，在“Planner 判断 → 工具执行”这根连线上补一个判断点：“工具是否已经放行？”“否”才允许旧请求与补充内容一起重算；“是”则把旧请求放进中断背景，把真实工具结果继续回传。图上不要只用“是否出了首字”替代这个判断。

出处：输入管理技术方案“执行重放边界”“S8 Tool 执行中用户反悔”“模块边界”。属于拟改造约束，不是已上线承诺。

### 2. “可以接着想”与“可以接着说”分开判断

以下可直接插入 TTS 讲解或工具回传小节。

**【拟改造：先计算，后放出结果】** 再看一个等待场景：豆包还在说“我帮你看看附近的充电站”，查询工具已经把几个站点查回来了。旧方案在部分多轮链路里会等这一段播完，再让模型继续想；新输入管理方案希望把这段时间用起来——只要这一轮该回来的工具结果已经收齐，就允许模型先准备下一段回答。

但“下一段准备好了”，不代表马上播给用户。系统还要等上一段在车机上真的播完，并检查准备期间有没有新的有效输入。如果用户补了一句“我只要快充”，先前按旧条件准备的内容就要作废，带上新要求和真实工具结果重新算。这样做的目的，是减少两段话之间的空等，同时避免把过期答案播出来。

这里有两个许可：**计算许可**决定“现在能不能开始准备下一轮”；**输出许可**决定“这份准备好的回答现在能不能正式交给用户”。正常播放进度上报只更新播到哪里，不应该每隔一小段就让模型重算。没有新要求、候选结果仍有效时，上一段结束就释放同一份结果，不再多请求一次模型。

画图时，把“工具反馈齐全 → 下一轮预计算”画成一条线，把“车端实际播完 → 允许输出”画成另一条线，在“输出下一段”前汇合。旁边加新输入分支：“有效新输入 → 废弃旧候选 → 重新计算”。这是一套拟改造方案，文档前半部分仍有串行等待旧表述，需评审统一后再作为实现验收口径。

出处：输入管理技术方案“Input Manager 消费规则”“新增 TTS 播报状态事件”。不是说所有 TTS 已经具备预计算。

### 3. 云端发完音频，不等于用户听完

拟改造方案要求按真实播放器事件认定状态：
- STARTED：第一个有效音频样本真的进入播放渲染；收到网络包、解码完成、排队都不算。
- PROGRESS：播放器实际消费了多少媒体时长；暂停和缓冲期间不增加。
- FINISHED：这一轮结束标记已收到，所有解码和播放队列尾部也已消耗完。
- ABORTED：这一轮永久停止，队列已清理，不能恢复同一播放轮。

TaskRoundEnd 是云端这一轮音频的发送边界；SubTTSEnd 是一个 Provider 子流的结束，都不能代替车端 FINISHED。断网、最后一包到了、估计时长到了，同样不能伪造“播完”。如果最终确认不了，方案允许记录“播放状态未确认/超时推进”，必须和正常播完分开。

临时听到人声时，方案写的是先本地暂停；最终拒识且允许恢复，继续原播放轮。形成有效高优输入时才永久中止。不能把这段泛化覆盖基础语音 OnePager 明确的单人打断不恢复等例外，具体接入还需项目确认。

## 其余新证据怎样放进业务闭环

**下游结果至少有三种用途。** 三方 Agent 协议分别定义 content（展示）、tts_content（播报）和 model_content（交给 Planner 继续判断）。例如查天气，可以先在界面显示“正在查询”，查询结果交给 Planner，再由 Planner 决定怎样说。卡片 JSON 也不能直接等同于可播的中文话术。协议示例还说明正常 TTS 往往由 Planner 总结，三方不必自行填写；字段表关于 null 回退到 content 与示例“只展示不播报”的表达存在歧义，接入时应核验实际路由，课堂不要讲成所有 content 都自动播。is_finish=true 是响应数据返回结束，仍不是车控成功或音频播完。预查询 QueryType=2 默认不启用，需要双方对齐，因此不能因为语音主链路有 ASR 预请求，就画成所有三方 Agent 都已支持预执行。

**Context 查询与 Context 同步是两个方向。** 弋途指南的 /aidv/v1/context/query 是“向公共上下文服务取资料”，可选瞬时/短期/长期/长期情景记忆、基础天气日期、端状态、情景描述、车辆通用信息、Agent 事件、记忆标签等。它支持范围筛选和端状态筛选；不代表每次无脑全量塞给模型。基础语音 OnePager 的 context/sync 则是“端上自己处理完，告诉云端刚才发生了什么”，两者不能画成同一个接口。弋途指南明确是服务端专用接口，不包含车机客户端、公版通用接口；它未补齐 context/sync 的幂等、重试和失败补偿定义。

**主动推荐“受理”与“用户看到”还隔一段。** 弋途 recommend 接口说明成功只代表指令受理，随后异步推送卡片。Goal 生命周期回调区分创建成功、创建失败、条件触发；完成结果另有 goal/finish。课堂可以据此强调“上游返回成功 ≠ 已展示 ≠ 已执行”。但这是一组弋途专用接口，不能套给所有普通语音。

**不要把平台的 S2S 能力替换成整车现状。** 端到端语音 ONEPAGE 介绍的是音频输入到音频输出的模型能力，与传统 ASR → 语言模型 → TTS 串联作比较；有 Omni 与 StrongCharacter 的能力说明及演示文件。任务 Planner PRD/S7 目标却明确普通闲聊由 Planner 回复，需要悄悄话、方言、唱歌、语气扮演等时调用 S2S。Agent 执行清单也写 S2S 支持语音或文本请求。因此课堂应画“按业务需要路由到声音演绎/闲聊能力”的分支，不要删掉整车 ASR/VAD/TTS 主链路。ONEPAGE 文中约 1 秒和表格 1.5 秒的数字口径不同，都不是本车实测。

**Context 的历史规划不等于当前固定参数。** Context 管理规划中，80% 窗口触发总结、保留近 10 轮、会话开始预注入后会话内固定等是方案/示例；中长期还提到情景记忆重构、从工具变为 Agent、自学习和多模态等方向。不能据此说“当前每 10 轮聊天必定压缩”。本地公共 Context 图上真正写的“每 10 轮”是情景描述的滚动总结，详见图 10。

**模型切换只定位对应环节。** 26.3 月 Onepage 主要解决 lite 基模下线后的联网判断和文本生成替换，表内“0324 已上线”指主线资源池联网能力部署。它不是整车全部模型或 Planner 推理模型的上线证明。0318–0323 提示词也有迭代，比如视觉环境问询何时联网的口径变化，不应混合成一套通用永久规则。

**旧目标与当前参数分开。** Planner 2.6/S7 文档给的是首字、准确率和控制时延目标；S7 单步、S8 多步/条件、S9–S10 持续任务属于排期。任务 PRD 还有每 30 秒查温度、百分比展示任务进度、自动恢复等愿景示例，不能替代当前端信号能力和任务服务策略。
