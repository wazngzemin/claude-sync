# W 章设计（Claude 定稿，Codex 照此写作和画图）

章名：W · 可见即可说：从说出屏幕上的词，到真的点下去

## 和前三章的分工
- V 章：讲过热词，以及可见即可说的入门。
- R 章：讲过端云仲裁、上屏、回写。
- I 章：讲过输入管理、历史记账。
- W 章只做这些章没做的事，讲深讲细。前面讲过的内容一律点回，不重复讲。

## 资料冲突的裁决（写作一律照这里讲，正文里不提“有冲突”）
1. 主线做法是业务主动注册页面词。自动扫描屏幕是另一种设计选项，有的车型用“扫描为主、注册兜底”。两种做法的利弊都要讲。
2. 同一句话命中多个元素时，按设计交给注册方消歧。有的车型不支持多命中，这一点作为设计选项来讲。
3. 执行失败的反馈：用户用语音触发的，失败由豆包统一播报；纯界面层面的失败，用 toast 提示。
4. 优先级：页面匹配命中后，在车上直接拦截执行，和 R 章的固定说法一样，都属于“有把握就先办”。没命中的，按 R 章的端云规则走。
5. 泛化：车上只认白名单，加上有限的规则，比如前后缀、归一化，不做语义理解。泛化的说法交给云端的动态工具处理。要讲清楚为什么这样分工：车上要快、要稳，云端负责理解。
6. 动态工具：服务端已经上线，各车型陆续接入。这一点用一句产品事实交代即可。
7. 语音选择照常走拒识；手点产生的是事件（event），不是模拟的 query，不走拒识。
8. 卡片成熟度：即时卡片已量产；长时卡片和任务中心还在预研。
9. 卡片相关性判断：上汽用一个单独的云端模型来判断，不写具体用的是哪个底座。
10. 多屏：默认各屏独立展示，通知类出在中控屏，个别场景联动。手点不会自动同步到所有屏，导航上的手点是事件。
11. 延时聆听按 30 秒讲。
12. 95% 是历史上的 ASR 句准，不是点击成功率。评估要另外看命中率、误点率、端到端完成率和延迟，这几项指标要讲清楚各自的含义。
13. 任务消息的类型编号、卡片通道编号这类协议细节，不进正文。正文只讲“展示数据、推荐卡、任务状态、执行指令是四条不同的通道”，具体编号放到附二。

## 大纲与每段必须讲到的事实

### 开篇：屏幕上看得到，就该说得到
- 三个场景：
  - 导航页上说“开始导航”；
  - 抖音页上说“暂停视频”（这里有个 badcase：说完反而打开了音乐）；
  - 餐厅列表卡片上说“就这个”或“第二个”。
- 讲清这一章和 Planner 的关系：有的话根本不经过 Planner，有的话靠 Planner 理解。
- 新图：w2-three-paths（放在开篇）。

### 一、说屏幕上的东西，有三条路
- 三条路分别是：
  - 页面匹配：车上拦截，直接点；
  - 动态工具：云端理解，下发点哪个按钮；
  - Planner 靠对话历史理解“第二个”（V 章讲过）。
- 讲清三条路各自什么时候走、谁做判断、错了会怎样。

### 二、页面先登记“我有哪些按钮”
- 讲页面词注册（卡片 17），第一次出现时要讲全。
- 要讲：进入页面时注册、离开时清除；每页最多 500 个词；同名元素怎么区分。
- 两种设计选项：主动注册、自动扫描。
- 真实问题：识别还没结束，页面词就被清掉了。
- 注册的词同时交给 ASR 作热词，这一点要点回 V 章。

### 三、识别出的文字怎样对上按钮
- 讲页面匹配（卡片 18），第一次出现时要讲全。
- 要讲：只看最终文字；归一化；精确匹配和前后缀匹配；只认白名单，不做泛化；多命中怎么处理。
- 拦截器把这一句拦下，返回 INTERCEPTED。
- “暂停视频”这个案例：ASR 已经写对了，匹配器却没有命中，请求被送到云端，结果进了音乐链路。这个问题已经修复。
- 新图：w2-match。

### 四、对上以后，谁来点
- 讲执行方（卡片 19），第一次出现时要讲全。
- 要讲：各车型的分工；控件目标走无障碍；抖音这类目标走业务自己的执行链路；执行结果有哪几种；匹配成功、选中按钮、执行成功是三个不同的时点。
- 失败怎么反馈（按裁决第 3 条）。
- 页面匹配在车上拦截以后，云端那边可能已经在处理同一句话。这里点回 R 章的“只办一次”，并讲清这里有什么风险、该怎么防。
- 新图：w2-who-clicks。

### 五、没对上，交给云端理解
- 讲动态工具（卡片 20），第一次出现时要讲全。
- 要讲：AgentServer 怎样按场景加载工具；条件引擎；current_page_specific 这个工具收到什么；select_button 怎样下发给车机去点；为什么不把卡片工具常驻在 Planner 的工具列表里。
- “第二个”“就这个”三种处理路径的区别。
- 新图：w2-dynamic-tool。

### 六、卡片上的按钮
- 讲卡片（卡片 21），第一次出现时要讲全。
- 要讲：四类卡片；语音选择和手点走的路不同；卡片什么时候保留、什么时候收起（相关性模型）；多屏；卡片成熟度。
- 四条通道：展示数据、推荐卡、任务状态、执行指令。
- 新图：w2-voice-vs-tap。

### 七、点完以后，下一轮还要接得上
- 拦截后，要把这次模拟点击上报到历史，还要写进 Planner 的工具调用记录。
- 点回 R 章的回写、I 章的历史记账。
- 讲清这里的风险：本地已经办完了，但下一轮云端可能没拿到正确的历史。
- 新图：w2-history。

### 八、不同车型的分工
- 用一张表讲上汽、奇瑞、赛力斯的分工：页面解析、执行、SDK、多命中支持、扫描还是注册。

### 九、怎么评估、怎么排查
- 指标：命中率、误点率、端到端完成率、延迟。95% 的 ASR 句准不能当成点击成功率。
- 排查顺序：页面词有没有注册 → 用的是哪份最终文字 → 匹配结果 → 拦截有没有生效 → 执行回执 → 页面状态 → 历史。
- 用 2～3 个真实案例演示排查过程。

## 新图设计
- w2-three-paths：起点是“用户说出屏幕上相关的话”，分三条路：
  - 页面匹配：车上，规则，直接点；
  - 动态工具：云端理解，下发 select_button；
  - Planner 读历史，理解“第二个”。
  - 每条路下面写一个例子。
- w2-match：横向流程：最终文字 → 归一化 → 精确或前后缀匹配 → 命中或多命中或未命中。命中走拦截；多命中交注册方消歧；未命中交给端云正常链路。旁边用一个红框标出“暂停视频”这个案例卡在哪一步。
- w2-who-clicks：两条泳道（车企或业务方、豆包 SDK），展示分工；三个时点依次是“匹配成功 → 按钮被选中 → 执行成功”；执行失败分两支：语音播报、toast。
- w2-dynamic-tool：车机上报卡片信息 → AgentServer 判断条件，加载工具 → Planner 选 select_button → 下发车机 → 车机执行，再回执。用虚线标出“普通对话时，这个工具不在 Planner 的列表里”。
- w2-voice-vs-tap：两条并排的路。
  - 语音选择：拒识 → Planner 或动态工具 → 执行；
  - 手点：event → 业务直接执行 → 上报。
  - 底部写：两条路都要进入历史。
- w2-history：时间线：本地拦截执行 → 上报模拟点击历史 → Planner 下一轮读到“刚才点了什么” → 接住“再往下一个”。用红色标出断点风险：上报失败，或者车机版本太旧。
