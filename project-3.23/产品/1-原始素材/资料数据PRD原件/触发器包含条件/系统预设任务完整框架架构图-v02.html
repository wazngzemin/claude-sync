一个状态真源

任务中心点击只是意图。接入业务真正保存后，端/云 Runtime 才能按 ENABLED 运行。

一种拓扑，一个产生方

链路可为 EDGE、CLOUD 或 HYBRID；但同车、同任务、同版本只能由一侧创建本次 RunEvent，冲突时双方都停止。

一个 RunEvent

硬候选通过后先建事件，再调模型或出卡；条件、模型、卡片、授权、车控和回读必须用同一事件关联。

L1 · CONTROL / STATE / RUNTIME

任务定义、任务中心与 Runtime 状态链：三条数据不能混

最容易讲错的地方：配置发布必须拆成 DisplayMetadata 与 RuntimeDefinition；任务中心只拿展示元数据和真实状态，Trigger 从 RuntimeDefinition 与状态同步链拿规则/状态，不能从任务中心页面“读规则”。

读图方法：A1/A2 是同一完整性门禁通过后的两个并列发布物；B1/B2 是请求与回包的相反方向；C1/C2/C3 是快照、增量、重同步三种机制，不是三个依次执行的步骤。

→

→

生产者：RuntimeAssignment 指定的唯一 producer　消费者：模型、卡片、原业务、执行、结果/日志

⑥ InteractionRequest / Events

原业务怎样请求卡片，以及卡片怎样把三类事实还回来
请求方：端侧 Trigger 原业务 / 云端原业务　展示方：即时卡 / VUI　结果消费方：原业务、VAS/Planner
task_definition_reftask_instance_refrun_event_refsource_typeinteraction_modecontent / actionsTTS / voice_routeclick_routeexpires_at / priority
DisplayAck｜展示事实：run_event_ref · card_ref · display_state（QUEUED / VISIBLE / FAILED）· failure_reason · occurred_at
InteractionEvent｜用户选择：run_event_ref · card_ref · user_result（CONFIRM / REJECT / CLOSE / TIMEOUT / INTERRUPT）· input_source（CLICK / VOICE）· element_semantic · occurred_at
LifecycleEvent｜生命周期：run_event_ref · card_ref · card_state（VISIBLE / HIDDEN / EXPIRED / REPLACED / RESTORED）· failure_reason · occurred_at
底线：请求先携带任务定义、任务实例和本次 RunEvent；展示、选择、生命周期都必须原样带回同一 RunEvent。卡片只提供交互事实，不判断业务、不直接车控。

⑦ ExecutionProof

根据 InteractionMode 证明本次动作为什么可以执行
生产者：原业务　消费者：ExecutionRequest 组装方、端侧执行前复核

⑧ ExecutionRequest

原业务把本次一次性执行依据交给端侧
生产者：端侧原业务或云端执行编排（正式发送方 TBD）　消费者：端侧执行前复核/车控

门禁：端侧拒绝旧代次、串车、过期、重复、缺本模式执行凭证、缺必要推理或车况不安全的请求。

⑨ Result

把交互、准入、车控与真实状态逐层区分并同事件收口
生产者：交互/原业务/车控/状态域　消费者：原业务、VUI、Runtime日志；任务中心结果回显 TBD
run_event_refinteraction_or_policy_resultprecheck_resultcontrol_resulttarget / observedquality / observed_atfinal_business_resultterminal_reasoncooling_until
终态：真实状态达标=SUCCESS；明确未达=FAILED；不可判=UNKNOWN。终态后清理卡/上下文/执行凭证并进入 Cooling，长期任务仍保持原 ENABLED 状态。
L1 · INTERACTION MODE & BIDIRECTIONAL ROUTES

交互不是只有“弹卡确认”：先选三种 InteractionMode，再走端侧或云端回路

InteractionMode用户看到/听到什么若后续需要执行，原业务必须提供什么不能做什么
SILENT静默不出卡、不播 TTSsilent_policy_decision_ref：关联 RunEvent、策略版本、scope、有效期和一次消费；必须经过安全/业务会签不能因为“没有交互”就省掉执行准入证据或端侧复核

L2 · EDGE CLOSED LOOP · 19 STEPS

端侧天气/路况保护：从任务中心到真实车况的 19 步

天气任务不是一条规则：同一个长期任务下有“雨/湿滑、雪/结冰、浓雾”三个分支。下方 19 步用雨/湿滑分支走完整链，另两个分支复用同一状态、RunEvent、卡片、授权、复核与回读框架。

分支触发前共同门禁本分支判断卡片确认后的动作执行前必须重读最终成功真相
雨 / 路面湿滑任务真状态=ENABLED；定义/产生权版本有效；车速门槛满足weather=RAIN OR road=WET，且当前非 WET_MODE切换湿滑模式最新任务、产生权、事件/授权、天气/路面、车速、模式、幂等真实 drive_mode=WET_MODE
雪 / 覆雪结冰同上；正式车速阈值、时效、防抖次数 TBDweather=SNOW OR road=SNOW/ICE，且当前非 SNOW_MODE切换雪地模式最新天气/路面、车速、驾驶模式与公共八项门禁真实 drive_mode=SNOW_MODE
浓雾同上；数据必须是同车、新鲜、质量可判weather=DENSE_FOG 且 rear_fog=OFF打开后雾灯最新浓雾、车速、后雾灯真实状态与公共八项门禁真实 rear_fog=ON

当前资料中的数据来源示例（非正式 IDL）：vision.outside.scene → 天气情况描述/路面情况描述，tri_speed / vehicle_control_0004，con_vehDrive / vehicle_control_0003，con_rearFogLight / signal_light_0004。产品需拍板业务语义，研发专项确认正式字段和能力 ID。

演示快照：任务 ENABLED｜RAIN + WET｜46 km/h｜NORMAL 模式产品语义演示；正式信号枚举、阈值、时效、TTS 和动作能力均由专项确认
