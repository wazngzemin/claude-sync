### S1-1 主例的“续航建议”在第三段、第四段、时间线图里是三种处理，且违反本章自己的准入规则

  - 方案 A（推荐，让主例服从已定规则）：把续航提醒改成**与主驾同时到达、Chat 还空闲时**进入（t1），这样它是 E1 的一部分，E2 合并重推时作为“旧输入”一并带上，与准入表不冲突。INTRO 改为：“主驾说“找附近的充电站”的同一刻，一条续航提醒也到了；紧接着副驾补了一句“要快充”。”第三段交接改为：“主例 t2：打断 E1，把 E1 里的两条（主驾的话、续航提醒）和副驾的新话合并，开启 E2。”

### S1-2 “工具结果单独处理”与主例 t6“工具结果 + 主驾补话一起重推”冲突，正文没有解释
- 问题：第一段说工具结果“单独交给 Director”，准入图写“工具结果（P1，单独）”；时间线 t6 却把“两处可达快充站”和“选便宜一点的”合在 E4 里。读者无法自圆其说。技术方案原文其实给了答案：合并属性**只决定出队后和其他普通输入是合并还是单独**，不管被用户插话重推时带不带上本轮的工具结果。
- 原句（m-s1）：“<b>标签三：能不能和别人合并。</b>用户的话、主动建议、事件可以合并；工具结果“保守地单独交给 Director……”（技术方案原话）。这个标签按来源写死，不由模型临时判断。”

- 依据：技术方案第 431 行“mergeable / isolated 只决定出队后是合并处理还是单独处理”；第 719 行“第二轮被补话时，待重推的是本轮 feedback + 新用户 + waiting”。

### S1-4 方案专题二误述 PRD 的边界：PRD 不是“以首字为界”，PRD 自己定义的就是“还没调用工具”
- 问题：专题二的立论是“PRD 以首字为界，技术方案改成以工具为界”。核对 PRD v0.5 原文，PRD 的合并条件是“正在推理 且 未输出完整 且 TTS 未起播”，并明确“未输出完整：表明还未调用工具，包括了首token未出以及首token出了但模型还没输出完的情况”。也就是说 PRD 的合并窗口**比“首字之前”更宽**，而且已经用“没调工具”来定义。技术方案真正补的是：PRD 默认“没输出完 ≈ 没调工具”，但模型流式输出时可能**先发工具**，所以要把“工具放行”做成一个明确登记的事件。更早的多人同时 PRD 也已用“任务的 FC 还没下发/输出”定义同时说。“以首字为界”是 10/19 宣讲 1 讲的线上规则，不是 PRD。图 m-replay 底部黄框同样有此问题。
- 原句（m-plan-replay）：“<b>PRD 怎么写的：</b>以“首 token 是否出现、TTS 是否起播”为界，首字之前统一“打断并合并重推”。PRD 自己也补了一句：“未输出完整：表明还未调用工具”。”
- 改写：“<b>三份材料的边界不一样。</b>线上（10/19 宣讲 1）：第一句“还没输出首 token”就合并，已经出了就“直接打断第一个指令，丢弃就好了”。PRD v0.5：推理“未输出完整”且 TTS 未起播就合并，并解释“未输出完整：表明还未调用工具，包括了首token未出以及首token出了但模型还没输出完的情况”。技术方案：把“工具有没有放行”做成输入管理亲自登记的事件，因为 DT 可能先发工具、后出字，“没输出完”不等于“没调工具”。”
- 图 m-replay 黄框原句：“PRD 把“首个字之前”统一写成“打断并合并重推”；技术方案补了一条工程约束……” → 改为：“线上按“首个字”划线；PRD 按“还没调工具、还没起播”划线；技术方案把“工具放行”变成明确登记的事件，放行后即使首字未出也不再合并。”
- 同步改：易错对照表“首字没出就可以合并重推”一行保留，但“应该是”补一句“（首字是线上旧规则）”。
- 依据：PRD 原文第 105–115 行；多人同时 PRD 第 5 行；宣讲 1 00:12:55 段；技术方案第 392 行（技术方案对 PRD 的转述本身就是“首 Token 前”，属于技术方案自己的说法，不能当 PRD 原话引用）。
