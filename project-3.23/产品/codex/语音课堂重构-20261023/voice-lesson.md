# 从“豆包，把空调调到 24 度”讲清语音入口
## 先把这句话放进车里
咱们先不背缩写，就拿一句话走到底：“豆包，把空调调到 24 度。”这句话是课堂示例，实际唤醒词和有没有免唤醒，要看具体车型配置，不能因为例子只写一次“豆包”就认为实车一定这样唤醒。我们假设这轮交互已经有效启动，用户接下来完整说出了调温要求。今天要看清的是：车怎么听见这句话，怎么知道你说完了，怎么确定最终文字，再把正确的要求交给办事模块。你先记住，车收到的是声音，不是一句天然准确的文字，更不是一条已经执行成功的空调命令。[S1、S6]

## 第一站：收音之后，两件事同时发生
用户开口时，车端麦克风持续采集声音，经过音频前处理，把适合识别的音频交给语音链路。OnePager 写的是每 200 ms 上送一帧音频。这里“帧”可以理解成一小包声音，边说边传，不需要等整句话说完再上传。图上到这里要分成两条同时向前的线：一条叫 ASR，一条叫 VAD。ASR 是语音识别，回答“你说了哪些字”；VAD 是语音活动检测，在这里主要帮助回答“你是不是还在说，这一段什么时候收尾”。所以不是先等 VAD 结束，ASR 才开始干活；用户还在说的时候，两者已经各自处理声音。[S1]

我们看文字这条线。你先说“把空调”，屏幕或识别服务可能已经拿到“把空调”；你接着说“调到”，过程文字变成“把空调调到”；你最后说“二十四度”，文字继续补齐。这叫流式 ASR。“流式”说的是文字陆续返回。系统里常把这种过程结果叫 partial，你直接把它记成“还可能修改的草稿文字”。这里的逐字变化是教学演示，不是实车日志，具体分片方式不能凭例子当事实。重要的是：这个时候有文字，不代表用户已经说完，也不代表文字已经定稿。[S1]

## 第二站：为什么停了一下，系统只能先准备
现在看 VAD 那条线。如果用户说“把空调调到……”停了一下，还没说温度，我们希望系统继续听。否则它提前把不完整要求交下去，后面就不知道调多少度。反过来，如果用户整句话已经说完，系统还一直等，用户就会觉得车反应慢。VAD 要处理的就是这个取舍：既别抢话，也别让人干等。因此内部方案把判停分成不同阶段，不是用同一个停止信号解决所有问题。[S1、S4]

按本课采用的 OnePager 基线，较短停顿达到 Soft VAD 的 300 ms 阈值时，系统先获得一次“可以提前准备”的机会。Soft 的意思不是声音轻，而是这次判断还不作为最终收尾。预请求就是拿当前已有的文字，先跑允许提前做的部分工作，保存结果。OnePager 提到拒识和 Context 等前置处理。拒识是判断这句话该不该被助手接住；Context 是准备理解这句话需要的场景信息。这里不等于直接执行空调动作，也不是先把一句回复播出来。用户仍可能继续说，因此资料明确 Soft 可以多次触发，而且不结束 ASR。[S1]

假设用户说完“把空调调到 24 度”后有了短暂停顿，系统可以先用这份文字准备一次。随后用户又补“只调主驾”，准备时用的内容就不再是最终要求。你作为产品要抓住这个区别：提前做准备可以提高速度，但不能让系统提前把用户的意思定死。技术方案称前置“无状态任务”，在课堂里可以解释成先算、先备，不因为这一步就产生不可撤回的车辆动作。旧 PRD 还明确不抢跑到 FC、Planner、DM 这些正式办事模块；不同文档的前置模块清单要保留各自版本，不能混成一份已实现清单。[S4、S5]

## 第三站：Hard VAD 收尾，二遍 ASR 给出定稿
停顿进一步达到 Hard VAD 的阈值，系统按当前策略确认这一段结束。本课基线写 600 ms。注意这是停顿阈值，不是从用户说第一个字开始计时，也不是 Soft 300 ms 后再追加 600 ms，更不是停顿 600 ms 就已经听到回复。资料在主链路里直接写了顺序：Hard VAD 确认说话结束，ASR 返回二遍 final 文本，再发送正式最终 Query。Query 就是这轮交给后续处理的用户请求文字。[S1]

“流式二遍 ASR”容易误会，我们在这里讲透：用户不用说两次。第一遍尽早把文字送出来，第二遍针对同一段声音做重新识别，得到本段最终文字 final。ASR 最佳实践描述，音频可以同时送两路识别，一路及时出字，一路在分句或结束条件后返回更适合定稿的结果。因此“二遍”不等于一定等第一遍全部做完，才把整段音频第一次交给第二个模型。它讲的是两种识别处理及结果用途，不是两次用户输入。[S2、S3]

为什么值得多做这一遍？因为早出的字可能听错，也可能缺少后半句帮助。二遍争取用更完整的这一段声音修正结果。旧 PRD 的设计示例是“播放音月”后来修正为“播放音乐”。不要把这个例子说成当天实车一定纠对。我们调温例子里，也必须以最终识别出来的温度为准，不能拿过程草稿偷偷执行。final 只表示这次识别定稿，仍然可能听错；如果二遍超时该用什么降级，当前证据没有明确规则，不能补写成自动用一遍兜底。[S1、S3、S4]

## 第四站：正式文字来了，前面的准备还能不能用
这时我们已经有最终要求，云端要检查之前的准备是否适用。OnePager 写得很具体：同一 request_id，并且正式 Query 与前一轮预请求 Query 完全相同，才复用支持缓存的模块结果。request_id 是给这一轮输入贴的编号，避免把不同轮次串起来；round_id 区分同一次输入里的多次预请求及最后的正式请求。[S1]

如果草稿和定稿都是“把空调调到24度”，前面的部分准备可能省下来。如果草稿是24度，定稿改成了26度，或者用户补了“只调主驾”，文本不一致，就按正式内容重新处理必要模块。准备没用上不等于系统坏了，它本来就是有条件的加速。真正不能接受的是拿旧意思的结果办理新要求。你在评审时可以问：“用户补了后半句之后，旧缓存会不会误用？我们能不能拿同一 request_id 的预请求和正式请求对照看？”这样问题就有了验收对象。[S1]

## 第五站：端云选择，和二遍纠错要分开
到这里还有一个容易混的概念叫端云仲裁。端是车机本地，云是联网服务；仲裁是决定本轮采用哪一路处理结果。二遍 ASR 关心“字听得准不准”，端云仲裁关心“哪条办理路径被采用”，两者不能画成同一个判断。[S6]

离在线仲裁 PRD 的正常网络、正常唤醒场景写的是音频并行进入端侧和云端链路。端侧命中白名单可先执行；没命中则按规则等待云端，异常时再走兜底。“把空调调到24度”是否属于某辆车当前允许本地处理的指令，不能只凭它看起来简单就下结论，需要查该车型配置与协议。若走云端，最终 Query 与 Context 才交给 Planner 理解并安排工具调用；若本地命中，执行结果和回复也要同步云端，让下一轮对话知道刚才发生过什么。[S1、S6]

最后，空调工具返回了什么、车辆温度设置是否真的变化，与豆包嘴里说了什么是不同的证据。生成回复文字之后，TTS 才把文字合成声音；端侧还要收到音频标识、拉取音频并播放，用户才真正听见反馈。ASR 是声音变文字，TTS 是回复文字变声音，中间还有理解、决策和真实执行。我们验收这句话，就要逐段对：声音有没有收全，final 温度对不对，选了哪条路，工具是否成功，最后有没有正确播出来。这样才是一轮完整交互。[S1；执行验收为产品解释]

## 参数旁注：把版本差异摆出来
旧多级 VAD PRD 写 Soft 300 ms、Hard 500 ms、语义 VAD 1000 ms，并注明暂定；OnePager 主链路写 Hard 600 ms；通用 ASR 模型说明写二遍默认 VAD 800 ms 且可配置。这些不是三个需要相加的等待时间。我们课堂主线用 OnePager 的 600 ms，但实车验收必须确认车型与构建。语义 VAD 的作用是再判断句子像不像说完整，比如“把空调调到……”缺目标值；它与 600 ms 的完整优先级和延长上限，最新主链路没有全部展开，要留作待核验，不能把旧版1000ms当全部车辆现状。
