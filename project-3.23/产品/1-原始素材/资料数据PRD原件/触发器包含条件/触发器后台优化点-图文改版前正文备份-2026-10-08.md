一、背景与目标
配置人员需要把业务需求写成触发规则：什么变化发生时开始检查、还需满足哪些条件、满足后交给哪个业务、多久允许再次触发。目前相关需求分散在条件、信号、交互和任务接入中，容易出现“页面能保存，但实际配错或下游接不住”的问题。
本次优化面向配置规则的产品／运营、接入业务研发和联调测试。需要解决两类问题：基础配置效率低，以及系统预设任务需要把车辆条件、视觉判断、用户开关与下游建议组合起来，但现有平铺配置难以表达和排查。
产品价值：相似任务复用已有判断与下游能力，减少每新增场景就开发一条专用链路；配置人员能看清什么时候开始检查、需要满足什么、交给谁处理；测试能定位未触发、重复触发或请求失败在哪一环。以三项云端任务的真实配置与正反例验收衡量，不以增加字段数量或画布节点数量衡量。
本期目标：保留并完善静态条件非必填、场景复制、指定泳道、测试／正式筛选四项需求；补充简单／Workflow 模式、当前所需视觉与开关条件、主动推荐带交互卡、必要执行策略和节点运行记录。具体上线批次由平台评审确认。
本文是产品需求评审稿，保留现有章节和原始需求。技术方案已经明确的字段与模式写入配置要求；未确定的策略、接口责任和实现范围集中列在 8.2，待评审后回填。需求要求、技术已设计、实际已实现与已上线分别核对，不作同一结论。

背景与问题
现有触发器配置平台已经能支撑基础配置，但在真实使用里，卡效率：静态条件必须填写，导致很多场景被迫补无意义字段；不能复制场景，重复劳动多；场景无法指定泳道生效，灰度验证不够灵活；测试/正式标签缺少筛选能力，查找成本高。
用户场景
1. 创建简单场景时，不希望被静态条件必填。
2. 配置相似场景时，希望一键复制后再做改动。
3. 联调或灰度时，需要让场景只在指定泳道生效。
4. 排查配置时，需要快速区分测试场景和正式场景。
需求内容
需求一：去掉静态条件必填限制
- 静态条件改为非必填。
- 当业务场景不需要静态条件时，允许直接保存。
需求二：支持场景复制
- 配置平台提供场景复制能力。
- 复制后应保留原场景主要配置内容，并生成新场景实体。
- 复制后的场景名称或标识需避免与原场景冲突。
需求三：支持场景在指定泳道生效
- 场景配置中新增泳道生效范围控制。
- 支持指定场景仅在目标泳道生效，未命中泳道时不生效。
- 需保证默认线上逻辑不被误伤。
需求四：支持按测试/正式标签筛选场景
- 列表页支持按测试标签、正式标签进行筛选。
- 支持单独筛选，也支持组合筛选。
- 筛选结果需与场景真实标签状态一致。
二、整体方案与职责
配置流程：场景列表 → 新建／复制 → 选择简单／Workflow 模式 → 基础信息与适用范围 → 配置判断及查看实际启动信号 → 命中后的下游参数 → 运行策略 → 校验、测试、发布。
运行流程：指定信号更新启动检查 → 读取本次输入与真实任务状态 → 完成条件／模型判断 → 最终满足且策略允许时交给既有下游；不满足或无法判断时记录原因、结束本次。后台配置顺序不等于车辆执行顺序。
排查流程：场景详情 → 运行记录 → 查看输入、条件结果、拦截原因和下游反馈。
后台管理规则，不直接执行车辆动作。Trigger（触发器）负责启动与场景判断，可以使用确定性条件或模型理解已有视觉描述；满足后发出业务事件或约定请求。DT 负责下游模型处理与工具调用，VQA 负责按需视觉问答；Trigger 的模型判定不等于 DT 调 VQA 获取新信息。
即时交互卡由接入业务注册、发起并处理结果，Planner 不直接负责注册拉卡。端侧天气链路由原业务本地闭环，不经过 DT；云端三项任务沿已评审的主动推荐／DT 链路处理询问与执行。这里新增的是判断组合及下游参数配置，不重新分配卡片或车控职责。
后台发布不等于用户开启任务。后台管理规则定义、发布状态和适用范围；任务中心提供本车任务列表及用户开关；单车状态由对应接入与保存接口落实，Trigger 读取真实状态。AI 设置是另一层控制，不能代替单任务开关。云端单车接口已在技术方案提出，首读、ID 对应和初始策略继续收口；端侧保存与通知单独确认，不能替其他模块认领。
三、场景管理页：找得到、分得清、能复用
3.1 新建与筛选
新建场景先选择配置模式（简单／Workflow），再填写场景类型、业务分类及适用范围。简单模式复用现有条件配置；Workflow 模式用于组合条件与模型推理判断，详细操作见 4.7。配置模式与场景类型分开，不按“走不走 DT”划分模式。
筛选项平铺展示：渠道、环境、名称、ID、状态、来源、类型、业务分类。业务分类支持全部／普通／预设；多个筛选共同生效，分页保留筛选条件。测试／正式筛选沿用原需求，不通过来源字段推导。
来源、业务分类、场景类型与环境分别表示不同含义，分别配置和筛选：
来源与业务分类：source 记录场景由谁注册，例如 aidv_backend、aidv_task_service；是否属于系统预设任务，使用独立字段 scene_category 区分：normal 为普通场景，preset 为预设场景。存量场景默认 normal，需确认迁移清单后再标记为 preset；不能把所有后台创建的场景都视为预设任务。
环境标签：tag=test 为测试，tag=formal 为正式。按技术方案，由服务端根据部署环境附加标签；页面展示实际环境，筛选支持测试、正式或两者。创建和发布时如何选择目标环境，需要与部署入口统一，不能任意修改标签就改变实际运行环境。泳道控制与此分别处理。
场景类型：vehicle_resource 为信号条件场景，vlm_inference 为模型推理场景，timer 为定时场景，mix 为条件与推理混合场景。本期混合判定按技术方案前述范围暂不开放定时；后文 Timer 适配是否仅为预留，列入评审确认。
3.2 列表与详情
列表明确展示场景名称／ID、渠道、环境标签、生效范围、更新人／时间和发布状态；补充场景类型、普通／预设分类及配置模式。所属任务、来源、运行位置和当前定义版本在详情展示。生效范围以摘要呈现，展开查看车型、客户端版本和车辆范围，不把完整条件平铺在列表。
详情区分规则发布状态与单车任务状态，不显示一个混合的“开启”值。Workflow 场景展示当前判断图及关联动作；查看历史运行时使用当次定义，不以最新配置替代。
人工配置规则与动态任务注册规则应能区分。动态规则详情显示所属任务、注册方和注册／更新／停止／注销状态；默认作为查询入口，编辑和停止权限按注册方协议开放，不能直接套用人工场景操作。
3.3 复制场景
复制条件、下游输入和运行策略，生成独立的新场景。建议以草稿打开，要求确认名称与适用范围后再发布。不得复制原场景的运行计数、发布状态和车辆用户开关；跨渠道复制后重新检查信号、单位和下游能力。
验收：筛选结果与实际字段一致；复制后的场景独立修改，原场景不变；新建测试场景不自动在正式环境生效。
3.4 Workflow 场景的编辑与替换
已有 Workflow 按当前技术方案暂不支持直接修改判断流程。详情页明确标识“判断流程只读”，编辑入口说明可修改范围，不提供会失败的节点编辑操作。动作、基础信息和范围是否可单独修改，由后台研发确认。
需要调整判断时，采用复制重建方案进行评审：复制原定义，生成新场景及独立 Workflow，重新校验与测试；不复制运行记录、运行计数、发布状态和单车用户选择。仅在保存方与任务关联方案确认后，才允许替换旧规则；不能直接把新场景默认状态当作原用户选择。
替换必须避免同一任务的新旧规则同时有效，也不能在新规则准备失败时先关闭旧规则。具体切换、回退、任务关联及用户选择保持方式待确认。删除场景前展示任务关联和运行影响，保留历史记录的追溯关系；不因删除配置而删除用户已作出的选择。删除／停用的具体权限与方式沿用平台机制。
四、场景编辑页：按一次配置的顺序组织
4.1 基础信息与适用范围
配置场景名称、场景类型、普通／预设分类、所属任务、适用渠道／车型／客户端版本／车辆范围及运行位置；展示由服务端确定的环境。关联预设任务时明确任务 ID 与场景 ID 的对应关系。同一任务关联多条规则时，共享该任务的用户选择，不重复创建任务中心卡片；当前单车接口按场景 ID 生效时，需要确认多规则状态一致的实现办法。
发布页展示实际目标范围。技术方案中“预设发布默认全部渠道生效”不能绕过能力适用校验：缺少必需信号或下游接入的车辆不得参与有效运行。相关 VLM 当前仅赛力斯渠道接入，其他渠道的任务展示、发布拦截和范围限制方式需联合确认，不默认全部车辆可运行。
增加“生效泳道”：只在选定的隔离运行环境中生效。泳道控制实际运行范围，测试／正式标签用于分类展示，两者不能互相替代。未选泳道时沿用什么默认范围，需要在发布前明确显示。
任务中心需要的任务名称、副标题、展示顺序和初始开关策略，由任务定义统一提供。若已有任务管理入口，本页关联并展示，不再维护第二份。发布新版规则不得覆盖用户已保存的选择。
4.2 启动事件：什么时候开始检查
单独展示启动方式及参数。例如“挡位从非 P 挡变为 P 挡”表示一次停车变化；“当前挡位等于 P”只是当前状态，不能把持续上报 P 挡当成多次停车。
根据所选场景类型展示对应配置：端状态变化选择信号和变化范围；定时场景填写执行时间及已支持的重复周期；模型推理场景选择已接入的输入和判断能力。
静态条件改为非必填。有合法启动方式且无需额外条件时允许保存；启动方式与条件全部为空时，不得形成无约束触发规则。多个事件同时配置时，页面说明是任一更新启动检查，还是其他已支持组合规则，不把连续变化默认当作时序能力。
4.2.1 实际启动信号
页面根据当前配置展示“收到哪些信号更新会开始检查”，包括中文名称、信号 ID 和选取依据。该清单由运行规则生成，不与判断条件另维护两份。

混合流程需要确认从哪些节点汇总启动信号，以及多个输入同时更新时如何避免同次处理重复启动。节点之间不能任意拼接不同时间的数据；本次输入、补齐来源、采集时间和过时处理必须可追溯，具体有效期按信号协议确定。
业务反例：儿童锁仅配置“档位变为 D”启动时，车辆已在 D 挡后才识别到儿童，不一定再次启动。产品需明确是否要覆盖；需要覆盖时补合法启动设计，不把静态年龄条件变化默认当成已支持的启动入口。
4.3 判断条件：开始检查后，还需要满足什么
一条条件包含“信号＋对象位置＋运算符＋比较值”。例如“车门／主驾／开关状态／等于／打开”，位置不拆成另一条条件。可选值、单位和运算符从公共能力定义中读取。
支持“全部满足／任一满足”的条件组，并清楚显示组间关系。例如“主驾门打开或副驾门打开，且车速为 0”。保存后显示可读摘要，避免括号含义变化。
缺失、未知、过时与 0、关闭分别处理，不能默认当作满足。多个变化条件做“全部满足”，不代表支持先后顺序；持续多久、首次发生、阈值跨越、地理距离等能力，只有运行侧明确支持后才允许配置。
涉及时间时写清时区、统计范围和重置条件；涉及位置时写清地点来源、距离单位，以及使用导航剩余距离还是坐标距离。字段旁展示解释，不让配置人员自行猜测。
4.3.1 结构化视觉条件
选择流程：已接入的 VLM 信号 → 对象位置 → 属性 → 合法比较方式 → 比较值。当前技术方案明确补充舱内低频信号的条件元数据，不能由产品手写一份与运行侧不同的枚举。

位置和年龄必须来自同一个乘客对象，不能用主驾的儿童年龄与后排成人的位置拼成命中。多个位置的任一／全部关系在页面显式表达；不支持的组合不得保存为可运行规则。字段名、位置与年龄分类按真实协议归一化，详情和运行记录保持同一中文含义。
4.3.2 开关与单任务状态
条件选项从真实开关目录获取名称、配置键、车／账号维度、数据类型、可选值及比较方式；运行时查询相应维度的实际值。目录返回的默认值不能在真实值读取失败时当作已开启。

云端预设列表通过 scene_category=preset 查询，服务端附加部署环境标签；任务中心通过 UpdateSceneStatusForVehicleRequest 更新单车场景状态。还需确认首次状态读取、任务／场景 ID 映射、初始策略、更新失败回显和新版选择保持。端侧持久保存与变化通知单独接入，不从这项云端接口推导保存责任；徐燃不默认承担所有单任务状态保存。
4.3.3 模型推理判断
模型节点选择已接入的 VLM 输入，填写判定目标 goal 和原始判断描述 original_query；字段用途和示例与条件编辑分开。该节点理解已有视觉描述是否满足目标，不编排 DT 调 VQA，也不凭提示词补出缺少的湿度、洗车退出或温差信号。
判定结果区分满足（PASS）、不满足（REJECT）、无法判断（UNKNOWN）。输入缺失、查询失败、模型调用失败、返回无法解析或超时按无法判断记录，不作为满足继续下发。要求结果互斥且无歧义；“未达成”“无法判断”不能因包含某个关键词被误判为通过。输入、耗时、判定依据和失败原因按已有权限展示。
4.4 命中后处理：交给谁、传什么
选择已接入的处理类型，再展示该类型需要的参数。不向所有场景开放同一套卡片、模型和工具字段。
类型一：提交主动推荐。 配置固定建议 Query（交给下游的业务说明）、变量引用、交互策略及协议要求的按钮／出卡参数。保存前预览最终提交内容，区分已知事实与仍需判断的信息。
云端儿童锁、后视镜加热和充电口盖按 9 月 15 日评审链路接入：Trigger → 主动推荐 → DT → 询问与执行。儿童锁、后视镜不需额外设备识别，不代表不经过 DT。充电口盖需 DT 调用 VQA（视觉问答）判断充电设备，明确发现后再询问；Trigger 不自行编排这段工具调用。
固定 Query 按已约定格式填写：“[类别]advisor：你的目标之一是[业务目标]，[当前依据与建议]。策略：语音确认。”本次三项询问任务不能改成静默执行。卡片正文与播报按该链路生成，按钮及出卡参数按真实协议接入，不另加一套自由编辑卡片的规则。
类型二：发送业务事件。 选择已接入的接收业务和事件定义，填写约定参数。端侧天气任务由天气业务接事件、接入即时交互卡并处理用户回应，本地确认不经过 DT。后台若尚不支持端侧规则下发，本页只管理定义和交付版本，不提供无效的“发布到端侧”。
类型三：生成业务事件日志。 配置事件 ID、来源、模板、关联信号和位置，按需要携带变化前后值。内容预览应能说明“哪个对象发生什么变化”；不能把“歌曲变化”直接写成“用户点击下一首”。日志合并按事件类型确定，不预设统一 30 秒窗口。
三种出口都保留场景、规则版本及本次命中的关联信息。切换处理类型时，提示不兼容配置；缺少接收方或必填参数时阻止发布。

1）列表： 来源、环境和类型筛选准确；复制产生独立草稿，不带走用户选择和运行计数。

刘杨与产品确认：混合图从哪些节点汇总启动信号、多路输入如何避免重复运行；已经进入 D 挡后才识别出儿童是否再次检查；各节点读取什么时刻的数据，补齐与过时如何处理。输出实际启动清单及会触发／不会触发的正反例。
8.2.7 多分支汇合与未知
刘杨与测试确认 4.7.3 的三态建议表、等待／短路方式和超时边界；明确儿童分支通过、宠物分支失败时是否继续。输出可直接验收的结果关系与被阻断节点记录，不仅回答“支持 AND／OR”。
8.2.8 修改替换与环境范围
后台前后端、任务中心确认：已有 Workflow 的可修改范围、复制生成的 ID、旧规则停用与新规则启用、用户选择保持和替换失败恢复。同步收口服务端环境标签、泳道隔离与预设默认全渠道的能力限制；缺少必需能力的车辆不能参与有效运行。
8.2.9 记录与联合验收
刘杨、后台与测试确认：运行详情实际保存哪些输入与模型摘要、权限与保留时长、历史按当次定义回显，以及下游能回传到哪一环。按 7.1 执行专项样例；明确带卡推荐模拟器不支持时的实际联调入口，不用请求成功代替展示或车辆结果。
