- 客户所有需求均通过解决方案\(张航\)的链路完成，客户只需要传入session\-id来区分不同对话session，对话历史统一由解决方案\(张航\)管理，客户也不需要自行调用方舟API

## 多轮对话意图识别
在真实场景中，可能存在少量需要关联上下文，才能理解最后一句话的意图。需要测试一下，在多轮对话中，LLM是否能够准确把握用户最后一句话想要表达的意图。用户的最后一句话可能是独立表达当前意图的语句（不需要联系上文，上文可能构成误导），也可能需要联系上文才能形成完整的意图表达
数据集构建思路（组成部分）
- 构建2轮对话，第一轮对话直接使用单轮对话意图识别数据。在此基础上，用户追问一句和上文有关系的问题，表达和上一次相同的意图识别，如：
    ```Python
    user：明天北京天气如何
    assistant: 明天北京天气xxx
    user：那后天呢
    ```
- 构建2抡对话，第一轮对话直接使用单轮对话意图识别数据。在此基础上，用户追问了另一个意图的问题，和上文没有任何关系，如：
    ```Python
    user：明天北京天气如何
    assistant: 明天北京天气xxx
    user：我喜欢北京的天气
    ```

## 天气插件说明
插件名称：WeatherPlugin
插件参数：
- city：城市
- district：区县
- start\_time：开始时间，格式为yyyy年mm月dd日
- end\_time：结束时间
插件调用说明：
1. 天气插件不论如何都会返回今天的天气，如果传入了`start\_time`和`end\_time`是一段未来的时间，还会额外返回未来天气
2. 天气插件不支持查询过去时间的天气，如果`start\_time`早于今天，那么返回为空
3. 天气插件不支持查询太远未来的天气，如果`start\_time`晚于2周后，那么返回为空
4. `end\_time`如果早于`start\_time`，判断`start\_time`是否满足条件2/3，如果满足，返回为空，否则返回今天的天气
5. 如果`start\_time`传了，但是`end\_time`没传，判断`start\_time`是否满足条件2/3，如果满足，返回为空，否则返回今天的天气。如果想要查询未来某一天的日期，建议`start\_time`和`end\_time`传入同一天。
6. `start\_time`支持传入`今天`这个值，但是也仅支持`今天`，不支持`明天`，`昨天`等。所以建议直接传入日期
7. 天气插件如果查询国外天气，`district`字段大概率没用，只能用`city`查询大范围的天气

#### 提槽追问
提槽追问的主要作用是当用户的一次query文本，不足以提取出所有函数参数的时候，需要追问用户。但是天气接口一共是4个参数，由于该场景用户汽车语音助手，在用户进行query查询时，同时会输出一些结构化信息（包含今天的日期、当前所在位置），所以当query没有提到时间和位置信息时，可以自动填充日期为今天，位置为当前所在位置。所以天气插件的场景不需要多轮提槽。
### 插件参数预处理
经过LLM提槽后，针对天气插件的4个参数被提取出来，还要经过一些预处理，才能拿去调用插件
- 由于prompt中提示LLM，对无法提槽的字段设置值为`无`，但插件入参不支持`无`，需要将值为`无`的地方改成空字符串
- 如果`start\_time`合法（两周内的日期），且`end\_time`为空，此时需要将`start\_time`的值赋值给`end\_time`
### 插件返回结果后处理
天气插件的返回结果格式为Json，格式如下：
```JSON
{
    "plugin_observation": {
        "observation": "真正的有用的信息"
        ... // 其他字段
    }
    ... // 其他字段
}
```
我们需要从插件返回的结果中，拿到最有用的部分，用于输入后续的总结模型
- 如果天气查询成功，那么`observation`会返回一个json字符串，里面包含了天气信息。拿出这个字段作为后续总结模型的输入
    - 测试skylark\-pro\-2\.1对json字符串的总结效果还不错，人设模型的总结能力还未测试
- 如果天气查询失败，那么`observation`将返回一个字符串：`执行成功返回空结果`。这种情况，我们将信息修改为`抱歉，我无法为你查询到天气状况`，然后再输入后续的总结模型

### 插件返回内容总结
视频插件的返回结果不需要使用LLM总结，直接用固定话术总结
插件返回格式为json，如下
```JSON
{
    "plugin_observation": {
        "observation": "一个json字符串"
        ...(其他字段)
    }
    ...(其他字段)
}
```
`observation`字段中json字符串的格式大致如下
```JSON
{
    "data": {
        "list": [...],  // 这里是返回的视频列表，如果没有搜到视频，则是一个空列表
        ...  // 其他字段
    }
}
```
从`data/list`中可以获取视频检索的结果，插件的内容总结话术如下：
- 如果搜索结果不为空，话术为：`已为您找到x条视频`，其中x为list元素的数量
- 如果搜索结果为空，话术为：`抱歉，无法找到相关视频`

# 天气提槽优化
## PE优化
最初的prompt1
- 输入输出token较多，few\-shot充分
优化后，prompt2
- few\-shot中有些本身就能答对的，可以去掉
- LLM回答的日期格式经常会加入空格，如`2023 年 10 月 22 日`，把日期变成6位数字，减少token
- `start\_time`和`end\_time`每个算3个token，换成`start`和`end`，只算1个token
优化后，prompt3
- 在prompt2上发现对city和district提取不太准确，模型对中国行政区划理解不是很深刻，需要大量的few\-shot来举例，所以加了一个example，用少量输入token换取效果
- 把原来输出格式（4行），换成了1行，用逗号分割，去掉了keys，只保留values，节约大约8个输出token
优化后，prompt4
- prompt3的满分率和prompt1差距过大
- 优化了一下few\-shots的例子，尽量能覆盖到一些典型case
- 修改了一些说法：如天气\-\&gt;自然气象（解决日出日落无法理解为天气的问题）
- 输出格式经常不符合指令，prompt中再次强调输出格式
- 把结束时间的字段去掉，换成了持续时间。节约了大概5个输出token

## 吉利关键词匹配
对用户输入的query\+当前的history所有内容进行判断，判断内容中是否包含吉利关键词。如果发现query\+history中包含吉利关键词，后续会有特殊处理逻辑。
- 关键词数据文件：https://code\.byted\.org/3rd\_rec/geely\-llm/blob/master/intent/assets/safety\_check/geely\_keywords\.txt（这部分目前在方舟代码库，但后续建议由工程模块维护，提供客户快捷配置的能力）
- 数据文件怎么用？
    - 数据文件中每一行代表一个关键词，有2种格式
    ```Python
    AAA  # 格式一，直接代表关键词本身，直接判断是否包含AAA关键词本身
    BBB:xx,yy  # 格式二，需要判断两次，先判断是否包含BBB关键词，如果包含，判断是否包含xx或yy中的任意一个，如果包含，则认为包含吉利关键词
    ```

## 推荐倾向性干预
背景：吉利客户希望当遇到`推荐一辆车`类似的query时，如果没有指定品牌，则推荐吉利的车，而不是其他车。
典型case如下
```Python
推荐一辆比亚迪的汽车，20万左右  ->  推荐比亚迪
我这辆比亚迪的车开了好久了，想换一辆，预算20万左右  ->  推荐吉利
推荐一辆200万左右的豪车  ->  推荐吉利
我有30万预算，应该买比亚迪还是特斯拉  ->  推荐比亚迪或特斯拉
我有30万预算，应该买比亚迪还是极氪  ->  推荐极氪
给我推荐一辆35万以内的车  ->  推荐吉利
推荐一辆20万左右的新能源汽车  ->  推荐吉利
给我推荐一辆十万左右的新能源汽车  ->  推荐吉利
```
### 方案一：意图\+SP
- 意图模型中新增`推荐`类型的意图。当`意图=推荐`时，记录一个标志位`intent\_buy\_car=True`，然后进入`意图=其他`（即闲聊或联网）的逻辑
    - 意图模型EP：ep\-20240314120253\-fk6vj
    - 注意，该模型仅用于测试，发版时，应当把这个模型覆盖到\-\&gt;【吉利意图常驻】ep\-20240229102432\-6b8tk
- 经过联网意图判断，当`意图=联网`时，接下来该调用query改写接口。
    - query改写接口默认参数temperature=1\.0
    - query改写接口默认参数top\_p=0\.7
    - query改写接口默认参数top\_k=0
    - 如果有车型信息
        - SP加上这段话`用户当前位于\{car\_info\}车内。`
    - 如果`intent\_buy\_car=True`
        - SP加上这段话`如果要你推荐汽车，优先推荐吉利旗下产品。`
        - query改写接口temperature=0\.01
        - query改写接口top\_p=0
        - query改写接口top\_k=1
> 也就是说，如果即有车型，又满足`intent\_buy\_car=True`，SP=`用户当前位于\{car\_info\}车内。如果要你推荐汽车，优先推荐吉利旗下产品。`并且要修改默认参数。
> 
>

# 联网插件实时性
测试query改写\+总结，分开和一起的时延差距
query改写\+总结连一起请求：平均latency=1\.8623639917373658秒
query改写和总结分开请求：平均latency=1\.8485259532928466秒
query改写平均耗时：0\.23235592246055603秒
总结平均耗时：1\.586040884256363
**所以query改写和总结可以分开，没有什么时延损失**
方案一：替换query中的时间标签
```Bash
"今天有什么新闻" -> "2024年3月12日有什么新闻"
"最近有什么新闻" -> "2024年3月02日-2024年3月12日有什么新闻"
```
问题：存在典型badcase
```Bash
"网上搜一下为什么如今天才这么稀缺" -> "网上搜一下为什么如2024年3月12日才这么稀缺"
```
方案二：增加补充信息
```Bash
"今天有什么新闻" -> "今天是2024年3月12日，今天有什么新闻"
"最近有什么新闻" -> "最近是指2024年3月02日-2024年3月12日，最近有什么新闻"
```
问题：query改写不一定能保留日期
```Bash
"今天是2024年3月12日，今天有什么新闻" ->经过query改写后-> "今日新闻"
```
经过多个方案测试，踩坑，最终决定方案如下：
## 最终方案
直接替换日期的case
```Bash
"今天", "今日" 
```
增加补充信息的case
```Python
"大大前天", "大前天", "前天", "昨天", "昨日", "明天", "后天", "大后天", "大大后天"
```
## 修改方法
1. query前处理
如果意图=联网，那么对query做前处理（调用query改写和联网接口之前）
- 提前加入额外词汇
- 先用jieba分词
- 针对分词结果，如果遇到“今天”，“今日”，则替换成日期，如果是其他时间描述词，则在query后增加补充信息
样例代码
```Python
import jieba
simple_time_labels = ['大大前天', '今日头条', '今日说法']
for w in simple_time_labels:
    jieba.add_word(w)
def get_date_from_word(today_date, time_label):
    # 把时间描述词改成具体的日期，自行实现
    # 如：today_date="2024年3月13日"，time_label="昨天"
    # 返回："2024年3月12日"
    pass
def rewrite_query_time_label_simple(today_date, query):
    replace_candidates = set(["今天", "今日"])
    replenish_candidates = set(["大大前天", "大前天", "前天", "昨天", "昨日", "明天", "后天", "大后天", "大大后天"])
    final_query, replenish_info = "", ""
    for word in jieba.lcut(query):
        if word in replace_candidates:
            target_day = get_date_from_word(today_date, word)
            if target_day is not None:
                final_query += target_day
            else:
                final_query += word
        elif word in replenish_candidates:
            final_query += word
            target_day = get_date_from_word(today_date, word)
            if target_day is not None:
                replenish_info += f"。{word}是指{target_day}"
        else:
            final_query += word
    return final_query + replenish_info
```
输入输出举例：

# 位置信息过召问题
位置信息过召是指在query改写阶段（如联网query改写或视频query改写），错误的将位置信息改写到了query中。
为了解决这类问题，将位置信息从原来的input prompt中挪到system prompt中（因为在训练query改写模型的时候，input\_prompt也只有时间信息，只有极少的数据包含了位置信息）
典型Badcase
```Python
当前时间：XXXX年XX月XX日XX时星期X，当前位置：上海市徐汇区
如果你希望借助搜索引擎回答下面的问题，你会如何搜索。如果需要搜索多次，请用[next]分割。
问题：给我找点资讯
-> query改写结果：上海徐汇资讯
```
- 旧方案
    - System prompt
        ```Python
        当前车型：{car_info}
        ```
    - Input prompt
        ```Python
        当前时间：{time_hour}{weekday}，当前位置：{city}{district}
        如果你希望借助搜索引擎回答下面的问题，你会如何搜索。如果需要搜索多次，请用[next]分割。
        问题：{query}
        ```
- 新方案
    - System prompt
        ```Python
        当前位置{city}{district}
        当前车型：{car_info}
        ```
    - Input prompt
        ```Python
        当前时间：{time_hour}{weekday}
        如果你希望借助搜索引擎回答下面的问题，你会如何搜索。如果需要搜索多次，请用[next]分割。
        问题：{query}
        ```
- 视频query改写方案类似，只是把prompt中的`搜索引擎`换成`抖音视频`
