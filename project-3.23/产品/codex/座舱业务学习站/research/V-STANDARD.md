# 学习站章节标准（以 V 章 v60 为基线，只能更好，不能更差）

## 读者和目标
读者是初级 AI 产品经理，负责 Planner。目标用费曼学习法检验：读完能把这一章讲给别人听，面试时讲得出设计理由；遇到 badcase，知道先查哪一步。

## 一、讲法（硬性要求）
1. 用设计者的口吻讲系统本身。每个 h2 都要讲清四件事：
   - 这一步解决用户的什么问题；
   - 为什么这样设计，而不是别的设计；
   - 这样设计的代价或风险；
   - 出了问题先查哪里。
2. 正文里不出现来源和核验的说法。禁用词：资料、文档、PRD、需求、清单、宣讲、会议、纪要、原文、口径、写明、日志显示、待确认、尚未确认、没有展开、未展开、不能据此、资料冲突，以及书名号里的文档名。资料之间有冲突时，按最合理的那种讲；车型之间的差异，讲成设计选项。产品成熟度用一句产品事实交代（例如“目前还在预研”）。
3. 部件第一次出现就讲全：它是什么模型或系统，跑在哪里，什么时候被调用，收到什么，输出什么，学过什么或包含什么，为什么这样设计，关键数字。之后再出现时，用统一叫法，并点回前文。全站统一叫法以 component-cards.md 为准；本章出现新部件，先由 Claude 写进卡片，再开始写正文。
4. 每个术语第一次出现时，当场用一两句话讲清楚。英文缩写要附中文全称。
5. 句子要短，一句只讲一件事。不要用连续否定的句式（“不能……也不能……”）。

## 二、结构
- 开篇：这一章讲什么，和 Planner 有什么关系，主例是什么，配一张总图。
- 若干编号 h2（一、二、三……），沿着一次真实请求往下推进。每个 h2 下有若干 h3，h3 标题就是这一小节要讲明白的那个道理。
- 每个 h2 的最后一段，以“这一段讲给别人听，可以这样说：”开头，接 2～4 句第一人称口述。
- 收尾：三分钟口述稿（第一人称）、最容易讲错的地方、复述路线图。
- 附一：术语表（术语 / 一句话定义 / 模型与部署位置 / 在第几段讲）。
- 附二：历史版本与关键数字，放在折叠里。
- 全章只有两种折叠：原始全图、附二。

## 三、例子和案例（硬性数量）
- 每个 h3 至少 1 个例子，以“**例子：**”开头：拿一句具体的话，把机制走一遍，写出用户原话，以及每一步拿到什么、判断什么、交出什么。
- 每个 h2 有 2～4 个案例，以“**案例：标题**”开头，按这个顺序讲：用户看到了什么 → 系统里实际发生了什么 → 问题出在哪一步 → 怎么改、怎么防。优先用真实发生过的情况，用设计者口吻讲（“我们遇到过……”）。

## 四、图
- 原章节已有的图全部保留，放进对应的段落。
- 每个难点配一张新图：一句话讲不清的、最容易混淆的、有分支或循环的地方。每张图只讲一件事，节点不超过 9 个；颜色要有含义并配图例；“预研”的内容用虚线框表示。图上的文字同样遵守第一节的禁用词和统一叫法。
- 每张图前面加一句话，告诉读者这张图该看什么。

## 五、重点
- 每个 h3 加粗 1～2 处：核心结论、最容易混的区分、关键数字。每处不超过 40 字。

## 六、覆盖
- 对照《AI汽车SOP功能清单》中属于本章的模块，逐项核对：每个二级功能都要在正文里讲到。
- 对照本章原有内容（旧版网页 + research/chapters/<章>/ 下的 notes 和 raw），确认知识点没有丢。去向登记在 destinations.md。

## 七、流程（Claude 指挥，Codex 执行）
1. 研究（Codex）：读本章原有内容、notes、raw 原文、SOP 清单中的对应条目，输出 facts.md（内部用，每条事实标来源）和 destinations 底表。
2. 设计（Claude）：写本章大纲、新增的部件卡片、每张新图的设计、每个 h2 必须讲到的事实清单。
3. 写作（Codex，多个任务按 h2 并行）：一次写到位，包括设计者口吻、例子、案例、加粗、图位和 SOP 覆盖。必须增量保存，每次回复要短（单次回复超过约 16 分钟会被切断）。模型用 gpt-6.1-sol，推理强度 high。
4. 画图（Codex，可与写作并行）：按 Claude 的图设计画图。
5. 审核（Claude）：检查禁用词、部件首次出现的完整性和叫法统一、例子和案例数量、SOP 覆盖、知识点去向；在真实浏览器里逐张看图。不合格就退回给 Codex，最多 3 轮。
6. 生成网页并验收（Codex 生成，Claude 用浏览器验收）：结构、搜索跳转、编辑保存、手机宽度、控制台、其他章节未被改动。
