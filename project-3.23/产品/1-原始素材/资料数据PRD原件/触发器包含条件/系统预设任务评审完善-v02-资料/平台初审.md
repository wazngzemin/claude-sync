# 平台产品负责人视角：业务必要性与投入产出审核

对象：当前《PRD-系统预设任务配置平台与端云交互框架-评审完善-v01.md》及保存的用户原稿正文。这里只判断产品论证是否充分，不重新证明现平台已实现，也不代替项目排期。四项任务范围必须保留；以下“本期/后续”均是供主产品会签的优先级建议，不是擅自缩项决定。

## 结论

现稿已经说明怎样避免误执行，但还没有充分回答：“为什么四个任务值得做平台改造、哪些重复成本应被消除、增加这些配置后产品到底少做什么、研发到底少改什么？”应保留业务闭环，补一页平台建设取舍与复用验收，而不是继续扩充回调、字段和异常。

## 1. 现状判断仍缺可核验的改造基线

**现稿问题：** 1.2 以“此前页面核验”统称平台已有内容，原稿说“每新增一项云端任务都要重新接状态、模型、卡片和车控”。这能作为待解决问题，但不足以证明每项现有能力都必须重建。若研发说明某接口已通用，整段价值论证容易被推翻。

**应改什么：** 不把“重复接入”直接作为已量化事实；在平台章前增加最小基线：已观察的页面入口、它能完成的配置、四任务中不能完整表达的具体业务、拟扩展点、需哪位确认。重点区分“已有能力但未注册本场景”和“公共能力缺失”。

**可直接写入 PRD：**

> 当前已观察到的配置入口包含基础信息、条件组、下游动作及频控。用户原稿提出的明确缺口，是同一份配置尚未完整说明任务实际许可、识别结果如何进入询问、用户回答如何进入后续动作及最终结果。是否已有可复用接口、哪些仅需场景注册，须由相应模块在能力清单中确认。本期优先补缺口和接入，不重复建设已有通用能力；本文不据此推断所有新增任务都必须重写全部链路。

**落地证据：** 平台/业务研发填写“现有入口或能力引用—当前支持—本场景缺口—新增交付”，不需要先写全公司能力百科。

## 2. 四任务只被并排列出，没有证明它们复用哪一层

**现稿问题：** 1.3 写“复用能力和阶段”，2.1 列四任务，4 章主要围绕充电；读者仍会问天气端侧、充电云端、加热退出不同，为什么称同一框架。

**应改什么：** 加一张“共同部分/差异部分”表，明确共同产品规格不等于一套代码或同一发布平台。

| 层次 | 四任务能共同定义什么 | 不应强行统一什么 |
|---|---|---|
| 任务许可 | 哪个任务、作用车辆/账号、用户是否允许继续服务 | 状态实际由哪个服务承载、各任务总开关关系 |
| 条件事件 | 启动事件、当前条件、时效、稳定判断、频控依据 | 天气标签、成员识别、充电设备、温差窗口等具体信号与算法 |
| 本次业务处理 | 一次事件如何接收、何时结束、结果怎样关联 | 充电进一步识别、天气三路动作、加热多个原因合并 |
| 交互 | 询问/告知/无需交互的定义，卡片选择的有效范围 | 儿童锁尚未确定的交互、端侧本地词与云端语音能力接入 |
| 执行结果 | 按已批准动作执行、按真实状态判定目标、避免重复 | 车辆限制、左右锁、模式恢复、加热反向关闭资格 |

**可直接写入 PRD：**

> 本框架统一的是一项任务必须写全的业务信息、可重复使用的交接和运行阶段，不统一四项任务的具体判断与动作。四项任务均在本次需求范围内；云端平台先表达已经确定可接入的云端阶段，端侧按相同任务规格落地并复用可用本地能力。端侧配置下发没有完成前，不宣称四项任务都能在同一个页面发布。

## 3. 缺少“逐 Case、有限平台化、通用编排”之间的取舍

**现稿问题：** 从业务缺口直接跳到五组编辑、能力抽屉、发布接收、整链记录。已经说“不做任意工作流”，但没有解释为什么这些投入是值得做的最小集合。

**应改什么：** 用可复用变化类型选择建设方式，避免“平台化天然更好”。不虚构研发人天、节省百分比或后续任务数量。

**可直接写入 PRD：**

> 四项任务都需要许可、触发、处理、结束和结果定义；其中条件阈值、文案、适用范围及频控属于可预期的配置变化，不应每次修改都重新接整条业务。首次接入的新信号、视觉判断、卡片路线和车辆动作仍需要研发。为此，本期选择“固定阶段＋已接入能力的参数配置”：覆盖已确定链路中的重复部分，保留任务特有逻辑由业务实现。暂不建设任意节点、任意循环的流程引擎，因为当前四项任务不能证明该投入必要。

| 方式 | 本期如何使用 |
|---|---|
| 逐 Case 开发 | 保留用于新能力和任务特有判断，不重复写已经有的通用展示/结果交接 |
| 固定阶段配置 | 本期建议采用：配置已有规则、参数、文案和已支持分支，由已接入业务消费 |
| 任意流程编排 | 后续有真实多场景需求且固定阶段不能表达时再立项，不借本次扩大范围 |

## 4. “产品可以配置”与“产品必须每次手填”混淆，容易把工程负担转给产品

**现稿问题：** 4.5—4.12 让产品填写多个时效、回业务、复核、真实状态、结束策略；仅写“已会签”还不够。若每个场景都要手填同样的回调和防重策略，平台没有降低成本，反而增加出错入口。

**应改什么：** 将字段分成业务可改参数、引用的固定策略和不可在普通表单关闭的保护。优先复用已批准模板，展示来源和实际值，而不是重复录入。

**可直接写入 PRD：**

> 同一配置页不意味着全部项目都需要产品手填。产品可编辑场景阈值、适用范围、文案和已开放的频控参数；任务许可、业务承接入口、结果关联、去重方式、动作复核及回读标准优先随已接入模板或能力带入，只读展示或按授权范围调整。变更保护策略须进入专项会签，不能通过取消勾选跳过用户许可、确认有效性或真实状态校验。

| 类别 | 产品的操作 | 例子 |
|---|---|---|
| 常规可编辑 | 填值、选已开放参数，发布前校验 | 车型版本、建议文案、会签阈值、允许的频次 |
| 引用策略 | 选择已批准方案，查看实际值及来源 | 同次停车去重、点击路线、等待与超时处理 |
| 接入或保护项 | 查看能力状态；缺失则提接入，不能随意关闭 | 业务入口、确认只消费一次、端侧安全复核、真实回读 |

## 5. 需要明示“平台改造”和“后续业务运行实现”是两份交付，不能只验表单

**现稿问题：** 虽然每字段已经有消费方，但 4.6 的“引用主动推荐/DT/VQA组合”及 7.1 的“固定阶段处理”仍可能让团队误以为有字段就有执行器；也可能误以为必须新造一个系统预设服务。

**应改什么：** 补一句明确的研发工作包和依赖关系，而非再加模块名称。

**可直接写入 PRD：**

> 本期交付必须同时包含“配置表达”和“运行消费”。平台负责录入、校验、保存和发布；系统预设任务业务负责读取已发布的后续处理定义，并将其转换成对现有主动推荐、交互卡和端侧执行能力的调用。该业务职责可复用现有模块，不强制新建服务。若目前某阶段仍只能写死业务代码，平台应标明该阶段只支持已接入方案，不开放虚假的自由组合选项；平台与运行接入分别认领和验收。

**评审需落结论：** 第一次充电接入中，哪些是表单开发、哪些是公共业务处理、哪些是 DT/VQA/卡片/车控适配；后续只改参数时哪些代码不应再改。

## 6. 本期交付优先级不足，可能把展示增强与业务必需一起绑成首发阻塞

**现稿问题：** 所有新增字段、能力抽屉、状态诊断、卡预览、全链时间线、版本生效等均在“本期”同一层，没有区分必须具备的语义与必须做成完整 UI 的范围。业务需要可追溯，不等于首发就必须新建完整可视化监控系统。

**应改什么：** 不删四任务，增加“按能力而非按任务缩项”的会签优先级。以下建议须由产品和研发会签，不擅自取消已批准能力。

| 层级 | 内容 | 理由与交付方式 |
|---|---|---|
| 本期闭环必须 | 四任务唯一规格、任务许可、已选链路、确认/静默边界、复核和真实结果、停止与防重 | 决定行为是否正确；不能因排期减少保护 |
| 本期云端配置必须 | 已接入任务/能力选择、五组固定配置、必填与兼容校验、可控发布与回退、版本和结果可查 | 决定平台不是只显示表单；可沿用现有发布/日志入口，避免重复后台 |
| 本期建议分批做的易用性 | 业务摘要、卡片/TTS预览、缺项定位、单次详情可读化 | 直接服务产品配置和评审；可按投入优先级实现，不影响结果语义 |
| 后续评估项 | 任意流程编排、独立能力治理后台、跨端统一下发、自动端云切换、复杂可视回放/分析 | 原稿不能证明当前必须，另经真实需求和成本评估 |

特别说明：原子能力的元数据和状态必须可查，但“全新能力后台”不是必选实现；结果关联必须存在，但可以先接现有日志/详情，不重复造监控平台。

## 7. 原子能力表仍是类别目录，未给“最小可用接入单元”和“新增能力的完成标准”

**现稿问题：** “主动推荐/DT/VQA组合”“用户交互”“车辆动作与回读”颗粒度跨度大。研发会问一个能力到底是一个接口、一个完整场景还是一组组件，能否复用、缺哪里怎样定位。

**应改什么：** 用本次充电的能力边界作规格，不虚构正式接口名或固定服务部署；选项只暴露业务可消费的已完成接入，不让产品自由拼未兼容底层接口。

**可直接写入 PRD：**

> 本期“可配置能力”指任务业务能够按约定输入调用、取得可解释结果，并且已标明车型/版本与运行限制的接入单元。它不要求等于单个底层接口：例如设备检查可以封装当前已接通的主动推荐/DT/VQA路径；产品选择检查目标与允许参数，不自行拼底层调用顺序。能力完成接入至少要证明：输入可提供、结果枚举可解释、错误与超时有输出、本次事件可关联、适用范围有依据、调用方已消费并完成正反例测试。只建名称或 SourceID 不算完成。

**应留下的最小清单：** 本期支持的任务状态读取、档位事件/SOC/口盖状态、充电设备检查、确认卡及已选回答路线、开盖及真实回读。四任务其他专属能力继续保留在各任务清单，不假称已能云端发布。

## 8. 验收主要验证‘能跑’，没有验证‘平台化是否真的减少重复接入’

**现稿问题：** 7.3 大量正反例是必要的，但没有一条证明更改需求能通过配置完成；7.4 全是运行质量指标，不能证明平台建设价值。单条充电案例跑通可能仍是一条后台展示配置、实际写死的定制链路。

**应改什么：** 加 3 条复用验收和投入记录，不造新业务 Case、不改四任务范围、不编造 ROI。

| 复用验收 | 操作 | 成功标准 |
|---|---|---|
| 参数变化无需重接 | 在隔离模拟中，对同一已接入充电任务修改获准开放的阈值/适用范围，并用对应边界样本验证；实车参数先会签 | 通过新配置生效，Trigger判断随之变化，后续卡片/DT/车控接入代码不因该参数变更重写 |
| 内容变化不重写卡片 | 修改确认文案/TTS但保留相同按钮含义和动作范围 | 新卡呈现变更，展示/选择/回读链路复用；没有另造一个场景专用卡或回调 |
| 未接入能力不会伪配置 | 在相同模板选择不支持车型或未接入信号/动作 | 明确阻止该路径发布并定位接入缺口；不能靠填名称绕过；已支持路径不受影响 |

**可直接写入 PRD：**

> 平台验收除链路正确外，还须证明已开放的常规变更通过配置完成，不重复改造无关模块。记录首次接入涉及哪些模块、一次配置变更需要哪些人工操作、仍需改代码的原因以及配置错误返工；以实际记录形成基线，再评估后续节省，不预设百分比。是否新增能力、变更业务保护或调整车控限制，仍按研发接入及会签处理，不能为了“零代码”目标降低安全边界。

## 给主稿的最小修改顺序

先在第 1 章补“已有事实—真正缺口—为什么有限平台化”，第 2 章补共同/专属边界及交付优先级；第 4 章把可编辑参数和引用保护分开；第 7 章加复用验收。不建议把本审核全文塞进 PRD，更不建议继续堆字段。
