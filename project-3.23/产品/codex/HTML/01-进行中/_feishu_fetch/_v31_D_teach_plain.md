# D Planner / Director

summary: 把用户目标与当前事实联系起来，生成这一轮一致的回复与动作列表；工具结果回来后再决定下一步。

## INTRO

用户说“带我去昨天那家游泳馆附近的餐厅”。语音链路已经把补充接完整，Context 也提供了当前身份和相关背景。Director 此时要判断的第一件事，是当前是否已经知道那家游泳馆的位置。知道了才能搜索附近餐厅，不知道就先查记忆；找到餐厅后，还要确认目标和路线。

Planner、Director、DT、对话推理引擎是同一职能的不同称呼。按 10 月 22 日产品宣讲口径，这一代用支持 ReAct 的核心推理模块替代原先的意图分类、简单复杂仲裁以及部分独立 NLG：模型先推理下一步该做什么，再调用工具，拿到反馈后继续推理。

真正查记忆、搜索地点、发起导航由下游工具办理，工具结果再返回，让 Director 决定下一轮。多步任务由这种连续判断形成，不要求模型第一次就猜出后面所有结果。

## d-intake 先确认最终目标，再查清会改变动作的缺失信息

Director 收到的不只是用户一句话，还包括来源、时间、位置、历史、当前状态和可用能力。若输入是用户请求，它要理解用户现在想达成什么；若是 Advisor 建议，判断此刻是否适合执行；若是工具反馈，看原计划办到哪一步；若是 event（例如误打断后请求恢复），根据事件原因和原轮进度判断，不当成用户重说一遍。

D2 先认目标和对象：明确指令准确保留；模糊感受才结合车况补足；建议先判断采不采纳；feedback 只看进展。主体认错，后面参数和工具都会跟着错。

D3 同时核对事实、能力与安全。事实缺一块走 D4 只发查询；不能直接做走 D5 澄清或说明限制。语控不支持不等于车上没有该功能——查车书给手动方法，比假装能语音执行或硬说“没这个功能”更准确。

## d-plan 本轮只发现在有条件执行的动作，依赖结果的步骤留到下一轮

Director 的 action_list 是本次准备交给下游的动作列表。每项要明确调用哪个工具、需要它做什么以及已经确定的参数。模型说“我来帮你找找”并不会自动产生搜索，只有相应工具动作真正发出，搜索才开始。

D6 区分即时执行与任务系统跟进：注册成功不等于未来动作已完成。D7 把人话改成明确对象和参数；D8 用现场事实排除不合适动作。

D9：单轮 action_list 默认并发；有数据依赖必须拆轮；数组顺序不等于串行保证。地址没查到就不能同一轮先发导航。

## d-talk 说话内容跟着办理进度变化，同批结果统一向用户交代

输出同时包含是否讲话、讲话内容、表情与动作列表。talk_or_not、talk_content、emoji_id、action_list 分别交给输出与执行链路。用户只要求一个明确车控时，冗长前置解释会增加等待；复杂搜索时，简短进度说明能让用户知道任务已被接住。

没有执行证据前不说已经完成；简单查询和车控可以不播首轮空话；同轮多工具等齐 feedback 再统一说。下游工具不自主播报。

说做一致看实质：当前只能开到 3 档，话术就按 3 档说。需要情绪或方言时用方括号标签，第一个标点前尽量短，方便快速合成。

## d-feedback 用完整目标和真实结果判断规划质量，再定位错在哪一步

评价“去昨天游泳馆附近的餐厅”，不能只核对模型是否调用了标准答案中的一个工具名。正确实现可能在 Context 已有地址时直接查餐厅，也可能先调用记忆；关键是是否使用了正确地点、保留附近关系、得到可选餐厅，并最终把用户选定的目标交给导航。

反馈经输入管理回到同一大脑，不另建第二条直回路径。结果足够就确认；部分成功只认成功部分；未完成则补查或下一步，仍走 D11 统一出口。

画板上 10 月补充的打断后信息价值、展车引导等口径，指回主路对应节点；未在主图落地、证据不足的扩展节点，不写成现行全车型能力。

## CLOSING

到这里，Director 已经交出说做一致的一轮决策，并准备读真实反馈。下一章（工具执行）看动作怎样真正落到车控、导航和查询；不要在规划章把 action_list 发出写成“车里已经办成”。
