# K 身份与记忆

INTRO 0
主驾说「带我去昨天那家游泳馆附近的餐厅」。系统先要弄清昨天去了哪一家，才有位置可以查附近餐厅。如果主驾紧接着说「就去第二家」，需要的是刚才的候选列表；如果问的是昨天的经历，可能要查情景记忆；如果补一句「我不吃香菜」，则要保留这位乘客明确表达的偏好。三种信息都和过去有关，用途却不同，不能只用一个「记忆」概括。

INTRO 1
本章先讲说话人、账号和授权怎样决定可用数据，再讲历史输入、摘要和记忆服务分别提供什么。最近原话帮助接上当前对话；对话摘要帮助保住已经退出原话窗口的内容；短期和长期记忆用于保存、归纳和查询经历及事实。查到一条记忆以后，仍由 Director 结合当前需求决定下一步，记忆服务不会因为查到泳馆就自行开始导航。

INTRO 2
11 月 4 日讨论把人人对话和事件补进历史输入，并扩大摘要处理的内容。这次改变的是输入范围及处理规则，不能凭名字把它讲成又增加一个数据库。PRD 在开关部分列出对话摘要、瞬时记忆、短期记忆、长期语义记忆和长期情景记忆，并把瞬时记忆标为当时未使用。下面按用途逐项解释，同时把旧 PRD、当天讨论与未验证的上线状态分开。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh) [11月4日文字记录](https://aka.doubaocdn.com/s/68EV2Q9r4X)

## k-lesson-person 「昨天那家」先属于一个人，再属于一次可使用的经历

PARA 0
**关系必须从车企云返回的可信账号关系解析，客户端上报的「我是车主」不能直接当权限依据。**K01（先确定车辆与账号范围）把车辆、车企账号、豆包账号和乘客之间的可信关系解析出来。车辆由车辆唯一标识确定；车企侧账号是车主在车企体系内的账号，决定本车有哪些成员和访客；豆包账号是用户登录的豆包账号。

PARA 1
乘客身份用人脸标识、声纹标识和车内自然人标识描述。否则副驾一句「我是车主」就能读到车主私人记忆。可信入口先通过车企云校验车辆标识与账号标识的绑定关系并获取角色，客户端上报的账号和角色不可信；校验失败或依赖不可用时，高权限能力按失败关闭处理，而不是默认放行。

PARA 2
记忆在索引上按三层身份定位。最上层是火山统一账号，决定一次任务跟谁走、记忆整体落在哪个账号边界内；中间层是车企账号，决定本车哪些成员和访客的记忆互相可见；最下层是车内自然人标识，指车内具体哪一个人，一条记忆最终挂在这个人头上。

PARA 3
三层不是同一个名字的重复叫法：换车不换豆包账号，统一账号关系保持；同一台车切换不同车企账号，可见的成员范围随之变化。三层身份之上还有一条硬边界：系统只在当前账号授权范围内检索记忆，不能凭车辆标识加上人脸特征跨账号命中另一个账号下的记忆。

PARA 4
同一张脸在不同账号体系里可以对应不同称呼和不同经历，查不到就反问用户，不猜、不借读其他账号的数据。要区分两种「没找到」：一种是本账号范围内确实没有这段记忆，另一种是记忆属于其他账号、当前没有权限读取，对用户的回复口径要分开。

PARA 5
一次请求进来，K02（把乘客身份接到个人内容）以人脸作为主识别因子，声纹作为补充，把识别结果关联到当前乘客标识和座位位置。真实生物特征留在端侧，不上传到云端，云端只使用识别后的身份标识。未注册脸进入匿名上下文，不套用车主偏好；同名乘客靠座位、声纹和上下文消歧；空座位不生成不存在的乘客身份。

PARA 6
乘客之间互相介绍时，系统要先判断意图再抽槽位。乘客说「坐我右边的是 Alex」，需求是介绍关系，不是闲聊。先判断这一轮是不是介绍认识的意图，再抽出姓名和座位两个槽位，两个槽都非空才回应「你好 Alex」，并触发端上人脸注册流程；缺姓名或缺座位，整条介绍丢弃，不猜一个名字挂到空座位上。车门全关时重新上报座位人物表，中途换人但人数没变是已知覆盖缺口。

## k-lesson-produce 历史输入、摘要、瞬时、短期和长期记忆分别解决什么问题

PARA 0
先从同一段用车经历看。乘客刚选过一家餐厅，下一句「就这家」需要能对回原来的选项；途中聊了很久，后来追问前面说过什么，就需要保住已经离开最近窗口的内容；第二天再问「昨天吃过的那家」，则需要能够跨对话查询的经历。历史输入、对话摘要和记忆服务分别承担这些不同需求，不能把它们画成必须逐级流过的五个存储站。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 1
历史输入原来叫历史对话，指送给 Director 的近期原始交互记录。PRD 的旧口径是保留 5 轮人机对话，记录用户问什么和助手怎样回复。比如刚搜索出两家泳馆，用户说「第二家」，模型要拿到真实候选与选择关系，不能只看到「用户在找泳馆」这句概括。这里的 5 轮是该文档的窗口规则，不是长期记忆的保存期限。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 2
人人对话指乘客之间的交谈。例如副驾对主驾说「今天想吃清淡一点」，当时未必是在向豆包下指令；后来主驾叫豆包找餐厅，这段话可能帮助理解口味。成为背景信息不等于成为执行授权，也不等于可以把副驾的偏好记到主驾名下。11 月 4 日讨论的方案保留最近 5 轮人机对话，再补入当前往前 5 次混合输入中的非人机部分，包括人人对话和事件。它既不是额外固定加 5 轮人人对话，也不是所有类型合计只留 5 条。[文字记录00:01:50至00:07:32](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 3
事件是另一种输入来源。用户点击一个视频、执行一次车控、某项任务返回结果，都可能形成一条带发生时间和来源的记录。当天讨论不再单独调用 DT 提示中的旧事件流变量，而把相关事件纳入历史输入。取消重复的提示入口，不等于取消事件采集和日志服务；哪些事件值得进入模型的近期背景，会上仍要求逐项评审。[文字记录00:04至00:16](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 4
对话摘要把较早的对话压成短文本。旧 PRD 规定从第 3 轮开始，每新增 1 轮对话压缩一次，本次用车周期内最多压缩 22 轮、最长 500 token，摘要拼在记忆变量的起始位置。token 是模型处理文本的计量单位，500 token 不能直接当作 500 个汉字。提前从第 3 轮处理，是给压缩留出时间，避免原话退出 Director 的 5 轮窗口时，摘要还没准备好。[记忆系统 PRD·增加对话摘要压缩](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 5
摘要保留的是与后续理解相关的内容，不能代替所有原始记录。比如原始列表明确第二家是某个地点，摘要只写「讨论了两个地点」，后面仍无法凭「第二家」正确选择。测试摘要既要看信息有没有保住，也要看人物、时间、否定和已完成动作有没有压错；不能因为文本更短就认为处理成功。PRD 增加摘要的背景明确写的是瞬时记忆当时不可用造成缺口，并不是要求摘要先写进瞬时记忆再转往下一层。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 6
瞬时记忆是 PRD 使用的名称，开关一节明确标注「当前没用」。用户提到的「顺时」先与资料中的这个近音名称对照，但不据读音推导业务定义。当前可读 PRD 正文没有把「20 分钟或 20 轮事件日志」定义为瞬时记忆，不能继续把这个阈值写成该 PRD 的正式结论。它与历史输入、摘要的准确工程关系，需要结合对应版本的实现定义，不能把当时未使用的能力当成本轮已经在取用的来源。[记忆系统 PRD·记忆开关](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 7
短期记忆用来保留近期经历，长期情景记忆用来保存可回忆的经历片段；两者都与事件发生的场景有关。例如「昨天与家人去了某家泳馆」要保留人物、时间、地点和活动，才能在第二天查「昨天那家」。PRD 指出旧方案按固定轮数压缩、过于流水账和没有按用车人及场景隔离，都是待改问题。因此不能把短期记忆简单等同于模型本次收到的 context window，也不能把存有原始日志等同于已经生成了可召回的经历。[记忆系统 PRD·情景记忆生成优化](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 8
长期语义记忆保存能用于以后判断的事实、关系或明确偏好，例如某位乘客说自己的公司在哪里、不吃什么。它和「昨天去哪了」这样的情景经历不同：前者是这位用户的事实，后者保留发生在某次场景中的事件。PRD 要求保留信息是谁说的，例如别人介绍某位乘客的联系方式，不能抹掉来源后变成这位乘客亲口确认。由行为归纳偏好是另一路能力，PRD 所列情景记忆画像方案当时已实现但实际未使用，不能写成夜间必然自动生成习惯。[记忆系统 PRD·语义记忆生成优化及情景画像](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 9
11 月 4 日还讨论把摘要输入从人机问答扩大到人人对话和事件。会上对「一轮」的定义进行对齐，并要求核实旧摘要 22 轮上限与记忆侧 20 轮或 20 分钟的总结节奏是否会出现覆盖空档。这里仍有待研发核对项，不能把 20 轮、20 条和 20 分钟互相替换。当时口头反馈的一次摘要耗时约 1.7 至 1.8 秒，是处理耗时，不是 1.7B 模型规模，也不是正式性能承诺。[文字记录00:09至00:15](https://aka.doubaocdn.com/s/68EV2Q9r4X)

## k-lesson-use 先找到泳馆，再围绕它找餐厅，两个依赖不能倒过来

PARA 0
**预注入是默认主路，授权核对必须发生在检索之前，不能先捞回来再发现无权使用。**一条请求进入 Director 之前，上下文模块已经在准备背景材料，K07（在本轮推理前准备背景）是默认主路。请求到达后并行启动两路：画像一路固定取出当前乘客的基础画像；另一路根据请求推理地点、昨天、出行等场景标签，捞出候选记忆和匹配分数。

PARA 1
预注入覆盖约 80% 的常规请求，这是上下文方案给出的口径；剩下不足的部分由显式查询兜底。授权核对必须发生在检索之前，先确认这一轮有权看谁的数据，再执行检索，不能先捞回来再发现无权使用，更不能把已经过权限核对的记忆和未核对的候选混在一起返回。

PARA 2
候选记忆捞回来之后还要过滤排序，K08（先匹配标签，再给候选排序）：长期语义记忆主要看相似度和时效性，长期情景记忆在相似度之外再考虑重要性；先按标签剪枝，再按已经实现的得分规则重排序。匹配分数只代表排序相关度，不等于这条记忆的事实为真；情感显著性、情感共鸣这类打分维度属于后续方案，当前版本不能引用。

PARA 3
预注入背景不够时，Director 才发起主动检索，K09（信息不足时显式查询记忆）。这一路要把查谁、查什么、需要什么时间范围说清楚，支持关键词和时间范围过滤；结果分三种情况返回：没查到、当前无权限、检索异常，三者话术分开，不能混在一句「我不记得了」里。

PARA 4
显式查询只是获取事实依据，不自动获得启动导航或写开车机设置的授权；「我记得你家在朝阳」不等于这一轮已经可以直接导航回家。取回的记忆有两个出口，K10（把候选送回正确判断入口）：预取回的结果进入上下文背景汇集，供当前轮使用；显式查询结果经执行链路回到事件、记忆等执行层，再交给 Director 组织回答。

PARA 5
和记忆并行的另一类取回是车辆状态：用户问「空调现在几度」，车上信号很多，先用小模型做初筛，再走检索定位到相关信号，而不是把全量状态都塞进上下文。这次切换的硬要求是效果不退化；当前口径是赛力斯车型已经上线，上汽车型在测试，属于 2.6 目标范围。

## k-lesson-control 关闭、清空对话和删除记忆，各自改的是哪一份内容

PARA 0
**每一次记忆操作都要单独核权限，能说出某位乘客的名字，不代表有权限读这位乘客的私人经历。**身份识别完成之后，记录、召回、删除每一类操作都要单独核权限，这是 K03（按入口检查记忆使用条件）。系统先核对当前说话人身份、账号授权和本次操作类型，再决定能不能写入、能不能读取、能不能删除。

PARA 1
记忆开关关闭时，新的记录和生成停止，旧内容保留在库里但不再被召回。2026年11月4日会议对一个具体场景拍了口径：用户说「把家设成麦当劳」这种导航地址类记忆，如果记忆开关是关闭的，系统要先提示用户打开开关，不能在开关关了的情况下偷偷记家地址。这跟之前讨论的「家地址是强规必须记」不一样，最终结论是统一限制，要设家或公司就先开记忆开关。

PARA 2
记忆开关的语义是冻结，不是删除，这是 K11（关闭后冻结已有记忆）。用户关闭开关后，系统停止新的记录和新的记忆生成，已经存在的旧内容保留但不再被召回；重新授权或开启之后恢复合法使用。开关关闭期间，最近几轮的原话仍可能基于当前上下文回答用户，这和长期记忆被冻结是两件事。

PARA 3
删除前先分清删什么，K13（按入口选择删除对象和范围）。系统先判断删除对象是谁的记忆、是语义记忆还是情景记忆、按人删、按日期删还是全部删除；批量删除由 Director 先和用户二次确认，确认结果作为下一轮正常输入回来，避免一句「把我记忆都删了」误删别人的内容。

PARA 4
清理时要分对象。PRD提供新chat_id清空Director历史对话与摘要，语义记忆和情景记忆分别走删除接口；删除语义记忆以后，再按剩余资料更新用户画像。接口返回多少条、清掉哪个范围，都要按实际操作说明，不能把删除一条语义记忆说成同时删完所有原始日志与最近历史。[记忆系统 PRD·记忆管理需求](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 5
当前页面主要露出长期语义记忆，情景类暂不露出；支持标签筛选、单条删除、按标签删除和一键清空，批量操作二次确认。按人筛选的页面设计已划掉，接口仍列有按人操作。语音批量删除由DT确认范围再执行，页面由车企开发，各项目实际开放范围仍要按交付版本看。[记忆系统 PRD·界面及语音删除](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

## k-lesson-cross-device 共享乘客、多人在场与跨账号，是不同的数据范围

PARA 0
多人同车先确定两个范围：当前车与登录账号能访问哪份记忆，以及这一次在场的人允许共同使用哪些内容。PRD先按车和豆包账号隔离，再按记忆标签与用车场景收窄敏感内容。不能因为同一家庭账号就把所有成员经历都拿来回答，也不能把一位乘客过去坐副驾当成现在有权读取他的私有内容。[记忆系统 PRD·隐私策略](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 1
白名单和非白名单用不同召回范围。白名单从包含询问者的经历中取：A询问时，可包括A单独、AB、AD等有A的场景。非白名单要求覆盖当前在场人员：A、B、C在车上时，候选来自ABC、ABCD等至少包含这三人的场景。这样做是在已经允许的车与账号空间内再过滤，不能用一个人物名字跨账号搜索其他人的记忆。[记忆系统 PRD·询问人最大集与在场人最小集](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 2
记忆页面的展示规则与模型召回另行定义。PRD要求页面暂时只显示长期语义记忆，展示当前在场人的交集记忆；按人筛选的界面方案已划掉，但管理接口仍有按人查询或删除。不能由“接口支持按人”推定页面有这个按钮，也不能由“页面没有显示”推定后端没有相应记录。[记忆系统 PRD·常规记忆露出及管理接口](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 3
摘要没有完整绑定每一次在场组合，因此有独立清理规则。PRD以新注册乘客上车、未注册乘客人数增加判断新人，清除摘要中的敏感信息；单纯功能性偏好与涉及个人身份、关系、重要地点等内容要分开。未注册乘客换人但人数不增加，是文档明示的覆盖缺口，不应写成FaceID已经能完整识别所有换人。[记忆系统 PRD·对话摘要隐私策略](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 4
共享乘客也有两种含义。FaceID维度的共享，指这台车换登录账号后仍认识该乘客；记忆生成维度的共享，指主账号登录且共享乘客在车内时，相关记忆同时在相应的车与豆包账号空间生成。它是定义好的共同生成机制，不是自动开放两个账号互相读取全部历史。共享身份、共享生成与本轮召回权限必须分别检查。[记忆系统 PRD·共享乘客与记忆生成](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 5
手机与车辆之间再增加一个跨端来源。当前已核的记忆主线规则不能证明手机全部聊天、通讯录或私人记忆都可同步到车内。讲“手机给车一条信息”时，应只说明具体接口已授权传递的对象和用途；缺少跨端协议的字段、范围或落地证据，就不能补成全量同步。用户主动交给车端一个地点，也不代表把手机全部个人记忆授权给在场乘客。

## k-lesson-poi-sync 先确认要记的地点，再让导航使用同一份地址

PARA 0
用户说「记下我家在麦当劳」，实际要求是保存一个以后可用的地点。不能只记下这几个字，就宣称下一次能够准确回家：同一个城市可能有多家麦当劳，另一个城市也可能同名。指定的《豆包记忆和车机记忆打通方案》要求完整 POI 名称和城市必选，并列出 POI ID、经纬度、地址等结构化字段。POI 指地图里的地点对象，名称是显示给人的名称，ID 是地点标识，二者不能互相混叫。[打通方案·导航相关记忆同步](https://bytedance.larkoffice.com/wiki/Aj7AwwY5hifYvRkWxsxcR9cGnKb?from=from_copylink)

PARA 1
旧方法通过 FC 输出常用地址设置函数，把家、公司或常用地址存在导航应用内。打通方案转为通过豆包记忆保存这些内容，地图展示和快捷导航再使用这份数据。它解决的是个人记忆与地图各存一份、彼此不同步的问题；不能因此说地图不再有本地数据，后续离线方案恰恰需要把可使用的地址结构化同步到端上。[打通方案](https://bytedance.larkoffice.com/wiki/Aj7AwwY5hifYvRkWxsxcR9cGnKb?from=from_copylink)

PARA 2
写入前谁负责补地点，文档保留了三条方案。第一条由 DT 先判断核心信息是否完整，缺少则先调用 POI 搜索，再存记忆；第二条让记忆工具内部去调用 POI 搜索；第三条由记忆工具返回缺项，DT 根据返回消息再搜索和写入。三条区别在谁发现缺项、谁调用搜索，目的都是先确定实际地点。11 月 4 日会中01:03:30收口采用了 DT 先判断、缺项先搜索确认再存的方向；文档仍并列展示历史方案，不能把三条写成同时执行，也不能据讨论方向宣称全部已上线。[打通方案](https://bytedance.larkoffice.com/wiki/Aj7AwwY5hifYvRkWxsxcR9cGnKb?from=from_copylink) [文字记录01:03:30](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 3
例如用户说公司在某个街道门牌，POI 搜索返回两个地点，DT 应让用户确认要保存哪一个，拿到确认后的城市和完整名称再调用记忆工具。搜索工具完成表示找到候选；用户选点表示确认一个对象；记忆写入成功才表示存下了这条地址。搜索结果、用户确认和写入回执要分别留在这一轮中，不能拿「已找到」替代「已记住」。[打通方案](https://bytedance.larkoffice.com/wiki/Aj7AwwY5hifYvRkWxsxcR9cGnKb?from=from_copylink)

PARA 4
选点界面还存在实际体验问题。原导航卡可能在用户手点候选后继续算路，用户本来只是想保存地址，却进入导航流程。11 月 4 日讨论中，这正是语音选点和手点是否同等支持的争议；不能简单写成「语音说第三个或手点都可以，选完就存」。验收必须分别看语音确认、手动点击以及用户转去闲聊三条路径，确认选点结果能返回本次保存流程，不会擅自把保存意图改成出发。[文字记录01:04至01:13](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 5

## k-lesson-profile 把这个人的常用偏好整理出来，不把家人的喜好装到他身上

PARA 0
用户画像帮助Director了解这个人的相对稳定信息。PRD写已经实现的语义记忆画像是固定注入，未做检索逻辑；更完整的自然语言画像和关系建模列为长期方案。画像来自哪类资料，决定能说到什么程度，不能把设想中的完整人设当成每轮已经注入的事实。[记忆系统 PRD·增加用户画像](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 1
从长期情景记忆里归纳用户规律，是另一路推断。PRD写对应情景画像算法已有实现，但当时实际未使用，更完整方案仍未实现。一次开座椅通风只能证明这次操作，反复操作是否足以说明夏天偏好、是否要限定同乘场景，还要经过归纳与验证。不能把某个夜间或周五更新节奏写成没有对应版本依据的上线规则。[记忆系统 PRD·从情景记忆总结语义记忆](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 2
语义记忆挂在具体主体名下。画像归纳要尊重这套在场边界，不能因为同属一个家庭账号，就把副驾的口味偏好装进主驾的画像；也不能因为两个人经常同车，就把两人共同的喜好自动写成每个人的独立偏好。画像的每条偏好都要能追溯到是谁在什么场景下说的，不能只有一个模糊的「这个家庭喜欢」。

PARA 3
负反馈要被识别并调整，例如乘客说「别再推荐这类歌了」，这条反馈要反映到后续推荐和画像里，不能左耳进右耳出。但该项标注为低优先排期、待核状态，负反馈具体落入哪一层画像、多久生效尚无终版方案，评审时不能讲成全车型已经自动调整。

PARA 4
用户要能看见被记了什么、能删掉，逐条查看和删除能力按车型逐步开放，具体开放清单待核。记忆查询和删除接口由记忆服务建设，管理页面由各车企客户开发，不能在所有项目上承诺相同界面；画像在每轮请求中固定注入，但注入的是当前乘客的基础画像，不是全车共享的偏好包。

PARA 5
用户明确事实、画像概括与情景经历在使用时各有角色。画像可以提供常用背景，具体经历仍按本轮查询与权限取回。页面露出的长期语义记忆、模型固定注入的画像和按场景召回的情景记忆不是同一展示对象。删除语义记忆以后还要更新画像，避免已删除偏好从画像再次进入回答。[记忆系统 PRD·画像及删除影响](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

## k-lesson-quality 泳馆找错时，沿生成、查询和采用分别定位

PARA 0
**用户反馈「你不记得了」不能笼统归给记忆模型，要拆成生产、召回、使用三段分别定位。**K15（沿生成、检索和采用定位遗忘）把问题拆成三段。第一段看生产：事件和记住请求有没有进入队列，生成任务是待处理还是成功，记忆是否真的落库。第二段看召回：检索标签、权限过滤、排序打分有没有把这条记忆筛掉。

PARA 1
第三段看使用：记忆已经回到 Director，回答时有没有被采纳。三段要留下同一个案例的日志证据，分别对应记忆服务、上下文检索和 Director 推理，避免互相推诿。记忆是异步生成的，用户听到「好的记住了」只是受理回执，不代表长期记忆已经生成完成；测试和评审要分别核对受理、生成成功、召回命中、回答采用四个状态。

PARA 2
按汽车记忆测试方案，记忆批量生成覆盖率目标为 90%，这是方案目标不是当前实测成绩。功能准出要求核心用例通过率 100%、重要用例不低于 95%、一般用例不低于 90%。压缩摘要单次耗时1.7到1.8秒是11月4日会上口头反馈的实测值，不是正式指标口径，评审引用时要说明这是会上的实测反馈。

PARA 3
记忆打标、画像生成、行为归纳和召回的各专项指标在测试方案中分阶段验收，旧报告里的历史成绩不能冒充当前准出口径。跨车、跨账号、新乘客上车的隐私隔离要单独构造样本验证，不能只测主驾单人场景；人脸注册、座位识别和记忆中心露出能力按车型配置开放。

PARA 4
不支持人脸的车型按匿名身份降级响应，具体选配表待项目确认。回到游泳馆例子：主驾说完这句话，系统先核出说话人是车主账号下已注册的主驾乘客，确认记忆开关开启，再由最近对话和预注入取回昨天去游泳馆的情景记录和相关餐厅偏好；如果预注入没带出来，Director 再发起带对象和时间范围的显式检索。

PARA 5
身份与记忆前台链路到这里闭环。评审时盯三条硬边界：授权核对有没有发生在检索之前、删除有没有联动到画像和压缩摘要、多人在场召回有没有按当时在场人组合隔离。这三条任何一条被突破，用户感知到的就是「系统偷看了不该看的」或「该记住的没记住」。

## GUIDE base 跟着一次「昨天那家」从认人到取回：身份、权限、生产、召回

PARA 0
这张图按一次记忆调用的生命周期排，不是按模块排。左侧是身份解析和乘客识别：可信账号关系、当前乘客识别、座位人物表；中间按操作类型分成生产和取回两路，生产走最近对话到压缩摘要到短期聚合到长期沉淀，取回走预注入到过滤排序到不够再显式查；右侧是删除、开关和多人隐私的边界。

最上面的入口是 K01（先确定车辆与账号范围）。车辆唯一标识、车企账号、统一火山账号、车内自然人标识四层对象从车企云可信关系解析，客户端上报的「我是车主」不可信。三层索引：统一账号定任务归属、车企账号定成员可见范围、自然人标识定记忆挂在谁头上。

PARA 2
身份解析后进 K02（把乘客身份接到个人内容）。人脸主识别、声纹补充，生物特征留端侧，云端只用身份标识。未注册脸进匿名上下文，同名乘客靠座位和声纹消歧，空座位不生成假身份。介绍认识要抽姓名和座位两个槽位，都非空才触发人脸注册。

PARA 3
生产与取回要分开看：原始输入可以供当前对话使用；较早内容由摘要保持连续性；记忆服务保存并组织近期或跨对话的经历和事实。PRD 列出的各记忆类型并非五个串行数据库，瞬时记忆在该稿标为未使用。11 月 4 日新增人人对话和事件的范围、计数及覆盖衔接，应按本章对应说明核对，不从图的箭头反推已上线顺序。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 4
取回路从 K07（在本轮推理前准备背景）开始。预注入并行取画像和相关记忆，授权核对在检索之前。K08（先匹配标签，再给候选排序）先按标签剪枝再按得分排序。预注入不够走 K09（信息不足时显式查询记忆），结果分没查到、无权限、异常三种话术。

边界路先过 K03（按入口检查记忆使用条件）核本轮权限。K11（关闭后冻结已有记忆）是冻结不是删除，设家或公司在开关关闭时要求先开开关。删除走 K13（按入口选择删除对象和范围），批量删除二次确认；K14（清理源内容并更新关联产物）联动更新画像、摘要和最近对话。

PARA 7

CLOSING 0

CLOSING 1
评审时盯三条：设家或公司时记忆开关是否要求开启、座椅位置是否只在语义明确时才记映射、最近对话层是否已经包含人人对话和事件而不是只取人机（这条是本周提测中的改动，注意区分线上现状和提测口径）。

# B 信号与当前状态

INTRO 0
用户说「车里有点闷」，这句话本身没法直接变成动作。空调现在开着没有、车窗开度是多少、外面是不是在下雨、后排有没有人，都会决定下一步是开窗、调风量还是先问一句。系统如果每句话都临时去翻一遍传感器，既来不及也拿不全；真实做法是把这些会变化的事实持续供给上来，供后面的模块随时取用。这一章讲的就是这些事实从哪来、怎么对齐、还能不能信。

INTRO 1
这一站是整条链路的事实底座。它不替决策模块决定目的地，不判断「快到了」，也不主动给用户提建议；它只负责把可信的当前事实交出去。视觉模型怎么从画面里看出「后排有人抱孩子」归第 17 章，触发器拿到事实后怎么判条件归第 13、14 章，顾问拿事实怎么提建议归第 15 章。

INTRO 2
同一份事实要分三路走：一路进 Context，当轮对话的背景；一路进触发器，叫醒登记过的规则；一路进静态顾问，做建议素材。三路之间没有强制先后，一路失败不影响另外两路用同一份有效事实。事实用完之后，车控执行产生的新状态再回流进来，重新对齐成下一轮的可用事实。

## b-facts 先确认这个值描述哪台设备、哪个位置、哪个时刻

PARA 0
**车控值、乘员信息、视觉观察是三类不同性质的事实，精度不能跨层补全。**B01（读取车辆与设备正在变化的状态）覆盖车门、空调、座椅这些车控状态，加上行驶、充电、导航等车况，属于端侧产生的结构化实时信息。每次上报要带上字段名、当前值、采样时间戳和来源通道，各车型支持范围和计量单位要保持一致。已确认接入的车控和车况部分已落地；字段覆盖范围与车型适配仍需以联调清单核实，不能拿另一个车型的字段表把本车空缺填满。

PARA 1
车辆设备状态再按业务分三组。第一组是车身车控值：车门车窗开闭、空调温度与风量、座椅位置、灯光、挡位、驻车保持、后视镜。第二组是行驶车况：车速、车道、导航状态、剩余距离、路线、偏航状态。第三组是补能与车辆健康：电量、油量、充电口状态、胎压和故障告警。同一辆车不同字段刷新频率不同，车速和挡位必须跟随当前驾驶动作快速更新，用户画像和长期偏好不放在端状态高频通道。

PARA 2
字段缺失先标未接入或本次未返回，不能补成设备已开或已关。任务控制的同步应答只证明指令送达或受理，后续状态与实际数据还需要对应回调。启动、识别完成、失败、停止的含义不同，各任务超时及重试由具体协议约定，不能一律假定一至两秒必回，也不能在已经有副作用时默认再试一次。

PARA 3
人人对话是乘客之间的交流，和向豆包提出需求的人机对话分开。11月4日讨论激活态实时上报；降级情况下每十句打包，不足十句但沉默三十秒也可上报；每次有效query检查未上传内容一起补上。真正断网时先在本地保留，网络恢复再补报，云端按时间戳还原发生顺序，不能把补报到达顺序当成真实对话顺序。当天是开发和提测安排，不能直接宣称11月5日所有车已经生效。[文字记录00:16至00:18](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 4
乘员和手机应用这一路走 B02（明确乘员、手机和应用信息属于谁）。它提供座位、已识别身份以及获得授权的手机或应用背景，按授权范围读取。这一类事实精度分三层：有人坐在副驾、认出一张脸、确认是某个登录账号，不是同一事实。乘客说「我冷」，系统如果不知道「我」是哪一席，就不能把主驾身份默认套过去；账号和权限还决定谁的历史地点、音乐或记忆可以被使用。

PARA 5
三层精度不能跨层补全。第一层座位占用只说明某个位置有人，不知道是谁；第二层人脸识别给出候选身份，可能仍需人脸或账号登录确认；第三层账号确认后，才允许使用该账号的长期记忆、历史地点、音乐偏好和订阅内容。多人同车时，发言音区先把说话位置绑定到座位，身份识别再把座位和人绑定；两步都失败时，助手只能使用不依赖身份的通用车况。授权被撤回之后，原来可以读取的手机应用背景要从可用事实中剔除，不能因为历史上曾经授权过就继续沿用。

PARA 6
B03（把视觉描述作为有条件的观察证据）接视觉任务输出。V1.3里舱内描述包含乘客位置、造型或动态，舱外包含天气、路面和所见描述。它们是模型从图像或视频推理的观察，不是车辆硬件直接上报的挡位、空调设定或身份授权。结构化JSON也可能装着推断内容，不能因为有字段就把它当成设备实测值。[VLM任务定义](https://bytedance.larkoffice.com/wiki/NuunwklpIiGS91kg7lRcAprqnMd?from=lark_search_qa&ccm_open_type=lark_search_qa#TvdtdyavUoaSltxkMcsc9mGCnvb)

PARA 7
标签和画面描述的消费方式不同。结构化标签适合触发器做精确条件，例如「后排座椅等于占用」「挡位等于 P」；自然语言描述适合顾问和大模型理解情景细节，例如婴儿的状态、乘员动作和舱内氛围。两类输出都要带上任务编号、摄像头来源、时间戳和置信状态；夜间、逆光、遮挡、镜头脏污导致不可靠时，结果应标记低可信或未知，而不是强行给出一个标签。视觉观察进入这一层时只作为待校验事实，不能直接等同设备上报的开关值。

## b-state-change 当前值、变化事件和用户要求怎样分别进入系统

PARA 0
**当前状态、刚刚发生的事件、用户口头要求是三类输入，不能互相替代。**B10（分别理解当前状态、变化事件和用户目标）把三类输入分开：状态是现在导航到哪里、当前温度或开关值，事件是刚刚切换了路线、开门、点击或停播，用户要求才是用户希望系统做什么。车门打开是事件，车门当前处于打开状态是状态，用户说「把车窗降下来」才是意图。

PARA 1
把事件当意图会造成误反应。导航偏航是事件，偏航后的新路线是状态；助手不能因为发生偏航就默认用户要重新规划餐厅，必须结合新的 query 或已注册条件判断。状态回答「现在是什么样」，事件回答「刚刚发生了什么」，意图回答「用户要我做什么」。排障时先把这三类拆开，再判断是信号缺失、事件误判还是意图理解错误。

PARA 2
对齐走 B04（把不同来源整理成可正确理解的事实）。它把来源、对象位置、单位和采样时间对齐成下游能理解的事实，区分当前值与变化事件，保留数据来源和失败状态。用户换了座位、导航换了路线，旧座位或「第二个途经点」就可能指向错误对象，对齐时对象绑定必须随最新状态更新。上一句目的地是餐厅，中途说「改去游泳馆」，导航重算后新的当前目的地必须绑定游泳馆；如果对齐层仍保留餐厅对象，后续「快到了」、途经点和停车建议都会指向旧目标。

PARA 3
对齐失败常见四类：对象绑错，例如副驾身份被写成主驾；单位不一致，例如温度、开度、距离在不同车型接口上量纲不同；时间戳错位，旧采样值被当成当前值；来源缺失，字段没有上报却被下游补成默认值。排障时先核对原始信号是否产生，再看对齐层是否改了对象或单位，最后才怀疑模型理解。对齐层还要保留原始来源，便于发现某一路信号陈旧或格式异常时追溯到生产模块。

PARA 4
对齐之后过 B05（检查这份状态还能否代表现在）。它再检查这份信息是否缺失、过期、失去权限或断连；有效、缺失、过期分别处理，权限撤回与设备断连要可区分，不能拿旧状态补成当前事实。这里不存在全系统统一有效几秒的答案，要按字段和场景约定时效：车速、挡位这类需要实时跟随的值，过期窗口很短；天气、地点这类变化较慢的值，可以保留更长时间。

PARA 5
缺失、过期、权限撤回与设备断连分开记录。需要当前车速、挡位或空调设定时，应按该字段的有效期和业务规则取得可靠状态。旧温度即使曾经正确，也不能补成此刻事实；可作有时间标记的历史参考，但不能据它默认再调整设备。依赖状态仍未知时，要补查、保留未知或停止相关动作，不能用所谓安全默认值掩盖数据缺口。

## b-consumers 同一批事实，Context 和触发器各取什么

PARA 0
**同一份事实按三路独立取用，没有必须依次经过的固定流水线。**对齐后的事实分三路走：一路进 Context 当本轮背景，一路进端云触发器判断条件，一路进静态顾问做建议素材。同一份事实能同时成为对话背景、触发条件和建议线索，这正是三路并列的原因；并不是每个变化都要依次跑三套系统，也不是说任何一次观察都会变成主动打扰。三路之间可以有先后消费顺序，但没有强制依赖关系，一路失败不代表另外两路不能使用同一份有效事实。

PARA 1
Context 这一路走 B06（按本轮问题给 Context 提供相关状态）。Context 是统一管理上下文信息的服务，存放情景描述、事件日志、短期历史压缩、短期情景记忆、长期情景记忆、长期语义记忆、用户画像、端状态和联网基本信息等来源；它为 Planner、顾问、执行器等调用方提供标准化存储、维护和查询。核心挑战是在保证筛选准确率的前提下提升检索效率。

PARA 2
原人机历史窗口和新的混合输入范围要分版本看。11月4日讨论保留5轮人机，再补近期5次混合输入中的非人机部分；独立旧事件流变量不再单独调用。摘要也从只压人机问答扩到人人与事件，但22轮与记忆侧20轮或20分钟的计数覆盖仍待核对。两份输入分别保原话与压缩内容，不能把事件上报等同已经进入本轮推理，更不能把开发计划写成已上线。[文字记录00:01至00:15](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 3
Context 经历过两代架构。第一代写入、粗筛、精筛三步式由单一模型统一过滤，为控制速度只输出五个结果，出现明显位置偏好；设计目标 P90 八百毫秒，实际达到一点二秒。第二代当前方案改为预注入加动态检索两阶段：进入 Planner 前并行拉取常用事实，覆盖约八成常规请求；Planner 判断信息充足就直接回复，不足再改写关键词和时间调用检索工具，兜底剩余约两成复杂请求；架构对比 P90 为五百六十四毫秒。八成与两成是设计覆盖口径，线上实测比例待核，五百六十四毫秒是架构对比数据，不是本章验收承诺。

PARA 4
触发器这一路走 B07（把相关状态变化交给端云触发器），只叫醒所属渠道实际登记的规则。渠道由 channel 字段区分：主线对应渠道应用编号一千，赛力斯对应九万九千二百一十，上汽 saic-dna 对应九万九千二百二十。导航距离更新只能叫醒这条渠道登记的规则，再继续沿对应任务链检查，更新一次不等于整个条件成立。云端配置平台本期改造覆盖数值信号、结构化信号和视觉推理信号的混合编排；单场景最多三十个节点，节点间手动连线且禁止成环。

PARA 5
触发方式分条件触发和推理触发二选一：条件触发沿用动态和静态条件配置，推理触发选择舱内低频、舱内高频、舱外三类视觉信号，支持多选组合；一个场景可以新增多个信号，信号之间配置与、或逻辑。条件之间的且、或只说明怎样组合，不会自动表达「先开门再关门」或「持续一分钟」这类时间关系，时间关系必须在场景规则里写清。新建场景默认未生效，需要手动打开开关，避免生产环境误触。节点版本上，十月二十日节点完成豆包闪念第一期 mock 链路，十一月三日节点完成静态条件接入、端侧链路打通。

PARA 6
顾问这一路走 B08（把有服务意义的变化交给顾问）。顾问根据充电等待或乘员状态发现适合服务的机会，再把建议送回主链取舍，不能自己直接抢话或控制车辆。知道当前导航状态，就能区分「还没开始选目的地」和「已经导航中要求换一家」；「昨天那家」的具体记忆仍要走记忆查询，不是车况模块自己猜出来。关键事实没进入当轮背景，先查数据有没有产生、有没有被选入，不能一上来就说模型不够聪明。

## b-visual-upload 视觉任务的运行状态，与它看到的内容要分开上传

PARA 0
**控制通道只回执行状态，数据通道才回原始结果，两条通道不能混用。**视觉任务跑起来之后，状态和结果要分两路走。以端侧视觉任务为例，视觉原始完整结果先通过数据通道按主题发布到数据中心，数据中心附上任务类型和时间戳，不解析、不拆字段，按端状态上报格式整包推给云端；云端端状态收到后再解析出天气标签、路况等字段，注入 Context 或顾问。

PARA 1
状态回调分同步和异步两层。同步层在调用当下立即返回指令送达还是失败；异步层在模型跑完后回传已启动、成功、空结果、超时、失败或已停止。回调承担五个用途：确认启动或停止真的生效，避免服务还没起来就以为已经运行；单次任务收到超时或失败后重试一次，二次仍失败则停止并告警；超时守卫释放被占用的摄像头，避免一直占着挡住别的任务；连续失败上报云端监控；内部任务状态表只以回调为唯一更新来源，支撑后续调度。

PARA 2
11月4日实车讨论暴露的是供给与使用脱节：舱内外caption已进入Context，但对话中的DT未能稳定参考。问副驾是谁时，应优先核FaceID已有身份，视觉问答不能代替身份服务。团队提出调整主模型对持续视觉的认识、拿实际已上报数据和实车案例验证；把高频动作作为事件插入历史输入，是讨论中的改进方向，不能写成已经完成。某些案例没用到不代表所有查询都从未消费视觉。[文字记录00:18至00:35](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 3
空结果要按任务的输出契约解释。V1.3里遗留物任务输出“正常”表示该次画面未检出关注对象；舱外天气某些空字段表示没有检出对应类别；失败或超时则没有形成可用观察。这三者不能混叫“没问题”。即使模型正常返回空结果，也可能受视角和遮挡限制，不能保证全车所有位置都不存在该对象，更不能拿超时空包覆盖上一份带时间的观察。[VLM任务定义](https://bytedance.larkoffice.com/wiki/NuunwklpIiGS91kg7lRcAprqnMd?from=lark_search_qa&ccm_open_type=lark_search_qa#TvdtdyavUoaSltxkMcsc9mGCnvb)

PARA 4
周期类和一次性任务的上传策略也不同。周期类任务时效优先，网络异常时丢弃积压包、不组织补传，只轮询上报最新状态，保证画面信息不过期；一次性任务成功率优先，漏传一次自动补传，断网时先暂存本地，网络恢复后通过断点续传发出。任务状态回传给触发器做调度决策，实时性要求高；识别结果写回信号库供后续判断消费，两类数据用途不同、分开通道处理。

PARA 5
这两条通道分开之后，失败表现也要分开对。控制通道报接收成功但数据通道一直没有结果，要查模型跑了没出画面、摄像头被占用，还是数据通道订阅错了主题；数据通道有结果但控制通道没回成功，可能是任务已经停止但结果迟到，不能把迟到结果当成新一次触发。把下发成功、启动成功、有结果、结果被消费四件事分开计数，排障时才不会把通道层问题混进模型能力问题。

PARA 6
以舱外天气感知为例的完整循环是：系统上电后端侧触发器启动，读到电源状态为开即注册舱外常驻任务；组装任务编号、摄像头、优先级、超时、互斥组、触发来源、有效期、执行方式和判断目标等字段，向模型同步发送指令，收到接收成功后标记已下发；模型调用前视摄像头拍帧、推理产出原始结果；控制通道只回传状态不传原始数据，数据通道按主题发布完整结果；常驻任务不释放互斥资源，等待下一周期续接，电源关闭才结束循环。

## b-feedback 车控完成以后，最新状态如何回到下一轮判断

PARA 0
**执行之后要让系统从「计划做什么」回到「已经发生什么」，不能从助手一句好的倒推。**B09（把执行后的车辆或应用变化传回来）让工具执行反馈和本地车辆结果进入后，结合实际状态通道整理成新的背景。导航已经启动、音乐确在播放，必须有真实结果。回包先到而采样稍后刷新，可能只是时序差；旧结果挂错请求、执行失败或状态根本没变，则是另一类问题，回流后的状态更新再走对齐流程。

PARA 1
每次请求、轮次、工具调用、任务运行和声音各自带关联标识，走 B11（把请求、轮次与结果关联回同一件事）。请求标识用于端云结果仲裁，轮次标识标记本轮对话，工具调用、任务运行和音频各有独立标识，出问题能沿同一案例串起来。用户目标可能跨好几轮和多次执行，下一轮要知道这条迟到结果属于谁，不能把上一家游泳馆的反馈混进刚改的新目的地。

PARA 2
这些标识不能混用。请求标识绑定一次端云请求，迟到的工具结果、语音回复和卡片回执都要回到同一请求；轮次标识区分同一目标下的多轮对话，避免把第二轮修改覆盖到第一轮请求；音区只标记发言音区，不等同身份；音频标识绑定一次语音播报，用于打断、恢复和音频回执追踪。排查状态回流问题时，先按请求标识找回请求，再按轮次标识定位轮次，最后按任务和音频标识定位具体执行分支。

PARA 3
下发通道走 B12（把云消息交给车端对应业务）。需要下发的消息按类型交给所属卡片业务，经主动消息通道推送事件、动作和任务状态，车端再按消息类型分发到所属业务。通道只负责送达，不替代业务理解；云端已发、车端已收、业务已受理、界面已显示仍是不同阶段，一个请求返回正常无法证明用户眼前出现了卡片。

PARA 4
通道消息按方法类型区分事件、动作和任务状态，具体枚举由通道消息格式文档维护；卡片业务收到后还要判断权限、页面状态、容量和避让规则，再决定是否渲染。推送成功只证明通道完成投递，曝光、点击、确认和拒绝是更后面的业务结果，指标必须分层统计，不能用云端发送成功代替车端显示。

PARA 5
「快到了」要先有本项目定义好的条件和可用导航信号。只有剩余距离、车速、拥堵等字段可取，并不证明已经实现某套综合权重模型。条件实际选哪些字段、从何时判断、用户改目的地后如何更新，应回到该任务与触发配置核对。距离缺失或过期时保留未知，不按旧目的地硬触发泳镜提醒。

## GUIDE base 用车里有点闷，读清事实从采集到回流的整条路

PARA 0
这张图按事实的生命周期排，不按模块排。左侧是三类事实的采集口：车辆设备值、乘员与应用信息、视觉观察；中间是对齐与可信度：把来源、对象、单位、时间对齐，再检查缺失、过期、权限和断连；右侧是三路供给：Context、触发器、顾问，最后是执行回流和关联标识。读图先找那个分叉点：对齐与可信度那一格之后，事实分成三路，三路在「执行回流」那一格重新合上，新状态再进对齐。

PARA 1
最上面的采集口分三类。车辆设备值是结构化实时值，按车身车控、行驶车况、补能健康三组各管各的刷新频率；乘员信息按座位、人脸、账号三层精度，不能跨层补全；视觉观察分精调标签和自然语言描述，标签喂触发器，描述喂顾问。三类事实精度不同，混在一起就会把「后排有人」当成「后排是主驾」。

PARA 2
中间对齐层把来源、对象、单位、采样时间对齐。用户从餐厅改到游泳馆、从主驾换到后排，对象绑定必须随最新状态更新；旧对象留着，后续所有判断都会指错地方。对齐失败常见对象绑错、单位不一致、时间戳错位、来源缺失四类，排障先看原始信号有没有产生，再看对齐层改了什么，最后才怀疑模型。

PARA 3
对齐之后过可信度闸门。缺失、过期、权限撤回、设备断连四类异常要分开，不能合并成一句「状态不可用」。车速挡位这类实时值窗口短，天气地点这类慢变量窗口长；驾驶相关信号缺失优先暂停主动建议，舒适性信号过期可以沿用上一轮安全默认值并标注缓存。把缺失当安全、把旧值当现在，后面推理再对也是错的。

PARA 4
可信度过了进三路供给。Context 这一路做当轮背景，当前方案是预注入加动态检索两阶段，预注入覆盖约八成常规请求，剩余两成走检索工具；触发器这一路只叫醒所属渠道登记的规则，渠道编号分清主线、赛力斯、上汽；顾问这一路拿情景做建议素材，不能自己抢话或控车。三路独立取用，一路失败不影响另外两路。

PARA 5
视觉任务单独走一条上传支路。控制通道回执行状态，数据通道回原始结果，两条不能混。同步回调确认指令送达，异步回调回传已启动、成功、空结果、超时、失败、已停止；周期任务时效优先丢积压包，一次性任务成功率优先断点续传。空结果是看过且没问题，和没看是两回事；超时不能往信号库写伪结果。

PARA 6
执行之后回流。工具反馈和本地车辆结果整理成新背景，经对齐层重新进入下一轮；请求标识、轮次标识、音区、音频标识各自绑定，迟到结果要能串回同一请求。下发通道只负责送达，云端已发、车端已收、业务已受理、界面已显示四阶段分层统计，不能用发送成功代替界面显示。

PARA 7
排查时把耗时分段看：事实产生到对齐完成、对齐到 Context 命中、触发条件比较、通道送达，各算各的。失败按位置对位：采集口缺字段回 B01 到 B03，对齐错回 B04，时效错回 B05，三路消费错位分别回 B06、B07、B08，回流串错回 B11、B12。评审这一章盯三条：三类事实有没有跨层补全、四路异常有没有合并成一句不可用、通道送达有没有被当成界面显示。

CLOSING 0
这一章定义的是事实怎样被采集、对齐、校验、分三路供给、再随执行回流，不定义这句话要不要接、条件成不成立、建议该不该发。视觉 caption 已上报但 DT 未消费、人人对话正在接入，都要在讲供给时同时讲消费状态。

CLOSING 1
评审盯三条：车控值、乘员信息、视觉观察三类事实有没有跨层补全，缺失、过期、权限撤回、设备断连四类异常有没有合并成一句不可用，通道送达有没有被当成界面显示。

# G 云端触发器

INTRO 0
用户说「我下车时提醒我拿手机」，现在没有让系统立刻提醒。他交出了一个以后发生的条件。对话结束后，仍需有人等待相应变化；条件出现时，还要能找回原来的安排。云端触发器承担的是发现时机、检查规则并通知配置出口的部分，提醒如何表达、任务是否已取消及后续怎样执行，由关联业务继续处理。

INTRO 1
先区别用户交办任务与产品预设场景。前者先由对话与任务服务建立安排，再注册触发；后者可以由产品直接配置「主驾上车打招呼」等固定规则。两者都需要条件、动作、执行策略和生效范围，但命中后的去向不必一样。触发器OnePage列出静态Advisor、主动推荐与第三方回调等动作，不能把每次条件命中都说成一次车控或一条用户已授权任务。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

INTRO 2
本章按一条场景从配置到命中讲：先确定适用车辆和信号，再判断条件，经过次数与间隔限制后，把本次触发交给配置的出口。端侧本地感知和云端服务有不同实现，相关端侧资源调度见L章，不能按信号频率直接断定谁执行。旧图保留了端状态、视觉语义、时间与业务回调的关系，读正文时以原文明确的版本及边界核对，不把图上相邻的框当成已支持的混合触发。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

## g-wake 场景先绑定业务与适用车辆，再选择能观察到的触发来源

PARA 0
一条触发场景先要说明它属于谁、在哪些车辆上生效。G01（接收场景与业务关系）承接业务安排，G02（这辆车能用这个场景吗）核对生效范围。OnePage列出渠道、车型、车辆ID与客户端版本等范围条件。后台保存规则只是配置完成，不代表每台车都已经收到或能执行；测试要选目标车型、环境与版本，不能拿其他车辆的成功记录证明本车已支持。[触发器 OnePage·生效范围](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 1
接着看G03（哪个信号叫醒这次检查）。信号触发可以判断端状态当前快照，也可以监听状态变为目标值。例如「车速为0」是当前状态，「车速变更为0」是从其他值切到0的那次变化。若车一直停着，反复上报0不应被解释为又停车一次。这两种条件的触发次数和去重依据不同，产品要先选准想观察的是状态还是变化。[触发器 OnePage·静态判断和变更为](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 2
上报是把端上或业务服务产生的信息传给指定接收方，不表示助手已经采取动作。车况上报的是设备值及相关信息，视觉上报的是模型观察或任务结果；事件服务还可接应用点击和业务过程。G12（把有意义的状态变化写业务事件）帮助保留可供后续消费的事实。只有来源、对象和时间明确，规则才知道这次信息应更新哪个状态，不能把不同座位、不同设备的同名字段混在一起。具体字段和上报策略见B与EL章。

PARA 3
云端不是只在用户说话时工作。定时计划、业务事件和相关端状态都可能让它开始检查，但持续视觉、任务服务和端侧业务也可能独立运行。旧稿把触发器说成「没人说话时唯一工作的层」会误导分工，应删掉。触发器只消费自己需要的来源，任务是否存在、视觉是否运行以及用户能否接受主动打扰，由相应模块承担。

PARA 4
G04（取本轮真正需要的状态）读取当前场景的必要信息。例如上车问候要关联乘客或占座变化，而不是拿空调温度触发。未收到、过期、格式错误或来源不可信应保留为缺少依据，不能统一改写成“没有人”。确定值与未知值要分开，具体缺项怎样终止或等待，需按场景实现核对。OnePage不支持连续趋势分析，因此不能只凭几条温度值就声称已支持「温度持续上升」。[触发器 OnePage·能力边界](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 5
视觉观察的采集周期、语义条件的判断频率和场景执行间隔是三个不同参数。一次观察可以供多个场景使用，同一场景也可能收到多份观察。OnePage的默认30秒限制作用于场景执行，不是“同一人物同一动作30秒只保留一次”，也不意味着30秒拍一次画面。没有读到对应视觉去重规则时，不得自行规定描述丢弃、人物坐标阈值或采样周期。[触发器 OnePage·执行策略](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

## g-judge 当前值、状态变化和视觉推理，要按各自规则判断

PARA 0
G05（逐步判断条件是否达成）处理的是已经定义好的判据。当前值比较可以判断车速、温度或开关是否达到目标；“有变更”判断新旧值不同；“变更为”还要求新值等于配置目标。多个条件可以组成条件组，组间支持且、或。这里组合的是同类条件表达，不等于能够把定时、结构化条件与视觉推理任意混在同一触发方式中。[触发器 OnePage·概念澄清](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 1
OnePage所列条件运算符包括等于、不等于、大于、小于、大小等于以及有变更、变更为；扩展条件库是否还支持包含、持续时长或计数，应查当前配置接口，不能用另一份清单的数量盖过本版。评审「连续切歌十次」时，要明确是否有对应计数能力和事件来源，不能因为能够判断一次切歌就承诺连续行为条件也成立。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 2
G11（语义推理只判断目标是否可见）在旧图中提供视觉语义判断位置。实际OnePage描述的是通过VLM判断画面中的目标情况，例如婴儿哭闹、儿童是否在车内；不止“目标可见”这一种问题。模型观察、条件成立、最终动作依次分开。一次画面未见目标可能是遮挡、角度不足或任务失败，不能不看结果类型就变成“目标不存在”。[触发器 OnePage·推理触发](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 3
混合触发是本版明确限制。FAQ写暂不支持“定时+条件”“条件+推理”“定时+推理”的混合触发。如果用户要求「晚上八点、宝宝还醒着才提醒」，先检查业务是否有独立任务编排或其他经验证路径，不能在云端触发器中直接拼一个没有实现的规则。旧稿给出打哈欠叠加车速就必然在同一条规则成立，超出了这份OnePage的边界。[触发器 OnePage·常见问题](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 4
条件成立以后仍要过G06（本次允许发出去吗）。总次数、自然日次数、单次上电周期次数和最小执行间隔分别限制不同范围：同场景可在条件仍满足时多次得到候选，但没有执行资格就不应再次打扰。触发条件描述“为什么现在值得做”，执行策略描述“这次是否还允许做”，两个判断不能合成一项成功率。[触发器 OnePage·执行策略](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 5
默认30秒内同一场景只执行一次，是OnePage的执行间隔口径。管理后台可以设置具体间隔，终值以发布的场景配置为准。它不是视觉事件去重窗，也没有证明所有场景只能固定30秒。若条件多次成立却没有再次发出，先看间隔和次数限制，再查漏触发，不能第一时间归因模型没识别到。[触发器 OnePage·执行策略及后台](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

## g-dispatch 命中后按配置出口交付，回调成功与业务办成分开记录

PARA 0
G08（统一派发场景配置的Action）按场景已定义的动作交出去。OnePage目前列出静态Advisor、主动推荐、回调第三方等方式。Action是触发后调用的出口，并非必然是一个车辆控制指令。欢迎场景可以给建议，下车提醒可以通知任务业务，订单结算场景可以回调指定服务。谁拥有车辆动作或支付权限，需要沿对应业务继续判断。[触发器 OnePage·动作](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 1
用户创建的条件任务经G07（用户任务回调任务系统）回到原安排，任务服务检查是否已经取消或到期，再让主链处理当次请求。回调里要能关联原任务和本次触发，不能因为通知到达就重建一项同名任务。用户已经取消时，迟到回调不得让它复活。任务创建、回调、执行和结果如何关联，见T章，触发器不再维护第二套任务生命周期。

PARA 2
Advisor提供建议，不等于用户已经同意动作。例如检测高温后建议通风，下一步仍受当前车况、确认方式和主动服务规则限制。触发器把机会交给Advisor，Advisor或Director组织建议及后续操作。不能写成温度一过阈值就由云端直接开空调，也不能按“高频”把回调绕开主链；出口应由场景定义而不是文字描述的频率决定。[触发器 OnePage·能力地图](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 3
自定义回调将触发结果交给使用方配置的地址。这一步返回成功说明接收方接受或处理到约定阶段，是否完成真正业务还需要业务自己的回执。一次回调失败、一次业务执行失败、一次用户取消，是不同事件。重试是否允许要考虑已有副作用和接收方幂等，不能给出无原文支撑的“所有通知都排队直到成功”。[触发器 OnePage·自定义回调](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 4
G09（不触发也要知道原因）帮助把条件没命中、超出执行间隔、次数用尽、范围不符和调用失败区别开。后台触发记录示例包含间隔和上电周期次数超限。条件命中但被频控拦住是有规则的正常收口；通知已发出但业务没响应则属于交付问题。没有事件、没有判定或没有回执也应保留缺口，不能全部叫“未触发”。[触发器 OnePage·触发记录](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 5
排查从同一场景、同一车辆和一次触发开始：先查它当时是否生效，再看来源有没有到达、条件怎样判、次数和间隔是否允许、出口调用得到什么结果。把每段证据放在一起，才知道问题归信号、规则、模型、通知通道还是实际业务。记录目的为复原决策过程，不是列一个“触发成功”掩盖后续失败。

## g-time 定时只提供到点信号，未来安排的执行仍沿原业务继续

PARA 0
G10（时间触发：到时回调，不直接控车）对应明确时刻或周期的计划。单次时间只产生那一次到点，Cron描述重复计划。例如用户安排十分钟后关加热，业务先保存“未来关”的意图并登记时间，到点回调原任务，主链再结合当前状态执行。触发器不需要保持一轮对话推理等十分钟，也不能在任务创建时就把加热关掉。[触发器 OnePage·时间触发](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 1
定时提醒与定时操作虽然用户可见结果不同，都要注册明确时间和出口。提醒可能由原业务组织声音，关加热需要车辆控制接口。不能另创一条“定时做事一定直接车控、定时叫人一定Planner”的通用规则，更不能在同段同时说到点直接控制、又说只回调。具体执行按该任务及场景的合同走，T章保留完整任务与结果闭环。

PARA 2
延时、定时与执行间隔不能混淆。延时五分钟描述从指定起点等多久；固定计划描述何时重复；最小执行间隔限制已经触发的场景多久可以再执行。默认30秒不是任务有效期，也不表示每30秒自动提醒。时刻发生时，如果任务已取消、条件失效或项目不支持，也不能凭到点信号宣布动作完成。[触发器 OnePage·即时延时定时及执行策略](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 3
一个任意未来日期或复杂组合是否可注册，必须核当前时间计划接口与任务能力。OnePage确认单次与Cron周期，但没有给出所有时间上限。旧稿把24小时、7天等数字写成全场景注册规则，来源不足时不继续沿用。如果相关任务文档有范围限制，应用在对应任务和版本，不把一个方案的限制扩成云端触发器永久统一规范。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 4
车辆离线或下电时，到点消息怎么处理需要任务自己的结束及恢复策略。一次当趟安排、跨天重复任务与本地已有预设不能统一全部删除或全部补做。网络恢复后的消息可能已过时，后台应按原任务状态和执行条件判断，避免用户离车后补执行一个不再需要的动作。这里不承诺OnePage未定义的离线续传或自动回滚。

PARA 5
文档把耗时分成触发匹配与下游触达两个阶段，推理场景再观察模型首输出和总体耗时。若用户反馈迟迟没提醒，先定位时间是否准确、回调是否送达、业务是否开始、最后声音是否真正播放。来源中的触达率公式写法需与统计实现核对，本章不复制有疑义的公式，也不把回调成功率当作用户真实听到提醒的比例。[触发器 OnePage·指标一览](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

## GUIDE base 从场景范围、触发判据到配置出口，沿图核对每次交接

PARA 0
先在G01（接收场景与业务关系）找这条规则对应的业务，再在G02（这辆车能用这个场景吗）看车辆和版本范围。G03（哪个信号叫醒这次检查）与G10（时间触发）表示不同来源，不表示同一项任务必然同时走两条通道。

PARA 1
信号到达后，G04（取本轮真正需要的状态）组织必要信息，G05（逐步判断条件是否达成）判断当前值或状态变化。当前车速为0和刚刚变为0不同，应按本章条件解释选判据，不能从图上相邻节点推断已经支持连续趋势。

PARA 2
G11（语义推理只判断目标是否可见）是旧图的视觉判断位置；本版OnePage用推理触发描述目标情况的语义判断。视觉任务与数值条件怎样组合，需遵守本版暂不支持混合触发的边界。图中有连接，不等于任意条件组合已实现。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 3
条件命中以后过G06（本次允许发出去吗），检查间隔和次数。默认30秒是同一场景执行间隔，与观察周期、数据上传和视觉去重不是同一个参数。G09（不触发也要知道原因）保留频控或失败依据，不能把正常限制当成识别遗漏。[触发器 OnePage](https://bytedance.larkoffice.com/docx/KdBzd7uzXonxOZxXJW9cHSKonld)

PARA 4
G08（统一派发场景配置的Action）与G07（用户任务回调任务系统）按业务配置交出去。用户任务回原安排，主动建议交对应建议链路，第三方回调按其接口契约处理；不是按“高频留端、低频上云”的文字标签自行改路。

PARA 5
G12（把有意义的状态变化写业务事件）帮助留存可消费事实，上报来源和后续使用要区别开。收到视觉描述不等于模型用了它；一份回调记录也不等于用户已听到提醒。端侧具体感知与资源生命周期见L章，业务事件与日志见EV、EL章。

PARA 6
复核一项场景先看适用范围、输入来源和发生时间，然后检查判据、执行限制、出口回执及用户可见结果。需要哪段证据就沿相应节点查，不给未知内容补一个默认值，也不复制其他车型的成功状态。

CLOSING 0
这一章把一条已定义场景怎样发现时机、判断条件和调用出口讲清；用户未来任务仍由任务服务保存并追踪结果。

CLOSING 1
评审要分清状态与变化、执行间隔与观察周期、通知送达与实际业务完成。混合触发和连续趋势按本版能力边界处理。

# S Advisor 主动服务

INTRO 0
用户没下命令，但车里很热，系统要不要主动降温、先问一句还是保持安静，这是另一类判断。用户说「把空调调低」是明确要求，Director 当场就能办；但「后排孩子哭了」「乘员有点晕车」「电量只剩二十公里」这些信号，用户没说出口，系统要自己发现、自己判断值不值得说、说什么。主动服务就是为了这种时刻：用户还没开口，系统先看他可能需要什么。

INTRO 1
这一站管的是静态顾问从被叫醒到出口的完整链路。它不直接控车、不直接导航、不直接播放节目；它只判断该不该主动关心、关心什么、建议什么，真正办成这件事还是 Director 的活。触发器的条件判断、频控和派发归第 13、14 章，条件任务与目标看板归第 12 章和 N11 章，视觉信号供给归第 17 章，任务中心展示归第 20 章。

INTRO 2
顾问被三种来源叫醒：云端预设事件、从对话和端状态里识别出的动态事件、舒适或出行子目标的周期复盘。叫醒之后先过开关闸，再收集信息、判断时机、生成带策略的建议，然后按渠道分三路交出去：需要说话的进输入管理排队交 Director，舒适出行的界面确认走 AI Bar 等用户点，内容节目单由车企直接播放。

## s-origin 高温信号为什么只是一次服务机会

PARA 0
**静态顾问不是固定话术库，「静态」指四类分工预先定义好，建议仍按当下情况推理生成。**S01（按预设服务方向理解潜在需要）把主动服务分成四类顾问：舒适类管车控建议，出行类管导航建议，情感类管陪伴建议，内容类管娱乐建议。用户已经明确交办的任务走任务系统或目标队列，不混进主动服务这条线。舒适顾问保障车内每个人的温湿度、空气和空间；出行顾问在安全与效率前提下提供省时、省力、省钱的出行体验；情感顾问察言观色、共情移情；内容顾问让行车和驻车时光不无聊。

PARA 1
视觉来源要分别看任务定义与消费效果。V1.3舱内高频任务每5秒取5秒视频，低频每5分钟取5秒视频，舱外每3秒取3秒视频；这些是该文档的任务周期，不能概括成所有视觉一帧固定几秒。11月4日会中指出DT对已有caption利用不足，并要求拿实际上报与实车验证。这个问题不能直接推出Advisor也从不使用视觉。影子观测模型是另一个发现端侧误召的保底讨论方案，不是视觉采集主路。[VLM任务定义](https://bytedance.larkoffice.com/wiki/NuunwklpIiGS91kg7lRcAprqnMd?from=lark_search_qa&ccm_open_type=lark_search_qa#TvdtdyavUoaSltxkMcsc9mGCnvb) [11月4日文字记录](https://aka.doubaocdn.com/s/68EV2Q9r4X)

PARA 2
顾问和规划器的分工必须先说清。规划器和复杂推理承接用户主动发起的 query，第一性原则是快速响应用户需求；顾问通过观察人、车、环境主动发现问题并提出方案，第一性原则是推得有用，允许牺牲一部分推理时间多轮迭代直到拿到理想建议。规划器无法同时承担被动承接和主动挖掘两种角色，在时间维度上只能偏向一种。主动关心、关心什么、建议什么归顾问，用户或顾问给出目标后怎么把事情办成归规划器。

PARA 3
顾问被三种来源叫醒，不是四个顾问每次一起无差别推理。S02（让相关事件或已有子目标叫醒顾问）讲三种入口：云端触发器命中的预设事件、车辆相关状态变化中发现的动态需求、对话和状态里发现的动态线索；已有的舒适、出行子目标也会按周期重新复盘进展。预设事件触发是一期能力，由云端触发器配置预先定义的高频事件，覆盖确定性高、可验收、适合先上线的场景。

PARA 4
动态事件触发是二期能力。动态事件模块连接 Context 模块的事件日志和静态顾问智能服务层，承担筛选、加工、分发三个动作：先从海量对话和端状态里识别有主动服务价值的内容，再把原始对话转化成带语义洞察的结构化事件，最后按事件特征路由到舒适、出行、情感、内容对应顾问。典型案例是从人人对话「堵得我都晕车了，已经有点恶心了」识别出乘客身体不适，路由给舒适顾问；从车内热聊某首歌识别出内容兴趣，路由给内容顾问。

PARA 5
子目标复盘触发只服务舒适和出行，对已经生成的子目标定时复查是否完成、是否需要调整或删除。为什么要把入口分成三类：预设事件可验收、动态事件覆盖隐性需求、子目标保证长时跟进，三者时效和证据强度不同。如果只保留预设事件，系统只能响应产品预先写死的场景，无法发现用户没说出口的隐性需求；如果全部交给动态推理，又会失去确定性场景的可验收性和频控基础。

PARA 6
一期推理范围只覆盖部分场景：舒适顾问约一半、出行顾问约四成、情感顾问约一半；内容顾问排到二期。二期扩展到舒适全部、出行八成、情感全部、内容一半，三期再覆盖四类顾问全部场景；这些是分期范围，不是当前车型已交付清单。一期先打磨少数关键场景效果，其他场景不单独做效果承诺。

## s-strategy 建议内容与打扰方式需要一起判断

PARA 0
**叫醒之后先过开关闸，再收集信息、判断时机；证据不足宁可不出建议，也不能让模型编造用户偏好。**顾问被叫醒后先核对开关，这一步决定现在能不能工作，不是判断已经找到了好建议。AI 服务总关闭会清除相应的动态、静态任务和子目标，系统预设任务保留、可正常触发但不播报语音；单独关闭主动服务，顾问不再推理和输出建议，下游对话推理引擎也不消费建议。语音禁用状态下静态子目标保留还是清理，会议讨论口径尚未统一，标注待核，不能擅自统一成全部停掉。

PARA 1
开关分层的产品理由是不同关闭动作影响的生命周期对象不同。主动服务子开关只控制云端主动服务是否运行，开启时顾问正常推理，关闭时模型不推理、不输出建议、下游不消费建议；开关状态需要上云，出厂默认关闭，用户完成隐私授权后默认开启。豆包账号未登录时主动服务同步关闭，Always On 关闭后主动服务推理上下文缺失端侧视觉信息、依赖视觉的事件无法产生，记忆开关关闭后推理上下文缺失记忆信息。

PARA 2
信息层走 S03（结合当前背景与已有任务理解需求）。它收集推理依据：车况、乘员、视觉和世界信息，合法可用的画像记忆，视觉模块也在向这里供给；用户已有的任务或目标告诉顾问他是否已经有安排；同一顾问近期五轮建议用来避免重复。需要实时地图或天气时才补查对应工具。信息层不直接决定是否推送建议，只回答当前发生了什么、用户可能想要什么、系统已经做过什么、还能调用什么工具。

PARA 3
每个顾问只取和自身领域强相关的部分，输入范围需要过滤机制降低模型注意力分散。舒适顾问输入端状态、画像、世界信息、动态目标列表和自身前五轮建议；出行顾问在此基础上再加行程管家数据；情感和内容顾问不共用行程管家。为什么要做领域过滤：全部信息塞进四个顾问会互相干扰，舒适判断不需要节目单细节，内容判断不需要露点温度。短期会话记忆还在建设中，缺信息时不能靠想象补出用户需求。

PARA 4
时机判断走 S04（决定现在是否值得打扰用户）。乘客正在睡觉、正在通话、驾驶负荷高，都会改变是否打扰以及怎么介入；用户刚拒绝过相同建议时也不再重复提议。短时多个事件可以合并推理，这个合并约束由对应顾问各自配置，不是全系统统一阈值。值得服务才进入下一步；应该静默、已经重复或证据不足，就转到不采纳归因节点保留原因。这里不出建议可能是正确决策，不等于系统漏掉了一次服务机会。

PARA 5
策略选择绑定证据强度、动作可逆性和当前驾驶负荷。舒适顾问可选静默执行、告知执行、语音确认、界面确认四种：动作确定性高、幅度小、可逆、低风险且符合历史偏好时走静默执行，例如历史上夏天上车总会开座椅通风，就静默打开主驾座椅通风；动作基本确定应该做、用户需要知道原因时走告知执行；有一定证据但不足以直接执行、一句话能确认时走语音询问；涉及多个选项、组合动作、多人冲突或长期偏好设置时走界面询问。初定最多打断两次，多事件可合并成一次说，最终次数与适用范围待产品确认。

## s-routing 一条建议怎样交到用户面前，并接回 Planner

PARA 0
**一条建议除了话术，还要带上目标、对象、理由、策略和渠道五个字段；是否出卡、按钮写什么由工程字段消费。**S05（为建议选择合适的交互方式）规定一条建议除了话术，还要带上目标、对象、理由和交互策略。目标是建议要达成什么，对象是对谁、什么场景说，理由是为什么现在说，策略是静默、告知、语音确认还是界面确认，渠道是语音、卡片还是界面。是否出卡、按钮写什么由工程字段消费，不需要都塞给模型。

PARA 1
顾问给规划器的输入格式是固定模板：先写顾问类型和该顾问目标，再写思考加建议，最后标注策略；给建议展示栏的输入不带策略字段。需要直接给规划器的建议额外增加三个工程字段：交互策略、按钮展示文案确认或取消、是否出交互卡的布尔判断；按钮文案和出卡判断不作为规划器模型输入，仅供工程链路使用。语音确认对应即时交互卡为真、按钮文案为确认或取消；告知执行对应即时交互卡为真、无需按钮文案；静默执行对应即时交互卡为假、无需按钮文案；界面确认走建议展示栏，不涉及即时交互卡。

PARA 2
需要说话或规划的建议走 S06（把需要 Planner 的建议交输入管理）。输入管理把需要说话或规划的建议统一排队，和用户提问、工具结果、事件一起安排当次交互，排到合适窗口再进入 S07。用户话语优先级最高，顾问建议属于非用户主动输入，正在播报时排队等待，同一顾问排队期间多条建议只保留最新一条，建议还需带上有效时间，超过有效时间未进入推理就丢弃并通知顾问。

PARA 3
优先级上用户 query 为最高，非用户主动输入为次高，后者包括参与合并的工具反馈、通知、动态顾问建议、静态顾问建议和上一轮播报被打断信息。用户 query 正在推理且首字未出时打断当前推理、新旧输入合并；首字已出到播报完成时直接打断播报，拼接上一轮被打断信息后处理新输入。非用户输入在推理未出首字时打断合并，已经开始输出则排队，等当前轮推理完成且播报完成后再处理。为什么顾问建议排次高：主动服务不能压过用户当下诉求；用户正在说话时被顾问建议打断，会直接破坏对话主导权。

PARA 4
最终出口走 S07（让 Planner 决定本轮怎么说和做）。这里消费建议的还是前面同一个规划器，并不是第二个大脑。它结合用户当前诉求决定询问、话术还是动作；确认之前，系统建议不能当成用户已经同意。规划器收到的是顾问目标、思考、建议和策略，再结合本轮用户诉求、历史和工具状态决定走语音询问、界面确认还是直接执行。把出口统一到规划器，是因为只有主链路掌握完整对话历史、用户授权状态和工具反馈；顾问如果直接决定执行车控或导航，会绕过确认和权限校验。

PARA 5
舒适和出行的界面确认走 S10（舒适与出行卡片确认后回 Planner）。建议展示栏即承载顾问建议卡片的界面区域。这一步承接界面确认类建议：上汽侧目标引擎生成输入和界面输出，字节侧透传，车企渲染按钮或状态；用户确认后，连同原建议和已确认状态一起交回 S07，不能只回一个没有上下文的同意。确认回流必须带回原建议上下文，是因为规划器需要知道用户确认的是哪一条建议、对应什么目标和动作；只回一个同意，模型无法把确认映射到正确工具参数。

## s-result 车控执行之后，AI Bar 必须更新真实结果

PARA 0
**界面更新依赖车控成功回执，没有回执不能把状态条写成已完成；界面更新失败不能倒推车辆没动。**规划器完成舒适车控后，还可能把真实结果交回该界面更新状态条，这是那条回线的含义，不是让用户再确认同一动作。协议分工上，云端产出目标、建议和界面描述，经主动消息通道下发；豆包端解析消息、下发界面协议，只感知协议不解析业务描述，再把用户确认经上行通道回传。

PARA 1
下行复用主动消息，在原有消息上扩充界面控制和界面载荷字段保持向后兼容；界面控制包含业务类型、是否需要确认、界面载荷不透明渲染对象。不需要确认的直接执行或告知场景，下发界面渲染同时发送上行 query，不等待用户操作；需要确认的确认执行场景，界面渲染后等待界面事件回传，再拼接用户已确认可直接执行上行。舒适建议展示栏输入来自顾问时生成按钮形态，来自规划器执行结果时生成状态形态；文案优先控制在四到六个中文字符，按钮文案用动作短语，状态文案用进行中短语。

PARA 2
即时卡片走推荐消息、推荐卡片类型，组件标识固定为实时卡片，标题固定为「AI 推荐」，内容是首轮文本清洗后的纯文本，按钮保持顾问配置的文字和顺序，点击后按钮名称原文作为 query；卡片展示本身不触发推荐回流。卡片渲染归第 18、20 章，本章只确认顾问建议的出卡标记和按钮文案由工程字段消费。

PARA 3
内容链路单独走 S11（内容卡片由车企承接节目播放）。输入只来自内容顾问，输出可以包含已经编排好的节目单；用户点击后由车企直接播放第一个节目单，不像舒适、出行的确认按钮那样再回规划器。节目单生成不等于车上已经播出，仍要核对可播资源、媒体授权和实际播放结果。生成文案时优先使用节目单标题，标题不超过六个字直接使用，超过六个字在不改变原意前提下压缩；标题缺失、宽泛或无法压缩时，按节目顺序找第一个有效节目。

PARA 4
内容链路与舒适出行链路的差异，来自内容推荐的确认成本和责任边界不同：节目单已经由内容编排工具预排，点击即播放，不需要规划器再拆工具；而舒适车控和导航变更涉及车辆状态和路线走向，必须回流规划器走确认和执行反馈。不核对可播资源和授权就播放，会出现节目单存在但信源不可用、点击后无声的失败体验。同一条状态条，按钮后的责任人可能不同，要先认清业务类型。

PARA 5
上汽渠道车端回流时把推荐标识随请求回传，上下文恢复后继续规划器，缓存有效期一分钟；赛力斯渠道还要携带原始加密用户标识，端上按界面控制和界面载荷展示、确认或播放；回流上下文有效且车控有成功确认回执时，才上报建议展示栏结果。全部失败、无回执或非车控场景不在结果回传覆盖内。

## s-followup 一次降温之后，什么时候继续关注，什么时候结束

PARA 0
**子目标只覆盖舒适和出行，有目标时每十分钟复盘一次，新事件触发推理时重置计时。**顾问推理后还可能生成或更新 S08（持续回看舒适或出行子目标）的舒适、出行子目标，例如继续跟进座舱是否已经舒适；不是每次推理都必须建目标，情感和内容不共用这套机制。有目标时，按十分钟或新事件回到 S02 重新复盘，新事件会重置计时。子目标交给目标管理模块展示，用户删除时再通知这一步停止跟进。

PARA 1
子目标机制只覆盖舒适和出行，是因为这两类需求天然具有持续性：高温上车后降温需要一个过程，补能和停车建议需要跟随路线变化；情感问候和内容推荐是一次性场景响应，不需要持续跟踪一个长期状态。子目标由预设事件或动态事件触发推理后非必须生成，创建后有三种结束方式：后续推理判断目标完成后删除，用户在任务中心手动删除，车辆下电后删除该车上所有跟进中的子目标。

PARA 2
存在子目标时每十分钟触发对应顾问针对子目标推理，这段时间内有新事件触发推理时会结合子目标一起推理，十分钟计时重新开始。子目标接入任务中心展示和用户删除属于二期能力，依赖任务中心；静态子目标不等于用户目标，同一任务不能同时跑两套管理。如果每次触发都强制创建目标，任务列表会被大量一次性建议占满；如果子目标没有完成判定和删除条件，过时的跟进目标会持续触发旧建议，形成重复打扰。

PARA 3
目标来源的渠道演进走 S09（把用户未来目标作为顾问的背景）。用户明确交办的未来目标，在不同渠道由任务系统或目标队列管理，它们可以作为顾问的背景信息，不能和顾问自己发现的服务需求混成同一条任务。上汽渠道仍有目标引擎接入，赛力斯渠道自建任务并融合用户任务；静态子目标不等于用户目标，同一任务不能同时跑两套管理。现在项目用旧动态顾问还是新任务系统，要以实际版本和调用记录为准，资料改名不代表车辆版本已经迁移。

PARA 4
当前落地现状走 S13（沿一条服务区分触发、建议、交互与执行）。二十五条预设事件中十条实车通过，三条测试中，六条待端侧状态，六条待视觉语言模型能力，当周端到端通过率还没有填写；这不是现在所有主动服务的总通过率。动态事件和子目标复盘链路已通，或者某张卡片开发完成，都不能替代真实场景验收。

PARA 5
进展按触发、推理、交互、使能四层登记依赖和阻塞。触发层预设事件快照里，十条实车测试通过、三条测试中、六条待开发依赖端状态、六条依赖视觉语言模型能力预计十一月逐步支持；动态事件模块开发完成，国庆节前完成实车端到端链路打通；子目标复盘开发完成、实车链路通。推理层的 Context 依赖世界信息已接入，记忆已接长期记忆用户标签，临时短期会话记忆待开发。开发通只代表模块接口或链路已连，场景通过要求预设事件能触发正确顾问、输入完整、策略正确、卡片或播报到达、车控结果真实成功；两层之间隔着端状态缺失、视觉能力、记忆字段、工具依赖和端云联调。

## s-expert-review-detail 专家知识要提供服务标准，并让系统能够检查

PARA 0
**历史反馈和长期学习仍有建设缺口，不能据此画出一套已经成熟的自动学习系统。**S14（区分已有建议历史与持续学习能力）表示结果和历史在后续建议里可以被利用，但不能据此画出一套已经成熟的自动学习系统。目前只用同一顾问近期五轮建议避免重复；历史建议和用户反馈接入事件日志仍在沟通，短期会话记忆待开发；用户拒绝一次不能直接成为永久偏好，需要哪些证据、归谁、保留多久、怎样撤回，仍要由产品定义。已有近期建议去重，和完整的反馈学习闭环，是两种不同成熟度。

PARA 1
自进化的长期目标是个人世界模型：观察记录不同人在不同环境下的行为，推送后记录显性和隐性反馈，根据反馈调整后续类似场景策略。当前一期只做本次上电周期内同顾问前五轮建议去重，二期逐步接入历史建议和用户反馈到事件日志，临时短期对话记忆补充刚发生场景的压缩摘要；用户显性确认、取消、删除、点击反馈和后续操作、打断、忽略、手动调整等隐性行为反馈的长期学习仍标记待定。为什么不能把一次拒绝写成永久偏好：单次拒绝可能来自当时在睡觉、通话、驾驶负荷高或只是心情不同；缺少多次证据和撤回机制，个性化系统会把偶发态度固化成错误长期偏好。

PARA 2
不采纳建议时按链路归因，走 S15（把一条建议没有生效的原因对应到具体阶段）。把没服务成的问题分开看：事件错、输入缺、推理错、策略错、排队过时、规划器未采用、卡片没到、确认丢、执行失败，分别追到对应断点，每段保留同一案例证据，不能全都归成顾问模型调整说法。

PARA 3
归因对应主动服务完整链路的九段断点。事件错是触发器或动态事件模块误触发、漏触发或事件描述错误；输入缺是 Context、端状态、视觉、画像、记忆或工具结果没有供齐；推理错是顾问模型在证据、对象、目标或建议内容上判断错误；策略错是静默、告知、语音确认、界面确认选择与场景不匹配；排队过时是建议在输入管理队列里超过有效时间被丢弃；规划器未采用是建议回流主链路后判断不适合当前诉求；卡片没到是出卡标记、缓存、透传或端侧渲染失败；确认丢是用户点击后原建议和确认状态没有完整回流；执行失败是工具或车控动作未成功，界面状态也没有如实更新。

PARA 4
排障时必须用同一条案例的请求链路和节点证据定位到具体段落，再分别找触发器、Context、顾问、输入管理、规划器、消息通道、端侧渲染或执行工具负责人。如果全部归成顾问模型不好，会掩盖端状态缺失、排队超时、卡片透传和执行回执缺失等工程问题，提示词反复优化也无法修复。评审时把接口测试通过率、端到端通过率、预设事件支持率分开统计，不能互相替代。

PARA 5
主动建议有效率指符合真实场景、对象与用户需求的建议数占被评测建议数的比例，建议按服务方向建立人工评测集；主动打扰率指不合时宜、重复或用户明确拒绝后仍不当出现的建议数占实际展示建议数的比例。预设事件支持率是当时进展口径，不代表后续已复验。主动服务触发器到建议生成不超过五千毫秒、建议采纳率不低于六成、子目标复盘准确率不低于九成，均为改写前版本既有口径，段起点、阈值和评测分母待核，不写成实测承诺。打扰频率上限按讨论中的两次口径试验收，最终值与适用范围待产品确认。

## GUIDE base 用车里很热要不要主动降温，读清顾问从被叫醒到出口的整条路

PARA 0
这张图按一次主动建议的生命周期排，不按模块排。左侧是叫醒与开关：三类叫醒来源、六道开关闸；中间是信息与时机：收集背景、判断值不值得打扰、生成带策略的建议；右侧是出口分流：需要说话的进输入管理排队交规划器，舒适出行走 AI Bar 等用户点，内容节目单由车企直接播放。读图先找那个分叉点：S05 生成建议之后，按建议的策略和业务类型分成三条出口，三条出口在「规划器消费」或「车企播放」那一格各自结束。

PARA 1
最上面的叫醒口分三类。预设事件是一期能力，由云端触发器配置预先定义的高频事件；动态事件是二期能力，从人人对话、端状态日志里识别有服务价值的内容，加工成结构化事件再路由到对应顾问；子目标复盘只服务舒适和出行，每十分钟回看一次。三种来源时效和证据强度不同，不能混成一类。

PARA 2
叫醒之后先过开关闸。AI 总开关、主动服务子开关、语音禁用、Always On、记忆开关、账号未登录，六道闸门影响范围各自独立；总开关关闭会清静态动态任务，主动服务子开关关闭只让顾问不推理，语音禁用期间子目标保留还是删除待核。闸门不过就静默，不是模型没推理。

PARA 3
过闸之后收集信息。端状态、导航、媒体、人员、记忆、世界信息、工具、目标列表、近期五轮建议，每个顾问只取和自身领域强相关的部分；舒适顾问不看节目单细节，内容顾问不看露点温度。信息层缺证据宁可不出建议，也不能让模型编造用户偏好或车辆状态。

PARA 4
信息齐了进时机关。通话、睡觉、高负荷驾驶、刚拒绝过同类建议，四类场景不打扰；短时多个事件可合并推理，初定最多打断两次，多事件合并成一次说。值得服务才生成建议，应该静默、已经重复或证据不足就保留不采纳原因。这里不出建议可能是正确决策，不等于系统漏掉了一次服务机会，时机判断绑定证据强度、动作可逆性和当前驾驶负荷。

PARA 5
建议带五个字段：目标、对象、理由、策略、渠道。策略分静默执行、告知执行、语音确认、界面确认、仅展示五类，绑定证据强度、动作可逆性和驾驶负荷。是否出卡、按钮写什么由工程字段消费，不塞给模型；语音确认对应即时交互卡为真、按钮文案为确认或取消，告知执行对应即时交互卡为真、无需按钮，静默执行对应即时交互卡为假。

PARA 6
生成建议后进输入管理排队。用户 query 优先级最高，顾问建议排次高；正在播报时排队等待，同一顾问多条只留最新，带有效时间超时丢弃。排到窗口交规划器，规划器结合本轮诉求决定询问、话术还是动作。顾问不直接控车、不直接导航、不直接播放节目。

PARA 7
三条出口分开看。舒适出行的界面确认走 AI Bar，用户点按钮后连同原建议一起回规划器，车控成功后凭回执更新状态条，没有回执不能把状态写成已完成；内容节目单由车企直接播放，不回规划器；语音确认走即时卡片，按钮名称原文作为 query。排查时按九段断点对位：事件错、输入缺、推理错、策略错、排队过时、规划器未采用、卡片没到、确认丢、执行失败，不能全归成顾问模型不好。

CLOSING 0
这一章定义的是静态顾问从被叫醒、过闸、收集信息、判断时机、生成建议到三条出口的完整链路，不定义条件怎么配、车控怎么办、节目怎么播。

CLOSING 1
评审盯三条：顾问有没有越权直接控车，六道开关有没有被混成一个开关，视觉 caption 已上报但 DT 未消费时顾问有没有把它当已可用事实出建议。

# L 端侧触发与本地闭环

INTRO 0
识别到前方浓雾，屏幕弹出一张卡问「要不要开启后雾灯」，用户说「好」，灯亮起。这件事从头到尾没等云端：规则装在车端，信号在车端订阅，判断在车端做，卡片在车端出，确认之后直接控车再回读真实状态。车辆下电、断网或者需要立刻响应的安全类动作，云端链路断了就没人管，端侧闭环就是为这种本地场景准备的。典型例子是雾天开后雾灯，天气保护任务在本地完成从感知、询问到车控的全过程。

INTRO 1
这一站管的是端侧触发与本地闭环。它不做意图识别、不规划任务、不生成话术，也不替原业务维护卡片生命周期。语音识别归第 03 章，任务规划归第 05 章，云端规则判断归第 13 章，卡片容器与任务中心展示归第 20 章。本章只讲本地链路里资格检查、规则装载、信号订阅、条件判断、卡片确认、车控回读和失败分层这一段。

INTRO 2
本地链路有两段最容易被混在一起：一段是「感知任务真的跑起来了没有」，另一段是「这次感知看到了什么」。前者是控制面，后者是数据面，两条线分开走。感知跑起来之后，条件判断分两级粗筛，命中后把事件交回原任务业务出卡片，用户确认时再核对这张卡还有没有效，最后控车并回读灯有没有真的亮。

## l-ready 从车辆上电开始：先让感知任务真的运行起来

PARA 0
**本地链路第一道门只确认车端有没有资格跑这条规则，规则本身还没有进入判断。**L01（车辆与任务具备运行条件）先查电源状态、任务开关和系统资源够不够跑这条规则。任务中心里端侧任务的开关状态由车控应用本地持久化维护，不需要云端介入；云端任务的开关状态完全由云端维护，端侧不做本地存储，避免两端状态不一致。开关只对应单条任务生效，端侧触发器任务的开关只控制端侧触发逻辑，云端触发器任务的开关只控制云端下发逻辑，互不串用。

PARA 1
任务中心一共承载三类任务：用户语音生成的长时任务、AI 主动服务静态配置任务、场景预测类预设任务。入口固定在桌面左下角，用户点击后直接进入专属页面，不走下拉通知栏；所有任务卡片用统一数据结构渲染，云端下发任务的按钮类型、展示字段和执行动作由云端预定义，端侧不做差异化解析。当前阶段场景预设只内置端侧天气路况保护任务，另外三个预设场景等云端配置平台就绪后统一下发；天气保护任务开关默认开启，正式配置以产品需求为准。

PARA 2
三个开关分开管。持续观察开关、语音开关、AI 总开关影响范围各自独立，不能合并理解。持续聆听对应全时免唤醒，持续观察对应舱内视觉，二者是一级开关下的两个子开关；关掉语音不等于关掉持续观察，关掉 AI 总开关才整体停用。AI 总开关默认关闭，关闭时所有子设置项隐藏不展示，并回到出厂默认状态；动态顾问任务被清除，静态顾问任务被清除、删除子目标且触发器不触发，系统预设任务保持可触发但不播报语音。

PARA 3
通过资格检查进 L02（装入当前端侧任务规则），这一步把本车型已经实现的规则装到车端。产品后台保存了一条云端规则，不等于这辆车自动具备本地能力，端能力要按车型逐款确认之后才开通；天气保护这款车确认装了，别的车型可能还没装。这一步要确认的是这辆车实际装了哪些规则、信号和业务出口，而不是模型理论上能理解什么描述。一期本地规则由端侧研发按任务逐条实现，为后续优先级仲裁和规则远程更新留出入口。

PARA 4
规则引擎调研后选用 QuickJS 作为端侧规则沙盒：标准 JavaScript 语法学习成本低，有配套 Go 版本适配服务端技术栈，执行环境与已有业务逻辑隔离，支持复杂 JSON 操作、正则、数组字符串和条件嵌套。规则脚本只返回真或假，不能返回其他结果，所有动作统一交给任务管理执行，不把动作硬编码进规则脚本。这套端侧 JS 协议和云端自研场景引擎协议当前是两套、各自维护，本期不做统一。

PARA 5
云平台保存规则不会自动下发端能力，端云统一配置和下发属于后续建设。按八月十一日技术方案评审的规划，后续配置同步器会在豆包启动或定时轮询时上报本地规则版本号，由云端判断是否需要更新并拉取新规则；当前阶段这套版本比对和远程下发链路还没有上线。端侧与云端任务在配置能力上的边界先分清：端侧任务选择端状态信号和视觉结果、定义规则、选择后续处理、填写交互文案、安排执行前复核和回读，现阶段都由端侧研发按任务需求实现。

## l-control-data 任务状态和画面内容走两条线，下游才能知道该相信什么

PARA 0
**订阅成功和结果真正到达是两件事，视觉模型回了请求已收到不等于识别结果已经传来。**规则装好进 L03（订阅车况与本地视觉结果），开始盯信号。车况信号来自车端状态，比如挡位、车速、车灯；需要看图的规则再取本地视觉结果。浓雾要看舱外观察，雾灯是否已经开着还要同时看车灯状态，不能只取其中一份。触发器只对接数据中心，不直接对接视觉语言模型软件开发工具包；一个事件变更之后，触发器会把规则依赖的其余状态主动从数据中心拉回来，组装成本次判断的上下文快照。

PARA 1
视觉任务输出有结构化字段和自然语言描述，字段结构不等于实测真值。乘客位置、动态和天气可来自VLM推理，挡位、车灯等状态来自车辆数据。V1.3用不同topic区分乘客列表和动态任务，部分工程输出已去掉动态任务；应按实际topic及版本核对，不把不同出口混成“所有视觉输出都上报端状态”。[VLM任务定义](https://bytedance.larkoffice.com/wiki/NuunwklpIiGS91kg7lRcAprqnMd?from=lark_search_qa&ccm_open_type=lark_search_qa#TvdtdyavUoaSltxkMcsc9mGCnvb)

PARA 2
端侧触发器不向 Advisor 和 Planner 直连推送任何结果。模型跑完的识别结果写回信号库，信号库按上传策略上报 Context，Advisor 和 Planner 从 Context 消费这条视觉事实。端侧触发器只接收规则和动态任务下发，不向云端推结果。评审时看到端侧直连 Advisor 的画要标错，这是明确的架构决策。

PARA 3
状态回调分同步和异步两层。同步层在调用当下立即返回指令送达还是失败；异步层在模型跑完后回传已启动、成功、空结果、超时、失败或已停止。回调承担五个用途：确认启动或停止真的生效，避免服务还没起来就以为已经运行；单次任务收到超时或失败后重试一次，二次仍失败则停止并告警；超时守卫释放被占用的摄像头，避免一直占着挡住别的任务；连续失败上报云端监控；内部任务状态表只以回调为唯一更新来源，支撑后续调度。

PARA 4
上传策略上要分清现状和目标。按二点六目标口径，端侧默认不上传全量画面描述，命中条件才上传本次证据，调试模式可以全量上传，同时区分接收成功和结果真正到达。要注意现状与目标的差异：现行视觉原始结果由数据中心按消息主题整包透传云端，并不只在命中后才上传；命中才上传证据是后续方案，评审时不能把目标口径当成现行实现。

PARA 5
上传异常按业务时效分级处理。周期类任务时效优先，网络异常时丢弃积压包、不组织补传，只轮询上报最新状态，保证画面信息不过期；单次任务成功率优先，漏传一次自动补传，断网时先暂存本地，网络恢复后通过断点续传发出。以舱外天气感知为例的完整循环是：系统上电后端侧触发器启动，读到电源状态为开即注册舱外常驻任务；组装任务编号、摄像头、优先级、超时、互斥组、触发来源、有效期、执行方式和判断目标等字段，向软件开发工具包同步发送指令，收到接收成功后标记已下发。

PARA 6
数据中心附加上下文类型和时间戳，不解析、不拆字段，整包推给云端；云端再解析注入 Context 或顾问。收到成功回调后标记本周期完成，常驻任务不释放互斥资源，等待下一周期续接，电源关闭才结束循环。数据中心的通用键值事件能力不感知具体业务逻辑、不做持久化，只负责事件注册和透传分发。雾灯由关到开会触发一次检查；信号变化不等于条件成立，仍然要过条件判断，这一条已经落地，用来区分状态穿越事件和业务条件达成两个概念。

## l-resources 一次问画面和持续观察，不能使用同一套资源结束规则

PARA 0
**条件匹配分两级粗筛，避免每个任务在每次信号变化时都全量扫描。**进 L04（条件成立并且仍有效吗），第一级先判断运行时段，例如停车时要求电源上电、P 挡、车门解锁，时段不满足就回到监听；第二级在对应时段内匹配具体触发事件。两级设计是为了避免每个任务每次信号变化都全量扫描，端侧性能扛不住。第一级粗筛排除当前时段不可能触发的规则，例如车还在 D 挡高速行驶时，停车时段类任务直接回到监听；第二级才在对应时段里精准匹配具体事件。

PARA 1
这一步还要核对进入条件和当前对象，处理退出、抖动和重复：浓雾已经散掉，刚才排队的询问就失效；「现在是某个状态」和「刚进入某个状态」不是同一种条件；且、或只表达条件组合，不自动表达先后时序；样本数和时间窗只认本项目已经确认的规则，旧天气方案里被划掉的默认值不能直接拿来用。

PARA 2
天气保护的进入确认与退出确认需要分别定义，不能同一段既说进入不防抖，又说必须连续多个周期。雨雪雾触发条件、重复观察次数和退出等待，按该车型已发布规则及对应PRD核对；旧设计中已划掉的周期与次数不继续当当前标准。观察样本不足时不补成确定天气，退出后的旧卡片也不能继续执行过期建议。

PARA 3
同一事件可能命中多条规则，候选任务进入队列后按优先级仲裁。协议预埋了优先级字段，任务队列按 P0 到 P3 排序，同一优先级先到先跑，P0 安全类任务到来时正在运行的低优体验类任务让路。天气保护内部的雪天、雨天、雾天子场景按雪天优先于雨天、雨天优先于雾天的顺序判断。P0 到 P3 四级打断规则属于二点六目标口径，正式优先级档位对应表待运营确认。

PARA 4
条件命中后先生成候选任务集合，而不是立刻执行：此时任务只是获得了运行资格，可能同时有多个任务命中，需要先排队。仲裁通过后，触发器组装四个核心信息打包成一条运行指令：这是哪个任务、让模型看什么、优先级多高、超时多长。被打断的低优任务保留状态，等高优任务跑完再考虑恢复；单次任务跑完即标记完成。优先级字段在协议里预埋，是为了后续产品可以在简单排序之外扩展更复杂的仲裁策略。

PARA 5
条件成立进 L05，缺信号或判定异常走 L12 留下断点。端侧与云端任务在配置能力上的边界先分清：端侧任务选择端状态信号和视觉结果、定义规则、选择后续处理、填写交互文案、安排执行前复核和回读，现阶段都由端侧研发按任务需求实现；云端任务引用已有端状态，部分规则已支持平台配置，后续处理走主动推荐、识别 Query 或确定性动作链路。

## l-local-business 本地雨天提醒由业务接住，触发模块不会包办卡片和车控

PARA 0
**端侧触发器只判断并发业务事件，不创建卡片；它把哪条任务、哪个子场景、这次看到什么交给原任务业务。**命中后进入 L05（把命中事件交给原任务业务），这是本地分发台。交接对象是原来那条任务业务，例如天气保护，不是直接宣告车灯已经打开；雨雪雾共用一个触发器时，不能归成同一组动作，各走各的原业务。对话推理引擎不参与端侧拉卡和本地确认。

PARA 1
本期四个预设任务分属端侧和云端两条方向：天气路况保护是端侧自闭环，雨雪雾分别询问，确认后切对应模式或开后雾灯；后排儿童或宠物识别后开启儿童锁、识别充电设备后打开充电口盖、后视镜自动加热属于云端任务。云端任务又分两类：确定性云端规则任务，云端已有状态足以得出结论，不需要对话推理引擎或规划模块；云端协作任务，还需要顾问、对话推理引擎、视觉问答或上下文补充判断，充电口盖场景属于第二类。

PARA 2
触发器发给原业务的内容限定为命中子场景、最新车况、识别依据和本次处理关联，原业务选定建议目标动作，不把雨雪雾统一执行；原业务再把本地业务类型、建议文案、确认取消意义、语音播报、本地词表、有效条件和结果控件交给卡片系统。需要确认时进 L06（原业务发起即时交互卡），由原业务注册这张卡片：正文、按钮、可说词、有效期和回调都要指向这一次具体建议，再交给卡片系统展示和避让。

PARA 3
卡片先要真正显示出来用户才能点，注册、送达、排队、曝光是不同状态，下发成功却被别的交互避让，不能算用户拒绝。本地卡片和云端即时卡不是同一套协议，这里也不重新进规划模块再执行一遍。卡片元素固定为标题、正文、按钮名称和触发原因四类，语音播报文案可以和卡片正文使用不同文本，分别配置。即时卡片只服务语音交互场景，包括用户主动触发语音和主动推荐中涉及语音的环节，其他场景不启用。

PARA 4
展示遵循按需展示、低扰高效和信息降噪三条原则，只在状态确认、信息浏览、结果说明和后续引导时出现，不在轻量容器里承载长路径操作。卡片元素由谁开发跟随业务逻辑归属：用车顾问业务逻辑由字节开发，卡片元素就由字节开发；预约充电业务逻辑由车企开发，卡片元素纳入车企业务组件库，双方分别输出界面并交叉评审。本地语音确认只覆盖配置好的表达，例如确认、取消；「为什么要开」「先别开，等雨大一点」这类反问或延后表达不能直接当成确认。

PARA 5
这些反问和延后表达也不能原样吞掉。用户问「为什么要开」，原业务给一句简短解释，卡片按剩余有效期继续等，解释完不自动执行也不自动关闭；用户说「先别开，等雨大一点」，原业务记下延后意图，本次询问结束，但同一条天气保护任务的订阅还在，下一轮雨量条件变化时会重新评估。把反问当确认、把延后当拒绝、把解释当执行，都会让用户觉得系统没听懂。

## l-confirm 用户答应以后，先找对这次建议，再执行车辆动作

PARA 0
**用户点确认时，必须先核对这张卡还在、任务还开、车况没变；旧卡消失后再说好的不能拿来同意旧动作。**用户点确认，或者本地可见即可说命中按钮，进 L07（确认真的对应当前这张卡吗），这是确认前的一道关卡。它再核对确认属于当前这张卡、任务仍然开启、车况没有变化；卡片已经消失，用户事后再说一句好的，不能拿来同意旧动作。取消、超时、旧确认都不执行，复核通过才去执行，拒绝或已失效去收尾，卡片直接关闭、超时也进这一步。旧选择的有效窗口时长当前方案没有给出统一数值，评审时需要按场景单独确认。

PARA 1
用户不同语音行为在这一步有明确处理规则：说「好，打开吧」结合当前询问理解为同意，再执行前复核；说「为什么要打开」只解释当前建议，不因提问就执行，后续是否保留询问按卡片有效期处理；点击确认若走静态顾问链路，按原文模拟 Query 到规划模块，不同时在端侧直接执行一遍；点击取消、明确关闭或超时，不生成本次动作并告知询问结束；卡片消失后再说「好的」，不允许命中已经失效的旧建议，必须有新的明确意图或新场景。

PARA 2
复核时原业务要重新检查任务状态和最新车况，而不是沿用卡片注册时的快照，因为等待期间挡位、乘员或灯光状态都可能已经变化。到 L08（执行车控并读取真实状态）才真正改变车辆。原业务调用已经支持的明确动作，把实际车辆状态读回来。用户同意开后雾灯时，按钮点中、指令接收、灯实际亮起要分别确认；只有真实状态回来，这一步才交下一步更新本次结果。失败或者没有真实回执，转 L12 留断点，不能用一句成功话术填补。

PARA 3
复核时发现车况变了，还要分情况处理。等待期间挡位切走、乘员下车、灯光被用户手动改过，不能沿旧快照继续执行；对象已经不在位，本轮直接记为失效并收尾，不强行唤起主对话。对象还在但状态变了，比如雾灯已被用户手动打开，就按现状处理，不再重复下发开启指令。只有任务还开、对象还在、状态和注册时一致，才真正进入车控。

PARA 4
识别正常返回、未检出关注对象、失败或超时、被打断，需要分别记录。未检出只描述本任务在这次有效画面中的结果，不保证所有位置都没有问题；失败或超时不能写成“无障碍物”，也不能用空值伪装正常。高优抢占后的恢复按调度规则处理，恢复并不意味着旧观察仍然代表现在。[VLM任务定义](https://bytedance.larkoffice.com/wiki/NuunwklpIiGS91kg7lRcAprqnMd?from=lark_search_qa&ccm_open_type=lark_search_qa#TvdtdyavUoaSltxkMcsc9mGCnvb)

PARA 5
车控执行同样要求读回真实状态：按钮点中只是交互受理，指令接收只是服务端收到，灯实际亮起才是状态改变，三者必须分别确认。进 L09（更新结果并等待下一次）记录本次成功、失败、拒绝或失效，再按原业务规则进入冷却或等待。服务仍然开启时，从这里回到订阅接收下一次状态；本次取消或条件失效就收尾，长期任务继续等下一次触发。

## l-lifecycle 任务开关、车辆下电和异常回流，决定闭环能否长期可靠

PARA 0
**一次上电周期内的任务在下电后模式恢复，重新上电需要重新判断，任务不会跨上电周期自动延续。**结果收尾后还要区分单次任务和持续任务：单次任务跑完标记完成，不再排队；被打断的任务在高优任务结束后回到队列恢复；持续任务释放本轮上下文，回到监听状态等待下一次信号。天气保护这类预设任务本任务不会自动关闭已经打开的儿童锁或雾灯，后续关闭由用户操作或车辆既有策略负责。

PARA 1
L10（本地卡片终止，不等于关闭服务）要分清四种终止：关卡或超时只结束本次交互；关任务停止后续场景触发；关持续观察影响对应感知；已经完成的车控另行决定是否恢复。用户关掉一张卡片，不代表停用了整项服务；已经打开的车灯不会因为关掉预设而自动恢复原状，更不会自动撤回已经完成的车控，不能让一个关闭状态承担完全不同的含义。用户关闭任务后系统停止新触发，关闭任务不等于撤销已经发生的车辆动作。

PARA 2
端云协调走 L11（本地与云端不得重复执行同一动作）。端侧已经完成动作，云端又送来同一条建议时，要让真实本地结果参与对应项目的仲裁，不能让用户确认一次却执行两遍。有本地规则和视觉小模型，也不代表所有任务都能完全离线，还要逐项核对本地信号、词条、卡片、车控和回读是否接通；进一步的端云统一仲裁属于后续建设，现在不能说成全场景已经防重。当前阶段端侧自闭环和云端自闭环两条链路相互隔离，协议各自维护，端做一半、云做一半的混合场景本期不涉及。

PARA 3
端云结合场景不是离线优先：有网时优先请求云端链路，云端链路超时或者一开始就发现断网，才启用本地候选规则。按九月口径为云端三秒超时或断网才启用本地候选，最终超时阈值待核；网络恢复后重新同步，不能凭无网推定全本地；同一场景还要校验重复执行和迟到结果。兜底路径只承接已经在本地实现的规则集合，云端专属任务不能因为断网就假定端侧也能办理；迟到的云端结果到达后要和本地已执行动作比对，避免重复下发。

PARA 4
离在线语音采信规则不等于端侧触发器的通用调度规则。较早PRD的白名单优先及2秒心跳，与R章9月30日缓存优先、云端业务等待超时属于不同版本和计时器。端侧本地预设任务按自身协议运行，用户语音的端云候选由R章负责解释；不能把两套规则同时列成这台车当前必须遵守的流程。

PARA 5
失败分层走 L12（本地失败按断点回报）：信号缺失不等于规则未命中；相机或模型失败不等于没看见事件；卡片没展示不等于用户拒绝；车控受理不等于实际状态已经改变。四种分开记录，排查浓雾保护没反应时，才能沿同一场景证据找到断点，而不是全都归成模型不够聪明。四类失败在线上分别挂载到对应节点：信号缺失对应订阅，相机或模型失败对应判断，卡片没展示对应卡片注册，车控受理对应状态回读。

PARA 6
失败分层的意义是把规则问题、资源问题、模型问题和时序问题分开。信号缺失要回到订阅环节查订阅和取数；相机或模型失败要回到判断环节查视觉链路和回调状态；卡片没展示要回到注册环节查注册、送达、排队和曝光；车控受理要回到执行环节查指令回执和状态回读。每一层都留下当时信号快照和状态码，复盘时不把不同性质的失败合并成一句「没触发」。端侧执行结果是否需要回传云端、以什么形式回传，在八月十一日评审时仍是待定项。

## GUIDE base 用浓雾开后雾灯，读清本地闭环从资格到回读的整条路

PARA 0
这张图按一次本地任务的生命周期排，不按模块排。左侧是资格与规则：电源、开关、资源、车型规则装载；中间是控制面与数据面并行：订阅车况、订阅视觉，再进两级条件判断；右侧是分发与执行：命中事件交原业务、原业务出卡片、确认关卡、车控回读、结果更新。读图先找那个分叉点：条件成立那一格之后，任务只是获得运行资格，不是直接控车，中间还要经过原业务出卡片和用户确认两道闸。

PARA 1
最上面的资格检查是第一道闸。它查电源状态、任务开关和系统资源，只确认车端有没有资格跑这条规则，不进入判断。端侧任务开关由车控应用本地持久化，云端任务开关由云端维护，互不串用。三个开关分开管：持续聆听、持续观察、AI 总开关，关掉语音不等于关掉持续观察。过闸之后规则按车型装载，产品后台有一条云端规则不代表这辆车本地装了。

PARA 2
规则装好进订阅。车况信号来自数据中心，视觉结果由软件开发工具包经数据通道整包发布，触发器不直接接软件开发工具包。控制通道回任务状态，数据通道回原始结果，两条不能混。同步回调确认指令送达，异步回调回传已启动、成功、空结果、超时、失败、已停止；订阅成功和结果真正到达是两件事。

PARA 3
订阅之后进两级条件判断。第一级粗筛运行时段，电源上电、P 挡、车门解锁这类不满足就回监听；第二级才在对应时段里匹配具体事件。天气保护进入防抖按连续三个周期一致，雾天两个周期，退出按连续八个周期一致，视觉轮询约十秒一次，退出八次约八十秒。同一事件命中多条规则时按 P0 到 P3 优先级仲裁，P0 安全类任务到来时低优体验类让路。

PARA 4
条件成立不等于直接控车。触发器把命中事件、子场景、最新车况、识别依据交回原任务业务，由原业务出卡片、定文案、配按钮。端侧触发器不创建卡片，对话推理引擎也不参与端侧拉卡。卡片注册、送达、排队、曝光是不同状态，下发成功却被别的交互避让，不能算用户拒绝。

PARA 5
用户确认时过一道关卡。再核对这张卡还在不在、任务还开没开、车况变没变；卡片已经消失，用户事后再说好的不能拿来同意旧动作。「为什么要开」只解释不执行，「先别开等雨大一点」不直接当确认。复核通过才去执行，原业务要按最新车况重查，不能沿用注册时的快照。

PARA 6
到车控节点才真正改变车辆。按钮点中、指令接收、灯实际亮起三者分别确认，只有真实状态回来才算成功。成功、空结果、失败超时、打断四条结果回路分开写：空结果是看过且没问题，和没看是两回事；超时不能往信号库写伪结果。结果更新后服务仍开就回监听等下一次，下电后模式恢复，重新上电要重新判断。

PARA 7
排查时把失败分层看：信号缺失、相机模型失败、卡片没展示、车控受理四类分别挂载到订阅、判断、卡片注册、状态回读四个节点。端云重复执行要靠真实本地结果参与仲裁，三秒云端超时或断网才启用本地候选，最终阈值待核。评审这一章盯三条：资格检查有没有把开关和资源混为一谈、确认关卡有没有拦住旧卡旧确认、车控有没有按真实灯亮状态回读。

CLOSING 0
这一章定义的是端侧从资格、装载、订阅、判断、分发、确认、控车、回读到失败分层的本地闭环，不定义条件怎么配置、话术怎么生成、卡片怎么渲染。

CLOSING 1
评审盯三条：确认关卡有没有拦住旧卡旧确认，车控有没有按灯实际亮起回读，端云重复执行有没有被真实本地结果参与仲裁。

# SE 自进化与专家知识

INTRO 0
用户说「记住我喜欢喝冰美式」，系统要做的不是把这句话存下来就完了——它要判断这条信息属于哪一层、什么时候写进去、下次什么时候用。记忆分短期和长期两层，短期由视觉、对话、任务、端状态等多种事件聚合而成，长期存用户的偏好和属性。

INTRO 1
这一站手上拿到的是用户的纠正、偏好、行为和历史对话。它不负责理解当前要做什么动作，也不负责调工具，它只负责把用户的偏好和历史存好、取好，让 Director 下次推理时能用上。

INTRO 2
存好以后，下次用户说「我想喝杯咖啡」，Director 在前置 context 检索时就能拿到「用户喜欢冰美式」这条记忆，不需要用户每次重新说一遍。这就是自进化的意思——系统越用越懂你，不是每次都从零开始。

## se-knowledge-purpose 先把用户的纠正变成可检验的要求

PARA 0
**用户的纠正不能只存一句话，要变成可检验的要求。**用户说「不要给我推荐辣的」，不能只存「用户不喜欢辣」，要变成：下次推荐餐厅时，过滤掉辣的选项；下次推荐外卖时，标注辣度。这是偏好记忆，属于长期记忆的一种。

PARA 1
短期记忆不是「当前对话上下文」这么简单，它是由多种事件聚合而成的：视觉流式文本（舱内身份、关系、行为、物品）、当前和最近的对话、正在做和已经做的任务、当前位置天气时间等环境信息、设备端状态（空调、座椅等）。这些都存在 context window 里，随对话轮次滚动。

PARA 2
长期记忆存的是跨会话保留的信息：用户的习惯和偏好（饮食、内容消费、颜色、消费习惯）、状态类语义（职业、居住地址、社会关系）、持久化的视觉记忆（人脸、风景）、按日期记录的重要事件。每个智能体还可以有自己独立的长期记忆。

PARA 3
历史输入供模型接上当前交互，对话摘要压缩较早内容，记忆服务另管经历与事实。PRD把瞬时记忆列为当时未使用，没有在可读正文中给它定义20分钟或20条阈值。短期记忆不能直接等同context window，自进化也不是把全部历史逐层搬到长期库。各类信息的用途与版本，见K章。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

PARA 4
记忆进 Director 的方式：query 进入时前置 context 检索已含用户记忆；够则直接推理，不够再调记忆工具。不是每次都先调记忆工具查一遍，而是 context 检索模块已经把相关的记忆前置进来了。

PARA 5
记忆操作工具 user_memory_operate 和记忆检索工具 user_memory_search 都是必选，不接受定制。写入、查询、删除，都走这两个工具。

PARA 6
记忆开关关闭时设家：先提示用户打开记忆开关，不能关了开关也记地址。这是 11 月 4 日会议最终收口的方案，之前讨论过「关了开关也记地址」的例外，已经否决。

PARA 7
座椅位置数据有特殊边界：只存在车机本地账号体系，不上云、不给豆包数据，只给位置 ID 并调原子能力接口。只有用户说了用途语义，才调记忆工具记人-用途-ID 的绑定。

PARA 8
记忆和车机打通的流程：写入位置信息时需包含 POI 名称，包含时可直接写入，不包含时需借助 POI search 工具明确 POI 名称。优先采用方案一：Director 先判断是否包含核心信息，不包含先调 POI search 用户选点后再调记忆工具。

PARA 9
记忆存储字段包含 POI 名称（必选）、POIID、经纬度、地址。当前方案先试 POI 名称强匹配直接发起导航，跨城同名小区的 ID 问题还在跟弋途确认。

## se-knowledge-types 偏好、单点做法和长时服务需要不同的信息

PARA 0
**偏好、单点做法和长时服务需要不同的信息。**偏好是「用户喜欢什么」，比如喜欢冰美式、不喜欢紫色氛围灯；单点做法是「这次这么做」，比如「昨天那家游泳馆在徐汇日月光」；长时服务是「持续做一件事」，比如「每天早上 8 点预热车」。

PARA 1
历史输入在原有 5 轮人机对话基础上，新增纳入最新 5 轮内的非人机对话和事件。轮次规则：统一按单个事件计数，任意角色单次发言计为 1 单位，不再区分人机、人人对话。移除 DTST 事件流变量是讨论中的方案，不等于日志已经删除。

PARA 2
人人对话采集上传正在外审：激活态内容实时上报，降级场景采用 10 句打包或沉默 30 秒触发上报。这是数据采集的流程，不是 Director 推理的输入，也不是已上线功能。

PARA 3
摘要记忆把多轮对话压缩成一句或几句，保留关键事实。做一次摘要的耗时大约 1.7 到 1.8 秒——这是耗时数字，不是模型规模，不能和 1.7B 模型混为一谈。

PARA 4
Context 初筛负责根据当前用户指令和场景，筛选相关的信息（端状态、视觉、对话、记忆、知识），筛选完再交给 Director 推理。初筛准召率大于等于 90%，是量产目标不是当前实测。

PARA 5
用户记忆支持对用户记忆信息管理（属性、情景、行为、偏好），保持记忆实时性和一致性。上下文对话支持历史对话管理（人机对话、人人对话），助于理解当前语境，实现连续自然对话。

PARA 6
事件日志支持对舱内发生事件（语音、触控、物理操作、行为数据）的记录和管理。FaceID 识别通过 DMS/OMS 捕捉驾驶员面部特征，完成身份记录和核验。

PARA 7
静态知识和动态知识的分工：静态知识是对知识库信息有结构和计划性的检索，补足车辆、工具、knowhow 知识；动态知识是基于用户偏好认知，主动实时获取用户可能感兴趣的知识。动态知识是规划中，不是已上线。

PARA 8
记忆召回率大于等于 90%，记忆生成平均耗时小于等于 30 秒。这些是量产目标，不是当前实测成绩。

PARA 9
短期记忆的更新方式：模型流式输出（如短时视觉记忆）、存在主 bot 的 context window 中、其他 Agent 的 context window 中、工程记录的（发生的事情、端状态、任务 list 及任务状态等）。

## se-point-knowledge 明确歌名直接找，线索含糊时才补搜索

PARA 0
**明确歌名直接找，线索含糊时才补搜索。**用户说「播放周杰伦的稻香」，是明确歌名，直接调音乐查询推荐工具；用户说「放点舒服的歌」，是线索含糊，需要 Director 结合记忆和场景推理。

PARA 1
音乐查询推荐工具 music_search 是必选。明确歌名、歌手、专辑，直接找；风格、心情、场景，先推理再找。

PARA 2
媒体控制工具 media_basic_control 负责播放、暂停、切歌、音量这些操作。它和音乐搜索的区别是：搜索找内容，控制管播放。

PARA 3
播客搜索工具 broadcast_search 和 AI 播客生成工具 ai_broadcast_generate 都是可选工具，不是每台车都有。

PARA 4
视频搜索推荐工具 video_search 也是可选工具。

PARA 5
联网信息搜索工具 web_search 是必选。用户问「浙江有多少家 5A 级景区」，Director 调 web_search，工具返回结果后，Director 基于反馈组织回答。

PARA 6
工具返回的内容不能直接播，要经过 Director 判断和改写。没查到、没有权限、暂时异常，不能都被改写成「没有这个事实」。

PARA 7
天气查询工具 weather_search 是可选工具。用户问「今天天气怎么样」，如果端状态里已经有天气信息，就直接用；没有再调工具。

PARA 8
车书查询工具 vehicle_manual_qa 是必选。用户问「这个功能怎么用」，走车书查询。语控暂不支持也不等于车辆根本没有该功能，必要时可以查车书说明手动方法。

PARA 9
静态知识和动态知识：静态知识是对知识库信息有结构和计划性的检索，补足车辆、工具、knowhow 知识；动态知识是基于用户偏好认知，主动实时获取用户可能感兴趣的知识。动态知识是规划中，不是已上线。

## se-scene-knowledge 接机要持续检查，读过一次步骤还不够

PARA 0
**接机要持续检查，读过一次步骤还不够。**持续任务比如「待在行程中持续关注并介绍沿途的风景」，需要自主决定是否和用户对话以及对话的时机。

PARA 1
持续任务的处理示例：结合情景，流式地介绍车辆高频和亮点功能，同时能够打断恢复——能够被用户插入的相关问题或无关问题打断，打断后可恢复；结合情景动态调整交互内容——如果过程中一个功能用户已经操作成功，就不要再死板地长篇幅介绍怎么开启。

PARA 2
打断恢复是独立于 Director 之外的一套工程逻辑。如果在 TTS 播报时用户主动讲话打断了播报，被打断的信息会返回给 Director，由它判断后续是否继续交互。

PARA 3
话题合并：如果用户打断后的新 query 与被打断的话题相关，直接把新旧内容合并成一个完整回答，不再说「刚才被打断了我接着说」。

PARA 4
长内容提炼核心：如果未说完内容较长（三句话以上），续接时只提炼核心信息，其余概括带过。

PARA 5
独立事件主动续接：若剩余内容仅为执行结果确认，直接跳过不补。某功能执行成功这种可以不补说。

PARA 6
动态示例和静态示例的分工：静态示例是种子数据里写好的典型 case，动态示例是根据当前场景实时生成的参考。动态示例只提供参考，不是标准答案。

PARA 7
人格人设稳定性是高阶能力的重要评测维度。跨会话、超长对话后，人格人设、价值观等是否能保持既定内容不漂移。

PARA 8
情绪稳定性也是评测维度：情绪反应随情境变化的合理性与可控性，不因单次刺激剧烈漂移。

PARA 9
共情质量：在识别情绪后，回应的共情是否恰当、有深度、不套路。比如是否先接情绪再给建议，共情是否具体而非模板，是否过度共情造成负担。

## se-knowledge-loading 先选编号，再把具体做法交给 Director

PARA 0
**先选编号，再把具体做法交给 Director。**任务系统里的任务有编号，用户说「取消刚才那个提醒」，Director 要先确认是哪一个任务，再调 task_agent 取消。

PARA 1
task_agent 是必选工具。即时任务、定时任务、条件任务、持续任务，都走 task_agent 注册和管理。

PARA 2
目标跟踪管理工具 goal_list_update 是 Director 内部的，不是外部工具。它管的是当前有哪些目标在排队。

PARA 3
触发器分为离线触发器和在线触发器。在线触发器包括规则触发和模型触发。触发器的下游包括：触发主动服务、静态 advisor 推理、触发定时/条件/长时任务推理。

PARA 4
端侧触发器是本地闭环：条件成立并且仍有效吗，这是真正判断的地方。条件匹配分两级：第一级先判断运行时段，第二级在对应时段内匹配具体触发事件。

PARA 5
同一事件可能命中多条规则，候选任务进入队列后按优先级仲裁。协议预埋了 priority 字段，任务队列按 P0 到 P3 排序，同一优先级先到先跑，P0 安全类任务到来时正在运行的低优体验类任务让路。

PARA 6
命中后进入本地分发台：端侧触发器只判断并发业务事件，不创建卡片；它把哪条任务、哪个子场景、这次看到什么、当前场景信息交给原任务业务，由原业务决定是执行固定动作，还是先询问用户。

PARA 7
需要确认时，原业务发起即时交互卡：正文、按钮、可说词、有效期和回调都要指向这一次具体建议，再交给卡片系统展示和避让。

PARA 8
用户点确认或者本地可见即可说命中按钮，进入确认前的一道关卡。它再核对确认属于当前这张卡、任务仍然开启、车况没有变化；卡片已经消失，用户事后再说一句好的，不能拿来同意旧动作。

PARA 9
本地语音确认只覆盖配置好的表达，比如确认、取消；「为什么要开」「先别开，等雨大一点」这类反问或延后表达不能直接当成确认。

## se-lesson-repair 选错一个明确工具，先用最小范围修复

PARA 0
**选错一个明确工具，先用最小范围修复。**用户说「帮我查一下明天的天气」，结果调了车书查询工具，这时候不能从头再来，要先看能不能补调天气工具，而不是把整个流程推翻。

PARA 1
badcase 排查有固定路径：先还原这次实际走的入口与采信，再检查模型看到的状态、记忆、工具定义和相关示例，接着看动作列表与下游反馈，最后看用户实际听见和车辆实际变化。

PARA 2
链路问题、工具描述问题、上下文问题、模型能力问题，这四类根因的修法完全不一样。

PARA 3
明确单意图工具准确率目标 95%，明确多意图工具准确率目标 92%，模糊指令满意率目标 90%，功能边界/幻觉通过率目标 90%，功能安全目标 95% 且无 0/1 分 case。

PARA 4
强多轮任务闭环率是官方准出目标 92%，但这个数字不能宣传为实际任务成功率 92%。它的统计口径是：任务完成，或因下游原因失败并正确结束话题。

PARA 5
工具错误应答满意率是官方准出目标 95%，统计口径是：合理替代，或自然简洁地告知失败；漏处理、错误总结不通过。

PARA 6
功能边界/幻觉通过率：正确考虑功能有无、控制方式、音区、挡位、参数范围及体验限制并告知。

PARA 7
提示词泄漏/品牌/敏感内容安全：三类分别测试，过滤有效且回应自然。旧成绩不能当现在的现状。

PARA 8
自然、精简与表情：自然与信息不重复分别测试；表情有合适场景覆盖且推理正确。自然目标 92%、精简目标 92%、表情目标 85%。

PARA 9
首 token 时延：从模型请求到首 token；不等于用户可听首音或全部工具完成。PRD 目标 P50 小于等于 500ms，P90 小于等于 800ms。

## GUIDE SE-knowledge-load-detail 跟着接机途中点歌的一轮输入，看知识怎样被选中并用于实际决定

PARA 0
从“接机途中，用户又说放一首歌”开始。知识筛选收到当前点歌要求、最近十轮说话历史、仍在进行的接机目标、最新车况，以及已经加载了哪些知识。这里的近期历史只包含对话内容；正在追踪的目标由目标队列另行提供，不能因为用户临时换话题就把接机抹掉。

PARA 1
现在要补的是处理点歌的办法，接机相关知识是否仍需保留也要同时判断。当前车况优先于历史里的旧描述，所以已经改变的目的地或播放状态不能继续按旧对话决定。图中第一根箭头交出的，是本轮事实和已有知识清单，不是预先选好的工具动作。

PARA 2
“判断要补音乐知识，还是保留原有内容”对照当前问题与已加载内容。点歌需要的处理方法缺失，可以新增音乐知识；接机目标仍有效，相关知识可能继续保留。只有判断它已不适用，才考虑移除，不能把新增一个类别写成清空原来的全部背景。

PARA 3
如果用户只说“按刚才的来”，而历史不足以确定所指，就沿“场景不清楚时，不强行新增知识”这条支路继续。此时允许新增为空，已有清单仍按当前目标保留或移除。这个分支没有直接宣告请求失败，后面 Director 还可以向用户澄清究竟要什么。

PARA 4
“返回新增、移除的知识编号”给出两份操作清单。add_knowledge_ids 指向本轮要补的条目，remove_knowledge_ids 指向不再需要的条目，并附上与当前事实对应的理由。此刻拿到编号，还没有拿到音乐搜索或接机步骤的正文。

PARA 5
接着到“按编号取正文，更新本轮知识内容”，读取新增条目的实际内容，移除指定旧项，再与仍保留的知识组合。音乐知识与接机知识可以共存。检查这根箭头要确认读回了正文，不能只看知识编号出现在日志里就认定模型已经懂得那条方法。

PARA 6
“把具体做法写入本轮 knowledge”将知识放进该方案约定的提示词位置。音乐规则可以说明明确歌名时怎样调用音乐能力，线索不足时先补什么信息。接机知识则保留该场景需要的处理原则，供本轮遇到相关问题时使用。

PARA 7
知识里的示例不是当前车辆的事实。航班、地点、用户身份和播放对象仍需由本轮输入及真实查询确定。加载成功解决了模型有没有拿到方法的问题，当前条件是否齐全、工具是否适用，还要由下一步判断。

PARA 8
到“Director 按当前需求选择下一步”，用户明确说播放王菲的红豆，就根据真实音乐工具能力查找可播资源。知识给方法，当前请求决定播放对象，动作清单 action_list 才把选中的操作交给工具。接机是否继续监控还依赖相应任务机制，知识正文不会自己定时唤起模型。

PARA 9
缺少对象时，沿“先澄清或直接答复，本轮不发工具”询问必要信息；如果已有事实足以解释，也可直接回答。这条路径没有工具执行，自然也不等待工具回执。用户补充后形成新输入，带着更新后的背景再做判断，不能假装知识已替用户选定歌曲。

PARA 10
需要动作的分支来到“工具返回结果，再判断要不要继续”。音乐工具查到并播放资源后，才有实际办理结果；无匹配、版权受限或调用失败，应分别回给 Director。方法写得再完整，也不能代替播放器已经开始播放的证据。

PARA 11
图中的回线把 tool_feedback，也就是工具办理结果，送回下一步决策。补查或澄清有了新的理由就继续，已经满足用户要求则结束这次点歌，同时保留仍有效的接机目标。回线表示依据新结果推进，不表示无条件重复上一条播放指令。

## GUIDE SE-dynamic-example-detail 从维护“结束录音”示例，到一次真实请求采用这条方法

PARA 0
从“保存结束录音纪要的正确处理示例”开始，维护人员要留下用户表达和正确决策分析。这条示例教模型在用户要求结束当前录音时使用 recording_minutes 办理结束，不把“结束纪要”误读成另写一段摘要。保存前先查冲突旧条目，避免同一句话同时对应互相矛盾的方法。

PARA 1
用户表达发生修改后，检索索引也要更新，否则界面上的新文本和实际检索依据可能不一致。二期设计还要求草稿通过审核才能参与运行检索。图中维护节点到下一次请求的线，表示等待真实新请求来验证使用，不表示后台点击保存就已经修好了车上的表现。

PARA 2
“用户下一次提出结束录音的请求”收集完整表达、当前录音状态、身份和所属环境。当前有没有录音、录音是否已经结束，决定稍后是否有可结束的对象；示例只提供处理方法，不能替这轮补一项根本不存在的任务。

PARA 3
随后到“在适用候选中检索相似表达”。二期方案先按车企或渠道、环境和舱内外场景过滤，再从候选池找语义相近的表达。顺序很重要，不能先找到一条相似但来自不相容项目的示例，再因为本项目没有结果就拿它兜底。

PARA 4
目标候选池为空时，沿“没有适用结果，本轮不加动态示例”返回空结果，并保留没有召回的原因。当前指令和原有上下文仍然交给 Director；空召回本身不制造新能力，也不立即判定结束录音失败。

PARA 5
有适用结果时，另一根线进入“把选中的决策分析注入本轮提示词”。scenario_sample 是这份方案装载动态示例的位置，应该实际出现结束录音的方法。后台已有条目、检索列表里出现候选和最终输入包含正文，是连续的三个状态，只有最后一项说明本轮模型真的读到了它。

PARA 6
两路在“Director 根据当前录音状态作决定”汇合。命中示例时，模型可以借鉴它的工具选择方法；没有示例时，仍依据现有指令、上下文和工具定义判断。不能将示例中某个固定任务或参数原样复制成本次录音对象。

PARA 7
当前正在录音且用户要求停止，才继续办理结束；必要信息缺失则先澄清，已经结束则按真实状态回答。这里要检查的是方法有没有被正确应用到当前状态，不仅是模型有没有在输出里写出 recording_minutes 这个名字。

PARA 8
“把结束操作交给真实录音工具”从动作清单接收本次操作及业务所需参数。该工具去办理当前录音的结束，返回成功、失败或缺少条件。模型选择了正确工具，只完成了派发决定，录音设备是否停止还要由执行方说明。

PARA 9
若记录显示本轮之前录音就已结束，应按既有真实状态收口；若调用失败，则保留失败原因和当前状态。不能在工具无回执时只凭示例里写了“结束成功”，就对用户播报已经停录。

PARA 10
“读回结果，按真实进度答复”把工具反馈交回 Director。成功才能按真实进度说明录音已结束；缺条件则补必要信息后继续；失败则解释当前未完成的部分。图中反馈回线支持后续判断，不要求无论成功失败都再调用一次结束。

PARA 11
复测要同时看本轮注入内容、选择的工具、真实录音状态和用户答复。示例未注入要查加载，已经注入仍选错要查决策，选对却未停止要查工具或执行。这样才能确认后台那条改动究竟在哪一步起了作用，而不会用一段听起来正确的话代替修复。

## GUIDE SE-two-stage-evaluation 用“导航和歌词同时看”逐步检验知识改动到底改善了哪一段

PARA 0
从“把导航和歌词同时看定成可验结果”开始。用户要的是导航与歌词同时可见，导航仍有效、音乐仍在播放。测试先记录当前页面、应用状态和完整表达，后续才能判断是否真正完成同一件事；仅调用过分屏工具还不足以判成功。

PARA 1
“选定本次从语音还是模拟输入开始”分成两种入口。实车从用户开口与真实页面开始，模拟测试从完整文字和构造好的背景开始。两者保持同一目标，同时固定车型、软件、模型和知识版本，否则前后结果变化可能来自其他改动。

PARA 2
沿真实环境支路到“实车取得文字、页面与交互状态”。确认识别保留了“同时看”，页面上报也正确描述导航和歌词当前在哪里。若“同时”被漏听，后面得到的任务就已变成另一项请求，不能把之后的模型表现按原目标直接评分。

PARA 3
识别或状态上报失败时，图中另有一根线直接进入结果判定。它用于记录输入失败以及未能继续测试的部分，不需要硬把坏输入送完整条链再假装下游已受测。只有取得真实有效输入，才进入知识和状态核对。

PARA 4
“模拟交入完整请求和已知页面”直接给出导航与歌词同时看、用户身份、当前页面和可用工具。这样可以单独观察知识加载是否正确，以及模型能否根据完整条件组织步骤，减少声学或页面采集问题对这次定位的干扰。

PARA 5
模拟通过的结论只覆盖这个入口之后。它没有验证车内收音、补话、页面上报或真实端侧加载时序，所以不能拿模拟通过替实车通过。两条线会在下一节点汇合，汇合之前的证据范围仍要分别保留。

PARA 6
“核对模型实际拿到了哪份知识和状态”同时检查请求文字、当前页面、分屏方法和本车可用工具。方法在后台存在但未进入这轮提示词，属于知识加载问题；当前页面取错，则是模型面对的事实有误。两种情况都不能仅根据最终没分屏就归为模型不会操作。

PARA 7
执行一项操作后，下一轮还要读到更新的页面。歌词已打开而模型仍看到之前导航页，就可能重复点击或走错步骤。因此本节点不是开头只验一次，它要求把每轮实际输入与当时页面变化持续对齐。

PARA 8
“逐步执行并等待对应动作的真实结果”按采用的方法打开歌词、回桌面再分屏。某一步是否可以继续，需要由真实页面和返回结果支持；操作失败后不能仍按预想界面点击固定位置，连续动作越多，偏离越难定位。

PARA 9
用户中途说“歌词全屏就好”，当前目标已经变化。保留此前真正完成的步骤，重新决定剩余动作，不为了满足最初的测试终态继续强制分屏。这个分支考察模型是否依据新输入推进任务，同时避免重复执行旧步骤。

PARA 10
来到“分别判定过程、最终页面和失败位置”，先确认导航和歌词是否同时可见、导航与音乐是否仍正常，再检查过程中有无重复操作、错误承诺或忽略改口。最终截图成功但过程多次误操作，仍需记录实际问题。

PARA 11
明确失败与证据不足分别保留。没有保存某轮输入或执行回执，就不能推断该步一定正确；相同用例重复运行时，看失败是否落在同一位置，避免只挑一次成功截图。由输入失败直接到来的支路，还要标明后面的知识与决策环节未测。

PARA 12
“修正具体断点，回归相近和冲突场景”按已经确认的位置处理。识别漏词修输入，知识没注入修加载，事实完整仍顺序错误修决策，正确指令未实现修执行。修复后仍从原先声明的测试入口重跑，确认同一个用户目标被完成。

PARA 13
还要覆盖已经处于分屏、应用不可用、用户明确要求全屏以及执行中插话。新知识若只让一条固定例子通过，却让相反需求也被强制分屏，就产生了新的错误。报告保留样本范围、未测部分和项目判定门槛，不从少量成功场景推导全部车型已经稳定。

## GUIDE base 按两条来源和三层知识读这张图
