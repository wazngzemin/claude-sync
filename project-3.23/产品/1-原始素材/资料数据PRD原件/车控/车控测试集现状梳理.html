一、测试集总体规模概览

当前测试集可按简单集与复杂集两大类梳理。简单集已形成较大规模，覆盖车控、媒体、导航、通讯，以及多轮、查询、多参数、多函数、不完整表达等多种测试维度；复杂集目前以车控与媒体导航为主，但整体规模和结构化程度仍有提升空间。

核心结论： 现阶段测试集建设已经具备较好的规模基础，尤其是简单集覆盖面较广；但从体系化建设角度看，仍存在分类粒度不足、结构统计不完整、复杂场景覆盖偏弱等问题，后续更适合往“分层分类 + 结构均衡 + 真实场景增强”的方向继续完善。

四、可补充与优化方向建议

4.1 建议先做的结构化治理动作

  1. 建立统一分类框架
    • 以“领域 → 一级功能 → 二级功能 → 测试维度 → 表达类型 → 数据来源 → 轮次类型”为主线，重构现有测试集标签。
    • 这样可以同时回答“覆盖了什么”“缺了什么”“优先补什么”三个问题。
  1. 统一统计口径
    • 明确各测试集是否允许交叉计数。
    • 区分“基础主集”和“专项增强集”，避免统计时重复累加造成规模判断失真。
  1. 补齐来源维度标签
    • 为每条样本补充来源标签，例如：线上数据、客户回捞、自编、规则扩写、历史沉淀。
    • 复杂集尤其建议统计各来源占比，便于判断真实性与覆盖均衡性。

4.2 简单集优化建议

  1. 强化一级/二级功能分层盘点
    • 不再只看“车控/媒体/导航/通讯”模块级分类，而是下沉到更细粒度功能点，便于发现空白功能与薄弱表达。
  1. 继续补充高频自然说法
    • 优先增强导航、媒体方向。
    • 增补内容可包括：口语化表达、简称、代称、模糊说法、习惯性省略表达、连续说法等。
  1. 补强通讯专项
    • 当前通讯控制规模仅 126，多轮为个位数，建议优先补充：
    • 联系人变体叫法
    • 指代类表达
    • 多轮追问/确认
    • 拨打、发送、查看、回拨等常见链路
  1. 梳理专项集边界
    • 对多参数、多函数、不完整表达、单实体、多轮单实体等专项，建议明确样本定义、准入标准和是否允许与主集重叠。

4.3 复杂集优化建议

  1. 把“复杂多轮”作为下一阶段重点
    • 复杂集不应只停留在单轮复杂表达。
    • 建议新增以下类型：
      • 上下文承接
      • 模糊指代
      • 追补信息
      • 自我纠错/反悔
      • 并列/串联复杂指令
      • 跨域组合指令（如车控 + 媒体、导航 + 通讯）
  1. 增强与真实 AI 汽车交互贴合度
    • 优先从真实车内表达中抽取复杂话术模板，再进行扩写。
    • 避免复杂集过度依赖“人为编写但不自然”的表达。
  1. 明确来源比例并建立配比目标
    • 建议对复杂集定义一个参考配比，例如：线上数据、客户回捞、自编样本分别占多少。
    • 这样更利于后续长期维护与迭代。
  1. 建立复杂度分层
    • 可将复杂集进一步细分为：
      • 复杂单轮
      • 复杂多轮
      • 跨域复杂
      • 异常/边界复杂
    • 这样既方便评测，也更利于发现模型真实短板。

4.4 一个更适合后续推进的建设思路

短期优先：

  • 统一分类口径
  • 盘点一级/二级功能覆盖
  • 补导航、媒体高频说法
  • 补通讯专项规模与多轮

中期重点：

  • 建复杂多轮测试集
  • 统计来源占比
  • 建立专项集边界定义
  • 形成可持续扩充机制

建议总结： 如果把当前测试集建设看成“从有数据走向有体系”的阶段，那么下一步最关键的不是单纯继续加量，而是先把分类体系、统计口径、来源结构、复杂场景策略建立起来。在这个基础上再补数据，后续评测、复盘和迭代效率都会更高。

六、本次整理工作的期望目标-满恕哥哥

本次整理工作的核心目标，不只是补齐现有测试集信息，更希望通过明确分工，推动各模块测试用例持续丰富与结构化沉淀。

目标方向

具体说明

模块责任清晰化

希望每个人重点盯几个模块，持续补充和维护对应模块的测试用例，提升专项建设效率

补充常用、高频与复杂说法

在现有基础上，进一步补充常用说法、高频说法和复杂说法，让测试集更贴近真实用户表达

重点增强复杂车控场景

结合近期 AI 汽车侧反馈，当前车控测试仍偏简单，后续应重点丰富复杂车控用例，尤其是多轮承接、状态切换、恢复类表达等场景

补充真实复杂案例

例如“帮我调整个适合开车的座椅状态”，上一轮进入零重力，下一轮再说“恢复吧”这类带上下文承接的复杂表达，需要重点扩充

建立模块级规模统计

希望后续对每个模块形成相对清晰的量级统计，便于了解覆盖规模、识别短板并安排后续补充优先级

目标重点： 后续测试集建设应从“已有基础覆盖”进一步走向“复杂场景增强 + 模块责任明确 + 量级统计清晰”，尤其要把复杂车控、多轮承接、恢复/反悔/切换等真实驾驶场景表达补起来。

七、结语

整体来看，当前主线与特斯拉车控相关测试集已经具备较好的基础规模，简单集尤其丰富；但从体系化和长期可维护性角度看，仍有明显提升空间。建议后续围绕更细粒度分类、更真实的表达覆盖、更强的复杂多轮能力建设持续推进，从“规模积累”逐步升级到“高质量测试资产建设”。

面向测试用例设计的直接结论

  • 导航退出/结束/关闭/取消是最强主诉之一，且同义表达非常集中，后续导航类用例必须覆盖：退出导航 / 关闭导航 / 结束导航 / 停止导航 / 取消导航 / 导航结束 / 取消路线。
  • 空调开关与空调相关控制强势高频，且存在大量口语近义表达，后续空调类用例必须覆盖：打开/关闭/关掉/开/关/把空调打开/把空调关了/请开空调/请关闭空调/空调打开/空调关闭。
  • 候选确认与多轮承接量级很高，例如 第1个 / 第2个 / 第1条 / 1 / 2 / 都不是 / 不看 / 不查看，说明多轮候选选择、拒绝、重选是线上核心场景。
  • 媒体播放虽然绝对量低于导航和空调，但表达形态更分散，需要覆盖：播放音乐 / 播放歌曲 / 放一首 / 放歌 / 放首歌 / 打开酷狗音乐 / 打开QQ音乐 / 打开网易云音乐 / 打开蓝牙音乐 / 暂停 / 停止播放。
  • 电话类真实需求偏联系人直呼直说，如 打电话给老婆 / 打电话给妈妈，后续通讯类用例应优先使用亲属称谓、常用联系人，而不只用标准姓名。
  • 系统/闲聊/噪声 query 占比不可忽视，如 嗯 / 啊 / 哦 / 唉 / 谢谢 / 没事儿 / 你好，说明测试集要补充无效输入、唤醒后放弃、轻闲聊打断、拒识恢复。
  • 天气类是高频跨域 query，后续测试设计可加入车控流程中穿插天气/闲聊的上下文切换场景，验证是否错误继承车控状态。
  • 存在不少不完整 query，如 导航到 / 导航去 / 空调 / 音乐 / 妈妈，这类需要重点设计澄清、补全、联系人/地点候选交互。
