# 总结

本次会议围绕豆包汽车评测体系展开讨论，涵盖评测目标、评测集构建、评测方法等内容，明确了产品与测试的分工及时间节点，以确保评测集能有效衡量产品在用户基础用车场景下的表现。内容如下：

- **评测体系讨论背景与目标**

        - 团队协作需求：明确团队内部（产品、测试等）的配合方式，做好评测工作，并形成评测 \- 产品优化的良性循环。

    - **评测目标与里程碑**

        - 产品目标：今年产品方向有三个里程碑，分别是使 AI 汽车拥有人的基础能力、认知和推理能力、初步的情商能力。

        - 评测对应：评测工作的方法论一致，但评测集和评测标准会根据三个里程碑进行调整。本次先讨论评测人的基础能力对应的评测集和方法论。

- **产品评测与功能测试定义**

    - **产品评测定义**

        - 视角与目标：站在用户视角，模拟真实使用场景，聚焦用户体验，判断产品能力水位、问题根源及聚类，并提出解决方案。

        - 评测集体量与特点：体量不大，但多样性高，尽量覆盖关心的方面。

    - **功能测试定义**

        - 目标：确认功能是否符合需求文档定义，是否稳定、无过多 bug，功能点是否覆盖完全。

        - 数据体量：相对较大。

    - **两者区别与联系**

        - 区别：目标、数据体量和着重方面不同。

        - 联系：可能使用相同的方法、评测集和维度进行评测。

- **基础评测集构建**

    - **评测集组成**

        - 线上数据来源：对已上线的 Tob 线车企的线上数据进行分析，包括各个懂妹中的话题和高频话术，以及系统中的拒识数据。

        - 构建原理：按照实际场景频率抽取数据集，进行分类标准化和频率统计，以真实反映用户实际体验。

    - **评测集分工建议**

        - 张航建议：基础评测集包含功能覆盖和高频场景两部分，功能覆盖部分由测试负责构建，产品负责典型场景的闭环测试。

        - 各方讨论：认为需要一个覆盖度高的集来衡量用户日常基础场景，产品和测试可共同构建，同时产品还需维护一套从场景出发的评测集。

- **具体场景分析**

    - **POI 搜索场景**

        - 场景闭环：POI 搜索需经历多个步骤，包括用户意图触发、列表调整、辅助决策等，不同类型的 POI 搜索决策因素不同。

        - 分析框架：提供了 POI 搜索场景的分析框架和维度，但具体内容需进一步补充。

    - **其他场景**

        - 导航场景：导航是多轮交互场景，需通过不同阶段和行为完成需求。

        - 音乐播放场景：也是线上高频的复合型场景。

        - 提新车复合场景：包含提车阶段、上路阶段和持续使用阶段的意图、行为和话术。

- **评测方法 \- 检查点**

    - **评测方法演变**

        - 准确率阶段：最初用准确率作为评测指标，但无法体现模型能力。

        - 能力维度阶段：在不同域设计不同能力维度打分，但存在主观域评分难、维度打分主观、难以处理多轮任务等问题。

        - 检查点阶段：根据具体 case 生成检查点，拟合模型能力，每个 case 有针对性的检查点，直观可解释，能处理多轮任务。

    - **检查点设计与应用**

        - 设计原理：根据能力建模和具体场景设计检查点，每个 case 的检查点不同。

        - 应用示例：以秘书岗位面试为例，说明通过设计场景和检查点来评测豆包的能力。

        - 评分方式：检查点通过与否代表豆包在该能力上的表现，分为基础分和惊喜分。

    - **检查点相关问题讨论**

        - 检查点设计差异：不同人设计的检查点可能不同，标注成本较高。

        - 张航建议：现阶段先由产品梳理出覆盖用户最基础用车场景的核心场景和检查点，进行小批量快速试错，后续再用模型打分实现自动化。

- **后续工作计划**

    - **时间节点**
