## 如何阅读

主图只有一张。按语音入口、端侧快路/云端分流、Context、Planner、工具、真实执行、结果回流阅读。条件任务、视觉感知、卡片交互围绕同一条业务链连接。

HTML 可搜索工具或节点，点击小模块查看上下游、相关问题和指标；支持逐题记录证据并导出 Markdown。它包含 27 项 SP 工具定义、88 个模块考题、47 项建议指标。指标不是团队线上成绩，也不是未经商议的生产门槛。

## 与原图对应的几个关键校正

| 原图范围 | v11 的处理 |
|---|---|
| 1–2 语音 | 拆开唤醒、音频、ASR、说话人、判停、Query 封装和打断。 |
| 3–4、11–12 信号/缓存 | 作为持续更新的事实来源，分别连接端规则、云条件和 Context；不是每条 Query 必须串行经过的四个模型。 |
| 5–8 本地 FC/白名单/执行 | 明确保留不绕云 Planner 的本地闭环；标出云超时、端候选与迟到重复执行问题。 |
| 9–10 拒识/意图 | 依 Director PRD 展示条件分流；拒识、拒识模型超时、云整体超时不是同一种处理。 |
| 13–15 配置/解析/触发 | 分开规则配置、条件构建、订阅、观察、条件求值、抑制和回调；触发成功不等于动作执行成功。 |
| 16–18 Advisor/Goal | 旧 Goal List + 动态 Advisor 有独立实体链；新 Task Service 用紫虚线标为演进方案。 |
| 19–21 Director/Context | Planner 与 Director 为同一角色；用户、建议、工具反馈进入对应的同一决策闭环。 |
| 22 工具 | 按 27 项实际 SP 名称展开输入、领域处理、结果与边界，接回统一反馈入口。 |
| 23 任务中心 | UI 展示和用户操作不是生命周期编排；取消运行与删除记录不混为一件事，能力按版本核对。 |
| 24 端触发 | 信号订阅、当前快照、规则求值、频控/冲突、本地执行及结果回流相连。具体运行时和端云冲突契约不补造。 |
| 25 视觉 | 按需 VQA、默认 AlwaysOn、带 task_id 的动态观察分为三条真实不同的输入/输出路径。 |
| 26–29 交互/输出 | 播报、卡片和真实动作不是强行串成“TTS→数字人→车控”；另外展开可见即可说和确认后的业务复核。 |
| 30 拒识日志 | 拒识内容可作为背景事件，但不能直接当成用户授权执行的指令。 |

## 证据边界

原始来源和各模块自测定义在 `knowledge.mjs` 中，也可从 HTML 的“来源”入口查看。当前读取的 PRD、技术设计、本地 SP 快照不等于全部车型生产部署证明。27 是该 SP 快照中去重后的定义数；运行时数量需要从车型 × 环境 × 版本的实际注册表核验。

未核验的统一校验、权限、取消、反馈关联、状态回读及 Task 迁移部署均保留方案/待核边界。没有把会议摘要作为已确认上线结论。

## 学习深度

不要求把全部模型、数据库或 SDK 都学到可实现再评估下一份工作。主责 Planner/Trigger 应能依据真实 Trace 定位根因、提出改法、定义评测/回归并验收；相邻模块至少说清输入输出、能力边界与失败归属。用一个真实目标的成功、恢复、时延与成本证明 AI 产品能力，而不只是罗列模型或工具数量。
