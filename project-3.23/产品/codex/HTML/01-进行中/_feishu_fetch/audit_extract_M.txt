# M 输入管理｜把并发消息排成可交给 Director 的一轮
SVG_MISS 0: []
## INTRO
前两章已经把一句有效话语从入口状态、端云候选和最终采信中收口。走到输入管理，系统面对的是另一个并发问题：用户新话、主动服务建议、工具刚返回的结果、播报被打断的事件可能先后到达——谁先进入推理、谁先等待、旧候选还能不能取消、已经发出的车控会不会被新话重复触发。
输入管理（Input Manager）位于 Adapter 与 Director 之间：把这些并发、乱序、来源不同的消息组织成一次可以交给 Director 的输入。它不调用模型，也不判断用户最终意图；Director（旧称 Planner）才负责理解要做什么、规划动作并读回结果。
工具怎样执行见工具章；多人首 token 合并与打断恢复细节见插话章；一句闲聊是否有效归属入口章。本章只接收已经进入准入范围的消息，并保留输入状态、排队边界、身份归属和播放许可。
## LESSONS
### 先分清四类输入，再核正在算、正在说、已在做
到达的消息分成 query、advice、feedback、event。Adapter 标准化并补齐优先级与合并属性。工具结果是已经发生的事实，不是用户又说了一遍；打断 event 只报告交互变化，不自动理解成取消导航。
准入前分开核对：模型是否仍在生成、声音是否真正起播、工具是否已对外下发。ChatRuntimeState 用 IDLE / PROCESSING / RESPONDING 描述整段对话占用情况。只看首字会误判，可能把已发动作整体重跑。
空闲才直接接入下一条；后台提醒或长时任务不自动锁前台。独立推送、不进 Director 播报的 AIGC 本期不纳入。新链路 request_id 非空，旧渠道空值不混进新流程。
### 用户新话优先；已发 Tool 只能作中断上下文
忙时先问旧候选能不能取消：Tool call 尚未放行，可合并重算；一旦允许下发，旧 Input 不可再作为可执行输入重放，只能作中断上下文。这是技术方案的执行重放边界。
用户 query 是 P0，按打断处理；普通建议和事件是 P1，忙时等待。高优抢占结构预留、本期不启用，不能把普通主动服务写成已有抢占权。
取消时只停关联候选与声音，保留已播、未播和已下发事实；旧 feedback 仍按原调用身份接收。车控不会因插话自动回滚。P1 在计算中排队还是合并，产品稿与 TECH 有冲突处标待核，不擅自统一。
### 组成有效身份，计算准入与发布许可分开
新一轮生成 DirectorExecutionID（即 TaskRoundID），推理、播放与工具各有关联标识。旧结果不能冒充新轮输出；完整同步工具批次收齐后，仍要重新经 Input Manager 取得下一次计算准入。
计算准入不等于对外发布：播放结束且候选仍有效才发布。新输入使过时候选失效，已下发工具的真实结果继续保存。首期同步 Tool 的下一轮模型调用必须再准入；独立异步 callback 尚未接入。
普通输入排队时保持任务归属；同 advisor 多条建议只留最新有效；客户端接管结束对应 Input，不影响其他等待项。
### 播放以客户端实况为准；恢复不重放已发动作
用 STARTED / PROGRESS / FINISHED / ABORTED 等客户端事件更新播放状态，不能只靠云端“已下发 TTS”推断。静默轮、纯工具轮、合成失败各有结束路径，漏收结束信号会堵死后续提醒。
等不到终态时按配置解锁等待，但不把解锁记成播完；迟到事件仍更新原请求。
故障恢复先读已发动作，不重放已经发出的请求。异常先保存真实进度再释放等待——恢复不能重做已发生的副作用。
## CLOSING
到这里，并发消息已经被排成可交给 Context / Director 的一轮，且已发动作不会被新话偷偷重做。下一章（Context）按本轮问题准备背景；不要在输入管理章把“取得计算准入”写成“Director 已经理解并办完”。
## SAMPLE NODES
### M1 | 接住四类输入，保留来处
LINES: query：用户明确要做什么 | advice：主动服务或任务建议 | feedback：工具已返回的真实结果 | event：打断、接管等交互变化
用户先让豆包找昨天游泳馆附近的餐厅，系统正在整理候选；这时主驾又说“第二家”，一条低电量主动建议等待触发，POI 查询返回三家餐厅，客户端上报上一轮播报被打断。这些消息都进入同一条对话，但来路不同。

M1 把它们分成四类：query 是用户明确要做什么；advice 是主动服务或任务建议；feedback 是工具已经返回的真实结果；event 是打断、接管、状态变化等已经发生的交互事件。Adapter 先把不同来源统一成标准输入，补齐来源身份、优先级和合并属性；它不调用模型，也不判断用户意图。

工具结果不能被当成用户又说了一遍；event 只报告交互变化，本身不携带新任务。四类共用准入入口，不等于拥有相同抢话权。新链路要求 request_id 非空，旧渠道空值不能混进新流程。
### M2 | 核对正在算、正在说、已在做
LINES: 模型是否仍在生成候选 | 声音是否已经实际播放 | 工具是否已经对外下发 | 三种状态不能互相替代
准入前要核对系统此刻处于什么状态，而不是只看有没有出现第一个可见字。把三种“还没结束”分开：模型仍在生成还是已经交出结果，声音是否真正从车内播放器播出，工具是否已经发出对外副作用。

这三类事实分别来自模型执行、客户端播放回执和工具执行回执，来源不同，不能互相顶替。只盯着“首字到了”会误判：可能文本已生成但声音还没出声，也可能工具动作已下发而话术尚未播报；这时若把旧请求整体重跑，就可能重复开窗、重复拨号或重复提交订单。

ChatRuntimeState 用 IDLE / PROCESSING / RESPONDING 描述整段对话在干什么：空闲、Director 已启动但还没有给用户首 Token、或已开始输出/客户端仍在播报。
### M5 | 谁插入：用户优先，普通消息排队
LINES: P0 用户输入优先处理 | P1 普通建议与事件等待 | 高优 advice 结构预留、本期未启用 | 同轮反馈汇集后交回原执行
真实用户新话属于 P0（最高优先级），按打断流程处理；普通建议和普通事件属于 P1，忙时等待。同一模型轮次收集完整的工具反馈批次单独接入。

结构上预留了高优 advice 位置，但当前没有实际高优建议类型，不能把普通主动服务写成已经具备抢占权。技术方案非目标也写明：高优任务抢占本期不启用。

主交互会议口径：主动服务优先级低于用户 query，需要等用户 query 处理完后再进入处理窗口。
### M9 | 发计算许可，再看输出许可
LINES: 完整工具批次可取得计算准入 | 播放结束且候选有效才对外发布 | 新输入使过时候选失效 | 已下发工具的真实结果继续保存
同步工具批次收齐，并不意味着可以绕过输入管理立即开始任意输出。下一次模型调用仍要取得续轮准入，保留原目标及完整工具事实。

计算准入和对外发布是两道许可：完整工具批次可取得计算准入；播放结束且候选仍有效，才对外发布。新输入会使过时候选失效，但已下发工具的真实结果继续保存。

首期继续使用同步 Tool 执行方式，但其下一次模型调用必须重新经过 Input Manager 准入；独立异步 callback / 持久结果回流当前尚未接入。
### M12 | 故障恢复先防重复副作用
LINES: 状态异常按限定范围重试 | 无法确认时停止相应发布 | 恢复不重放已经发出的请求 | 无音频轮有自己的结束方式
故障恢复时先读取已发动作。状态异常按限定范围重试；无法确认时停止相应发布，而不是把旧 Tool call 再发一遍。

恢复不重放已经发出的请求——这与 M4/M6 的副作用边界一致。已经开过的空调、已经提交的导航，不能因为云端重连就被当作从未发生而再做一次。

无音频轮、纯工具轮各自有结束条件，恢复逻辑要按原轮类型处理，不能统一当成“再播一遍”。
