按图逐步读懂
T01 · 接住未来或持续的诉求
Director 接到未来/持续诉求；任务类入口透传原话与对象；现在关加热走即时车控；创建受理不等于未来执行。
用户说“十分钟后关主驾座椅加热”，当前这一轮只能把安排交出去，不能立刻关闭加热。Director 通过 task_agent 把任务文本交给任务系统。这个入口也承接条件任务、循环任务和长时跟进任务；“现在关闭加热”则直接走即时工具执行。创建任务成功只代表安排被接住。入口名称须按渠道版本核对，技术方案写 task_manage，宣讲使用 task_agent。
T13 · 渠道路由：谁拥有长期任务
Seres：自建 Task Service；saic-dna：Extour Goal；不是所有渠道都已迁移；同一任务不能双系统同时接管。
Task Service OnePager 明确自建系统用于 Seres；动态 Advisor OnePager 保留 saic-dna 的 Extour Goal 入口。它们都能在未来把建议交回 Director，但谁保存目标、谁取消、创建卡如何出现并不一样。“动态 Advisor 融入 Task”不能扩大成全车型已经统一替换。评审和排障先确认渠道与版本，再沿对应分支走，不能把新旧系统串成一条或让同一任务由两边重复执行。
T14 · 上汽：提交并创建 Extour Goal
add_goal 携带目标和上下文；Extour 管目标与触发；creating 只表示请求受理；静态 Advisor 仍另行运行。
上汽分支由 AIDV 封装用户原话、对话上下文和车辆身份，调用 Extour 的 add_goal。Extour 保存长期目标并负责后续条件；creating 只是创建请求受理，尚不能确认安排已生效。创建成功、创建失败和未来条件触发分别有回调，不能用一个“返回成功”节点包住。静态 Advisor 的主动服务依旧独立，不会因为这里被称为动态 Advisor 就由同一接口管理。
T02 · 弄清要办哪一件事
Seres：先查询现有 TaskView；Spec Builder 决定增改删查；Task Agent 只做请求入口；修改/取消必须定位原任务。
任务系统先结合已有任务，把用户这次请求分成新增、修改、取消或查询。“改成二十分钟后”必须定位原任务再重校验；“取消刚才那个提醒”走 T11 管理分支；“我还有什么提醒”走 T12 读取 TaskView，只返回状态。Director 负责交办，不直接维护生命周期；规格解释与事实保存归 Task Service。不能让查询或取消误走创建分支，生成一条新任务。
T03 · 条件能看见，动作能执行吗
对象、观察条件、动作、结束策略；检查实际信号/工具/开关/配额；不能观察的目标须拒绝或澄清；信息齐备才建立可靠安排。
系统先核对等待条件是否能被实际感知、动作是否在该车型能力范围内，以及用户究竟指谁。比如“宝宝发烧时告诉我”不能只凭视觉任务承诺做到；“到那里提醒我”还缺地点。只有必要信息明确、能力可承接，才登记等待。原文规定合理性检查，具体失败提示要按项目验收。视觉并发三条与任务中心总数限制不是同一个门槛。
T15 · 上汽：创建成功直出 Goal 卡
创建前铺垫话术可播报；creating/成功禁播，只同步状态；成功Goal卡直达；失败回Planner；创建卡≠触发≠实际执行。
上汽7/1交互方案允许创建前的铺垫话术，但 creating 与 create_success 都不播报“已创建”，成功由 Goal 卡直接通知，不重新进入 Planner；失败才经推荐链路回 Planner 告知原因。禁播工具反馈只同步系统状态，不代表用户听过成功承诺。卡片出现只能证明展示安排，条件是否生效与未来动作是否完成还要分别核验。该稿为改造设计，不能仅凭协议完整认定端到端已准出。
T05 · 先保存 Task，再登记触发
Task 保存目标与结束策略；Run 保存某次执行；Event 留状态变化事实；保存成功≠规则注册成功。
赛力斯任务技术方案先保存 Task 事实，再调用 Trigger 注册规则；并非登记全部完成后才保存。Task 是长期目标，Run 是一次执行，Event 是状态变化，TaskView 是查询视图。例如周期按摩会有多次 Run。保存成功却注册失败必须可查询、可解释，不能仅凭数据库有任务或卡片已出现就告诉用户安排正常生效。后续补偿与重试细节仍需按实际实现核验。
T04 · 登记什么时候再叫醒任务
按时间/条件/周期/视觉注册；Trigger Adapter 转换规则；保存任务与回调关联；注册失败不可宣告正常等待。
任务系统根据任务类型向触发能力登记规则：到指定时刻、车辆状态满足条件，或视觉描述符合观察目标。它同时保存规则与用户任务的对应关系。例如“后排宝宝哭了告诉我”需要明确后排对象和观察目标。登记失败时不能把任务展示成可正常等待；不同项目的定时承接方应分别核对。规则更新、停止及失败补偿需与任务状态一致。
T16 · 上汽：触发建议经客户端回流
触发先发Recommend执行卡；首跳不播报，二次上行回Director；7/1方案：无操作默认执行；多条建议当时latest wins，不排队。
上汽7/1方案中，条件命中先下发 Recommend 执行卡，第一跳不播报；点击携带推荐 ID 二次上行，文档也写无操作默认执行，但具体等待时机须由交互定版。多 Trigger 当时仍用单槽缓存，后到 advice 可能覆盖前一条，不承诺排队或合并。身份、缓存过期和迟到回调必须校验；60秒请求缓存与10分钟推荐缓存仅属对应 OnePager 版本，不能当全局值。
T06 · 等待下一次触发
Seres Task 等条件，不占 Director；周期任务每次产生新 Run；技术 waiting 指等待激活；UI v0.4 waiting 却指创建中。
等待阶段由任务系统和触发能力持续托管，而不是让 Director 一直推理。比如“每小时提醒我活动”需要保存后续安排；“帮我介绍沿途风景”需要在后续进展出现时再次推进。车辆下电、账号退出、任务过期等是否终止，必须看对应任务规则，不能默认所有任务都跨行程恢复。状态名在任务中心和早期技术方案有差异，必须先做业务映射。
T07 · 触发来了，任务还有效吗
恢复任务，拒绝关闭/重复回调；Trigger 已完成原条件判断；额外执行约束才查 Context；无人等情况可跳过本轮。
触发器回调说明“条件到达”，任务系统仍须找到对应任务并检查当前有效性。例如用户已经取消加热关闭任务，晚到的触发通知不能重新把任务执行起来。技术方案区分整条 Task 与单次 Run：每次实际执行单独记录，循环任务的一轮失败也不能自动等同于整条任务结束。Task 不重复匹配原条件；只有额外执行前约束才决定执行或跳过。
T17 · 上汽：消费、关闭和 done 分开
consumed设计：进入Planner≠完成；close关闭目标；finish仅同步done；update入口与消费回报路径待补；Goal状态与Task状态需分渠道映射。
consumed 的设计含义是建议送入 Planner，不是用户同意或车辆执行成功；根架构材料尚缺回报接口路径，不能画成已验通。close 会关闭 Extour Goal 并同步 done，goal/finish 只改客户端 done，update入口与协议仍有缺口。上汽查询接口使用 creating/pending/running/done，任务中心又用 running/paused；字段 enabled 与示例 enable 也不一致，应先定状态和协议映射，避免 UI 结束而后台继续触发。
T08 · 把本次建议交回 Director
先绑定 Task/Run 与推荐 ID；Recommend→Frontier→客户端；客户端回流→输入管理；Director 再规划本轮动作。
通用任务被激活后，Task Service 先把 recommend_id 与 Task/Run 关联，再经 Recommend、Frontier 让客户端回流，输入管理安排进入 Director。这样既有消息链路不需要客户端额外透传内部任务编号，服务端也能把结果记回正确一轮。advice 不是用户新说的话、更不是动作完成。GUI 生态任务可由 Provider 推进，不强行每一步都回 Director。
T09 · 拿到真实执行结果再记账
Flow 汇总真实 Agent/Tool 结果；独立 Result Hook 更新 Task/Run；成功/失败/跳过分别记录；TTS播完不等于任务成功。
Director 决定本轮动作，下游工具执行后返回结果，任务系统据此更新这一次执行。例如车控接口受理了请求，却尚未确认座椅加热状态，应保留待反馈，不能标完成。技术方案要求结果回写可追踪；产品验收要同时看用户听到了什么、卡片显示什么、车端状态实际变成了什么。独立结果 Hook 不应只依赖尽力而为的异步 afterFlow。
T18 · 终止后截断迟到回调与旧目标
取消/下电/过期按各类策略关闭；停规则、更新有效视觉目标；直接GUI在途停止仍待验证；迟到回调不应再推进旧任务；已执行动作不会因删卡自动撤回。
已支持的普通任务取消或到达结束策略后，要关闭任务、清理 Trigger 并更新有效视觉目标，不只是删卡。已关闭视觉任务的迟到结果只记录，并补发全量目标列表纠偏；已发生车控不能靠状态修改撤回。直接创建的 GUI 任务尚未被普通取消覆盖，其在途停止、正式多用户及并发重试仍待验证，不能统一宣告已取消执行。AI总关清动态任务有设置PRD；语音禁用对静态子目标保留/删除仍须统一。
T11 · 用户修改、取消或暂停
修改：更新规格与原规则；取消：关目标、清规则、停后续；直接GUI不在普通取消覆盖内；一期删除/预设暂停；周期暂停二期；GUI多用户/重试/用户取消待验。
用户说“取消刚才那个提醒”或点击删除，普通任务链路会关闭目标、清理规则并停止后续触发；已发生车控不会因删卡自动撤销。当前普通取消尚未覆盖直接创建的 GUI 任务，不能承诺所有生态在途执行都能停止。GUI 正式多用户、并发重试和用户取消仍待验证。任务中心一期支持删除我的任务和 AI 服务、暂停场景预设，循环定时/条件任务暂停列为二期；服务支持修改不等于全部 UI 已落地。
T10 · 继续等，还是结束整条任务
单次完成→关闭整条目标；周期/持续→按策略继续等待；失败/跳过是否续跑单独定义；结束同步规则清理与视图。
一次执行结束后，任务系统按结束策略决定关闭整条任务还是继续等待。比如“每小时按摩”本轮因座位无人被跳过，不能未经规则确认就删除整个周期任务。旧技术方案列出完成、取消、过期、失败和车辆下电等结束原因；各项目的跨下电保留与失败续跑仍需按当前规则核验。Run done 不是 TTS 播完，通知失败也不回滚已保存事实。
T12 · TaskView查询与任务中心展示
语音查询只回状态，不代表执行完成；我的任务 / AI服务 / 场景预设；我的任务46：定时20+条件20+长时6；云更新push；开机/登录拉取；UI状态须与后台真实事实映射。
语音查询读取 TaskView，把现有状态返回原调用，不新建 Run，也不把查到任务当执行完成。任务中心 v0.4 分我的任务、AI 服务、场景预设，我的任务只展示 running/paused；waiting 指创建中，与早期等待状态须映射。云更新推送、上电拉取；退登清长时跟进和条件任务，不扩成清全部。我的任务上限46（定时20+条件20+长时6），不套用AI服务/预设；AI Bar两条任务时的边界未定义。
