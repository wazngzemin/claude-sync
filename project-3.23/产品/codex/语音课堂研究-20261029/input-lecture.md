# 从一句声音到可以办理的正式请求

用户说“带我去昨天那家游泳馆”，停了一下，又补充“附近的餐厅”。用户最终要去的是餐厅；游泳馆只是寻找餐厅的位置参照。系统既要完整接住补充，也要利用中间的时间提前工作。提前准备、保留修正、按最终意思执行，是语音入口需要同时做到的三件事。

**热词先告诉识别服务哪些名称值得关注，减少专有词被听错的机会。**

当用户说联系人姓名、具体泳馆名称或页面按钮时，仅凭普通词汇识别容易写错。热词是业务提供给识别服务的候选词，帮助它在声音相近的情况下更有依据地选择文字；它不是用户已经选中的对象，也不是把任何相近发音强行改成该词。

OnePager 列出通讯录及当前人员名称、导航目的地与途经点、播放内容、可见即可说页面词、车型专有词等来源，还使用最近对话和当前位置辅助识别。不同来源要先按本项目权限与数据规则提供给对应维护链路；云端维护适用热词，在识别建联及后续上行信息中读取、注入。不能把“使用人名热词”直接写成默认上传所有人的全部通讯录。

页面上的词先由页面业务登记和更新，识别服务再拿适用词表增强听准。匹配页面动作还在另一条链路上：听准“开始导航”不证明找到了当前按钮，找到了按钮也不证明操作已经成功。切页后应更新或注销失效映射，不能拿旧页面对象执行新话。

产品验证要串起原始来源、词表维护、当次识别请求是否真正注入，以及 final 是否改善。配置台保存成功、列表里有这个词，都不能单独证明本次识别已经用了它；OnePager 也明确热词不保证百分之百生效。本次热词技术方案链接无权读取，评测表只取回部分区域，因此不编造当前命中阈值或全量修复成绩。

**一遍 ASR 边听边给文字，让系统尽早得到信息，但文字仍可能变化。**

ASR 是语音识别，负责把声音转成文字。车端持续采集声音，在本文采用的云端识别链路中把声音分片上送识别服务；识别服务陆续把过程文字返回车端。声音已经在上传，不代表这句话已经作为正式业务请求提交。

系统可能先拿到“带我去”，再拿到“带我去昨天那家游泳馆”。这类 partial 是过程结果，后续声音可能让文字增加或修正。它可以供允许的显示、拒识判断和提前准备使用，不能据此直接启动导航。界面是否立即显示过程文字，还要结合激活状态、拒识和车型交互规则，不能把未激活车内聊天全部上屏。

这里要分开检验三件事：原始声音是否清楚，处理后声音是否保留了关键内容，识别文字是否正确。餐厅名字错了，先对应同一段音频看最早在哪一步变错，不能一看到模型回答错就认定 Planner 推理弱。

**Soft VAD 在短停顿时发起预请求，让允许的准备与继续收音重叠进行。**

VAD 是语音活动检测，这里帮助判断用户是否继续出声、停顿持续多久。它与识别同时工作，不是 ASR 完成后才启动。用户在“游泳馆”后停下来，只证明此刻没有继续出声，不能证明后面没有补充。

按较新的语音 OnePager，短停顿达到 300 毫秒，车端可以触发 Soft VAD 预请求。车端拿当前识别文字，通过网络发给承接汽车业务的 AIDV 云端服务。推荐技术方案用 POST /aidv/v1/pre_query；POST 就是提交一份待处理信息。用户不用再次说话，也不需要点击提交。

这份消息包含当前文字 content，query_type=2 标记“这是预请求”，round_id 标记本次输入内部轮次，request_id 关联本次输入，sound_zone 保留说话音区；chat_id 或所需历史帮助服务找到对应对话背景。字段的产品意义是让云端认出：这是哪一次说话、哪份文字、什么阶段，可以做哪些处理。

“预请求”不是猜测用户下一句，也不是导航先执行一遍。它是针对当前已有文字，提前运行该项目支持的前置计算。300 毫秒是触发准备的时刻，不代表准备已经全部完成。

**提前做拒识和 Context，分别解决该不该响应、目前有哪些可靠背景。**

拒识判断这句话是否应由助手处理。副驾对主驾说“昨天那个泳馆不错”，并不必然是在要求豆包办事；把车内聊天当命令，会让用户感到被打扰。这里的拒识不是安全拒绝，也不能因为无权限控制某个设备，就说用户没有在对助手说话。

Context 是统一组织和提供背景的服务。它按需要从相应来源取得近期交互、车况、任务、世界信息和可合法使用的记忆。车辆上报状态提供当前导航和位置，对话历史提供刚才的候选与用户选择，记忆系统提供权限范围内的相关经历。各来源处理自己的范围与质量，Context 组织后供 Planner 判断。

Context 不创造缺失事实。只有“昨天游过泳”，不能改写成“昨天去过某某泳馆”；没有地址仍然缺地址。常用背景可以在 Planner 之前提供，缺少的信息再由 Planner 明确查询。OnePager 概括允许预跑 Context，但未给出每次语音预请求全量运行哪些来源及每项失效规则，因此不能宣称预请求已经把所有背景或昨天地点查完。

前置计算结果需要按模块、对话、输入及轮次关联保存。正式请求才能找到对应准备。技术方案描述了云端临时缓存；这不等于长期用户记忆，也不是让车端先下载全部结果再上传。预请求不进入正式对话历史，不播正式答案，不下发真正车控或导航动作。

**用户继续补话时，用更新后的整句再准备，不让半句话造成不可接受的后果。**

用户第一次停顿约 400 毫秒后补上“附近的餐厅”，识别仍在进行，文字更新为“带我去昨天那家游泳馆附近的餐厅”。第一次准备没有执行导航，现在只需要重新核对准备方向，不需要让用户撤销一次错误导航。

补话后再次出现短停顿，满足规则时可以再发预请求。再发不是第一次失败后的重试，而是同一次输入有了新版本。发送的是更新后的当前句子，不是把“附近的餐厅”孤零零交给下游自行猜它接在哪里。

**request_id 认出同一次输入，round_id 认出其中哪一份准备。**

用 A 表示这次输入：前半句预请求为 A/1，补完后的预请求为 A/2，正式请求可以为 A/3。request_id 是共同的 A，round_id 是递增的 1、2、3。“本次输入编号”在这段说明里主要指输入关联编号，不是另造一个字段。

不同服务可能还有自己的 ASR 编号和调用编号，排查要核对映射。chat_id 对应对话背景，同一对话中用户先说餐厅、再问天气，并不代表是同一次输入。这里的 round_id 也不是 Planner 调完工具后再次判断的轮数。

**Hard VAD 按较长停顿让音频段收尾，300 和 600 毫秒来自同一个计时起点。**

按 OnePager 的配置，最后一个字结束后，停顿从 0 开始。到 300 毫秒触发准备，再经过 300 毫秒，总停顿达到 600 毫秒，达到该版 Hard VAD 音频分段门槛。不是先等 300，再额外等完整 600，总共等 900。

第一次停顿只有约 400 毫秒，用户就继续说话，没有达到这一版示例的 600 毫秒收尾点。补话后的新停顿从新起点计时，不能把前后的沉默相加。

语义判断还要处理“我想去……”这类声音停了、意思却明显未完的表达。旧待评审 PRD 写过 300/500/1000 毫秒和语义延长，新 OnePager 写 300/600；更早的动态 VAD 也有另一套短时与拼接方案。它们属于演进资料，不能拼成一套所有车型都在运行的配置。实际门控顺序与最长等待仍需对应版本确认。

**二遍 ASR 重识别已经采集的这一段录音，返回本次识别的定稿文字。**

一遍识别需要边听边尽快返回，后面的声音可能还没有到。音频分段后，二遍识别使用这段已有录音重新处理，可能修正过程文字的错字，再给出 final。用户不需要重说一次，麦克风也不是重录第二遍。

final 只表示这次识别定稿，不保证每个字都正确，不表示已知道昨天的泳馆，也不是模型最后的答案。达到 600 毫秒也不保证此刻 final 已经回来，识别收尾和网络传递仍有时间。判停耗时、识别结束耗时与最终用户首声必须分开统计。

**正式请求只复用符合条件的准备，更新后的目标不能沿用过时结果。**

如果 A/2 已按“泳馆附近的餐厅”准备，A/3 的最终文字也完全相同，对应模块支持且结果可用，就按规则继续使用相应准备。如果前一轮仍是“去泳馆”，最终文字增加“附近的餐厅”，则按最终文字重算对应前置处理。

同一 request_id 只证明属于同一次输入，不证明内容没变。规则比较前一轮实际文字，不是在全部旧结果里找一句意思相近的。重算不是用户重说，也不意味着录音和整条系统全部从头做；它是修正不再符合复用条件的准备。

产品验收既要看该复用时有没有减少重复计算，也要看不该复用时有没有正确重算。高复用率不能代替正确率；用户补话导致重算，有时正是系统正确接住完整意思的表现。

**正式提交交清楚最终文字与来历，后续业务仍要补齐事实和验证执行。**

车端提交定稿文字、说话音区和相关编号，云端关联可以复用的前置结果。音区表示声音来源，不直接证明身份或动作对象。主驾说“开副驾座椅加热”，说话来源是主驾，实际设备目标是副驾，两者都要保留。

后面的 Planner 要依据最终表达和背景继续判断。昨天泳馆的地址未知，就查询或澄清；餐厅有多个，就处理真实候选；地点确定以后，才发导航动作。查询结果回来再判断、再执行，不能在一次并发动作列表里猜地址先导航。

语音入口把话交清楚，不等于整件事做成。工具受理、导航界面出现、正确目的地真实启动、结果播到用户，是不同阶段。最终验收要回到用户有没有去对地方。
