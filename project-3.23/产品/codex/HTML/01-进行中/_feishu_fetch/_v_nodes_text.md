
### V13 先确认语音能不能用
1. 主驾要说「带我去昨天那家游泳馆」，还可能补「附近的餐厅」。在任何一个字被听成文字之前，先过可用性：麦克风权限、AI 开关，以及通话、手机助手、OTA、CarPlay 等互斥。
2. 用户感知是喊了没反应，或提示去设置；系统决定是这一轮进不进识别。电话占线时再优化拒识也接不了——失败点在入口。
3. 未授权给设置入口；互斥提示随车型配置，不把所有失败播成「网络不好」。使用中撤权等未写全的分支标缺口。
4. 没过本节点，后面声学、ASR、VAD 都不应被讲成已经发生。验收「喊了没反应」先举证权限与互斥。

### V1 麦克风收音：保留这一次是谁在说
1. 入口放行后，麦克风采原声，同时把正在播放的音乐、导航或助手播报作为参考音交给声学；本轮挂上说话音区与 request_id。
2. 用户感知：可以说了，车在听。系统决定：留下可追溯的原声、参考音、音区与编号。
3. OnePager：云端识别约 200 毫秒一帧上送——这是分片节奏，不是 200 毫秒内答完，更不是声音已正式交办。
4. 这里不下导航、不查昨天地址、不做最终拒识。已放行仍听不清，带原声与参考音往声学与识别追。

### V14 声学前端：压低噪声和自己的回声
1. 麦克风里是混合声：用户话、风噪胎噪、后排聊天、扬声器回声。前端降噪并用参考音做回声消除，整理后的声音同时送给一遍 ASR 与 VAD。
2. 越安静不等于越好——「昨天那家」被削掉，后面 Context 再强也找不到日期锚点。
3. 豆包播报时用户插话，参考音不对或处理过重，常表现为误打断或吞字，根因往往早于拒识。
4. 电子设备外放抑制、车外唤醒抑制若供应商暂不支持，标缺口。交出去的仍是声音，写成字是下一步。

### V15 确认声音来自哪一座，不等于操控哪一座
1. 来源座位与操控对象拆开：主驾说开副驾加热，来源主驾、目标副驾。本例保留主驾来源，是为了后面选对人的上下文。
2. 音区不是身份，也不自动打开私人记忆；FaceID、声纹、记忆授权归后章。
3. 音区关闭要提示；靠背放低不能把主驾判成后排——那是定位与配置问题，不是模型不聪明。

### V16 热词增强：把当前人名、地点和按钮交 ASR
1. 热词是业务提供的候选，帮识别在声音相近时更有依据地选字；不是用户已点中的对象，也不是强行改写任意近音。
2. 人名、POI、媒体、页面词、车控词由云端维护，在 ASR 建联与上行注入才生效。
3. 验收串四步：来源是否按权限进入维护、词表是否更新、当次是否注入、final 是否改善。配置台有词≠本次用上了。
4. 听准「开始导航」≠找到按钮≠操作成功；切页后旧按钮词要注销。OnePager：热词不保证百分百生效。

### V17 先约定 ASR 来源和上屏规则
1. 区分在线/离线各自产字，以及本次业务采用哪一份。允许先显示离线过程字、再被在线 final 刷新；无网用离线。
2. 上屏与采信分开：看见「去游泳馆」只说明某份字到达，不授予车控，也不决定端云谁办理。
3. 未激活全时态不应把闲聊全部流式上屏。

### V2 一遍 ASR：边听边写出文字
1. 一遍 ASR 边听边出字：可能先有「带我去」，再有完整前半句，再被「附近的餐厅」改写。与 VAD 并行，不是先识别完再计时。
2. 用户感知是字幕在跳；系统决定是尽早给出可准备的字。「昨天」是哪一天，交 Context / Director。
3. 声音已上传 ≠ 正式请求已提交。地域与语境可增强同音区分，增强的是文字候选，不是导航决策。
4. 验收分原声、处理后、识别字；餐厅名错了沿同一段音频找最早变错点。

### V3 过程文字：能准备，还没定稿
1. 过程字叫 partial：可供激活后上屏、流式拒识、Soft 预请求——但不是执行授权。补「附近的餐厅」会改目标。
2. 用户以为字幕出来就等于懂了。当场拆开：过程字 ≠ 定稿 ≠ 正式 Query ≠ 车已执行。
3. 流式拒识可提前停 TTS，最终仍可能判拒识并恢复；细节归插话章。本章只留：停声不是取消任务。
4. 「字幕对了却办错」先问用的是 partial 还是 final。

### V18 识别失败：不要把临时文字偷偷当指令
1. 无有效声音、识别超时或二遍空结果，沿失败线说明原因，不静默，不拿半截字控车。
2. 前面闪过的「去游泳馆」过程字，失败后不能当默认指令；空 final 不能猜成「想关窗」。
3. 无音频、空结果、超时分账。失败出口不绕过定稿进导航，不把预请求结果当成已办成。
4. 验收必须能拿出原声、处理后声音、过程字与时间戳。

### V4 VAD：观察说话和停顿
1. VAD 看人声与停顿时长，不必等 ASR 写完整句。图上 ASR∥VAD：左轨出字，右轨看停了多久、是否又开口。
2. 游泳馆后思考怎么补餐厅，右轨先动；开口补话后两轨一起更新。
3. VAD 不解析地址、不代替最终拒识、不在停顿瞬间下工具。
4. 把并行讲清，Soft/Hard 同起点计时才站得住；串行口误会把 300 与 600 加成 900。

### V5 Soft VAD 短停顿：先做准备（300 ms）
1. 停在「游泳馆」后，只证明此刻没出声，不证明不会补餐厅。同一次停顿约 300 毫秒可发预请求，继续收音；可多次触发，不结束 ASR。
2. 只停约 400 毫秒又开口，不会走到 Hard。补话后新停顿重新计时。
3. 用户感知：短停时车没抢跑，还能补话。系统决定：启动允许的准备并继续听。
4. 图上 Soft 之后仍回到继续听，箭头不进执行层。

### V6 预请求只提前准备，不让车先行动
1. 预请求针对当前文字预跑已支持的无状态任务（拒识、Context）。专用入口与正式对话入口分开，避免刷出多轮正式历史。
2. 三不：不进正式历史、不播答案、不下导航/车控。300 毫秒是触发时刻，不代表准备做完。
3. request_id 认同一次输入，round_id 认第几份准备；补话后再发，送更新后的整句。
4. 把预请求说成「先导航再改」，直接拉回三不。路径与字段以项目协议为准。

### V7 Hard VAD：本段收尾（600 ms）
1. 同起点继续计时到约 600 毫秒：本段收音结束，等待二遍定稿。收尾 ≠ 定稿已回 ≠ 已播报 ≠ 车已执行。
2. 到 600 毫秒也不保证 final 已返回；判停、识别结束、用户首声要分账统计。
3. 补话后新停顿重新计时，前后沉默不能相加。
4. 「说完很久没反应」先分：没收尾、定稿未回、下游未接。

### V8 二遍 ASR：给出本段最终文字
1. 二遍 ASR 用刚采完的同一段录音做整段再识别，给出 final；不是用户重说，也不是麦克风重录。
2. 若收尾前已补「附近的餐厅」，定稿应保住完整目标——这是硬检查。
3. final 不保证字字正确，不表示已解析昨天地址，不是导航已启动。
4. 无音频、空结果、超时分账，禁止拿残缺「关……」默认关窗。

### V9 正式文字能沿用上一份准备吗
1. 复用门槛同时满足：同一 request_id；正式文字与上一轮预请求全文相同；模块已支持复用。缺一不可。
2. 大意接近不算；少了「附近的餐厅」不算；换了 request_id 的另一次说话不算。
3. 匹配则把仍适用结果带到正式提交；不匹配走重算线。
4. 高复用率≠好体验——用户常补话时复用率下降是正确副产品。

### V10 语义判停：这句话意思说全了吗
1. 语义判停处理声停意未完，例如「帮我把……」。结合表达与计时，按车型配置决定继续等还是收尾。
2. 旧 500/1000 与语义延长 vs OnePager 300/600 并列【待核】，不叠成全车型固定多等一秒。
3. 它仍不进入工具执行。

### V11 不匹配：按最终文字重新准备
1. 上一轮仍是「去游泳馆」，最终变成「……附近的餐厅」，按完整餐厅诉求重算已支持的拒识与 Context。
2. 重算的是尚未执行的准备——预请求本就不能开导航，故不存在撤回已发导航。
3. 图无「大意接近就部分复用」。图上回到重算节点的线=重算准备，不是回滚车控。
4. 两分支都到正式提交，差别只在用了哪一轮准备。

### V12 把最终输入交给正式业务链路
1. 交出定稿文字、来源音区、request_id/round_id、仍适用的预准备。入口还要做最终拒识与端云采信；需要时再查记忆、找餐厅。
2. 用户感知：话说完了，等豆包接。系统决定：完整诉求已离开语音层。音区不直接决定车控目标。
3. 交接清单：定稿有没有餐厅、音区对不对、编号能否对上预准备、有没有把预请求误当已执行。
4. 记忆授权与自进化不在本清单——音区≠身份记忆，自进化不在本步。
5. 验收分开「音频已上传 / 正式请求已提交 / 车辆已执行」。
