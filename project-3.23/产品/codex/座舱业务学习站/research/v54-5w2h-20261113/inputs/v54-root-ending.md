## 19. 三分钟讲给别人听：全链路口述稿

### 配图说明

新图用 7 个节点：用户开口 → 声音成为文字 → 接完整句话 → 接话与端云采信 → 背景交给 Planner → 工具返回真实结果 → 展示、播报与回写。节点之间分别标“录音”“过程文字”“最终请求”“本轮背景”“工具调用”“结果”；最后一节点用回线连到背景，标“供下一轮使用”。青色是处理，紫色是背景，橙色是判断，灰色是用户可见结果。拒识和失败画成出口，不能把所有输入都画向成功。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 用同一条找餐厅的请求，说明每一环收到什么、决定什么、交出什么。 |
| Why 为什么要 | 会背模块名不代表能解释为什么补话后不该导航到游泳馆。 |
| Who 讲给谁 | 讲给不了解内部系统的产品、设计和项目同学，第一次出现术语就解释。 |
| When 什么时候用 | 入职讲解、需求评审或复盘某一条办错的请求时。 |
| Where 从哪讲起 | 从用户开口讲到实际结果，记忆和 Launcher 放在它们发生作用的位置。 |
| How 怎样讲清楚 | 每次交接说出已经知道什么、还不知道什么、所以接下来找谁。 |
| How much 讲到多细 | 主口述约三分钟，数字与版本留在查阅区，追问时再展开。 |

### 第二步：七个问题逐条讲透

**1. What：复述和背概念有什么区别？**

| 容易混的说法 | 能讲清的版本 |
|---|---|
| “ASR、VAD、DT 一路处理” | “识别先写出文字，判停决定是否收尾，Planner 再根据完整请求安排工具。” |
| “模型有记忆，所以懂昨天那家” | “它要收到或检索到可归属给这个用户的昨天地点；没有证据就仍然不知道。” |
| “发了导航指令，所以成功” | “工具和车机反馈导航真正启动，才知道请求办到了哪一步。” |

**2. Why：讲不清会造成什么后果？**

评审只说“模型没懂”，声学、语音、记忆和导航同学都不知道该查哪条证据。把问题改成“最终文字完整，但 Context 没带昨天那次地点，检索又没找到”，团队才能知道下一步该查谁的数据。这里给的是沟通方法，不是假设已经找到实际根因。

**3. Who：复述时怎么交代责任？**

每句都尽量有主语：“车端上传音频”“识别服务返回文字”“Planner 调记忆工具”“导航工具返回结果”。不要把所有动作都说成“豆包自动完成”。如果资料没有写哪个服务负责，直接说责任方待确认，不补一个听起来合理的团队名字。

**4. When：什么时候展开分支？**

先把找餐厅主线讲完，再回答“若用户停得更久”“若豆包正在播报”“若没联网”“若记忆没有内容”。分支用原来的请求变式来解释，避免讲到一半换成多个互不相关的例子。

**5. Where：记忆和模型放在哪儿讲？**

讲到“昨天那家还不知道”才解释记忆，讲到“这句话谁来办”才解释固定说法、端侧 FC 和云端 Planner。热词只能帮助写对专有名字，不能补出昨天去哪；AI Launcher 提供另一种发起请求的入口，也不是语音必须经过的关卡。以上业务职责分别见单元 4、9、11～16。

**6. How：对方听完怎么检查自己有没有讲懂？**

按这个顺序追问自己：为什么前半句不能直接执行？为什么停播不等于接单？为什么两个 1.7B 不能当一个模型？为什么识别全对还可能找错？为什么写入记忆不等于车机已经同步？为什么“已为你导航”不能代替执行结果？如果只能回答“有模型负责”，就回对应单元查输入、判断与输出。

**7. How much：怎么控制时间？**

下面口述稿按约三分钟设计，实际时长取决于语速，未做录音计时。只保留理解主链必需的名字。不要把历史测试百分比和版本号塞入口述；它们是查证时的依据，不是理解顺序。

### 第三步：放回主例——可直接照读的口述稿

> 用户说：“带我去昨天那家游泳馆”，停了一下，又补上“附近的餐厅”。他真正要去的是餐厅，游泳馆只是搜索附近的参照。
>
> 车先得把声音收清楚，降低噪声和自己的播报回声，再记住声音来自哪个座位。识别服务把声音逐步写成文字。热词会帮助听准人名地名，但用户没说泳馆名字，所以热词不能告诉我们“昨天那家”在哪里。
>
> 用户还在说的时候，文字会变。系统一边识别，一边观察停顿；短暂停顿可以先做允许的准备，不能先开始导航。他补上“附近的餐厅”以后，要检查之前准备是否还适用。等这一段收尾，识别给出最终文字。
>
> 接下来有两个不同的问题：这句话是不是对豆包说的，以及本地还是云端来办。流式拒识主要帮助播报及时让出说话机会，最终拒识再判断完整请求是否该接。固定说法、端侧车控模型和云端处理可能产生不同候选，由仲裁决定采用哪份，不能两边都执行。两个都叫 1.7B 的能力，一个偏交互判定，一个偏车控指令解析，职责不同。30B 的视觉能力和端侧简化 DT 的评估，也不能当作云端当前模型的名字。
>
> Planner，也叫 Director，收到完整请求和这一轮的背景。背景里可能有近期对话、摘要、车况和允许使用的记忆，但不保证已经有泳馆地址。它先查证昨天是哪家；找不到，就需要补信息，不能猜。拿到地点后再搜索附近餐厅，工具返回真实列表，车机展示并播报。
>
> 用户接着说“第二个”，系统要能对应刚才那份列表。选中餐厅之后是否启动导航，要看执行反馈。端侧办理过什么、展示了什么、实际成功还是失败，还要留给后续对话使用。
>
> 如果用户之前和乘客聊过泳馆，那是人人对话；只有在资料规定的采集、上报和使用范围内，才能成为背景，不能直接当命令。家和公司等长期地址还有专门同步方案，不能把记住了等同于车机已经更新。整条链路的关键，是每一环都把真实输入与结果交给下一环。

### 第四步：讲给别人听（30 秒）

> 先听清、接完整，再决定接不接、哪边办。Planner 根据完整请求和可用背景补齐地点，调用工具找餐厅；车机展示或执行后，把真实结果留给下一轮。声音、文字、候选指令、实际结果是不同阶段，排查时沿这条交接线找最早出错的地方。

### 查阅区

本单元是单元 0～18 的教学复述，不新增上线结论、阈值或模型版本。事实来源沿用对应单元台账；三分钟、30 秒是表达目标而非产品时延，见 V19-F01。

## 20. 术语速查表

### 配图说明

新图 5 个节点：声音 → 文字 → 交互与采信判断 → 请求和背景 → 动作与反馈。把术语贴到对应节点：ASR 在声音到文字的箭头上；VAD 在声音旁；拒识与仲裁在判断框；Context 和 DT 在请求与背景框；FC、tool feedback、TTS 与回写在动作与反馈框。青色表示处理，灰色表示数据，紫色表示背景；每个词只按主要用途定位，不能用颜色暗示所有车型部署相同。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 这是把研发常用词翻译成业务交接动作的索引。 |
| Why 为什么要 | 同样叫模型、缓存或记忆，实际可能负责完全不同的事。 |
| Who 谁使用 | 产品经理用它找负责环节，与研发对齐输入输出。 |
| When 什么时候查 | 遇到缩写、同名概念，或者文档把能力名和模型名写在一起时。 |
| Where 怎么定位 | 看“在哪一步”和“在哪里算”，前者是职责，后者是部署。 |
| How 怎样读 | 先看一句话定义，再核对输入到输出，最后回对应单元看规则。 |
| How much 有什么边界 | 此表不补充资料没有确定的模型基座、超时或保存期限。 |

### 第二步：七个问题逐条讲透

**1. What：词表不是模型清单。**

| 容易混的维度 | 应回答什么 | 例子 |
|---|---|---|
| 业务职责 | 解决什么问题 | FC 把意图变成可调用的结构化指令 |
| 基座模型 | 用哪套模型实现 | Qwen3 是模型家族名，不能代替“负责什么” |
| 参数规模 | 模型有多大 | 1.7B、30B 表达规模，不是上线状态 |
| 部署位置 | 在哪里运行 | 端侧与云端需按车型和版本核对 |

**2. Why：词混了会怎样？** 误把“拒识”理解成“本地做不了”，就可能把一条应交云端处理的请求丢掉；误把“上报”理解成“发命令”，就可能把乘客聊天办成操作。词的差异直接改变用户结果，不能只背中文译名。

**3. Who：谁来确认词的含义？** 优先看当前项目的 PRD（产品需求文档）与接口说明。会议里有人换用另一种叫法，要把“输入什么、输出什么”说出来再确认；两个名字相近不等于同一份服务。

**4. When：什么时候需要连同版本一起说？** 涉及模型基座、判停阈值、采信规则、历史保留窗口和跨端同步时，需要一起交代车型及资料时间。纯定义可以通用，具体规则不能跨版本搬用。

**5. Where：为什么同时写步骤与部署？** “在拒识阶段”说明业务职责，“在车上”说明运行地点。同一能力在不同项目里可能部署不同，因此不能画出一个云端框就推断所有车型都一样。

**6. How：排查顺序是什么？** 先查词对应的输入和输出，再查适用单元，再查资料与状态，最后确认本次运行实际采用哪一版。找不到就标待确认，不靠缩写猜全称或实现。

**7. How much：这张表能替代多少正文？** 它只用于快速找回概念，不能替代失败分支与例外规则。表里写“按项目”表示位置或实现存在版本差异，不表示没有职责分工。
