00 · HOW TO READ

先分清三个平面，再看流程

这是本文为方便评审使用的解释框架，不是飞书原文中的正式模块命名。

展示与操作面

任务中心 / VUI

让用户看见任务、启停任务、点击或语音确认。它只收集操作，不替业务判断真实状态。

配置与判断面

配置平台 / 端云 Trigger

定义规则模板，接收任务有效状态和各种信号，判断是否达到触发条件。

执行与回传面

端侧 Task Manager / 云端 Planner / 车控

完成二次推理或本地闭环，执行真实动作，再把结果和状态回传。

一句话：用户打开任务中心开关，只代表“允许这条任务以后生效”；只有当 Trigger 后续观察到业务条件满足，任务才会真正触发。
范围隔离：新《Task 任务管理设计》明确“静态 Advisor（预设）不属于本方案”。因此本文没有把动态 Task Service 的目标架构直接套在四条系统预设任务上，只引用任务中心通用契约来说明 task_id、event_id 与状态回调语义。

  • 消息盒子优先级低于用户 Query，不得中断正在进行的主交互。

  • 语音交互需要比固定词条更强的泛化能力。
  • 临时选择能力与卡片生命周期绑定。

技术评审必须拍板

  • 动态选择工具是否用FC，如何定义选项和失败收口。
  • 断网时语音是否降级为本地固定词条。
06 · PRIORITY & LIFECYCLE

卡片之后还有两个共性模块：仲裁与生命周期

徐洋评审里争论最久的不是UI，而是多来源同时抢卡片/语音时谁先谁后，以及卡消失后云端临时能力怎么销毁。

体验要求清楚 · 承载模块待定

1. 已确认的优先级原则

用户正在发起的 Query 高于普通主动服务和消息盒子。低优先级业务不应粗暴打断用户对话。

系统安全类是否作为 P0 是会上建议，不是已定完整优先级表。

2. 当时的能力现状

端侧被认为没有排队能力；云端更接近“新任务打断旧任务”。因此不能只在 PRD 写“排队”就当作已能实现。

技术上可能用排队、延迟调度或“非实时抢占+恢复”，会上未拍板。

3. 候选承载点

晓伟的任务管理模块被提为统一优先级与任务恢复的候选承载点，但需专项评审确认是否包含系统预设和外部消息。

不能因为会上提到它，就把它画成当前已实现的中央队列。

为什么不能说“配置平台现在已经端云统一”？
9月1日会议 02:08:14—02:10:22 明确：云端在端状态齐全后可以配置一部分规则；端侧部分仍依赖端侧开发；端云同步尚未完整建立；TTS、二次确认尚未纳入配置。长期目标才是配置平台统一生成、同步和运行。
为什么不能说“所有卡片都走可见即可说”？
端侧 Trigger 卡需要本地可见即可说；云端 Static Advisor 的语音确认要进 Planner / Director，为了避免语义和NLG降级，反而要避免被普通可见即可说抢走；消息盒子手点在本地，泛化语音则拟用动态选择工具。所以客户端必须根据卡片来源路由。
为什么不能说“消息盒子卡已经走 Planner”？
会议确认的只是“外部卡需要语音泛化，手点后要同步 Planner 上下文”。卡片信息是通过事件、Context、模拟Query还是新链路上云，以及最终是否用FC，都留到技术评审收口。
为什么不能说“无卡、无TTS就是端侧任务”？
卡片/TTS决定的是交互方式，端云归属由实时性、信号位置、规则确定性、模型/上下文依赖和安全要求共同决定。儿童锁无卡无TTS，但会议仍出现“云端直接判断”表述；后视镜虽然很像端侧候选，会议并未定部署侧。
