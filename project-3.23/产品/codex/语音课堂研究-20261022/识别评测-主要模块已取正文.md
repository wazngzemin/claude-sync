## 拒识测试方案

### 背景与目的

拒识模型主要用于判断出用户的query是对人机对话还是人人对话。

需要构建一个符合实际用户对话的场景集，来评判拒识模型的实际效果。

以及构造一个能AI自动闭环的方案

### AI 自动化闭环：拒识大模型的实践

#### 范式革命：从「人工战役」到「AI 自动闭环」

**拒识大模型 **的核心目标是 **去掉唤醒词**，重构语音交互入口 ，实现 **全时免唤醒 **的自然交互体验，让用户真正做到「开口即用」。



在传统研发模式下，每一次模型迭代都像组织一场复杂的人工战役 —— 从数据采集、清洗、标注，到模型训练、评测、灰度上线，任何环节出现人力瓶颈，全链路都会陷入停滞等待状态。



而 AI 自动化闭环模式则通过大模型技术接管原本依赖人工的关键环节，实现全流程的自主运转与高效迭代。

#### 整体方案：AI自动化闭环

构建 \&\#34;数据采集 \- 智能标注 \- 模型训练 \- 自动评测 \- 上线监控\&\#34; 的自动化闭环，实现模型的持续优化与迭代。其中 **AI 标注员、AI 评测裁判、AI质检员** 是AI自动化的核心，每一项能力都是由 大模型 替代一个原本完全由人完成的关键动作。

#### 核心能力

##### AI 标注员

- **人工痛点**：标注复杂度高，标注需同时结合 对话上下文、座舱功能清单、用户意图 综合判断，才能符合 CoT（思维链）标注标准，对标注人员的业务理解能力与逻辑推理能力要求极高，人工标注一条要读上下文、理解场景，人工标注的产出约为300条/人/日。

    - 标注合格的案例：

- **AI标注 的核心目标**：让大模型读懂语义并分类，输出标签 \+ 思考过程，产出可训练的数据集。

<div class="callout">

让 LLM 当标注员的\&\#34;主力\&\#34;，人当复核员。

</div>

##### AI 评测官

- **人工痛点**：拒识场景的评测不仅是简单的对错判断，更需要复杂的语义理解

    1. 效率瓶颈 ：人工需逐条分析对话上下文、判断拒识合理性、撰写评测报告，一轮评测耗时长达数天，严重拖慢迭代节奏 。

    2. 质量不稳定 ：人工判断易受主观因素影响，不同评测人员对同一案例的判定可能存在差异，导致评测标准难以统一。



- **AI裁判 的核心目标：**用能力更强的 大模型 替代人工完成评测全流程

    - 大模型充当裁判，对每条评测案例进行深度分析，输出详细判因和自动归类问题，并基于评测数据总结共性问题，为后续模型训练提供优化方向

<div class="callout">

把 “评测官” 这件事交给一个更大的 大模型。

</div>

##### AI 质检员

- **人工痛点**：线上流量巨大，但bad case占比低且隐蔽性强。人工抽样排查、用户反馈的模式，存在 发现效率极低、严重滞后 的核心问题，无法及时捕捉真实场景中的模型缺陷。



- **AI质检 的核心目标：**构建一个能自动运转的【**拒识大模型的数据飞轮**】

    - 大模型充当质检员，自动分析线上回流数据，精准识别模型判错的bad case，喂回标注环节，驱动下一轮模型迭代，构建完整的 数据闭环 机制，让模型在使用中持续迭代升级。



- **实现机制**：在不影响主链路正常运行的前提下，构建 **影子模式 **并行链路 ，实现 \&\#34;响应 \- 发现 \- 优化\&\#34; 的协同运转：

    - **主链路** ：专注于在线实时响应，确保用户交互的流畅性与稳定性

    - **影子链路** ：负责问题发现与沉淀，通过旁路分析捕捉真实场景中的各类问题

    - **数据飞轮** ：将影子链路发现的问题转化为可训练资产，驱动模型持续优化

### 评测标准

用户说话后ASR会有一遍和二遍，所以最终要以最终的文字上屏为准。

#### 词准

#### 字准

#### 句准

分为严格句准和放宽。因为对于大模型来说，一些文字只要错的不是很离谱，模型是能够理解的。

举例：

1. 帮我导航去亦庄通泰二期3号楼。（严格是“二”/“3”；若出“2/三”算放宽通过，不会影响模型的理解）

2. 打开风量2档。（严格是“档”；若出“挡”算放宽通过，不会影响模型的理解）

3. 打开风量2档。如果最终上屏的是“打开风量 2 档”（有空格）。算通过，不会影响模型的理解

## VLM视觉感知测试方案

### 背景与目的

开发技术用于支撑具体需求的实现场景，所以基于项目开发里程碑计划，制定对应的测试规划。

**端状态上报的一些特殊逻辑**

1. 车辆仅首次上电上报时会将该车辆在数据库vehicle\_resource\_info表中的数据进行清空，重新将新的数据进行落库，这时created\_at时间应该都是大于等于该时间，有小于该时间的数据，说明上报是有问题的。

首次上报还要注意一些状态灯的信息，一些车辆的协议是只有该灯开启状态才会有相关的信息，默认是关闭状             态，那这种情况首次上报的时候是需要将这些默认状态进行上报的

2. 首次上电上报后后面的数据都是进行更新上报

##### 常见的问题

1. 上报数据字段错误

```JSON
05-12 08:40:06.118 29194 31117 I AiCar   : NovaReportEventImpl on receive report increment： {"resource_value":[{"event_time":"2026-05-12T07:50:24.910+08:00","id":"adsd_0022","subresource":[{"mode":"警示"}]}],"report_cycle_flag":"202605120750_0d73e877c24b478db17a6b2d5d980462","report_type":"Update"}
```

需求要求字段是switch，上传的字段是mode， 服务端在入库的时候会进行字段校验不通过的不会进行落库

2. 上报的字段值不对导致落库失败

当取值范围是on/off，客户端上传开启/关闭，服务端进行了值校验，校验不通过就不会落库

3. 上传信息与实践不一致

该车辆无第三排座椅，上传的数据有该数据

```JSON
05-13 08:02:13.703   521  4116 I AiCar   : NovaReportEventImpl on receive report increment： {"resource_value":[{"event_time":"2026-05-13T08:00:16.540+08:00","id":"vehicle_control_0049","subresource":[{"position":"车顶","states":"0"},{"position":"车顶前","states":"0"},{"position":"车顶后","states":"0"},{"position":"主驾","states":"0"},{"position":"副驾","states":"0"},{"position":"二排左","states":"0"},{"position":"二排右","states":"0"},{"position":"三排左","states":"0"},{"position":"三排右","states":"0"}]}],"report_cycle_flag":"202605130800_8d466b94a647403e8ffa0c78f455ac0c","report_type":"Update"} 
```

4. 上传信息重复

上传有多个右后的数据，这样的数据仍可以正常落库，但是后面的数据会将前面的数据覆盖（比如：右后最终落库数据是\{\&\#34;position\&\#34;:\&\#34;右后\&\#34;,\&\#34;switch\&\#34;:\&\#34;off\&\#34;\}）

```JSON
05-13 08:26:56.254   521  6112 I AiCar   : NovaReportEventImpl on receive report increment： {"resource_value":[{"event_time":"2026-05-13T08:00:16.536+08:00","id":"vehicle_control_0027","subresource":[{"degree":"100","position":"主驾","switch":"on"},{"degree":"12","position":"副驾","switch":"on"},{"degree":"40","position":"右后","switch":"on"},{"degree":"37","position":"右后","switch":"on"},{"degree":"43","position":"右后","switch":"on"},{"position":"右后","switch":"off"},{"degree":"87","position":"右后","switch":"on"},{"position":"左后","switch":"off"}]}],"report_cycle_flag":"202605130800_8d466b94a647403e8ffa0c78f455ac0c","report_type":"Update"}
```

## Context测试方法

### 背景

Context广义上泛指模型推理的上下文，为模型推理补充除了prompt以外的重要背景信息。测试团队主要保证context查询各个阶段提供的各种数据的准确性

### 基本功能介绍

Context广义上泛指模型推理的上下文，为模型推理补充除了prompt以外的重要背景信息。

我们所说的Context模块狭义上指的是：一个信息处理、组织模块，负责将处理后的端状态、记忆、世界信息、情景描述等信息注入Director SP的变量中去。

- 信息存储

    - 车端状态信号信息

    - 用户记忆信息

    - 事件信息

    - vlm信息

    - 知识库

- 信息生成

    - 短期记忆

    - 长期语义记忆

    - 长期情景记忆

- 查询功能

    - 端状态信息查询

    - 用户记忆信息查询

    - 天气信息查询

    - 日历查询

    - 知识库查询

## Director测试方案

**核心摘要：** Director（Planner）作为AI座舱系统的任务规划引擎，负责将用户复杂需求拆解为可执行任务序列。本方案覆盖功能（6项）、安全（4项）、交互（4项）共14个评估维度，测试策略包括人工评测（4分制打分）与自动化回归两条主线。

### 测试目标与范围

#### 测试对象

Director（又称 Planner）是 AI 座舱系统核心任务规划模块，自研任务规划引擎，依托链式逻辑推理能力完成时序任务拆解与条件任务链生成，将复杂用户需求转化为可落地执行的标准化任务序列。。

**核心能力：**

- 需求解析：识别用户需求复杂度等级（单步/多步/复合场景）

- 任务规划：工具调用、条件设计、时序拆解、优先级排序

- 动态知识检索：根据当前场景动态加载/卸载专业知识

### 已知高频问题与重点关注

<div class="callout">

基于历史测试数据分析，以下是Director当前高频问题类型，测试时需重点关注：

</div>

**推理类问题：**

- 过度推理：用户未明确要求时擅自执行额外操作

- 违背用户意图：用户说\&\#34;直接导航\&\#34;仍在反复询问

- 人物方位识别错误：座位与人员匹配错乱

- 幻觉：凭空编造端状态信息（温度、灯光状态等）

**工具调用类问题：**

- 说做不一致：话术提到要做但未调用工具

- 工具选错：车书知识问题误用web\_search

- 参数改写错误：人名、位置等关键参数改写不准确

- 无依赖任务串行调用：本可并行的工具调用串行执行

**话术类问题：**

- 铺垫和总结话术过度重复

- 暴露专业名词（\&\#34;车辆状态信息\&\#34;\&\#34;舱内视觉\&\#34;）

- 主动推荐场景使用对话式回复（\&\#34;好的帮你xxx\&\#34;）

- 历史对话干扰当前轮次

**Context类问题：**

- 未结合端状态（如空调已开仍重复拆解）

- 未结合舱内视觉（如已有人但报无人）

- 过度参考记忆（将偏好音量强加于当前请求）

## Advisor测试方法

### 背景与目的

主动服务（Advisor）是指车辆在无需用户主动发问的情况下，由系统根据车内外信号的变化，主动发起思考并给出关怀、推荐等服务。

触发器链路：客户端持续采集端信号（端状态、VLM、埋点、电子围栏、日期时间、云侧服务等），当某个信号的快照命中预先配置的场景条件（生效范围 \+ 条件 \+ 执行内容）后，触发器会调用对应的 Advisor 进行主动推理，推理结果再通过 callback 回调下发到端上

模拟器链路：为了方便，因此另外提供\&\#34;模拟器\&\#34;工具：通过接口直接注入 Context 最终响应（世界信息、端状态、情景描述、用户记忆、行程数据），无需经过 Context 初筛/精筛/后处理，即可在无实车的情况下驱动 Advisor 推理并回调，用于日常功能测试。

### 触发器真实链路测试

用于验证\&\#34;端信号变化 → 场景条件命中 → 触发 Advisor → 推理 → callback\&\#34;的完整闭环。

#### 测试方法

1. 在车辆上制造对应的端信号变化（例如上车/下车、调整座椅、打开车窗等），或通过模拟信号方式修改对应信号值，使其命中已配置的场景条件。

2. 观察是否触发了预期的 Advisor（情感 / 舒适），并跟踪推理结果与 callback 回调是否正常。

3. 通过日志（logid）\+ 接口 / 数据库确认每一段链路的输入输出是否正确。

注：任何结果以链路日志与落库数据为准，日志未见触发或数据未正常落库即测试不通过。

此处使用触发器：

https://console\.volcengine\.com/aidv\-admin

### 模拟器链路测试

模拟Context 接口最终响应，无需经过 Context 初筛、精筛、后处理，直接驱动 Advisor 推理与回调。适用于测试车而非真实用户车；一个车可对应多个配置，但只有一个生效，配置与乘客 / context 关联。

#### 测试方法

模拟器链路的标准测试步骤：

1. 创建模拟器（客户端）并配置数据组（注入世界信息 / 端状态 / 情景描述 / 用户记忆 / 行程数据）。

2. 开始模拟，触发主动推荐（指定要触发的 advisor 及 attention）。

3. 由模拟器驱动 Advisor 推理，推理结果通过 callback 回调（callback\_from = simulator）。

4. 查询推荐历史 histories，确认结果正确落库。

### Face ID测试

#### 功能测试

- 正向流程：Face ID的识别、注册流程、Face ID持久化、query泛化

- 异常或边界：Face ID未识别、无人、未授权等场景的引导提示、异常打断

#### 提槽测试

验证在各种泛化说法下，提槽的准确率

### Face ID后台数据查询

#### 快速验证Face ID是否注册成功

查询乘客表（vehicle\_user）。

需准备vehicle\_id、account\_id、姓名。如能查到记录，且account\_id正确，则代表注册成功。查询语句如下：

```SQL
SELECT * FROM `vehicle_user` WHERE vehicle_id = "ppetest20260520123"  AND name = "小明" AND deleted_at IS NULL  ORDER BY id DESC;
```

> 
> 

```SQL
SELECT * FROM vehicle_resource_info_history where vehicle_id = "ppetest20260520123" AND resource_id = "vehicle_control_0028" order by id desc limit 100;
```

3. 检查Face ID是否正确识别并上报，可通过vehicle\_resource\_info\_history或vehicle\_resource\_info表进行确认。

> 
> 检查2:subresource是对应座椅上报的Face ID信息
> 
> 

```SQL
SELECT * FROM vehicle_resource_info_history where vehicle_id = "ppetest20260520123" AND resource_id = "system_control_0003" order by id desc limit 100;
```
