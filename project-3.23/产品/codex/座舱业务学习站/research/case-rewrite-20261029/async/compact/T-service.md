# Task Service One\-pager
> **模块概览：**在 Seres（赛力斯）渠道，以自研任务服务统一管理时间、条件、周期目标与 GUI 多步任务，衔接任务创建、触发、执行、结果回写和车端状态展示。
> 
> 
# 模块定位
Task Service 是 AIDV 面向跨会话任务的管理模块，将用户目标保存为可持续管理的任务，负责触发、运行记录、结果回写与状态通知。任务可以等待未来时间或条件，也可以跨多个步骤和多轮交互持续推进。
**通用长时复杂任务**进一步要求系统围绕同一目标持续工作：“长时”表示任务跨越当前同步会话，期间可以等待或持续跟踪；“复杂”表示需要组织多个动作，并结合新信息调整后续安排；“通用”表示不同场景复用统一的任务理解、编排和事件驱动机制。
在 Seres 渠道，现有 Task Service 承接原动态 Advisor 的用户目标，管理时间、条件、周期任务及 GUI 多步执行，规则匹配复用 Trigger，具体动作由 Planner、Agent／Tool 或 GUI Runtime 承担。下一期计划将任务职责迁至独立 Task Agent，由模型理解和编排、Runtime 推进执行，兼容现有业务能力。**下文标注“二期／规划”的能力尚未实施**，执行流程见 3\.6。
### 任务、运行与执行计划
对象
 | 
作用
 | 
**Task／TaskSpec：目标及定义**
 | 
Task 保存用户目标和生命周期，TaskSpec 描述触发方式、约束、执行内容与结束条件。用户管理的是任务。
 | 
**Run：一次运行**
 | 
记录某一轮执行及结果。周期任务可以有多轮 Run；一次 GUI 多步操作或二期的一次持续跟踪，可以在同一 Run 内推进。
 | 
**Script：执行计划（二期）**
 | 
描述接下来有限的步骤和等待条件，属于 TaskSpec 的执行编排部分。运行中可根据新事实修订后续计划。
 | 
**Step／Action：步骤与调用（二期）**
 | 
Step 表达调用能力、等待事件或重新推理；其中需要执行的步骤由 Runtime 转成实际 Action，关联执行反馈。
 | 
**Event／Snapshots：事实与摘要**
 | 
已有 Event 记录状态变化；二期扩展用户补充、工具反馈和相关外部事件，并用 Snapshots 保留影响后续判断的事实与执行摘要。
 | 
**TaskView：任务视图**
 | 
向 Planner、车端和其他服务提供目标与当前状态；二期补充执行进度，生命周期通知独立发送。
 | 
例如，“每小时开启一次座椅按摩”每次触发产生一轮 Run；二期的“一场比赛持续播报”则可在同一 Run 内反复查询、播报和等待。Script 更新、一次工具返回或一次等待结束，都只推进当前运行；整个任务按用户目标和结束条件关闭。

**发起任务：**用户通过主对话提出目标，Planner 选择 Task Agent 入口。当前由 Task Service 处理时间、条件和周期任务的创建与管理，明确的 GUI 请求进入专用分支。二期由独立 Task Agent 结合已有任务和上下文判断新建或续接，确定目标、约束、可用能力及完成依据。任务始终按渠道、车辆和登录用户定位。
**继续推进：**当前主要由 Trigger 的时间／条件回调，以及车端 GUI 步骤请求驱动。二期还将接入工具反馈、用户补充和车辆／行程等相关事件：能按既定安排继续时推进下一步，需要新判断时再调用模型，修订后续 Script。
**过程中管理：**除查询、修改和取消外，二期还需理解“只说关键比分”“先回家”等补充对原目标的影响。暂停／继续仅面向产品指定类型，具体状态处理与恢复方式仍需明确。
场景效果取决于当前渠道和车型实际接入的工具、数据及事件。视觉条件需要真实感知与语义匹配配合，导航进度需要有效事件或查询能力；任务规划和完成判断都应以这些可用信息为依据，具体依赖见 4\.3。

# 核心链路
**定时提醒流程：**用户约定提醒时间后，Task Service 创建任务并注册时间规则；到点后通过主动推荐链路唤起主对话执行提醒，回写执行结果并结束本次任务。图上半部分展示系统链路，下半部分对应用户体验。
**复杂长时任务流程（二期方案）：**以“每 5 分钟播报比赛结果”为例，系统核实比赛后，在同一 Task／Run 内循环完成等待、查询、播报和反馈处理；未终场则继续下一次播报，终场总结确认交付后结束任务。运行中可按用户补充调整计划，也可随时取消。
### 创建：从一句需求到等待中的任务
用户提出目标后，Planner 将请求交给 Task Agent，由任务服务结合已有任务理解意图，生成目标、触发方式、执行内容和结束条件。校验通过后保存 Task、注册 Trigger 规则并进入等待，向主对话和车端返回创建结果；具体动作在后续触发时执行。
### 触发：从规则命中到主对话执行
时间到达或条件命中后，Task Service 校验回调有效性和执行前提，激活本轮 Run；前提不满足时记录跳过。随后经 Recommend／Frontier 通知车端，车端携推荐标识回流，主链路恢复任务关联，由 Planner 结合当前上下文完成提醒或调用执行能力。周期任务每次有效触发各产生一轮运行。
### 结果回写：本轮完成后是否继续
主链路收集执行反馈后回写 Run：车控依据结构化执行状态，内容任务依据有效内容结果。任务服务保存本轮结果，再按次数、期限和结束策略决定继续等待，或关闭任务并清理规则，随后更新车端状态。Run 完成不代表车端音频已经播放结束，异常与超时处理见第四章。
### GUI：跨多个步骤推进同一轮任务
GUI 请求创建 Task 和本轮 Run 后启动车端执行。后续步骤通过请求标识与步骤序号关联同一轮运行，由 GUI Runtime 处理界面操作，任务服务保存进度。步骤返回运行中则继续等待输入，返回成功或失败则结束本轮；启动成功表示开始执行，最终结果由后续反馈确认。
### 修改、取消和查询
用户可通过对话查询当前任务、修改等待中的任务，或取消已有目标。修改会更新定义与触发规则；取消会关闭任务、清理规则并停止后续触发。当前普通任务取消链路尚未覆盖直接创建的 GUI 任务，具体管理与展示边界见第四章。
### 下一期规划：复杂长时任务（方案中）
**下一期方案尚未实施。**计划由独立 Task Agent 承接任务理解与编排：Planner 分发请求，模型生成 Script，Runtime 按“调用能力、等待事件、重新推理”推进。
工具反馈、用户补充或相关状态变化到来后，继续已有步骤，必要时修订后续计划；任务内部等待与 Script 更新仍归属当前 Run，最终依据实际结果和目标完成条件结束。目标场景与依赖见第二、四章，详细设计见[复杂任务 Task Agent 技术方案](https://bytedance.larkoffice.com/wiki/Hb8lwI2hxiwphYkLXmRcO2TdnvV)。
# 能力演进与实施边界
### 生命周期与结束策略
Task 管理等待、执行中和关闭等生命周期，Run 记录每轮执行结果。一次性时间任务执行一轮后结束；周期任务按次数、期限继续或关闭，取消和过期会停止后续触发。一轮失败不必然关闭周期任务，是否继续由结束策略决定。
二期复杂任务可在同一 Run 内多次查询、执行和等待，以目标达成作为结束依据，具体动作与以实际模型输出 script 为准。计划内等待需与异常超时区分，下电、离线和中断后的恢复方式需按场景明确。
### 状态展示与工程保障
- **状态与追溯：**持久化保存任务定义、运行结果和状态变化，向主对话、车端提供任务信息，支持沿触发与执行链路定位问题。
- **执行可靠性：**已有回调去重、修改与回写校验、异常记录和部分状态修复能力。
- **展示与管理：**状态变化通过消息通知车端，通知失败不回滚已保存状态，展示需结合查询更新；保留任务数量限制及账号退登清理。
### 二期建设与待完善能力
**独立 Agent 与通用任务能力（二期规划，尚未实施）：**在兼容现有能力的基础上，由独立 Task Agent 理解任务、生成计划，Runtime 推进执行，并补齐步骤记录、上下文摘要和恢复能力，详细设计见 3\.6。
**GUI  Agent 正式接入：**已有启动、步骤续接和结果回写，当前仍保留单用户联调兼容；正式多用户、并发重试及用户取消仍需验证。
**任务中心与客户端：**任务岛暂不包含直接 GUI 和持续条件任务；完整任务中心及指定类型的暂停／继续需端侧配合。二期技术方案聚焦服务端，UI 另行推进。
**场景依赖：**赛事播报需稳定数据源，现有通用搜索尚不足；车控与体验介绍需车型知识、真实工具及反馈；导航需路线和行程事件；视觉与情绪判断需感知支持。交付范围以实际接入和场景联调结果为准。
