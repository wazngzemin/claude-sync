# 原图核读记录

2026-10-22，通过已登录 Chrome 的飞书页面逐图查看，截图保存在 assets。截图是页面可见区域，不是声称已取得原始可编辑画板文件。

已核读 6 张嵌入画板：4.1 主链路时序、4.2 打断恢复时序、5.1 热词处理、5.2 预请求、5.3 TTS、5.4 恢复处理流程。长图分段查看。

- 主链路图：端侧 → AIDV 的“流式拒识判断”，AIDV → 端侧的“下发流式拒识结果”，端侧停止当前 TTS。支持云端判断、端侧停播这一画法；正文仍有“端侧做判断”矛盾。恢复时序图又把流式拒识箭头画向 ASR，因此不能声称所有图已统一职责。
- 主链路中段：Soft 300 ms 发 pre_query；前置任务与 Context；存 Query/结果。Hard 600 ms 后向 ASR 发两帧结束标识，返回二遍 final，再发正式请求。正式校验 requestID 相同与文字完全相同；不满足则重算。仅“两帧结束标识”是工程补充，课堂不需其实现细节。
- 主链路尾段：最终 Query+Context → Planner；回复文本和音频标识下发；端侧 WSS 流式取音频；本地命中另走 context/sync 上报 Query/Answer/Observation。图中 TTS 标识下发和合成箭头顺序不用于证明精确并发时刻。
- 热词图：端状态变化上报，通讯录按条件触发更新；数据库保存热词/状态。ASR 建联取热词数据，音频 start 帧携带可见即可说与 chat_id（对话编号），构建热词后交识别。不能把“有数据上报”直接当作 ASR 必然正确。
- 预请求图：连续说“关闭窗户”“再把空调打开”形成 round_1、round_2，正式 round_3；正式复用上一轮缓存。图中话语时长 0.6 s、后续 0.3 s 是示意标注，不能推出 Hard=300 ms 或固定总响应时长。图中的前置模块包括意图/拒识/简单复杂仲裁，正文还列 Context，应注明模块范围据版本。
- TTS 图：Planner/Agent/S2S 可产生音频；云端维护 TTS 队列，记录来源 cloud_planner/cloud_agent。根据取信结果按服务顺序读队列，跳过不采信来源，读至 EOF（该段结束）切下一队列。音频存缓存，端侧收到标识后拉取。此图支持队列存在，但未定义所有优先级/取消竞态。
- 打断时序：端侧上报播放秒数和原因；结合打轴定位已播/未播；先判断是否播完、原因、是否需要恢复。符合恢复条件后，最终 Reject 经 Event 再请求正式链路；Recall 交 Planner 融合新需求与未播内容，保留核心去重。
- 恢复末图：示例主驾问上海天气，副驾“好无聊”插话；非拒识构建打断信息交 Planner；拒识分支下发 Event 经端侧重新进入 Planner，生成“天气还没说完，今天下午可能会下雨哦”。旁边便签写“此处 advisor 的下发后续改成由事件上报→触发器链路触发”，属于后续改造，不能画成已上线现状。
