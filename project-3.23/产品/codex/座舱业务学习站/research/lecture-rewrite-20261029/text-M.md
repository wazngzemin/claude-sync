INTRO

前面已经得到一句可以交给业务处理的话，例如“去昨天那家游泳馆”。这时车里可能还在播上一段回答，查天气的工具也可能刚刚返回。输入管理要先把这些事情分清，决定谁现在可以进入下一轮、谁需要等一等，以及上一轮哪些动作已经发生。

你可以先盯住一个变化来理解它。用户刚说完“找一家餐厅”，紧接着补了一句“不要辣的”。如果旧轮还没发出动作，可以把补充带进新的计算；如果餐厅搜索已经发出，就要保留这次搜索和后来返回的结果，再让下一轮判断怎样使用。输入管理守住的正是这条时间线。

## m-lesson-1 先认清这条消息是在提要求，还是在报告进展

用户的 Query 是这次想办的事。Advisor 发来的 advice 是主动服务建议，例如“车内较热，可以帮助降温”。工具发来的 tool_feedback 是执行事实，例如“空调调整失败”。event 则记录已经发生的交互，例如用户打断了一段播报。这些消息都可能进入输入管理，但它们需要保留各自的身份，否则一句失败反馈就可能被模型误解成又一次操作要求。

每条消息还要带着来处进入。谁说的、来自哪个音区、属于哪辆车、哪个会话、哪次请求，都会影响后续判断。主驾的补话应接到主驾刚才那件事上；几秒后返回的音乐结果，也仍属于原来的音乐调用。不能只凭文字相似就合并，更不能把迟到结果塞给当时正在问天气的人。

## m-lesson-2 新话来了，先看旧事已经走到哪里

接住消息以后，要同时看三件正在发生的事。模型是否还在生成候选回答，车里是否仍在播放声音，工具是否已经发出了动作。它们的进度可以不同。豆包一句话还没说出来，空调指令可能已经发出；云端已经发完音频，车里也可能还在播放最后一句。

如果前台交互空闲，新消息可以按规则进入下一轮。后台仍在生成播客或等待十分钟提醒，并不必然占住前台。若前台忙碌，先检查旧候选能否安全取消。尚未发布动作时，可以重新组织输入；动作已经发出时，就必须把它作为已经发生的事实保留下来。用户说“不用了”后停止旧回答，不能顺带假定空调也自动恢复原样。

向豆包提出的新用户诉求应及时处理，普通建议则按相应输入规则等待。工具反馈还要保持调用批次和归属，不能任意拆碎后反复插话。对于普通建议究竟在何时合并，评审应要求给出实际采用的规则；这里最重要的业务底线，是不能让建议抢掉用户正在处理的事，也不能重放已经产生效果的旧动作。

## m-lesson-3 这一轮可以开始计算，还要另看能否对外说和做

输入管理确定本轮内容后，要给这次执行建立独立关联。DirectorExecutionID 用来区分模型的这次执行，TaskRoundID 关联对应播放轮，tool_call_id 找回具体工具调用。你不需要背下所有字段拼写，但要能用它们回答“这条结果到底归哪次请求”，尤其要查旧轮取消后是否还会写入新轮。

在支持提前计算的链路里，上一段回答尚未播完，下一轮可以先准备候选。例如餐厅搜索结果已经到了，可以先生成推荐说明，等前一段必要信息结束后再发布。计算许可和输出许可需要分别检查。候选算好了，不意味着它已经可以抢播，也不意味着其中新的车控动作可以提前下发。未启用这项能力的渠道仍按自己的串行规则运行。

解除等待要依靠客户端实际播放状态。STARTED 表示已经出声，PROGRESS 表示实际播到了哪里，FINISHED 还需满足本轮结束且待播队列清空，ABORTED 表示该播放实例终止。被有效新请求终止的旧实例不能自行复活；临时听到人声、后来判定并非对豆包说话，则交给打断恢复策略处理。

## m-lesson-4 没有听到回答时，沿这一轮找到最早的断点

用户说完后车里没有声音，只能先确认用户没有听到答复。你还需要继续查，正式文本是否产生，入口是否放行，输入管理是否接收，消息在等待还是被新请求替换，Director 是否产出回答，以及音频有没有真正播放。某一段没有记录，不能直接解释成拒识模型主动拒绝了用户。

如果播放结束事件丢失，系统需要避免一直锁住下一轮，同时保留“结束未确认”的事实。后来补到的结束事件只能更新它原来的轮次。若状态存储失败或执行者恢复，还要先核对外部动作是否已经发布；否则一次恢复就可能让车控、下单等动作执行两次。

### guide M-mechanism 跟着“找餐厅，再补一句不要辣的”读这张图

从 M-stage-1 看起，第一次找餐厅和后来的“不要辣的”都是用户输入，搜索返回的餐厅列表则是工具反馈。这里先保留它们的来源和原请求关系，接着进入 M-stage-2，看旧请求正在计算、正在播报，还是已经发出了搜索。

沿 M-stage-2 到 M-stage-3，这次判断决定补话怎样接入。如果搜索还没发出，可以在允许的边界内组织新候选；如果已经发出，就保留原调用，下一轮结合“不辣”筛选返回结果。普通主动建议经过同一入口时，也要按自己的优先级等待，不能套用用户插话规则。

M-stage-3 到 M-stage-4 表示组织好输入后再取得所需许可。读到“许可”时要分两层理解，可以计算和可以对外发布。支持预计算时，候选可以先准备；真正播报或发出新的动作，仍要等输出条件满足。

最后到 M-stage-5，客户端把实际播放进度、工具把执行事实交回来。这些事实会成为下一次调度的依据。阶段图到这里收尾，但业务没有失去前文，下一句“换一家”仍能知道刚才查过哪些餐厅、已经说到哪家，以及有没有动作尚在处理中。

把这张职责图的交接连起来看：输入类型、来源与当前请求身份；当前推理、播报和动作进度；本轮获准接入的输入及发布约束；实际处理与播报进度更新。具体命中条件和例外出口，继续沿下方完整节点图中的条件箭头读取。

### guide base 先走空闲主路，再读忙碌、打断和恢复三条支路

主线从 M1 到 M2，再到 M3。M1 接消息并保留类型，M2 查询当前推理、播报和动作状态，M3 判断前台是否空闲。比如车里没有待回答的话，也没有占用当前交互的播报，“去昨天的游泳馆”就可以沿 M3 到 M7 组成新一轮输入。

若 M3 判断忙碌，箭头转向 M4。这里要看旧候选是否已经对外发布动作。旧候选尚可取消，便沿 M4 到 M7 重新组织；已经发布或不能合并，则转向 M5，继续按新输入的类型决定怎么处理。不要把 M4 理解成只问“豆包开口了吗”，因为尚未开口也可能已经发出了工具。

在 M5，真正的新用户诉求走向 M6。例如用户说“别找了，导航回家”，M6 停止相关旧推理与声音，带上已经发生的搜索或车控事实，再交 M7。普通消息和完整工具反馈则走 M8 等待。M6 和 M8 是不同条件下的出口，无需先执行 M6 再排进 M8。

M7 给本轮输入建立执行关联，随后到 M9 申请计算与发布许可。M8 等待的输入在满足准入条件后，也进入 M9。M9 再把这轮交给 C1 准备上下文。因此，从云端有效 Query 进入时，你可以沿 R8、M1、相关判断支路、M9、C1 串起前后模块。

再看从输出端返回的线。O04 的真实播放事件进入 M10，M10 再向 M9 释放相应输出许可。这里解释了为什么上一轮语音还没实际结束，下一轮即使算好了也不能随便抢播。服务端生成完文本，不能代替这条客户端回来的事实。

M10 如果等不到终态，走 M11，再按异常解锁规则回到 M9。解锁是为了不让用户后续的话永远被堵住，同时仍保留原播放未确认的状态。它没有把超时变成“用户已经听完”。

还有一条从 M2 分向 M12 的故障恢复线，专门面对状态存储或执行者异常。M12 先核已发布动作，安全恢复或明确失败后交 M8。读这条线时想一想，空调指令若早已发出，恢复过程能不能再次发送同一指令；这正是要守住的重复执行边界。

最后回到 M1 的多条入口。E8 交回工具反馈，S06 和 T08 交来建议，I7、I8 交来恢复或插话事实。它们都通过输入管理进入后续判断。图里的汇合点说明主链可以反复运行，并不表示每轮都必须先经过所有这些上游模块。

CLOSING

走到这里，系统已经选定这轮应该处理什么，也知道哪些旧事不能抹掉。下一步进入 Context，把做这次判断需要的车况、身份、记忆和历史准备好。输入管理决定这轮何时进入，Context 再帮助模型看清这轮发生在什么环境里。
