# 02 有效入口与端云采信｜v14 全景图 SVG 中的 R 模块（节点 18 个）

框标题：R · 入口与端云采信：有效请求交给谁，只允许一次真实执行
框说明：区分已激活与免唤醒入口，在各路候选之间确定实际执行者。

## 节点（编号与文档画板一致；措辞为 10/26 最新版，含每个节点两段讲解）
### R1｜根据唤醒和接话状态选择入口（蓝底）
- 要点：识别唤醒词、按键与激活续说免唤醒先判断是否需要接话保留当前开放音区范围
- 讲解①：唤醒词或按键可以让助手进入聆听，已经激活时还可以继续说话。未激活的免唤醒入口则需要先判断车里这句话是否值得助手接住，例如乘客对朋友聊天不应直接变成新任务。
- 讲解②：入口会影响何时上传声音、怎样放行以及哪些音区参与，具体按车辆配置运行。按键属于主驾，也不自然意味着只收主驾声音。确认这次入口以后，R2 再按激活状态分路，同时保留用户这句话的归属。

### R2｜激活接话与免唤醒采用不同处理路径（金底）
- 要点：激活时可让端云并行准备未激活先做本地流式召回采到声音不等于全部直接上传
- 讲解①：已经唤醒助手时，本地和云端可以并行准备候选，让各自处理支持的内容。未激活时则先用本地流式识别和拒识观察这句话，满足提前放行条件后才把声音交给云端。
- 讲解②：因此不能让所有请求都等本地模型处理完再上传，也不能把车里采到的声音全部当成有效 Query。当前开放的音区和持续聆听范围仍由车辆配置决定。分路后还要通过 R3 关联各处结果，确保它们属于同一次输入。

### R3｜让本地、云端与回包认出同一句话（蓝底）
- 要点：贯穿请求编号、会话和音区区分两侧识别与最终采信旧结果始终关联原来的输入
- 讲解①：同一句话可能在本地和云端各产生一份文字或动作候选。request_id、会话、音区和时间帮助系统把它们关联起来，并记录最终采用哪一方。端侧与云端编号不同，还需要明确映射关系。
- 讲解②：比如本地已经打开空调，几秒后云端才返回开启动作，仍然属于刚才那个请求。后面的采信与防重必须认出这一点，不能把迟到回包当成用户新命令。不同车辆、不同会话的结果也不能仅因文字相同就合并。

### R4｜本地模型在支持范围内生成候选（蓝底）
- 要点：理解已支持的车控与基础操作承接有限对象和位置继承有效上文不因闲聊被清空生成候选后仍等待采信
- 讲解①：本地模型处理当前车辆已支持的车控、系统或导航基础操作，并承接有限上下文。用户说“再开一点”，需要知道上一轮操作的是哪个窗；中间一句被拒识的闲聊不应让这个有效对象丢失。
- 讲解②：联网搜索与复杂多步计划超出本地范围时，要保留不支持的结果。图中的云端优先策略也不允许本地一算好就抢先执行，候选先交 R16 分类，再由 R5 根据断网或超时等条件决定是否采用。

### R5｜确认本地候选此刻是否可以生效（金底）
- 要点：正常联网时不抢先采用本地模型断网或配置超时才检查兜底候选FC、拒识与不支持分别处理确定性缓存有独立优先路径
- 讲解①：本图采用云端优先的模型采信方式。常规联网时，本地模型即使先给出结果，也不立即执行；断网或云端等待达到配置期限后，才检查本地候选是否可以接手。本图这套超时示例为 3 秒。
- 讲解②：得到采信后，可执行 FC 去 R6，无关话去 R10，有效但本地不会则去 R18。确定性缓存仍有独立优先通路，不能把这套本地模型限制混用到所有入口。实际条件满足后才放行动作，不能凭哪边先出字决定。

### R6｜把已采信的操作写成明确执行参数（蓝底）
- 要点：写清设备、位置、动作和数值核车型能力与参数范围适配车辆接口交给执行方
- 讲解①：FC 是约定的结构化调用。把“打开副驾座椅加热”交给车辆时，需要明确设备、目标座位和开启动作；如果还指定档位，也要传入允许范围内的数值，不能只留一句模糊的“加热开关”。
- 讲解②：参数形成后继续核车型能力，再转换成车企实际接口交执行方。这个节点完成的是明确下发内容，车辆是否接受、是否已经加热，还需要 R9 的真实结果。生成了一份正确参数，本身不能支持“已经调好了”的回复。

### R7｜判断这句话是否在向豆包提出诉求（金底）
- 要点：依据最终输入判断是否应接话无关聊天走静默出口有效需求再进入输入管理能力不足另走能力判断
- 讲解①：正式拒识要判断用户是否在对助手说话。副驾对朋友问“你冷不冷”，不应直接引发空调操作；用户明确叫豆包查餐厅，即使本地不会查，也仍然是有效需求。是否接话与能否执行需要分别判断。
- 讲解②：有效且未由本地完成的输入交 R8，再由输入管理和 Context 送到 Director。无关话则去 R10。这个节点不负责把所有需求分成简单或复杂，也不能因为当前一句被拒识，就取消前面已经接住的有效任务。

### R8｜把有效请求交给输入管理继续处理（绿底）
- 要点：保留用户文字、说话人和音区输入管理决定合并、打断或等待配齐本轮背景后交 Director
- 讲解①：通过拒识且没有在本地处理完的请求，带着用户原话、说话人和音区进入输入管理。此时若上一轮还在说话或工具正在返回，需要按交互状态安排新请求，不能直接抢占已有工作。
- 讲解②：输入管理准入后，Context 准备本轮车况、历史、记忆等信息，Director 再决定怎么做。例如“我好热”需要先看当前环境。这里直接衔接现有主链，不要求每条请求都先经过一套额外的简单复杂分类漏斗。

### R9｜用实际执行结果判断这一项做到了哪里（蓝底）
- 要点：执行方检查当前条件并操作完成、失败和部分成功分开回传受理或处理中不能报成完成真实结果同时供回复和历史使用
- 讲解①：执行方收到已采信指令后，仍要核设备、位置、参数与当前车辆状态。例如副驾不支持请求档位，应返回具体限制，不能只因指令已发送就说调好了。多个子动作也需要分别给出结果。
- 讲解②：完成、失败和仍在处理会影响后续答复，同时成为下一轮的背景。若这一轮只是受理，历史中也不能提前写成设备已改变。结果一方面接输出核验，另一方面通过 R12 同步，让下一句“再低一点”接着真实状态往下走。

### R10｜无关对话结束，保住原来有效的任务（绿底）
- 要点：拒识后不创建新的助手任务尚未上传的免唤醒输入可静默结束误停过声音时按恢复规则处理原有效任务和在途结果继续保留
- 讲解①：拒识表示这句话不应成为新的助手需求。免唤醒时整段没有上传且最终判为无关，可以静默结束；已经上传的请求则继续由云端最终判断处理，不能在本地假装撤回。
- 讲解②：旁人闲聊也不能取消主驾正在查天气的有效任务。如果过程文字曾引起停播，再按当前恢复策略决定是否补说。本地 unsupported 仍属于有效需求，只是当前做不了，需要走相应说明，不能和这里的无关话混在一起。

### R11｜等待云端超过期限后检查本地兜底（蓝底）
- 要点：监测真实断网或云端等待超时本图超时示例为 3 秒仅启用本车已支持的本地能力恢复网络也不能擅自重放旧动作
- 讲解①：云端一直没有返回时，用户不能无限等待。本图这套策略在断网或云端等待超过 3 秒后，解锁本地候选采信。计时从哪里开始、何时停止，应使用当前实际配置；网络格数本身不能证明业务已经超时。
- 讲解②：兜底只覆盖这辆车具备的本地能力，无法自动补出联网搜索和复杂任务。接手后还要隔离迟到云端，恢复网络时也不能悄悄补执行旧请求。输入和结果怎样重新同步，需与后面的本地历史回流配合。

### R12｜把本地做过的事交给后续上下文（绿底）
- 要点：同步用户输入、回复和实际结果保留音区、调用参数与时间区分已下发和已经完成云端接收结果后才能正确承接
- 讲解①：本地处理后，把用户 Query、回复和实际观察结果连同请求编号、音区、函数参数及时间同步出去。下一句“再调低一点”才知道刚才调的是哪一座、哪个设备，以及上次是否成功。
- 讲解②：这里接到 C5，让后续云端判断承接本地历史。同步内容必须反映真实状态，不能把已下发写成已完成。本地已经记住与云端已经收到还要分开，离线积压、重复回传和重连补同步都需要保持原请求归属。

### R13｜免唤醒时边听边判断是否值得接话（金底）
- 要点：本地过程文字参与流式召回attend 可以提前放行音频未放行时继续等最终判断最终无关且未上传可静默结束
- 讲解①：在未激活的免唤醒场景，本地识别与流式拒识一起观察用户的话。出现 attend，表示这句话值得继续让云端接话，可以提前启动音频上传，减少等整句定稿后才开始处理的时间。
- 讲解②：一直没有召回时，系统继续听完再看最终结果。若最终判为无关且从未上传，可以安静结束。这条支线使用过程文字，早于正式 Query；提前放行只决定继续处理，最终是否承接仍要由后面的判断完成。

### R14｜放行后把有效音频交云端继续判断（蓝底）
- 要点：提前召回后启动云端处理必要时补发完整音频本地后续拒识不能撤回已上传内容
- 讲解①：本地流式召回已经放行音频后，云端会继续识别和拒识。后来本地最终结果即使变成 reject，也不能假装这次请求从未上传，后续处理需要尊重云端最终判断。
- 讲解②：如果此前没有提前放行，最终却得到本地操作候选或本地不支持的有效需求，这套入口会补发整段声音。没有上传、提前上传和最后补发是不同状态，应关联同一输入，避免误当三次请求，再交 R7 判断是否接话。

### R15｜明确且无需上下文的指令可走缓存（金底）
- 要点：匹配当前项目配置的确定性规则要求对象、意图和参数唯一命中可跳过本地模型计算依赖历史的短句不直接套用
- 讲解①：确定性缓存适合单轮、无需历史、意图与参数唯一的指令，例如明确设备的开关要求。命中以后可以跳过本地模型计算，再按实际车型能力把操作交下去，节省一次理解过程。
- 讲解②：“暂停”“继续”“就选它”依赖前文对象，不能只因常见就当成同类缓存。否则系统可能对错设备优先执行。没有命中时，本地模型和云端可以并行处理；命中时也仍要经过执行参数校验，不能把匹配成功当成设备成功。

### R16｜分清无关话、操作候选与本地不会（金底）
- 要点：reject 表示无关助手诉求FC 表示结构化操作候选unsupported 表示有效但本地不会分类完成后还未产生实际动作
- 讲解①：本地结果有三种需要分开的含义。reject 表示这句不应成为助手需求；FC 表示已解析出结构化操作；unsupported 则表示用户确实在求助，但本地能力无法承接，例如需要联网搜索。
- 讲解②：三种结果先保存为候选，接下来由采信策略决定如何处理。把 unsupported 当成无关聊天，会让有效需求被静默吞掉；把 FC 当成已经完成，又会提前报喜。分类后继续检查执行权和实际结果，不能只留一个成功或失败标签。

### R17｜本地接手后隔离迟到的云端动作（蓝底）
- 要点：记录同次请求已经采用哪一侧迟到云端不再获得执行资格同时防止重复回复和重复历史
- 讲解①：本地因断网或等待超时接手后，旧云端请求仍可能稍后返回。系统要根据同一请求编号和采信记录，阻止这份迟到结果再次执行。只隐藏第二次回复还不够，动作也必须被隔离。
- 讲解②：例如“副驾车窗再降一点”若执行两次，实际降幅就超过用户要求。后续核验应看设备到底变化几次，以及历史是否重复记录。迟到结果仍归原请求，不能借新一轮输入身份重新获得执行权。

### R18｜本地无法承接时给出受限说明（蓝底）
- 要点：unsupported 保留有效需求身份说明网络或当前能力限制本图同一唤醒周期最多提示一次恢复后是否重试须遵守明确规则
- 讲解①：断网或云端超时后，本地候选若是 unsupported，表示用户确实提出了需求，但此刻没有可完成它的能力。这套本地交互采用网络异常提示，并在同一唤醒周期最多播一次，避免连续尝试时重复打扰。
- 讲解②：系统不能用静默拒识代替这次失败，也不能生成没有执行依据的成功答案。网络恢复后是否重新办理、是否需要用户再次发起，必须遵守明确规则；旧动作不可自动补做，当前未完成状态也应保留给后续对话。
