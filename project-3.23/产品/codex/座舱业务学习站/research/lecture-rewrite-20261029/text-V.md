INTRO

我们先坐进车里，从你说‘去昨天那家游泳馆’开始。此时，系统收到的只是一段声音。它还不知道你说的完整句子，更不知道‘昨天那家’是哪一家。语音模块要先把这段声音变成一份可信的输入，让后面的业务模块有东西可办。

这一步最容易让人误会的地方，是屏幕已经出现字，车却还不能照着做。你可能先说‘去昨天那家游泳馆’，停一下，又补‘附近的餐厅’。系统既要利用前半句提前准备，又要等你真正说完，才把完整意思交出去。下面就顺着这句话，看看它怎样同时做到这两件事。

## v-listen 先听清是谁说了什么

车端先检查麦克风是否获准使用，以及当前交互状态是否允许语音工作。通话或其他占用声音的功能，可能影响收音和响应。假如入口根本没有放行，后面的识别服务就收不到有效声音。这种‘叫了没反应’，要从入口查起。

允许开始后，麦克风持续收音。车里同时有轮胎声、空调声，还可能正在播放音乐或豆包自己的回答。声学前端负责先压低干扰，并利用车机正在播放的声音作为参考，消除自己的回声。否则，助手有可能把自己的播报听成用户的新一句话，造成误打断。

处理声音时还要确定说话位置，这就是音区。主驾说‘打开副驾座椅加热’，说话位置在主驾，动作目标在副驾。这个区别要一路保留下去，后面的车控不能只看说话位置就打开主驾加热。具体有哪些音区，取决于这辆车的配置。

为了听清人名、地点和屏幕上的按钮，系统还会把当前有用的词交给识别服务，这叫热词。例如屏幕出现一家名字比较生僻的餐厅，热词可以帮助识别服务把店名写对。但词表必须真正进入本次识别请求才有作用，页面退出后，失效的按钮也不能继续作为当前页面的操作依据。

## v-text 屏幕上的字为什么还会变化

声音处理好后，ASR 开始工作。ASR 就是语音识别，它把声音写成文字。用户还在说话时，系统可能先得到‘去’，接着得到‘去昨天那家游泳馆’。这一遍边听边出的结果叫过程文字，也常写成 partial。

过程文字还会修正。假如先听成了‘播放音月’，后面可能改成‘播放音乐’。因此，这些字可以帮助系统提前准备，也可以参与允许的插话判断，但还不能直接拿去启动导航或控制车辆。否则用户补了一个‘不要’，车已经先动了。

在线和离线识别可能各自产生文字。界面为了及时响应，可以先显示一份过程结果，再用最终采用的文字刷新。你看到本地文字先上屏，只能说明显示层先拿到了这份字。哪一方的动作方案有权执行，还要到下一个模块判断。

如果最终没有有效声音、结果为空或识别超时，这次输入会留在语音失败分支。不能把仅听到的‘关……’自行补成‘关车窗’。查这种问题时，把原始音频、处理后的音频和识别文本对到同一次输入，才能分清声音丢了、词听错了，还是用户本来就没有说完。

## v-pause 用户停了一下，系统先准备到哪一步

ASR 在写字的同时，另一条处理线在观察用户是否还在说话，这叫 VAD，也就是语音活动检测。它关注人声和停顿。你说‘我想去……’之后停一下，ASR 已经有字，VAD 也检测到停顿，但目的地仍没有说出来。文字到齐、声音停下和意思说全，需要分别判断。

图中这套判停方案在短停顿达到 300 毫秒时先发起准备请求，称为 Soft VAD。系统继续听，同时可以提前做获准的拒识或上下文准备。例如先检查‘昨天那家’需要什么上下文，能让最后的正式处理少等一会儿。这里不能提前启动导航、播正式答案或把半句话写成已完成的对话。

同一句话中可以发生多次短停顿。系统用 request_id 标识同一次输入，用 round_id 区分这次输入里的各轮准备。你在第一次停顿后又补了一句话，准备内容也可能更新。后面必须知道采用的是哪一轮，避免把先到的旧结果接到最新意思上。

这套方案在停顿达到 600 毫秒时让当前语音段收尾，称为 Hard VAD。300 和 600 都从同一次停顿计算，不相加。600 毫秒也不等于整次请求的响应时间，因为接下来还需要最终识别、业务判断、执行或播报。具体阈值要随项目配置使用，理解这里时，先抓住短停顿准备、长停顿收尾这两个不同动作。

收尾以后，二遍 ASR 对这段声音给出最终文字，常写成 final。用户不需要再说一遍，服务处理的是刚才那段录音。最终文字只表示这次识别已定稿，仍可能听错。系统还要核对它是否与上一份准备完全一致；只有同一次输入、文字一致且该模块支持复用，才沿用已经算好的结果。

## v-handoff 把完整的话交出去，还没有替用户把事办完

回到‘去昨天那家游泳馆附近的餐厅’。如果准备阶段只看到了‘去昨天那家游泳馆’，两份文字已经不同，就必须按最终句子重做相关准备。否则，后面即使每个模块都运行正常，也可能认真地把你导航到错误的地方。

还有一种情况，声音确实停了，但‘我想去……’在意思上没有说全。语义判停负责观察这种不完整表达。它和前面的停顿计时怎样配合、最多延长多久，需要按项目规则明确；在没有明确规则时，不给图补一个自动通过的步骤。产品要检查的体验很具体，既不能截断正常补充，也不能让已经说完的用户一直等。

当最终输入可以提交时，语音模块交出文字、说话音区、输入编号和允许沿用的准备结果。普通请求进入入口与端云采信模块。如果项目启用了可见即可说，并且当前页面存在有效词表，则还有一条页面匹配分支。两条路都从最终文字开始，页面上的一个词出现过，并不自动授权一次点击。

到了这里，‘说了什么’这件事才有了可用答案。下一步还得判断这句话是不是对助手说的、由本地还是云端承接，以及当前有没有旧请求正在处理。至于昨天那家游泳馆的地址，则要等后面的上下文、记忆和工具链继续补齐。

### guide V-mechanism 先沿五个阶段，把同一句话走通

从 V-stage-1 看入口允许接收声音以后，两条线同时开始：V-stage-2 把声音写成文字，V-stage-3 观察用户有没有停顿。不要沿编号把它读成先识别完，再开始判断停顿。

两条线在 V-stage-4 汇合。这里拿到最终文字、判停结果和此前准备，核对是否属于同一次输入、准备是否仍可复用。V-stage-5 才把正式请求和音区交出去；导航或车控还没有因此执行。

### guide base 再沿完整图，看清并行、复用和失败出口

先找 V13‘权限与互斥’，不要从编号最小的一格猜起点。允许使用语音以后，沿 V13 → V1 → V14 → V15，看权限检查、麦克风收音、声学处理和音区定位。主驾说‘开副驾加热’时，这条路保存主驾这个声音来源，具体操作副驾的含义留给下游理解。

声音可用于识别后，V15 → V17 → V2 进入文字来源选择和一遍识别。旁边的 V16 也连向 V2，它送来本次可用的热词。这是一份辅助识别的输入，不需要用户先讲完一句话才去更新，也不表示热词自己能触发操作。

到 V2 后，沿 V2 → V3 看过程文字怎样陆续出现，再沿 V3 → V6 看当前文字进入准备。这时把目光移回 V14，它还有一条线连 V4。V4 观察声音中的停顿，所以文字识别和停顿检测是并行关系，不能把图读成‘先识别完，再开始计算停顿’。

在 V4 处分两路读。短停顿走 V4 → V5 → V6，发起有限的提前准备；较长停顿走 V4 → V7 → V8，让当前语音段收尾，再取得二遍识别的最终字。V7 旁的 V10 表示还要关注意思是否说全，它与计时怎样配合要按具体项目明确，图中没有一条可随意补上的必经放行线。

现在看两条线怎样汇合。V6 提供此前的准备，V8 提供最终文字，两者都交到 V9 核对。只有属于同一次输入、文字满足精确复用条件，才从 V9 直接走到 V12。最后多了‘附近的餐厅’，就从 V9 → V11 → V12，按新文字重新准备后再提交。

V18 是失败出口，它接在 V8 之后。二遍结果为空或失败时沿 V8 → V18 处理。它不接在 V12 后面，因此不能读成‘已经正式提交以后，再回头识别失败’。失败出口也没有一条默认把残缺过程文字变成正式车控的线。

最后从 V12 跨出本模块。普通入口走 V12 → R1，交给端云采信；满足当前页面条件的输入可走 V12 → W04，先做可见即可说匹配。如果 W05 判断没有命中，再回 R1。V3 → R13 是另一条较早的支线，只服务未激活免唤醒的流式召回，不能拿它代替全部正式请求的入口。

你提到的 R12 要到下一个模块里看，它保存的是本地已经处理后的对话和实际结果。它和这里的 V12 职责不同，中间也没有一条 V12 → R12 的直连。读图时先看箭头上的条件，再读编号旁的中文动作，就能分清‘输入已准备好’和‘事情已经办过’。

CLOSING

现在，你手里有了一份正式输入。下一课继续拿‘去昨天那家游泳馆’往下走，先决定谁有权接这句话。带着这个结果去看 R 模块，会比重新背一遍端云术语容易得多。
