## 收尾：用回家买花，把这一版提示词讲给别人听

### 三分钟口述稿：我先看这一轮知道什么，再看按哪条规则往下办

再看这张总图：固定部分教做法，每轮背景补现场，工具结果回来以后再作下一次决定。

<!-- figure:sp2-overview -->

**例子：**我用主驾傍晚这句话讲整章：“今天情人节，先导航回家吧，路上顺道买束花。”我负责检查赛力斯 AIVA ME7 在 2026 年 11 月 17 日使用的这一版提示词，能否把这件事按正确顺序办下去。

我先看七万多字里有什么。这一版约有 7.6 万个非空白字符，包含工具定义、输入输出、能力、安全、表达规则和参考示例。固定部分定规矩，每轮再填身份、记忆、车况等背景。**参考示例约占一半，错误示范也会教出错误动作。**这让模型容易照着完整过程办事，也增加了同步维护的工作。

这一轮，我已经拿到主驾身份、家在莲花路 321 号、车速 40 公里/小时、未导航和情人节背景。我先认输入是用户交办；建议、回执和事件各按自己的用途处理。事件报告变化，收到以后仍要分别判断要不要说、要不要做。

我让 Planner 同时交出说不说、说什么、表情和动作。它先说“先设导航回家，路上帮你找花店”，表情可空，只发回家路线规划。沿途找花店需要正在导航的路线，这几个导航工具也要串行，所以我把搜索留到后面。

三条路线回来，我只推荐一条最合适的，等主驾选。主驾说“就第一条”，我交出选择路线，选择后会自动导航。收到导航成功，才搜沿途花店。多家店回来，我推荐一家，问“要加途经点吗”，这轮动作留空。主驾同意以后再添加，成功以后就停，完成话术只说实际结果。

用户接着提出别的事，我先分清入口。以后提醒买花，完整原话一次交任务入口；只打开应用与在应用里办业务分开。找歌、看画面、订座也各守自己的范围。动作生成前，我还要检查能力、位置、精度和安全条件。少问询放在这些前提之后；一旦问了，就等回答。

我检查每轮实际填入的内容。插槽留了名字，家地址和导航状态仍可能空着。背景缺失先补背景，收到了却用错再查决定。C、M、I、K 章讲过的组装、调度、续接和身份，我沿对应交接定位。

这一版要改的，我在第十一段分成规则、功能映射、名称、格式和示例行为来审。**先让规则和示例教同一种做法，再测模型。**主例成功后重复添加的问题，第十一段讲过；我会把正确停止方式一起改进去。

改完，我先逐块解析输出，核对工具名、参数和表情；再给每条规则配正反例，连着相邻工具测。安全要换座位、挡位和临界车速，最后跑完整的回家买花过程。提示词决定正确后，车辆实际做了什么，继续按 E、F 章往后查。

### 最容易讲错的地方：把条件、动作和结果分别说准

口述时把“知道了”“可以做”“发出了”“做成了”连在一句里，很容易跳过中间的条件。**每说一个完成，都问它对应哪一步。**下面八处尤其要守住。

1. 固定工具按实际定义数。这一版是 28 个，最大编号 34 只帮助定位；动态区另计。评审问：“这个数的计数对象是什么？”
2. 事件来了，先判断价值与允许条件，可以不说也不做。评审问：“这里为什么值得打扰用户，动作又依据什么？”
3. 问了用户，就等被询问的那件事。已交办的其他事可以继续。评审问：“这一轮有没有一边问加花店，一边已经添加？”
4. 能力分三路：明确支持的按边界办，明确不支持的解释并引导，未列项通过合适工具看实际结果。评审问：“拒绝是因为明确限制，还是只因没列到？”
5. “先做后确认”要先满足安全、权限和必要信息。大跨度音量先问，当前禁止的动作继续拦住。评审问：“用户同意后，车辆状态还允许吗？”
6. 示例直接教整轮做法，写错会影响选工具、参数和停止位置。评审问：“改完规则，哪几轮示例也跟着改了？”
7. 插槽名只代表预留位置，具体填入的内容才是本轮依据。评审问：“请指出这轮真正交进来的家地址和导航状态。”
8. 回执成功要对上原动作和目标，成功后及时停。评审问：“这轮还有哪一步没完成，为什么需要再发相同动作？”

**例子：**主驾说“就这家，加上”。Planner 拿到上轮花店候选，先把“这家”对应为花时间，交出一次添加途经点。下一轮拿到该调用的成功回执，判断添加已完成，说“花时间已加为途经点”，表情可空，动作为空。若只有一句“我来加上”，它仍处于办理阶段。把这两个时刻分开，才看得出该继续还是该停。

**案例：成功后的动作没有停** 第十一段讲过主例末尾的回执错配和重复添加；复述时只需点出“成功后动作应为空”，别把“出发啦”当成收尾正确的全部依据。

### 复述路线图：先沿主例讲决定，再沿偏差找负责的那一步

复述按这一条路线走：第一段认结构 → 第二段分输入 → 第三段看四项输出 → 第四、五段选工具 → 第六、七段查能力和安全 → 第八段对齐说与做 → 第九段审示例 → 第十段找本轮背景 → 第十一段定改法 → 第十二段测改后行为。

**每到一站，都说清拿到什么、决定什么、交出什么。**主例已有完整地址时直接用，未导航时先建路线，多候选时等选择，成功后停动作。这条路线让别人听懂规则为什么改变行为。代价是要多看几轮输入和回执，单截一句回答容易漏掉错误位置。

**例子：**主驾说“今天情人节，先导航回家吧，路上顺道买束花”。若检查时发现第一轮就搜沿途花店，我先取本轮导航状态；确实未导航，就回第四段检查搜索前提和同轮动作。若模型拿到的状态本身已经错了，就按第十段回查组装。先找最早的偏差，再决定修背景还是修教法，交出对应负责方和复测输入。

**案例：建议被变成了未来委托** 第十一段讲过后排休息建议被示例扩成任务；复述时点回“谁交办了未来责任”这道检查，修订时把任务定义与相关示例一起统一。

这一段讲给别人听，可以这样说：我用回家买花串起固定规则、现场背景、四项输出和逐轮结果。我会把等待、权限和停止条件讲清，指出这一版在哪一步教错了模型。改完再用正反例、安全边界和完整任务检查，让每一项改动都有对应的行为结果。

**例子：**主驾说“今天情人节，先导航回家吧，路上顺道买束花”。查“相关记忆”时，我回第十段找这轮家地址；查“导航域串行”时，我回第四段检查先后；查“询问后等待”时，我回第三、八段检查选花店的停点。拿到各步输入以后，才能判断该发路线、该搜店还是该留空动作。术语表省去翻找时间，具体允许条件仍在正文，评审可以问：“你用这个词指的是哪一轮、哪一项决定？”

**案例：事件与事件历史容易叫成同一件事** 第十段讲过两者的使用时点；复述时分别指向“这一轮新来的变化”和“帮助理解刚才的背景”，避免把过去变化再办一次。

**案例：可以为空与可以省字段混在一起** 第三段讲过表情字段的教法问题；查词以后还要回到输出约定，统一空值形式，再同步修改相关示例。

这一段讲给别人听，可以这样说：我用术语表找负责这项决定的段落，再看这个词属于规则、背景、输出还是执行入口。我会把当前事件与历史、工具回执与用户交办分别说明。查出名称以后，我还会回到本轮具体内容，判断它是否足以支撑动作和回答。

**例子：**主驾说“打开铁路 12306”。Planner 收到打开应用的动作，选系统设置 `vehicle_system_settings`，等回执回答是否打开。换成“查明天上海到北京的余票”，它保留日期和两地，交任务入口 `task_agent` 的 `task_text`（任务原话字段），等应用办理结果。这一对说法按第五段的分界走；评审问：“两个动词对应的业务结果一样吗，为什么选这个入口？”把英文名和职责同时核对，会多一步检查，却能看出名称正确、业务选错的调用。

**案例：订座标题带排队，动作说明只覆盖订座** 我们评审这一版时发现，排队出现在工具中文名中，具体操作却只定义了订座及其查询、修改、取消。读者容易把标题理解成排队已经可直接交办。问题在工具范围，会教模型仅凭标题扩展承诺。应补上排队的适用说法、最小参数和返回阶段，或收窄名称；评审问：“用户说‘帮我取号’，本轮到底交什么、等什么结果？”

为了查找方便，这里把这一版表情按用途归为六组，每条只归一组。**49 条记录里有一个重复标识。**开心的 `happy` 出现两次，所以不同标识共 48 个；分组数量按记录数相加。

| 阅读分组 | 这一版记录数 | 几个例子：中文名与标识 |
|---|---:|---|

### 逐项改法：D01～D31 都要落到明确的修改对象

下面每项用一句话保留偏差与改法。**先改会教错的条件和示例，再检查模型行为。**第十一段按影响分组，第十二段讲测试方法；这里便于逐项跟进，避免只修了最显眼的几处。

| 编号 | 这一版要改什么 |
|---|---|
| D01 | 统一自发任务的来源、授权、确认与持续范围，让顶层规则、任务定义、后排休息和制冷示例使用同一种条件，避免把建议或即时操作扩成未来委托。 |
| D02 | 给导航启停、地图显示、路线引导和智驾实际动作分别确定唯一归属及状态优先级，避免同一句开始导航或路口转向随机落到两个入口。 |
| D03 | 请底盘能力负责人校正“入弯灵活度调小”被映射成“动能回收强度调小”的动作，并同步检查相邻技巧与正反例，避免调成另一种驾驶参数。 |
| D04 | 把 `task_agent_update`、`route planning`、`customised_playlist_agent` 等名称与当前定义统一，氛围灯、界面点击工具按本轮实际开放情况补定义或改示例，避免调用与回执认错入口。 |
| D05 | 修复这一版 121 个输出块中 6 个非法 JSON，并一起修输入中的裸换行和未转义引号，再检查参数结构，避免把不可读取的格式教给模型。 |
| D06 | 将零重力座椅按座位、行驶状态、挡位和音区列成统一条件，明确副驾“无挡位限制”仍受哪些前提约束，避免模型误放行行车操作。 |
| D07 | 把高德示例中两处同轮导航工具调用改为分阶段串行，等前项结果再发后项，避免把参数齐全当成可以同时改导航的充分条件。 |
| D08 | 把主例添加途经点的回执对回路线规划，并在成功后的输出中清空该动作，避免模型把重复添加学成完成闭环。 |
| D09 | 统一“去花店”这类模糊目的地由谁先给候选、何时让用户选、失败后怎样接回，避免地点搜索与路线规划相互转交或跳过选择。 |
| D10 | 把具体商家详情查询与前往某地导航的范围分别说清，保留查店详情能力，避免模型把查营业时间误拒成精准导航。 |
| D11 | 按形象端可用值统一表情的标识、名称、字段键和引用，处理比心位置、开心重复、后 17 条键名及缺项，避免选出无法对应动画的值。 |
| D12 | 明确四项输出的必填、选填、空值类型和唯一动作结构，统一示例中表情为空或省略的写法，避免接收方要猜每轮会交什么字段。 |
| D13 | 统一基础信息记忆对事实与偏好的记录、更新范围，把查询交给记忆检索，避免把读内容与写内容混成同一入口。 |
| D14 | 按本车型实际接入统一视频工具对腾讯视频和哔哩哔哩的长视频范围，避免错误拒绝或提前承诺本车无法完成的搜播。 |

**例子：**二排左乘客说“宁字做错了，是宁静的宁”。按 D29 修示例时，输入先保留这句用户原话、说话人、二排左座位和时间。Planner 结合刚才注册的名字，判断这次在纠字，交给人脸记忆工具修改为陈宁。收到修改成功以后才确认。若输入只是一般工具成功回执，就没有这次用户纠正，不能凭空改名；评审问：“这句话是谁说的，为什么允许修改这个人的称呼？”

**案例：尊重左右指向，被误读成所有方向都能识车** 我们评审这一版时发现，视觉工具一处限制车辆识别的左、右、后方向，另一处又强调用户问左边就看左边。用户按后一条理解，会以为各方向车辆都能问；模型却缺少区分场景的条件。问题在能力范围，要补对象与方位的对应关系，再测左侧车辆、左侧舱内人物和屏幕对象等相邻说法，分别检查应调用还是应解释限制。

逐项改动会增加维护与测试量，先用第十一段的分组判断影响，再按第十二段补对应正反例。评审可以问：“这一项具体改了哪条规则、哪轮示例，什么输入能看出改动生效？”如果输入本身缺身份或车况，就沿第十段先补本轮背景，避免把缺事实归成模型没遵守。

这一段讲给别人听，可以这样说：我读数字会带上这一版和计数对象，查工具会同时看名称、职责与本轮是否开放。我用示例主题、插槽拼写和逐项编号定位修改，再把每项送回对应测试。最后我仍回到同一次交办，看该等时有没有等、成功后有没有停。
