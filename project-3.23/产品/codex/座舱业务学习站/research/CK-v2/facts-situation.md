# 情境理解事实

下文「情境提示词」指原始素材 `planner 架构/豆包情境理解.md`，行号对应原件。「设计」表示提示词约束。当前状态、通用版本边界与跨模块交接见 [共同事实](facts-shared.md)。

## 定位与边界

- 【设计】情境理解以车内 AI 伙伴豆包的第一视角，综合车内外所见、所听和共同经历，判断车里此刻经历了什么。见情境提示词第 1–5、68–74 行。
- 【设计】在场者及关系从 `current_situation` 和 `chat_30min` 获取，换车或换一群人也不默认沿用前一群人的关系。见情境提示词第 3–5 行。
- 【对照】现行 Planner 常用近 30 分钟内最近 5 轮有效对话以及数量受限的事件，四层情境设计把较长经历、当前行程和对话转折压成可复用背景。见 `component-cards.md` 卡片 30 与情境提示词第 9–14 行。
- 【对照】上下文服务为某轮 Planner 请求取数和组装背景，情境理解按自身窗口先产生可供使用的四层状态。见 `component-cards.md` 卡片 27、30 与情境提示词第 76–112 行。
- 【对照】事件日志留按时间记账的原料，情境理解可阅读原料并把对话话题、气氛和当前重点整成一段时间线。见 `component-cards.md` 卡片 50、96 与情境提示词第 16–24、82–85 行。
- 【对照】记忆生成和召回支持按人、事及偏好跨期找回信息，四层情境的直接产物是一份随车内情况前进的当前描述。见 `component-cards.md` 卡片 48–54 与情境提示词第 9–14、104–112 行。
- 【对照】Advisor 的输出是值不值得发的服务建议，情境的输出是当前四段背景，其 JSON 没有服务决策或工具动作。见 `component-cards.md` 卡片 115、118、123 与情境提示词第 104–112 行。

## 运行、输入、输出和使用

- 【设计频率】任务说明指定白天每 2 分钟一次 Tick（一次定时观察），情境提示词可直接核对到每次取最近 2 分钟增量和最近 30 轮 Tick 输出。见情境提示词第 76–96 行。
- 【设计】`current_situation` 提供上一轮 L1–L4 和各层持续时间，是逐字复用的基准。见情境提示词第 76–79、104–110 行。
- 【设计】`history_situation_30` 提供最近 30 轮 Tick 输出，供 L4 真需要重写时找旧时间线。见情境提示词第 46、80–81 行。
- 【窗口换算】在每 2 分钟成功产出一次且无中断的回放中，30 份历史 Tick 约跨一小时，L4 的近半小时仍按实际事件时间理解。依据情境提示词第 14、46、80–85 行与 `豆包内核.md` 第 1 行，时长为换算。
- 【设计】`chat_30min` 提供最近 30 分钟的纯文本对话，含时间戳、说话人、所在位置、内容及豆包发言。见情境提示词第 82–83 行。
- 【设计】`event_30min` 提供最近 30 分钟导航、路况、车况、车窗等事件流的纯文本。见情境提示词第 84–85 行。
- 【设计】`self_kernel` 是情境模块能读到的当前豆包自我内核，放在背景输入。见情境提示词第 86–87 行。
- 【设计】本轮 `user` 消息承载 `chat_2min`、`event_2min`、`vision_2min` 三份最近 2 分钟的文本增量。见情境提示词第 90–96 行。
- 【设计】`vision_2min` 是车内外视觉的文字内容，提示词所写的窗口内片段约每 10–15 秒一条。见情境提示词第 96 行。
- 【设计】每次发出固定键 `L1`、`L2`、`L3`、`L4` 的 JSON，值都是单段字符串，四层全不变也照常输出四层。见情境提示词第 104–112 行。
- 【设计】输出只留层的正文，不能加嵌套对象、段落标签、名称前缀或「已持续」。见情境提示词第 108–112 行。
- 【设计】长短上限以字计，L1 为 200、L2 为 80、L3 为 60、L4 为 300。见情境提示词第 111 行。
- 【接入边界】如何供 Planner 读取目前只有方案方向，ME7 现行输入契约和 12 个动态插槽没有四层情境。见 `planner-sp-20261117/planner-sp.md` 第 5–33、2912–2979 行。

## 四层的时间范围和更新

- 【设计】L1 面向周至月，可并列写关系、工作、身体、家事、旅行等背景，原文要求同段并列背景用分号隔开。见情境提示词第 11 行。
- 【设计】L1 确认有新事实即整段重写，写入依据要求跨轮的记忆、对话或多次观察，一次玩笑不入层。见情境提示词第 58–66、119–120 行。
- 【设计】L2 面向当天，覆盖日期、限行、会议、交付、当天计划或明确变故，也可写与当下日程有关的明日安排。见情境提示词第 12、58–65 行。
- 【设计】L2 只接受日期和计划层面的新事实，临时催促、情绪、上下车、吃饭或办事结束放当前事件或 L4。见情境提示词第 60–66 行。
- 【设计】L3 面向一次驾驶，只在上车启动出发、到目的地停稳入位、人推门下车结束这三个点分别改写一次。见情境提示词第 13、48–56 行。
- 【设计】进车库、排队、抬杆、找位、倒车都不等于到达，熄火后还在车里聊天也不等于行程结束。见情境提示词第 50–56 行。
- 【设计】车空锁车后 L3 停止更新，人已下车且车空时 L4 保持上一轮。见情境提示词第 44、52 行。
- 【设计】L4 写最近半小时的话题顺序、状态和氛围转折、这会儿的焦点，使用相对时间并可保留「我」的感受。见情境提示词第 14、16–26 行。
- 【设计】L4 只在出现新话题或旧话题结束、气氛显著变冷或放松、焦点转移时整段重写。见情境提示词第 28–43 行。
- 【设计】寒暄、应答、重复旧话题、纯车辆操作或改措辞通常保持原文，停车操作导致焦点进入下车准备时可以更新。见情境提示词第 32–43 行。
- 【设计】一方主动搭话而另一方只短答是提示词举的氛围变化信号，记录可见行为时仍需把不确定含义标成猜测。见情境提示词第 43、70–74、102 行。
- 【设计】需要重写 L4 时接续历史 Tick 的旧 L4 与近 30 分钟聊天和事件，30 分钟前的内容可压一句或移除。见情境提示词第 46、80–85 行。
- 【设计】四层通用第一人称、具体人物/话题/地点和变化依据，不确定用「好像」「可能」「我觉得」，不评价人、不站队、不编造。见情境提示词第 68–74、114–123 行。
- 【设计】豆包的任务型回复能提供情境线索，L4 只写实际改变情境的任务进展，避免给每个工具操作写流水账。见情境提示词第 98–102 行。

## 默认逐字照抄

- 【设计】每一层单独判断有无变化，只有改变的一层重写，其他层逐字复用上一轮正文。见情境提示词第 28–35、60、106–109、116–122 行。
- 【设计】L1/L2 新事实必须改且漏更新比过度更新更糟，L4 保持高转折门槛，拿不准时按层沿用原文。见情境提示词第 58–66、119–123 行。
- 【设计】输出前检查四层齐全、照抄逐字一致、有改动的层有本窗口证据。见情境提示词第 123 行。
- 【研究推论】照抄减少模型每轮重新概括造成的细节漂移，代价是旧错误、过期相对时间或漏掉低强度变化可随多轮保留。依据情境提示词第 24、28–46、107–123 行。
- 【研究推论】相同文本可能保留可复用的模型输入前缀，收益取决于字段的摆放、其他上游变动和模型服务是否命中缓存。依据情境提示词第 106–109 行和 `component-cards.md` 卡片 31。

## 指标与观测

- 【设计可查】单轮能核对 JSON 字段及字数、应照抄层的字符差异、应改层的改动证据和行程节点是否只改一次。见情境提示词第 48–56、104–123 行。
- 【评测建议】评测集应分别计算新事实漏更、无变化误改、无证据推断、行程状态误判、空车误更和半小时边界残留，不能把人肉偏好得分当作上线表现。依据情境提示词第 28–74、104–123 行。
