# 零基础入门：先看懂这一章（新增到 V 章最前面，全部正文显示，不折叠）

## 入门 1｜这一章在讲什么，和 Planner 有什么关系

你负责 Planner。Planner 每次工作，收到的是一句**已经写成文字的话**，比如“带我去昨天那家游泳馆附近的餐厅”，外加“是主驾说的”。

这句文字不是凭空来的。从主驾在车里张嘴，到 Planner 收到这行字，中间车上和云端做了好几件事。**这一章讲的就是这几件事。**

其中任何一步出错，Planner 收到的就是错字、半句话，或者别人的话。这时 Planner 再聪明也会办错，你在 badcase 里看到的却是“Planner 理解错了”。学这一章，是为了能分清问题到底出在 Planner，还是出在它前面。

两个贯穿全程的词：
- **端侧**：在车机自己的芯片上算。不用联网，速度快，但能力有限。
- **云端**：把数据发到服务器上算。能力强，但要联网，也要多等一会儿。

每一步不是在端侧做，就是在云端做，或者两边一起做。

## 入门 2｜从张嘴到 Planner 收到文字，要过四关

例子：主驾说“带我去昨天那家游泳馆”，停了一下，又补一句“附近的餐厅”。

### 第零步：叫醒豆包（唤醒）
- **唤醒**：用户说“你好豆包”这类**唤醒词**，车机在本地一直监听这个词，听到了才算“开始跟豆包说话”。
- **免唤醒 / 全时聆听**：不说唤醒词也能直接说需求。这时系统得自己判断这句话是不是在找豆包，所以更依赖后面的**拒识**。

### 第一关：听清楚，并知道是谁在说 → 叫“声学前端”
车里有空调声、在放歌，豆包自己也可能正在说话。这一关在端侧做，发生在识别文字之前。
- **降噪**：压低空调声、胎噪。
- **AEC（回声消除）**：从录音里减掉车机自己在放的音乐和豆包的播报。不做的话，豆包会把自己说的话当成用户的新请求。
- **音区 / 声源定位**：判断声音来自主驾、副驾还是后排。标错的话，副驾要的事会被当成主驾的事去办。

这一关交出去的是：一段干净的声音，并且知道这是主驾说的。

### 第二关：把声音写成文字 → ASR（自动语音识别）
- **ASR**：输入声音，输出文字，和手机上“语音转文字”是同一件事。
- **流式识别 / 过程文字**：边听边出字。主驾刚说两个字，屏幕上先出现“带我去”，再变成“带我去昨天那家游泳馆”。这种中途文字叫**过程文字**（研发也叫中间结果、partial），会被后面的字改掉，所以不能拿它去办事。
- **二遍识别 / 定稿**：说完后，用整段录音再识别一遍，得到**最终文字**（final）。
- **热词**：识别前给 ASR 一份“常用名字清单”（导航地点、联系人等），让地名、人名更容易写对，比如不把“副驾”写成“负价”。
- **云端 ASR 和端侧 ASR（离线识别）**：两套可以同时跑。云端更准，端侧不联网也能用。
- 常听到的指标：
  - **首字延迟**：用户开口后，多久出第一个字。
  - **尾字延迟**：说完后，多久拿到完整文字。
  - **识别正确率**。

这一关交出去的是：一行还在变化的文字。

### 第三关：判断他说完没有 → VAD（语音活动检测，也就是“判停”）
人说话会停顿。主驾说完“游泳馆”，停了一下，才补上“附近的餐厅”。系统在这里两难：
- **停一下就算说完**：系统只拿到“去游泳馆”就开始导航，办错了。他要找的其实是餐厅。
- **每次都等很久**：用户会觉得反应慢。

现在的做法分两档。例子里用的数值是方案中的 300 / 600 毫秒，线上数值以项目配置为准。
1. **短停顿（Soft VAD，例子里 300 毫秒）**：先不算说完，但趁这个空当，用半句话发一个**预请求**，让云端提前做准备。
2. **用户又开口了**：刚才是按半句话准备的，那份准备不能直接用了，停顿重新计时。
3. **长停顿（Hard VAD，例子里 600 毫秒）**：认定说完。ASR 再整段识别一遍，得到最终文字：“带我去昨天那家游泳馆附近的餐厅”。

切句太早，Planner 收到的是半句话；切句太晚，用户觉得反应慢。

这一关交出去的是：一句完整、不会再改的话。

### 第四关：他是不是在跟豆包说 → 拒识
车里的人也会互相聊天。比如副驾问主驾“你昨天去的那家游泳馆怎么样”，这句话不是对豆包说的，豆包不该插嘴。
- **拒识**：把不是对豆包说的话挡掉。
- **最终拒识**：拿到完整的一句话后，云端判断接不接。
- **流式拒识**：豆包正在说话时有人插嘴，边听边判断要不要让豆包停下来，见“入门 4”。

这一关交出去的是：一句确认是对豆包说的完整的话。

### 然后才轮到 Planner
Planner 收到三样东西：
- 那句话：“带我去昨天那家游泳馆附近的餐厅”；
- 说话的人：主驾；
- 一些背景（**Context，上下文**）：车在哪、之前聊过什么、记忆。

接下来是 Planner 的工作。它发现不知道“昨天那家”是哪家，先调用 search_user_memory 查到地址，再搜附近的餐厅，这就是 **action_list → 下游 Agent 执行 → tool_feedback**。

### 最后：说出来 → TTS（语音合成）
- **TTS**：输入文字，输出声音。Planner 生成的回复文字，由 TTS 念给用户听，这叫**播报**。（TTS 在车上合成还是在云端合成：待确认）
- **回写**：这一轮实际办了什么、展示了哪个列表，都记进对话历史。用户下一句说“第二个”，豆包才知道指的是哪个。

**一句话串起来：** 听清是谁在说 → 写成文字 → 等他说完 → 确认是在跟豆包说 → 交给 Planner → 播报并回写。每一关都在给下一关准备材料：没听清就写不对；没等他说完，交出去的就是半句话；没挡掉闲聊，Planner 就会去回答不该回答的话。

## 入门 3｜端云：同一句话，车上和云端各算一遍

### 为什么两边都要算
- “打开空调”：车上自己就能办，几百毫秒就能执行。专门联网问云端反而慢，在隧道里断网还会办不了。
- “带我去昨天那家游泳馆附近的餐厅”：要查记忆、要联网搜餐厅，车上的小模型办不了，只能交给云端的 Planner。

所以系统不是车上算完再交给云端，而是两边同时开工。以赛力斯的链路为例：同一段声音，一份进车上的离线识别，一份进云端 ASR，车上不用等云端。

### 车上那条路：先查对照表，再请小模型
1. **固定说法**（研发也叫高频缓存、正则缓存）：一张“这么说就执行这个”的对照表，比如“打开空调”。只有不依赖前文、意思明确的话才能放进去。“暂停播放”要知道当前在播什么，“就选它了”要知道“它”是谁，这两句都不行。
2. **端侧车控模型**（Qwen3 1.7B）：理解更多说法，把一句话翻译成**函数调用（FC）**。例如“副驾座椅加热开两档”，翻译成功能=座椅加热、位置=副驾、档位=两档。

车上最后交出三种结果之一：

| 车上的结论 | 意思 | 例子 | 接下来 |
|---|---|---|---|
| 能办（给出 FC 候选） | 有把握能办，并且参数已填好 | 副驾座椅加热开两档 | 还只是候选，要经过仲裁才能执行 |
| reject（拒识） | 有把握判断这句不是对豆包说的 | “老张你……” | 按采纳规则处理，不能在所有情况下都压过云端 |
| unsupported（办不了） | 可能是给豆包的请求，但车上办不了或拿不准 | 找游泳馆附近的餐厅 | 交给云端，不能当成“不理用户” |

最容易混的是 reject 和 unsupported：reject 是“这句不该接”，unsupported 是“这句该接，但车上没能力办”。

### 云端那条路
先做**最终拒识**（Doubao-Seed-2.0-lite），判断这一整句是不是在找豆包。如果是，就交给 Planner 规划和调用工具。

### 端云仲裁：两边都有结果，听谁的
本地算得快，不代表它的结果就能先执行。决定采用哪一边的环节叫**端云仲裁**。下表是资料里的赛力斯规则，上汽 D6X 以项目当前生效的版本为准。

| 情况 | 例子 | 听谁的 | 原因 |
|---|---|---|---|
| 命中固定说法 | “打开空调” | 车上直接执行 | 对照表经过准入限制，可靠又快 |
| 有网，云端按时返回 | 找餐厅 | 听云端 | 云端看到的信息更全，能力更强 |
| 断网，或云端 3 秒还没返回 | “副驾座椅加热开两档” | 用车上的候选兜底 | 候选满足采纳条件，就不让用户一直等 |
| 云端超时，车上也办不了 | 找餐厅时断网 | 提示网络异常 | 不能编出一家餐厅给用户 |

硬规则：车上已经执行了，后到的云端结果就不再执行，否则同一个动作会做两遍。

### 车上办完，也要告诉云端（回写）
用户说“打开空调”，车上执行了；接着又说“再低一点”。这句话交给云端时，云端必须知道刚才开了空调、开到多少度，否则接不上。所以每一轮都要回写：用户说了什么、采用了哪一边、实际执行了什么，执行失败也要记。

### 做错会怎样
- 把找餐厅判成车上能办：查不了记忆，结果办错或者没反应。
- 把“副驾”填成“主驾”：话听清了，但指令写错了，开错了座位。
- 车上办成了但回写失败：下一句“再低一点”接不上。

**面试一句话：** 同一句话车上和云端并行算。车上先查固定说法，再用小模型给出车控候选，或者判断办不了交云端。仲裁时，固定说法命中可以先执行；有网听云端；断网或超时用车上的候选兜底；已经执行过的，云端结果晚到就不再执行。最后把实际结果回写，保证下一句接得上。

## 入门 4｜打断：豆包正在说话，用户插嘴了

### 场景和两难
豆包正在介绍刚搜到的餐厅，主驾插了一句：“帮我把副驾座椅加热打开。”车里还坐着副驾。
- **豆包一直讲完**：主驾得和它抢着说话。
- **一有人声就停**：主驾和副驾聊天、咳嗽一声，都会把豆包打断。

所以要在主驾还没说完时，就判断这次开口是不是在找豆包。这个过程叫**打断**（研发也叫 barge-in），中间“边听边判断”的环节叫**流式拒识**。（流式拒识跑在车上还是云端：待确认）

### 第一步：先按规则分流，不是每次都请模型

| 豆包在播报时 | 系统怎么做 |
|---|---|
| 用户开口就叫“豆包” | 直接停止播报 |
| 车上只有一个人，识别出超过两个字 | 直接停止播报，不请模型 |
| 车上有多人，超过两个字，开头没叫“豆包” | 请流式拒识模型判断 |

“超过两个字”是为了过滤“嗯”“啊”、咳嗽这类短声音。“一个人还是多人”也是系统判断出来的，人数判错就会走错这张表里的分支。

### 第二步：每出一版文字，模型就判断一次
识别文字一版一版地更新：“帮我”→“帮我把副驾”→“帮我把副驾座椅加热”→整句。每来一版，模型就读这版文字加最近的对话，给出三种结论之一：
- **召回**：在找豆包，通知车上停止播报；
- **拒识**：不是在找豆包，继续播报；
- **继续等**：信息还不够，等下一版文字。

只有“帮我”两个字时，后面可能是“把副驾座椅加热打开”，也可能是对副驾说“拿一下水”，所以只能等。

### 第三步：停止播报，不等于打开座椅加热
流式拒识只决定豆包要不要闭嘴，好让主驾把话说完。停播之后，这句话还要像普通请求一样，把流程走一遍：

继续收音 → VAD 判断说完 → 拿到定稿文字 → 最终拒识判断接不接 → 车上或云端去办 → 仲裁 → 执行

两次判断可能不一样：前半句像在找豆包，所以先停了播报；整句话结合前文一看，其实是在和副驾聊天，那就不执行。

### 同一句话会经过三个模型（两个 1.7B 各管什么）

| 模型 | 什么时候用 | 收到什么 | 交出什么 | 能不能直接执行 |
|---|---|---|---|---|
| 流式拒识（Qwen3 1.7B） | 用户还在说的时候 | 过程文字 + 最近的对话 | 召回 / 拒识 / 继续等 | 只能决定停不停播报 |
| 端侧车控模型（Qwen3 1.7B） | 车上那条路处理时 | 车上识别出的文字 + 有限的历史 | 函数和参数（FC 候选） | 不能，要经过校验和仲裁 |
| 云端最终拒识（Doubao-Seed-2.0-lite） | 拿到定稿文字后 | 定稿文字 + 对话历史 | 接 / 不接 | 不能，通过了也只说明这句该处理 |

### 做错会怎样
- **误打断**：乘客之间聊天，豆包却停了。
- **停得太慢**：主驾已经在提问，豆包还在讲。

这两个指标要一起看。被打断的介绍要不要接着播，属于 I 章“插话、打断与恢复”。

**面试一句话：** 豆包播报时用户插话，先按规则分流：叫了豆包，或者车上只有一个人且说了超过两个字，就直接停播；车上有多人时，才请流式拒识模型逐版判断。停播只是让用户能说完，这句话还要经过判停、定稿和最终拒识，才决定接不接、交给谁办。

## 入门 5｜行业词速查表

| 词 | 在哪一步 | 在哪里算 | 输入 → 输出 |
|---|---|---|---|
| 唤醒 | 开始前 | 端侧 | 声音 → 开始收这句话 |
| AEC / 降噪 / 音区 | 第一关 | 端侧 | 原始声音 → 干净的声音，加上说话座位 |
| ASR | 第二关 | 云端为主，端侧有离线识别 | 声音 → 文字 |
| 热词 | 第二关 | 云端 ASR | 名字清单 → 名字更容易写对 |
| VAD | 第三关 | 端侧 | 声音有没有继续 → 说完了没有 |
| 预请求 | 第三关 | 云端 | 半句话 → 提前准备好的判断 |
| 流式拒识 | 打断时 | 待确认 | 过程文字 → 停不停播报 |
| 最终拒识 | 第四关 | 云端 | 完整的一句话 → 接，或不接 |
| 端侧执行 / FC | 端云分叉 | 端侧 | 一句话 → 车控指令，或“办不了” |
| 端云仲裁 | 端云分叉 | 端侧 | 两边的结果 → 采用哪一边 |
| Planner | 处理 | 云端 | 一句话加背景 → 要调用的工具 |
| TTS | 回复 | 待确认 | 文字 → 声音 |
| 回写 | 结束后 | 云端记录 | 这一轮的实际结果 → 下一轮用的对话历史 |
