## 一句话结论

本次会议确认的不是单独一段 SP，而是一条“TaskService 动态注册和下发—端侧 VLM 输出自然语言描述—TaskService 转发动态结果—Trigger 用统一语义模型判定—命中后回调 TaskService”的舱内动态 VLM 条件触发链路。

会议同时明确：动态 VLM 结果不走 Context、任务 ID 用于上下游对齐、端侧最多同时承载三个动态任务、Trigger 按上报驱动推理、不做固定轮询、不抽标签、模型只输出三态结果。场景删除、一次性任务、端侧承接模块、定时能力、舱外能力和整体 DDL 没有在本次会议中全部定完。

## 会议讨论脉络

### 1. 背景与目标（00:01:31—00:02:38）

- 用户提出“后排宝宝哭了告诉我”“有人抽烟提醒我”等持续观察类任务。
- 端侧 VLM 只提供画面描述，不直接给出“条件达成/未达成”的业务结论。
- 因此需要云端 Trigger 把描述与用户目标进行语义比较；条件达成后再把结果推给 TaskService。

### 2. 任务注册与触发是两个阶段（00:02:38—00:07:45）

注册阶段：

1. 用户 Query 进入 Planner/Director。
2. Planner/Director 判断这是持续观察任务，交给 TaskService。
3. TaskService 创建任务，并做两路动作：
   - 向 Trigger 注册推理场景，提供任务标识、感知目标和命中后的回调动作。
   - 向端侧下发动态 VLM 任务，使端侧开始针对用户目标持续输出描述。

触发阶段：

1. 端侧 VLM 输出“任务编号/ID + 当前识别描述”。
2. 动态结果经端侧数据中心和云端 TaskService 长时任务模块转发给 Trigger。
3. Trigger 找到该 ID 对应的注册场景和感知目标。
4. Trigger 将“感知目标 + VLM 当前描述”交给语义模型判断。
5. 达成时回调 TaskService；未达成时不执行任务，等待下一次上报。

### 3. TaskService 必须同时负责两条腿（00:09:41—00:15:22；00:52:26—00:53:12）

- 第一条腿：向 Trigger 注册场景。
- 第二条腿：向端侧下发动态 VLM 目标，并在动态结果上报后转发给 Trigger。
- 会议最后刘杨再次确认：云端长时任务字段模块属于 TaskService；动态高频 UP 结果也是由 TaskService 转给 Trigger。
- 因此 Trigger 不直接向端侧 VLM 拉取结果，也不承担动态任务下发。

### 4. 任务 ID 的真实作用（00:11:11—00:19:27）

- 任务 ID 不是固定类别枚举，不表示“8 就是哭泣”之类的预训练标签。
- 任务 ID 不要求模型理解其业务含义；模型真正理解的是自然语言目标和观察描述。
- 任务 ID 用于路由和关联：Trigger 必须知道本次上报属于哪一个已注册任务，才能取到正确的目标。
- TaskService 下发给端侧的 ID、端侧结果带回的 ID、Trigger 注册场景绑定的外部任务标识必须一致。
- 如果存在多个动态任务，不能把任务 A 的描述与任务 B 的目标配对。

### 5. AlwaysOn Context 与动态 VLM 是两条数据链路（00:19:50—00:27:44；00:34:14—00:35:00）

默认 AlwaysOn 链路：

- 端侧没有额外动态目标时也会运行默认 VLM 任务。
- 默认结果通过端状态上传到云端 Context。
- 内容可能是乘客列表、位置、状态等整包描述。

动态 VLM 链路：

- 用户创建的针对性动态任务结果不进入 Context。
- 动态结果走独立 Topic，经 TaskService 的长时任务模块转发到 Trigger。
- 默认结果和动态任务结果是两个 Topic，端侧数据中心在其中主要承担透传。

会议中间曾讨论能否把 Context 的整包描述也交给模型做条件判断，但对于本次“TaskService 动态注册 VLM 场景”的链路，最终对齐的是独立动态结果路径。当前 Q11 技术方案也只设计了动态推理场景注册和 `scene_id + data` 触发接口。

### 6. 端侧任务如何执行（00:09:07—00:11:11；00:27:44—00:29:31）

- 端侧同一时间只进行一次 VLM 推理流程。
- TaskService 下发的多个动态目标会与原有舱内 AlwaysOn 高频任务拼接到同一份端侧 SP/任务输入中，而不是为每个目标独立起一个 VLM 进程。
- 端侧当前最多同时拼入三个动态任务。
- 三个任务虽然一起推理，但每个任务必须通过 ID 与自身的目标、位置和结果对应。
- 高优先级端侧任务可能抢占 VLM，导致动态结果某次没有上报；会议没有给出用户侧超时或补偿方案。

### 7. 第四个动态任务怎么处理（00:40:40—00:42:24）

- 端侧上限为三个同时运行的动态任务。
- 第四个任务不能直接继续叠加到端侧。
- 任务侧支持增删改；可以先删除或替换一个已有任务，再下发新的三任务集合，例如从 1、2、3 更新为 1、2、4。
- 达到上限时，倾向由 Advisor/TaskService 与用户交互兜底，并通过任务中心 HMI 让用户管理已有任务。
- 会议没有形成完整的第四任务交互文案、默认替换策略和优先级规则。

### 8. 位置如何对应（00:33:17—00:34:14）

- 多个动态任务可以拼到同一份端侧 SP。
- 每个任务的自然语言目标本身包含位置，例如“后排宝宝哭了”“副驾宝宝睡着了”。
- ID 用来锁定哪条结果属于哪条任务，模型再比较该任务目标中的位置和对应描述中的位置。
- 会议没有给出“二排右侧=副驾后方”等完整位置映射表；当前 PRD 中的映射属于后续产品规则，不是本次会议逐项确认的结论。

### 9. 为什么不做标签抽取（00:15:48—00:17:03；00:35:02—00:35:52）

- 端侧输出是开放式自然语言描述，用户目标也可能是长尾自然语言。
- 如果先抽“哭闹/睡眠/抽烟”等标签，需要维护大量枚举和转换规则，不能覆盖长尾目标。
- 会议最终选择统一语义匹配：把自然语言目标和自然语言观察描述直接交给模型判断。
- 因此不需要先把 Caption 转成标签，也不需要每类任务分别写规则。

### 10. 模型输入与输出（00:06:12—00:06:56；00:35:44—00:37:04）

模型真正需要的语义输入：

- 感知目标：TaskService 注册时保存的自然语言目标。
- 观察结果：端侧 VLM 本次上报的自然语言描述。

ID/scene_id 是服务端路由字段，不需要模型解释。

输出结论：

- 不抽标签。
- 最终输出三种状态：达成、未达成、无法判断。
- 不输出置信度，因为会议没有定义任何下游消费策略。
- 不输出依据。依据被认为主要用于 Debug，不会显著提高业务判断准确率；最终选择直接输出结果。

会议没有确定具体模型规格。会议中只讨论“可能用轻量模型”；后来才在刘杨单聊和 Q11 技术方案中确定先用 Doubao-Seed-2.1-Pro 测效果。

### 11. 推理频率不是云端轮询（00:07:45—00:09:27；00:37:07—00:38:08）

- 端侧动态 VLM 预计以不固定周期上报，会上估计约 10—20 秒一次。
- Trigger 不设置固定 11 秒、30 秒等轮询任务。
- 端侧上报一次，云端处理一次；没有上报就不调用模型。
- 网络和处理会自然产生少量延迟，但不改变“上报驱动”的原则。
- 刘杨提出了上一次云端模型还没完成、下一次上报又到达的并发风险；会议只提出问题，没有给出最终策略。
- 后续 Q11 技术方案补充了默认 30 秒最小间隔，以及“未出首 Token 则取消旧请求、已出首 Token 则缓存最新请求”的实现方案。这是会后技术设计，不是 7 月会议结论。

### 12. 命中后的边界（00:06:56—00:07:45）

- 达成：Trigger 通过注册时配置的 Action 回调 TaskService。
- 未达成：不回调任务执行，等待下一次 VLM 上报。
- 会议没有讨论清楚“无法判断”是否回调、是否结束任务或是否转成创建失败。
- 会议也没有确定命中后场景如何删除、VLM 任务是否都是一次性任务。
- 场景失效是刘杨会后单独追问的问题；当前 Q11 技术方案的正式设计是：Trigger 回调后，由 TaskService 根据任务执行结果决定是否调用已有接口删除场景。

### 13. 定时任务不属于本次 VLM 条件链路（00:38:12—00:40:11；00:43:07—00:44:01）

- 当前讨论的是“条件满足时触发”，即使条件由模型判断，本质仍是条件触发。
- “每分钟看一次宝宝”“10 分钟后看看宝宝是否睡着”等属于定时或定时+视觉组合。
- 本次会议没有完成定时器方案，也没有要求当前 VLM 链路额外做云端定时轮询。
- 与会人倾向后续单独评审定时能力；具体是否同一期、依赖谁、何时上线没有定案。

### 14. 舱内和舱外边界（00:49:42—00:51:53）

- 本次动态链路只覆盖舱内 OMS/VLM。
- 舱外当前没有同样的端侧动态描述生产能力。
- 舱外 VQA 是按需调用的工具：Planner/模型需要时主动调用，VQA 返回 Tool Feedback；不是持续上报、不是 Context 订阅，也不是本次 Trigger 动态 VLM 链路。
- 舱外动态 Advisor 场景是否需要纳入，需与 VQA 和 TaskService 负责人另行确认。

### 15. 模块承接和排期没有全部对齐（00:31:16—00:33:12；00:44:19—00:49:40）

会议明确需要拆成多段需求，而不能只看 Trigger：

1. TaskService 如何下发动态目标到端侧。
2. 端侧哪个服务接收下发并交给 VLM。
3. 谁负责把多条动态任务拼入端侧 SP。
4. VLM 结果如何拆解成动态 Topic 和默认 Topic。
5. 动态结果如何从 AI Service 透传给 TaskService 长时任务模块。
6. TaskService 如何转发给 Trigger。
7. Trigger 如何推理并回调 TaskService。

当时的状态：

- 斯华被认为负责端侧 SP 拼接和结果拆解。
- 端侧具体宿主/消息处理模块仍需找赵衍、汪帅、杨哥等继续确认。
- TaskService 长时任务模块的具体承接和上线时间需要找晓伟确认。
- Context 8.4 节点只对应默认链路，不能直接代表动态链路的 DDL。
- 动态链路整体交付节点没有在会上定下来。

## 会议已确认的结论

1. 本期核心是舱内动态 VLM 条件触发。
2. TaskService 同时负责 Trigger 注册和端侧动态任务下发。
3. 动态 VLM 结果经 TaskService 转发给 Trigger，不进入 Context。
4. ID 用于任务关联，不是任务类别标签。
5. 模型使用自然语言目标和自然语言描述直接做语义匹配。
6. 不做标签抽取。
7. 输出只保留达成、未达成、无法判断；不保留依据和置信度。
8. Trigger 由上报驱动推理，不做固定轮询。
9. 端侧同时最多承载三个动态任务，可通过增删替换任务集合。
10. 当前范围不含定时器方案和舱外 VQA 链路。

## 会后技术方案已经补充的内容

以下来自 Q11，不应写成 7 月会议原结论：

- 场景类型：`vlm_inference`。
- 注册字段：`external_unique_id` 可使用任务系统 ID，`InferenceParams.goal` 保存推理目标。
- 触发字段：`InferenceTriggerParams.scene_id + data`。
- Action：`callback_rpc_task_service`。
- Trigger 在“判断结果”字段完整输出后回调 TaskService。
- 场景执行最小间隔默认 30 秒，可由创建方配置。
- 并发时根据首 Token 状态取消旧请求或缓存最新请求。
- Trigger 回调后，由 TaskService 根据任务执行结果决定是否删除场景。
- 首期先使用 Doubao-Seed-2.1-Pro 验证效果。

## 当前 PRD 与会议/技术方案的冲突

1. “整条链路”章节为空，没有写 TaskService 双路下发、动态结果转发和 Trigger 回调。
2. SP 仍输出“依据”，与会议最终结论冲突。
3. SP 使用“乘客列表/物品列表/整体描述”的 Context JSON 作为主要输入示例，混入了 AlwaysOn Context 链路；当前 Q11 的动态链路应以 `goal + data` 为准。
4. PRD 没写 task_id/scene_id 的关联规则，无法防止多任务错配。
5. PRD 没写最多三个动态任务和第四个任务的产品处理。
6. PRD 没写上报驱动、端侧上报可能被抢占、云端并发策略及端到端时延。
7. PRD 没写达成、未达成、无法判断各自的下游动作。
8. PRD 没写回调成功、任务执行成功和场景删除是三个不同状态。
9. PRD 没写当前仅覆盖 TaskService 动态注册，不包含预置 VLM 场景。
10. PRD 没写定时和舱外 VQA 不在当前范围。
11. PRD 没写各模块 Owner、依赖项和联调交付物。
12. PRD 没写异常、幂等、重复触发、任务取消、车辆离线和超时策略。
