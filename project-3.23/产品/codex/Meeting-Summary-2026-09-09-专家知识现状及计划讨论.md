# 《专家知识-现状及计划讨论》总结与方法论拆解

## 一、会议信息与证据边界

- **时间**：2026-09-09 20:02—21:05（GMT+08）
- **主题**：重新定义 Driver Agent 的“专家知识”是什么、怎么组织、由谁消费，以及如何与自学习、记忆、动态示例、感知和原子能力衔接
- **依据**：本地材料内嵌的原始文字记录，不是只依据 AI 智能纪要
- **参与人说明**：文字记录把几乎所有发言都标成“李明骏”，但正文显然存在多人问答。因此可以总结观点，不能据此可靠判断每句话的真实发言人或全部参会人
- **状态口径**：下文把内容分为“已暴露的现状”“方向性共识”“讨论方案”“待确认项”；会上提出的想法不等于已经上线

## 二、一句话结论

这场会表面在讨论“专家知识怎么写”，实际是在重构一套 **AI 汽车如何被教会、如何持续把一件事做好、如何越用越好用的知识运行机制**。

他们最终关心的不是再填一张场景表，而是让系统具备下面这条闭环：

> 先知道什么叫“好” → 观察当前是否达标 → 找出没达标的原因 → 采取动作 → 再观察结果 → 持续调整，直到达到标准 → 将有效经验沉淀为以后可复用的知识。

所以，这场会同时牵动了专家知识、Dynamic Advisor、Director/Planner、动态示例、用户记忆、自学习、触发器、端状态、原子能力、车型品牌差异和成本策略。

## 三、他们到底在讨论什么

### 1. 旧的“专家知识”为什么不好用

旧版本大约在 2026 年 2—3 月由赛力斯参与填写，沿用了专家测试集的一至四级场景目录。会上认为它存在四类根本问题：

1. **把具体 case 当成了通用知识**
   - 例如在“周末游”知识里直接写某个具体地点、几点吃饭。
   - 这类内容只对一个 case 有效，换一个用户、城市或时间就失效。
   - 真正的知识应是：“当用户偏好小众体验时，选点需要结合用户偏好、拥挤度、路线和时间约束。”

2. **把 know-how 和考察点混在一起**
   - know-how 是可复用的做事方法。
   - 考察点只是某条评测 case 用来判断模型有没有答对的检查项。
   - 把考察点塞进知识，会得到大量为评测题定制、无法泛化的内容。

3. **知识假设了系统并不具备的能力**
   - 一些知识把尚未接入的感知信号、触发条件或执行能力当作前提。
   - 文案即使写得很好，运行时也没有数据判断、没有工具执行，因此不可能闭环。

4. **知识放进 Director/Planner 后，多步遵循不稳定**
   - 当前主要按 query 和 context 检索知识，再注入上下文。
   - 短步骤尚可；步骤一多、任务一长，模型容易漏步骤。
   - 加入打断与恢复后，长知识更容易被新输入干扰。

这意味着旧方案不是“内容润色一下”就能解决，而是知识定义、结构、检索、消费角色和底层能力都要一起重想。

### 2. 他们重新定义了什么叫“专家”

会上形成的核心判断是：

> 专家不是记得更多注意事项，而是有明确的好坏标准，并能围绕目标持续 review（复盘检查）。

以“活跃车内氛围”为例，专家型 Agent 不能只播放一次音乐就结束，而要：

1. 定义什么叫氛围好，例如大家有参与、情绪有改善、内容符合当时情境；
2. 读取舱内状态，判断现在是否达标；
3. 如果未达标，分析是成员冲突、内容不对、互动方式不合适，还是 Agent 自己的话术不自然；
4. 选择缓和矛盾、换内容、改变互动方式等预案；
5. 执行后再次观察；
6. 未达标就继续调整，达标才结束或降低关注频率。

因此，一份真正能驱动“专家表现”的知识，至少要包含：

- 目标和场景特征；
- “好”的标准；
- AI 可获得的判断证据；
- 阶段、步骤和检查点；
- 常见失败原因；
- 不同原因对应的解决思路；
- 执行后的复查与退出条件。

### 3. 知识颗粒度：点、面、体

这是整场会最重要的抽象框架。

| 层次 | 它解决什么 | 典型结构 | 会议中的例子 | 是否持续 review |
|---|---|---|---|---|
| **点** | 一个原子动作或局部技巧怎么做得更好 | 触发条件 + 一条经验/动作建议 | 大车找停车场时避开立体车库；搜音乐何时切联网；歌词分屏的操作顺序 | 通常不需要完整闭环 |
| **面** | 一个具体情景或一类长程任务如何完整完成 | 多阶段 + 每阶段标准 + 异常原因 + 处理办法 | 接人、带人看病、一次日常出行服务 | 需要逐阶段检查 |
| **体** | 跨多个情景的长期体验目标如何持续达成 | 顶层体验标准 + 子场景拆解 + 动态建任务 | 一次好的长途游、自驾游是否轻松、是否留下好回忆 | 需要宏观、长期 review |

关键不在于“面由很多点堆起来”。会议里进一步讨论到：

- 点是碎片经验；
- 面多了**阶段关系、先后关系、检查点和闭环标准**；
- 体多了**跨场景的顶层目标，以及发现不足后创建新子任务的能力**。

所以，面和体不是更长的知识文本，而是更高层的任务结构和评判结构。这本质上是“分而治之 + 分层抽象 + 信息压缩”。

### 4. 不同知识应该由谁使用

会议中的方向性判断是：不同知识不应全部塞给同一个模型。

- **Director/Planner**：这里是同一套对话推理与执行主脑的业务名/内部名，不应理解为前后串联的两个模块。它更适合当前轮的理解、交互、任务创建、任务拆解和下游动作调度。
- **Dynamic Advisor（动态顾问）**：更适合持续盯住一个长目标，按标准反复观察、诊断、提出下一步任务，尤其适合“面”和“体”。
- **静态 Advisor**：可以持有领域内相对稳定的专家要求，给当前场景提供建议。
- **点状知识**：更像当前动作的使用技巧，可按 query、行为或工具检索后提供给执行侧。

理想运行链路可以理解为：

> 用户提出长期目标 → Dynamic Advisor 持有目标和专家标准 → 读取端状态/环境 → 判断当前差距 → 产生下一步建议或任务 → Director/Planner 负责交互和调度工具 → 下游返回 tool feedback 与新状态 → Dynamic Advisor 再 review。

这条分工仍是方案方向，具体模板、检索方式、打断恢复和模块接口没有在会上定完。

### 5. 专家知识、品牌知识和个人自学习是什么关系

会上提出了一个三层结构：

1. **基础模型能力**：豆包像一个具备通识和基础工具能力的人；
2. **品牌/车型专家标准**：上汽或赛力斯像给这个人做岗前培训，告诉它在本品牌下怎样服务才算好；
3. **用户个人偏好**：用户长期教出来的习惯和要求，原则上优先级更高。

方向上更倾向于：三层知识可以共用一套结构，但来源和优先级不同。

- 专家知识：由场景专家或车企定义，经过人工 review 后注入；
- 自学习知识：从用户明确纠正、反复使用和真实运行结果中沉淀；
- 个人知识与品牌知识冲突时，倾向优先个人要求。

但“个人知识是覆盖品牌知识、修改原知识，还是在上面叠加一层”并未最终定案；会上更偏向解耦、叠加并建立优先级。

### 6. 自学习要分阶段做

他们没有把“自学习”理解成模型自动学会一切，而是拆成两个阶段。

**短期先做可调教：**

- 系统已经有一条正确知识时，先保证它能稳定检索、稳定遵循；
- 知识替换后，系统仍能按新知识执行；
- 内部调试人员在车上直接说“你刚才错在这里，以后应该这样做”；
- 后台把明确纠正转成可检索的动态示例或点状知识；
- 调试/研发账号沉淀公共知识，正式用户账号沉淀个人知识。

**长期再做自动归纳：**

- 模型从一次任务中识别失败、绕路成功和用户纠正；
- 多次积累后归纳共性；
- 一个系统级模型判断哪些属于模型健康问题、哪些可升级为公共知识；
- 人工审核后进入公共知识体系。

他们特别警惕“一次成功绕路就自动记成知识”，因为这会产生大量噪声和错误泛化。因此，显式纠正可更快沉淀，隐式经验需要多次观察和审核。

### 7. 为什么又讨论到传感器、触发器和原子能力

因为专家闭环不是只靠文字知识完成的。

如果标准是“歌曲播完后继续播报”“接近接人地点时提醒”“大家情绪改善”，系统必须分别拿到音乐播放状态、导航位置、舱内感知等信号；如果需要调整，就必须有对应工具和原子动作。

会上提出一个非常重要的产品原则：

> **有没有能力，和当前用不用这个能力，是两个问题。**

- 底层感知、触发信号和原子能力应尽量完整，给未来组合留下空间；
- 是否订阅、是否触发、触发频率和是否调用大模型，可以在上层按场景和成本控制；
- 如果源头根本没接信号，未来想做个性化长尾场景时就没有补救空间。

这就是他们说“用通用框架满足个性化需求”的底层条件：先让系统拥有可组合的积木，再把高频场景做稳定，用通用组合覆盖长尾。

### 8. 为什么讨论到 Leading Car 和走量车型

他们把技术选择放到了产品阶段和商业使命里看：

- 第一辆标杆车（Leading Car）的任务是展示能力上限、建立市场信心，早期可以容忍一段时间较高成本；
- 后续走量车型的任务是规模化和成本控制，可以采用不同部署、信号覆盖或体验策略；
- 同一套方案不能用一个成本结论覆盖所有车型和所有阶段。

这是“按产品使命分配成本和能力”的组合策略，不是简单地说成本不重要。

## 四、会议形成了哪些方向性共识

以下是从多人反复确认中归纳出的强共识，但仍不等同于正式立项或上线结论：

1. 旧专家知识质量和结构都有问题，不能直接大规模沿用。
2. 专家知识的核心是“可判断的好标准 + 持续 review 闭环”，不是场景注意事项合集。
3. 知识至少要区分点状经验与有阶段结构的长任务知识；“点—面—体”是当前候选抽象。
4. 面/体知识更适合由 Dynamic Advisor 持有并持续追踪，Director/Planner负责当前交互和执行调度。
5. 专家知识与自学习知识可以共用结构，差别主要在生产来源、审核方式和优先级。
6. 短期先实现“可调教、能记住、能复用”，再逐步追求自动总结和自主学习。
7. 先挑少量代表性场景跑通模板和闭环，不应先批量生成一大堆未经验证的知识。
8. 感知、触发器和原子执行能力是紧迫底座；成本应通过订阅和调用策略控制，而不是提前砍掉底层可用性。
9. 产品路线采用“高频场景稳定 + 通用框架覆盖个性化长尾”。

## 五、还没有定下来的问题

1. 点、面、体最终是否是正式分层，还是只保留“碎片知识/结构化 Skill”两种形态？
2. 面类知识的统一模板具体有哪些字段？不同场景能否共用同一套模板？
3. 点与面是否需要显式引用关系，还是分别检索后由模型临时组合？
4. 不同知识由 Director/Planner、静态 Advisor、Dynamic Advisor 各自消费到什么程度？
5. 长任务被用户打断后，知识、阶段和检查点如何恢复？
6. 基础能力、品牌标准和个人偏好冲突时，完整优先级规则是什么？
7. 显式纠正、一次成功绕路、重复失败分别满足什么条件才可沉淀？
8. 公共知识与个人知识如何隔离、审核、回滚和评测？
9. 自学习在 2026 年 12 月赛力斯 SOP 前究竟交付到哪一层、用什么指标验收？
10. 自学习与记忆、条件任务、连续人设之间的边界仍需专项讨论。

## 七、他们为什么能讨论得比较深

### 原因一：他们讨论的不是名词，而是“运行时会发生什么”

每提出一个概念，他们都会继续问：谁拿到它、什么时候加载、输入是什么、怎么判断、调用什么、打断后怎么办、结果怎么回读。这会自然把产品讨论推进到系统设计层。

### 原因二：他们不断用反例拆假设

- 周末游的具体地点说明“case 不等于知识”；
- 大车避开立体停车场说明什么是点状经验；
- 接人和带人看病说明什么是面类知识；
- 自驾游是否轻松、是否留下回忆说明什么是体类标准；
- 歌词全屏改分屏说明口述调教如何转成动态示例；
- 米其林餐厅检索失败后切联网说明一次成功绕路不一定能直接变知识。

他们不是先选一个抽象框架再往里填，而是用不同尺度的案例反复检验框架是否成立。

### 原因三：他们同时具备五层上下文

1. 旧专家测试集和赛力斯填写材料；
2. Director/Planner 的上下文负载、多步遵循和打断恢复现状；
3. Dynamic Advisor、静态 Advisor、记忆、动态示例的架构方向；
4. 真实上车体验和具体 badcase；
5. 对其他 Agent 的 Skill/Memory 机制的使用经验。

会上很多话只说半句，是因为这些背景在他们之间已经共享，不是因为内容天然容易理解。

### 原因四：他们有一套稳定的推理顺序

整场会反复出现下面这条路径：

> 真实 case → 找当前方案为什么失败 → 抽象共同机制 → 划分层次和职责 → 检查底层能力是否支持 → 提出短期实验 → 再讨论长期产品与商业策略。

这种顺序让讨论既能往上抽象，也能回到落地条件。

### 原因五：他们允许“不知道”存在

会上多次明确说“还没想清楚”“这个例子不一定对”“需要再试模板”。这反而让大家能继续探索，不必为了显得确定而过早封死方案。

## 八、你为什么会觉得“我怎么不知道”

这更像是**共享上下文不对称**，不代表你理解能力不够。

1. **这不是一场从零讲背景的评审**：它直接从几个月前的旧表、旧会议和实车体验接着聊。
2. **关键信息散在多个工作流里**：专家测试集、动态知识、动态示例、Advisor、自学习、记忆、触发器并不在一个文档中。
3. **大量知识来自非正式积累**：有人在车上反复试过，有人长期用过其他 Agent，还有些思路来自之前会议、食堂讨论和个人体验。
4. **转写本身不友好**：多人声音被统一标成一个人，简称和语音识别错误很多，没有配套页面上下文时很难跟上。
5. **你的工作切入点与他们不同**：如果你主要从 Planner、Trigger 或配置平台接需求，你更容易看到“字段和链路”；他们这次从“什么才是专家体验、如何持续变好”这一层往下推，所以看起来像突然跳了一层。

你真正缺的不是再背一批名词，而是先补上这条母链路：

> 专家标准由谁定义 → 运行时谁持续持有目标 → 通过哪些端状态判断 → 由谁生成下一步任务 → Planner 如何调度执行 → 结果如何回读 → 哪些经验进入个人记忆、动态示例或公共专家知识。

## 九、他们实际使用的方法论

| 方法论 | 会上怎么用 | 你可以怎么复用 |
|---|---|---|
| **目标倒推** | 先问用户最终要“省心、稳定、越用越好”，再谈知识结构 | 评审先说用户结果，不从字段表开场 |
| **闭环控制** | 标准→观察→诊断→行动→复查 | 每个主动服务都要问“执行后谁判断真的好了” |
| **分层抽象** | 点—面—体，对应动作、场景、长期体验 | 先判断需求处在哪一层，避免把一个点包装成完整场景 |
| **分而治之** | 大目标拆成小情景，小情景拆成原子动作 | 把长程任务拆成阶段、检查点和异常分支 |
| **案例—反例校验** | 用周末游、接人、歌词分屏等检验抽象 | 每个规则至少准备一个正例、一个反例、一个边界例 |
| **职责与数据同审** | 不只问“知识写什么”，还问谁消费、数据从哪来 | 把 owner、输入、输出、状态变化放在同一张链路图里 |
| **能力与消费解耦** | 底层信号尽量全，上层决定订不订阅、调不调用 | 不用“当前不用”推导“底层无需接入” |
| **公共标准与个性化分层** | 基础模型→品牌标准→个人偏好 | 明确冲突优先级、数据隔离和回滚方式 |
| **短期可验证、长期演进** | 先让现有知识可稳定遵循，再做自动生成 | 把愿景拆成一两个可实车验收的最小闭环 |
| **双飞轮** | to C 改善个人体验；to B 汇总共性、修系统 | 个人知识和公共知识分别设准入与审核规则 |
| **产品组合思维** | Leading Car 展示上限，走量车优化成本 | 不同车型、阶段用不同成功指标 |
| **品味训练** | 通过体验优秀内容、逐帧分析来形成“什么叫好”的标准 | 专家知识生产前，先建立可共享的体验标尺 |

## 十、你下次参加这类会，可以直接问的 10 个问题

1. 这个场景最终想让用户感到什么，什么结果算真正完成？
2. 这是一个点状技巧、一个面类长任务，还是体类长期体验？
3. “好”的标准能否写成模型能判断的条件？
4. 判断这些标准需要哪些端状态、传感器、历史信息或工具反馈？
5. 当前哪些信息真的已经接入，哪些只是知识文案里的假设？
6. 谁持续持有这个目标：当前轮 Planner，还是 Dynamic Advisor？
7. 未达标时有哪些常见原因，每类原因对应什么动作预案？
8. 执行后谁回读结果，退出、继续、降频和异常条件分别是什么？
9. 这条经验应该进动态示例、个人记忆、品牌专家知识，还是底层工具规则？
10. 我们先选哪一个真实 case 跑通，验收数据和失败归因怎么定义？

只要你能沿着这 10 个问题追问，你也会很快进入他们的讨论深度；因为所谓“讨论深”，本质上就是把抽象愿景一直追到可判断、可执行、可回读、可验证。
