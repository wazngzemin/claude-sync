先别记模块名：只看车里发生的一件事

你先在脑子里放一辆正在开机的车

车里每秒都有东西在变：档位、车窗、空调、音乐、账号、任务。系统不能把每一个数字都塞给 Planner，也不能等用户开口问了才知道。所以它需要一套办法，把“值得记住的变化”写成事实。

先看现实车里或业务里到底发生了什么。
再找知情人哪个模块掌握第一手证据。
最后才记账把事实存好，给需要的人使用。
先建立四个画面
不要背词
车现在是 D一个当前数字
→
刚从 P 变成 D一次变化
→
系统写下一条事实可查、可追溯
只有第三个画面，才是我们说的“事件日志”。
先把最容易混的地方拆开

“现在是什么”“刚刚变了什么”“系统记了什么”不是一回事

D 是一个状态。P→D 是一次变化。“档位由 P 设置为 D”才是一条可读的系统事实。

很多图一上来就写 event，你会不知道它是在说数字变化、数据库记录，还是 Planner 的输入。这三件事必须分开。

系统已经知道端侧这次报了 D；运行上下文里可能有上一次的 P。
系统还不知道这次变化值不值得记、应该由谁生产、哪些业务会用。
术语在最后贴：当前数字叫“端状态”；判断变化的规则盒子叫 Trigger；写进统一底账的事实叫事件日志。
先记一句话
全貌
事实发生信号 / 点击 / 业务结果
→
正确的人记下来不是都找 Trigger
→
需要的人再使用记忆 / Planner / 下游
中间的“统一账本”就是事件服务。
整套方案只解决三件事

谁生产、怎么记、谁使用

谁最清楚事实，谁负责生产；事件服务统一保存；每个消费者按自己的规则取用。

Trigger 只是“端状态变化”的生产者。客户端和云端业务也能直接生产。Planner 也不是终点之一，它只是可能使用事实的消费者。

接下来怎么读：先跟档位 P→D 走一遍标准主链；再看删除任务、TTS 打断和下游订阅。看完故事以后，模块名会自然落位。
事件日志不是专门唤醒 Planner 的消息。它先是一份统一事实底账。

故事一：主驾把档位从 P 换到 D，系统怎么知道？

这条故事把标准主链一次讲透：端状态 → Trigger → 事件服务 → Context SP → Planner。先跟现实走，不先背接口。

评审确认的设计口径档位事件做过局部 UP 联调不等于完整业务白名单已上线

现实发生

→

档位故事 · 第 0 幕

现实动作是起点，不是 Trigger 日志

主驾真的换了档。这是唯一不能靠后面模块“补出来”的事实。

如果端侧没有把变化报出来，云上后面再聪明也没有用。产品验收必须从原始信号开始，而不是从 Trigger 的“命中成功”开始。

现实已经发生档位物理状态从 P 切到 D。
云上还不知道现在是 D，也不知道之前是 P。
下一位接手：端状态服务把车辆此刻的档位值报上来。
评审可以直接问“换挡发生后，原始端状态由哪个服务上报？联调时能不能拿到车辆、渠道、时间和原始值？”

档位故事 · 第 1 幕

车端只报“现在是 D”，没有直接报“P 变成 D”

当前值只回答“现在是什么”。它没有回答“之前是什么”。

所以 Trigger 收到 D 的那一刻，手里只有半个答案。它不能立刻写“档位由 P 设置为 D”。

Trigger 已知车辆、渠道、信号名、current_value=D。
Trigger 未知old_value 是什么；有没有变化；是否命中产品场景。
车端上报示意 vehicle_id = vehicle_xxx channel = saic signal = gear current_value = D
下一位接手：Trigger 先按渠道解释字段，再去运行上下文找旧值。

档位故事 · 第 2 幕

同名字段不能默认跨车企通用

Trigger 先看这是上汽还是赛力斯，再用对应信号表解释当前值。

不同渠道可能有不同字段、子字段和值域。如果这里选错，最常见的表现不是报错，而是“后台配置看着正常，运行永远不命中”。

这一步确认当前上报确实是上汽支持的档位 D。
还没确认是否从 P 变来，是否要生成事件。
评审可以直接问“这个信号在上汽和赛力斯分别叫什么？后台展示的是交集，还是分渠道真实支持集合？有没有一份可验的 signal define？”

档位故事 · 第 3 幕

Trigger 从运行上下文取 P，再和这次的 D 比较

有了 P 和 D，系统才第一次能说：“发生了换挡变化。”

会议口径是旧值从 Context 里拿。不能把它讲成 Trigger 临时猜旧值，也不能没证据地说 Trigger 自己持久化所有状态。

Trigger 已知old=P、current=D，确实发生变化。

档位故事 · 第 4 幕

Trigger 查找依赖 gear 的场景，再按预置表达式判断

产品配置的是 AND，就必须全部条件都成立；不是“差不多像换挡”就算命中。

这一步是规则盒子的核心。它不判断要不要对用户说话，只判断“这个预先定义的场景是否发生”。

命中后知道场景条件成立，可以执行 generate_event_log。
它不负责知道Planner 会不会说话、Context 或 UP 会不会消费。
术语现在贴上：event 是让场景开始判断的变化，condition 是检查条件，action 是命中后执行的动作。
评审可以直接问“这个场景是 AND 还是 OR？依赖的其他状态从哪里拿？缺一项时是不命中、等待，还是使用默认值？”

档位故事 · 第 5 幕

把 P→D 翻译成一条标准事实

给人看的是“档位由 P 设置为 D”；给程序用的是 old=P、current=D。

自然语言方便人和模型直接读。结构化字段方便程序精确使用。两份都要有，而且含义必须一致。

Trigger 构造的事件示意 event_id = gear_changed event_time = Trigger 匹配成功时间 event_info = 档位由 P 设置为 D resource_info = {old_value:P, current_value:D} vehicle_id = vehicle_xxx channel = saic
这里已经完成一条标准事件的构造。
这里尚未完成事件服务入库，也没有任何消费者看见。
评审可以直接问“event_info 和 resource_info 的变量来自同一份运行数据吗？模板缺变量时怎么处理？三个时间字段的口径分别是什么？”

档位故事 · 第 6 幕

Trigger 把事件送到事件服务，但“调用成功”还不是“入库成功”

RPC 只证明请求发到了接口。它不能单独证明数据库里已经有这条事件。

联调时必须保存请求体、响应、车辆、渠道、场景和 event_id。随后还要用查询接口回查。

调用方能证明我发了什么，事件服务回了什么。
仍需继续证明服务有没有补字段、有没有真正写入主库。
这一段的验收证据Trigger 原始输入 → 场景命中日志 → RPC 请求/响应，三份能按同一追踪信息串起来。
评审可以直接问“RPC 失败以后谁重试？是否补发？幂等键是什么？这些如果还没定，能否明确标成待确认而不是默认支持？”

档位故事 · 第 7 幕

事件服务补齐公共信息，再把事实写进统一底账

调用方有 event_info 就直接用；没有才用默认模板。没有 user_in_car 时，事件服务去查端状态补。

它不会重新判断 P→D 是否成立，也不会决定要不要提醒用户。它负责的是接收、补全、入库、查询和订阅。

事件服务负责公共字段、存储、查询、Listener。
事件服务不负责车企信号规则、Planner 表达、UP 历史拼接。
真正入库的证明按 vehicle_id、event_id 和时间范围查询，能返回同一条 gear_changed；自然语言和结构化字段一致。
评审可以直接问“服务返回成功以后，联调怎么回查？模板更新是否回刷历史？补不到 user_in_car 时是空值、失败还是降级？”

档位故事 · 第 8 幕

Context 按时间范围和白名单拿近期事件

事件服务存绝对时间。Context 根据本轮时刻，把它写成“3 分钟前档位由 P 设置为 D”。

这条事件只有在 SP 白名单里，才会进入本轮 SP。白名单漏配时，会出现“事件库里明明有，Planner 却看不见”。

Context 已知本轮时间、SP 白名单、查询返回的事件。
Context 不决定Planner 最后要不要表达或行动。
下一位接手：拼好的 SP 作为本轮背景进入 Planner/Director。
评审可以直接问“Context 在什么时候查？时间窗口多大？最大条数多少？查询结果和 Planner 最终 SP 入参能否同时回读？”

档位故事 · 第 9 幕

Planner 看见事实，不代表一定要对用户说

档位变化可以只是背景。只有场景真的需要，Planner 才表达或行动。

这也是事件日志和 Planner event 的区别。事件日志可以安静地存在于主库、记忆或 SP；主动 event 才是要求 Planner 立刻再决策的一种输入方式。

Planner 已知本轮 SP 带来了档位变化事实。
结果取决于用户意图、当前上下文、事件价值与动态示例。
到这里模块名才完整落位：端状态负责报数；Trigger 负责从状态生产事件；事件服务负责记账；Context 负责本轮近期背景；Planner 负责反应。
最终验收不能停在 Trigger 命中。要依次看：RPC → 事件查询 → Context 返回 → Planner 最终入参 → Planner 输出。
档位故事的主链是：车端报当前值 → Trigger 找旧值并命中规则 → 构造预定义事件 → 事件服务入库 → Context 按白名单查询 → Planner 按需使用。

例：拿到 old=P、current=D，命中预置规则后，生产“档位变化”事件。它不决定 Planner 要不要说话。

事件 / 标准事件

人话：一件已经发生、可以被追溯的系统事实。

例：“14:12 档位由 P 设置为 D”。同时带 event_id、时间、自然语言和结构化资源。

事件日志 / 事件服务

人话：统一事实底账，以及负责登记这本账的服务。

接收各生产方事件，补公共字段、入库、提供查询和订阅。它不是所有业务的判断大脑。

Planner event

人话：发给 Planner 的一张“情况通报”。

它是 Planner 输入类型之一，不天然等于事件库记录。《红豆》当前链就是直接情况通报。

event_id

人话：这类事实的稳定身份证。

程序靠它查、订阅和配白名单。名称和文案可以让人读，event_id 负责让系统别认错。

event_info

人话：给人和模型直接读的一句话。

例：“档位由 P 设置为 D”。模板变量必须与真实运行数据一致。

resource_info

人话：给程序精确使用的结构化证据包。

例：{old_value:P, current_value:D}。它和 event_info 应表达同一事实。

Context SP

人话：给 Planner 准备本轮背景材料的人。

按时间范围和白名单查询近期事件，再写成“3 分钟前……”。它不替 Planner 做最终决策。

UP

人话：把历史对话和期间发生的非对话事实一起补齐。

它不会伪造一条用户话术，而是把事件当系统背景插入，让“再建回来”有指代对象。

context_info

人话：这轮回答实际参考过哪些背景的回执。

它方便复盘“Planner 当时看见了什么”，不是事件主库，也不能替代事件入库。

Listener / TCC

人话：按产品授权名单，把指定事实通知给指定下游。

TCC 管允许哪些 event_id；Listener 负责匹配、格式转换、回调和记录结果。

tool_feedback

人话：工具执行完以后，给 Planner 的结果回执。

Planner 先输出 action_list；工具执行后才有 tool_feedback；Planner 再决定是否继续。没有 Action 就没有这一步。

Planner / Director

人话：同一个决策职能的业务叫法与内部叫法。

它根据用户请求、背景和事件决定说什么、做什么或沉默。不要把两者画成前后两个决策模块。

听到一个模块名，马上追问三件事：它拿什么输入、只负责做什么、把什么交给谁。
