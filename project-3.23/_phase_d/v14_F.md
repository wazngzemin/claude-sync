# 10 工具准入与单 Agent 协议｜v14 全景图 SVG 中的 F 模块（节点 15 个）

框标题：F · 能力准入与单 Agent 协议｜定义、运行条件和三路输出
框说明：确认当前能力与参数，调用正确 Agent，再把结果交回原业务。

## 节点（编号与文档画板一致；措辞为 10/26 最新版，含每个节点两段讲解）
### F01｜分别定义工具做什么与在哪里执行（蓝底）
- 要点：定义说明名称与业务能力实现说明接入参数、渠道和版本同一定义可以对应多个实现有工具名称还不等于当前可调用
- 讲解①：工具定义告诉模型这个能力做什么，包含标识、中文名和描述；具体实现则说明在哪个项目、通过什么参数与接入点执行。同一种音乐搜索能力可以有多个实现，未必意味着模型看见多个不同工具名。
- 讲解②：开始调用前，先找到当前项目实际选用的实现，再检查发布和运行条件。只有定义而没有可用接入，用户的需求仍无法落地。把这两层分开，也便于区分能力说明写错与实际服务接错。

### F02｜选中当前渠道与环境允许使用的实现（蓝底）
- 要点：渠道和应用隔离具体实现已发布且启用才进入可用集合集成位置与提供方分别记录是否参与模型推理单独配置
- 讲解①：同一能力可以保留多个测试草稿，运行时却要按渠道、应用、环境和启用状态选中具体发布实现。后台曾创建一个版本，不意味着当前请求已经使用它。
- 讲解②：车端或云端描述集成位置，内部或第三方描述提供方，不能混成同一种分类。是否参与 Director 推理还有独立开关，未向模型展示不等于底层能力不存在。明确选中的实现后，继续检查当前用户权限与车辆条件。

### F03｜调用前核可信权限与当前车辆能力（金底）
- 要点：读取可信账号角色与项目权限检查设备、音区和驾驶状态工具可见不保证每次都能执行拒绝时保留具体原因
- 讲解①：模型看得见一个工具，只说明它知道有这项能力。当前用户是否有权调用、这辆车有没有设备、驾驶状态是否允许，还需要独立校验，不能由模型凭感觉认定应该放行。
- 讲解②：权限来自可信账号与项目规则。设备不存在、语音暂不支持和此刻条件不满足，应分别返回，方便 Director 解释或给出允许的手动方法。被拒绝时不能伪造成功，也不能为了执行而扩大用户角色或能力范围。

### F04｜满足本轮条件后再加载动态工具（金底）
- 要点：推理前检查当前请求参数支持存在、集合及与或条件条件不符则不加入本轮工具任意状态触发需另有接入能力
- 讲解①：动态工具按本轮条件出现，无需把所有能力长期放进提示词。本图这套条件检查读取请求参数，支持字段存在与否、是否属于某集合，以及与或组合。当前有实时卡片信息时，才可能提供相应页面工具。
- 讲解②：条件失败就不加载，避免模型对不存在的界面作操作计划。更复杂车端状态或 Trigger 条件需要另外接入，不能从已有参数判断扩大成任意条件都支持。通过之后才继续准备本轮可见工具描述。

### F05｜用当前卡片内容明确页面可操作对象（蓝底）
- 要点：端侧提供卡片标识与按钮内容用户序号选择对应当前卡片无卡片不能猜出页面操作卡片更新后旧对象须失效
- 讲解①：端侧把当前卡片标识、标题、内容和按钮名放进请求，页面工具才知道眼前可以操作什么。用户说“选第二个”，必须对应这张有效卡片中的真实按钮，不能从旧历史猜一个对象。
- 讲解②：这条方式依赖请求里的实时卡片信息，不能默认所有页面都已自动进入 Context。用户说话期间卡片可能变化，因此执行前仍需核有效性。当前按钮可以操作，也不意味着整个应用的任意界面操作都已开放。

### F06｜把符合条件的工具描述放入本轮输入（绿底）
- 要点：静态与动态工具按各自条件注入描述和参数来自实际发布配置调试改动需同步管理配置当前页面能力仅在满足条件时出现
- 讲解①：可用定义与实现参数会转成 Director 本轮能读到的工具说明，动态条件成立的能力再放入对应位置。这样模型才能依据当前允许范围选择动作，而无需假设所有工具一直存在。
- 讲解②：提示词里调通的新描述，还需同步到实际管理配置并发布，参数、提示与限制才会一致生效。当前页面工具尤其依赖有效卡片和接入配置，不能仅因说明中有这个名字，就算成每辆车永久可用的一项能力。

### F07｜模型选中工具后再校验实际参数（金底）
- 要点：核工具名、必填项、类型与范围页面操作对应真实卡片按钮车控明确设备、动作与对象错误参数不能靠默认值补发
- 讲解①：Director 选中能力以后，执行层仍需按参数合同检查。卡片工具要选真实按钮并关联当前卡片，车控要有明确设备、位置、动作和允许数值，不能仅因工具存在就发一份不完整指令。
- 讲解②：参数生成错误与用户表达含糊也要分开。前者需要系统纠正，后者可以请用户补必要信息；两者都不能擅自填一个可能改变对象的默认值。校验通过并满足发布许可，才把动作交给实际执行方。

### F08｜补齐单个 Agent 的依赖并选择执行器（蓝底）
- 要点：读取元信息与所需背景填充请求并绑定业务后处理按提供方选择对应执行器总体多步计划仍由 Director 负责
- 讲解①：AgentServer 先读这一项 Agent 的元信息，再取得它需要的历史、记忆、端状态或提示词依赖，填好请求并绑定业务后处理。之后根据提供方类型选择执行器，把这次能力调用真正送出去。
- 讲解②：这一步负责单个 Agent 的内部接入。音乐工具有自己的子流程，也不意味着它可以绕过外层权限或替 Director 重排全部目标。执行器适配协议差异，结果仍要按统一返回方式交回当前调用。

### F09｜把流式返回整理成可关联的统一协议（蓝底）
- 要点：关联会话、问题、Agent 和调用接收流式内容与明确结束标志错误码和终止原因继续保留流结束不代替业务完成
- 讲解①：下游流式内容到来时，通用层按会话、问题、Agent 与追踪标识关联这次请求，再整理成统一格式。结束包中的 is_finish 表示响应流已经结束，缺少结束信息时不能悄悄当作正常完结。
- 讲解②：错误原因与已返回部分也要保存，供后续决定如何处理。即使收到正常终包，车窗是否关闭、订单是否成立仍要看业务内容。协议结束只完成了通信这一层，不能直接向用户宣布所有目标已经达成。

### F10｜分别整理给界面、声音和模型的内容（蓝底）
- 要点：界面内容保留展示结构语音内容用于相应播报链模型内容提供继续判断的事实页面透传不等于自行抢占声音
- 讲解①：统一协议后还可能有业务加工。例如音乐返回结构化歌曲列表，界面要保留列表结构，模型则需要能理解的候选事实。content 面向界面，tts_content 提供可播文字，model_content 供 Director 继续判断。
- 讲解②：三路内容不能一律当成最终回答直接播放。协议即使支持语音内容为空时使用展示文字，也仍受当前交互话语权约束。整理之后按各自出口交付，让模型、界面和声音都围绕同一真实结果工作。

### F11｜保存本次 Agent 历史并交回业务结果（绿底）
- 要点：保存真实内容与结构化观察终包结束当前 Agent 请求业务状态交执行层继续核对下一动作由 Director 再决定
- 讲解①：响应正常结束时，保存本 Agent 生成的内容与结构化观察，再把结果交回执行层。例如导航给出几条路线，下一句“选红绿灯少的”需要引用这份真实候选，不能只保留一句概括话术。
- 讲解②：历史保存也要遵守身份、隐私和会话范围。保存成功或终包结束都不会自动触发后一步，如果用户目标还差导航选择，仍由 Director 读反馈再决定。这样连续对话有依据，也不会让工具内部越过总体计划直接行动。

### F12｜仅在明确配置时直接交付工具结果（金底）
- 要点：direct_return 是条件化交付方式可跳过再次模型总结界面、文字和声音分别按协议处理未配置时继续正常反馈主链
- 讲解①：启用 direct_return 的工具，可以按配置直接交付本次结果，而不再强制送 Director 总结。它适用于明确约定的渠道与工具，不能因系统支持这个字段，就让所有执行方自行决定直返。
- 讲解②：还要分清交付的到底是界面、文字还是声音，透传卡片不自然获得自主播报权。无论是否经过再次总结，说法仍应与真实业务状态一致。未满足直返配置时继续正常反馈路径，避免同一结果又直出又重复生成回复。

### F13｜下游无法继续时把原因交回重新规划（蓝底）
- 要点：Fallback 带着无法承接原因回主链保留已有结果和外部效果Director 决定替代、澄清或结束不默认重试相同工具
- 讲解①：Fallback 表示下游无法继续办理，把原因和已有结果交回 Director，让它决定是否换允许的工具、补问或结束。比如能力不支持当前要求，回传限制比单纯报一个失败更有助于后续判断。
- 讲解②：如果此前已经形成订单或车辆动作，也必须一并说明，避免换工具再做一份相同操作。各 Agent 是否支持这种回退及何时使用，取决于实际接入。回退不是自动重试许可，后续仍要依据真实状态重新规划。

### F14｜下游明确指定下一 Agent 时由调用方转交（金底）
- 要点：Redirect 指出明确转交目标调用方核目标实现与权限携带原问题和已发生状态转交成功不等于目标执行成功
- 讲解①：Redirect 的返回会明确指出下一 Agent，由调用方按协议调度。它与回到 Director 自由重规划不同，转交前仍要核目标实现与权限，并保留原会话、问题和已经发生的事实。
- 讲解②：收到转交指令，只说明下一步去哪里，尚不能证明目标 Agent 已经执行。跳转次数、超时和循环防护需要明确接入规则，不能无限绕圈。到目标后的真实结果仍应关联回原任务，让用户知道事情进展到哪一层。

### F15｜取消连接时仍保留业务真实状态（蓝底）
- 要点：先通知下游取消再结束连接保留已经生成的内容和结果预请求需要单独约定才可启用超时重试遵守具体工具规则
- 讲解①：取消调用时，先向下游发取消要求，再断开相应连接，同时保存已经生成的内容。车辆动作、订单或文件生成如果已经发生，不会随连接关闭自动回滚，后续还需核实际业务状态。
- 讲解②：预请求也不是默认开放的正式调用，需要双方明确允许范围。超时多久、是否可重试，应按工具分别定义。尤其取消与结果同时到达时，要保住真实结果，防止新轮恢复后把旧副作用再执行一次。
