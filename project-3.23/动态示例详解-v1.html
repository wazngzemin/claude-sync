动态示例详解

依据《动态示例解bug指南》+ 0706 能力边界 + 当前 SP，结合我们这几天真实写的 30 条 case
是什么怎么写写到什么程度为什么怎么做

1动态示例究竟是什么

一句话：动态示例是「用户 query → 决策分析」的示例对，在用户说话时按相似度检索出来、临时塞进 SP（系统提示词）的 {{scenario_sample}}（场景示例）槽位，给模型当"参考答案"。

它的工作机制

用户说话
"空调改到快速制冷模式"
→
检索匹配
用 query 在动态示例库里找最像的几条
→
注入 SP
塞进 {{scenario_sample}} 槽位，模型这轮能看到
→
模型决策
参考示例的推理路径，输出正确的工具调用
两个推论（决定了后面所有写作规则）
① 检索是单条命中：模型这轮只能看到被检索到的这一条，看不到表里其他行——所以每条必须自包含，不许写"同 XX 链""参照上一条"。
② 它是给模型看的"解题示范"不是"故障报告"：决策分析里只写正确做法，bug 复盘（"之前错在哪"）写进"其他说明"列，不进 SP。

动态示例 vs 静态示例

动态示例静态示例
比喻授模型以"鱼"——这条照做授模型以"渔"——这类都会做
注入方式按 query 相似度动态检索注入，命中才进 SP常态化写在 SP 里，每轮都在
解决什么低频、无法归类抽象的单点 bug（如"让模型学会用通讯录"）某一类问题的通用能力（如多轮 react 任务拆解）
内容query + 决策分析（调什么工具），不需要完整 input/output完整的 input + output 多轮示范
成本写一个 case 治一个 case，快要提炼共性、设计多轮，重

来源：《动态示例解bug指南》开篇定义。

2什么问题该用它解、什么不该

✅ 该转动态示例❌ 不该放动态示例
简单、明确、无法抽象归类的单点 bug。典型如：模型把"查看前方路况"错路由到视觉工具；把问歌清单当成播放指令；并行删两个途经点被打断。 能提炼共性的一组例子——应做成静态示例。比如"离6月18日还有几天/春节有什么电影/下个节气是什么"是一组，共性是"时间类问题先用 timestamp（时间戳）"，一条静态示例就能教全。
模型有能力但选错路（链路走错、工具用错、参数越界、该拒答没拒答）——动态示例给它指条路就回来了。 模型推理能力本身不够（信息给全了还是推错）——动态示例只能治标，得靠 SFT（监督微调）或模型迭代治本。
对应 badcase 排查路径
链路问题（走错模块）→ 动态示例最有效；工具描述问题 → 动态示例可解，但改 SP 工具描述更治本；上下文问题（缺端状态字段）→ 先补 env_info（端状态）上报，动态示例才能写分支；模型能力问题 → 别指望动态示例。

3怎么写：格式与风格

基本格式（指南模板）

字段写什么
Query触发这条示例的用户原话（或多轮时的最后一轮）
决策分析针对这类 query，模型应如何决策的一句话：调什么工具、怎么改写、结合什么状态分什么支。只写正确做法
其他说明不进 SP 的备注：这条修哪个 badcase、失败模式是什么、依据哪条边界

风格三原则（都是我们踩坑踩出来的）

原则说明真实教训
① 一句话人话和 SP 里其他示例的口吻一致，自然语言叙述，不用符号框架第一版用【定位】【查】【分支】【边界】【调用】五要素堆叠，被批"瞎写乱七八糟"
② 自包含单条写全，禁止跨行引用检索单条命中，模型看不到别的行
③ 教推理不硬背给"结合什么状态→分什么支"的推理路径，不给脱离状态的固定答案李强批"死记硬背要推理出来"；罗丽批"必须结合 context+说话人方位+对话历史"

对照看：同一个 case 的三种写法

以"删除多个途经点"为例：

✗ 太粗（没信息量）
决策分析：
调用导航工具删除途经点。
→ 模型还是可能并行发两条，bug 照旧
✓ 刚好（定稿版）
决策分析：
删除多个途经点需要一个一个串行来（导航类工具无法并行，并行会被打断）：先调用 route_planning 删除第一个途经点，等 tool_feedback（工具返回）返回删除成功后，再下发下一个途经点的删除指令，全部删除成功后再统一告知用户。
✗ 过头（bug 复盘混进决策分析，被批"还有些问题"的那版）
决策分析：
删除多个途经点必须串行、一个一个来：先调用 route_planning_qa 删除第一个途经点……不能在同一轮 action_list 里并行下发多个途经点操作——并行时后一条会打断前一条（返回"上一条指令已被打断"），只删成一个。全部删除成功后再统一告知用户，只删成功一个时不能声称都删了。
→ 加粗部分是故障描述不是做法，且工具名 route_planning_qa 与线上 route_planning 不符

指南官方范例的风格（对照找感觉）

Query决策分析（指南原文）
前挡都是雾，看不清了首先结合端状态的车内车外温差判断是车内有雾还是车外有雾，其次结合端状态判断是否已经打开除霜除雾，未打开的情况下，如果车内起雾开空调除雾模式，如果车外起雾开雨刮器。
结束录音纪要无需改写，调用 recording_minutes（录音纪要工具）结束录音纪要即可。
切换壁纸无需改写，调用 vehicle_basic_control（车控工具）下发命令即可。

找规律：简单明确的 → "无需改写，调用 X 即可"；依赖状态的 → "结合端状态……如果 A 就……如果 B 就……"。就这两种句式。

4写到什么程度

太粗
刚好 ✓
过细
只写"调车控工具"
模型照样错
工具名 + 状态分支 + 改写后措辞
模型照着能做对
完整 output 话术/bug 复盘
冗长且串味

"刚好"的验收线——四条缺一不可

要素标准例子
工具名准确用线上真实 FC（函数调用）名，和主表/线上 trace（调用链）一致route_planning、music_search、auto_drive、vehicle_communication_control；不写 media_search 这种虚构名
状态分支具体写明结合哪个状态字段、分几种情况"结合 env_info 蓝牙连接状态：未连接先提示连接；已连接则调用……"
改写措辞给出需要改写 query 的，把改写后的句子写出来"前年怀旧曲"→结合时间戳算出 2024 年，改写为"2024年怀旧歌曲"
边界口径正确数字、模式清单严格按 0706 边界文档温度上限 30.5℃、按摩 8 种模式仅主副驾、风量 1~11 档
不用写的
完整 output 话术（talk_content 逐字稿）不用写——那是静态示例的活；bug 复盘不用写——放"其他说明"列；多轮完整 input/output 不用写——指南明确"不需要静态示例那种完整的 input 和 output"。

5为什么这些规则成立

规则为什么
每条自包含检索是单条命中注入，模型永远看不到"表里其他行"——跨行引用等于引用空气
决策分析只写正确做法这段文字会原样进 SP 当示范，模型会模仿它看到的一切——把故障描述写进去，等于教模型复述故障
教推理不硬背用户说法千变万化，"我好热"的相似 query 可能是"好闷""有点燥"——只有"结合温度状态→分支"的推理路径能迁移，固定答案迁移不了
工具名必须线上名示例和 SP 的 {{tool_list}}（工具清单）并列出现，名字对不上模型就可能自己编一个（media_search 就是这么来的）
模糊指令要写状态分支郝晓伟批"模糊指令这么写有问题"——"我有点冷"没有唯一解，必须写"结合空调/座椅加热状态分情况"，否则就是瞎答
能归类的别进来动态示例库越来越大后，同类重复条目会互相抢检索、答案打架，污染注入结果
和 SFT 的关系（当前策略背景）
动态示例 = 快速止血：写完下一轮就生效，适合线上救急和验证解法；SFT（监督微调）= 长期固化：把验证过的决策模式训进模型，不占 SP token、不依赖检索命中。当前团队策略就是 bug 统一转 SFT 训练解决——所以动态示例写得越规范（query+决策分析），越能直接当 SFT 的训练数据用。

写入前检查清单（每条过一遍）

  • 工具名是线上真实名（route_planning/music_search/auto_drive…）
  • 决策分析只有正确做法，无 bug 复盘
  • 单条自包含，无"同 XX""参照上条"
  • 一句话人话，无【】五要素式符号框架
  • 依赖状态的写了"结合 env_info/speaker_position/对话历史"分支
  • 边界数字按 0706（30.5℃/8 种按摩/风量 1~11 档…）
  • 改写的把改写后措辞写全
  • 该拒答的写明拒答+替代引导，不幻觉工具

常见死法（这几周真实踩过的）

  • 五要素符号堆格式 —— 被批"瞎写乱七八糟"，全部重写
  • 只挑未通过的写、跳过了通过的 —— 评测集要全量转
  • 决策分析里混"并行会打断、只删成一个"等故障描述 —— 被批"还有些问题"
  • 工具名凭印象写 route_planning_qa/search_and_control_music —— 线上是 route_planning/music_search
  • 凭感觉写边界（温度 31℃）—— 家越 07 实际是 30.5℃，先查 0706 再落笔
