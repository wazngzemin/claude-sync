# 司机 Agent 2\.0舱驾融合 产品需求 PRD
## 1\. 项目背景与产品定义
### 1\.1\. 需求背景
当前高端智能汽车市场，“智能化”已成为核心战场。用户对智能座舱的期待，已从被动的“语音指令\-功能执行”模式，升级为对“更懂我、更主动、更像人”的智能伙伴的渴望。然而，市面上多数产品仍存在以下痛点：
- **“听不懂人话”**：系统理解能力有限，无法处理模糊、复杂、带有真实世界参照物的用户指令，如“就在前面那个星巴克门口停一下”，系统往往需要用户精确说出 POI 名称。
- **“舱驾分离”**：座舱的语音交互与智能驾驶的执行能力之间存在巨大鸿沟。用户无法通过自然语言直接、精细地控制车辆的驾驶行为（如调整驾驶策略、发起临时停车），导致体验割裂。
- **“信任黑盒”**：智能驾驶的决策过程对用户不透明，何时接管、为何执行此操作，用户心中无数问号，导致“不敢用、不常用”的信任危机。
为解决上述问题，打破座舱与智驾的壁垒，提出舱驾融合 Agent 2\.0 项目，旨在打造一款真正懂人言、看路况、能协同的智能副驾，将驾驶员的模糊意图，无缝转化为安全、舒适、高效的车辆自主行动。
### 1\.2\. 产品定义
**舱驾融合 Agent 2\.0** 是一款以完成**驾驶任务**为核心目标的车载 AI 智能体。
它并非一个简单的语音助手，而是一个深度整合了**大语言模型（LLM）的意图理解与推理能力**、**多模态感知能力（语音、视觉）**以及**高阶智能驾驶执行能力**的协同决策与执行系统。
**核心特征：**
1. **基于多模态融合的场景意图理解**：不仅能听懂“前面星巴克停一下”，还能“看懂”用户手机里“就停在这个门口”的照片，结合车辆自身传感器数据，实现真正的“所说即所见，所见即可控”。
2. **带解释、可选择的驾驶策略建议**：面对拥堵，它会提供“走辅路，能快 5 分钟，但红绿灯多 2 个”这样带解释的选项，将决策权清晰地交还给用户，建立信任。
3. **安全边界清晰的协同执行框架**：Agent 负责**提供建议与策略**，而所有驾驶相关的指令必须通过**智驾系统的安全仲裁与冗余校验**才能执行。AI 的“想象力”被严格限定在物理世界的“安全红线”之内。

## 4\. 全局交互原则与状态机
为了确保 Agent 在不同场景下行为一致且可预测，建立统一的交互原则与状态机至关重要。
### 4\.1\. 全局状态机
Agent 在与用户的交互生命周期中，会处于以下几种核心状态之一：
**状态**
**定义**
**典型用户交互/系统表现**
**状态转移条件**
**待机 \(Idle\)**
Agent 未被唤醒，或已完成上一轮任务，处于聆听唤醒词的状态。
- **用户**：说出唤醒词“豆包豆包”。
- **系统**：无主动交互，仅监听唤醒。
收到唤醒指令 → 转移至**理解中**。
**理解中 \(Understanding\)**
Agent 已被唤醒，正在接收并解析用户的语音指令和多模态输入。
- **用户**：说出具体指令，如“前面路口右转”。
- **系统**：交互动效（如呼吸灯）启动，表示正在聆听与思考。
- 指令解析完成，意图清晰 → 转移至**执行中**。
- 指令存在歧义或风险 → 转移至**需确认**。
- 指令无法理解或不满足执行条件 → 转移至**已拒绝/已降级**。
**需确认 \(Confirmation\)**
系统识别到指令存在歧义、高风险或多个可行选项，需要用户二次确认。
- **系统**：“您是想走五环路还是六环路？”
- **用户**：“走五环路。”
- 用户确认后 → 转移至**执行中**。
- 用户取消或长时间无回应 → 转移至**待机**。
**执行中 \(Executing\)**
系统已确认用户意图，并将指令下发给智驾或车控系统执行。
- **系统**：“好的，已切换到运动模式。”
- **车辆**：开始执行相应驾驶或车控动作。
- 任务成功完成 → 转移至**待机**。
- 任务执行失败 → 转移至**已拒绝/已降级**。
- 用户主动介入 → 立即转移至**待机**。
**已拒绝/已降级 \(Rejected/Degraded\)**
系统因安全、法规或能力限制，无法满足用户指令，并给出解释。
- **系统**：“抱歉，当前路段无法掉头，已为您规划至前方可掉头路口。”
播报完原因后 → 自动转移至**待机**。
### 4\.2\. 核心交互原则
1. **安全优先原则**
    - **规则**：任何可能影响驾驶安全的指令，必须经过 MMT 智驾系统的安全校验。当便利性与安全性冲突时，永远选择安全。
    - **示例**：用户说“立即在这里掉头”，如果当前是实线车道，系统必须拒绝并解释：“抱歉，这里是实线，不能掉头。”
2. **用户控制权原则**
    - **规则**：用户在任何时候都拥有最高控制权。任何物理操作（方向盘、刹车、油门）都将立即中断 Agent 当前任务。
    - **示例**：Agent 正在执行“自动变道”时，用户轻转方向盘，变道任务立即取消，控制权交还用户。
3. **可解释、可选择原则**
    - **规则**：对于影响路线、耗时、成本的策略性建议，系统必须提供带有明确利弊的选项，而非替用户决定。
    - **示例**：系统应说“为您找到两条路线，路线一多花 5 分钟但能节省 10 元高速费，您选哪个？”，而不是“已为您选择经济路线”。
4. **单轮交互优先原则**
    - **规则**：在驾驶场景中，交互应尽可能在单轮对话内闭环，避免连续追问干扰驾驶。
    - **示例**：如果用户指令“找个地方吃饭”过于模糊，系统应优先推荐“附近评分最高的3家餐厅”列表，而不是连续问“您想吃什么菜系？预算多少？”。
5. **状态反馈明确原则**
    - **规则**：Agent 的每一个状态（聆听、思考、执行、失败）都必须有清晰、即时的多模态反馈（语音、UI、氛围灯）。
    - **示例**：执行“靠边停车”时，需语音播报“好的，正在为您寻找安全停车位”，同时中控地图上高亮显示目标区域。

## 5\. 行车场景 \(Driving Scenarios\)
行车场景覆盖了用户在道路上行驶时的主要交互需求，核心是让用户通过自然语言，安全、高效地控制导航与驾驶行为。
### 5\.1\. 核心交互时序（行车态）
### 5\.2\. 导航路线控制
#### 5\.2\.1\. 修改路线（即时指令）
- **用户价值**：在行驶中快速调整路线，无需在中控屏上手动操作，减少注意力分散。
**用户话术示例**
**系统核心行为**
**业务规则**
**异常与提示**
“下个路口左转”
“前面路口别右转，直行”
“走地面，不上高架”
1. **NLU 解析**：识别意图为“修改路线”，提取方向（左转/直行）、道路类型（地面/高架）等槽位。
2. **安全仲裁**：判断指令的合法性（如路口是否允许左转）。
3. **智驾执行**：若合法，向 MMT 发送新的 TBT \(Turn\-by\-Turn\) 指令。
4. **反馈**：语音播报“好的，已规划新路线，将在下个路口左转”，并更新地图显示。
- 指令必须基于当前导航路径，且针对前方第一个决策点。
- 系统必须优先保证路线合法性，即使这意味着违背用户指令。
- 若新路线会显著增加耗时，应进行提示。
- **指令无法执行**：“抱歉，该路口禁止左转，已为您保持原路线。”
- **指令不明确**：“您是想在哪个路口左转？请在接近路口时告诉我。”
- **执行后耗时增加**：“好的，已切换到地面道路，预计将增加 10 分钟车程。”
#### 5\.2\.2\. 切换路线策略
- **用户价值**：根据个人偏好（时间、成本、驾驶体验）动态选择最合适的路线。
**用户话术示例**
**系统核心行为**
**业务规则**
**异常与提示**
“换条不堵的路”
“有没有更快的路？”
“我想走高速”
“换一条红绿灯少的”
1. **NLU 解析**：识别意图为“切换策略”，提取偏好（时间优先/躲避拥堵/高速优先/红绿灯少）。
2. **多路线查询**：向地图服务请求符合新策略的多条路线。
3. **策略呈现**：若存在多条可选路线，以语音和卡片形式呈现带解释的选项。
4. **用户确认**：等待用户选择。
5. **反馈**：用户确认后，切换至新路线并语音播报。
- 系统必须提供至少两条（含当前路线）带有利弊解释的选项。
- 解释应简洁明了，突出核心差异（时间、距离、费用、红绿灯数量）。
- 若只有一条符合条件的路线，则直接切换并告知用户。
- **无更优路线**：“当前已是最佳路线。”
- **选项呈现**：“为您找到两条新路线。路线一，走高速，快 15 分钟，但多 20 元高速费；路线二，走国道，与当前时间差不多。您选哪个？”
- **用户超时未选**：“将继续沿当前路线行驶，您随时可以再次让我换路。”
#### 5\.2\.3\. 途经点管理
- **用户价值**：灵活增删改行程中的途经点，应对临时起意的出行需求。
**用户话术示例**
**系统核心行为**
**业务规则**
**异常与提示**
“先去趟陆家嘴”
“帮我加个加油站”
“不去第二个地方了”
“把公司改成家”
1. **NLU 解析**：识别意图（增/删/改）、目标 POI/地址、顺序。
2. **POI 搜索/地址解析**：调用地图服务确认目标点的具体位置。
3. **路线重算**：更新导航路径，并重新计算预计到达时间。
4. **反馈**：语音播报“好的，已添加陆家嘴为途经点，将先经过那里”，并更新地图。
- 添加途经点时，若用户未指定位置，默认插入为第一个途经点。
- 删除/修改时，若有多个同名途经点，需向用户澄清。
- 新增途经点后，应重新评估全程电量/油量，必要时进行提醒。
- **POI 不明确**：“请问是哪个陆家嘴？附近有陆家嘴中心和陆家嘴地铁站。”
- **删除澄清**：“您有两个‘超市’途经点，您想删除哪一个？”
- **电量预警**：“已添加新途经点，但剩余电量可能不足以到达最终目的地，建议您稍后充电。”
### 5\.3\. 驾驶指令与风格
- **用户价值**：在智驾开启状态下，通过自然语言微调车辆的驾驶行为，使其更符合个人习惯和当前路况，实现更高阶的“人机共驾”。
**用户话术示例**
**系统核心行为**
**业务规则**
**异常与提示**
“跟车近一点”
“离前车远一些”
“开快点”
“开慢一点”
“别那么蹿” \(要求加速平缓\)
1. **NLU 解析**：识别意图（跟车距离/速度/加速风格），并映射到对应的智驾参数。
2. **安全仲裁**：判断调整后的参数是否在安全范围内。（例如，速度不能超过当前路段限速）。
3. **智驾执行**：向 MMT 发送调整驾驶风格的指令。
4. **反馈**：语音播报“好的，已调整跟车距离为‘标准’”，并在 HMI 上进行视觉反馈。
- 所有风格调整必须是档位式的（如跟车距离：近/标准/远），而非无级调节。
- 速度调整不能超过法定限速和智驾系统的设计上限。
- 若当前处于手动驾驶模式，系统应提示需开启智驾功能。
- **超出安全限制**：“抱歉，当前路段限速80，无法再提高了。”
- **模式不匹配**：“请先开启领航辅助驾驶，我才能为您调整驾驶风格。”
- **已达极限**：“已经是最近的跟车距离了。”
“帮我超了前面那辆慢车”
“换到左边快车道”
1. **NLU 解析**：识别“变道超车”意图。
2. **环境感知**：MMT 系统评估目标车道是否安全、是否存在足够超车空间。
3. **执行或拒绝**：若条件满足，执行自动变道；若不满足，则拒绝。
4. **反馈**：语音播报“好的，正在为您变道”或“左侧车道有车，暂时无法变道”。
- 变道指令的执行权完全归属 MMT，Agent 只负责传递意图。
- 在路口、实线、弯道等禁止或不建议变道的区域，系统应拒绝执行。
- 执行变道前，必须通过 HMI 和声音提示驾驶员。
- **条件不允许**：“抱歉，左侧车道车辆过近，无法安全变道。”
- **法规禁止**：“前方为实线区域，无法为您变道。”

- VLM 识别的置信度必须高于 90% 才能发起确认。
- 识别范围优先考虑车辆前方和侧方 30 米内。
- 系统必须明确标示出是泊入哪个具体车位（例如，在 AR\-HUD 中绘制泊车框）。
- 如果参照物旁边没有可用车位，系统必须明确告知。
- **识别失败/未找到**：“抱歉，我没有看到红色的特斯拉，您可以换个参照物吗？”
- **置信度低**：“我不确定那是不是一辆特斯拉，您能说得更具体一些吗？”
- **无可用车位**：“那辆红色特斯拉旁边没有空车位，需要我继续寻找吗？”
- **环境遮挡**：“目标车辆被遮挡，无法确认位置，请开近一些。”

## 7\. 接管与协同场景 \(Takeover \&amp; Collaboration Scenarios\)
该场景是建立用户信任、明确能力边界的关键。它定义了在智驾系统遇到困难或用户意图不明时，Agent 如何通过清晰的沟通，将控制权安全、平滑地交还给用户。

### 7\.2\. 智驾边界与风险接管
- **用户价值**：让用户在智驾功能退出或即将达到能力边界时，获得清晰、及时的预警和明确的指导，消除对“黑盒”的恐惧，提升安全感。
**触发场景**
**系统核心行为**
**业务规则**
**人机交互表现**
**系统请求接管 \(TOR\)**
- 天气恶劣（暴雨/大雾）
- 传感器失效/遮挡
- 地图数据缺失
- 遭遇超复杂路况（如事故）
1. **风险预判**：MMT 智驾系统预判未来 10\-15 秒内可能需要人类驾驶员接管。
2. **多模态预警**：Agent 立即触发多模态警告（语音、HMI、氛围灯闪烁）。
3. **状态说明**：清晰告知用户需要接管的原因。
4. **状态监控**：监控驾驶员状态（DMS），确保其已准备好接管。
5. **控制权交还**：在驾驶员手握方向盘后，平稳退出智驾模式。
- 接管请求必须至少提前 10 秒发出。
- 接管流程分为“提醒”、“警告”、“强警告”三级，逐级加强提示强度。
- 在用户未接管期间，车辆应保持当前车道安全行驶或减速。
- 若用户持续未响应，系统应执行风险最小化策略（如靠边停车）。
- **语音**：“注意，前方进入隧道，需要您准备接管。” \(提醒\) → “请立即接管！” \(警告\)
- **HMI**：屏幕顶部出现醒目的黄色/红色警告条，显示“请接管方向盘”。
- **氛围灯**：由蓝色（智驾状态）变为黄色/红色闪烁。
- **声音**：配合“滴滴”的警告音。
### 7\.3\. 用户意图的澄清与降级
- **用户价值**：当用户的指令模糊或无法执行时，系统不是简单地拒绝，而是通过澄清或提供替代方案，引导用户完成任务，保证交互的流畅性。
**触发场景**
**系统核心行为**
**业务规则**
**人机交互表现**
**指令存在歧义**
- “去那个星巴克” \(附近有多家\)
- “靠边停” \(旁边是公交站\)
1. **歧义识别**：LLM 模型识别到指令的多个可能解释或潜在风险。
2. **生成澄清选项**：生成清晰、易于选择的选项。
3. **用户确认**：通过语音或屏幕点选，让用户做出选择。
- 选项不能超过 3 个，避免给用户造成选择困难。
- 每个选项都应有明确的区分点。
- 若用户长时间未选择，应有默认的安全选项或退出任务。
- **语音/HMI**：“附近有两家星巴克，一家在您左前方50米，另一家在对面商场一层，您想去哪家？”
- **语音/HMI**：“这里是公交站，不能停车。我可以为您在前方50米处的白线区域停车，可以吗？”
**指令无法执行**
- “在这里掉头” \(实线\)
- “开到150” \(超速\)
1. **不可行性判断**：MMT 或 Agent 安全仲裁模块判断指令违反法规或超出能力范围。
2. **给出明确理由**：用自然语言解释无法执行的原因。
3. **提供替代方案 \(降级\)**：如果可能，提供一个最接近用户意图的合法、可行的替代方案。
- 拒绝原因必须具体、易于理解，不能是“无法执行”。
- 提供的替代方案应该是建设性的。
- **语音**：“抱歉，这里是实线，不能掉头。我已经为您规划到前方路口的可掉头处。”
- **语音**：“当前路段限速120，无法为您提速到150。已为您设置到120的最高限速。”
