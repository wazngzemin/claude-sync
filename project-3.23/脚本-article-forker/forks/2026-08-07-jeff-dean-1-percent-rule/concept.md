# 从 1% 问题到可靠 Agent：你的五环工作法

## 核心问题

这篇访谈最值得你复用的是一个产品闭环：怎样找到基础模型解决不了、用户又真正需要的问题，并把它一步步做成稳定系统。

用大白话说，五环分别是：

1. 挑题：这件事值得做吗，通用模型会不会很快自己学会？
2. 写清：成功长什么样，失败有哪些样子？
3. 补料：模型缺什么状态、记忆、工具和方法？
4. 跑通：任务怎样跨时间保存、唤醒、执行和恢复？
5. 对账：怎样快速判断这次改动到底有没有用？

## 场景映射

| 文章里的机制 | 你的 Planner / Agent 场景 | 可迁移动作 |
|---|---|---|
| 1% 法则 | 判断某个座舱场景值不值得投入 | 先测裸模型，再判断剩余差距是否来自车内私有信息和行动闭环 |
| 私有数据 | 端状态、VLM、用户记忆、目标进度 | 建 Context 缺口表，明确来源、时效、可信度和缺失降级 |
| performance skill | SP 规则、动态示例、场景知识、工具说明 | 从 badcase 提炼通用方法，孤例才留在动态示例 |
| 软件本身是规格 | 期望工具调用、状态分支、动作回执 | 每个场景写输入、状态、动作、验收和失败恢复 |
| Agent 跑几周 | 条件任务、持续任务、跨行程目标 | 用 task_id 和快照持久化，事件到来时再短推理 |
| 第 30 步脱轨 | 多步任务中间状态错误、错误累积 | 每个关键步骤后加检查点，保存可恢复状态 |
| 评估器 | Planner 评测集、动态示例实测、线上反馈 | 从只看总分升级为定位失败步骤和改动归因 |
| 品味 | 选择本季度真正值得负责的问题 | 写 12 个月押注，半年小复盘，年底总复盘 |

## 五环方法框架

### 第一环：挑题，使用「1% 三门」

模型低成功率只是入口。一个问题要同时过三道门。

#### 门一：结果有价值

问：如果做成，用户会明显更安全、更省心、更高效，还是只会觉得有点酷？

车里一个会说漂亮话的助手可能只是酷；能持续照看后排儿童、在异常时可靠提醒，价值更明确。

#### 门二：基础模型单独做不到

问：把当前最强通用模型直接拿来，不给车内状态、不接工具、不提供记忆，它的成功率有多高？

这里测的是裸模型。不要把你们现有系统已经提供的 Context 和工具算成模型本身的能力。

#### 门三：你能建立闭环

问：剩余差距能否靠你拿得到的私有信息、现场工具、业务规则和评估数据持续补齐？

若模型不会，是因为没有摄像头、没有任务状态、没有车控权限，这些差距可以由系统补齐。若模型不会，是因为需求没人要、结果无法判断，投入价值就很低。

### 1% 机会评分卡

每项 0 到 2 分，总分 10 分。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 用户价值 | 只是好玩 | 有帮助但可替代 | 解决高频、高痛或安全问题 |
| 裸模型缺口 | 已能稳定完成 | 能完成一部分 | 几乎无法完成 |
| 专属资产 | 大家都能拿到 | 有一点现场信息 | 有持续私有数据、工具或关系 |
| 可评估性 | 成败说不清 | 主要靠人工判断 | 可快速、重复判断 |
| 产品闭环 | 一次性交付 | 偶尔回流 | 使用越多，系统越强 |

- 8 到 10 分：值得进入重点候选。
- 5 到 7 分：先做小实验，别直接立大项目。
- 0 到 4 分：大概率是包装、伪需求或会迅速同质化的能力。

### 你的场景示例

| 场景 | 裸模型大致位置 | 真正难点 | 1% 判断 |
|---|---|---|---|
| 「打开车窗」 | 高成功率 | 工具参数、权限、安全边界 | 适合走稳定快速通道，不适合作为核心差异 |
| 「我有点热」 | 能理解一部分 | 温度、座位、车速、历史偏好、当前空调状态 | 机会在 Context 与执行闭环，不在语言理解 |
| 「宝宝哭了告诉我」 | 无现场信息时接近 0 | 持续视觉、任务状态、误报控制、触达时机 | 典型 1% 候选，但必须有可靠评估和隐私边界 |
| 「沿途看到值得讲的风景再介绍」 | 接近 0 | 长时感知、位置、时机、去重、打扰控制 | 是持续任务候选，先解决评估器 |
| 通用闲聊话术 | 已有较强能力 | 人设一致性与安全 | 容易被模型升级覆盖，少做重资产 |
| 跨行程记住并兑现用户偏好 | 基础模型单独无法完成 | 身份、记忆、更新、遗忘、冲突处理 | 私有数据路径，适合长期积累 |

### 第二环：写清，把想法变成 Agent 能执行的规格

Agent 不怕任务复杂，怕目标含糊。一个可执行规格至少回答八个问题：

1. 谁发起任务？
2. 任务从什么时候开始生效？
3. 需要哪些状态与事件？
4. 哪些信息缺失时不能继续？
5. 哪一步可以调用什么工具？
6. 什么动作需要用户确认？
7. 怎样算完成、失败、超时或取消？
8. 中断后从哪里恢复？

#### 「宝宝哭了告诉我」规格示例

- 输入：用户创建持续观察任务。
- 任务对象：本次行程内，二排指定座位的儿童。
- 需要信息：座位占用、VLM 最新描述、车辆是否在本次行程、提醒是否已发出。
- 唤醒方式：相关视觉事件或固定低频检查。
- 判断：视觉描述与「哭泣」目标是否匹配，置信不足时继续观察，不立刻提醒。
- 动作：向 Planner 提交建议，由 Planner 决定播报；不得直接执行高风险车控。
- 完成：提醒成功、用户取消、行程结束或任务超时。
- 防抖：同一段哭泣只提醒一次，状态恢复后才允许下一次提醒。
- 恢复：系统重启后若仍在同一任务有效期，读取 task snapshot 继续；否则关闭。

### 第三环：补料，Context 不是越多越好

上下文工程的目标是让模型在此刻看到「完成这一步所需的最少充分信息」。塞入越多文本，相关信息反而可能被淹没，也会增加延迟和成本。

#### Context 缺口矩阵

每个重点场景做一张表：

| 信息 | 来源 | 新鲜度 | 可信度 | 缺失时怎么办 |
|---|---|---|---|---|
| 当前说话人和座位 | 端侧身份与音区 | 当前轮 | 高或待确认 | 不执行座位相关动作，先追问 |
| 车内温度 | 车辆状态 | 最新状态 | 高 | 不做精确温控判断，给保守建议 |
| 宝宝视觉描述 | VLM | 最近一次观察 | 依场景而变 | 继续观察或说明暂时无法判断 |
| 用户温度偏好 | 用户记忆 | 长期记忆 | 中 | 采用默认舒适区并允许用户纠正 |
| 当前任务进度 | Task snapshot | 最新写入 | 高 | 禁止重复创建或重复提醒 |

#### 动态示例与 skill 的分工

- 能提炼出通用步骤的问题，优先写成规则、skill 或场景卡。
- 只有孤立例外、模型有能力却经常走错路时，才使用动态示例。
- 缺端状态或工具能力的问题，先补链路，继续堆示例通常无效。
- 每条新示例必须有基线实测、加入后实测和副作用检查。

你现有材料里已经出现了 114 条动态示例相关资产。数量增长后，重点应从「继续增加」切到「召回是否正确、是否重复、是否真的带来净增益」。

### 第四环：跑通，把长时 Agent 做成状态机

长时任务可以持续数小时，单次模型调用仍应尽量短。最容易理解的结构如下：

```text
创建目标
→ 保存 task_id、有效期、成功标准
→ 向 Trigger 订阅事件
→ 任务休眠，不持续烧模型
→ 事件到来
→ 读取最新 Context 与 snapshot
→ Planner 做一次短推理
→ 工具或交互执行
→ 检查动作回执
→ 更新进度
→ 继续等待 / 完成 / 失败 / 取消
```

#### 每个长时任务的五个检查点

- 创建后：任务是否真的注册成功？
- 唤醒后：事件是否与任务相关，是否重复？
- 决策前：关键 Context 是否新鲜、完整？
- 执行后：工具回执是否成功，用户是否收到？
- 结束时：订阅是否清理，任务是否留下错误残留？

### 第五环：对账，用评估器驱动系统进化

评估器不能停在给一个总分，它还要回答三件事：失败在哪里、为什么失败、哪次改动真的解决了它。

#### 四层评估

1. 任务层：用户目标最终达成了吗？
2. 安全层：是否越权、误触发、重复打扰或做了危险动作？
3. 过程层：Context、任务拆解、工具选择、参数和回执处理哪一步出错？
4. 系统层：延迟、token、端云流量和调用成本是否可接受？

#### Jeff Loop 周报

每周只跟踪一张表：

| 字段 | 要写什么 |
|---|---|
| 本周问题 | 一个明确 badcase 簇，不要写泛泛的「Planner 不稳定」 |
| 基线 | 当前版本多少条通过，失败集中在哪一步 |
| 假设 | 缺 Context、规则、工具还是模型能力 |
| 改动 | 具体改了哪一条字段、规则、示例或工具说明 |
| 结果 | 成功率、延迟、副作用怎样变化 |
| 决策 | 保留、回滚、继续实验或转交其他模块 |

这张表的价值在于让「我写了很多」变成「我知道哪一次改动为何有效」。

## 操作 SOP：把一个新场景从想法做成闭环

### 输入

- 一个用户场景或职业方向。
- 当前最强通用模型的基线表现。
- 可用的私有数据、工具、状态和评估方式。

### 步骤

1. 用 1% 评分卡打分。
2. 找 10 到 20 个真实样本测裸模型，不凭感觉估计成功率。
3. 把失败拆成信息缺口、方法缺口、工具缺口、模型能力和伪需求。
4. 写八问题规格，明确完成、失败、超时和恢复。
5. 建 Context 缺口矩阵，只注入最少充分信息。
6. 设计短调用、持久状态和事件唤醒链路。
7. 建四层评估器，先测基线。
8. 一次只改一个主要变量，再测。
9. 记录增益和副作用，确认是否形成数据回流。
10. 连续三轮有稳定净增益，再扩大范围。

### 输出

- 《1% 场景机会账本》
- 《长时任务闭环一页纸》
- 《Context 缺口矩阵》
- 《Jeff Loop 周报》

### 失败模式

- 只因为模型很差就判定是机会。
- 没做裸模型基线，无法判断系统层到底补了什么。
- 把长时任务做成超长上下文，成本和错误一起累积。
- 只看最终答案，不看失败步骤。
- 用动态示例掩盖缺状态、缺工具或下游失败。
- 评估指标过于单一，模型学会讨好分数却伤害用户体验。

## Prompt 模板：让 AI 帮你评估一个 1% 问题

```text
你是我的 AI 产品机会评审员。请评估下面这个问题是否值得投入。

问题描述：<填写>
目标用户：<填写>
成功结果：<填写>
我能获得的私有数据：<填写>
我能调用的工具或线下服务：<填写>
当前可用的评估方法：<填写>

请完成：
1. 先指出这个问题对用户的真实价值，区分高痛点和仅仅有趣。
2. 给出测试裸模型成功率的 10 个样本，不准凭印象直接下结论。
3. 把失败原因分成信息缺口、方法缺口、工具缺口、模型能力、需求不成立。
4. 按用户价值、裸模型缺口、专属资产、可评估性、产品闭环五项各打 0 到 2 分。
5. 说明模型未来升级后，产品还有什么无法被直接覆盖的资产。
6. 给出最小实验，限制在一周内可完成，并写清通过线和停止线。
```

## 30 天行动计划

### 第 1 周：建机会账本

- 从当前工作中列 10 个任务级场景。
- 每个场景完成五项评分。
- 选一个 8 分以上、你能拿到完整链路的场景。
- 建议优先候选：持续观察和条件触发类场景，而非通用闲聊。

### 第 2 周：做闭环规格

- 写八问题规格。
- 画出 Task、Trigger、Context、Planner、工具和回执的责任图。
- 找触发器与端侧相关 owner 核对事件、状态、新鲜度和失败分支。
- 评审时可以直接说：

> 这次先不争论模型够不够强。我会先给出裸模型基线，再说明系统补了哪些现场信息和行动能力，最后用同一套评估验证增益。

### 第 3 周：做评估器

- 收集 20 个真实或高保真样本。
- 标记最终任务结果、失败步骤、安全问题和延迟。
- 跑一次基线。
- 明确停止线，例如误提醒率超过某阈值就不能进入主动播报。

### 第 4 周：跑三轮 Jeff Loop

- 每轮只改一个主要变量。
- 每轮都记录增益和副作用。
- 做一页总结，展示「问题、假设、改动、结果、结论」。
- 把该页变成你后续面试具身智能或 FDE 岗位的作品集材料。

## 对你未来转具身智能的具体影响

### 应该寻找的方向

- 长时间持续观察并在合适时机行动。
- 依赖客户现场私有数据和流程。
- 需要把视觉、语言、任务状态和物理执行连成闭环。
- 有明确安全边界和可重复评估。
- 每次部署经验能回流产品，而不是每个客户从头重做。

### 应谨慎的方向

- 只给机器人增加聊天或通用问答。
- 主要卖演示效果，缺少真实运行数据。
- 每个客户都重写一套，经验无法复用。
- 成败只能靠主观感受，没有任务成功率与安全评估。

### 你需要的代码能力

你无需先成为算法工程师。短期目标是做到：

- 看懂 JSON、API 参数、日志和基本状态机。
- 能用 Agent 生成并修改简单测试脚本。
- 能独立搭一个小型评测工具或场景原型。
- 能与工程师讨论数据从哪里来、何时更新、失败怎样恢复。

这足以让你从「写需求的人」向 builder 和业务型 FDE 靠近。更深的模型训练与系统工程，可以继续和专业工程师协作。

## 判断标准

### 做对了的信号

- 你能说清裸模型为什么失败，系统具体补了什么。
- 长时任务通过 task_id、快照、唤醒和恢复来运行，没有依赖超长对话。
- 每次规则或示例改动都有基线、结果和副作用记录。
- 重点场景的成功率、安全、延迟与成本可以同时查看。
- 你能用一页纸讲清一个场景从用户价值到技术闭环。

### 仍然停留在表层的信号

- 只会复述「做 1% 问题」「上下文工程很重要」。
- 用更多 Prompt 和更多示例代替缺失的状态或工具。
- 把任务持续时间和模型单次推理时间混为一谈。
- 汇报中只有做了多少条，没有说明解决了什么失败原因。
- 职业规划只写「转具身智能」，没有具体任务类型、数据来源和评估方式。
