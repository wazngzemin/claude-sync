1动态示例到底是什么 先把机制原理吃透，后面所有写法规矩都是从原理推出来的

一句话：动态示例 = 一条「用户 query（用户原话）+ 决策分析」的参考答案，平时躺在示例库里；用户一说话，系统拿这句话去库里检索，最像的示例被挑出来塞进 SP（系统提示词），模型这轮就照着它做决策。

注意菱形判断框和每条线上标的原因

四条机制原理（写法规矩全部由此推出）

原理展开推出的写法规矩
① 语义检索、单条命中 系统拿用户 query 和库里每条的 Query 列算语义相似度，取最像的 1 条注入。模型这轮只看得到这一条，看不到你写的其他任何行。 每条必须自包含：禁止"同上""同 R12 那条"这类跨行引用；Query 列要用用户原话/常见说法（决定能不能命中），别写成书面语。
② 用完即走 命中才注入，这轮在这轮用；下一轮用户换话题，没命中就不在 SP 里了。 不占常驻 token（词元），写多少条都不拖慢日常对话；但也意味着它管不了"每一轮"的通用能力——通用能力要进静态示例。
③ 模型会模仿看到的一切 决策分析这段文字原样进 SP，模型把它当"标准答案"模仿——包括里面的措辞、语气、甚至错误。 决策分析只写正确做法。"之前把并行调用打断了只删成一个"这种故障复盘写进去=教模型复述故障，必须挪到"其他说明"列（该列不进 SP）。
④ 入库即生效 写入示例库，下一轮对话就能被检索命中，不用发版、不用训练。 它是所有修法里最快的（对比 SFT（监督微调）要训练+评测+发版，按周计）。所以定位是"先快速验证决策路径对不对"，验证过的条目将来直接当 SFT 训练数据。

动态示例 vs 场景卡：用 7 月观影 bug 分清这条边界
后排观影 bug 单里有人建议"加动态示例"，但车内观影要同时按说话人位置（前排/后排）、车辆状态（行驶/驻车）、观影模式（普通/5D）三个维度判断，还有"偏好确认后再播、严禁随机盲播"等通用规则——拆成一条条动态示例会互相割裂，单条之间看不到彼此约束。所以正解是场景卡（ID_002）整卡注入，动态示例只兜底"场景卡触发词覆盖不到的冷门说法"。判断口诀：一条规则能说清的→动态示例；要一张表才说清的→场景卡。

车内观影 bug 单：把"后排观影整族场景"当动态示例写——要按位置/车辆状态/观影模式三维判断，一条 query+决策分析装不下。

正确分流

整族场景走场景卡（ID_002 已含 5 个分支示例）；动态示例只兜底场景卡触发词覆盖不到的冷门单点说法。

为什么：动态示例是"单条命中"，每条之间互相看不见。一族规则拆成多条后，模型命中其中一条时看不到其他条的约束（比如命中"后排观影"那条时看不到"严禁随机盲播"那条），规则就漏了。

句式Query决策分析（入库原文）
A 直接执行空调风量调到3档3档在风量 1~11 档可调节范围内：直接调用 vehicle_basic_control（车控工具）调节，无需额外确认或改写。
B 状态分支吹热风结合 env_info（端状态）空调 A/C 状态和当前温度："吹热风"=制热，制热需 A/C 开启且温度≥27℃；若当前温度已≥27℃（如28℃），只需打开 A/C 即可，不得把温度调低到 27℃；若当前温度低于 27℃，则打开 A/C 并将温度调至 27℃。调用 vehicle_basic_control。
C 拒答生成个小狗视频视频生成超出车机能力（仅支持图片生成）：直接告知用户做不了视频生成，可提议生成一张小狗图片作为替代，不要追问视频风格继续往下做。

句式 B 的错误/正确对照（被点名最多的一种）

错误写法 · 被批"死记硬背"的版本

"我有点冷"→打开座椅加热。
"我旁边人想休息"→调低音量。
（给个脱离状态的固定答案，硬背）

正确写法 · 状态分支

"我有点冷"→结合 env_info 空调温度和座椅加热状态：温度低于 22℃ 就调高空调温度；温度正常但座椅加热没开，就打开座椅加热（按 speaker_position 定座位）。

为什么："我有点冷"没有标准答案——车里 18℃ 和 25℃ 的正确动作完全不同。写死一个答案，模型换个状态就做错。正确写法给的是判断路径（读什么字段、怎么比），不是固定答案。
错误写法 · 五要素符号版（被批"瞎写"）

【定位】制热【查】温度【分支】≥27℃→开A/C｜<27℃→开A/C+27℃【调用】vehicle_basic_control

正确写法 · 一句话人话

结合 env_info 空调 A/C 状态和当前温度："吹热风"=制热，制热需 A/C 开启且温度≥27℃；若当前温度已≥27℃，只需打开 A/C；若低于 27℃，打开 A/C 并将温度调至 27℃。调用 vehicle_basic_control。

为什么：决策分析要原样进 SP，和 SP 里其他参考示例的口吻一致。符号框架版口吻突兀，模型模仿起来效果差——被批"瞎写乱七八糟"，全部推翻重写过一次。

6一条示例在模型脑子里是怎么起作用的 （吹热风实例：有/无示例对比）

图 4 · 同一句"吹热风"，有没有动态示例，模型走的两条路
这张图就是"教推理不硬背"的全部含义：示例里没有写死"吹热风就开 A/C"，而是写了怎么判断（读温度、比 27℃）。所以换个温度（22℃）模型照样做对——它学到的是判断路径，不是固定答案。上面那条红泳道就是"死记硬背"：没有判断路径，模型只能瞎猜。

7手把手走查 ×3 三个真实 bug，从 badcase 原貌到入库成品，一步不跳

走查一：高速开窗（教"状态分支穷举"）

  1. bug 原貌：提需求"车辆高速行驶时（车速>80），用户要打开车窗，无论要求开 100% 还是 50%，为行车安全都只能开 10%"。
  2. 归因：这是安全限制规则，模型不知道这条规则 → 属于"给它规则就会做"，走图 2 第二个菱形=有能力只是缺指引 → 动态示例。
  3. 选句式：怎么做要看车速 → 句式 B。
  4. 初稿（真实被批版）："车速>80 只开 10%；≤80 按用户要求开度正常下发。"——被批："怎么就写两个分支？"
  5. 用四问穷举法补全：问自己四个问题——
    四问这条 case 里的答案
    ① 依赖的信号缺了怎么办？车速字段未上报/为空 → 先调 vehicle_status_search 查车速再判断
    ② 主规则是什么？车速>80：无论要开 100% 还是 50% 都只开 10%，告知"降速后可再开大"
    ③ 设备当前状态要不要管？车速>80 且车窗当前已开超 10% → 提示建议关小，询问是否关到 10%
    ④ 环境/异常干扰？正在下雨 → 开窗前先提醒确认；≤80 未指定开度 → 默认全开
  6. 定稿入库：①车速未上报先查；②>80 只开 10% 并告知；③>80 且已开超 10% 提示询问关小；④≤80 有指定开度按指定；⑤≤80 未指定默认全开；⑥下雨先提醒确认。调用 vehicle_basic_control。
  7. 自查：工具名✓（vehicle_basic_control 是线上真名）；字段✓（车速、车窗开度都是真实上报字段）；只写正确做法✓；自包含✓。
走查一的心法
带安全限制的车控类示例，状态分支要按"四问"穷举真实信号（信号缺失/主规则/当前状态/环境干扰），只写两个分支一定会被批"不够详细"。

走查二：酒吧乱答（教"该查必查"类写法）

  1. bug 原貌：用户问"附近好像有一家世界排名很高的酒吧"，Planner 没调任何工具，凭记忆答"Sober Company 在进贤路"——实际该酒吧已换地址，信息过时。
  2. 归因：工具有（poi_search/web_search），模型该查没查 → "有能力走错路" → 动态示例。
  3. 选句式：查不查、用哪个工具查，要看 query 形态 → 句式 B（按"地址模糊/时效性强"分支）。
  4. 关键决策——规则要上升一层写：这条 bug 表面是"酒吧答错"，但根因是"生活服务类凭记忆乱答"。所以决策分析不只写酒吧，而是写整个生活服务类（酒吧/餐厅/酒店/加油站/景点）——一次写透，这类 query 都能命中。
  5. 定稿入库："用户询问生活服务类信息时，必须先调用工具查询再回答，禁止凭记忆/常识直接乱答：若地址或范围模糊，调用 poi_search；若信息时效性强、需要最新排名/新闻，调用 web_search。拿到具体名称、地址、评分后再转述并询问是否需要导航；返回多个结果时提炼距离、评分、特色推荐 1 个最合适的。"故障复盘（答了老地址）写进"其他说明"列，不进 SP。
  6. 自查：工具名✓；转述要求✓（给了拿到结果后怎么做）；边界✓。
走查二的心法
单点 bug 要想一层"这是不是一族病的其中一个症状"——是就把规则写到族级别（Query 列仍放具体原话保证命中，决策分析写族规则）。

走查三：坐垫充气（教"低频功能口语映射"写法）

  1. bug 原貌："坐垫充气"是把大腿顶起来的座椅气袋功能，上汽特殊座椅支持，但属低频功能——按"高频能力进工具描述、低频能力走动态示例"的原则，需要动态示例教模型认识它。
  2. 归因：模型不认识这个功能名 → 可能回"不支持"或只解释不执行 → "缺一条指引" → 动态示例。
  3. 选句式：要按用户口语映射到不同动作 → 句式 B（映射型分支）。
  4. 关键决策——把用户可能的说法穷举成映射表：用户不会说"座椅坐垫前部气袋充气"这种标准名，会说"坐垫硬一点""把大腿顶起来""包裹紧一点"。每条口语都要给出对应标准动作。
  5. 定稿入库："坐垫充气是座椅坐垫气袋功能（把坐垫顶起来支撑大腿），听到后直接调用 vehicle_basic_control 执行，不要回复'不支持'或只解释功能不动手：'坐垫充气''把大腿顶起来''坐垫硬一点/鼓一点'→下发座椅坐垫气袋充气；'坐垫放气''坐垫软一点/瘪一点'→放气；'包裹紧一点''侧翼夹紧一点'→座椅侧翼气袋充气/放气。"
  6. 自查：工具名✓；能力口径✓（对齐能力表：坐垫前部/后部气袋充放气=座椅坐垫气袋充放气，侧翼气袋充放气=座椅侧翼气袋充放气）；自包含✓。
走查三的心法
低频功能示例的核心是"口语→标准动作"的映射穷举 + 一句"禁止只解释不执行"。能力口径先去查边界文档/能力表再落笔，别凭印象写功能名。

七种死法的错误/正确对照（全部真实踩过）

死法 1 · 符号框架用【定位】【查】【分支】【边界】【调用】五要素符号堆写决策分析
正确一句话人话，和 SP 里其他示例口吻一致
教训：被批"瞎写乱七八糟"，96 条全部推翻重写。
死法 2 · 挑着转评测集只挑"未通过"的转动态示例，跳过"已通过"的
正确评测集不管通过与否全量转——已通过的也要防回退
教训：28 条漏了 13 条，返工。
死法 3 · 故障描述进 SP决策分析里写"并行会打断、只删成一个"
正确故障复盘挪到"其他说明"列（不进 SP）；决策分析只写正确做法："一个一个删，禁并行"
教训：模型会模仿看到的一切，写故障=教它复述故障。
死法 4 · 工具名凭印象写 route_planning_qa / search_and_control_music
正确route_planning / music_search——先对主表或真实 trace（调用链日志）再落笔
教训：工具名错=示例教模型调一个不存在的工具。
死法 5 · 边界凭旧印象温度写 31℃、写"极速制冷模式"
正确家越 07 口径：30.5℃、无极速制冷——先查 0706 边界文档
教训：边界数字错，示例就是在教模型越界。
死法 6 · 硬编码答案"我有点冷"→打开座椅加热（不看状态给固定答案）
正确写成判断路径：结合温度+座椅加热状态分支
教训：被批"必须结合 context（上下文）""不能死记硬背"，约 160 条重写类返工。
死法 7 · 分支只写两个高速开窗只写">80 开10% / ≤80 正常"
正确四问穷举成 6 分支（信号缺失/主规则/当前状态/环境干扰）
教训：被批"怎么就写两个"——状态分支要穷举真实信号。

入库前检查清单（可打印）

  • Query 用的是用户原话/常见说法（决定检索能不能命中）
  • 决策分析是一句话人话，没有符号框架
  • 工具名和线上 trace 核对过
  • 状态分支过了"四问"：信号缺失怎么办/主规则/当前状态/环境干扰
  • 边界数字对过 0706 文档（温度/风量/按摩/驾驶模式/巡航）
  • 只写正确做法，故障复盘在"其他说明"列
  • 单条自包含，没有"同上""同 XX 链"跨行引用
  • 需要改写的，改写后的完整句子写出来了
  • 入库后拿原 badcase 重放验证过
