语音 Query → 决策 → 执行 → 长时任务：可验证的全链路

这不是把原图继续“加框”，而是先拆开五种不同性质的链路：实时请求、端云分流、Planner/Director 多轮闭环、Task/Trigger 生命周期、两条 VLM 感知流。每个模块都标明证据状态，避免把旧架构、WIP 和产品提案误画成同一套线上系统。

结论：原图覆盖面很广，但不能按一条实际时序来理解。最严重的三处是：把 Planner 与 Director 画成两个大脑；把配置平台塞进每次 Query 的实时链；把 TTS、数字人、车控画成串行。新版的唯一决策主心骨是 Context 组装 → Planner/Director → action_list / talk_content → 执行反馈 → 下一轮决策。

01｜实时主链：从声音到用户真正拿到结果

蓝色是一次用户请求的主干；绿色是执行；粉色虚线是反馈回路。Advisor、事件和 tool_feedback 都是“触发本轮推理的输入”，Context 是推理前组装的参考快照，不是 Director 之后的下游模块。

协议 + 旧 PRD 可确认

一次 Planner 调用是什么

固定 SP + 动态 Context + 本轮输入，输出 JSON 决策。它不是“一次性把整件事想完”，工具结果回来会再调用一轮。

AI 能力真正落在哪里

不是只看模型回答，而是看它能否利用 Context，正确拆动作、控制依赖、解释失败，并用真实反馈修正下一轮。

完成的判定

action_list 生成 ≠ 下发成功 ≠ ECU 生效 ≠ 用户目标完成。四层状态必须在指标和日志里分开。

03｜两条 VLM 感知流：默认 AlwaysOn 与任务专属观察不能串起来

原图把视觉、VQA、Trigger VLM 推理揉成一条。正确理解是：默认感知用于生成最新环境事实，任务专属流才携带 task_id 与某个用户目标绑定；用户主动问“你看到了什么”又是独立的按需 VQA 工具。

飞书原始文字记录 + 最新技术方案

当前已确认

默认结果进入 Context；任务专属结果带 task_id/task_version 经 Task Service 送 Trigger 做云端语义匹配；命中后回 Task Service。

仍是产品补充提案

现有 VLM inference 技术链只消费本 Task 的动态结果；“已有 Context 状态优先、能力不覆盖才下发动态观察”在本地仍是补充 PRD，不能写成已实现。

当前矛盾要追

迟到结果阈值存在版本差异：TaskService 文档出现约 20 秒，Trigger 方案出现约 3 分钟。图中不固化数值，需联调书面定版。

04｜产品必须掌握的状态机与异常门

Trigger 命中只是从“等待”进入“可执行”，并不是任务已经成功。状态变化必须由事实和反馈推进。

09意图模型和 Director 都解析/注册同一个条件任务路由模型只分流；Director 理解用户目标；Task Agent/Spec Builder 结构化；以 task_id/idempotency_key 确保一次注册。重复所有者
10Goal List、动态 Advisor、Task Center、Task Service 被画成同代模块当前 SP 是 goal_list_update；Task Service/task_manage 是 WIP 演进；静态 Advisor 保留为独立建议源。必须标版本。版本混叠

12Director 的 action_list 直接等同工具执行中间补 Runtime Dispatcher：依赖串并行、参数/安全校验、超时重试、幂等、结果聚合、工具适配。缺关键层
13工具 feedback 就算任务成功区分接口受理、下发成功、真实状态生效、用户目标完成；必要时回读 observed_state，Planner 再判断。完成态错误
14TTS/卡片 → 机器人 → 车控执行被画成串行talk_content/emoji 走响应呈现；action_list 走工具执行，两者并列，由响应协调器保证“说做一致”。明显错误
15默认 VLM 与动态任务 VLM 是“先失败再兜底”的一条流它们是两种来源：默认结果进 Context；专属任务先下发才产生带 task_id 的结果，经 Task Service → Trigger。视觉链错误
16端 VLM 直接判断“目标达成”或动态结果回写 Context端 VLM 只给观察描述；云 Trigger 用 goal + data 做语义判断。当前专属结果走独立任务链，不直接进 Context。技术方案
17固定 500ms / 3s / 5s、P0-P4、阈值穿越等被画成通用事实这些细节存在版本差异或未逐项核验，应标“特定方案/待确认”，不能成为主链硬编码。证据不足
18缺取消、更新、迟到、重复、断网、下电和可观测链补 task_version、callback 幂等、stale 丢弃、重试/结束策略，以及 request/task/run/action/scene 全链 ID。闭环缺失

06｜你需要理解到什么程度

不是“每个服务的代码都看懂”才有资格判断去留。你要把精力集中在能决定产品质量、能在评审里追问、能给 badcase 定责的接口和状态上。

L4｜必须能独立画、讲、验收

  • Planner/Director：四类输入、Context、决策分支、依赖、重规划与结束条件。
  • Task/Trigger：何时创建、等待什么、命中什么、Run 怎么产生、失败后是否保留、何时清理。
  • 反馈语义：受理/成功/生效/目标完成四层；失败码、重试性、部分成功。
  • 评测与归因：能把 badcase 定到路由、Context、Planner、工具契约、执行、反馈或触发时序。

L3｜要懂契约与边界

  • ASR 与 Input Manager：输入字段、低置信度、打断/合并。
  • Advisor、Context、VLM、Dispatcher、Tool/Agent：谁触发谁，输入输出和异常。
  • 端云职责：为何走端、为何走云、断网怎么降级。
  • 版本边界：当前、WIP、提案、待确认。

L1–L2｜知道原理，不必下钻实现

  • ASR 声学模型、VLM 网络结构、LLM Attention/KV Cache 数学细节。
  • Trigger 的具体数据库表、Go 类名、RPC 框架实现。
  • 除非它们直接造成时延、成本、容量或安全取舍，再定向深入。
