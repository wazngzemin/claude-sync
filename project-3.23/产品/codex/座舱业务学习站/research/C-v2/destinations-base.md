## old-page.json 与当前页差别

旧 JSON 的 `sections` 是 8 个旧段落，当前 v64 是 15 个重写段落并新增 `v34` 正文；其余旧字段（teaching、feynman、mainline、concepts 等）仍与旧 JSON 相同，属于残留数据，不能误认成当前正文。当前原始节点全图也保留部分旧说法；“匿名硬门槛”“跨源保留出处作为现行能力”“背景包指标”等均需回源核实。

- **DEST-429｜旧版待核对｜old-page.sections/c-lesson-1/段1**：**Context 干的第一件事，是把九路来源并行铺开，而不是把所有东西揉成一段顺畅的话。**C1（接本轮输入按需要并行取背景）把身份、车况、情景、最近历史、任务视图、记忆、车型能力和适用经验分路去取。这九路数据形态不同：情景描述是多模态感知，事件日志是结构化即时数据，短期和长期记忆是非结构化文本，用户画像和端状态是结构化标签。Context 按标准化结构存和查，给规划模块、顾问、各执行方供数，但它自己不存原始业务数据。
- **DEST-430｜旧版待核对｜old-page.sections/c-lesson-1/段2**：这一步要解决的老问题，是传统座舱里的 AI 只听得见语音，看不见用户在别的界面做了什么、车况变成什么样、舱里坐着谁，于是连续对话接不上、场景理解差。产品体验上限一半靠模型能力，另一半就靠上下文理解；Context 既要按统一结构把这些异构数据管好，又要在海量来源里快速定位这一轮真正需要的那几条。
- **DEST-431｜旧版待核对｜old-page.sections/c-lesson-1/段3**：架构上经历过一次明确换代。最早的集中式方案走写入、粗筛、精筛三步：各源先各自粗筛一遍，再交一个统一模型精筛。上线后暴露两个毛病——为保速度把输出限到 5 个，靠前的数据更容易被放行，某一源准确率上去就挤掉另一源；端状态筛选要调两次模型，设计目标 P90 800 毫秒，实际跑到 1.2 秒。这两个瓶颈就是后来拆分的直接原因。
