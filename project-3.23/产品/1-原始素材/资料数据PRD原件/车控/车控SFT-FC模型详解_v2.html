车控 SFT FC 模型是什么：无网时替你"听懂人话并直接动手"的端侧小模型

一句话定义：SFT FC 模型 = 用"函数调用（Function Calling）协议"做训练数据、监督微调（SFT）出来的端侧小 LLM。它的唯一工作：把用户的语音指令在本地（不联网）翻译成结构化的函数调用 JSON——"空调调到23度" → {"函数":"空调温度调节","value":"23"}——200ms 内完成。它就是"三层漏斗"的第一层，Director 大脑前面站岗的快手。v2 变化：核心链路全部改成流程图，先看图再读字。

1为什么需要它：三个痛点 + 两个硬指标

痛点（PRD原文）车上的真实场景
网络依赖风险地下车库、偏远山区、隧道——弱网/无网，云端解析延迟高甚至失效
隐私安全隐患语音上云涉及通话内容、目的地等隐私，本地解析不出门
实时性不足在线解析走网络传输+云端排队，驾驶场景容忍阈值极低（紧急调温）
指标目标含义
响应延迟≤200ms从说完到函数调用出来的上限，比眨眼还快
指令识别准确率≥95%（日常场景）100句最多错5句——且错的代价是"没执行"，不是"执行错"
缓存命中准确率100%、50ms缓存层是"背答案"，不许错
对比体感：云端 Director 首 token P50=500ms，FC 模型 ≤200ms 出完整函数调用。简单指令要的是快不是聪明——FC 模型用"放弃理解深度"换"确定性的快"。

3.2 解剖一个函数：空调温度调节（槽位设计有多讲究）

槽位必填取值设计意图
value必填high/mid/low/max/min 或 "+15"/"-30%"/"23""调高点"→"+"，"调到15度"→"15"，"调高15度"→"+15"——相对/绝对靠 +/- 前缀区分
unit非必填摄氏度/华氏度/空单位独立成槽（你盯过的"带单位字符串剥单位"问题，这里正面解决）
position非必填主驾/副驾/左后/右后/前排/后排/全车/空"我这"→音区（说话人位置，不写死座位）
协议里的样本对（=SFT 训练数据长这样）
"主驾空调调高15度" → {"value":"+15","position":"主驾"}
"主驾空调调高到15度" → {"value":"15","position":"主驾"}
"副驾冷得不行温度调到顶" → {"value":"max","position":"副驾"}
"我要把右后的空调温度调到十分之九" → {"value":"90%","position":"右后"}
前两行差别只在一个"到"字。这种细微差别，规则系统写到崩溃，SFT 模型见几百个样本就学会了。协议表的"举例输入→举例输出"每一行就是一条训练样本，582 行表 = 这份模型的教科书。

4图③：SFT 是什么、为什么必须 SFT

图③ SFT 训练数据流｜协议表不是文档，是教材；模型不是"看懂"协议，是被协议"喂大"的
为什么不直接在端侧跑 Director 那套 prompt？原因
算力车端芯片跑不动 30K token SP 的大模型，只能跑小模型（十亿参数级）
时延200ms 硬指标，prompt 越长越慢，SFT 模型输入只要一句话
格式稳定性函数调用 JSON 必须 100% 合法（下游直接执行），prompt 约束小模型总会抽风；SFT 把格式练成肌肉记忆
协议变更成本改协议=补样本重训，vs 改 prompt=逐字调。表格驱动天然适合做数据管线
"如不属于离线范围时，离线模型输出「其他」" —— PRD 不包含范围
"输出「其他」"是最被低估的设计：它教会模型说"我不知道"。需要理解情绪的、需要联网的，模型不硬答，交回云端。一个离线系统的可靠性，不取决于答对多少，取决于能不能识别自己不该答的。

5白名单：27 个放行 / 24 个拦下，为什么

白名单"是"（27个，端侧直接执行）白名单"否"（24个，云端优先，端侧只兜底）
空调全家（5）、座椅（3）、车窗、氛围灯（3）、阅读灯、远近光、雾灯、方向盘加热（2）、驾驶模式、后备箱、全景影像；屏幕亮度/昼夜/音量/静音/退出语音；拨打电话；指定应用开关导航全家（13）、媒体全家（4）、危险警示灯、雨刮全家（4）、低速行人提示音、紧急呼救
三类"否"各有各的道理：
① 导航/媒体：协议会解析，但动作依赖在线数据（地图/曲库），离线执行了也是错——云端优先，端侧只兜底。高频说法（"导航回家""上一首"）由缓存层接管。
② 危险警示灯/紧急呼救：安全敏感，错了代价大，宁可慢点走云端确认。
③ 雨刮/低速提示音：v0.3 变更记录——"白名单与主线赛力斯可控制的车控范围对齐"。白名单=车型能力边界在离线层的投影。
同一句话在不同车型命运不同："打开雨刮"在赛力斯=否→云端；某车型开了雨刮语音=是→离线直接刮。FC 模型是同一份协议训的，白名单按车型配置——模型共享，放行策略定制。这就是"协议与策略分离"。

6拒识模块：前台接待，决定"这句话该不该理"

单轮拒识多轮拒识
管什么无上下文的单句意图判断需上下文关联的判断（代词/继承）
不拒识（召回）"打开空调"——意图明确的功能控制"打开空调"→"调到23度吧"——主客体动作与上文强相关
拒识"嗯嗯呀"/"继续防晒要走"——不通顺；"你晚上别和孩子玩太晚"——不是对车机说的"这个拒识效果还行"接"这台车的功能"——上下文无关
两个指标反着看：过拒=该理不理（用户喊三遍没反应）；漏拒=不该理瞎理（两口子聊天，车机插话"好的，已开空调"）。这是跷跷板，阈值往哪偏是产品决策不是技术决策。"车机乱插话/装听不见"类 badcase 就归这里。

7指令缓存：30 条背诵答案，50ms/100%

原则防什么
单轮解析：不引用历史"就选它了"依赖上下文，缓存没法知道"它"是谁
上下文无关：与会话状态无关"暂停播放/继续播放"依赖播放状态，不纳入
结果唯一：一条指令唯一意图+槽位有歧义要澄清的，回退到 FC 模型路径

30 条摘录：查看通话记录、播放下一首/上一首、打开歌词、播放蓝牙音乐、返回桌面、打开设置、媒体音量小一点、导航去公司/导航回家、退出导航、放大/缩小地图、打开空调/关闭空调/空调调到23度、打开座椅按摩、打开车窗、打开全景影像、退出语音。

清单里混着导航和媒体（"导航回家""上一首"）——它们在 FC 白名单里是"否"，但在缓存里是"是"。缓存是绕过 FC+白名单的第三条快速通道：这些说法太标准，连解析都不用，原样匹配直接出结果。"空调调到23度"能 50ms 响应，是因为它根本没经过模型。

9对抗式审查：协议数据里的三个坑 值得提给协议 owner

#坑证据（协议原文样本）后果
1车窗 action 标注自相矛盾"车窗开50%"→{"action":"关闭","value":"50%"}；而"车窗开到一半"→{"action":"打开","value":"50%"}；"车窗下降20%"（明明是开）→{"action":"关闭","value":"+20%"}SFT 最怕脏数据——同类说法两个 action，模型学出来就是掷硬币。车窗是安全敏感件，必修（大概率是"开度0=全开/100=全关"坐标系在标注员之间没统一）
2FC 协议有"强力制冷"，荣威家越07边界说没有空调开关 mode 枚举：制冷，强力制冷，制热，强力制热…；家越07 SP 能力边界："空调没有极速制冷，极速制热模式"车型能力错配：协议按赛力斯主线写的，荣威用同一套协议就会解析出车不支持的模式。解法：协议层支持≠白名单放行≠边界承诺，三层按车型对齐
3多轮样本混进"单轮解析"协议车窗函数里混着完整多轮样本（"副驾开10%→再开大点→主驾调成一样的"→{"value":"20%","position":"主驾"}）；驾驶模式也有"…给我切换一下吧"与缓存层"单轮/上下文无关"原则冲突——FC 到底吃不吃上下文？协议没表态。吃：时延和状态管理成本变；不吃：这些样本在教用不上的能力
第 1 个坑是最实的锤。修法建议：action 统一为"调节"、value 带方向；或明确定义开度坐标系后全表体检。提 bug 时把两种修法都写上，让对方选。

10对你工作的接口 落到你的地图

你的领域和 FC 模型的关系
三层漏斗排查路径"走错模块"类 badcase 前两站在这：该走 FC 的走了 Director（"打开车窗"等2秒），或该走 Director 的走了 FC（"我好热"被输出「其他」草率兜底）。FC 召回边界=体验快慢边界
信号格式 owner（仁杰线）FC 输出 JSON 就是端上执行契约——unit 独立槽、value +/- 前缀、position"音区"——和你盯的"端上报格式带单位"同一哲学：格式归产品约束，不是端上自由发挥
触发器条件任务触发后"[任务原文]+条件已触发"发给 Director——触发器叫醒的是 Director 不是 FC。但纯车控类条件动作（"10分钟后关座椅加热"）触发后完全可以走 FC 执行，这是时延优化空间
评测/badcaseFC 的 95% 和 Director 的 90% ACC 分开考核：FC 测"说法→JSON槽位对不对"，Director 测"缺失/冗余/错误"。别用同一把尺子
一句话收尾：FC 模型是"快手"，Director 是"大脑"。快手求确定性——确定的协议、白名单、时延；大脑求理解力——情景、记忆、目标。车控体验的 80% 满意度来自快手不犯错，20% 惊喜感来自大脑够聪明。两个都要懂，但评判要用两套标准。
