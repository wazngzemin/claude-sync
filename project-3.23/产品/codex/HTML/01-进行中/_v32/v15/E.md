## 06｜工具执行与反馈

Director 交出动作列表以后，动作不能停在一句打算上，得真正跑到车上、跑到工具里，再把真实结果收回来。这一层最容易出三类问题：受理成功就被当成事情已经做完；几个工具各说各的，节奏被打乱；失败了不回传，系统以为还在正常推进。

这一节讲执行层，承接上一章 Director 交出的动作列表，把每一项动作真正执行，收齐逐项真实结果，再交给输入管理送回 Director 判断。进门的是动作列表，交出去的是逐项执行事实。

主回路只有执行层、输入管理、Director 这一条。受理、流结束、业务完成和用户听见是四个不同的记录点，不能混成一个绿色成功。

## 进门四件核对：工具名、参数、权限、可否运行

这张图跟着游泳馆这一轮走。Director 交出的动作可能只是“查昨天那家游泳馆地址”，执行层从 **E1（接动作列表，核对调用身份）** 进门。E1 先做四件核对：工具名对不对得上、参数合不合法、这次调用有没有权限、现在能不能运行。每个动作关联唯一调用标识，保留原用户目标与本轮身份；格式错误就明确返回，不能一边解析失败一边给成功话术。这里的工具名是 Director 在系统提示词里看到的定义名，和实际跑起来的执行实现不是同一层对象，核对身份也是为了后面迟到回调还能放回正确的一次请求。

进门核对要解决的问题，是把模型输出的动作意图转成一次合法、可追溯、有权限的真实调用。模型生成动作时只看到工具描述和参数说明，并不掌握线上实现是否已发布、当前用户是否有权限、参数是否落在允许范围；如果不进门先核对，错误动作会直接发到下游，轻则接口报错，重则误操作车辆设备。四件核对各有分工：工具名核对解决模型是否选对了工具定义，参数核对解决参数格式、必填项和取值范围，权限核对解决当前用户、音区和租户是否被允许调用，可否运行核对解决工具当前是否在线、是否处于可执行状态。每个动作带唯一调用标识并保留原用户目标，是为了多工具并发、回执迟到和中断恢复时，仍能把每一项结果归回原动作，不会把 A 工具的结果记到 B 动作头上。不做这道核对的后果有三类：格式错误被下游吞掉后系统误报成功；无权限动作绕过检查落到设备；迟到回调找不到原始调用上下文，无法判断是否还要继续执行。

核对通过后，**E2（找本项目已发布可用实现）** 先在当前项目真实发布、已启用且有权限的实现里找对应能力。Agent 定义描述一个工具“是什么”，包含英文名、中文名、UI 名称（界面上展示给用户看的名称）和能力描述；Agent 实现描述它“怎么跑”，包含参数、租户归属、接入点和版本状态，同一定义通常要为不同渠道各建一份实现，渠道按 channel 加 channel_app_id 隔离。资料里出现过业务名不代表本车已经接入，同一个名字在不同渠道可能对应不同执行实现；找不到就走 **E12（失败出口：少承诺，不盲目重试）**，不能换个名字相似的工具碰运气。定义、实现、发布状态和权限的维护流程见[Agent 管理平台使用 SOP](https://bytedance.larkoffice.com/wiki/LCIvwi858iuqvWkTN7mcVZrBnhb)，单次调用与编排调度的职责分界见[Agent Server OnePage](https://bytedance.larkoffice.com/docx/KDJpd1kTmoDgEexJpTicZAlin8e)。

定义和实现分开管理，是因为同一个能力描述可能对应多个落地版本：不同车型渠道、不同租户、不同部署环境需要各自的接入点、参数适配和鉴权配置。管理面负责定义管理、租户实现管理、版本与环境管理以及动态工具信息，Director 能看到的工具名称、描述、参数说明、使用注意和提示语都由这一层控制；控制面在运行时按 agent_id 加租户加环境选择具体实现，环境草稿可以覆盖发布配置用于实验。把“是什么”和“怎么跑”拆成两层，模型侧只需要稳定的定义接口，工程侧可以独立更新实现而不必改动规划提示词；如果定义和实现混在一起，改一个渠道接入点就要重新训练或改写模型可见内容，风险很高。找不到实现时换相似工具碰运气，会让模型在错误业务域里连续尝试，错误被层层放大，因此合同要求如实走失败出口。

**E3（获得发布许可，按同轮规则发出）** 先确认候选仍然有效、登记调用，才把动作发出去。互不依赖、不争抢资源的工具同轮并发，相互排斥的工具分开执行；用户刚打断旧轮时，迟到的旧计算不会再替用户操作一次车。候选在发出前重新核对启用状态和权限，草稿、测试环境配置不能被当成线上可用；发布流程要求先在平台快速测试通过，再把版本状态从草稿变为已发布，这也是 E2 与 E3 不能跳过的原因。动态加载与准入条件在第 10 章展开。

发出前再核对一次状态，是因为从模型选出工具到动作真正发出之间存在时间差，期间工具可能被禁用、下线或权限变更。同轮并发的依据是动作之间没有参数依赖、不争抢同一硬件资源，并发能缩短整批等待；相互排斥的工具必须串行，避免两个动作同时控制同一设备产生状态冲突。先登记调用再发出，是为了中断、超时和迟到回执都有记录可查；用户打断旧轮后，旧请求已经发出的部分仍要收回执，但不允许再产生新的车辆动作。草稿和测试环境实现被误发到线上，会造成测试逻辑影响真实车辆，所以先测后发、草稿到已发布的状态流转是硬性流程。

## 单个 Agent 内部执行与回执阶段

**E4（交单个 Agent 执行内部业务）** 把这一项能力交给对应执行单元，由它补齐背景、填好参数、选执行器，查记忆、未来提醒、主动问图各走各的内部业务。Agent Server 处于链路底层，对外提供通用方式调用各类 Agent，屏蔽底层调用细节，自己不负责按 Planner 规划做编排调度，编排由 Director 完成。预处理阶段先按 agent_id 取出配置，再从请求参数或 Context 取得上下文依赖，挂上业务后处理；正式调用按 Agent 类型交给对应执行器；后处理把不同执行器的响应统一转座舱协议格式，特殊业务再做自定义后处理。外部三方 Agent 按统一 SSE（Server-Sent Events，服务器推送事件，服务端持续向客户端流式推送消息）协议接入，请求带 chat_id、question_id、conversation_id、query、agent_context 和 common_info，响应里三路内容必须分开：content 是上屏展示内容，tts_content 是交给语音合成播报的文字，model_content 是给 Planner 总结的上下文，具体字段、鉴权和错误码约定见[三方 Agent 接入协议](https://bytedance.larkoffice.com/docx/ZS6rd5ytKomVEwxDVebcKGTkn6d)。

Agent Server 内部按管理面、控制面、数据面与执行面分工。管理面维护定义、租户实现、版本环境和动态工具信息；控制面负责运行时实现选择、工具发现与准入、控制指令和生命周期控制；执行面负责请求转换与协议适配、执行通道、业务前后处理和响应收尾。执行通道支持 HTTP、SSE、Kitex（字节内部高性能远程调用框架）、MCP（Model Context Protocol，模型上下文协议）、Frontier 主动消息通道和本地工具等多种类型，业务处理器分为 BeforeRequest 请求前处理、AfterResponse 响应后处理、AfterAgent 单 Agent 结束后处理三类。这样分层的原因是上游 Director 只需要统一的动作接口，不需要知道下游是云端三方、内部 RPC 还是本地工具；协议适配集中在执行面完成，新增一种下游接入方式不必改动规划层。

协议请求里 chat_id 贯穿多轮对话，question_id 标识单轮问答，conversation_id 标识一组会话，trace_id 贯穿客户端一次请求里的全部操作，用于链路追踪；响应每帧带 chunk_type 回复块类型、content_type 内容类型、agent_id、is_finish 是否最后一块、finish_reason 结束原因，除三路正文外还有 reasoning_content 思考内容、command 跳转或降级命令、error_code 错误码和 error_message 错误信息。三路内容分开是因为上屏文字、播报语音和模型总结对表达要求不同：界面文字可以较长，播报文字要口语简短，模型上下文需要结构化事实；混在一起会出现屏幕文字被直接念出、模型拿到口语化内容难以推理的问题。command 命令对象正常情况不返回，只有合同允许的降级、跳转才出现，避免工具自行改变导航或界面走向。

**E5（返回的是受理、处理中还是完成）** 先分清“成功”落在哪一层。协议里的 is_finish 只表示这一帧是流的最后一块，座舱侧依赖它做收尾和落历史，不等于业务已经履约：执行单元回应流结束不等于车窗已经关上；任务注册成功不等于提醒已经送达；图片还在生成不等于图片已经交付。生图方案把状态分为未知、生成中、生成成功、生成失败四种，当前轮被打断后图片仍可由异步通道下发，正是“生成中”不能说成“已交付”的实例，状态口径见[生图云端技术方案](https://bytedance.larkoffice.com/wiki/MWVgwmcA9iq1KTk7yHZcWTgvnQh)。录音纪要则是另一类异步回执：语音只控制开始和结束，音频上传后才进入总结生成，纪要生成完成再异步推送，主请求先拿到的是受理状态，结果晚到，流程见[录音纪要接入技术方案](https://bytedance.larkoffice.com/wiki/W5OewmeRJiqp9nk37P1cRCFYnKe)。

把受理、处理中、完成分开记录，解决的是车内动作链路天然存在异步阶段：工具收到请求、业务开始办理、车辆状态真实改变、用户听到反馈之间可能相隔数秒甚至数分钟。is_finish 是流协议的传输结束标识，只告诉座舱这一帧之后没有更多流式数据，座舱据此收尾和写历史；业务履约状态要由工具自己在结果字段里表达。生图状态机把未知、生成中、成功、失败显式区分，当前轮对话结束后图片仍可经 Frontier 异步下发，说明生成中状态不能提前播报完成。录音纪要主请求先返回受理，音频上传、纪要生成、推送各有独立阶段，主对话不能把受理回执当成纪要已经生成。如果不区分这几层，最常见后果是语音提前说“已经帮你记好了”，实际后台还在排队或失败，用户被误导；排障时也无法判断断点在受理、执行还是异步交付。

## 逐项事实回流、同批汇集

**E6（把执行事实返回，保留错误原因）** 交回逐项事实。查询要区分“没查到”和“数值为零”，并带上真实地点、候选和必要时间范围；任务类回执区分注册已保存、本次查询到的任务状态、本次管理调用失败或取消三种来源，完整生命周期见第 12 章；车控说明哪个设备已经成功，失败保留具体原因和错误码。工具不能把自己返回的提示文字直接当作最终播报话术。单工具合同示例看停车缴费：面向 Planner 只暴露一个工具，内部封装注册、续费、查询、注销多个下游接口，对上游仍归一化为固定结构输出，缺少车牌时先由 Planner 追问，工具只做兜底校验和错误码映射，卡片与二维码由客户端渲染，合同口径见[停简单停车缴费工具技术方案](https://bytedance.larkoffice.com/wiki/M4MCwk9V0ihhETknqKtcYHiuneu)。同一句话包含多个操作时，要保留各项结果，成功项不能遮住失败项。

逐项事实回流要解决的问题是让 Director 拿到可判断的结构化结果，而不是一段工具自述文案。查询类结果区分空结果和零值，是因为“没找到游泳馆”和“找到的游泳馆人均为零”语义完全不同，模型需要知道缺的是事实本身还是事实取值。任务类回执区分保存、查询、管理失败三种来源，对应不同的后续动作；车控回执必须指明具体设备和成功状态，失败保留错误码才能定位是参数越界、设备离线还是权限拒绝。停车缴费工具把多个下游接口收敛成一个 Planner 工具，上游只看到统一合同，内部接口变化不影响模型调用；缺少车牌时由 Planner 先向用户追问，工具不替模型编造参数。多个操作并存时逐项保留结果，是为了让上层判断部分成功如何对外表达，避免一个成功动作掩盖另一个失败动作。

**E7（同批反馈汇集，迟到和缺失有归属）** 按本批汇集后再交；某个工具失败或超时，按工具合同形成终止事实，不无限等待，也不自造统一等待秒数。每条结果仍按原调用身份关联，迟到结果知道自己属于哪一批、哪一次请求；独立异步反馈这一期仍有缺口，不在主链路承诺。

同批汇集解决的是一轮动作列表里多个工具返回速度不一致的问题：快的结果不能单独提前打断 Director 决策，慢的工具也不能让整批无限等待。每个工具合同自己定义超时和终止条件，执行层不另造全局等待秒数；迟到结果携带原调用身份和批次归属，事后可以判断它是在本批决策前到达还是晚到补充。不做汇集直接逐项回流，会让 Director 被多个中间结果反复打断，动作规划碎片化；无限等待则会让一个超时工具拖住整轮响应。独立异步反馈一期缺口要如实标注，不能在主链承诺所有晚到结果都会自动回流到当前对话。

**E8（反馈只经输入管理回到Director）** 把整批结果交给输入管理，由输入管理安排何时进入 Director，不在执行层内另起推理。用户新话的插话优先级、旧轮取消和模型责任，都要统一回到这个大脑处理；执行层拿到结果后不能自己接着干，也不能自己组织新动作。

反馈必须经过输入管理回流，是因为执行层只看到单个工具的局部结果，看不到用户新插话、旧轮取消、主动服务建议等并发事件；由输入管理统一排队和插入，才能保证最新用户诉求优先，旧轮结果在取消后不再触发新动作。执行层自行组织新动作会绕过全局规划和权限核对，在多工具、多音区场景下容易发出互相矛盾的指令。这一规则也和第 03 章输入管理职责闭合：执行层负责把事实交回，理解和下一步决策归 Director。

## 核对口、话语权、真实结果核对

**E9（结果核对口：交给 D12 判断还差哪一步）** 把进展整理清楚，交回 Director 的 D12 判断原目标还差哪一步，成功部分、待确认部分分别标清；执行层不从这里直接生成新工具动作，下一轮决策仍由 Director 的 D11 输出一份说做一致的动作列表发出。

核对口存在的意义，是把“这一批工具做完了什么”和“用户原始目标完成了没有”分开。执行层只能确认本批动作各自回执，无法判断目标整体还差导航、还差确认还是已经完成；交回 D12 由大脑结合目标、背景和工具反馈判断下一步，执行层越权发起新动作会破坏规划闭环。成功部分和待确认部分分开标注，D12 才能决定继续调用、追问用户还是结束话题。

**E10（统一话语权，按项目保留直返例外）** 默认由 Director 根据事实组织回复，工具只把事实交回，不自己组织话术、不抢占播报；少数在配置里允许直接交付的工具，按自己的合同直接交付。旧的直返方式必须有配置依据，不能没有依据地沿用。三方协议里 tts_content 默认留空、播报由 Planner 总结，正是默认话语权归 Director 的协议体现；降级、跳转等命令只在合同允许时返回。

统一话语权要解决多工具同时回包时谁说话的问题。如果每个工具都按自己的结果组织话术，车内会出现多个模块抢播报、话术风格不一致、成功失败互相覆盖；默认由 Director 基于全部事实统一组织，可以保证回答承接上下文、风格一致。直返例外只留给合同明确允许、结果格式固定且不需要模型二次总结的工具，并且必须在平台配置里登记；协议中 tts_content 留空时使用 content，默认由 Planner 总结播报内容，就是这条规则在接口上的落点。没有配置依据沿用旧直返，会绕过统一话术和安全检查。

**E11（核对用户真正获得的结果）** 回到用户目标本身：空调是否真的改变、路线是否真的启动、卡片是否真的上屏、声音是否真的播到用户。接口回包成功不等于体验完成，核对不一致就走失败出口排查。工具清单与参数口径以[AI 汽车下游工具输入输出整理](https://bytedance.larkoffice.com/wiki/NxMVwYmqLijlubkKE54cVHfrnib?sheet=a471b5)为准；该清单包含重复标识与已弃用项，不能直接当成当前本车可调用工具数量，各车型实际可用范围按项目发布配置为准，当前工具数量【待核】，赛力斯、路特斯线另有差异。

E11 把核对口径从接口层拉回到用户真实体验。接口回包成功可能只是请求被服务端接收，车辆状态、界面卡片、音频播放都可能尚未完成；需要逐项比对模型话术、工具反馈、实际车辆、订单、卡片和播放结果。工具清单是配置参考而非实时线上工具池，重复标识和弃用项必须剔除，车型差异以发布配置为准。不做真实结果核对，验收会被接口成功率掩盖，用户听到的体验问题无法暴露。

**E12（失败出口：少承诺，不盲目重试）** 把停在哪一步说清楚，区分不可用、超时、拒绝和部分成功；有安全替代就交 Director 重新规划。失败也要走 E6 把执行事实返回、保留错误原因，失败不能不回；部分工具合同明确请勿重复调用，任务取消不回滚，需要人工接管时要向用户说明。文档没写的功能，不主观判定不存在，必须调工具按实际返回反馈，查不到就如实返回，不编造。

失败出口解决的是执行异常时如何避免二次伤害。盲目重试在车控、下单、缴费类场景可能造成重复动作或重复扣款，因此是否可重试由工具合同定义；不可用、超时、拒绝、部分成功需要区别处理，部分成功要保留已完成项和失败项。失败事实必须回流，否则 Director 和用户都以为流程还在推进；任务取消后已经执行的动作不会自动回滚，需要明确告知用户。对文档未覆盖的功能，先调用工具按实际返回判断，不凭模型先验编造不存在的结果。

回到游泳馆这一轮：查地址这一项从核对入口进门，走完核对、查找、登记、执行到回流，E5 确认拿到的是“地址已经到手”这一层，E8 把事实送回输入管理。地址回来时导航还没有开始，Director 判断还差导航，再发下一轮动作。

## 底部补充口径

画板底部五条是 2026 年 10 月执行侧补充口径，不改变 E1 到 E12 主回路。

**E13（离线白名单与云端仲裁）**【最高优先级】：无网时开空调、开车窗、调音量、问续航由端侧白名单直接执行和应答，不上云；云端拒识仲裁只在联网时生效，离线白名单与兜底规则的完整分工见第 02 章。离线白名单存在的原因是断网时基础车控和状态查询必须保持可用，这类动作参数明确、风险可控；但它和云端仲裁是两套条件，不能反过来要求联网时本地优先。

**E14（工具无自主播报权）**【已落地】：工具结果不直接抢占播报，多工具结果由上层统一组织，工具只交事实、不组织话术；话语权归属 E10 与 Director 的决策出口，本章不重复展开。这条规则已落地后，评审时重点检查是否还有旧工具绕过统一播报直接发声。

**E15（事件流注入窗口）**【输入侧口径】：最近十分钟以内、最近三十条事件以内才进下一轮推理，超出窗口不补、不追问；窗口长度与条数是否可配，按输入侧事件流配置核对。窗口限制解决的是上下文长度和相关性问题：过旧事件可能与当前诉求无关，全部带入会挤占上下文并干扰判断；超出窗口的事件不自动补取，需要用户明确追问再由对应模块查询。

**E16（车控耗时三说）**【资料冲突，待核】：导航和媒体执行 90 分位不超过 1500 毫秒各份资料一致；车控执行 90 分位有三份说法，路线图写不超过 100 毫秒、耗时分解画板写 150 毫秒、另两份转述写 1500 毫秒，验收前必须先对齐计时口径，不能挑一个对自己有利的数字上报。三份说法冲突可能来自计时起点不同、统计动作不同或版本不同，对齐时要明确从请求发出、工具受理、设备响应到状态回执各自的起止点。

**E17（失败话术模板七类）**：无此功能、有此功能不支持该方式、已是当前状态、超最大最小范围、未知错误、功能操作中无法控制六类已列入，由固定模板生成，不是模型现编；第七类口径【待核】。固定模板的好处是失败表达稳定、可审计，避免模型在失败时承诺不存在的能力；模板与工具错误码一一映射，新增失败类型先补模板再上线。

## 验收要点、性能口径与待核边界

评审这一章要先分清成功到底落在哪一层：工具返回“成功”时，要能指出成功的是受理、流结束、任务注册还是真实履约，受理成功不能对外说成动作已完成。遇到两个工具一个成功、一个超时，还要核对对外怎么说、能否重试，整体成功和盲目重试会制造误导和重复副作用，必须按具体合同核对超时和可重试性，不自造统一重试次数。工具结果之所以必须经输入管理回到 Director，而不能由执行层自己接着干，是因为插话优先级、旧轮取消和模型责任要统一在 Director 这一个大脑里。车控执行耗时在三份资料里口径不一致，验收前先要定清测量口径，否则性能验收每次都可以被解释掉。

参数与音区口径单独登记。数值参数支持直接到某度、正负相对调节、正负百分比三种写法；空调 16 到 31 度，“调一点”约定为 2 度，风量 1 到 9 档，车窗和座椅开度 0 到 100%、精度 10%；主驾副驾音区各自独立，后排跟随对应区。以上参数范围来自旧稿赛力斯能力口径记录，本轮未取到对应参数原始 PRD，数值范围【待核】，对外实现前按车型配置重新核对。参数三态要区分未传、显式默认和用户指定，相对调节必须以当前真实车辆状态为基准，不能以上一轮对话值代替当前设备状态。

准出指标从 Director 14 维评估表登记，不是执行层单独自测。强多轮任务闭环率考察导航、人脸注册、生态长程等强多轮任务，任务有效闭环包含任务完成，以及因下游原因失败并正确结束话题，不等于真实履约成功率，官方准出目标 92%；工具错误应答满意率考察工具发生错误后，是否推理出其他合理替代方案，或自然简洁地告知用户失败，漏处理、错误总结不通过，官方准出目标 95%。两项口径与打分细则见[Director 评测重点与打分指南](https://bytedance.larkoffice.com/wiki/EvErwmyvsirt8Tka41wckFxxnue)与[Director 评估维度和准出指标表](https://bytedance.larkoffice.com/wiki/GA6bwfWXIim2FmkOFJlcZfkmnnb?sheet=YWVS0m)，模块输入输出定义见[Director（对话推理引擎）PRD](https://bytedance.larkoffice.com/wiki/XRuKwJ0VPisdUhkxH0ecY1rRn9g)。真实结果一致性要求逐项比对模型话术、工具反馈、实际车辆、订单、卡片和播放结果，这一项是新增产品验收建议，数值门槛待补；端到端耗时要分别看首次工具、整批反馈、真实动作、首音和播完，不只看模型开口第一个字。独立异步反馈、少数工具直返例外都要回到配置依据核对，下一章看工具准入与单 Agent 协议怎样约束谁能被调用。

## N4｜工具使用与工具执行三类：控制、查询、复杂 Agent

用户一句话说完，系统听懂了意思，不等于车就会动。这一步要把这句话翻译成车上真实存在的一个操作：调哪个功能、填什么参数、交给谁去办，办完再用一句人话告诉用户。翻译错了，要么调不出功能，要么参数离谱，用户听到的就是一句答非所问。

前面简单和复杂的分流已经做完，这一章站在两条路的汇合点：一句话经过工具映射调度，再按控制、查询、复杂三类走下去，看它怎样被翻译成一次真实执行，执行结果又怎样回到用户耳边。

## 先按复杂度分四路，让最简单的话走最短路径

映射调度是翻译的第一道关卡。**N4-01（映射调度分关卡｜四路按复杂度走）**接收上游 N3-05 分来的简单任务，以及 D 图 Director 给出的 action_list，也就是任务序列，再按这句话的复杂度选一条翻译路线：高频简单的指令走 SFT 路线，需要抽取参数的走 PE 路线，要判断交给哪个下游执行体的走 Agent 解析路线，断网时只走离线指令解析路线【2.6 目标】。分路线的目的是让最简单的话用最短的路径出结果，不把每句话都送进大模型做一轮完整推理，路线划分依据见 [Director（对话推理引擎）PRD v1.7](https://bytedance.larkoffice.com/wiki/XRuKwJ0VPisdUhkxH0ecY1rRn9g)。

Director 在分路线之前拿到的背景材料由几部分组成：对话历史、端状态、舱内外乘员与情景描述、人人对话和人机对话记录、工具调用的输入输出、屏幕信息以及用户记忆。这些材料决定一句话能不能被理解成简单指令；同样一句“有点热”，结合端状态看到空调已经开到最低，就不会再拆解出调低温度，结合记忆看到用户不喜欢吹风，就不会拆解出大风量。四路分流本质上是按推理成本和句式稳定性分层：固定句式、固定槽位的高频控车交给小模型直出，说法发散、需要补槽位的交给提示工程路线，找不到单一函数承接的再交给 Agent 解析，网络不可用时退到端侧离线白名单。如果不做分层，所有指令都走云端大模型完整推理，高频控车的响应时延和云端算力都会被无谓抬高；反过来如果把复杂指令也交给小模型直出，槽位和对象更容易填错。

**N4-02（FC-SFT｜小模型直接出函数）**处理“把空调调到 24 度”这一类高频简单控车，模型直接给出函数名和参数，不再多做一轮语义拆解。这类话句式固定、槽位少，直出最快，例如“调到 24 度”对应函数 set_hvac_temperature，参数为 24。需要强调的是，SFT 路线只输出函数调用，不是让小模型生成给用户听的话术。按 [【ToB 主线】车控 2.0 方案总文档](https://bytedance.larkoffice.com/docx/NG9fwYX7IiOBv9k4sIDcvr9dnif)记录，SFT 链路历史耗时约 160 毫秒，这是方案文档中的历史测试口径，不是当前线上承诺阈值。SFT 与 PE 的范围拆分由车控 2.0 方案划定：训练覆盖的高频指令走 SFT，未覆盖但意图明确的走 PE 提示工程，工程校验环节还会拦截非法函数名和非法参数值，不让模型把没登记的函数发到执行层。

**N4-03（FC-PE｜需要槽位提取）**承接意图已经清楚、但参数要从话里抽出来的指令，例如“把我刚才说的那个地址设为常用地点”。PE 指提示工程路线，按槽位规范先把对象抽出来，再填进函数。它和 SFT 的分界看槽位多少与句式稳定性：槽位一多、说法一散，直出就容易填错，必须先做提取；槽位提错，后面执行跟着错。同一份车控方案文档记录，PE 路线历史上函数选择 P90 约 700 毫秒，提槽复杂集 P90 约 1.06 秒，整体比 SFT 慢，这些是历史测试数据，当前线上阈值以项目评测基线为准【待核】。PE 路线先补全必填参数，缺参数时向用户澄清，能按音区、默认值补齐的先补齐，补不齐才发起追问；这一步宁可多问一句，也不能把错误参数填进函数直接下发。

**N4-04（Agent 解析｜交给哪个 Agent）**处理找不到单一函数承接的请求：先判断这条请求该送进哪一个下游 Agent，再由执行体走自己的业务通道。这一步的下游执行体归属、接入渠道和版本范围仍在建设中，不代表所有复杂请求都已有对应执行体承接【2.6 目标】。

**N4-05（离线指令解析｜断网兜底）**是单独的一条断网路径：只有端侧保存的一小份离线白名单能在无网时办理，例如开空调、开窗、调音量、问续航；清单之外的事项，端侧只能提示用户稍后再试。画板登记离线白名单为 573 行，与在线清单分开维护，离线条目数量在可读一手文档中未再次核对到出处，按画板口径引用【P1，待核】。在线清单和离线白名单分开维护，是因为断网时云端协议一份都取不到，必须提前把最基础的控车项固化在车上；在线不可用时自动降级到离线路径，超出离线范围只给出网络异常提示，见 [车载语音助手控制类工具 DM 设计](https://bytedance.larkoffice.com/docx/CD4gdPqD3oz3F2xWfD5cFLuHnFc)。离线优先策略是离线 NLU 范围内高置信召回优先使用离线模型加离线话术；离线未命中再优先云端结果，云端超时无结果时端上有结果就用端上结果，端上无结果才走兜底提示。语音来源还要区分车内和车外：车内音区为主驾、副驾、二排、三排，车外另有前后左右四个独立音区；车外语音只开放白名单功能，新一轮唤醒音区来源切换时清除上一场景上下文，不跨场景继承参数。

## 函数先过协议清单核对，再分三类并排执行

不管走哪条路线，函数名都要先过 **N4-06（FC 协议清单核对｜所有函数必须对得上清单一条）**。所有调用必须对得上清单里已登记的一条，清单上没有的功能，模型想调也调不出来，这是防止它编出一个不存在的车控功能；模型输出不属于协议范围的函数、参数或参数值时，工程校验直接拦截并返回不支持。画板登记在线清单 1115 条，分类为车控 664、系统 170、导航 132、媒体 112、电话 20、应用 15，分类计数以清单实时版本为准【已落地】。参数按三种形态表达：绝对值、相对值加减、相对值百分比，例如调到某个固定温度、风量调高一点、音量上调一个档位；空调温度区间、“调一点”约定步进、风量档位范围都在清单里写死，模型不能自造温度区间、约定步进或风量档位。离线另有一份单独成表，和在线清单分开维护。核对这一步还要看当前车型有没有开放这项能力：同一套协议表在不同车型上的开关不同、可用集合不同，某车型不支持的条目在该车配置下置灰，模型不会把它当成可用能力，具体置灰条目以该车配置为准【待核】。清单核对之外，Agent Server 在控制面还要做工具发现与准入：按 Planner 可见性过滤可调用集合，支持 DirectAgent 直调，并在调用前做用户权限预检查；管理面登记每个 Agent 的英文名、中文名、界面名称、能力描述、租户实现、版本环境与动态工具信息，保证 Planner 看到的工具集合和实际可执行集合一致。

核对通过后按三类并排执行。**N4-07（控制类｜函数落在车上）**承接车控车设、行程导航、媒体娱乐和应用操作，“调到 24 度”命中这一路，动作直接作用在车辆或设备上，回应要快。车控执行耗时目前存在三套口径：Roadmap 写 ≤100 毫秒、画板标注 150 毫秒、口头转述为 1500 毫秒，三套资料相互冲突，最终阈值以项目评测基线为准【待核】；画板另标导航、媒体 P90 ≤1500 毫秒，这两类依赖车企侧响应，不与车控回执混在同一口径下考核。Director 引擎整体首 token 目标为 P50 500 毫秒内、P90 800 毫秒内，这是对话引擎口径，不等于工具回执时延，两组数字不能混用。

控制类指令真正下发前，DM（对话管理）按六个阶段串行处理。第一阶段语义接入与来源裁决，判断函数来自在线还是离线、语音来自车内还是车外，来源标记贯穿后续所有阶段。第二阶段参数补全与澄清，必填参数缺失时先按 NLU 已有信息、说话音区和默认值补全，补不齐再向用户澄清。第三阶段音区权限校验，判断哪个音区在说话、该函数在该音区是否可控，例如后排只能控制后排车窗，儿童锁打开后仅主驾音区可控后排车窗或车门。第四阶段安全兜底与二次确认，根据车辆状态决定直接放行、二次确认、条件降级还是硬拦截。第五阶段执行分发与接口闭环，下发指令并回收成功、失败、超时状态码。第六阶段话术生成与 TTS 输出，在线路径由云端 Director 生成自然话术，离线路径匹配端侧固定模板。校验分两层互为补充：DM 层能提前拦的提前拦，减少无效指令下发；车企接口层是最后一道安全兜底，即使 DM 未拦截，接口侧也会基于实时车辆状态拒绝或降级，例如车速超过 80 公里每小时车窗只允许打开一点点、雨量传感器联动关闭天窗、障碍物检测防碰撞、洗车模式拦截。正常路径六阶段全通过后下发并播报；权限不足或硬约束触发走拦截分支终止执行；软约束触发走二次确认分支，播报风险提示并等待用户确认；安全边界内可有限度执行时走降级分支，参数自动降级并附带降级说明。

**N4-08（查询类｜不改车状态只取信息）**承接联网查询、知识查询、端状态查看和视觉查看，“附近有什么馆子”命中这一路。它只把信息取回来，不改动车上任何状态；这一类慢是正常的，答案要去外面问、去知识库里找。端状态查看同时是一道防线：系统先读到空调已经打开，就不会再下发打开空调或调低温度的指令，避免车已经开着空调仍被推开这一类 badcase。工具归属与输入输出范围见 [AI 汽车下游工具输入输出整理](https://bytedance.larkoffice.com/wiki/NxMVwYmqLijlubkKE54cVHfrnib?sheet=a471b5)。查询类与控制类分开考核时延，是因为两类等待的外部条件不同：控制类等待车辆回执，查询类等待网络、知识库或视觉结果，混在同一个时延指标里既看不出车控慢在哪，也看不出查询慢在哪。

**N4-09（复杂 Agent｜单条函数搞不定）**留给一条函数办不成、需要分步调多个工具的请求，下游分三种：三方 Agent 对应外部生态，GUI（图形用户界面，指屏幕界面操作）Agent 负责操作屏幕，复杂豆包 Agent 负责多步推理。“找人均一百左右的日料店，再导航过去”要先查餐厅、再让用户选、再发起导航，依次经过查询、选择、导航多个环节。这一路仍在讨论中，执行体覆盖范围随版本推进【讨论中】。三方 Agent 的接入规范、鉴权方式和回包格式见 [三方 Agent 接入协议](https://bytedance.larkoffice.com/docx/ZS6rd5ytKomVEwxDVebcKGTkn6d)；Agent Server 负责单次 Agent 的管理、协议适配和前后处理，不负责 Planner 层面的编排调度，职责边界见 [Agent Server OnePage](https://bytedance.larkoffice.com/docx/AQxOwJet9ieV5bkstANcvYHLn5f)。

Agent Server 处在链路最底层，把各类 Agent 的调用细节屏蔽给上层，内部按管理面、控制面、数据面与执行面分工。管理面负责 Agent 定义、租户实现、版本环境和动态工具信息；控制面负责运行时实现选择、工具发现准入和控制指令；数据面与执行面负责请求转换、协议适配、执行通道、业务前后处理和响应收尾。单次调用的预处理分三步：按 agent_id 检索配置信息，从请求参数或 Context 模块取上下文依赖，挂上该 Agent 需要的后处理逻辑；调用阶段按 Agent 类型由对应 Executor 执行；后处理把不同 Executor 的响应统一转成座舱协议回包格式，特殊业务再走自定义后处理。控制指令分三类：Redirect 最多两次，用于指定下一跳目标 Agent，支持 A2A 场景；Interrupt 结束当前调用；Fallback 没有通用自动重规划，失败后不自动换一个 Agent 重试。Context 取消信号会向下游传播，少数任务允许 WithoutCancel 不被取消。上下文获取包括历史对话、长短期记忆、端状态和系统提示词、用户提示词，其中记忆的传递和使用方式仍在待定；Agent 输出在 IsFinish 为真的包时存入历史表并结束本次调用。Planner 负责编排、工具选择和结果总结，Agent Server 只负责单次调用及调用内控制，两者边界不能混。

还有一条并列出口 **N4B（GUI 操作执行｜生活服务出卡片）**：用户要的是订座、点餐这类生活服务而不是车控时，动作落到小程序动作上并列执行，屏上直接拉出对应卡片，例如“附近餐厅订位”真的打开订座卡片。虚拟屏是给小程序开的专用画布，GUI Agent 可以在虚拟屏中后台运行，不打断用户当前使用；该方案依赖系统方提供稳定投屏连接、应用列表与截图权限，以及 Virtual Display 虚拟屏能力，哪些车型开放需要单独核对，属于量产风险项【量产风险，待核】。涉及付款、提交订单等敏感步骤，Agent 在确认前停止执行，等待用户确认，不替用户完成支付。

GUI Agent 当前有两套技术方案并存。方案一是 RPA（机器人流程自动化，模拟用户在界面上操作的流程自动化软件）加小程序加前台运行，UI-Tars 视觉模型做兜底和识别增强；局限是生态有限、泛化性弱，新增场景需要大量标注等前期工作，并且必须在前台运行，可能干扰用户正常信息展示。方案二是 UI-Tars 这类 VLM（视觉语言模型）加手车互联反控加虚拟屏后台运行；局限是手车互联依赖投屏协议，不同设备适配成本高，手机熄屏可能导致无法反控，VLM 执行速度慢、单步达到秒级，并且强依赖模型能力、可能产生幻觉。执行引擎把动作分成四类：常规事件如点击、双击；Clarify 澄清，需要用户补充信息，例如收货地址缺失；Approve 授权，敏感操作需要用户确认，例如查到停车费 8 元后询问是否直接付款；Handoff 交接，Agent 无法处理时交给用户接管。实测中暴露的工程风险还包括页面未渲染完成就截图，导致下发的点击坐标失败，截图时机需要产品、研发、测试共同确定策略；模型具备一定反思能力，发现操作不符合预期时可以回退并尝试另一种方案。生活服务覆盖订座、外卖、电影、酒店、机票、快递、会议等场景，统一在支付或提交订单前停止执行。

## 执行完先套模板说人话，再交到播报出口

三类执行完，结果都汇到 **N4-10（NLG 模板｜执行完说人话）**。NLG 即自然语言生成，把执行结果套进固定模板说成用户听得懂的话。成功话术走固定模板，参数从槽位填进去，例如“开啦～”“调到「参数」啦～”这种短句；失败按固定类别各配一句说法，覆盖没有这项功能、不支持这种操作方式、已经是当前状态、超出最大最小范围、未知错误、功能正在操作中无法控制等枚举情形。话术由模板生成，不是模型现场现编，现场自由发挥就可能编出清单里根本没有的功能名。工具本身没有自主播报权限，工具清单中基础车控与查询工具的“是否要工具播报”均为否，工具只交回事实，说什么话统一由上层组织。在线路径由云端 Director 生成自然话术，离线路径匹配端侧固定模板，失败原因码回传后再生成解释话术。

话术质量和工具调用质量在评测中分开打分。按 [Director 评测重点与打分指南](https://bytedance.larkoffice.com/wiki/EvErwmyvsirt8Tka41wckFxxnue)，核心维度包括说做一致、工具调用错误、工具错误应答满意率、首工具调用时延、闭环总耗时和 token 消耗。说做一致要求话术承诺的动作和实际执行结果一致，说了开灯却没开属于明显扣分；工具错误应答满意率考察工具返回失败后，系统解释得是否清楚、用户是否接受；首工具调用时延衡量从请求到第一次发起工具调用的等待；闭环总耗时衡量从 query 到任务办完；token 消耗衡量一轮闭环平均用掉的上下文规模。打分采用 0 到 4 分：4 分任务完美解决且结合背景主动推演，3 分核心意图准确、主指令全部执行无多做无少做，2 分大方向对但有轻微参数错误或遗漏非核心小指令，1 分任务拆解严重缺失或主体错乱，0 分南辕北辙、做出危险操作或严重幻觉。模板话术的价值就在于把成功和失败的表达稳定落在 3 分以上的合格区间，避免模型在失败时临场编造不存在的功能名。

最后由 **N4-11（交 O 图播报｜绿出口）**把这句话和卡片交给播报展示侧；真实车态同时回流到 M 图记忆与状态侧，出口在画板上标向 O 图。这一步只负责交接展示，不重新决策动作。

## 沿“调到 24 度”走完整一圈，以及评审要盯住的问题

沿“把空调调到 24 度”走完整一圈：N4-01（映射调度分关卡｜四路按复杂度走）分到高频简单控车，N4-02（FC-SFT｜小模型直接出函数）直接给出函数名和参数，N4-06（FC 协议清单核对｜所有函数必须对得上清单一条）确认参数合法、本车型开放，N4-07（控制类｜函数落在车上）真正把空调调到车上，N4-10（NLG 模板｜执行完说人话）填出一句“调到 24 度啦”，N4-11（交 O 图播报｜绿出口）交到播报端。空调真的调过去了，话也播出去了，这一轮执行闭环才算走完；下一轮要不要继续调整，由后续规划结合结果再判断。

评审时按顺序逐项问清。先确认这个功能登记进清单了吗，在当前车型开关下是不是亮的：模型只能调用清单里有、且本车型本渠道开放的条目，清单没有或车型关闭，都调不出来。接着判断这条指令走直出还是走槽位提取：路线选错会拉长响应，槽位一旦提错，执行结果跟着错。再确认断网时这份指令端侧能不能办理：离线白名单之外的事项断网只能提示，需要提前知道哪些基础控车项被固化在车上。之后核对失败话术走模板还是模型自由发挥：自由发挥会编出清单里不存在的功能名，用户照着找只会更困惑。最后排查功能已经在清单里、为什么这一轮运行时仍然看不到：定义存在、渠道接入、发布启用、用户权限和这一轮条件是几道分开的门，逐层都要有证据，不能只凭清单存在就判定可用。

准出指标以 [Director 评估维度和准出指标 v0.2](https://bytedance.larkoffice.com/wiki/GA6bwfWXIim2FmkOFJlcZfkmnnb?sheet=YWVS0m) 为准：明确单意图指令工具调用准确率准出 95%，明确多意图指令工具调用准确率准出 95%，模糊指令满意率准出 90%，强多轮任务闭环率准出 92%；以上是准出目标，不是当前线上实测成绩。旧稿记录的协议解析出参 P50 350 毫秒、P90 450 毫秒，以及映射与执行整链通过率后续目标 95%、再往后 100%，在可读一手资料中未核对到出处，本章不写成承诺指标【待核】。车控执行时延从函数下发到收到车辆回执单独统计，导航、媒体执行时延从函数下发到动作生效单独统计，话术首字时延从执行完成到播报第一个字单独统计，三类口径不混算；工具错误应答的满意率要求见 Director 评测重点与打分指南。评测集分基础能力、关键场景和高阶能力三层组织：基础能力覆盖单意图、多意图车控与查询，关键场景覆盖导航、VQA 等高频真实场景，高阶能力覆盖人格价值观、情绪情感、认知智力、自主性与关系记忆等维度；准出通过率按各层测试集分别统计，功能边界、幻觉、安全和风控测试集单独考核。

画板补充区属于下游通道实现细节，本章不展开：协议适配层按项目选择 aidv、dpfm、doubao、ecology、internal_rpc（内部远程过程调用协议）五种协议；执行通道共六条，分别是 HTTP、SSE（服务器推送事件，服务端持续向客户端流式推送消息）、Kitex（字节开源的 RPC 框架，RPC 即远程过程调用，像调用本地函数一样请求另一台服务上的方法）、MCP（模型上下文协议，统一模型连接外部工具与数据源的标准协议）、Frontier 和本地工具；所有通道都过 BeforeRequest、AfterResponse、AfterAgent 三个前后处理钩子，结构化结果才回 Director；音乐只有结构化数据，必须先转成文本再进入模型上下文；联网请求按场所美食、娱乐、知识、风险等主题路由到对应 Agent 或兜底能力。通道归属与接入规则见 Agent Server OnePage 与三方 Agent 接入协议。三类执行耗时预期不一样：车控属于毫秒级回应，导航和媒体依赖外部响应属于秒级，复杂分步不设统一硬指标；失败时不能预设结果，要拿到真实回执再决定话术，已经产生车辆动作的事项也不能为了显得积极就重复下发。下一章看这些背景事实在进入推理之前怎样被筛选、打分和压缩。
