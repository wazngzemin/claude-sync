## 10｜工具准入与单 Agent 协议

上一章可见即可说里，语音已经把“第二个”匹配到卡片上一个按钮。这个按钮到底由谁、按什么规矩真正执行，属于工具准入这一环。这一章讲工具准入与单 Agent 协议：一个工具怎样被定义、这一刻允不允许运行、调用完怎样按统一协议把结果交回来；它不是车上第二个规划大脑，总规划还是 Director。

## 准入闸门一：定义、渠道版本、人与车

先看 F 图在链路里的定位。Director 面前摆着若干候选工具，哪些此刻能用、参数是否齐全、结果怎样存进历史，需要一组闸门逐层把关。F 图是工具执行模块内部的细化支路，不做整套任务编排，干三件事：定义工具能做什么、判断这一刻能不能运行、按统一协议交回结果。

准入闸门要解决的根本问题，是模型可见的工具集合和真实可执行的工具集合并不天然一致。模型提示词里出现某个工具，可能只是后台曾经配置过，并不代表当前车型已发布、当前用户有权限、当前条件成立；如果不逐层把关，模型会调用不存在或不允许的能力，造成报错、越权或误操作。闸门按定义、渠道版本、人车权限、动态条件顺序排列，前一层不通过就不进入下一层，每一层都留下可追溯证据，评审时可以逐层回答“为什么这个工具此刻不可用”。

从背景准备进来，先到 **F01（先有业务定义，再找具体实现）** 立规矩：这个工具负责什么、叫什么、给模型看什么能力描述、在哪里执行。Agent 定义描述工具“是什么”，包含英文名、中文名、UI 名称和能力描述；同一个业务标识可以绑定多个实现变体，模型看到的工具名并不会因此凭空变多；定义、实现和版本分别维护，不是一张工具名表就能调用。

定义和实现分离，是为了让模型看到稳定的能力契约，工程侧可以独立更换落地方式。定义层维护工具身份、对外名称、能力描述、参数说明、使用注意和提示语，这些内容直接进入模型提示词；实现层维护接入点、参数格式、租户归属和运行状态。同一定义为不同渠道各建实现变体，模型侧不需要感知渠道差异。如果把定义和实现合并成一张表，调整接入点或参数格式就要改动模型可见内容，工具描述和真实能力容易脱节；定义先行也保证工具发现阶段先确认业务存在，再讨论怎么落地。

定义之后到 **F02（选择渠道、环境和启用发布版本）**，在变体里挑当前这一次请求用哪一个，渠道 channel、应用 channel_app_id、环境和已发布且启用的版本一起核对。后台存过测试草稿，只能证明有人配置过，不能证明这次请求会用到；车端还是云端集成、由谁提供承接是另一层信息，是否参与 Director 推理还有独立配置。定义、实现、发布状态和权限的维护流程见[Agent 管理平台使用 SOP](https://bytedance.larkoffice.com/wiki/LCIvwi858iuqvWkTN7mcVZrBnhb)。

渠道和环境核对要解决同一工具在不同车型、租户、部署环境之间的隔离问题。channel 加 channel_app_id 确定租户归属，环境区分草稿测试和线上发布，只有已发布且处于启用状态的实现才能被当前请求选中；环境草稿可以覆盖发布配置用于实验对比，但线上正式请求不能落到草稿上。工具是否参与 Director 推理还有独立可见性配置，和实现是否存在是两件事。不做这一层核对，测试环境工具可能被线上请求调用，或者同一工具在不同渠道落到错误实现。

接着 **F03（检查用户权限与车辆能力）** 查人又查车。可信账号确定角色，车型、设备、音区和驾驶状态约束一起核。车机同时存在车企 OEM（原始设备制造商，即车企）账号和豆包账号，OEM 账号负责车辆关系与权限，豆包账号负责豆包会话与智能体体验；请求进入业务前先校验 vehicle_id 与 account_id 的可信绑定和角色，客户端上报的角色不能直接作为可信依据，再由 Agent 权限守卫在 Agent 或工具执行前综合登录态、账号角色、FaceID 人脸身份和车辆状态做授权。模型这一轮输入里看得见这个工具，不代表此刻对这位乘客就允许执行，开车时某些屏幕类操作就应当被禁止；拒绝要给出原因，不能伪造成功，身份与权限边界见[账号/乘客 OnePage](https://bytedance.larkoffice.com/docx/Y9sod55uXoWKkDxhDyMcRuNunid)。

身份体系分四层对象：vehicle_id 是车辆唯一标识，可用 VIN（车辆识别代号）或其加密映射，确定数据归属车辆；account_id 是 OEM 体系内全局唯一的车企账号，承载车辆所有权、授权角色和车控权限；volcano_account_id 是 AI 汽车抽象的统一火山账号，屏蔽豆包账号与非豆包账号差异，作为任务和账号配置的稳定关联键；vehicle_user_id 是车内可持续识别的乘客编号，统一承接 FaceID、声纹、昵称、关系和乘客类型。可信入口先通过车企云校验 vehicle_id 与 account_id 绑定关系并获取角色，客户端上报的账号和角色不可信；账号域维护 OEM 与豆包登录态，乘客域在 account_id 边界内完成注册识别，最后由 AgentPermissionGuard 在执行前综合登录态、账号角色、FaceID 和车辆状态放行。校验失败或依赖不可用时，高权限能力按失败关闭处理，而不是默认放行。这样设计是因为车内同时存在多乘客、多账号和驾驶安全约束，只靠模型判断“能不能用”无法承担权限责任；权限策略按渠道和 Agent 集中配置，避免散落在各业务代码里。未识别乘客或账号校验失败时只使用匿名上下文，不读写乘客私有记忆，同车不同账号之间的乘客关系也不能互相命中。

## 准入闸门二：动态条件与实时卡片

通过账号和车辆检查后，到 **F04（检查动态工具的运行条件）** 看当前条件。动态加载机制把静态工具和动态工具分开：静态工具常驻工具集，动态工具只在特定场景成立时才出现，避免普通语音交互干扰工具选择。条件引擎采用逻辑组合加原子条件两层结构，多组条件之间是且或关系，每个原子条件由字段来源、字段名、字段类型、判定方式和取值列表构成；本期字段来源只支持请求参数 param，判定方式支持存在、不存在、属于集合、不属于集合四类。接入端状态和触发器条件是后续方向，届时复用触发器服务已有的端状态解析判定能力。条件不成立，这一轮就不加载，不能靠模型自己补一个成立的场景，机制细节见[动态加载型工具技术方案](https://bytedance.larkoffice.com/wiki/T8jDwzwO9iiNF0kbFEVc1uyrnIf)。

动态条件闸门解决的是工具集合随场景变化的问题。常驻工具数量有限，而页面卡片、媒体状态、乘客身份等场景条件随时变化，如果把所有可能工具都常驻注入提示词，模型选择面被稀释，参数混淆概率上升；动态工具只在条件成立时进入本轮工具集。logic_type 定义多组原子条件之间的且或关系，conditions 数组每一项是一个原子条件，field_source 指定从哪类数据源读取字段，field_name 指定字段名，field_type 指定类型，judgement 指定判定方式，values 给出取值列表。本期 field_source 只支持 param，即从本轮请求参数读取；exist 判断字段非空，not_exist 判断字段为空，in 判断属于集合，not_in 判断不属于集合。端状态条件后续复用 Trigger 服务已沉淀的信号解析和判定能力，避免重复建设。条件不成立时工具不进入候选，模型不能自行假设条件已经满足；这一层把场景判断从模型自由推理变成可配置、可回放的规则。

条件成立时，**F05（实时卡片提供可操作按钮语义）** 把卡片标识 card_id、标题、内容和真实按钮名称带进请求，用户说“第二个”才有对象可核对；卡片换了或不存在，不能凭旧历史假造按钮。常驻工具和条件工具槽位分开，这条支路不是视觉模型读屏点页面；本期卡片信息通过实时卡片参数传入，未来归入 Context 统一管理，属于规划方向。

实时卡片条件解决的是页面按钮对象如何进入工具参数的问题。real_time_card 参数携带标题、内容、按钮、理由和卡片标识，工具条件判断该参数存在才加载；出参 select_button 回传用户选中的按钮。卡片是当前会话临时对象，随页面出现和退场变化，不能被缓存成长期工具；卡片不存在时凭历史假造按钮，会把旧页面对象套用到新请求。本期由参数直接携带卡片信息，未来归入 Context 统一管理，是为了和其他背景来源的组织方式保持一致。

条件成立的卡片工具和常驻工具一起进入 **F06（把符合条件的工具描述注入 D）**，可用工具说明放进这一轮输入，再交 C11 组装这一轮背景给同一个 Director，Director 才能选择。有条件加载的页面工具不是所有车永远存在的固定工具；工具说明更新后要随版本一起发布，否则车上仍可能读到旧定义。Director 侧取在线工具集、拼成工具列表注入提示词变量的过程，见[Planner One Page](https://bytedance.larkoffice.com/wiki/EWziwFVftiGvnlk0FA4cadqonud)。

注入阶段解决模型如何看到候选工具的问题。Planner 准备阶段先调用 GetPlannerAgentList 取在线工具集，再由 injectToolInfos 把每个工具的中文名、tool_name、描述、参数、notice 注意事项和 tips 提示拼成 tool_list 注入提示词变量，随后构建 ReAct（推理加行动循环）图启动。工具描述、参数说明、注意和提示直接影响大模型选工具和填参数，因此平台配置内容必须和发布版本同步。如果条件成立的工具没有进入本轮输入，模型只能在常驻工具里猜测；如果已失效工具仍被注入，模型会选中不存在的能力。

## 选中后校验与单 Agent 执行

Director 选中之后还不能立刻发出，**F07（模型选中后校验）** 逐项核对参数名字、必填项、类型和取值范围。卡片工具要选真实按钮并关联正确卡片，车控工具要说清设备、位置和动作；用户表达含糊可以澄清，模型漏掉已明确参数属于系统问题。条件仍有效、业务和副作用许可都满足，才发出调用；校验失败交回模型说明原因或发起澄清。

选中后校验是模型输出和真实执行之间的第二道保险。模型生成动作时可能出现参数名写错、必填缺失、类型不符、取值越界，或者把卡片按钮关联到错误卡片；这一层在发出调用前拦截，避免错误参数直接打到下游。条件在模型思考期间可能已经失效，发出前需要重新核对；存在副作用的车控、下单、缴费类动作还要确认业务许可。用户表达含糊时由模型发起澄清，模型遗漏已经明确给出的参数则属于系统校验问题。不做这层校验，下游接口报错会直接暴露给用户，或者错误参数被设备部分接受产生非预期动作。

通过校验进入 **F08（单 Agent：取依赖、填请求、选执行器）**：先读取工具说明，取出这一次需要的历史、记忆、车况材料，填好参数，挂上对应业务的结果处理，选定承接服务。在 Planner 内部，每个 Agent 被包装成图内工具，模型产出动作列表后才进入 Agent Server；Agent Server 按 AgentType 分发到对应执行器，六类并列：内置 AIDV 服务、DPFM（车控领域执行器代号，承接车控与车辆领域工具以及部分面向车企的 B 端模型能力）、豆包云能力、生态第三方服务、端侧离线和内部 RPC（远程过程调用）服务型 Agent。承接服务只完成这一个工具调用，不能代替 Director 重新排“先查记忆、再导航”的整套计划，单次调用与编排调度的职责分界见[Agent Server OnePage](https://bytedance.larkoffice.com/docx/KDJpd1kTmoDgEexJpTicZAlin8e)。

六类执行器按能力域分工：AIDV 是服务内置 Agent，本仓库直接实现，不走外部 Agent 服务；DPFM 承接车控、车辆领域工具和部分面向车企的 B 端模型能力；Doubao 承接豆包云通用内容、搜索和豆包生态；Ecology 承接生态和第三方服务；Offline 是端侧离线虚拟 Agent；InternalRPC 承接内部远程调用服务型 Agent。Planner 基于 ReAct 图运行，模型每轮输出严格 JSON，有 action_list 就执行工具，把结果作为 observation 观察事实回灌再推理，无动作或命中直返工具则收口；工具节点内部用 uuid 重写动作标识、做工具名映射、注入回答来源标记，再逐帧转发并采集执行反馈。Agent Server 预处理按 agent_id 取配置、取上下文依赖、挂业务后处理，正式调用按类型选执行器，后处理统一转协议格式。单次调用边界保证编排顺序始终归 Director，执行器不能自行决定下一步调用哪个工具。

## 协议归一、三路内容与正常结束

承接服务返回后先到 **F09（流式响应先做通用协议归一）**。标准协议允许按流一片片返回，不必等全部生成结束才收到内容；会话、问题、Agent 标识和 trace 编号把片段归到同一次调用，请求方式为 POST 提交一份待处理信息加 SSE 服务器推送事件流。末尾终包只表示这股响应流结束，不表示用户目标已经做完，候选刚返回和导航已经出发是两种业务事实；缺终包不能悄悄当成结束，错误码和结束原因也要保留。

协议归一解决不同执行器输出格式不一致的问题。内置服务、云端模型、第三方生态和离线工具返回结构各不相同，执行面先把它们统一转成座舱 Agent 协议，上游才能按同一套字段处理。chat_id 贯穿多轮对话，question_id 标识单轮问答，conversation_id 标识会话，agent_id 标识承接工具，trace_id 关联一次请求里的全部操作。流式分片靠这些编号归并，避免片段错配；is_finish 终包只标记传输流结束，finish_reason 记录结束原因，error_code 和 error_message 保留失败信息。缺少终包不能按正常结束处理，否则历史可能漏写或状态误判。

**F10（业务后处理把三路内容分开）** 再做具体业务处理，把面向界面的 content、可供语音的 tts_content、给模型继续决策的 model_content 分开；卡片结构和透传指令另有内容类型。候选卡片要保留结构，模型需要读懂地点和选择结果，声音还要遵守项目话语权；某一路为空是合法回包，界面透传不等于下游可以自己播报。三路混成一段文字，最容易出现卡片对、模型误解，或者下游和主模型各说一遍，字段口径见[三方 Agent 接入协议](https://bytedance.larkoffice.com/docx/ZS6rd5ytKomVEwxDVebcKGTkn6d)。

三路内容分开对应三类不同消费方：content 给界面上屏，tts_content 给语音合成，model_content 给 Planner 总结下一轮决策，另有 reasoning_content 记录思考内容。界面可以保留卡片结构和长文本，播报文字需要口语简短，模型上下文需要结构化事实；三者混排会导致界面文字被念出、模型拿到口语化表达难以推理。tts_content 为空时才使用 content，正常情况播报内容由上层统一组织。部分特殊业务只有结构化数据，后处理还要把结构化结果转成模型可读文本。command 跳转或降级命令只在合同允许时返回。

三路分开之后，正常结果进入 **F11（正常结束：记 Agent 历史并回传完整结果）**，把真实内容和结构化观察存进历史，再交 E5 核对业务进展。候选路线要留全，用户下一句“挑红绿灯少的”才有真实对象；历史保存和流结束都不会自动启动下一个工具，地址查到后要不要导航，仍由 Director 再决定。

正常结束要解决观察事实如何沉淀给下一轮推理的问题。工具返回后 mergeToolOutputs 合成包含 tool_feedback 和 tool_name 的 observation 回灌模型；历史重建结合聊天历史、规划历史和任务列表，按用户、助手观察、用户反馈的时序组织，并入近十分钟最多三条事件日志并按时间稳定排序。候选地点、参数和真实结果必须完整保留，下一轮指代才有承接对象。历史保存不等于自动触发下一个工具动作，下一步仍由 Director 结合观察判断；非最后一轮的车辆手册和联网搜索反馈需要脱敏处理。

## 直返、回退、转交、取消

**F12（历史直返：仅在明确配置下走 direct_return）** 是明确配置的例外：某些渠道或工具把结果直接收口，不再让 Director 总结。它需要真实直返配置依据，还要核对直返的是界面还是语音；统一话语权主线不允许把旧分支改成所有工具默认直出，没有运行证据时只能按条件例外读，界面透传不等于语音自播。

直返机制解决少数格式固定、不需要模型二次总结的工具如何快速收口。Planner 图中命中 ReturnDirectlyTools 配置的工具不再回灌大模型，直接进入 direct_return 节点收口；结果已经在模型或工具节点流式产出，收口节点只做图结束。直返必须区分界面直返和语音直返，界面透传不授予自主播报权；没有配置依据的旧分支不能扩大为默认行为。不限制直返范围，会让大量工具绕过统一话术组织，造成播报失控和上下文缺失。

下游接不住、也没有指定承接者时走 **F13（Fallback：回Director 重新规划）**，把原因和已完成部分交回输入管理，请 Director 重新规划或结束。回退不是默认同工具自动重试；已有订单或车辆动作必须先交代，否则换工具再做会重复执行。

Fallback 解决下游无法处理当前请求时的退路。接入方 Agent 发现本次请求无法处理时可主动回座舱侧，由座舱决定使用哪个 Agent；回退把失败原因和已完成部分交回 Director，由大脑重新规划替代方案或向用户说明。回退不等于同工具自动重试，Agent Server 不提供通用自动重规划；已经产生订单、车控或文件的动作必须先交代状态，避免换工具重复执行造成重复扣款或重复操作。

下游点名转交走 **F14（Redirect：指定下个Agent）**，由调用方按指定目标转交，回到 F02 重新核对渠道、版本和权限，并带着原问题、已发生状态和关联身份继续；收到转交不等于下一工具已经做完。哪些 Agent 支持转交、如何防循环、跳转上限和超时边界，尚无完整共同合同【待核】，Agent Server 侧 Redirect 最多两次，回退不做通用自动重试。

Redirect 解决当前工具识别出更合适承接者时的定向转交。转交后不能跳过准入闸门，必须重新核对渠道、版本、权限和动态条件；原问题、已发生状态和身份关联要随转交携带，保证下一个工具在完整上下文里执行。防循环和跳转上限是为了避免多个 Agent 互相转交形成死循环；当前合同只明确 Agent Server 侧最多两次，具体支持范围、防循环规则和超时边界仍待统一合同确认。

取消或异常走 **F15（取消与异常：结束连接不撤销业务）**：先发 cancel 通知再断开连接，已生成内容存入历史；断连不自动撤回车控、订单和正在生成的文件，事后仍要核对真实状态。提前调用默认关闭，需双方另行约定；各工具超时和重试按具体合同处理，不统一猜测。

取消与异常处理解决用户打断、连接中断和工具超时时如何收尾。取消先发送通知再断开连接，已经生成的内容仍写入历史；业务动作一旦下发，断连不会自动撤销，车控、订单和生成文件需要事后核对真实状态。Context 取消信号向下游传播，少数任务合同允许不被取消。超时和重试策略由各工具合同定义，执行层不设统一猜测值；这和第 06 章失败出口口径一致。

## 底部补充口径

画板底部六条是 2026 年 10 月工具准入补充口径，不改变 F01 到 F15 主流程。

**F16（全域 FC 按车企分版本）**【2.6 目标】：FC 即 Function Calling 函数调用，工具名称、参数和取值范围按车企车型对齐合同表，赛力斯主线、上汽量产、对外协作、东风奕派等并行维护，跨车型不能互相套用；当前在线工作簿按主线、赛力斯和全功能等多张子表分版本维护，评审函数前先问清是哪家车企、哪一份表，函数表版本记录见[座舱大模型主线全域 FC 协议](https://bytedance.larkoffice.com/sheets/Z3wewToJtirMJUkbBmpcncc7ned)。函数表分版本演进，v1.0 到 v1.10 主线函数、sls 定制和全功能集合分别记录；不同车型硬件能力、参数范围和函数命名存在差异，直接套用其他车企合同会出现参数越界或调用不存在函数。

**F17（Agent Server 只管单次调用）**【已确认，通用】：Agent Server 帮调用方屏蔽 Agent 版本差异，一次只处理已经决定好的这一个工具调用，不编排整套计划；先查记忆再导航是 Director 定的顺序，转交次数上限以已发布合同为准【待核】。这一职责边界和第 06 章一致：Server 提供管理面、控制面和执行面能力，编排调度归 Planner，避免执行层长出第二个规划大脑。

**F18（工具无自主播报）**【已确认，通用】：谁开口由 Director 文案决定，声音内容可以为空；历史直返也不授予播报权，直返不等于拿到播报权。工具只回传事实和结构化结果，话术组织和播报时机由上层统一控制；界面透传、卡片展示和语音播报三者权限分开。

**F19（条件任务注册：If-Then）**【已确认需求，通用】：用户表达“满足某条件就执行某动作”时，Planner 拆成条件任务，条件任务 Agent 先做日程提醒与条件任务二分类，再交触发器注册；执行周期默认一次，任一条件注册不出则整单失败，不能先挂上一半；触发器只判断条件、不开口，触发后动作仍由 Director 推理调度，注册口径见[触发器与 Planner 条件任务需求](https://bytedance.larkoffice.com/wiki/GCfiwlJJei6fY7kYIOhcBXcxnlc)。条件注册整单失败的原因是部分条件挂起会留下永远无法完整满足的规则，到点触发时动作语义残缺；触发器只负责条件命中通知，不直接执行车控，保证动作决策仍经过主链规划。

**F20（注册后视觉模型持续扫描舱内）**【已确认，赛力斯外渠道暂不支持】：注册后视觉模型持续扫描舱内，真判断到条件才回调叫起 Director，判断不到不打扰用户；当前接入范围以发布配置为准。视觉条件任务和端状态条件复用后续 Trigger 判定能力，当前仅赛力斯渠道接入，其他车型不能按已支持口径对外承诺。

**F21（高优事件直接叫起）**【已确认，通用】：播报被拒识打断、手动操作、上下车等事件不走正常排队，直接起 Director 新一轮；实际支持车型与版本以发布配置为准。高优事件绕过普通消息队列，是因为这些事件要求即时响应，排队等待会错过上下车、打断等时机；事件类型和车型支持范围仍按发布配置核对。

## 验收要点与待核边界

评审这一章要逐层核对工具为什么在运行时看不到：定义、渠道实现、发布启用、权限和动态条件是不同闸门，必须逐层给出当前请求证据，而不是只展示工具清单。回退、转交、历史直返的去向也要分开看，分别对应回 Director 重规划、指定下一 Agent、按配置直接返回，并标注版本，混为“重试”会画错责任和副作用。终包不能证明车辆或订单完成，协议传输终态和业务履约状态是两回事，要找到工具业务字段和实际结果，再决定用户话术。函数表还要核对跑的是哪家车企的哪一份，跨车型不能互相套用；条件任务注册失败时用户听到什么同样要验收，任一条件注册不出来整单失败，不能先挂上一半。

验收时先看能力准入一致性，核对工具说明可见、权限合法、已发布启用实现和车型能力一致，当前部署集合需实查，这部分属于产品验收建议。接着看协议完整性，核对终包覆盖、错误原因保留、模型、界面、语音三路内容映射及取消结果归属，按协议测试，不能用一次快速测试替代实车闭环，同样属于产品验收建议。动态工具条件准确性则要分别核对应加载、不应加载的卡片和参数组合，检查旧页面误调用与权限问题，属于方案设计要求，尚未获得量产验收成绩。

待核边界需要在评审时明确标注。F14 哪些 Agent 支持 Redirect、防循环规则、跳转上限和超时边界尚无完整共同合同；F17 转交次数上限以已发布合同为准；F16 各分车型函数名、参数和取值范围本轮未逐行核对，上线前按具体车企合同表复核；F20 当前仅赛力斯接入，其他渠道暂不支持；F21 实际车型和版本以发布配置为准；F04 端状态条件与 Trigger 复用、F05 实时卡片归 Context 管理均为后续规划方向。工具能不能看见、参数对不对、结果怎么存都有了规矩。Director 说出“带我去昨天那家游泳馆”时，“昨天那家”的地址从哪来，下一章讲身份与记忆。

## N17｜三方智能体、A2A 与 AgentCard：旧能力向子 Agent 怎样映射到今天的工具

上一章看完排期，这一章回看长期架构里的分工设想：当年设想多个能力向智能体各自负责一块，今天这些能力怎样进入主链。用户不会感知智能体数量，只会感知一句话能不能被理解、动作能不能完成；评审这一章要看旧设想怎样收敛成当前可交付的工具和边界。如果继续按多个独立智能体互相调用设计，每新增一类能力都要单独维护身份、记忆、上下文和打断规则，链路长，排障也更难。任务规划归第 05 章 Director，工具发现准入与调用归第 06 章和 N4，屏幕操作细节归 N8，手车互联六项归 N12，本章只讲旧多智能体设想向今天工具形态的映射关系、三层服务分工与仍保留的子 Agent 方向。

## 先分清 Agent 和 Tool：这一章讨论分工的起点

讨论多个智能体之前，先把两个容易混用的概念分开。Agent 即智能体，是一个能自己理解目标、调用工具、持续推进任务、再把结果交回来的独立执行主体；Tool 即工具，是一个按固定参数被调用、执行完只返回信息或结果的能力条目，它不理解任务目标，也不决定下一步做什么。按[长期架构子智能体表](https://bytedance.larkoffice.com/wiki/XM8GdtFsTok8CwxcMrKcywMmnQg)，两者最直接的区别是沟通方式：智能体之间用自然语言描述任务目标和约束，工具之间用固定参数和返回字段对接；智能体处理的是一段具体任务，工具完成的是一次原子操作。

用餐厅打比方，主智能体相当于大堂经理，负责听懂顾客要什么、安排先后顺序；工具相当于后厨里切配、炒菜、摆盘这些固定工位，喊到谁、传什么料、出什么菜都由大堂经理决定。一个独立子智能体更像另一家分店的店长，大堂经理把整桌客人的需求转交给分店店长，店长自己组织人手、跟进进度、再回传结果。用户说“帮我找附近游泳馆，顺便看看泳镜价格”，找游泳馆走本地生活工具，查泳镜价格走联网工具，两件事由主智能体依次调度工具完成，不需要专门养一个游泳馆智能体，也不需要一个泳镜智能体。

为什么长期架构曾经设想多个子智能体，是因为长难任务需要垂域知识、专属环境和持续跟踪：一个任务可能跨几十步，中间要观察状态、记住偏好、处理失败，单靠主智能体加一堆工具，上下文和排障都会变重。这是多智能体设想要解决的问题；但设想成立的前提是任务足够复杂、垂域边界足够清晰。回到 v15 车载场景，多数诉求是单次问答、单次车控、单次导航或单次内容播放，任务短、边界清楚，硬拆成多个独立智能体反而增加身份管理、记忆同步和打断回收的成本。

## 从 12 个子 Agent 愿景到 Director 加工具的现实

**N17-01（W1 愿景：12 个能力向子 Agent）**画的是长期架构设想：主智能体旁边挂 12 个能力向子智能体，再连接三方智能体，彼此按能力分工调用。按长期架构表，设想中的每个子智能体都登记自己的目标、感知与注意、记忆方式、思考方式、工具集合和行动表达方式；长难任务由专门智能体持续跟踪，再通过智能体间通信和主智能体协调。这张表回答的是未来能力可以怎样拆分，不等于今天线上还保留多个独立智能体，属于长期愿景。

这一设想来自 Dream Car 对座舱体验的长期定位：全双工多模态实时沟通、多任务多目标长难追踪、多工具多智能体协同、主动思考服务、持续学习记忆、多模态表达和独立人格七类体验，最终要让助手呈现鲜活、伙伴、智慧、进化的感受。长期架构把整体链路划成 Perception 感知、Attention 注意、Thinking 思考、Memory 记忆、Action 行动与 Express 表达五段：感知汇总端信号、视频流和音频流；注意由工程注册事件和模型自主判断共同触发，区分 Listen 倾听、Reject 拒识、Interrupt 打断和 Response 回应；思考结合任务队列、短长时记忆、可用工具和智能体清单形成表达、队列更新、记忆更新和执行决策；记忆分短时上下文窗口和长时偏好、状态语义、视觉与情景记忆；表达上语音统一由主 Bot 输出避免冲突，图形界面可按智能体分别呈现。

设想中智能体按目的而不是按功能划分。如果把音乐和播客拆成两个按功能命名的智能体，两者很容易在“播放什么内容”上给出矛盾结论；按目的划分之后，每个智能体对应一类用户目标，便于单独评估、后续强化学习，也降低主 Bot 的任务压力，减少工作重合和冲突。除功能向子智能体外，长期架构还设想内心向子智能体，分别承担记忆、动机价值观、情绪和自我探索，为主智能体提供符合人设、三观和情绪状态的上下文；功能向子智能体通过 A2A 与主智能体沟通并支持外接，内心向智能体不直接面向用户执行任务。这些都是 W1 长期规划，v15 线上没有对应实体。

**N17-02（今天的现实：Director + 40 工具）**是当前主链形态：Director 统一规划，各能力收敛成工具表里的工具条目，一条请求走一条链。长期记忆由上下文材料提供，持续观察由触发器补足。这样收敛以后，新增能力不需要单独维护一套身份、记忆、打断和回收规则，排障也能定位到具体工具；代价是能力交付粒度变成工具，不再以独立智能体对外呈现，这一形态已落地。

原来设想的能力域覆盖导航、媒体、车控、天气、本地生活、联网网页、记忆、视觉、任务、生图、播客和通讯十二个方向，画板底部也对应这十二类工具条目：导航 route、媒体 music、车控 vehicle、天气 weather、本地生活 local、联网 web、记忆 memory、视觉 visual、任务 task_agent、生图 image、播客 broadcast、通讯 vehicle_comm。Director 判断需要哪一类能力，再调用对应工具；工具完成后把结果交回主链，不自己决定下一句说什么。工具名称、输入输出和弃用状态统一查第 21 章工具字典，本章不重复登记参数。

如果不做收敛，坚持每个能力域都设独立子智能体，会出现三类成本。第一是身份与可见范围重复维护：每个子智能体都要单独登记渠道、环境和可用工具，新增车型就要逐个同步。第二是任务状态分散：用户中途取消或改主意，取消信号要逐个通知下游，任何一个子智能体没收住就会继续执行旧任务。第三是排障链路变长：一次请求经过多个智能体转手，失败时要逐层判断是理解错、工具错还是交接错。当前用 Director 加工具的形态，正是为了把这三类成本压在主链一处。

## 三层服务：管理面、控制面、数据面

收敛之后，旧设想里子智能体之间的管理、调度和对接职责，拆成三个服务面。三者都只做适配、准入和边界控制，不另设决策中心；真正理解用户意图、决定调用顺序的仍然是 Director。可以把三个面理解成一家公司的行政部、调度台和对外联络处：行政部管谁能进哪个办公室，调度台管任务派给谁、出错怎么退回，联络处管用什么协议和外部对接。

**N17-03（管理面）**负责智能体定义、租户隔离、版本环境和动态工具对 Director 的可见性。租户隔离按渠道加渠道应用标识 channel_app_id 区分，画板登记上汽渠道标识为 99220；不同品牌、车型、环境能看到哪些身份和工具，由管理面控制，不能把一个渠道尚未开放的能力直接暴露给另一个渠道。版本环境区分开发、测试和线上，同一套工具在不同环境看到的清单可以不同；动态工具的上下线只改变对 Director 的可见性，不需要改主链代码。这一层已落地。管理面要回答的问题是“这个身份在这个渠道、这个环境下允许看见什么”，而不是“这个任务该不该做”，后者归 Director。

**N17-04（控制面）**负责工具发现与准入、DirectAgent 直调、转交最多两次、打断与回退，也把取消上下文向下游传导。工具发现指 Director 在发起调用前先确认目标工具存在、当前渠道可用、参数齐全；准入指不符合条件的工具不允许被选中。DirectAgent 直调指 Director 直接调用一个工具，不经过中间转手；Redirect 转交指把任务交给下一个处理方，画板登记最多两次，超过两次仍未完成就不再继续转手，避免任务在多个模块之间空转。Interrupt 打断处理用户中途插话或取消，Fallback 回退处理工具失败后的替代路径；用户中途改变主意时，取消上下文必须向下游传导，下游不能继续执行旧请求。这一层已落地。控制面要保证调用顺序、转交路径和失败回退都有统一规则，而不是每个工具自己约定一套。

**N17-05（数据面）**负责智能体间对接协议和通道。A2A 即 Agent-to-Agent，智能体间对接，指两个独立智能体之间按约定协议委派任务、回传状态和产物的方式；本节数据面就是 A2A 在豆包汽车内部的落地形态，不要讲成多个智能体在后台互相打电话。协议包括 aidv、dpfm、doubao、ecology、internal_rpc 等内部对接约定，通道包括 HTTP 超文本传输协议、SSE 服务器推送事件、Kitex 字节开源远程过程调用框架、MCP 模型上下文协议和 Frontier 主动消息下发通道；外部智能体按约定的协议和通道把结果回传主链。这一层已落地。

放到行业背景里看，MCP 解决的是模型连接工具和外部资源的问题，架构是客户端、主机、服务器；A2A 解决的是智能体与智能体之间对等协作、委派和任务交接的问题，架构是客户端到服务器。按[Agent 通信协议与 A2A 协议调研实践](https://bytedance.sg.larkoffice.com/docx/ZC9Zdisdno2cV1xbaJCc5zbjnec)，标准 A2A 以 HTTP 为传输基础，配合 SSE 做流式推送，数据交换使用 JSON-RPC 2.0，即基于 JSON 的远程过程调用协议，围绕任务对象组织通信，任务可以即时完成、长时运行后轮询状态，或在线时由服务端流式推送、离线时由外部通知服务推送更新；身份认证不在协议正文中交换，认证信息通过 HTTP 头带外传递，服务端在自己的名片里声明支持的认证方式。豆包汽车当前的数据面并没有直接套用这套公开标准，而是用内部协议和通道完成对接，公开 A2A 只作为长期参考。

## GUI Agent：2.6 唯一保留的子 Agent 形态

**N17-06（GUI Agent，2.6 仅存的子 Agent 形态）**是当前仍保留屏幕操作思路的方向，属于 2.6 目标。GUI 即图形用户界面，指通过图标、菜单、窗口和点击、拖拽完成人机交互的界面。它在车机屏幕之上，通过对界面元素的结构化理解和视觉理解，模拟点击、输入和滑动，独立闭环，不绑定某一个系统页面。

这一方向要解决的问题是驾驶中手动操作手机或车机容易分散注意力、操作风险高。传统 GUI 自动化多依赖 RPA 机器人流程自动化脚本和规则：页面元素位置固定、流程写死，输入匹配规则就执行对应动作，页面改版、流程超出规则就失效；AI Agent 方案基于视觉语言模型理解当前页面，能处理未预设的界面变化，根据实时页面动态调整步骤，泛化能力更强，但代价是模型理解和执行稳定性需要持续打磨。按[GUI Agent 需求文档](https://bytedance.larkoffice.com/wiki/KZYAwBQ34ik1KKkZLDAchpbwnWe)，26 年路线为自研工程链路加 seed 1.8 模型、以车机小程序为核心迭代；早期方案基于 AutoGLM 屏幕操作模型做微调，并约束提示词与协议格式。

历史方案对比也能说明为什么 2.6 只保留这一形态。早期方案一是 RPA 固定脚本加小程序，再用 UI-Tars 视觉模型兜底识别，操作必须在前台进行；局限是生态有限、泛化弱、需要大量标注，前台运行还会干扰用户正在看的界面。方案二以视觉模型加手车互联反控、虚拟屏后台运行为主，局限是依赖投屏协议和设备适配，手机熄屏可能无法反控，视觉模型单步耗时较长且存在幻觉风险；同时需要系统方保证投屏连接稳定，锁屏不中断、反控区域支持触摸、长按、拖动、滚动和输入法切换，任务管理器权限放行读取车辆基础信息、已装应用列表、截图和本地存储，虚拟屏最小化或悬浮隐藏后仍能取到投屏截图。

覆盖场景分即时通讯（IM，instant messaging）和生活服务两大类。IM 通讯包括微信、QQ 的消息发送、消息总结、红包转账、朋友圈编辑查看，以及飞书、钉钉、企业微信的消息发送、消息总结、会议预约和会议查看；生活服务包括美团、大众点评的外卖、美食查询、餐厅订座、休闲娱乐，淘票票、猫眼的电影查询与购票，携程、去哪儿的机票、动车、酒店查询与预订，以及菜鸟快递查询和取件。发送消息、提交订单、填写用户信息、支付之前一律停止，交用户确认。内部链路分四段。

第一段视觉界面理解：屏幕截图之后做元素识别，区分按钮、文本框、下拉菜单、图标，配合 OCR 光学字符识别，即识别截图界面中的文字、布局空间关系理解和状态感知，判断元素是否可点击、是否已选中、页面是否加载完成。第二段任务规划与思考：把用户目标拆成子任务和操作序列，单任务生命周期内携带全量思考过程和最多五张图片作为上下文供模型推理。第三段动作执行与状态反馈：完成坐标计算、动作选择、时序等待和错误检测，再把状态回传主链做任务管理。第四段结果反思与学习：评估是否达成目标、诊断失败原因、尝试备选方案，这一部分属于进阶能力，开发过程中结合主链反思模块再定。

执行动作覆盖一组固定类型：tap 单击、double_tap 双击、long_press 长按、swipe 滑动、input 文本输入、launch 启动应用、back 返回上一层、home 回到桌面、wait 等待加载，再加上三个需要主链配合的交互动作。Clarify 澄清指条件不清或存在多个可选结果时，先向用户确认，例如咖啡的温度、杯型、糖分需要分次问清；Approve 授权指发送消息、提交订单、支付等高敏感动作前必须取得用户确认；Handoff 接管指遇到登录、支付、验证码、同意用户协议等阶段，交还用户手动操作，用户完成后若干秒自动继续任务；finish 表示任务结束。反馈状态对应四类：任务进行中只通知 Advisor 做持续任务管理，不打扰用户；需要澄清由 Planner 加 Advisor 向用户二次确认；需要接管明确告知用户接下来手动操作；任务完成再向用户播报结果。

任务管理有明确的抢占规则：单次只能执行一个 GUI Agent 任务。原任务执行中用户补充信息，先暂停原任务、补完信息再继续；用户取消原任务就终止；用户发起另一个 GUI 任务，先暂停原任务，完成新任务后再询问是否继续原任务；车控、导航、媒体等其他短时任务不打断 GUI 任务，新任务完成后，需要和用户交互的内容排队或合并执行。

操作来源分两种：手车互联投屏和车机小程序。投屏又分离屏渲染和镜像投屏：离屏渲染由手机系统生成一套专门给车机看的虚拟屏幕，不影响手机当前界面，可在锁屏和后台稳定运行，但需要手机厂商和车厂深度合作；镜像投屏只是把手机当前真实画面录下来传到车机，手机锁屏或反控都会影响画面。仲裁策略按用户指定和连接状态决定走哪条路径：用户明确指定手机，手机未连接就提示先连接；用户指定小程序，优先找支持的车机小程序；只说应用名时优先车机小程序，没有再退回投屏；未指定应用名时按停车场支持情况、用户常用偏好和产品排序选择。虚拟屏方案则是把目标应用跑在车企提供的常驻后台屏幕上，默认中控屏不可见，需要接管时再把投屏页面拉起。

安全与隐私上，截图和自动化操作会采集大量个人信息：禁止自动操作的应用直接告知用户手动处理；上云图片全链路加密，推理完成后删除不存储；高敏感行为分类分级，同意协议、登录、支付必须用户确认或接管。记忆结合用于减少操作步长：显性记忆如车牌号、不能喝冰饮直接带入任务；情景记忆记录某次下单内容；偏好记忆从多次行为归纳出常点选项，未指定时先向用户确认再使用。

按需求文档开发计划，第一阶段打通三个承诺车机小程序链路，第二阶段接入主链路并补充澄清、接管 knowhow，第三阶段结合上下文记忆和虚拟屏后台静默操作，第四阶段探索 Advisor 主动调用并覆盖停车缴费、餐厅订座、充电加油、外卖、团购等专项场景。准确率口径区分简单任务，即十步以内且单应用内完成，和复杂任务，即十步以上或跨应用完成；单步准确率要求每个动作五十条样本不低于 95%，任务成功率简单任务内部不低于 92%、对外不低于 90%，复杂任务内部不低于 85%、对外不低于 80%；单步时延内部不超过四秒、对外不超过六秒。早期基于 AutoGLM 加 seed 1.8 preview 的测试中，成功、半成功、失败比例为 32 比 6 比 7，属于历史轮次体感口径，不代表线上水平；单步耗时在十秒以内，快的约六秒，分布为截图约一秒、模型推理四到七秒、执行一到两秒。测试也观察到基础反思能力：发朋友圈时第一次误生成长按动作，变成发文字，模型发现不符合预期后退回上一层，改用短按完成图文发布；敏感操作发送消息、提交订单需要用户授权，支付前自动停止。暴露的问题集中在输入键盘唤起失败、模型理解偏差、信息只看第一屏不滑动、动作执行不彻底、白屏就截图、应用未安装卡住、验证码不请求接管、键盘遮挡按钮等，正是后续自研工程链路要解决的方向。

## 长时任务例子与操作边界

**N17-07****（长时任务例子，**[**官方 one page**](https://bytedance.larkoffice.com/wiki/P5yuwBK2jiCjrokLEnecdcohnlc)**）**用点外卖和交停车费说明边界。点外卖时，系统先辅助用户搜索川菜、选择商品并提示进入结算；交停车费时，先匹配车牌、查询费用、准备开票。系统给操作指引，关键支付环节必须等用户 Approve 确认，不替用户全自动下单。贯穿案例“订个评分 4.5 以上的餐厅”走本地生活工具域，并不存在一个独立的餐厅智能体。

以停车缴费走完整流程：用户说“帮我交一下停车费”，主链先判断属于场景类操作，分发给 GUI Agent；Agent 先读取记忆中的车牌号，再进入停车小程序匹配当前停车场，查询费用，有可用优惠券先识别领取，到达支付页面前停止，弹出 Approve 确认，用户确认后才完成支付。如果用户中途说“算了先不交了”，控制面打断当前任务并终止；如果小程序连续多次下发相同动作都没有反馈，判定卡屏，终止任务并提示用户关闭小程序后重新下发；用户手动打开另一个小程序，因为限制同时只有一个小程序进程，自动操作停止并提示用户已手动介入。

外卖场景同理：搜索商家、筛选评分和人均、选择商品和规格，需要补充口味、温度、杯型时走 Clarify 分次确认，进入填地址和支付页面之前停止；用户指定的应用没有安装时，任务不会反复循环打开，而是告知缺少应用并给出替代建议。

需求文档枚举的专项场景还包括：停车支付先通过小程序确认车牌、查询订单并要求支付，未来公众号和 H5 移动网页（HTML5 网页应用）自动支付属于法规与无人场景下的 P1 方向；美团订座走小程序订座，地图融合查找评分 4.5 以上餐厅后再预约，不能线上订座时改为拨打电话；任一点餐覆盖饮品和食物提前点单的多步流程；电影票完成查询和预订多步，到达支付前停止。这些场景与主动服务章节的餐厅推荐衔接：Advisor 知道 GUI Agent 能提供哪些服务，在合适场景先给出建议，再由 Planner 统一和用户对话或执行。

这些边界写在产品规则里，是因为驾驶场景下误发消息、误支付的代价远高于普通手机操作，辅助指引必须止步在授权动作之前。屏幕操作智能体的辅助指引和全自动下单边界、支付类动作授权规则，以需求文档场景枚举为准，属于 2.6 目标推进中口径。

## AgentCard：未来智能体名片

**N17-08（AgentCard 名片 9 字段，W1 原表）**保留未来智能体名片的定义方向。AgentCard 即智能体名片，用于向主智能体声明一个可调用智能体是谁、能做什么。字段包括名称 name、说明 description、访问地址 url、提供方 provider、版本 version、能力范围 capabilities、默认输入模式 defaultInputModes、默认输出模式 defaultOutputModes 和技能清单 skills；其中名称、说明、访问地址、版本为必填，提供方选填；能力范围标注是否支持流式、主动推送和事件预警；技能至少一个，并写明技能说明、输入和输出。

长期表给的示例是“路线规划智能体”：名片声明它接收起点、终点和偏好输入，输出路线方案；默认输入模式和默认输出模式分别登记它接受的文本、语音、图片等形式，以及它能返回的文本、网页、图片、视频、语音形式；能力范围里标注是否支持流式返回、主动推送和事件预警。主智能体先按这些字段判断任务是否适合转交，再决定是否调用，而不是把所有任务都尝试发给同一个外部智能体。

按公开 A2A 调研，名片在标准协议中承担发现机制：客户端先通过访问地址拉取名片，判断远程智能体是否具备完成任务的能力，确认需要哪种认证方式，再建立通信；服务端在名片里声明认证方式，认证材料通过 HTTP 头带外传递，不在任务内容里交换身份。任务执行中如果还需要额外授权，返回需要补充输入的状态，再通过带外方式获取材料。豆包汽车当前只有管理面使用类似的智能体定义概念，完整名片格式、发现地址和认证流程仍在讨论中，不是已交付形态，属于长期愿景。

## 三方候选与手车互联

**N17-09（三方候选 & 手车互联）**要分开看。三方候选指座舱主智能体之外、由外部团队或厂商提供的智能体，按长期架构表可分为 IP 类，即已有知识产权或知名角色形象、儿童教育类、社会职业类、原创 IP 和专项硬件等方向；当前画板上的具身智能体和 AI 导航仅为占位，2.6 不交付，后续评估责任方与排期待核。功能向子智能体和外接三方智能体的共性是都按 A2A 方式交互、拥有自己的感知认知记忆工具和界面、可注册事件；差异在于自有智能体可以使用座舱声音、硬件身体和屏幕，三方智能体受接入边界限制。

手车互联六项已落地：远程控车、远程车况查询、用车知识查询、地点 POI 同步、深度研究与播客内容同步，不同步视频，以及对话历史展示，具体规则归第 12 章。这里的 POI 即兴趣点，指可检索的地点。三方智能体接入后排期、数据边界和授权方式待架构方案明确，本章不承诺接入时间。

## 收口边界与评审核对

架构收敛后，Director 仍是唯一决策出口；工具只执行和回传结果，不形成第二个决策中心。评审先区分三层服务职责：管理面管身份、渠道和可见范围，控制面管调用顺序、转交、中断和回退，数据面管协议和通道；再核对 GUI Agent 的澄清、授权、接管三类命令是否把住安全边界，最后核对任务抢占规则是否和任务中心、主动服务章节一致。本章不展开单个工具的参数与失败回执，不展开 GUI Agent 的界面识别算法细节，也不承诺三方智能体接入时间。

待核事项集中在几处：12 个能力域是否长期都以工具交付、不另设独立子智能体的最终产品决策；管理面、控制面、数据面在不同品牌、车型、环境的开放程度清单；GUI Agent 2.6 目标范围、车型清单、成功率与场景覆盖终值；三方候选评估推进方与排期；AgentCard 正式格式、发现机制与接入时间；屏幕操作辅助指引与全自动下单的最终授权边界。工具名称、参数、输入输出和弃用状态以第 21 章工具字典实时版本为准。
