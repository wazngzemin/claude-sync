# AI 时代产品经理的七层价值迁移：从功能 PM 到 Physical Agent Owner

## 核心问题

当模型会写文案、画原型、写代码、拆任务时，产品经理还凭什么值钱？

答案不是再学更多概念，也不是立刻辞职去做 FDE。你要把自己的工作从“提出功能并协调交付”升级为“选择高价值问题，并对现场 Agent 的完整结果负责”。

## 先把七个词翻译成人话

| 词 | 大白话 | 放到你身上 |
|---|---|---|
| 基座模型 | 通用大脑 | Seed 等模型，能理解和推理，但不知道车里此刻发生什么 |
| Context | 当前案件材料 | 说话人、座位、车况、VLM、记忆、任务进度、天气与时间 |
| Harness | 管住 AI 的工作台 | SP、规则、工具、状态机、检查点、重试和降级的总和 |
| Skill | 给 AI 的做事方法 | 遇到某类问题时按哪些步骤查、判断、执行和复核 |
| Eval | AI 的考试卷和判卷标准 | 任务是否完成、是否误触发、哪一步错、延迟和成本如何 |
| FDE | 进入真实业务现场的 AI 落地者 | 一边理解车企和用户，一边把问题做成系统，再把共性带回平台 |
| Physical Agent | 能感知现实并采取行动的 AI | 车内 Agent 通过传感器看见状态，通过车控、导航和交互影响现实 |

## 七层价值迁移

### 第一层：通用生成，价值快速变薄

写话术、总结材料、出原型和常规信息问答，会越来越便宜。这里仍需要人，但很难构成长期差异。

你的对应工作：只改 talk_content、只补一条 Prompt、只增加一个孤立示例。

### 第二层：问题选择，决定时间花在哪里

Jeff Dean 的 1% 法则和黄钊的“大事”标准都在说：先选一个模型单独几乎不会、做成后又有明显价值的问题。

你的对应工作：区分“打开车窗”这种成熟指令，与“跨一段行程持续照看后排并在正确时机提醒”这种新任务。

### 第三层：私有现场，给模型看见现实

通用模型不知道当前谁坐在哪里、宝宝是否睡着、车辆在什么位置、用户过去偏好什么。现场信息让同一个模型产生不同价值。

你的对应工作：Context 13 类信息、用户记忆、端状态、事件、VLM 描述、任务快照。

### 第四层：行动闭环，让 AI 真正把事做完

只回答正确还不够。AI 要知道什么时候行动、调用什么工具、工具失败后怎么办、任务何时结束。

你的对应工作：Planner/Director、23/26 工具版本、Task、Trigger、tool feedback、取消与失败恢复。

### 第五层：评估闭环，让系统越做越准

没有 Eval，团队只能靠感觉改 Prompt。Eval 要告诉你哪一步错、为什么错、这次修改有没有净增益。

你的对应工作：A-F 分诊、L0-L6 介入、动态示例基线、任务成功、打扰率、延迟与成本。

### 第六层：关系与持续学习，形成长期资产

夏勇峰的 Soul、梁文锋的持续学习和用户记忆指向同一件事：系统要在多次互动中保持连续理解。信任和记忆只有在用户可控、可纠正、可删除时才成立。

你的对应工作：face_id、search_user_memory、operate_user_memory、跨行程任务、稳定人格与权限边界。

### 第七层：平台复用，把一次交付变成复利

FDE 和外包的分水岭在反馈去向。一个车型的坑若只在当前项目修掉，是交付；若沉淀成事件定义、工具协议、场景模板和评测资产，让下一车型更快，是平台能力。

你的对应工作：统一智能底座、跨车型状态/事件/条件、通用 TaskSpec、场景卡与评测模板。

## 场景映射

| 文章里的角色或机制 | 你的 Planner / Agent 场景 | 可迁移动作 |
|---|---|---|
| 1% 问题 | 宝宝哭了提醒、沿途风景、跨行程偏好兑现 | 先测裸模型，再列系统补齐项 |
| 复杂且边界清晰 | 多状态、长时、低打扰、安全要求 | 写“必须做、允许做、绝对不能做、无法判断” |
| 私有数据 | 端状态、VLM、记忆、事件日志 | 建字段来源、新鲜度、可信度、缺失降级表 |
| 上下文工程 | SP、动态知识、示例、工具描述 | 每轮只注入完成当前步骤所需信息 |
| 长时 Agent | Task + Trigger + Context snapshot | 任务长时间存在，模型按事件短时醒来 |
| Eval 新 OKR | A-F 分诊与评测集 | 从总通过率下钻到失败步骤和副作用 |
| FDE 暗线 | 车企说“要主动服务” | 追问谁用、最怕什么、谁判对错、怎么验收 |
| 统一智能底座 | 多车型复用 | 底层协议共用，车型能力和策略可配置 |
| Soul | 记忆、人格、关系 | 允许用户查看、纠正、删除，避免暗中积累 |

## 七门机会筛选

每项 0 到 2 分，总分 14 分。10 分以上进入重点实验，7 到 9 分先做小样，6 分以下暂缓。

| 门 | 核心问题 | 2 分长什么样 |
|---|---|---|
| 价值门 | 做成后谁明显受益？ | 解决高频、高痛、收入、风险或安全问题 |
| 模型缺口门 | 裸模型今天会多少？ | 没有现场和工具时几乎无法完成 |
| 现场门 | 你有什么专属信息？ | 有持续私有状态、数据或关系 |
| 行动门 | AI 能改变现实吗？ | 有真实工具、系统接口或物理执行器 |
| 边界门 | 好坏能否说清？ | 成功、失败、禁区、降级均可明确 |
| 评估门 | 能否快速判卷？ | 可重复测量，能定位失败步骤 |
| 复用门 | 做完一次以后会怎样？ | 经验进入平台，下个场景明显更快 |

## 旧需求与新需求怎么区分

### 旧需求换 AI 做

- 用户以前会说“打开空调”，现在仍说同一句话。
- 输出和过去相同，只是生成或执行更便宜。
- 模型升级后，多家公司一起变强。
- 价值主要是效率、成本和体验微调。

### AI 才让它成立的新任务

- 用户只说一次目标，系统跨时间持续观察。
- 系统结合现实变化决定何时行动。
- 需要记忆、事件、工具、恢复和低打扰。
- 用户以前不会雇一个人长期做，软件规则也覆盖不了长尾。

### 你的候选对照

| 场景 | 类型判断 | 下一步 |
|---|---|---|
| 打开车窗 | 成熟旧需求 | 走低延迟稳定链，不投入复杂 Agent |
| 我有点热 | 旧需求的情境升级 | 验证 Context 与偏好是否真提高体验 |
| 宝宝哭了告诉我 | 新的持续任务 | 建 VLM、Task、Trigger、Planner、提醒评估闭环 |
| 到达前提醒收拾物品 | 状态驱动的新服务 | 用导航距离、档位、座位与去重验证低打扰 |
| 沿途值得讲时再介绍 | 新的长时内容服务 | 先定义“值得”和打扰上限，再做系统 |
| 跨行程记住家人偏好 | 关系型长期服务 | 先做身份、授权、冲突与遗忘机制 |

## 你的岗位应该怎样重新命名

### 旧标签：Planner 产品经理

听起来像负责一个模型模块、维护提示词和工具调用。

### 新标签：Physical Agent System PM / Owner

更准确的职责表述：

> 我负责把真实座舱中的人、车、环境和长期任务组织成模型可用的 Context，再通过 Planner、Task、Trigger 和工具完成行动，并用评测闭环提升端到端任务成功率。

这句话的价值在于把你的资产从“某家公司的一段 SP”提炼成可迁移能力。

## FDE 职业路线怎样理解

FDE 不等于一个人永远驻扎在客户公司，也不要求供应方自己训练基础模型。模型公司、云平台、行业软件公司和解决方案公司都可以基于 API、开源模型或云服务做 FDE。关键有三点：进入真实现场、负责落地结果、把共性反馈回产品。

### 业务会分成五类

1. 模型与云平台 FDE：帮助客户把模型能力接进生产系统。
2. 行业产品 FDE：围绕金融、制造、医疗、汽车等垂直流程落地。
3. 内部 FDE：在大公司内部改造自己的业务流程。
4. Physical AI FDE：车辆、机器人、仓储和工厂现场的部署、数据和评测。
5. 产品化 FDE：从多个客户项目提炼可配置模块和平台。

### 你可以进哪些行业

- 最近邻：车企、Tier 1、座舱和智驾平台、机器人、仓储物流、工业制造。
- 次近邻：模型公司或云平台的汽车与制造 FDE。
- 进一步迁移：零售、教育、企业运营等流程型行业。

行业可以换，前提是你能证明这套通用能力：挖暗线、写规则、搭原型、接 Context、做 Eval、推动上线、把经验产品化。

## 你不会写代码，应该补到什么程度

目标不是先成为全栈工程师。你要达到“能独立搭出验证、能和工程师对账”的 Builder 基线。

- 能读写 JSON、YAML、Prompt 和工具 schema。
- 能用 Codex 修改小型 HTML 原型和简单脚本。
- 能跑评测、看日志、定位某一步输入输出。
- 能解释 API、状态机、事件、工具回执和失败恢复。
- 能把业务规则写成测试 case。

满足这些后，你仍然可以以产品和业务翻译为主，复杂生产代码由工程师兜底。

## 12 个月操作 SOP

### 0 到 1 个月：选一条参考闭环

建议主场景：`宝宝哭了告诉我`。

建议对照场景：`到达前提醒收拾物品`。

一条依赖 VLM 语义事件，一条依赖结构化状态事件。两条都跑通，才能证明 Task、Trigger、Context、Planner 和评估体系具备复用性。

交付物：`《Physical Agent 参考闭环 v1》`

内容必须包含：

1. 用户真正害怕什么。
2. 输入来自哪里、多久更新一次。
3. 状态机和每个模块的输入输出。
4. 无法判断、误触发、重复提醒、下电、取消的处理。
5. 端到端验收指标。

### 1 到 3 个月：建立可证明的评测

交付物：`《Physical Agent 30 例评测集 v1》`

每条 case 至少有：

- 前置状态与事件。
- 必需 Context。
- 期望决策与禁用动作。
- 期望提醒或静默。
- 失败归属 A-F。
- 端到端结果、延迟、打扰和重复情况。

一次只改一个主要变量，保留基线和副作用。

### 3 到 6 个月：从项目修补升级为平台资产

交付物：`《跨车型可复用能力清单 v1》`

把每次车型问题分成三类：

1. 通用底座问题：协议、状态、任务、评测。
2. 车型配置问题：设备能力、信号映射、策略阈值。
3. 单一项目问题：只对当前客户成立。

目标是让第二个场景或第二车型的建设时间显著下降。

### 6 到 12 个月：准备职业迁移证据

交付物：`《Physical Agent Portfolio》`

作品集只讲一个完整故事：

1. 为什么这是通用模型的 1% 问题。
2. 现场私有信息是什么。
3. 你怎样把暗线翻译成规则、流程和 Eval。
4. 你如何推动多团队对齐。
5. 结果提高了什么，代价是什么。
6. 哪些能力已跨场景复用。

拿这份作品集测试三类岗位：Physical Agent PM、行业 FDE、机器人部署产品。先用面试反馈校准，不必提前辞职押注。

## 下周可直接执行的五件事

### 1. 写一页纸，不写大 PRD

文件名：`Physical-Agent参考闭环-宝宝哭了-v1.md`

第一页只回答五个暗线问题：谁在用、最怕什么、谁判断、怎么验收、出错谁承担代价。

### 2. 开一次 45 分钟责任对账会

照说台词：

> 这次我不评一整套架构，只确认一条用户任务。请大家逐段确认输入、输出、owner 和失败兜底。任何一段无法确认，我会标成未闭环，不用 PPT 把它盖过去。

### 3. 建 30 条 case

先用已有日志、动态示例和会议 case，不追求全量。必须同时有正例、反例、信息缺失、重复事件、任务取消和下电。

### 4. 跑一次基线

记录模型决策、工具调用、任务状态、触发时机、最终提醒。不要只看 Planner 输出文字。

### 5. 在下一次评审主动要一个决定

照说台词：

> 当前卡点有两个方案。A 的风险是误报，B 的风险是漏报。我的建议是先选 B，并用 30 条评测验证。今天需要确认 owner 和可接受阈值，否则排期只能算占位。

## Prompt 模板：综合评估一个 AI 场景

```text
你是 Physical Agent 产品评审员。请用大白话分析下面场景。

场景：{填写}
用户：{填写}
现有链路：{填写}
可用状态、事件、记忆、VLM、工具：{填写}

请按以下顺序输出：
1. 用户真正想解决的问题，避免复述方案名。
2. 裸模型能做多少，哪些部分必须依赖现场系统。
3. 七门评分，每项 0 到 2 分，并说明依据。
4. 必须做、允许做、绝对不能做、无法判断时怎么办。
5. Task、Trigger、Context、Planner、工具、回执的责任表。
6. 10 个正例、10 个反例、5 个信息缺失 case、5 个中断恢复 case。
7. 任务成功、安全、打扰、延迟、成本五类指标。
8. 哪些经验能复用到下一个场景或行业。
9. 明确标注：资料已知、合理推导、仍待验证。
```

## 判断标准

### 做对了的信号

- 评审从“Prompt 怎么改”转向“用户任务在哪一步失败”。
- 同一套状态、任务、触发和评测能力能承接第二个场景。
- 你能用数据说明某次改动的净增益和副作用。
- 工程、算法、端侧和业务方知道各自的输入输出与兜底。
- 作品集离开公司内部名词后，机器人、制造或云平台面试官仍能理解。

### 仍然停留在表层的信号

- 继续用文档页数、示例条数和会议次数证明产出。
- 一个 badcase 就补一条 Prompt，没有共性归因。
- FDE 项目做完后没有任何能力回到产品。
- 把具身智能等同于人形机器人 Demo。
- 等行业“正式成熟”后再准备能力。
- 用“心力、品味、愿景”代替用户证据和评测结果。
