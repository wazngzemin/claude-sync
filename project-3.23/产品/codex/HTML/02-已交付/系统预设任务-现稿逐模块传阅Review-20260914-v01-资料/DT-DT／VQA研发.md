# DT / VQA 模拟研发传阅意见

以下是模拟该角色的评审意见，不代表真实研发会签。审核依据是当前 source.txt 编号正文、原稿图 2 与图 5；没有依据把 DT、Director、Planner 判定为三个独立组件。整体已写清先产出识别结论、原业务拉卡、确认后端侧复核的方向，主要需要把识别接口和失效条件写到可实现程度。

## 1. 谁发起观察请求、谁取图、谁把识别结果交给原业务？

- 会上直接问：正文写“端侧上行并获得当前 event_id 结果”，图 5 写“Director 调用 VQ 最后一帧”，这里端侧是上传图片、上报已有视觉结论，还是接收云端结果？请沿一次请求把每一跳的发送方、接收方和返回内容说清。
- 原文已写：0057—0063 明确识别结论先回原业务；0403—0406 写 DT 推理结果来源为“DT + 端侧上行”；0475—0478 有 event_id 和结果分支。图 2 已画原业务请求指定范围观察、接收四类结果。
- 缺口：实际取图/取结果入口及失败返回责任未落定；图 5 仍由 Director 拉卡和调车控，与 0057、0060、0063 的业务分工冲突。DT / Planner 名称关系本身不能作为拆分接口的依据。
- 为什么要问：否则两侧可能各自等待另一侧发请求，或把“已提交推理”当“已拿到当前识别结果”。
- 可粘贴补文：本任务由原业务在接收有效触发事件后发起一次观察请求。请求包含本次事件关联、当前停车关联、观察目标与范围、结果截止时间。DT / VQA 协作链路返回识别结论及其采集时间、实际观察范围和失败原因；请求受理不等于识别完成。取图、上行、推理与结果回传的具体承接模块在接口会签中逐跳填写，沿用现有组件命名，不因本图的名称差异假设新增组件。识别结论统一回原业务，由原业务拉卡并在有效确认后发起端侧执行；同步修订图 5。
- 待确认：原业务研发、DT / Planner 对接研发、端侧视觉 / VQA 研发共同确认每一跳；本文没有真实个人姓名依据。

## 2. 识别范围是什么，FOUND 到底证明了什么？

- 会上直接问：0387 的“后排 / 车外”、图 5 的“后视”“最后一帧”分别指哪个摄像头和画面？看到一个充电桩，能否只得出“画面内有充电设备”，不能进一步保证它空闲、正常、接口匹配或就在本车可用位置？
- 原文已写：图 2 写“指定范围查看有无充电设备”；图 5 写“看一下后视是否有充电桩”“最后一帧图像”；0387 写“后排 / 车外充电设备”。
- 缺口：观察范围表述不一致；没有定义识别类别和结论边界。图 5 的“你可能在充电桩附近”也需要明确是视觉推断，不是设备可用性结论。
- 为什么要问：有限视角没拍到不能证明周围没有；拍到了也不代表可以充电。范围不清会直接影响误报、漏报和询问文案。
- 可粘贴补文：本任务只判断约定车外观察范围内是否可见充电设备，不判断设备空闲、故障、接口兼容或可供本车使用。正式上线前列明摄像头 / 视角、设备识别类别及有效采集条件。FOUND 表示有效画面内识别到目标；NOT_FOUND 仅表示在有效观察范围内未识别到目标；范围缺失、遮挡或图像质量不足不能按 NOT_FOUND 处理。询问使用“检测到附近可能有充电设备，要打开充电口盖吗？”等与结论强度一致的文案，最终表达由产品与视觉研发确认。
- 待确认：产品确认观察目标和文案；端侧视觉 / VQA 研发确认视角、覆盖和画面质量判定。

## 3. 四类结果如何区分，旧停车或取消后的结果由谁丢弃？

- 会上直接问：四个结果已经列了，UNKNOWN 和 ERROR 的分界是什么？结果回来时车已驶离又重新停好，或用户已关闭任务，原业务凭什么判断这不是本次还能用的结果？
- 原文已写：0027 提到超时、过期和关联；0431—0432、0477—0478 列 FOUND / NOT_FOUND / UNKNOWN / ERROR 及其余结束；0483—0484 写切出 P、未停稳、开关关闭、结果过期即终止。图 2 的事件已有“本次停车”，并要求有效结果。
- 缺口：结果枚举含义、采集时间与截止时间的判定值、同次停车标识、在途取消和迟到 / 重复回包处置未具体化。不能把已有“四类结果”和“执行前过期复核”说成完全没写。
- 为什么要问：只核对 event_id 或当前处于 P 档，仍可能误用上次停车拍的图；只在车控前拦截，还可能先弹出过期推荐。
- 可粘贴补文：FOUND 为有效观察中识别到目标，NOT_FOUND 为有效观察中未识别到目标，UNKNOWN 为已获得观察输入但不足以判断，ERROR 为取图、调用或推理链路失败；请求超过截止时间由原业务按超时结束。结果回传必须关联本次事件和本次停车，并提供采集时间。原业务在拉卡前和执行前均校验关联、采集时效及事件未终止；不同停车、过期、重复或已取消事件的回包仅记日志，不恢复询问或执行。任务关闭、场景失效或本次流程取消时，原业务立即终止该事件并尽力取消在途请求；即使推理无法取消，也必须忽略其后续返回。图像有效时长、推理超时及停车边界由产品与端云研发会签具体值。
- 待确认：原业务研发负责终止和丢弃；端侧研发确认停车关联与采集时间；DT / VQA 研发确认结果语义、截止时间和可取消能力；产品确认时效数值。

## 4. 本期究竟先识别还是先询问？D-09 还需保留为分支吗？

- 会上直接问：0042、图 2 和图 5 都是先识别再询问，0480 却允许“按 D-09 在 DT 前或 DT 后获得确认”。当前充电任务是否已确定先识别后询问？如果已确定，应删除这个未决分支。
- 原文已写：0042 明确“识别到设备后询问，有效确认后开盖”；0057—0063 与图 2 支持该顺序；图 5 同样先 VQ 判断再用户反馈。
- 缺口：0480 留下互斥顺序，且当前所读正文未提供可落实的 D-09 决策内容。不能要求研发同时按两条链路实现。
- 为什么要问：先询问会改变请求何时创建、拒绝时是否还有推理在途，以及用户确认究竟授权识别还是授权开盖。
- 可粘贴补文：本期充电口盖任务固定为“触发条件满足 → 识别充电设备 → 当前有效结果为 FOUND → 原业务询问是否开盖 → 用户明确确认 → 端侧复核并执行”。识别前不发起本次开盖确认；确认只授权当前有效建议对应的一次开盖。删除“按 D-09 在 DT 前或 DT 后获得确认”的未决表述，并同步流程图及事件表。
- 待确认：产品负责人确认本期顺序；原业务与 DT / VQA 对接研发据此确认请求时点。此补文沿用正文已选择的方向，并非新增产品路线。
