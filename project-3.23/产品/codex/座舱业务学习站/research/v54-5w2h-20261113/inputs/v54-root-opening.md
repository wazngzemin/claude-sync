# V 章：一句话怎样被听完整、办正确，并成为下一轮可用的背景

这章沿着“带我去昨天那家游泳馆……附近的餐厅”讲清：声音怎样成为完整请求，系统怎样决定接不接、谁来办，Planner 又怎样利用背景和工具把事情做完。

阅读约定：正文用同一个教学例子；例子中的停顿、餐厅列表和后续选择不是真实测试记录。事实后面的编号对应 facts-ledger.md。“已确认”表示已在指定资料中核到，不表示今天所有车型已经上线；需求、历史实测、讨论中观点和上线状态分别标记。热词单元按用户确认样稿逐字保留，样稿里的证据缺口另列校注。各单元查阅区中的“v52 对照保留”用于防止旧知识点丢失，其中尚未回到一手材料的说法不能当作当前规则。

## 0. 整条链路总览

### 配图说明

沿用 v52 图标题“一句话从开口到 DT 开始思考：12 个步骤”。它是全章唯一保留超过 8 个节点的总图，后面的新单元图各不超过 8 个节点。保留原编号：收音 → 热词辅助 → 一遍识别；识别旁边并行画“流式停播判断”和“软判停 → 预请求”；硬判停 → 二遍定稿 → 最终拒识；本地处理与云端处理分别流向仲裁；Context 交给 DT，实际结果再回写。蓝色是车端，青色是云端处理，紫色是背景与记忆，橙色表示待决或不可直接执行的候选。箭头必须写“音频”“过程文字”“定稿文字”“候选结果”或“执行反馈”，不能只画一条没有含义的线。[V00-F01]

图中的数字是阅读索引，并不表示每个模块都依次等上一个完成。ASR（自动语音识别，把声音写成文字）和 VAD（语音活动检测，观察发声与停顿）会并行；本地候选也不是等云端全部算完才开始。图后半段需连上“工具执行 → 屏幕/播报 → 结果回写”，否则只看到 DT 开始思考，解释不了用户为什么仍没到目的地。[V00-F02]

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 这是一条把声音变成业务结果、再把结果留给下一轮的处理链。 |
| Why 为什么要 | 听到前半句就开始导航，用户补上的“附近的餐厅”就来不及改变目标。 |
| Who 谁负责 | 车机收音与执行，识别服务写字，拒识判断是否接话，Planner 组织工具办理。 |
| When 什么时候发生 | 从用户获准交互、开始讲话，一直到实际结果返回并留下记录。 |
| Where 在哪里 | 声音采集与车辆动作发生在车上，在线识别和复杂处理通过云端协作。 |
| How 怎么接起来 | 每一环把下一环需要的信息交齐，并保留这是哪次输入、哪个说话位置。 |
| How much 看什么效果 | 分别看是否听准、是否完整、是否接对、是否办成，以及用户各段等了多久。 |

### 第二步：七个问题逐条讲透

**1. What：这一章到底在解释什么？**

用户听到“好的”时，可能以为事情已经完成；系统此时却可能只完成识别，或刚发出一个工具请求。学习这一章，就是能指出现在到哪一步、还缺什么证据。

| 容易混的东西 | 已经获得什么 | 还不能推出什么 |
|---|---|---|
| 听写正确 | 文字确实是“昨天那家游泳馆” | 不代表知道游泳馆地址 |
| 判断该接话 | 这句话是在找豆包 | 不代表本车有对应能力 |
| 模型发出工具调用 | 系统决定去查或去做 | 不代表工具成功、车辆已经动作 |
| 用户看见实际结果 | 地点列表显示，或导航真正启动 | 还要确认结果能否被下一轮使用 |

Planner 是业务侧称呼，Director 是内部名称，DT 在本章指这套对话推理功能。它接收用户请求和 Context（本轮可用的背景集合），判断直接回答、追问，还是调用已接入的业务工具；它不是一个单凭名字就能确定大小和部署位置的模型。[V00-F03]

**2. Why：为什么不能只学“模型听懂后执行”？**

主例前半句像是去游泳馆，后半句把目标改成了餐厅。假如识别少了“附近的餐厅”，Planner 会拿着错误输入继续办；假如文字正确但记忆找错了游泳馆，结果也会错；假如地点正确但导航工具失败，嘴上说“已开始导航”仍然不算成功。三种用户后果可能都叫“导航错了”，要修的位置却不同。这里是教学推演，不冒充真实故障记录。

**3. Who：谁把什么交给谁？**

车端是车内运行的设备和软件，负责麦克风、屏幕、扬声器和实际车辆控制。AIDV 是承接汽车业务的座舱云服务：它对接 Speech 云提供的识别与合成能力，也组织汽车业务处理。在线语音路径中，识别文字先回车端，车端再把文字作为正式对话送入豆包云端，由它衔接 AIDV；音频上云与正式交办不是同一次动作。[V00-F04]

**4. When：什么时候允许先做，什么时候必须等？**

过程文字还会变化时，可以进行资料明确允许的提前准备；用户补话后，要检查准备结果还适不适用。不能因为屏幕上出现“带我去”就提前执行导航。正式定稿后，还需接话判断与端云采信。对于资料允许的固定说法，本地存在先执行的分支，因此全链路不是所有请求统一等待云端完成。[V00-F02；V10-F01]

**5. Where：和 Planner 的边界在哪？**

前面的语音链路先解决“听到了哪些字、这一段结束没有、是不是在找助手”。Planner 接下来解决“这些字在当前背景下是什么意思、缺什么信息、该调用什么工具”。记忆服务提供有关昨天经历的内容，地点工具提供位置与餐厅结果，导航应用负责实际路线。不能让 Planner 猜出没被记录的昨天行程，也不能把语音识别当作记忆检索。[V00-F03]

**6. How：用户说办错了，按什么顺序查？**

1. 先对原始声音和最终文字，确认有没有漏掉补话、否定词、地点名。
2. 再对接话判断，确认系统接的是用户对助手说的话。
3. 再看哪一路被采信，避免两路都执行或采用过期候选。
4. 再看 Planner 实际收到的背景和工具返回，确认“昨天那家”有证据。
5. 最后对屏幕、车辆/服务结果和回写记录，确认说的、做的、下一轮记得的相互一致。

这是本章建议的排查方法，不是已部署的一条自动检查程序。每一步都用同一轮请求关联，才能避免把不同次尝试拼成一条假链路。

**7. How much：怎样评价整条链路？**

先约定起点与终点：用户最后一个字说完、系统完成判停、首次出声、列表出来、导航启动，是不同时间点。“开始说话更快”不能代替“结果更快”。准确率也要说明场景与统计规则，单独报一个百分比无法判断是听写、拒识还是执行。旧版具体数字全部放相应单元查阅区，不把不同车型、不同时间的结果当作同一组成绩。

### 第三步：放回主例

主驾说“带我去昨天那家游泳馆”，中途停顿，接着说“附近的餐厅”。识别补全后半句，过期准备作废或更新；系统接住完整请求后，先找到昨天游泳馆的具体地点，再搜附近餐厅。用户说“第二个”时，需要读到刚才展示列表的真实顺序；选择后导航是否启动，以执行反馈为准。任何一步证据不足，都应按该模块的规则补信息、提示失败或停止，不能凭流畅回答假装办成。

### 第四步：讲给别人听（30 秒）

> 这一章不是只讲一个模型。车先把声音听清、把补话接完整，再判断是否在叫豆包、该用车上还是云端的结果。Planner 接到请求和背景后，先补齐“昨天哪家游泳馆”，再调用工具找附近餐厅。工具返回后，车机展示或执行，并把实际结果留给下一轮。每一环都要看输入和输出，才能知道错在哪里。
