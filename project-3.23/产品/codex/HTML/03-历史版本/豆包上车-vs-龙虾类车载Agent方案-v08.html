先看懂三张架构图：安卓、定制车机、特斯拉自研

这是全篇最重要的一屏。用手机行业打比方：OpenClaw 是"安卓开源系统"，车载龙虾是"厂商定制的车机版安卓"，豆包上车是"不基于安卓、自己从车载需求长出来的特斯拉式自研系统"。

第一张 · 市面的龙虾架构
像"安卓开源系统"：一台通用躯干，不带脑子、不懂车

OpenClaw / Hermes 提供五个固定零件，谁都可以拿来装：

  • 收件口（网关）：接收网页、聊天软件、语音等各种消息。
  • 大脑插槽（模型）：可以插不同大模型，Claude、GPT、通义千问都行。
  • 双手（工具与技能）：调电脑上的软件、网页、接口。
  • 便签本（任务流与后台任务）：没做完的事记下来，跨会话继续。
  • 保险柜（沙箱与策略）：限制它不乱来。

干活方式就一句循环：听话 → 想 → 动手 → 看结果 → 再想 → 交差。

但它天生不懂车：不知道车速、挡位、座椅加热、主驾副驾。就像安卓系统本身不会开车。

第二张 · 车载龙虾怎么在上面跑
像"厂商定制的车机版安卓"：躯干还在，外面加七件汽车装备

不是把 OpenClaw 代码塞进车机，而是给它加装七件装备，由车企和供应商完成：

  1. 车载入口：语音、音区、座位、方向盘按键、摄像头。
  2. 座位信任：从"一个账号"变成"人 × 座位 × 驾驶角色"。
  3. 车辆上下文：车速、电量、空调、导航、信号新鲜度。
  4. 车控工具：开空调、调座椅、导航、媒体。
  5. 车辆任务本：车下电了任务不丢，回来接着做。
  6. 车规保险柜：高速不许开门、重复支付要拦截，模型外硬裁决。
  7. 车企技能商店：签名、灰度、回滚，第三方技能要审核。

OpenClaw 那层还在，但只是底座；决定量产能力的是外面这七层。

第三张 · 我们的架构
像"特斯拉自研系统"：不从安卓长出来，从车载需求反着长

我们不基于通用躯干，而是从"这一辆车怎么服务好"倒推出来的闭环：

  1. 快路："打开车窗"这类明确指令秒回，不走大模型。
  2. 仲裁：判断这句话是简单还是复杂。
  3. Director（规划器）：云端大模型听懂"我老婆睡着了十分钟后关加热"，拆任务、调 27 个工具。
  4. 一圈零件：座位与记忆上下文、目标列表、触发器、工具反馈闭环。

优势：很懂这一辆车，量产闭环、27 个工具、座位身份都已打通。

缺口：任务本、技能货架、独立保险柜、端侧——这些正是龙虾平台天生就有的，所以我们是"补装备"，不是"换系统"。

三句话记住区别：通用龙虾＝先造好通用躯干，再学开车（缺车的知识）；车载龙虾＝用通用躯干加汽车装备，卖平台（第一辆车慢，后面快）；我们＝先当上老司机，再补装备（现在更快，平台化要补课）。

先把黑话翻译成人话

下面这些词会反复出现，先统一翻译，后面读起来就不费劲。产品名（如 OpenClaw、KaKaClaw）是专有名词，保留原文并在旁边解释。

OpenClaw（龙虾）
通用智能体运行框架
开源的"让 AI 连续调用工具、记住状态、完成任务"的底层框架，类似早期安卓系统给手机提供的运行环境。官方文档称 Gateway 架构，强调自托管。
Hermes
另一款通用智能体执行框架
和 OpenClaw 同类的开源项目，定位偏向"可扩展的 AI 执行中间件"，不是车载产品。注意：不是"Hanes"。
Harness
承载层 / 运行框架
套在大模型外面，负责调度工具、管理会话、保证安全的一套环境。比喻：大模型是发动机，Harness 是整车底盘。
Runtime
运行时
程序真正跑起来的地方和时刻。比喻：Runtime 是舞台，技能是演员，模型是导演。
Gateway
网关 / 统一入口
所有请求和消息进入系统的门口，负责身份校验、路由、排队。比喻：小区大门加物业前台。
Session
会话
一次连续的交互上下文。比喻：你和客服的一通连续电话。
Skill（技能）
可插拔的能力包
封装好的"会做某事"的模块，比如查天气、订咖啡、调空调。比喻：微信小程序。
Plugin（插件）
插件
与技能类似，但更偏向扩展某个具体功能。比喻：浏览器插件。
MCP
模型工具调用协议
让 AI 模型统一调用外部工具和服务的接口标准。比喻：Type-C 接口，什么设备都能插。
Provider
模型供应方
提供大模型推理服务的厂商或接口。比喻：加油站，车可以加不同品牌的油。
Task Flow（任务流）
多步任务编排
把多步任务按依赖关系编排成可等待、可恢复、可取消的流程。比喻：美团外卖从下单到送达的全链路。
Background Task
后台任务
用户离开后仍然继续运行的任务。比喻：你睡了，扫地机器人继续扫地。
Cron
定时任务
按时间表触发的事情。比喻：手机闹钟、日历提醒。
Sandbox（沙箱）
受限执行环境
防止某个技能越权的隔离区。比喻：机场安检区，进去的人只能带允许的东西。
Policy
策略 / 规则
决定什么能做、什么不能做、什么需要确认。比喻：公司财务审批权限表。
Context
上下文 / 情境信息
模型做判断时能看到的全部信息。比喻：你进餐厅时，服务员看到的人数、天气、你之前点的菜。
Trigger（触发器）
条件触发
由时间、车辆状态或视觉事件触发动作。比喻：人体感应灯，检测到人就亮。
SP（系统提示词）
岗位说明书
每次请求都固定发给模型的"培训手册"。我们的 SP 约 3 万到 3.5 万字符，含 23 个工具定义和 69 个示例。
UP（用户提示词）
本轮输入
用户问题、顾问建议、工具返回结果组成的本轮输入，约 1 万到 1.5 万字符。
A2A
智能体间通信协议
不同 AI 智能体之间互相协作的协议。比喻：公司之间的合同和对接流程。

你当下真正能拿出去讲的竞争力

直接回答"我们现在比龙虾类方案强在哪、弱在哪、该补什么"。

我们的
竞争力
是什么

1. 我们不是在做一个通用智能体，而是在做一个"懂这辆车的智能体"。车辆状态、说话人和座位、记忆、目标列表、27 个明确工具、执行反馈闭环，已经全部接入 D6X。原版 OpenClaw / Hermes 没有这些车载事实和权限，直接替换会退化。

2. 三层漏斗让我们又快又稳。简单指令走快路不进大模型，复杂任务才进规划器；这在响应时延和模型成本上都是结构优势。

3. 量产闭环是真护城河。真实车型、问题案例、链路诊断、版本回滚——这些是演示能力替代不了的，正是车载龙虾最缺的。

4. 短期不需要换底座，长期必须补平台。任务运行时、技能登记册、策略引擎、沙箱、端云协同，这些才是未来平台竞争的核心。

可以理直气壮讲的（资料明确）

  • "当前 Director 已经是一个车载智能体承载层：能接用户、顾问、工具反馈和事件，输出表达与行动清单。"
  • "当前系统提示词明确列出 27 个工具，并注入成员位置、用户记忆、目标列表和车辆状态。"
  • "对当前 D6X，原版 OpenClaw / Hermes 不具备可直接替换的车载上下文、工具和安全边界。"
  • "简单指令走快路，不必每次进入大模型。"

正在建、要如实说的（建设中）

  • 统一任务运行时（任务 / 运行 / 事件）仍为建设中的技术方案。
  • 技能登记册和标准化技能生命周期尚未落地。
  • 策略引擎仍在从提示词迁移到独立服务。
  • 端侧模型和弱网体验弱于车载龙虾的目标形态。

现在还不能说的（未定义 / 未证实）

  • "我们的准确率已经超过理想、华为、智己"——本地材料多为目标、测试设计和问题案例，没有同口径实车横评结果。
  • "Driver Agent 已经比 KaKaClaw 更好"——本地有产品文档和评测集，没有对等量产结果。
  • "开源龙虾免费，所以整车成本更低"——免费的是框架许可证，不是芯片、模型、适配、认证和运营。
  • "Auto Claw、KaKaClaw 都用了 OpenClaw"——官方没有证明；目前只有 AquaDrive 系统 2.1 明确披露基于 OpenClaw 架构。
给老板的一句话：
"我们今天赢在更懂这一辆车，车载龙虾赢在更容易复制到很多车。我们不该换掉已经会办事的管家，而要补上不会丢的任务本、可升级的技能货架和独立的车辆保安。"

建议目标架构与下一步路线图

保留当前优势，吸收龙虾的运行时工程，并把开放能力锁进车规治理边界。目标不是"把 OpenClaw 原样搬进车"，而是做"最懂汽车约束的车载承载层"。

保留（我们的优势）

  • 快慢路三层漏斗
  • 车辆、乘员、导航、记忆上下文
  • 27 个车型工具与执行反馈闭环
  • 量产问题案例与版本治理

吸收（龙虾的长处）

  • 任务 / 运行 / 事件持久化
  • 技能登记册与签名沙箱
  • 端侧路由与弱网技能
  • 动态工具披露与提示词分层

新建（车规必须有）

  • 独立策略引擎（大模型外裁决）
  • 执行收据与幂等、补偿
  • 车辆信号来源、时间戳、有效期
  • 追踪与评测定位到版本

第一阶段 · 0–3 个月

  • 把 27 个工具收敛到唯一的工具与技能登记册。
  • 从系统提示词移出互斥、权限、车型能力与安全规则。
  • 落实任务 / 运行 / 事件与幂等、恢复、取消。
  • 统一工具反馈为标准执行收据。

第二阶段 · 3–6 个月

  • 提示词分稳定、上下文、易变三层，支持动态工具披露。
  • 建立端侧路由加轻量模型加弱网技能。
  • 上线车企签名技能包、沙箱与灰度。
  • 补齐上下文来源、时间戳、有效期。

第三阶段 · 6–12 个月

  • 开放受控服务智能体开发包，而非开放任意代码。
  • 端云模型按风险、时延、成本动态路由。
  • 跨车型技能复用与自动兼容性检查。
  • 用真实任务完成率和三年总拥有成本驱动架构选型。

我们的当前架构：车载闭环很强，但规则还压在一本大手册里

当前本地系统提示词为 2026-07-31 版本：约 12.8 万字符、2186 行；4 类输入、27 个明确工具、4 个输出字段、25 个示例块。S1

快路持续任务域触发 / 事件必须确定性治理

已有优势（资料明确）

  • 简单指令有快路，不必每次进入大模型，首字响应目标快。
  • 车辆、乘员、导航、记忆是业务上下文，不是后补的。
  • 27 个工具定义清晰，调用结果回流到规划器。
  • 量产车型 D6X 已闭环，问题案例可定位到链路。

当前短板（资料明确 / 可推导）

  • 大量规则、示例、车型能力还压在一个大系统提示词里。
  • 目标链能管持续任务，但统一任务运行时仍在建设中。
  • 缺少标准化的技能登记册（谁、什么能力、什么权限）。
  • 策略和权限未完全独立于模型，存在提示词漂移风险。
  • 端侧和弱网能力弱于车载龙虾的目标形态。

一句话画像

一位车感极强、但工作流程还写在厚厚手册里的车载管家。办事很稳，但带新人（新车型）成本高。

07

通用龙虾架构：一个聪明的通用实习生，但不懂车

OpenClaw 与 Hermes 不是同一个项目，但都属于通用智能体承载层：它们不是模型，而是包在模型外面、让模型能连续使用工具、保存状态、接收消息和完成任务的一套运行时。

OpenClaw 更像"完整的个人智能体操作系统"

  • 常驻网关统一连接渠道、客户端与设备节点。
  • 每个会话串行执行，避免工具和对话记录竞争。
  • 技能、插件、工具协议、模型供应方和承载层都可插拔。
  • 当前已有任务账本、任务流、定时任务、审核与维护机制。
  • 但官方安全模型仍明确以"一个网关一个可信操作者边界"为前提。

Hermes 更像"以智能体为中心的可扩展执行框架"

  • 命令行、网关、协议、接口、批处理等入口都进入同一个智能体。
  • 提示词构建器、供应方解析、工具分发是三个核心模块。
  • 本地数据库保存会话；工具注册表覆盖 70 多个工具、约 28 个工具集。
  • 定时任务会创建新的智能体会话，并可按任务限制工具集。
  • 它同样没有车辆上下文、电控网关与车规权限模型。

通用龙虾怎么"上车"：不是移植代码，而是外面再加七层汽车能力

同一句需求，四套方案怎么一步步跑

用一句真实的车上需求来对比："副驾乘客睡着了，10 分钟后把座椅加热关掉。"这句话同时考验：理解、定时、状态感知、条件判断、安全执行、恢复。

"我老婆睡着了，10 分钟以后把副驾座椅加热关了吧"

通用 OpenClaw / Hermes 能做一半

只拿到一句文本，默认不知道副驾是谁、是否有人、加热当前开没开。
智能体能拆出"10 分钟加条件加关加热"。
可创建定时任务或任务流，持久化目标并等待。
"仍在睡"必须另接视觉或状态工具，否则只能到点直接执行。
若没有车辆上下文适配器，只能猜或再次询问。
沙箱不能判断当前车速、座椅占用、乘员权限。
结论：通用任务骨架成熟，但缺车辆语义，量产前必须重建。

豆包上车当前 闭环最实

指令进入后先分流：这句话是"条件持续任务"，走规划器。
规划器读上下文：座位身份、乘员、座椅加热状态、车辆状态。
规划器输出动作列表，并把条件写入目标链。
定时器或视觉触发到点唤醒，读最新上下文复核"仍睡着"。
通过车控工具执行，返回执行结果回写目标。
当前权限规则部分依赖提示词约束，需要策略引擎兜底。
结论：车语义和闭环已打通；短板在任务运行时的持久化与策略独立。

成熟车载 Claw 目标 平台化最强

统一事件入口接收语音、座位、视觉、信号。
风险感知路由判断：这是低风险持续任务，可走端侧技能或云端规划。
任务运行时创建"任务 / 运行"，触发器注册"10 分钟加睡眠条件"。
到点后由触发回调唤醒，策略引擎按身份、车况、权限裁决。
执行总线调用车控技能，返回标准执行收据。
追踪与评测记录全程，问题可定位到版本。
结论：每个环节都有平台设施，但需要完整工程落地，不能只看发布会。
这里真正的差距：OpenClaw 已经有通用任务流的"骨架"；我们的任务化设计已经补上车辆任务需要的任务 / 运行 / 事件、触发适配器和上下文入口。现在竞争不再是"谁想到了任务"，而是"谁先把车辆生命周期、策略、结果格式和量产可观测真正跑通"。

安全差异：沙箱不是车规安全，提示词也不是权限系统

真正量产必须把"模型建议"与"动作授权"分开。无论我们还是龙虾，都不能让模型自己决定自己的权限。

① 身份域

谁说的、坐哪里、是否注册、是否主驾、是否具有付款、通讯、车控权限。

② 车辆状态域

车速、挡位、车门、动力状态、驾驶模式、当前执行任务与信号新鲜度。

③ 动作风险域

信息查询、舒适控制、付费交易、驾驶相关动作应有不同的确认、审计和回滚策略。

④ 运行时域

工具白名单、参数格式、幂等键、超时、重试、补偿、沙箱、网络出口与供应链签名。

安全问题仅靠提示词的结果通用龙虾沙箱的结果车规正确做法
高速行驶时"帮我打开车门"模型可能拒绝，但存在提示词漂移和绕过沙箱允许它正常调用一个已暴露的车控工具电控单元和车辆策略根据车速与挡位硬拒绝，模型只负责解释
重复工具反馈导致二次支付靠上下文记忆"不再调用"，不可靠工具循环检测可能发现重复，但不理解交易幂等订单幂等键加事务状态机加二次确认
技能被恶意更新提示词无法治理外部代码技能商店扫描和插件策略能降低风险车企签名、版本锁、灰度、软件物料清单、权限声明、回滚和隔离执行
旧车态误触发历史对话可能压过实时事实通用记忆不知道车态有效期每个信号带来源、采集时间、有效期；过期不得参与条件判断
座舱智能体影响智驾提示词不构成隔离容器和受限终端只隔离计算环境座舱与智驾物理或强隔离，跨域接口最小化；KaKaClaw 官方明确提出堡垒隔离
对我们的直接建议：把系统提示词中的"注意事项、工具提示、车型能力边界"迁移成机器可执行的策略登记；Director 输出的是意图和动作建议，策略引擎输出的才是可执行动作。

02

三句话先把三种方案分开

它们不是三只差不多的"龙虾"，而是解决三个不同阶段的问题。

通用龙虾（OpenClaw / Hermes）
一个会办事的"通用实习生"

它能用电脑、查网页、写代码、管理文件，但默认不懂车。把它直接放进车里，就像把一位办公室白领直接塞进驾驶室——他需要重新学开车、学交规、学这辆车的按钮在哪里。

豆包上车（当前）
一位培训过的"车载管家"

他已经会开这辆车、知道每个按钮、记得用户喜好、能听懂车内多个人说话。但这位管家的"工作流程"还写在一本很厚的培训手册（系统提示词）里，换辆车要重新培训。

车载龙虾（Auto Claw / KaKaClaw / AquaClaw）
一个"标准化车队管理平台"

想把通用实习生的聪明劲，加上车载管家的车感，做成一套可复用的系统：培训手册、任务派发、安全审批、绩效追踪全部平台化。第一辆车不一定更快，但第十辆、第一百辆车会更便宜、更稳定。

所以真正的答案不是"谁绝对更好"。今天要把 D6X 这一辆车做好，选我们当前链路；要做跨车型的长期平台，就应该保留我们的车载经验，同时吸收车载龙虾的任务、技能和安全骨架。
03

用你每天都在用的互联网产品做比喻

把抽象架构对应到具体产品上，方便向老板和同事解释。

通用龙虾
像"微信加小程序"

微信提供聊天、登录、支付、消息通知等基础能力；小程序让各种服务快速接入。通用龙虾也一样：提供会话、工具循环、定时任务、记忆、沙箱等基础能力，技能和插件就像小程序。

但它不是车载微信：默认没有车辆状态、座位身份、车规安全。

豆包上车当前
像"滴滴司机端"

深度绑定一辆车、一个司机角色：知道路线、乘客、车辆状态、计费规则、安全规范。完成一单（一个任务）的闭环能力很强，但它不是为"同时管理全国所有司机"设计的。

优势：懂车、任务完成率高、闭环快。短板：换车型要重新适配，规则还压在一本大手册里。

车载龙虾
像"滴滴平台加自动驾驶车队"

它不仅想让一个司机把车开好，还想把派单、调度、安全、培训、车辆监控全部平台化，未来还能复制到很多车。目标很大，但平台化意味着第一辆车不一定比老司机更快。

优势：可复制、可管理、可扩展。风险：平台成熟度决定实际体验，不能只看发布会。

车内设备联动
像"智能家居中枢"

你说"我困了"，智能家居中枢会调暗灯光、拉窗帘、放白噪音；豆包上车会调暗氛围灯、把座椅躺倒、开空调、播放助眠音乐。通用龙虾也能做，但它不知道你现在"在车里行驶中"还是"在家里沙发上"。

车规安全
像"银行 App 的权限系统"

银行 App 不会让用户自己决定"能不能转账一百万"，而是由后台根据身份、设备、风险、额度做硬拦截。车控安全也一样：高速行驶时"打开车门"这种请求，应该由车辆电控单元和策略引擎硬拒绝，而不是靠模型"自己判断"。

任务编排
像"美团外卖履约链路"

你点了一份外卖，系统要：接单、通知商家、骑手取货、配送、送达确认。多步任务有依赖、有等待、有异常。车载任务也一样："十分钟后如果副驾睡着了，关座椅加热"就需要任务流加触发器加状态回读。

技能生态
像"应用商店加小程序平台"

车载龙虾想做应用商店：第三方开发者可以上传技能（比如肯德基点餐、停车场预约），但需要平台审核、签名、权限声明、版本管理。我们当前更像"预装 27 个官方 App"，扩展性弱但稳定性强。

端云协同
像"音乐软件的在线和本地曲库"

在线曲库全、更新快，但弱网时听不了；本地曲库受限但稳定。车载智能体也一样：云端大模型聪明但依赖网络，端侧模型弱但响应快、隐私好。成熟方案会动态选择。
