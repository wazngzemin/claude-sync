# 上汽AI汽车功能需求SOR\-外采需求

# **第一章  项目总体概述**

## **1\.1 项目背景**

上汽AI汽车是上汽乘用车智能座舱的核心产品平台，旨在通过 AI 驱动的多模态交互能力，为车内用户提供智能化、个性化、主动化的出行与座舱体验。本 SOR 覆盖 上汽AI汽车平台下属六大核心模块的开发需求，包括：AI播客Agent、动态Advisor \&amp; 任务中心、静态Advisor、美团Agent、AiNavi、豆包车载机器人SDK。

各模块围绕 AI car 整体架构协同运作：静态Advisor 负责基于车辆与用户上下文的主动推理服务；动态Advisor 负责延时触发、条件触发与持续推进的任务管理；任务中心统一承载任务全生命周期；AI播客Agent 提供音频内容消费（调用喜马拉雅Agent）与实时播客生成能力；美团Agent 提供车载生活服务闭环；DNA AiNavi Tool 提供自然语言驱动的导航全链路能力。豆包车载机器人通过圆形屏幕中的豆包形象与用户交互，使人车交互更具情感化和氛围感。

## **1\.2 整体方案与分工**

整体策略：

- 伙伴除负责实现下面描述的各种功能开发和测试、交付之外，也要对端到端体验负责，包括端到端测试、体验测试以及推动各关联方问题优化（只围绕提供模块对体验负责，不对火山主线问题兜底），以最终端到端交付为目标导向，积极协助火山推动关联方一起做好体验，不能“只提供独立模块交付”。

- 伙伴产品设计、技术设计、测试等环节参照火山要求执行

各模块的整体方案与分工如下：

**【AI播客Agent】**

- 云侧：对接火山director，播客 Agent 功能 tools 接口化，为 planner 提供工具调用能力

- 端侧：提供播控 SDK 被集成到客户端中，并提供 AI 播客交互卡片承载信息展示与交互

- 基于用户个性化内容诉求，生成实时轻口播和深度播客内容

- 调用三方喜马拉雅APK 应用\(客户提供\)进行内容搜播

**【动态Advisor \&amp; 任务中心】**

- 动态 Advisor：将延时触发、条件触发或持续推进的目标转化为可托管、可追踪、可恢复、可终止的任务。

- 任务中心：为动态advisor提供统一的任务接入与生命周期管理能力。

**【静态Advisor\-情感advisor】**

- 基于车辆用户的 context 进行主动推理，提供持续运行、懂你所想、思你未想的主动服务。

**【美团Agent】**

- 美团侧：提供搜索、点餐、排号、订座等核心 API 接口，以及通知卡片状态查询能力，以及车载APK。

- 伙伴侧：对接火山director，让用户可以通过自然语言实现订座、POI信息查询（功能保留，后续上）以及外卖（搭载sop\+3）等生态体验；

- 车厂侧：语音隐私协议补充（允许美团获取用户常驻地址等数据）；美团APP白名单保活；车机端UI适配。

**【AiNavi Tool】**

- 云侧：对接火山director，AI Navi 功能 tools 接口化，为 planner 提供工具调用能力。

- 让用户通过自然语言完成\&\#34;找地点、选地点、规划路线、调整途经点、启动导航、规划行程\&\#34;的出行闭环。

- 系统理解复杂推理给到的 Query，承接上下文，调用端侧地图 SDK 能力，在 AI 地图或系统地图中给出可展示、可继续选择、可真实执行的结果。

**【豆包车载机器人SDK】**

豆包车载机器人以圆形屏幕作为核心显示载体，用于展示豆包 IP 形象；通过本体内置的水平云台电机实现机器人头部转动。豆包车载机器人复用座舱 SoC、DDR、EMMC、麦克风、扬声器。

## **1\.3 通用策略**

以下通用策略适用于美团Agent模块，其他模块参照执行：

- 车厂语音隐私协议补充条款：需车厂按美团要求提供授权隐私协议及相关材料，补充允许美团获取并使用用户常驻地址信息的条款。

- 应用保活需求：车厂需将美团APP加入白名单，确保订单信息同步和通知卡片推送正常。

- 美团Agent返回内容不支持修改。

# **第二章  AI播客Agent**

## **2\.1 背景介绍**

AI播客Agent 核心是为车载场景提供智能化的、个性化的播客内容生成与播控服务。该 Agent 基于用户 query、context 和 tool，让用户在行车和驻车场景中获得\&\#34;随心所播\&\#34;的全新音频播客内容体验。该Agent包含两种生成层级：

- 完整播客：可带双人对话和背景音的完整节目，并支持播客中的。

- 轻量口播：提供分钟级、单主播的详情讲解和主题资讯速报；

- 播客搜播：集成喜马拉雅平台音频资源，提供播客/有声书的搜索、推荐与播放控制能力。

整体采用三层内容能力：喜马拉雅播客Agent负责“找现成内容”，轻量口播负责让用户“快速听懂一件事”，深度ai生成播客负责“完整听一期节目”。整体采用搜\+生成双层能力，喜马拉雅播客Agent负责“找现成内容”，AI实时生成播客负责“完整听一期定制节目”。当用户实时生成额度达到上限时，切换至播客搜索，匹配平台已有相关内容。

## **2\.2 核心体验目标**

**2\.2\.1 AI播客Agent核心体验目标**

- 即时生成：基于用户给定主题或当下热点，实时生成可播报的轻量播客音频稿，实现\&\#34;即听即走\&\#34;

- 通过三方APK搜索、推荐和播放平台已有音频内容，完成从\&\#34;找内容→精筛→播放控制\&\#34;的一站式播客消费体验

- 个性化内容：结合用户 query、上下文与工具调用能力，生成满足个人偏好的播客内容

- 上下文复杂推理：支持 query\+context\+tool\+语音链路的端到端能力，自主抽取 context 信息并调用 tool，提升服务准确率

- 面向车载收听场景设计，适用于新闻速览、热点解读、趋势分析与主题电台类内容

# **第三章  动态Advisor \&amp; 任务中心**

## **3\.1 背景介绍**

动态 Advisor 的核心是将用户需要延时触发、条件触发或持续推进的目标，从单轮对话转化为可托管、可追踪、可恢复、可终止的任务；由系统在合适的时间或条件下主动唤醒并继续执行，并通过任务中心统一承载任务全生命周期，让 AI car 的服务真正做到有始有终。

## **3\.2 核心体验目标**

- 持续场景任务：面向需要多阶段或持续陪伴的目标，支持任务在非连续时间跨度中推进并在达成目标后可靠收尾

- 条件任务：将自然语言条件解析为可执行规则，在车辆、用户或外部状态满足条件时主动触发，支持单次与循环执行，并对不明确或不支持的条件进行澄清或拒绝

- 定时任务：理解绝对、相对、循环及模糊时间表达，完成时间合法性校验，并按分钟级精度触发、执行和管理任务

- 任务中心：提供统一的任务接入与生命周期管理能力，使用户能够清晰感知任务状态与执行结果

## **3\.3 整体方案以及分工**

- 动态Advisor 与任务中心协同运作：动态 Advisor 负责任务的推理与生成，任务中心负责任务的接入治理、状态管理、查询与事件回调。

- 动态Advisor负责时间条件、信号条件的解析，并且持久化为待执行的任务，在条件满足时并获得回调时，通知火山Planner完成实际任务的执行。

- 触发器（火山）需负责对车辆信号的感知，接收来自伙伴订阅的信号条件，在信号条件得到满足时，通知动态Advisor模块推进对应任务。

- Planner（火山）需负责与用户交互，理解用户的条件任务、延时任务、持续场景任务的需求，并创建对应目标。同时在任务触发时，根据advice完成对实际任务的执行。

# **第五章  美团Agent**

## **5\.1 背景介绍**

美团 Agent 核心是将美团的生活服务（核心为餐饮）能力集成至车载语音导航系统，使用户能通过自然语音交互，完成从餐厅发现、排队取号、餐厅预定的全流程操作，提升出行便利性与用户体验。

## **5\.2 核心体验目标**

- 餐厅搜索与发现：支持多种搜索方式（附近搜索、城市/区域搜索、分类搜索、榜单搜索、沿途搜索），通过列表展示结果并引导导航

- 餐厅订座：支持语音预订餐厅座位，包含人数、时间、位置偏好等参数收集与确认

- 外卖点餐：按照沟通约定，需要在2026年内支持美团外卖点餐功能。（依赖美团agent AP）

## **5\.3 整体方案以及分工设想**

- 美团侧：提供搜索、点餐、订座等核心API接口，以及通知卡片状态查询能力

- 伙伴侧：数据透传；根据用户意图执行查看详情、导航任务；数据透出至车厂

- 车厂侧：语音隐私协议补充（允许美团获取用户常驻地址等数据）；美团APP白名单保活；车机端UI适配

## **5\.4 通用策略**

- 车厂语音隐私协议补充条款：需车厂按美团要求提供授权隐私协议及相关文件，补充允许美团获取并使用用户常驻地址信息的条款

- 应用保活需求：车厂需将美团APP加入白名单，确保订单信息同步和通知卡片推送正常

- 美团Agent返回内容不支持修改

## **5\.5 项目许可范围**

本项目覆盖美食搜索、餐厅订座功能模块的云侧接口开发、端侧集成与多轮语音交互能力建设。当前到店取餐仅支持咖啡、茶饮、快餐品类。

# **第七章 豆包车载机器人**

## **7\.1 背景介绍**

豆包车载机器人是一个位于座舱中控台中央的前装车载智能硬件。机器人通过圆形屏幕中的豆包形象与用户交互，使人车交互更具情感化和氛围感。

每台车在对应账号登录模式下有且只有一个豆包。车辆已登录账号时，该车豆包为该账号用户的豆包，用车人账号需与豆包账号建立对应绑定关系；车辆未登录账号、处于访客模式时，该车豆包不与特定用户建立从属关系。车内不同用户均可与该豆包交互并享受豆包服务。

## **7\.2 核心体验目标**

基于座舱芯片算力，借助座舱麦克风和扬声器，结合机器人本体的屏幕与电机，构建“听、说、动、神”的全模态类人化交互体验，使机器人的交互方式更具人味，拉近用户与豆包车载机器人之间的关系。

- 通过圆形屏幕展示豆包IP形象，并在对应场景中组合豆包表情、配饰和背景。

- 通过水平云台电机实现听声辨位转动，使用户获得更直观的交互反馈。

- 通过屏幕形象与电机动作的组合，增强上车欢迎、语音交互、智驾、泊车、充电等场景的仪式感和情绪价值。

- 多人同时与机器人交互时，在保证交互反馈感的同时减少频繁左右转头带来的干扰。

## **7\.3 整体方案及分工**

豆包车载机器人以圆形屏幕作为核心显示载体，用于展示豆包 IP 形象；通过本体内置的水平云台电机实现机器人头部转动。机器人复用座舱 SoC、DDR、EMMC、麦克风、扬声器、Wi\-Fi 和蓝牙能力。

伙伴侧：承担AIBot关联产品设计工作、对AIBot本体的通信控制和联调、主机侧功能设计、功能实现以及联动主机侧和AIBot侧的全链路功能测试，确保满足用户要求和体验目标。

# **第十一章  质量要求 **

## **11\.1 通用质量规范**

本章从内在品质、设计准则、过程约束与通用规范四个维度，对 上汽AI汽车各模块的研发、生产与实施过程提出质量底线要求。以下通用规范适用于全部模块。

### **系统稳定性与响应**

- 各模块云侧服务须具备高可用性，单实例故障不应导致整体服务中断，核心接口可用性不低于 99\.5%。

- 端侧 SDK 须在座舱 SoC 目标硬件上稳定运行，连续运行不低于 8 小时无 crash、无内存泄漏。

- 所有涉及用户感知的交互链路须保证响应流畅，云侧接口 P90 响应时延须满足各模块验收阈值，端侧渲染与动画帧率不低于 30fps。

- 异常场景下须具备降级与兜底策略，不得出现白屏、卡死或无反馈状态，所有异常路径须有明确的 TTS 或 UI 提示。

### **代码与架构质量**

- 代码须符合公司编码规范，包含命名、注释、目录结构与异常处理规范，代码审查无中高危漏洞。

- 云侧服务须采用分层架构，业务逻辑、数据访问与接口协议层清晰分离，模块间通过标准接口通信，避免硬编码耦合。

- 端侧 SDK 须提供版本管理机制，接口变更须保持向后兼容，版本升级须提供迁移说明与兼容性测试报告。

- 代码可维护性须达到：核心模块圈复杂度不超过 15，重复率不超过 5%，关键业务逻辑须有单元测试覆盖。

### **安全与合规**

- 所有涉及用户数据的接口须遵循《个人信息保护法》及相关行业安全规范，敏感数据传输须加密，不得明文存储用户隐私信息。

- 三方接入须通过鉴权与白名单机制管控，未授权请求须被拒绝并记录审计日志。

- 车载场景下所有交互须符合驾驶安全规范，不得在行驶状态下展示需要长时间注视或复杂操作的界面。

- 各模块须通过安全漏洞扫描，无高危及以上漏洞方可交付。

### **UI 视觉与兼容性**

- 各模块界面视觉须遵循 上汽AI汽车统一设计规范，包括色彩、字体、图标、间距、动效等，保持全平台视觉一致性。

- 通知卡片、交互卡片须在不同屏幕尺寸与分辨率下正确适配，折叠态与展开态切换无错位。

- 端侧 UI 须与车机系统主题兼容，支持深色/浅色模式切换，不得出现样式冲突或渲染异常。

### **数据与接口质量**

- 所有接口须提供完整的 API 文档，包含请求参数、响应结构、错误码说明与调用示例，文档与代码保持同步更新。

- 云端与端侧状态须保持一致性，状态冲突时以云端为准并同步至端侧，同步延迟不超过 3 秒。

- 各模块须具备数据回流与监控能力，关键业务指标可通过 agentops 平台追踪与分析。
