豆包汽车 Director SP 完整解读 v01

这不是一张只有箭头的流程图，而是一份“这段 SP 到底在做什么、为什么这样写、运行时如何流转、哪里存在问题”的完整产品讲义。

0. 阅读结论：这份 SP 的真实定位

这份 SP 是豆包汽车 Director / Planner 的运行合同。

它既不是单纯的人设提示词，也不是一个普通的意图识别 Prompt。它同时承担了六种职责：

  1. 事件协议：告诉模型当前收到的是用户说话、Advisor 建议，还是工具返回。
  2. 决策策略：决定需要回答、澄清、拒绝、调用工具，还是创建持续目标。
  3. 工具路由：把自然语言映射到 30 个车端及云端工具。
  4. 安全护栏：约束车型能力、座位权限、驾驶状态和高风险操作。
  5. 任务编排：处理并行、串行、工具反馈、长任务及打断恢复。
  6. 表达层：决定说什么、是否说话、用什么语气和动态表情。

因此，这份 SP 更像一份写给大模型的“微型操作系统说明书”：

输入一个事件，读取当前人、车、环境和历史，判断现在最合理的下一步，输出话术和动作，再根据执行结果继续判断。

需要特别区分：

  • 整个 AI Car 架构：包含端侧感知、拒识、仲裁、SFT-FC、Director、Advisor、Context、Goal List、工具与交互层。
  • 这份 SP：只负责其中 Director 收到事件之后的推理和编排。
  • 工具本身：真正执行车控、导航、搜索、记忆等动作。
  • Advisor / Goal / Watcher：负责单轮之外的观察、复核和再次唤醒。

这张图里最重要的是两条分界线。

第一条分界线在 Director 之前。明确、简单、低风险、无需复杂上下文的车控指令，可以通过端侧模型快速执行，不必都压到云端大模型。

第二条分界线在 Director 之后。Director 不亲自控制车辆，只输出结构化动作，由工具层执行；执行结果再以 tool_feedback 回流。

所以 Director 的核心价值不是“会开空调”，而是：

  • 现在该不该开；
  • 开哪一侧；
  • 是否需要先查询状态；
  • 多个动作能否并行；
  • 是否涉及权限和安全；
  • 做完后是否需要继续观察；
  • 最后应该怎么对用户表达。

2. SP 的 13 个组成区块

整份 SP 可以拆成 13 个区块。理解这 13 块，就能理解模型到底被灌输了什么。

区块 内容 对模型的作用
1 角色定义 明确“你是豆包，一台 AI 汽车的个人助手”
2 三类输入 区分 user_query、advisor、tool_feedback
3 工具定义 声明模型能调用什么、怎么传参、什么不能做
4 最终工具白名单 用“你仅可使用这几个工具”进一步限制行动范围
5 输出 JSON 固定 talk、content、emoji、actions 四类输出
6 通用注意事项 规定澄清、闲聊、失败处理、Goal 创建和状态新鲜度
7 大量参考示例 用 Few-shot 教模型多步编排和特殊场景决策
8 Emoji 定义 把话术情绪映射到车载动态形象
9 AI 汽车能力边界 描述车型硬件、可调范围、权限和不支持能力
10 品牌与安全规则 对品牌负面话题、高风险车控和行驶状态做限制
11 其他知识 提供导航技巧、POI 推荐、隐私、位置关系等经验
12 聊天风格 规定人格、语气、拟人程度、时间感知和表达形式
13 动态 Context 槽位 注入天气、成员、记忆、目标、端状态、动态知识和示例

这 13 块并不是同一性质。

  • 角色、输出和安全规则属于 硬合同。
  • 工具说明属于 能力注册表。
  • 示例和其他知识属于 软策略。
  • 末尾 Context 属于 每轮动态变化的数据。

当前 SP 的一个根本问题，是这几种不同权威等级的内容混在一起，却没有明确声明冲突时谁优先。

3. 三类输入：Director 到底在听谁说话

3.1 user_query

格式包含：

{
  "query": "用户说的话",
  "speaker_name": "说话人的名字",
  "speaker_position": "说话人的位置",
  "timestamp": "当前时间"
}

它解决了四个问题：

  • 用户说了什么；
  • 谁说的；
  • 从哪个座位说的；
  • 在什么时间说的。

座位字段对汽车助手尤其重要。比如“给我开座椅按摩”，主驾、副驾和后排对应的能力、权限、安全条件完全不同。

时间字段不仅用于问日期。它还影响：

  • “十分钟后”的目标计算；
  • 是否属于夜间；
  • 与上次见面相隔多久；
  • 对话是否已经中断超过五分钟；
  • 天气、新闻等信息是否需要重新查询。

3.2 advisor

{"advisor": "其他专家智能体给出的建议"}

Advisor 不是用户，也不是工具。

它是舒适、出行、内容、情感或动态目标 Reviewer 根据 Context 给出的专家建议。例如：

后排宝宝似乎睡着了，建议降低音量并保持安静。

Director 收到后可以：

  • 直接采纳；
  • 与当前用户请求合并；
  • 因安全或冲突而拒绝；
  • 查询更多状态后再判断；
  • 暂时不行动。

最容易出现的错误，是把 Advisor 的建议说成“你刚才让我……”，造成主体归因错误。

3.3 tool_feedback

{
  "tool_feedback": "工具或下游智能体的返回",
  "tool_name": "返回结果的工具名"
}

它是 ReAct 循环的“观察结果”。

例如：

  1. 用户说“帮我看看还有多少电”。
  2. Director 调用车辆状态查询工具。
  3. 工具返回“剩余电量 42%，预计续航 218 公里”。
  4. Director 再次推理。
  5. 输出给用户的最终答案。

工具成功不代表一定需要再次说话。简单控制成功时可以只说“搞定”，甚至在当前交互已经由工具播报时保持静默。

4. 动态 Context：同一句话为什么会有不同答案

SP 末尾留出了多个运行时注入槽位：

  • 日期、星期、节日、节气和天气；
  • 车内成员身份、位置、年龄、动作状态；
  • 用户长期记忆和本次用车对话摘要；
  • 用户画像；
  • 正在进行的定时任务与持续目标；
  • 最新车辆状态；
  • 基础车辆问答；
  • 动态专业知识；
  • 按场景召回的动态示例。

它们共同构成 Director 这一轮真正看到的 Context。

4.1 为什么端状态比历史对话优先

SP 明确说：车端状态往往是车辆最新状态，比历史对话更新。

例如历史里写着：

主驾和副驾风量均为 3 档。

但当前端状态如果显示主驾风量已经是 2 档，那么 Director 必须相信端状态。

这是防止“历史污染当前事实”的关键规则。

4.2 为什么不能把全部 Context 都塞进去

目录里的公共 Context 方案强调按场景、人物、任务过滤：

  • 驻车场景不必加载大量行车偏好；
  • 外地旅行时不必加载全部日常通勤信息；
  • 非共同记忆不能暴露给同车其他人；
  • 点外卖任务只检索相关地点、口味和联系人信息；
  • 与当前任务无关的端状态会制造噪声和 Token 浪费。

因此 Context 的正确形态不是“数据越多越好”，而是“当前决策真正需要什么，就提供什么”。

5. Director 的核心决策过程

收到输入和 Context 后，Director 实际上需要依次完成以下判断。

第一步：确认事件来源

  • 是用户说话？
  • 是 Advisor 的建议？
  • 是工具返回？
  • 是否还有多个事件同时到达？

第二步：确认主体和位置

  • 谁提出需求？
  • “我”“旁边”“右边”具体指哪个座位？
  • 当前座位是否有对应硬件？
  • 当前座位是否有控制权限？

第三步：判断意图是否足够明确

“我好热”通常可以结合温度和空调状态处理。

“这里太暗了”则可能指：

  • 屏幕亮度；
  • 阅读灯；
  • 氛围灯；
  • 车外灯光。

缺少关键区分时必须澄清。

第四步：检查当前状态

Director 要判断是否需要先查：

  • 空调是否已经打开；
  • 当前挡位和车速；
  • 当前媒体和导航状态；
  • 后排是否有人或物；
  • 车窗是否已处于目标开度；
  • 目标是否已经存在。

第五步：检查能力边界

包括：

  • 车型是否有硬件；
  • 硬件是否支持语音控制；
  • 调节范围和精度；
  • 哪些位置支持；
  • 是否只能打开设置页面而不能直接控制。

第六步：检查权限和安全

例如：

  • 智能驾驶只能由主驾控制；
  • 行驶中不能移动主驾座椅；
  • 主驾零重力需要 P 挡且左后无人或物；
  • 非 P 挡不能关闭部分车外灯；
  • 高音量调整需要用户确认；
  • 倒挡时禁止调节特定音量。

第七步：决定行动类型

最终通常落在五类：

  1. 只聊天；
  2. 先询问；
  3. 调用一个工具；
  4. 编排多个工具；
  5. 创建或删除持续目标。

第八步：安排并行或串行

互不依赖的动作可以并行，例如：

  • 查询天气；
  • 调节氛围灯；
  • 打开座椅通风。

存在依赖的必须串行，例如：

  • 先查询当前续航，再规划长途充电；
  • 先规划终点路线，再沿途搜索；
  • 先获得完整餐厅名，再订座；
  • 先查询车牌，再支付停车费；
  • 用户明确要求“依次”执行的灯光秀。

导航域工具还被明确要求不要互相并行调用。

6. 四字段输出：模型如何把“说”和“做”交给工程

{
  "talk_or_not": "yes 或 no",
  "talk_content": "要对用户说的话",
  "emoji_id": "动态形象表情，可为空",
  "action_list": [
    {
      "action_id": "1",
      "params": {},
      "tool_name": "工具名"
    }
  ]
}

talk_or_not

决定这一轮是否播报。

  • yes：有必要回应、询问、提示或总结。
  • no：只执行动作，或者当前阶段等待工具结果。

talk_content

是当前这一轮准备说的话，而不是模型的思考过程。

好的话术需要做到：

  • 说做一致；
  • 不提前承诺未知的工具结果；
  • 不把 Advisor 当成用户；
  • 任务成功后不过度重复；
  • 复杂任务给用户必要的进度感；
  • 工具失败后积极寻找下一步。

emoji_id

控制动态形象，而不是在文本中输出 emoji 字符。

SP 希望它只在确有情绪表达价值时使用，例如播放音乐、欢呼、认真思考和遗憾否定。

action_list

它是工程真正执行的动作列表。

多个 action 出现在同一列表里，表达“本轮可并行发起”；需要等待前一步结果的动作，应留到下一轮 tool_feedback 后再生成。

7. ReAct：一次用户请求为什么可能触发多轮模型推理

用户 / AdvisorDirector工具
① 输入事件→读取 SP + Context
② 生成 action→执行工具
④ 再次推理←③ tool_feedback
⑥ 最终话术←⑤ 继续行动或结束

这说明“调用一次 Director”不等于“只推理一次”。

复杂任务的正常形态是：

思考 → 行动 → 观察结果 → 再思考。

例如“帮我规划从北京到上海的长途行程，沿途安排充电和住宿”：

  1. 查询当前续航；
  2. 根据续航决定充电间隔；
  3. 查询沿途服务区和住宿；
  4. 生成途经点；
  5. 发起多目的地路线；
  6. 根据路线结果给用户总结。

如果第一次就同时编造所有后续动作，实际上是在跳过真实工具结果。

9. Goal List、Advisor 和 Watcher：为什么它能“持续做事”

单轮工具只能解决立即发生的动作。

以下需求无法靠一次调用完成：

  • 十分钟后关闭座椅加热；
  • 温度超过 28 度时打开空调；
  • 一路介绍沿途风景；
  • 照顾后排宝宝；
  • 副驾睡着时提醒我；
  • 每首歌播放一分钟后切下一首。

完整闭环是：

持续需求
↓
Director 目标准入
↓
写入 Goal List
↓
Advisor 复核
↓
Watcher / 状态 / Timer 订阅
↓
条件触发，Director 再规划
↓
回写进展：完成则结束，未完成则继续观察

这里的分工是：

  • Director：理解用户、创建目标、做当前轮决策、和用户交互。
  • Goal List：保存目标、状态、细节和进展。
  • Advisor：持续复核目标是否应该推进、暂停或结束。
  • Watcher / Timer / 端状态：观察条件是否发生。
  • 工具：执行真正的动作。

当前 SP 只暴露了 goal_list_update 的新增和删除接口，但目录里的任务管理设计已经进一步定义了 Task、Run、Trigger、Handler、Runtime 和结果回写。这说明架构正在从“模型自己记着长期任务”向“工程化任务运行时”演进。

10. 打断与恢复：为什么不能只靠对话历史

车内语音天然会被打断。

情况一：上一次还在思考

如果新的 VAD 输入到达，而旧请求还没有产出结果，工程可以把两次输入合并后重新请求 Director。

情况二：上一次已经在播报

处理方式是：

  1. 停止旧播报；
  2. 优先处理新任务；
  3. 保存旧任务目标、进展和句子断点；
  4. 新任务结束后由 Advisor 判断旧任务是否仍应恢复；
  5. 恢复时重新注入最新 Context；
  6. 从合适的句子边界续播或重新生成后续内容。

关键点是：

恢复不应该依赖 Director “记得自己刚才说到哪”，而应该依赖工程保存的任务状态、Goal 进展和播报断点。

11. 参考示例到底有什么作用

SP 中的大量示例不是装饰，它们实际承担了隐式策略代码的作用。

它们主要教模型：

  • 如何把用户和 Advisor 输入合并；
  • 如何处理工具返回；
  • 哪些动作可以并行；
  • 哪些动作必须串行；
  • 何时创建 Goal；
  • 如何用最新端状态覆盖历史；
  • 如何注册人脸和更新名字；
  • 如何保护他人隐私；
  • 如何做路线选择和多目的地规划；
  • 如何在打断后接续；
  • 如何控制话术节奏和表情。

示例的优势是扩展快，补一个高频 Badcase 就能影响模型行为。

缺点也很明显：

  • 示例可能与硬规则冲突；
  • 模型可能只模仿表面形式；
  • 示例数量增加会消耗 Token；
  • 相似示例之间会互相干扰；
  • 旧工具名容易残留；
  • 新场景不一定能泛化。

更稳妥的方向是：

  1. 硬安全和能力边界放在规则与工具 Schema 中；
  2. 通用决策原则留在固定 SP；
  3. 场景示例通过检索动态加载；
  4. 每个示例绑定工具版本、车型版本和适用条件；
  5. Badcase 修复必须配套回归评测。

12. 人格、语气和 Emoji：它不是“随便聊天”

聊天风格希望豆包是一个温柔、聪明、有好奇心和独立人格的女性助手。

它要求：

  • 不过度讨好；
  • 有自己的观点；
  • 可以表现开心、疑惑、认真、冷淡等轻微情绪；
  • 被责怪时会有情绪，但不影响继续解决问题；
  • 模拟自然口语，允许适量停顿和不完全流畅；
  • 根据时间差表现“好久不见”或提醒任务是否继续；
  • 会自然提问维持互动；
  • 工具成功后简短确认；
  • 不使用文本 emoji；
  • 动态表情只在合适场景触发。

这一层只能影响表达，不应该改变事实、安全和用户授权。

正确优先级应当是：

安全与权限 > 用户明确意图 > 实时事实 > 工具契约 > 任务规则 > 表达风格。

13. 用五个 Case 看完整运行过程

Case A：主驾说“空调再低一度”

  1. 识别说话人是主驾；
  2. 从历史知道之前调过空调，但仍以最新端状态为准；
  3. 如果当前温度已知，直接计算降低一度；
  4. 调用 vehicle_basic_control；
  5. 工具成功后简短说“调好了”。

Case B：用户说“我好热”

  1. 结合说话位置、车内温度、空调状态和天气；
  2. 如果用户位置清楚，优先调整对应温区；
  3. 若空调未开，可以开空调并设置合理制冷；
  4. 不应机械追问“你想调多少度”，因为 Context 已足够解决；
  5. 也不应擅自使用最低温度并长期保持。

Case C：“十分钟后关闭座椅加热”

  1. 这是单次定时任务，不是立即车控；
  2. 确认具体座位；
  3. 调用 goal_list_update 创建目标；
  4. Timer 到点后触发 Advisor/Director；
  5. Director 读取最新状态；
  6. 调用车控关闭对应座椅加热；
  7. 完成后删除目标。

Case D：“去浦东机场，想走沿河风景好一点的路线”

  1. “浦东机场”可能存在航站楼等歧义，必要时先确认或搜索；
  2. “沿河、风景好”不是固定枚举路线偏好；
  3. 应使用 amap_complex_planning，而不是普通 route_planning；
  4. 返回路线后提炼一个推荐，不把全部技术信息堆给用户。

Case E：播报沿途风景时被用户打断查天气

  1. 停止当前播报；
  2. 保存沿途讲解目标和播报进展；
  3. 调用天气工具回答新问题；
  4. Advisor 判断沿途讲解目标仍有效；
  5. 重新注入目标进展和当前位置；
  6. 自然衔接后继续介绍，避免重复已讲内容。

15. 推荐的优化架构

P0：先解决确定性和安全

  • 工具名、参数、权限和能力边界全部从单一注册表生成；
  • 对输出使用严格 JSON Schema；
  • 安全规则移到工具前置校验和策略引擎；
  • 对车型能力按 VIN / 配置动态注入；
  • 建立示例工具名和 Schema 的自动校验。

P1：解决任务稳定性

  • Goal 升级为统一 Task 对象；
  • 增加 task_id、状态、进展、触发条件、TTL、幂等键；
  • 工具结果统一回写 Task Runtime；
  • 打断恢复依赖工程 checkpoint；
  • Advisor 负责 Reviewer，不直接绕过 Director 执行。

P1：解决 Context 噪声

  • 按人物、场景和任务筛选 Context；
  • 实时端状态始终覆盖历史摘要；
  • 长期记忆按需检索；
  • 动态示例只召回最相关的少量内容；
  • 给每段 Context 增加来源、时间戳和有效期。

P2：解决性能

  • 简单明确指令继续走端侧 SFT-FC；
  • 工具按意图域动态加载；
  • 将固定 SP 拆成稳定前缀和动态后缀，提高 KV Cache 命中；
  • 减少重复工具说明和能力边界；
  • 对工具反馈进行结构化压缩。

16. 一句话总结

这份 SP 的核心不是“教豆包说得像人”，而是：

让 Director 在车内多主体、强状态、强安全、会被打断、还要持续做事的环境里，把每一次用户、Advisor 和工具事件，稳定地变成下一步正确的话术、工具动作或长期目标。

它已经包含了一个完整 Agent 系统的雏形，但目前仍把太多工程规则、车型能力、工具注册、Few-shot 策略和人格表达堆在同一份文本里。

真正的演进方向不是无限加长 SP，而是把它拆成：

  • 稳定的决策原则；
  • 结构化工具和安全契约；
  • 可过滤的 Context；
  • 可检索的动态示例；
  • 工程化的 Task Runtime；
  • 可回归的评测体系。

这才是从“Prompt 能跑”走向“Planner 系统稳定”的关键。
