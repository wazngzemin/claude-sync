## 二、卡片模块必须具备的完整产品定义

### 2.1 三个对象不能混成一个状态

- 长期任务：用户是否允许今后继续判断；一次卡片关闭不关闭长期任务。
- 本次业务处理：当前哪一次条件命中，接下来是否识别、询问、执行；结束后不能由旧回调重新启动。
- 卡片：本次询问是否注册、排队、展示、可操作、已消费、撤销或结束。卡片创建成功不代表用户已经看见。

### 2.2 业务给卡片的内容

| 信息 | 产品要写清楚的内容 | 缺少后的行为 |
|---|---|---|
| 本次关联 | 哪项任务、哪辆车/账号范围、哪一次事件、哪一个卡片实例 | 不建立可执行询问，避免串车或串事件 |
| 展示内容 | 模板、标题、正文、目标动作说明 | 关键文案缺失不展示；不能由卡片猜测天气或目标动作 |
| 交互方式 | 仅告知或需要确认，确认/取消各代表什么 | 未定义确认意义不得绑定车辆动作 |
| TTS | 是否播、播什么、播报失败后的体验 | 语音播报失败不自动表示用户拒绝，也不自动执行 |
| 点击路线 | 本地业务回调、云端业务回调，或明确选定的兼容 Query | 未接入路线不发布对应交互方案，不能双路触发 |
| 用户语音 | 本地按钮表达，或云端 Planner 上下文与选择能力 | 能力未接入时不承诺语音；是否允许退化为仅点击需产品会签 |
| 有效范围 | 卡片等待时长、场景失效条件、本次任务关联 | 过期禁止旧确认；排队超过场景有效期则撤销 |
| 结果更新 | 执行中、成功、失败、结果暂不能确认的文案和控件 | 不把请求已发出呈现为动作成功 |

### 2.3 返回、处理与清理规则

1. 卡片返回注册/请求接收结果。业务只能据此进入待展示，不开始用户回答倒计时。
2. VUI 返回真正展示结果。业务从此刻开始回答等待；总体事件/识别有效期独立计时，不能因排队重新延长。
3. 点击与语音形成一个本次选择。业务校验同一事件、仍有效、未消费后再进入执行前复核。
4. 拒绝、关闭、超时、被替换、任务关闭分别记录事实；它们都不执行，但不要全部记录成用户拒绝。
5. 卡片失去可操作资格时停用本地按钮词和云端卡片选择上下文，防止随后“好的”消费旧任务。
6. 执行请求发出后卡片更新失败不再次执行车控；已执行动作不因卡片关闭而自动反向恢复。
7. 卡片暂时隐藏再恢复时，不自动恢复旧授权。恢复条件、是否继续倒计时、业务是否仍有效需约定；暂不支持恢复就不宣传该能力。

### 2.4 语音的三个独立环节

| 环节 | 负责什么 | 不等于什么 |
|---|---|---|
| TTS | 设备把配置文案念给用户听 | 不等于设备已开始听用户回答 |
| 可见即可说 | 在当前可操作卡片范围把支持表达匹配到按钮，走原按钮处理 | 不默认支持“等一下”“为什么”等自由语义；不能假设本地能力现已接入 |
| Planner 泛化理解 | 结合当前可操作卡片理解自由回答，给原业务选择结果或已注册能力调用 | 不注册/拉卡；理解“好”不等于端侧已允许车控；不把未命中的表达当确认 |

需要分开验收“有卡无TTS”“有TTS但不支持语音回答”“卡片点击可用、云端语音断网不可用”。全局禁语音、单项TTS策略、麦克风/识别能力的具体关系应由VUI确认，不能自动捆绑。

## 三、四项任务案例必须补的可评审细节

### 3.1 天气保护

连续案例：任务开启→收到有效路面湿滑标签连续3次→当前速度大于30且不是湿滑模式→Trigger发雨天事件→业务确定只建议湿滑模式→卡片真正展示→用户说已支持的“确认”→模拟当前确认按钮→业务复核雨天建议、任务与车况→执行湿滑模式→读取实车模式→更新结果。

退出案例：路面和天气连续8次均不支持雨天，且不是被定义的隧道抑制期间→先确认是否满足“建议关闭”的资格→显示新的关闭询问→有效同意后执行已确认的恢复目标。**关闭湿滑/雪地模式具体切换到什么模式未写，不能用“关闭模式”代替动作参数。** 也不能关闭用户后来手动选定的模式；是否只对本任务开启的状态建议退出需会签。

雨雪同时命中时，图中优先级先选择雪；另两条是否延后、合并或丢弃，以及雾灯可否独立询问，原稿未确定，应给出明确选项影响，不能静默捆绑动作。

### 3.2 儿童锁

正向案例应在最终选定 A/B 后写：开启任务→触发指定档位事件/状态检查→目标成员识别有效→目标侧锁关闭→按选定静默或确认策略→执行前读最新成员、档位、门/锁状态→开启确定的侧别→读目标侧真实锁状态。

需要确认：仅儿童/老人和儿童枚举是否包含其他成人+儿童；宠物字段猫/狗是否本期接入；前排宠物是否算后排任务；后排占座识别范围；门开时允许锁动作的车辆限制。功能退出是结束推荐，不自动解锁儿童锁。

### 3.3 充电口盖

正向案例：D→P为示例来源档位，SOC19%、口盖关、任务及必要开关有效→一次停车只产一个事件→业务调用主动推荐与DT/VQA→返回明确发现且观察仍属本次停车→业务注册询问→真正展示→确认结果回业务→端侧复核本次停车与最新状态→一次开盖请求→真实口盖OPEN才成功。

四类结果分开：未找到是明确不满足；无法判断是信息不足；调用失败是链路错误；发现设备是进入后续策略资格。四者都不是用户授权。

本任务不会自动关闭口盖。展示“设备可用”需另有兼容性/占用/位置判断能力；当前只识别设备时不得承诺能充电。用户另提导航诉求时不消费为当前开盖同意。

### 3.4 后视镜加热

应拆三条配置：雨天中低速状态规则、洗车退出一次事件、高湿温差窗口规则。三个原因可能同时存在，不能当三个互不相干、各自都能随时关闭同一加热的任务。

雨天案例展示满足条件且关闭→静默开启→回读ON→记录开启原因；条件消失后的关闭行为按D-07会签。洗车案例展示收到新退出事件→静默开启→回读ON→15分钟计时→判断能否关闭→回读OFF。高湿案例在计算窗口未定前只能作为待接入方案，不能给固定周期演示成需求定值。

## 四、测试 Agent 应追问的重点用例

| 用例 | 前置与操作 | 预期中间状态 | 预期最终结果 |
|---|---|---|---|
| T01 请求接收非展示 | 拉卡已接收，但一直排队 | 待展示，不计用户回答超时 | 场景过期撤销，无车控 |
| T02 拒绝不是关任务 | 卡片已展示，点击取消 | 本次已拒绝，旧确认失效 | 本次无动作；长期开关仍开 |
| T03 语音点击并发 | 用户说确认同时点击确认 | 同一选择只消费一次 | 最多一次车控，不重复播成功 |
| T04 跨卡回调 | 新询问展示后旧卡确认回调迟到 | 旧事件失效，记录丢弃原因 | 不执行旧目标，不影响新卡选择 |
| T05 先关任务再确认 | 云端卡展示中用户关闭任务，再确认 | 业务与端侧校验不通过 | 不执行，撤销可操作卡片 |

| T07 TTS不可用 | 卡片可显示，TTS播报失败 | 按会签降级保留点击 | 不假设用户已听见，不自动同意 |
| T08 泛化疑问 | 用户问“为什么要开” | 不是同意；可解释且保留/结束按有效期 | 不开盖 |
| T09 过时设备结果 | 设备识别返回前车辆切出P又进入新P | 老结果归旧停车 | 不复用结果；新停车按频控重新判断 |
| T10 RPC已接收状态未知 | 请求成功但回读超时 | 执行结果待确认 | 不显示成功，不盲目再次开盖 |

| T13 隧道保护 | 已有模式，进入隧道天气暂消失 | 退出询问被抑制（需可靠隧道信号） | 不误推荐关闭；信号未接入不得宣称此用例通过 |

| T15 用户手動锁状态 | 系统动作前用户已开童锁 | 复核“目标已达成” | 不再次发车控，记录无需执行 |
| T16 加热原因重叠 | 洗车15分钟到期但雨天原因仍成立 | 识别仍有有效加热需求 | 按会签合并策略，不由一个计时器盲目关闭 |
| T17 加热手动接管 | 本任务开加热后用户手动关闭 | 识别用户反向操作 | 按会签抑制重复开启，不能下一帧又打开 |

## 五、可直接向评审人说明的边界

“这次不是开发一个全新的卡片系统，而是由系统预设任务业务把四项任务接到已有或待完成的交互能力上。通用框架负责排队和展示，业务负责本次问什么、选择对应什么动作、何时失效和真实结果。卡片可用、本地语音已接入、云端泛化已接入要分别验收。原稿里有冲突的图不会继续作为实施口径；我们在本稿逐条统一，并把没有会签的策略明确留作决策，不让研发自行猜。”
