按图逐步读懂
C1 · 接本轮输入，按需要并行取背景
Context 只组装，不包存储；身份、状态、视觉、历史并行供给；常用信息预注入，缺项再查；不是所有 query 固定查全套。
Context 把各系统已有的信息组织成 Director 能使用的背景，不替每个来源保存全部原始数据。根据当前请求与项目 scope，并行获取必要来源；不是先查身份，再查车况，再查记忆的一条长队。比如“开主驾车窗”可能不需查网上天气；“去昨天那家店”则需要身份与记忆。V2 把高频预注入和后续显式查证分开，避免每轮都走最重流程。
C2 · 确认当下说话人与操作对象
当前乘客姓名、座位和可信身份；人名→此刻座位，不用旧记忆猜；未知/冲突交 K 身份链处理；给明骏加热→明确副驾加热。
姓名和座位来自本次车内身份信息，而不是历史聊天里曾坐哪个位置。Context 将说话人、所在音区和其他在场人提供给 Director，隐私授权由 K 区先把关。比如“给明骏把加热打开”，只有确认明骏当前在副驾才能改写；未知或同名不能猜一个座位。身份识别、座位定位和是否有权操作是三件事，不能用认识名字替代车辆权限。
C3 · 取车辆此刻的值和时间
空调/车窗/挡位/续航/导航等；常用状态固定注入并去重；缺失或过期不当关闭/零值；当前上报优先于旧对话印象。
Context 给模型当前已知状态，并保留采样或发生时间。用户刚手动调了空调，最新车端上报应比旧话术“已设24度”可信。SLS 文档有常用状态固定注入和按查询筛选，不能据此推定所有信号每轮齐全。缺数据应明确未知，必要时调用状态查询；已经最低温度时不再降低，已关闭的车窗也不应重复关闭。
C4 · 取舱内外情景，不把视觉当身份
天气、位置、时间及感知描述；乘员动作、外部环境按来源提供；FaceID 与视觉人物要对齐；背景感知≠每次主动拍图问答。
持续感知提供最近舱内外描述，世界信息提供位置、天气与时间，供 Director 理解一句话发生的环境。视觉描述中的人要与可信 FaceID 对齐，不能凭模型多造一名乘客。比如外面下雨、后排宝宝睡了，会约束开窗和大风量；但背景已经有的信息不必每轮重新调用 VQA。需要看特定方向或细节时，才由 Director 发起额外视觉查询。
C5 · 接最近对话、工具事实和摘要
保留用户目标与已完成动作；工具反馈与用户话语分清；摘要隐私清理见 K12；新轮不重复旧轮已下发动作。
历史不是一段普通聊天文本，它还要让 Director 知道上轮调过什么工具、回了什么事实、哪些话已播过或被打断。近轮保留多少、远轮怎样压缩要按项目配置，不能把旧10轮策略全局写死。比如刚查到一家餐厅，用户说“第二家”，必须保留真实候选映射。摘要在新人上车时另有敏感信息清理，不能把私密旧话原样递给新乘客。
C6 · 带任务视图，区分旧 Goal 与新 Task
本项目注入 goal_list 或 task_view；只读正在跟进什么及其状态；创建成功不代表条件已触发；具体生命周期转任务系统。
Context 提供本项目仍在跟进的目标或任务视图，帮助 Director 避免重复创建并理解当前进度。旧 Goal List/动态 Advisor 与新 Task Service 不是前后串行的两个必经模块，应按渠道分别显示。比如“十分钟后关加热”已注册，当前只是等待时间，不等于加热已关。修改和删除要落到对应真实任务标识，不能凭标题假造成功。
C7 · 第一路：推理前预取常用记忆
用户画像与相关记忆并行取；query→标签→记忆及匹配分数；记忆来源按分数过滤再注入；隐私与授权先走 K 规则。
根代理核验的 Context V2 原图以记忆为例：画像一路并行获取，用户 query 另一路经标签模型检索，得到记忆列表与匹配分数，再按规则过滤后预注入。该算法不能扩大成所有 Context 数据都这样检索。是否准许读某人的记忆先由身份和授权决定；如果已拿到昨天游泳馆地址，Director 就无需再做一次显式记忆查询。
C8 · 注入本车型可用能力与知识
真实车型/配置/功能边界；工具定义和实现按渠道筛选；动态工具准入细节见 F；有工具名≠有设备/已上线。
Context 和提示词必须告诉模型这辆车实际有哪些设备、参数范围、座位限制与可用工具。工具标准化表列了名字，不等于低配车装了按摩，更不等于当前渠道有已发布实现。F 区负责工具定义、实现与运行时条件。比如车书说高配有流光氛围灯，当前低配就不能照搬；能力知识缺失时要查证或澄清，而不是靠语言把功能补出来。
C9 · 选适用示例，不覆盖真实约束
静态示例教通用决策方法；动态示例检索低频单点经验；先核渠道/环境/车型/舱内外；召回、注入、采用分别验收。
动态示例把类似 query 的决策分析放进提示词，帮助模型选择工具；它不是新增硬件或绕过安全规则的授权。9月3日逐字稿记录低配车被召回按摩示例导致回答错误，当时车型、舱内外等二期能力尚未开发。绘图要区分需求与已发布配置。排查时逐段看正确库、召回、注入、模型采用及实际工具结果，不因“已召回”就宣布问题解决。
C10 · 各来源各自过滤，保留未知
V2 已取消统一模型精筛；来源校验范围、时效和相关性；冲突信息保留出处和待确认；不能混成一条万能“真相”。
当前 Context OnePage 的 V2 已移除统一精筛，由不同来源分别处理相关性和质量。身份、状态、知识和记忆并行完成后汇集，不能再画成一个大模型替所有数据做最终判真。比如旧记忆说不爱开窗、最新用户明确要求开窗，需要 Director 结合当前意图决策；状态缺失和视觉不确定则必须保留未知，不能让整理层擅自补值。
C11 · 组装本轮背景给同一个 Director
背景＋输入＋项目提示词；静态规则与动态数据分开放；按目标渠道变量映射注入；信息够则回答，不够再查证。
汇集后的背景连同本轮输入交给同一个 Director：工具、示例、车型规则与记忆、状态、历史分别有来源，便于定位错误。Context 只提供证据，不直接替用户发车控。比如天气已说明下雨、空调状态已齐，Director 可以立即规划；若还不知道具体餐厅地址，则转显式工具查证。不同项目提示词字段可能变动，不能靠固定截图推断线上全部变量。
C12 · 第二路：Director 缺记忆才显式查
携关键词与需要的时间范围；记忆工具重新检索并做权限过滤；结果作为 feedback 进入下一轮；不绕过输入管理直推新动作。
当预注入不足以回答“昨天去过的游泳馆在哪”，Director 调记忆检索工具，带清楚对象、关键词及时间范围。工具重新完成合法检索，将具体事实作为 tool_feedback 返回，随后通过输入管理再让 Director 判断导航，不是 Context 自己启动导航。原图最后还有交互历史同步，支持后续连续对话；这条显式查询支路只在信息不足时发生。
