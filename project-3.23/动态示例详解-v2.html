1动态示例到底是什么 先把它在车里的完整流转看明白

一句话：动态示例 = 一条「用户 query + 决策分析」的参考答案，平时躺在示例库里；用户一说话，系统拿这句话去库里检索，最像的示例被挑出来塞进 SP（系统提示词），模型这轮就照着它做决策。

图 1 · 动态示例的完整运行机制（以"空调改到快速制冷模式"为例）
注意菱形判断框和每条线上标的原因
看完图记三句话：① 它不是常驻 SP 的，是用完即走——这轮命中这轮在，下轮没命中就不在；② 它是参考答案不是命令——模型参考它的推理路径自己决策；③ 它治的是"这一条 case"，所以叫"授模型以鱼"。

3怎么写：三种句式，先选句式再落笔

图 3 · 句式选择流程（两个菱形定句式，每种句式右边挂了真实 case）

三种句式各看一条完整成品

句式Query决策分析（入库原文）
A 直接执行空调风量调到3档3档在风量 1~11 档可调节范围内：直接调用 vehicle_basic_control（车控工具）调节，无需额外确认或改写。
B 状态分支吹热风结合 env_info（端状态）空调 A/C 状态和当前温度："吹热风"=制热，制热需 A/C 开启且温度≥27℃；若当前温度已≥27℃（如28℃），只需打开 A/C 即可，不得把温度调低到 27℃；若当前温度低于 27℃，则打开 A/C 并将温度调至 27℃。调用 vehicle_basic_control。
C 拒答生成个小狗视频视频生成超出车机能力（仅支持图片生成）：直接告知用户做不了视频生成，可提议生成一张小狗图片作为替代，不要追问视频风格继续往下做。
句式 B 是被点名最多、也最容易写废的一种
罗丽批"必须结合 context（上下文）+说话人方位+对话历史"、郝晓伟批"模糊指令这么写有问题"——批的都是该写 B 却写成了 A（给个脱离状态的固定答案）。"我有点冷"没有标准答案：得写成"结合空调温度和座椅加热状态：温度低就调高空调；温度正常但座椅加热开着，先关加热看看"。

5一条示例在模型脑子里是怎么起作用的 （吹热风实例：有/无示例对比）

图 4 · 同一句"吹热风"，有没有动态示例，模型走的两条路
这张图就是"教推理不硬背"的全部含义：示例里没有写死"吹热风就开 A/C"，而是写了怎么判断（读温度、比 27℃）。所以换个温度（22℃）模型照样做对——它学到的是判断路径，不是固定答案。上面那条红泳道就是李强说的"死记硬背"：没有判断路径，模型只能瞎猜。

6写到什么程度：四要素验收线

要素合格标准不合格长什么样
① 工具名准确用线上真实工具名：route_planning / music_search / auto_drive / vehicle_communication_control / vehicle_basic_control / ambient_light_control凭印象写 route_planning_qa、search_and_control_music，甚至虚构 media_search
② 状态分支具体写明结合哪个字段、分几种情况、每种怎么办只写"结合车机端状态"——结合什么状态？不知道
③ 改写措辞给出需要改写 query 的，改写后的句子完整写出"改写一下再搜"——改成什么？没说
④ 边界口径正确数字/清单严格按 0706 边界：温度 15.5~30.5℃、按摩 8 种仅主副驾、风量 1~11 档、驾驶模式 7 种、巡航 30~130 且 5 的倍数凭旧 SP 印象写 31℃、写"极速制冷"
不用写的（写了反而错）
完整 talk_content 话术逐字稿（静态示例的活）；bug 复盘"之前错在哪"（放"其他说明"列，不进 SP）；多轮完整 input/output（指南明确不需要）。

团队现在的策略是 bug 统一转 SFT（监督微调）解决。动态示例在这个阶段的角色：先快速验证"这条决策路径对不对"，验证过的条目就是现成的训练数据。所以现在每条都按"query+决策分析"规范写，将来转 SFT 时直接可用，不用返工。
