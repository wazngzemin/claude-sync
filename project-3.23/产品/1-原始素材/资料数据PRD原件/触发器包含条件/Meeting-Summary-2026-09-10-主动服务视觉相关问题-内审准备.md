# 主动服务视觉相关问题：会议复盘与内审准备

## 1. 会议信息

- 时间：2026 年 9 月 10 日 15:10–15:26
- 主题：主动服务如何消费端侧视觉识别结果
- 参会人：丁彬、王泽民、赵益红
- 本文依据：用户提供的原始会议转写

## 2. 一句话结论

视觉侧能够把舱内外识别结果上传云端，技术链路有两种可行做法；真正需要内审决策的是，量产方案到底优先保留开放视觉能力，还是优先控制云端成本、并发和时延。

会议只把两条路线聊通了，没有完成方案选型，也没有确定解析模块的正式 owner、量产性能指标和首期标签范围。

## 3. 会议在说什么

### 3.1 问题为什么出现

动态 Advisor 面对用户当下的一次 Query，完成一次判断后任务即可结束。系统预设的静态主动服务不同：任务可能长期打开，还可能同时存在十多个视觉场景。若每个任务都持续轮询 Caption，再调用云端模型解析，一辆车就会产生多路持续推理；扩展到量产车辆后，模型调用成本、并发量和耗时都会被放大。

这里的 Caption 是视觉模型输出的一段自然语言画面描述，例如“窗外出现古典建筑”。

### 3.2 当前数据怎么流转

丁彬介绍的现状是：Always-on 视觉能力把舱内外识别结果封装成一整包 JSON，上传到云端端状态/数据中心。DT（Director，负责理解上下文和继续决策的模型链路）可以把整包数据放进 Context，直接由模型理解，不需要先拆成业务标签。

主动服务若不想使用模型解析，就需要从整包 JSON 中按约定规则取出需要的字段。会议中仍存在一个需要澄清的技术点：新增的“美景”究竟是结构化枚举字段，还是 Caption 字符串里的一段文本。如果已经是结构化 JSON 字段，云端通常只需按字段读取；如果藏在自然语言 Caption 中，才需要额外的规则或模型解析。

### 3.3 两条可走的方案

| 路线 | 数据形态与使用方式 | 优点 | 代价 |
|---|---|---|---|
| A：开放描述 + 云端模型理解 | 端侧保留丰富 Caption；云端将结果交给模型继续理解 | 能识别预先没有定义的内容，例如“古典建筑”等长尾美景，发挥视觉模型能力 | 持续模型调用带来成本和并发压力；链路增加推理时延；量产容量尚未测算 |
| B：有限标签 + 云端规则读取 | 双方预先约定有限标签，例如海、沙漠、森林、日落；视觉整包上传，云端按字段或规则读取 | 处理确定、成本低、容易控制时延，适合高频量产任务 | 必须提前定义标签；标签外信息无法直接触发；视觉模型的开放识别能力被限制 |

丁彬和王泽民确认两条路线技术上都能走，但应由内审/周会结合成本、资源和体验进行决策。

### 3.4 对时延的讨论

- 视觉侧称结果上传周期较快：舱外最快 3 秒一次，舱内 5 秒一次。
- 王泽民担心完整链路还包括数据中心、主动服务判断、赵益红侧的处理以及 DT，累加后会错过“转瞬即逝”的景色；当前纯语音 Query 的 DT 主链路已经约 5–6 秒。
- 丁彬判断新增链路最多约 10 秒。

以上都是会议中的口头判断，不是实测结论。内审不能用“3 秒上报”代替“用户 3 秒内收到服务”，需要把每一段耗时拆开实测。

## 4. 为什么会议会落到“成本—体验”决策

这不是单一模块能独立优化的问题。

- 视觉侧输出越开放，能覆盖的长尾场景越多，但下游理解越依赖模型。
- 主动服务要长期监听，模型调用不是一次性成本，而是“车辆数 × 开启任务数 × 轮询频率 × 单次推理成本”。
- 美景类场景有很强的时效性。系统识别对了但提醒晚了，用户已经驶离景点，产品结果仍然是失败。
- 标签收得太窄会漏掉长尾内容；标签放得太宽，规则和运营成本又会上升。

所以内审真正要确定的是产品取舍和工程边界，而不是只确认“链路能通”。

## 5. 建议内审主推的方案

建议首期采用“结构化基础标签 + 原始丰富描述保留 + 候选事件后再使用大模型”的分层方案：

1. 视觉侧每个周期只计算一次环境事实，输出结构化字段，如 `scene_labels`、`confidence`、`timestamp`、`ttl`、`schema_version`，同时保留原始 Caption 供 DT 或后续复杂场景使用。
2. 端状态/数据中心保存最新事实。多个主动服务任务订阅同一份状态，不要让十个任务各自重复调用模型解析同一帧结果。
3. 高频、强时效的 P0 场景先用有限标签和规则筛选。只有候选事件成立、标签置信度不足或命中长尾场景时，才调用一次云端模型复核。
4. Trigger 只负责判断条件并发出业务事件；后续推荐、卡片/TTS、用户确认、车辆动作、结果回写仍需各自 owner 明确，不应把“发出事件”当成用户闭环完成。
5. 对每类场景设置有效期、去重和冷却。例如“发现日落”超过 10 秒即作废；同一景色短时间内只提醒一次。

这套方案的核心不是简单折中，而是把昂贵模型从“持续轮询每个任务”改成“有候选事件时按需调用”。

## 6. 内审必须讨论并拍板的内容

| 内审问题 | 为什么必须问 | 会后需要留下的明确结果 |
|---|---|---|
| 首期走路线 A、路线 B，还是分层方案 | 会议只确认两种都可行，没有选型 | 一条主路线、适用场景、降级路线和决策人 |
| 首期支持哪些视觉场景和标签 | 标签范围直接决定体验上限和开发成本 | P0 场景清单、标签枚举、明确不支持项 |
| “美景”结果是结构化字段还是 Caption 文本 | 决定云端能否直接读取，以及谁开发解析能力 | JSON Schema、示例报文、字段类型、版本策略 |
| 谁负责云端解析/状态标准化 | 会议只说“之前有一个模块”，没有确认正式 owner | 模块名、开发 owner、调用方、接口时间表 |
| 多任务如何复用同一视觉结果 | 若每个任务独立解析，资源会随任务数线性放大 | 一次感知、多任务订阅的架构说明，或说明为何不能复用 |
| 量产资源账是否成立 | “成本高”“并发有限”目前没有数字 | 单车调用次数、峰值 QPS、并发上限、单次/单车成本和车型规模 |
| 端到端时延目标是什么 | 3 秒/5 秒只是视觉采样周期，不是用户体验时延 | 各阶段 P50/P95、总 SLA、超时后的处理方式 |
| 识别质量如何验收 | 有限标签会漏识别，开放描述可能误识别 | 准确率、召回率、误触率、标签外比例及测试集 |
| 过期、重复、低置信度和网络异常怎么处理 | 主动服务错时或重复提醒会直接打扰用户 | TTL、置信度阈值、去重/冷却、降级和重试规则 |
| 用户闭环由谁完成 | 视觉识别成功不等于主动服务成功 | 卡片/TTS、确认、动作、结果回写、任务状态的逐段 owner |

## 7. 会上可以直接这样发言

### 开场定调

“我先确认一下，今天需要评审的不是视觉能不能识别，而是量产主动服务怎样消费视觉结果。现在两条链路都能通，但成本、时延和开放能力不同。我希望今天至少拍板首期路线、数据协议、性能门槛和各段 owner。”

### 追问数据协议

“这里说的有限标签，最终是 JSON 里的独立枚举字段，还是仍然写在 Caption 字符串里？如果是独立字段，主动服务应当直接按字段消费；如果仍要做文本规则解析，协议稳定性和解析 owner 需要在今天确认。”

### 追问成本和并发

“目前只知道静态任务需要持续运行，但还没有量化。能否按单车同时开启 10 个视觉任务、舱外 3 秒一次，算出一天的请求量、峰值并发和模型成本？没有这组数，我们无法判断开放模型方案到底是不可接受，还是可以通过共享结果和事件门控解决。”

### 追问体验

“美景是强时效场景。视觉 3 秒上报不代表用户 3 秒收到提醒。请把视觉、上传、状态中心、Trigger、Advisor/业务处理、DT 和展示逐段列出 P95；如果总时延超过景色有效期，这条链路即使识别正确也不算成功。”

### 提出建议

“我建议首期不要二选一做死。P0 场景使用结构化标签和规则，保留 Caption 给 DT；只有候选事件出现或置信度不足时再调云端模型。这样一份视觉结果能被多个任务复用，也能把模型调用从持续轮询变成按事件调用。”

### 收口

“会后我需要四项结论：首期方案、P0 标签表、接口 owner 和量产验收指标。没有这四项，‘链路聊通’还不能进入排期和验收。”

## 9. 会议已确认与未确认

### 已确认

- 视觉结果可以作为 JSON 整包上传云端。
- DT 可以把整包结果放进 Context，由模型直接使用。
- 不使用云端模型时，可以通过有限标签和规则消费视觉结果。
- 开放模型方案与有限标签方案技术上都可走。
- 舱外最快周期约 3 秒，舱内约 5 秒。
- 方案将提交内审，由更高层决策选型。

### 未确认

- 最终选择哪条路线。
- 首期标签和场景范围。
- 云端解析模块及正式 owner。
- 李鑫侧目前是纯透传还是具备部分专用解析。
- 全链路真实时延、量产并发和成本。
- 识别准确率、误触率、过期/重复处理方式。
- 每段用户闭环的责任人和交付时间。
