端状态 2.0 信号管理技术方案
一、需求背景
端状态 2.0 的信号管理部分要解决两个问题：
当前不同渠道的端状态配置用的不同的Excel表格，多人都能改容易混乱，多渠道定义存在大量的重复定义；
解法：把多项目渠道的端状态信号从离线表格维护升级为可编辑、可验证、可发版的后台能力，提高维护管理、发布验证的效率；
开发依赖该excel跑脚本更新代码的信号定义，整体效率低下
解法：编辑修改协议后通过验证流程自动生成idl文件打overpass包，原先下游服务需要根据协议从端状态数据的map[string]string中取值，现在可以直接对应的端状态对象属性里取值，更简单高效；
二、目标与非目标
2.1 目标
建立统一的端状态信号管理中心：将信号 ID、名称、描述、数据类型、字段层级、单位 / 枚举等信息沉淀为协议元数据，统一承载通用信号与项目定制信号的定义、维护和检索。
支持多项目 / 多渠道的差异化配置：通用信号可按字段标记生效渠道，项目定制信号通过项目 / 渠道维度隔离，减少下游消费方对不同车企、不同项目取值差异的兼容成本。
完整表达结构化端状态：协议元数据支持 int、bool、float、string、struct、map 等类型，并支持 struct / map 的多层嵌套，使复杂端状态能够在管理后台可视化展开、编辑和追踪。
建立发布单化的信号变更机制：项目维度的端状态调整统一进入发布单管理，支持草稿态持续新增 / 修改 / 删除待发布数据，已发布基线不被直接修改，并限制单项目同一时间仅存在一个进行中的发布单。
形成自动化验证闭环：管理后台点击验证后，基于“已发布基线 + 待发布变更”生成 Thrift / IDL，自动完成 Thrift 校验、Git 分支提交、Overpass 打包和协议包验证；任一环节失败均回退草稿并展示失败原因，验证通过后再允许发布写回已发布数据。
2.2 非目标
不改变车企侧原始信号的产生方式；源侧差异由网关或 aidv 转换层吸收；
不在端状态微服务内保留 v1 适配器；只接受v2数据，由aidv做适配；
用top鉴权作权限管理，本期不实现复杂审批流，只保留操作人记录；
本期信号管理的技术方案评审不考虑端状态数据的上报查询等流程；
三、数据链路
管理端链路按「Web 页面 → HTTP 接口 → aidv → RPC 接口 → 端状态微服务 → MySQL / Redis」组织。Web 侧做页面交互和参数提交，aidv 负责鉴权、转发，端状态微服务负责元数据持久化、发布快照、上报校验与缓存刷新。

五、管理页面草图
5.1 协议元数据管理
协议元数据管理页面调整为列表页：每行展示信号 ID、名称、描述、类型、生效渠道与操作；生效渠道展示该信号被引用的渠道，例如 seres、saic-dna。顶部仅保留系统、子系统筛选和搜索 / 新增入口；基础类型信号不可展开，struct / map 信号点击行首箭头后，在当前行下方展开多行字段定义，仅叶子字段展示生效渠道，字段层级、缩进和类型展示方式参考接口 API 管理里的 Request Body 定义。

5.2 项目配置管理&发版管理
页面分为发布单中的元数据和已发布元数据两部分。发布单区域头部展示版本号、状态、上次失败原因、发布操作和新增待发布元数据；操作新增待发布元数据时让用户基于信号元数据做勾选，已发版的字段不支持删除，只允许新增。已发布区域展示当前线上已生效的基线元数据。该页面不展示生效渠道列（页面入口已选当前项目渠道），重点对比发布单版本与线上基线。

六、核心流程设计

6.1 协议元数据管理
元数据维护分为元数据信号编辑和元数据字段编辑两类入口。新增信号时先创建信号 ID、名称、描述、类型等基础信息，并进行参数命名规范校验，校验 signal_id、字段名等是否符合统一命名规则；当类型为 struct / map 时，可继续新增字段节点并补齐字段名、字段类型、说明、枚举、单位等约束。删除规则按生效渠道判断：已有生效渠道的信号或字段不支持删除，避免破坏线上项目引用；没有生效渠道的信号或字段支持删除，草稿态配置也算有生效渠道不支持删除，不影响验证中或已发布的数据。

6.2 项目配置&发版管理
发版管理以发布单为载体承接待发布元数据。新增发布单时系统自动生成发布单版本；从发布单入口点击新增待发布元数据后弹窗让用户从元数据列表中选择信号 ID，页面展示选中信号的数据结构并允许在发布单内编辑。
草稿：支持不断新增、修改、删除草稿中的待发布元数据；已发布元数据不支持修改。草稿态可操作验证和废弃。
验证中：不支持新增、修改、删除，只能操作回退草稿、发布和废弃。用发版中的协议合并覆盖已发版协议生成用于本次验证的协议，以信号id为key去覆盖。
发布：点击发布后，发布单中的待发布元数据合并到已发布元数据中，成为新的线上基线。

6.3 验证和发版
验证
管理后台点击验证后，元数据服务先合并待发布数据和已发版数据，生成本次验证用的 Thrift 文件并执行校验；Thrift 校验失败时，发布单退回草稿并展示失败原因。Thrift 校验通过后弹窗展示，研发拷贝Thrift文件操作overpass打包并发布验证：
发版
验证通过后，发布单进入可发布态，用户点击发布时再将待发布数据写回已发布数据，形成新的已发布数据。overpass自动流程本期先不做；

7.2 signal_schema_node 信号节点表

system、sub_system、keyword、page、page_size

signal_id

signal_id、name、desc、value_type、owner

更新信号

PUT /api/metadata/signals/{signal_id}

name、desc、status、extra_schema

删除信号

DELETE /api/metadata/signals/{signal_id}

signal_id

仅无生效渠道时允许删除；已有生效渠道返回不可删除原因。
