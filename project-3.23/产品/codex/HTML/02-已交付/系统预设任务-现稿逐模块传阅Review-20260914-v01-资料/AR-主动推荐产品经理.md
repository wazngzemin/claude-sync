# 主动推荐产品经理独立 review

已阅读 source.txt 全文及白底图 2、图 5。以下只评新稿的主动推荐交接。新稿已明确儿童锁、充电口盖、后视镜加热属于云端任务，不再以任务归属未定提问题；DT、Director、Planner 的名称需对齐，但不能据图中分列就断言它们是两个实际组件。以下补文均是供会签的建议规则，不代表已确认的现网能力。

## AR-1｜P0：充电任务专图与总链路采用了不同的交接和执行方式

- 位置：正文 0057–0063、0425–0432、0473–0481；图 2「Cloud Trigger→系统预设任务业务→主动推荐/DT/VQA」；图 5「Advice→Director调用VQ→Director调用卡片→Director调用车控」及底部第二次正反馈开盖。
- 产品会问：我接到的是待判断的业务事件，还是可直接执行的 Query？设备识别成功后，是谁把建议交给原业务？充电任务到底以总时序还是专图实现？
- 缺口证据：图 2 明确由原业务请求识别、接收结果、注册卡片并在确认后请求端执行；图 5 省略原业务，并写 Director 调卡、调车控，随后又出现 VUI 正反馈开盖。正文 0427–0428 仍写 Trigger 发送 Query 并调用 DT，与 0058 的 Trigger 只生成业务事件没有对齐。图 5 不能直接作为同一新版链路的实现依据。
- 影响：各方可能分别实现识别后的直接拉卡和原业务拉卡，产生重复推荐；图 5 的两次开盖位置也无法判断是重复绘制还是两个动作入口。
- 可补正文：本期充电任务以图 2 的责任顺序为准。Cloud Trigger 将一次命中的业务事件交给系统预设任务原业务；原业务发起充电设备判断请求，主动推荐及识别能力只返回本次识别结论与建议。识别请求不表达用户同意，也不授权开盖。原业务接收有效建议后注册询问卡，收到有效确认后才请求端侧复核和执行。图 5 按此顺序改画，开盖只保留一个业务执行入口。文中 DT、Director、Planner 的对应关系在术语表统一确认。
- 需谁确认：系统预设任务原业务负责人、主动推荐负责人、Planner/Director 能力负责人、端侧执行负责人。当前材料没有个人姓名，不能指定人。
- 不能杜撰：谁是实际接口调用方、DT 是否就是 Director/Planner、当前是否已有重复执行、旧链路是否必然只能模拟 Query。

## AR-2｜P1：静态 Advisor 的交互等级没有落实到本期充电任务，确认时机仍有冲突

- 位置：正文 0024、0042、0057–0061、0479–0481；图 2「结果且建议仍有效→注册并拉起卡片」；图 5 识别之后推荐开盖。
- 产品会问：充电任务命中后先静默识别，还是先打扰用户？静态 Advisor 配什么交互等级、是否播 TTS、是否需要回复？一次任务用户会不会被询问两次？
- 缺口证据：全文要求填写交互等级，但没有充电任务具体交互模式和等级映射。0042 与两图指向识别成功后询问，0480 却仍允许 D-09 决定在 DT 前或后确认；D-09 的具体决策表在所读正文中不存在。用户开启长期任务与同意本次开盖也没有在这一分支明确分开。
- 影响：可能把设备检查提示播给用户，或先问一次、识别后再问一次；也可能把前置确认直接延伸为识别后任意时刻的执行授权。
- 可补正文：充电任务推荐采用先静默识别、再询问开盖的顺序。识别结果明确且仍有效时，原业务发起一次需要用户确认的开盖询问；只有卡片实际展示后才按所选交互等级播报和承接回复。任务开启仅表示允许该服务运行，不代替本次开盖确认。静态 Advisor 的等级枚举、TTS 策略、卡片排队及最长等待时间由主动推荐与 VUI 会签后填写；未识别到设备或无法判断时不生成开盖询问。删除或落实 D-09 的前后确认二选一。
- 需谁确认：主动推荐产品、VUI/交互产品、充电任务原业务产品；如保留识别前确认，还需 Planner/识别能力方共同确定其具体确认对象。
- 不能杜撰：交互等级枚举值、语音播报优先级、等待秒数、前置识别是否需要单独用户授权、D-09 已有结论。

## AR-3｜P0：静态 Advisor 点击兼容路线缺少可验收的 Query 语义与回调约束

- 位置：正文 0061–0063、0077–0078；图 2 点击分支仅绘「返回本次被选选择→原业务」。
- 产品会问：按钮点下去模拟的 Query 究竟是什么？Planner 收到后返回本次“确认”给原业务，还是作为新车控请求直接开盖？旧询问已经过期时，模拟 Query 还能生效吗？
- 缺口证据：0061 允许直接回原业务或显式模拟 Query，0078 指定静态 Advisor 按原文模拟 Query 到 Planner，但没有给出 Query 样例、需携带的本次询问关联、结果返回方。图 2 未覆盖该兼容路线。0062 规定 DT 只回语义结果，但没有明确同样约束模拟 Query 入口。
- 影响：自然语言“打开充电口盖”可能被处理成新的独立请求，从而绕过当前卡片关联；即使没有双执行，也无法验收取消、超时后的迟到点击应如何处理。
- 可补正文：同一卡片实例只能选定一种点击路线。直接回调时，由 VUI 返回本次询问和所选按钮；模拟 Query 时，表达“确认当前这一次开盖建议”，并保留本次任务、事件和询问关联，Planner 返回选择结果给原业务，由原业务统一校验询问仍有效、尚未处理后请求执行。模拟 Query 不作为独立新车控意图执行。配置中补齐 Query 示例、关联方式与返回业务；若旧接口无法保留关联并回到原业务，该兼容方式应列为待补能力，不可按已闭环验收。
- 需谁确认：静态 Advisor/主动推荐接口负责人、Planner 能力负责人、VUI 点击接入负责人、原业务负责人。
- 不能杜撰：当前 Query 的真实文本及接口字段名、现网 Planner 已支持结构化确认返回、旧接口是否已支持询问关联。

## AR-4｜P1：已写结果有效与失败结束，但尚不能区分静默结束、展示失败和用户拒绝

- 位置：正文 0027、0059–0063、0071–0082、0429–0440、0476–0487；图 2「不满足有效的识别结果」「未实际展示或提前失效」；图 5「是充电桩？否→结束」。
- 产品会问：我等待识别十几秒才拿到 FOUND，还能推吗？卡片排队期间驶离了，谁撤掉？识别失败、排队失败和用户拒绝会不会都算负反馈，导致以后不推荐？
- 缺口证据：稿中已有 FOUND/NOT_FOUND/UNKNOWN/ERROR、执行前过期复核及图 2 失败结束，不能说完全没有失败分支。但没有定义结果新鲜度和卡片排队有效性的判定口径；0439–0440 将拒绝、关闭、忽略、超时合并频控，未区分是否真正展示、技术失败与明确拒绝；0072 的拒绝后频次仍待会签。图 5 只有二值判断，未对齐正文的无法判断和失败。
- 影响：推荐可能展示已失效场景；若用同一负反馈口径，技术失败会污染用户偏好，用户明确拒绝也可能很快被新停车事件再次打扰。
- 可补正文：原业务对识别返回、卡片实际展示和执行前分别检查本次场景是否仍有效；识别结果需能对应本次事件及观测时间，有效窗口由任务规格会签。NOT_FOUND、UNKNOWN、ERROR、识别超时及未展示即失效分别记录原因，结束本次且不计作用户拒绝。已展示后的明确拒绝、主动关闭、无响应超时分别记录；频控按事件去重与用户打扰策略配置，具体期限会签后填写。卡片排队期间条件失效时由原业务撤销，VUI 回报撤销/展示状态并清理上下文；用户已确认后的执行失败或状态未知，由原业务反馈准确结果，不宣称成功。
- 需谁确认：主动推荐产品、原业务产品、识别能力负责人、VUI 生命周期负责人、端状态/车控结果负责人。
- 不能杜撰：有效时长、冷却周期、重试次数、VUI 撤销接口现状、已存在何种推荐偏好学习或负反馈模型。
