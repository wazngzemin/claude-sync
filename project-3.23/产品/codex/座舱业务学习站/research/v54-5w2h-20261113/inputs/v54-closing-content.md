## 16. AI Launcher：用户从哪里发现、打开豆包的能力

### 配图说明
新图《桌面入口怎样接上业务》，共 7 个节点：①可展示的问候、引导、场景、技能 → ②Launcher 桌面 → ③用户点入口；③分到④直接业务接口或⑤模拟用户请求 → Planner；④⑤都指向⑥实际业务结果；⑥指向⑦界面更新与结果上报。灰色表示用户与界面，紫色表示展示内容，青色表示业务处理；③到④⑤使用虚线，注明“依具体入口协议选择，不代表所有 Launcher 已接这两路”。这是业务边界示意，不新增一套 Launcher 接口事实。[V16-F01～F04]

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | AI Launcher 是车机桌面上的智能服务展示与操作入口，帮助用户知道豆包能做什么。 |
| Why 为什么要 | 用户没有说出需求时，也需要看到可用的能力和适合当前场景的建议。 |
| Who 谁负责 | 产品定义展示与点击行为，桌面展示内容，具体业务接口或 Planner 完成后续处理。 |
| When 什么时候用 | 用户浏览桌面、看推荐或点技能时会经过它，直接说话并不要求先打开它。 |
| Where 在链路哪里 | 它在用户看得见的界面层，与语音入口、结果卡片相连。 |
| How 怎么工作 | 先展示可用内容，再按入口约定发起业务，最后核对真实结果与页面是否一致。 |
| How much 有多少、多有效 | 功能范围、刷新规则和展示数量要按车型版本核对，现有沟通稿不能代表最终全量交付。 |

### 第二步：七个问题逐条讲透

**1. What：它是什么，容易和什么混？**
Launcher 原意是启动入口。在本项目里，它承载桌面的引导语、问候语、任务、推荐场景和技能展示；“技能”就是用户可以使用的能力入口，不等于一个新的推理模型。[V16-F01]

| 名字 | 做什么 | 在主例中的位置 |
|---|---|---|
| AI Launcher | 展示能力、推荐和交互入口 | 用户可能从桌面发现出行能力 |
| Planner／Director | 根据请求与上下文判断下一步做什么 | 判断应先找昨天的游泳馆，再找附近餐厅 |
| 结果卡片／导航页面 | 呈现本轮查找或导航的结果 | 给用户看餐厅候选项和执行结果 |

不要因为都能显示卡片，就把桌面推荐和本轮语音结果当成同一个页面。产品 OnePage 分别列出了 Launcher 与导航、舒适、媒体等页面。[V16-F02]

**2. Why：为什么需要它？**
用户未必知道可以让豆包帮忙找餐厅，也未必知道应该怎样说。桌面的引导和能力入口可以降低发现成本。反过来，如果入口显示“找附近餐厅”，点完却没有反馈，用户会觉得整个助手不可用。这个后果是教学推演；不能据此宣称发生过该条真实故障。HMI（人机界面）方案把首页定位为直接与用户互动的界面，但文件自己注明“非最终全量文档”。[V16-F03]

**3. Who：谁提供、谁负责？**
这里至少有展示与业务两个责任面：展示侧要让用户看懂、点得到；业务侧要接到点击意图并真正完成服务。Planner 是否参与，由这一个入口的协议决定。已有 VUI（语音交互界面）PRD 把卡片点击分成直接执行、模拟用户请求、事件上报等路线；它能证明“点击不止一种路线”，不能证明每个 Launcher 入口都已经采用其中哪一路。[V16-F04]

**4. When：什么时候进入？**
主例用户直接开口说话，可以沿语音链路进入 Planner，不必先打开 Launcher。用户从桌面点服务，则要检查点击后发起的是接口调用、模拟请求，还是只打开另一个页面。HMI 沟通稿有首页、全局技能页、下拉刷新和图标配置，但这些设计存在多个修改阶段，刷新频率和当前实车范围待确认。[V16-F05、F06]

**5. Where：它在链路哪里？**
Launcher 位于展示与交互入口层。它收到的是可展示的内容，向后交出的是由具体入口定义的操作。识别用户声音、判断是不是对豆包说话、找记忆，属于前面讲过的其他模块。不要把“桌面推荐出现了”当成“Planner 已经执行服务”。

**6. How：怎样排查“看得见，点了没用”？**
1. 留下车型、版本、当时的卡片内容和用户点的位置，先确认展示的是哪个入口。
2. 核对该入口约定的行为：打开页面、直接业务调用，还是模拟请求；不要靠按钮名字猜。
3. 查点击事件有没有发出、接收方有没有收到，参数是否指向用户看到的服务。
4. 若经过 Planner，再查收到的请求、选中的工具与返回结果；若直接执行，查对应业务接口。
5. 看实际业务状态和页面有没有更新；只有页面变了、业务没变，也不能验收通过。

这是一组产品排查建议，不是声称存在一套已上线的统一 Launcher 日志字段。[V16-F06]

**7. How much：范围与效果怎样判断？**
“方案写了任务”与“某一期真的交付任务”是两件事。可读的产品定义包含任务，但具体车型版本的任务入口、能力清单及推荐质量，需要当前版本证据；不要把设计文档当成上线清单。本单元不编造统一的卡片数量或刷新间隔。[V16-F01、F03、F06]

### 第三步：放回主例
主驾直接说“带我去昨天那家游泳馆……附近的餐厅”，Launcher 不负责补全“昨天那家”。Planner 找到地点并检索餐厅后，结果应由对应卡片或导航页面呈现。若用户随后回到桌面点另一个出行入口，需要按该入口协议重新判断它携带了什么信息；不能默认它继承了刚才所有对话。

### 第四步：讲给别人听（30 秒）
> AI Launcher 是用户在车机桌面发现和打开豆包服务的入口。它可以展示问候、引导、推荐和技能，但不会自己识别声音或推理“昨天那家”是谁。点入口后怎么执行，要看具体协议。验收要连着看展示、点击、业务结果和页面更新，不能看到推荐卡片就说服务已经做成了。

### 查阅区（不用背，用到时再查）
产品范围见《AI汽车产品 one page》；页面设计见《HMI 交互方案—双方沟通文档》，该文档明确非最终全量；点击路径的边界参考《VUI主交互需求》“卡片链路”。本单元全部来源与行号见 V16-F01～F06。**待确认**：当前车型实际开放的 Launcher 能力、每个入口的执行协议、刷新和排序策略、任务入口的最终位置。

## 17. 回写：车上做过的事，云端怎样接得上

### 配图说明
新图《本地完成之后，下一句怎样接住》，共 7 个节点：①本轮请求 → ②端云采纳结果 → ③本地实际执行／拒识结果 → ④整理请求、回答、执行观察 → ⑤同步接口 → ⑥云端对应上下文 → ⑦下一轮读取。③到④注明“执行了什么、成功没有”；⑥分两条标签“可用于任务承接的信息”“仅用于情景判断的信息”，不新增节点。青色表示处理，紫色表示记录，灰色表示用户请求；⑤失败用橙色虚线标“补同步是否实现需按版本核验”。[V17-F01～F05]

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 回写是把本地处理过的请求和结果同步到云端记录，供后续对话接着理解。 |
| Why 为什么要 | 否则车上刚做完一件事，云端接到“就选这个”时却不知道“这个”是什么。 |
| Who 谁负责 | 本地链路整理结果并上报，云端按信息类别接收进相应上下文。 |
| When 什么时候做 | 本地处理完成、端云融合确定采用哪份结果之后，按同步规则回写。 |
| Where 在链路哪里 | 它位于本地处理结束到下一轮上下文读取之间。 |
| How 怎么工作 | 把同一轮的身份、文字、采纳结果和执行信息对齐，再核对云端收到与下轮读到。 |
| How much 写多少、留多久 | 同步字段和进入哪类上下文有规则，保留时长遵循对应上下文策略，不能把回写理解为永久记忆。 |

### 第二步：七个问题逐条讲透

**1. What：回写与什么容易混？**
回写不是让模型重做一次本地操作，而是让云端知道“刚才已经发生什么”。OnePager 描述本地命中的可见即可说或简单车控，把 Query（本轮请求）、Answer（回答）、Observation（执行观察或结果）通过 `context/sync` 同步进历史。[V17-F01]

| 名字 | 写的是什么 | 不能据此推出什么 |
|---|---|---|
| 回写历史／上下文 | 刚才的请求、处理和结果 | 不能推出已经形成长期偏好 |
| 工具反馈 | 某次工具调用返回的执行信息 | 不能推出所有后续读者都已收到 |
| 长期记忆 | 经过提取并按记忆规则保存的信息 | 不能用“同步接口成功”证明已生成 |

**2. Why：缺了会怎样？**
假设用户在本地页面选择了餐厅，随后对豆包说“开始导航”。如果云端没收到刚才选了哪一家，就可能重复问、选错对象或认为没有候选项。这是主例的教学推演。可见即可说框架明确要求这类内容进入对话历史，并标记来自模拟点击，目的就是防止下一轮推理出错。[V17-F02]

**3. Who：谁写，谁读？**
本地把本轮结果整理后交给云端，云端再按类别放入相应上下文。这里最容易漏掉一条边界：本地拒识、未唤醒的对话也有同步要求，但本地 PRD 指定它们在云端进入“情景上下文”，不进入 DT 的上下文。因此，“上报成功”和“Planner 下一轮必然看到”不是同义句。[V17-F03]

**4. When：究竟哪份结果要回写？**
本地 PRD 同时保留了旧的“无论本地输出什么都同步”和后续修改：“根据端云融合的结果，将本地被采纳的结果同步给云端”。读文档时应把前者标旧逻辑，不能把两段合成当前规则。本地拒识／不唤醒的同步是另有说明的分支。[V17-F03、F04]

**5. Where：云端写到哪里？**
先问写给谁用，再问保存在哪。用于下一轮承接的记录，与辅助判断车内聊天的情景信息，读者不同。回写这一步不承诺永久保存，也不自动把内容存成个人偏好。其保留和清空时间应回到第 13 单元的对应记忆或上下文规则核对；本地同步段落没有给出独立的永久保存期限。[V17-F07]

**6. How：怎样查“车上做过，云端不知道”？**
1. 确认本轮最终采纳的是本地结果还是云端结果，避免把未采用的候选当成执行事实。
2. 查本地是否实际执行，以及执行结果是否与播报一致。
3. 用请求编号和会话编号对齐文字、音区、结果类型与时间，确认上报的是同一轮。[V17-F05]
4. 看同步接口有没有发、有没有成功、云端写到了哪个上下文；只看到发包不算已接收。
5. 用下一句省略对象的请求验收，比如“就去这家”，看系统是否引用了正确记录。
6. 若中途断网，再单独测恢复后的补同步。网络专项文档把“失败不重试”列为当时现状，把恢复后重新同步列为预期，不能直接写成已经可靠补齐。[V17-F06]

**7. How much：产品经理需要盯哪些信息？**
不必背接口结构，但应会核对本轮是谁、在哪个座位、说了什么、采用哪份理解、调用什么、结果如何。本地 PRD 列了请求与会话编号、音区、端云文字、最终结果类型、函数名及参数、回答和时间；这些字段用于对齐证据，不代表每条拒识记录都执行了函数。[V17-F05]

### 第三步：放回主例
“带我去昨天那家游泳馆……附近的餐厅”找到候选后，用户可能通过页面选一家。如果这一步本地完成，需要把选择和结果接到后续上下文；用户再说“开始导航”，Planner 才有机会知道目标。即便回写成功，也要看实际导航是否启动，不能用“记住了”替代“做到了”。

### 第四步：讲给别人听（30 秒）
> 回写让云端知道车上刚才做过什么，好接住下一句。关键是写最终采用的结果，并带上请求、位置、文字和执行信息。被拒识的聊天也可能上报，但它进入的上下文不一定给 Planner 读。验收要看本地做成、云端收到、下一轮读对；断网补同步还要单独核对版本。

### 查阅区（不用背，用到时再查）
`context/sync` 是 OnePager 的同步接口写法；本地 PRD 的同步字段原文及旧／新规则见 V17-F01、F03～F05。网络专项的“现状／预期”见 V17-F06。**待确认**：当前车型的断网补同步是否上线、失败重试和重复记录消除规则、每类同步记录的实际保留期限。[V17-F07]

## 18. TTS 播报与打断恢复：说出来，还要说得合时宜

### 配图说明
新图《停播之后，不是统一从头再说》，共 8 个节点：①Planner 可播文本 → ②TTS 合成 → ③车端拉取并播放 → ④用户插话、触发停播 → ⑤记录已播／未播内容 → ⑥最终判断新话要不要接；⑥分支到⑦拒识后以事件触发恢复、⑧接话后由 Planner 融合新话与未播内容。青色为处理，灰色为播放，紫色为上下文，橙色为“某些打断原因不恢复”的旁注；⑦⑧均用虚线回到①，注明“是否恢复受打断原因与版本规则约束”。[V18-F01～F06]

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | TTS（文本转语音）把准备说的文字合成声音，打断恢复决定停播后哪些信息还需要说。 |
| Why 为什么要 | 用户希望随时插话，也不希望一句乘客聊天就让重要回答永久消失。 |
| Who 谁负责 | 云端组织和合成可播内容，车端播放与停播，Planner 结合新请求处理仍有价值的信息。 |
| When 什么时候用 | 有内容要播报时进入 TTS；播报中被打断，且规则允许恢复时才进入恢复分支。 |
| Where 在链路哪里 | 它在回答输出到用户耳朵之间，并把播放进度带回后续理解。 |
| How 怎么工作 | 先确认停播原因和已播位置，再看最终拒识与新请求，决定恢复或重新组织话语。 |
| How much 恢复多少 | 目标是补有价值的未播信息而不重复，不能承诺每次打断都恢复或全部从头重播。 |

### 第二步：七个问题逐条讲透

**1. What：这些东西不是一回事。**
TTS 的输入是可播报文字，输出是音频。OnePager 描述云端合成并下发音频流标识，车端依据标识拉取声音并播放。因此“文字出来了”“声音合成了”“用户听到了”是三个可分别失败的环节。[V18-F01]

| 名字 | 做什么 | 错了用户看到／听到什么 |
|---|---|---|
| NLG（自然语言生成） | 组织回答文字 | 回答内容不对，或屏幕文案不合适 |
| TTS（文本转语音） | 把文字变为声音 | 文字正确但声音没来、发音不对 |
| 播放与停播 | 决定何时放音、何时停止 | 声音继续盖住用户说话，或突然断掉 |
| 打断恢复 | 决定停播后怎样接着说 | 重复整段、漏掉重要内容或不该说时又说 |

**2. Why：为什么停了还要再判断？**
流式阶段为了让用户及时插话，可能先停播；等整句话完整后，才发现乘客是在和别人聊天。此时继续新任务不合适，但丢掉原回答也可能影响体验。OnePager 为此分别定义了最终拒识后的恢复事件，以及未拒识时把新请求和未播内容交给 Planner 的路径。[V18-F02、F03]

**3. Who：各自负责什么？**
Planner 提供可说的内容，TTS 服务负责声音合成，车端负责真实播放。云端需要知道已经说到哪里、后面还有什么，才能组织恢复内容。这里说的“反馈播放进度”是恢复所需信息，不能仅凭云端合成完整音频就断言用户听完了。OnePager 的恢复示例明确包含“你已经说了”和“没说完的话”。[V18-F01、F03]

**4. When：什么时候恢复，什么时候不恢复？**
OnePager 的打断场景表把流式非拒识停播、云端未拒识、多人以“豆包”开头等列为可恢复场景；新播放替换、服务挂起、第三方停止、离线车控结果播报、进入静默态等列为不恢复。表中单人直接打断也标不恢复。因此“最终拒识就恢复”只能在允许恢复的打断流程里理解，不能覆盖所有停播原因。[V18-F04～F06]

**5. Where：恢复信息交到哪里？**
新话最终被拒识时，OnePager 通过 Event（描述发生了什么的事件）触发恢复；新话有效时，把它与上一条未播内容一起交给 Planner，生成自然且不重复的新回答。两条路线都不是播放器把旧音频无条件倒回开头。[V18-F02、F03]

**6. How：怎样查“被打断后不说了／重复说”？**
1. 查原回答文字是否生成、TTS 是否合成、车端是否真正开始播放，先定位断在哪。
2. 找到停播原因：用户插话、另一段音频抢占、第三方停止或进入静默，不能只看“停止”二字。
3. 对齐最后已经播到的位置与未播内容，防止把“已生成”误当“已听到”。
4. 查新话最终是拒识还是有效请求，以及本次打断是否允许恢复。
5. 看恢复事件或融合输入是否真的送到 Planner，再听新回答有没有重复、漏掉重点或沿用过期任务。
6. 同时验屏幕与声音。VUI PRD 写“打断后拒识，NLG 不恢复”，OnePager 写 TTS 恢复；前者处于上屏交互段，后者讲音频及新请求，不能未经核对把二者合并成一个规则。适用车型与版本待确认。[V18-F07]

**7. How much：恢复到什么程度才算好？**
产品验收的重点是用户还能不能接着办事：新要求已经改变目标时，旧回答可能不再有价值；只是被闲聊打断时，重要的未播内容可能仍值得补。具体是否恢复要服从该版本规则。本文不补造统一恢复时长、成功率或音色表现指标。

### 第三步：放回主例
用户说完“带我去昨天那家游泳馆……附近的餐厅”，豆包开始介绍候选。用户插话“要安静一点的”，这是新约束，应由 Planner 结合未播内容重新组织，不能机械补完旧名单。若插话其实是乘客对同伴说的“你把水递给我”，且该次停播允许恢复，则按最终拒识后的事件路径处理。两句都是教学例子，不是实测承诺。

### 第四步：讲给别人听（30 秒）
> TTS 把回答变成声音，车端负责实际播放。用户插话时可能先停播，完整理解后才决定接不接新话。允许恢复的场景里，如果只是乘客聊天，就通过事件处理旧回答；如果是新要求，就让 Planner 结合没说完的内容重新回答。恢复不是统一重播，必须看停播原因、已播位置和版本规则。
