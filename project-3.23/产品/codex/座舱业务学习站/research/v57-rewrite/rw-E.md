## 收尾　三分钟讲给别人听

下面这张图沿着同一段对话，把找餐厅、插话开座椅加热和接回“第二个”串起来。

<!-- figure:v56-journey -->

我设计这条链路，先想的是让用户自然说话，事情还能办对。主驾叫“豆包豆包”，说“带我去昨天那家游泳馆”，停一下，再补“附近的餐厅”。唤醒负责打开交互入口，免唤醒让他在开启范围内省去喊名字。声学前端先处理麦克风声音，减轻噪声和车机播报的回声，再交出适合识别的声音和说话座位。座位帮助理解“我的座椅”，身份帮助区分具体的人。

我让 ASR，也就是自动语音识别，把声音逐步写成字。在线识别在云端，离线识别在车上。过程文字还会改，最终文字才定稿。热词帮助写准地名，“昨天那家”则要查经历。VAD，也就是语音活动检测，接收发声和停顿，给出分段信号。我利用短停顿发预请求，提前判断、准备背景，同时继续听。**预请求只做准备，正式收尾后才提交完整请求。**补上“附近的餐厅”，目标已经变了，提前做的准备要跟着更新。

我把完整请求交给 Planner，也叫 Director。它负责读懂请求、安排动作。Context 就是这次交给它的上下文，包含对话、记忆和车辆状态等背景。我先让它找出“昨天那家”是哪家泳馆，已有背景不足就查用户记忆，查清再搜附近餐厅，仍不明确就追问。它交出动作列表，工具返回办理结果，它据此决定下一步。

我把记忆分层，是为了兼顾细节和处理成本。近期历史保留原话和列表，摘要保住较早的任务约束；短期情景整理当天经历，长期情景承接跨天经历，长期语义保存稳定事实和偏好，瞬时记忆保留最近事件的原始细节。乘员聊天也能按权限提供背景，助手保持安静，聊天本身不触发操作，一次表达也不会直接变成长期偏好。

豆包介绍餐厅时，主驾插话“帮我把副驾座椅加热打开”。我先让流式拒识读取过程文字和背景，决定是否停播、让用户说完；再让最终拒识读取完整文字，决定是否接下请求。**停播、接话和采用哪端结果，是三项决定。**固定说法规则和本地模型提供简单操作候选，复杂查询交云端。端云仲裁负责从两边结果中选定一份，避免重复执行；本地路径减少对网络的依赖，代价是支持范围有限，办不了就继续交云端。

我让车辆收到明确的副驾加热指令，再核对实际结果。采用本地结果后，还要回写请求、回答和执行观察，也就是把这次办事经过同步给云端。回答交给 TTS，也就是文本转语音，云端合成音频，车端拉取播放。我还要保留餐厅介绍实际播到哪里，才能自然接着说。

最后主驾说“第二个”，我让它接回用户实际看到的原餐厅列表，取出第二家的具体地点，再交导航执行。这样保留原列表要占用背景空间，却能避免选错店，也能避免把插话后的“第二个”当成加热第二档。出错时，我先沿声音、文字、接话判断、背景、工具和实际结果，找最早偏离的那一步。

### 最容易讲错的地方

- 唤醒打开交互入口，ASR 写出文字，最终接话判断接受请求，车辆或业务工具真正执行。
- 在线与离线说明识别在哪里运行，过程与最终说明识别走到哪一步，离线识别也能持续返回过程文字。
- 热词帮助写准说出的名字，“昨天那家”要靠经历和具体地点补齐。
- **软判停后的预请求只做准备**，补全后要重新检查准备结果是否适用。
- 流式停播、最终接话和端云采纳各管一步，本地不支持时要继续寻找办理路径。
- 历史、摘要和各层记忆保留的细节不同，回写执行结果也不会自动生成长期偏好。
- **“第二个”对应用户实际看到的原列表**，座椅插话和重新搜索都不应替换它。
- 回答生成、音频合成和用户听到各有进度，导航与车控是否成功要看实际执行结果。

这一段讲给别人听，可以这样说：我把整条链路分成听清、接话、理解、执行和让用户知道结果，每一步都交出下一步需要的东西。我宁可多保留一份原列表、多同步一次执行结果，也要让插话前后的任务接得上。遇到错误，我先找最早偏离用户意思的交接点，再查后面的影响。

| AI Launcher／车机智能桌面入口 | 展示引导、任务、推荐场景和技能，让用户发现能力并选择操作入口。 | 第十二段 |
| 入口协议 | 约定用户点击后交给谁、携带什么，以及打开页面、调用接口或提交请求的规则。 | 第十二段 |
| 模拟请求 | 将点击选择表达成供云端理解的一次用户请求，不需要用户再念出卡片文字。 | 第十二段 |
| VUI／Voice User Interface／语音用户界面 | 用户通过语音与系统交互的界面，包含卡片、上屏表现及相应操作。 | 第十二、十三段 |
| HMI／Human-Machine Interface／人机界面 | 用户在车机上查看内容、完成操作的界面。 | 第十二段 |
| NLG／Natural Language Generation／自然语言生成 | 将需要表达的内容组织成用户能理解的话。 | 第十三段 |
| TTS／Text-to-Speech／文本转语音 | 接收可播文字并合成音频，再交给车端播放。 | 第十三段 |
| talk_content | 提供给云端语音合成的待播文字。 | 第十三段 |
| 音频流标识 | 帮助车端找到本次合成音频流的标识。 | 第十三段 |
| 流式播放 | 车端陆续取得声音、陆续播放的方式。 | 第十三段 |
| last_talk_content | 带入上一条被打断播报的内容和位置，帮助重新组织后续回答。 | 第十三段 |
| SingleInterrupt | 单人且识别文字字数大于 2 时直接停播的一项特定停止原因。 | 第十三段 |
| 播报恢复 | 停止原因允许且新话最终拒识时，通过事件发起新请求，处理上一条未播完内容。 | 第十三段 |
| 回答融合 | 一起考虑有效新请求、未播完内容和实际结果，组织自然且不重复的新回答。 | 第十三段 |
