# 触发器配置平台改造：分章精细补充

> 合并说明：本文件按目标飞书既有八章提供增量正文，不替换整篇主稿，也不将主稿的原型版本 v10 降回 v08。以下截图来自此前可核实的 v08 原型，只用于解释字段和规则；与当前原型不一致的控件按正文要求收敛，不作为 v10 当前页面证明。技术方案中的字段与运行规则属于设计依据，不表示生产已全部上线。

## 补入第 1 章「需求背景」

### 本次为什么要改造

现有后台能配置场景、条件和动作，但新的业务不都是“一项状态满足就做一件事”。儿童锁要把共同前置、儿童与宠物两个替代分支、目标锁状态放在同一条逻辑里；闪念收到的可能是一句画面描述，而不是“有人睡觉=true”这样的结构化字段。若继续平铺条件，产品难以说明条件如何组合，研发也难以区分没有命中究竟是规则不成立、输入没有接通、模型无法判断，还是通知没有展示。

本次保留简单配置和原有列表、筛选、动作与执行策略，补齐三件事：**复杂判断能画出来，视觉输入能按真实能力配置，每次运行能分层查清楚。**不为每个场景单独建设一套后台，也不把 Trigger 扩成工具或车控编排平台。

闪念是本期新增的具体业务：使用已有视觉描述判断目标，满足后发一句固定文字。它需要补预配置描述监听、已有模型判断、普通通知动作及客户端接收展示，不能把已有动态任务能收到描述，直接当作预配置已经接通。固定正文不等于判断不用模型；一期复用已有模型，语义匹配、小模型降耗属于后续优化。

完成标准不是页面能点或保存成功，而是真实输入可用、规则可回读、目标环境采用正确配置，并能拿到判断、策略、动作发送及客户端实际反馈的证据。

## 补入第 2 章「产品定义」

### 一条场景的完整定义与职责边界

平台面向内部产品、业务、研发和测试。一条场景由“适用范围、启动与判断、动作、执行策略、运行证据”五部分组成，分别回答给谁用、何时检查和检查什么、满足后交什么、允许执行几次及多久再来、这次实际发生了什么。

| 概念 | 在本产品中的含义 | 不能混同的内容 |
| --- | --- | --- |
| 简单／Workflow | 判断内容的组织方式，前者用表单，后者用有依赖的节点 | 不是是否使用模型，也不是是否调用 DT |
| VLM 与 Caption | 视觉模型与它产出的画面文字描述 | 描述到达不等于业务条件已经成立 |
| 条件节点 | 比较已经接入的字段和值 | 不能虚构睡眠、宠物等布尔标签 |
| 推理节点 | 用本次已有描述判断目标是否达成 | 不临时取图，不调用 VQA，不生成通知正文 |
| Action 动作 | 图外共用出口，接收最终判断后的合法动作请求 | 不把卡片、确认、车控画进判断图 |
| 普通通知 | 闪念一期的固定正文出口，经 Frontier 下发 | 无标题、按钮、TTS，不进入 DT |
| 带卡建议 | 沿现有主动推荐链路提交建议 Query | 正式一期固定确认／取消，不开放自定义按钮 |

后台规则的启停、AI 总许可、某车某项任务开关和用户对本次建议的确认是不同状态。平台生效不替代车主开关，拒绝一次也不自动关闭长期任务。本次不重新指定端侧任务状态的持久化归属。

## 补入第 3 章「整体架构与链路」

### 视觉来源、启动与最终动作分开理解

【插图 D1：VLM 来源与使用边界】

| 视觉来源 | 进入业务的方式 | 本次使用边界 |
| --- | --- | --- |
| 系统预设用既有观察 | 从已经接入的端状态／Context 等读取对应值或描述 | 目录和接入方共同证明来源可用；预配置 Caption 监听需单独接通 |
| 用户动态观察任务 | TaskService 根据任务 ID 和目标转交专属结果 | 不将别的任务专属结果作为所有预配置规则的通用输入 |
| DT 按需调用 VQA | 下游 DT 发起新视觉问答，并接收结果 | 不作为 Trigger 判断节点，也不默认返回 Trigger 继续编排 |

“启动检查”与“条件满足”分开：挡位从非 P 变为 P 是启动变化，当前挡位为 P 是状态。一直上报 P 不应反复解释为刚停车；缺旧值不能编造变化成立。页面分别展示使用的输入和实际启动检查的输入，依赖清单不能冒充已注册的真实订阅。

【插图 D2：配置、校验、保存流程】

配置人员选范围与模式，填判断、动作和策略；完整校验通过后看摘要。Workflow 先注册不可变定义，再关联场景；仅定义注册成功不能显示整个场景保存成功。保存后回读配置，再按现有机制发布和验证车辆采用情况。修改已保存 Workflow 应复制新定义，旧规则替换及用户 OFF 保持一并落实。

运行时，条件／推理返回 PASS 满足、REJECT 明确不满足、UNKNOWN 无法判断。唯一真实终点给出最终判断；按技术设计整图收敛后，终点 PASS 再查共用策略与锁，之后才调用图外动作。UNKNOWN 不发动作，但要与明确不满足区分记录。

## 补入第 4 章「HTML 原型怎样设计、链路怎样搭」

### VLM 配置先选合法输入，再确定判断方法

【插图 D5：视觉配置选择逻辑】

渠道能力目录返回信号、字段、数据类型、枚举、比较符和接入状态，页面据此生成选择项。目录读取失败显示失败和重试；真实无数据显示暂无；待接入显示具体缺口。不能用演示字典掩盖线上无数据，也不能让配置人员手填不存在的信号编码绕过校验。

| 输入设计 | 配置方式 | 关键限制 |
| --- | --- | --- |
| 舱内低频 vlm_inside_001 | PassengerInfos 位置、性别、年龄类别可按设计目录做条件；其他文字走推理 | Position 设计仅等于；Gender、AgeRange 仅开放目录支持的等于／不等于／包含 |
| 舱内高频 vlm_inside_002 | 使用当前动作描述判断目标 | 不能把“正在睡觉”自行变成可选布尔字段 |
| 舱外 vlm_outside | 当前目录设计按描述推理使用 | 原始报文看似枚举，不等于前端已开放结构化比较 |

位置与年龄必须属于同一乘客。例如“后排有儿童”不能由主驾儿童的年龄加后排成人的位置拼接成立。Position 当前仅等于时，位置备选须通过合法等于组合表达；若服务无法保持对象关联，应阻止正式发布，不能直接提交原型中的 Position in。

推理配置至少包括合法输入、判断目标 goal 和业务边界说明 original_query。输入决定看哪份描述，目标决定判断什么。来源改变后标记目标需复核，清理不兼容字段与旧试跑结果；不无条件删除可复用人工文字。缺输入、过时、位置不明、超时或解析失败归 UNKNOWN；不能用“包含达成”把“未达成”误判为 PASS，也不新增无依据置信度滑杆。

### Workflow 搭建与汇合

【插图 D3：Workflow 三态与汇合】

有共同前置、替代分支或依赖关系时用 Workflow；单视觉目标仍可用简单模式。本期只提供条件和推理两类节点，不开放 DT、VQA、定时、等待、用户确认或车控节点。AND／OR 不能表达持续时长、多帧聚合或事件先后。

| 关系 | 判断问题 | 规则 |
| --- | --- | --- |
| 前驱 AND | 上游何时允许本节点开始 | 全 PASS 才执行；有 REJECT 阻断；无 REJECT 但最终有 UNKNOWN 则无法判断 |
| 前驱 OR | 任一上游是否允许本节点开始 | 有 PASS 可启动；无 PASS 且最终有 UNKNOWN 则无法判断；全 REJECT 则不满足 |
| 节点内部 AND／OR | 本节点自身条件怎样通过 | 与前驱关系独立，后继开始仍需完成自己的判断 |

OR 提前允许后继启动，不取消其他分支；按方案整图等待终态后再按唯一终点进入动作，不收到第一个 PASS 就发消息。删边后不足两个前驱恢复 AND。保存前须同时检查空节点、非法字段、重复边、自连、循环、孤立分支及唯一真实终点；一次列出可定位错误，不因报错清空内容。

## 补入第 6 章「三项系统预设任务怎样验收」

### 三项任务的关键配置边界

儿童锁用“共同前置 → 后排儿童／后排宠物 → 目标锁未开”说明判断。儿童是同一乘客的位置与年龄条件，宠物用已有物体描述推理；两分支 OR 后仍需检查目标锁。儿童 PASS、宠物 UNKNOWN 可以继续终点判断；两分支均无 PASS 且有 UNKNOWN，则不能建议开锁。左右位置与目标锁映射、D 挡后新识别是否补提醒按业务确认，不由后台自行扩展。

充电口盖只在 Trigger 配置进入 P 的启动、任务许可、电量和口盖未开等前置。阈值以任务正式需求为准，不能把技术样例 ≤20% 自动当最终值。前置通过后建议下游检查设备；DT 调 VQA 明确发现设备才询问，未发现或未知不询问。设备结果不回画布续跑，用户回答不接回 Trigger 调工具。

后视镜加热使用已确认车况、真实加热状态和已有天气描述；无需新设备 VQA，不等于 Trigger 可以调车控。加热状态缺失不能当关闭，天气缺失不能当无雨；未确认洗车、湿度温差分支不恢复成正式配置。

### 闪念一期完整 Case

【插图 D4：闪念一期运行链路】

以睡眠关怀为配置样例：选真实舱内描述，goal 写“判断当前是否明确有乘客正在睡觉”，业务说明限定本次观察、不推测历史；选择普通通知，固定正文示例“愿这一程，陪你安心休息。”，再核对正式次数、间隔和统计范围。该例不代表文案已签字或已有 PHUD 睡眠场景。

| 场景 | 预期 |
| --- | --- |
| 描述明确睡觉且有效 | PASS；策略通过才发送 |
| 明确清醒在交谈 | REJECT，不发送 |
| 仅闭眼、遮挡、来源不明或缺输入 | UNKNOWN，不发送 |
| 描述反复上报睡眠 | 按正式策略防刷屏；动作间隔不冒充推理降耗 |
| 用户说话／高优内容占用 | 按本版本明确仲裁，不擅自覆盖；不能宣称排队已完成 |
| 已发送但没有展示证据 | 记录真实阶段，不能标已展示 |

一期复用已有模型，不先建设小模型或语义匹配；现有文字容器先验证能否复用。会议中的覆盖现状、排队规划需区分，等待后的内容时效与丢弃策略由客户端收口。任意风景目标需先确认真实描述覆盖；天气／路面输入不自动代表湖泊等景物已支持。

## 补入第 7 章「核心异常与完成标准」

### 分层验收与异常恢复

| 层级 | 必须拿到的证据 | 不能据此推断 |
| --- | --- | --- |
| 配置保存 | 成功回执＋回读一致 | 已发布或车辆已采用 |
| 发布生效 | 目标环境实际采用正确规则，非目标不运行 | 条件已满足 |
| 判断完成 | 当次输入、节点结果、唯一终点 | 策略已放行 |
| Action 发送 | 真实出口调用与返回 | 客户端已接收 |
| 下游接收 | 真实受理／接收证据 | 用户已看见 |
| 展示／业务完成 | 真实展示或后续业务反馈 | 缺回传时可以默认成功 |

目录失败、未开放、待接入三种情况分别提示。改上级残留不兼容值、跨乘客拼接、非法 Position in、空推理目标、图结构错误都应定位到具体字段或节点。定义注册成功但场景关联失败须分阶段提示，重试不重复创建，原生效场景不应被破坏；新定义启用前处理旧规则，不能两份同时提醒。

运行状态与业务判断结果分栏：正常结束也可能 REJECT 或 UNKNOWN；前驱阻断的节点显示未运行和阻断来源，不伪造输入、耗时。超时后迟到返回不得覆盖已终结结果或重发动作。终点 PASS 但频控／锁未过，显示策略原因，不改成模型不满足。多规则同任务重复提醒不能用单场景锁冒充已解决。

原型人工模拟只验证页面与给定结果的传播，不证明模型、异步并发、Frontier 或车辆完成。真实历史保留当次定义和输入；后续编辑不能删除已经发生的事实。无展示回传时标“未取得反馈”，联调用客户端实际日志补证。
