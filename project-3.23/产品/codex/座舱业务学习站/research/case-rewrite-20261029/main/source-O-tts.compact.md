# 需求背景
考虑到车辆行驶环境的复杂性——频繁进出地下车库、隧道、山区等网络信号不佳或无信号区域——纯粹依赖在线云端合成的 TTS 服务无法保证全场景的可靠性。
为确保在任何网络环境下，核心的语音播报功能（尤其是导航和安全警示）都能稳定、高效地运行，我们必须构建一套能够智能调度在线与离线资源的混合 TTS 服务。
# 产品目标 
- **保障服务高可用**：在有网、无网、弱网等所有车载网络环境下，均能提供稳定可靠的 TTS 服务，确保关键语音播报（如导航指令、安全警示）**不中断**。
- **优化用户体验**：网络良好时优先调用在线 TTS，提供更自然、表现力更强的音质；离线模式下通过缓存，对高频请求实现“零延迟”响应，减少用户等待。
- **提升资源效率**：通过音频缓存机制，显著减少离线 TTS 引擎的重复计算，节省车机资源，并降低对车载存储介质的读写频率，更快的响应用户。

# 详细需求定义
## 需求范围
包括：离线TTS和在线TTS的调用策略；离线TTS缓存策略，播报优先级策略
不包括：在线合成中断后的离线断点续播
## 离线TTS和在线TTS的调用策略【P0】
根据网络情况动态选择在线TTS或离线TTS
- 在线TTS
    - 车辆网络正常
    - AND
    - 无大量的网络波动。
- 离线TTS
    - 车辆无网络
    - OR
    - 当前车辆网络波动大，或者网路速度较差
    - OR
    - 在线ASR本次调用时发生异常（如请求服务异常，云端超时）
    - OR
    - 未登录豆包账号
通过场景限定明确走在线TTS或离线TTS
- 强制离线TTS：系统警告与提示场景
- 强制走在线TTS：用户的历史上下文中有对「播报风格特殊要求」，如：你接下来用四川话和我对话。你之后都悄悄和我说。

## 离线缓存策略【P0】
缓存是实现离线场景下快速响应的关键。其核心原则是：对相同的文本与语音配置，只在首次合成时消耗资源，后续重复请求直接复用已有音频。缓存音频仅对在线合成的信息进行缓存，离线合成的不缓存。
**缓存类型**
「预置缓存」会将车载场景的高频播报文案提前合成好，进行存储在本地。存储数量上限不超过500条音频（数量暂定）。
「动态缓存」会将需要合成的音频，首次进行合成，合成并播放完成后缓存至本地。存储数量上限不超过1500条音频。（数量暂定），需缓存最新合成的音频，超出最大缓存范围时进行替换刷新缓存池。
**缓存匹配规则**
当需求进行TTS合成时，根据“待合成文本”与“缓存音频文件名”进行匹配，如完全一致即命中，直接播报缓存音频。
## **播报优先级与抢占策略【P1】**
由于所有的播报音色都是「豆包桃子」音色，车上不能同时「导航播报」又「语音交互反馈」因此为保证关键信息的有效传达，不同模块的 TTS 播报需遵循严格的优先级抢占规则。高优先级播报可打断低优先级播报。低优先级的播报请求时，如有高优先级的在播报则拒绝。
TTS优先级仅供参考（字节开放P0～P5，6个等级，至于各模块的优先级需车企音频管理的模块来定义）
# **服务能力输出【P1】**
由于车载场景各类业务模块，都有播报的场景，因此需要提供一个对外的接口进行TTS合成。
# 交互展示要求
只有豆包内部的语音交互流程才需要联动交互动效（如灵动岛的背景光效和机器人的播报表情），导航播报等其他业务调用TTS时无需展示交互动效。
# 离线TTS能力描述
产品需求
1. 离线语音合成
在无网络环境下，系统应能够将输入文本转换为语音并正常播放。
2. 音色一致性
合成语音应使用桃子音色，整体保持稳定、自然，无情感化和方言表达的需求；与在线桃子音色的相似度应高于90%。
3. 语音自然度
合成语音应自然、流畅，无明显机械感、异常停顿、断句错误或语速突变，主观听感MOS评分应高于4\.2。
4. 文本合成准确性
合成结果应与输入文本保持一致，不得出现错读、漏读、增读等问题。
5. 特殊文字处理
系统应支持生僻字及多音字的正确识别与发音，识别准确率应不低于99%；多音字应结合文本语境选择正确读音。
# 性能要求
## 响应时间
输入文本进行合成，到可以听到合成后的第一个音频信息。
离线缓存：\&lt;100ms
离线TTS：\&lt;300ms
在线TTS：\&lt;500ms
