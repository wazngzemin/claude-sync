车控 SFT FC 模型是什么：无网时替你"听懂人话并直接动手"的端侧小模型

一句话定义：SFT FC 模型 = 用"函数调用（Function Calling）协议"做训练数据、监督微调（SFT）出来的端侧小 LLM。它的唯一工作：把用户的语音指令在本地（不联网）翻译成结构化的函数调用 JSON——"空调调到23度" → {"函数":"空调温度调节","value":"23"}——200ms 内完成，让车在地下车库、隧道里也能听懂话。它就是"三层漏斗"的第一层，Director 那个大脑前面站岗的快手。

这段话是全链路仲裁的"宪法条文"，读三遍：① 命中白名单 → 端侧结果直接执行（不等云端，快）；② 没命中 → 云端优先（端侧结果压着不用）；③ 云端超时/挂了 → 才拿端侧结果兜底。FC 模型的身份因此很清楚：它是"优先执行者"只对白名单内函数，对其他一切是"备胎兜底者"。

1为什么需要它：三个痛点 + 两个硬指标

痛点（PRD原文）车上的真实场景
网络依赖风险地下车库、偏远山区、隧道——弱网/无网，云端解析延迟高甚至失效
隐私安全隐患语音上云涉及通话内容、目的地等隐私，本地解析不出门
实时性不足在线解析走网络传输+云端排队，驾驶场景的容忍阈值极低（紧急调温）
指标目标含义
响应延迟≤200ms从说完到函数调用出来的上限，比人眨一次眼还快
指令识别准确率≥95%（日常场景）100句里最多错5句——且错的代价是"没执行"，不是"执行错"
缓存命中准确率100%、50ms缓存层是"背答案"，不许错
对比体感：云端 Director 首 token 目标 P50=500ms，而 FC 模型是 ≤200ms 出完整函数调用。"打开车窗"这种话如果也等云端，用户在车上会觉得"这车反应慢半拍"。简单指令要的是快不是聪明——FC 模型用"放弃理解深度"换"确定性的快"。

3.2 解剖一个函数：空调温度调节（看槽位设计有多讲究）

槽位必填类型取值设计意图
value必填enum+strhigh/mid/low/max/min，或"+15"/"-30%"/"23"等自由值档位话术和温度数字共用一槽："调高点"→"+"，"调到15度"→"15"，"调高15度"→"+15"——相对量和绝对量靠 +/- 前缀区分
unit非必填enum摄氏度/华氏度/空单位显式化（你盯过的"带单位字符串剥单位"问题，这里用独立槽位解决）
position非必填enum主驾/副驾/左后/右后/前排/后排/全车/空/其他"我这"→音区（说话人位置，不写死座位，换人说话不用改逻辑）
协议里的样本对（=SFT 训练数据长这样）
"主驾空调调高15度" → {"value":"+15","unit":"空","position":"主驾"}
"主驾空调调高到15度" → {"value":"15","unit":"空","position":"主驾"}
"副驾冷得不行温度调到顶" → {"value":"max","unit":"空","position":"副驾"}
"我要把右后的空调温度调到十分之九" → {"value":"90%","position":"右后"}
注意第二行和第三行的差别只在"到"字——"调高15度"是+15，"调高到15度"是15。这种细微差别，规则系统写到崩溃，但 SFT 模型见几百个样本就学会了。协议表的每一行"举例输入→举例输出"就是一条训练样本，582 行表 = 这份模型的教科书。

4SFT 是什么、为什么必须是 SFT

SFT（Supervised Fine-Tuning，监督微调）：拿成对的"输入→标准答案"样本（这里就是协议表的举例列），在一个预训练小模型的基础上继续训练，把"说法→函数JSON"的映射烧进模型权重。

为什么不直接在端侧跑 Director 那套 prompt？原因
算力车端芯片跑不动 30K token SP 的大模型，只能跑小模型（十亿参数级）
时延200ms 硬指标，prompt 越长越慢，SFT 模型输入只要一句话
格式稳定性函数调用 JSON 必须 100% 格式合法（下游直接执行），prompt 约束小模型总有一定概率抽风；SFT 把格式训练成肌肉记忆
协议变更成本改协议=补样本重训，vs 改 prompt=逐字调。协议是表格驱动的，天然适合做成数据
"如不属于离线范围时，离线模型输出「其他」" —— PRD 不包含范围
"输出「其他」"是这个模型最被低估的设计：它教会模型说"我不知道"。"我失恋了放首歌安慰我"这种需要理解情绪的、"导航去国贸评价最高的川菜馆"这种需要联网的，模型不硬答，输出"其他"把话筒交回云端。一个离线系统的可靠性，不取决于它答对多少，取决于它能不能识别自己不该答的。这也是拒识模块存在的同一哲学。

5白名单：27 个放行 / 24 个拦下，为什么

白名单"是"（27个，端侧直接执行）白名单"否"（24个，云端优先，端侧只兜底）
空调全家（5）、座椅（3）、车窗、氛围灯（3）、阅读灯、远近光、雾灯、方向盘加热（2）、驾驶模式、后备箱、全景影像；屏幕亮度/昼夜/音量/静音/退出语音；拨打电话；指定应用开关导航全家（13）、媒体全家（4）、危险警示灯、雨刮全家（4）、低速行人提示音、紧急呼救
三类"否"各有各的道理：
① 导航/媒体全否：协议会解析（模型懂"导航去国贸"），但这些动作依赖在线数据（地图/曲库），离线执行了也是错——不如让云端优先，端侧只做云端超时兜底。高频说法（"导航回家""上一首""放大地图"）由缓存层接管，不进 FC 直接执行。
② 危险警示灯/紧急呼救：安全敏感动作，错了代价大，宁可慢点走云端确认。
③ 雨刮全家/低速提示音：v0.3 变更记录写了——"离线白名单全局更新，与主线赛力斯可控制的车控范围对齐"。赛力斯主线这些功能不可语音控，白名单就对齐关掉。白名单=车型的能力边界在离线层的投影。
同一句话在不同车型上命运不同："打开雨刮"在赛力斯=白名单否→云端；如果某车型开了雨刮语音→白名单是→离线直接刮。FC 模型是同一份协议训的，白名单按车型配置——模型共享，放行策略定制。这就是"协议与策略分离"。

6拒识模块：前台接待，决定"这句话该不该理"

单轮拒识多轮拒识
管什么无上下文的单句意图判断需要上下文关联的判断（代词/继承）
不拒识（召回）"打开空调"——意图明确的功能控制"打开空调"→"调到23度吧"——主客体动作与上文强相关
拒识"嗯嗯呀"/"继续防晒要走"——不通顺；"你晚上别和孩子玩太晚"——不是对车机说的"这个拒识效果还行"接"这台车的功能"——上下文无关
两个指标要反着看：过拒=该理不理（用户喊三遍没反应，砸车的心都有）；漏拒=不该理瞎理（两口子在后排聊天，车机突然插话"好的，已为您打开空调"）。PRD 说目标是"提升自然对话体验（减少过拒）+精准指令响应（减少漏拒）"——这是一个跷跷板，阈值往哪边偏是产品决策，不是技术决策。你评审遇到"车机乱插话/装听不见"类 badcase，归属就是这里。

7指令缓存：30 条背诵答案，50ms/100%

三条定义原则（每条都在防一类事故）

原则防什么
单轮解析：严格限定单轮，不引用历史"就选它了"这种依赖上下文的，缓存根本没法知道"它"是谁
上下文无关：与会话状态无关"暂停播放/继续播放"依赖播放状态，不纳入缓存
结果唯一：一条指令只能映射唯一意图+槽位有歧义要二次澄清的，回退到 FC 模型路径

30 条清单摘录：查看通话记录、播放下一首/上一首、打开歌词、播放蓝牙音乐、返回桌面、打开设置、媒体音量小一点、导航去公司/导航回家、退出导航、放大/缩小地图、打开空调/关闭空调/空调调到23度、打开座椅按摩、打开车窗、打开全景影像、退出语音。

注意清单里混着导航和媒体（"导航回家""上一首"）——它们在 FC 白名单里是"否"，但在缓存里是"是"。缓存是绕过 FC+白名单的第三条快速通道：这些说法太标准了，连解析都不用解析，原样匹配直接出结果。这就是为什么"空调调到23度"能 50ms 响应——它根本没经过模型。

8全链路仲裁 + 三个 case 走一遍

case 1：地库无网，"打开360度影像"
缓存无此条 → FC 模型解析 → {"函数":"全景影像开关","action":"打开"} → 查白名单：是 → 端侧直接执行，200ms 内影像亮起。无网照样秒开——这就是这套系统存在的意义。
case 2：隧道里弱网，"空调调到23度"
缓存直接命中（30条清单里有这条原话）→ 50ms 出结果 → 执行。用户还没感觉，已经调完了。如果他说的是"空调给我调到二十三度五"（缓存没有）→ FC 模型解析 → 白名单是 → 200ms 执行。
case 3：有网，"我好热"
缓存无 → FC 模型看这句话：没有明确指令，不是函数调用 → 输出「其他」→ 走云端 → 拒识+仲裁 → 非简单车控 → 进 Director → 结合端状态/记忆/情景拆出"开空调+21度+风量3档"（Round 7 §2 那套流程）。同一套语音系统，"打开空调"走 FC 200ms，"我好热"走 Director 500ms+——快与聪明各司其职。
case 4（兜底）：有网但云端超时，"打开车窗"
FC 已解析出 {"函数":"车窗开关","action":"打开","value":"100%"}，白名单是。但按仲裁条文"未命中白名单时优先云端"不适用（这条命中了白名单，直接端侧执行了）。真正用到兜底的场景：导航类——"导航去公司"FC 解析出来了但白名单否 → 云端优先 → 云端超时 → 拿端侧解析结果执行。风险：端侧兜底用的是本地缓存地图，路线可能不是最优。

9对抗式审查：协议数据里的三个坑 值得提给协议 owner

#坑证据（协议原文样本）后果
1车窗 action 标注自相矛盾"车窗开50%"→{"action":"关闭","value":"50%"}；而"车窗开到一半"→{"action":"打开","value":"50%"}；更怪的："车窗下降20%"（明明是开）→{"action":"关闭","value":"+20%"}SFT 最怕脏数据——同类说法标了两个 action，模型学出来就是掷硬币。车窗是最安全敏感的开合件之一，这个坑必须修（大概率是"开度0=全开/100=全关"的坐标系在不同标注员手里没统一）
2FC 协议有"强力制冷"，荣威家越07边界说没有空调开关 mode 枚举：制冷，强力制冷，制热，强力制热…；家越07 SP 能力边界："空调没有极速制冷，极速制热模式"车型能力错配：协议按赛力斯主线写的，荣威用同一套协议就会解析出车不支持的模式。解法同 Round 6 §A：协议层支持≠白名单放行≠边界承诺，三层要按车型对齐
3多轮样本混进"单轮解析"协议车窗开关里混着完整多轮对话样本（"副驾车窗开10%→再开大点→主驾调成一样的"→{"value":"20%","position":"主驾"}）；驾驶模式也有"…给我切换一下吧"与缓存层"单轮解析/上下文无关"原则冲突——FC 模型到底吃不吃上下文？协议没表态。如果吃，时延和状态管理成本都变；如果不吃，这些样本在教模型它用不上的能力
第 1 个坑是最实的锤：同样的"开50%"两种 action 标注，这在 SFT 数据里属于硬伤级脏数据。你如果把这份协议往上提，先让他们把车窗函数的标注坐标系统一（建议：action 恒为"调节"，value 带方向；或明确定义"开度100%=全关"并全表体检）。

10对你工作的接口 落到你的地图

你的领域和 FC 模型的关系
三层漏斗排查路径"走错模块"类 badcase 的前两站就是这：该走 FC 的走了 Director（"打开车窗"等了2秒）或该走 Director 的走了 FC（"我好热"被输出「其他」草率兜底）。FC 的召回边界=体验的快慢边界
信号格式 owner（仁杰那条线）FC 输出的 JSON 就是端上执行的契约——unit 独立槽位、value 的 +/- 前缀、position 的"音区"值，这些设计和你盯的"端上报格式带单位"是同一个哲学：格式归产品约束，不是端上自由发挥
触发器条件任务注册后，触发时"[任务原文]+条件已触发"发给 Director——注意触发器叫醒的是 Director 不是 FC，因为条件任务的动作可能复杂。但纯车控类条件动作（"10分钟后关座椅加热"）触发后完全可以走 FC 路径执行，这是时延优化空间
评测/badcaseFC 的 95% 准确率和 Director 的 90% 推理 ACC 是分开考核的。评测集也要分开：FC 测"说法→JSON 槽位对不对"，Director 测"任务拆解缺失/冗余/错误"。别用同一把尺子
一句话收尾：FC 模型是"快手"，Director 是"大脑"。快手的全部追求是确定性——确定的协议、确定的白名单、确定的时延；大脑的全部追求是理解力——情景、记忆、目标。车控体验的 80% 满意度来自快手不犯错，20% 惊喜感来自大脑够聪明。你管的产品版图里，这两个都要懂，但评判它们要用两套标准。
