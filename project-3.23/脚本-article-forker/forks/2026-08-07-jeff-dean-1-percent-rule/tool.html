01 · 1% 法则

先把最容易误读的一句话拆开

「去找模型成功率是 0% 或 1% 的问题，而不是 20%。」

Jeff Dean 在创业选题部分的核心建议

大白话翻译：如果通用模型已经能做出一点样子，你只给它换个界面、加几个 Prompt，下一代模型很可能把你的产品吃掉。更长久的机会在模型单独完全干不了、但你能通过独有数据和完整系统让它干成的地方。

为什么 20% 反而危险？

模型能做 20%，说明它已经学到这个任务的基本套路。未来增加训练数据、模型规模或工具能力后，20% 可能快速变成 60% 或 80%。如果你的产品价值只等于剩下那点语言能力，护城河会越来越薄。

为什么 0% 也可能是坑？

模型不会做有五种原因：缺信息、缺方法、缺工具、基础能力不足、需求根本不成立。前四种有时能工程化解决，第五种没有商业价值。因此你要加三道门：

门要问的话没过会怎样
价值门做成以后，用户会明显更好吗？模型 0%，用户也 0% 在乎
差异门你能拿到什么别人拿不到的数据、工具或现场？任何人接同一个 API 都能复制
闭环门你能快速判断结果好坏并持续改进吗？做了很多，始终不知道有没有变强
关键纠偏：20% 也不必一律放弃。如果客户需要 99.9% 可靠，剩下差距依赖私有现场、工具执行、合规与服务网络，系统公司仍有很大价值。Jeff 的话是创业筛选启发，不是机械淘汰公式。
02 · 你的真实场景

同样是座舱 AI，位置可能完全不同

场景裸模型表现真正难点你该怎么判断
打开车窗通常能理解工具参数、车速安全、座位权限走快速稳定通道，少投入复杂 Prompt
我有点热能理解情绪和意图车内温度、座位、空调状态、个人偏好价值在 Context 与执行，不在一句话理解
宝宝哭了告诉我没有现场信息时接近 0持续视觉、任务状态、误报、防抖、触达典型 1% 候选，先做评估器和隐私边界
沿途遇到值得讲的风景再介绍单次聊天做不了长时观察、位置、时机、去重、打扰控制长期价值高，难点在跨时间闭环
通用闲聊润色模型已经较强人设一致和安全可能快速同质化，控制投入
跨行程兑现偏好模型无法凭空知道身份、记忆更新、冲突、遗忘与授权属于私有数据路径，可持续积累

这里最关键的一点：模型能不能听懂「宝宝哭了告诉我」不重要。通用模型早就能听懂。真正的 1% 缺口是它没有眼睛、没有持续任务、没有事件唤醒、没有误报管理，也无法在车内安全地采取行动。

你以后评审一个场景，先说这句话

「我先把裸模型能力和系统能力分开。裸模型能理解需求，不代表它能在真实车里持续完成任务。我们要评估的是现场信息、任务状态、工具与回执补齐后，端到端成功率能提高多少。」

03 · 上下文工程

Jeff 描述的那张桌子，你已经坐在上面

上下文工程就是安排模型此刻能看见什么、能调用什么、该按什么方法行动。重点在相关、准确和及时，不在于塞入更多文字。

Jeff 的 performance skill 对应你哪部分？

Jeff 把「跑微基准、改代码、再测、扩大测试、检查缓存」写成模型能遵循的 skill。你做动态示例和场景知识，本质也在把人的决策方法交给模型。差别在于：通用方法适合写成 skill 或规则，孤立例外才适合留在动态示例。

你现在最值得做的升级：动态示例资产已经进入百条规模，下一步重点应从继续堆数量切到三件事：是否召回正确、是否与其他示例重复、是否有基线与净增益证据。
04 · 长时 Agent

「跑几周」不等于模型连续思考几周

这是整篇最容易被媒体标题带偏的地方。可靠的长期 Agent 更像值班系统：大部分时间在等待，有事件时醒来，读取最新状态，做一次短判断，执行并记录，然后再次等待。

你在评审里可以直接这么解释

「持续任务的时长和模型单次推理时长要分开。任务通过 task_id 和 snapshot 活两小时，模型只在相关事件到来时短暂工作。这样能控制成本，也能避免超长上下文累积错误。」

05 · 脱轨

Agent 为什么到第 30 步开始胡来

每一步只有一点小误差，走三十步后会积累成很大的偏差。如果中间没有检查，错误结果又会被下一步当成事实，系统就进入开环。

原因 1：跑出熟悉范围

模型进入训练时少见的状态，不知道下一步的标准动作。

原因 2：错误写回上下文

前一步的猜测被当成事实，后面所有判断都建立在错地基上。

原因 3：没人检查中间过程

只在最后看答案，无法及时砍掉已经跑偏的路径。

原因 4：环境已经变化

任务执行期间状态变化，旧计划仍继续运行。

Jeff 的解法放到你的系统使用边界
skills 与提示状态分支、规则、场景知识、动态示例能提炼共性就别用大量孤例
多路径搜索离线生成多个方案，评估器筛选高风险车控不适合运行时自由投票
评估器任务成功、过程轨迹、安全、延迟模型裁判也会错，需要抽检与硬规则
工具反馈tool feedback 回到 Planner 后重规划回执必须结构清楚，不能只写模糊文本

你已有的 A-F badcase 分诊有一个特别大的价值：它先判断错误是否真的属于 Planner。Jeff 的脱轨解释补充了下一层，真正属于 Agent 的问题还要定位到具体步骤，才能知道应该补 Context、补方法、修工具还是转模型训练。

06 · 能量与延迟

这一段看似偏硬件，其实和车载很近

Jeff 说芯片内部搬数据的能耗可能比做一次乘法高三个数量级。你不需要记住皮焦耳，但要记住产品判断：系统慢或贵，原因可能在数据怎么搬、何时搬、搬多少，未必在模型不够聪明。

边界：「一千倍」描述的是加速器内部数据移动与乘法能耗的量级对比，不能直接拿来证明云端网络一定比推理贵一千倍。

你可以问工程师的五个白话问题

  1. 这份数据最初在端上、云上还是模型内存里？
  2. 每次要传多少，多久传一次？
  3. 用户需要多新鲜的数据，旧十秒还能不能用？
  4. 哪些判断能在端上先过滤，哪些必须上云？
  5. 现在的等待时间分别花在 ASR、网络、Context、模型和工具哪一段？

对智能座舱来说，低延迟和低功耗会直接决定主动服务能否自然。若每次视觉观察都上传大量信息、每个简单动作都走完整云端链路，模型再聪明也会显得迟钝。Jeff 的「延迟快 50 倍后能做什么」适合用作产品想象题：哪些今天因为等待太久而做不了的自然交互，会突然成立？

07 · 评估器

真正让 Agent 越跑越强的发动机

自动化实验能复利，前提是系统很快知道哪次尝试更好。评估器太慢、太贵或不准，Agent 只能大量产出，无法稳定进步。

你现有材料曾记录一版方案从 79.38% 提升到 88.38%，这是很好的闭环证据。下一步要补的是改动归因：哪一组示例、哪条规则、哪类 Context 带来了多少增益，又产生了什么副作用。

Jeff Loop 周报，只写六格

本周问题 → 基线 → 失败假设 → 单一改动 → 结果与副作用 → 保留、回滚或继续实验。它能把你的大量产出压缩成可证明的能力。

我的独立判断：黄钊最有价值的补充是把 1% 法则连接到「大事」和 builder。最需要降温的地方是具体年份和过满结论。你应根据模型基线、客户付费与岗位变化每半年复盘，不押一个无法验证的 2030。

09 · 你的职业路线

从座舱 PM 到具身，不靠突然跳槽，靠带走一个闭环

具身智能里更值得看的 1% 问题

  • 机器人在客户现场持续数天完成任务，并能从失败中恢复。
  • 把现场操作数据、视觉状态和任务结果回流成可复用能力。
  • 在安全约束下做长时间观察、判断与物理行动。
  • 为每个客户适配流程，同时把共性沉淀成平台能力。

你不会代码，先补到什么程度？

目标不是转算法工程师。你先做到四件事：看懂 JSON 和 API，能读日志，能用 Agent 改简单测试脚本，能独立搭一个评测小工具或交互原型。这样你就能从需求提出者走向 builder，也能胜任偏业务和部署的 FDE。

10 · 30 天行动

别再把文章变成一堆金句，做出四份产物

第 1 周：1% 场景机会账本

列 10 个任务级场景，逐项打分。选一个 8 分以上且你能掌控完整链路的场景。

第 2 周：长时任务闭环一页纸

写清创建、订阅、等待、唤醒、判断、执行、回执、完成和恢复。

第 3 周：Context 缺口矩阵

逐项写来源、新鲜度、可信度和缺失降级。用 20 个样本跑基线。

第 4 周：Jeff Loop 周报

连续三轮单变量改动，记录结果和副作用，形成一页面试作品。

建议你拿「宝宝哭了告诉我」当样板

它同时覆盖 VLM、Trigger、Task、Context、Planner、主动播报、误报与结束清理，正好能把你现在分散的工作收成一个完整闭环。若这个场景的业务优先级已变化，可替换成另一个持续观察任务，但结构保持一致。
