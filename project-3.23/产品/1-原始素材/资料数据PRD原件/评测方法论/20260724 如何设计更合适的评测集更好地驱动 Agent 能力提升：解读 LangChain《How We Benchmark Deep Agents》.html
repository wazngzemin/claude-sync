一、原文核心内容拆解

1.1 为什么评测 Agent 这么难

原文开篇点出核心矛盾: Agent 设计难, 很大程度上是因为 Agent 评测难。在开发 Deep Agents(一个开源、模型无关的 agent harness)的过程中, 团队持续面临大量决策——怎么写 prompt、包含哪些工具、加载哪些 middleware 等。要在快速迭代中保持方向正确, 就必须有一套稳健的评测集作为决策依据 [How We Benchmark Deep Agents]。

LangChain 明确指出与传统 LLM 评测相比, Agent 评测有两个本质差异:

差异维度

传统 LLM 评测 vs Agent 评测

运行环境

传统 LLM 评测无需环境, 直接调用 LLM; 而 Agent 评测中环境如此重要, 以至于必须作为任务定义的一部分被显式声明(Dockerfile / Docker Compose)。

评判方式

Agent 常会产生额外文件或修改状态, 用脚本(test.sh)来评判, 而不只是看最终回复——必须检查它沿途创造的产物(artifacts)。

1.2 用 Harbor 做端到端评测

LangChain 近期把评测重心从早期的小型"单元式"测试, 转向端到端(end-to-end)评测, 因为 Agent 任务越来越长、越来越复杂。他们选用 Harbor 作为评测运行器(eval runner)——这是一个流行的开源 Agent 评测框架, 以驱动 Terminal Bench(领先的编码基准)而知名[How We Benchmark Deep Agents]。

使用 Harbor 需要提供三样东西, 而每个数据集里的 task 又由三部分构成:

Harbor 三要素

  • 你的 Agent: 此处即 Deep Agents
  • 你的数据集: 见下方三大基准
  • 你的沙箱: 本地或 LangSmith Sandboxes

每个 Task 三部件

  • Environment: Dockerfile / Docker Compose YAML
  • Instruction: Markdown 指令
  • Evaluation 脚本: test.sh 判分

Deep Agents 是通用型 harness,因此需要在多个领域验证能力。LangChain 目前跑三个基准, 各自覆盖一类不同的 Agent 工作[How We Benchmark Deep Agents]:

1.4 "行之有效"的四条工程实践

  1. 每个任务多次运行: 被测 Agent 本质上是非确定性的, 方差足够大, 单次运行往往无法得到经良好校准的估计。
  1. 保留一个 lite 基准用于快速迭代: 这是一个冻结的子集, 偏向"困难但可解"的前沿区。该 lite 基准比全量约快 8 倍、便宜 6 倍——迭代时用 lite, 关键时刻才跑全量。
  1. 在基准之外保留一套能力测试套件(capability suite): 这些是快速、确定性的单元测试, 各自针对某个具体的 harness 行为(工具选择、记忆、文件操作)。它是基准(集成测试层)之下的单元测试层。
  1. 用基准支撑"有信心的迭代": 做决策时, 对变更做基准测试能确保方向正确。

0.7 版本实战案例: 为准备 Deep Agents 0.7 发布, 团队计划精简 harness——移除曾经必要但现已冗余的 prompt。这对使用者的收益是: 每次运行更少 token、模型注意力更聚焦于用户真正写的指令。两个正在评估的具体改动是——移除 todo-list middleware, 以及大幅精简 system prompt。基准正是用来判断这些内置项对 harness 是否仍然必要。

二、结合开源代码的深入解读

2.1 Deep Agents 是什么:被评测的对象

Deep Agents 是 LangChain 开源的"batteries-included" agent harness(github.com/langchain-ai/deepagents, MIT 协议, 约 3.6k fork)。它构建在 LangGraph 之上, 模型无关, 内置四大核心能力, 理解这些能力是理解"为什么这样评测"的前提[Deep Agents overview - Docs by LangChain]。

核心能力

实现要点(对应评测维度)

任务规划 Planning

"Planning First"原则: 执行前先生成结构化 TODO 列表。由 todo-list middleware 提供——正是 0.7 拟评估移除的对象。

文件系统 Filesystem

虚拟文件系统作为上下文管理手段, 把大输出 offload 到独立文件而非塞满上下文窗口。对应多后端: StateBackend / FilesystemBackend / StoreBackend / CompositeBackend / LangSmithSandbox。

子 Agent Subagents

复杂任务拆给隔离的子 Agent, 各自拥有独立上下文窗口, 主 Agent 专注编排。对应 GeneralPurposeSubagentProfile 等 profile 配置。

上下文管理 Context

SummarizationToolMiddleware 做历史摘要与上下文卸载; /memories/ 目录持久化用户偏好、研究结果与学到的行为模式。

正因为 Deep Agents 内置了 planning、filesystem、subagent、memory 这些"会修改状态、会产生文件"的能力, 原文所说的两个评测差异(环境即任务、脚本判分)才成为必然——评测必须能观察 Agent 在文件系统里留下的产物。

2.2 双层评测架构: 能力套件 vs 端到端基准

结合更早的技术博客《How we build evals for Deep Agents》(2026-03), 可以看到 LangChain 完整的评测哲学。其核心主张是一句反直觉的话——"更多的 eval ≠ 更好的 agent", 应该构建能反映生产环境所需行为的定向(targeted) eval[How we build evals for Deep Agents]。

┌─────────────────────────────────────────────┐
│  集成测试层  Benchmarks（本文重点）              │
│  Harbor-Index / τ³-bench / ContextBench       │
│  端到端、非确定性、多次运行、有 lite 快跑子集      │
├─────────────────────────────────────────────┤
│  单元测试层  Capability Suite                  │
│  快速、确定性、针对单一 harness 行为             │
│  tool selection / memory / file operations    │
└─────────────────────────────────────────────┘

其 eval 数据的三个来源也值得借鉴[How we build evals for Deep Agents]:

  • Dogfooding(自用)反馈: 每天自用 Agent, 每个错误都成为写一条 eval、更新 agent 定义与上下文工程实践的机会。
  • 从外部基准(Terminal Bench 2.0、BFCL)选取并针对特定 Agent 改编。
  • 手写(artisanal)自认为重要行为的 eval 与单元测试。

关键工程细节: 每条 eval 都带 docstring 自解释它测量的能力, 并打上 tool_use 等分类标签以支持分组运行; 所有 eval 运行都 trace 到共享的 LangSmith 项目, 让团队共担"维护好 eval"的责任。同时他们明确把 SDK 单元/集成测试(system prompt 透传、interrupt 配置、subagent 路由)与模型能力 eval 分开——因为任何模型都能通过前者,纳入评分不增加信号。

2.3 从 4 个"单元式"到端到端的演进

更早的《Evaluation Patterns for Deep Agents in Production》记录了 LangChain 在一个月内基于 Deep Agents 上线四个生产应用(DeepAgents CLI 编码 Agent、LangSmith Assist、个人邮件助手、Agent Builder)时总结的五种评测模式:逐数据点定制断言、单步评测、完整 Agent turn 测试、带条件逻辑的多轮对话、以及干净可复现的环境搭建[Evaluation Patterns for Deep Agents in Production - ZenML]。本文所述的 Harbor 端到端体系, 正是这套早期"unit 式"实践在任务变长、变复杂后的自然升级。

3.2 Sierra 𝜏-bench: pass^k 与"模拟用户"的源头

LangChain 的 𝜏³-bench 直接脱胎于 Sierra 的 𝜏-bench 系列。Sierra 在 2024 年 6 月提出 𝜏-bench(tool-agent-user benchmark), 其突破在于不只测 Agent 能否完成一次任务, 而是测多次运行的一致性——引入 pass^k 指标衡量跨多次试验的可靠性[𝜏-bench | Sierra]。原文所说"每个任务多次运行以对抗非确定性"正是这一思想的延续。值得注意的是,连 Anthropic 的模型卡都开始讨论 pass^k, 说明该方法论已影响到头部厂商的内部评测实践。其升级版 𝜏²-bench(sierra-research/tau2-bench)进一步支持文本与语音(全双工)双模态评测[tau2-bench leaderboard submission]。

3.3 Terminal-Bench: Harbor 的旗舰基准

LangChain 选择 Harbor 并非偶然——Harbor 最知名的应用正是 Terminal-Bench(tbench.ai), 一个由 Stanford 与 Laude 合作、面向命令行硬核真实任务的基准。它是 Harbor-native 基准集, 采用长程单任务、沙箱脚本判分的模式,与本文所述 task 三部件(环境/指令/判分脚本)完全同构[Terminal-Bench]。其 2.1 榜单上 Claude Code、Codex、Cursor CLI 等主流 Agent 得分集中在 74%–84% 区间, 可见"真实、困难"任务对当前 Agent 仍是明显挑战。

3.4 Anthropic: 用技术组合匹配系统复杂度

Anthropic 在《Demystifying evals for AI agents》(2026-01)中提出与 LangChain 高度一致的观点: 让 Agent 有用的能力, 恰恰也让它难以评测; 跨部署有效的策略是组合多种技术来匹配被测系统的复杂度, 并强调好的 eval 让问题在影响用户前就可见, 其价值在 Agent 生命周期中不断复利[Demystifying evals for AI agents | Anthropic]。这与 LangChain"每条 eval 都是一个改变系统行为的向量"的表述异曲同工。

3.5 SWE-bench: 编码 Agent 的行业标尺

在软件工程维度, SWE-bench(尤其人工校验的 Verified 子集)已成为跨厂商公认标尺, 判分方式是直接运行仓库的真实测试用例——与 LangChain"脚本判分 + 检查产物"的思路一致。据第三方榜单, 当前 SWE-bench Verified 头部模型(如 Claude、GPT-5.5、Gemini)准确率已达 78%–95% 区间[SWE-bench Verified | vals.ai]。Deep Agents 的 Harbor-Index 正是从含此类基准在内的 54 个基准中蒸馏而来。

3.6 NVIDIA: 反向印证"harness 即产品"

一个有力的反向印证来自 NVIDIA:其为 Nemotron 3 Ultra 专门调优 LangChain Deep Agents harness, 在 LangChain 的 Deep Agents benchmark 上取得开放模型中最高准确率, 并以约 1/10 的推理成本实现与顶级闭源模型的业务任务对等——关键是无需重训模型,所有提升都来自围绕模型工程化环境(调 system prompt、工具描述、middleware)[NVIDIA Nemotron Achieves Benchmark-Leading Performance | NVIDIA]。Harrison Chase 的原话是: "构建更好 Agent 的方法,是持续改进模型周围的系统。"这恰恰说明——LangChain 的 benchmark 不只是自评工具, 已成为业界调优开放 Agent 栈的公共标尺。

四、关键洞察与启示

可直接借鉴的做法

  • 环境即任务: Agent 评测必须把可复现环境(容器)当成一等公民
  • 脚本判分 > 看最终回复: 检查 Agent 产生的文件/状态产物
  • 多次运行取均值: 用 pass^k 类指标对抗非确定性
  • lite 子集快跑: 8× 快、6× 省,迭代用 lite、关键跑全量
  • 双层结构: 确定性能力单测 + 非确定性端到端基准

容易踩的坑

  • 堆数量陷阱: 更多 eval 制造"变强的错觉",不等于更好的 Agent
  • 把 SDK 单测混入模型能力评分,稀释信号
  • eval 无文档、无 trace, 团队无法共维护
  • 只信单次运行, 被方差误导决策
  • 只调模型不调 harness, 错失最高性价比的提升空间

本质判断: LangChain 把 Agent 评测从"事后测分"重构为"研发基础设施"。三大基准对应三类工作、Harbor 复用业界成熟运行器、lite/全量分层控成本、能力套件兜住确定性行为——这套组合拳的核心不是"测得多准", 而是让每一次 harness 变更(删 middleware、精简 prompt)都能被快速、廉价、可信地验证。这与 Sierra 的 pass^k、Anthropic 的"技术组合"、NVIDIA 的"调环境不调模型"共同指向同一个行业共识: Agent 时代的竞争力, 越来越多地沉淀在"模型周围的系统"以及验证这套系统的评测能力上。
