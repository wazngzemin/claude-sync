# v14 业务连线审计

审计范围：`parts/director.json`、`parts/async.json`、`parts/tools.json`、`parts/presentation.mjs`。仅检查现有数据与已读材料的一致性，未再次检索。以下是生成总图前必须处理的 7 项；修改应落在总图连线／呈现规则，不必删除有用的模块解释。

## 1. Context 的独立信息源不能画成串行必经步骤

- **位置**：C2→C3、C4→C5→C6、C7→C8→C9，以及 C11→C12→C11。
- **问题**：这些线意味着先有身份才取车况、先有记忆才取工具和示例，也意味着每轮都经过全部来源；资料只支持这些是可选背景来源，不支持这种执行依赖。C12 又把显式记忆查询画成 Context 内部自循环，遗漏了真正的工具与输入管理。
- **改法**：C2～C9 各自以“背景供给”线汇入 C10/C11，不相互串联；缺失／不适用也允许组装已知信息，不能画成全部齐备才运行。前置记忆保留 C7→C11；第二路改为 **D 判断缺信息→E 调 `user_memory_search`→M 接反馈→D 下一轮**。C12 仅作为这条跨模块路径的说明入口，不能自行返回 C11 形成另一个推理循环。C10 的相关性／新鲜度应注明“验收责任，具体算法待确认”，避免被看成已部署固定流水线。

## 2. 全图只保留一个工具反馈与再推理回路

- **位置**：D11→D12→D1、E7→E8→E9→E1，以及 T08→T09、S05→S06→S07。
- **问题**：D 内直接收到反馈，E 内又包含一次输入管理和 Director，接上全局连线后会出现多个“大脑”、多次等待和不同的返回入口。任务／Advisor 的图内跳转也可能绕过同一个输入管理。
- **改法**：运行主回路固定为 **D11 动作列表→E1～E7→M1～M9→D1**；有下一步时从 D11 再发新一轮动作。D12、E8、E9、E10 保留说明但标成“跳转到 M／D／O 的引用节点”，不能再建立独立执行链。T08 与 S05 都接 M1 的 advice 入口；创建任务结果和普通工具结果接 tool_feedback 入口。T09 是一次执行的结果回写，不可由 T08 直接视为完成。跨轮须遵守上一轮语音播放完成后的推理窗口。

## 3. 输出图要明确“说话”和“执行”并行，不以播报作为执行门槛

- **位置**：`presentation.mjs` 的 O01～O07，特别是 O02→O07、O04→O05→O06→O07、O07→O03。
- **问题**：当前连线让“不需要首轮话术”直接进入结果处理；需要首轮话术时，则像是播放、卡片、听取插话之后才等待工具。它还在 O07 重复实现了 E7 的反馈收齐和 D 的结果判断。
- **改法**：从 D11 明确分三路：**动作列表→E1；有话术→O03；表情／卡片呈现→对应呈现端**。无首轮话术时，只跳过语音，不跳过 E。E 汇总结果经 M、D 后，D 新输出结果话术再进入 O03。O07 改成对这条回路的引用，不再运行第二次等待／推理。O06 的打断分支显式回语音判定与 M，不能悬空。音频和卡片“配合”用关联线，不能暗示所有卡片必须等音频起播。

## 4. 不要把人工验收画成已存在的运行时自动监控

- **位置**：E10→E11→E12、O07→O08→O09。
- **问题**：E11、O08 的正文是在讲产品验收，但实线会让人理解为系统每次播报后自动验证声音、卡片、音乐、导航和全部车辆状态，并在不一致时自动返回 Director；现有证据没有确认这套通用监控已实现。
- **改法**：E11/O08 改成虚线侧挂的“验收与观测”节点；只把已经有明确接口的执行反馈、状态更新、事件日志画成运行回流。将“收到了受理结果”“业务完成回包”“车辆／应用实际变化”“用户听到／看到”分别标注，不替未知工具统一补出最终状态回调。

## 5. 所有判断节点补齐否／未知／失败出口，避免看起来只会成功

- **位置**：T03、T07、G02、L01、L04、S04、P02/P07、A01/A11。
- **问题**：例如 T03 只有能力齐备出口、T07 只有任务有效出口、L04 只有命中出口、S04 只有值得建议出口；A11 没有任何出口。正文提到异常，但读图仍会误以为条件不成立后流程消失。
- **改法**：T03 不可承接→失败反馈／澄清；T07 取消或过期→丢弃本次旧回调并记账；G02/L01/A01 无权限或不可用→不启动并保留原因；L04 不满足→继续等，未知→按项目异常规则处理；S04 不合适→不产出 advice；P02/P07 校验失败→修订且不得发布；A11 补“仅回答→Director 反馈、需要确认→交互确认、确认后动作→执行、无法识别→说明／重查”。这些分支不要自行填重试次数或超时秒数。

## 6. “同轮并行”必须同时展示依赖与互斥例外

- **位置**：D9、E3、E9 及工具详情里的导航工具、`vehicle_basic_control`。
- **问题**：统一说“同轮同时发出”若不带条件，会诱导把同一导航状态的多个操作并发；“失败后重试或替代”也会被误读成所有工具都能重试。工具表明确存在导航串行约束，以及车控无回包超时不重复调用的边界。
- **改法**：D9/E3 主标题或可见行写成“**无依赖且不冲突的工具才同轮并行**”；先查地点再规划、先确认再导航分轮。反馈后只处理未满足部分，不重做已成功动作。对车控超时显示“结果未知／按当前表失败告知，不重复调用”，恢复、重试和迟到结果只能按对应工具确认的协议处理，不由一条总线默认提供。

## 7. 工具版本和未确认机制要在图面可见，不能只藏在详情

- **位置**：工具总览标题、`tools.json` 的 `countExplanation`、`coverageNote`、`additionalInventoryFindings`，以及 E5/E12。
- **问题**：33 行本身已核对正确，但若只渲染 `tools` 数组，会隐藏额外库存、唱歌缺口、高德测试状态以及输入输出表后半段未读全，用户会误认为 33 个均已上线、机制全部核实。
- **改法**：总览必须直接显示“**当前 PRD 33 业务行／34 英文标识；非全车型上线数**”。`goal_list_update / task_agent` 保留同一行并注明“版本／项目入口差异”，不是连续调用两工具。高德两项标测试；唱歌、`trip_plan_record`、`map_location_pick` 单独列“补充核对，不计入本表 33 行”；后半段机制与异步终态保留待接口确认。E5 的受理／完成是业务必须区分的概念，不等于全部工具均有这两个统一字段。

## 已核对正确，保持不变

`async.json` 的 S09 已把旧动态 Advisor／Goal List 作为演进说明，且无运行连线，这一点正确；新 Task 是任务生命周期承接方，不应再把旧动态 Advisor 接成并行执行链。T12 已指出旧技术方案与任务中心对 `waiting` 的含义不同，不能删除这项版本提醒。33 行工具清单、两路记忆、四类输入、下游不自行播报和“受理不等于真实完成”文字口径均正确；本次问题主要发生在运行连线、可见例外和证据状态的呈现。
