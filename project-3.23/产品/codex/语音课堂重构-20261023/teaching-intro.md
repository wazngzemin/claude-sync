# 课堂导入与连续带路讲稿

这是根据真实产品培训的讲解方法重写的教学稿，不是会议逐字引语。术语阈值、部署位置、项目现状由事实核验章节提供；本稿先建立产品理解框架。

## 开场讲稿：先跟着用户，把一句话办成一件事

我们先看一个场景。你坐在主驾，说：“豆包，去昨天那家游泳馆。”说完以后，你会看什么？首先，你得知道它有没有听见，所以屏幕最好能让你看到这句话正在被识别。接着，你会等它找出昨天去的那家，而不是随便搜一家名字相近的。最后，你要看到正确的路线开始导航，听到与实际结果一致的反馈。我们今天就跟着这句话，把这三个结果怎么发生讲清楚。

这里先约定，这是一个用来解释机制的教学例子，不是实车验收记录。假设语音入口可用，有网络，昨天的地点需要查记忆。等正常链路走通，我们再把条件换掉：没有记忆会怎么样，工具失败怎么办，你中途改口又会发生什么。这样每次只改变一件事，你就能看出每个模块到底解决什么问题。

先看总图最左边。用户说话，麦克风收到的是声音，还不是文字。车里同时有音乐、风声和胎噪，所以前面需要把可用的人声交出去。这一段叫音频采集和前处理。产品在这里要关注的不是算法叫什么，而是用户的原话有没有完整留下、环境声音有没有让它听不清，以及说话来自哪个座位。声音已经丢了，后面模型再聪明，也不能可靠地补回用户没被录到的词。

接下来点亮 ASR。ASR 的中文是语音识别，你先把它理解成把声音写成字。你说一句，它不一定等整句话结束才给字，而是边听边返回当前识别结果，这就是流式。屏幕上先出现几个字，接着变成一整句，中途还可能修正。所以，我们现在拿到的是不断更新的听写稿，不能看到“去游泳馆”几个字，就直接认为用户已经说完。

那谁来判断还要不要继续等？旁边这条线叫 VAD，语音活动检测。它和 ASR 同时工作：ASR 关心认成了哪些字，VAD 关心这一段声音的起止和停顿。用户说“去……”时停一下，可能是在想后半句，也可能真的不说了。Soft VAD 和 Hard VAD 是资料中用于提前准备和收尾的不同节点；具体怎么触发，下一小节用时间轴展开。你现在先记住，短暂停顿不等于可以执行，收尾也不等于已经把事情办完。

再看“二遍 ASR”。用户不需要再说一次，系统是在同一段输入上，既尽早给你过程文字，又在分句收尾后给出最终识别结果。我们把它们分别叫 partial 和 final，也就是过程稿和定稿。定稿仍可能有错，但后面的正式处理必须知道采用的是哪一份。前面提前准备的结果，如果依据的文字已经变了，就不能不检查地接着用。

现在，声音已经变成最终文字：“去昨天那家游泳馆。”我们是不是可以立刻导航？还不行，因为这句话听对了，不代表地点已经知道了。ASR 解决的是用户说了什么；后面还要判断这是不是对豆包提出的有效需求，再结合上下文理解怎么办。Context 就是这次办理可用的背景信息；Planner，也叫 Director，负责利用这些信息安排下一步。它发现“昨天那家”没有具体地址，就需要查记忆，而不是自己编出一个地点。

我们看这根往返箭头。Planner 发出查记忆的动作，工具去查，结果再回来。工具就是实际提供某项查询或操作能力的模块；返回结果叫 tool_feedback。查到一家、查到两家、没有查到，下一步不应该一样。查到唯一地点，可以继续办理；多个候选可能需要澄清；没有结果，就要承认缺信息。这个“判断一下、做一步、看结果、再判断”的循环，比记住某个模型名字更重要。

地点明确后，Planner 才能安排导航。这里我们再停一下：动作被生成、请求被接收、导航真正开始，是三个不同状态。产品验收要一直追到目标端结果，不能听到一句“好的”就打勾。如果工具只确认受理，回复就不能抢先说已经办成；如果执行失败，后面的解释也得跟着失败结果走。

最后看右侧。系统把结果组织成要说的话，这叫自然语言生成；TTS，也就是语音合成，再把文字变成可以播放的音频。音频交到车端播放器，扬声器真的播出来，用户才听见。这里可能一边生成后半句，一边合成前半句，同时播放已经到达的声音，所以总图表达的是职责交接，不是所有模块必须排队做完才能轮到下一个。生成结束、合成结束、播放结束，也要分别确认。

到这里，我们才走完这次请求。接下来每一讲都沿同一个例子往前走：先看当前拿到了什么，再看还缺什么，所以交给谁；最后看用什么证据确认这一步完成。正常场景讲通以后，我们会在图上加入停顿、认错、查不到、执行失败和插话。你不需要一次背下所有缩写，但要逐渐能指出：用户的问题最先出现在哪一步，下一步为什么没有接上。

## 节点之间的带路句：正文应自然衔接，不当作碎片卡片堆放

### 从收音接到听写

“现在我们确认用户这句话被完整录下来了，来源也是主驾。但声音本身还不能直接告诉业务系统要做什么，所以接下来要把它认成字。图上保留声音轨，把 ASR 轨点亮：它收到的是音频，交出的是识别文字。以后遇到听错，要先确认声音是否完整，再看文字在哪里第一次偏离，避免两边互相推。”

### 从听写接到判断说完

“屏幕已经出现‘去昨天那家’，但用户还没说‘游泳馆’。所以看见文字，并不等于可以下导航命令。我们把时间轴往后拖，看看用户停了多久、有没有续说，VAD 在旁边判断边界，ASR 仍继续更新文字。两个模块此时同时工作，不能把箭头画成先听写完，再开始检测停顿。”

### 从最终文字接到理解

“现在定稿出来了，我们终于可以明确这次用户说了什么。但‘昨天那家’仍然缺地址。下一步把最终文字、说话来源和可用背景交给理解与规划，先确认是有效请求，再确定需要补什么信息。到这里如果文字全对却找错馆，问题就不应继续笼统叫 ASR 错误。”

### 从理解接到行动

“Planner 现在知道要导航，但它还没有目标地址，所以先安排查询。请看图上的两条输出：一条是给用户的话，一条是交给工具的动作。说‘我帮你找一下’不等于已经查到，发出查询也不等于查成功。我们让动作去到工具，把结果箭头画回来。”

### 从行动接到回执

“工具开始处理了，这一站最重要的是结果回来。回来的可能是候选、成功、失败或仅受理，Planner 必须认清这个结果代表哪一步完成。我们先不把箭头直接接到成功播报，而是回到判断：现在掌握的事实，足不足以继续？”

### 从回执接到生成

“如果反馈已经证明导航开始，回复可以说明真实结果；如果只收到受理，就还不能这样说。自然语言生成负责把这些事实组织成用户听得懂的话。它可以边处理边输出，但不能把还没发生的结果说成已完成。”

### 从生成接到合成

“这时我们已经有一段要说的话，但文字本身没有声音。把允许播报的文字交给 TTS，它才生成音频。字幕和播报可能按项目定义有不同表达，但地点、执行结果这些关键信息不能互相矛盾。现在把文本轨和音频轨分开，你就能看到哪一段已经生成、哪一段仍在合成。”

### 从合成接到播放

“首段音频到了，用户仍不一定听见，因为车端还要接收、排队、开始播放。我们再往后推进，直到播放器真正开始，体验上的等待才结束。最后一包到达也不等于用户听完，播放进度必须继续走到实际结束。后面讲插话时，就会用到停在什么位置、哪些内容已经听过。”

## 产品验收思路：同一条请求，分开核对四份事实

| 要核对的事实 | 本例要看的证据 | 不能直接推导什么 |
|---|---|---|
| 用户输入 | 原始/处理后的音频、最终文字、来源音区、适用交互状态 | 有文字不代表识别完整正确，正确文字不代表有效需求 |
| 系统判断 | 实际可用上下文、工具请求、候选结果、下一轮决策 | 说知道不代表有依据，发出 action_list 不代表下游完成 |
| 外部执行 | 请求下发、下游受理、工具反馈、导航目标端状态 | 受理不代表成功，停止推理不代表取消动作 |
| 用户感知 | 展示内容、允许播报文本、音频到达、实际播放及进度 | 合成完成不代表听到，云端结束不代表播完 |

验收应拿同一请求的证据贯穿这四份事实。状态可以并行推进，例如工具查询期间先生成过渡话，音频播放期间继续收音；但状态名称与成功证据不能混用。没有现行证据支持的并发策略、门控机制和取消行为，应标拟改造或待核验，不由教学示例替项目补齐。
