INTRO

普通导航的目标是到达一个地点，用户说“去 D 栋，停负二层充电车位”时，又加上了泊车位置与车位类型。两部分必须一起保留下来，否则系统可能把路导对了，却忘了用户最后想停在哪里。司机 Agent 这层专项协调，就是为这类跨导航与停泊车的任务服务。

沿这一场景往下看，你会看到目标先从人话变成具体参数，再对应到真实地点、路线、园区和车位，最后由智驾判断与执行。任何一个中间步骤完成，都需要继续对照最初的停车目标，不能提前把“已选地点”或“正在找车位”说成“已经停好”。

## dr-lesson-1 Director 交完整诉求，专项层协调任务，智驾承担实际执行

Director 负责听懂用户这轮究竟要新建、补充还是改变任务，并结合前文把完整诉求交出去。司机 Agent 接住导航与停泊车的专项关系，调用导航或控制工具，跟踪它们的依赖。AI Navi 负责地点与路线等导航能力，auto_drive 承接具体智驾控制。用户需要选地点、选路线或澄清时，仍由 Director 组织对话。

再往下，系统导航或泊车 App 把园区、楼层、区域、车位类型对应到真实地图与车位。ADC 是智驾域控制器，它根据路况与车辆条件判断能否安全执行，并报告进展。专项 Agent 能够协调任务，不代表它可以替代执行层判断实时转向与制动。

读这层还要先看场景分路。导航加指定车位泊入、指定地图点临停等组合任务可以进入专项层；仅导航后激活智驾，则存在 Director 先导航、确认成功后再调用控制工具的路径。局部场景接入司机 Agent，并不能推出所有导航和智驾都已迁入这一层。你应逐个场景核当前谁接收、谁调用、谁回报。

## dr-lesson-2 先保留停车要求，再把它落到真实车位

“去 D 栋，停负二层充电车位”交到专项层后，先拆出去哪和到了以后怎么停。控制工具把负二层、充电车位等要求变成参数，司机 Agent 再把这些参数与导航诉求一起交给 Navi。这样用户后面选地点和路线时，最初的停车偏好不会丢掉。

Navi 返回候选，Director 请用户作必要选择。地点与路线确定后，组合任务交系统导航和泊车 App。此时需要做 mapping，也就是把园区、楼层、区域、车位类型映射到实际地图对象。负二层充电车位只是条件，直到匹配完成才有具体目标位置。

匹配失败要继续分原因。目的地没有地图时，组合出行方案需要询问是否仍以智驾前往目的地，用户同意才改变目标，拒绝则取消。已有地图却没有对应楼层、区域或车位时，则按支持范围引导到泊车地图界面选择其他位置，并把新选择带回后续背景。更换目标后，应按新目标验收，不能仍声称原车位要求已实现。

单独泊车还受园区范围约束。这里整理的 SLS 方案中，有导航时围绕导航终点园区，无导航时围绕当前位置园区。无图时能否漫游找车位，需要下游支持与可执行判断。组合出行的无图确认，和单泊车的漫游选择，是两个不同条件下的分支，不能统一写成自动降级。

## dr-lesson-3 临停先有一个有效路线点，再给这个点加停靠要求

“先去 A，再去 B，A 靠边停一下”里，路线经过 A 和要求在 A 停靠是两份信息。专项层先让 Navi 算路并成功添加途经点，再为这个真实存在的点设置临停属性。这里存在明确先后依赖，不能把加点和设临停同时扔出去，只看其中一个返回成功。

临停要求需要绑定正确的 POI，也就是地图中的具体地点对象。设置后，系统导航 App 把最新路径和停靠要求同步给智驾。路线成功只证明会经过哪里，属性成功说明这个点带着停靠意图，最后真正靠边仍需看智驾执行。

如果用户后来补充“再经过 D”，要保留前面的 A、B、目的地和已经设置的停靠要求。不能只把新点 D 交下去，让旧任务上下文消失。只换路线选项、重新算路修改目的地、删除途经点，可能触发不同的缓存与保留行为，评审时必须说明到底使用哪种操作。

例如经过 A 后，相关途经与临停记录会随进展更新；取消 B 的临停只应修改 B 的停靠要求，并不自然等于删除 B。你可以用完整路线列表、点位身份、顺序、临停属性与最新车端状态作一组前后对照，才能验证改动只影响了用户要改的部分。

## dr-lesson-4 用户确认与任务变更，要等各自真实结果

语音激活智驾需要相应的二次确认。卡片出现只表明正在征求同意，用户确认后还要等智驾是否允许激活。卡片超时消失、被新卡片替代，都不能当作用户同意。挂起指令如何清理、旧确认何时失效，还应由实际交互与控制合同明确。

用户把“停负二层充电车位”改成“到了路边停就行”，应先关联旧泊车任务，再请求取消。确认取消成功后，才能让 Navi 设置目的地的临停要求。取消只发出但没有成功反馈时，不能让新旧目标同时向下推进。取消失败和超时也需要真实出口，不能用新话术掩盖旧任务仍可能执行。

视觉参照物临停还存在另一条专门路径。用户说“停在拉行李箱的人旁边”，系统传出目标描述，智驾向端侧视觉能力请求识别，再用位置与图像时间等信息判断。它不意味着每一帧都要绕回司机 Agent。视觉找到目标、智驾可以执行、实际完成停靠，各自都是独立需要验证的事实。

你掌握这一模块的标准，是拿同一出行任务说清当前目标、尚缺信息、下一步为什么允许，以及哪一个反馈证明前提成立。特别是选地点、匹配车位、确认激活、取消旧任务、真正停车这几个关口，不能用一个笼统的成功把它们压在一起。

### guide DR-d2d-flow 沿“去 D 栋，停负二层充电车位”一路走到停车结果

从 DR-d2d-1 到 DR-d2d-2，Director 保留去哪、是否激活智驾和停车要求，再交专项层。到 DR-d2d-3，司机 Agent 分出导航与泊车两部分，先到 DR-d2d-4 提取楼层、区域、车位类型。此刻系统知道的是停车条件，尚不知道真实车位。

参数回来后，DR-d2d-4 到 DR-d2d-5，把泊车要求与导航诉求一起交 Navi，缓存关联并搜索地点。随后到 DR-d2d-6，让用户选定地点和路线。A、B、C 候选出现时还没有确定目标，因此不能绕过选择直接宣称已经开始去指定车位。

选定后到 DR-d2d-7，系统 App 才把园区、楼层、区域与车位类型映射到真实位置。匹配成功走向 DR-d2d-10；没有地图走 DR-d2d-8；有图但缺所需车位、楼层或区域则走 DR-d2d-9。这三条线分的是不同失败条件，不应混为一个“没找到”。

在 DR-d2d-8，询问用户是否改为仍前往目的地。同意才进入 DR-d2d-10，拒绝则到 DR-d2d-12 报告取消。DR-d2d-9 则引导用户在支持的泊车界面重选，选位并满足确认条件后再到 DR-d2d-10。无论哪条替代路径，都要记住用户最终接受的目标已经可能发生变化。

DR-d2d-10 表示激活确认与安全可执行判断。图把业务门槛集中说明，实际确认卡在接口链上的位置仍需与接入对应。满足条件才到 DR-d2d-11，由 ADC 执行并回状态；用户取消、拒绝或无法激活时，直接到 DR-d2d-12 解释真实结果。

DR-d2d-11 返回后也到 DR-d2d-12，由 Director 表达进展或终态。读到这里再回看最初目标，激活成功、正在泊入、已经泊入指定位置分别到达了不同阶段。若用户已经改成只前往目的地，最终结果也应对应这个新目标，不能继续把原来的负二层充电车位算作完成。

### guide DR-poi-flow 在 DR-poi-5 停一下，确认地点已经成功加入路线

DR-poi-1 说清“先去 A，再去 B，A 靠边停”。DR-poi-2 保留本轮与前序完整目标，DR-poi-3 再拆成导航点顺序和指定点临停两项任务。若前面已有路线，这里也不能只带新说的地点，把原有点位悄悄丢掉。

先从 DR-poi-3 到 DR-poi-4，让 Navi 算路并添加点。DR-poi-5 读取添加结果，是整张图的依赖关口。只有这个具体点已经成功存在，才能向 DR-poi-6 设置临停属性。若失败或没有成功证据，则转 DR-poi-10，保留加点这一层的错误。

DR-poi-6 把临停绑定到正确地点。属性设置成功才到 DR-poi-7，同步最新路径与停靠意图；属性设置失败也到 DR-poi-10。两种失败都可能让用户没有停靠成功，但修复对象不同，一个是路线点没建立，一个是点有了却没有设好停靠要求。

DR-poi-7 到 DR-poi-8，智驾按条件在目标位置执行。此时先前设置完成也不能替代真实停车。进展与结果再到 DR-poi-9，Director 按事实告诉用户。DR-poi-10 的失败原因同样进入 DR-poi-9，不能只让成功路径有解释。

用这张图评审“再加一个点 D”时，除了看新点成功，还要核 A、B 的顺序和临停属性是否保留。用户只改一项，系统就应在这一项的范围内更新；不能用一次重新算路，把已经约定的停车要求一起清掉。

### guide DR-change-flow 先取消旧泊车目标，再允许新临停目标往下走

DR-change-1 是已有的负二层充电泊车任务。用户在 DR-change-2 说“到了靠边停就行”，是在变更同一个出行目标。到 DR-change-3，Director 把新要求与旧任务关系一起交专项层，不能只提取一句“靠边停”就新开第二个任务。

DR-change-3 到 DR-change-4 请求取消旧泊车，再由 DR-change-5 让系统 App 向 ADC 处理。这里发出了取消要求，仍要到 DR-change-6 读取消结果。图中明确把请求与结果隔开，避免刚点击取消就让新任务接着下发。

DR-change-6 确认已经取消后，才到 DR-change-7 设置目的地临停，再到 DR-change-8 跟踪新任务。如果取消失败、超时或没有结果，则走 DR-change-9 保留未解决状态，不自动推进新目标。进一步怎样恢复需要实际合同，不能用猜测填上一条自动重试箭头。

最后读 DR-change-8 时，检查的是新临停目标的真实结果。旧的指定泊位目标已经被用户改变，不应再记作成功完成。前后目标、取消事实和新执行结果一起保留，下一轮用户再问“现在会停哪里”，系统才有连续且一致的答案。

CLOSING

专项层最终也把真实进展交回整体对话，让 Director 决定如何回应。下面继续看输出链，你会发现“已经决定怎么说”“确认卡已经出现”和“用户真的听见、车辆真的完成”之间，还有几次必须接住的交接。
