## N19｜自进化：从专家知识到车自己学会你的习惯

还是车里那句延续下来的场景：用户说过一次“找停车场不要给我找立体停车场”，下次系统最好自动避开，不用反复交代；与此同时，品牌方也希望先把一套成熟的服务标准装进车里，让不同用户上车都先得到稳定的基础体验。这一章讲的自进化，就由这两条线组成：一条是品牌方先写好通用专家知识，告诉系统遇到这类场景应该怎么做；另一条是系统从用户每次表达和纠正里沉淀个性化规则，下次遇到相似场景自动用上。两条线指向同一个目标：不为每个长尾场景单独开发，而是用一套通用知识框架把个性化需求接住。

本章只讲知识从哪里来、怎样沉淀、下次怎样用上。N5 反思与自我认知讲一轮交互结束后系统怎样回看执行结果、找出偏差；N9 记忆层保存用户说过的事实、偏好和经历；自学习规则是可以复用的行动准则，它和个人记忆的边界目前还没有完全划清，本章在对应位置单独标注待核。

## 逐个场景开发接不住长尾，所以需要一套知识框架

先讲这一章要解决的问题。用户在车上说过一次偏好、纠正过一次做法，下次系统最好直接记住，不用反复交代；品牌方也希望把一套成熟的服务标准装进车里，让不同用户都先得到稳定的基础体验。如果逐个场景单独开发，成本太高，也覆盖不完用户五花八门的个性化要求。个性化需求本质上都是长尾需求，以前靠定制开发只能聚焦高频场景，长尾只能放弃；现在的思路是用一套通用知识框架把长尾需求接住，高频场景先做到稳定，长尾场景由框架和个性化规则组合覆盖。这套框架同时服务两类目标：面向用户，系统越用越贴合本人习惯；面向车企，品牌可以把本品牌认可的服务方式注入系统，达到品牌期望的体验水准。

专家知识要达到的专家感有三条标准。第一，系统对什么是好、什么是差有判断能力，知道好的标准之后会持续回看执行过程，主动发现问题并向标准靠近；第二，能关注到细节上下文，做出正确的行动决策；第三，知识只在需要的时机加载，既聚焦注意力，又节省上下文 token 成本。用户最终感受到的是操心更少、可以把大部分思考交给系统，收获更多情绪价值和实际便利，并且同类场景下表现稳定，不会时好时坏。这些期待决定了知识不能只是零散提示词，而要有分层结构、可校验标准和检索机制。

现有品牌知识并不是从零开始，它是二三月份赛力斯配合专家测试集结构编写的第一版，起始年份未在三份来源中核到【待核】，按场景分成一到四级，覆盖出行等领域。按 [专家知识现状及后续规划思路讨论](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef) 和 2026 年 9 月 9 日 [专家知识现状及计划讨论逐字稿](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe) 复盘，这一版有三类质量问题：一是具体案例被当成通用知识写进条目，换一个用户就不适用；二是系统当前并不具备的感知条件和执行条件，被写成了触发条件或判断逻辑；三是做法经验和考察点混在一起，know-how 写得不清楚，考察点也没有独立成标准。除内容质量外，落地机制也有三处缺陷：检索以 query 加上下文匹配目录树知识为主，缺少专门模块判定场景，多轮遵循效果差，长步骤任务容易丢失逻辑；多步骤任务插入现有 Director 链路后，打断和恢复机制会进一步干扰执行，任务成功率明显下降；专家级场景需要持续回看和迭代，这种特性无法直接适配现有 Director 架构，需要依托动态 Advisor 承载。

这一版旧知识在重构完成前不会整体废弃：团队先把其中质量可靠、场景匹配的条目挑出来临时使用，长期再按新框架重写。整体结论和阶段安排见 [专家知识现状及计划讨论智能纪要](https://bytedance.larkoffice.com/docx/BLgJd0WUeohjoVxTiqlcigpinch)。不先梳理旧版问题直接叠加新知识，会把案例化、条件缺失、标准混杂的缺陷继续带进新框架；不保留可用条目临时过渡，又会造成重构期间基础服务没有知识可用。

## 知识按抽象程度分成点、面、体三层

画板主标题“三层知识结构 × 两条知识来源 × 自学习闭环”概括了本章骨架：三层是点、面、体，两条来源是品牌通用知识和用户自学习规则，闭环是观察、沉淀、复用。三层之间是分而治之的关系：大场景拆成小情景，小情景再落到点状经验。分三层的原因是不同抽象程度的知识，形态、载体、检索方式和使用主体都不一样，平铺混在一起会导致存储混乱、检索不准；分层之后，专家注入的知识和自学习生成的知识可以复用同一套结构框架，降低后续对接成本。

**N19-1（点状知识）**是最碎的一层，指特定工具的使用技巧、特定任务的细节思路，对应一个原子动作。例子包括搜音乐什么时候该走联网工具、找停车场不要推荐立体停车场。点状知识只给当下可参考的小技巧，没有统一的好坏标准，也不要求系统持续复盘；好处是加载快、见效直接，缺点是零散、不稳定，今天想到就照做，明天没想到就漏掉，也不能举一反三。这类知识游离在场景框架之外，独立匹配即可，当前形态与成熟度仍在讨论中，不写成已上线能力【讨论中，待核】。点状知识解决的是单个动作的技巧问题，它不承担把一件长程事情做完的责任；如果所有经验都只沉淀成点状，系统表现会像一个没有标准流程的人，靠临场回忆碎片应对任务，稳定性和专业度都上不去。

**N19-2（面状知识）**面向某一个情景或某一类长程任务，把事情拆成阶段和步骤，每个环节都给出系统可以自己判断是否达标的标准；标准必须能让模型通过对应工具或数据客观判断是否达成，同时配上检查点、注意事项、异常原因和对应预案。以接人为例：先和用户确认会合点，规划线路，提示怎样通知被接人，接近目的地再通知，每一步都有对应标准，系统可以一步步复盘推进。面状比点状稳定，因为它有完整框架；但要写出一套面状知识，作者必须在这个场景里非常资深、经验丰富，还具备抽象能力，普通整理很难写到位。面状知识主要供动态 Advisor 调用，主链 Director 只需要知道怎样把任务创建出来。这一层的模板形态和承载架构仍在讨论中【讨论中，待核】。面状知识里的标准之所以要求可客观校验，是因为动态 Advisor 需要据此自主回看执行效果、分析偏差原因并选择预案；标准如果只是主观感受描述，模型无法判断当前是否达标，也就无法持续迭代。Director 与动态 Advisor 的知识分工不同：Director 偏任务澄清、拆分和过渡话术，复杂长程任务做到专家级表现交给动态 Advisor。

**N19-3（体状知识）**是最高一层，对应更宏观的体验标准，比如什么才算一次好的自驾游、一次轻松的长途出行。一个大场景里包含无数小情景，体状标准看的是整段旅程有没有创造好的回忆、过程是不是足够轻松；发现达不到标准时，系统还可以自己拆出小任务去追踪改进。这一层目前还没有想清楚，强依赖后续动态 Advisor 的设计，现在只保留方向，不展开具体形态【讨论中，待核】。体状知识解决的是跨多个情景的整体体验评价问题：一次长途出行包含出发、路途、休息、到达等多个面状任务，单看每个步骤达标不等于整体体验好，需要一层宏观标准回看全程；这一层能否成立，取决于动态 Advisor 是否具备持续追踪、自主创建子任务和效果校验的闭环能力。

在落地形态上，当前讨论倾向于不再设计复杂的层级嵌套，只区分点状游离知识和面状结构化知识两类，避免存储混乱；两类知识的检索逻辑和使用主体不同，点状知识通过检索匹配，面状知识供给动态 Advisor；全类型知识复用同一套结构框架，后续专家注入和自学习生成的知识都能直接适配，降低对接成本。单条知识的范式包含两部分：一段文字化的精炼知识陈述，加上一组 ReAct 式示例，每一步带思考过程，用来强化思维范式和泛化能力。知识检索有三类依据：根据当前 query 检索，根据进行中的任务或目标匹配检索，根据当前情景类型和上下文检索。

检索输入包括当前 query、近期对话历史、进行中的目标队列、最新车辆状态和已加载知识列表，输出新增和移除的知识 ID，规则见 [动态知识检索与使用需求说明](https://bytedance.larkoffice.com/wiki/EZ0PwsuFjiCg85kJqu8cmQRinLb)。车辆状态信息优先级高于对话历史中的车辆状态描述，防止用户口头说法和实际车况不一致时检索依据失真。输出为严格 JSON，包含新增知识 ID、移除知识 ID 和新增、移除理由；理由部分用于后续分析迭代，运行时只解析知识 ID。检索遵循五条原则：场景绑定推理，先结合 query、历史、车况和舱内视觉判断当前具体场景，再匹配知识；关注环境变化，变量趋势比绝对值更有决策价值，例如温度急剧上升、车内人数增加、车辆进入地库分别触发不同知识；目标持续关联，只要进行中的目标存在，支撑该目标的知识持续保留，目标明确终止才移除，目标变更时同步替换；增量更新，对比已加载知识只输出变化部分，失效知识及时删除；信息不足时不虚构，需求模糊且无法推断场景时新增列表保持为空，交由下游进一步确认。这套动态加载替代把所有知识写死在系统提示词里的做法，目的是在有限上下文内只装入当前场景需要的知识。

## 左边来源：品牌通用专家知识

**N19-4（品牌通用专家知识）**是品牌方先写好的一套服务标准，也就是赛力斯先整理的现有版本，按场景分一到四级，覆盖出行领域。它解决的问题是：基础模型本身具备通识能力，但品牌希望把本品牌认可的服务方式、话术尺度和场景判断先教给系统，相当于出厂前给豆包做一次品牌培训；没有培训到的场景，仍然使用模型原本的通用能力。品牌知识大部分各车型通用，迎宾等少数场景可以按品牌、车型调性定制装载，模块化切换。旧版本质量问题和重构方向见前文，现有版本属于已经存在的品牌知识版本，不等于重构完成的新体系。

品牌知识放置位置受架构方案影响。如果仍由 Director 做任务，非长时类专家知识动态或静态放入 Director 系统提示词，长时目标类知识考虑下放到任务智能体；如果由 Director 做任务分发、领域 Agent 做任务，知识按类别放入不同领域 Agent 的系统提示词，Director 只保留弱领域特性知识，例如怎样聊天更有趣、怎样更好安慰人，以及复杂任务澄清和拆分的专家知识，长时目标类知识同样下放任务智能体。品牌调性差异主要体现在主动性强弱、氛围营造风格和迎宾等少数场景，车控、导航等基础场景的服务标准多数通用；不同车型上线时装载对应品牌的一套专家知识，未培训场景回落到模型通识。如果品牌标准不注入，不同车型和品牌会共用同一套模型默认风格，无法满足车企对服务尺度和调性的差异化要求；如果把品牌差异扩大到所有场景，又会造成知识重复生产和车型之间难以复用。

## 右边来源：用户自学习个性化规则

**N19-5（用户自学习个性化规则）**把用户明确说过的偏好和纠正沉淀下来，下次遇到同类场景自动用上；比如用户说不喜欢立体停车场，之后找停车场就自动避开这类车位。它和记忆的区别目前还没有划清：哪些话存成个人记忆、哪些沉淀成可复用的规则，需要后续专门对齐，边界不清会造成同一信息重复存储或互相覆盖【待核】。沉淀形态也有两种可能：直接更新专家集，或者在专家集之上解耦叠加一层更高优先级的规则，两种形态尚未确定【待核】。

自学习规则与品牌专家知识在结构上应当保持同一套框架，只是生产方式不同：品牌知识由专家和人工 review 后注入，自学习规则由系统在被用户纠正后自行挖掘沉淀进同一结构。这样做的原因是同一结构才能共用检索、优先级和审核机制，避免个人规则另起一套存储导致检索不到或冲突无法仲裁。自学习要达到的第一层目标是可调教：用户指出哪里做得不好，系统把指导记下来，下次做同类事情改进；用户持续关心的事项，系统逐步都能做好。第二层目标才是从运行日志里自主提炼新知识，覆盖长尾需求。在现有知识还不能被模型稳定遵循之前，不急于开放新知识沉淀，先保证给定知识能被稳定执行、更换知识后同样遵循，这是自学习分阶段推进的前提。

**N19-7（优先级）**当前倾向是用户自学习沉淀的个性化规则优先于品牌通用知识，两者冲突时以用户当下要求为准。更完整的层级顺序和冲突覆盖规则还没有核验结论，不能当成已定规则对外讲【待核】。优先级规则要解决的是品牌标准和用户本人偏好不一致时听谁的问题：品牌知识保证基础体验底线，个性化规则覆盖用户本人的特殊要求，个人要求应当覆盖通用标准；但除用户规则高于品牌知识之外，自学习规则、记忆、顾问建议和工具结果之间的完整冲突顺序仍需架构方案确定。如果品牌标准长期压过用户明确要求，系统会显得刻板，反复违背用户意愿；如果个人规则可以无约束覆盖一切，又可能在用户临时情绪表达上固化错误偏好，所以需要完整层级和审核机制配合。

## 自学习闭环：先改进单车体验，再提炼公共知识

知识沉淀要跑通，靠的是 **N19-6（自学习闭环）**，闭环顺序就是画板上的观察到什么、沉淀成什么、下次怎么用上。第一层面向这台车的体验：用户指出哪里做得不好，系统把指导记下来，下次做这件事时改进。第二层面向公共知识：再设一个环节从大量交互里提炼共性，判断哪些是模型本应做好却出错的地方，经过人工核对后升级成通用知识，既优化单车体验，也优化整套知识体系。自学习分两步走：先保证现有品牌知识能被模型稳定遵循，再扩展从用户交互里沉淀新知识。内部验证阶段口述的规则可以先沉淀为公共动态示例，正式开放后转为用户个人规则【讨论中】。

两层闭环对应两类价值。第一层面向单车和单个用户，把用户的指导转化为本车后续行为改进；第二层面向全量车型和公共体系，相当于一个系统健康检查器，从大量单车沉淀里筛选共性问题，识别模型本应做好却反复出错的地方，人工核对后升级为通用知识。专家知识与自学习的本质区别就在生产方式：专家知识是有人 review 之后注入系统，自学习是系统通过不断被教育、沉淀，自己挖掘出知识再送入同一结构。闭环方向先单车后公共，是因为公共提炼需要足够样本和稳定的单车沉淀机制，直接从少量交互归纳通用规则容易以偏概全。

用户对自己沉淀下来的规则能不能看到、能不能修改、能不能删除，目前还没有定论；如果不能删除，系统记错之后用户没有纠正入口，错误偏好会一直影响后续体验，这是评审要盯住的风险。闭环跑通还有前置条件：各类触发器和感知信号要先全量接入，是否使用可以后续按需订阅控制，避免源头漏接、将来想补接却接不上；专家知识只在需要时按需加载，用来节省上下文成本。信号有没有接入和规则要不要订阅是两件事：源头先把传感器、触发器和事件信号接全，主动服务模块可以通过订阅控制是否使用和触发频次，不能为了降频从源头不接信号，否则未来需要时无法补接。动态 Advisor 必须先跑通自主回看、问题分析、方案迭代和效果校验的完整闭环，专家知识体系才能在其之上落地；依赖的感知能力和原子工具如果缺失，知识里写的好坏标准没有数据和工具可判断，属于巧妇难为无米之炊。

## 成本分层与 12 月底专项

**N19-8（成本）**区分不同定位车型：主打影响力的首发车型优先保障能力上限，不计短期成本，相当于品牌广告投入，待首个 OTA（over-the-air，远程在线升级）周期后可按需降级；后续走量车型采用成本更低的轻量模型方案压缩成本，不同定位产品承担不同使命，不要求统一成本标准。专家知识只在需要时按需加载；具体哪些能力保留、哪些延后，目前尚未列出清单，需要按车型方案逐项核对【待核】。成本分层的理由是首发车型承担展示能力上限、建立市场信任的使命，预算允许换取体验高度；规模化走量车型以单位成本可控为目标，端状态接入数量、模型规模和情感能力都可按成本档位裁剪，两类产品商业模式不同，不能用同一套成本标准考核。轻量模型方案在纪要中简称 SMT，全称未在一手资料中确认，本章不展开其技术细节【待核】。

**N19-9（12月底专项）**是已排期的自学习专项，目标是先定清自学习能学什么、学到什么程度、达到什么效果。2026 年 9 月 9 日讨论后，团队计划组织专项会议，对齐赛力斯 SOP（标准操作流程）节点 12 月底自学习可落地的范围、效果标准和模块分工。当前这不是已上线能力，落地范围以专项结论为准【待核】。本章讲的知识分层、品牌知识重构和用户自学习，整体仍处在讨论和规划阶段；现有版本品牌知识属于已经存在的旧版本。

知识体系建设按月份推进节奏，阶段划分见 [专家知识现状及后续规划思路讨论](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)：9 月先理清整体架构方案，尤其是 Director 新架构和异步任务体系；10 月根据新架构定义专家知识结构，优先做被动交互、可直接放入 Director 的知识，其次做高频且相对简单的场景，同时搭建场景识别等检索基础、输出检索方案和提示词，并用内部手写知识在实车验证；11 月形成标准知识生产要求，协同车企成员批量生产知识并批量测试验收，再根据实际表现优化知识本身和检索效果。这条节奏把架构、结构、检索、生产、验收依次排开，避免在架构未定阶段批量生产无法适配的知识。自学习专项还要专门对齐沉淀与个人记忆的边界、条件任务触发与激励关系，这些议题与记忆、主动服务模块互相勾连，在专项结论落地前保持待核口径。

## 本章边界与待核口径

知识和个人记忆的边界、面状与体状知识的模板形态，分别回到 N9 身份记忆章和后续专项讨论，本章只讲知识沉淀这一条线。当前没有已上线的自学习功能可以验收；已计划的专项需要先对齐目标范围，包括能学什么、学到什么程度、达到什么效果，范围以专项结论为准。回到游泳馆例子：用户这一程对餐厅、停车和路线提出的纠正，短期先作为单车经验沉淀，专项跑通后再判断哪些上升为可复用规则；品牌通用知识保证基础服务稳定，个性化规则在其上覆盖用户本人的特殊要求。事件日志和记忆分层归 N9 章，一轮结束后的回看纠错归 N5 章，动态 Advisor 的任务生命周期归 N18 章。

评审沿四个顺序核对。第一，自学习规则和个人记忆的边界划在哪里：哪些用户表述存入记忆、哪些沉淀为可复用规则，边界不清会重复存储或互相覆盖。第二，自学习规则的沉淀形态是更新专家集还是叠加更高优先级规则：两种形态对后续检索、冲突仲裁和用户删除能力的影响不同，需要在专项中定案。第三，除用户规则高于品牌知识外，完整优先级层级和冲突覆盖规则是什么：当前倾向不能表述为已定层级。第四，用户对自学习规则的查看、修改、删除入口是否具备：缺少纠错入口时错误偏好会持续放大。同时核对感知信号和触发器是否全量接入、动态 Advisor 的回看闭环是否先跑通，这两项是知识体系落地的前置条件。

待核口径集中在八处：自学习规则与个人记忆边界未对齐；沉淀形态两种方案未定；N19-7 完整层级与冲突覆盖仅有当前倾向；面状、体状模板强依赖动态 Advisor 设计；走量车型延后清单和轻量模型覆盖范围未列；12 月底专项可学范围、学习程度、效果标准与分工以专项结论为准；用户查看、修改、删除规则能力尚无定论；点状知识检索方式、面状知识供给动态 Advisor 的分工仍属方案预期。以上各项在专项结论或新方案文档落地前，正文均按【讨论中】或【待核】陈述，不写成已上线能力或已定规则。

## N5｜反思与自我认知

前面几章讲的都是用户开口、系统办事。还有另一半工作是系统对着自己做：用户拒绝了一条建议、执行失败了、随口聊出一句感受，系统要回头看看这次哪里做得不对、用户是什么倾向，下次能不能接得更顺。这一章讲反思与自我认知。

这里要和后面讲知识沉淀的章节分开：N19 讲专家经验和品牌用车知识怎样沉淀进来，这一章讲系统怎样回看自己的交互，形成偏好、情绪和人设。N5 的偏好来自系统回看自己这一轮交互后形成的背景倾向；把经验沉淀成可复用规则、品牌专家知识入库，归 N19 自进化一章。这一章除记忆 Agent 已打通外，反思层和内心向能力大多还在规划中，会上只讲目标和边界，不讲成已经会自动持续学习。

## 一张图分反思层和内心向模块，内心向模块不直接控车也不播报

这张图分两层。上面是反思层，系统从对话和执行过程里回看自己；下面是几个内心向模块，分别维护人设、情绪、记忆和探索。它们统一的职责是给主 Agent 提供背景，本身不直接控制车辆，也没有对外播报的出口。图里灰色虚线框表示这部分在当前版本还没有承载，会上只讲目标，不能当成已经上线的能力。反思素材来自两类来源：一类是对话和执行过程里产生的原始交互，包括用户反馈、车上发生的事件、探索内容；另一类是系统自己留下的执行记录，比如工具返回结果、车控执行回执。这些原始记录先沉淀到记忆里，作为后面复盘的素材，反思层本身不另存一套用户数据。内心向四个子 Agent 的分工与触发方式，见 [豆包 incar1.0 长期架构梳理](https://bytedance.larkoffice.com/wiki/XM8GdtFsTok8CwxcMrKcywMmnQg)。

这一章要解决的问题是：车载助手怎样从每一次对话和执行里积累经验，而不是每一轮都从零开始回应。没有反思机制时，系统只能依赖预设规则和当前上下文，用户拒绝过的建议下一轮还会重复提出，执行失败的原因也不会被归类和改进；有了反思层，系统才能区分哪些反馈需要当场接住、哪些可以离车后慢慢复盘，哪些反复出现的倾向可以沉淀成长期偏好。把反思和内心向模块放在同一张图里，是因为复盘得到的结论最终要进入人设、情绪、记忆和探索这几个背景模块，再影响下一轮表达；它们共同构成系统的自我认知，而不是一套独立于对话主链之外的后台统计程序。

为什么内心向模块必须和对外执行模块分开，而不是让每个专业 Agent 自己维护情绪和人设，原因在于对外表达需要统一。如果舒适、出行、内容等子 Agent 各自带一套人设和情绪，同一轮里多个建议的语气和立场会互相冲突，用户听到的是几个性格不一致的声音。把人设三观、情绪状态、记忆和自我探索收为内心向模块，只产出背景材料，由主 Agent 统一组织语言和动作，才能保证整段对话立场一致、语气连续。内心向模块也不直接控车：它们不调用车控工具、不发布任务指令，只回答“以什么立场、什么情绪、带着什么记忆开口”这类背景问题，动作和工具选择仍归主 Agent 与工具层。

## 反思层三路：实时反思、离线反思、偏好优化

N5-01（实时反思）在对话进行中即时总结这一轮反馈和事件，形成短期记忆候选。它的输入是这一轮用户说法和工具执行结果，产出写进短期记忆区；这一路还在规划中【讨论中】。实时反思解决当场能不能接住反馈的问题，执行失败或被拒绝之后先在本轮留下复盘线索。当场需要复盘的场景包括用户明确拒绝了一条建议、工具执行返回失败、用户打断正在进行的播报、用户纠正了系统刚才说错的事实；实时反思把这一轮的输入、系统动作、用户反应和结果记录成候选，供后续离线复盘和偏好判断使用。之所以要在本轮留下线索，是因为离车之后再回看，本轮的上下文顺序和现场语气已经丢失，当场记录才能保住归因所需的原始材料。

N5-02（离线反思）在用户离车、车辆闲置之后异步把整段对话重新复盘，像“教练真凶”这类主观感受被压成长期记忆候选，写进长期记忆，排在 2.6 目标范围内，时间节点为 10 到 11 月【2.6 目标】。在线反思解决当场能不能接住反馈，离线反思解决长期能不能沉淀下来；两条线分开，是因为当场要保证主链路响应速度，不能把整段复盘塞进用户正在对话的这一轮。离线复盘可以调用更长的历史记录，把一天内分散的对话串起来判断：同一件事被拒绝几次、出现在什么场景、用户当时的语气和后续行为如何，再决定压缩成哪一类长期记忆。离线反思机制设计文档当前未取得可读链接，具体触发频次和覆盖范围以 2.6 阶段方案为准【待核】。如果不做离线复盘，当天对话里反复出现的偏好和情绪线索只能散落在短期记录里，第二天上车无法形成稳定认知；如果把复盘放在行车过程中同步执行，大模型总结会和用户对话争抢算力，首字耗时和执行稳定性都会受影响。

复盘得到的倾向交给 N5-03（偏好优化）：按用户长期的采纳和拒绝调整推荐策略。这里有一条底线，拒绝一次不等于永久偏好，单次拒绝只能作为证据之一，要结合多次行为再判断，避免用户一时不想要就被永久打上标签；这样处理是为了让偏好跟着长期稳定的行为走，而不是被某一次情绪或临时需求带偏。证据链同时记录用户采纳和拒绝过的提案、提案所处场景和后续反馈，偏好优化在多次证据方向一致之后才调整推荐权重；场景发生变化时，同一条偏好也要按场景区分，例如用户工作日拒绝轻音乐不等于周末也拒绝。这条偏好优化和系统学习能力共用同一份证据链，目前仍在规划中【讨论中】。不设多次证据门槛的风险很直接：用户某次开车赶时间拒绝了闲聊，系统就永久把情感陪伴关闭；用户某天不想听某首歌，系统就从推荐里删掉整个歌手，短期波动被固化成长期标签，体验会越来越窄。

反思产出按用途分成三类：长期记忆、能力改进和问题归因。长期记忆沉淀用户偏好和经历，能力改进指推荐策略和话术策略的调整，问题归因要区分模型能力问题、工程链路问题和其他来源：模型能力问题是理解或生成本身出错，工程链路问题是信号、接口、超时或工具回执异常，其他来源包括用户表述不清、外部服务不可用等。当前埋点能否稳定区分这三类，需要在方案落地时核对【待核】；归因混在一起时，复盘无法指导对应团队改进，模型侧会替工程链路背锅，工程侧也发现不了接口问题。Director 对话推理引擎在模块职责里明确把从用户反馈、错误反思和情景学习构建自我迭代能力列为长期方向，本章反思层对应这一方向在车载场景的落地形态，模块定义见 [Director（对话推理引擎）PRD v1.7](https://bytedance.larkoffice.com/wiki/XRuKwJ0VPisdUhkxH0ecY1rRn9g)。

## 四个内心向模块只产出背景，开口说话的永远是主 Agent

N5-04（人设三观）持续更新豆包的动机和价值体系，由定时触发或用户聊到深层话题触发，输入是历史对话和原有人设，产出更新后的人设背景。目标是让决策有一致的逻辑和真实感、和用户立场对齐，同时保留新鲜感、有自己的立场；面对目标冲突时，由这套价值观做综合判断。这个模块只产出背景，不自己开口说话，这一路还在规划中【讨论中】。人设三观模块解决的是系统立场前后一致的问题：面对主动提醒会不会过度打扰、遇到用户隐私请求怎样婉拒、不同场景下优先照顾舒适还是效率，这些取舍都需要一套稳定的价值顺序，而不是每轮由模型临时决定。触发方式有两种，定时触发用于周期性回顾长期交互并微调价值观，深层话题触发用于用户谈到世界观、人生观、价值观时即时吸收立场信息；模块读取自身初始设定、交互历史和自身经历，输出更新后的人设和三观，不调用外部工具。如果人设每轮都由主模型自由生成，立场会随上下文漂移，同一个问题上一轮热情推荐、下一轮保守拒绝，用户感知到的就是性格不稳定。

N5-05（情绪状态）维护当前情绪。情绪会随这一轮事件变化，也会随时间衰减，但不归零，而是趋向个性化的情绪基线；相邻几轮之间情绪要能继承；画板登记为 5 轮以内，长期架构梳理写短期情感记忆存储最近 5 到 10 轮对话产生的情感变化，两处轮数口径不一致，最终继承范围由算法侧统一【待核】；情绪记录挂在人脸身份或账号上，不混到另一位乘客身上。情绪递归更新可概括为新情绪等于当前情绪乘保持系数加事件影响乘敏感度，再加记忆权重乘过往相关情绪的召回影响，具体权重由算法方案确定【待核】。它同样只产出背景，不自己开口说话；这一路在规划中【讨论中】。情绪输出供语音到语音端到端对话（speech-to-speech，S2S）做情感演绎使用。

情绪判断依据三层信息。第一层是当前情景：和谁在一起、双方关系、对方状态、正在做什么，现场已经发生和正在发生的事情，周围有哪些对象，处在什么空间位置；第二层是未来可能发生的事情，例如马上要进入假期；第三层是之前情感轨迹的延续，情绪是连续变化而不是离散跳变。短期情感记忆保存最近若干轮对话产生的情绪变化并高频访问，长期情感记忆记录重要情绪节点和总体情感基调，塑造个性化互动。没有新刺激时情绪按指数衰减，不同情感维度衰减率不同，积极情绪衰减较慢，紧张情绪衰减较快；衰减不会归零，而是趋向个性化设定的情感基线。情绪状态模块的感知输入包括车内成员身份、状态、行为和表达内容，环境信息与事件，任务信息和状态，正在播放的内容，天气和堵车等环境背景，以及出行目的；记忆里保存近期情绪轨迹、用户近期情绪和近期重要事件。把情绪做成连续轨迹而不是单轮标签，是为了避免上一轮还在轻松闲聊、这一轮突然变成严肃语气；衰减到基线而不是清零，是为了让系统在安静等待时保持符合人设的常态，而不是情绪空白。情绪绑定身份是为了防止主驾和副驾的情绪互相串用，换人之后上一位乘客的情绪基调不延续到下一位。

已经打通的是 N5-06（记忆 Agent）：反思形成的长期、短期候选由它完成增删改和重要性区分。记忆怎样分层、按什么触发生成，归 N9 记忆生产一章讲，这里只把它作为反思素材的落点。记忆 Agent 是这一章当前真正在主链路上工作的部分，其他内心向模块围绕它提供补充背景；它的短期、长期记忆准出口径与 N9 章一致，本章不重复承诺指标。记忆 Agent 的触发时机包括用户主动要求记住或遗忘某件事、到达指定沟通轮次、到达指定时间、用户离车闲置，以及发生值得关注的事件，例如看到雪山、彩虹或有人哭泣；输入是近期对话、交互、场景描述和历史记忆，输出记忆的新增、合并、删减、描述加工和呈现形式变化。它读取全部历史用户交互日志、自身运行日志和其他 Agent 的运行日志与记忆，保证反思结论有完整证据来源；除记忆库写入工具外，还可使用图像和视频生成工具把记忆具象化。反思层产出的候选必须先经过记忆 Agent 的组织和重要性区分，才能进入后续背景，避免未经筛选的复盘结论直接影响对话。

N5-07（自我探索）是另一条规划中的能力【讨论中】：唯一触发时机是用户离车闲置，按照豆包自己的兴趣、用户兴趣和近期话题去外部浏览探索，沉淀成探索记忆和文件。它不和行车任务争抢时机，也不会在用户正在对话时自行展开。画板举例：离车后系统浏览相关内容，记下看到的人脸机器人，第二天上车才有谈资；这一路同样不占用行车时的主链路资源，探索到的内容经过筛选后才允许进入背景。自我探索模块的输入包括自身兴趣爱好、用户兴趣爱好、最近聊过的话题和最近消费过的内容，输出沉淀下来的探索记忆，以及音频、网页、PDF、图片、视频和链接等文件；工具包括浏览各类应用和网站的通道、网页读取工具，以及 PPT、图像、视频等内容加工工具。设置唯一离车触发时机，是因为行车过程中外部浏览会占用网络和算力，还可能在用户对话时插入未经准备的谈资；探索内容先沉淀为记忆和文件，第二天由主 Agent 判断是否适合提起，而不是探索到什么就当场说什么。可访问的外部平台范围、二次加工规则和合规过滤要求，当前方案文档未取得正文【待核】。

## 背景打包注入主 Agent，跑完一轮再异步回流形成闭环

到 N5-08（打包 context 注入），也就是把背景打包进这一轮：人设三观决定豆包以什么立场开口，当前情绪状态决定语气基调，用户记忆和近期探索记忆提供具体谈资，三样东西一起打包，作为背景交给主 Agent 的系统提示词（SP，即交给模型的预设指令）与用户提示词（UP，即本轮输入模板）。这里要强调，内心向模块没有自己的播报出口，排障时不能去找“情绪模块说了哪句话”，说什么话始终由主 Agent 决定。打包环节要解决的是背景组装顺序问题：人设属于长期稳定信息，放在系统提示词里固定生效；情绪、近期记忆和探索内容属于本轮变化信息，放进用户提示词或上下文队列；如果把所有背景都堆进系统提示词，长期不变的人设会挤占本轮可变信息的位置，反之如果人设每轮临时拼入，立场一致性又会下降。

N5-09（主 Agent 组织语言和行为）收到这份背景之后，自己判断这一轮怎么开口、用什么语气、要不要主动提起昨晚看到的谈资。对外出声的永远是主 Agent，它是唯一的思考主体。主 Agent 跑完这一轮之后，新的交互和事件再异步回流到反思层，形成下一轮复盘的素材，这就是这张图的闭环。对照 Director 模块输入类型，主链收到的内容包括用户输入、顾问建议、工具反馈和事件四类；主 Agent 的上下文里同时装有人设人格和聊天风格、可用工具与表情、静态和动态示例、场景知识、能力边界、车辆知识、感知上下文、用户记忆和画像，内心向模块提供的人设、情绪和记忆正是其中长期背景部分。闭环方向是单向回流而不是实时改写：本轮对话结束后，新的反馈先进入记忆和反思候选，经过离线复盘和审核再更新背景，不在对话进行中临时修改人设和情绪规则。

这一闭环解决的是经验怎样积累又不污染当场对话的问题。实时反思留下本轮线索，离线反思离车后批量复盘，偏好优化按多次证据调整策略，内心向模块把结论整理成背景，打包注入主 Agent，主 Agent 统一表达，新一轮交互再回流。不形成闭环时，系统每次都只使用出厂设定和当前车况，无法随用户长期使用变得更贴合；闭环缺少审核环节时，错误复盘结论会被直接写进长期记忆，后续对话持续放大错误判断，这也是长期记忆和能力改进上线前需要人工或规则审核把关的原因。

## 沿游泳馆案例走一遍，以及评审要盯住的规则和口径

沿游泳馆案例走一遍：导航结束下车，主驾随口说“昨天那个教练真凶”，N5-05（情绪状态）记录下对游泳教练的这层感受，属于未来才会承载的能力；离车后 N5-02（离线反思）把这段对话压缩成长期记忆，N5-07（自我探索）在闲置时浏览相关内容；第二天上车，N5-08（打包 context 注入）把人设、情绪、记忆和探索一起交给主 Agent，N5-09（主 Agent 组织语言和行为）决定主动聊起昨晚看到的人脸机器人。把案例拆成环节看：当场对话时主 Agent 只完成导航和正常回应，情绪和复盘不在本轮阻塞链路；离车后离线反思把“教练真凶”这条主观感受连同场景压缩成候选记忆，自我探索按近期话题浏览外部内容并沉淀文件；第二天上车，记忆 Agent 取回这条经历，情绪状态给出延续的语气背景，探索记忆提供谈资素材，打包进主 Agent 上下文后，由主 Agent 判断主动提起的时机和措辞，而不是情绪模块或探索模块直接开口。

这一章有六条边界要讲清。第一，反思是系统对着自己做的动作，不是用户主动下达的指令；除记忆 Agent 已打通外，实时反思、偏好优化、人设、情绪和自我探索在当前版本都未承载，不能讲成已经会自动持续学习【讨论中】。第二，反思产出分三类：长期记忆、能力改进、问题归因；问题归因要能区分模型能力问题、工程链路问题和其他来源，当前埋点能否稳定区分三类需要核对【待核】。第三，记忆 Agent 的短期、长期记忆验收口径见 N9 记忆生产一章，本章只核对反思产出是否经过审核再进入背景。第四，情绪状态随事件更新、随时间衰减到个性化基线，相邻若干轮内继承情绪，超过轮数不再带入；情绪记录绑定人脸身份或账号，换人不继承。第五，自我探索只在离车闲置触发，行车过程中不启动外部浏览，探索内容经筛选后才进入背景。第六，内心向模块只产出背景，对外语音、表情和动作取舍统一由主 Agent 完成，排障时按这条归属定位问题。

评审沿三个顺序核对。第一，在线反思和离线反思的边界划在哪里：哪些问题必须当场归因、哪些可以等离车再复盘，边界不清会让在线反思占用主链路资源，影响实时响应。第二，反思出来的长期记忆怎样保证不污染用户真实偏好：反思结论不一定正确，直接当成偏好去推荐，会在后续对话里持续放大错误判断。第三，问题归因分模型能力、工程链路和其他几类，现在的记录能不能区分开：混在一起就分不清该从模型侧还是工程侧改进，复盘得不出有效结论。

三条目标口径如下，均属于方案目标。在线反思覆盖率：用户拒绝建议或执行失败后必须触发归因，统计触发次数除以应触发场景次数【2.6 目标】。离线反思频率：每天一次，每次覆盖当天全部对话，统计复盘批次和覆盖对话范围【2.6 目标】。反思产出可用率：长期记忆和能力改进必须经过人工审核才能进入使用，未审核产出不计入可用【讨论中】。这些口径在可读的方案说明文档中尚未核对到准出数值，落地前以最新 2.6 评测方案为准【待核】。

边界上要讲清：反思结论不一定正确，直接当成用户偏好就会出错；长期记忆和能力改进上线前需要审核把关，自我探索得到的内容同样要经过筛选再进入背景。除记忆 Agent 已打通外，实时反思、偏好优化、人设、情绪和自我探索都还是规划方向，不与现行主链路能力并列讲。Director PRD 把内心世界、人设人格、情绪情感和自我成长列为长期方向，要求从用户反馈、错误反思和情景学习构建自我迭代能力，当前主链只承载其中已经打通的记忆部分。下一章看进入推理之前，这些背景怎样被筛选、打分和压缩。
