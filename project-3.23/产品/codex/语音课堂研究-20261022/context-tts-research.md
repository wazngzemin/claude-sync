## 课堂一：为什么要在听清文字前，先给 ASR 提供热词

“我们先看一个具体问题。用户明明说的是通讯录里的一个人名，车却转成了几个常见字。后面的 Planner 再聪明，也只能接着错误的文字去理解。所以这一步先解决‘听成什么字’，还没开始决定‘要办什么事’。”

ASR 是语音识别，在这条链路里接收用户音频，输出识别文字。热词是提供给 ASR 的候选名称，例如通讯录的人名、当前导航目的地、正在播放的歌名。S1 写明云端维护热词和对话上下文，在 ASR 建联前读取候选热词及最近对话，也会在 ASR 上行链路中读取并注入。

“你可以把这里的产品规则记成：我们把当前车里很可能会被提到的名称告诉识别服务，让它更有机会听对。热词不是强制替换表。文档已经提醒，注入以后也不会 100% 生效。”

| 热词/辅助信息 | 为什么和当前语音有关 | 已写明的数据来源 | S1 的数量 |
|---|---|---|---|
| 人名 | 用户可能叫联系人、当前乘客 | 蓝牙通讯录 contact_name；乘客身份 system_control_0003 的 name | 1000 |
| 导航地点 | 用户可能复述目的地或途经点 | navigation_0004、navigation_0007 的 poi_name | 500；标记需要冷热处理 |
| 媒体 | 用户可能复述歌名 | media_0001 的 audio_name | 1000；标记需要冷热处理 |
| 可见即可说词 | 用户可能念当前页面按钮或内容 | 车企按页面注册；页面切换时获取 | 500 |
| 车控专有名词 | 用户会说车型特有功能 | 固定配置，可按车企车型调整 | 1000 |
| 最近对话 | 连续对话里会再次出现前面说过的内容 | 用户与车机的语音交互 | 5 轮 |
| 车辆位置 | 帮助地点识别 | navigation_0002 的 address | 未写数量 |

“冷热处理”的具体频次、多久淘汰、容量满了删什么，S1 没写；S2 无权限。课堂只能解释“导航和媒体词需要做冷热处理”，不能编造“只保留 7 天”“最近访问优先”之类具体规则。

画图应当放在 ASR 的输入侧：端状态/通讯录/页面词 → 云端热词与最近对话 → ASR 识别。不要画成 Planner 理解错以后才补热词，也不要把“1000 个”写成每个用户当前已有 1000 个词。

## 课堂二：本地已经执行了，为什么还要告诉云端

“比如用户先说‘打开车窗’，这一句命中了当前允许在本地处理的车控，车端已经执行。接着用户说‘再开一点’。第二句如果交给云端，而云端不知道前一句做了什么，它就可能不知道‘再开’指什么。端云同步解决的就是这类连续对话断档。”

这段是教学示例，不代表‘打开车窗’在任意车型、网络、配置下一定走本地。S1 的明确前提是“可见即可说或简单车控且本地命中”。

| 顺序 | 谁做什么 | 输入 → 输出 | 这一步为什么必要 |
|---|---|---|---|
| 1 | 端侧判断本地是否命中 | 用户本轮文字 → 命中/未命中 | 只有命中当前本地能力才进入本地处理 |
| 2 | 命中则端侧执行并生成回复 | 本地动作 → 实际执行结果与回复 | 不能只记录用户提了要求，漏掉实际结果 |
| 3 | 端侧调用 context/sync 同步 | Query + Answer + Observation → 云端对话历史 | 后续云端理解能接上本地发生过的事 |
| 4 | 后续请求组装上下文 | 当前话 + 最近历史/车况等 → Planner 输入 | 支撑“再来一个”“刚才那个”等连续表达 |
| 未命中 | 进入云端正式链路 | 最终用户文字 → 云端拒识/Context/Planner 等 | 本地没办成，不等于系统没有其他能力 |

Query 是用户本轮说的话；Answer 是系统给用户的回复；Observation 是执行返回的信息，也就是“实际查到了什么/执行结果是什么”。它们回答三个不同的问题：用户想做什么、系统说了什么、最后发生了什么。S1 确认三者经 context/sync 写入历史，但没有写全其失败重试、去重、顺序乱序处理，课堂图中不能擅自增加保证成功的箭头。

还要区分两个“上下文”：ASR 侧使用最近对话辅助听清文字；Planner 侧使用 Context 理解当前场景并决定怎么做事。它们出现的时间和用途不同，不能在图上只放一个泛泛的“记忆”框。

## 课堂三：Context 先给什么，Planner 信息不够怎么办

“我们不是把车上所有数据都一股脑塞给 Planner。常用的信息先准备好；真正遇到不知道的地方，再补查。这样日常指令不用每次都等一大轮检索。”

S3 写明 V2 为“预注入 + 动态检索”。预注入是在 Planner 开始处理前，给它大多数日常请求常用的数据；动态检索是 Planner 已开始判断后，发现缺信息，再调用检索工具拿需要的内容。原文中的 80%/20% 是该文方案口径，不宜在课堂写成对当前实车所有请求的已核验统计。

Context 管理的内容不仅有对话，还包括车内外情景、事件日志、短期历史压缩、短期与长期情景记忆、长期偏好、用户画像、端状态、联网时间地点天气。具体到某次请求，不代表上述来源都会注入。

教学例子：“去昨天那个游泳馆。”先看当前上下文是否已经有明确地点；没有就让 Planner 调记忆查询工具；拿到地点后再决定导航动作。若查询没拿到唯一地点，需要继续判断/向用户澄清，不能在图上直接连到‘导航成功’。这个例子用于说明产品链路，不是 S3 指定的原始测试用例。

## 课堂四：Planner 说‘好嘞’，事情是否已经做完

“这里最容易误判。用户听到‘好嘞，给你放首歌’，只能说明系统准备响应；它能不能真的放出来，还得看后面的工具执行结果。讲课时要把‘对人说的话’和‘让下游做的事’分成两条线。”

S5 说明模型每轮输出中的 talk_content 走播报链路，action_list 走工具执行链路。工具结果整理成 observation，其中有 tool_feedback 与 tool_name，再送回模型判断下一步。没有动作，或命中允许直接返回的工具，则收口。不要把所有工具都画成必定再回 Planner，也不要把首次话术画成执行成功证明。

| 节点 | 课堂里怎么讲 | 输入 | 输出/下一站 |
|---|---|---|---|
| Planner 理解与规划 | “先判断这件事缺什么信息、要分几步。” | 用户文字、Context、历史、工具说明 | 回复话术 + 动作列表 |
| TTS 支路 | “把这一轮准备对用户说的话变成声音。” | talk_content | 合成、拉流、播放 |
| 工具支路 | “把具体任务交给导航、车控、媒体等能力处理。” | action_list 内工具名和参数 | 实际工具执行 |
| 结果回传 | “把做成没做成、查到了什么带回来。” | 工具返回 | tool_feedback / observation |
| 再判断 | “信息够了就给结果；没办成或还缺信息就继续处理。” | 原诉求 + 新反馈 | 下一动作/回复/结束 |

S5 还记载本轮发过 TTS 时，分支会等端侧播完再继续，最多等 1 分钟。这是该文记载的轮次协调实现，不能直接用来概括全部语音链路都要等整段话播完才干活。画课堂总览可以保留“播报进度回报/轮次协调”的旁路，详细卡片标注该源码梳理口径。

## 课堂五：TTS 到底干什么，为什么云端先合成，车端还要拉流

“TTS 就是把文字合成语音。Planner 负责决定说什么，TTS 负责让这段话变成用户能听到的声音，车端播放器负责真的把音频播出来。这是三个不同的动作。”

S1 当前链路：云端生成回复文本 → 云端请求 TTS 提前合成 → 下发音频标识 → 车端经 TTS WSS 通道拉取音频 → 流式播放音频分片。WSS 在课堂可以解释成“持续接收音频的安全长连接”，无需展开协议细节。

为什么这样拆：S4 历史方案说明，旧路径是车端请求音频时再根据标识找文本并合成，新路径在文本生成时就开始合成，端侧来取时拿已生成的音频，目标是减少等待。约 100 ms 是该旧技术方案的预期收益，不能写成当前每一次必然节省 100 ms。

S1 与 S5 都支持情绪分段：例如“[高兴的说]好嘞，给右后放首中文歌”，前面的标签指定怎么说，后面才是实际要播的字。标签不会作为正文照念；一段话有多个情绪标签时按段处理。没有情绪标签时，S1 写使用用户 query 作为情感信息。标签包含“唱”时，转入唱歌处理链路，不能画成普通朗读无差别合成。

原文将音频标识拼成 tts_auiod_id，疑似字段拼写问题。面向产品图建议写“音频标识”，附注“精确字段拼写需按接口协议核对”，不要自行改成某个拼写再冒充原文。

## 课堂六：TTS 打轴不是打断，它回答‘播到哪儿了’

“用户插话时，系统要知道刚才那段话已经说到哪里，哪些话还没说。如果只知道‘停了’，不知道‘停在哪里’，恢复时就容易整段重说，或者漏掉后半句。”

S1 将打轴定义为音频数据和文本数据的对应关系；S5 进一步明确优先使用逐字时间信息 WordTimestamp，把回复划成“已播内容”和“未播内容”。缺少逐字信息时，按默认 100 ms/字估算。这个兜底比真实字级时间信息粗，不能把估算位置描述为精确对齐。

可用教学动效（标注教学示意，不捏造真实音频时间戳）：
- 回复全文：“上海天气晴，但是下午可能下雨哦。”
- 高亮走到“上海天气晴，但是”，用户插话，进度冻结。
- 前段标绿色“已经听到”；后段“下午可能下雨哦”标橙色“还没听到”。
- 右侧显示下一轮收到的信息：“上一条已经说了……；后面还没说……；新问题是‘好无聊’。”

S5 明确这个信息被组装进 last_talk_content 后交给下一轮。中文名可写“上一条播报到哪儿了”。这里不要把打轴画成负责判断用户是否在对车讲话的模块，也不要画成自动恢复播放器的指令。

## 课堂七：打断后怎么恢复，必须先看打断原因

“我们先别急着画‘打断 → 恢复’。先看这次为什么停。如果是用户插话，可能还有续说的价值；如果是车机低功耗、第三方主动停止，或者新播报替换旧播报，不能一会儿又自己说回来。新文档已经逐项区分了。”

按 S1 的恢复列：

| 中文场景 | 原始标识 | 是否进入恢复 |
|---|---|---|
| 新 TTS 播放优先级不低于当前，替换旧请求 | ComeNewPlay | 否 |
| 车机低功耗，服务挂起 | OnServiceSuspend | 否 |
| 第三方停止指定 TTS | ThirdPartyStopById | 否 |
| 第三方停止全部 TTS | ThirdPartyStopAll | 否 |
| 收到云端未拒识消息，打断当前 | NotRejectQuery | 是 |
| 播放离线车控执行结果 | PlayOfflineVehicleControl | 否 |
| 豆包退到静默态 | VoiceSilence | 否 |
| 流式结果判断非拒识，停止当前 | StreamNotRefusal | 是 |
| 多人场景，一句话以“豆包”开头立即打断 | MultiPersonSayStartWithDoubao | 是 |
| 单人场景，ASR 字数大于 2 字直接打断 | SingleInterrupt | 否 |

“进入恢复”仍不等于“把旧音频原样继续放”。S1 接着分两类：

- 新话最终被拒识，也就是确认不是对车机的请求：通过 Event 事件触发新 Query，告诉系统“谁和别人说话，刚才已说了什么，尚未说完什么”，让上一段继续衔接。
- 新话最终未拒识，也就是用户确实在对车机提新需求：Planner 同时看到新问题与上一条未播内容，生成自然、不重复的新回复。不是每次把新旧两段机械拼接，更不保证全部未播内容都必讲完。

S1 原例是“上海天气晴，但是（被打断，后面没说完：下午可能下雨哦）”加新 query“好无聊”。课堂可以说：“现在 Planner 同时知道新需求和没说完的天气提醒，接下来要考虑怎么自然衔接。”不能把自行编写的最终话术当作系统固定输出。

## 图的建议连线

热词/最近对话 → ASR（辅助把声音听成字）。
最终文字 + 常用 Context → Planner；信息不够 → 检索工具 → 新信息回 Planner。
Planner → 回复文本 → TTS 提前合成 → 音频标识 → 端侧拉流 → 播放。
Planner → 动作列表 → 下游执行 → 结果回传 → Planner（直返工具走直接结束）。
端侧本地命中 → 执行/回复 → Query/Answer/Observation 同步 → 云端历史 → 下一轮上下文。
播放中的新语音 → 按单人/多人/豆包开头/流式拒识判断是否停播 → 记录打断原因与已播/未播。
不允许恢复的原因 → 结束旧播报；允许恢复的原因 → 最终拒识结果 → Event 恢复或 Planner 融合新需求。
不能把 TTS 停播连线画成“取消已完成车控”，这几份文档没有给出这个保证；语音停止与动作取消要分别解释。
