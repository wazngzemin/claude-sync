# 系统预设任务：触发器配置平台与二轮交互人话详解

> 适用对象：系统预设任务/端侧 Trigger 产品负责人（王泽民）  
> 版本：V0.1  
> 日期：2026-09-02  
> 本文只解决四个问题：现在谁做、你做什么、平台到底配什么、触发以后到二轮交互怎么走。

---

# 0. 先给结论：你之前为什么一直听不懂

会议里同时出现了两套口径：

1. **当前交付方式**：产品把“触发 + 条件 + 交互 + 动作 + 异常”写成任务脚本/PRD，端侧研发用代码实现；云端已有平台只能配置一部分规则。
2. **未来目标方式**：原子能力补齐后，在统一配置平台上选择触发、条件、卡片、TTS、二次确认和动作，再把规则发布到云端或同步到端侧。

所以，不能把“未来平台应该能配什么”理解成“你今天已经要到平台里把所有东西填完”。

## 0.1 对你三个问题的直接回答

### 问题一：这块逻辑谁做，需要我做吗？

**需要你做产品定义，但不需要你写代码，也不默认由你亲自完成平台录入。**

你负责定义：

- 什么事件启动任务；
- 启动后还要检查哪些条件；
- 满足条件后是静默执行，还是先问用户；
- 如果问用户，出什么卡、说什么 TTS、用户可以怎样回答；
- 用户确认、拒绝、关闭、超时分别怎么办；
- 真正车控前还要复核什么；
- 成功、失败怎样反馈和记录；
- 一次上电最多提醒几次、冷却多久、怎样防重复。

研发/平台团队负责：

- 把信号、卡片、TTS、可见即可说、Planner、车控封装为可调用能力；
- 实现端侧 Trigger、卡片展示、语音识别、回调、车控和日志；
- 当前端侧规则按你的 PRD/脚本写入代码；
- 未来再把这些能力接进配置平台。

### 问题二：需要我在后台配置平台上配置吗？

**当前端侧系统预设任务：不是。**

- 9 月 1 日会议中，韩杰明确说：在线任务可以配置；离线/端侧任务当前由产品定义、研发在代码里实现。
- 最新《座舱 AI 编排引擎需求文档》也把可视化配置平台标为“远期规划、非强制落地”。阶段一仍是产品交付“触发、条件、动作”文档，由客户端实现。
- 因此天气路况保护这类端侧任务，你现在的交付物是完整 PRD/任务脚本，不是去一个现成平台点完就结束。

**当前云端任务：只能配置已有原子能力覆盖的部分。**如果所需事件、条件、动作已经注册，可以在现有平台配置；缺能力仍要提研发需求。

**未来统一平台：是。**但要先由研发把卡片、TTS、二次确认、回调等注册成原子能力，平台才会出现对应字段。

### 问题三：需要配置 TTS 和卡片全部内容吗？

**产品需要定义这些内容，但当前不等于你已经能在平台里配置。**

你需要给出：

- 卡片用哪个标准模板；
- 卡片标题、正文、按钮文案；
- 每个按钮对应的业务结果，例如 `CONFIRM`、`REJECT`；
- 是否播 TTS；
- TTS 文案；
- 语音禁用时怎么降级；
- 本地语音可以说哪些确认/拒绝表达；
- 卡片多久超时；
- 成功、失败、过期时怎么显示。

你**不需要**做：

- 设计或开发卡片组件；
- 录制一段声音文件；
- 自己实现 TTS 合成；
- 自己实现可见即可说或 Planner；
- 自己把用户的“可以”解析成按钮点击；
- 自己写车控代码。

目标平台里应保存的是“模板 ID + 文案/槽位 + 路由 + 策略”，而不是让产品自由画一张卡或上传语音文件。

# 1. 韩杰、张嘉锋、徐洋分别在说什么

## 1.1 韩杰：当前能力没有全进入配置平台

韩杰的核心意思有三层：

1. 当前只是根据已有 case 陆续沉淀触发、条件和动作原子能力，不是所有能力都已可配；
2. 端侧规则当前仍依赖端侧研发，长期才由配置平台生成/下发规则脚本；
3. TTS、二次确认等能力当时“应该都没有加”进配置平台。

翻成人话：**今天不能假设平台已经有“出卡 + 播 TTS + 等用户回答 + 回调执行”的完整节点。你的任务之一，是把这个能力缺口定义清楚并要求对应团队接入。**

## 1.2 张嘉锋：不要四个 case 各写一套

张嘉锋追问的不是“天气条件有没有写对”这么简单，而是：

- 下雨、下雪、儿童、后视镜这些事件和条件能否作为通用组件复用；
- 新增任务时，是只组合已有原子能力，还是每个 case 仍需研发写新代码；
- 配置框架有没有覆盖二次确认、TTS、交互回调等后半段。

翻成人话：**评审要证明的是“框架能复用”，四条任务只是用来验证框架完整性。**

## 1.3 徐洋：卡片、Planner、可见即可说要按链路分开

徐洋的关键口径：

- 大部分在线卡片不注册可见即可说，优先由 Planner 负责泛化理解和上下文；
- 只有无法走云端、必须本地闭环的少数任务，才注册可见即可说；
- 天气路况保护属于端侧自闭环，可使用即时交互卡 + 可见即可说；
- 卡片基础容器和可见即可说能力存在，不代表具体天气业务已经接好；业务仍需提供词条并由相关研发注册；
- 语音禁用时，安全任务仍可以出卡，但不播 TTS；用户只能点击处理。

翻成人话：**卡片负责“展示”，TTS 负责“说”，Planner/可见即可说负责“听懂回答”，原任务/Trigger 负责“确认后是否执行”。这不是一个模块包办。**

# 2. 当前真实交付方式与未来平台方式

| 阶段 | 你交付什么 | 谁实现 | 能否由你直接在平台完成 |
|---|---|---|---|
| 当前端侧任务 | PRD/任务脚本：触发、条件、频控、交互、动作、异常、验收 | 端侧 Trigger、VUI、可见即可说、车控研发 | 否，端侧主要仍靠代码 |
| 当前云端任务 | 已有能力范围内的规则配置；缺失能力仍写需求 | 云端 Trigger/Planner/能力 Owner | 部分可以 |
| 端云混合任务 | 前置条件、云端 Query/DT、结果协议、端侧复核和车控闭环 | Trigger + Planner/DT + 端侧研发 | 只能配置已有部分 |
| 未来统一平台 | 在页面选择标准原子能力、填写参数、发布版本 | 平台研发提供能力后，产品/运营按权限配置 | 目标是可以，但目前不是现状 |

## 2.1 “原子能力存在”和“平台可配置”不是一回事

必须区分五个状态：

1. 底层能力存在，例如系统本来能播 TTS；
2. 能力有标准调用接口；
3. 能力已注册进配置平台；
4. 云端任务能配置调用；
5. 平台配置能同步到端侧运行。

例如：TTS 基础能力存在，不等于 Trigger 平台已经有 `TTS` 节点；即时交互卡能展示，不等于平台已经能配置标题、按钮、回调和生命周期；可见即可说存在，不等于天气卡片已经完成词条注册。

# 3. 未来触发器配置平台到底要配置什么

一条系统预设任务不是只有“触发条件”。完整配置应分为十一组。

## 3.1 任务基础信息

| 配置项 | 说明 | 天气示例 |
|---|---|---|
| `task_id` | 全链路唯一任务标识 | `preset_weather_protection` |
| 任务名称/说明 | 任务中心展示及运营识别 | 天气路况保护 |
| 适用车型/版本 | 哪些车可运行 | E68 + 最低软件版本 |
| 默认状态 | 出厂默认开或关 | 待赛力斯确认 |
| Owner | 业务和能力负责人 | 产品/Trigger/VUI/车控分别登记 |

## 3.2 任务有效状态门禁

这里不是车辆端状态，而是任务中心管理的任务状态。

至少需要：

- `task_enabled=true/false`；
- 状态版本或更新时间；
- 车辆上电/进程重启后的全量快照；
- 用户启用、停用时的状态变更事件；
- 未拿到状态时是默认不执行，还是使用本地最后值。

Trigger 的第一道门必须是：**本任务当前有效吗？**任务关闭，即使下雨、车速、模式都满足，也不能出卡、播 TTS 或车控。

注意：任务有效状态、AI 主动服务总开关、语音禁用状态是三个独立值，不能混成一个“总开关”。

## 3.3 启动事件（Trigger）

配置“什么变化发生时启动一次判断”，例如：

- 天气从其他状态变成下雨/下雪/浓雾；
- 路面从正常变成湿滑/结冰；
- 档位从非 P 切入 P；
- 洗车模式从开启变成退出；
- 定时器到点；
- 用户点击或卡片回调事件。

这里要配置变化方向、枚举范围、防抖次数和重复事件处理。不能只写“天气=下雨”，否则系统不知道是持续轮询还是状态穿越时触发。

## 3.4 条件树（Condition）

配置事件发生后还要检查什么：

- AND/OR/NOT；
- 数值大小、区间、枚举相等；
- UNKNOWN/缺值怎么处理；
- 条件是否需要持续一段时间；
- 使用当前实时值还是某个事件快照。

天气示例：

```text
任务有效
AND 车速 > 30 km/h
AND (天气风险成立 OR 路面风险成立)
AND 当前目标驾驶模式未开启
AND 本上电周期未超过提醒次数
```

## 3.5 频控、去重和冲突

至少需要配置：

- 一次上电最多提醒几次；
- 两次提醒最短间隔；
- 用户拒绝后冷却多久；
- 同一个 `event_id` 只能处理一次；
- 卡片正在等待确认时，新事件是合并、覆盖还是忽略；
- 与其他安全提醒、用户 Query、正在执行车控冲突时的优先级。

## 3.6 执行策略

不是所有任务都要问用户。平台至少需要标准档位：

| 策略 | 含义 | 示例 |
|---|---|---|
| `SILENT_EXECUTE` | 条件满足后静默执行 | 儿童锁、后视镜（按 9/1 最终交互口径） |
| `INFORM_ONLY` | 只通知，不等待确认 | 纯提醒类任务 |
| `CONFIRM_LOCAL` | 本地卡片/语音确认后执行 | 天气路况保护 |
| `CONFIRM_CLOUD` | 云端 Planner 理解用户确认后执行 | 需要泛化语义的在线业务 |
| `RECOMMEND_QUERY_DT` | 先发模拟 Query，调用 DT/VQA，再决定是否询问/执行 | 充电口盖 |

## 3.7 卡片配置

产品需要定义的不是自由设计一张页面，而是调用标准模板时的参数：

- `card_template_id`：使用哪个标准卡片；
- 标题、正文、图标/风险等级；
- 按钮数量和按钮文案；
- 每个按钮的 `action_id`；
- 点击路由：直接回原业务、模拟 Query、仅上报事件；
- 卡片显示屏幕、优先级、超时时间；
- 关闭、忽略、超时算什么业务结果；
- 成功、失败后卡片如何更新；
- 卡片消失后如何注销语音能力。

## 3.8 TTS 配置

产品需要定义：

- 是否播；
- 播报文案或文案资源 ID；
- 何时播：卡片出现前、同时或后；
- 优先级、是否允许打断；
- 语音禁用时的降级；
- 成功/失败是否需要再次播报。

这里配置的是“文本和策略”，不是录音文件。TTS 服务负责把文字合成为声音。

## 3.9 用户回答路由

| 路由 | 谁理解用户回答 | 适用场景 |
|---|---|---|
| `VISIBLE_SAY` | 端侧可见即可说把“确认/不用”等映射成按钮 | 必须本地/离线的少量强规则任务 |
| `PLANNER` | Planner 根据上下文和卡片按钮理解自然语言 | 在线、需要泛化理解的业务 |
| `CLICK_ONLY` | 不开放语音，只能点按钮 | 语音禁用降级或简单卡片 |
| `NONE` | 不需要用户回答 | 静默执行任务 |

本地需要配置/提交的不是一个大模型，而是按钮对应的词条和同义表达，例如：

- `CONFIRM`：确认、可以、调整吧、帮我开；
- `REJECT`：不用、取消、先不用、保持现在。

这些词条由产品提供，相关业务/卡片/可见即可说研发按最终分工注册。

## 3.10 动作和执行前复核

需要配置：

- 动作能力 ID 和参数；
- 串行还是并行；
- 动作前重新读取哪些状态；
- 失败是否重试；
- 车控返回后以接口成功还是实际状态变化为准。

必须把“用户同意”与“立即车控”隔开。用户同意后仍要复核：任务还开着吗、卡片还有效吗、车辆条件还满足吗、目标状态是否已经变化。

## 3.11 反馈、日志和发布

至少记录：

- `task_id`、`event_id`、规则版本；
- 触发事件和条件快照；
- 卡片是否展示、TTS 是否播放；
- 用户点击/语音/关闭/超时；
- 车控请求、返回码、真实状态；
- 失败原因和结束状态；
- 车型、渠道、版本、灰度和回滚记录。

# 4. 触发以后到“二轮交互”的完整逻辑

## 4.1 什么叫第一轮、第二轮

- **第一轮**：系统主动问用户。例如弹出卡片并播报“当前路面湿滑，是否切换湿滑模式？”
- **第二轮**：用户回答“可以/不用”或点击按钮，系统识别用户选择并决定是否执行。

二轮交互不是重新创建一条独立 Trigger。它必须绑定第一轮生成的同一个 `event_id`，否则用户一句“可以”不知道是在确认哪张卡。

## 4.2 通用完整链路

### 步骤 1：Trigger 收到启动事件

例如 VLM 上报“路面由正常变为湿滑”。Trigger 生成一次 `event_id`，保存本次事件来源和状态快照。

### 步骤 2：先过总门禁

按顺序检查：

1. 任务中心中的该任务是否有效；
2. 任务要求的 AI 主动服务总开关是否开启；
3. 当前车型/版本是否支持；
4. 是否处于冷却或已在处理中。

任一不满足，本次结束，不出卡、不播报、不车控。

### 步骤 3：检查业务条件

读取当前实时状态，计算 AND/OR 条件树。不要只用很早以前缓存的状态。

### 步骤 4：选择交互策略

- 静默执行：直接进入执行前复核；
- 需要确认：进入 `PENDING_CONFIRM`（等待确认）状态；
- 需要云端推理：先调用 Planner/DT，拿到有效结果后再决定是否进入确认。

### 步骤 5：拉起卡片

原业务/Trigger 给即时交互卡组件传：

```text
task_id + event_id + card_template_id
+ 标题/正文
+ 按钮文案/action_id
+ 超时时间
+ 回调目标
```

卡片只负责展示和收集操作，不自己判断天气，也不直接决定车控。

### 步骤 6：处理 TTS 和语音状态

- 语音可用：按配置播 TTS，并打开对应的回答链路；
- 语音禁用：仍显示安全卡片，但不播 TTS、不开放语音回答，只保留点击；
- 卡片展示失败：需要确认的任务必须结束，不能偷偷降级成静默车控。

### 步骤 7：注册本地或云端回答能力

本地链路：

- 卡片出现时注册 `CONFIRM/REJECT` 词条；
- 用户说“可以”后，可见即可说把它转换成该卡片的 `CONFIRM` 按钮事件；
- 卡片消失时注销词条。

云端链路：

- 卡片及按钮上报 Planner，建立与卡片生命周期绑定的动态选择能力；
- 用户说“那就帮我调一下”，Planner结合上下文匹配 `CONFIRM`；
- 卡片消失后删除本次动态选择能力。

### 步骤 8：统一回调原业务

无论用户是点击、本地语音还是 Planner 语音，最后都应收敛成同一种结果：

```text
interaction_result = {
  task_id,
  event_id,
  action_id: CONFIRM | REJECT,
  input_method: CLICK | LOCAL_VOICE | CLOUD_VOICE,
  timestamp
}
```

### 步骤 9：原业务/Trigger 校验二轮结果

原业务检查：

- `event_id` 是否属于仍存活的卡片；
- 是否已经处理过，避免重复执行；
- 是否超时；
- 当前任务是否仍有效；
- 用户选择是否允许进入动作。

拒绝、关闭、忽略、超时：不执行，进入冷却并记录原因。

### 步骤 10：执行前重新复核车辆状态

即使用户刚刚说“可以”，仍需读取最新状态：

- 车辆是否仍在允许档位/速度；
- 目标能力是否已经由用户手动打开；
- 场景条件是否已经消失；
- 云端推理结果是否仍在有效期；
- 是否有更高优先级动作冲突。

复核失败就不执行，并向用户给出适当反馈。

### 步骤 11：车控、状态回读和收口

- 调用端侧动作能力；
- 获取接口结果；
- 再读真实状态确认是否生效；
- 更新卡片为成功/失败；
- 写事件日志；
- 关闭卡片、注销词条/动态能力；
- 进入冷却，等待下一次独立事件。

# 5. 用天气路况保护完整跑一遍

## 5.1 你在 PRD 中需要交付的内容

```text
任务：天气路况保护
运行位置：端侧
任务有效状态：来自任务中心，false 时不运行
启动事件：天气/路面枚举进入风险状态
业务条件：车速 > 30；目标驾驶模式/后雾灯尚未开启
频控：上电周期次数、冷却时间待确认
执行策略：确认后执行
展示：即时交互卡
TTS：当前天气路况不佳，是否为你调整到合适的驾驶模式？
语音路线：端侧可见即可说
语音禁用降级：只出卡，不播 TTS，仅点击
确认：重新复核后切换目标驾驶模式/后雾灯
拒绝/关闭/超时：不执行，记录并冷却
成功/失败：更新卡片和日志
```

## 5.2 用户实际体验

1. 车辆行驶中，端侧发现路面湿滑；
2. Trigger 检查任务开启、车速、当前模式和频控；
3. 条件满足，生成 `event_id=W123`；
4. 弹卡：“当前路面湿滑，是否切换湿滑模式？”；
5. 语音可用时同步播 TTS，并注册“可以/不用”等本地词条；
6. 用户说“可以”或点击“确认调整”；
7. 回调携带 `W123 + CONFIRM` 返回天气任务；
8. Trigger 再查一次车速、任务状态和当前驾驶模式；
9. 仍满足才执行切换；
10. 回读状态成功，卡片显示“已切换”；失败则显示失败原因；
11. 关闭卡片、注销词条、记录全链路并进入冷却。

## 5.3 四个容易做错的点

1. 可见即可说只负责把语音变成按钮结果，不负责判断天气和车控；
2. TTS 只负责播报，不负责理解“可以”；
3. 卡片只负责展示/收集操作，不负责决定是否能执行；
4. Trigger/原业务必须保存 `PENDING_CONFIRM` 状态并在确认后复核，不能收到 `CONFIRM` 就直接车控。

# 6. 充电口盖为什么和天气不一样

你已确认的前半段链路是：

```text
Trigger 前置条件满足
→ 主动推荐携带模拟 Query
→ 主动推荐调用 DT/VQA
→ 端侧上行并取回同 event_id 的推理结果
→ 端侧执行
```

完整产品链路还需要在专项中关闭三个问题：

1. 用户确认放在 DT 前，还是识别到 `FOUND` 后；
2. 卡片属于静态 Advisor 链路还是系统通知三方调用链路；
3. 语音回答走 Planner，卡片点击是直接回业务还是模拟 Query。

建议的安全链路是：

```text
档位切 P 等前置条件满足
→ 生成 event_id
→ 模拟 Query 调用 DT/VQA
→ FOUND
→ 出卡询问“检测到充电设备，是否打开充电口盖？”
→ 用户点击/Planner 语音确认
→ 原任务收到同 event_id 的 CONFIRM
→ 端侧复核仍在 P、车辆停稳、口盖关闭、结果未过期
→ 打开口盖
→ 回读状态并更新卡片
```

该段目前是**产品建议**，不是会议已经完全拍板的接口结论。你要找徐洋确认卡片链路和语音路由，找张嘉锋确认 Planner/DT 上下文与点击路由，找韩杰确认 Trigger/配置能力和回调协议。
