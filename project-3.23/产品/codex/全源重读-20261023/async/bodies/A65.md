# 产品功能概要设计

## 业务场景

视觉问答，核心是通过语音交互即时识别并解答用户关于舱内和舱外的事物提问，适配多类高频行车场景：

1. 日常通勤：满足用户对沿途新奇事物的即时求知欲，丰富通勤体验；

2. 自驾出游：助力用户了解陌生路段的事物信息，同时为突发需求（如就医）提供参考，丰富旅途见闻；

3. 新手驾驶：在不分散注意力的前提下，帮助新手掌握路况相关信息，提升驾驶安全感与便捷性；

4. 亲子出行：快速回应孩子的好奇心，兼顾驾驶安全与亲子科普互动，让出行更具教育意义；

5. 观影搭子：根据车屏幕播放的视频画面，满足用户对于人物、剧情的好奇心；

整体而言，该功能既贴合车载场景的安全需求，又能满足用户的信息获取与情感互动需求，显著提升行车过程的便利性与趣味性。

## 产品目标

### 战略目标

- **打造车载场景下的智能视觉问答标杆**：以高精准识别与极速响应为核心，成为用户行车途中获取沿途事物信息的首选工具，填补车载即时视觉交互的体验空白。

- **兼顾行车安全与用户多元需求**：在保障驾驶安全的前提下，满足用户求知、科普、应急参考等多维度需求，实现安全性与实用性的统一。

- **强化用户与车机的情感联结**：通过场景化定制功能与趣味交互设计，打破传统车机的工具属性，让行车过程更具趣味性与温度，提升用户对车机系统的粘性。

### 功能目标

- **聚焦核心领域，保障关键需求**：优先实现车辆、路牌、常用建筑等核心品类的高精准识别，确保用户高频需求得到可靠满足，筑牢功能核心价值。

- **兼顾品类覆盖，优化兜底体验：**尽力拓展非核心品类的识别范围，同时设计友好的兜底响应机制，在保证功能全面性的前提下，降低识别局限对用户体验的影响。

- **打造高效安全的交互体验：**以语音为核心构建便捷交互模式，结合场景化优化逻辑，在保障驾驶安全的基础上，满足不同出行场景的个性化需求。

# 屏幕识别需求（新增）

<div class="callout">

**文档说明：**本章节为 2026/8/27 专项讨论会后新增的屏幕识别相关需求，基于会议纪要（聊下屏幕识别）整理。新增内容均以红色标注。

</div>

## 业务场景

屏幕识别（Screen Recognition）旨在通过获取车机屏幕信息，为 DT（Director）提供更完整的上下文感知能力。核心目标是让豆包看到\&\#34;所有与人相关、上下文一致\&\#34;的信息，弥补端状态、埋点等传统方式的信息缺口。

主要覆盖场景：

1. **页面指代问答：**用户指代当前屏幕页面内容提问（如\&\#34;后视镜页面怎么操作\&\#34;、\&\#34;这个页面为什么打不开\&\#34;），通过 VQA 识别屏幕内容辅助回答。

2. **导航信息补全：**地图界面有但端状态接口缺失的信息（前方拥堵时长、路名、限速标识等），通过单次 VQA 截屏识别补全。

3. **系统感知增强：**通过页面注册/埋点/事件上报，让 DT 感知当前系统状态（当前 APP/页面、按钮元素、交互事件等）。

4. **拒识增强：**屏幕上已出现的内容不应被拒识拦截，通过关键页面埋点信息辅助拒识规则判断。

5. **画布层级与遮挡感知：**解决豆包对话框遮挡系统弹窗等体验问题，通过工程规则优化确保系统弹窗优先级最高。

## 产品功能详细设计

### 页面指代 VQA

#### 流程说明

页面指代 VQA 链路复用影视剧搭子的 VQA 链路，但触发场景不同：

1. **预截图：**每次 VAD 识别到人机对话开始时，自动截取当前屏幕画面并缓存

2. **触发条件：**当用户 query 涉及页面指代（如\&\#34;这个页面怎么操作\&\#34;\&\#34;为什么打不开\&\#34;）时，DT 调用 VQA 工具

3. **识别处理：**取对应时间戳的截图，通过 VLM 识别页面文本、按钮元素、页面状态等信息

4. **结果返回：**将识别结果作为工具返回给 DT，DT 结合上下文进行推理回复

<div class="callout">

**注意事项：**

- 需避免误召回：需设计合理的触发规则，避免用户非页面指代的 query 频繁触发 VQA

- 页面指代与可见即可说的边界：页面指代侧重\&\#34;理解页面内容\&\#34;，可见即可说侧重\&\#34;执行页面操作\&\#34;

</div>

### 导航信息补全（VQA）

#### 方案说明

导航信息补全采用单次 VQA 截屏识别方案，而非 Always On 持续识别。原因是：

- 端侧算力有限，已有舱内外两个高频 Always On 任务串行，再加一路会导致所有任务周期拉长

- 合规风险：持续识别导航内容可能引发图商侵权问题

- 导航截屏识别不全：导航截图比例尺可能与全览视图不一致

**前置评测要求：**在正式确定方案前，需先评测现有端状态导航\+联网\+八方位接口的实际效果，明确具体信息缺口场景，再决定 VQA 方案覆盖范围。

### 娱乐搭子截图优化

#### 方案说明

优化娱乐搭子（观影搭子/游戏搭子）的截图与识别策略，降低云端成本：

- **持续采集：**开启娱乐搭子模式后，端侧持续预截图，本地缓存 3\-5 张历史图片（循环替换）

- **按需识别：**仅当 VAD 识别到用户发起相关查询时，才取对应时间戳的图片调用 VLM 识别

- **不上报全量：**不持续全量上报截图到云端，避免高量级车辆场景下的成本过高

## 已知卡点与约束

- **端侧算力：**端侧 VLM 目前只有一个 batch，每加一路任务会拖慢所有 Always On 任务周期（舱内外已有 2 个高频任务串行）。屏幕识别是否值得占用这一路资源需要场景价值论证。

- **云端开销：**单次查询走端侧或云端差别不大；但多用户长时间开启云端 VLM 开销较大。

- **合规风险：**赛力斯安全合规侧对屏幕截图持续有侵权、合规方面的顾虑，法务口径反复（尤其是导航，担心图商侵权）。

- **导航侧反对截屏：**导航同学认为截图截不全，建议用 LBS 方式获取 POI 和位置信息；但全品类 POI 的信源调用量和成本与现状不同。

## 会议决策结论

1. **915 核心任务：**搭建页面指代 VQA 链路（非 OVS 链路），采用预截图\+单次识别方案

2. **Always On vs 单次：**当前仅采用单次识别（预截图），不启用 Always On 持续识别

3. **系统感知：**优先通过页面埋点、事件日志、工程注册方式解决，不依赖屏幕视觉

4. **导航信息：**先评测现有方案效果，明确缺口后再决定 VQA 覆盖范围

5. **执行结果 Review：**归类为工程 bug，暂不做视觉兜底

6. **拒识增强：**暂不依赖屏幕识别，优先通过关键页面埋点、事件上报获取核心页面信息

7. **可见即可说增强：**暂定\(TBD\)，后续评估动态页面工具和 GUI agent 兜底两种路径

8. **AI 伴游：**优先采用 LBS 方案，叠加 VQA 舱外视觉识别做多路径互补
