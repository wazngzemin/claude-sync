# 端侧离在线仲裁技术方案

# 整体架构

从客户端视角看，车机系统会从车机系统采集 N\*Mic 和 N\*Ref 的音频数据。离线语音（VehicleSpeech SDK ） SDK 会通过对音频进行处理，拆解出每一路 mic 对应的音频完成 WakeUp ASR 以及输出处理后的音频数据。



触发唤醒后，豆包 APP 会完成以下主要的几件事情  

1. 和服务端建立 RTC 通道的连接

2. 和服务端建立 IM 消息通路的连接

3. 启动离线语音对话模块

4. 获取配置信息



端侧的 ASR 结果将由离线对话系统处理

处理后的音频数据将通过 RTC 链路交给云端处理

在之后的端云的对话系统中，要保证上下文，VAD 时间，以及任务的一致性。







## 技术难点

1. 云端的 VAD 需要和端侧一致。因为端侧的 VAD 时间很多，并且传递给云端的音频已经是 SSP 模块处理过的，不一致会导致云端的 Speech 模块无法判停，后续业务一直卡在 Speech 侧触发 RTC 超时 

方案1: 端侧给音频标记出 VAD 的开始和结束时间，云端按照端侧标记触发后续流程

方案2: 云端调整 VAD 时间和端侧一致 

2. 端云如何标识同一轮任务 

 方案：在离线对话系统中，pcm 精力 ssp，vad，对话任务链的处理后追加上 taskId 发送给云端

3. 端侧接收云端任务的路径有三个路径，Froniter ，IM （Message）消息，RTC 通道。如果云端消息先于端侧触达到端侧，如何 block 住云端的结果去等待端侧 LLM 输出的结果。

4. 端侧需要 block Message 消息是否会影响流式上屏的效果
