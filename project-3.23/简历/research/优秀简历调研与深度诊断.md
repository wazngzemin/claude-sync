# 优秀简历调研与深度诊断

调研日期：2026-11-17。目标岗位：具身智能产品经理 / AI Agent 产品经理。

**主要判断：当前字节部分的深度原料并不缺，缺的是把原材料里的问题、判断依据和取舍写出来。** 正文让人知道你负责哪些模块，但不少要点还不能回答：当时哪件事做不成？你作了什么决定？这个决定改变了谁的工作或用户体验？

本报告以用户指定的 [v18 定稿正文](</private/tmp/claude-501/-Users-bytedance-Desktop-3-23/8dd7d7ad-e8f7-4a56-b0c7-ff3578d8a2ca/scratchpad/resume_v18_text.md>) 为诊断基准；已用文本解析核对现有 HTML，字节部分的 19 条内容一致。19 条分属 Planner 6 条、司机 Agent 5 条、主动服务 4 条、语音/记忆/交付 4 条。这里只调研和诊断，不生成用户经历的改写稿。

本地证据使用 `简历/research/feishu/*.json`、[JD—证据对照](JD-证据对照.md)，必要时按对照文件回溯原件。联网仅使用搜索工具的搜索、网页读取功能，未启动 Chrome、Playwright 或其他浏览器；未修改简历 HTML、来源表、JD 对照或 PRD 快照。

## 1. “深度不够”具体发生在哪里

| 现在的写法 | 读者仍不知道什么 | 真正需要补的材料 |
|---|---|---|
| “定义链路、明确分工、拉通团队、形成口径” | 不同团队原本在哪里冲突，你促成了哪个具体决定 | 一个争议点、双方限制、最后采用的规则与接受依据 |
| “23 个能力、4 类 Advisor、259 条信号” | 这些设计规模为什么重要，使用者因此有什么变化 | 规模背后的问题、复用或隔离边界、谁采用、采用状态 |
| “准确率目标、时延目标、113 条用例” | 指标测的是什么，是否实际测试，是否改变版本取舍 | 指标定义、测试场景、样本/分母、结果及据此作出的发布决定 |
| “升级为主动服务、从规则升级为统一决策” | 原方案在哪类真实请求中失效，升级承担了什么代价 | 失败请求、旧方案瓶颈、备选方案、阶段与保留边界 |

不是每条都要塞进一整套故事。项目开头交代一次背景，核心要点各保留一个最能证明判断的事实，才能增加信息密度。没有经营指标的工作，也可以用“消除了哪种歧义、谁采用了规则、通过了哪次验收”证明变化；方案、目标和测试成绩要分别表述。

## 2. 七条可操作的深度标准

以下是结合已读指南与目标岗位作出的综合标准；“体现约束、展示取舍”是面向 Agent / 具身产品工作的应用判断，不声称每个仓库都逐字提出了同一套要求。

| 编号 | 标准：每条一句话 |
|---|---|
| S1 | 每条围绕一个问题，写清本人关键动作或决策，以及可核验的结果或状态变化。 |
| S2 | 用会改变方案的真实约束解释难度，例如感知不确定、时延预算、资源上限或跨系统依赖。 |
| S3 | 至少在核心成果中交代比较过的路径、最终选择及代价，让读者看见判断依据。 |
| S4 | 数字要说明对象、基线、统计范围与阶段，区分设计规模、验收目标和实测结果。 |
| S5 | 写清谁使用成果、覆盖到哪一层，以及用户、团队或交付流程具体发生了什么变化。 |
| S6 | 对陌生项目在开头用一句话交代服务对象、关键问题和本人负责范围，后续要点直接讲决策。 |
| S7 | 区分个人贡献与团队成果、方案与上线；没有可信数字时，用具体定性变化证明价值。 |

S1 可用两种常见结构：XYZ 是“做成什么（X）＋用什么证据衡量（Y）＋通过什么方法（Z）”；问题—决策—结果结构则先点出障碍，再交代个人选择和变化。不要为了套公式，把一个仍在方案阶段的项目写成已经实现效果。Google 的公开材料推荐交代基线、具体贡献和受影响对象；Reactive Resume 的要点指南同时允许规模句式和定性结果句式。[Google 简历指导，第 3、6 页](https://services.google.com/fh/files/misc/resume-writing-tips-for-veterans-2021.pdf)、[Reactive Resume 要点写作章节](https://github.com/reactive-resume/reactive-resume/blob/main/plugins/reactive-resume/skills/resume-bullet-writer/SKILL.md)

### 每条标准一组“浅 → 深”示例

**以下全部是虚构的通用教学场景，与王泽民经历无关；方括号只表示需要真实记录填写的证据位置，不能直接放入成品简历。** 示例刻意同时包含定量和定性写法。

| 对应标准 | 浅：只能看见动作 | 深：能看见问题、判断或变化 |
|---|---|---|
| S1：动作连接变化 | 负责客服机器人的需求设计，完成知识库接入。 | 针对退货咨询反复转人工，优先接入订单状态核验与材料补全；同一类咨询在同口径评测中的独立解决率由 `[基线]` 变为 `[实测]`。 |
| S2：解释真实难度 | 负责复杂仓储场景下的机器人调度。 | 在货架遮挡、通道频繁占用且首期不能更换传感器的限制下，将“识别到货位”和“可安全到达”分开验收，并为不可达任务设置人工接续规则。 |
| S3：体现选择与代价 | 设计智能退款流程，提升服务体验。 | 比较全自动退款与人工复核后，首期仅自动处理可由订单规则核验的低风险退款，高金额争议单保留人工；接受少量处理时长，优先控制误退款风险。 |
| S4：让数字有解释力 | 把模型准确率提升到 `[数值]`。 | 在固定 `[样本范围]`、同一版本的人工答案标准下，将可回答问题的正确率从 `[基线]` 提升至 `[实测]`；无依据问题另测拒答，避免靠少回答抬高准确率。 |
| S5：说清受益对象 | 建设统一运营配置平台，支持多个业务。 | 将各城市分别提交的活动配置整理为共用模板和本地例外规则，供城市运营与审核人员使用；审核方据同一规则退回冲突配置，替代逐城市口头确认。 |
| S6：一句背景建立理解 | 智能运维平台｜项目负责人；负责告警、知识库和工单模块。 | 项目背景：面向夜班设备值守人员，解决告警分散、定位故障需切换多个系统的问题，本人负责首期故障定位与工单接续范围。 |
| S7：如实表达阶段与贡献 | 主导系统全面上线，实现效率大幅提升。 | 负责定义灰度范围、退出条件及异常转人工规则；当前已完成联合评审并进入试点，尚未取得稳定的人效数据，成果先限定为试点采用的准入规范。 |

S3 和 S7 的示例说明：即使没有额外数字，也能靠真实约束、明确选择和采用状态写出深度。相反，“赋能业务、打造闭环、全面升级、提升体验”若没有对象和事实，仍然是浅的。关于内容比模板更重要，招聘经理作者 Gergely Orosz 也在其模板页明确作出这一提醒。[The Pragmatic Engineer 简历模板说明](https://blog.pragmaticengineer.com/the-pragmatic-engineers-resume-template/)

### 项目开头是否需要一句背景

需要，前提是读者只看项目名还不能理解服务对象和问题；不是每条要点都重复一遍背景。可用“为谁，解决什么关键问题，本人负责哪段，当前处于什么阶段”，只选理解项目必需的字段；不先解释完整技术架构。

| 当前分组 | 背景最值得补什么 | 不宜继续重复什么 |
|---|---|---|
| Planner | 用户提出带记忆、依赖或持续条件的请求时，原有分发方式为什么承接不了；本人对决策与执行边界负责什么 | “车载大脑”“统一调度”与工具名清单 |
| 司机 Agent | 模糊自然语言如何变成智驾能接受的目标，座舱与智驾能力为何不能直接等同 | 再写一遍语言→视觉→规划→执行的通用链路 |
| 主动服务 | 为什么持续满足条件不能持续重复提醒，以及不同风险服务为何采用不同端云路径 | “从被动到主动”这一愿景 |
| 语音、记忆与交付 | 这是一组责任范围而非一个连续项目，应让各条交代各自的用户问题与采用状态 | 生造一个把语音、记忆、量产治理全部包住的宏大项目背景 |

### 对本次最有价值的 3 个

1. **Tech Interview Handbook**：把动作和结果连接，并要求筛选关键成果，直接对应“条目够多但像职责清单”。
2. **ResumeSample 的 etc.md**：中文直接追问“最难的问题、你的办法、结果”，比套用更强的动词更有效。
3. **Reactive Resume 的 resume-bullet-writer**：给出从职责挖到影响、再检查归属与因果的完整方法；允许没有数字但可验证的成果，适合本次真实材料约束。

这 3 个都能访问正文，星数分别有仓库首页证据；第 3 个是高星工具仓内的写作指南，不能把主仓星数冒充该指南的独立认可。

### 样例的参考价值与证据限度

- **署名 PM 样例 G10**：把公司整体交易量/用户量放在背景行，个人要点另写；这能提醒读者不要把公司规模直接当个人成绩。可借其组织方式，但其每个百分比仍需要被追问基线与时段。
- **虚构 AI PM 样例 G11**：最有参考价值是“质量、幻觉率与成本共同构成发布门槛”“未达门槛则延后”的判断表达，不是那些虚构数字。
- **before/after 点评 G12**：同一个漂亮百分比，补上具体干预与实验窗口后才可追问；无法证明时退回过程与交付事实。未核验作者招聘官身份，不包装成大厂官方点评。
- **机器人 PM 样例缺口**：本轮用 robotics/product manager/resume 组合检索，找到了个人 GitHub 自述，但没有核验到同时满足公开全文、可信质量背书及真实录用依据的机器人 PM 简历，因此不将其计为优秀样例。
