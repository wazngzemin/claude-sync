对话历史驻留（方案未评审，方案待讨论，需要 POC）



</td>
<td>

特殊场景逻辑。

任意 qa 同步方都可以设置当前同步的 qa 需要在对话历史中驻留。如果设置为驻留，在驻留QA被使用时，强制需要经过【对过长 A 的总结】机制的清洗。

驻留的效果为：该轮 QA 会随着对话的进行持续远离当前轮，当超过最大历史长度 L 后，该轮内容会持续 append 在对话历史的结尾（导致目前的对话历史为 L \+ 1）。

实现方式：在收到获取 QA 历史请求后，按正常流程取到历史结果后，检查是否存在驻留 QA。如果存在，则检查当前 QA 历史 list 中是否有驻留 QA，如果有则直接返回；如果没有则在当前 QA 历史 list 的末尾（里当前 Q 最远的地方）增加经过【对过长 A 的总结】机制清洗后的驻留 QA。

驻留存在最大持续时间，超过 20 分钟失效。

驻留可以通过 QA 唯一标识主动取消，需提供接口。

会存在多个驻留，仅最后一次注册的驻留生效。每个驻留有单独的最大持续时间和主动取消机制。当最后一个驻留失效后，倒数第二个还有效的驻留开始生效，直到无生效的驻留。

</td>
<td>

当端侧播放了一首歌/播放了一个新的新闻（feed 流场景）。

将播放内容作为驻留 QA 上传到历史。例如：

Q：我想听体育新闻/（用户手动播放了周杰伦的稻香）

A: 樊振东 balabala/（正在播放周杰伦的稻香）

效果是在当前新闻或者歌曲播放结束前，这轮 QA 信息都在对话历史中。这样可以保证用户和这些内容的互动在信息上不丢失。

播一个，更新一次历史。当一个播完，取消驻留；播放下一个时，更新 QA，增加驻留。

这个方案不能解决【上一个新闻讲的 balabala】

</td>
<td>

这只是一种实现形式。

可以将当前播放的信息放在各个总结模型的 sp 里。这两个方案各有各的优缺点。

放 sp 对很多模型都会存在影响，需要总结模型都支持传入新闻，甚至是提槽模型也需要支持。好处是机制简单，不需要这么复杂的制作 QA 历史的机制。

放对话历史的优点是所有 llm原生支持这种形式的输入，不需要过多的微调。即使是第三方智能体大概率也能支持保留这些信息。并且因为远离最近几轮 QA，不太会导致指代消解的混乱。

## 功能点详述

### 短期对话历史的存储和使用

- 问题：

    - 目前项目中发现，当一次回答中被新的 query 在客户端打断，新的 query 在云端处理这一刻，大概率没办法拿到上一句对话的部分 answer。问题的原因是从服务被打断开始到被打断的 answer 被记录并同步需要的时间通常会大于下一句 query 进入云端开始处理的时间。



- 方案：

    - answer 的存储和同步需要较强的时效性要求。

        - 对于非生成的答案需要立即存储和同步进对话管理中；

        - 对于生成的答案，需要在吐给调用方的同时存储和同步进对话管理。

            - 换句话说：对于生成的答案，可以在生成的同时进行存储，每生成一个 token 或者一个子句，就在本次的 answer 上 append 一个 token或者子句。

                - 这显然会产生大量的数据库压力，所以这里可能要考虑使用内存数据库而非 sql。

            - 这样当对话历史在任意时间被使用的时候，取得的结果都会尽可能的是当时用户实时收到的结果。

            - （这里需要注意后续适配和扩展：在模型生成和吐给调用方之间，还应当存在后处理逻辑，例如 tts 清洗等。只有在后处理结束后才可以被同时吐出给调用方和存储对话历史。）

### question\_id 概念

目前整个基于大模型的对话系统包含了很多模块，各个模块在整个调用链路的不同上下游环节，这导致需要有一个ID可以标识一对QA，在整个调用链路中都可以用这个ID跟踪到Q经历的各个环节以及最后得到的A。

这里提一个可能的大致思路：当一句Q被接收到的时候，需要：1\. 为整段QA生成一个唯一标识。或者2\. 由调用方提供一个标识用于唯一标识此次QA。后续调用的各个步骤中的各个模块都需要把这个唯一标识作为必填入参。并且各个模块的log中也需要在每行业务log开头增加这个唯一标识，便于后续使用log时能够针对某一次QA很方便的串起所有模块的log。最后在写入对话历史模块时也需要存储此id，同时输出answer的时候也需要将此id传给调用方，用于调用方在需要的时候修改此次对话的结果内容。
