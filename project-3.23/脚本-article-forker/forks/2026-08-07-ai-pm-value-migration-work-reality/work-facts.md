# 王泽民真实工作事实底稿

## 一、可以直接确认的主责工作

### 1. 场景知识、Selector 与 Skill

- 历史工作梳理显示，王泽民负责过场景知识、Selector、Skill 与场景编排相关问题。
- 已做过数值运算符、音频分类、字段类型、车企能力差异的系统修正。
- 2026-08-05 场景知识召回评测共有 60 条，53 条完全命中，准确率 88.3%，平均耗时 1.12 秒。
- 主要错误包括 5D 定义冲突、动漫误扩展到儿童场景、普通温度误触发极速温控、别名缺失、雨天表达漏召回、已删除场景被错误召回。
- 评测表给出的下一阶段目标是：同一批 60 条回归，准确率达到 95% 以上，发布阻断问题为 0。

### 2. Trigger、Condition 与信号清单

- 6 月多次会议中，云端推理触发任务、端云触发范围、信号和条件梳理被明确交给王泽民对齐或评估。
- 高频触发条件初稿有 20 条，使用“信号、运算符、值、动作”的表达方式。
- 真实例子包括：车内温度大于 26 度、车速大于 120、座位占用变化、落锁、到达前 10 分钟、P 挡到达、电量过低。
- 一部分字段当时仍缺失或待确认，包括剩余距离、电量百分比、上电状态、登录状态。
- 7 月后，独立 Trigger 的讨论逐步进入统一 AI 编排引擎，核心抽象变成 Trigger、Condition、Action、Variable 四类原子能力。

### 3. Planner badcase 分诊与动态示例

- 6 月 Planner Bug 排查会中，王泽民被分配车控问题分类、导航文档合并、代表案例抽取、真实 Planner 问题占比量化等工作。
- 约 40 条导航问题中，真正属于 Planner 的只有 2 到 3 条，说明他做过跨模块归因，而非只改 Prompt。
- JIRA 分诊表有 138 条，A 类推理问题 102 条，F 类无日志 17 条，C 类下游接不住 9 条，其他为少量幻觉、非 Planner 和体验问题。
- 动态示例修复工作簿中，74 条需要重写，63 条进入平台更新视图。工作链路覆盖 query、trace、环境、根因、新决策分析、风险边界、平台状态和回归。
- 文件名“114 条”与实际非空行数 86 存在口径冲突，需要先统一版本与计数。

## 二、共同设计和推动的工作

### 4. Task、动态 Advisor 与 VLM 语义匹配

- 7 月方案将动态 Advisor 逐步并入 Task 管理。Task 成为顶层业务抽象，负责 waiting、running、closed 生命周期。
- Trigger Adapter 承担时间、条件、周期和 VLM 语义匹配。
- VLM 负责观察，Trigger 负责匹配和防抖，Planner 或 Director 负责面对用户的最终判断，Task 负责跨时间保存状态。
- 王泽民参与了 Task 注册、VLM 上报、云端语义判断和 Task Center 回调的评审与说明，但不应据此认定他独自负责 VLM 模型或 Task Service 工程实现。

### 5. 804 场景与原子能力补齐

- 7 月 24 日后，工作从讨论独立 Trigger 进一步转向统一编排和 804 场景落地。
- 7 月 28 日产出明确补了 4 个原子能力点：tri_passbyPoint、chargePortCoverState、con_chargePortCover、con_battery。
- 仍需确认两个问题：座位占用位置能否多选，发起导航与目的地变更是否互斥。
- 这说明王泽民的工作已经从“写一个触发器模块”迁移到“用场景反查可复用积木是否齐全”。

## 三、相关但不能算作个人主责的模块

- Planner 与 Director 是同一个决策功能的不同叫法，不能画成前后两个大脑。
- Context 是公共材料层，记忆、端状态、视觉、任务和历史对话都会进入，但不能据此说王泽民拥有整个 Context 服务。
- 记忆系统、FaceID、operate_user_memory 与常用地址同步会依赖 Trigger 信号，王泽民被拉入补字段，但记忆模型并非他的主责。
- VLM 有独立的模型、任务控制、并发和视频处理体系。王泽民参与接口和语义匹配链路，不能把 VLM 本体算到个人业绩。
- Planner SP 有 13 块、不同版本有 23 或 26 个工具口径，示例数量和工具数存在版本差异。对外表达时必须标明版本。

## 四、最能代表当前能力的三条闭环

### 闭环 A：场景知识评测

场景定义与边界 → 检索召回 → 60 条考试卷 → 53 条完全命中 → 错因分类 → 修知识与互斥规则 → 同卷回归。

当前值：88.3%。目标值：95% 以上，发布阻断为 0。

### 闭环 B：动态示例运营

线上或评测 badcase → 看 trace 和环境 → 判断属于 Planner、下游、状态缺失或评测问题 → 选择动态示例、静态规则、场景卡或 SFT → 平台更新 → 回归。

当前底稿：74 条待重写，63 条平台视图；版本计数需要先统一。

### 闭环 C：804 原子能力补齐

804 场景 → 画实际流程 → 对照 Trigger、Condition、Action、Variable → 找缺口 → 补原子能力 → 对齐 owner 和排期 → 场景验收。

当前明确补点：tri_passbyPoint、chargePortCoverState、con_chargePortCover、con_battery。

## 五、由资料推导出的职业判断

王泽民的实际工作已经超过单一 Planner 产品。更准确的职业描述是：车载 AI 系统集成型产品经理，或内部 FDE 型产品经理。

他持续做四种翻译：

1. 把用户场景翻译成可验证的任务。
2. 把任务翻译成模型可见的 Context、知识、示例和评测。
3. 把模型决策翻译成车端信号、触发条件、工具和安全边界。
4. 把系统缺口翻译成具体 owner、接口、排期和验收标准。

当前最大缺口也很清楚：解释材料很多，能代表个人的“单条生产闭环结果”还不够醒目。下一阶段应减少新文档版本，把时间转到同一批评测回归、平台运营指标、跨 owner 决策和一条可复用的完整链路。
