# E 章设计（Claude 定稿，Codex 照此写作和画图）

章名：E · 工具执行与反馈：动作交出去以后，怎样真的办成、结果怎样回来

## 和前几章的分工
- V 章第八段讲过入门：动作列表是待办，工具反馈是已经发生的事实；Planner 根据反馈决定下一步。
- R 章讲过端云谁说了算、本地结果回写、只办一次。I 章讲过打断不撤回已下发动作。W 章讲过动态工具（卡片 20）。M 章讲过工具放行、执行重放边界、工具结果单独一轮（卡片 22、24、25）。C 章讲过工具结果在历史里怎样保留（卡片 30）。D 章讲过 Planner 怎样选工具、写参数、并行和串行、等齐再说、能力边界和假成功的 Planner 一侧（卡片 32～35）。
- E 章只讲执行这一侧：从 Planner 交出动作列表，到 Planner 读到工具反馈之间发生的事。前面讲过的一两句点回，不重复。
- 留给后面章节：F 章讲工具准入（哪些工具能进本轮列表）和单个 Agent 的接入协议、注册上线流程；O 章讲播报话术本身怎样自然、说的和车上看到的最终是否一致；DR 章讲司机 Agent 内部；T 章讲任务登记以后怎样触发和运行。E 章碰到这些只点到为止。
- 卡片 37～45 在 E 章第一次出现，必须讲全。

## 读者视角
读者是负责 Planner 的产品经理。他每天看到的是 Planner 的输入和输出，看不见中间这一段。这一章要让他能回答：动作发出去以后到底谁在执行；为什么同一个工具在上汽和赛力斯表现不同；回执里那句“执行成功”是谁写的、证明了什么；一批工具有一个超时怎么办；为什么有的车控结果是车上自己播的；用户说“没开”时，该从哪一环查起、找谁。

## 主例
接着 D 章的主例：主驾说“我好热，顺便找个附近能停车的咖啡店”。D 章讲到 Planner 第一轮交出四个动作：查车况、开空调、调风量、搜附近咖啡店。E 章跟着这四个动作走一遍：
- 查车况：交给车辆状态查询工具（自建），返回空调、车窗等当前状态的文字。
- 开空调、调风量：交给车辆控制工具。云端车控模型把“打开空调、风量调高一档”翻成两个函数和参数，经长连接推给这辆车；车控应用调车辆服务执行，回一个执行结果；云端把它改写成一句话。
- 搜咖啡店：交给地点查询工具（三方服务商提供），返回按顺序排好的店名、地址、距离；要写清是“当前位置附近”找到的。
- 四个结果收齐，作为一批交回输入管理，单独一轮交给 Planner；Planner 统一说一次。
- 反面版本一（讲超时和一批收齐）：调风量那一步车上没回话，超时了。正确做法：这一项回“执行失败，请勿重复调用，需要告知用户”，其余三项照常交回；Planner 说“空调开了，风量没调成，你可以手动调一下”。错误做法：整批算失败，或者自动再发一次。
- 反面版本二（讲回执的局限，真实路测）：用户要“24 度”，Planner 下发了“调到 4 度”，回执是“空调温度调节，执行成功，可简洁回复做好了｜完成”。回执只说调了哪个函数、成没成，没说车现在是多少度，所以这一路没有一环把 4 度拦下来。
每段都用这个主例的某一刻来讲。D 章讲过的 Planner 侧判断只点回。

## 资料冲突的裁决（写作一律照这里讲，正文里不提“有冲突”）
1. 工具数量：Planner 每一轮看到的是二三十个工具，随车型和版本不同（点回 D 章）。后台登记的工具实现更多：一份配置快照里有两百多条配置、约五十个工具编号，因为同一个工具在不同项目、不同环境各有一份实现。正文讲清“看到的工具”和“登记的实现”是两回事，不写一个固定的“共有多少工具”。
2. 谁执行：Planner 只交动作列表，不直接调用工具。解析动作列表、按轮次调度的是云端编排（AIDV 编排，也就是 D 章讲的决策循环）；Agent Server 只管“单个工具这一次怎么调”。讲清这两层。
3. 工具注册与管理平台：按卡片 38 讲成现行做法。剩下少数工具还写死在代码里、正在收进平台，一句带过。
4. 执行结果的统一归一：现在是每个工具各自把结果改写成 Planner 能读的一句话；跨工具统一的结果归一能力还在预研。讲成“各管各的，统一的还在做”，不展开。
5. 车控模型：按卡片 39。赛力斯：微调后的车控模型优先出函数，函数不在白名单或参数越界时，才用检索出来的候选。上汽：车控模型正在切到同一套主线微调方案，已测一版在修问题。和车上的 1.7B 模型（卡片 1）是两个不同位置的翻译，点回 V 章。
6. 动态参数（上汽）：服务端已经做好，车端上报在陆续接入。不提分隔符的问题。
7. 超时：没有一个全工具统一的超时秒数，各工具自己定。超时后回统一一句“执行失败，请勿重复调用，需要告知用户”。“10 秒”只是排查时的分工线：已下发 10 秒还没有车上回执，就转车端同学查；不要写成执行超时。不要和 R 章的 3 秒、2 秒，D 章的模型调用 60 秒，M 章的播放期限混在一起；正文可以用一句话把这几个时间分开。
8. 重试：不自动重试。车控、导航、媒体的超时回执都写明“请勿重复调用”。同一次调用因为网络重发，沿用原来的调用编号，下游要能认出是重复的（点回 M 章卡片 24）。有的应用工具会在错误里写明能不能重试（问题反馈工具：内部错误可重试，其他错误不可重试），用它当例子。
9. 工具结果怎样进输入管理：按卡片 22，同一轮的完整结果作为一批，单独一轮处理，不和用户新说的话合并。旧的“车控、记忆结果可以合并”的分法已经不用，正文不提。工具结果逐个异步返回是后续方向，一句带过。输入管理的现状点回 M 章。
10. 谁来播结果：讲成“通则加车控例外”。通则：下游工具不自己说话，结果回 Planner 统一说。车控例外：简单车控、多意图车控全部成功，用车上固定模板和车上 TTS 播；复杂车控、或者有任何一项失败，由云端说清哪项成了、哪项没成、为什么；云端车控干预命中时用车上播报。车书查询结果由车书自己播。不提这一点仍在讨论。
11. 简单车控要不要先说过渡话：不需要无意义的首轮话术（点回 D 章第五段）。旧页“先念正在调 4 度再说调好了”的写法不用。
12. 不支持的指令：分两类，“车上没有这个功能”和“有这个功能但不支持语音控制”。手动替代路径只从用户手册（车书）里找。车书查不到时，不断言车上没有，回答“没查到可用信息，可能没配备，或者不支持语音控制”。“车控不支持就自动去讲车书”曾答非所问，已经改了；不写改后的具体规则。
13. 云端车控干预：名字里常带“离线”，其实跑在云端：规则命中就直接返回车控函数，取消已经预先启动的 Planner，用车上播报。优先级在句法规则之后、Planner 之前；拒识优先，干预不能绕过拒识；没命中或出错就回到原链路。和 R 章的车上固定规则抢跑是两回事，点回 R 章。
14. 动态工具：服务端已上线，各车型陆续接入（点回 W 章卡片 20）。
15. “成功”的四层：已推送、车收到并回了结果、车执行了某个函数、车到了用户要的状态。每一层都可能断。D 章讲过假成功的 Planner 侧，E 章只讲回执和执行侧。23 个假成功复盘里回执缺陷的比例点回 D 章，不再重复数字。
16. 24 度变 4 度：只说确实下发了 4 度、收到了成功回执、用户后来纠正；回执里看不出车上实际调到多少。不说“没有任何参数校验”，不分析是语音识别还是其他原因（点回 V 章）。
17. 空调自动模式那一例：只说“要切自动，执行的是空调开关函数，回执写的也是空调开关成功”，不说是第几轮。
18. 问题反馈工具：按卡片 45 讲 10 月的新设计（最多追问 3 轮、总结不超过 100 字、用户确认才提交、任务状态）。赛力斯已发版、在修问题。8 月面向内部种子用户的版本一句带过。不提文内状态表的不一致。
19. 车控的失败原因（工程上叫 DM 逻辑）：主驾权限、档位限制、二次确认这些业务前提，要在回执里写成用户能听懂的原因；连接器异常这类代码问题归为未知原因。一个原子能力可能要补好几条这样的逻辑，车控变更已经锁定，新增要两边产品负责人评估。
20. 性能和指标：车控模型一条日志约 1 秒、检索约 0.1 秒，当例子讲，不当整体指标。模型评测里的准确率（例如 96.56%、92.36%）是模型测试，不等于实车执行成功率；正文只讲“要分层看：下发、回执、真实执行、目标达成”，具体数字放附二。
21. 群聊和会议笔记里的线索（家/公司设置二次确认循环等）可以当“**案例：**”，但只写看到的现象和确认过的原因，不补推测。
22. 原文里的提示词示例、设计用例（买花加途经点、温度超上限、尾翼、NFC 开关、反馈点踩又撤销）是设计推演，只能当“**例子：**”。真实路测和测试问题才用“**案例：**”。
23. 内部系统名：Frontier（云到车的长连接推送通道）、Fornax 和 Argos（查日志和调用链的平台）、内部能力平台（DPFM）、弋途（三方服务商）、方舟（模型服务平台），第一次出现用一句话解释是什么，之后可以直接用。

## 大纲与每段必须讲到的事实

### 开篇：Planner 交出四个动作以后
- 主例第一轮的四个动作各自去哪里、谁执行、回什么。
- 反面版本二（24 度变 4 度）：回执“成功”证明了什么、没证明什么。
- 这一章回答的问题。
- 图位：e-overview（原图，清理后）。

### 一、动作交出去以后，谁接手
- 动作列表里每一项有动作编号、工具名、参数（点回 D 章）。云端编排解析动作列表、同一轮的动作同时调用、等结果、再叫 Planner 下一轮。
- 讲卡片 37（Agent Server）：单个工具这一次怎么调；按工具编号查端点和类型、补上下文、选执行器、把结果转成统一回包；音乐这类只回结构化数据的，要再改写成文字；调用结束标记只表示这次调用的输出结束，不表示车上办成了；用户打断时可以通知下游结束请求。
- 工具执行结果和 Planner 整次输出分开存：查“工具到底调没调”要看工具执行记录，不能只看播报历史。
- 真实案例至少 2 个：只口头答应开阅读灯、开全车车窗、开座椅通风，这一轮根本没有调工具（要先和“调了但失败”分开）；答应“每次执行完自动退下”，任务工具没有执行。

### 二、同一个工具名，怎样找到这辆车的实现
- 讲卡片 38：工具定义和工具实现分开；定义全系统一份，描述能力；实现按项目（渠道加应用编号）各存一份，带参数说明、使用提示、端点、版本；每个项目、每个环境只有一个生效版本，发布是一次性整体切换。
- Planner 看到的工具说明从平台动态加载；产品改工具描述要在测试副本验证后同步到平台（工具描述的写法点回 D 章）。
- 接入方式：HTTP、kitex（内部服务调用）、MCP、Frontier 推车端；三方工具现在都走 HTTP。
- 提供方：内部能力平台（车书、音乐、导航控制、系统设置、通讯、媒体控制、智驾、氛围灯等）、AIDV 自建（记忆、人脸、录音纪要、停车缴费、车况查询、目标跟踪、问题反馈）、三方服务商弋途（地点、路线、行程、订座、播客生成、高德两工具）、豆包（联网搜索、图片生成）、方舟智能体（视觉问答）、车端离线（离线车控、离线可见即可说）。
- 同一个工具，不同项目不同提供方：天气查询在上汽由内部能力平台提供、在赛力斯由弋途提供；播客搜索正好反过来。
- 动态工具点回 W 章，一句话。
- 真实案例：一份配置快照里查出启用的配置缺定义、启用的工具编号缺代码映射（讲成核查发现，没有用户侧事故）；管理后台删除接口越权，已修复；美团订座 Agent 经常连接报错。
- 新图：e2-resolve。

### 三、工具清单：谁在干活，各回什么
- 按工具家族讲（车控类、导航地点类、媒体内容类、记忆与人脸类、查询问答类、生活服务类、生成类、任务与目标类、反馈类），每类挑一两个讲输入什么、返回什么。
- 返回不只有成功和失败：地点查询失败要分普通没结果、沿途没结果、缺导航路线；人脸注册失败分账号、缺信息、昵称重复、没检测到人脸、座位上没人。
- 中间状态不是办完：停车缴费回“待扫码支付”，订座回“已提交，待商家确认”，目标工具回“创建中”，用车报告回“正在生成”，图片生成先回“这就帮你生成”。
- 工具会演进、会弃用（车控拆成车辆控制、系统设置、通讯三个；订座改成美团餐厅服务并加排队）；弃用的工具不再出现在当前列表。
- 真实案例：用户自建歌单没有接口，只能打开应用；行程规划还不完整，路测时先关掉这个工具；专辑听一两首说下一首，跳回系统节目。

### 四、车控：一句话怎样变成车能执行的函数，以及不经过 Planner 的快路
- 讲卡片 39，这是本章重点之一。Planner 写的是一句自然语言指令（“打开空调，风量调高一档”）；云端车控模型把它翻成函数编码和参数。为什么要两步：Planner 管理解和规划，不背几百个函数和每款车的参数范围。
- 赛力斯的做法：微调后的车控模型优先，函数不在白名单或参数越界时用检索候选。地图控制也走这一步（“回到地图首页”被翻成“位置复位”）。一条日志里车控模型约 1 秒、检索约 0.1 秒、返回 6 个候选。
- 动态参数（上汽）：用户自己装的应用、自定义的座椅位置、场景、用车习惯名称、联系人，每辆车都不一样；车端把可用值报上来，按车存，翻函数时用；不能把一辆车的名字套给另一辆车。上报成功只说明参数报上来了，不说明车动了。
- 和车上 1.7B 模型的翻译分开（点回 V 章、R 章）。
- 真实案例：老车控模型升级后高并发下输出不稳定，没达到上线标准，继续用旧版本；海外车控模型服务被异常缩容，车控和车设整体异常；公司地址设置多轮确认后，“确认添加”被翻成了播放列表新增。
- 同一段后半讲卡片 44（云端车控干预，裁决 13），作为第四段的一个 h3：为什么要有（常见、明确、容易被模型翻错的车控说法，用规则直接给出函数，又快又稳）；规则按渠道、环境、应用编号分开配，规则命中的函数和泛化问法分开存；验收看三件事：拒识优先、Planner 已取消、车上标了简单车控；真实案例：有预请求时干预偶尔漏命中，修法是在预请求阶段就并行做干预，主链路最多等 200 毫秒，已上线；例子：一句车内聊天里带了车控关键词，拒识先判不是对豆包说的，干预不执行。和 R 章车上固定规则抢跑的区别点回 R 章。
- 新图：e2-fc-translate。

### 五、下发到车，车上回话
- 讲卡片 40。Frontier 长连接把函数推给这辆车，带上函数列表、音区、是否简单车控、请求编号和轮次编号；车上回执按请求编号对上。
- 车控应用调车辆服务执行，回一个执行结果：函数编码、状态、说明，还可能带一句车上建议的播报。
- 四层：已推送（云端日志）、车收到（单台车的设备返回码：30000 看下一步，30001 表示车离线）、车回了执行结果（状态 0 表示成功）、车到了用户要的状态。只有最后一层是用户要的。
- 10 秒是排查分工线（裁决 7）。
- 同一句车控在不同车上有通有不通，原因常在车上控制器的版本，所以不能用一台车的成功当车型完成。
- 真实案例：不同车车窗和天幕有的能控、有的控不了；退出语音的回执写“执行失败，请勿重复调用，需要告知用户”，豆包如实告知；回执成功但车没动（排查指南里的分支）。
- 图位：e-fake（原图，清理后），放在讲四层的地方或第九段，二选一，写作时放在第九段，这里只用文字讲四层。

### 六、回执怎样变成 Planner 读到的那句话
- 讲卡片 41，这是本章重点之一。外层两个字段：工具名、反馈正文；正文可以是自然语言，也可以是一段结构化数据。
- 车控：改写后的指令加函数名加状态，失败附原因。赛力斯：云端读函数编码、状态、说明，不用车上建议的播报；状态成功但说明为空时，补一句“执行成功，可简洁回复做好了｜完成”。这句是云端补的。
- 回执要写清的几件事：实际做了什么、对哪个对象；失败分“已是当前状态”“车上没有这个配置”“这个音区没有权限（写明哪个音区）”；超出能力要分“车上没有”和“有但不支持语音”；用了近似方案要说明，调小了解释原因，调大了或扩大范围先问用户；可以附下一步提示（简洁回复、请勿重复调用、请用户选择）；地点要说清是沿路、某地附近还是目的地附近。
- 失败原因来自车控的业务前提处理（裁决 19）。
- 结构化结果的工具要再改写成文字（音乐要带实际播放的歌名、歌手、专辑，这样 Planner 才说得清放的是替代歌）。
- 长结果：这一轮整段交给 Planner，由它挑重点说；变成历史以后才省略（点回 C 章卡片 30）。
- 真实案例：收藏了错误对象却报成功（只回“收藏地址，成功”）；路线要从朱家角出发，下游用的是当前位置，回执只说成功；音乐回执带了实际歌名，Planner 能说清放的是替代歌。
- 图位：e-feedback（原图，清理后）。

### 七、一批结果怎样收齐，超时和重复怎么办
- 讲卡片 42。同一轮的动作同时调用（点回 D 章），结果一个个回来，编排等这一批都有结果；超时的那一项用失败结果占位，成功的照常保留；整批作为一份完整的工具结果交给输入管理，单独一轮交给 Planner（点回 M 章卡片 22）。
- 主例反面版本一完整走一遍。
- 为什么不自动重试；网络重发沿用原调用编号（裁决 8）。
- 打断：已下发的动作不撤回（点回 I 章）；还在执行中的结果回来后仍然归原来那一步。
- 异步逐个返回是后续方向，一句带过。
- 真实案例：切歌出错的回执在用户打断以后没有交到 Planner，用户却已经在屏幕上看见了错误结果；要切空调自动模式，执行的是空调开关，回执写的也是空调开关成功。
- 图位：e-batch（原图，清理后）。新图：e2-batch-timeout。

### 八、谁来说结果：车控播报和不支持的指令
- 讲卡片 43。通则加车控例外（裁决 10），每种情况举一个主例里的实例：开空调成功（简单车控，车上模板播）；开空调成功、风量失败（有失败，云端说清）。多意图的定义：一句话里有两个以上独立的车控意图。
- Planner 输出的语气标签决定下游用哪种播报能力（唱歌走唱歌工具，其他走 TTS），点回 D 章一句。
- 不支持的指令（裁决 12）。说清是哪个功能：没有尾翼就说没有尾翼，不说“尾翼不支持语音控制”。
- 真实案例：车控不支持时自动讲了无关的车书，已经改了；车书先说不知道、联网搜索再给结果，两条回答割裂（直接调联网的做法上线后回退了）；打开强制保电，先说开了，又说暂时无法开启。
- 设计推演当“**例子：**”：NFC 开关有功能但要在中控屏手动确认；左转向灯和双闪不能语音控制。
- 新图：e2-who-speaks。

### 九、执行这一侧的假成功
- 四个断点（卡片 40 的四层），每个断点怎样造成“说办了其实没办”：回执为空、笼统成功、模式只写占位值、执行错误没回传。
- 要先和“根本没调工具、只是口头答应”分开（第一段讲过），也要和“调了但办错对象”分开。
- 修法：回执写实际结果，再拼一句核对提醒（Planner 侧点回 D 章）；不能靠逐个补车上状态通吃所有问题：事件日志不能随每个函数无限扩充，三方应用状态受接口和隐私限制。
- 一次误报成功会把后面的操作继续带偏：声称已开窗但实际没开，后面又按错误状态去关窗。
- 真实案例至少 3 个：避人吹没生效却说调好了（理想回执应写“副驾打开避开模式”，而不是“切换到某模式”）；人脸注册反复失败时系统设置多次回“摄像头开关成功”，人脸工具却仍报车内智能感知没开；按摩要“舒缓”开了别的模式。
- 图位：e-fake（原图，清理后）。

### 十、问题反馈工具：一个要走好几步的应用工具
- 讲卡片 45。用它看清一个应用工具从受理到办完要经过哪些状态：用户说“刚才导航绕路了”→ Planner 只把这句话转给反馈工具，不自己追问、不预告成功 → 工具第一次进入就建一个反馈任务，通知车上开始采集日志 → 最多追问 3 轮 → 生成不超过 100 字的总结和固定类别，让用户确认 → 用户明确确认才提交 → 车上补齐车辆信息和日志后提交工单。
- 任务身份由服务端按车辆、账号、来源、状态找最近一条，模型不能自己编任务编号。
- 推送成功只说明消息被推送通道接受，不说明车上开始采集了；业务成没成看工具实际处理结果。
- 错误码：未登录、目标不允许、参数不合法、找不到任务、找不到草稿、草稿过期都不可重试；内部错误可重试。
- 同一次请求按车辆加请求编号加来源去重，同一个动作按任务编号加动作幂等。
- 卡片点踩是另一条路：不经过 Planner，卡片消失后才提交。
- 赛力斯已发版、在修问题；8 月有一个面向内部种子用户的早期版本，一句带过。
- 把工程上的错误码接进反馈工具、形成工单是长期想法，一句带过。
- 例子（设计推演）：语音反馈导航早高峰绕路；点踩后又撤销；重复点确认或旧任务已过期。
- 真实案例至少 2 个：可以用路测中用户反馈后豆包没有回应的问题（例如反馈推荐的饭店太远，豆包没有回应），讲为什么需要专门的反馈工具；再用一例真实问题说明反馈要带上当时的语境。

### 十一、怎么排查
- 车控排查从上往下七关：拒识和打断 → 这句话的意思 → Planner → 翻成函数 → 云端下发 → 车上回话 → 车上执行。每关看什么证据、找谁（Planner 改写错找 Planner 算法；改写对但函数错、或车控模型说处理不了，找车控算法；回执超时或回执对了车没动，找车端）。
- 先收齐日志编号、用户原话、预期和实际、时间、视频。用日志编号找调用链，查推理、函数、下发和回执；调用链现在已经能写进数据仓库，用明细查询看。
- 测试环境回执超时，先看车上调用的服务是不是三个机房都部署了。
- 平台的快速测试指定工具时会跳过 Planner，只适合纯文本工具，不能代替实车车控验收。
- 观测分层：下发、回执、真实执行、目标达成分开统计；端到端的六个耗时（说完到出声、到出字等）是用户感受指标，不是单个工具的耗时。
- 每个模块建核心必过集，贴走查结果和视频，持续看通过率。
- 真实案例至少 3 个完整演示：导航 A、B 两地漏了 B（Planner 漏发、工具漏处理还是车上没保存，要逐层看）；找 A 搜回 B；舱内视觉问答只有部分车通。
- 图位：e-debug（原图，清理后）。

## 新图设计（风格和前几章的新图一致，节点不超过 9 个）
- e2-resolve：同一个工具名怎样找到这辆车的实现。从左到右：Planner 的动作（工具名 + 参数）→ Agent Server → 查工具定义（全系统一份）→ 按项目查实现（渠道 + 应用编号）→ 按环境取生效版本 → 执行器（HTTP / kitex / MCP / Frontier）→ 提供方。下方一个小对照：天气查询，上汽 → 内部能力平台，赛力斯 → 弋途。
- e2-fc-translate：车控的两步翻译。左边 Planner 写的话“打开空调，风量调高一档”；中间云端车控模型：先用微调模型出函数，判断“函数在白名单里、参数没越界吗？”是 → 用它；否 → 用检索出来的候选；上方虚线框“上汽：按这辆车上报的动态参数（自装应用、座椅位置名、联系人）”；右边输出两个函数和参数，下一步交长连接下发。底部一句：Planner 管理解，车控模型管函数和参数。
- e2-batch-timeout：主例第一轮一批四个工具：查车况（成功）、开空调（成功）、调风量（超时 → 补“执行失败，请勿重复调用，需要告知用户”）、搜咖啡店（成功，3 家）→ 收齐一批 → 输入管理（单独一轮）→ Planner 统一说“空调开了，风量没调成……”。右侧红色两条错误做法：整批算失败；自动再发一次。
- e2-who-speaks：谁来说结果。一个判断树：云端干预命中？→ 车上播报；是车控吗？→ 否 → 结果回 Planner 统一说（车书查询由车书自己播）；是 → 全部成功且是简单或多意图车控？→ 是 → 车上固定模板 + 车上 TTS；否（复杂车控或有失败）→ 云端说清哪项成、哪项没成、为什么。旁边一个小框：不支持的指令分“车上没有”和“有但不支持语音”，手动方法查车书。
