# VAD、流式二遍 ASR 与预请求：证据研究及课堂讲稿

研究日期：2026-10-22。研究范围：用户指定 OnePager、其引用的多级 VAD PRD 与服务端方案，以及 ASR 一手能力说明。仅供主代理合并到课堂；没有改动课堂 HTML。

## 先把最容易教错的地方说清楚

**这几件事同时发生，但不是同一个判断：ASR 负责把声音写成文字；VAD 负责判断现在还要不要继续等用户说话；预请求利用等待的间隙提前做部分准备；正式请求才把最终文字交给完整业务链路。** 把它们画成“先做完 VAD、再开始 ASR、然后整条链路重跑两次”，会教错。

本次主线应按用户指定的《AI汽车语音基础体验链路 OnePager》讲：Soft VAD 300 ms、Hard VAD 600 ms；Soft 可多次触发且不结束 ASR；Hard 结束该段 ASR，拿到二遍 final 后发正式请求；复用同一 request_id 下前一轮预请求的结果，要求文本完全相同。[S1]

**“按 OnePager 描述”不等于“所有车型当前配置已核验”。** 旧多级 VAD PRD 写 300 / 500 / 1000 ms，明确标“暂定”“待评审”；文末还提出“最短路径”匹配变更。应另列版本说明，不能把这些参数及策略拼成同一套已上线规则。[S2]

## 1. 可以直接用于课堂的讲法

### 1.1 我们先看用户到底在经历什么

假设主驾说：“去……昨天那家游泳馆。”我们先不急着讨论 Planner 怎么找地点。前面还有两个问题要先解决：第一，车到底听到了哪些字；第二，这个停顿是在想下一句话，还是已经说完了。

如果系统一听到“去”就急着处理，后面“昨天那家游泳馆”可能被截掉；如果每次都等很久，用户又会觉得车机反应慢。所以这里要把“尽早准备”和“正式提交”分开：感觉用户可能说完了，先准备；确认这一段结束，拿到最终文字，再决定到底办什么。[S1、S2；场景为教学示意，非实车记录]

### 1.2 ASR：先把话听成字

ASR 就是语音识别。用户说话时，车端持续采音，OnePager 描述为每 200 ms 上送一帧音频。云端识别服务边接收声音，边返回当前识别出的文字。这就是“流式”：用户还在说，文字已经陆续出来，不用等整句话全部讲完。[S1]

这里会看到 partial 这个词，中文可以直接标“过程文字，还可能改”。例如先出来“去”，再出来“去昨天那家游泳馆”。这一路文字适合做及时反馈，也可以支撑流式拒识——判断用户是否在和车机说话，从而决定是否提前停掉正在播报的声音。但它不是最终定稿。[S1]

**200 ms 是这一份 OnePager 写的音频上送分片长度，不是“200 ms 就一定出字”，也不是“200 ms 就回答用户”。** 后面还有识别、网络、判停和业务处理。[S1；解释为直接推导]

### 1.3 VAD：现在是还在说，还是已经停了

VAD 在这里可以先记成“说话活动与停顿检测”。它观察音频中的说话和静音状态，帮助系统决定何时分句、何时结束这一轮收音。ASR 解决“说了什么字”，VAD 解决“这段还要不要继续等”。[S2、S4]

Soft 和 Hard 不是声音的软硬，也不是用户说话音量大小。它们是两档判停策略。按 OnePager，Soft 在较短的 300 ms 停顿上先触发准备；Hard 在 600 ms 上确认结束该段语音。这里说的是停顿阈值，不能从用户开口的第一个字开始倒计时，不能把 300 和 600 相加说成一共 900 ms。[S1、S4]

### 1.4 Soft VAD：我先准备，但还继续听你说

用户停了一小会儿，达到 Soft VAD 的阈值，系统先拿当前已有的文字发起“预请求”。这个词就是“提前准备一次”。它把拒识、上下文等支持提前处理的工作先做起来，并保存结果；此时收音与 ASR 仍继续，不因为准备过一次就认定用户彻底说完。[S1]

为什么要提前做？因为用户还在等待判停的这段时间里，云端可以先处理一部分工作。最终文字如果没变，正式链路就能接着用，用户少等一段。服务端方案写“整体耗时减少 200 ms 左右”，这是方案的预期收益，不能讲成每条请求实测都必省 200 ms。[S3]

预请求只适合准备工作，不能在这里提前把车窗打开或者已经开始导航。早期 PRD 明确只抢跑拒识、意图、简单复杂处理，不抢跑到 FC / Planner / DM；新 OnePager 写拒识、前置无状态任务与 Context。课堂主线应表达成“只跑文档允许的前置准备，不据此提前执行业务动作”。[S1、S2]

这里的“无状态”不要教成完全不读上下文。技术方案专门要求拿到正确会话标识，以便组装对应历史；它要避免的是预请求造成正式对话历史或业务执行上的影响。可以讲：“先看材料、先做判断，但不把这次临时准备当成一次已经正式说过的话。”[S3；后一句为业务解释]

### 1.5 为什么同一句话可以预请求多次

因为用户可能停顿、继续说，又停顿。OnePager 明确 Soft 可多次触发。每次拿到的文字可能更完整，所以同一次用户输入会有多份准备结果。[S1]

request_id 可以在图上标“一次输入的编号”。它把这次输入的预请求和正式请求串起来。round_id 标“这次输入里的第几次请求”：第一份预请求是 1，第二份是 2，正式请求接着是 3。不要把 round_id 解释为三轮用户对话。[S1、S3]

### 1.6 Hard VAD：这一段可以收尾，再等最终识别文字

按 OnePager，当停顿达到 Hard VAD 600 ms，客户端确认这一段结束，让 ASR 对这一段收尾，随后拿二遍识别的 final 文本发送正式请求。[S1]

“600 ms”不是“用户停顿后 600 ms 一定已经听到车机回答”。600 ms 是判停节点；二遍识别结果返回、正式业务处理、回复生成及声音播放还有自己的耗时。调小判停阈值也不等于把所有延迟都解决了。[S1、S4；延迟分段为直接推导]

### 1.7 流式二遍 ASR：不用用户再说一遍，是系统再识别这段声音

一遍流式识别强调尽早出字；二遍识别在分句后，使用非流式模型重新识别这一段音频，给出 final，也就是供后续正式请求使用的最终文字。[S1、S5]

为什么需要二遍？过程文字可能随新音频到来被修正，完整一段音频及句内上下文能帮助识别得更准。内部 ASR 能力说明明确流式输入或二遍模式准确率高于双向流式模式。但“更准”不是“永远正确”；final 的意思是本次识别定稿，不是绝不会听错。[S4、S5]

“非流式”容易让人误会为整段音频必须最后才上传。最佳实践说，音频可以同时送入两种 ASR，流式一路及时上屏，另一条在收到分句或结束信号后给结果。课堂要区分“音频是否边说边传”和“识别结果是否边说边出”，这是两个维度。[S4]

可以用 PRD 中的真实设计示例讲：Soft 阶段识别为“播放音月”，后面最终识别为“播放音乐”。这不是用户说了两次，也不是 Planner 自己把字改对了，是识别结果在正式提交前发生了修正。[S2；该例为 PRD 示例，非实车实测]

### 1.8 最后文字变了，预请求结果还能用吗

按 OnePager，要同时满足“是同一次 request_id”和“正式文字与前一轮预请求文字完全一致”，支持预请求的模块才复用准备结果。否则正式重算拒识与 Context。[S1]

所以“播放音月”的判断不能直接拿来执行“播放音乐”。同样，准备时是“去昨天那家游泳馆”，最后用户补成“去昨天那家游泳馆附近的餐厅”，目的地已经变了，必须按最终文字重新处理。后一个例子为教学示意。[S1、S2]

“前一轮”也很重要：OnePager 写的是复用前一轮 round_id，不是随意在历史缓存中找一句相似的话就拿来用。它也不等于 Prompt / KV Cache；这里复用的是前置业务模块已经算出的结果。[S1、S3]

## 2. 用一个暂停场景把并行关系画清楚

以下为教学示意，300 / 600 ms 按 OnePager；不代表已验证这一句在实车上的语义判定。建议动画上方始终显示“持续收音 / 文字可能更新”，下方分出“临时准备”和“正式提交”两条线。

| 时刻 / 用户行为 | 车端及识别服务正在做什么 | 云端业务正在做什么 | 用户看到或感受到什么 |
|---|---|---|---|
| 用户开始说“去……” | 采音并上送；ASR 逐步返回 partial“去” | 此时不能靠一个“去”知道最终目的地 | 系统仍在听 |
| 停顿到 Soft 300 ms | 触发预请求机会；不结束 ASR | 按当前链路对已有文本做允许的前置处理。若引入旧 PRD 的语义判断，不完整分支要继续等待，不能把两版强行合并 | 不应因为临时准备就开始导航 |
| 用户继续“昨天那家游泳馆” | ASR 接着收到音频，过程文字更新 | 先前准备依据可能已经变化 | 后半句仍能进入当前语音段，前提是尚未被正式截断 |
| 又停顿到 Soft 阈值 | 可再触发一次预请求，round_id 增加 | 以更完整的文字再次准备 | 仍然没有因预请求提前执行导航 |
| 达到 Hard 600 ms | 结束该段，拿到二遍 final | 收到正式请求，检查 request_id 和前一轮文字是否完全相同 | 开始按最终意思正式办理 |
| final 等于上一份预请求文字 | ASR 这一段已经定稿 | 支持缓存的模块复用结果，后续组装正式 Context | 减少重复等待 |
| final 发生修正或用户补充对象 | 以 final 为准 | 不复用不匹配结果，重新做必要前置判断 | 正确性优先，准备时间可能没有省下来 |
| 最终文字交给 Planner | 语音转文字阶段完成 | Planner 结合上下文判断“昨天那家”是否已知；需要时查记忆，再交给导航工具；工具返回后继续判断 | 逐步得到正确地点和导航结果。此行是链路衔接示意，具体工具规则由主代理的 Planner 资料核验 |

注意：“去”是否被完整性模型判为不完整、Soft 后到底取消还是跳过哪类预请求、重新开口时计时器如何重置，不能仅凭本次已读文字补成实现细节。图上可以用“若判断不完整”分支；不要画成模型永不犯错。

## 3. 语义 VAD：听到停顿，还要看意思是否说全

我们开会时可以这样解释：“停了 300 ms，只能说明用户暂时没有继续说。像‘我想订一张去……’，后面明显还缺目的地。语义 VAD 想解决的就是这类问题：结合目前识别出的句子，判断要不要多给用户一点时间。”[S2]

旧 PRD 的具体设计是：Soft 300 ms 做一次完整性判断；Hard 500 ms 也做一次独立判断；表达不完整时进入延长等待，表中写语义 VAD 1000 ms。1000 ms 到时不再继续判断完整性，直接进入后续处理，避免无限等。[S2]

这里有两个必须保留的边界。第一，PRD 写“语义完整性暂不做定义”，要先测试思必驰输出结果，再考虑自研。所以不能自己发明“只要有动词和宾语就是完整”等验收标准。第二，文字同时用了“1000 ms 的时间”和“需多等待收音结束时间 1000 ms”，没有充分写明从哪个时刻起算。不要在教学动画里擅自把它画成额外等 1000 ms，或者固定总计 1000 ms 的精准计时器；应标“延长等待策略，起算与配置待确认”。[S2]

最新 OnePager 的预请求介绍仍写 Soft + 语义 VAD / Hard + 语义 VAD，但主链路明确 300 / 600 ms，没有展开完整性判定门控顺序，也没有写 1000 ms 配置。结论应是“语义完整性有参与依据，具体与 600 ms 的优先关系和延长上限未在这一份资料展开”，不能据此宣称已下线，也不能宣称旧三级方案全量生效。[S1、S2]

ASR 最佳实践另有“语义分句（NLU 分句）”，它在获得识别文字后、甚至拿到后一句后，再判断前一句边界。这是通用 ASR 分句机制说明。不要直接把它与车端多级 VAD PRD 的“语义完整性延长”当成完全相同的实现。[S4]

## 4. 图上该怎么连，每根线为什么成立

| 起点 → 终点 | 线上直接写的中文 | 连线理由 |
|---|---|---|
| 车端收音 → ASR | 持续上传音频分片 | 不等说完才开始识别 |
| ASR → 过程文字 | 边听边返回，文字可能修正 | 用于实时反馈、流式判断 |
| 停顿检测 → Soft 分支 | 可能说完，先准备 | 把一部分计算提前到等待间隙 |
| Soft → 预请求 | 当前文字 + 本次编号 + 次序 | 区分同一句话的多次准备 |
| 预请求 → 缓存结果 | 仅保存前置判断，不进入正式历史 | 避免临时输入污染正式对话 |
| Soft → 继续收音 | 不结束识别 | 用户可能还有下半句 |
| Hard → 二遍 final | 确认段落结束，拿最终文字 | 正式业务不能只依赖临时文字 |
| final → 缓存校验 | 与前一轮文本完全相同吗 | 判断准备结果还适不适用 |
| 校验“是” → 正式后续 | 复用支持缓存的准备结果 | 省掉重复处理 |
| 校验“否” → 重算前置判断 | 最终文字变了，以最终输入为准 | 防止按旧意思执行 |
| 正式输入 → Planner | 最终文字 + 正式上下文 | 这时才规划怎么办事 |
| 语义不完整 → 延长等待 | 旧 PRD 设计，参数待确认 | 避免犹豫和自然停顿被截断；应以虚线标版本边界 |

不要把 ASR 一遍与二遍画成两个不同用户发言，不要把“Soft 预请求”画成“提前播报回答”，不要把“Hard 600 ms”画成“正式回答已播放”。

## 5. 资料口径与易误读点

| 项目 | 文档明确 | 不能擅自补成的结论 |
|---|---|---|
| Soft / Hard 数值 | OnePager 300 / 600 ms；早期 PRD 300 / 500 ms，均有来源 | 500 与 600 是同一配置；全车型均已使用 600 |
| 语义延长 | 旧 PRD 表为 1000 ms，暂定；OnePager 提到语义参与但未写延长上限 | 600 ms 必然覆盖语义等待；或者 600 后固定再等 1000 |
| 预请求范围 | 旧 PRD：拒识、意图、简单复杂；OnePager：拒识与 Context 等前置任务 | 所有 Planner / 工具都提前执行 |
| 缓存匹配 | OnePager：同次请求、前一轮、文字完全相同 | 语义相近即可命中；任意历史结果可命中 |
| 旧匹配变更 | PRD 文末“2 月底演示需求变更”提“最短路径”匹配 | 它已经替代当前 OnePager 的完全一致规则 |
| 预请求方案路径 | 服务端方案三推荐：预请求直接到 AIDV，不走豆包文本链路 | 方案一、二、三同时运行；推荐方案等同上线验收 |
| 无状态 | 允许读取对应会话历史；预请求不进入正式历史 | 预请求完全没有上下文 |
| 缓存时间 | 服务端表 intent_and_refusal 2 min | 所有模块所有版本都统一缓存 2 min |
| 二遍模型 | 内部能力说明：分句后非流式模型重识别该段，二遍结果有 definite 标记 | 用户要重复说；final 必然正确 |
| 通用 ASR 默认 | 模型能力说明默认 800 ms，参数可配置 | 车端 Hard 600 ms 与 800 ms 要简单相加；汽车项目必用默认 |
| 识别次数与请求轮次 | 一遍/二遍讲识别方式；round_id 讲预请求/正式请求次数 | 二遍 = round_id 2 |
| 预计收益 | 服务端方案预期整体减少约 200 ms | 当前实测每次省 200 ms |

## 6. 可直接用于评审的提问

1. “我先确认一下这版交付口径：OnePager 写 Hard 600 ms，早期 PRD 写 500 ms。咱们这次验收哪款车、哪个版本，以哪个配置为准？”
2. “用户说‘我想去……’停顿时，语义判断如果认为没说完，600 ms 会不会直接截断？延长等待从哪里起算，上限多少？我想把这条边界加到验收里。”
3. “咱们现在预请求复用是文字完全一致，还是已经用了 PRD 后面提到的最短路径匹配？如果最终从‘游泳馆’变成‘游泳馆附近的餐厅’，怎么保证不会拿旧结果？”
4. “这次说的耗时下降，是从最后一个字结束算到开始播报，还是只算正式请求进云到前置模型结束？我们把用户等待和模块耗时分开看，避免局部变快但整体没感觉。”
5. “Soft 触发多次时，界面会不会反复从聆听变成思考？原技术方案一提过这个风险，咱们现有方案的验收结果是什么？”
6. “预请求拿的是不是同一话题下的历史？如果新话题标识没带对，‘昨天那家’的准备结果会不会读错上下文？”
