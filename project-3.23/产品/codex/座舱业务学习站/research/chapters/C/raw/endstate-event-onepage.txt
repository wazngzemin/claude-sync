端状态&事件日志上报 One Page

主要判断：车辆数据上报不应被理解为“端状态、VLM、事件日志三条接口”，而是 AI 汽车的车辆情境数据底座：端状态提供实时快照，VLM 提供空间与乘员感知，事件日志把变化串成时间线。当前优先把协议、接入、分发、查询和责任边界收敛清楚，让触发器、Context、Planner、记忆和下游订阅方都拿到同一套可信数据。

一、定位与范围
车辆数据上报服务承接车端、触发器和云端业务产生的状态与事件，目标是把“车里现在是什么状态”和“刚刚发生了什么”变成模型与业务都能消费的标准上下文。



端状态
记录车辆设备、座舱硬件、用户位置等最新状态，支撑规则判断、Context 查询和状态类触发。


VLM
记录舱内外视觉描述、乘员状态和安全/舒适线索，让模型获得“看见车内外”的能力。


事件日志
记录可感知、非规律、发生在时间点上的变化，作为 Context、记忆、主动服务和研发排查的原始事实。
本 One Page 聚焦数据接入与使用链路，不展开字段级协议、代码实现和表结构细节；这些内容保留在技术方案与接口文档中。

二、总体架构
设计上采用“生产层统一接入、规范层统一定义、存储层区分状态与事件、分发层按订阅消费、查询层服务模型上下文”的分层方式。

关键分界：端状态和 VLM 更像“当前世界快照”，事件日志更像“时间线事实”。同一份上报可以进入历史记录，但只有满足事件定义、白名单或触发规则的数据才应进入事件日志和模型输入，避免把高频噪声直接灌给模型。

三、核心设计
3.1 协议：一套定义承接多类数据
端状态、VLM、事件和 Agent 过程数据都沿用“资源定义 + 子资源参数 + 事件时间 + 上报类型”的抽象。产品负责定义资源含义、分类、字段约束和自然语言拼接规则；服务端负责校验、写入、覆盖、分发和查询。
端状态保留最新值，同时沉淀历史，用于“当前车况是什么”。
VLM保留最新场景描述，用于“车内外现在发生了什么可被看见的事实”。
事件日志只保留时间点事实，用于“刚刚发生了什么”，默认不承担总结和推理。
3.2 覆盖：状态按新旧合并，事件按时间追加
状态类数据需要解决“最新可信状态”的问题，因此采用全量、增量、删除三类上报语义，并按事件时间处理乱序；带主键的座位、设备、成员类子资源按主键合并。事件类数据不覆盖事实，只按时间线追加，并通过事件定义、白名单和去噪规则控制进入 Context 的范围。

四、事件专项设计
事件日志是本次调整的重点。事件技术方案和 PRD 的共同结论是：事件不是“状态表的另一份拷贝”，而是车内时空情境中的时间线事实。
4.1 事件生产
事件来源分三类：端状态满足触发器规则后生成事件，客户端直接上报用户操作或设备事件，云端业务记录人车对话、人人对话、任务执行和记忆开关等事件。三类来源都应落到统一事件定义上，避免每个业务自造事件名和文案。
4.2 事件使用
Context：按时间窗口注入事件流，例如最近 10 分钟、最多 30 条，帮助模型理解对话前后发生了什么。
主动响应：高优事件可直接以 event 输入触发新一轮 query，例如 TTS 播报被拒识 query 打断、手动操作车机、上下车等。
记忆：事件日志作为原始事实，供短期记忆总结和长期画像沉淀使用。
研发排查：客户端事件上报保留 request_id、log_id、device_id、event_time 和透传参数，服务端提供受限查询能力。
4.3 事件治理
事件治理要前置到定义阶段。需要明确事件口径、主体、时间、分类、自然语言拼接规则、是否进入 Context、是否触发主动响应、是否进入记忆。对于高频状态变化，优先做去噪、聚合和频率节制；对于人人对话、视觉描述等高信息密度数据，需要补充权限、脱敏和白名单策略。

六、规划与验收
推进节奏建议按“先收敛协议与入口，再打通事件消费，最后做治理平台化”分阶段落地。

P0

统一车辆数据入口

端状态、VLM、事件沿用统一资源定义；补齐基础校验、覆盖和查询。

P1

事件链路闭合

客户端、触发器、云端三类事件进入统一事件日志；支持订阅、短窗口查询和记忆任务生成。

事件可进入 Context，并能触发指定主动响应场景。

P2

事件治理与平台化

建设事件定义管理、白名单、去噪、聚合、订阅配置和可观测看板。

新增事件不再依赖硬编码，业务方可按定义接入。
待确认项
事件口径：哪些端状态变化直接转事件，哪些只保留状态历史。
隐私边界：人人对话、Face ID、车内用户信息进入事件日志和记忆前的授权、脱敏、保留周期。
订阅机制：下游是同步回调、异步消息还是按 Context Query 拉取，需要按业务实时性分层。
模型输入策略：Context 事件窗口、排序、去重和高优事件插入 DT 的规则需要与 Planner 一起定稿。
