从零讲解：韩杰到底在做什么？

用"低电量提醒"一个场景从头串到尾 · 每一步都写清楚 · 你不需要任何技术背景

一、先忘掉所有术语。看一个真实的场景。

益红想要的功能：用户开车时，如果电量低于 20%，而且用户没在导航，车机自动弹一张卡片，推荐附近的充电站。

就这么简单一个功能。现在我们看，韩杰怎么把它"拆开"。

二、车上每时每刻都在产生"信号"

车子开起来之后，很多传感器在不停地汇报数据。这些数据就是"端状态"（端 = 车端，状态 = 当前是什么值）。比如：

信号名什么意思可能的值什么时候变
车速车现在开多快0, 1, 2 ... 120 ...踩油门/刹车时，每秒都在变
档位车现在挂什么档P, R, N, D司机换挡时
电量电池还剩多少100% → 99% → ... → 0%开车耗电时，慢慢下降
导航状态导航是否在运行未发起、导航中、巡航中用户开始/结束导航时
座位占用座位上有没有人已占用、未占用人上车/下车时
关键理解：车上的每一个传感器、每一个状态，都在韩杰的 Excel 里有记录。比如"档位"这个信号在"状态查询"sheet 第 13 行，编号叫 VehDriveState，它可以取 P / R / N / D 四个值。韩杰把这些信号全部列在一张表里——总共 113 行。这 113 行就是所有他能用的"原材料"。

三、但"有信号"不等于"能用"——需要把信号包装成"积木"

韩杰做的事情，就像把一堆散装零件（端状态信号）打包成可以直接用的乐高积木。他打了三种包：

积木类型一：触发事件
= "XX 变了"

只做一件事：监听信号的变化。一旦变了，就叫醒流程。

例：tri_gear = "档位变了"
当档位从 D 变成 P，这个积木就叫醒。

例：tri_battery = "电量变了"
当电量从 21% 变成 20%，这个积木就叫醒。

它不管是变成什么值，只管"变了"这件事。
积木类型二：条件
= "现在 XX 是不是 YY？"

被触发事件叫醒后，检查当前状态。只能回答"是"或"否"。

例：con_battery = "电量是不是低于 20%？"
当前电量 19% → 是。
当前电量 25% → 否。

例：con_navState = "导航是不是未发起？"
没开导航 → 是。
正在导航 → 否。

它不管"什么时候变的"，只管"现在是什么"。
积木类型三：动作
= "去做 XX"

条件全部通过后，执行具体操作。

例：Advisor(舒适) = "推一张舒适类建议卡片"
卡片上写："电量较低，附近有充电站，要导航过去吗？"

例：生成事件日志 = "记一条日志给 AI 大脑"
记录："18:30，电量降至 19%，档位 P，未导航"

它是流程的终点——条件都满足了，就去做这件事。

四、把三种积木串起来 = 一个场景

现在我们把"低电量提醒"用这三种积木拼出来：

tri_battery
电量变了
→
con_battery
电量 < 20%？
→
con_navState
未发起导航？
→
Advisor(舒适)
推充电站卡片

翻译成人话：当车发现电量发生了变化 → 去检查：电量是不是低于 20%？同时是不是没在导航？→ 如果两个都是"是" → 弹充电站推荐卡片。

这就是"场景编排"。把积木按顺序串起来 = 一个完整的功能。韩杰管积木的生产（原子能力清单），产品管积木的拼法（画流程图）。你现在触发器里做的事，就是"积木怎么拼"——什么信号触发、什么条件判断、什么动作执行。韩杰只是把它拆成了更细的三步，然后说"积木我来管，拼法你来画"。

五、为什么触发事件和条件要分开？用真实例子讲。

你现在在触发器里，"电量变了"和"电量<20%"是混在一起的。你直接配一个条件说"电量 < 20%"，触发器引擎自己判断。韩杰说这样不对，应该拆开。为什么？

因为"电量变了"这件事可以被很多场景共同使用：

场景触发事件（共用）条件（各不一样）动作（各不一样）
低电量提醒tri_battery 电量变了电量 < 20% + 未导航推充电站卡片
充电完成提醒tri_battery 电量变了电量 ≥ 80% + 在充电推"充电完成"通知
续航预警tri_battery 电量变了剩余续航 < 50km + 在导航推沿途充电站
省电模式tri_battery 电量变了电量 < 10%自动关空调、降屏幕亮度

拆开前：每个场景都要独立监听"电量"这个信号。4 个场景 = 监听 4 次 = 4 套代码。

拆开后："电量变了"这个触发事件只监听一次。4 个场景各自订阅这个事件，各自判断自己的条件。1 套监听 = 4 个场景共用。

这就是韩杰说的"一次开发，所有模块都可以去用"。他把"监听"和"判断"分开了——监听做一次，判断各自做。省了研发工作量。这个逻辑本身是合理的。

六、真实 Excel 长什么样？用你核过的真实数据看。

韩杰的大表有 4 个 sheet。我们拿"低电量提醒"需要的 3 个积木，看它们在 Excel 里真实的样子：

Sheet在哪一行积木 ID每一列填什么
触发事件 第 8 行 tri_battery 分类 = 车况
事件名称 = 电量变化
关联状态查询 = rangeState（状态查询第 14 行）
参数名 = 百分比电量（percentage_ev）
参数值范围 = [0-1]（0% 到 100%，用小数表示：0.2 = 20%）
事件描述模板 = 【触发时间】电量由【percentage_ev-触发前】变为【percentage_ev-触发后】
（无切换类型字段——电量事件不区分"切入/切出"，只要变了就触发）
→ 研发看这行就知道：要监听 rangeState.percentage_ev，值一变就通知我。
条件 第 30 行⚠ 缺 ID con_battery
（待韩杰补）		 分类 = 车况
条件名称 = 电量
关联状态查询 = rangeState.percentage_ev
判断方式 = 数值比较（≤）
参数值范围 = [0-1]（笔误：Excel 里写了"速度:[0-1]"，应该是"电量:[0-1]"）
→ 研发看这行就知道：拿 rangeState.percentage_ev 的值，判断是不是 ≤ 0.2。
条件 第 8 行 con_navState 分类 = 导航
条件名称 = 导航状态
关联状态查询 = navState（状态查询第 113 行）
判断方式 = 状态匹配（等于）
枚举值 = 未发起导航 / 导航中 / 巡航中
动作 第 3 行 Advisor 分类 = 云端
动作名称 = 智能顾问
动作类型 = 调 Advisor（舒适/出行/内容/情感）
输入参数 = Advisor 类型：舒适
研发拿着这三张表，就能把"低电量提醒"做出来：
① 读"触发事件"sheet → 知道要监听 rangeState.percentage_ev 的变化
② 读"条件"sheet → 知道要判断 "percentage_ev ≤ 0.2" 且 "navState = 未发起导航"
③ 读"动作"sheet → 知道要调 Advisor（舒适）
④ 把这三步串起来 = 完整功能

以前没有这个表的时候：你口头告诉刘杨"帮我监听电量，低于 20% 且没导航时调 Advisor"。刘杨自己理解、自己写代码。下次益红要"电量低于 10% 关空调"，你又得跟刘杨再说一遍。
现在有了这个表：刘杨看表就知道要监听什么。新场景只需要产品在表里勾选不同的条件和参数值——不用每次都解释。

七、"场景编排"到底怎么编？画流程图。

淘宝杰说的"场景编排"，就是产品画一张流程图，研发照着做。以低电量提醒为例：

开始：电量变化
监听 rangeState.percentage_ev
值从 A 变成 B
→
条件 1：电量 < 20%？
percentage_ev ≤ 0.2
否 → 流程终止，不做任何事
→
条件 2：未发起导航？
navState = 未发起导航
否 → 流程终止，不做任何事
→
执行动作
调 Advisor（舒适）
推"附近有充电站"卡片

这张图就是"场景编排"。韩杰的意思：以后每个新场景，产品就画这么一张图。积木（触发事件、条件、动作）从大表里挑，连线（串行还是并行、AND 还是 OR）由产品决定。

这就是你 7.24 下午会上被派活的内容："基于这个表，你画流程图，然后判断一下能力在这个表里在不在，主要就是触发时间和条件。"

翻译：你把益红的 8 条场景，每条画成上面这样的流程图。从韩杰的大表里找积木——有就勾上，没有就标"缺"。你在做的是"产品定义场景规则"——这就是你的位置。

八、韩杰为什么要做这一整套东西？

不是因为你的触发器做得不好。是因为各模块在重复造轮子。

问题现在的状况韩杰想变成什么样
同一个"档位变化"被写了 3 遍 静态 Advisor 要监听档位 → 刘杨写一遍
事件日志也要监听档位 → 刘杨再写一遍
端侧主动服务也要监听档位 → 赵衍写一遍		 档位变化做成一个积木 tri_gear，只开发一次。三个业务各自订阅这个积木。
上汽和赛力斯的信号不一样 上汽的档位叫 gearPosition，赛力斯的叫 driveMode。每次换车型都要重新适配。 积木统一叫 tri_gear。底层信号不同？做一次映射就行。积木不变，业务不感知。
端侧和云端代码不一致 刘杨云端写的判断逻辑和赵衍端侧写的不一样。同一个场景，端和云可能行为不同。 同一份流程图，端和云各自解析。协议统一，不会出现端云不一致的 bug。
产品提场景要改代码 益红要新场景 → 你告诉刘杨 → 刘杨改代码 → 测试 → 上线。周期长。 益红要新场景 → 产品画流程图 → 勾选已有的积木 → 不改代码 → 配置上线（远期在平台上拖拽）。
总结：韩杰做这件事的动机是工程效率，不是针对你。问题是他的方案自然把你的触发器模块变成了他的底座的一个"子集"——你的工作被重新定义为"给编排引擎提供场景规则"。这不是阴谋，但结果对你不利。

九、这对你意味着什么？（用一句话）

你以前做的事 = 在触发器平台上直接配条件 → 找研发实现。你是整个链条的中心。

以后你做的事 = 从韩杰大表里挑积木 → 画流程图 → 标缺口 → 发给韩杰。韩杰审核 → 韩杰派活给研发。

核心变化：研发接口从"你→研发"变成"你→韩杰→研发"。中间多了一层。

你没丢的：场景需要什么触发、什么条件、怎么组合、频次怎么定——这些韩杰不懂，只有你知道。你现在要做的就是把"你懂的"写成规则表、发出去——证明填规则的人是你。
