按图逐步读懂
W01 · 页面业务解析当前可交互控件
车企或业务方读取最上层界面；挑选能执行点击的可见元素；提取显示文字和对应控件对象；不是让 VLM 看图猜怎么点。
可见即可说的入口不是用户先说一句话，而是页面业务先把当前可交互控件整理出来。原流程图由车企或业务方负责界面元素解析与指令生成，字节负责识别和匹配，执行再交回业务方。例如设置页的“座椅加热”按钮需要先注册，普通装饰文字不应都变成可点击对象。root 已浏览器核对原图；VLM 读屏或 GUI Agent 只是长期演进评论，不能写成此方案的当前机制。
W02 · 注册可见词、泛化词与控件 ID
把可说名称与控件 ID 绑定；按规范配置可识别的泛化表达；注册范围对应当前页面或卡片；框架要求每页最多 500 个词。
业务方将控件显示文字、允许的泛化表达和唯一控件 ID 交给框架，形成“用户说什么、要交给谁点击哪个对象”的对应表。每页最多 500 个词是该框架需求上限，不是工具总数。注册完成也不表示能立即点击成功，还要看识别是否使用这些词、页面是否仍有效以及执行回执。例如两个同名按钮不能丢掉各自 ID，否则后续匹配再正确也无法准确定位目标。
W03 · 把有效注册词加入识别热词
注册内容进入在线和离线热词；随有效页面/卡片更新识别词表；热词帮助听对按钮名称；注入成功不等于最终必然命中。
可见即可说把注册词提供给 ASR 热词机制，帮助识别当前页面特有名称。它解决的是“听成哪些字”，还没有决定点击哪个控件。识别服务需要实际收到本轮有效词表，不能以注册接口成功替代。比如用户说歌曲卡片上的生僻名称，ASR 即使听对，还要继续匹配与业务执行。页面切换后旧词是否仍在生效也需要检查；热词技术方案本轮缺权限，具体失效接口仍待核。
W04 · 用户 final 到来，带回本次有效界面
语音链路给出最终识别文字；保留请求编号、音区和页面上下文；过程文字不能直接模拟点击；动态卡片也可注册当前可选项。
用户说出的按钮名先走正常语音识别，等 final 到来后再与本次有效界面的注册内容匹配。不能用尚可能改字的 partial 提前点击。主交互还支持生成卡片的动态 selector，把当前选项注册进来，供“第二个”“就选它”这类选择使用。此类表达依赖卡片与上下文，不能当作本地无上下文缓存。具体卡片入口是否已经准出要按车型核验，不以框架存在推导全车可用。
W05 · 全文、局部或模糊规则产生匹配候选
按框架规则比较文字与注册词；匹配结果可能为零、一个或多个；无匹配就回正常有效 Query 链；不能把任意语义相似都判为按钮。
字节侧语音框架根据最终文字和注册词进行全文、局部或模糊匹配，产出候选控件 ID。规范对较长文字和连续片段有阈值描述，边界需按原规范或负责人确认，不能自行改成自由语义相似。没有候选时，用户仍可能在提出正常车控或问答需求，应回到普通入口处理，不要静默吞掉。一个候选也要确认控件仍有效，多个候选则交回注册方处理，而非随机点一个。
W06 · 多个命中：返回全部候选给注册方
字节不擅自挑第一个控件；把多个候选 ID 交给注册业务；业务按规则选择或完成消歧；尚未确定目标时不得假报成功。
如果同一句话匹配到多个已注册控件，框架把这些候选 ID 一起返回给注册业务，由它依据界面信息处理选择或消歧。比如页面上有两个同名“播放”按钮，仅凭文字不能知道用户要哪个。原材料没有给全车型统一消歧交互，因此图不能发明必然弹框或默认选第一个。产品验收要追到最后确定的对象和实际结果，不能把“返回候选列表成功”算成点击完成。
W07 · 把确定的控件 ID 交回业务执行入口
匹配服务输出确定的目标 ID；注册业务接收并对应当前控件；检查页面及控件仍然有效；尚未点击只是明确了执行对象。
匹配完成后，字节将确定的控件 ID 交回当初的注册业务，业务把它映射到当前界面的真实交互对象。这一步只是交付执行目标，不代表按钮已经被点击。用户说话期间可能切了页面、卡片可能退场，所以必须核对当前对象仍有效。原框架明确业务方负责操作执行，不能把它画成 Director 任意操作屏幕，更不能将注册成功或匹配成功提前说成用户需求已经完成。
W08 · 车企或业务方执行模拟点击
由控件所属业务完成实际操作；使用本页面既有点击执行能力；触发对应界面变化或业务请求；字节匹配层不直接代替业务完成。
业务方收到控件 ID 后，通过该页面已有交互能力完成模拟点击，触发真实界面变化或后续业务请求。例如音乐卡片的播放按钮要由音乐业务真正启动播放，而不是语音框架只展示一个“已点击”标记。点击动画可帮助用户感知，但动画不是最终业务成功。执行责任留在控件所属方，发生权限、页面过期、操作失败等情况时，也应由这一层返回真实结果和原因。
W09 · 业务返回真实成功、失败与可播内容
执行方回传实际点击/业务结果；附上需要统一播报的内容；失败和未完成必须明确区分；匹配成功不能代替执行回执。
操作执行后，业务方将成功或失败等结果及播报内容交回豆包。语音识别、候选匹配和控件接收都可能成功，但真实业务仍失败，例如卡片目标过期或服务不可用，因此一定要等执行回执。混合操作若存在部分成功，不能用一个成功词覆盖失败项。具体回执字段应按正式接口核对；本图不虚构字段名，重点是让用户可见结果与真正发生的行为一致。
W10 · 豆包统一播报，界面按交互规则反馈
播报内容交豆包统一合成播放；成功可有对应点击/结果反馈；失败由系统显示相应 UI 提示；不把失败 Toast 逐字机械念出。
业务返回后，播报内容交给豆包统一处理，而不是每个页面各自抢麦。界面可提供点击动画、成功结果或失败提示，但材料明确失败系统提示不需要把具体文言机械播出来。产品需要分开检查点击后的真实状态、屏幕反馈和用户实际听到的声音。TTS 合成成功还可能被音频优先级拒播或抢占，所以不能仅看回调“有音频”就认定整条可见即可说已经交付完成。
W11 · 把模拟点击写入历史，给下一轮使用
历史标明本次来自模拟点击；同步用户原话、目标和真实结果；避免模型误认为普通问答或 FC；下一句“返回/再选”才能接上。
可见即可说完成后，应把交互结果同步历史，并明确来源为模拟点击，避免云端模型把它误理解成自己生成的普通问答或车控调用。比如用户在卡片中选了第二个地点，后续说“就去这里”，Context 需要知道实际选择了什么，而不是只记下一句“第二个”。同步对象应包含真实成功或失败，不得只写拟执行目标。历史进入系统与实际点击完成仍是两项需要独立验证的状态。
W12 · 卡片退场后注销，页面变化后更新范围
动态 selector 随结果卡片注册；卡片消失时删除对应选择器；新页面重新维护有效注册范围；旧控件不能跨界面继续被点中。
主交互材料明确动态 selector 随卡片出现注册、随卡片消失删除，否则用户离开卡片后仍可能语音点中旧内容。普通页面也必须维护当前可交互对象，但具体注销时点和接口需要按框架确认，不能擅自补一套全局生命周期。产品应验收切页、卡片超时、手动关闭及新卡片替换，确保旧 ID 不再执行；注册列表变化还要同步热词有效范围，避免听对了过期按钮却点错对象。
