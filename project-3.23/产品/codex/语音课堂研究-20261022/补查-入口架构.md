## 2. 可直接插入课堂：为什么“本地先做”还需要端云仲裁
建议插在第四讲，配下文的 3 张离在线仲裁原图。标记：**通用/上汽离在线 PRD 的历史图示，不覆盖 AIVA 0930 的车型差异。**

我们先看一个你在车上真的会碰到的问题：用户只说“打开空调”，结果本地模型很快给出一个答案，云端稍后也给出一个答案。这时候，产品要定义的不是“谁跑得快”，而是**这一轮究竟采纳谁、另一边怎么结束、最后只做几次动作**。这件事叫离在线仲裁——从本地和云端候选中选定本轮要执行、要展示、要播报的结果。

这里要分两种入口。普通唤醒、对话已经激活时，原图允许离线和在线并行准备；本地结果不需要先等云端二遍识别完成。免唤醒还没激活时，原图先让本地判断这句话要不要接：先拒掉与助手无关的话，再检查是否命中本地优先的白名单；需要云端处理的再继续上云。**所以“麦克风收到了声音”不等于“这句话已经决定上传给 Planner”。**

“白名单”就是这套策略明确允许本地优先处理的一组指令范围，不等于“所有车控”，也不等于“所有简单句”。命中名单时先采纳本地；没命中则等待在线；在线超过约定等待时间后，再看本地非白名单能力能不能兜底；还处理不了，就给明确的失败说明。原图写出的顺序是：**本地白名单 ＞ 在线结果 ＞ 本地非白名单 ＞ 通用兜底**。但图没有给等待阈值，也不能据此推定今天每个车型的白名单内容。

再看一个为什么要用上下文的例子。用户先说“打开主驾车窗”，下一句说“再开一点”。“再开一点”本身没说是什么设备，系统需要知道上文。这时本地离线模型是不是掌握了足够信息，会影响它能不能可靠给出答案。旧图因此区分“需要场景上下文”和“不需要”：前者本地范围收窄到白名单，后者可放到更大的离线范围。课堂应把它解释成**给本地判断划清可靠边界**，不要只写一个没有条件的“端云并行”箭头。

动作最终只采纳一份还不够，端云还得认出“这两个结果属于同一句话”。云端技术方案把 request_id 作为一次端云上下文更新和仲裁的凭据；产品可以把它理解为**这一轮请求的编号**。端侧技术方案使用 taskId 描述对齐同一轮任务，具体字段映射需按实现确认，不能把不同文档字段简单画成同一个字段。没有共同关联，后到的旧答案就可能被当成新答案，造成重复回复、错误上屏或对话历史错位。

最后，两个地方判断“用户说完了”的口径也要一致。端侧技术方案明确写了一个风险：端侧处理过的音频送云端后，如果云端判停口径与端侧不一致，云端 Speech 可能一直不结束，后续业务卡住直至 RTC 超时。文档提出“端侧标开始/结束时间，让云端跟着触发”与“调整云端 VAD 时间和端侧一致”两种方案；VAD 事件怎么上传、能否挡住云端 TTS 等仍是 Todo。**这证明需要对齐，不证明已经选了其中一条并上线。**

开会可以这样问：
- “我们先按这一台车、这一版配置对齐：命中白名单以后，是只取消云端展示，还是连云端任务也终止？能不能给我一条端云都返回的日志，确认用户最终只收到一次执行？”
- “这条是需要上文的指令，本地到底拿到了哪些上文？如果没有拿到，我们是等待云端，还是允许它先执行？”
- “弱网兜底的计时从哪个时刻开始？到点之前云端有文字但没音频，算已经返回还是还没返回？这两种对用户等待的影响不同。”
- “端侧说这一轮结束了，但云端还在等，最终页面会卡在哪个状态？这条异常能不能独立验收？”

## 3. 可直接插入课堂：同样叫豆包，不同车型不能直接抄同一条状态机
建议第四讲/第七讲加一个“车型差异”框，来源 AIVA VUI，不改通用流程主结论。

我们在评审中最容易踩的坑，是拿一张通用图去解释所有车。比如通用离在线图讲本地白名单优先，**AIVA 的 0930 更新却明确写：当前赛力斯本地 LLM 的拒识和语义结果都不被采纳，需要等云端，状态机以云端结果为准。** 因此，本地已经算完，不代表这台车已经可以进入执行态、把识别文字认定为有效，或结束“思考中”。本地返回 unsupported，也只是“本地处理不了”，不等于整轮失败，仍要等云端。

这里“状态机”用产品话讲，就是**用户眼前的状态在什么条件下从‘在听’切成‘在想’，再切成‘在说’**。AIVA 表里的明确唤醒词、方向盘按键先进入聆听；“豆包＋有效指令”和全时免唤醒下的有效指令直接进入思考；主动服务拉起可以直接进入播报。不能把每个入口都硬塞到同一个“先唤醒，再等用户说一句”的流程里。

再看屏幕。未激活时，AIVA 不把过程识别文字逐字打上屏，而是等整句被判断为有效指令后才展示；激活以后才流式显示，最终被拒识再清掉。这不是 ASR 有没有识别出来的区别，而是**产品要不要让一句尚未确认对助手说的话，立刻占用车内屏幕**。硬按键唤醒归属主驾，但默认收全车四音区，也不能画成只打开主驾麦克风。

多人合并的边界也必须看版本。AIVA VUI 写的是**第一条指令输出首 token 前**插入第二条有效指令可以合并，之后第二条打断第一条。旧多人 PRD 用的是 FC/工具下发边界。首 token 指模型开始输出的第一个小片段，它和工具指令发出不是同一时刻。评审应问“本车型究竟以哪个事件为准”，不能为了图简洁把它们写成一个判断。

最后说打断后恢复。AIVA 写：播报中先被流式判断打断，但新话最终被判拒识时，**NLG 不恢复，ASR 清空，进入延时聆听**。这和新语音 OnePager 的部分原因允许恢复不是一句话。课堂要并列说清“通用技术链路存在原因门控恢复”和“该 AIVA 文档在此场景规定不恢复”，不能删掉其中一个来制造表面一致。

这篇 VUI 内部还保留一个参数冲突：前面基础定义写延时聆听默认 **60 秒**，后面专门章节和状态表写 **30 秒**。应该标为文内口径待确认，不能自行替团队决定。开会可以问：“前面 60 秒和后面 30 秒，我们这一版按哪一个验收？计时结束时如果用户还没说完，文档要求延长到说完；这条能否一起确认？”

其他已读的 AIVA 结果边界：
- 工具调用名称从 Director 输出工具名持续到工具反馈；TTS 和上屏文字允许不完全一致。
- 卡片生成以工具反馈且该工具定义需出卡为前提。折叠卡片不停止 TTS，也不停止生成。
- 延时聆听期间，拒识/本地 LLM/云端结果未返回或 TTS 播报时暂停计时；临近结束还在说，延长到 VAD 结束，最终有效刷新计时，拒识则退出。
- 主动服务有模型建议和端侧规则两种；静默执行/静默展示不拉起语音，有 TTS 则拉全车音区。
- 多屏显示优先看说话音区，不是控制对象在哪；导航/订餐等跨轮容器按首个交互屏接续。后排无关新任务不必清掉前排旧卡。
- 915 结论明确头枕模式不改变语音 TTS 播放位置；后面旧头枕策略已划掉，不能恢复到课堂。
- 安全警示优先于对话状态；同类默认后打断前。此处是 HAI 多载体呈现优先级，不是端云仲裁顺序。

## 4. 可直接插入课堂：长期架构为什么把“看到—想—做—记住”画成一个圈
建议放总结或主动服务专题，配 D7v/OpIZ/J5q 三图。标题必须带“长期架构愿景”。

我们先别把长期图看成一串系统名字。它在回答的是：**用户没有持续下指令，豆包为什么还会在合适的时候提供帮助？** 例如下雨了、副驾窗还开着，车辆先观察到“雨”和“窗状态”；注意模块判断这是值得关注的变化；舒适方向的 Advisor 给出建议；主 Agent 再结合现在的对话与任务，决定要不要提、怎么提、是不是先问用户；需要执行时交给车控；收到执行结果后再更新任务和记忆。只有把“确实关上了吗”送回去，这个圈才闭合。

Perception 就是**把现在发生了什么收集清楚**，输入可包括车辆信号、音频、视频，输出经处理的状态和场景描述。Attention 就是**从持续发生的事情中选出现在值得开始思考的一件**，可能是工程注册的时间/位置条件，也可能是模型识别出的行为。Thinking 就是主 Agent 的判断和安排，输出不只是话术，还包括动作、任务变更和记忆更新。Action/Express 是动作真正执行、语音和界面真正呈现。Memory 把相关历史保留下来，让下一轮不是从零开始。

这张图为什么有从云端回端侧的箭头？因为有些事不是现在马上做完。用户说“等到家附近提醒我”，系统需要把“到家附近”交给负责观察条件的模块。等条件发生，再带着这个事件回到思考链路。**注册条件成功、条件真的发生、提醒真的播出来，是三个不同的完成点。**

四类 Advisor 不等于每句语音都要排队经过四个模型。旧图将舒适、出行、内容、情感画成可持续观察自己目标的建议方；Planner 接受用户请求，也接受建议。某个事件同时触发多条建议，文档的案例希望汇总再交主 Agent，避免它频繁改计划。这是长期组织方式，具体当前入口和调度应以现行 Planner/Task/Trigger 文档为准。

同样，图里写“全时多模态聆听，替代 ASR 和拒识”，是在描述 Watcher 的长期方向，**不是说今天系统已经没有 ASR/VAD/拒识**。0.8 图、1.0 长期图和 2.6 阶段图应当放进演进栏目，现行课堂主图继续沿本轮核实的语音技术 OnePager 讲。

开会可以这样问：“这条是当期要交付的链路，还是我们希望未来实现的体验？如果是当期，条件由谁观察、建议由谁生成、最终由谁决定执行，执行结果又回给谁？我想把四个责任人和四个完成点在图上对应起来。”

## 5. 其余正文新增事实及不能混写的版本
### 5.1 内部技术架构 202607
端侧 SDK 直接请求 Speech ASR；TTS 在座舱云生成缓存、端侧拉取；当时 S2S 采用纯文本接入。豆包云负责入口通用能力、风控等，AIDV 负责座舱业务编排。句法 RAG 可绕过 Planner，简单分流也可直达 Agent。因此大图不能写“所有 query 都先由 Planner 理解”。该文把视频与 Planner 隔离、纯文本 S2S 局限、RTC 成本/多音区问题作为改造背景。

### 5.2 服务端 AIDV 架构
Flow 决定规则快路、Director 等处理路径；Director 负责具体做什么，Context 提供场景材料，不负责把“我冷”固定改写成车控指令。Agent Server 将展示内容回端、model_content 整成 tool_feedback 回 Director，通常再推理；配置直接返回时可结束。不能画成每个工具都必然再跑一次 Planner。

当前这篇的 saic-dna 示例已写 **2.1 Turbo 标准模型＋详细 SP**，后训练是研发方案。不要直接沿用旧背景里的 Seed 1.8 作为当前确定模型。文中 2026 年 9 月独立 Planner 耗时表和服务模块表口径不同：Director 首字 1300 ms 与 TTFT 1000 ms 不应拼成一个当前承诺。本文档表述的代码现状本轮仅作为该文证据，未独立检查代码或生产配置。

主动服务先经 Frontier 下发建议，再由车端带推荐标识请求 AIDV 回流；不能把“送达”当“执行成功”。Extour Goal 与赛力斯新版 Task Service 的职责不同；文档还明确 Extour Goal 的建议已消费通知缺接口路径，不能画成反馈已接通。

### 5.3 自建平台化与非 IP 改造
平台化的核心动机是把音视频、S2S 也作为可由 Planner 调度的能力，并支持非豆包 IP；当时旧链路视频/语音与主 Bot 能力只能二选一，RTC 多音区连接成本高。该设计写优先 QUIC，但协议章节又给 WebSocket 阶段与会话级长链，属于设计材料，应核实现行选型，不能说全量已切换。

会话级长链方案以 request_id 区分轮次；云端升级在当轮回复结束后发重连信号，端侧保持采音再重连；也要求静默断连节约资源。文本响应、工具结果、ASR 结束、TTS 合成结束是不同事件，**TTS_END 不等于端侧已经播完**。

非 IP 改造进一步描述：原来端音频→AIDV ASR→火山 ASR→识别文字回端→端侧再次请求云端；拟改为音频经 Gateway 到 ASR，一边回文字一边发预请求/正式请求。文本输入仍保留，热词在建联注入。TTS 取消是否需要仍待确认。不得以这份方案覆盖用户所给 OnePager 的每个技术动作。

### 5.4 云端/端侧仲裁技术方案
云端文档区分 request_id（单轮仲裁/上下文凭据）、conversation_id（会话）、chat_id/section_id（话题）、question_id/message_id（单轮问题）。它写配置隔离到渠道、车型、版本；示例白名单只能教结构，不当作当前真实名单。

云端旧 RTC 方案 1 已废弃：希望只传有效音频，但改动大，RTC 又有连续音频限制；方案 2 将文字链路与 RTC 按类别处理。“在线 ASR 前置端侧”在其上下文是端侧先拿在线识别结果再组织文本请求，不意味着在线识别模型被部署到车内。首次启用 RTC 可能增加延迟，不能承诺所有场景首轮无额外建联。

端侧文档列出唤醒后 RTC、IM、离线对话启动、配置获取；端 ASR 交离线对话，处理后的音频交云端，要求 VAD、任务、上下文一致。它还在问 Frontier/IM/RTC 云消息先到时如何挡住、是否损害流式上屏、能否阻塞 TTS，所以这些只能列为风险与待解决项。

### 5.5 路特斯 0.5 V3 与通用对话需求
路特斯 V3 明确 2025 车型范围 Lambda/Alpha/T132A；“沉浸模式”开后没有文本拒识、只听唤醒音区，不能替换当前四音区全时免唤醒。语音合成当时仅云端，异常用固定离线缓存；10 秒弱网超时是该旧版规则。车控执行结果区分无功能、不支持语音、已是目标状态、位置不支持、参数超范围、执行失败及部分成功。该分法适合作为产品训练例子，参数与能力不能照搬当前车型。

对话需求包含 S6/S7/S8 历史目标，提到按需建 RTC、建联中走文本、建好后并行 Planner/S2S，再按 Planner 后仲裁采信；“4 次不用 S2S 且 15 秒无人机对话断联”须标该历史方案。无网本地 NLG 可映射缓存音频，有网可缓存或在线合成；缓存与在线 TTS 是不同分支。文中有旧 Lotus 自我认知写死和特斯拉知识库等实验，不当作今天所有车的配置。
