# 产品目标

- 本地链路目标：轻量决策层，核心目标是“重准轻召、快速执行、有效分流”。

    1. 对简单控制指令做functioncall，缩短响应时延，并提升离线场景可用性。

    2. 对明确不响应的 query 输出 `reject`，为 Always on 提供前置流量过滤，减少无效上云。

    3. 对本地支持范围外或低置信的需求输出“不支持”标签，云端拒识及planner 继续决策。

    4. 通过干预缓存模块承接快速配置正则，支持将特定 query 本地直出

- 本文范围

    - 定义本地LLM模型的核心能力（指令理解、拒识、继承、打断）

    - 定义本地链路的模块职责、端云链路流转及协同的关键机制

# 整体链路

<div class="callout">

**设计思想**

1. **本地重准轻召，云端负责开放能力**：本地只承接确定性强的拒识和简单控制指令；凡是语义开放、依赖实时信息、依赖复杂 planner、依赖第三方内容或低置信的需求，都不在本地硬召回。

2. **本地语义采纳规则：缓存规则抢跑云端，本地LLM只用于弱网，**

    1. 命中白名单正则的 query，优先按配置输出，优先于云端planner作抢跑

    2. 未命中干预时，再请求本地 LLM。

    3. 本地LLM结果是否被采纳取决于网络状态及云端结果返回

3. **全时态前置分流**：Always on 全时态下，用户并未显式唤醒助手，端侧必须靠**流式拒识模型**先判断是否需要唤醒/响应，避免所有音频直接上云造成流量浪费和误唤醒。

4. **激活态端云双跑**：激活状态下，用户有较强交互意图。为降低响应时延，本地链路与云端链路并行启动：本地能确定执行的先执行，不能确定的等待云端。



</div>

【特殊说明】

1. 全时态：

    1. 本地**流式拒识**模型判断attend，则提前音频上云

        - 为提升唤醒首句响应速度，采用本地流式asr请求本地流式拒识模型，

            - 判断attend则提前将音频流式上云，开启云端ASR识别及拒识模块请求

            - 未判断attend则等待完整query最终请求进行判定

        - 提前上云的query不采信本地拒识结果，需等待云端拒识决定reject或recall；~~若本地输出functioncall可以直接采纳（~~0930修改后，不直接采纳本地模型fucntioncall）

    2. 完整query识别完后，根据本地llm的对话结果做判断

        1. ~~若输出functioncall则直接采纳，如果已提前上云，则中止云端请求~~

        2. 若输出reject，

            - 音频已提前上云，则等待云端拒识结果作为最终标准

            - 音频未提前上云，则直接丢弃不唤醒不上云

        3. 若输出funcioncall或不支持则将完整音频上云，请求云端ASR、拒识及planner结果

2. 激活态：

    1. 流式打断：在TTS播报中，用户继续说话，采用partialasr流式请求本地模型，做tts打断判断，打断后则等vadend进入主对话链路判断

    2. 端云双跑：vad结束后，同时走端云两条链路

        - 本地请求ASR和对话结果

        - 音频流式上云请求云端asr及链路

    3. 本地采纳标准

    - ~~若本地对话输出functioncall，则直接采纳，中断云端请求；~~

    - 若本地对话输出reject，则不采信，等待云端拒识结果

    - 若本地对话返回functioncall或不支持，则等待云端结果，继续后续判断

        1. alwayson：需流式拒识判断有效

    - 特殊端云分工：

# 详细设计

## ASR

1. 本地新接入豆包输入法，端云ASR整体策略：

    1. 全时聆听态：

        1. 上云：先用本地asr，且采用本地流式模型做判断是否有效（attend），有效则上云开启在线asr

        2. 唤醒上屏：全时态ASR不流式上屏，最终recall后上屏fianl\_asr

    2. 激活态：

        1. 直接双跑，同时跑端云asr，

        2. 流式上屏：用户说话流式上屏，final\_asr根据端云采纳结果做最终刷新

2. final\_asr根据端云采纳结果做判断，

    - 采纳本地functioncall结果，则使用local\_asr

    - 采纳云端planner结果，则使用cloud\_asr

- **关于流式上屏评审补充**，产品只定义体验需求，不限制先用本地asr流式上屏（可能云端asr更快）

    1. 体验快：字随嘴动，打字机效果

    2. 保持一致：不会多个结果来回切换

    3. 可解释性：最终刷新nlu对应的文字

    

## 上下文

1. 支持范围：

    - 本地上下文是公共context模块的子集，遵循现有context生成、摘要、清空、滚动策略，仅作内容筛选，保留支撑简单理解、拒识判断和本地继承所需的轻量信息。

2. 规则过滤：

    - 暂不支持筛选器做语义检索，仅靠类型规则做过滤

3. 上下文窗口：

    - 本地上下文窗口限制为 30分钟内最多10轮对话。

    - 超出窗口后，本地只保留对话摘要

        - 对话摘要来源：支持端侧获取云端已生成的对话摘要内容

        - 拓展摘要生产范围：同时覆盖端和云的对话问答



4. 上下文同步

    1. （930前置分流逻辑）对话流程结束后，无论本地输出 `reject`、`functioncall`、`unsupported/cloud`，都需要同步进入端云context。

        后续修改：对话流程结束后，根据端云融合的结果，将本地被采纳的结果同步给云端

    2. 若当前轮被本地拒识/不唤醒，也需要同步对话结果

        - 本地进入context，用于拒识结果判定

        - 云端进入情景上下文，不进DT上下文

    3. 同步字段需包含`request\_id/session\_id/sound\_zone/local\_asr\_text/cloud\_asr\_text/final\_result\_type`

`function\_name/function\_arguments`/nlg/`timestamp`

### 流式打断及上云

1. **需求描述**：

    - 解决豆包 TTS 播报期间，用户继续输入导致的交互混乱、说话打不断问题。

    - alwayson下作出提前音频上云的判断

2. **变更项：**把云端实现的流式拒识能力下沉到端侧，

    1. 用于提高打断速度，打断需求层保持一致

    - 请求：使用partialASR流式请求流式拒识模型

    - 响应：

        - 流式拒识预测结果为**barge\_in，**立即打断当前 TTS 播报，继续收音直到vadend，~~后续不做tts恢复~~，按照对话节奏需求做恢复

        - 流式拒识预测结果为**reject****，**静默等待，等新的asr进入继续请求

    2. 用于在alwayson开关开启，且对话未激活时，用户开始输入时做的提前召回判断

    - 整体算法效果待评估

## 端云仲裁

1. 本地和云端的仲裁逻辑如下

    - （原需求为本地llm分流）本地缓存\&gt;本地白名单funcitoncall\&gt;云端planner\&gt;本地非白名单funcioncall（仅断网或超时兜底）

    - （930变更为本地llm兜底）在线时本地缓存可抢跑，无网或超时才兜底采纳本地llm

        - 本地正则缓存\&gt;云端planner\&gt;本地llm（仅断网或超时兜底）

        - 断网或超时：走本地模型functioncall

2. 断网状态

    1. 若本地输出 `functioncall` / `reject`则直接采纳，无需在白名单后处理范围内

    2. 若本地输出 `unsupported\_cloud`，但当前无网络，则播报异常话术：

        - NLG：网络异常，请稍后再试。

        - 频次控制：单次唤醒周期内同类网络异常 NLG 只播报一次，避免重复打扰。

3. 超时状态

    1. 云端请求超过 3 秒未返回，视为云端超时

    2. 若本地已有可执行 `functioncallfunctioncall` / `reject`则采纳，无需在白名单后处理范围内

    3. 若本地输出 `unsupported\_cloud`，则播报异常话术：

        - NLG：网络异常，请稍后再试

        - 超时后云端结果若晚到，不再触发执行





## 离线TTS

- 本地具备TTS播报能力，采用思必驰三方能力输出
