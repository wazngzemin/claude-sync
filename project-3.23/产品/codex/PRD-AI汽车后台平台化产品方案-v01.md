# AI 汽车后台平台化产品方案

v0.1 · 产研评审稿 · 2026 年 11 月 19 日

## 一 方案摘要

**沿用火山 AI 汽车管理平台作为统一入口。对客先把已经在用的触发器做成可交付的权限流程。对内先做一个能自动带入车况的 DT 调试工作台，用来验证对话推理的结果。** 日志二期建议以 2027 年 1 月内部试用为目标，先做单条请求的详情。系统提示词标准化从按项目查看最终拼接结果开始，能力边界的在线编辑和发布另行定范围。

| 评审项 | 建议怎么定 | 第一版交付 |
| --- | --- | --- |
| 对客触发器 | 用已有模块和权限一期做客户试点。优先从已在用的赛力斯项目核定试点，具体渠道、车型和对客动作由交付确认 | 指定车企和角色通过正式开通流程进入火山，能在获准范围内完成场景查看和触发记录查询。配置、测试和发布按双方确认的实际需要开放 |

2. **Planner 调试依赖业务数据。** Planner 根据用户的话和环境决定下一步。系统提示词（SP）给它判断规则，实际输入还可能含端状态、记忆、动态示例和车型能力。Fornax 可以维护提示词、测试 Planner 输出，当前讨论的痛点是车况等动态信息经常要手工填。已有快测能连到一部分 Agent 执行。导航等执行还依赖车端。 [11 月 11 日逐字稿 01:17–10:48](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh) · [Director 对话推理引擎 PRD](https://bytedance.larkoffice.com/wiki/XRuKwJ0VPisdUhkxH0ecY1rRn9g)
3. **车型越多，业务规则越难核对。** 一份项目提示词里可能同时有通用规则、某车型可用工具和项目专属说明。各项目整份独立维护时，改共用规则要同步多次。已经有按车型写的真实能力边界，例如上汽 DNA 的车控能力与语音限制。先让评审者看见项目实际拼接出来的内容，后续再讨论编辑与发布。 [11 月 11 日逐字稿 10:48–13:31、28:14–30:19](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh) · [上汽 DNA 车型能力边界](https://bytedance.larkoffice.com/wiki/JFt0waC0XiIElOkSoHocpfHVnTe)
4. **查问题时要把原话、模型判断和执行结果对在同一轮。** 已有火山日志页和 Fornax Trace（一次请求的处理记录），旧日志需求还有导出和标注场景。文涛有按时间段查历史并播放两路音频的 PPE 测试版，现场版本的原接口缺端状态。PPE 是发布前的预览测试环境。陈西钺与泽民后来聊过 1 月，具体承接和上线口径仍需拍板。11 月 18 日提到「12 月底力争基本完成」的是数据埋点与指标看板一期。 [历史日志需求](https://bytedance.larkoffice.com/wiki/Mw1Bww6rTiV27CkibZkcwdj3nXc) · [11 月 17 日周会 01:23:51–01:25:43](https://bytedance.larkoffice.com/docx/BG24dXxR5oeDt2xjjxzc37b5nih) · [11 月 18 日埋点与看板排期](https://bytedance.larkoffice.com/docx/RnQ2d0o66oQvNgxfQogcXkNwnTh)

## 四 目标与验收口径

以下是评审建议采用的验收标准。先拿项目实际样例建立基线，时间与覆盖规模由负责人确认。

| 目标 | 可核的结果 | 证据 |
| --- | --- | --- |
| 首个车企试点能正常交付 | 一个获准车企的测试账号按真实开通步骤完成业务动作。另一个车企的记录、超范围模块和未授权全渠道创建按各自规则拒绝 | 开通记录、角色和数据范围、实际操作结果、研发与测试回执。测试用两个明确隔离的样本渠道 |
| 内部调试能复现一个真实问题 | 使用者可以固定输入与模型版本，切换同一项目两个有效车况样本，核对平台实际传入的值和 Planner 输出。约定的车况字段由页面获取 | 原问题、Fornax 提示词版本、输入输出、字段来源和时间、人工步骤前后对比 |
| 项目切换可核对提示词差异 | 用两份现有项目配置预览，验证通用规则一致，各项目只显示自己配置的能力、示例或工具。缺值时页面给出来源和提示 | 两套版本快照、配置提供者复核结果 |
| 日志能回答一条请求发生了什么 | 试用至少覆盖一条信息齐全、一条关键字段缺失的记录。显示与原 Trace 同一请求，能指出已知和缺失信息。若接回放，再加从指定轮次定位、播放的用例 | 测试样例标识、页面与原记录对照、芮婷确认原导出及标注使用方式 |

## 六 产品价值

**对车企和交付**，知道去哪里申请、登录后可以做什么、卡在哪一步。对客方案能复用到后续项目时，交付人员可以按既有入口和规则开通实例，减少逐个工具找人开权限。

**对内部产研**，同一条问题可以先查现场，再选择要不要重跑。日志留下当时的证据，DT 调试验证换了车况或提示词会怎样，项目预览帮忙确认当时应该加载哪份车型规则。三个入口围绕实际问题衔接，各自有可见结果。

## 七 功能方案

### 7.1 火山入口和工具接入

沿用 [火山 AI 汽车管理平台](https://console.volcengine.com/aidv-admin) 现有菜单和账号。触发器、模拟器、动态示例使用现有入口。建议 DT 调试放在「Planner 管理」，日志二期沿用「日志查询」。外部登录人只看到权限对应的业务模块。尚无模块角色时沿用权限一期的申请页。内部先把常用工具链接和所属项目说清楚，接入时按下面规则决定形态。

| 工具状态 | 接入形态 | 用户怎样验证 |
| --- | --- | --- |
| 已接入火山、功能可用 | 沿用现有业务菜单和页面。以当前版本和实际权限为准 | 从火山入口完成约定操作，结果仍在原业务模块可追 |
| 已有独立平台，内部偶尔使用 | 经负责人确认后从内部快捷入口跳转，展示工具名称、用途和所需空间权限。举例，Fornax 继续维护提示词和 Trace | 进入正确空间和对应版本，使用现有访问权限 |
| 需要火山里的项目、车况或日志记录配合使用 | 把要联动的业务动作做到对应菜单内。优先做 DT 车况带入，以及请求详情到原 Trace | 从项目或记录出发，在关联页能定位同一次测试或同一条请求 |
| 还在规划或需开对客 | 盘点表先写清状态与开放边界，作为评审输入。具备对应业务和权限能力后进入菜单 | 项目有可用入口、可完成约定动作、使用范围可按真实账号验证 |

### 7.2 触发器对客试点

#### 正常流程

1. **产品和交付确认开放对象。** 先用一个已有车企项目做试点，候选是已有使用场景的赛力斯。写清客户主账号、车企渠道、车型、业务模块、允许的动作和有效期。首批最低动作建议为查看本项目获准场景、定位对应触发记录。在测试和正式配置都发生的项目，再明确各自查、建、改、生效的权限。
2. **账号经过诺亚产品白名单进入。** 产品按已注册的 AI 汽车条目跟进申请，核对开通结果和有效期。研发在该主账号上配置允许的模块及渠道，主账号与子账号共用这份范围。旧 ToB 开白条目服务其对应产品。 [诺亚白名单手册](https://bytedance.larkoffice.com/wiki/Rm1uwiYnGietgukxBwFcpLCqnyh)
3. **实际操作人申请对应模块。** 主账号和子账号都按实际登录人分别授权。还没有站内模块角色时，页面显示「申请模块权限」入口，从所属主账号获准的模块里申请。按现有方案，获批先得到目标模块运营角色。首位外部模块管理员另行授予。子账号要有火山 IAM 准入，IAM 是控制子账号能否调用火山平台对应功能的权限。
4. **在火山完成约定的触发器操作。** 岗位通过「触发器 → 场景管理 / 触发记录」进入。页面和查询数据都按账号范围及模块角色展示。在现有运营角色无法切出客户需要的最小操作范围时，由交付先协助查询或配置，等粒度明确后再开放自助使用。
5. **研发和测试留真实证据，产品核业务边界。** 用已授权账号核正常路径，再用其他角色和测试渠道核拒绝路径，确认最终保存、权限和页面提示一致。权限一期的正式测试结果按现有 Meego 跟，产品统筹跟进客户范围、版本和回执。

#### 角色和操作边界

| 操作场景 | 产品规则 |
| --- | --- |
| 已开白、账号还没有任何模块角色 | 暂无业务菜单与业务数据。用户可从申请入口选择所属主账号允许的模块 |
| 有触发器运营权限 | 进入触发器。只见获准的渠道和模块数据，操作范围按触发器当前规则配置。具体能查哪些人的场景、能编辑哪些记录，以刘杨确认的试点口径为准 |
| 普通管理员或运营创建场景 | 在原授权范围内办理。已有「全渠道生效场景创建权限」细分需求适用时，两者均不可创建全渠道生效场景，测试和正式场景执行同一权限规则 |
| 被单独指定的全渠道管理员 | 按独立细分规则获得创建全渠道场景的能力，实际保存结果与选择范围一致。此权限以该独立需求的版本验证为准 |
| 页面执行本期已经接入审批的敏感操作 | 走站内工单，状态对应待处理或实际执行结果。审批范围按权限一期实际接入项确认。全渠道创建细分这条按原有生效流程处理 |

| PER-03 | 若全渠道创建细分已进入试点版本，用运营和普通管理员各做一次测试与正式场景创建 | 获准渠道的正常创建可用。全渠道选项按权限处理，未授权的操作未产生全渠道场景，提示反映权限原因。已指定的管理员用测试资源验证可选以及回读一致 |
| PER-04 | 如果试点包含一个已接入站内审批的敏感操作 | 测试人员能看到申请、审批到实际执行的结果。拒绝、撤销时配置未变更。工单可定位卡住的状态 |

### 7.3 DT 调试工作台首版

**首版用一个发生过的错误场景，证明汽车的业务状态可以自动跟着这一轮调试走。** DT 是这次讨论里要调试的对话推理模块。页面呈现的首版结果是 Planner 的判断，车端实际执行由已有测试链路验证。首版建议先选一个有可用端状态的项目，固定评审认可的测试模型和提示词版本。

    Planner 管理 / DT 调试

    车辆　[从本项目可用的测试车辆中选择]　[读取状态]
    待带入　字段 | 值 | 数据来源 | 上报时间

| 步骤 | 人做什么 | 平台做什么 |
| --- | --- | --- |
| 1 选定测试对象 | 选受支持的测试项目、提示词版本和车辆 | 显示项目、渠道、测试环境与模型信息，车辆选择范围跟随项目 |
| 2 准备这次用的车况 | 确认所需的车端状态字段 | 取该测试车辆**最近一次上报**的约定字段。先展示值、来源和时间。换车、切项目或提示词版本时刷新确认 |
| 3 输入并运行 | 输入用户原话，核对车况后点击运行 | 将已确认值作为本次输入交给 Planner。结果区显示实际使用的值和判断，包括选中的动作或可获得的原始输出 |
| 4 比对两次结果 | 同句话在另一份有效车况下再测一次。按已对齐的案例预期核结果 | 分别保留每次结果的输入快照，方便定位是车况改变、提示词版本变了，还是模型本身出现不同判断 |

**缺数据时给出可行动的状态。** 车辆无上报、字段缺失、状态超出端状态负责人确认的时效，页面说明缺哪一项并提示重新读取或换已授权的测试样例。页面明确显示上报时间，避免把最近一次上报误读成现场实时值。调试请求失败时保留本轮输入和失败信息，使用者可以重试。

**评审演示建议**用一条现有车控问题，例如用户说「关闭副驾车窗」。先由业务和算法确认该车型对这一句的有效动作和判定预期。用两个已知的车窗状态样本，分别跑同一句话。现场核四件事：使用哪版提示词，接入的是哪个项目的状态，本轮实际读进了什么，Planner 返回了什么。项目切换用另一个受控样例检验旧项目状态已刷新。

**后续扩展顺序**为现有模拟器状态接入、车型与模型切换、其他提示词模块和事件输入。进入下一阶段的依据是实际使用者确认首版能省掉手填变量，且现有测试能复现剩余痛点。记忆、用户画像等字段按具体案例和可用范围逐项接入。 [11 月 11 日逐字稿 01:17–10:48、22:21 起](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh) · [Fornax 提示词开发](https://fornax.bytedance.net/space/7522018773168046082/prompt/develop?page=1&page_size=20&key_word=planner)

### 7.4 项目提示词预览和车型能力边界

**第一步交一页按项目看的最终提示词。** 平台按当前项目找到一版通用模板和约定的项目配置，把模型会用到的文本拼成可阅读版本。请求级的车辆状态由 DT 调试单独展示。项目配置负责车型能力、可用工具、动态示例等随项目变化的内容。

| 页面区块 | 内容和规则 |
| --- | --- |
| 项目选择 | 显示项目、渠道、车型或约定的配置层级。产品与研发用两份已配置项目确认匹配方式 |
| 内容来源 | 每个区块显示名称、来源和可获得的版本。通用模板、项目工具、车型能力和动态示例分别可核 |
| 完整预览 | 展示该项目选定版本的拼接文本，可定位到某个区块。更换项目后所有区块以新项目重算 |
| 异常提示 | 必要的车型或项目配置缺失时提示缺哪一块与维护方，该预览作为缺失待核。页面标识「预览」或「已核对运行版本」，后者需研发能核实真实运行版本 |

**验收**让左晨或相应项目产品选两份已有能力边界。例如对一款有明确车控档位限制的上汽车型，检查预览是否带入该车型的原文、可用工具和动态示例。切另一车型后对照另一份真实材料，找出差异，并确认通用规则一致。对于没有配置的车型，页面指出缺失，模型实际运行时的取值口径由项目和研发确认。

能力边界的后续工作是把现有按渠道手配的文字变成可按车型维护、审核和发布的内容。先确认配置粒度、谁有权审核、如何看生效版本和恢复旧版，再做编辑发布。问答示例是一条典型输入及其期望行为，车型能力边界是一段能做什么的事实描述，两类内容分别由其维护人确认。 [11 月 11 日逐字稿 10:48–13:31、28:14–30:19](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh) · [车型能力边界实例](https://bytedance.larkoffice.com/wiki/JFt0waC0XiIElOkSoHocpfHVnTe)

### 7.5 日志二期和会话回放

**内部试用先做到「找到一条、看懂这轮、能转给研发」。** 从已有火山日志查询进入，按渠道、环境和时段定位。拿到日志 ID 或 Trace ID 时，计划由可用数据源支持精确定位。打开详情，把请求、决策和工具结果对上同一条记录。原记录的完整链路通过 Fornax 查看。

| 能力 | 内部试用建议 | 可用条件 |
| --- | --- | --- |
| 定位一条真实请求 | 用火山日志已有筛选先找到记录，补实际排查需要的精确定位方式。详情显示项目、环境、时间和记录标识 | 数据源经确认能把列表行和原 Trace 对上。同一条请求的两个标识不一致时能说明当前落在哪一条 |
| 看懂发生了什么 | 先展示用户输入、助手回复、能拿到的上下文、Planner 的关键判断和工具执行结果。上下文指模型那一轮读到的对话或车况信息 | 对每项确认有数据、未上报、暂未接入或当前角色不可见。页面按可证实的状态展示 |

| 定位某一轮回放 | 点列表选中的请求，从对应轮次开始听用户原声和助手播报。保留前后轮次浏览 | 先在文涛的 PPE 回放版核音区、时间和历史记录映射。单条日志到回放的精准定位及播放验证通过后再开放 |
| 原导出与标注 | 保留芮婷实际用的字段和取数路径。字段或数据源要改时用现有样例对照，确认新旧结果 | 芮婷核对需要的筛选、字段和下游标注方式。研发核字段是否能从 Trace 拿到，再确定切换范围 |

**回放依赖**是文涛给的测试环境 ppe_cockpit_replay。本轮实际确认到普通日志查询页及会上已有测试回放的证据，指定 PPE 的命中和实际播放还待验证。安排文涛或兆乾用一条获准测试案例展示「列表这一轮 → 对应回放 → 上行和播报」，确认数据源后把界面改动纳入版本。建议 1 月试用的底线是用户输入、时间、执行结果或其明确缺失提示能定位到同一条请求，且可以继续查原 Trace。记录无法可靠关联时，研发先补关联能力，产品在现有页面说明可查的字段和入口。

**用一个共同案例验收三件事。** 从项目和时间定位到同一条请求。用对话原文、Planner 输出和工具结果判断缺口发生在哪一段。拿不到当时的车况时，页面说明缺端状态，能听到音频仍可作为语音证据。出现触发类问题时，可以用同一记录分别核规则版本、端侧有没有及时产出信号、相同测试输入下模型判断有没有波动，以及信号、判断和执行的先后时间。
