🔥 核心：三层漏斗架构分流
用户请求不是全部走最重的 Planner 推理，而是按复杂度分三层处理：
第一层：句法 RAG（毫秒级，规则匹配）
处理范围：明确简单指令，如"打开车窗"、"空调最大"
处理方式：规则级拦截，直接调用车控工具，不进 Planner
优势：极快响应，准确率高，资源消耗低
第二层：情景 RAG + 仲裁模型
处理范围：需要注入用户记忆/车况/情景的请求
处理方式：判断简单/复杂分流，简单的快速执行
注入内容：车辆当前状态（空调温度/车窗状态/电量）、用户画像（不喜欢紫色）、环境信息（外面下雨/气温）
第三层：Planner 深度推理（云端 LLM）
处理范围：复杂需求，如"有点热又有点闷还想听点提神的"
处理方式：多步规划 + 调度多工具 + 跟踪进度反馈
输入：SP（~30K tokens 系统提示）+ UP（对话历史 + 动态变量）
输出：JSON 决策（talk_or_not / talk_content / action_list）

分支 A：对车说话（人机）
→ 立即停止播报
→ 处理新请求
→ 执行新指令
→ 不恢复旧播报
分支 B：人人闲聊（拒识）
→ 继续播报未播内容
→ Event 续播机制
→ 不打断当前服务
→ 保持任务连续性
⚠️ 重要区分
打断播报 ≠ 回滚动作
停播是中断音频输出，但已发出的车控指令（如开空调）不会被取消。
会话、任务、播放是三种不同状态，不能混淆。

六、KV Cache 与上下文优化机制
KV Cache（Prompt Cache）原理
作用：输入前缀完全匹配时复用已算好的 KV 向量
同一请求内多轮调用：第 2/3 轮复用前序全部 token 的 KV，只算增量（几百 token），显著更快
跨请求：仅 SP 固定部分（~30K tokens）可命中；动态变量不同则缓存断裂
长对话问题：超过 20 轮 → KV Cache 占用大 → 易被挤出 → 命中率下降 → 更慢
上下文优化方案（远区精简 + 近区完整）
策略：将 10 轮历史分两区处理
远区（1-8 轮）：只保留 user query + talk_content，删除 tool_feedback 和 action_list
近区（9-10 轮）：完整保留所有信息
效果：节省对话历史 40-70% token，总 input 减少约 10%，实际计算量减少 ~19%（因 Attention O(n²)）
