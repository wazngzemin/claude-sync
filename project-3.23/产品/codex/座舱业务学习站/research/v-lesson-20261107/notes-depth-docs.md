**b. 设计取舍**

- **热词的数量和速度互相牵制**（6 月初实测，环境为上汽 wifi）：
  - 配置 5000 个热词：火山 ASR 首字 P50 680ms，尾字 P50 520ms。
  - 只配置少量热词：首字 P50 538ms，尾字 P50 120ms。
  - 结论：热词越多，识别越准，但尾字明显变慢，所以热词要分类控制数量。（测试周会 6-1 期；H1 双周报：“会带来一定 ASR 识别耗时增长（context 变长）”）——历史 / 已上线
- **ASR 要不要带 FC（让识别结果参考函数调用信息）**：4/13–14 实验显示开 FC 后整体句准反而下降 2.3pp，媒体类下降 5.7pp。当前口径是否带 FC，本次没有找到最终决定。——讨论中 / 历史实验
- **RTC（S2S）链路和文本链路的分工**（2025-12）：
  - RTC 链路负责“体验”，用于联网问答、演绎、闲聊；文本链路负责“稳定”，用于车控、精确任务。
  - 交互的起点始终是文本链路（ASR 上报 → Planner 决策）。用户发出执行类指令时，文本链路会把控制权抢回来。
  - RTC 的代价：需要长连接、带宽高；S2S 长时间不说话会断连，不建议用非官方方式保活。（RTC链路与文本链路的比较分析；自有语音链路技术调研）——历史（后续主链路改为火山 ASR + 文本链路）
- **ASR 指标的口径**：
  - 目标为句准：车控安静 ≥95%、嘈杂 ≥90%；导航/媒体安静 ≥92%、嘈杂 ≥88%；闲聊安静 ≥90%、嘈杂 ≥85%。首字 P50 <300ms，尾字 P50 <200ms。
  - “句准-放宽”指产品允许的差异不算错，例如长句里出现分号、少了“吧啊哦呗”等语气词。
  - （ASR 测试报告页）——已定方案

**c. 真实 badcase**

1. **“24 度”被听成“4 度”并直接执行**（0914 路测）。
   - 用户说“我要通风”，豆包回答“副驾空调调到4度、风量降一档”，工具回执显示“执行成功”。
   - 根因：ASR 识别出的数字错了，下游没有对温度这类车控参数做合理性校验，直接执行。
   - 出处：0914 问题分类汇总（分类“VAD/打断”）——当时线上现状，修复方式未写
2. **“智驾”被识别成“支架”**（0908 外部体验）。
   - 用户问“现在还是退出支架状态对吧”，豆包回答“支架状态是硬件物理状态哦，我没法直接检测”。
   - 根因：同音词识别错误，DT 按错误的文本理解，没有结合车型上下文纠错。
   - 修复方向：0916 方案沟通里写的是“增加ASR的本地化能力，提升对地名的识别率”；“智驾/支架”这类车控词归热词治理。
   - 出处：用户体验问题汇总_算法分析版；问题定义表（“智驾识别为支架”是 ASR 类的定义样例）——修复中
3. **离线 ASR 车控词同音错误清单**（2025-12-18）：副驾→负价、后排→后台、智驾→支架、除雾→储物、小憩→小鸡、座椅→做一、氛围灯→贝蚊灯、刹车→啥车。
   - 根因：离线模型对车控专名的覆盖不足。后续通过热词和替换词修复。
   - 2026-04-01 配置热词后通过率 96.56%，剩余 Fail 主要是人名和“小憩”（被识别成“小汽”或“小七”）。
   - 出处：ASR 测试报告页、热词测试报告——历史 / 已上线（热词）
4. **句首第一个字容易漏识别**：其他车辆上也能复现。出处：0914 问题分类汇总——当时线上现状
5. **识别错误后继续虚构内容**：0811 路测中，“沪”被识别成“互”，豆包接着虚构了植物园的分区。根因归为“链路问题：ASR、说话人身份与上下文纠错未闭环”（L01）。出处：车载豆包典型问题分析——当时线上现状

**b. 设计取舍**

- **单一 VAD 窗口的两难**：窗口短会截断用户的话，窗口长让用户等。多级 VAD 的思路是用“短窗口抢跑 + 长窗口确认 + 语义不完整时多等”来分阶段处理。（PRD 需求背景）
- **语义 VAD 用自研还是用供应商**：PRD 写的是“先测思必驰输出的完整性结果评测后，再考虑是否「自研」”。后来走向是把“说没说完”合并进流式拒识模型的 INCOMPLETE 标签（8 月）和“流式四合一”的 Attend / Wait 标签（10 月）。——历史 → 开发中
- **代价**：切句过细会导致半句话被当成完整 query 发出，引发“过拒”（没回应）或答非所问。见下面的 badcase。

**c. 真实 badcase**（问题定义表：VAD = “语音端点检测过早结束，截断用户说话”）

1. **“那你帮我打开 / 那个 / 设置的地方”被切成三句，三句都没有回复**（0908 外部体验）。根因：VAD 在用户思考停顿时判停，每段半句话都被拒识。出处：问题定义表、算法分析版——当时线上现状
2. **“附近的 / 中石化 / 加油站”**（0912）。第一段就触发回复“你是想搜附近的什么呢”，用户接着补全。根因：VAD 截断后，“附近的”被当成完整意图，多了一轮无效澄清。出处：算法分析版——当时现状
3. **“OK哎我我想那个我那个大灯 / 可以设置成自动吗”**（0911）。第一句没有回复；第二句被当成新问题，答成“电子手刹自动拉起”。根因：VAD 切断后，上下文没有拼接，指代丢失。出处：算法分析版——当时现状
4. **NOA 吐槽长句**：“刚刚我们开了 NOA 它就是自己变道的呀我们都没有拨杆 然后还不打灯”被切句或拒识，用户追问“听到了吗”也没有回复。被列为“过拒”的定义样例。出处：问题定义表——当时现状

**d. 数据**

- 0916 外部体验 184 条问题记录中：VAD 7 次（3.80%），打断/VAD 合计 7.1%，过拒 36 次（19.57%，最大单类）。出处：外部体验报告——评测结论（2026-09-08~14）

**e. 未决**

- 当前线上 Soft / Hard 的取值本次没有找到新的原文（见第 3 节）。
- 流式四合一的首轮准确率只有 15.75%，距离上线还很远。——开发中

**b. 设计取舍（为什么选方案三）**

- **方案一：不改豆包代码**，在 extra 里透传 RequestID / QueryType / RoundID，并控制预请求不落库。
  - 问题 1：豆包侧第二个请求会打断第一个，预请求可能还没到 AIDV 就被中断。
  - 问题 2：端侧 UI 会在“聆听态”和“思考态”（小云朵图标）之间来回切换。
  - 结论：暂无好的解法。
- **方案二（舍弃）：改造豆包文本链路，让它支持预请求 signal。**
  - 侵入性大：文本链路的每个请求都是独立的。
  - 影响面未知：文本链路默认 Signal=1、PSessionId=1，改动后容易踩坑，梳理成本高。
- **方案三（推荐，已采用）：预请求不经过豆包。**
  - 好处：保证豆包链路里的请求全部是正式请求。
  - 预请求只缓存“意图、拒识、简单复杂仲裁”这些无状态结果。Redis key 为 `pre_query:{module}:{channel}:{chat_id}:{request_id}:{round_id}`，缓存 2 分钟。
  - 要解决的问题：端侧还没发起对话时，需要拿到豆包最新的 SectionID 来构造 chat_id，以便对齐对话历史。已确认端侧能拿到。
- **round_id 规则**：每轮 ASR 识别从 1 开始，每发一次预请求加 1，最后的正式请求也在此基础上加 1。同一句话的预请求和正式请求共用一个 request_id。

**c. badcase / 问题**

1. **Soft 时刻 ASR 文本和 Hard 时刻不一致导致抢跑作废**（PRD 场景二）：300ms 时识别成“播放音月”，500ms 时变成“播放音乐”，只能用新文本重新请求，响应略有延迟。这正是 2 月把比对方式改为“最短路径匹配”、并加入 0.75 相似度阈值的原因。——已上线
2. **预请求成本**：上汽每次预请求都调一次 ToB 意图模型；正式请求没命中时还要再调一次。已在 notes-wiki-v.md 记录，这里不重复。

**d. 指标口径**

- Argos 面板“**sft拒识命中预请求占比**”：指标 `aidv_rpc.pre_query.hit.count`，func_key=`reject-analyze-sft`；分子是 `hit_pre_query=1` 的请求数，分母是 SFT 拒识请求总数，计算 hit/total×100。代码位置 `biz/service/pre_query/reject.go:192-202`。——已上线（AIDV Metric 指标与 Argos 看板映射，核对日期 2026-10-28）
- 拒识测试集 Readme 定义了 `hit_pre_query`（True 表示命中）和 `query_similarity`（1 为完全相似）。
- **注意**：H1 双周报 6/15–6/26 有一条“tesla上线，高频词缓存方案，命中率12%”。那是 ToB 特斯拉项目的高频词缓存，**不是**豆包汽车的预请求命中率。两个“12%”容易混，见第 3 节。

**b. 设计取舍**

- **拒识的两种模式**（Argos 面板）：
  - 宽松模式：走拒识 SFT 模型，指标 `rejection.latency model=sft`。
  - 严格模式：走 Judgement 模型，指标 `model=judgement`。
  - 流式拒识另有一个接口 `v1.StreamRefusalHandler`，打点 key 为 `refusal-with-stream`。——已上线
- **单人不拒识的取舍**：数据上准确率只有 80%，但产品认为单人场景的“松弛感”很重要，所以采用云端开关、默认打开、可随时关闭，继续观察线上数据。
  - 背景：原先是端侧 debug 开关。9 月中旬线上回流发现多人场景被误判为单人，走了不拒识策略。
  - 代价：多人被误判成单人时，会把人人对话当成指令回应。
  - 出处：测试周会 9-21、9-28——已上线（开关）
- **流式拒识的谨慎与打断速度**：流式拒识模型为了避免误打断偏保守，往往等 ASR 出 7–8 帧才给出 recall。

  - 出处：测试周会 10-12（数据 9.11–9.14）——当时现状 / 开发中
- **流式拒识对 TTS 的两种动作**：
  - query“帮我把”被判为召回 → 先打断 TTS，再往后判断。
  - query“123456”被判为拒识 → 不打断，只降低播报音量。
  - 依赖车厂提供当前音量；上汽、赛力斯曾经拿不到音量值。
  - 出处：测试周会 4 月——已上线

**c. 真实 badcase**

1. **过拒（漏接）**：“打开前备箱”“帮我关闭零重力”“呃帮我 打开 辅助驾驶”“方向盘上的驾驶辅助键是什么按键”，助手都没有回应（0908–0913 外部体验）。过拒是外部体验第一大类问题（36 次，19.57%）。0914 路测里“那个纯K人民广场店营业到几点”在前两轮“嗯”之后也被漏接。根因：拒识模型对口语化、带填充词、或接在拒识历史之后的有效指令判得过严。出处：算法分析版、0914 汇总、外部体验报告——当时线上现状
2. **过召（误接）**：用户对车里的人说“那我们家在哪呢”，豆包抢答家的地址，用户回“废话谁问你了”。还有“吃饭了吗宝贝”“我都没机会问他”这类话也被回应。根因：人人对话被判为人机对话。出处：算法分析版——当时现状
3. **流式打断错误**：上汽线上 495 条打断，正确率 74.75%（370/495），错误集中在流式 query 不完整、ASR 出字抖动的场景。10.25–10.28 的 310 车回捞数据又发现 5 类 P0 问题：
   - 流式 ASR 打断时的 query 和最终 query 不一致；
   - 单人 ASR 打断时字数过多；
   - 赛力斯同时跑了本地和云端两个流式拒识模型；
   - 流式模型大量错误打断；
   - 打断时 prev_query 等字段为空。
   - 出处：测试周会 10-19、11-02——修复中
4. **打断恢复不合时宜**：用户已经手动导航了 10 分钟，让豆包打开 CarPlay，豆包回答“刚才没说完，回家路线有几个选项……”。0811 路测也出现两个独立任务交替回答（BABA）。根因：被打断内容的恢复优先级过高，没有考虑失效时间。出处：算法分析版、典型问题分析 I01——当时现状（输入管理方案在开发中，见 notes-wiki-v.md）
5. **单人被误识别为多人**：副驾位测试时，日志误报为主驾音区的 query。根因是端侧音区识别。出处：测试周会 9-28——当时现状

**b. 设计取舍**

- **离线指令缓存（cache，也就是“正则/精确缓存”）的三条原则**：
  1. 单轮解析，不引用历史；
  2. 和上下文无关，“暂停播放”“就选它了”这类依赖上下文的指令不放进缓存；
  3. 结果唯一，有歧义的指令回退到其他解析路径。
  - 换来的是命中准确率 100%、耗时 50ms 以内。
  - 初始清单约 30 条，例如“打开空调”“空调调到23度”“导航回家”“放大地图”“退出语音”。
  - 出处：离线LLM指令解析 PRD——已定方案 / 已上线
- **离线模型输出“其他”就上云**：
  - 如果离线模型给出的函数参数值是“其他”，classify=2，走云端。
  - 参数正确时，再按产品定的白名单判断：在白名单内 classify=1，由端侧出结果；不在白名单内，按研发的过滤规则 classify=2，走云端。
  - 出处：仲裁测试集 Readme——已定方案
- **为什么 E68 仲裁通过率只有约 69%**：10-12 期的问题分布里仲裁错误占 77%，说明主要瓶颈在“该不该端侧处理”的判断，而不是函数解析本身。H2 双周报也写“端侧 LLM 部署后 2% 掉点主要来自规则与白名单问题，量化本身 <0.5%”。——讨论中

**c. 真实 badcase**

1. **本地对话链路实车测试**（10-12，113 条，通过率 55.7%），Fail 项包括：
   - 本地拒识把很多明显应拒识的 query 放到云端；

   - history 只有端侧数据，没有云端数据；
   - 少数白名单内的 FC 走了云端；
   - 跨音区继承失败；
   - 不同音区同时说有效 query，只处理了一个音区。
   - 出处：测试周会 10-12——开发中
2. **端云模型版本不一致**：离线流式拒识准确率反而高于在线。原因是端侧已经更新到 9 月优化数据后的版本，云端流式拒识还停在 7 月中的版本。出处：测试周会 10-12——当时现状

**b. 设计取舍**

- **偏好抽取的时机**：豆包 MOA 每轮实时异步抽取。AI 汽车的偏好抽取是**每天凌晨定时离线触发**，只有用户明确要求记住、修改或删除时才实时触发（由 Director 调记忆工具即时生成）。原因是“工程侧在计算资源上的综合考虑”。代价：当天说的偏好要到 n+1 天才进入长期语义记忆。出处：MOA vs Mem0；记忆测试方案——已上线
- **为什么要顺序消费**：长期语义记忆合并要“查老记忆 + 新记忆，再合并”，所以同一用户必须按顺序处理，多个用户之间可以并发。为此从扫表定时任务改为消息队列（推荐 EventBus）。出处：记忆服务优化——已定方案
- **记忆类型与生成频率**（记忆测试方案 10-28）：
  - 短期情景记忆：每 20 轮事件或每 20 分钟生成一次，分导航、车控、多媒体、闲聊（按主题合并）四大类。
  - 长期情景记忆、长期语义记忆、画像：夜间更新（n+1）。
  - 即时语义记忆：Director 调工具时立即生成。
  - 状态：已上线
- **隔离方案选“加字段”还是“新建多对多表”**：选了方案一（在三张表加 `associated_users` JSON 列），改动量小、好落地。方案二改动量大，没选。集合的子集、超集判断放在召回链路的代码里做，因为放在向量库或数据库里“难以平衡效率和结果”。——已定方案

**c. 真实 badcase**

1. **缓存和数据库不一致，导致敏感历史重新进入 Planner**（LogID 202609061616…）。
   - Redis 里的旧历史已经标成拒识，按“成功”类型读取后结果为空。
   - 代码把“过滤后为空”当成错误，降级去查 MySQL。
   - MySQL 中同一条历史的 finish_type 仍是 0（成功），于是被当作成功历史返回。

**c. badcase**

1. **一个连接里多个模块各自生成 TTS，音频顺序乱了**。根因：Sami 返回的音频不带对应文本，同一请求的所有 TTS 写进 Redis 同一个 List。修复方案是统一入口生成 TTS，或者按模块序号分队列写入。另有 Sami 音频前 100ms 是空帧的问题。——已解决
2. **S2S 返回的音频不完整**。根因：Sami TTS 和 S2S 共用一个 chan；Sami websocket 空闲太久被服务端断开，defer 逻辑关闭了 chan，导致 S2S 音频缓存失败。修复：把 Sami 最大空闲时长调到约 180s（和会话时长一致），会话结束时主动关闭连接。——已解决
3. **TTS 在无人说话时断断续续，像被反复打断**（0811 路测 L03）。排查方向：VAD 误打断、音频焦点抢占、长时任务切歌并发。——当时现状
4. **耗时告警是假的**：10.25–10.30 P90 告警超过 5.5 秒，最终定位为端侧上报偏差（见 notes-wiki-v.md）。
5. **火山 ASR 偶发无响应**。根因：火山侧建联 30 秒超时后关闭连接。——已修复（H1 双周报）
