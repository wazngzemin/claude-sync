# I 章设计（Claude 定稿，Codex 按此写作和画图）

章名：I · 插话、打断与恢复：停什么、怎么排、怎么接回来

## 和前两章的分工

- V 章讲过的：流式拒识、打断入门，以及播报被打断后的两种结局。
- R 章讲过的：对话状态机、只办一次。

I 章在这些基础上讲深。凡是前两章讲过的，只用一两句点回，例如“V 章第五段讲过……”。

注意：R 章原来写“以首 token 为界”，这条已按卡片 9、卡片 13 统一改成现行规则。I 章要把“边界为什么往后放宽”讲清楚。

## 资料冲突的裁决

写作一律按下面的结论讲，正文里不提“有冲突”。

1. 合并边界按现行规则讲（见卡片 13）：
   - 回复还没完整输出、语音也还没开始播：新话和旧话合并，重新推理；
   - 语音已经开始播：新话算打断。
   
   早期以首 token 为界，后来放宽，原因是让晚一点开口的人也能被合并进来。要讲出这样改的代价：旧推理被作废的次数变多，多花算力。

2. 主动建议不抢占：用户请求正在处理时，主动建议进入等待队列。

3. 工具反馈单独处理，不和用户的话合并。即时卡片在工具结果返回时就出卡。

4. 主动建议的去重：每条建议单独排队，按 task_run_id 去重。

5. 新话被最终拒识之后（见卡片 14）：
   - 现行做法：新话来时，旧播报先暂停而不是停止；新话被拒识后，从断点接着播；
   - 旧做法：用一个恢复事件让 Planner 重新生成。
   
   两种都讲，讲成一次演进：为什么从“重新生成”改成“暂停后续播”——前者慢，而且重新生成的话可能和原来的不一样。

6. 新话被接住之后：Planner 把新要求和没说完的旧内容合在一起，生成一段不重复的新回复。

7. 不恢复的情况：单人打断、离线车控打断。永久中止的播报不能复活。

8. 停下来的四个层次，分开讲，这是本章重点：
   - 停声：暂停或停止播报；
   - 停推理：让旧推理失效；
   - 不再执行：旧推理里还没下发的动作，不再下发；
   - 已经执行的动作：不会自动撤销。例如空调已经开了，不会因为用户插话就关掉。这是有意的设计，要讲为什么——自动回滚的风险更大。

9. 算和发分开：下一轮可以提前开始算，但要等前一轮播完才能发出去。

10. 延时聆听按 30 秒讲。

11. 长时任务被打断后再拉起来：目前还在开发，用一句产品事实交代，不展开。

12. 途经点被删除后，相关任务怎么处理：讲成两种设计选项及各自的利弊。
    - 选项 A：自动取消任务；
    - 选项 B：保留用户目标，并询问用户要不要清理。

13. 首字速度和实际听感：讲清两者不是一回事。首字统计快了 400～500 毫秒，用户听起来不一定觉得快。

### 四、旧话说到哪了：播放进度
- 讲播放进度上报（卡片 14），第一次出现时要讲全；

- 打轴；已说和未说的切分；
- “未知”不等于 0；
- 为什么要报真实进度：生成了不等于用户听到了。

### 五、怎么接回来：三种恢复方式
- 暂停续播、事件重推、融合新话（裁决第 5、6 条）；
- 不恢复的情况；
- 恢复价值判断（卡片 15）。
- 图位：i-forms（原图）。
- 新图：i2-resume-paths。

### 六、接回来以后：历史和真实结果对得上
- 讲历史记账（卡片 16）；
- 没播的话不能记成说过；
- 旧执行失效，但工具的真实结果要保留；
- 卡片和屏幕：即时卡片的时机、多屏；
- 多轮语义相关判断：上汽用一个单独的模型，判断后一句和上一轮是否同一话题，以此决定卡片保留还是收起。
- 新图：i2-ledger。

### 七、不同车型和场景的设计选项
- 上汽和赛力斯：主逻辑大体相同，差异主要在界面容器和第三方卡片；
- 流式拒识跑在车上还是云端；
- 连续对话时长；
- 途经点变更的处理（裁决第 12 条）；
- 长时任务的恢复（开发中）。

### 八、怎么评估、怎么排查
- 打断通过率、恢复正确率、首字速度和实际听感的区别；
- 排查顺序：判断 → 停了哪一层 → 输入管理怎么处理的 → 播放进度 → 恢复路径 → 历史；
- 用真实案例演示排查过程。

## 新图设计

风格与 V、R 章的新图一致，节点不超过 9 个。

- **i2-stop-layers**：四层阶梯，从浅到深依次是停声 → 停推理 → 不再下发 → 已执行不撤销。每层写清：谁来做、用户看到什么。用例子“讲餐厅时插话开座椅加热”贯穿四层。
- **i2-merge-boundary**：一条时间轴。旧请求依次经过：开始推理 → 首 token → 完整输出 → 语音起播。在轴上标两条线：“早期边界（首 token）”用虚线，“现行边界（起播）”用实线。线左边是合并重推，线右边是打断。
- **i2-input-queue**：输入管理示意图。左边四类输入（query P0、advice P1、event、feedback），中间是输入管理，右边是五种处理结果。用颜色区分可以合并的和必须单独处理的。
- **i2-resume-paths**：起点是“播报中被插话 → 先暂停”，分三支：
  - 新话被拒识 → 从断点续播（现行）；
  - 新话被拒识 → 恢复事件、重新生成（旧做法，用虚线）；
  - 新话被接住 → 融合新话和未说的内容。
  
  底部单列“不恢复：单人打断、离线车控、永久中止”。
- **i2-ledger**：四栏对账，分别是：模型生成了什么、用户真正听到了什么、屏幕显示了什么、工具真实结果是什么。用例子说明哪些内容进入历史。
