# R 入口与端云采信

summary: 确认这句话是不是在跟豆包说，再决定本地还是云端办理；同一句话只真实执行一次。

## INTRO

上一章已经把“带我去昨天那家游泳馆附近的餐厅”变成最终识别文字，也留下了说话音区和同一次输入编号。走到这里仍有两件事没有发生：系统还没有确认这句话是不是在向豆包提出需求，也还没有决定由车上本地能力还是云端链路办理。

用户刚刚喊过唤醒词，或者正在回答豆包的问题，这次属于已激活对话的续说；如果车上支持并开启全时免唤醒、对话又还没有激活，则要先判断用户是不是在叫助手。这两种状态会影响音频何时上云、识别文字何时上屏。

车上有一个本地小模型，云端有一个大模型，两边可能同时算出结果。入口与端云采信要保证同一句话只真实执行一次：联网时以云端为准；断网或云端 3 秒没回，才放本地去办；云端结果晚到了，要拦住它不让车再做一遍。

## r-activation 先认入口与激活态，免唤醒才边听边判断要不要接

入口的第一个判断是这次话语来自唤醒词、物理按键、已激活后的自然续说，还是未激活状态下的全时免唤醒。并不是每一句话都必须先喊唤醒词。系统还要确认本车型是否开放该能力、当前开放哪些音区。

已经激活的对话允许本地和云端并行准备候选，减少等待；尚未激活的全时态先走本地流式召回，不把所有车内声音直接送上云。出现 attend 可以提前放行音频；未放行且最终无关、音频从未上传，可以静默结束。

音频一旦提前上云，即使本地后来判 reject，也不能随意撤回云端处理，要等云端最终召回或拒识。客户端、豆包云、AIDV、Speech 云分工见 AIDV 端云链路 OnePager；本章只管激活态与免唤醒态走哪条准备通路。

屏幕文字也服从状态：未激活全时态不把闲聊逐字上屏；激活态可以流式展示，再按被采纳结果刷新。屏幕先出现几个字，只说明正在收听，不表示已经接受操作。

## r-reject 正式拒识先分清“不该接”和“本地不会”

完整话语定稿后，正式拒识判断这段话是否应该进入助手处理，不是判断导航能不能做，也不是简单复杂分类。副驾问主驾“昨天那家怎么样”可能只是聊天；明确让豆包找餐厅，才是诉求。

本地候选要分成三类：FC 是结构化操作候选；reject 是无关助手；unsupported 是有效但本地不会。把有效联网需求当成 reject 会安静吞掉；把闲聊当成需求又可能突然搜索打扰聊天。

拒识不创建新任务，也不能取消原来正在办理的有效工作。有效请求交给输入管理，再配 Context 进入 Director。10 月 22 日宣讲口径：Director 替代早期意图分类与简单复杂仲裁，旧漏斗不是每条请求的必经层。

## r-arb 并行准备省时间，采信才决定谁真正生效

有效需求确定后，本地和云端可以一起准备候选。“并行”解决等待时间，“采信”控制哪一个结果真正生效，两者必须分开看。画两根箭头分别通向车辆，容易把“两边都在准备”误解成“两边都能控制车辆”。

最先匹配的是确定性缓存：单轮、无历史依赖、意图和参数唯一。没命中再由本地 LLM 在有限范围内生成候选。9 月 30 日之后：正则缓存可优先；正常联网云端 Planner 优先；本地模型只在断网或云端超过 3 秒未返回时获得兜底资格。

较早的离在线仲裁稿写过 2 秒无心跳降级，与本地链路 3 秒业务等待超时不是同一计时器。当前车型从何时计时、如何降级，要对照软件版本核验，不能拿旧方案定义全部车型。

本地接手后必须拦住迟到云端，尤其是“再低两度”这类相对操作。本地真实办理过的事还要同步回端云上下文，否则下一句云端承接会丢事实。网络恢复后的补同步仍标待核，不能写成全车型已上线。

## r-channel 云端接到的是正式文字请求，识别与汽车业务分通道

当请求由云端办理，当前文本链路并不是把声音直接送给 Planner。车端先经 AIDV 请求语音识别，识别文字回到车端；车端再向豆包云发起正式文本对话，豆包入口完成通用处理后，把汽车业务交给 AIDV。

AIDV 再组织输入管理、Context、Director 和下游工具。识别通道和业务通道前后相接，承担不同责任。一次语音交互会经过用户音频 → ASR 识别文本 → 待播报文本 → TTS 音频四种数据形态。

工具真实执行、回执和播报口径在工具与输出章展开；本章只讲到入口判断和结果采信。

## CLOSING

到这里，系统已经确认这句话该不该由豆包接，以及本地与云端谁的结果生效。下一章（输入管理）面对的是并发到达的用户新话、建议、工具反馈和打断事件，谁先进入推理、旧候选还能不能取消；不要在入口章把“有效请求已交出”写成“Director 已经办完”。
