## 1. 唤醒与全时聆听：先决定这句话能不能进入交互

### 配图说明
新图，七个节点：灰色“车内有人说话”分成两条线，分别进入青色“喊唤醒词”和“全时免唤醒已开启”；前者连接“进入激活态”，后者连接“本地先判断是否应接话”，再连接“有效输入上云”；两条线汇入“后续识别与理解”。灰色是输入，青色是处理，紫色标注开关和当前交互状态。旁注：箭头表示进入后续处理，不表示动作已执行。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 唤醒是明确叫助手开始接话，全时聆听是允许它在未被叫醒时先判断这句话是否值得接。 |
| Why 为什么要 | 既要减少反复喊名字的麻烦，也要避免乘客聊天时助手不断插嘴。 |
| Who 谁负责 | 车端记录开关和交互状态，唤醒或本地判断触发后续链路。 |
| When 什么时候用 | 每次说话前，系统都需要知道当时处于未激活还是已激活状态。 |
| Where 在链路哪里 | 在声音进入正式助手交互的入口。 |
| How 怎么判断 | 显式唤醒和全时免唤醒分开处理，后者先在本地判断是否需要提前上云。 |
| How much 范围多大 | 音区、开关和持续时间依项目需求，不能把一份 PRD 的暂定参数当作所有车的现状。 |

### 第二步：七个问题逐条讲透

**1. What：它到底改变了什么？**
用户喊“豆包豆包”是在明确指定交互对象。车内语音 PRD 定义了这个唤醒词；识别出它之后，助手进入可以接续对话的状态。[V01-F01] 全时聆听又叫 Always on，全时免唤醒开启时，未激活状态也能检查用户输入，不要求每句话前都喊名字。AIVA 本地链路要求这时先用本地语音识别产生文字，再用本地流式模型判断是否需要提前上云。[V01-F02]

| 容易混的东西 | 真正含义 | 不应据此推断什么 |
|---|---|---|
| 麦克风收到声音 | 有声音可供处理 | 不代表已经唤醒或发起任务 |
| 全时免唤醒开启 | 未激活时也有接话判断入口 | 不代表所有声音直接上传或都要回答 |
| 已激活的连续对话 | 当前正在与助手交互 | 不代表后续每句都能跳过项目的拒识规则 |

**2. Why：为什么不能只靠一个开关？**
教学例：主驾向副驾说“带我去昨天那家游泳馆附近的餐厅”，如果把“全时开启”理解成“一律接话”，导航可能在乘客讨论时自己启动。反过来，如果始终要求唤醒词，用户接着说“附近的餐厅”又会被丢掉。入口要同时考虑用户是否开启功能、当前是否已激活、这句话是否在叫助手。这里说的是可能的用户后果，不是新增实测 badcase。

**3. Who：谁负责哪一段？**
车机提供当前开关和状态，并运行本地处理。全时未激活时，本地流式判断给出 attend，可理解为“值得让云端继续听”；云端再做识别和拒识。已激活时，本地 PRD 规定端云并行处理。[V01-F02] “提前上云”只是把判断接力给云端，不能当作“已确认该执行”。

**4. When：什么时候状态会变？**
全时 PRD 区分“开启且未激活”和“已激活的连续对话”。前者不把闲聊的过程识别文字实时显示在屏幕；最终召回后才上屏。连续对话期间则显示实时识别文字。[V01-F03] 文档中的连续对话倒计时写为暂定，具体车辆的值要查其配置；不能用这个历史需求反推当前实车。

**5. Where：它和 Planner 的距离有多远？**
Planner 是后面负责决定查什么、调用什么工具的任务规划模块。唤醒成功只打开入口，声音仍要经过识别、判停、该不该接话的判断，才有机会交给 Planner。入口错了，后面的模型可能根本没收到请求。

**6. How：用户说“它没理我”，按什么顺序查？**
先确认测试当时的开关、音区和激活状态；再看唤醒事件或本地 attend 是否产生；接着看音频有没有按对应路线送到云端；最后才查云端的拒识和任务执行。评审时可以直接问：“这条失败样本停在哪个入口？请把当时状态和上云记录放在同一条时间线上。”不要只拿“功能已开启”的截图证明语音已经进入正式链路。

**7. How much：哪些数字不用背？**
全时 PRD 写了连续对话 30 秒，但明确标注“暂定”。它还定义了依据座椅传感器和 Face ID（人脸身份标识）判断位置有人后再开该音区的需求。[V01-F03、V01-F04] 这些是范围和验收问题，不能表述成已在所有车型上线。

### 第三步：放回主例
主例默认用户已经明确对助手发起交互，再说“带我去昨天那家游泳馆”，停顿后补“附近的餐厅”。如果改成未激活的全时场景，必须先经过本地入口判断；后面的“停顿补话”故事才开始。主例不假设仅凭这句话就一定能成功唤醒。

### 第四步：讲给别人听（30 秒）
> 唤醒和全时聆听解决的是助手什么时候开始接话。喊唤醒词是明确叫它，全时免唤醒是在未激活时也先检查用户输入。进入交互、音频上云、最终接话和实际执行，是不同状态。遇到不响应，先查开关、音区和激活状态，再查是否进入后续链路。

### 查阅区
- 唤醒词“豆包豆包”：车内语音 PRD 的需求定义。[V01-F01]
- 全时连续对话 30 秒：暂定需求，当前项目值待确认。[V01-F03]
- 旧车内语音 PRD 的“主驾免唤醒”小节明确标“删除”；不要拿其中“无需拒识”作为现行全时规则。[V01-F05]

## 2. 声学前端：先把声音和说话位置处理好

### 配图说明
新图，七个节点：灰色“人声 + 环境噪声”进入青色“麦克风采集”，随后经过“降噪”“回声消除”；紫色“扬声器参考声音”指向回声消除；处理结果连接“声音 + 音区”，再连接“语音识别”。灰色表示现场输入，紫色表示辅助信息，青色表示处理。旁注：降噪和回声消除是职责示意，不宣称工程算法严格串行。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 声学前端把麦克风收到的混合声音处理成更适合识别的声音，并提供说话位置。 |
| Why 为什么要 | 风噪会盖住人声，扬声器播报可能被再次收进去，音区错了可能把指令算到另一个座位。 |
| Who 谁负责 | 车端语音处理能力负责，车机提供麦克风和扬声器参考信号。 |
| When 什么时候用 | 声音采集后、交给后面的语音识别之前。 |
| Where 在链路哪里 | 在车上处理声音这一段，输出还不是用户指令。 |
| How 怎么排查 | 先听原始输入，再比较处理后声音和音区，最后检查识别文字。 |
| How much 好到什么程度 | PRD 有处理时延和信噪比要求，但需求指标不能当作已达成成绩。 |

### 第二步：七个问题逐条讲透

**1. What：这一步没有“听懂”什么？**
它先处理声音质量。降噪降低空调、轮胎、风雨等噪声的干扰；AEC 是 Acoustic Echo Cancellation，中文叫声学回声消除，它利用扬声器输出的参考声音，减少车机自己的音乐、导航或播报再次进入麦克风的影响。[V02-F01、V02-F02] 音区则回答“声音来自哪个座位区域”。输出仍是声音和位置，后面的 ASR 才负责把声音写成文字。

| 容易混的东西 | 输入 → 输出 | 不负责什么 |
|---|---|---|
| 降噪 | 混有噪声的人声 → 干扰较少的声音 | 不判断话是对谁说的 |
| 回声消除 | 收音 + 扬声器参考 → 减少自身回声的声音 | 不等于可以消掉一切外部手机声音 |
| 音区识别 | 声学等信息 → 说话座位区域 | 不等于认出这个人的账号身份 |
| 后续拒识 | 文字及相关上下文 → 是否接话 | 不代替麦克风和声学处理 |

**2. Why：错了会出现什么可见后果？**
教学例：豆包正在读餐厅介绍，自己的声音又被识别成用户输入，界面可能跳出一段“用户说的话”；主驾声音被算成副驾，后续“我这个座椅”就可能指错对象。这些症状看起来像模型理解差，但如果处理后的声音或音区已经错了，单改 Planner 提示词不能修正入口事实。

**3. Who：产品经理该向谁要证据？**
先让端侧语音与车机集成侧提供同一时刻的原始收音、处理后收音、参考音和音区记录。离在线仲裁技术方案明确，车机采集麦克风和参考信号，离线语音模块处理后，一路产生端侧识别，一路把处理后的音频送云端。[V02-F03] 产品经理需要确认“送出去的到底是什么”，不必先背算法名字。

**4. When：播报时为什么尤其要看它？**
播报时麦克风可能同时收到人声和车机声音。回声消除的需求覆盖音乐、导航提示和电话等不同输出，并要求在不同音量下有效。[V02-F02] 所以安静驻车、没有播报的测试通过，不能替代“播报中用户插话”的验收。

**5. Where：音区为什么要一路带下去？**
音区让后续模块知道谁在什么位置说话，用于交互归属和相关控制。它是座位位置，不直接等于人名或 Face ID。PRD 甚至专门要求座椅躺倒时仍识别原座位，避免主驾被算成后排。[V02-F04] 是否进一步绑定身份，属于后面的状态与记忆体系。

**6. How：排查顺序是什么？**
先还原噪声、播报音量和乘坐姿态；再听原始人声是否清楚；然后比较处理后有没有丢字或残留播报；再核对音区；最后比较端云识别文字。如果声音已经缺了一段，要先修声音输入；如果声音完整、文字错了，才进入 ASR 排查。建议同一条样本关联所有记录，避免不同录音条件的结果互相比较。

**7. How much：需求数字怎么读？**
车内语音 PRD 要求处理时间不超过 50 ms、信噪比至少 20 dB；信噪比是在比较有效人声与噪声的强弱。[V02-F05、V02-F06] 它们是需求，不是本轮读取到的实测结果。是否满足，要看车型、麦克风配置和测试工况。

### 第三步：放回主例
用户说“带我去昨天那家游泳馆”，此时系统先要保住“昨天”“游泳馆”等声音并认对说话位置。用户停顿后补“附近的餐厅”，如果后半句被噪声盖住，后续系统拿到的请求就缺了真正目标；记忆再好也无法凭空补出这句话。

### 第四步：讲给别人听（30 秒）
> 声学前端先解决声音能不能被听清，以及从哪个座位传来。降噪压环境干扰，回声消除减少车机自己播报的干扰，音区给出位置。它不负责理解需求。出错时先比较原始声音、处理后声音和音区，再追识别文字，不能一上来就怪大模型。

### 查阅区
- 处理时间 ≤50 ms；信噪比 ≥20 dB：PRD 需求，非实测。[V02-F05、V02-F06]
- 多参考音“暂定 4 路”、定位误差 ±20 cm、躺倒角度大于 120 度的示例：保留为需求细节，具体项目验收口径待确认。[V02-F07、V02-F08、V02-F04]

## 3. ASR 语音识别：声音怎样变成过程文字与定稿

### 配图说明
新图，七个节点：“处理后声音”分到“端侧 ASR”和“云端 ASR”；云端 ASR 连接“过程文字 partial”和“二遍定稿 final”；过程文字连接“提前判断”，定稿连接“正式请求”。灰色是声音与文字，青色是处理，紫色标注当前采纳哪一路。箭头必须写明传的是声音还是文字。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | ASR 是自动语音识别，把声音写成文字，过程结果可以变化，定稿用于正式请求。 |
| Why 为什么要 | 下游必须拿到准确文字，才有机会理解正确需求。 |
| Who 谁负责 | 端侧和云端各有识别能力，最终采用哪一路要配合端云采纳结果。 |
| When 什么时候用 | 用户说话时持续出过程文字，分句结束后再产出定稿。 |
| Where 在链路哪里 | 位于声音处理之后、语义判断和任务规划之前。 |
| How 怎么排查 | 对齐原始声音、过程文字、定稿和最终被采纳的文字，找第一次出现偏差的位置。 |
| How much 有多准 | 准确率要连同车型、测试集和识别版本看，不能拿一次历史成绩代表所有条件。 |

### 第二步：七个问题逐条讲透

**1. What：屏幕上的字为什么还会变？**
ASR 的英文全称是 Automatic Speech Recognition，自动语音识别。流式意味着声音还在进来，文字就逐步返回；partial 是尚未定稿的过程文字。二遍识别是在分句后重新识别音频，产生 final，也就是供正式请求使用的定稿。[V03-F01、V03-F02] 看到屏幕出现“游泳馆”，不代表整句已经结束，更不代表系统已经确认要导航。

| 容易混的东西 | 判断的维度 | 例子 |
|---|---|---|
| 流式与二遍 | 什么时候、以什么方式出文字 | 边说边出字；结束后重新识别定稿 |
| 端侧与云端 | 在哪里计算 | 车上识别；上传处理后声音由云端识别 |
| 过程文字与定稿 | 结果当前能否当正式输入 | “去游泳馆”可能继续变成“去游泳馆附近的餐厅” |
| 识别正确与理解正确 | 写字与办事是不同问题 | 写对“昨天那家”，仍不知是哪家 |

**2. Why：为什么必须区分过程结果和定稿？**
如果拿半句话当最终目标，就可能先搜索游泳馆，而用户真正要的是附近餐厅；如果等待所有后续处理结束才显示文字，用户又看不到系统有没有听见。过程文字让提前反馈和预处理成为可能，定稿则为正式处理提供稳定输入。这是体验上的分工，不能把“字随嘴动”当成“字已经不会变”。

**3. Who：两路识别分别收到什么？**
车端离线识别直接使用本地音频；云端收到车上处理后的音频再识别。技术方案明确两路并行所需的一致性。[V03-F03] AIVA 本地 PRD 进一步规定：如果最终采纳本地函数结果，上屏最终文字对应 local_asr；采纳云端 Planner 结果则对应 cloud_asr。[V03-F04] 这些字段是日志里的两路识别文本。

**4. When：什么时候需要重新看文字？**
当用户继续补话、二遍修正错字或端云结果不同，就要检查最后采用的文字。不能只截屏记录过程文字，再据此认定 Planner 输入也是这句话。本地 PRD 还要求避免上屏在多个结果之间反复切换，同时允许根据采纳结果刷新定稿。[V03-F04]

**5. Where：离线识别能不能替代云端全部能力？**
端侧 ASR 只解决断网时仍能把声音变成文字。它后面能执行哪些任务，取决于本地规则、模型和已接入的功能。会写出“找昨天那家游泳馆”不代表离线端具备历史检索、地图检索或复杂规划。

**6. How：文字错了按什么顺序查？**
先听本次实际送识别的声音；再看正确的名字有没有作为热词带入；再比较过程文字与定稿；然后核对最后送给下游的是端侧还是云端文本；最后才看后续理解。若端侧写对、云端写错但系统采纳云端，问题还涉及采纳链路，不能只报“ASR 不准”。

**7. How much：怎样看识别成绩？**
至少同时记录测试场景、语种或口音、热词条件、最终采用哪路。OnePager 的传输描述为每 200 ms 发送一帧音频，这说的是上送节奏，不是“每句话 200 ms 就识别结束”。[V03-F05] 本单元不为当前车型补造准确率。

### 第三步：放回主例
过程文字先出现“带我去昨天那家游泳馆”；用户继续补“附近的餐厅”，定稿应覆盖整句。此处“应”是主例的验收预期：实际是否覆盖要看判停和识别日志。即便定稿全对，“昨天那家”仍要交给后面的记忆检索解释。

### 第四步：讲给别人听（30 秒）
> ASR 负责把声音写成字。流式过程文字让系统边听边准备，二遍定稿给正式请求使用。端侧和云端说的是计算位置，不是过程与最终的区别。排查时要看同一条声音的过程字、定稿字和最终采纳字；写字正确之后，才轮到判断它理解得对不对。

### 查阅区
- partial 不是 final；二遍识别在分句后重识别音频。[V03-F01、V03-F02]
- 每 200 ms 音频帧：OnePager 链路描述，不是响应耗时承诺。[V03-F05]
- 当前各车型端云 ASR 供应商、模型版本和离线实测效果：待确认。[V03-U01]

## 5. VAD 判停：停顿不等于已经说完

### 配图说明
新图，七个节点：“持续声音”→“出现停顿”→“Soft VAD”→“可先预处理”；Soft VAD 同时连到“继续收音”，继续收音连“Hard VAD”→“分句定稿”。用户补话画回到“持续声音”的弧线。青色表示判断，灰色表示声音，紫色表示暂存的预处理结果；不把不同文档阈值画成一个已上线常量。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | VAD 是语音活动检测，用来识别说话和停顿，Soft 与 Hard 对应不同的结束判断阶段。 |
| Why 为什么要 | 太早收尾会漏掉补话，太晚收尾会让用户觉得没有反应。 |
| Who 谁负责 | OnePager 描述由客户端控制判停，并衔接云端识别和请求。 |
| When 什么时候用 | 用户说话期间和停顿之后持续判断。 |
| Where 在链路哪里 | 它连接音频收取、识别分句和请求发起。 |
| How 怎么排查 | 对照声音停顿、Soft 事件、继续说话、Hard 事件及最终文字。 |
| How much 等多久 | OnePager 写 Soft 300 ms、Hard 600 ms，旧 PRD 写 Hard 500 ms，必须分来源理解。 |

### 第二步：七个问题逐条讲透

**1. What：两次判停各自允许什么？**
VAD 全称 Voice Activity Detection，语音活动检测。Soft VAD 是较早的停顿信号：用户可能说完了，可以先准备；它不结束 ASR，可以多次触发。Hard VAD 是本次音频分段、进入定稿与正式请求的信号。[V05-F01、V05-F02] 它判断的是一次表达何时收尾，不负责判断目标地点和指令权限。

| 容易混的东西 | 回答的问题 | 后果 |
|---|---|---|
| Soft VAD | 可以先准备了吗 | 可发预请求，继续听 |
| Hard VAD | 这一段可以结束了吗 | 结束分段，衔接 final 与正式请求 |
| 语义 VAD | 这句话意思看起来完整吗 | 旧 PRD 用它讨论延长等待，具体生效范围需核对 |
| 最终拒识 | 整句话该不该由助手接 | 不负责决定音频何时分段 |

**2. Why：为什么不能把时间压得越短越好？**
主例中“带我去昨天那家游泳馆”本身看起来完整，但用户还想补“附近的餐厅”。太早结束，系统会把目标认成游泳馆；拖得太长，用户说完后又会等待。判停的产品任务是处理这类矛盾，不是追求一个脱离句型与场景的最短时延。[V05-F03]

**3. Who：端云为什么要用一致的边界？**
OnePager 写客户端控制判停。离在线仲裁方案指出，端云 VAD 不一致可能导致云端无法判停，业务卡在语音侧直到超时。[V05-F04] 所以“车上已经认为说完”不能证明云端收到并采用了同一个结束事件。

**4. When：补话来了怎么办？**
Soft 之后还在收音，后续文字可以改变预处理输入；正式请求是否复用旧结果，交给下一单元的预请求校验。若补话已经落在 Hard 之后，它可能成为下一段输入，具体如何续接不能靠本单元承诺。验收时要分别测“Hard 之前补”和“Hard 之后补”。

**5. Where：语义完整性放在哪？**
多级 VAD PRD 提出，短窗口先看语义是否完整，不完整则延长等待；但该文档状态为待评审，相关时间也标注暂定。[V05-F05] 因而正文可以教这个问题是什么，不能把旧 PRD 的整套设计写成所有项目现行算法。

**6. How：一句话被切断了怎么查？**
先标出录音中真正的停顿位置；查 Soft 和 Hard 事件时间；看补话发生在 Hard 前还是后；核对端云是否使用相同分段；再看定稿有没有丢字。最后检查后续请求是否错误复用了旧文本结果。这里每个检查都服务于定位：是收音结束早、识别漏字，还是下游用了过期结果。

**7. How much：500 和 600 到底哪个对？**
两边都有原文，不能改成同一个数。OnePager 写 Soft 300 ms、Hard 600 ms；多级 VAD 初版写 Soft 300 ms、Hard 500 ms、语义 VAD 1000 ms，且说明时间暂定。[V05-F01、V05-F02、V05-C01] 它们证明文档范围不同；当前指定车型应以实际配置和日志为准，待确认。

### 第三步：放回主例
用户说完“游泳馆”稍作停顿，Soft 可以让系统先准备。补上“附近的餐厅”后，最终目标变了。只要仍在同段，定稿要包含补话；如果已经分段，就必须检查下一段如何衔接，不能假设系统总能自动拼回。

### 第四步：讲给别人听（30 秒）
> 判停是在决定用户什么时候说完。Soft 是可以先准备，Hard 才衔接分句和正式请求。停顿太短容易切掉补话，太长会拖慢响应。查问题要把录音、两次判停事件和最终文字摆在一条时间线上；不同文档的阈值要保留版本范围。

### 查阅区
- OnePager：Soft 300 ms，可多次触发、不结束 ASR；Hard 600 ms。[V05-F01、V05-F02]
- 多级 VAD PRD v0.1，2025-12-4，待评审：Hard 500 ms、语义 1000 ms，时间暂定。[V05-F05、V05-C01]

## 6. 预请求：先做准备，最终对得上才复用

### 配图说明
新图，七个节点：“Soft 时的文字”→“预请求”→“拒识/Context 预处理”→“暂存结果”；“最终文字”进入“同轮且文字一致？”；匹配时从暂存结果连到“正式链路”，不匹配时从判断节点连“正式链路”，线注明“重算”。紫色为暂存，青色为计算，灰色为文字。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 预请求是在正式输入确认前，先做可复用的准备工作。 |
| Why 为什么要 | 用户最终说的没变时，可以省下重复计算的等待。 |
| Who 谁负责 | 端侧触发，云端链路预跑支持预请求的模块并保存结果。 |
| When 什么时候用 | Soft VAD 之后、正式请求之前，可随本轮过程多次发生。 |
| Where 在链路哪里 | 位于正式拒识与上下文准备之前的加速支路。 |
| How 怎么生效 | 正式请求核对请求标识和文字，符合条件才复用，否则重新计算。 |
| How much 能快多少 | 取决于本次是否命中，不能把预请求发出了当作已经节省耗时。 |

### 第二步：七个问题逐条讲透

**1. What：预请求提前做了什么？**
OnePager 将它定义为 Soft VAD 后抢跑的前置无状态任务，例子是拒识和 Context。Context 是提供给后续判断的相关背景材料，本章后面会拆开讲。无状态在这里的业务意义是“先准备，不把这次准备当正式对话写入历史”。[V06-F01、V06-F02]

| 容易混的东西 | 可以发生什么 | 不能据此宣布什么 |
|---|---|---|
| 预请求 | 提前计算、暂存候选结果 | 用户已完成表达、车辆已执行 |
| 正式请求 | 用定稿进入后续正式链路 | 所有预请求结果都可直接使用 |
| 预请求命中 | 本轮正式处理复用已准备结果 | 另一个请求的结果也能拿来用 |
| 本地规则缓存 | 固定说法匹配已配置结果 | 与本轮云端预请求是同一种缓存 |

**2. Why：为什么不能先导航再等补话？**
主例在停顿时看似要去游泳馆，补话后才知道要找餐厅。如果预请求提前执行导航，用户还没说完就被带错任务。它的价值是减少后面的准备时间，同时保留改口和补话的空间。旧 VAD PRD 也明确写过不抢跑到 FC（函数调用，把指令变为功能与参数）、Planner 等执行或规划模块；这属于该版本设计边界，不是所有历史实现的统一断言。[V06-F03]

**3. Who：谁来保证没拿错结果？**
链路使用 request_id 标识同一请求，用 round_id 区分其中多次预请求与正式请求；这些可以理解为“同一件事的编号”和“第几次版本”。OnePager 描述正式链路复用同一 request_id 下前一轮 round_id 的预请求结果。[V06-F04] 产品经理不必读完接口，但要能要求日志把这两个编号与文本放在一起。

**4. When：用户继续说了还算同一个预请求吗？**
新的过程文字可能带来新的预请求轮次。正式请求也继续递增轮次编号；判断复用时不能只找“曾经有一个预请求”，而要找对应的那一轮。[V06-F04] 否则很容易拿到同一会话里另一句话或更早半句话的准备结果。

**5. Where：它有没有进入历史记录？**
技术方案明确预请求消息不落库、不进入对话历史。[V06-F02] 正式请求和最后采用的处理结果才有各自的历史同步逻辑。若把每次试算都当用户正式说过的话，会让后续上下文出现用户没有确认的版本。

**6. How：用户觉得没变快，怎么查？**
先确认 Soft 是否触发；再确认预请求是否真的运行到目标模块；随后核对正式请求与前一轮的请求编号和文字；再看缓存命中标记；最后比较实际省掉了哪段计算。若补话使文本变化，重算可能是正确行为，不能简单算成“预请求失败，需要强行命中”。

**7. How much：相似就能复用吗？**
OnePager 明确要求正式文字与前一轮预请求文字完全相同，并且 request_id 相同。[V06-F05] 另一份测试表保留过相似度 0.75 的测试口径，旧 PRD 也有最短路径匹配的演示变更。[V06-C01] 这属于资料口径冲突，不能偷偷把“完全相同”改成“差不多”。当前项目策略需要实查。

### 第三步：放回主例
预请求输入可能是“带我去昨天那家游泳馆”，正式输入变成“带我去昨天那家游泳馆附近的餐厅”。按 OnePager 的完全一致规则，这两句不能复用同一个预请求结果。系统重新准备后续材料，是在保护最终目标，不是白白变慢。

### 第四步：讲给别人听（30 秒）
> 预请求是在用户可能说完时先做准备。正式文字确认后，如果属于同一请求、内容又满足复用条件，就省下一段重复计算；内容变了就重算。它不代表提前执行，也不应把试算写成正式历史。排查要看实际预跑和命中记录，不能只看接口发没发。

### 查阅区
- 预请求不进入对话历史；支持模块例子为拒识与 Context。[V06-F01、V06-F02]
- 完全一致 vs 相似度 0.75：保留来源冲突，不定当前车型结论。[V06-C01]

## 7. 流式拒识与打断：先决定要不要让用户说

### 配图说明
新图，七个节点：“豆包正在播报”与“用户过程文字”汇入“打断触发条件”；条件命中单人或规定的唤醒词规则时直达“先停当前播报”，其余符合模型调用条件的输入才到“流式拒识判断”；模型分支指向已有的“先停当前播报”或“继续等待”；停播后进入“继续收音到正式判断”。青色为判断，灰色为声音状态，紫色为人数等规则条件。不能把停播箭头直接连车辆执行。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 流式拒识在用户尚未说完时，判断当前输入是否足以打断助手播报。 |
| Why 为什么要 | 用户需要插话时不能一直等助手讲完，但乘客闲聊也不该总把播报打断。 |
| Who 谁负责 | 流式判断模型与模型外的触发规则共同负责，部署位置要按项目核实。 |
| When 什么时候用 | 当前有播报且新语音持续产生过程文字时。 |
| Where 在链路哪里 | 它是播报期间的快速判断支路，早于完整句子的最终拒识。 |
| How 怎么排查 | 依次看播报状态、触发规则、模型输入、判断结果和真实停播动作。 |
| How much 模型多大 | 盘点资料写 Qwen3 1.7B（Qwen3 是模型家族，1.7B 表示约 17 亿参数的规模），但模型名称不能单独证明部署位置或当前车型版本。 |

### 第二步：七个问题逐条讲透

**1. What：为什么叫拒识，却会让系统停下来？**
这里的拒识是判断输入是否属于要对助手说的话。流式表示每次拿到还在变化的过程文字就能先判断。如果判断这句话值得接，先停下当前 TTS。TTS 是 Text-to-Speech，文本转语音，即豆包正在播放的回答声音。停播后仍要继续收音，到正式阶段再判断整句。[V07-F01]

| 容易混的东西 | 当时输入 | 直接决定 |
|---|---|---|
| 流式拒识 | 过程文字及相应背景 | 要不要先停当前播报 |
| 最终拒识 | 完整定稿及正式背景 | 整句话该不该接 |
| 本地车控 FC | 支持范围内的指令文字 | 给出函数和参数候选 |
| 播报恢复策略 | 打断原因和后续判断 | 是否以及怎样恢复旧回答 |

**2. Why：先停后拒是不是一定矛盾？**
不是。教学例：用户刚说“你帮我……”，系统先让出说话机会；后面接“跟小李说一下”，上下文最终显示是在对乘客说。前后输入不同，两次判断可能不同。产品要看用户最终感受：该插话时能否停下，闲聊时是否频繁误停，以及误停后是否按对应策略处理，而不是把两次结果强行要求一样。

**3. Who：Qwen3 1.7B 到底在哪儿？**
算法盘点写流式拒识使用 Qwen3 1.7B，并记载 H20（服务器计算设备型号）部署；工程双周报也记录上汽的该模型在 H20 部署。另一方面，本地 PRD提出把相关能力下沉端侧。[V07-F02、V07-F03] 因此，“端侧模型”可能是在说模型来源或能力方向，不足以证明这次计算就在车上。两个 1.7B 的职责必须分开讲，是否同一权重、同一交付包，资料不足。[V07-U01]

**4. When：是不是一开口就请求模型？**
OnePager 的流式拒识触发前提包括：多人、ASR 大于两个字、前缀不含“豆包”、TTS 正在播放。它另列规则：多人以“豆包”开头立即打断；单人 ASR 大于两个字直接打断。[V07-F04、V07-F05、V07-F06] 这是模型外规则与模型判断的分工，不能说每次停播都由小模型决定。

**5. Where：它收到哪一路过程文字？**
本地 PRD 写使用 partial ASR 流式请求模型；OnePager 也描述了端侧转发流式文本请求云端判断。[V07-F01、V07-F07] 但具体项目在当次打断时取本地还是云端过程文字，不能只凭概念名确定；这是待确认项。[V07-U02]

**6. How：为什么“我一说话它就停”仍需查？**
先确认当时是否正在播报，再看人数与唤醒词前缀规则是否直接触发；如果走模型，查当次过程文字和背景；然后核对模型返回标签；最后看端侧真实停止播放的时间。把“没请求模型”误判成链路失败，可能漏掉正常规则路径；把“模型判停”当“音频已停”，又可能漏掉播放执行问题。

**7. How much：准确率如何使用？**
盘点记录准确率 87.39%、H20 上 300 QPS 稳定性压测通过；QPS 是每秒请求数。[V07-F08、V07-F09] 它们分别说该盘点评测和服务承载，不能推出当前车辆误打断率，也不能拿来证明车上算力满足要求。

### 第三步：放回主例
若豆包正在播报旧内容，主驾开始说主例，流式判断可能先停旧播报；随后继续听到“附近的餐厅”。停播只是让用户讲完，最终是否接话、去哪查“昨天那家”、是否启动导航，都还没发生。

### 第四步：讲给别人听（30 秒）
> 流式拒识是在用户还没说完时决定是否先停播报。它和说完整句后的最终拒识是两次判断，也和车控函数输出不同。人数、唤醒词等规则可能直接决定打断。模型虽然写 Qwen3 1.7B，具体在车上还是云端算、用了哪路文字，还要按项目查。

### 查阅区
- Qwen3 1.7B、87.39%、H20、300 QPS（每秒请求数）：算法盘点范围，不宣称全车型现状。[V07-F02、V07-F08、V07-F09]
- 单人/多人、字数和前缀规则见 OnePager；实际车型开关待核验。[V07-F04—V07-F06]
- 两个业务职责是否共享当前权重/交付包、打断采用哪路 partial：待确认。[V07-U01、V07-U02]

## 8. 最终拒识：这整句话到底是不是在叫豆包

### 配图说明
新图，七个节点：“最终文字”与“相关背景”进入“规则条件检查”；规则可直通“召回继续处理”，否则进入“最终拒识模型”，分到“召回继续处理”或“拒识，不作本轮指令执行”；第七节点“播报恢复判断”接收相应打断原因与结果。紫色为规则与背景，青色为判断，灰色为结果。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 最终拒识用完整文字判断这句话是否应该由助手接话。 |
| Why 为什么要 | 避免乘客聊天被当作指令，也避免用户真的叫助手却被静默丢掉。 |
| Who 谁负责 | 云端拒识能力与首句、单人等产品规则共同决定。 |
| When 什么时候用 | 完整输入进入正式链路时，以及相关打断恢复处理时。 |
| Where 在链路哪里 | 在正式请求进入 Planner 处理的前段。 |
| How 怎么排查 | 先查文本与规则条件，再查模型判断，最后查实际是否进入下一步。 |
| How much 用什么模型 | 算法盘点普通拒识列为 Doubao-Seed-2.0-lite 260428/SFT，车型实际版本需另核。 |

### 第二步：七个问题逐条讲透

**1. What：“拒识”不是不认识这几个字。**
识别已经把声音写成字；拒识判断的是交互对象。召回 RECALL 表示继续按助手交互处理，拒识 REJECT 表示不按本轮用户指令继续执行。OnePager 区分基于过程文字的流式拒识和基于 final Query 的最终拒识。[V08-F01] Query 在这里就是本轮待处理的用户文字。

| 容易混的东西 | 为什么没办事 | 产品应该怎么解释 |
|---|---|---|
| ASR 识别错 | 写错了用户的话 | 先修输入文字 |
| 最终拒识 | 认为不是对助手说的 | 检查交互判断及规则条件 |
| 本地 unsupported | 本地能力不支持这件事 | 有网时交给后续云端判断 |
| 工具执行失败 | 已尝试办事但下游失败 | 根据真实结果回复，不能伪称成功 |

**2. Why：两类错误要一起看。**
用户对副驾说“开一下窗”，助手却执行，是过召；用户明确叫豆包开窗却没有回应，是过拒。这是用于理解指标的教学例。只减少插嘴可能伤害正常召回，只追求有问必答又可能增加误响应。评审需要看到两类失败及场景分布，不能只看合并后的准确率。

**3. Who：最终拒识用哪个模型？**
奇瑞海外算法盘点的普通拒识栏写 Doubao-Seed-2.0-lite 260428/SFT。[V08-F02] SFT 是监督微调，用带答案的样本训练已有模型，使其适合这里的判断任务。这个栏位证明文档记录的模型口径，不能直接证明所有车企、所有时间都使用同一线上版本。[V08-U01]

**4. When：唤醒后首句为什么可能直接接？**
测试需求写：关闭所有位置免唤醒的前提下，唤醒后首句首字与唤醒的间隔不超过 5 秒，首句强制召回；超过则走相应拒识判断。[V08-F03] 这是带前提的首句规则，不是“唤醒后的任何话永远不拒识”。它也不意味着含糊句子能直接执行，后续仍可能需要补充信息。

**5. Where：“单人不拒识”是不是模型自己判断车内只有一个人？**
不是这么推。测试表列出单人不拒识开关以及免唤醒开启的条件；开关开启与关闭的预期不同。[V08-F04] 人数信号和开关是规则侧必须核对的事实，不能因为模型结果异常就推断“模型数人错了”。该规则与其他免唤醒条件的最终优先级，需要按项目确认，不能把不同测试前提混用。[V08-U02]

**6. How：同一句话有时接有时不接怎么查？**
先确认两次定稿是否真的相同；再比较当时唤醒方式、距唤醒时间、人数、开关和音区；然后检查输入给模型的背景与标签；最后看标签是否被规则覆盖、后续链路是否实际运行。如果规则侧直接放行，不能拿这次样本证明模型召回能力；如果输入文字本就不同，也不能称为同条件不稳定。

**7. How much：怎样读模型成绩？**
算法盘点写普通语义拒识准确率 92.5%、训练集 4.3W+，并写拒识 2.0 已启动。[V08-F05、V08-F06、V08-F07] “已启动”不是“已上线”；训练样本多也不能替代当前车上场景的验收。当前项目的过召、过拒和规则覆盖占比仍需实际报告。

### 第三步：放回主例
最终文字完整包含“附近的餐厅”，并判断是对豆包说的，才继续交给 Planner。若这是主驾与副驾的讨论，被拒识不代表“昨天那家”没记住；它是在更前面决定本轮不接话。先分清停在哪一步，再判断是不是记忆问题。

### 第四步：讲给别人听（30 秒）
> 最终拒识负责判断整句话该不该由助手接，不负责判断本地有没有这个功能。唤醒后首句和单人不拒识是带条件的产品规则，不能和模型能力混算。排查时先看文字、状态和开关，再看模型标签，最后看系统实际走没走下一步。

### 查阅区
- Doubao-Seed-2.0-lite 260428/SFT：算法盘点模型字段。[V08-F02]
- 首句首字间隔 ≤5 秒：关闭所有位置免唤醒条件下的测试需求。[V08-F03]
- 单人不拒识：带开关和免唤醒前提，不代表所有单人场景无条件接话。[V08-F04]
- 92.5%、4.3W+、拒识 2.0 已启动：盘点历史记录，非本轮线上验收。[V08-F05—V08-F07]

## 9. 固定说法与 1.7B 端侧 FC：把简单指令变成可调用的功能

### 配图说明
新图，八个节点：“最终指令文字”→“固定说法规则”；命中连“配置的函数结果”，未命中连“本地 FC 模型”；模型分到“函数与参数”“reject”“unsupported”；可执行候选连“端云仲裁”。青色是判断，紫色是规则配置，灰色是候选结果；所有执行候选必须经过仲裁箭头。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 固定规则匹配已配置说法，本地 FC 模型把支持的简单指令转换成函数和参数。 |
| Why 为什么要 | 高频控制需要快，断网时也要尽可能保住已支持的基础操作。 |
| Who 谁负责 | 规则配置、本地模型、车机能力接入和端云仲裁各负责一段。 |
| When 什么时候用 | 本地链路处理指令时，规则或模型产生结果后再决定是否采纳。 |
| Where 在链路哪里 | 位于车端候选理解与执行入口之间。 |
| How 怎么排查 | 依次查规则命中、模型输出、函数接入、采纳结果和车辆真实动作。 |
| How much 能做多少 | 训练覆盖多少函数与当前工程实际支持多少函数不是一个数字。 |

### 第二步：七个问题逐条讲透

**1. What：FC 不是另一种声音识别。**
FC 是 Function Calling，函数调用。可以把函数理解为“车机已经提供的一项操作”，参数是“操作哪个对象、调到什么值”。模型收到文字，给出要用的函数和参数；它不直接等于车辆已经动作。固定说法规则则把符合配置的文字直接映射成预设结果。[V09-F01]

| 容易混的东西 | 真实含义 | 下一步 |
|---|---|---|
| 固定说法命中 | 符合已配置规则 | 产生配置结果，仍看采纳与执行 |
| functioncall | 有函数与参数候选 | 检查是否支持及是否采用 |
| reject | 判断不应把这句话当助手指令 | 还需遵守端云拒识采纳边界 |
| unsupported/cloud | 本地支持范围外或低置信 | 交云端继续判断，离线则按异常策略处理 |

**2. Why：为什么不能把“不会做”写成“不该理”？**
“带我去昨天那家游泳馆附近的餐厅”明显可能在叫助手，但需要历史与地点查询，超出本地轻量处理范围。本地应承认能力边界，不能因为不会做就把用户话当闲聊丢掉。反过来，“我的心很冷”也不能仅匹配到“冷”就控制空调。后一个是本地 PRD 用于解释干预的示例，不是新增实测事故。[V09-F02]

**3. Who：1.7B 说明什么？**
算法盘点把端侧模型基座列为 Qwen3 1.7B。它训练覆盖车控、通用拒识、流式拒识，但本单元只讲“理解简单车控并产生函数”的职责。[V09-F03] 1.7B 是模型规模标签，不能当“支持 1.7B 个功能”。也不能仅凭名称就说它和前面流式拒识使用同一线上权重。

**4. When：规则和模型谁先跑？**
AIVA 本地 PRD 写：离线 ASR 的 Query 先进入干预模块，命中直接输出配置结果，不再请求本地模型；未命中再请求模型。[V09-F01] 算法盘点另写“规则与模型并行”。[V09-C01] 两份材料描述的范围不完全相同，本稿分别保留；具体项目调用顺序待查，不能拼成一套万能流程。

**5. Where：它和云端 Planner 差在哪里？**
本地 PRD 明确不支持开放问答、联网搜索、内容生成、复杂地点推荐、多步工具编排和依赖大量状态或长期记忆的判断。[V09-F04] 这些能力边界解释了为什么主例需要云端规划。端侧有模型，不等于把云端助手整套搬进车上。

**6. How：模型输出正确，车却没动怎么查？**
先确认是不是固定规则命中；再查函数名、对象和参数；随后查该函数是否已接入当前车型；再查本轮端云是否采纳它；最后查车机回执和实际状态。若函数没有接入，这是能力接入问题；若仲裁未采纳，要查规则；若执行回执失败，要查下游。不要统一归因为“模型不稳定”。

**7. How much：600 多个函数为什么不能当销售清单？**
盘点写训练覆盖 600+ 个车控函数，但工程链路实际生效不足 100 个。[V09-F05、V09-F06] 前者说明训练数据见过的范围，后者说明该盘点所述工程实际接入范围，都不等于某一车型完整可用清单。验收必须拿当前车型的函数、参数和真实执行结果逐项核对。

### 第三步：放回主例
主例依赖“昨天那家”的历史线索和餐厅搜索，不属于可直接本地生成简单车控结果的示范。应交云端继续处理；如果车已断网，也不能编一个餐厅并宣称已经导航。换成“打开副驾座椅加热”才适合解释简单函数调用，但它只是旁例，不替代全章主线。

### 第四步：讲给别人听（30 秒）
> 固定规则处理配置好的说法，端侧 FC 模型理解支持范围内的简单指令，输出函数与参数。reject 是不该当指令，unsupported 是本地做不了，两者不能混。即使有函数结果，还要检查工程接入、端云采纳和真实执行；训练覆盖不等于车上可用。

### 查阅区
- Qwen3 1.7B：端侧模型基座记录。[V09-F03]
- 600+ 训练函数、实际生效不足 100：同一算法盘点中的两种口径。[V09-F05、V09-F06]
- PRD 缓存先行 vs 算法盘点规则模型并行：资料冲突，具体项目待确认。[V09-C01]

## 10. 端云仲裁：两边有结果，最后用谁的

### 配图说明
新图，七个节点：“同一轮请求”分到“本地规则/模型结果”和“云端结果”；“网络与等待状态”指向“端云采纳判断”；判断连接“采用一个结果”→“执行并同步”。灰色为候选，紫色为状态，青色为选择；迟到结果以虚线止于采纳判断，标“已完成采纳后不重复执行”。

### 第一步：先记住这 7 句（5W2H 速览）

| 问题 | 一句话答案 |
|---|---|
| What 是什么 | 端云仲裁是在同一轮本地与云端候选结果中决定最后采用哪一份。 |
| Why 为什么要 | 否则可能重复执行、端云互相覆盖，或把一个不该采用的本地结果先执行。 |
| Who 谁负责 | 端云协作链路依据规则、网络状态和返回时序做采纳。 |
| When 什么时候用 | 两路有候选结果、云端超时或网络不可用时。 |
| Where 在链路哪里 | 位于候选理解结果与真正执行之间。 |
| How 怎么排查 | 把请求编号、两路结果、返回时间、采纳原因和执行回执放在同一时间线。 |
| How much 等多久 | 本地 PRD 写云端超过 3 秒未返回视为超时，这是该需求口径。 |

### 第二步：七个问题逐条讲透

**1. What：并行不是谁快就听谁的。**
本地和云端可以同时处理一句话，但结果承担的可信范围不同。AIVA 本地 PRD 的 9 月 30 日变更把本地模型从前置分流调整为兜底：在线时本地正则缓存可以抢跑，普通本地模型仅在断网或超时采用。[V10-F01] 正则缓存就是按文字模式匹配的本地规则，和前面预请求的临时计算结果不同。

| 容易混的东西 | 意味着什么 | 不意味着什么 |
|---|---|---|
| 本地先返回 | 本地已有候选 | 一定先执行 |
| 云端先返回 | 云端已有候选 | 可以忽略本地已采用结果 |
| 并行计算 | 两边同时准备 | 同一操作执行两遍 |
| 已采纳 | 本轮决定用这份结果 | 下游必然执行成功 |

**2. Why：不仲裁会让用户看到什么？**
教学例：本地已经按“调高一点”执行一次，云端晚到又执行一次，用户就会觉得调过头。另一个问题是屏幕展示云端文字、实际却执行本地解释，让用户无法理解。仲裁要同时约束动作、上屏和历史同步，不能只给一个抽象优先级。

**3. Who：谁提供选择所需的证据？**
本地提供规则命中与模型结果，云端提供处理结果，端侧提供网络与等待状态。请求编号把它们对应到同一轮。离在线技术方案把端云上下文、VAD 时间和任务一致性列为必要条件。[V10-F02] 如果两路不是同一段话，再精细的选择规则也会选错。

**4. When：什么时候用本地兜底？**
9 月 30 日变更段写“本地正则缓存 > 云端 Planner > 本地 LLM（仅断网或超时兜底）”。LLM 是大语言模型，此处指本地轻量语义模型。超时段写云端超过 3 秒未返回视为超时；采纳后云端晚到，不再触发执行。[V10-F01、V10-F03、V10-F04] 这是文档定义，当前项目是否同配置需要核验。

**5. Where：为什么 reject 要单独讲？**
本地 PRD 多处写：音频已上云时不采信本地 reject，应等云端拒识；但超时段又写本地 functioncall / reject 可采纳。[V10-C01] 这是同一文档的边界冲突，不能自行选择一条当统一现行规则。评审要具体问“已上云但超时，允许本地 reject 最终结束吗”，并要求项目规则和日志确认。

**6. How：出现重复执行或一直没响应怎么查？**
先核对两路请求属于同一轮；记录本地、云端返回时间；查当时网络判定和超时计时起点；核对命中的是固定规则还是模型；查看最终采纳原因；最后查实际执行次数、上屏文本与同步记录。若云端迟到再次执行，是采纳后拦截问题；若从未采用任何结果，是结果等待或超时处理问题。

**7. How much：无网时不会做该怎么表现？**
PRD 规定本地 unsupported_cloud 且无网或超时时播报“网络异常，请稍后再试”，并规定单次唤醒周期内同类网络异常话术只播报一次。[V10-F05、V10-F06] 这个频次规则也有项目范围。不能把“网络异常”当所有失败的统一解释，更不能在本地不支持时伪造已完成。

### 第三步：放回主例
在线情况下，主例应交具备相关查询与规划能力的云端处理。本地即便先输出 unsupported，也不是拒绝用户；它是在说明本地做不了。断网时，本地没有查清“昨天那家”和附近餐厅的依据，就不能承诺导航成功，要按当时适用的异常策略结束或等待。

### 第四步：讲给别人听（30 秒）
> 端云仲裁决定同一轮最后用哪份结果，不是谁返回快就执行谁。文档把固定规则抢跑与普通本地模型兜底分开，云端迟到也不能再执行一次。查问题要对齐两路结果、时序、采纳原因和真实动作；已上云又超时的本地 reject 边界，现有资料仍需确认。
