# 补查：识别、动态 VAD 与评测证据
核读日期：2026-10-22。此报告只更新研究材料，不改课堂或 HTML。以下“文档明确”指原文在相应版本中的描述，不等于今天所有车型已上线。没有观看的图片、白板、音视频明确列为缺口。

## 先给课堂的两个关键修订
第一，动态 VAD 不是一个永远固定的“100 → 300 → 500 → 600 → 1000 ms”阶梯。这几组数字来自不同历史方案。必须按版本解释，不能拼成一个当前流程。

第二，评测要沿链路找证据。用户听见“没反应”“重复播报”“说错了”，只是现象；同一个现象可以来自识别、拒识、上下文、规划、工具、音频生成、采信或播放。下面的真实历史问题可以作为培训例子，不能当作当前故障公告。

## 1. 可直接插入课堂：100/500 与 300/600 到底差在哪

我们先看一个具体场景。用户说“介绍一下”，停一停，又说“泰勒斯威夫特”，再停一停，最后补上“的猫”。如果系统只抓住第一小段就开始回答，很容易答错对象；如果每次都等很久，又显得反应慢。

2024 年 12 月 13 日的[《主链路—语音动态 VAD》](https://bytedance.larkoffice.com/docx/Y0jWdwxdsoQqD1xCbJAcX7QGn9f)尝试解决这个矛盾：短停顿 100 ms 时先截取“目前识别出来的文字”，并行做拒识与意图判断；在 500 ms 的中等时间窗里，用户继续说话，就把后续文字和前文拼起来重新判断，必要时取消先前召回的插件。这里截取的是文字，不是把同一句声音硬切成几次独立 ASR。原文专门说明 ASR 仍持续识别。超过 500 ms 后再做语义拼接，是文中另一层后续支持设想。这个版本的“截断召回 P0”“拼接 P1”实施状态都标了叉号，不能讲成今天已上线的机制。

现在回到用户指定的[主链路 OnePager](https://bytedance.larkoffice.com/wiki/GBcCw5c6xiWvGukPMQgcMiuKnEc)。这份资料采用 Soft VAD 300 ms 与 Hard VAD 600 ms：前者把阶段性识别文字拿去做预请求，ASR 继续听；后者结束这次识别，二遍给出最终文字，再走正式请求。预请求是提前做允许提前做的计算，不是提前执行车控。最终复用还要符合相同 request_id、与前一轮 query 完全相同等条件。多级 VAD 技术评审的细节见[服务端技术评审](https://bytedance.larkoffice.com/wiki/PJMUwwRCNiC2A8kjXCjcs4Bun7Y)。

所以培训时我们可以这样说：“这两版都想让系统更快，同时不抢话。但旧版重点讨论‘短文本截取、继续拼接、取消旧召回’；OnePager 重点说明‘先做预请求、最后拿最终文本核对并进入正式处理’。不要把旧版的 100 ms 塞在当前 300 ms 之前，也不要认为 Hard VAD 永远就是 500 ms。”

| 来源 | 原文明确 | 状态边界 | 不能补猜的部分 |
|---|---|---|---|
| 2024-12-13 动态 VAD 初版 | 100 ms 短停顿文字截取；500 ms 内继续说则拼接；重新拒识可取消前插件；不切断连续 ASR | 截断召回、拼接实施栏均为 ✖️ | 不能视为当前上线链路；100 ms 与当前 Soft 300 ms 无明确串行关系 |
| 多级 VAD 产品体验旧 PRD | Soft 300 / Hard 500 / 语义 1000 为暂定；语义完整性暂不定义，先评估供应商结果 | 后有 2 月底演示变更；不是所有内容同时生效 | 1000 ms 的完整计时起点、相对 Hard 的优先级未明确 |
| 用户指定 OnePager | Soft 300 可多次、ASR 继续；Hard 600、二遍 final、正式请求；缓存条件 | 按该文实现描述讲解，仍存在文图责任冲突 | 不把 1000 ms 自动接到 600 ms 后；不把预请求当真实执行 |

课堂示意（不是原始测试录音）：用户说“去……”停顿时，系统可能拿到很短的阶段性文字；用户继续补上“昨天那家游泳馆”，文字会继续更新。产品关心两件事：有没有过早把“去”当成完整目的地执行；最终正式处理有没有使用补完后的文字。具体能不能等到整句，还要看当时运行版本、VAD 判定以及语义策略，不能因为例子需要就假设一定会拼接成功。

## 3. VAD 前置到客户端：为什么产品要关心
来源：[VAD前置到客户端后，云端音频协议变更说明](https://bytedance.larkoffice.com/wiki/Ana1wyB2HilVBtkjiCQcfoL9n7e)。本次文本返回完整。

原文描述当时链路由云端连接接收持续音频、云端控制；AIcar 1.0 要同时支持离线 ASR/NLU 与云端处理，提出把 VAD 前置到客户端，让同一句声音切分结果可以对齐本地与云端。对云端提出 ASR-only、接收开始/结束信号、外部指定或获知 RequestId 等要求。

产品课堂可以这样讲：“本地与云端要竞争处理同一条指令，我们先得确认它们认的是同一句话。如果本地已经把‘打开车窗’当成一句，云端还把后面聊天接在一起，两边即使各自识别准确，也可能无法正确仲裁。这里讨论 VAD 放在哪里，是为了对齐一句话的边界与身份。”

文中还有替代方案：如果目标接口不支持上述能力，考虑 RTC 音频经第三方 ASR 后以文本送入豆包；同时提示 S2S 闲聊体验和第三方在指令/通用场景识别效果的代价。这是方案讨论，不能把替代路线画成已确定主线，更不能据此断言所有车型的 VAD 已全部迁到客户端。

## 4. ASR 不只评“有没有字”：评最终文本、关键槽位与性能
来源：[AiCar-主要模块测试方案/方法](https://bytedance.larkoffice.com/wiki/EOEKwyi61iJqklkDNvBc2VUHn5d#X8xydRgmaobzGAxORrOcFucXnUb)。返回被截断，但 ASR、拒识、唤醒节已取得；ASR 背景明确写赛力斯，不能转述成 D6X 方案。

原文明确：一遍、二遍识别后，以最终上屏文字为准。指标有词准、字准、严格/放宽句准、首字性能、尾字性能。严格/放宽区分的例子包括数字“二/2”“3/三”、“档/挡”及不影响理解的空格；原文判断这些可不影响大模型理解。这里不能扩成“错字都无所谓”：地点、人名、数值、否定词、左右座位等关键信息仍需要核对。

在线/离线共用一套测试集方便比较；静态场景覆盖闲聊联网、车控、导航、媒体、车书、电话人名；动态场景提出从各场景挑选 500 条实车录音跑批。ASR 热词 P1 针对通讯录人名、媒体名、导航 POI、可见即可说；端侧替换词 P2 则用于某些暂时无法解决的错误，例如“主家”“负家”的临时修复。二者不能混讲成同一个算法。

拒识 P0 提出使用真实用户 query 与历史：体验评测集、7500 条基础集、持续更新的 badcase 集。流式拒识单列 P1，但建设详情是空白。该文不足以补出流式拒识的具体阈值、模型输入或线上效果。

### 5.2 对话评测：文本内容、语音效果、端到端耗时分别验
评测标准明确先参考座舱标准，再评价 S2S 表现。座舱标准要求正确参考车信息、状态、车控能力；语音标准另看错读/漏读/截断、韵律、情绪、旁白人设等。表内有音频文本与评分，不等于我们已听过音频。

“测试报告”第 41/42 行记录 2026 年 2 月旧环境下强制 Sami 与 section_id 的相关对照。带 section_id 的行提到方言一直继承，后续要求夹子音仍方言回复；也记有情绪不继承、播报不全。不同条件下 63% 与 93% 的表内数字，不能解释为当前产品指标，也不能在没核对样本与配置前声称这是严格因果实验。课堂可借此说明：上下文保持既可能帮用户连贯对话，也可能把上一轮的风格错误带到下一轮，必须评估切换与清除。

第 50/51 行把端到端性能定义为“用户语音结束 → TTS 开始播放”，分别用录屏数帧与日志，样本分别 10 组与 5 组。这与下节 TTS 服务首包性能完全不同，不应放在同一列比较。

## 6. ASR/TTS 日志：把“没有声音”拆成可追的几个问题
来源：[ASR与TTS 日志排查及问题整理](https://bytedance.larkoffice.com/wiki/WwpFwoUNLikhxmkIhKwciSCEnYy)。本次文本返回完整，图与音频未看/未听。

ASR 排查用 WebSocket LogID、RequestID、近似发生时间关联 Fornax span 与原音频。原文曾记录 channel/车辆标识缺失导致路径字段为空，这是当时记录，不能断言目前仍缺。

TTS 的 StartTask/TaskStarted 只证明任务开始，不证明有可听音频。原文统计首包时从“首次实际文本送出”，到首次 audio_length 大于 0 的返回；空任务信号不算首音频。示例 20:54:07.983 到 20:54:08.535 约 552 ms，文中约称 600 ms；这只是单例，不是平均值或当前目标。

另一个容易误读的点：S2S 生成过音频，不代表这段音频一定送到客户端。还要看是否被获取、是否被采信。日志中的 tts_audio_id 与端请求 fetch_request_id 关联，再追音频块与结束标志 with_eof_flag。课堂应把“生成成功、发出成功、端收到、采信、开始播放、播完”分开。

历史问题中，“多模块写同一 Redis 列表导致顺序混乱”列了两个候选方案；不能因此认定两个都已实施。“Sami 与 S2S 共用本地 chan，Sami 空闲关闭连带关闭通道，导致 S2S 缓存失败”则是资源生命周期冲突的具体历史案例。原文标记解决并讨论空闲阈值/会话结束清理，培训可以用它说明：播报断了不总是模型没生成完整，可能是传输或缓存通道提前结束。

原文里被划掉的旧 TOS 缓存查询路径不能继续当现行必走步骤；更新方向是 AudioDataToVodOrTos span 的 vid、chat_history_detail 等关联 VOD 音频。是否仍可用需当次环境核验。

## 7. 可直接插入课堂：沿链路定位问题的评审话术
以下是基于上面资料整理的产品排查方法，属于培训建议，不冒充既定 SOP。

我们先别把“豆包没反应”直接归给大模型。拿一条失败录音，从用户说话开始找它在哪一步偏离预期：

| 用户现象 | 先拿什么证据 | 下一步怎么区分 | 评审可以这样问 |
|---|---|---|---|
| 说“昨天那家游泳馆”，识别成别的店 | 原音频、阶段文字、最终上屏文字、说话音区 | 原音频已含整句而 final 丢字/错名，先查识别；原音频本身被切短，再查采音/VAD 边界 | “先对一下最终文本和原音频，错从识别开始，还是后面记忆查错了？” |
