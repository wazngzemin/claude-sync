## 2. 按链路步骤整理的事实

### 步骤 1：四路输入先变成“标准输入”
| 事实 | 出处 | 状态 |
|---|---|---|
| 背景：Director 同一 Chat 同一时刻只允许一次执行生效；输入管理位于各类输入入口与 Director 之间，把“并发、乱序、多源”的输入组织成可串行执行的调用 | 技术方案·背景与边界 | 已定方案 |
| 现状问题：输入合并、打断、等待分别由多音区缓存、Director、主动推荐逻辑各自处理，优先级、合并窗口、完成条件难以统一；播放完成靠临时事件键；取消靠本地上下文和轮询，取消后仍可能有文本、工具调用或历史写入 | 技术方案·现状与问题 | 当时线上现状 |
| 本期是第一阶段，兼容豆包 IP 和非豆包 IP 项目，作为主线通用模块 | 技术方案·本期范围 | 已定方案 |
| 本期输入来源：用户 Query（单音区、多音区、模拟 Query）P0；高优任务 P0（当前暂无）；主动服务 advice P1（Task Service 与静态 advice 都接）；同步 Tool Feedback P1；有效 Event P1；客户端播报状态与客户端接管属于控制事件，不形成输入 | 技术方案·本期范围表、本期来源映射 | 已定方案 |
| 合并属性：用户 Query mergeable；主动消息 mergeable；Tool feedback isolated（“保守地单独交给 Director”）；有效 Event mergeable；严格按映射，不由输入管理或模型临时判断 | 技术方案·本期来源映射、通用规则 | 已定方案 |
| 适配层（研发叫 Adapter）只做格式统一、补来源身份/优先级/合并属性，不调模型，不判断意图 | 技术方案·字典 | 已定方案 |
| 幂等身份：用户 Query 复用端云仲裁已在用的 request_id；Task 用 task_run_id；云端异步 feedback 用 tool_call_id。request_id 目前非强制（RTC 等链路上行未携带），新链路只接 request_id 非空的请求，其他渠道继续走旧链路 | 技术方案·通用规则 | 已定方案（RTC 属哪个项目：待确认） |
| PRD 的四类输入：有效 user input（含单音区、多音区、last_talk_content=上一轮播报被有效 query 打断）；有效 tool feedback；有效 advice（主动服务、任务）；有效 event（手动操作、状态变化、对话打断 event=上一轮播报被无效 query 打断） | PRD·种子数据 | 已定方案 |
| PRD 需求背景：用车是连续场景，“只有一个豆包生命体”“豆包同一时间只能跟一个人讲话”，车状态互相影响且连续 | PRD·需求背景 | — |
| DT 宣讲：“我们只有一个交互流”，所以需要单独模块决定什么时候把什么送进 director；“总不能说豆包整体表现给用户是自己打断自己” | DT 宣讲 00:14:14、00:35:46 | 讲解 |
| 非目标：高优抢占不启用（结构预留）；有独立 UI 推送、不进播报链路的 AIGC 不纳入；独立异步 callback 不存在；不设队列长度上限，提供按 channel+vehicle_id 清理等待队列的应急接口 | 技术方案·非目标 | 已定方案 |

### 步骤 3：准入（谁先进 DT）
| 事实 | 出处 | 状态 |
|---|---|---|
| 准入矩阵：空闲→所有输入立即处理（isolated 单独处理）；处理中+用户 Query：旧输入可重放→打断+合并+重推，已越过工具边界→打断，只处理新 Query，旧的作中断上下文；处理中+P1→排队，结束后 mergeable 合并、isolated 单独；输出中+用户 Query→客户端先停播，打断后只处理新 Query，已播/未播和原输入作中断上下文；输出中+P1→排队 | 技术方案·准入与状态流转 | 已定方案 |
| P1 在处理中和输出中都不抢占；真正要抢占的必须定义为 P0 | 技术方案 | 已定方案 |
| 与此并存的表述：有效 Event “模型未完成推理且未启播时参与合并重推”；第 8 章“有效新 Input 到达时，未发布候选原子 STALE 并与新 Input、waiting 及完整工具事实合并重算。P1 不停止当前 TaskRound” | 技术方案·本期范围表、Input Manager 消费规则 | **文档内部口径不一，待确认** |

### 步骤 6：播完才算完，推进队列

## 3. 演进、取舍、badcase、争议

### 演进
1. **最早（2026-01 起）分散处理**：多人同时说靠多音区合并缓存（1/13 发版合入），播报中插话靠打断恢复链路（未拒识→last_talk_content，拒识→event），主动推荐自己等待，工具结果由 ReAct 续轮消费。宣讲 1 的规则：首 token 前合并、首 token 后打断丢弃、主动服务排队。
2. **多人同时语音 PRD（8/24 版）**：定义“同时说”（FC 还没下发时其他人也说完）→合并给 Planner；任务执行中按任务类型（文本/控制）决定打断、提示音还是排队，排队要界面可感知。
3. **输入管理 PRD（7/11 起，10/13 v0.5）**：把所有 DT 输入收进一个模块，用“推理是否完成 × TTS 是否起播 × 输入类型”定处理；旧版里的 advisor 有效时间、同 advisor 只留最新、长程工具反馈不参与合并等写在“先不看”区，未进新策略。
4. **技术方案（10/23）**：落成三种 Chat 状态 + 两档优先级 + 合并属性 + 执行重放边界 + 全局唯一执行身份 + 客户端播放事件 + 超时兜底；多音区合并收编进来。
5. **还在往前走**：高优 advice（预留）、query 触发直接打断 DT（10/21 讨论）、异步工具结果（后续扩展）、外部主动推荐接口（11/7 讨论）。

### 取舍
- **只用一个交互流 vs 并行多窗口**：PRD/DT 宣讲明确选一个流，代价是必须排队。
- **合并 vs 排队**：合并省一次推理、减少“各说各的”，但要求旧输入还没产生副作用；排队安全但慢。技术方案用“工具是否已放行”做分界，比 PRD 的“首 token 前”更保守。
- **Tool feedback 单独处理**：“保守地单独交给 Director，避免不同 Tool 结果或交互问题被错误拼在同一批”；代价是多一轮推理。
- **不设业务有效期和队列上限**：先埋点观察；PRD 旧版的“advisor 有效时间、超时丢弃并通知 advisor”没进本期。代价是旧提醒可能晚播（需要 DT 自己判断还要不要说）。
- **超时不伪造完成**：宁可多等到硬期限，也不把“没收到回执”写成“用户听完了”。

## 4. 与旧版（old-page.json / base-modules M 节点）的冲突

1. **执行身份**：旧版素材（10/29 副本）写“DirectorExecutionVersion 每启动一次递增”；10/23 现行技术方案已改为全局唯一 DirectorExecutionID，“不是序号，不能通过加一计算”，不比较大小。

4. **首 token 后的处理**：宣讲 1 说已出首 token 就“直接打断第一个指令，丢弃”；新方案是旧回答作中断上下文交给 DT，不是简单丢弃。

6. **旧版写的“意图理解、拒识召回、打断体验 >98%、>98%、>80%”**：本次读的输入管理 PRD、技术方案、周报里都没找到，不采用。
7. **旧版“最近 30 分钟最多 10 轮”“真召回时带上最近 5 个话题”**：不属于输入管理原文（前者是上下文规则，后者是全时免唤醒 PRD 的设想），本章不写。
