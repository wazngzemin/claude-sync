服务端 AIDV 架构梳理

本文面向产品、研发、行解同学。
目标是建立共同的系统视角：用业务场景讲清楚 AIDV 的定位、与豆包及合作方的分工、需求如何变成回复和操作，以及主要等待和运行开销发生在哪里。
阅读路径：先读第 1 章了解业务定位、第 3 章看架构总览、第 5 章看具体案例；第 6 章了解合作分工，第 7 章讨论方案、时延与成本。第 2 章作为术语字典随时查阅，第 4 章查模块职责与输入输出，第 8 章及附录供研发按需深入。
业务背景：我们在做什么
一个深度绑定豆包 IP，使用豆包大模型、豆包 app 能力的车上 AI 助手
它不是单点车控服务，也不是单纯聊天机器人，而是把豆包入口、车端状态、用户记忆、环境信息、车辆工具、GUI 操作、主动推荐、长时条件任务串起来，帮助用户在车内把事情做成。
AIDV 是其中负责座舱业务编排和模型调用的云端服务，主要负责将用户的自然语言描述拆解成具体的执行需求，并调用对应的 Agent 执行；具体实现的丰富功能，如联网搜索，比价下单，任务跟踪等能力，由内部 / 三方团队开发提供。本文档从服务端的视角展开，介绍当前工程链路的现状，以及各种场景下以 AIDV 为中心的各方依赖、调用与多轮反馈机制。

对比传统车机有如下优势
更自然的交互：用户可以直接用语音和自然语言表达需求，不需要学习固定指令。
更省事的车控：导航、音乐、空调、座椅、车窗等车内操作，可以直接说出来由车机完成，减少找按钮、翻菜单、记路径的麻烦。
更完整的任务办理：把原本需要掏手机、打开 App、搜索、比价、下单的事情，逐步迁移到车内完成。
更懂当前场景：结合车端状态、座舱环境、用户记忆和历史偏好，理解“我有点冷”“帮我找个顺路的咖啡”等隐式需求。
更主动的陪伴与跟进：结合时间、位置、车况、用户偏好和长期目标，主动给出建议，并在需要时持续推动任务完成。

AIDV 主流程


名词

解释

Flow（请求分流）

决定请求走规则快路径、Director 或其他处理路径，并承接主动推荐回流。进入 Director 的请求，由 Director 决定具体说什么、做什么。

syntax_match（规则快路径）

规则快路径，适合简单、高频、低歧义请求。

intent_and_refusal（意图分类与拒识）


提供拒识、意图分类及简单/复杂仲裁结果，供 Flow 选择处理路径；具体要做哪些事由 Director 拆解。


JSGF（句法规则格式）

Java Speech Grammar Format 句法规则匹配策略

Gateway（接入层）

把不同入口传来的问题、会话和车辆信息整理成 AIDV 可处理的请求，再交给对应业务模块。

Director

AIDV 的任务编排中枢，负责理解用户需求、拆分任务、组织回复、选择工具和处理工具反馈。

Agent Server

工具和 Agent 的执行适配层，负责注册、路由、调用和结果转发。

Tool / Agent

可被 Director 调用的能力单元。主要通过 Agent Server 接入 Director，进而被模型调用，将结果返回给模型进行下一轮推理。
在工程实现上，Tool 更偏单个能力，Agent 可以是更完整的外部执行系统。

Context

提供当前场景信息组装的能力，负责组织本次请求需要的信息，包括端状态、视觉描述、基础信息、短期/长期记忆等。

Memory

提供 Context 中与历史和偏好有关的信息，比如用户偏好、历史对话、长期语义记忆、长期情景记忆等。
AIDV 的下游依赖


名词

解释

Trigger

判断条件是否满足，并通知对应的业务模块。
能够感知车辆的实时状态，世界信息，并根据预设条件触发对应的动作。
主要和端状态、时间、地理信息等关联紧密，实际执行的动作依赖下游业务工具。

车控，联网搜索，车书，VQA 等

我们实现的一系列 Agent / Tool，能够被 Director 调用，执行结果同样返回给 Director 进行下一轮推理。

Task Service

将任务诉求整理为任务定义，管理触发条件、任务状态和每次执行结果；触发后交给 Director 或 GUI 执行链路处理。

GUI Agent

在已支持的应用和版本内，结合页面结构与视觉信息，代用户执行界面操作；具体可用范围取决于车型和应用的接入情况。

Extour 依赖：系统中部分工具由 Extour 承接，调用、联调、服务管理和排查问题的方式与内部工具不同，这里单独列出来。



AI Navi


Extour 提供的最重要的导航 Agent 系统，由多个工具组合而成，共同实现根据用户的自然语言提供路线规划和导航能力。

Advisor

Extour 提供的建议/目标管理相关能力，通过主动推荐的能力实现长时/条件任务的触发和执行。
请求、车辆与用户身份


名词

解释

OEM / 渠道

OEM 指汽车厂商；渠道用于区分具体接入及其配置，例如 saic-dna。不同渠道的可用能力、车辆信号和业务策略可能不同。

车辆 id

在渠道下唯一标识某一台车的 id 号，通常与渠道配合，共同定位到全局唯一的车辆

车辆账号 / 乘客身份

车辆账号表示当前登录关系，由车企提供 OEM 账号登录能力。
乘客身份帮助确定本次是谁在说话，以及个人记忆和偏好属于谁。

FaceID / 音区

FaceID 是识别乘员所用的人脸身份标识；
音区表示声音来自哪个座位或区域。二者帮助 Director 关联到当前说话人。

Doubao ID / uid

车主登录的豆包账号。只有同时登录了车企的 OEM 账号和豆包账号才能使用车辆的全部 AI 能力。
持续任务与端云反馈


名词

解释

Task Service / Advisor

持续任务的主要提供方。

Frontier

我们的云端下发基础设施，用于把结果、指令或长链路消息推给端侧。

主动推荐

Frontier 链路在我们项目中的业务实现，具体表现为：云端先把建议下发到车端；车端携带推荐标识再次请求 AIDV，恢复建议来源及相关上下文，再继续处理；来自任务的建议还会关联回对应任务。

Task / Run

Task Service 领域的概念。
Task 是需要持续管理的任务，Run 是任务的一次执行。例如一个每天提醒的任务，可以有多次执行记录。

Goal

Advisor 领域的概念。
长时任务或持续目标，例如点咖啡、持续保持舒适环境、持续讲解某主题。

Callback（回调）

一方在处理完成或状态变化后，调用约定接口通知另一方，例如 Extour 把目标创建结果或触发事件回调给 AIDV。

ACK（回执）

对一次消息或指令的确认、状态或结果反馈。它表示“已收到”还是“已执行成功”，需要看具体协议。

tool_feedback

工具或下游 Agent 返回的执行结果，供 Director 判断下一步；它可以包含状态和数据，与给用户看的话术不完全相同。
算法、提示词与交互体验


名词

解释

System Prompt

提供给模型的角色、工具能力、行为规则和输出要求，用于指导每轮理解与决策。算法方案也需要配套 SP。

SFT（监督微调）

用整理好的输入与期望输出示例训练模型，让模型学习所需的回答和任务处理方式。

RL（强化学习）

在训练过程中通过反馈信号进一步优化模型行为，使输出更符合训练目标。

Token

模型处理文本时使用的计量单位，与字数不等同。SP 的 token 数描述提示词规模，整次请求还可能包含历史和动态上下文。

Fornax

管理和调试 Prompt、查看模型调用与链路记录的平台。本文第 7 章的产品 SP 可在这里查阅。

Fornax trace/span

线上链路观测方式。trace 是一次请求链路，span 是链路中的一个节点。

SSE / 流式返回

SSE 是服务端向客户端持续发送事件的一种通信方式；流式返回让内容在生成过程中分段送达，客户端逐步展示或播报。

ASR / TTS

ASR 把用户语音识别成文字；TTS 把回复文字合成为语音，分别连接语音输入和播报环节。

首响应耗时 / 端到端耗时

前者看多久开始返回有效内容，后者看到约定完成点一共多久。比较时需说明终点是 Director 回复完成，还是车端操作完成。

模块

职责与交接

接入与协议转换（Gateway）

整理不同入口的用户问题、会话和车辆信息；对话请求交给 Flow，业务接口进入相应模块。

账号与乘员身份

确认登录关系、角色和当前说话人，为权限、个人记忆和偏好提供归属。

请求分流（Flow）

决定是否响应、是否命中规则快路径、是否进入 Director，并承接主动推荐回流。

场景信息组装（Context）

按当前问题选择车辆状态、座舱描述、时间天气、车辆知识和记忆，供 Director 等调用方使用。

记忆与会话历史

AIDV 保存对话和事件线索、提交记忆处理；记忆服务生成和检索相关信息，再按需提供给 Context。

任务规划（Director）

决定说什么、做什么；把动作交给 Agent Server，依据执行反馈继续规划或结束本轮。

能力执行适配（Agent Server）

按配置找到工具和调用方式，处理参数与结果差异；将车控、GUI、搜索等能力的反馈交回上层。

车辆状态与业务事件

接收车端上报，维护车况、乘员和场景信息；供 Context 查询，并按业务需要同步触发器或提交事件处理。

持续任务与主动推荐


跟踪跨轮任务，承接 Trigger、Advisor、Task Service 等触发和回调；组织主动下发及后续执行。

结果回端与语音

回复随当前请求返回；主动指令、卡片等经 Frontier 下发。语音链路负责识别、合成、播报协同及反馈。

车型与渠道适配（OEM）

提供当前厂商、车型适用的能力、信号和策略，为 Flow、Context、Agent Server 及端侧配置提供依据。

配置运营与质量回溯


管理 Agent/规则/环境配置，支持场景模拟、录制、反馈和链路观测，帮助产品、QA 与研发定位问题。

打开空调：规则快路径链路
明确的车控指令命中规则后，Flow 直接选择车控能力，无需 Director 拆解。车控能力经 Agent Server 转换为指令，再由 Frontier 下发给车端。图中的单个简单车控以直接下发为主，云端发出指令与车端实际打开空调要分别理解。

打开空调并讲个笑话：Director 复合请求链路
这句话同时包含“说”和“做”，需要 Director 统一理解。AIDV 并行准备上下文和判断是否需要响应；图中的“仲裁”不负责拆任务，拆解由 Director 完成。话术与工具动作分别进入播报和车控链路，Director 还可根据执行反馈继续处理。

打开空调、讲笑话，再点杯咖啡：跨执行域链路
Director 组织话术，并通过 Agent Server 将车控和 GUI 操作交给各自能力。GUI 需要根据页面状态逐步生成动作，由客户端执行并继续回传，可能跨多次请求推进；AIDV 分别记录对话结果和任务进度。本轮回复结束或听完笑话，并不代表咖啡已经下单完成。

我有点冷：Context 驱动结合当前场景理解需求
“我有点冷”没有直接指定设备和参数，需要结合语境理解。Context 提供可获取的车内状态和已有偏好，Director 再结合本次请求的说话位置选择合适动作；Context 本身不负责把这句话固定改写成车控指令。调空调或座椅加热是示例，实际方案由当前状态和可用能力决定。

附录：Eino Graph 编排实现

代码上我们使用了 Eino Graph 来驱动、关联我们的业务场景。
Eino 的官方文档：Eino 用户手册
这里比较容易误解：业务上说“调用 Agent”，但在 Director 的 Eino Graph 里，Agent 是被包装成 tool.BaseTool 编排进去的。也就是说，Graph 看到的是 tool，真正的 agent 调用被藏在 Tool 的 StreamableRun 后面。
工具调用与反馈在 Graph 中按以下关系衔接：
Director 准备工具：GetPlannerAgentList 和 GetToolsByIDs 拿到一批 Eino tools。
工具被放进 Eino ToolsNode
Graph 从 llm 开始：模型输出包含工具动作时进入 tools，无需调用工具时经 direct_return 结束。
进入 tools 后，Eino 调用 tool 的 StreamableRun。
内部创建 AgentStreamRunner，这一步才真正进入 Agent Server。
Agent Server 根据 agent_registry 里的 AgentType 选择 executor；工具结果中的 model_content 被整理为 tool_feedback，供 Director 后续规划使用。
tools 后通常回到 llm，让 Director 基于反馈继续规划；工具配置为直接返回时，经 direct_return 结束。
