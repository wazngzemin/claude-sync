## 04｜上下文准备

这一轮要给推理准备哪些背景：身份、车况、情景、最近历史、任务视图、记忆、车型能力和适用经验并行去取，常用信息预先放进来，缺少的项再单独查证。上一章排好优先级、确认可以接的输入从这里进入。主驾说“带我去昨天那家游泳馆”，系统已经拿到一句明确诉求，却未必知道“我”对应哪个人、“昨天”是哪段经历、那家店的真实地址是什么；本章讲 Context 服务怎样把其他系统已有的相关事实组织成当前背景，它负责组装和供给，不包办原始数据存储，也不直接替用户发导航。

## 背景准备在全链路的位置

**C1（接本轮输入，按需要并行取背景）**先把身份、车况、情景、最近历史、任务视图、记忆、车型能力和适用经验分路铺开。Context 是统一组织和提供背景的服务，按需要从相应来源取得近期交互、车况、任务、世界信息和可合法使用的记忆；车辆上报状态提供当前导航和位置，对话历史提供刚才的候选与用户选择，记忆系统提供权限范围内的相关经历。各来源先处理自己的范围与质量，Context 组织后交给 Director 判断。常用信息预注入，缺项再安排查证，不是每一句诉求都固定把全部背景重查一遍；Context 只组装，不负责长期原始数据的存储，也不替用户直接发起导航。Context 服务管理的上下文源包括情景描述、事件日志、短期历史压缩、短期情景记忆、长期情景记忆、长期语义记忆、用户画像、端状态和联网基本信息，整体职责与 V1、V2 架构演进见[Context OnePage](https://bytedance.larkoffice.com/wiki/OjGMwBX8fiLS0ikDWqVceVjhnPg)。

这一步要解决的根本问题，是传统座舱系统里 AI 只能听见语音指令，看不见用户在其他界面做了什么、车辆状态变成什么样、舱内坐着谁，连续对话衔接差、理解不了场景，体验显得很笨。Context 模块承担 AI 汽车全量上下文信息的管理职能，产品判断体验上限一方面靠模型能力，另一方面靠上下文理解能力，后者正是和竞品拉开差距的关键。服务要做两件事：一是按标准化结构完成上下文信息的存储、维护和查询，为 Planner、Advisor、Agent 等各类调用方提供高效数据支撑；二是在海量繁杂、类型多样、结构各异的上下文数据里，精准快速定位当前业务场景需要的信息。九类来源的数据形态并不相同：情景描述是车内采集的车内外高频低频多模态感知数据，事件日志是当前轮次交互的即时结构化数据，短期历史压缩、短期情景记忆、长期情景记忆、长期语义记忆是非结构化文本，用户画像和端状态、联网基本信息是结构化数据。

架构经历过一次明确换代。最早 V1 采用写入、粗筛、精筛三步式：写入阶段先提取锤炼原始数据，粗筛阶段并行让不同上下文源按输入条件各自筛一遍，尽量包含相关数据，精筛阶段再基于粗筛结果统一细致过滤，保证返回内容可直接给上游使用。上线后从线上数据和评测暴露两类问题。第一类是各源筛选效果难以平衡：集中式架构用单一模型对各源数据统一过滤，为保障速度限制模型输出个数为 5 个，筛选结果存在明显位置偏好，靠前的数据更容易被放行；同一轮评测里某一个源准确率提升，必然挤压另一个源的召回。第二类是速度不达标：为让 Planner 尽快回复，Context 模块设计目标 P90 为 800 毫秒，实际 P90 达到 1.2 秒，其中端状态筛选需要调用两次模型，是主要性能瓶颈。V2 当前方案因此重新划分每个上下文源的职责边界，保证各模块数据尽量不重叠，取消统一精筛模块，把筛选控制权下放给各上下文源，由各源独立保障自身筛选质量，从架构上消除数据源之间的效果不平衡；同时把原有单一筛选拆成预注入和动态检索两阶段，形成常用场景快速响应加复杂场景兜底覆盖的分层机制。为什么必须从集中式改成自治式，原因就在 V1 的两个瓶颈：统一精筛同时承担相关性判断和跨源取舍，既受输出个数限制产生位置偏好，又在端状态这类需要两轮模型判断的环节拖垮时延；把筛选权还给数据源，每个来源最清楚自己数据的时效、范围和合法边界，也更容易独立评测和迭代。

Context 不创造缺失事实。只有“昨天游过泳”，不能改写成“昨天去过某某泳馆”；没有地址仍然缺地址。常用背景可以在 Planner 之前提供，缺少的信息再由 Planner 明确查询；OnePage 概括允许预跑 Context，但没有给出每次语音预请求全量运行哪些来源以及每项失效规则，不能宣称预请求已经把所有背景或昨天地点查完。前置计算结果要按模块、对话、输入和轮次关联保存，正式请求才能找到对应准备；云端临时缓存不等于长期用户记忆，预请求不进入正式对话历史，不播正式答案，也不下发真正车控或导航动作。如果 Context 在预跑阶段就把猜测补成事实，Director 会把缺项当成已知条件直接执行，地址、人和动作都可能错配；保留缺失标记，才能触发后面的显式查证路线。

## 并行分路：身份、车况、情景

身份这一路由 **C2（确认当下说话人与操作对象）**处理。说话音区、当前乘客和可信身份，帮助系统确定该查谁的昨天经历；“给明骏开加热”要先把名字映射到这个人此刻的座位。过去坐过副驾不等于现在还在副驾，同名、未知或空座时不能猜；认识名字、知道位置、有权操作是三个不同条件，涉及私人记忆时先展开可信身份与授权链。音区只说明这句话从哪个座位传来，不自动规定操作哪个座位，主驾让系统打开副驾座椅加热，来源仍是主驾，操作目标才是副驾。身份这一路解决的是“这句话是谁说的、要对谁做”的归属问题：车内多人共用一套座舱，记忆、偏好和权限都按人隔离，说话人和操作对象一旦混淆，就会把主驾偏好用到副驾，或者读取错误乘客的私人记忆。识别链路先靠音区定位语音来源，再结合 FaceID 乘客列表和账号可信关系解析自然人，缺身份或身份校验失败时只使用匿名上下文，不读写乘客私有记忆。

与身份同时准备的是 **C3（取车辆此刻的值和时间）**。当前导航、车窗、空调、挡位、续航等常用状态按这一轮需要取用，并带上报时间；刚刚的车端上报应比旧对话里一句“已经调到某温度”更可信，缺失、过期或未上报也不能被整理成关闭或零值。判断“快到”时，导航事实不能只靠旧聊天印象。SLS（赛力斯车型项目代号）一侧把日常最高频的导航状态、目的地位置、途经点、播放状态、车辆行进状态、空调四合一、车窗、续航等设为常驻端状态，与筛选结果去重后默认注入；座椅位置状态在该版本被屏蔽；工程上把同类信号合并，减少模型注意力分散，端状态筛选输入为多轮对话历史、核心端状态名称和状态知识，输出端状态名称与不超过 100 字的筛选理由，具体信号清单与合并规则见[SLS Context 需求](https://bytedance.larkoffice.com/docx/RLW7dLbgBoc9TyxMX8hcdMddnuh)，该需求按车型项目区分，不是全部车型统一实现。

端状态这一路的产品背景，是模型需要看见车辆此刻的真实状态才能给出合理动作。SLS Context 需求 v1.0 于 2026 年 7 月 3 日形成主线初稿，端状态部分和 DNA 方案保持一致，本期变化集中在 LLM 筛选：先扩大初筛范围，为每个端状态补充知识说明，筛选模型输入是多轮对话历史、核心端状态名称和状态知识，输出是端状态名称或编号，外加不超过 100 字的筛选理由。常驻端状态覆盖导航状态、收藏地址位置、目的地位置、播放模式和状态、当前播放音频、车辆行进状态、空调状态、风向模式、循环模式、制冷开关、车窗状态、续航状态，途经点位置为 7 月 7 日新增；座椅位置状态在本版本被显式屏蔽。后处理在工程上合并同类信号以优化模型注意力：空调四合一合并空调状态、风向、循环和制冷开关，导航二合一合并导航状态、目的地、途经点和沿途服务区，音频二合一合并当前音频与播放模式状态，视频二合一合并当前视频与播放模式状态，输出统一用 YAML 结构化格式。世界信息和端状态同属客观背景，天气通过和风 API 获取当前所在城市实时天气，日历提供公历、农历、星期、节日、节气和季节，当前车辆位置单独成项，同样按 YAML 结构注入。把常驻高频状态直接预置、其余状态走模型筛选，是为了平衡覆盖率和注意力带宽：全部状态每轮都塞进提示词会挤占模型处理任务的空间，全部临时筛选又会让高频状态反复消耗模型调用。

**C4（取舱内外情景，不把视觉当身份）**准备地点、时间、天气和感知系统已有描述。天气、日历、当前位置属于世界信息，按结构化格式注入；舱内情景描述由端侧视觉模型观察生成，乘客列表要和 FaceID（人脸身份识别结果）乘客列表比对，以 FaceID 为准，多余人物信息在情景描述中过滤掉，视觉说“后排有人”不能直接变成可信身份，更不能凭描述多造乘客；舱外路面情况和所见文字以自然语言注入世界信息。讲到宝宝睡着、雨天车闷，这些事实会约束风量或开窗方案；背景已经足够时，不必每轮重新拍图问一遍，需要特定视角或细节时才由 Director 再发显式视觉查询。动态查询结果暂不注入 Context，不作为通用舱内描述。

情景描述的内部结构分乘客列表、物品和动物列表、不安全因素、整体描述和动态查询结果几个部分：乘客列表记录位置、性别、年龄段和造型动态，物品动物列表记录中控扶手、副驾等位置的物品，不安全因素单独成项，整体描述用一句话概括舱内状态。为避免情景描述里的乘客信息和状态变量中的 FaceID 乘客信息冲突，两侧列表必须比对，以 FaceID 结果为准，视觉多识别出的多余人物要从情景描述中过滤。舱外 Always On 观察到的路面情况和所见文字，以自然语言注入世界信息，例如路面湿滑、沿海公路行驶、左侧途经风车群、前方有跨海大桥。视觉情景只承担环境描述职责，身份判定仍归 C2 的可信身份链路；这一分工避免视觉模型一次识别错误就改变乘客归属和隐私边界。

## 并行分路：历史与任务视图

**C5（接最近对话、工具事实和摘要）**接最近交互已经发生了什么。本地做完的动作、后续交互和真实页面点击进入历史，目的是避免重做，不是让云端再执行一次；前一轮查到两家泳馆，用户说“第二家”就得保留真实候选映射，只剩一句摘要不够。最近历史要保留工具事实、真实候选映射、已播与未播内容；对话摘要属于历史延伸，新的人上车时要按隐私规则清空其中的敏感信息，不把旧私事说给新人听，敏感信息包括情感偏好、带私人身份标签的地点和重要日期，功能性偏好例如“喜欢冷空调”不在此列。事件流窗口暂定 10 分钟内最多 30 条，倒序注入，先进先出滚动，重要事件再和 query 按时序拼进对话历史。

历史这一路要解决的是多轮指代和重复执行问题。事件流在 Context 里扮演串联角色，把一帧帧定格画面连接成一段电影，让 AI 从孤立切片里看到情境全貌，理解用户对话和行为之间的内在因果。窗口内事件按倒序排列，例如 9 分 28 秒前打开系统设置页面、8 分前按键设置主驾空调 23 度、6 分 17 秒前语音搜索播放了某首歌、2 秒前副驾睡着；窗口滚动采用先进先出，新事件挤出旧事件。重要事件再按当前轮次 query 和最旧 query 的时间段截取，和 query 按时序拼进对话历史，而不是把全部事件流平铺给模型。对话摘要压缩从第 3 轮开始，对本次用车周期内的人机历史问答做压缩，消除 Director 只保留 5 轮对话造成的时间缺口并关联上下文，每新增一轮重新压缩，最多压缩 22 轮，最长 500 token，摘要拼在记忆变量起始位置。历史分层保存工具事实、候选映射和摘要三层，是因为指代承接需要真实对象，任务判断需要真实状态，而长期语义归纳需要压缩后的事实；把三层混在一段口语化摘要里，模型既无法定位第二家候选，也无法判断本地动作是否已经完成。

**C6（带任务视图，区分旧 Goal 与新 Task）**是另一类背景：系统现在正在跟进什么。用户补一句“快到时提醒我拿泳镜”，注册成功后任务视图应显示还在等待条件，不能显示成已经提醒；以后修改或删除提醒要找到真实任务标识。这里按项目注入 goal_list 或 task_view，只读正在跟进的任务及其状态，背景准备不替任务系统做管理操作；创建成功不代表条件已经触发，具体生命周期归第 12 章。任务视图和最近对话分开，是因为正在等待的条件任务不属于已经发生的历史事实，却直接影响当前能不能再注册一个重复提醒、上一个目标是否还需要继续跟进；把任务状态混进对话历史，模型会误以为提醒已经执行，或者重复创建同一条规则。

## 并行分路：预取记忆、能力知识、适用示例

**C7（第一路：推理前预取常用记忆）**这条线发生在推理之前。系统并行取用户画像，用当前诉求推理相关标签，检索候选记忆和匹配分数，过滤后把合法结果预先放进背景，这叫预注入；取之前先核身份和授权。记忆服务独立于 Context，负责记忆提取、标签提取、画像推理和语义检索，记忆分短期情景记忆、短期历史记忆、长期情景记忆、长期语义记忆、记忆打标、记忆标签、记忆打分和记忆画像，短期情景按 20 分钟或 20 个文本合并、有效期 1 天，长期情景按天合并，长期语义记忆只基于用户说过的话提取偏好、不自行扩展；召回采用标签召回加打分排序，而不是纯向量表层匹配，记忆类型、召回逻辑和已实现与规划边界见[Memory OnePage](https://bytedance.larkoffice.com/wiki/KAAMwb7vsiHpd0k7PVPctGfKnHf)。昨天泳馆地址已经可靠拿到，Director 直接使用即可，这套标签与得分路线不扩大到全部背景数据。记忆支持车主语音删除语义和情景记忆，批量删除要二次确认；删除语义记忆后要同步更新用户画像，隐私隔离与多人上下文清理规则见[记忆系统](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)，其中情景记忆隐私策略施工中、语义记忆隐私策略规划中，混合检索等能力仍在规划。

记忆服务单独抽象出来，是因为火山汽车多个业务场景都需要记忆，需要统一管理流程和算法。服务职责包括对业务方输入数据做记忆提取、记忆标签提取和记忆画像推理，支持业务方获取已提取记忆，支持按 query 做语义级检索，也支持按标签类型取数；语义检索可能存在过召，需要业务方自行处理过滤。九类产物的衍生关系各有分工：短期情景记忆负责按时间维度合并用户行为信息，20 分钟或 20 个文本触发一次总结，有效期 1 天；长期情景记忆按天维度对短期情景再合并，默认无过期策略，可按业务配置；短期历史记忆对超过指定轮次的历史再做总结，有效期 1 天，触发依赖业务方提交；长期语义记忆从用户表达中提取长期偏好，输出自然语言描述，例如“我喜欢吃牛肉火锅”，提取只基于用户说过的话，不自行扩展；记忆打标在长期情景或语义记忆产生后运行，把原始记忆打上“音乐偏好、上下班通勤”这类标签；记忆标签把长期记忆结构化成“喜欢的歌手、喜欢的餐厅”这类字段；记忆打分对生成记忆再排序或过滤；记忆画像在语义记忆基础上做额外推理，从喜欢麦当劳、肯德基、必胜客归纳出喜欢西式快餐，后续可以推荐同类餐厅。

召回方案没有直接采用主流向量数据库，是因为纯向量路线在车载场景存在四类问题：口语化表达相似度落在阈值边界容易漏召或过召，角例难以覆盖；召回逻辑黑盒，badcase 难以定向优化和迭代；对语义模糊指令覆盖不稳定；情景记忆对时效性有强诉求，纯语义排序无法满足时序优先期望。因此自研标签召回加打分排序方案，先用标签锁定相关记忆，再结合语义相似度、信息重要性、时效性和情感显著性重排。2026 年 9 月 9 日评测快照记录：长期记忆召回准确率 96.3%，长期情景记忆召回准确率 90.79%，长期记忆提取准确率 91.29%，长期情景记忆提取准确率 93.6%，标签生成准确率 95.7%，画像生成准确率 83.3%，该快照为历史测试口径，不代表线上实时水平。里程碑上，长期语义记忆、长期和短期情景记忆、独立记忆服务、标签画像、短期历史、情景绑定相关人等已完成，情景记忆隐私策略施工中，语义记忆隐私策略规划中，混合检索、记忆标签动静区分、多模态记忆仍在规划，多模态记忆因业务侧暂未看到进一步收益而暂缓；情绪感知融合记忆三条路径为语音、语义和 VLM，当前先安排基于 VLM 的方案调研。

**C8（注入本车型可用能力与知识）**告诉模型这辆车能做什么，把车型配置、座位和参数边界、工具能力放进背景。有一个工具名字，只说明资料里定义过这种业务，不等于这辆车有设备、当前渠道已接入或用户有权限，不能把高配功能照搬到另一辆车。车书知识就是这一路的典型来源：常用静态车书问答从原先独立工具调用前置到 Context 初筛阶段，先做 query 改写，再按租户、车辆、车型过滤检索，召回最多 3 条、低于置信阈值不注入，过滤后无结果则知识变量留空，Director 不使用车书知识推理；车书与记忆、场景 RAG（retrieval-augmented generation，检索增强生成）数据在向量库中各自使用独立 collection（向量库里的一个集合或分区）隔离，链路设计见[车书 QA 技术方案](https://bytedance.larkoffice.com/wiki/Vp7cwOgx5i49s8kIxHacd9Ggnkd)。动态工具准入的细节归第 10 章。

车书前置要解决的是独立工具调用的链路耗时问题。旧方案里查询车书知识是一个独立下游工具，由 Director 判断后再调用；本期把 2000 条常用静态车书 QA 对前置到 Director 之前的 Context 初筛步骤，如果车书工具本来就是唯一工具调用，这一次 RPC 请求耗时被拿掉；如果车书知识不是 Context 最慢的粗筛环节，这段成本会被其他并发来源隐藏。入库阶段先完成 QA 对结构化清洗，新 collection 字段包括唯一编号、租户 channel、租户应用 channel_app_id、车辆 vehicle_id、车型 vehicle_type、向量化 query 和纯文本 answer。检索先用 DPFM 的 rewrite_query 插件改写用户 query 以支持多轮，意图类型固定为操作手册场景，带入历史和渠道车辆信息；改写后向量检索，按渠道和车辆条件过滤，存在车型版本差异时追加车型过滤，召回 TOP3 后用分数阈值做低置信过滤，低于阈值不注入；过滤后无结果则 knowledge 变量为空，本期只考虑纯文字，图片交给端侧展示。把能力知识和车型配置绑在一起注入，是为了让模型在规划阶段就知道这辆车能不能做，而不是选中工具后才在执行侧发现设备缺失；能力边界如果留在工具执行阶段才暴露，用户会先听到准备动作再被告知不支持，体验更差。

**C9（选适用示例，不覆盖真实约束）**为模型提供适用经验。静态示例常态化注入系统提示词，授模型以渔，教会一类问题的通用处理方法，例如氛围灯、座椅模式的多轮处理；动态示例动态检索注入，授模型以鱼，解决低频、无法抽象归类的单点问题，内容是用户 query 加执行答案，不需要完整输入输出。可提炼共性的一组例子应放静态示例，不应当成动态示例堆积。示例只能辅助判断，不能覆盖当前车型、真实状态和安全边界；资料记录过低配车召回座椅按摩示例、与车书车型知识冲突导致回答有误的历史问题。读这条线要分清找到了示例、确实注入、模型采用、业务最终做对四个阶段，分别验收；静态与动态分工、工具别名约定见[动态示例解 bug 指南](https://bytedance.larkoffice.com/wiki/LKSKwWCoJiE4SHk8xb7c842Dnrf)。动态示例的车型隔离在 2026 年 9 月 3 日会议上确定为倾向单库加字段过滤、而非按条件拆多个库；当时只有分车企和分环境隔离上线，场景域、车型车系、检索逻辑、审核机制和批量导入导出尚未完成，后续需求不能改写成当时现状，会议口径见[动态示例车型分库 9/3 文字记录](https://bytedance.larkoffice.com/docx/YXzMdAbUxo7YGcxX7VUcna1znxc)。

静态和动态示例的分工来自解 bug 方式不同。静态示例解决可以归纳成一类方法的问题，比如时间日期类 query 先取 timestamp 再计算，一个例子教会同类处理；动态示例只收简单明确、无法抽象归类的单点 bug，格式是 query 加决策分析或执行答案，不需要完整输入输出。9 月 3 日会议暴露的冲突来自上汽一台低配车：车书 QA 已经按高中低配分库回答没有座椅按摩，但动态示例里保留了早期解 bug 的座椅按摩内容，两类背景同时注入导致模型回答有误。讨论结论是不按每一组条件拆多个物理库，条件组合一多会产生数量爆炸；倾向在一个库里加车型、场景域等字段，检索时按车型等于 ALL 或当前车型过滤。会议当时已上线的只有分车企和分环境隔离；场景域、车型车系、检索逻辑、审核机制、批量导入导出属于二期范围，车型车系因上汽量产进度最为紧急，其余列为较低优先级。示例背景之所以必须服从真实车型约束，是因为示例只提供处理套路，不能代表当前设备存在；车型知识和示例冲突时，应以车型配置和安全边界为准。

## 各自过滤与组装

这些分支接着汇到 **C10（各来源各自过滤，保留未知）**。V2 方案取消了旧 V1 集中式统一精筛模型，筛选权下放给各个上下文源，由各源独立保障自身筛选质量；身份、车况、情景、历史、记忆和示例先各自处理范围、时效、相关性和质量，再交过来。汇集不等于抹平冲突：旧记忆说不爱开窗、最新话语却要求开窗，要保留来历交给后续判断；未知车况不补成确定值，冲突信息保留出处和待确认标记，不能混成一条万能真相。V1 集中式精筛受输出个数限制存在位置偏好，某一源准确率提升会挤压另一源，且端状态筛选要调用两次模型，P90 实际达到 1.2 秒，这是 V2 拆分预注入和动态检索的直接原因。

各源自治过滤解决的是相关性判断和资源归属问题。身份源只负责本轮说话人和操作对象是否可信，端状态源只判断哪些车辆值和本轮相关，记忆源负责权限范围内的相关经历，历史源负责保留未完成的工具事实和候选，示例源负责检索可参考的处理套路。每个来源先完成自己这一段的范围、时效、相关性和质量校验，再把带出处的结果交给 Context 组装。保留未知而不是补全，是因为背景准备阶段没有依据推断缺失事实；旧记忆和新话语冲突时，系统没有权力在背景层替用户更新结论，只能把两条事实和来历一起交给 Director，由它结合最新表达判断。如果各源统一由一个模型压缩成“标准答案”，跨源冲突会被错误抹平，排障时也无法追溯结论来自哪一类背景。

汇集之后到 **C11（组装本轮背景给同一个 Director）**，把这一轮输入、来源清楚的背景和当前项目提示词交给 Director。静态规则与动态数据分开放，按目标渠道做变量映射；Director 同时知道用户目标、已有事实、仍不确定的部分和可选工具，信息够就进入回答或执行判断，信息不够也不在背景准备里悄悄猜出一条地址。项目提示词字段和背景范围按项目与版本区分，不能把图上有背景推导成全量、实时、可用。组装阶段还要把常用预注入内容和动态检索内容、静态系统提示词分层放置，避免动态个案覆盖通用规则；不同渠道和车型的变量映射分别配置，保证同一套 Context 服务在多租户环境下取到各自合法的背景范围。

## 第二条路线：缺项由 Director 显式查证

缺项查证是另一条路线，和推理前预取记忆分开。预取足够就直接回答；预取不足，由 Director 明确提出查询需求，带对象、关键词和必要时间范围，先验权再检索，这就是 **C12（第二路：Director缺记忆才显式查）**。检索工具重新执行完整获取流程，结果作为 feedback 进入下一轮，不绕过输入管理直推新动作。缺项查证的实际动作仍交执行模块完成，结果经执行层和输入管理回到下一轮；背景准备不会自己查完就开导航。把预先取背景和后来查缺项分开，才能解释为什么有时一轮就能导航，有时必须先查记忆、再拿真实地址继续。V2 预注入覆盖约 80% 常规请求，动态检索兜底剩余约 20% 复杂请求，比例为 OnePage 方案口径，不是线上实测分布。

两条路线的分工对应 V2 两阶段架构。预注入阶段并行拉取常用上下文：Context 向记忆服务取用户画像，传入 query 计算相关标签，带标签查询记忆并取得匹配分数，按分数过滤后和画像一起注入 Planner；Planner 请求大模型时，信息充足就直接回复结束，并把交互历史同步回 Context。信息不足约 20% 的复杂请求，Planner 改写关键词和时间范围，调用检索工具动态检索，记忆服务重新执行完整获取流程，二次检索结果带回后再请求大模型生成，最后同样同步历史。动态检索之所以必须经过 Planner 发起，而不是 Context 自行补查，是因为缺什么、用什么关键词和时间范围、检索结果够不够，都需要结合当前任务意图判断；Context 只负责供给现成背景，不承担任务推理。检索结果作为 feedback 进入下一轮而不是直接下发动作，也保证新查到的事实经过输入管理和权限校验，和本轮其他背景一起被 Director 统一使用。

## 底部补充口径

画板底部五条补充口径是 2026 年 10 月 Context 读取侧产品口径，不改变 C1 到 C12 主流程。

**C13（本地执行结果回 C5）**【已落地】：本地办完后，诉求、回复和真实结果回写进最近对话上下文，下一轮才知道本地已经做过什么。公用 Context 按必读优先级分三级：最高必读是对话历史、车况、身份；次高选读是视觉、记忆、任务；偶发取用长期画像。分级注入的理由是三类背景对决策的必要性不同，身份、车况和对话历史缺失会直接导致任务无法理解，视觉和记忆在多数请求下作为补充，长期画像只在涉及个性化偏好时偶发取用；不分级会把低必要性背景长期占用提示词位置。

**C14（三维过滤，打断走 I 图）**【已落地】：按场景、人物、任务三维过滤后再注入，不全量塞进提示词；TTS（Text-To-Speech，文本转语音合成）播报中被打断的处理交第 08 章打断恢复，不在 Context 模块内重复决策。三维过滤保证只取和当前场景、当前人物、当前任务相关的背景，避免别的乘客历史和无关任务进入本轮；打断状态属于输入管理时序问题，Context 只负责供给背景，不决定是否合并旧播报。

**C15（任务队列五字段，长期能力在 N 章）**【长期愿景】：任务队列保留任务编号、排序、任务内容、截止条件、关联诉求五个字段，创建不等于触发；视觉持续任务、司机类长期能力在 N1、N2、N18 相关章节展开，本章不承诺已实现。五字段把任务对象和对话历史区分开，队列管理的完整能力属于任务生命周期章节。

**C16（视觉信号三类；状态角标）**：OMS 即 Occupant Monitoring System 舱内乘员监测，提供人脸信号；DMS 即 Driver Monitoring System 驾驶员监测，提供视线信号；再加手势动作信号，三类分别取数，区分舱内低频、舱内高频和舱外，按音区与座椅传感器触发。主链【已落地】，示例检索召回策略【讨论中】。三类信号来源、频率和用途不同，混在一路会让低频舱内信号干扰高频决策，也无法按渠道分别降级。

**C17（端状态上传三机制）**：事件触发、周期上报、变更推送三种机制并用，分别对应全量、增量、定时；缺失值不当成零值，未上报的状态不能被整理成关闭或默认数值。三种机制分别覆盖状态突变、周期性刷新和单点变更，组合使用才能兼顾实时性和上报成本；缺失值保留未知标记，是因为未上报和处于关闭状态在语义上完全不同，把缺失当零值会诱导模型做出错误车控判断。

## 验收要点、时延口径与待核边界

评审这一章要先看清预取记忆和工具查记忆是两条不同路线：强制每轮查两遍浪费时延，不查又会编造地址，预注入足够就直接回答，不足才由 Director 发起显式检索。旧对话、当前状态、动态示例冲突时还要分清分别由谁处理，三个来源的可信度、时效和作用不同，来源各自过滤后由 Director 统一判断，冲突保留出处。身份、记忆、示例注入前要确认走完授权和隐私校验，新乘客上车后旧敏感摘要也要清理。示例从召回、注入、采用到业务做对要分阶段验收，不能用模型召回了示例代替业务做对。车型提示词字段和背景范围按项目版本核对，图上有背景不等于全量、实时、可用。

验收时还要按来源分别统计背景可用率，而不是用一个总满意度概括。身份路核对说话人、操作对象和授权链是否对应；端状态路核对常驻信号、筛选信号的时效和缺失值标记；情景路核对视觉乘客与 FaceID 乘客列表是否一致、动态查询结果是否误注入；历史路核对工具事实、候选映射和摘要是否完整；记忆路核对召回、注入、采用和画像推断是否正确；知识路核对车型过滤、TOP3 召回和低置信过滤是否生效；示例路核对静态与动态归属、车型字段过滤和冲突处理。找到示例、注入提示词、模型采用、业务做对四个阶段分别埋点，才能定位问题出在哪一层。

时延数字要分环节登记，不能混为一谈。Context OnePage 文档口径为当前版本背景组装 P90 564 毫秒，对比旧集中式方案 1.2 秒；这不是语音全链路首音时延，也不是模型开口第一个字的时延，数字为文档口径、未独立实测。背景查询记忆时延只统计记忆查询环节 P90，记忆测试方案目标 P90 不超过 500 毫秒，不与整个背景组装或模型首字时延混同。复杂任务与背景推理可用率考察人名、空间、时间、端状态、视觉、记忆推理正确且工具或回答正确，官方准出目标 90%，打分口径见[Director 评测重点与打分指南](https://bytedance.larkoffice.com/wiki/EvErwmyvsirt8Tka41wckFxxnue)与[Director 评估维度和准出指标表](https://bytedance.larkoffice.com/wiki/GA6bwfWXIim2FmkOFJlcZfkmnnb?sheet=YWVS0m)，模块输入输出定义见[Director（对话推理引擎）PRD](https://bytedance.larkoffice.com/wiki/XRuKwJ0VPisdUhkxH0ecY1rRn9g)。

待核与规划边界单独标注：SLS Context 数据来源、固定状态和过滤规则非全部车型统一实现；核心端状态知识梳理和一期事件日志模板未单独读取，正文未据此展开额外结论；记忆系统语音删除要求与旧表部署口径待对齐；情景记忆隐私策略施工中、语义记忆隐私策略规划中；动态示例车型车系分库、场景域隔离、检索与审核机制后续版本逐步补齐；车书知识方案与标准化需求按项目和版本区分，分数阈值和混合检索权重待评测确定；长期规划还包括新增 profile 模块、解决跨源数据冲突、推动业务方接入结构化数据并废弃非结构化返回方案。背景只把可靠、有权限、来历清楚的事实交给 Director，缺项走显式查证，后续怎样推理和规划见第 05 章。

## 位置在原料汇集之后、推理之前，先解决背景质量问题

这一步解决的是背景质量问题。九路原料如果不筛直接全部塞进模型，无关信息会干扰判断，背景长度也会顶爆模型能接受的范围。走查里出现过“空调已经开着，系统又去推开空调”的问题，车状态其实已经传上来了，推理时没有真正消费，根子就在筛选和打包这一步没有把有效状态交到模型面前。这一章的位置在原料汇集之后、推理之前：原料从九个方向进来，经过筛选、打分、压缩，包成这一轮要用的背景包。九路原料由上下文准备章节并行取到，本章不再重复备料清单；这一步只判断哪些留下、按什么排序、压到什么粒度。Context 服务管理的上下文源、架构演进和当前链路，见 [公共 Context 管理（Context OnePage）](https://bytedance.larkoffice.com/wiki/OjGMwBX8fiLS0ikDWqVceVjhnPg)。

要先看清这九路原料分别是什么、是什么数据形态，后面讲筛选取舍才有对象。九路分别是情景描述、事件日志、短期历史压缩、短期情景记忆、长期情景记忆、长期语义记忆、用户画像、端状态和联网基本信息。情景描述是车内 AI 盒采集的车内外高频低频信息，属于多模态感知数据；事件日志是当前轮次交互的即时上下文，属于结构化数据；短期历史压缩是对近期对话与用户行为的压缩总结，属于非结构化文本；短期情景记忆按分钟或轮次记录用户行为；长期情景记忆按天维度把行为合并成时间线，例如某天在某城市做了哪些事；长期语义记忆从用户表达里抽出长期偏好，输出为自然语言描述；用户画像由长期语义记忆和长期情景记忆推理得到，是结构化标签；端状态是车辆实时结构化信息；联网基本信息是时间、地点、天气等联网取得的结构化信息。传统座舱系统只感知用户语音指令，不知道其他界面操作、车辆状态和舱内人员状态，连续对话衔接差、理解不了场景；公共 Context 服务把这些异构数据统一接入、统一管理，核心目标有两个，一是把通用上下文维护好，二是在海量繁杂数据里快速定位当前场景需要的信息，让回答贴合眼前需求。

**N6-01（筛选过滤）**按这一轮说法的相关性，把用不上的原料筛出去。用户问游泳馆，上周听过什么歌这一轮就不进背景。端状态这一路和普通文字不同，它是一批结构化信号，每条带信号编号、取值、时效和车型范围标记，模型读到的是字段化的车况，不是一段自然语言描述。筛这一步做减法而不是加法，目的是让模型这一轮只看到和当前说法有关的事实。端状态筛选的输入是多轮用户说法、端状态名称和状态知识，筛选模型输出保留的端状态名称与筛选理由，筛选理由限制在一百字以内；日常高频涉及的常驻端状态先和筛选结果去重，再默认注入系统提示词，部分信号按规则屏蔽，座椅位置状态就属于被屏蔽的信号；同类信号在工程上合并后交给模型，具体规则见 [SLS Context 需求](https://bytedance.larkoffice.com/docx/RLW7dLbgBoc9TyxMX8hcdMddnuh)。

同类信号合并有四组固定约定：空调四合一，把车内空调状态、空调风向模式、空调循环模式、空调制冷开关状态合并为一组；导航二合一，把导航状态、目的地位置、途经点位置、沿途服务区位置合并；音频二合一合并当前播放音频、播放模式和状态；视频二合一合并当前播放视频、播放模式和状态。合并的理由是同类信号分散罗列会让模型注意力被切碎，合并成一组之后模型对同一类车况形成整体判断，也减少背景包占用。端状态和客观环境信息统一用 YAML 格式输出，字段名和取值对齐固定模板，主键下只有一个参数时直接写成主键加参数名加参数值，不再套列表结构。情景描述里的乘客列表还要和端状态 Face ID 乘客信息比对，以 Face ID 为准，情景描述中多余的人物信息先过滤掉，避免两套身份来源在同一份背景里互相冲突。

车况问题的回答方式在这里有一次改造。用户问“空调现在几度”“车窗关了吗”这类车况问题，不再由模型凭记忆直接回答，而是先做一次检索：用一个更小的模型先初筛，再到知识库里找到对应切片拼给模型。这套方案赛力斯已经上线【已落地】，上汽 D6X 还在测试准备切换【2.6 目标】，切换的硬要求是效果不能比老方案退化；ToB 车型评测准确率在 90% 多，具体目标值以上汽本车型评测数据为准，不按其他车型成绩套用【待核】。车书问答知识在独立向量库中分渠道、分车辆、分车型过滤，最多召回三条，低于置信阈值的结果不注入，过滤后没有结果就把知识变量置空，不靠模型补齐，链路设计见 [座舱大模型-知识与状态检索需求（车书 QA 技术方案）](https://bytedance.larkoffice.com/wiki/Vp7cwOgx5i49s8kIxHacd9Ggnkd)。

检索这一段的顺序不能颠倒：先对用户真实说法做改写，多轮请求被补全成独立可检索的句子，再用改写后的句子在向量库中检索；本期静态车书问答共 2000 条，存放在 VikingDB 的独立集合与索引里，和用户记忆、场景 RAG 数据互相隔离，集合上带渠道、渠道应用、车辆、车型四级过滤字段，车型存在版本差异时追加车型过滤条件；向量检索召回 TOP3 之后，再用 score_threshold 置信阈值做低置信过滤，低于阈值的结果不注入 Director，全部过滤掉时知识变量留空；回答需要展示的图片交给端侧展示，不把图片内容塞进文本背景。参考知识要分清两种来源：品牌通用知识是全品牌的用车常识和车书手册，本车专用知识是具体车型的配置差异，两类按渠道和车型隔离存放，其他车型的车书不会混进当前车辆的背景【已落地】；当前渠道查不到的条目置空，如实说不知道【2.6 目标】。

## 筛完打分排序，动态示例与动态知识各管一类场景

筛完之后 **N6-02（打分分类）**给留下的原料按标签和匹配分数排序，记忆相关的判断走记忆模块自己的路线。用户说“找点吃的”，饮食偏好这条记忆的匹配分就高于上周歌单，排在前面。这里再补两类按需进入的原料。动态示例是按这句话的语义，从案例库里找少量最相似的处理案例喂给模型，专治长尾说法：模型没见过这种表达时可以参照一模一样的处理案例，同时把上千个老案例挡在背景之外，只放少量进来，控制背景长度。静态示例是常态化注入系统提示词、教一类问题的通用处理能力，动态示例是动态检索注入、解决低频且无法抽象归类的单点问题，两者分工与入库边界见 [动态示例与动态知识方案（One Page，动态示例解 bug 指南）](https://bytedance.larkoffice.com/wiki/LKSKwWCoJiE4SHk8xb7c842Dnrf)；动态示例还要按车企、环境和车型车系做隔离检索，上汽量产前暴露出低配车型没有座椅按摩却被通用示例带出的冲突，车型字段过滤是这一阶段的紧急需求，讨论记录见 [文字记录：动态示例车型分库 9/3](https://bytedance.larkoffice.com/docx/YXzMdAbUxo7YGcxX7VUcna1znxc)。

车型隔离的落地方案倾向单库加字段过滤，而不是把每个车型拆成独立案例库：在同一份案例库上用车企、环境、车型车系字段做检索过滤，车型车系字段是 P0 必做项，案例审核、批量导入导出、检索逻辑完善属于后续 P1、P2 阶段；现有主线、上汽、赛力斯三条渠道分别维护各自案例。这个取舍的理由是拆多库会让同一条通用规则在多个库里重复维护，车型新增时同步成本高；单库加字段只需要在检索条件里追加过滤，维护一处即可。反过来如果字段过滤缺失，通用案例就会像座椅按摩案例那样被错误召回，给低配车型带出不存在的功能。

动态知识是另一条路：先用一个小模型判断当前落进哪个场景，比如儿童安抚、急速调温、车内观影，再把这个场景的分步规矩交给推理模块，指导多步编排。前者教这句话怎么处理，后者教这一类场景一步步怎么走，两类机制不要混为一谈，覆盖边界不得重叠，避免重复占用背景长度【2.6 目标】。动态知识的场景清单、分类器规则和各场景分步规矩，当前未核到正式方案文档，场景划分以后续场景知识配置为准【待核】。

## 压缩分层、异常关卡与事件是否成立的判定

**N6-03（压缩·分层）**把进入这一轮背景包的长内容逐级压短：瞬时、短期、长期记忆之间逐级压缩，情境描述每满十轮压成前置总结加最新总结，不无限堆叠；一段三天的对话压成一两行，只保留时间、地点和目的，不把整段原文塞进去。瞬时、短期、长期记忆之间怎样转换和沉淀，归 N9 记忆生产一章讲。记忆侧的历史对话摘要压缩口径，即从第 3 轮起每新增一轮做一次压缩、最多压缩 22 轮、摘要长度上限 500 个 token，属于记忆模块自己的节拍，不与本章情境描述的十轮压缩混用，规则见 [记忆系统](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)。

加工过程中的异常走 **N6-04（异常分支（金关卡：缺项 / 过期 / 冲突））**这道关卡，分三种情况：该到的原料没到，当日长期记忆未更新，就置空继续，不硬补一条；内容过期或超过这一轮背景包长度上限时，按异常分支置空或截断，瞬时、短期记忆的过期与转存阈值归 N9 记忆生产一章讲；两路信息打架，比如云端迟到的记录和本地已经执行的结果冲突，当前按本地为准，这条取舍规则仍在讨论中【讨论中】。游泳馆地址没查到就反问用户，绝不借邻座或旧记忆猜一个地址。

事件这一路还要先判断是不是有效事件。猛打方向超过角度、突降暴雨、主驾开始抖腿、建议被采纳并行动属于正例；气流扰动、常规打方向、眨眼、建议没有被采纳不算事件。事件文案采用固定格式，由主体、做了什么或说了什么、客体三段组成，不经大模型生成；字段包含毫秒时间戳、事件编号、可多人绑定的人脸身份编号、手动或语音交互形式，以及一到四级分类、信号编号和信号名称，复杂事件由多个简单事件组合而成并替换简单事件。本期只做事件上报机制和事件日志表，任务串联、任务队列这些涉及任务的部分放到后续版本，验收时不能用任务级串联完整来要求这一阶段【2.6 目标】；端状态、视觉描述和事件日志三类数据的接入、订阅与消费边界，见 [事件日志产品需求文档 v1.2（端状态事件日志 OnePage）](https://bytedance.larkoffice.com/wiki/PRf0wRd3Uic0omkiiiGc70wanQN)。

车辆数据上报不是三条孤立接口，而是整车情境数据底座：端状态提供实时快照，视觉语言模型提供空间与乘员感知，事件日志把变化串成时间线，让触发器、Context、Planner、记忆和下游订阅方拿到同一套可信数据。工程上分五层：生产层统一接入，规范层统一定义事件口径，存储层区分状态与事件，分发层按订阅消费，查询层服务模型上下文；覆盖规则上状态按新旧合并，事件按时间追加。事件来源分三类：端状态满足触发器规则后生成事件，客户端直接上报用户操作或设备事件，云端业务记录人车对话、人人对话、任务执行和记忆开关等事件，三类来源都落到统一事件定义，不允许各业务自造事件名和文案。同源数据服务四类消费方：触发器消费最新快照和订阅事件，关注实时性和条件判断；Planner 和 Director 消费当前状态加短窗口事件，判断是否回复、追问或执行；记忆把事件日志当原始事实做短期总结和长期沉淀；下游订阅按指定事件和状态变化分发，避免每个业务重复建设查询和回调链路。高频状态变化先做去噪、聚合和频率节制，人人对话、视觉描述等高信息密度数据要补权限、脱敏和白名单策略；事件治理前置到定义阶段，先定清事件口径、主体、时间、分类、拼接规则、是否进入 Context、是否触发主动响应、是否进入记忆。

## 打包交推理模块，旁路交顾问，再沿案例过一遍

再到 **N6-05（Context 打包）**，把筛过、排过序、压好的内容整理成这一轮输入包，交给推理模块，另一条旁路交给顾问（Advisor）做主动建议。模型这一轮看到什么，就是这一包里的内容。这里要分清，压缩不是删除记忆：瞬时、短期、长期记忆在后台照常生产，这一步只是把这一轮要给模型的那份挑出来、压好。

Context 链路本身经历过一次架构调整。最早的 V1 采用写入、粗筛、精筛三步式集中架构，线上暴露出各数据源筛选效果难以平衡、统一模型输出个数受限带来位置偏好，以及端状态两次模型调用造成整体超时的问题，当时 P90 耗时约 1.2 秒，没有达到给 Planner（对话推理引擎）尽快回复的要求。V1 把所有源交给单一模型统一过滤，为保障速度限制模型只输出五个结果，靠前的数据更容易被放行，同一轮评测里某一个源准确率提升，另一个源准确率就会被挤低；端状态筛选需要两次模型调用，是主要性能瓶颈，Context 设计目标本为 P90 800 毫秒，实际没有达成。当前 V2 改为预注入加动态检索两阶段：进入 Planner 前只并行准备大多数场景会用到的常用数据，覆盖约 80% 的常规请求，保障核心场景响应速度；Planner 判断信息充足就直接回复，信息不足再调用检索工具按需精准召回，兜底覆盖剩余约 20% 的复杂请求；筛选权下放到各上下文源，由各源独立保障自身筛选质量，当前链路 P90 约 564 毫秒，口径见 Context OnePage。和传统集中式架构相比，V2 不再全量召回再统一精筛，也不是只靠初始上下文加动态检索补长尾，而是预注入高频常用数据加 Planner 按需检索，更贴合车载低延迟、高可靠的要求；记忆类动态检索时，Planner 会先改写关键词和时间，再调用检索工具重新走一遍完整获取流程。

沿游泳馆案例走一遍：用户说带我去昨天那家游泳馆，N6-01（筛选过滤）留下昨天去过哪家、车辆能不能开、导航工具在不在、当前没有别的挂起任务，滤掉空调温度、车窗开度和播到一半的歌；N6-02（打分分类）把昨天泳馆这条记忆排在前面；N6-03（压缩·分层）把长对话压成一行时间地点；地址没查到就走 N6-04（异常分支（金关卡：缺项 / 过期 / 冲突））置空反问；N6-05（Context 打包）把这份背景交给推理模块去规划路线。

这一章需要讲清几类边界，按主题连贯展开。端状态本身是结构化信号而不是自然语言，画板登记为 235 条信号；上传节奏为上电全量、之后增量上报，低频信号十秒一次、高频信号两秒一次心跳，起点和统计范围以车端上报口径为准【已落地】，具体信号条数与心跳周期需回最新信号库核对【待核】。车况查询先检索再回答，赛力斯已上线【已落地】、上汽 D6X 在测【2.6 目标】，准出要求效果不低于老方案，目标值以上汽评测数据为准。动态示例与动态知识的覆盖边界不得重叠，避免重复占用背景长度。品牌通用知识和本车专用知识按渠道、车型隔离存放，其他车型车书不混入当前车辆背景【已落地】；当前渠道查不到的条目置空，如实说不知道，不靠模型补齐【2.6 目标】。上传了不等于推理时被消费，走查 badcase 属于上传链路通了、推理环节未取用，排错要把供给问题和消费问题分开判断。进入这一轮背景包的长内容按粒度压缩，情境描述每满十轮压成前置总结加最新总结，长对话只留时间、地点、目的；记忆瞬时、短期、长期之间的转换阈值归 N9 讲。事件正反例标准为非规律、能被感知的变化才算事件，常规动作、搜了但没有建议的不算；本期 09S2（09S2 为本阶段版本代号）只做事件上报与事件日志表，事件与任务的关联串联放到后续版本【2.6 目标】。知识库配套低代码运维平台，客户和交付团队可以自行上传文件、调整切片、测试召回，按渠道和环境隔离，不需要每次改动都找产研发版；该平台在 ToB 客户环境已落地【已落地】，本项目渠道是否接入仍需核对【待核】，平台能力见 [座舱大模型-数据闭环-低代码检索运维平台](https://bytedance.larkoffice.com/docx/L7GJdLiCqoK880xt69KclTd5nfd)。

低代码平台的权限和存储规则也要讲清。角色分内部和外部两类，每类下再分管理员、普通用户和权限配置员：内部用户可以使用对话能力、模型设置、查看详情和切片编辑，权限配置员可以管理内部渠道；外部客户用户只能使用对话能力和切片编辑，不能使用模型设置，渠道配置权限只对外部权限配置员开放，避免客户改动全局模型参数。文件管理支持按渠道、环境、车型、模型筛选，正在生效的文件不允许删除，删除、生效和取消生效都要二次确认，未完成切片保存的文件显示处理中状态；新建文件走上传、内容解析订正、切片订正保存三步，解析失败支持自动重解析和手动重解析。存储上同一个客户的多本知识只占用一个向量库存储空间，降低成本并方便客户核算；新增切片收纳到对应渠道、环境、车型的运维切片集里，保证召回结果按车型隔离。

评审按下面的顺序逐项核对。这一轮说法进来先看端状态是否筛对，误筛会让推理模块基于错误车况做判断，得出的动作建议跟着错。接着看车况查询切到检索方案后上汽的准出指标定多少，赛力斯已上线、上汽在测，效果不能退化，但目标值要以上汽评测数据为准，不能照搬其他车型成绩拍脑袋。再看动态示例和动态知识各自覆盖哪些场景，一个治长尾说法、一个管多步编排，场景重叠会重复占用背景长度，需要把边界划开。之后确认查不到内容时话术和兜底走哪条，缺项置空是底线，但用户听到的句子要自然，不能把内部空状态直接播出来。最后核对长记忆压到什么粒度，压得太狠丢掉时间地点等关键事实，压得太轻又把背景长度顶满，粒度要在两者之间取平衡。

分阶段方案目标按模块分列，均属于方案目标。端状态筛选要求相关判断正确率不低于 96%，单次处理不超过 230 毫秒，自第六阶段起考核。车况查询先检索再回答，赛力斯已上线【已落地】，ToB 评测准确率 90% 多；上汽 D6X 在测【2.6 目标】，准出要求不低于老方案，具体目标值以评测数据为准。视觉事件、长期记忆、事件日志、短期记忆筛选要求各类相关判断正确率各不低于 90%，单次不超过 230 毫秒，自第八到第十一阶段起分别考核。背景包整体正确性不低于 85%，整体耗时以第七阶段摸底数据定值。压缩节拍上，情境描述每满十轮压成两段前置总结加最新总结，不无限堆叠。上述正确率、耗时和阶段编号在已读取的一手方案文档中尚未核对到当前实测基线，落地前以最新 Context 评测方案为准【待核】。

边界上，上传了不等于模型看到了：走查里的问题就是上传链路通了、推理时没有消费，排错要把这两类分开。品牌知识和专用知识的隔离、动态示例和动态知识的覆盖场景、长记忆压缩粒度，都在备查和评审里继续核对。下一章看背景和指令交出去之后，豆包用什么嗓音、什么表情把话说出来。
