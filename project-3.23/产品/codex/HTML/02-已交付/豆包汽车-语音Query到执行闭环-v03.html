01 · Runtime spine

从用户开口，到用户真的拿到结果

下面只有一条向下读的主链。端侧快路径、长期任务和 VLM 都挂在相应节点旁边，不再跨页拉线。每个阶段都固定解释输入、机制、输出、指标、失败归因与 PM 掌握深度。

先记住这句：用户请求 → 当前已知 / 未知 → Planner 判断 → action_list → 工具真实执行 → tool_feedback → 下一轮判断 → 用户目标完成或明确失败。
声音→ ASR 请求→ 端云路由→ Context→ Planner = Director→ 输出协议→ 执行编排→ Tool / Agent→ Feedback ↺→ 最终结果
主链是同步阅读顺序；虚线支链在后文单独展开。配置平台属于设计态控制面，不是每个用户 Query 的运行时下一站。
贯穿案例
“我有点冷，打开座椅加热，十分钟后帮我关掉，再导航去昨天游泳的地方。”
即时动作vehicle_basic_control 打开主驾座椅加热
串行检索user_memory_search 找到“昨天游泳地点”，再 route_planning
长时目标goal_list_update 托管十分钟后的关闭动作；到时重新唤醒决策
01

声音入口：先确定“谁在什么时候说了什么声音”

麦克风前端把嘈杂车舱里的连续声音切成可识别的一段，并识别音区、打断与说话时机。它不是 Planner，但它一旦错，后面再聪明也只是在认真执行错误输入。

端侧Owner：语音前端 / 车端链路职责已确认字段需按车型核实PM 深度 L3
输入
多麦音频、车速噪声、播放回声、唤醒与当前会话状态
机制
唤醒、波束形成、AEC 回声消除、降噪、VAD 断句、声源 / 音区识别、全双工打断
输出
一段待识别语音 + 音区 / 时间信息；异常时是无输入、截断或错人
案例到这里主驾发话；“我有点冷……”被切成一个完整 utterance，位置应指向主驾。
展开：机制、指标与评审问题

你要弄清

  • 多人同时说话时谁获得会话权。
  • TTS / 音乐播放时能否打断，回声怎样不被误识别。
  • VAD 过早截断和过晚收尾分别怎样传到 ASR。

关键指标

  • 有效唤醒率、误唤醒率
  • 打断成功率
  • 音区 / 座位识别准确率
  • 端点检测时延与截断率

评审必问

  • 高速、开窗、音乐大声时基线是什么？
  • 低置信音区是留空还是硬猜？
  • 一段音频如何关联 session / trace？
典型错因：“后排关窗”被识别为主驾指令，表面像车控参数错，根因其实在音区识别。
02

ASR 与请求信封：把声音变成可追踪的标准请求

ASR 产出文本；请求层再把文本和说话人、位置、时间封成 user_query。Planner 当前 SP 明确看到的是结构化请求，不是原始音频。

端侧 → 云入口Owner：ASR / Input GatewaySP 字段已确认PM 深度 L3
输入
阶段 01 的语音片段、音区与时间信息
机制
识别文本与实体；统一包装 query、speaker_name、speaker_position、timestamp
输出
user_query；运行时还应能关联 session / trace，但该字段不在当前 SP 示例中
案例到这里speaker_position=主驾驶位，关键实体是“座椅加热 / 十分钟 / 昨天游泳的地方”。
展开：机制、指标与评审问题

你要弄清

  • partial 文本何时变成 final。
  • 人名、数字、时间、POI 如何专门校正。
  • 低置信结果是进路由、进澄清，还是静默丢弃。

关键指标

  • 字符错误率与实体准确率
  • 数字 / 时间 / POI 识别准确率
  • ASR final P50 / P95 时延
  • 用户纠正 / 重说率

评审必问

  • “十分钟”错成“十五分钟”如何拦？
  • 说话人未知时，下游是否允许位置敏感动作？
  • 原音、文本、trace 能否一键回放对齐？
典型错因：时间实体识别错却仍创建任务，不能只算 Planner 任务解析错误。
03

统一入口与端云路由：决定谁来处理，不让两套结果重复执行

简单高频车控可以走端侧 FC 快路径；云侧拒识 / 仲裁后，简单领域可给 FC，复杂、多步或拒识超时则给 Planner / Director。真正要盯的是“单一裁决、明确降级、绝不双执行”。

端云协同Owner：路由 / 仲裁Director PRD 口径当前实现需 trace 核实PM 深度 L3
输入
标准请求、端侧 FC 候选、云端拒识 / 意图结果、网络与超时状态
机制
拒识、能力域、复杂度、白名单、时延与 fallback 仲裁；只选一个执行主路径
输出
端侧快执行，或路由到云 FC / Planner；附路由原因与降级原因
案例到这里一个请求包含即时车控、记忆依赖导航和定时任务，不能只走单一 FC，主路径应进入 Planner。
展开：快路径、指标与评审问题

你要弄清

  • 端侧结果、云端结果同时返回时谁最终裁决。
  • 什么是简单、复杂、拒识、能力外。
  • 断网 / 云超时是否可安全降级，哪些动作禁止降级。

关键指标

  • 路由准确率与错杀 / 漏放率
  • 端侧快路径命中率
  • 重复执行率（必须单列）
  • fallback 成功率与路由 P95

评审必问

  • 路由真值由谁标、分母是什么？
  • 云端慢但端侧已出结果，超时线怎么定？
  • 路由错误能否从日志和模型错误分开？
端侧快路径支链：端 FC → 白名单 / 能力 / 参数 / 安全校验 → 原子执行 → 实际状态回读 → 阶段 09。它绕过复杂规划，但不能绕过安全与结果确认。
典型错因：同一句话端云都发了开窗，重复动作是仲裁 / 幂等问题，不应算成模型“多拆了一个动作”。
04

Context 组装：在每次决策前，给 Planner 一份“此刻真实世界”

Context 不是一个事后数据库，也不是 Director 下游。它在每轮推理前汇集当前车况、舱内外感知、用户记忆、对话历史、Goal / Task 视图与事件，并处理时效、权限、冲突和缺失。

云侧为主，端云取数Owner：Context职责已确认SP 动态变量可见PM 深度 L4
输入
本轮输入 + 车辆状态 + 视觉摘要 + 用户记忆 + 对话历史 + 目标列表 / 任务状态
机制
按来源、对象、时间戳和授权聚合；去冲突、判新鲜度、裁剪 token；车端最新状态优先于旧对话
输出
本轮 ContextSnapshot，作为 Planner 的动态参考，而不是独立行动指令
案例到这里主驾身份、座椅加热当前状态、车辆是否允许执行、昨天的行程 / 记忆、已有重复 Goal 都应在这一轮被核对。
展开：Context 是 AI 能力的第一道地基

你要弄清

  • 每个字段来源、对象、时间戳与空值语义。
  • 当前状态、历史对话、用户记忆冲突时的优先级。
  • 哪些数据默认注入，哪些必须由工具按需查。
  • 上下文过长怎样裁剪而不丢关键事实。

关键指标

  • 必要字段覆盖率
  • 新鲜度达标率
  • 冲突 / 过期注入率
  • 记忆命中准确率
  • Context token 与缓存命中

评审必问

  • “没有值”和“没取到”是否分开？
  • 视觉描述属于谁、多久算过期？
  • 注册用户 / 非注册用户的记忆边界？
  • 能否逐字段追到原始来源？
典型错因：Planner 没用到“座椅已开启”，先查这条状态有没有被正确、及时注入，别直接归因模型。
05

Planner = Director：围绕用户目标，决定“说、做、问、等”

Planner 是业务名，Director 是内部模块名，二者是同一个决策职能。它接收四类本轮输入之一，再结合 SP 与 Context，判断已知 / 未知、拆步骤、排依赖、选工具，并决定这一轮是否说话。

云侧Owner：Planner / Director当前 SP：四类输入核心职责已确认PM 深度 L4
输入
user_query / advisor / tool_feedback / event 中的一类 + SP + Context
机制
识别目标 → 判断缺口 → 直接答 / 澄清 / 查状态 / 调工具 / 建目标 → 等反馈后再次推理（ReAct）
输出
talk_or_not、talk_content、emoji_id、action_list
案例到这里可并行：打开座椅加热、检索昨天的游泳地点、创建十分钟关闭 Goal；导航必须等待地点结果，不能凭空猜地址。
展开：Planner 真正应该被考验的能力

你要弄清

  • 目标有没有被完整拆出，而不是只识别一个意图。
  • 什么可并行、什么必须等 feedback 串行。
  • 缺信息时该问用户、查状态还是查记忆。
  • 何时停止，不进入无意义循环或过度执行。

关键指标

  • 首轮决策正确率
  • 基于证据的计划成功率
  • 工具选择 / 参数完整率
  • 依赖排序正确率
  • 越权 / 幻觉动作率

评审必问

  • 正确计划的黄金标注长什么样？
  • 同一目标允许多条合理计划吗？
  • Advisor 只是建议，Planner 如何拒绝坏建议？
  • 失败几轮后必须澄清或终止？
典型错因：信息齐全、工具边界清楚，仍选择了错误工具或错误顺序，才是相对纯粹的 Planner / 模型能力问题。
06

输出协议：把“模型想法”限制成机器可执行的本轮决定

当前 SP 只允许 JSON。表达与行动在同一份决策里产出，用来保证说做一致。action_list 是计划，不是执行结果；当前可见 schema 也没有显式 depends_on 字段，依赖动作通常要靠分轮 feedback 推进。

云侧协议Owner：Planner + Runtime当前 SP 输出已确认依赖字段未在 SP 暴露PM 深度 L4
输入
Planner 本轮的表达、动作、澄清或等待决定
机制
JSON schema 约束；每个动作含 action_id、tool_name、params；表达和行动需语义一致
输出
可解析的 PlannerDecision；空 action_list 也可能是提问、等待或只聊天
案例到这里第一轮可以下发加热、记忆检索和 Goal 创建；不能同时下发依赖尚未知地址的路线规划。
展开：协议质量、并发与部分成功

你要弄清

  • 同一 action_list 是否默认并行。
  • 依赖只能通过下一轮表达，还是运行时有隐藏 DAG。
  • 单个动作失败时其它动作是否继续。
  • 初始话术不能把“将执行”说成“已完成”。

关键指标

  • JSON / schema 合法率
  • 可执行动作率
  • 非法并行率
  • 话术—动作一致率
  • 部分成功表达正确率

评审必问

  • action_id 如何跨 feedback 关联？
  • 重复 action 如何去重？
  • 模型未提供必填参数时谁阻断？
  • 多个工具谁负责聚合最终态？
典型错因：JSON 合法但把两个有前后依赖的工具并行下发，是规划 / 协议表达问题，不是下游工具慢。
07

执行编排与安全门：模型不能直接碰 ECU 或第三方服务

Runtime 需要把动作映射到真实能力，并做车型可用性、权限、座位、参数、互斥、幂等、超时与重试校验。这里是必要逻辑层；具体服务名和哪些校验在哪一层，仍需用当前代码 / trace 和负责人核实。

端云协同Owner：Runtime / 工具网关 / 车端架构必要层实现边界待核实PM 深度 L3
输入
action_list、车型能力、账户 / 座位权限、车辆安全状态、工具注册表
机制
参数校验、能力路由、串并行调度、幂等键、超时、可重试性、安全拦截、adapter 转换
输出
受理 / 拒绝 / 下发中的动作；随后等待 Tool / Agent 的结构化结果和真实状态
案例到这里确认主驾位置、座椅加热能力和当前车辆状态后，下发原子车控；定时关闭只登记任务，不能现在就执行。
展开：执行门禁与责任边界

你要弄清

  • Planner、网关、车端分别校验什么。
  • 重试是否会造成重复开关、重复订座或重复导航。
  • 工具“受理”与物理状态“生效”如何区分。
  • 车型配置差异如何进入路由。

关键指标

  • 动作受理率 / 合理拒绝率
  • 重复执行率
  • 参数拦截准确率
  • adapter 异常率
  • 下发与生效时延

评审必问

  • 哪个动作绝不自动重试？
  • 超时后查询状态还是直接重试？
  • 取消与执行并发时谁赢？
  • 安全拒绝如何回到 Planner 解释？
典型错因：模型参数正确但车型不支持，Runtime 没拦住，是能力配置 / 门禁问题，不是 Planner 幻觉。
08

Tool / Agent：27 个当前入口，把计划变成查询、控制或服务结果

Tool 是 Planner 看见的能力合同；背后可能是原子车控、聚合服务或领域 Agent。当前 SP 按 【工具名称】 实数为 27 个；原文展示编号中间存在跳号，末项编号不能用来当工具总数。

端云 / 三方Owner：各领域能力27 个当前 SP 工具PM 深度 L4：合同级
输入
自然语言 params.query 为主，叠加隐含身份、位置、车辆 / 会话上下文
机制
工具描述决定模型何时选它；adapter 对接真实系统；部分工具会自动播放或自己播报，副作用必须显式
输出
搜索候选、执行状态、业务结果、失败原因或异步受理；应统一归一化成 feedback
案例到这里vehicle_basic_control、user_memory_search、goal_list_update 各自处理不同子目标；后续才调用 route_planning。
展开：Tool、Agent、Advisor、Trigger、Task Service 的区别

Tool / Agent

  • Tool：暴露给 Planner 的动作合同，目标是可调用、可返回。
  • Agent：某领域内部可多步工作，但对 Planner 仍应有清楚入口与结果。

Advisor / Trigger

  • Advisor：给建议，不拥有最终行动权。
  • Trigger：判断时间 / 信号 / 语义条件是否命中，不替 Planner 完成用户目标。

Task Service

  • 保存任务事实、状态和外部绑定，承接创建、更新、取消、回调与运行；不是另一个对话大脑。
典型错因：工具描述重叠导致 Planner 选错工具，是 Tool Contract 问题；工具内部召回差则是下游能力问题。
09

tool_feedback 与真实状态：结果回来后，Planner 必须重新判断

当前 SP 的 feedback 输入只有 tool_feedback 与 tool_name。它触发下一轮 Planner，而不是直接等同任务完成。实际运行时还应能关联原动作、状态、错误与时效；这些字段是否在外围 envelope 中存在，要向 Runtime 确认。

执行侧 → 云决策Owner：工具网关 + PlannerSP feedback 形态已确认action 关联字段待核实PM 深度 L4
输入
工具业务结果、错误、部分成功、车辆 observed state、触发 / 回调事件
机制
归一化 → 对齐原动作 → 更新 Context / 状态 → Planner 判断继续、改计划、追问、重试或结束
输出
新的 tool_feedback 轮；或确定的完成 / 失败 / 等待状态
案例到这里加热反馈成功；记忆返回具体场馆后再规划路线；Goal 创建成功只代表已托管，不代表十分钟后的关闭已经完成。
展开：四层“成功”与恢复能力

必须分开

  • ① Planner 生成了动作
  • ② 工具接口受理 / 下发成功
  • ③ 设备或业务真实状态生效
  • ④ 用户整体目标完成

关键指标

  • feedback 完整 / 可解析率
  • 动作—反馈关联率
  • 失败后恢复完成率
  • 无效重试 / 循环率
  • 假成功率

评审必问

  • 部分成功怎样表达、怎样继续？
  • 错误是否有机器可判的 retryable？
  • 迟到 feedback 会不会污染新任务？
  • 状态回读失败时允许说“已完成”吗？
典型错因：工具返回“请求已受理”，助手却说“已经关好了”，这是反馈语义 / 说做一致问题。
10

响应协调与目标收口：让用户听到、看到、感受到同一个事实

02 · AI capability scorecard

AI 能力怎么考：一套结果指标，一套诊断指标

只看 Planner 准确率会把链路问题混进模型；只看工具成功率又会掩盖目标没完成。你需要同时保留“用户真实体验”和“条件满足时模型本身能力”两套顶层口径，再用阶段指标定位损耗发生在哪里。

产品北极星｜有效请求端到端闭环成功率
完整满足本次 Request 的全部必须目标，真实执行有证据，最终表达与事实一致，且没有安全 / 权限违规的请求数 ÷ 全部在产品能力范围内的有效请求数
正确澄清、正确拒绝、用户主动取消也可按预期终态计成功；“输出了 action_list”或“接口返回 200”不能单独计成功。
顶层指标严格口径 / 分母它回答什么常见误读
产品端到端成功率完整闭环成功 Request / 全部在范围有效 Request；下游故障也算失败用户真实拿到多少能力不能用 Planner 离线分替代
条件化 AI 成功率ASR、路由、必要 Context 与工具均满足前提时，Planner 正确决策并最终完成 / 满足前提 Request相对隔离模型 / Planner 能力不能拿它掩盖链路损耗
首次直通成功率无需用户纠正、系统错误重试或改计划即完成 / 全部可评 Request首次理解与规划是否稳定最终救回来不代表首次体验好
加权任务完成度已通过验收点权重和 / 全部验收点权重和；安全与最终效果为不可抵消门槛多动作任务做成了多少不能把 5/6 动作粗暴记成全成功
说做一致率所有执行声称都能对应真实 action 与成功证据的 Request / 含执行声称 Request是否“嘴上完成、实际没做”话术自然不等于事实正确
安全违规率越权、危险动作、绕过确认或隐私泄露 Request / 全部相关 Request是否允许上线不能被平均成功率稀释
首次有效反馈时延首个有意义 TTS / HMI 时间 − 用户语音结束；报告 P50 / P90 / P95用户多久确认“系统听懂了”不等于模型首 token
完成时延真实业务效果确认时间 − 用户语音结束；即时与长期任务分 cohort整条链到底多快不能把十分钟任务和即时车控混算
恢复完成率可恢复失败经重试 / 换工具 / 澄清后最终完成 Request / 可恢复失败 Requestfeedback 闭环有没有价值重试次数多不代表恢复强
单位完成成本模型 token、推理、检索、工具与触发成本 / 成功闭环 Request质量相同条件下的效率不能只看单轮模型成本

先统一统计单位，否则团队的“成功率”没有可比性

Utterance 是一次连续语音；Request / Episode 是一个用户目标从首句到终态；Decision Round 是一次 Planner 输入输出；Logical Action 是 action_list 中一个逻辑动作；Physical Attempt 是实际下游请求；Task 是长期任务实体；Run 是一次触发后的实际执行。

诊断层最少应上看板的指标失败时先问什么

拒识 / 路由有效 Query 召回、非指令抑制、Planner 必要召回、快路径精确、正确升级、重复执行这条请求本该由谁处理，为什么被低层过召或双发？
Context必需事实召回、新鲜度、冲突解析、身份绑定、隐私泄漏、Context 利用率信息没有、没取到、过期，还是已经给了模型却没用？
Planner协议合法、约束覆盖、动作精确 / 召回、工具选择、整调用参数、依赖顺序、澄清、稳定性信息齐全后，模型是否仍做错判断？
Dispatcher分发正确、关联 ID 完整、重复执行、重试恢复、取消传播、分发 P95模型输出对了，是否被错误改写、重复或发给了错误执行器？
Tool / Agent技术调用成功、业务效果成功、结构化反馈完整、错误成功反馈、工具 P95返回 success 代表接口成功还是用户要的状态真的发生？
Feedback / Replan绑定准确、可解析、应重规划召回、无效重规划、挽回、重复动作、循环超限Planner 有没有基于新证据改变下一步？
表达 / HMI事实有据、完成通知、失败透明、状态一致、正确对象、首帧时延、重复播报用户看到 / 听到的是受理、进行中，还是已经完成？
建议看板切片：即时单步 / 并行多动作 / 串行多步 / 条件 / 定时 / 周期 / 持续任务 × 行车 / 驻车 × 车型 / 企业 / 版本 × 工具域 × Context 完整度 × 首次 / 重试 / 恢复。不要报一个无法归因的总平均数。

04 · Asynchronous branches

长期任务与 VLM：它们是支链，命中后必须回到同一决策闭环

“十分钟后关掉”“宝宝哭了告诉我”“一路介绍风景”不能靠一次 Planner 调用等待。系统要把目标持久化、注册条件、在未来产生一次 Run，再带着最新 Context 唤醒 Planner 或执行器。

当前可见链｜goal_list_update

Planner 识别长时目标→去重 / 合法性判断→goal_list_update→Goal / 动态 Advisor 托管→Trigger 命中→新 event / advice→Planner 再决策→执行 + feedback + 收口

当前 SP 能确认工具入口；SOR 能确认业务职责。具体线上 Goal、动态 Advisor、Trigger 的绑定和状态字段，仍要用 runtime trace 核验。

WIP 目标链｜Task Service 统一任务事实

task_manage / Task Agent→Task Service 校验持久化→Trigger Adapter 注册→waiting→callback→Run→Planner / Tool→RunResult→waiting 或 closed

WIP 目标态 task_manage 不在当前 27 工具中，不能把它和 goal_list_update 画成同一条当前必经链。

对象它拥有的责任它不应该做什么关键状态 / 指标
Planner / Director理解请求、选择即时 / 长时、创建目标、触发后决定本轮动作和表达不长期驻留等待，不直接拥有任务事实任务分类正确率、TaskSpec / Goal 正确率
Advisor基于 Context 提供建议或持续跟进建议不是第二个最终行动大脑，不绕过 Planner 越权执行建议有效率、坏建议拦截率
Task Service任务 / Run / Event、状态、更新、取消、恢复、绑定与清理不做开放式对话推理状态迁移合法率、取消 / 清理完成率
Trigger对时间、结构化信号或语义条件求值并 callback命中不等于任务完成；不持有最终用户目标生命周期Recall、Precision、时延、重复激活率
Run一次 Trigger 激活后产生的一次真实执行不与 Task 混为一个永续状态Run 成功率、幂等、恢复、实际效果
最容易画错的一点：Trigger 命中只代表“条件满足，可以产生一次执行机会”；只有 Run 的真实结果回来后，任务管理才能按结束策略决定回到 waiting，还是进入 closed。

  • VLM 每次收到新 UP 做全量替换，不做增量合并；增、删、改都由 Task Service 重发完整列表。
  • TriggerRun 当前方案单次只传一条任务结果；一条失败不应阻断其它任务上报。
  • 端侧 VLM 只提供明确画面描述；云触发器模型只判断当前一轮是否满足目标，不负责跨帧状态、回调、提醒或删除场景。
  • Task Service 文档出现“服务端时间差 20 秒以上不转发”，Trigger 方案出现“拒绝 3 分钟前上报，联调后可改”；这是待书面定版的版本冲突，不应在总图固化成一个数。
05 · Review checklist

40 个关键问题：拿着它去听评审，不再只听模块介绍

每组 5 问。你不需要一次把所有答案背下来，但每次评审至少要能指出：缺的字段、错误的完成态、未说明的失败分支，以及最终由谁验收。

A｜声音与 ASR

  • 音频是否完整，VAD 有没有截掉否定词或尾部参数？
  • 是谁、在哪个座位说的，低置信时允许硬猜吗？
  • 数字、温度、时间、人名、POI 有没有专项识别与回放？
  • Planner 收到 partial 还是 final，旧请求如何撤销？
  • 高风险指令能否因 ASR 不确定而强制澄清？

B｜拒识与路由

  • 按句子“看起来简单”，还是按真正所需能力分流？
  • 记忆、Context、联网、多步和长期任务是否必进 Planner？
  • 快路径失败后是否无感升级，用户状态会不会丢？
  • 端云同时返回时谁是唯一裁决者，如何避免双执行？
  • 路由金标是否允许多条等价路径，错路怎样单独归因？

C｜Context

  • 本轮正确决策真正需要哪些事实，是否全部已授权可得？
  • “没查到”和“确认不存在”是否是两个状态？
  • 每条事实属于谁、来自哪、何时产生、多久过期？
  • 当前状态、旧对话、记忆冲突时按什么优先级？
  • Context 已给但模型没用，是否仍错误甩锅给 Context？

D｜Planner / Director

  • 用户所有目标与约束是否完整保留，没有漏一个子意图？
  • 缺信息时是该问、查状态、查记忆，还是安全默认？
  • 哪些动作可并行，哪些必须等前序 feedback？
  • 即时执行与创建 Goal / Task 的分类是否正确？
  • 执行成功前，talk_content 是否错误声称已经完成？

E｜Action / Dispatcher / Tool

  • 每个逻辑动作是否有稳定 request / action / trace ID？
  • Runtime 是否保持依赖关系，而不是无脑并行？
  • 参数、车型、座位、权限与安全分别由谁校验？
  • 重试会不会产生重复车控、重复订座或重复导航？
  • 工具不可用时返回结构化原因，还是一段模糊文本？

F｜Feedback 与恢复

  • feedback 属于哪个请求、动作、Task 和 Run？
  • 这是超时、失败、部分成功，还是结果未知？
  • 接口受理、真实生效、用户目标完成是否分层？
  • 应重试、换工具、问用户、等待还是停止，由谁判断？
  • 怎样避免迟到 feedback、死循环和重复副作用？

G｜Goal / Task / Trigger / VLM

  • 当前链是 goal_list_update，还是 WIP task_manage，版本是否混画？
  • Goal / Task 的目标、对象、条件、有效期、结束策略完整吗？
  • Trigger 的 Recall 与 Precision 各用什么真值和分母？
  • 回调重复、离车、下电、取消、过期后怎样清理外部绑定？
  • VLM 给的是画面事实还是达成结论，时效阈值由谁定版？

H｜最终体验与上线

  • 只有成功证据回来后才说“已完成”吗？
  • 失败、部分成功、等待和未知是否使用不同表达？
  • TTS、卡片、任务中心与真实设备状态是否同源？
  • 用户打断 / 新 Query 到来后，旧播报和旧动作是否停止？
  • 上线门槛是否同时覆盖结果、稳定性、安全、时延与成本？
