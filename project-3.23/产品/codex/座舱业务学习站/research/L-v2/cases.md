# L 章真实问题与设计场景

真实问题包含逐字稿中已经发生的缺陷、联调阻塞和实际评测偏差。涉及台架或项目联调时，用户现象以前端记录范围为准。设计验证均来自明确标注的提议、示例或跨源推导。

## 排查入口

| 症状 | 先查哪条证据 | 继续追到谁 |
| --- | --- | --- |
| 没触发、误触或反复触发 | 本车开关、规则版本、事件新旧值、标签及时间戳、命中和仲裁记录 | 规则业务、端状态与视觉输出 |
| 发了指令却没观测 | 同步送达、异步已启动/终态、AI Box 就绪和相机占用 | VLM SDK 调度和计算资源 |
| 端云判断不同 | 同一次输入、字段映射、单位、有效期及两端规则版本 | 信号接入与规则归属 |
| 开关显示与行为不符 | 本地持久化或云端读回，再查数据中心通知、触发门禁 | 车控 APP、云触发器或任务中心接入 |
| 卡片出来，车没动 | 实际展示、按钮/本地语音有效确认、当前任务和最新车况、执行回执和物理读回 | 原业务、即时卡和车控 |

定位后按证据归因。规则设计缺陷看门槛、变化语义、授权和重复出口，例如 S11、S23、S24。端侧资源限制看摄像头、AI Box 和任务抢占，例如 S04、S12、R15。模型输出不稳定用有真值的评测复现，例如 R02、R03、R18。软硬件时序冲突看盒子和软件启停、输入可用与卡片有效期，例如 S10、R16、S28。分类仅作排查入口，每例以各自的根因证据为准。

## 真实问题

### R01 早期 VLM 结果绕过端侧触发器

- **用户现象｜**未记录。
- **系统经过｜**已有推理结果直接给 AI Service，触发器不知道何时完成，无法续接、释放互斥或恢复 AlwaysOn。
- **根因｜**早期缺少给调用方的结果状态回调。

### R02 舱内评测把打哈欠说成惊讶

- **用户现象｜**一条离线评测样本中，模型描述主驾驶可能惊讶，未记录面向实车用户的提醒。
- **系统经过｜**乘员原有动作包含看书、打哈欠、揉脖子等，模型将张嘴和表情描述成惊讶或困倦，保真样例得 5.7 分。
- **根因｜**未记录；直接差异是神态／动作判断。
- **改法或验收｜**按视频标签核对实际动作，使用独立信息点评分，具体修复未记录。
- **来源｜**`feishu/【AICar】主线端侧VLM需求汇总.md` L350–426。

### R03 舱外城市道路评测漏掉两辆附近车

- **改法或验收｜**按画面真值核对车辆关键信息完整性，具体修复未记录。
- **来源｜**`feishu/【AICar】主线端侧VLM需求汇总.md` L675–751。

### R05 天气规则复评把已做逻辑当新增

- **系统经过｜**对方称连续次数可标定、多类标签先触发先推荐已经有，产品同学此前未收到同步，拟增加低于 60 km/h 和 P 挡限制。

### R07 替代信号拉出了卡片，正式天气联调仍待验证

- **用户现象｜**联调人员看到即时卡已出现，尚无同次正式天气＋任务中心开关的实车结果。
- **系统经过｜**前次以独立联调场景测通本地 Trigger 到即时交互卡，9-21 新增天气开关并需把正式任务连上。
- **根因｜**已验证的是后段和联调场景，用户侧开关及正式信号未包含在该次验证范围。
- **改法或验收｜**单测正式天气脚本和开关，还原任务中心→状态回读→真实视觉→卡后实车动作，尾段另看车况。

### R08 用户长时观察先获承诺，稍后因视觉能力未开通被拒

- **用户现象｜**要求每分钟看后排同学是否睡着，先听到会看，约 10 秒后又听到视觉识别不支持。
- **系统经过｜**当时调用 `goal_list_update`，创建被 Advisor 拒绝、后续列表没任务，未进车端摄像头调度。
- **根因｜**承诺早于能力与创建结果，具体哪项车型权限导致视觉不支持未记录。
- **改法或验收｜**研究排查按版本核创建前视觉开关与能力，待受理结果再确认，避免把创建失败排为相机故障。
- **来源｜**`research/v-lesson-20261107/raw/d6x-issues.txt` L55，见 `research/T-v2/cases.md` R030。

### R09 手动改车况后 Planner 仍看不到最新变化

- **用户现象｜**先用语音打开，随后手动关闭，再要求语音关闭，系统对当前情况的判断可能与用户所见不符。
- **系统经过｜**会议称部分 bug 来自 DT 没拿到手动变更后的端状态。
- **根因｜**会议指向状态没有进入 DT，具体丢在哪个环节未记录。
- **改法或验收｜**沿手动变更、端状态读取、时间戳、是否需要 event 及其输入核对，检查 Planner 用的是最新状态。
- **来源｜**feishu/文字记录：小范围聊一下任务中心和端侧触发器的链路实现_2026年9月22日.md 00:37:56–00:39:11。

### R10 技术评审时数据中心还不能订阅或查询所需状态

- **用户现象｜**未记录，属开发依赖。

- **根因｜**接口尚未开发，缓存数据范围也需按场景明确。

### R11 静置台架复现不了湿滑完整触发条件

- **用户现象｜**未记录，联调人员在静置台架无法跑通完整场景。
- **系统经过｜**天气规则需要车速和雨量，车辆停在原地且不下雨不能自然满足。
- **根因｜**联调环境缺少真实输入。
- **改法或验收｜**先用电量、空调风量等可控制信号及模拟卡片验证引擎，再回真实雨量、行驶和实车卡片做验收。

### R16 低照度下的舱内红外视频流拉不起来

- **用户现象｜**未记录，测试中舱内观察取不到红外视频流。
- **系统经过｜**AI Box 在光照值低于 18 时应把乘员监控摄像头从可见光切到红外，原车的 DVT 灌装版本拉不到正式红外视频端口。
- **根因｜**红外视频所用正式端口需求在 PVT 阶段才支持，DVT 版本端口限制挡住取流。
- **改法或验收｜**调试版临时借用已有端口，仅有条件通过，使用正式端口的发布版本仍须单独验证。
- **来源｜**`research/v-lesson-20261107/raw/test-weekly.txt` L106、L164–171。

### R17 AI Box 升级失败和灌装耗时过长

- **改法或验收｜**周会记载密钥问题已修复且升级测试成功，远程灌装继续排查并做重庆环境验证。

### R18 舱内常驻观察漏掉连续动作中的一部分

- **用户现象｜**未记录，模型评测发现定向动作和其他动作识别有退步。

- **根因｜**模型输出缺少部分动作，具体帧采样或模型成因未记录。
- **改法或验收｜**建议用同一任务的输入片段、实际结果和规则消费记录逐层定位，分别复测模型读到的动作和业务是否误提醒。
- **来源｜**`research/v-lesson-20261107/raw/test-weekly.txt` L106、L148–162。

### R20 两张信号表口径不齐，触发器配置难统一

- **用户现象｜**没有记具体实车提醒，集成评审中接入方发现触发器无法直接按表充分理解单位、信号的多组上报和参数联动。

- **改法或验收｜**当场答应给数值补单位、合并成一份表并逐项复核标识、关联关系，是否改信号 ID 仍要再评。

### R21 端侧持续视觉有输出，Planner 仍绕去调视觉问答

- **改法或验收｜**会议安排回捞实际视觉上报，车端试车，按当前上下文先找已有的有效信息，找不到再调 VQA，暂未记录复测结果。

## 设计场景与验收样例

### S01 充电口没有自动打开，触发器却以为模型跑了

- **用户现象｜**停车后充电口盖没打开。
- **系统经过｜**指令下发后 VLM 没跑，数据中心和云端都等不到识别结果。
- **根因｜**仅使用同步送达，缺模型实际回调。
- **改法或验收｜**等工作回调，失败或超时后重试一次，二次失败停止告警并释放资源。
- **来源｜**`feishu/端侧触发器_-_PRD.md` L185–260、L277–308；表格对照示例。

### S02 增强哨兵遇到有人靠车时先区分危险与普通靠近

- **用户现象｜**停车时有人或车贴近，真正风险才有相应的记录或告警。
- **系统经过｜**基础哨兵区分不同距离与振动／位置偏移，增强模型结合视频或振动区分真实剐蹭、砸车和普通靠近。
- **根因｜**误报风险来自视觉近距离接触与真实碰撞不易区分。
- **改法或验收｜**补震动信号及相似场景负样本。
- **来源｜**`feishu/【AICar】主线端侧VLM需求汇总.md` L768–842、L1004–1019、L1250–1256、L1666–1673。

### S03 开门方向有水坑、坑洞或挡门障碍

- **系统经过｜**可能停在本地词匹配、确认关联或未通过复核，也可能是车控已调用但车辆未到目标状态。
- **根因｜**未记录真实个案，此场景用于分辨交互完成与车控成功。
- **改法或验收｜**同一个卡片或命中编号逐段查实际展示、有效确认、业务复核、是否执行一次、执行回执与最新雾灯状态；播报和结果卡都按实车结果。
- **来源｜**feishu/PRD｜系统预设任务配置平台与端云交互框架.md L246–329；../E-v2/full.md  L298–339。

### S29 一次观察超时或暂时没包，业务误判已无风险

- **用户现象｜**仍可能存在恶劣路况，车机却错误地询问关掉保护模式。
- **系统经过｜**若把 timeout、抢占、空输出、过期包都折成“无标签”，退出计数就会吃进无效轮次。
- **根因｜**设计风险，运行状态与业务状态未区分。
- **改法或验收｜**分别注入相机占用、失败、有效空帧和无新包，核状态、资源释放和计数推进，只有符合专项定义的新鲜观察才进入退出计算。

### S30 同一变化同时走端日志与云日志，可能出现两条

- **用户现象｜**评审推演的风险是同一变化被后续模块当成两个事件，原话未给已发生的用户表现。
- **系统经过｜**一条路径从端状态到云触发器形成日志，另一条由端侧三方事件直接上云，后者绕过云触发器。
- **根因｜**生产责任重叠时仅云触发器一侧无法拦双源，统一需求表本身也不会消除技术双路径。
- **改法或验收｜**按事件类型、生产方、编号和回放身份约束；没有记录对应去重已上线。
