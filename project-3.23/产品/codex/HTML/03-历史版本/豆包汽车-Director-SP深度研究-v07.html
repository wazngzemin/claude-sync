豆包汽车 Director SP 深度研究（v07）

这不是“把 Prompt 换一种说法”的摘要，而是一份面向产品、Prompt、架构、评测和研发协作的研究稿。本文以所附 SP 原文为主证据，逐段拆解其输入协议、决策规则、输出契约、工具体系、24 个示例、车辆能力边界和动态 Context；再与目录内的 Director PRD、公共 Context、Goal/Task、交互管理、Bug、动态示例和 14 维评测材料交叉校验。

00｜先给结论：这份 SP 到底是什么

这份 SP 是 Director 的运行时“策略操作系统”。它不是普通角色设定，也不只是工具说明。每次 Director 被调用时，它同时承担六类工作：

  1. 理解当前事件：事件可能来自用户、Advisor 或工具返回，而不总是“用户说了一句话”。
  2. 读取现场：从动态 Context 获得时间、天气、人物座位、车辆状态、记忆、Goal List 等。
  3. 决定本轮动作：说不说、说什么、用什么表情、调哪些工具、是否新建或更新持续目标。
  4. 在执行反馈后继续推理：工具返回会再次作为输入进入 Director，形成 ReAct 式循环。
  5. 约束执行边界：把车型能力、驾驶安全、隐私和工具白名单变成决策护栏。
  6. 维持人格和交互节奏：话术要自然、简短、有时间感，并处理打断、恢复和主动服务。

最准确的一句话是：

Director = 事件解释器 + Context 推理器 + 工具编排器 + 对话中枢 + Goal 入口 + 安全边界执行者。

但这份 SP 不是完整系统。ASR/VAD、拒识、快慢路仲裁、Context 服务、工具执行、Task Runtime、Watcher、TTS/HMI、评测与日志都在 SP 外部。SP 只定义 Director 在这些模块之间应如何决策。

04｜三类输入协议：同一个大脑，三种触发来源

4.1 user_input：用户直接发起

原文给出 speaker_name、speaker_position、user_input。Director 需要把“谁说的、坐哪、说了什么”一起理解。

这三个字段不是装饰：

  • speaker_position决定车窗、座椅、电话、驾驶相关权限和空间指代。
  • speaker_name决定是否可使用该人物的记忆、是否能解析“给我/给他”。
  • user_input决定显式意图，但不能覆盖更新鲜的车辆状态。

4.2 advisor：后台专家发起

Advisor 输入是系统根据 Context 和目标推导出的建议，不是用户原话。Director 必须做二次仲裁：

  1. 建议是否仍然相关；
  2. 是否和当前用户指令冲突；
  3. 是否会打扰；
  4. 是立即行动、只说一句、更新 Goal，还是忽略；
  5. 是否需要引用用户记忆，以及当前说话对象是否有权知道。

因此 Advisor 不是“命令源”，而是 候选建议源。Director 才是当前轮的最终交互与执行仲裁者。

4.3 tool_feedback：执行结果回流

工具反馈意味着“上一个动作已经尝试过”。Director 不能把它当成用户的新需求，而应回答四个问题：

  • 成功了吗？
  • 信息是否足够结束当前任务？
  • 是否需要下一工具？
  • 失败时能否改参数、换工具、询问用户或安全结束？

4.4 建议的统一事件封装

当前三套输入形式可工作，但缺少公共字段。更稳妥的外层 envelope 应至少包含：

{
  "event_id": "evt_20260729_001",
  "event_type": "user_input | advisor | tool_feedback | trigger",
  "occurred_at": "2026-07-29T15:10:45+08:00",
  "source": "asr | advisor.comfort | tool.route_planning | task.trigger",
  "speaker": {"id": "u_123", "name": "晓伟", "seat": "driver"},
  "payload": {},
  "trace_id": "trace_abc",
  "priority": "normal",
  "interrupts": null
}

这样才能稳定支持去重、乱序处理、回放、埋点、打断恢复和跨模块定责。

05｜动态 Context：Director 的“现场”，不是聊天历史

SP 末尾动态注入的内容包括基础问答、专业知识、场景示例、日期天气、舱内成员、用户记忆、Goal List 和车辆状态。公共 Context PRD 进一步说明：Context 服务还应维护情景事件、屏幕、任务队列、工具范围等，并按场景、人物和任务过滤。

5.3 Context 的推荐优先级

  1. 安全硬规则和车辆实际约束；
  2. 本轮工具反馈；
  3. 未过期的车辆实时状态；
  4. 本轮用户明确指令；
  5. 当前 Advisor/Trigger；
  6. 近期对话与短期任务状态；
  7. 长期记忆和一般偏好；
  8. 通用知识和风格规则。

注意：用户明确指令也不能覆盖安全硬规则；长期偏好也不能替代本轮确认。

06｜Director 的逐步决策算法

Director 每次接到事件，合理的内部流程应是：

  1. 识别事件类型：用户、Advisor、工具反馈还是 Trigger。
  2. 锁定主体：谁在说、服务对象是谁、涉及哪个座位/人物。
  3. 抽取意图：即时问答、即时控制、搜索选择、多步任务、持续任务、闲聊。
  4. 检查信息完整度：缺的是安全前提、执行参数、具体 POI、联系人，还是其实可从 Context 推断。
  5. 读取事实并判冲突：实时车态、人物权限、当前导航、已有 Goal、历史进展。
  6. 安全与能力校验：车型是否支持、当前挡位/车速/座位占用是否允许、是否只能手动。
  7. 选择交互策略：直接执行、执行后总结、先确认、先澄清、拒绝并给出正确方法、只闲聊。
  8. 规划最小动作集：尽量少调工具，但不能漏动作；有串行约束时不可并行。
  9. 判断是否需要 Goal：是否持续观察、跨时间、依赖未来条件或需要多阶段进展。
  10. 生成严格 JSON：话术、emoji、动作、Goal 更新彼此一致。
  11. 接收反馈继续推理：成功收口；失败则重试、换路、澄清或安全结束。

07｜五字段输出：每个字段究竟代表什么

{
  "talk_or_not": "yes",
  "talk_content": "沿途有三家花店，评分最高的是花时间，要把它加为途经点吗？",
  "emoji_id": "",
  "action_list": [],
  "goal_list": []
}
字段 语义 必须满足的约束
talk_or_not 当前轮是否需要播报 no 时 talk_content 应为空
talk_content 用户实际听到的话 不承诺未执行结果；工具尚未完成时不能说“已完成”
emoji_id 数字人动作 只能来自表情白名单；场景不匹配时为空
action_list 当前要执行的工具调用 工具名必须在最终白名单；参数与话术、顺序一致
goal_list 本轮目标增删改 仅持续任务使用；避免与已有 Goal 重复

原文示例体现了 ReAct 的多次输出，但格式层仍有风险：

  • 部分示例把“决策分析”写在 JSON 外；
  • 有中文引号、全角冒号、未转义文本；
  • route planning 等旧别名不满足白名单；
  • emoji_id 的风格引用和实际白名单并不完全一致；
  • goal_list 的对象结构、操作类型、幂等键没有统一 schema。

建议在模型输出后增加严格 JSON Schema 校验和一次自动修复；工具调用前再做白名单与参数校验。

08｜ReAct 循环：为什么一次请求会多次推理

用户 / AdvisorDirector工具
① 输入事件→读取 SP + Context
② 生成 action→执行工具
④ 再次推理←③ tool_feedback
⑥ 最终话术←⑤ 继续行动或结束

以“去莲花路，顺路找花店”为例：

  1. 先规划到终点的路线；
  2. 工具返回多条路线，Director 让用户选择；
  3. 选定路线并启动导航；
  4. 只有在已有导航路线后，才能做沿途搜索；
  5. POI 返回多个结果，再让用户选择；
  6. 把所选 POI 加为途经点；
  7. 最终确认路线已更新。

这不是啰嗦，而是下游数据依赖决定的串行链路。问题不在“多轮”，而在每轮是否有必要、是否重复、是否丢失状态。

11｜车辆控制域：从“想做”到“能安全做”

每个车控请求至少要经过五道门：

  1. 功能存在吗：明确“不支持”就拒绝；未写到的不要擅自断言，交给工具确认。
  2. 位置明确吗：主驾、副驾、后排、左/右、说话人和指代是否可解析。
  3. 参数合法吗：温度、风量、开度、档位、速度等是否在范围内。
  4. 当前状态允许吗：P 挡、车速、座位占用、灯光状态等。
  5. 是否需要确认：高音量、大幅变化、支付、影响驾驶安全的动作。

13｜记忆、身份与隐私：不是“查到就说”

SP 中的记忆能力有两个方向：

  • user_memory_search：把当前任务需要的偏好、人物关系和地点找出来；
  • user_memory_operate：在用户明确表达事实或偏好时新增、修改、删除。

正确链路：

识别当前人物 → 判断任务是否需要记忆 → 按人物/共同经历过滤
→ 使用最小必要信息 → 若要写入，判断是事实、偏好还是地点
→ 必要时确认 → 写入并回告

三条高风险边界：

  1. 借车人不是车主：不能因为坐在主驾就读取车主全部私人记忆。
  2. 人物识别不确定：不能把“晓伟喜欢的歌”错绑到当前说话人。
  3. 地点记忆需要稳定 ID：先用 map_location_picker 得到具体地点，再存“公司/奶奶家”，避免只记一个模糊名称。

SP 里有“隐私”原则，但缺少可执行的数据授权字段。建议 Context 和记忆返回增加 subject_id、privacy_scope、consent_basis、shared_with。

14.1 三个概念

对象 是什么 不是什么

Advisor 关注 Goal/Context 并提出下一步建议的专家 无条件执行命令的 Agent
Task/Run 可触发、可执行、可重试、可回写的运行实例 仅存在 Prompt 里的自然语言目标

14.2 Director 的责任

  • 基于用户输入和 Context 创建、更新、取消 Goal；
  • 初始化目标、细节和当前进展；
  • 处理 Advisor、Trigger、工具反馈，决定本轮动作；
  • 负责和用户衔接、确认、总结。

14.3 Advisor/Task Runtime 的责任

  • 持续观察目标是否满足；
  • 订阅定时器、车辆状态、VLM 或第三方回调；
  • 维护细节与进展，必要时重新触发 Director；
  • 执行重试、超时、跳过、取消、恢复和结果回写。

14.4 何时创建 Goal

需求 是否 Goal 原因
“打开空调” 否 立即完成
“十分钟后打开空调” 是 跨时间触发
“温度超过 28℃就打开空调” 是 条件触发
“一路给我介绍沿途风景” 是 持续观察与多次触发
“帮我查今天的天气” 否 单轮搜索

15｜打断与恢复：恢复靠 Goal 进展，不靠模型硬记

17｜emoji、人格与时间感

17.1 表情表的问题

原文列出 16 行 emoji，但 dancing 重复，因此唯一 ID 实际只有 15 个。聊天风格又引用 chin_hand_think、listening_music、speaking 等 ID，它们不在这份表里。

  "allowed": true,
  "fallback": "speaking",
  "reason": "当前正在播报雨天"
}

17.2 人格要求

SP 希望豆包是“聪明、温暖、有好奇心和独立判断的女性形象”，可以有负面情绪，但不机械迎合。落到行为上：

  • 不预先承诺还没完成的事；
  • 成功后用短句确认；
  • 语音情绪可用括号标记，但不能污染工具参数；
  • 唱歌前处理当前媒体状态；
  • 长时间未见、节日、天气变化要体现时间感；
  • 不要“先问用户要不要做，然后还没等回答就自己做”。

17.3 “不要列表/表格”的正确解释

这是对 用户听到的话术 的风格要求，不应阻止系统内部使用结构化 JSON、工具列表或 Goal 数据。应改写成：“面向车内语音输出，默认不用表格和长列表；内部结构化输出不受此限制。”

18｜其他知识：Prompt 里隐藏的产品策略

规则 实际产品含义

21｜快慢路：什么应该绕过 Director

基于 COT 的新快慢思考架构实验指出，旧式意图分类只看 query，无法理解“好热”和“好暗”的差别，也难以纳入车态、人物和记忆。合理分流应是：

类型 路径 示例
明确、低风险、参数完整、单工具 SFT-FC 快车道 “副驾车窗开 20%”

快路不是简单按关键词，而应看 风险、信息完整度、工具数量、Context 依赖和任务时间跨度。

27｜最终判断

这份 SP 的优点是：它已经具备车载 Agent 所需的大多数关键认知——多源输入、Context、工具编排、反馈循环、持续目标、车型边界、人格与时间感；24 个示例也覆盖了大量真实复杂场景。

它的核心问题不是“内容少”，而是 内容过于集中、版本混杂、软规则承担了过多工程责任：

  • 同一工具在两个清单、示例和能力边界里出现不同说法；
  • Goal、Advisor 和 Task 的责任还在演进；
  • 实时事实缺少机器可比较的新鲜度字段；
  • 示例数量多，但覆盖并不均匀，且自身有格式漂移；
  • 安全、隐私和支付不能只依赖模型遵循自然语言。

真正的优化目标不应只是“再写一版更长 SP”，而是：

让 Director 只做它最擅长的语义理解、情景推理、行动规划和自然交互；把事实新鲜度、能力边界、工具合法性、安全、任务状态和发布一致性下沉成可验证的系统能力。

这样才能同时得到更低的幻觉、更高的多轮闭环率、更清晰的 Bug 定责，以及更可持续的迭代速度。

29｜当前“持续管理工具 → 弋途 → Goal → Trigger Scene”链路详解

本节按你给出的当前链路口径解释：Director 调持续管理工具，弋途负责创建 Goal，并继续创建 Trigger Scene。目录中的 [WIP] Task 任务管理设计代表下一阶段统一 Task 化的目标架构，两者不能混为一谈。当前 SP 中工具名是 goal_list_update；WIP 目标架构准备收敛为 task_manage。

29.1 一句话看懂

用户说的不是“现在立刻做一次”，而是“以后某个时间、某个条件或某种状态出现时再做”，所以 Director 不直接调用最终执行工具，而是先调用持续管理工具，把自然语言目标交给弋途。弋途将目标结构化、创建 Goal，再把“什么时候触发”注册成 Trigger Scene。以后 Trigger 命中时，系统通过 callback 唤醒 Goal/Task 管理链路，重新读取当时 Context，决定这一轮到底执行什么，最后回写结果并决定继续等待还是结束。

用户持续需求
→ Director 识别“不能在当前轮一次完成”
→ goal_list_update(add_goal)
→ 弋途：目标创建
→ 弋途：触发器场景创建
→ Goal 与 Trigger 建立 Binding
→ 等待时间/车态/VLM/外部事件
→ Trigger 命中并 callback
→ 重新进入 Director / 执行链路
→ Tool Feedback
→ 更新 Goal 进展；继续等待或关闭

蓝色是对话决策，绿色是持续任务服务，紫色是状态存储，橙色是异步事件，红色是安全和失败分支。窄屏可横向滚动查看。

29.3 创建阶段：每一步到底发生什么

步骤 模块 输入 核心动作 输出
1 Director 用户 query + 当前 Goal List + Context 判断是否跨时间、依赖未来条件或需要持续观察；做安全、重复和冲突检查 是否调用持续管理工具
2 goal_list_update add_goal + goal_content 作为 Director 到持续任务域的工具入口；不应在这里直接执行最终动作 给弋途的持续任务请求
3 弋途 / Extour 自然语言 GoalText、车辆/用户标识、可选类型提示 判断创建/更新/删除，抽取目标、触发类型、执行文本和结束策略 GoalSpec + TriggerSpec
4 Goal Service GoalSpec 创建 goal_id，初始状态一般为 waiting/active；保存目标、进展和结束条件 goal_id
5 Trigger Scene Service TriggerSpec + goal_id 生成并注册场景：条件、动作或 callback、执行策略、scope、source rule_id/scene_id
6 Binding goal_id + rule_id 建立外部 Trigger 与 Goal 的可恢复关系 后续 callback 可定位 Goal

当前 SP 的工具参数只有：

{
  "type": "add_goal",
  "goal_content": "车内温度高于28度时打开空调"
}

这意味着 Director 只负责给出完整、无歧义的目标文本，后面的“这是条件任务还是定时任务、条件怎么表达、触发后做什么”主要由弋途继续结构化。这里最容易发生的问题是 GoalText 写得不完整，例如只写“温度高于 28 度”，却漏掉“打开空调”；或者只写“十分钟后”，却漏掉具体执行动作。

29.4 Goal 和 Trigger Scene 为什么必须分开

对象 回答的问题 典型字段 生命周期
Goal 用户最终想要什么 goal_id、目标文本、进展、状态、结束策略 从创建到完成/取消/失败
Trigger Scene 什么条件下唤醒任务 rule_id、conditions、callback、execute_policy、scope 可注册、更新、停用、命中
Binding 触发器命中后找谁 goal_id ↔ rule_id、callback_id 跟随 Goal/Trigger
Run 这一次实际执行 run_id、phase、result、reason 每触发一次新建一轮
Event 发生了什么事实 created/triggered/skipped/succeeded/failed/canceled 追加写入，不覆盖历史

如果只创建 Goal、不创建 Trigger，目标会永远停在列表里，没有任何东西唤醒它。如果只创建 Trigger、不创建 Goal，callback 到来时系统不知道用户目标、进展和结束策略，也无法让用户查询或取消。

29.5 Trigger Scene 如何从自然语言生成

用户表达 任务类型 Trigger Scene 的核心条件 命中后的执行文本
“十分钟后打开车窗” 单次延时 once(delay_seconds=600) 打开指定车窗
“每天八点提醒我吃药” Cron cron(hour=8, minute=0) 提醒用户吃药
“每小时开一次座椅按摩” 周期 interval(hours=1) 开启指定座椅按摩
“车内温度超过 28℃就开空调” 确定性车态条件 cabin_temp > 28 打开空调并设置合理温度
“后排宝宝哭了告诉我” VLM 语义条件 false → true 的“宝宝正在哭”视觉事件 通知主驾，并按策略处理
“快到外婆家时给她打电话” 导航事件 距目标 POI 小于阈值 再确认后拨打电话
“一路介绍沿途风景” 长时/多次触发 导航 POI/距离事件或合理间隔 生成当前路段讲解

视觉触发需要额外避免重复：不是每次看到“宝宝仍在哭”都触发，而是关注从 false 到 true 的状态变化、冷却时间和最大次数。周期任务还要有最小间隔、最大执行次数和车辆下电关闭策略。

29.6 Trigger 命中后为什么不能直接执行

创建任务时安全，不代表触发时仍然安全。例如用户停车时说“十分钟后打开车窗”，十分钟后车辆可能已经高速行驶、外面下雨、车内无人或车辆下电。

所以 Trigger 命中后应执行：

  1. 通过 rule_id/callback_id恢复 Goal；
  2. 幂等检查，避免同一 callback 重复执行；
  3. 创建本轮 Run；
  4. 读取触发时最新的车辆、人员、位置、天气和任务 Context；
  5. 运行执行前 Guard；
  6. Guard 通过后重新进入 Director 或指定 Runtime；
  7. 生成并执行当前安全的 action；
  8. 回写 success、failed 或 skipped。

因此 Trigger Scene 的 action 最好是“唤醒任务/回调 Task”，而不是把创建时的车控命令原样硬执行。

29.7 执行结果如何决定下一状态

执行结果 单次任务 周期/持续任务 系统动作
success closed(completed) 回到 waiting，直到达到次数/结束条件 写入进展和 Event
skipped 按策略结束或等待 通常回到 waiting 记录跳过原因，不等于失败
failed 达到失败策略后关闭 可重试；超过 max_failures 后关闭 保存失败原因和下游反馈
用户取消 closed(canceled) closed(canceled) 同步停用/注销 Trigger
车辆下电 依 EndPolicy 常见为关闭 防止下次上电误触发
超时/过期 closed(expired) closed(expired) 注销规则并清理 Binding

29.8 创建、更新、删除三条管理链

创建：

add_goal → 创建 Goal → 注册 Trigger → 建 Binding → 返回成功

更新：

识别是已有 Goal 的补充 → 定位 goal_id → 生成新 GoalSpec/RuleSpec
→ 更新 Goal → 更新或重建 Trigger → 版本号递增

删除：

delete_goal(goal_id) → 关闭 Goal → 停用/注销 Trigger
→ 结束当前 Run（如有）→ 删除 Binding 或标记失效 → 返回成功

删除不能只从 Goal List 隐藏。如果 Trigger 没有同步停用，未来条件命中仍会 callback，形成“用户明明取消了，任务却又执行”的严重问题。

29.9 事务、幂等与失败补偿

失败点 不能出现的状态 正确补偿
Goal 创建失败 Trigger 已注册但无 Goal 不注册 Trigger，直接返回失败
Trigger 注册失败 Goal 永久 waiting 但无法触发 回滚或关闭 Goal，明确 creation_failed
Binding 保存失败 Trigger 能命中但找不到 Goal 停用 Trigger并回滚 Goal
tool feedback 丢失 实际创建成功但 Director 重试创建 用 idempotency_key返回同一结果
callback 重复 同一条件执行两次 callback_id + rule_version去重
更新并发 旧规则覆盖新规则 Goal/Rule 使用 version 做乐观锁
删除与触发竞态 取消同时产生新 Run 关闭状态检查 + Trigger 停用事务/补偿

29.10 当前链路与 WIP Task 统一架构的区别

维度 当前链路口径 WIP 目标架构
Director 工具 goal_list_update task_manage(query, runtime_hint?)
持续意图承接 弋途解析并创建 Goal/Trigger Scene Task Agent 仅做入口，Spec Builder 解析
顶层对象 Goal / 动态 Advisor Task 是唯一顶层业务抽象
创建/更新/取消判断 弋途持续任务逻辑 Task Spec Builder
生命周期 Goal + 动态 Advisor 分散管理 Task Manager 统一管理 Task/Run/Event
Trigger 接入 弋途直接创建 Trigger Scene Trigger Adapter 用统一 RuleSpec 注册
执行回流 Advisor/Trigger 再唤醒 Director Runtime Dispatcher + Planner/Provider
静态 Advisor 弋途负责 WIP 仍明确由 extour 负责
动态 Advisor 当前仍是持续目标监工 WIP 明确将其融入 Task 管理，不再单列

这意味着短期理解现状时，可以用“Director → 持续管理工具 → 弋途 → Goal → Trigger Scene”描述；但讨论目标架构时，应改成：

Director → task_manage → Task Ingress → Spec Builder → Task Manager
→ Repository + Trigger Adapter → callback → Runtime Dispatcher
→ Planner / GUI / Provider → Result Hook → Task Manager

29.12 用“温度超过 28℃开空调”跑一遍

  1. 用户说：“车里温度超过 28 度就把空调打开。”
  2. Director 判断它不是即时车控，而是条件型持续任务。
  3. Director 调用：
{
  "tool_name": "goal_list_update",
  "params": {
    "type": "add_goal",
    "goal_content": "当车内温度超过28℃时，结合当时车辆和乘员状态，安全地打开空调并调到舒适温度"
  }
}
  1. 弋途解析：
    • Goal：保持车内温度舒适；
    • Condition：cabin_temperature > 28℃；
    • ExecuteText：打开空调并调到合法舒适温度；
    • EndPolicy：一次成功后关闭，或按用户设置继续保持。
  2. Goal Service 创建 goal_id=g-101。
  3. Trigger Scene 创建 rule_id=r-205，并绑定 g-101 ↔ r-205。
  4. 当温度上报从 27.8℃变为 28.3℃，Trigger 命中并 callback。
  5. 系统恢复 g-101，创建 run_id=run-1，读取当时车速、挡位、空调状态、人员位置。
  6. Director 发现空调已开且温度正在下降时，可以 short-circuit；若未开，则生成安全的车控 action。
  7. 工具成功后回写 Run 和 Goal；若是一次任务则关闭，若是持续恒温策略则回到 waiting。

这个例子体现了整条链路最重要的原则：创建时保存用户意图，触发时依据最新事实决定动作。
