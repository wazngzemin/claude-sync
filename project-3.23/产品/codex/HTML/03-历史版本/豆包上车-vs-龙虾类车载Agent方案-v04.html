先用 5 分钟得到你真正需要的结论

这里不要求你懂模型、Harness 或 Agent OS。先把“谁在什么情况下更好”说清楚。

现在谁更适合 D6X？
我们。因为现有方案已经接入车辆状态、说话人/座位、记忆、目标队列和 27 个明确工具，并形成执行反馈闭环。原版 OpenClaw/Hermes 没有这些车载事实和权限，直接替换会退化。
我们的核心竞争力是什么？
不是“模型更大”或“工具更多”，而是高频指令走快路、复杂需求才推理；推理前知道车内发生了什么；执行时受车型能力约束；执行后能收到结果继续处理。
车载 Claw 强在哪里？
通用 OpenClaw 已经把 Skill、Background Task 和 Task Flow 做成运行时；车载 Claw 再把这些能力与车辆 Context、端侧模型、Trigger、Policy、车型兼容和 ECU 安全域连接起来。它的真正优势是把通用 Agent 工程转成可复用的整车平台。
我们现在最危险的短板？
能力仍较依赖一个大 SP 和显式规则。统一 Task/Run/Event 仍是 WIP，Skill Registry、签名沙箱、模块化策略和端侧复杂推理尚不完整。继续堆 Prompt，会越来越慢、越来越难维护。
要不要换成 OpenClaw？
不要原样替换。保留我们的车载快慢路、Context、车型工具和中心仲裁；吸收 Claw 的 Skill、Task、沙箱、版本治理与端云运行时。
价格谁更便宜？
公开信息不足以比较 OEM 总价。OpenClaw/Hermes 的 MIT 代码费是 0，但车企真正支付的是模型、芯片、适配、验证、认证、OTA 和运营。车载 Claw 与豆包上车的单车许可/NRE 均未公开。

正确的战略动作

不是二选一，而是升级。

把当前 Planner 量产闭环演进为受控的 Vehicle Harness。

判断一项能力是不是“竞争力”，用这个公式：竞争力 = 用户可感知收益 × 当前可用性 × 难复制程度 × 迭代速度。只有 PPT、PRD 或 Demo，没有量产可用性和结果指标时，它是“潜力”，还不是“当下竞争力”。
01 / PLAIN

先把所有黑话翻译成人话

你可以把整套系统想成“一家帮乘客办事的车内服务公司”。

Model
基础模型 = 聪明的大脑

Seed、Qwen、Claude 都属于“大脑”。大脑决定理解和推理上限，但它本身不知道这辆车有哪些按钮，也没有车辆权限。

Planner / Director
Planner = 车内总调度长

听懂用户到底想要什么，决定先查什么、后做什么、哪些动作可以并行，并统一对用户说话。Planner 与 Director 在本项目里是同一功能。

OpenClaw / Hermes
Claw = 通用办事操作台

它提供会话、工具循环、Skills、插件、记忆、定时和运行环境。像一个很能干的通用助理，但默认不是汽车员工。Hermes（不是 Hanes）也是这一类。

Tool / Skill
工具 = 工人；Skill = 工种说明书

“开空调”是一个具体工人；“雨天接孩子回家”可能是一套包含查天气、导航、空调和提醒的技能流程。

Context
Context = 车内实时白板

谁坐在哪、车里几度、有没有下雨、当前导航去哪、用户偏好什么。没有它，“我好热”只是一句模糊的话。

Task Runtime
Task = 不会丢的任务工单

记录任务是谁创建的、现在做到哪、在等什么、失败几次、是否取消。它解决“十分钟后”和跨多轮、跨上电周期的任务。

Trigger
Trigger = 闹钟和门铃

条件满足时叫醒系统，例如十分钟到了、胎压下降、副驾睡着、到达某地。Trigger 负责“什么时候叫醒”，不应该越权决定高风险动作。

Policy Engine
策略引擎 = 保安和钥匙管理员

判断谁有权控制什么、哪些操作必须确认、当前车速下能不能做、失败后是否可重试。车里不能只靠大模型“自觉”。

最容易犯的比较错误：把 Seed/Qwen 这类“脑”、OpenClaw/Hermes 这类“办事操作台”、KaKaClaw/AquaClaw 这类“汽车操作系统方案”、IM Ultra Agent/车载小艺这类“用户产品”放在一张表里直接打分。它们不是同一层。
ARCH 01

先把“架构”看懂：不是看有几个盒子，而是看六件事谁负责

如果只看“都有模型、工具、记忆”，三套方案会显得差不多。真正的架构差异，是一个需求进入系统后，谁接住、谁保存、谁决策、谁有权执行、失败后谁收尾。

01
入口怎么进？文本、语音、触摸、车辆信号、VLM 事件是否走同一入口？系统知道是谁、坐哪里、是否在驾驶吗？
02
上下文怎么装？模型看到的是聊天记录，还是带时间戳、来源、人物和新鲜度的车辆事实？无关信息由谁过滤？
03
谁做决定？所有需求都进一个大模型，还是简单指令走快路、复杂需求才让 Planner 推理？模型输出是建议还是最终命令？
04
任务怎么活下去？“十分钟后”“到公司时”“宝宝哭了提醒我”由聊天历史记住，还是有独立 Task、状态机、Trigger 和恢复机制？
05
工具怎么执行？工具只是一个 API，还是带车型能力、权限、前置条件、幂等、超时、补偿和执行回执的车辆能力？
06
安全谁兜底？模型说“不能做”算不算安全？沙箱能否阻止错误车控？最终是谁挡住高速开门、非主驾控制智驾等危险动作？

控制面

管理会话、队列、任务、版本、模型路由和运行状态。它决定“这件事由谁处理、现在跑到哪”。

数据面

搬运 Query、Context、工具参数、执行结果和任务状态。它决定“做决定时到底看到了什么事实”。

安全执行面

把模型提议变成受控动作，经过身份、车辆状态、风险和 ECU 网关校验。它决定“什么真的可以发生”。

读后面所有图时只记住一句：模型负责提出下一步，运行时负责把事情持续推进，车辆策略负责决定这一步能不能真的落到车上。把三种责任混在一个大 Prompt 里，短期快，长期一定难维护。

OpenClaw 更像“完整的个人 Agent 操作系统”

  • 长驻 Gateway 统一连接渠道、客户端与设备 Node。
  • 每个 Session 串行执行，避免工具和 transcript 竞争。
  • Skills、Plugins、MCP、模型 Provider 和 Harness 都可插拔。
  • 当前已有 Task ledger、Task Flow、Cron、审核与维护机制。
  • 但官方安全模型仍明确以“一个 Gateway 一个可信操作者边界”为前提。

Gateway Architecture · Agent Loop · Security

Hermes 更像“以 AIAgent 为中心的可扩展执行框架”

我们已经做对的架构选择

  • 高频简单任务不必穿过完整 Agent Loop。
  • 一个 Director 对用户最终表达与动作负责，避免多 Agent 抢话。
  • 车辆 Context 先进入决策，不把模型当盲人。
  • Tool feedback 重新进入决策，避免“嘴上完成”。

我们的核心结构债务

  • 大量工具规则、车型 Know-how、示例和安全约束仍压在大 SP。
  • Context 以文本块注入，字段来源、新鲜度和权限没有统一运行时契约。
  • Goal / Advisor / Trigger 与新 Task 方案处于迁移期。
  • 固定工具可控，但新增跨车型能力的生命周期不够标准。

绝对不能混淆的边界

  • Planner 与 Director 是同一功能，不是前后两个大脑。
  • Advisor 只提建议，不是执行者。
  • Trigger 负责叫醒，不应该替代 Director 与 Policy 做业务授权。
  • 长期 A2A 蓝图不等于当前已经有开放多 Agent 平台。

5 GATES

一条车控命令真正落地前，至少要过五道门

① 身份门

谁说、坐哪、账号是谁、是否主驾、儿童还是访客。

② 能力门

这台车、这个配置、当前软件版本到底支不支持。

③ 状态门

车速、挡位、占用、设备状态和信号是否新鲜。

④ 风险门

能直接做、需要确认、只能建议，还是必须拒绝。

⑤ 回执门

命令被接受不等于完成，必须读取最终实际状态。

最重要的安全结论：Prompt 里的“不允许”属于模型行为指导；Sandbox 属于计算机隔离；Vehicle Policy 与 ECU Gateway 才属于车辆动作授权。三者都需要，但不能互相冒充。

最终问题答案为什么产品动作
通用龙虾能不能直接上车？不能直接量产它有会话、任务、工具、Skill 和沙箱，但没有车辆入口、Context freshness、座位权限、车辆 Trigger、Policy 与 ECU 边界。只能作为 Runtime 参考或非车控生态 Agent 宿主。
车载 Claw 是不是完全不同架构？底层范式相似，外层责任完全不同仍有 Gateway、Agent Loop、Task、Skill、Tool，但每一层都被车辆身份、端侧部署、安全和生命周期重新定义。评审时必须追问 Vehicle Adapter 与 Policy，不接受只展示“大模型 + Skills”。
我们的架构是不是落后？不是整体落后，而是优势与债务错位我们在车载入口、Context、快路、工具语义、统一表达和真实车型闭环领先；在 Runtime、Skill 生命周期、统一 Task 和策略平台化上偏弱。不要推翻已有闭环；把 Prompt 中的工程责任逐步下沉为服务。
我们今天能讲的竞争力是什么？懂车、快、可控、能闭环同一句话能结合人、座位、车况和记忆；高频动作不必全进大模型；工具结果能重新驱动决策。用正确座位成功率、P95 时延、误操作率、闭环率和线上 badcase 修复速度证明。
未来最该补什么？Task + Skill + Policy 三件套Task 让事情不丢；Skill 让能力可复用升级；Policy 让开放生态不越权。三者一起才构成 Vehicle Harness。先完成 Task WIP 与 Vehicle Receipt，再做 Skill Registry，最后开放受控生态。

我们现在的五个硬优势

  1. 车辆 Context 已进入决策：不是普通聊天机器人套车机皮肤。
  2. 快慢漏斗：高频车控的时延、稳定性和成本结构更合理。
  3. 单一 Director：一个角色统一动作与话术，适合驾驶中的连续交互。
  4. 车型工具语义：已经包含座位、串并行、参数和能力边界。
  5. 真实问题闭环：有车型、接口、评测和 badcase 资产，知道问题发生在哪一层。

我们现在的五个结构短板

  1. 大 SP 承担太多运行时责任：规则、工具、示例和车型 Know-how 耦合。
  2. 统一 Task 尚未完成：Goal/Advisor/Trigger 与新 Task 处于迁移期。
  3. Skill 生命周期缺失：能力难以标准安装、签名、兼容、灰度和回滚。
  4. Policy 不够独立：安全规则分散在 Prompt、工具和下游，难统一审计。
  5. 端云 Runtime 未完全标准化：弱网持续任务、本地复杂推理和跨车型复用仍需建设。
如果要给老板一句话：我们当前不是输在“没有龙虾”，而是已经有一套很懂车的 Agent 产品链路，却还没有把这条链路完整沉淀成可复用、可持久化、可安全开放的 Vehicle Agent OS。最好的路不是换掉 Director，而是把 Director 外面的运行时补齐。

Director 生成 action_list，例如开启制冷、调整对应位置温度/风量，而不是只回复“好的”。
工具返回 tool_feedback 后，系统确认成功、失败或继续调整，避免“嘴上说已完成，车却没动”。

原版 OpenClaw / Hermes 默认缺车

只拿到一句文本，默认不知道谁说、坐哪里、车内几度、空调当前状态。
模型可以猜“开空调”，但猜对意图不等于有车辆控制权限。
必须额外开发车辆状态工具、座位身份、车型能力和执行回执；否则只能聊天或冒险调用。
其通用沙箱解决的是电脑文件/命令风险，不自动等于车速、车门、主副驾权限等车规策略。

车载 Claw 平台潜力强

Auto Omni、KaKaClaw、AquaClaw 均强调端侧感知、车辆状态和端云协同。
本地模型可在弱网下完成感知、判断和部分执行，理论时延更低。
Skill 沙箱和策略引擎在 LLM 之外做权限裁决，更适合开放生态。
但厂商发布能力不等于某一量产车型在这个具体场景已经达到稳定成功率。
产品判断：在 D6X 当前项目里，我们胜在已有真实车辆 Context 和执行链；车载 Claw 胜在未来可以把同一能力做得更端侧化、模块化。真正验收指标应是“正确位置控制成功率 + 首响/完成时延 + 误操作率”，不是回答听起来多聪明。
SCENE 02

定时任务：“十分钟后关掉座椅加热”

我们处在新旧链迁移期
用户：“十分钟后关掉座椅加热。”

豆包上车 懂车，但工单仍在升级

Director 识别为条件/定时目标，当前 SP 可调用 goal_list_update 创建持续目标。
目标队列会再次注入后续 Planner，让系统知道“还有一件没做完的事”。
到点后需要 Trigger 唤醒，再调用车辆控制，收到反馈后删除/关闭目标。
本地 Task 技术方案正在把旧 Goal 链升级为 Task / Run / Event / Binding，支持 waiting、running、closed、重试和恢复；文档明确标注 WIP。

OpenClaw / Hermes 通用任务骨架成熟

Hermes 可用 Cron 创建一次性或周期任务；OpenClaw 当前还有持久化 Background Task 与 Task Flow，可等待、取消、恢复、审计和区分执行/结果投递状态。
但“十分钟后”到来时，通用 Runtime 仍不知道车辆是否下电、座椅是否有人、加热是否仍开着，也没有副驾权限和车型能力。
要量产必须把通用 Task 接到车辆 Context、Trigger、Vehicle Policy、真实状态回读和车辆生命周期。

车载 Claw 目标形态更优

本地 Task/Skill Runtime 可在车端保存任务和条件，减少云端依赖。
触发时先读最新车况，再由策略引擎决定执行、跳过或要求确认。
若 Skill 有版本、权限和回滚，跨车型维护会比大 Prompt 规则更清晰。
产品判断：我们比通用 Claw 更懂“副驾座椅加热在这辆车上怎么安全执行”；OpenClaw 当前比我们的 Goal 链拥有更完整的通用 Task/Flow 骨架。我们的 WIP Task Service 必须把两者合起来：既有持久状态机，又有车辆 Trigger、Context 和执行回执。

跨记忆办事：“去昨天那个游泳馆”

当前结构可证

路线工具反馈后再播报并继续导航，避免搜索结果和导航对象错位。

OpenClaw / Hermes 能做，但需拼装

通用记忆和地图工具可以形成类似链路。
必须额外解决车内多人共乘时“这是谁的昨天”、人脸/账号绑定和隐私授权。
还要适配车机导航协议和 HMI；否则只是把地址查出来。

车载 Claw 能力趋同

长时记忆、用户画像和本地存储是多家官方重点。
优势取决于是否真的完成身份隔离、车机导航和服务闭环，而不是宣称“记性好”。
产品判断：这里没有“神奇模型壁垒”。我们的领先来自记忆、身份、POI、路线和车辆 HMI 已按汽车链路组织；可防守性取决于真实记忆命中率、错误人物率和导航成功率。

高潜力，不是当前量产事实
用户：“在前面穿红衣服的人旁边停。”

豆包上车资料 PRD + 评测资产

VLM 先识别人和相对位置，把自然语言目标转换为可追踪的视觉参照物。
Driver Agent 结合道路、可停车区域、智驾状态和安全边界判断是否能执行。

本地已有司机 Agent PRD、113 条统一评测集和 101 条评测 Query 体系；这些证明团队已经把问题拆细，不证明量产通过率。

OpenClaw / Hermes 不能直接进入智驾域

通用框架可以理解句子和调用视觉工具。
但没有车规视觉链、可行驶空间、智驾接管、制动和功能安全边界，不能直接做执行主体。

KaKaClaw 等 官方方向一致

iCAR 是首发合作车企，但官方页面尚不能证明这个具体视觉停车能力已在指定车型 SOP。
产品判断：这是未来最有价值、也最不能吹过头的一类。我们有很强的产品定义与评测资产，KaKaClaw 有芯片/OS 一体化优势；没有双方真实整车通过率前，不能宣布谁已经赢。

豆包上车 产品设计更深

语音前端识别音区、说话人、是否对助手说话，并维护主副驾/后排上下文。

通常围绕一个可信操作者和一条消息渠道工作。
OpenClaw 官方明确：单 Gateway 不是互不信任多用户的安全边界。
车内多人不是“多个聊天账号”那么简单，还涉及座位、驾驶员优先、儿童权限和声区输出。

车载 Claw 必须补同样的车载前端

端侧多模态和本地身份有利于低延迟分区处理。
但最终体验仍取决于麦克风阵列、VAD、音区、OEM 策略和车型硬件，不是 Agent Runtime 单独解决。
产品判断：这是我们最容易被低估的竞争资产：汽车里的“对话”不是一个聊天框。团队已把声学、座位、打断、权限和反馈拆成产品规则；下一步要用实车指标把 PRD 资产变成可证明优势。

明确车控可走句法 RAG/离线链路，不必每次上云。
离在线仲裁、离线 LLM、ASR/TTS 均有产品方案；复杂 Planner 主要在云端，弱网下能力会降级。
正确体验应是先完成本地可做动作，再明确告知哪些复杂步骤等待联网，而不是整车助手“失聪”。

可配置本地模型，也可只用云模型；框架本身不保证车载离线体验。
即使本地运行，也要解决车机算力、内存、功耗、启动时间和模型适配。

Auto Omni 宣称 90% 感知—决策—执行链端侧闭环；KaKaClaw 强调核心功能本地；AquaClaw 强调 edge LLM。
这类“端侧核心 + 云端重思考”比纯云端大 Prompt 更适合弱网和隐私场景。
产品判断：当前基础车控我们不吃亏；未来复杂任务的弱网连续性，车载 Claw 架构更占优。我们的目标不是把所有模型塞到车里，而是按风险、时延、成本决定哪一步在端、哪一步上云。

我们最明确的平台短板

定义新工具输入输出、补 Planner 工具说明和规则、补示例、接服务、跑回归、跟车型 HMI 联调。
资料里的 GUI Agent badcase 已证明：工具层次和参数不统一，会让 Planner 把验证码当闲聊、把进行中误报为已完成。
规则继续进大 SP 会增加注意力分散、缓存失效和回归成本。

新增 Skill、Plugin 或 MCP Server 即可快速让 Agent 看见能力。
适合 POC 和非安全域服务，但社区 Skill 不能未经签名、权限和供应链检查直接进量产车。

车载 Claw 未来标准形态

把服务封装成带版本、车型范围、权限、前置条件、成本和回滚策略的 Vehicle Skill。
在沙箱运行，经 OEM 签名和策略引擎准入；Planner 只看当前任务需要的 Skill。
这既保留扩展速度，也避免通用 Claw 的无限权限。
产品判断：今天我们“接得深”，但“不够快”；通用 Claw“接得快”，但“不够车规”；车载 Claw 试图同时解决两者。我们最该吸收的不是龙虾名字，而是 Vehicle Skill Registry + 签名沙箱 + 动态能力披露。

04 / CLAIMS

评审会上哪些话能说，哪些话现在不能说

把“资料明确、可由资料推导、资料未定义或版本冲突”分开，能保护产品判断的可信度。

可以直接说

“当前 Director 已经是一个车载 Agent Harness：能接用户、Advisor、工具反馈和事件，输出表达与行动清单。”
“当前 SP 明确列出 27 个工具，并注入成员位置、用户记忆、目标队列和车辆状态。”
“对当前 D6X，原版 OpenClaw/Hermes 不具备可直接替换的车载 Context、工具和安全边界。”
“我们的短期竞争力是车型闭环；车载 Claw 的长期优势是端侧运行时、Skill 生态和平台化。”
“最佳路线是保留当前量产闭环，补齐 Task、Skill、Policy、Sandbox，而不是推倒重来。”

现在不要说

“我们的 Task Runtime 已经完整上线。”——当前权威技术方案仍标注 WIP，现网主要还是 Goal 链。
“Driver Agent 已经量产，并且比 KaKaClaw 更好。”——本地有 PRD/评测集，没有对等量产结果。
“Auto Claw、KaKaClaw 都用了 OpenClaw。”——官方没有证明；AquaDrive AIOS 2.1 才明确披露基于 OpenClaw 架构。
“开源龙虾免费，所以整车成本更低。”——免费的是框架许可证，不是芯片、模型、适配、认证和运营。
“我们的准确率已经超过理想/华为/智己。”——本地材料多为目标、测试设计和 badcase，没有同口径实车横评结果。

资料明确

当前 SP 的输入输出、工具清单、Context 内容；Task 技术方案的 WIP 状态；PRD/评测集实际存在。

可由资料推导

在 D6X 上，保留现有车辆集成比替换通用 Claw 风险更低；大 SP 继续增长会影响可维护性与稳定性。

未定义或版本冲突

各模块准确上线范围、统一线上成功率、OEM 商务价、对手实际 Skill 数和指定车型端侧闭环比例。

近期
我们更好

面向 D6X 和近期车型量产：保留豆包上车当前路线更合理。它已经拥有车载快慢分流、权威车辆 Context、固定工具边界、tool_feedback 闭环和真实车型集成；通用 OpenClaw/Hermes 直接替换会丢失车规能力。

面向未来三年平台竞争：Auto Claw、KaKaClaw、AquaClaw 展现出的端侧运行、任务池、Skill 包、沙箱和可扩展生态，确实比“继续把规则和示例塞进一个大 SP”更可持续。

最佳解：快慢路 + Director 中心仲裁 + 车规 Skill Registry + Task/Run/Event + Trigger + 端云混合运行时 + LLM 外确定性策略引擎。

真正的相同点

两者都有“理解目标 → 规划 → 调工具 → 看结果 → 再规划”的 Agent 循环。我们的 Planner/Director 本质上已经是车载 Agent Harness，而不是传统 NLU 指令树。

真正的差异点

我们偏封闭域、中心仲裁、模型云端、工具固定；Claw 类偏技能化、运行时化、端侧化、生态开放。差异不在有没有大模型，而在能力如何装载、任务如何持久、权限如何治理。

当前最大误区

“开源免费”不等于“车载方案便宜”。MIT License 只免框架授权；车端硬件、OS 适配、车型接口、功能安全、网络安全、OTA、数据闭环才是整车成本主体。

  • Goal、动态 Advisor、Task Service 处在演进期，不能假定已经统一。

A4 / CLAW

它们把模型外的会话、上下文、工具、Skill、插件、持久化、定时任务、安全和可观测做成独立运行时，而不是全部写进 Prompt。

  • Prompt caching、compaction、tool-loop detection 已运行时化。

A6 / SCENARIO

同一真实需求跑完两套链路

场景：“明早 8 点如果下雨，提前开空调除雾，导航去公司，顺路帮我买杯冰美式。”它同时包含时间、条件、车控、导航、第三方服务、支付和跨会话恢复。

豆包上车：业务 Task + Trigger 驱动

Director 判断任务类型
不是当前轮能完成的一次 Action；拆出“明早 8 点”“如果下雨”“除雾”“导航”“下单”与授权缺口。
创建持续任务
当前链路调用持续管理入口；目标链创建 Goal + Trigger Scene。WIP 目标态写入 Task、Run 策略、结束条件和用户管理信息。
Trigger 持续监听
Timer 到 8 点；再获取天气事件/状态。未下雨则按策略 skipped 或询问是否仍导航，不直接执行除雾。
回调并读取最新 Context
重新读取车辆是否在线、挡位、车窗/空调、用户是否上车、公司地址、支付授权、当前天气与路况。
Director 再规划
可并行的除雾与天气确认并行；导航与沿途咖啡搜索按依赖串行；支付需要用户确认或预授权。
执行回执与任务收口
每个工具返回 tool_feedback；失败时重试/降级/询问。Task 记录 finished / partial / skipped，并可查询、修改、取消。
优势：车辆条件、任务状态和用户安全语义明确。
当前缺口：Task 统一化仍是 WIP；第三方下单/支付工具是否真实可用需车型项目确认。

通用 OpenClaw/Hermes：Automation + Task/Agent Loop 驱动

Agent 解析并创建 Automation / Flow
把 8 点写入 Automation，把天气、导航、咖啡步骤写入 Task Flow、Skill 或任务状态；Hermes 则主要用 Cron + 新 Agent Session。
到点恢复任务并创建 Agent Run
OpenClaw Task Flow 可持久化 waiting 状态并在重启后恢复；Hermes Cron 默认新鲜 Session。两者都必须显式保存公司地址、授权边界和工作步骤。
调用天气与服务插件
Web/API 工具判断天气，再调用导航、外卖/咖啡插件。通用框架不知道哪个工具是车辆安全域。
任务可靠不等于车辆 Trigger 完整
Automation/Task Flow 能表达“8 点”和 waiting，但不能天然表达挡位边沿、用户是否入座、信号 TTL、VLM 连续 K 帧去抖，需要 OEM 自建事件与 Context 层。
缺整车事务边界
“除雾成功但导航失败”“咖啡下单成功但用户没上车”的补偿策略，需在 Skill 和策略引擎里额外实现。
汽车版 Claw 的补丁
Aqua/KaKa/Auto Claw 正是通过 AIOS、车辆 ontology、Skill library、Policy/Sandbox 和端侧模型把这些缺口补齐。
优势：流程可快速 Skill 化，生态接入灵活。
风险：若只把通用 Agent 装上车，而没有车辆事件、权限和事务层，Demo 很快，量产很危险。
