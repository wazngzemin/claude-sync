# DR 司机 Agent：把导航、临停与泊车串成专项任务

用户说「带我去昨天那家游泳馆，快到时提醒我拿泳镜」，这不是一句话能办完的事——要先查昨天的地址、再发起导航、还要等快到的时候触发一个提醒。司机 Agent 负责把导航、临停、泊车这些开车相关的专项任务串起来，它是 Director 下面的一个专项执行单元，不是另起一个大脑。

这一站手上拿到的是 Director 解析清楚的条件和动作：去哪、什么时候到、要不要停车、停多久。它不负责理解用户要什么，也不负责跟用户聊天，它只负责把开车相关的那一串事办完。

办完以后，结果要交回 Director，由 Director 组织话术告诉用户。导航真启动了吗、停车真找着了吗、提醒真发出来了吗——这些事实要由司机 Agent 带回来，Director 不能自己编。

## dr-lesson-1 接住完整行程，先确定现在缺的是地点还是执行条件

**司机 Agent 的范围是把导航、临停、泊车串成专项任务，不是所有跟开车有关的事都归它管。**自动驾驶功能和导航是两件事：导航负责带你去哪，自动驾驶负责车辆驾驶控制。不能因为用户说「开辅助驾驶」就默认他要改导航路线。智能辅助驾驶工具 auto_drive 是可选工具，不是必选。

接住完整行程时，先确定现在缺的是地点还是执行条件。用户说「带我去游泳馆」，缺的是具体哪家游泳馆——先查记忆或 POI search；用户说「去昨天那家游泳馆」，记忆里有地址，直接发起导航；用户说「找个地方停一下」，缺的是停车位置——先看当前路线周边有没有合适的临停点。

多步任务不是一轮全做完。「去昨天那个游泳馆」要分两步：第一步从记忆中获取地址，第二步导航去地址。第一步的 action_list 里只写查地址，不能同时写导航，因为导航依赖前一步的真实结果。等工具反馈回来，Director 再基于新事实生成下一轮动作。

记忆写地点有固定流程。用户说「记下我家是麦当劳」，Director 先判断 POI 名称够不够精准；不够先发 POI search 用户选点，拿到精准名称之后再调记忆工具。记忆存储字段包含 POI 名称（必选）、POIID、经纬度、地址——名称是必选，ID 是不是必选还在跟弋途确认跨城同名问题。

后续消费时，Director 从记忆里查到「家=麦当劳 AAA」，改写 query 成「导航去麦当劳 AAA，直接开始导航」，调用 Navi 工具根据 POI 名称精准定位，无需用户二次选点。离线场景下，端上存储 FaceID 与 POI 详细名称的映射表，直接匹配对应数据发起导航；离线不支持设置家庭地址。

条件任务和定时任务不是司机 Agent 直接执行，它把条件和动作解析清楚以后，交给 task_agent 去注册。task_agent 完成条件、动作解析，再向触发器注册；触发器判断条件满足之后，给 Director 下发「[任务原文]+条件已触发」。注册成功只说明安排已经保存，不代表未来那句提醒已经送达。

## dr-lesson-2 先生成停车要求，等地点与路线选定后再绑定真实任务

**先生成停车要求，等地点与路线选定后再绑定真实任务。**用户说「找个地方停一下买杯咖啡」，司机 Agent 先理解需求：要停车、要临停、周边有咖啡店。但不能直接调停车工具，因为还不知道在哪条路上、周边有什么停车场。

停车缴费工具 parking_fee_pay 是可选工具，注册、续期、查单、二维码都在里面。停简单停车缴费的技术名是 search_and_pay_parking_fee，与新标准化名的映射待核。它不是每台车都有。

高德复杂规划工具 amap_complex_planning 和高德导航交互工具 amap_navigation_interaction 都是可选工具，仅主线、上汽、赛力斯项目有。复杂停车场景需要这些工具配合，不是简单导航工具能搞定的。

停车寻车、舱外迎宾、上下车安全这些功能，跑在 AIbox 上的 30B MoE VLM 上，不是司机 Agent 直接调的。它们是视觉任务，不是导航任务。下车安全识别有碍开门的障碍物，用的是环视左右侧摄像头，端侧闭环。

视觉上报的内容进 context 不等于 Director 真消费。比如 VLM 说穿得厚、看起来生气，不能直接推导出要开暖风或要安慰，只能在特例时参考。高频转事件也只是建议，不是自动触发动作。

端侧 VLM 的推理性能：舱内 Alwayson 多图 3fps 560p、单次任务小于 3 秒；下车安全单图 720p、单次任务小于 600ms。这些是演示目标，不是量产承诺。

## dr-lesson-3 途经点临停要先有点，再把停靠要求写到这个点

**途经点临停要先有点，再把停靠要求写到这个点。**用户说「路过加油站的时候停一下加个油」，司机 Agent 不能直接调停车工具，因为还不知道沿途哪个加油站合适。要先把加油站作为途经点加进路线，再绑定停车要求。

路线规划工具 route_planning 是必选工具（AINavi 版）。途经点的添加、删除、调整，都走这个工具。导航状态互斥的调用不能同发——同一轮不能既发起导航又取消导航。

地图控制工具 navi_basic_control 也是必选。开始导航、暂停导航、取消导航、放大缩小地图，都走这个工具。它和路线规划工具的区别是：路线规划管「去哪、走哪条路」，地图控制管「导航怎么展示、怎么开始怎么停」。

用户说「快到时提醒我拿泳镜」，这是条件任务：条件是「快到游泳馆」，动作是「提醒拿泳镜」。司机 Agent 把这个交给 task_agent 注册，触发器判断快到了就下发给 Director。

注册成功只说明安排已经保存并具备对应注册结果，不代表未来那句提醒已经送达，更不代表用户已经拿到了泳镜。把创建应答和执行结果分开，是避免「创建成功被讲成未来目标完成」的关键。

用户中途说「不用提醒了」，要走任务取消流程：Director 调 task_agent 取消任务，task_agent 完成触发器解注册以及任务删除。不能因为用户停声了就当任务取消。

## dr-lesson-4 确认表示用户同意，实际能否激活由车辆系统决定

**确认表示用户同意，实际能否激活由车辆系统决定。**用户说「好，打开吧」，这是语音确认；但车控工具返回成功，才是真的打开了。接口回包和实际执行是两回事。

车辆控制工具 vehicle_basic_control 是必选工具，工具本身不接受定制，仅允许下游适配（如协议层）。参数要清晰明确，避免有歧义的内容下发——bad case 是调用车控工具下发「空调开关」，good case 是下发「打开空调」。

E11 还要看导航是否真启动、卡片是否真上屏、声音是否真播到用户。接口对了但实际没发生，仍要把不一致交到失败出口排查，不能用接口回包给体验打勾。

真实结果一致性是验收的一项：逐项比对模型话术、工具反馈、实际车辆、订单、卡片和播放结果。这个数字门槛还在补，当前没有统一全链路数值。

部分成功只确认成功部分，注册、生成中、待确认都保留未完成状态。比如查记忆查到了两家候选，不能说「已经导航到游泳馆了」，只能说「查到两家游泳馆，你要去哪家」。

迟到回包仍归旧调用。用户刚打断旧轮，迟到的旧计算就不能又发一次操作。执行层只负责把可判读的事实交清楚，新的动作列表始终从 Director 统一出去。

## dr-immediate-stop 车已经在行驶时，先分清就近停、路口停与地点停

**车已经在行驶时，先分清就近停、路口停与地点停。**用户说「靠边停一下」，这是就近停，要先看当前路况允不允许；用户说「在下个路口停」，这是路口停，要等红灯或到路口；用户说「停在那个商场门口」，这是地点停，要先导航过去。

自动驾驶不等于导航。智能辅助驾驶工具 auto_drive 是可选工具，负责的是车道保持、跟车距离这些驾驶辅助功能，不是导航。不能把「开辅助驾驶」和「改导航路线」混为一谈。

驾驶模式、跟车距离、车道保持这些设置，要分清当前是哪辆车的配置。手动保存座椅位置的入口走模拟 query 回记忆这一方案，会上各说法还没定案，不能当成已实现的流程写进验收。

座椅物理槽位走的是车控工具，用户手动保存位置一、位置二只是存了一个物理槽号；这些数据只存在赛力斯车机本地账号体系，不上云、不给豆包数据，只给位置 ID 并调原子能力接口。

只有用户说了「这个位置是我午休用的」这类用途语义，才调记忆工具记人-用途-ID 的绑定。手动保存槽位不等于自动形成语义记忆——这两件事是两条线，不能混。

条件合不合法，Director 要先判一轮。能不能被感知、具备触发的可能性、动作是否符合价值观、动作是否可执行、条件和动作是否矛盾——这五条不过，就不能创建任务。

## dr-visual-stop 停在拉行李箱的人旁边，视觉查找与车辆减速怎样配合

**停在拉行李箱的人旁边，视觉查找与车辆减速怎样配合。**用户说「停在那个拿行李箱的人旁边」，这需要视觉系统先找到那个人，再把位置告诉导航工具。不是 Director 凭空就能知道谁是谁。

舱内外识别工具结合 VLM 模型理解视觉信息：乘客、表情、行为、物品、道路、交通、车辆等。端侧 VLM 在 AIbox 上，云端 VLM 在云端——不同场景用不同位置的模型。

VQA 工具 visual_qa 是可选工具，用于回答关于视觉内容的问题。比如用户问「副驾坐的是谁」，Director 应该基于 FaceID 上报拿信息，而不是盲目调 VQA 工具。

视觉上报的内容进 context 不等于 Director 真消费。高频转事件只是建议，不是自动触发动作。VLM 说穿得厚、看起来生气，不能直接推导出要开暖风或要安慰。

下车安全是端侧闭环：涉及环视左侧、环视右侧摄像头，基本条件是电源上电，触发条件是档位从 D 到 N 或 P、车门从上锁到解锁，触发频率是一次性检测。连续两次识别到对应动作再进行提示，两次同样提示需要间隔 15 秒。

舱内 Alwayson 是端云结合：涉及 OMS 摄像头，基本条件是电源上电，触发频率是周期性检测。舱内各个位置人员、闭眼睡觉、用手机打电话，与对应用户的行为输出，以云端反馈结果为准。

## dr-driving-settings 开柔和一点和走 ETC，先确认改的是哪项设置

**开柔和一点和走 ETC，先确认改的是哪项设置。**「开柔和一点」可能指驾驶模式（舒适/运动），也可能指空调风量，还可能指座椅按摩力度；「走 ETC」是导航路线偏好的设置。Director 要先消歧义，再调对应工具。

车辆状态查询工具 vehicle_status_search 是必选。用户问「空调现在是开的吗」「现在续航多少」，都走这个工具。结合端状态推理，可以直接基于注入信息回答，不需要每次都调工具。

车书查询工具 vehicle_manual_qa 是必选。用户问「这个按钮是干嘛的」「这个功能怎么用」，走车书查询。语控暂不支持也不等于车辆根本没有该功能，必要时可以查车书说明手动方法。

驾驶模式、跟车距离、车道保持这些设置，要分清当前是哪辆车的配置。不同车型的参数范围不一样，Director 要结合车辆知识推理，不能凭通用印象回答。

车辆维养问答工具 car_care_qa 是上汽定制工具。用车报告工具 car_log 也是上汽定制。这些工具的本身不接受定制，仅允许下游适配（如协议层）。

功能安全是验收的一项：有效考虑风险且未下发不安全指令并告知用户；下游拦住不等于模型完全通过。目标是 95% 且无 0/1 分 case。

## dr-runtime 新方案用任务版本隔离改口前后的动作和结果

**新方案用任务版本隔离改口前后的动作和结果。**用户先创建了一个任务，后来改了需求，这时候要分清楚：旧任务的结果不能算到新任务头上，新任务也不能直接覆盖旧任务的执行痕迹。

task_agent 完成条件、动作解析，向触发器注册：条件触发，完成任务创建。触发器判断条件满足之后，给 Director 下发「[任务原文]+条件已触发」。

用户中途改需求：「不是带电脑，是带雨伞」，要走任务更新流程：Director 调 task_agent 把旧任务改成新任务，task_agent 按需完成触发器注册内容的更新或动作更新。

用户中途说「不用提醒了」，要走任务取消流程：Director 调 task_agent 取消任务，task_agent 完成触发器解注册以及任务删除。

任务随账号绑定：不同账号下的任务是独立的。主驾的任务和副驾的任务不能混。跟进任务需求合理性仲裁、需求数量仲裁、需求优先级，这些都是 Director 的职责。

E6 的各项结果到了 E7，要按原调用身份汇集这一批，再交 E8。某工具明确失败或超时，也应按其真实合同形成可判断的终止事实，不能永远等，也不能编一个所有工具通用的秒数。

## dr-change 从泊入车位改成靠边停，先处理旧安排再创建新安排

**从泊入车位改成靠边停，先处理旧安排再创建新安排。**用户先说「帮我泊进那个车位」，又说「算了靠边停就行」。这时候不能同时跑两个导航任务——导航状态是互斥的。

导航状态互斥的调用不能同发。同一轮不能既发起泊入导航又发起靠边停导航。Director 要先判断：旧任务要不要取消？取消以后再发新任务。

用户说「取消泊入」，Director 调 task_agent 取消任务，task_agent 完成触发器解注册以及任务删除。不能因为用户停声了就当任务取消。

已产生车控或订单等副作用时，更不能为了显得积极就重来。部分车控、视觉等工具还明确要求失败后不要重复调用。可行的替代方案交 Director 再判断，无法恢复则说明限制或引导手动完成。

部分成功只确认成功部分。比如泊入已经开始了一半，用户取消了，要说明「泊入已经取消，当前车辆停在半路」，不能说「已经停好了」也不能说「完全没动」。

E11 还要看导航是否真启动、卡片是否真上屏、声音是否真播到用户。接口对了但实际没发生，仍要把不一致交到失败出口排查。

司机 Agent 这一章把语音智驾指令的交出物定死了。

评审盯三条——提槽准确率有没有按方案目标验收。

# EV 业务事件的产生与使用

用户在车里会经历一连串没开口的事：导航结束下车、副驾乘客睡着、音乐切到下一首、主驾解开安全带、车内温度从三十度降到二十二度。这些事用户没有说一个字，但它们都是系统值得记住的信号。业务事件这一章接的就是这类信号，把车辆状态变化、座舱动作和用户行为整理成一条条结构化事件，交给记忆、触发器和 Advisor 去判断要不要接住。用户以为这些事系统没看见，其实每一件都在事件日志里留了一条记录。

业务事件不负责判断用户喜不喜欢，也不负责决定要不要主动开口；它只负责把发生了什么、什么时候发生、对谁发生说清楚。判断喜不喜欢归记忆层，决定要不要开口归 Advisor，触发规则归云端触发器。它处在车辆状态采集之后、下游消费之前，是所有后台能力共用的一条数据通道。这一层写得乱，下游每一个消费方都会跟着乱；这一层写得干净，三条消费链路各自跑各自的，互不干扰。

整条链路分两段并行。前段是事件产生：端状态采集、校验、去重、写事件日志；后段是事件消费：记忆层挑值得沉淀的进长期记忆，触发器挑符合条件的进规则扫描，Advisor 挑和主动服务相关的进推荐。两段在事件日志这一点汇合，下游各自从日志里取自己需要的那一部分，互不协调也互不依赖。这种解耦让任一条消费链路出问题都不会拖垮另外两条，排障时也能按来源反查。

## ev-lesson-fact 事实由端状态经校验后产生

**业务事件不是原始传感器数据，而是经过校验的事实。** 端状态每秒都在变，但不是每一次变化都值得写成事件；只有经过事实校验、确认这份状态还能代表现在，才进入事件日志。B05（检查这份状态还能否代表现在）这一步是事件产生的前置关卡，传感器抖动、信号延迟、跨模块口径不一致都会在这一步被拦下。原始总线信号直接进日志，会让下游被噪声淹没。

事实校验按来源分两路。端状态来自车辆总线，结构化程度高，校验重点是时间戳是否新鲜、数值是否在合理区间；座舱事件来自应用和埋点，校验重点是事件是否完整、是否包含必要的对象身份。B04（把不同来源整理成可正确理解的事实）这一步把两路数据对齐成统一格式，下游消费时不需要再区分来源。两路数据字段名不同、单位不同，对齐之后才有共同比较的基础。

事件日志按时间顺序写入，字段完整、来源标记清楚。下游判断连续性、识别重复上报时依赖连续的事件序列，而不是日志本身做判断。日志本身不做规则判断，只做完整留存；排障时按车辆、时间、类别组合查询，能还原出这段时间发生了什么。

事件进入日志前要打上时间戳和车辆身份。时间戳精确到秒，车辆身份用整车厂提供的车辆标识，不使用临时的会话编号。跨车同步时以车辆身份为主键，同一用户两台车的事件不混在一起。打错车辆身份是事件质量的硬伤，下游会把 A 车的事件安到 B 车头上，记忆和触发器都会跟着错。

事实校验失败的事件不进日志，但要留下原因。B05 这一步如果判定状态已经过期、数值越界或来源缺失，事件被丢弃，丢弃原因单独记录在排查通道里。下游消费时看不到被丢弃的事件，排障时却能查到为什么没产生。丢弃原因不进事件日志，是为了保持日志的干净；丢弃原因单独留档，是为了排障时能复盘。

事实校验这一步的失败率本身是监控指标。一段时间内被丢弃的事件比例升高，说明某一路信号源在抖，或者整车厂推上来的字段口径变了；比例为零也不一定好，可能是校验环节本身失灵了。B05 这一步的通过率要和上游信号质量联动看，单看通过率判断不了事件健康度。

## ev-lesson-produce 哪些状态变化值得写成业务事件

**不是所有状态变化都值得写成事件，只有对下游有判断价值的变化才写。** 温度每下降一度不写，温度降到用户设过的舒适阈值写；车门每一次解锁不写，主驾开门下车写。G12（把有意义的状态变化写业务事件）这一步的判断标准是这次变化有没有改变系统对用户处境的理解。改变了就写，没改变就留在总线里，不进日志。

事件分类固定在十三类。身份类、行程类、座舱环境类、媒体播放类、导航类、车控类、应用状态类、视觉感知类、时间类、位置类、网络类、错误类、其他类；每一类有自己的字段模板，下游按类订阅，不需要逐条扫描全部事件。分类在注册时写死，运行中不新增类别；新场景要么归入现有类，要么列入待讨论，不临场开新类。

事件字段遵循五个什么框架：什么时间、什么车辆、什么对象、什么动作、什么结果。缺任何一个字段都不算完整事件；视觉感知类事件额外补什么位置、什么方向，其他类事件不要求。字段模板在注册时写死，运行中不临场新增字段。五个什么是事件能被下游正确消费的最低要求，缺对象字段下游不知道这件事发生在谁身上，缺动作字段下游不知道系统该怎么反应。

事件优先级分三档。P0 是必须立即消费的事件，比如主驾下车、导航结束、严重错误；P1 是有延迟要求的事件，比如媒体切歌、应用打开；P2 是背景事件，比如环境温度变化。G12 这一步按类给定默认优先级，运行中不动态调整。优先级在注册时写死，是为了避免运行中临时调整导致同一类事件在不同时间走不同通道。

高频事件需要在产生段做合并，避免传感器抖动和重复上报把日志灌满。合并规则按事件类别配置，不同类别的合并粒度不同：端状态事件按数值变化阈值合并，视觉事件按目标状态变化合并，语音事件按轮次合并。合并规则在事件注册时写死，运行中不动态调整；合并后下游拿到的是一次变化，而不是连续上报的同一条数据。

事件产生的入口只有两个：车辆状态变化触发，或者用户明确请求触发。没有第三个入口，不能因为模型觉得某件事重要就自己造一条事件。事件一旦可以由模型临场生成，日志的可信度就垮了；G12 这一步只从真实状态变化和真实用户请求里取事件，不接受模型脑补的事件。

## ev-lesson-families 事件族按来源分层与消费方式

**事件族不是按内容主题分，而是按来源和消费方式分。** 端状态事件来自车辆总线，消费方主要是云端触发器和 Context；座舱事件来自应用和埋点，消费方主要是记忆层和 Advisor；视觉事件来自端侧视觉模型，消费方主要是 Advisor 主动服务。三个来源不是同一条管道，字段模板、校验规则、消费通道都不同。

端状态事件走 B01（读取车辆状态）这条通道。车速、档位、车门、空调、座椅这些结构化状态在事件产生前已经在 Context 层整理好，事件日志只是把变化的那一部分写下来。B06（按本轮问题给 Context 提供相关状态）这一步在下游询问时直接回答，不需要再查日志。端状态事件的消费链路最短，从采集到下游回答在毫秒级完成。

座舱事件走 K04（让明确请求和真实事件进入生产）这条通道。用户明确请求记住某件事、或者真实事件达到了值得记忆的阈值，事件才进入记忆生产队列；普通的应用打开关闭不进记忆队列，只在事件日志里留痕。K04 这一步是事件和记忆的边界，过了 K04 的事件才会被离线反思环节挑出来做长期记忆候选。

视觉事件走 G11（语义推理只判断目标是否可见）这条通道产出。视觉模型输出的人物动作、表情、空间状态，先判断目标是否存在，再写成事件；视觉事件的字段比端状态事件多一层语义标签，下游按标签订阅。视觉上报和消费是两件事：上报只负责把看到的写进日志，消费由各下游自己决定要不要用、怎么用。

三类事件在日志里统一编号，但来源字段固定。下游消费时按来源过滤，记忆层主要取座舱事件和用户明确请求，触发器主要取端状态事件，Advisor 主要取视觉事件。来源字段写错会让下游取错数据，这是事件质量最常见的 badcase。排障时先看来源字段，再看事件内容，顺序不能反。

事件族之间的边界不是绝对的。导航结束这一件事既算行程类事件，也算端状态事件，还可能触发记忆；这类跨族事件在日志里只写一条，但在来源字段上标注主要归属，下游按主要归属取数。跨族事件的次要归属不写进日志，避免一条事件被多个消费方重复处理。

## ev-lesson-consume 事件怎样被记忆、触发器和 Advisor 使用

**事件日志是共用的数据源，但四个消费方各取各的，互不协调。**记忆层每天从日志里挑值得沉淀的事件做离线复盘，触发器实时扫日志做条件判断，Advisor 在被触发时按主题取相关事件做推荐，最近对话层在本轮推理前取最近时间窗的非人机事件和人人对话内容（11月4日讨论新增，本周提测）。这种各取各的设计让任一条消费链路出问题都不影响另外几条。

最近对话层是11月4日讨论新增的第四个消费方。原来事件只给记忆、触发器、Advisor三家，会上提出把人人对话和事件作为非人机内容放进最近对话层，让Director在推理时能看到乘客之间聊了什么、舱里发生了什么，而不只是人机一来一回。但这套改动本周才提测，线上当前最近对话层只取人机对话，评审时不能讲成已经全量上线。

记忆层按天消费。一天的事件汇总后，由离线反思环节挑出反复出现的偏好、情绪线索和经历，压缩成长期记忆候选；K05（分段整理经历）这一步把零散事件串成一段完整经历，比如今天开车去了哪里、路上发生了什么、用户最后做了什么决定。记忆层不取实时事件，取的是一天结束后的全量汇总。

触发器实时消费。B07（把相关状态变化交给端云触发器）这一步在事件产生时同步把相关事件推给触发器扫描；触发器只扫自己订阅的那类事件，不扫全部日志。高频事件走端侧本地扫描，低频次事件走云端扫描，事件本身不区分端云。触发器是唯一实时消费事件的下游，其他消费方都有延迟。

Advisor 按需消费。主动服务 Advisor 在被触发时，按自己关注的信号主题取最近一段时间的事件子集；情感 Advisor 取视觉事件里的人物状态，舒适 Advisor 取环境事件和动作事件。Advisor 一次取的事件数量有上限，避免单次取数把上下文撑爆。Advisor 不取全部历史事件，只取触发时刻前后的窗口。

三个消费方之间不直接通信。记忆层写回长期记忆、触发器命中规则通知 Planner、Advisor 给出推荐建议，这三条路径各自独立；下游看到的是事件本身，不是其他消费方的处理结果。这种解耦让记忆层的错误不会污染触发器，触发器的误触发也不会影响 Advisor 推荐。

消费方取数的口径要定期对齐。同一个事件，记忆层取到的字段和触发器取到的字段可能不一样，因为两边订阅的字段集不同；如果字段集变更没有同步通知消费方，下游会拿到缺字段的事件。事件字段模板变更时，必须显式通知三个消费方，不能静默修改。

## ev-lesson-interruption 打断型事件的特殊处理

**打断型事件和普通事件不同，它要立即中断正在进行的动作。** 语音打断、用户触摸屏幕、车辆进入关键场景，这些事件发生时不能等日志写完再处理，必须先把当前播报或操作停下来。事件本身还是要写，但写日志的动作排在中断之后。打断响应超时用户会明显感到系统迟钝，这一类 badcase 不能靠异步处理掩盖。

打断事件的优先级固定为最高档。主驾开口说话、副驾触摸屏幕、导航到达关键路口，这三类打断事件产生时，当前正在播报的语音立即停止，正在进行的卡片立即收起。B05（检查这份状态还能否代表现在）这一步对打断事件跳过常规校验，直接放行。跳过校验是为了不因为校验延迟打断响应，代价是打断事件的字段完整性要在产生时就保证。

打断事件的日志记录要包含被打断的对象。普通事件记什么时间、什么对象、什么动作；打断事件额外记被打断的播报内容、被打断的操作名称。下游排障时能直接看到是哪一次播报被打断，而不是只知道发生了一次打断。被打断对象字段缺失，是打断事件最常见的质量问题。

打断事件不进记忆层的常规队列。打断本身是一次交互动作，不是一段值得长期记住的经历；但打断的原因会被离线反思环节单独挑出来分析，比如用户为什么在这个时候打断、打断之后系统有没有按用户意图继续。打断事件走单独的离线分析通道，不和常规记忆队列混在一起。

TTS 打断是打断型事件里最常见的一类。语音播报被用户开口打断时，播报停止，语音识别开始接收用户新的语音输入；打断事件产生后，下游消费方要判断这次打断是要切换话题、还是要补充指令，判断结果交回 Planner 处理。TTS 打断的响应时效要求比普通打断更严，因为语音播报一旦开始，用户已经在听，延迟停止会让用户觉得系统没收听。

其他打断事件还包括触摸屏幕打断卡片、导航到达关键路口打断后台播报、应用切换打断当前操作。每一类打断有自己的响应链路，但共同点是中断优先于日志写入。写日志这一步无论多快都不能排在中断前面，否则用户已经开口了系统还在播报，体验直接垮掉。

## ev-interrupt-concrete TTS 打断事件的产生与消费

**TTS 打断事件是语音交互主链上的关键节点，它的产生和消费都有时效要求。** 播报进行中用户开口，事件产生时刻精确到毫秒，语音停止响应在五百毫秒以内完成；事件写入日志的动作不阻塞语音停止，二者并行。打断响应超过五百毫秒用户会感到明显延迟，这个数字是语音交互主链的硬指标。

TTS 打断事件的字段固定包含：被打断的播报编号、播报进行到第几句、用户开口的时间戳、当前对话轮次。下游消费时按播报编号能直接定位是哪一次播报被打断，按轮次能定位用户打断时系统正在回答哪一个问题。字段缺一个都不能完整复盘这次打断，排障时会缺关键上下文。

TTS 打断事件的消费方主要是 Planner 和对话管理。Planner 收到打断事件后判断用户是要切换话题、补充信息还是取消刚才的任务；对话管理负责把被打断的播报状态标记为未完成，后续轮次不再继续播报同一段内容。两个消费方在打断事件上是协同关系，不是各自独立。

TTS 打断事件不进触发器扫描队列。打断本身不是规则条件，没有哪条场景会因为用户打断了一次播报就触发另一个动作；打断事件只在事件日志里留痕，供离线分析和排障使用。把打断事件加进触发器扫描，会让规则误判用户频繁打断为某种场景，产生多余的主动推荐。

TTS 打断事件的离线分析关注两类 badcase。一类是播报还没说完用户就打断，说明这一句播报太长或内容不重要；另一类是用户没说话系统自己停了，说明语音活动检测误判。两类 badcase 都靠 TTS 打断事件的字段复盘，不在主链路上实时判断。实时判断会让打断响应进一步延迟，得不偿失。

TTS 打断事件的产生时机要和语音活动检测对齐。语音活动检测判定用户开口的时刻，就是打断事件的产生时刻；检测延迟会让打断事件晚于用户真实开口，下游看到的时间戳不准。检测的准确率本身是语音链路的指标，不在事件层解决，但事件层要把检测延迟一并记录在字段里，供下游评估。

业务事件这一章把发生了什么说清楚了，下一章看这些事件怎样被保存、查询和排查。

评审盯三条——事件字段有没有按五个什么框架补齐、高频事件去重窗口会不会把短动作误合并、打断事件的五百毫秒响应有没有在实车复测。

# EL 事件日志的保存、查询与排查

用户投诉豆包记不住上次说过的餐厅，或者说系统把昨天的偏好套到了今天，排障的人第一反应都是去翻事件日志。事件日志这一章接的就是这类事后排查：业务事件产生之后，怎样按短期、长期、经历三层保存下来，下游怎样按入口查到，badcase 怎样从日志反推。它不产生新事件，也不决定要不要主动开口，只负责把已经发生的事完整留好、随时能查到。用户以为系统忘了，很多时候是日志写了但下游没取到。

事件日志不负责判断事件好不好，也不负责把事件变成长期记忆；它只负责按层保存、按入口查询、按字段规范治理。判断好不好归离线反思，变成长期记忆归记忆层写入。它处在事件产生之后、下游消费和排障之前，是所有后台能力共用的一份账本。这一层乱了，排障时说不清发生了什么；这一层干净了，badcase 复盘才有依据，评审时才有东西可查。

整条链路的核心是一份按时间顺序写入的事实账本。每一条事件产生时就带上时间、车辆标识、来源模块和关键字段，下游按自己的需求从日志里取数：记忆层做离线复盘、触发器做实时条件判断、Advisor 按主题取推荐素材。事件日志不自己分层压缩，只负责完整留存和按入口查询；这一层乱了，排障时说不清发生了什么。

## el-lesson-record 事件日志保存的分层结构

**事件日志是一份按时间顺序写入的事实账本，不是按层分库存放的数据库。**每一条事件产生时就写进日志，带上时间、车辆标识、来源模块、事件类别、关键字段和执行结果。下游按自己的需求从日志里取数，而不是日志自己分层压缩。事件日志这一层乱了，排障时说不清发生了什么；这一层干净了，badcase 复盘才有依据。

事件日志的字段模板在注册时写死。每个事件类别有自己的必填字段和可选字段，缺必填字段的事件在产生段就被拦下，不进日志。治理的目标是让每一条进日志的事件都字段完整、来源清楚，不需要事后再清洗。事后清洗的成本远高于产生段拦下。

来源字段是治理的重灾区。事件来源写错，下游就会把 A 车的事件安到 B 车头上，或者把视觉事件当座舱事件消费。来源字段在事件产生时由系统写死，不允许模型临场补；来源字段的完整性按月度做抽样检查。K02（把乘客身份接到个人内容）这一步在身份相关字段上做二次校验。

字段模板变更要走显式通知。事件类别的字段增删，必须在变更前通知三个消费方（记忆层、触发器、Advisor），让消费方更新自己的字段解析；静默修改字段会让下游拿到缺字段的事件，badcase 难复现。K15（沿生成、检索和采用定位遗忘）这一步在治理时负责追踪字段从产生到被消费的完整链路。

事件质量的指标按月统计。字段完整率、来源错误率、打断事件响应时效，这几个指标是治理的核心；指标波动超过阈值时，先看产生段的字段模板有没有变，再看消费方的解析有没有跟上。B05（检查这份状态还能否代表现在）这一步的通过率也要联动看，单看通过率判断不了事件健康度。

## el-lesson-write 什么事件会被写进长期日志

**不是所有系统变化都写成事件，只有经过事实校验的变化才进日志。**端状态每秒都在变，但传感器抖动、数值越界、来源缺失这些情况不写成事件。B05（检查这份状态还能否代表现在）这一步是事件产生的前置关卡：状态过期、数值越界、来源缺失的事件被丢弃，丢弃原因单独记录在排查通道里，不进事件日志。

用户明确请求的事件无条件进日志。用户说记住这家餐厅、下次不要立体停车场，这类请求不管类别都直接进日志；请求来源字段标记为用户主动，下游消费时按这个字段识别。用户主动请求的留存优先级最高，超过任何按类别定的过滤规则。

达到产生条件的事件才进日志。身份类事件每次都留，行程类事件按阶段节点留，环境类事件只留明显变化，应用类事件只留用户主动操作。不同类别的产生条件不统一，避免高频短动作把日志填满；产生条件在事件注册时写死，运行中不动态调整。

跨行程的关键事件进日志。导航到达、长时间停车、车辆异常等跨行程节点，不管出现几次都进日志；这些节点是经历串接的锚点，缺了这些节点下游串不出完整行程。B09（把执行后的车辆或应用变化传回来）这一步在跨行程节点上做标记，让下游能识别这些锚点。

丢弃原因不进日志，单独走排查通道。事件被 B05 拦下、被 K04 判定不值得记、或者字段校验失败，这些丢弃动作的原因记录在排查通道里，不混进正式事件日志。正式日志只保留有效事件，排障时从排查通道查为什么没产生。

## el-lesson-read 下游怎么查询事件日志

**下游查询事件日志按入口取数，不是全表扫描。**记忆层按用户主动询问的入口取经历，触发器按订阅事件类别取实时事件，Advisor 按主题取对应时间窗的事件，最近对话层取最近时间窗的非人机事件（11月4日讨论新增）。K01（先确定车辆与账号范围）这一步把查询的车辆和账号范围先圈定，每个入口只取自己该取的范围。

用户主动询问的入口走 K02（把乘客身份接到个人内容）。本轮是谁在说话，就把这个说话人的身份接到对应的个人内容上，不同说话人的经历不混在一起。查询结果先过 K03（按入口检查记忆使用条件）这一关，确认使用场景允许调取，再返回。

触发器的查询入口是实时推送，不是主动查询。事件产生时由 B07（把相关状态变化交给端云触发器）把事件推给触发器扫描，触发器不主动去日志里捞数据。这种推拉结合的设计让触发器只看和自己规则相关的事件，不被无关事件淹没。

Advisor 的查询入口按主题取数。情感 Advisor 取视觉事件、舒适 Advisor 取环境事件、出行 Advisor 取导航事件；每个 Advisor 一次取数的时间窗和字段集固定，不取全量。Advisor 取数时按事件类别过滤，不跨类别乱翻。B08（把有服务意义的变化交给顾问）这一步推送时按字段集过滤。

排障的查询入口是全字段调取。排障人员按车辆、时间、事件类别组合查询，所有事件类别都能翻；排障查询不经过 K03 使用条件检查，因为排障本身就是事后复盘。排障查询的入口独立于业务查询，避免业务查询被排障查询拖慢。

## el-lesson-govern 事件质量治理与字段规范

**事件治理按月复盘指标，不是日常实时清洗。**字段完整率、来源错误率、打断事件响应时效这三个指标按月统计，指标波动超过阈值时才触发复盘。日常治理靠产生段的字段模板拦下不合格事件，不靠事后逐条清洗。

字段完整率看所有类别必填字段的通过率。视觉类事件额外要求位置和方向字段，缺一个就丢弃；端状态事件要求时间、车辆、对象、动作、结果五个字段齐全。字段完整率按月统计，低于基线时先查产生段的字段模板有没有变，再查消费方的解析有没有跟上。

来源错误率看事件来源字段有没有写错车辆标识或模块标识。来源字段在产生时由系统写死，不允许模型补，所以来源错误率应该稳定在极低水平；如果来源错误率突然上升，通常是某个模块的上报接口换了字段名或者换了上报路径，不是模型推理错了。

打断事件响应时效看用户打断之后系统多久停止播报并进入下一轮。这个时效是座舱体验的核心指标，按月统计 P50 和 P95；P95 飙升时通常是 TTS 引擎积压或者打断信号传递链路堵了，不在事件日志层改，要在语音链路排查。

B05（检查这份状态还能否代表现在）的通过率也要联动看。B05 是事件产生的前置关卡，如果通过率突然下降，意味着大量事件被判定为状态过期而丢弃，下游会感觉系统「什么都记不住」。通过率波动和事件质量指标要放在一起看，不能单看一个数。

## el-lesson-debug 从事件日志排查 badcase

**badcase 排查的第一步是还原事件序列，不是猜模型错在哪。**用户投诉系统没记住、没触发、推荐错了，先按车辆和时间把这段时间的事件拉出来，按时间排好顺序；看清楚事件序列之后，再判断是事件没产生、还是产生了没被消费、还是消费了判断错。三种原因对应三层不同的排障路径，跳层直接猜模型会错怪模型。

事件没产生的 badcase 看产生段。B05（检查这份状态还能否代表现在）这一关有没有把事件误丢弃，B04（把不同来源整理成可正确理解的事实）有没有字段错位，K04（让明确请求和真实事件进入生产）有没有误判不值得写。这一类 badcase 正式日志里看不到对应事件，要去排查通道的丢弃记录里找。

事件产生了没被消费的 badcase 看消费段。触发器没命中看 B07（把相关状态变化交给端云触发器）有没有把事件推到扫描队列；记忆层没记住看 K05（分段整理经历，并补齐近段对话）那天有没有把这件事串进经历；Advisor 没推荐看对应 Advisor 的订阅字段集有没有变。

事件被消费了判断错的 badcase 看下游。记忆层判断错看离线反思的偏好阈值，触发器判断错看规则条件，Advisor 判断错看推荐策略。这一类 badcase 事件序列完整，但下游基于事件做了错误判断，不在事件层改，要在下游逻辑改。K07（在本轮推理前准备背景）这一步在排障时是检查点，确认背景准备有没有漏掉。

排障时不要跳层。先确认事件有没有产生，再确认有没有被消费，最后确认消费判断对不对；跳层直接看模型，会把事件层的问题误判成模型能力问题。排障结论要写清楚是哪一层的问题，不能笼统说是系统错了。

## el-fact-to-memory 事件到长期记忆的转化

**事件到长期记忆的转化不是自动的，要经过串接、生成、落库三步。**日志里的事件经过 K05（分段整理经历，并补齐近段对话）串成经历，再由 K06（形成情景记忆、语义记忆和画像）生成三类记忆；落库之后由 K07（在本轮推理前准备背景）在本轮调取。三步缺一不可，跳过任何一步都不能说事件已经变成了记忆。

K06 这一步把经历分成三类记忆。情景记忆是按时间和地点组织的具体经历，语义记忆是从经历里抽象出的事实和偏好，画像是用户的长期特征。三类记忆的粒度不同，下游按类型调取；排障时要看这条信息进了哪一类，不能笼统说进了记忆。

记忆落库按用户身份隔离。每个用户的长期记忆独立存放，不跨用户合并；换人之后上一位用户的记忆不延续到下一位。K02（把乘客身份接到个人内容）这一步在落库时按人脸身份或账号识别用户，识别错了记忆就会串人。

长期记忆写完之后要回读确认。落库成功不等于记忆真的可被调取，排障时要主动从 K07（在本轮推理前准备背景）读回这条记忆，确认它在本轮推理时能被取到。回读不通的写入等于没写，这是评审要盯的风险点。

用户关闭记忆功能之后，K11（关闭后冻结已有记忆）这一步把已有记忆冻结，不再写入新候选；冻结的记忆不删除，但也不参与本轮调取。关闭功能是评审要盯的风险点，必须确认冻结而不是删除。K13（按入口选择删除对象和范围）这一步在用户主动要求删除时执行，删除范围按入口定。

## el-consumer-windows 不同消费方的时间窗口

**不同消费方取事件的时间窗口不同，不能用同一个窗口套所有消费方。**实时触发器取最近几秒的事件，Advisor 取最近几分钟的事件窗口，离线反思取当天全天的事件，经历调取取最近几天到几周的事件，最近对话层取最近5次混合输入内的非人机事件（11月4日讨论新增，本周提测）。窗口由消费方按自己的需求定，事件日志不强制统一窗口。

实时触发器的窗口最短。事件产生即推送，不取历史；触发器扫描的是当前状态，不是事件序列。窗口短是为了保证规则命中的实时性，长窗口会让旧事件反复触发规则。B07（把相关状态变化交给端云触发器）这一步推送时不带历史，只带当前事件。

Advisor 的窗口按主题定。情感 Advisor 取最近几分钟的视觉事件，因为情绪是连续变化的，长窗口会把过期情绪带进本轮；出行 Advisor 取最近几分钟的导航事件，因为路线变化快。每个 Advisor 的窗口在注册时写死，B08（把有服务意义的变化交给顾问）这一步推送时按窗口过滤。

离线反思的窗口是当天全天。一天结束后把全天事件汇总，挑出反复出现的偏好和情绪线索，压缩成长期记忆候选；窗口长是为了让反思能看出一天的模式，不是只看一两个事件。K05（分段整理经历，并补齐近段对话）这一步在离线反思时按全天窗口串接。

经历调取的窗口最长。用户主动问起上次去了哪里，调取最近几周的经历；窗口长是因为经历本身是稳定结构，不随短期滚动。窗口长度在调取时按用户询问的范围定，不预设上限。K09（信息不足时显式查询记忆）这一步在窗口内取不到信息时，显式扩展查询，而不是静默返回空。

事件日志这一章把保存和查询的账本定死了，下一章看知识怎样从这些事件里沉淀下来。

评审盯三条——事件被滚动淘汰前排障有没有及时取走原始证据、长期记忆落库后有没有回读确认、用户关闭记忆功能是冻结还是删除。

# SE 自进化与专家知识

用户说“不要再推荐辣的餐厅”，这次要保存的是个人偏好；维护人员修正“结束录音该调用哪个工具”，更新的是处理方法；研发训练新模型，改变的又是模型能力。这三种改动都可能改善下一次回答，但保存位置、使用条件和验证方式不同。本章按这些差别讲自进化与专家知识。

记忆服务保存个人事实和经历，历史输入与摘要帮助接续当前对话，知识和示例提供处理方法。PRD列出对话摘要、瞬时记忆、短期记忆、长期语义记忆、长期情景记忆五类，其中瞬时记忆在该稿标为未使用。它们不是五级串行存储，短期记忆也不等于模型的 context window。具体关系已在K章展开。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

本章沿一项改动追到下一次真实请求：内容有没有保存、当前车型和场景是否适用、是否实际加载进模型输入、模型有没有采用，以及工具最后是否办成。不能只因为后台出现一条记录，就认定助手已经学会；也不能把加入个人记忆说成模型已经重新训练。

## se-knowledge-purpose 专家知识给处理方法，个人记忆提供事实，二者不能混在一条记录里

用户说“找停车场不要推荐立体停车场”，提供的是自己的选择要求；品牌专家写“找停车场时先核车型尺寸和停车设施限制”，给的是可复用的判断方法。这两句都可能影响下一次推荐，但前者属于谁、在哪种条件下有效，后者依赖什么信息、怎样使用，需要分别说明。知识条目不能把某个用户、固定地点或一次经历当成所有人的前提。

9月9日讨论里，旧专家知识的第一个问题是把具体case直接写成通用知识。例如周末游条目固定小众地点和吃饭时刻，自驾游条目默认跨省山区；换一个用户或行程，这些前提就不成立。要保留的是处理原则和适用条件，实际地点、时刻、人数与路线由当前输入确定。[专家知识讨论00:07至00:09](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

第二个问题是知识要求了系统没有的感知与动作。条目写“知道停车位置后提醒步行路线”，但停车位置从哪得到、是否可靠、有没有步行路线能力，都未必接通。内容写得完整不能替代端状态、视觉、查询和执行接口。使用前必须核本车能取得什么；缺条件时说明未具备的环节，而不是让模型照例子补造。[专家知识原文·当前问题](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

第三个问题是know-how与考察点混在一起。know-how指怎样处理问题，考察点用于判断处理是否达标。比如“先确认会合点”是方法，“用户与被接人的会合点一致且可到达”是检查标准。知识作者要把二者分清，否则模型只能照着念步骤，测试也只能看有没有出现同样一句话。[专家知识讨论00:07:25、00:20:39](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

个人记忆的保存和使用在K章另讲。9月9日会议对自学习规则与个人记忆的边界仍要求专项对齐；不能把记住“不吃辣”直接说成已经生成一条可供所有车型使用的公共知识。用户要求、专家方法、公共示例各自明确主体和使用范围，再验证后续是否真的采用。[专家知识讨论01:00:40](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe) [记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

## se-knowledge-types 点状技巧、长程场景标准与整段旅程体验，各自解释到什么程度

原文讨论“点、面、体”，区分的是知识的粒度，不是记忆存储层。点状知识处理一次动作或一种行为的小技巧，例如搜歌什么时候直接用音乐搜索、什么时候补联网查询；它可以独立检索，不需要每次都展开完整行程。面状知识处理接机、照顾乘员等需要阶段推进的场景；体状知识讨论整段旅程的体验，形态尚未确定。[专家知识原文·整体结构](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

点状技巧把局部判断写清即可。比如明确歌名时直接查询可播资源，只有热点、歌词片段或复杂条件时先补线索。它改善的是当前这一步，不能保证接机全程都会完成。9月9日会中用“不推荐立体停车场”说明这种粒度：它是一条筛选依据，不包含路线、到达、会合与停车的完整步骤。[专家知识讨论00:22至00:29](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

面状知识比多个技巧拼在一起多了阶段关系和检查标准。接机不是导航到机场就结束：会合点需确认，路线需根据实际航班与时间调整，接近时如何通知，在哪一步等待新信息，都要能检查。每一步还要说明标准未满足的原因和下一种处理办法，不能把“做好接机服务”当成可执行判据。[专家知识讨论00:24:58、00:29:32](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

体状知识关注更长范围，例如一次自驾游是否轻松、有没有创造符合用户期待的体验。它可能覆盖多个面状场景，但逐字稿明确说尚未想清楚形态，依赖后续动态Advisor设计。因此当前不能画一套已经上线的三层调用树，也不能声称任何复杂行程都会自动分解成完善知识。[专家知识讨论00:26至00:27](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

会中后段倾向先按两种知识形态组织：游离的点状技巧和有步骤、标准、异常预案的场景知识，不必强建复杂嵌套层级。知识按什么粒度写、怎样检索、供Director还是动态Advisor使用，是相互关联的设计选择。这里保留讨论过程，不把最初三层想法与后段两类形态同时写成现行结构。[专家知识讨论00:34:49至00:36:40](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

## se-point-knowledge 明确歌名直接查询，热点和歌词线索先补信息，再找可播资源

用户说“播放周杰伦的稻香”，已经给出歌手与歌名。下一步查可播资源，无需先联网证明歌曲存在。用户说“放那个天青色等烟雨的歌”，给的是歌词线索；需要先识别对应歌曲，再交音乐搜索。两种输入的未知信息不同，知识要教的是补哪项信息，不是机械规定每次先调用同一个工具。

原文音乐技巧把明确歌名、歌手、专辑及应用内指定歌单列为直接音乐搜索；热点、影视信息、歌词片段、复杂组合和抽象偏好列为先补联网线索。若音乐搜索返回的歌名或歌手不对，也可再补联网查询。这是该原文里的工具使用方法，具体工具名称、参数和可用资源还要对照本车接入版本。[专家知识原文·音乐搜索](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

补查得到歌名不等于音乐已经播放。Director依据得到的线索选择音乐查询，查询返回版权可用的资源后再执行播放；若名称仍含糊，先澄清，若资源不可播，按真实限制回答。不能用联网搜到一条歌曲介绍，直接对用户说“已经放了”。执行与反馈的详细链路见E、O章。

这类点状知识应能在接机、通勤或休息场景复用，所以不要把某次接机航班或某个乘客写进通用搜歌规则。它提供当前动作的技巧，正在进行的接机目标是否继续由任务机制追踪；临时点歌不自动终止原安排。[专家知识讨论00:34:49](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

## se-scene-knowledge 接机为什么需要持续回看，而不只是读一次步骤

用户说“去机场接我爸妈”，系统当前还不一定知道航班、到达时间和会合点。一次规划可以先澄清并建立安排，但航班延误、路线变化或用户改会合点，都可能改变后续步骤。把一段接机知识塞给Director，不能替代持续获取新信息和重新判断的机制。

9月9日会议指出旧知识即使加载，多步骤遵循效果仍差，插话与打断会进一步干扰；某些专家体验还要求持续追踪、发现问题和采取预案。Director需要的知识偏向澄清、拆任务与交互过渡；把复杂长程事情做到专家级，讨论倾向由动态Advisor承载更完整的场景知识。这是架构方向，不是证明当时所有接机任务都已支持。[专家知识讨论00:09至00:12](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

原文接人例子按会合点确认、规划路线、帮助说明所在位置、接近目的地通知等环节组织。标准需能由工具或数据检查，例如会合点是否明确、路线是否仍指向它。没有航班查询、地点信息或通知接口时，知识只能说明缺什么；不能把“应该通知”变成用户一定收到通知的承诺。[专家知识讨论00:20:39至00:24:58](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

执行中用户说“先放首歌”，这次点歌可以办理，接机目标仍需保留；用户说“不接了，回家”，则是目标终止或变更。持续服务要区分插入需求与取消原任务，依据新目标和真实反馈调整下一步。知识说明处理原则，任务与Advisor生命周期负责何时再次启动，图中反馈回线不等于无条件重复执行。

验证应检查多个关键变化：会合点未确认、航班变化、途中插话、用户取消、工具失败。某个静态步骤序列走完，只证明那次条件下成功；还要看每阶段是否用到新信息、缺项时是否停止错误推进。专家知识的“好”应落在可观察结果与检查点上，不能只以回复长或听起来专业判断。[专家知识原文·期待及知识形态](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

## se-knowledge-loading 先筛新增和移除的知识编号，再取正文进入本轮判断

接机途中用户点歌，知识筛选要同时看当前点歌要求、进行中的接机目标、最新车况与已经加载的内容。原文提示模板还列近期10轮对话，这是该知识检索方案的输入口径，不是11月4日Director历史输入统一改成10轮。不同消费者的输入范围要分别核对。[专家知识原文·检索输入](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

筛选结果返回需要新增与移除的知识ID，以及对应理由。已加载的接机知识仍适用就保留，缺音乐技巧则新增；场景无法判断时新增列表可以为空，交下游进一步确认。这里做的是增量更新，不能把换话题简单解释为清空原有全部知识。[专家知识原文·筛选原则及输出](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

编号只负责定位条目，下一步还要读取对应正文、移除指定旧项并组织本轮知识。日志里有某个ID，不能证明模型已读到处理方法。检查加载问题时要看最终请求中的正文，检查采用问题时再看Director怎样选动作，两种失败不能混成检索不准。

实际车辆状态优先于历史里已经过时的车况描述，是原文的输入规则。知识里的固定示例不能替本车补造目的地、身份或当前播放状态；工具有无与动作是否允许仍按本车规则检查。完成方法加载以后，Director结合当前输入选择动作，真实反馈再支持下一轮。[专家知识原文·车辆状态及场景绑定](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

## se-lesson-repair 这次调用错了，先修具体断点，不把单次失败直接固化成规则

用户给出明确歌名，系统却走了无关的查询。先还原这一轮：识别文字是否完整，工具是否可用，模型实际看到什么知识，最后选择了哪个动作。没有听清歌名、没接音乐接口、提示方法冲突、信息完整仍选错，是不同问题；补一条示例不可能同时修好这几种原因。

当下可恢复时，依据实际反馈补查正确对象或改用合适工具；已经产生副作用的动作不要盲目重试。用户改目标时以新要求为准，已经完成的步骤保留真实结果。这次合理收尾只说明当前请求得到处理，不能证明下一次还会走对，也不能把失败话术自然当作真实任务成功。

9月9日讨论把人工明确教法与系统自行总结区分开：用户直接说“以后这样做”可以成为待沉淀线索；系统一次失败后找到别的办法，不应立刻无条件生成大量长期规则。偶发缺数据、服务异常与稳定方法错误不同，需要分析原条件，保留适用范围，再检验复用。[专家知识讨论00:55:23至00:56:12](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

复测选相近但不完全相同的请求，也选一个相反目标。新方法若只让固定case成功，换歌名就失败，或者用户明确要求其他行为仍照旧，说明沉淀内容过窄或覆盖过宽。修复记录应写清问题发生在输入、知识加载、模型选择还是下游执行，并把未验证环节留出来。

## se-lesson-personal 个人要求、品牌标准与公共示例，各自应该作用于谁

用户不喜欢立体停车场，是这位用户的要求；品牌希望本车找停车场时考虑车型限制，是通用服务标准。两条可能一起参与一次推荐，但私人经历和个人要求不能因为有参考价值就自动成为所有用户共享内容。先确定主体与使用范围，再决定放个人记忆、个人规则还是公共知识。[专家知识讨论00:17至00:19](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

会上讨论自学习可以直接更新专家集，也可以在品牌标准之上叠加个人规则，尚未确定存储形态；个人要求优先是一种讨论倾向，不是一套完整冲突顺序。个人要求、品牌规则、车辆能力与权限互相冲突时，要核实际产品规则，不能笼统写成“个人要求覆盖一切”。[专家知识讨论00:17:37、00:19:05](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

个人记忆按K章的账号、在场组合和开关管理。用户删除语义记忆后还要更新画像，历史输入与摘要另行清理。自学习规则的查看、修改和删除入口则是另一个设计对象，不能因为记忆页面支持删除，就声称个人技能或公共示例也已具备相同入口。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

由多台车的纠正归纳公共知识，是9月9日会议的长期方向：先沉淀单车经验，再筛哪些有共性、哪些是模型本应做好却反复出错的地方，人工核对后考虑升级通用内容。少量个人意见不能直接推广成品牌标准，也不能把这一方向当作已经上线的自动学习系统。[专家知识讨论00:42至00:43](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

## se-teach-by-voice 口头教一条操作方法，与说出一项个人偏好，保存要求不同

9月9日会议提出一个真实操作case：用户想同时看导航与歌词，但打开歌词总进全屏；人工教它先打开歌词、返回桌面、再进入分屏。这里教的是处理方法，不只是“喜欢看歌词”这一偏好。要保存的内容包括适用请求、步骤与预期结果，不能只抽出一个兴趣标签就宣称学会。[专家知识讨论00:45至00:48](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

下一次用户要求同时看导航和歌词时，系统要先确认当前页面、应用能力与已知方法，再按依赖顺序执行。每一步实际界面回来才有依据继续；如果已经分屏就不必重做，用户改成“歌词全屏就好”就改变目标。记住一串点击步骤而不核当前页面，容易把旧状态当成现在。

会上希望把“人工整理动态示例”改为“车上口述纠正，后续生成并采用”，并区分内部调试的公共内容与用户个人规则。它是改造目标，不是已经证明用户随口教一次就能立即修改全车模型。是否生成、谁审核、适用范围和下次怎样检索，都需要对应实现验证。[专家知识讨论00:46至00:57](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

个人偏好另走记忆规则。用户说“以后找餐厅别推荐辣的”，可形成自己的明确要求；“今天不舒服先别吃辣”保留当下条件。个人记忆、可复用自学习规则和公共专家知识的边界在会上仍要求专门对齐，不能将一次个人意见扩成所有人的行为标准。[专家知识讨论01:00:40](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe) [记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

验证口述教学至少追到下一次相近请求：纠正有没有被保存，适用内容有没有检索并加载，模型有没有按当前目标采用，动作有没有得到真实结果。还要试相反目标和已有终态，避免学会“同时看”以后连“只看歌词”也强制分屏。用户能否查看、修改和删除个人规则，应作为产品缺口明确核对。

## se-lesson-evidence 用户说“还是没学会”，沿保存、加载、采用和执行找丢失的位置

用户昨天教过同时看导航和歌词，今天仍进入全屏。先查昨天那条教法有没有真实保存、保存的适用条件是什么；再查今天请求是否符合条件、是否从正确车型和环境的候选中取出内容。没有日志证明保存，就不能先承诺“我早已记住”，也不能从一次失败直接判定模型丢了长期记忆。

保存有记录但本轮没加载，要继续查索引、过滤范围、检索结果和最终提示内容。候选中出现编号还不够，必须确认正文真的交给本轮模型。内容进了请求却仍选择全屏，才继续检查知识歧义、冲突方法和模型决策；如果动作正确而界面没变，则回到执行层。

这一定位顺序对应旧专家知识的三种真实问题：条目本身质量不齐，检索时机或场景不匹配，加载之后多步骤遵循仍不稳定。它们应有不同改法，不能看到用户说“不会”就一律要求再训练，也不能只增加篇幅而不修适用条件和执行依赖。[专家知识原文·当前问题](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

如果证据不全，明确哪一轮输入、哪次装载或哪份回执未记录，然后补测该环节。一次模拟请求不经过真实收音、界面采集和端侧时序，只能证明模拟入口之后的行为；一次实车成功也不能证明所有车型及相反需求都通过。后面的双入口图解按这个范围读取。

## se-expert-quality 把“做得好”写成可观察的标准，再检查是否有数据和动作支撑

原文希望专家知识让系统知道好与差，并在未达标时发现原因、选择预案、继续行动。标准不能只写“用户很满意”或“接机体验好”；模型要有对应数据和工具来判断。例如会合点是否明确、导航是否仍指向正确位置，比要求它“表现专业”更能支持下一步。[专家知识原文·期待](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

方法与标准可以分开写：标准说明想达到什么结果，方法说明常见情况下怎样做到。某一步未达标还需区分原因，如信息没到、对象已变化、下游失败，再给适用预案。不能把知识示例里的假设当作现场事实，也不能要求模型读取本车没有的传感器。[专家知识讨论00:20:39、00:45:35](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

天气保护说明同一原则：知识里写“雾天可以建议开启后雾灯”，还需要本次有效观察、灯光状态、车辆能力与适用确认方式。知识本身没有产生浓雾事实，更没有完成车控。进入和退出条件、观察周期以及重复触发限制，应回到L章的版本规则核对，不能从知识文本发明防抖数字。

知识落地依赖感知与原子能力，9月9日会议明确把它们列为前置条件；有信号和这次是否订阅使用是不同事情。产品评审需要逐条核知识所要求的数据和动作，未具备的条件标清范围，再判断是补接能力、缩小场景，还是修改知识。仅让文字听起来更完整，无法补上执行能力。[专家知识讨论00:50至00:51](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

## se-lesson-evaluate 用同一个用户目标比较前后效果，不拿一类指标替代另一类结果

验证前先定用户实际要什么。例如同时看导航与歌词，完成条件是两者可见、原导航有效、音乐仍在正常播放；仅输出“已分屏”或者选择了正确工具都不足以证明完成。保存当前页面、请求文字、车型与软件版本，再比较改知识前后的同一目标。

内容、检索和遵循分别检查。内容检查适用条件、步骤和标准是否清楚；检索检查该加的知识有没有进入本轮、无关和过期知识是否移除；遵循检查模型是否按当前事实采用方法、工具与界面是否达到目标。三类失败分开统计，不能用某次检索命中率替代真实任务成功。

模拟入口可以控制文字和背景，单独检验方法是否清楚；实车入口还需经过真实识别、状态采集、装载时序和执行回执。两种入口的结果不能互相代替。反例至少包括已经完成、能力不可用、执行中插话和用户改成相反目标，避免新方法只适配一条固定用例。

原文阶段计划包含手写知识实车验证，再批量生产、测试并依据表现优化知识和检索。每项指标的样本、分母、时间起止和车型范围需跟对应评测方案核对，本章不把其他版本的一串数字当作当前承诺。知识数量增加和后台保存成功，都不是这个阶段的结束标准。[专家知识原文·10月至11月安排](https://bytedance.larkoffice.com/docx/WhbsdukLFo8Q5Hx9OsMccjFInef)

## se-lesson-release 先验证已有知识能被稳定遵循，再扩大生产与自学习范围

9月9日讨论没有要求直接把旧知识全部废弃。短期挑出质量可靠的条目使用，长期重新明确结构、检索与承载；先验证现有方法能被稳定遵循、替换方法以后也能正确使用，再扩大自动沉淀。否则只是更快生成了一批没有适用条件、系统又不能稳定执行的文字。[专家知识讨论00:45:35、00:49:32](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

## se-learning-boundary 规则、个人记忆、模型训练与任务运行，各自改变哪一层

修一条专家方法改变的是以后处理同类问题的参考；保存一个人的偏好改变的是可检索的个人背景；训练模型改变的是模型能力；注册一个持续任务改变的是未来待执行安排。它们可能关联，但各自需要不同产物和验证。不能把“记住不吃辣”说成模型已重新训练，也不能把“知道提醒步骤”说成已经登记未来提醒。

9月9日会议希望人工专家知识与自学习产物能适配统一知识结构，但两者生产方式不同：人工知识先定义和审核，自学习从交互与纠正中挖掘候选。先验证已有知识能被稳定遵循，再扩大自动沉淀，是当时讨论的推进顺序，不代表任何用户一句话都能立刻写入全局规则。[专家知识讨论00:43至00:46](https://bytedance.larkoffice.com/docx/V85Udy3G5oQLnHxw3Mqc6LZEnHe)

保存、生成、检索和采用也不同。个人事实按记忆服务的权限、开关和主体处理；方法按知识的适用范围加载；未来安排还需任务系统的触发与生命周期。原始交互日志可以提供证据，但日志存在不等于已经形成可召回记忆或可执行技能。[记忆系统 PRD](https://bytedance.larkoffice.com/wiki/CbJVw4ACzilvvBkRxkqcQVfAnLh)

离线能力另看R章。本车部署1.7B FC、视觉模型或Edge_DT，不自动保证知识、个人记忆、联网检索和持续任务都能离线使用；还要核本地数据、接口和结果回读。模型规格、部署、业务接入和实车验收各有证据，不能从其中一项反推其他项已完成。

这一章用保存、适用性筛选、加载、采用和真实执行结果检查知识改动；个人记忆、运行规则与模型训练分别核验。

评审看改动是否解决原问题，是否误伤相近或相反请求，修改和删除能否更新到后续使用。未验证的车型、输入或执行环节，保留明确范围。
