# 主动服务视觉结果消费方案｜老板内审 10 分钟讲稿

> 主讲目标：10 分钟说清问题、取舍和建议，再用现场拍板单逐项收口。  
> 建议带入会议：PRD v02、现场拍板单 v02、视觉真实 JSON、成本/QPS 测算表、场景草案。  
> 说话原则：明确区分“9 月 10 日会议事实”、“我的产品建议”和“待各位拍板”。

## 0:00—0:30｜开场：先说今天要什么

各位老板，今天我不想让大家再评“视觉模型能不能看到美景”，也不是同步整个主动服务项目。我今天申请拍板的是：**默认 Always-on 视觉结果持续上来后，十几个长期开启的静态主动任务怎么消费，才能同时守住能力、成本、并发和时效。**

我希望会后得到六个书面结论：主路线、场景入围方式、数据协议、慢路边界、资源与时延红线、以及各段唯一 DRI。

## 0:30—1:30｜用一个真实场景把问题说明白

假设用户开了“沿途美景提醒”。车在高速上经过一段落日和古典建筑，视觉输出一段 Caption：“道路右前方出现落日，附近有古典建筑。”

系统接下来要回答的不只是“文本里有没有日落”，还有：这包是不是当前车辆的新数据？摄像头是否可用？任务是否真的开着？同一次落日是不是已经提醒过？如果用户正在通话或听导航，谁决定要不要打断？等卡片真正展示时，这个景还在不在？

如果每个静态任务每收到一包都调一次云端模型，任务数会直接放大成本和并发。但如果只允许“海、沙漠、森林、日落”这几个固定标签，又会丢掉“古典建筑”这类开放长尾能力。今天就是要决定这个取舍。

## 1:30—2:30｜先对齐会议事实，不把方案当现状

9 月 10 日会议口径是：视觉侧以整包 JSON 和 Caption 形式上传；DT 可以把整包放到 Context 中使用；舱外最快约 3 秒一轮，舱内约 5 秒一轮。但这些还缺车型、版本、开关、Topic、真实 JSON 和现网状态书面证据，我不会把它写成已全量上线。

我们还要把三种“解析”分开：从 JSON 取字段不需要模型；任务开启且标签命中的规则判断也不需要模型；只有从开放 Caption 中理解“这是不是用户要的场景”才是语义模型问题。

## 2:30—4:30｜三套方案和我的建议

方案 A 是每个静态任务、每个视觉包都调模型。它最容易保留开放能力，但调用量按车数、刷新频率和任务数相乘，同一 Caption 会被重复理解。我建议把 A 只当作风险基线，不当作真实量产选项。

方案 B 是每车每包在云端只做一次公共语义理解，再将标准事实给多任务复用。它比 A 少了任务数倍的重复，但如果全量活跃车辆每 3 秒仍调一次模型，QPS 和费用仍可能很高。我建议 B 作为小流量或中期公共语义层预研。

方案 C 是“结构化快路 + 准入式语义慢路”。视觉一次输出 P0 结构化标签和原始 Caption。端状态保存最新有效事实，Trigger 读取任务许可、数据有效性、配置条件和局部去重，然后只产生候选事件。原业务/Advisor 决定建议什么，统一仲裁/VUI 决定通话、导航和高优事件下是否触达。我建议首期选 C。

如果慢路还来不及建设，可以临时只开 C 的标签快路，并明确宣告长尾不支持。这是 C 的阶段 1，不是另一套 B。

## 4:30—5:45｜慢路怎么避免变回全量调模型

“按需”不能只写两个字。我建议只有五类入口：第一，视觉确认进入了一个新的 `scene_instance_id`；第二，路线、地理围栏或时间窗先缩小了候选；第三，结构化标签处于已校准的置信度灰区；第四，用户明确创建了长尾视觉目标；第五，批准的低频影子抽样。每次调用都要记录准入原因。

同时要设单车频控、场景实例缓存、全局 QPS/并发/日成本熔断。超限时只关慢路，P0 快路继续。模型超时或无法判断，默认不触发。

还要把三个能力分开：Caption 语义模型只理解已有文本；VQA 是对画面重新提具体问题；DT 是复杂上下文决策和交互规划。它们不是一个“模型兜底”篮子。

## 5:45—6:45｜用数字说明为什么需要拍板

这里我先用假设数字说量级，不当作业务预测。假设峰值有 1 万辆活跃车，每车 10 个静态视觉任务，舱外每 3 秒一包。A 理论上约 3.33 万 QPS；B 每车每包一次，仍约 3333 QPS；C 如果只有 0.1%、1%、5% 的包进慢路，分别约 3.3、33.3、166.7 QPS。

正式结论必须用真实的能力车总量、开启率、峰值活跃车、任务数、包间隔、慢路率、活跃时长、每次模型调用数和 Token 单价重算。如果今天拿不到真实数字，可以先批架构原则，但这些数字必须是详细设计和放量的阻塞项。

## 6:45—7:45｜时延不能只看“3 秒一包”

3 秒是视觉周期，不是用户收到建议的时延。我建议同时验两个指标。第一个是在线链路：`delivered_at - frame_captured_at`，它能持续埋点，但不包含场景出现后等待下一帧。第二个是真实场景：`delivered_at - scene_visible_at`，它包含等待采样，只能在有人工标注真实出现时刻的路测集上算。

每个场景必须分别会签 P95 和 `expires_at`。“P95 8 秒、10 秒作废”只能作为高速掠过的瞬时目标的影子测试起始假设，不能说成所有美景的正式红线。

## 7:45—8:30｜场景范围：今天先不让老板盲选

会上只明确举了日落、海、沙漠、森林和古典建筑这些例子。赵益红的场景还是个人草案，陈杰团队尚未输入。所以我建议：日落可做第一个影子候选，海/沙漠/森林放第二批，古典建筑先走长尾研究。这不等于它们已是 P0。如果正反例、置信度校准、场景时效、文案和下游 DRI 不齐，本次只批入围原则，不批最终 P0 列表。

## 8:30—9:15｜责任不能用“某团队”代替

今天还必须认领全链路 DRI：谁对视觉标签和校准负责；谁对上传和公共状态负责；谁对 Trigger 任务许可、条件、局部去重和事件交接负责；谁对 Caption 慢路和 VQA 各自负责；谁接住候选事件做业务决策；谁对仲裁、卡片/TTS 和真实展示负责；谁做数据批次和 Go/No-Go。

会议中被点到的丁彬、赵益红、李鑫、刘杨等人，当前只能视为问题解释或沟通入口，不能自动当作最终 DRI。需要现场实名认领和给时间。

## 9:15—10:00｜收口：请各位现场回答 D1—D6

我的总建议是选 C：一次感知、公共事实、多任务复用；P0 结构化快路；Caption 保留；慢路只在准入、限频、缓存和熔断下运行；Trigger 只生成候选事件；业务、仲裁和触达完成用户闭环；先影子，后小流量灰度。

现在请按拍板单逐项确认：D1 选哪条主路线；D2 今天是只批入围原则，还是同时批 P0 列表；D3 数据协议和舱外 3 秒能力的真实边界；D4 公共复用、慢路准入和三种模型能力的 DRI；D5 量产资源和分场景时效红线；D6 影子批次、灰度门槛、止损与全链路实名 DRI。

如果某一项今天不能给数字，请不要留“后续对齐”，而是留具体的认领人、回收时间和书面结论位置。“两条路都能走”不等于内审完成。

# 备用追问与回答

## 1. 老板问：为什么不直接复用动态 VLM 链路？

回答：动态任务是用户临时创建、数量有限、带专属目标和生命周期；本次是十几个预置场景长期订阅默认感知流。数量、频率和成本模型不同。动态能力可做长尾入口，不能未压测就成为静态主路。

## 2. 老板问：JSON 都上来了，为什么还说要“解析”？

回答：如果“日落”已是稳定独立字段，云端只取字段和做规则，不需要模型。如果它只在自由 Caption 文本里，就还需要语义理解。请视觉侧现场展示真实 Schema，不靠口头猜。

## 3. 老板问：C 方案会不会限制端模能力？

回答：会限制 P0 快路能直接触发的范围，所以我们不删 Caption。结构化标签保证稳定量产，Caption/VQA 保留长尾空间。一轮推理能否同时稳定输出两者、会增加多少端侧资源，需要影子 AB 证明。

## 4. 老板问：为什么 B 不直接上量产？

回答：B 已经去掉任务数倍的重复，但仍是每车每包调一次模型。舱外最快 3 秒一包时，全量车 QPS 仍可能不可控。要用真实 `Vpeak/Δ/Token/单价`、时延和故障影响做预研结论。

## 5. 老板问：有了置信度，低于阈值就全走模型不行吗？

回答：不行。低置信度可能在连续多帧大量出现，会把慢路变成另一种全量轮询。只允许“经过该标签校准的灰区”进慢路，并同时受场景实例去重和单车/全局限频。

## 6. 老板问：谁对最终用户体验负责？

回答：视觉侧对事实与标签质量负责；Trigger 对任务许可、条件和候选事件负责；原业务/Advisor 对建议内容和价值负责；统一仲裁/VUI 对冲突、排队和真实触达负责；项目产品对端到端指标和责任闭环负责。但具体实名 DRI 需本次现场认领。

## 7. 老板问：为什么不统一定 8 秒/10 秒？

回答：日落、海、森林和高速掠过的瞬时目标可见时长不同。8/10 秒只是瞬时目标影子测试的起始假设。正式上线要求是“每个场景都有自己的 P95 和 `expires_at`”，数字由业务价值和标注路测数据会签。

## 8. 老板问：今天能不能直接让研发开工？

回答：可以先对已拍板的架构原则和证据补齐排期；但在 P0 场景、真实 Schema、公共状态归属、Trigger 事件接口、下游承接 DRI、数据批次和 Go/No-Go 门槛未齐时，不能说“可以量产”，也不能直接触达用户。

## 9. 备用证据：为什么要现场确认舱外能力边界？

回答：7 月历史材料中，任务专属动态链路主要说舱内，舱外 VQA 是 Planner/模型按需调用；9 月会议又说舱外 3 秒并展示整包 JSON。这可能是“默认舱外 Always-on”和“任务专属 VQA”两种能力，也可能是版本演进。在视觉侧给出车型、版本、Topic、开关和真实 JSON 前，不靠推测下结论。
