触发器条件任务全链路

目标态（WIP）案例：“当座舱温度降到 25℃ 时，播放《XX》”。将创建任务、持续观察、条件命中和工具执行拆成四个阶段。

本图主线是《Task 任务管理设计》所描述的目标态（文档标题明确为 WIP），不当作已上线现状。旧版已有 PRD 的短链是“Planner 直接注册 Trigger → Trigger 命中后 notify Planner”，同样没有 Advisor 必经环节。先过语义分流门：“把空调调到 25℃，再播放《XX》”是当前轮的连续动作；“当座舱温度降到 25℃ 时，播放《XX》”才需要 Task + Trigger。

你原流程里最关键的 3 个纠正

  • • Planner 与 Director 是同一决策功能的业务名 / 内部名，不应画成两个串行决策者。
  • • 条件和动作的结构化在 Task Service Spec Builder，不是由一个常驻 Advisor 解析后直接调 Trigger。
  • • Trigger 命中后先 callback Task Service 并创建 Run，再经 Runtime Dispatcher 回流 Planner / Director。

旧版现有 PRD 怎么读

  • • 旧链路：Planner 规整任务语句 → Trigger 解析 / 保存 condition + action → 命中后 notify Planner。
  • • “副驾上车后给她唱小星星”的旧示例中，action 就是 notify planner，并不是通知 Advisor。
  • • 旧动态 Advisor 的“Advisor 注册 Trigger”是另一类自驱任务，不能套到所有用户条件任务。

谁负责什么

  • • Task Service：任务语义结构化、保存、生命周期、Trigger 绑定、Run 产生和结果回写。
  • • Trigger：监听状态、判断条件、防抖去重、命中后回调；不选歌，不决定最终 action。
  • • Planner / Director：创建时识别 Task；回流时根据 TaskView 和当前 Context 生成本轮 action_list。

评审时必须追问

  • • “降到 25℃”使用哪个信号？首次已是 25℃ 是立即命中还是等待边沿变化？
  • • 歌曲播放失败时，是重试同一 Run，还是任务直接失败？成功口径是工具 ACK 还是车端真实开播？
  • • 用户取消、车辆下电、数据过期和同时命中时，Task / Trigger / Run 分别怎样收口？
结论证据状态说明
Planner 将 Task 类请求路由到 task_manage；Task Service 负责 Spec、生命周期和 Trigger Adapter技术方案明确来自《[WIP][技术方案]Task 任务管理设计》的当前方案分工。
动态 Advisor 融入任务管理，不再作为固定必经的常驻服务方案边界明确因此本图没有画成“Advisor 调 Trigger，Trigger 再回 Advisor”。
“座舱温度 ≤ 25℃”的正式信号 key、阈值语义、稳态持续时间、已满足时是否立即命中待按实际协议确认本图用 cabin_temperature 作为产品示例，不冒充已上线字段。
音乐工具的成功回执、重试和终态映射待跨模块评审产品底线是把“工具收到”与“用户真实听到”分开。
