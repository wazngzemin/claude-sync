事件日志全貌方案

从现实中发生一件事，到系统把它记成事实，再到记忆、Context、UP、下游业务和 Planner 真正用上它。先讲“谁生产”，再讲“怎么存、谁消费、哪里会断”。

● 原始逐字稿优先 ● 当前 / 长期分开展示 ● 未确认项不冒充结论 ● 每章都有 case
一句话全貌谁最清楚事实，谁负责生产；事件服务统一保存；不同消费者按自己的需要查询、订阅或转成 Planner 的新输入。
当前实现状态（截至可读的 8 月 24 日消息）链路做过局部联调；Trigger 侧生成与调用已有进展。但事件服务正式上线、业务白名单、屏幕操作事件覆盖和连续信号治理还没完整闭环。

先说范围：我们到底在解决什么问题？

会上先这么说

“今天先别看接口。我们先回答一个最基本的问题：车里发生了很多事，哪些事需要留下来？留下来以后，谁会用？”

事件日志解决的不是“怎么唤醒 Planner”这一个问题。它先解决更底层的事：把散落在车端、客户端和云端的事实，变成统一、可追溯、可查询、可订阅的系统底账。

问题 1：Planner 看不见非语音操作

用户在屏幕删任务、退登账号、切换开关，这些动作没有变成对话，Planner 可能还沿用旧历史。

问题 2：原始状态太多

档位、车速、车窗、温度都在变化。全部塞给模型，会形成噪声。必须先过滤、翻译。

问题 3：各业务自己埋点

来源冲突、格式不一、时间口径不同。最后谁都说自己上报成功，却没人能还原事实。

标准事件日志主链：先生产事实，再统一存储，最后并行消费
现实发生一件事端状态变化 / 客户端操作结果 / 云端结果
→
最懂事实的模块生产Trigger / 客户端业务 / 云端业务
→
事件服务统一登记接收 · 补字段 · 入库 · 查询 · 订阅
→
消费者按需取用记忆 / Context / UP / Listener / Planner event（长期）
TTS 当时真实链路

不进入上面的事件服务主链

TTS/GTS 先中断播报 → 直接构造 Planner event → Frontier → Planner 再判断。

TTS 长期讨论方向

未来才考虑纳入标准事件生态

TTS/GTS 生产标准事件 → 事件服务入库 → Planner 事件消费者订阅 → 转为 Planner event。

版本状态矩阵：不要把不同日期、不同成熟度揉成“都已上线”

先拆开四层：你之前卡住的根因就在这里

同一个词 `event` 在不同文档里指了不同东西。先拆开，再谈模块，否则图越大越乱。

① 原始状态

人话：系统现在看到的值。
例：gear=D
还不是：业务事件。

② 状态变化 / 业务事件

人话：与上一次相比发生了什么。
例：P → D
本例来源：Trigger 根据新旧状态判断；明确点击和云端结果可由对应业务直接生产。

③ 事件日志

人话：系统登记的一条业务事实。
例：“档位由 P 设置为 D”。
作用：保存、查询、订阅。

④ Planner 的 event 输入

人话：为了让 Planner 立刻再判断一次的情况通报。
例：TTS 被打断，已播到哪里、还剩什么。

用同一个档位 case 看四层变化
gear=D现在是什么
→
P → D和上次相比变了什么
→
档位由 P 设置为 D可保存的事实
⇢
是否需要唤醒 Planner？只有少量事件需要
事件日志可以存在但不唤醒 Planner；Planner 的 event 输入只是事件的一种消费结果。
02

第一块看入口：一件事到底由谁生产？

会上先这么说

“先别急着看 Trigger。我们只问一个问题：这件事谁最清楚？谁掌握第一手证据，谁负责生产。”

已确认：一个事件 ID 只有一个生产来源已确认：来源迁移时新增 ID

判断依据

上游掌握的是原始状态、新旧变化、明确点击、云端结果，还是 TTS 播放进度？不要为了“统一”就把所有事实都硬塞进 Trigger。

生产方按“谁最清楚事实”决定，不按“谁最方便接”决定。
A
只有端状态新旧值档位、车窗、导航、媒体状态变化
Trigger
B
客户端明确知道操作或真实结果点击事实由客户端确认；删除成功必须由拿到业务结果的模块确认
客户端/业务方
C
云端自己产生事实云端埋点、任务结果、账号变化
云端业务
D
掌握 TTS 已播 / 未播与打断原因《红豆》播报被打断
TTS / GTS

Case：为什么“点击下一首”和“媒体变了”不能共用一个 ID？

事实 1：用户点击了“下一首”

客户端能确认的是 user_clicked_next 这个点击事实；它不能仅凭点击就声称媒体已经切换成功。

事实 2：当前媒体由 A 变成 B

端状态只看到播放内容变化。生产方可以是 Trigger。

两件事可能同时发生，但含义不同：点击不保证切换成功；媒体变化也不保证来自按钮。正确做法是拆成两个事件 ID，而不是抢同一个 ID。

先定唯一生产方，再定接口。不要先接链路，后补来源规则。
03

运行前先配置：事件不是现场临时编出来的

会上先这么说

“到这里停一下。运行时 Trigger 不应该再临时想‘这是什么事件’。产品要在上线前把事件、场景和消费规则三件事配好。”

本期：Excel + Python 脚本导入长期：统一事件管理后台

事件定义

event_id、名称、唯一来源、人工模板、结构化字段、渠道。

Trigger 场景

渠道、监听信号、触发条件、生成事件 Action、绑定事件 ID 和模板。

消费白名单

哪些事件给记忆、Context、UP、下游 Listener，哪些需要主动唤醒 Planner。

配置期关系：一个事件定义，同时被生产配置和多类消费配置引用
产品事件定义 / ID
gear_changed · 模板 · 唯一 producer
Trigger 场景端状态生产规则
Context / UP 白名单查询哪些事件
Listener / TCC下游订阅哪些事件
Planner 主动事件规则长期：哪些事件立刻决策

Trigger 场景和消费规则是并列关系：消费白名单不会由 Trigger 生成，Trigger 也不决定某条事件最终进 SP、UP 还是 Planner。

档位事件定义示意
event_id: gear_changed
event_name: 档位变化
producer: cloud_trigger
template: 档位由 {old_value} 设置为 {current_value}
resource_info: [old_value, current_value]
channels: [saic, seres]

容易出错

同一 ID 多来源；模板变量缺失；把每个 UI 点击拆成过细事件；渠道没有对应字段。

怎么验收

Trigger 后台能选到正确 ID、名称和模板；不同渠道只显示真实支持的信号；消费白名单能关联同一事件定义。

配置期决定“允许发生什么”；运行期只执行已经确定的规则。
04

Trigger 运行期：把“现在是 D”翻译成“刚从 P 变成 D”

Trigger 的价值不是“收信号”，而是夹在原始状态和业务事实之间，做确定性过滤和翻译。事件服务不应该理解每家车企的原始协议，Planner 也不应该接收所有原始噪声。

事件时间＝Trigger 匹配成功时间支持批量 RPC本期不加 30 秒重复限制

收到端状态

输入channel=saic, gear=D
处理确认这是一条档位信号
输出当前值 D
Trigger 此时拿到的是状态，不是业务事件。

选择渠道协议

输入上汽 / 赛力斯
处理加载本渠道实际支持字段
输出正确的信号解释
不同渠道字段、子字段和取值范围可能不同。

从运行 Context 取旧值，再和当前值比较

端状态输入current=D
运行 Context（不是 Context SP）old=P
Trigger 输出P → D
会议口径是 Trigger 从状态运行上下文取旧值，再执行比较；不能写成 Trigger 自己持久化旧值。第一次没有旧值时，初始化规则仍需明确。

匹配预置场景

输入gear changed
处理查找依赖 gear 的场景，检查全部条件
输出命中 / 不命中
Trigger 执行产品规则，不在运行时临时理解业务。

执行 generate_event_log Action

输入命中的场景
处理绑定 event_id 和模板
输出进入事件构造
Trigger 只生产事实，不决定是否提醒用户。

同时生成自然语言和结构化数据

event_info档位由 P 设置为 D
resource_info{old:P,current:D}
输出人和程序都能用
event_info 给人和模型读；resource_info 给程序精确处理。

设置事件时间

端状态时间原始上报
event_timeTrigger 匹配成功
入库时间事件服务落账
三个时间含义不同；本期 Trigger 事件使用匹配成功时间。

批量 RPC 上报并记录结果

输入本次命中的多条事件
处理调用事件服务
输出RPC 结果、车辆、渠道、事件 ID
一次状态上报可能命中多个场景；联调必须能追踪请求和响应。
Trigger 上报结果示意
{
  "event_id": "gear_changed",
  "event_time": "Trigger 匹配成功时间",
  "event_info": "档位由 P 设置为 D",
  "resource_info": {"old_value": "P", "current_value": "D"},
  "vehicle_id": "...",
  "channel": "saic"
}

Trigger 要做

分渠道解析；从运行 Context 读取旧值并比较当前值；匹配预置规则；填 event_info；生成 resource_info；批量 RPC；保留联调证据。

Trigger 不做

不算 TTS 已播/未播；不直接写数据库；不维护白名单；不直接推 Planner；不决定 talk_or_not；不生成记忆。

Trigger 的输入是状态，输出是标准事件；它不负责事件后面怎么被消费。
05

为什么有些入口不经过 Trigger？

会上先这么说

“如果客户端已经知道用户点了什么、操作是否成功，还要不要让 Trigger 再从状态猜一遍？不需要。让最接近事实的模块直接上报，反而更准。”

标准直接入口：客户端 / 客户端业务

点击事实由客户端确认；授权、退登、删除成功等结果，必须由实际拿到业务结果的模块确认后上报事件服务。

标准直接入口：云端业务

云端任务结果、账号变化、服务端埋点，由掌握真实结果的云端业务直接上报事件服务。

TTS 当前

不是事件服务直接入口

掌握打断原因、已播位置和未播内容后，直接构造 Planner event，经 Frontier 进入新一轮决策。

TTS 长期

拟成为标准事件生产方

未来可能直接生产标准事件并上报事件服务；消费者和 Input Manager 路由当时均未收口。

教学 Case：用户在屏幕删除任务

点击删除task_id=123
→
客户端拿到真实结果delete success
→
直接上报事件服务user_deleted_task
→
UP 后续帮助理解用户说“再建回来”
教学示例：用来讲清入口归属当时屏幕操作事件清单与业务白名单尚未完整落地
删除任务事件数据示意
{
  "event_id": "user_deleted_task",
  "event_info": "用户手动删除了明早 8 点的会议提醒",
  "resource_info": {
    "task_id": "task_123",
    "operation": "delete",
    "result": "success"
  }
}
能直接知道操作对象和结果的业务，不要让 Trigger 再猜。
06

事件服务：统一登记处，不是业务判断员

标准事件生产方最终汇入事件服务。它负责统一接收、补字段、落账、查询和订阅，但不替 Trigger 判断端状态，也不替 Planner 判断要不要说话。TTS 当前临时链不经过这里，只有长期方案才考虑接入。

标准入口上报Trigger / 客户端业务 / 云端业务；TTS 仅长期
→
统一接收批量事件 + 公参
→
补全user_in_car / 默认模板兜底
→
事件日志入库可查询 · 可追溯
→
开放消费查询接口 / Listener 回调

事件定义列表 RPC

给 Trigger 后台返回事件 ID、名称和模板。

批量上报 RPC

接收一个或多个标准事件。

事件查询接口

按时间范围、事件 ID 白名单等条件查询。

Listener 注册 / 回调

下游登记关注事件和回调方式。

完整 Case：档位事件进入事件服务后，里面到底发生什么？

这里不再只看两个字段，而是看一只完整“事件信封”。

完整事件信封示意
{
  "event_id": "gear_changed",
  "event_time": "Trigger 匹配成功时间",
  "event_info": "档位由 P 设置为 D",
  "resource_info": {"old_value": "P", "current_value": "D"},
  "vehicle_id": "车辆公参",
  "channel": "saic",
  "user_in_car": "可由调用方传；未传时服务补齐"
}

输入

一个或多个事件；ID、发生时间、自然语言、结构化字段、车辆与渠道公参；user_in_car 可选。

处理

统一接收 → 缺车内人时查端状态补齐 → 有 event_info 直接用 → 没有则默认模板兜底 → 入库。

输出

上报结果、可查询的事件记录；若命中已授权 Listener，还会进入对应下游回调。

为什么不让 Trigger 直接写库？

否则客户端、云端、Trigger 会各自维护存储和查询规则。事件服务把公共字段、落账、查询和订阅统一起来，生产方只对“事实是否正确”负责。

异常与验收

未定义 ID、关键字段缺失、补不到车内人、模板变量缺失、入库失败，都可能让“接口返回”与“真实可查”不一致。必须用查询接口回查落账；幂等、重试、补发仍待确认。

调用方无 user_in_car 时，事件服务查询端状态补齐模板更新不回刷历史幂等、重试、补发未收口
RPC 返回成功还不够；必须继续回查事件是否真实入库。
07

事件入库后：五类消费者并行使用，不是串行链路

会上先这么说

“写进事件日志只是落账。后面谁用、怎么取，是五条并行路径。这里不要再画成 Context → UP → Planner 一条线。”

事件服务
事件日志主存储
查询 / 订阅接口
记忆服务生产记忆基础数据
Context SP近期重要事件流
UP穿插对话历史
Listener / TCC推给下游业务
Planner event少量事件主动决策

① 记忆服务｜当前主要消费者

输入：事件日志、豆包账号、user_in_car。
处理：判断事件属于谁，形成记忆基础数据。
异常：车内人补错会造成记忆归属错误。

② Context SP｜近期情况摘要

输入：时间范围、SP 白名单。
处理：查询、处理“几分钟前”等时间表达、拼入 SP。
输出：本轮 Planner 可见的近期事件流。

③ UP｜对话历史增强

输入：上轮时间 T1、本轮时间 T2、UP 白名单。
处理：查询、排序、穿插。
输出：带事件背景的历史与 context_info 引用。

④ Listener / TCC｜下游通知

输入：产品授权、事件 ID 白名单、回调信息。
处理：命中订阅后格式化回调。
输出：下游业务真实收到事件。

⑤ Planner 事件消费者｜长期能力，不能当成已上线

长期输入：少量需要立刻重新决策的事件。
处理：订阅 → 包装成 Planner event → 经待确认输入路由。
当前边界：《红豆》临时链直接走 Frontier，不是事件日志消费者；评审时该消费者尚未实现。

② Context SP：什么时候查？怎么进入 Planner？

它不是事件一入库就自动塞给 Planner，而是在一轮输入组装时，按本轮规则主动查询。

新一轮输入开始组装确定查询时间范围
→
Context 带 SP 白名单查询只查允许进入 SP 的事件
→
事件服务返回例如 gear_changed + 原始时间
→
Context 格式化把时间处理成“3 分钟前”等
→
拼入 SPPlanner/Director 本轮可见

Case 输入

本轮查询范围内已经存在“档位由 P 设置为 D”，且 gear_changed 在 SP 白名单。

为什么由 Context 处理时间？

事件服务保存事实和原始时间；“刚刚 / 3 分钟前”的显示跟本轮时刻相关，应该由使用它的 Context 现场计算。

异常与验收

白名单漏配、时间范围错误、条数过多、SP 拼装遗漏都会导致“库里有、Planner 看不见”。验收要回读 Planner 的最终 SP 入参。

③ UP：事件到底怎么“穿插进历史”？

UP 不是伪造一条用户消息，而是把两轮用户消息之间的重点事实，按真实事件时间放回上下文。

T1 用户消息“明早提醒我开会”
→
事件 A客户端删除任务
→
事件 B其他白名单事件
→
T2 用户消息“再帮我建回来”
取 T1～T2确定时间边界
→
查 UP 白名单事件不是把全库都拿来
→
按 event_time 排序穿插放回正确时间
→
记录 context_info标明引用自哪条事件
→
Planner 理解“建回来”再决定是否创建任务

UP 输出是什么

带事件背景的对话历史，以及可追溯的 chat_history.context_info。后者只记引用来源，不替代事件主库。

它不做什么

不把所有事件都塞进历史；不把事件伪装成用户说的话；不决定 Planner 最后要不要创建任务。

异常与验收

条数上限当时未确认。验收要同时检查：查询范围、排序结果、UP 最终内容、context_info 是否能回到原事件。

真实下游 Case：用户退登 / 喜马拉雅授权通知弋途

客户端 / 账号业务生产真实操作事件
→
事件服务入库结构化数据
→
TCC 白名单命中产品已授权
→
回调弋途下游真实收到

为什么走 Listener

弋途要的是确定的结构化通知，不需要 Planner 参与语义判断；产品授权和 TCC 白名单控制谁可以订阅。

异常与验收

漏配、回调失败、未授权订阅、只传自然语言都可能断链。验收要看到下游真实收到的数据和回调结果，不只看事件已入库。

入库不等于所有消费者都能看到；每条消费路径都有自己的白名单、查询或订阅规则。
08

《红豆》TTS 打断：必须分“当时现状”和“长期目标”

这条 case 解释的是 Planner 的 event 输入，不是 Trigger 标准主链。原始请求里，TTS 已经先被打断，系统再把“已播 / 未播 / 打断原因”包装成新一轮输入。

当时真实临时方案

直接 Frontier，不经过 Trigger 和事件日志

  1. 副驾请求唱《红豆》。
  2. Planner 生成完整 talk_content。
  3. TTS 实际只播到“会更”。
  4. 主驾与他人交谈，TTS/GTS 先中断播报。
  5. 取得已播内容、未播内容和时间。
  6. 直接构造 event，发送 Frontier。
  7. Planner 新一轮输出 talk_or_not=no。
长期讨论方案

纳入标准事件日志生态

  1. TTS/GTS 判断满足事件生产条件。
  2. 上报标准事件。
  3. 事件服务统一入库。
  4. Planner 事件消费者订阅。
  5. 包装为 Planner event 输入。
  6. 经最终确认的输入路由。
  7. Planner 重新决策。
是否经过 Input Manager：待产品确认消费者实现：当时未做

为什么输出 no？

解释性复盘：依据本次 Planner 入参和输出推导，不是会议确认的固定规则
剩余内容歌词，不是安全或操作信息
+
车内注意力主驾正在真人交谈
+
用户意愿没有说“继续唱”
→
当前轮保持安静talk_or_not=no · action_list=[]

event 做了什么

把“模型文本已经生成完”与“TTS 实际只播到哪里”重新对齐，给 Planner 一次重新判断的机会。

event 没做什么

它没有让 Planner 去停止 TTS。TTS 在 event 到达前已经被中断；event 只通报结果。

《红豆》event 是 Planner 的情况通报；它当时不是事件日志标准主链的产物。
09

Planner/Director：消费事实，决定反应

Planner 与 Director 是同一个决策职能，不要画成前后串行模块。Trigger、事件服务和 Listener 都不能替它决定说不说、做不做。

本轮输入user_query / event / SP / UP / tool_feedback
→
Planner/Director整理已知 / 未知，判断价值和时机
→
本轮输出talk_or_not · talk_content · action_list

分支 A：仅表达或保持沉默

action_list=[] → 不调用工具 → 本轮直接结束。《红豆》属于这个分支：talk_or_not=no。

分支 B：action_list 非空

调用工具 → 获得真实执行结果 → 以 tool_feedback 进入下一轮判断。只有这个分支才出现工具闭环。

user_query

用户主动对豆包说的话。

event

用户没说话时，系统送来的值得注意的情况。

SP / UP

规则、近期事件和带事件的历史。

tool_feedback

工具或下游智能体的真实执行结果。

两个对照 Case：一眼看懂“结束”与“继续”

《红豆》：没有工具

输入：TTS 打断的 Planner event。
判断：当前是否还需要表达或行动。
输出：talk_or_not=no、action_list=[]。
结果：本轮结束，没有 tool_feedback。

“导航去公司”：有工具的教学对照

输入：user_query。
判断：需要真实路线结果。
输出：action_list=[route_planning_qa]。
结果：工具返回路线 → tool_feedback → Planner 再决定如何回复或导航。

事件只提供事实；Planner 才决定说话、行动或保持沉默。
10

四个 Case 串起来看

方案设计 + 局部联调

档位 P→D：Trigger 标准 Case

端状态 gear=D → Trigger 取 old=P → 命中 changed → 拼 event_info/resource_info → RPC → 事件入库 → 白名单消费

为什么经过 Trigger：端状态只知道现在是 D，Trigger 才能结合旧值确认“P 变成 D”。8 月 21 日群里曾用档位事件测试 UP，结果被反馈符合预期；这不等于业务白名单已经完整上线。

教学示例

删除任务：客户端直接上报

用户点击删除 → 客户端拿到 task_id 和真实结果 → 直接上报事件服务 → UP 后续帮助理解“再建回来”

为什么不经过 Trigger：客户端已经知道用户点了什么、是否成功；让 Trigger 从状态消失反推，信息更少也更不准。屏幕操作被认为是 UP 重点方向，但具体事件清单和白名单当时未完整落地。

临时链路真实存在

《红豆》打断：TTS/GTS 直接构造 Planner event

TTS 被打断 → 取得已播/未播 → 直接 Frontier → Planner → talk_or_not=no

为什么不经过 Trigger：只有 TTS/GTS 掌握播放断点、剩余文本和打断原因。标准事件日志改造属于长期方案，Input Manager 路由未确认。

评审真实下游需求

用户退登 / 喜马拉雅授权：Listener/TCC

客户端或账号业务生产 → 事件服务入库 → 产品授权 → TCC 事件白名单 → 格式化数据回调弋途

为什么不是 Planner：弋途需要的是结构化业务通知，不需要大模型参与判断。验收重点是下游是否真实收到，并能追踪回调结果。

12

端到端验收：不是看到“匹配成功”就结束

会上先这么说

“我们不能验收一份协议，也不能只验收 Trigger 打了一行日志。必须从事实发生，一直追到消费方真的用上。”

1. 事实发生原始信号 / 点击 / 任务结果失败：没有原始输入
2. 生产方生成Trigger 命中或业务直接生产失败：归属 / 规则错误
3. 上报接口成功Trigger 用批量 RPC；其他来源走各自标准入口失败：接口 / 服务不可用
4. 事件入库事件服务真实可查失败：成功不等于落账
5. 消费方拿到查询结果 / Listener 回调失败：白名单 / 时间范围
6. 业务可用Planner 输入或下游真实生效失败：拼装 / 决策问题

每一级要留下什么证据？

生产侧

原始输入、渠道、场景 ID、旧值、新值、命中条件。

事件侧

event_id、event_info、resource_info、时间、对应上报请求/响应、查询结果。

消费侧

白名单、实际返回、UP/SP/Planner 最终入参、下游回调、Planner 输出。

Trigger 命中 ≠ 事件入库 ≠ Planner 可见；三段必须分别验收。
13

最后收口：完整业务模块怎么复述

入口

谁最清楚事实，谁生产。Trigger 不是唯一入口。

生产

Trigger 只把端状态变化按规则翻译成标准事件。

事件中心

统一接收、补字段、存储、查询、订阅。

消费

记忆、Context、UP、下游和 Planner 按自己的规则取用。

你在评审会上可以这样总结

“事件日志的主链不是 Trigger 到 Planner。主链是：事实由正确的生产方生成，事件服务统一落账，消费方再按自己的目标查询或订阅。Trigger 只是端状态事件的生产者；Planner 只是其中一种消费者。”
