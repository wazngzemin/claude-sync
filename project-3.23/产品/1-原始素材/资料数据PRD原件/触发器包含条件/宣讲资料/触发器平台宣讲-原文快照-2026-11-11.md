# 触发器平台宣讲

# 为什么需要触发器

车里有一类需求，用户说出口的时候并不需要马上执行，而是要“等某个条件成立”或“到某个时间点”再做：

- “十分钟后帮我关掉座椅加热。”

- “车里超过 28 度的时候，让我凉快一下。”

- “以后副驾一上车，就放一首《小星星》。”

**触发器把“盯住端状态、判断条件、按规则通知”做成一项公共能力。**

# 产品定位

## 触发器做什么

**触发器只回答一个问题：约定的条件，现在成立了吗？**成立了，就把事件交给下游的模块；没成立，就继续安静等待。它具备三个特点：

1. **持续等待：**场景登记后保留等待规则，收到声明的车况、时间、位置或视觉上报时开始检查；条件通过并满足运行策略才通知下游，其余时间不打扰用户。

2. **只判断：**只回答“场景发生了没有”，不理解用户意图、不生成话术、不直接控车；建议怎么说、动作怎么做，由下游模块结合最新车况决定。

3. **每一次都可解释：**区分唤醒原因、条件判定、下发、展示与执行结果，不拿前一层成功推断后一层；统一回溯查询按实际接入版本使用。

## 与下游模块的分工

# 触发方式与条件配置

## 四种触发方式

1. **条件触发：**车况、导航与位置或车机事件满足条件时触发，例如“车内温度超过 28℃”“副驾入座且系好安全带”。

2. **定时触发：**到达指定时间或按固定周期触发，例如“十分钟后”“每天早上 9 点”。

3. **语义触发（建设中）：**识别用户当前这句话是否与已配置的场景相关，**用于新手引导、运营活动和定制场景**；它不创建用户任务，也不做任意语义的泛化解析，判断规则见后文 query 语义触发章节。

4. **视觉触发：**端侧 VLM 提供当前观察描述，触发器判断描述是否符合登记目标，并结合车况与运行策略决定是否通知；用户说“二排右侧的宝宝哭了告诉我”，系统要解决的不是现在回答一次，而是之后持续观察，在目标成立时再提醒。车速、电量等条件可以比较数值，“哭了”“毯子滑落了”却通常没有现成的车辆状态字段。**VLM把画面转成文字描述；触发器再比较这段描述与条件，判断此刻是否具备触发。**

## 条件怎么配

结构化条件由“信号 \+ 比较方式 \+ 目标值”组成，多条条件可以按“且 / 或”组合。视觉描述条件则选择已接入信号并填写是／否判断目标，只允许推理判断，不做字符串相等比较。选定信号后，系统只提供该信号可用的比较方式，从源头避免配出“挡位大于 D”这类无效条件：

# 场景示例

以下三个场景分别对应定时、单一条件和组合条件，展示一次触发从登记到结果的完整过程。

## 十分钟后关闭座椅加热

<table><tbody><tr>
<td>

**触发方式**

定时 · 一次性

</td>
<td>

**登记方**

task agent

</td>
<td>

**用户价值**

随口一说，不必守着设置

</td>
</tr></tbody></table>

> 冬天刚上车时开了座椅加热，用户说：“十分钟后帮我关掉座椅加热。”
> 
> 

1. **登记：**task agent 把“十分钟后”换算成具体时间，向触发器登记一个一次性定时任务。

2. **到点复核：**十分钟后先确认三件事：车辆是否在线、座椅加热是否还开着、座椅上是否还有人。

3. **执行与回传：**三项都满足，通知下游关闭加热；车端回传关闭成功，任务才算完成。

4. **例外情况：**用户已下车或已手动关掉加热，本次跳过、不算失败；用户中途取消，定时随之撤销；车辆已下电时本轮是否执行、后续是否顺延，按目标渠道规则确认，不作为通用承诺。



## 副驾上车放首歌

<table><tbody><tr>
<td>

**触发方式**

组合条件 · 可重复

</td>
<td>

**登记方**

task agent

</td>
<td>

**用户价值**

给同行的人一点小惊喜

</td>
</tr></tbody></table>

> 用户说：“以后副驾一上车，就放一首《小星星》。”
> 
> 

1. **登记：**task agent 登记组合条件“副驾座位有人 且 安全带已插入”，两项同时满足才触发。

2. **触发：**副驾落座并系好安全带，触发器通知 task agent 播放歌曲；只坐下没系安全带，不会触发。

3. **数据异常：**座位信号缺失时记为“无法判断”，同样不会触发。

4. **重复控制：**这类“每次都要”的任务可以多次触发，但受最小间隔和每日次数约束，避免短时间内反复上下车导致重复播放。
