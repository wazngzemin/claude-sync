# 从“汽车长了脑子”到司机 Agent：AI Car 2.0 从 PRD 到量产的方法论

## 分享会大纲

### 分享人

王泽民（Ze.min）

### 分享时长

45-50 分钟，含 Q&A

### 面向听众

AI 产品经理、AI 训练师、Agent 产品从业者、智能座舱和大模型上车方向从业者，以及对汽车 AI 产品落地感兴趣的产品/业务负责人。

### 分享定位

本次分享以 AI Car / 司机 Agent 为案例，讲清一个 AI 产品经理如何把“用户模糊期待”转化为“可定义、可拆解、可执行、可评测、可量产”的智能体产品。

核心不是讲一个炫技 Demo，而是拆解一条完整的 AI 产品落地链路：

```text
用户调研
  -> 产品定义
  -> 场景故事
  -> 功能拆解
  -> AI 能力拆解
  -> Planner / Context / Agent 架构
  -> 评测体系
  -> 量产闭环
```

## 一、开场：为什么车载 AI 是 AI PM 的高难样本

**建议时长：4 分钟**

### 核心问题

如果一个 AI 只是在屏幕里回答问题，产品经理主要关心“答得对不对”。

但如果这个 AI 接入了车，可能影响导航、泊车、车控、智驾动作，产品经理还要关心：

- 能不能理解用户真实意图；
- 能不能知道当前车辆和环境状态；
- 能不能判断安全边界；
- 能不能决定是否需要澄清；
- 能不能失败后解释和降级；
- 能不能被稳定评测。

### 本节要讲清楚

车载 AI 的难点不是“让车机会聊天”，而是让 AI 在真实空间里理解目标、管理任务、调用工具、承担边界。

### 过渡

大模型上车不是把 Chatbot 搬进车机，而是让 AI 从“回答问题”进入“管理任务”和“连接物理世界动作”的阶段。

## 二、从用户调研到产品定义：AI 汽车到底是什么

**建议时长：8 分钟**

### 2.1 用户对 AI 汽车的认知

用户往往说不清“AI 汽车”到底是什么，但他们能描述自己期待的体验：

- 交互更精准；
- 能理解模糊指令；
- 能主动推荐；
- 能照顾情绪；
- 能根据路况、车内乘客状态、位置和偏好做判断；
- 能把一些事情直接办完，而不是只告诉用户怎么做。

### 2.2 当前车机 AI 的主要痛点

| 痛点 | 用户语言 | 产品含义 |
|---|---|---|
| 听不懂 | 听不懂话、上下文差 | 意图理解和 Context 不足 |
| 机器感强 | 反应慢、像机器 | 交互缺少场景感和情绪感 |
| 不够主动 | 只能被动响应 | 缺少任务预判和主动服务 |
| 不闭环 | 点外卖、订票、找 POI 还得自己来 | 缺少工具链和任务管理 |

### 2.3 产品定义

AI 汽车可以被理解为：

> 汽车长了脑子，让汽车活了，帮用户动脑子。

它不是“语音助手 + 大模型闲聊”，也不是“车机里多一个 Chatbot”，而是移动空间具备更多处理信息、理解目标、组织任务和行动反馈的能力。

### 2.4 空间智能

一个空间越能替人处理环境信息，人越少动脑、少动手，这个空间就越智能。

可以从三个维度理解：

1. 单位时间处理的信息量更多；
2. 单位信息里由 AI 处理的占比更高；
3. AI 可处理的信息边界更广。

### 2.5 四个价值

| 价值 | 含义 | 用户感受 |
|---|---|---|
| 松弛 | 车多想一步、多做一步 | 少操心、少动手 |
| 自由 | 车内连接生态和服务 | 在车里也能完成更多事 |
| 探索 | 结合偏好和场景主动发现价值 | 路上有更多惊喜 |
| 好玩 | 交互有生命感和陪伴感 | 车不再冷冰冰 |

### 本节小结

从用户调研到产品定义，真正的转折是：不再把车载 AI 定义为一个“语音入口”，而是定义为一个能处理空间信息和任务的“移动空间智能体”。

## 三、主线故事：一句话让车像司机一样行动

**建议时长：6 分钟**

### 场景故事

周五傍晚，用户开着智驾去接人。路上他不是像操作机器一样点地图、搜点位、切菜单，而是像对一个真人司机说话：

> “激活智驾去商场接人，路上经过前面那家星巴克时靠边停一下。到了地库以后，帮我停到离电梯口近一点的位置。”

### 一句话背后的任务

- 即时任务：激活智驾、开始导航；
- 条件任务：路上经过星巴克时临停；
- 目的地任务：到达商场/地库；
- 泊车偏好任务：离电梯口近；
- 失败兜底：找不到星巴克、不能临停、没有电梯口信息、没有合适车位时怎么办。

### 这个故事覆盖的产品能力

| 故事片段 | 对应能力 |
|---|---|
| 前面靠边停一下 | 无参照物临停 |
| 过了这个路口靠边停 | 路口参照临停 |
| 前面星巴克靠边停 | POI 参照临停 |
| 停在前面拉行李箱的人旁边 | VLM 视觉参照物临停 |
| 到地库停到电梯口附近 | 停车场静态参照物泊入 |
| 帮我盯着充电车位，空了去抢 | 长时任务 / 条件触发 |
| 指着那边说“停到那” | 手势 + 语音多模态临停/泊入 |

### 本节小结

司机 Agent 的产品难点，不是让车听到“停车”，而是让车知道停哪里、何时停、能不能停、停不了怎么说。

## 四、从故事拆场景：司机 Agent 的场景地图

**建议时长：7 分钟**

### 4.1 无参照物临停

典型表达：

- 现在靠边；
- 前面靠边；
- 靠边停一下；
- 找个地方靠边；
- 前面随便停一下。

产品定义：

用户只表达停靠诉求，没有 POI、视觉物体或具体设施，系统需要就近、安全靠边。

PM 要定义：

- 哪些表达属于无参照物临停；
- 是否改变导航目的地；
- 是否需要智驾确认可执行；
- 当前道路不允许停车时如何反馈；
- HMI 如何告诉用户“我会在前方合适位置停车”。

### 4.2 路口参照临停

典型表达：

- 过了这个路口靠边停；
- 下一个红绿灯靠边停；
- 这个路口前停一下；
- 路口右转之后靠边；
- 掉头后靠边停。

产品难点：

- “这个路口”和“下一个路口”不是同一个；
- “路口前”和“路口后”动作完全不同；
- 用户发起时如果已经在路口中心，需要统一解释规则；
- 路口前禁停时，需要切换到合规替代方案。

### 4.3 POI 参照临停

典型表达：

- 前面星巴克靠边停一下；
- 对面全家停一停；
- 右手边地铁站停一下；
- 前面公交站放我下来。

PM 要定义：

- POI 类型、名称、品牌如何识别；
- “前面/对面/左手边/右手边”如何结合当前位置和道路方向；
- 搜不到 POI 时是否扩大范围；
- 如果还是搜不到，是否澄清“是否就近靠边”；
- HMI 是否需要说清楚“即将停在前方某个点位附近”。

### 4.4 VLM 视觉参照物临停

典型表达：

- 停在前面拉行李箱的人旁边；
- 停在那辆白车旁边；
- 停到那个拿露营车的女生旁边；
- 指着一个方向说“就停那”。

PM 要定义：

- 哪些目标可被 VLM 识别；
- 目标距离和可见性要求；
- 多候选目标怎么消歧；
- 动态目标是否持续跟踪；
- 找不到目标时如何澄清；
- 是否降级为无参照物靠边停。

### 4.5 停车场静态参照物泊入

典型表达：

- 停到电梯口附近；
- 停到某门店旁边；
- 停到充电桩附近；
- 停到出口近一点的位置。

产品难点：

- 停车场有图有 POI；
- 有图但无 POI；
- 无图但智驾具备漫游能力；
- 无图且需要 VLM 辅助识别；
- 找不到参照物时怎么降级。

### 4.6 长时任务：盯车位 / 抢车位

典型表达：

> “帮我盯着前面的充电车位，空出来就去抢车位。”

复杂度：

- 这是长时任务，不是即时指令；
- 需要 VLM 持续监测；
- 需要判断是否满足激活条件；
- 需要同步状态；
- 需要在条件满足时触发智驾泊入；
- 需要失败原因和安全边界。

### 本节小结

同样一句“停一下”，背后可能是六套完全不同的产品逻辑。PM 要先把场景族拆清楚，系统才有可能稳定。

## 五、从场景拆系统：为什么需要 Planner、Context 和多 Agent 架构

**建议时长：10 分钟**

### 5.1 传统座舱架构的优势和局限

传统车载座舱架构的优势：

- 响应效率高；
- 高频任务准确；
- 预设多轮稳定；
- 成熟场景少出错。

局限：

- 模块协同不足；
- 全局信息共享弱；
- 场景感知薄弱；
- 用户记忆和实时环境接不进来；
- 长尾场景定制成本高；
- 泛化能力有限。

### 5.2 漏斗式 Agent 架构

车载 AI 架构不能简单理解为“一个大模型直接管所有事”，更合理的是漏斗式架构：

```text
用户 Query
  -> 句法 RAG：高频明确指令，快速稳定
  -> 情景 RAG：注入场景知识和 few-shot
  -> 简单/复杂 Planner：任务拆解与调度
  -> Agents / Tools：导航、车控、VLM、泊车、GUI
  -> HMI / Action：反馈与动作
  -> 数据回流：badcase / 训练 / 评测
```

### 5.3 Planner 的定位

Planner 不是“帮模型想一想”的抽象概念，而是一个任务管理系统。

它要负责：

- 识别任务复杂度；
- 拆任务；
- 排优先级；
- 维护任务状态；
- 处理打断；
- 做执行反馈；
- 在必要时进行重新规划。

### 5.4 Planner 要支持的任务类型

| 任务类型 | 典型表达 | 产品含义 |
|---|---|---|
| 单步单任务 | 打开车窗 | 简单高频，通常走快速链路 |
| 单步多任务 | 我好热 | 可能要空调、座椅通风、车窗多个动作 |
| 条件任务 | 5 分钟后关掉座椅加热 | 需要条件触发 |
| 多步任务 | 去个好吃的火锅店 | 搜索、推荐、确认、导航 |
| 持续任务 | 帮我介绍沿途风景 / 帮我盯着狗狗 | 长时间保持任务状态 |

映射到司机 Agent：

- “到星巴克旁边停一下”是条件任务；
- “到地库停到电梯口附近”是目的地 + 泊车偏好任务；
- “帮我盯着充电车位，空了去抢”是持续任务 + 条件触发 + 智驾动作。

### 5.5 Context 管理

Context 是 Agent 的“五感”和记忆。

车载 AI 需要知道：

- 当前环境是什么；
- 用户刚才说过什么；
- 当前任务执行到哪一步；
- 车速、车道、导航、车内设备状态如何；
- 用户是谁，有什么偏好；
- 工具能做什么，不能做什么。

可以归纳成四类：

| 类别 | 对应信息 | 价值 |
|---|---|---|
| 环境 Context | 情景描述、端状态、屏幕界面、车外环境 | 知道现在发生了什么 |
| 对话 Context | 历史对话、事件日志 | 记得刚刚发生了什么 |
| 用户 Context | 用户记忆、人物偏好、任务历史 | 知道用户是谁、偏好什么 |
| 系统 Context | 工具知识、任务状态、专有知识 | 知道自己能做什么、任务到哪了 |

### 5.6 Context 的产品原则

- Context 不是越多越好，而是要预处理；
- 需要压缩、总结、打标、过滤；
- 不同 Agent 需要的 Context 不同；
- 长期记忆不能全量加载，要按场景提取；
- 行车场景不要加载无关驻车记忆；
- 当前任务是什么，就优先加载和任务相关的信息。

### 5.7 回到主线故事：系统怎么跑

以“前面星巴克靠边停，到了地库停电梯口附近”为例：

```text
1. 语音输入
2. 句法/意图判断：这是临停 + 后续泊车偏好
3. Context 拉取：当前位置、道路、导航、车速、停车场状态、用户偏好
4. Planner 拆解：
   - 当前行车任务
   - POI 临停条件任务
   - 到达地库后的泊车偏好任务
5. Tools 调用：
   - 地图 POI
   - 智驾临停
   - 停车场地图 / VLM
   - 泊车能力
6. HMI 反馈：
   - 已理解
   - 正在执行
   - 找不到/不能停时解释与降级
```

### 本节小结

车载 Agent 架构的核心不是“大模型一把梭”，而是用漏斗把确定性、泛化性和安全边界分层管理。

## 六、从系统到评测：怎么证明它不是 Demo，而是可量产产品

**建议时长：7 分钟**

### 6.1 为什么司机 Agent 必须做评测

同一句话在车上会因为 Context 不同而完全不同：

- “停一下”在城市道路、高架、路口、停车场含义不同；
- “前面”可能是视线前方、导航前方、道路同侧前方；
- “那个”需要视觉或手势理解；
- “靠边”受道路规则和智驾能力约束；
- “停到电梯口附近”依赖停车场地图、POI、VLM、泊车能力。

所以评测要覆盖：

- Query 表达；
- Context 环境；
- 预期动作；
- 预期反馈；
- 异常分支；
- 安全边界。

### 6.2 评测 Query 集结构

| 大类 | 子类 | 价值 |
|---|---|---|
| 条件任务 | 无参照临停、路口参照、POI 参照、视觉参照、驾驶控制 | 验证行车中“何时何地做动作” |
| 目的地任务 | 有图路径、漫游路径、停车场复杂环境 | 验证泊车和目的地能力 |
| 异常与边界 | VLM 失败、多候选、禁停区、ASR 错误、安全指令 | 验证系统不会乱来 |

### 6.3 每条 Case 应该怎么写

| 字段 | 说明 |
|---|---|
| Case ID | 唯一编号 |
| 场景分类 | 属于哪类任务 |
| 用户 Query | 用户真实说法 |
| 优先级 | P0 / P1 / P2 |
| Context | 车速、车道、天气、导航、周边信息、停车场状态 |
| 预期执行动作 | 系统应该执行的最小动作集合 |
| 预期语音反馈 | 用户应该听到什么 |
| 异常分支 | 找不到、不能停、识别失败、多候选时怎么办 |

### 6.4 评测不只看结果，也看过程

| 评测层 | 看什么 |
|---|---|
| 结果正确 | 最终是否停在正确位置，动作是否完整 |
| 过程合理 | 是否正确理解、是否合理澄清、反馈是否及时 |
| 安全可靠 | 是否避免危险行为，是否在禁停、红灯、逆行等场景拒绝执行 |

对司机 Agent 来说，安全不是一个加分项，而是一票否决项。

### 6.5 评测 Case 示例

| 字段 | 示例 |
|---|---|
| 用户 Query | “前面星巴克靠边停一下” |
| Context | 城市道路，右侧前方存在星巴克，当前车速适中，右侧允许临停 |
| 预期理解 | POI 参照临停，不是变更导航目的地 |
| 预期动作 | 搜索前方同侧 POI，规划安全靠边点，触发智驾临停 |
| 预期反馈 | “好的，即将停在前面的星巴克附近” |
| 异常分支 | 搜不到 POI 时扩大范围；仍找不到时询问是否就近靠边 |

### 6.6 badcase 回流

```text
测试 / 实车 badcase
  -> 标注错误类型
  -> 判断归因：意图 / Planner / Context / Tool / HMI / Safety
  -> 补充规则、样例、Context 或工具边界
  -> 更新评测集
  -> 回归验证
  -> 进入版本验收
```

### 本节小结

大模型产品的评测，不是证明它偶尔能做对，而是证明它在边界条件下不会乱来。

## 七、从 1.0 到 2.0：从座舱 Agent 到物理世界具身智能体

**建议时长：5 分钟**

### 7.1 1.0：数字世界 Agent 上车

1.0 重点解决的是：

- 更自然的语音交互；
- 更好的问答；
- 车控、导航、娱乐、生活服务接入；
- GUI Agent / 本地生活 / 信息获取；
- 多工具调用。

可以理解为：

> 让数字世界的 Agent 进入座舱。

### 7.2 2.0：舱驾融合 / 司机 Agent

2.0 的关键变化：

| 维度 | 1.0 | 2.0 |
|---|---|---|
| 世界 | 数字世界任务 | 物理世界任务 |
| 核心能力 | 问答、车控、信息服务 | 临停、泊车、感知、动作 |
| 用户表达 | 帮我查、播、控 | 像司机一样帮我开、停、找、等 |
| 系统重点 | 交互和工具接入 | Context、Planner、智驾协同、安全边界 |
| 评测重点 | 意图和任务完成 | 动作、位置、过程、安全 |

### 7.3 AI Car 的长期演进

| 阶段 | 能力关键词 | 用户感受 |
|---|---|---|
| 第一阶段 | 快、稳、准，事事有回应 | 愿意用 |
| 第二阶段 | 有眼力见，会学习，记得住 | 开始懂我 |
| 第三阶段 | 持续感知、持续规划、像人一样行动 | 真的像一个智能体 |

### 7.4 AI 汽车亮点

| 亮点 | 对外讲法 |
|---|---|
| 任务规划 | 能同时处理多个任务、追踪长程目标 |
| 全模态交互 | 看见、听见、理解用户和环境 |
| 免唤醒全双工 | 更自然，不机械等待唤醒词 |
| 记忆进化 | 越用越懂用户，持续反思和学习 |
| 生成式 HMI | 每次交互都能生成适合当前场景的表达 |
| GUI / IOT Agent | 连接手机、车机、生态和服务 |

### 本节小结

AI Car 2.0 的本质，是从“座舱里的 AI 助手”升级为“物理世界里的任务智能体”。

## 八、收尾：AI PM 做大模型上车的三点方法论

**建议时长：3 分钟**

### 方法论一：产品定义从用户期待断层里长出来

不要从模型能力直接倒推功能。

更合理的路径是：

```text
用户真实痛点
  -> 理想体验
  -> 体验断层
  -> 产品定义
  -> 功能边界
```

### 方法论二：复杂 Agent 先写场景故事，再拆系统

复杂 Agent 不应该一上来就画架构。

先写清楚：

- 谁；
- 在哪里；
- 说了什么；
- 想完成什么；
- 环境是什么；
- 系统能做什么；
- 做不到怎么办。

再拆：

- 场景；
- 功能；
- 任务类型；
- Context；
- 工具；
- HMI；
- 评测 Case。

### 方法论三：AI PM 的核心价值是定义边界和闭环

AI PM 不只是写“支持某功能”。

还要定义：

- 支持哪些表达；
- 不支持哪些表达；
- 什么时候问；
- 什么时候不问；
- 什么时候拒绝；
- 失败怎么降级；
- 怎么评测；
- badcase 怎么回流。

### 结束语

大模型上车不是把 Chatbot 搬进车里，而是让 AI 开始在真实空间里理解目标、管理任务、调用工具、承担边界。
