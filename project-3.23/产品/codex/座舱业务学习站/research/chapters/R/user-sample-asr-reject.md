## 样稿的写法特点（要学）
- 每个概念先说“它不是什么”（识别出字≠接受请求≠执行成功；离线≠只在断网时用；在线/离线≠过程/最终；拒识里的召回≠记忆召回；拒识≠本地不支持）。
- 用同一句话在不同时间点的状态讲过程文字（“帮我把”→“帮我把副驾”→……），并说明它会被修正、不是四条请求。
- 每个判断都讲“实际读到了什么输入”，不脑补没提供的信息；同一句话换前文结论会变。
- 讲训练：样本=输入+应有结果；标注边界怎样影响误接/漏接；流式样本要保留“当时只看到多少字”；SFT、RL 各是什么、不能过度推断。
- 区分“教学示例”和“原文示例”。

## 样稿全文（用户原文，未改）

在线、离线 ASR 与流式拒识怎样接起来
用户说“帮我把副驾座椅加热打开”，系统首先要把声音变成文字，再判断这句话是不是在请求豆包帮忙，最后才能确定控制对象和动作。这几个环节使用的信息不同，解决的问题也不同。理解这条链路，要沿着声音、识别文字、交互判断和执行指令的顺序看。
一、在线和离线 ASR：声音在哪里变成文字
麦克风采到的是音频，还没有“帮我把副驾座椅加热打开”这句话。ASR 是语音识别模块，负责把音频转换成文字。识别完成只代表系统得到了文字，不代表已经接受请求，更不代表座椅加热已经打开。
离线 ASR 在车上运行。车机把采到的音频交给本地识别模块，本地模块返回文字，完成这次转换不依赖云端。这里的“离线”指识别不需要网络，并不表示只有断网时才使用。车有网络时，本地 ASR 同样可以工作，例如先在车上判断一段话是否值得交给云端处理。
在线 ASR 在云端完成识别。按端云链路方案，客户端把音频上传到 AIDV 座舱云，AIDV 调用 Speech 语音服务，识别出的文字再返回客户端。上行传输的是用户音频，下行返回的是识别文字；客户端拿到文字后，才衔接后续文本对话和汽车业务处理。
“在线、离线”和“过程、最终”是两组不同的概念。在线、离线说明识别在哪里运行；过程、最终说明这次识别进行到了哪一步。本地 ASR 和在线 ASR 都可以在用户说话过程中陆续返回文字。本地对话 PRD 明确使用本地流式 ASR 的文字请求本地流式判断模型，因此不能把离线 ASR 理解成只在用户说完以后返回完整句子。
两条识别路径何时启动，要结合豆包的交互状态。全时聆听但尚未激活时，系统先用本地 ASR 得到文字，再请求本地流式模型判断是否值得接话。判断值得接话后，才提前上传音频并启动在线 ASR。这样不需要把车内所有聊天都直接送进在线链路。豆包已经激活、正在与用户对话时，则可以同时运行本地和在线 ASR，减少等待。
端云同时识别，可能得到两份不同的文字。屏幕最终显示哪份文字，需要与实际被采纳的处理结果保持一致：采纳本地结果，对应本地识别文字；采纳云端结果，对应云端识别文字。先显示出来的文字，只说明识别已经产生结果，不能据此判断系统已经选择了哪条执行路径。
二、过程文字：同一句话当前已经识别出的部分
用户说话需要时间，识别模块不必等整句话结束才返回结果。它可以先返回已经识别出的部分，再随着后续音频更新。这个尚未定稿的结果叫 partial，也就是过程文字。流式 ASR 用它支持实时判断，最终文字则在本次识别收尾后用于后续正式处理。
例如，用户正在说“帮我把副驾座椅加热打开”，识别模块可能先返回“帮我把”，接着更新成“帮我把副驾”，再更新成“帮我把副驾座椅加热”，最后得到完整句子。这里展示的是同一次说话在不同时间点的识别结果，不是四条独立请求。实际每次返回多少字、返回几次并不固定。
后一次结果还可能修正前一次的错字。因此，过程文字不能被当成始终正确、只能追加的定稿。系统需要处理同一句话的持续更新，不能把每次返回的全文机械拼接，也不能让旧结果覆盖后来已经更新的文字。
过程文字首先存在于当前识别链路中。走本地路径时，本地 ASR 把文字交给车机对话链路，对话链路再用这版文字请求本地流式判断模型。走在线路径时，云端识别文字经 AIDV 返回客户端，再供相应链路使用。ASR 负责生成文字，拒识模型读取文字并判断交互意图，两者承担不同职责。
从产品逻辑上，可以把过程文字理解为“本次说话正在更新的识别数据”。它可以被交给判断模块，也可以供界面展示，但不能因为它已被使用，就认定它已成为一条正式历史记录。具体使用哪个内存变量、是否保存日志、怎样清理临时数据，属于实现细节，不能把过程文字直接等同于某个数据库或 Redis 缓存。
屏幕只是过程文字的一个使用方。全时态尚未激活时，PRD 要求不逐字上屏，最终召回后再显示完整文字；激活态可以流式显示，并根据最终采纳结果刷新。因此，没有显示文字不代表系统没有识别，显示了文字也不代表请求已经被正式受理。
三、召回与拒识：判断这句话应不应该由豆包接手
拒识环节判断的是交互对象：这句话是否应当由豆包处理。在这个语境里，“召回”表示判定为应由豆包接手，“拒识”表示判定为不应接手。它不同于记忆检索中的召回，也不同于语音没有听清或车辆不支持某项功能。流式拒识使用过程文字提前判断，最终拒识使用完整文字确认。
系统并不会直接收到“主驾正在对副驾说话”这个标准答案。它拿到的是识别文字，以及请求实际提供的历史和场景信息，再据此推测交互对象。所以，同样一句话放在不同背景下，判断可能不同。
“你是不是把座椅加热打开了”，既可能是主驾在问副驾，也可能是主驾在质问豆包刚才的操作。如果前文是豆包说“座椅加热已打开”，这句就很可能仍然属于人机对话。仅凭句子里出现“座椅加热”，既不能决定执行，也不能决定拒识。
“帮我打开座椅加热”具有比较明确的请求特征，但它也可能是主驾在请副驾操作屏幕。请求式表达提供了判断依据，却不能保证交谈对象一定是豆包。真正困难的地方，是区分含有车域词的人人对话和用户对助手发出的请求。
功能能不能做，要放到另一项判断里。例如“我心情不好，给我讲讲故事解解闷”，本地模型可能无法完成，但它仍然可以识别出这是一条人机需求，再交云端继续理解。本地 PRD 明确区分了“拒识”和“本地不支持”，不能因为本地处理不了，就把用户请求当成无效聊天。
四、模型实际读取什么，怎样形成判断
打断 PRD 的参考输入包含两部分：历史对话和当前过程文字。历史对话说明前面用户说了什么、豆包回答了什么；当前过程文字说明这一次说话已经识别到哪里。历史可以为空，此时模型只能依靠当前文字和其他实际提供的信号判断。
假设主驾刚问“附近有什么餐厅”，豆包回答“有三家，第一家是……”，主驾接着说“第二家呢”。这句话没有“帮我查”或“打开”这样的命令词，但它承接了豆包刚才列出的选项，具有明确的人机续说关系。模型需要结合前文，才能理解这句话是在继续询问餐厅。
如果主驾和副驾此前正在讨论两家餐厅，同样一句“第二家呢”就未必属于豆包。模型的判断取决于实际输入，不能自行补造没有收到的前文。本地 PRD 也明确，本地上下文只是公共 Context 的子集，保留支撑本地理解、拒识和继承所需的轻量信息，并不意味着每次判断都读取全部长期记忆。
表达方式是另一项依据。“帮我查”“给我规划”“打开空……”具有请求、问询或控制特征，PRD 用这些前缀说明模型可以怎样提前预测。但这些是参考例子，模型需要泛化到其他说法，不能做成只支持几个词的固定名单。
明确的其他交谈对象也会影响判断。例如“老张，你帮我把外套拿一下”，已经指向了另一个人。本地 PRD 把“老张你……”列为具有明确呼唤对象、并非对助手发起请求的情况。它比单独出现“帮我”提供了更多交互关系信息。
人数和视线可以作为辅助信号，但不能替代语义判断。PRD 提出的方向是：看屏幕意味着更强的召回倾向，不看屏幕不代表必须拒识；单人意味着更强的召回倾向，多人也不代表必须拒识。相关信号只有被正确获取并提供给判断模块，才能发挥作用。
五、信息不足时为什么继续等，召回后为什么不再重复判断
用户刚说“我想”，系统还不知道后面会接“听周杰伦的歌”，还是“今天早点回去”。模型不能提前使用尚未说出的后半句。此时需要保留“当前信息不足”的结果，等待新的识别文字。后续模型记录增加了 IGNORE 标签，用来表达“信息不足，无法确定是否在与车机对话”。
假设豆包正在播报餐厅介绍，主驾开始说“我想……听一首周杰伦的歌”。第一次 ASR 返回“我想”，链路用这版文字请求模型，模型可能继续等待。第二次返回“我想听一首”，请求里换成了新的过程文字，模型此时才可能获得足够的请求特征，作出提前接话判断。
每次判断使用的都是当时那一版文字和背景。第一次判断不能拿最终句子解释，第二次判断也不能被当成用户又发出了一条独立请求。模型是在同一次说话过程中，随着信息增加重新判断。
一旦某次流式判断已经满足停播条件，车机停止当前播报，用户继续说完后半句。此后不必为同一次停播继续重复预测，因为这项动作已经完成。打断 PRD 所说“召回后不再做后续流式判断”，指的是停止这项提前判断，不是停止 ASR 收音，也不是跳过完整请求处理。
同一个 1.7B 模型可以在不同阶段被多次调用。未激活时，它用于判断是否提前上云；豆包播报中，它用于判断是否打断；用户说完后，完整文字还要重新请求模型，输出完整拒识或指令转换结果。提前上云、提前打断和最终受理，是不同阶段的决定，不能统一讲成“模型已经接受并执行了指令”。
六、模型怎样通过训练学会区分这些情况
训练发生在模型投入使用之前或版本迭代时，车上调用模型则是在使用已经训练好的参数进行预测。用户每说一句话，系统会发起判断请求，但不等于车上的模型马上重新训练一次。
工程双周报确认，拒识、流式拒识和车控三合一模型的数据工程包含数据生成、标注和审查，训练采用 SFT 加 RL，并吸收回流数据进行迭代。这里的训练目标不只是让模型认识“空调”“座椅”等词，还要让它在不同前文和表达方式下作出合适的交互判断。
一条训练样本需要包含输入和应有结果。例如，前文为空，当前文字是“老张，你帮我把外套拿一下”，应有结果可以是非人机交互；前文是豆包问“座椅加热要调到几档”，当前文字是“三档”，应有结果可以是人机交互。这些是用于解释训练方法的教学示例，说明模型需要学习“前文与当前文字怎样共同决定结果”。
标注就是给样本确定正确答案。标注质量直接影响模型学到的边界。如果含有“座椅加热”的句子都被标成人机，模型就容易错误接住乘客聊天；如果没有明确命令词的短句都被标成拒识，模型又容易漏掉“三档”“第二家呢”这样的有效续说。因此，需要覆盖容易混淆的正反例，并处理标注分歧。
流式训练还必须保留“当时看到了多少文字”。完整句子是“我想听周杰伦的歌”，不代表只看到“我想”时就应该作出相同判断。早期片段和完整句子具有不同的信息量。模型需要学习什么时候可以提前决定，什么时候应该继续等待，不能用后半句的答案替前半句作判断。
SFT 是监督微调：训练程序把输入交给模型，对比模型输出和标准答案，计算错误并调整参数。通过大量样本，模型逐渐学到请求表达、交谈对象和上下文关系，从而尝试处理没有原样见过的新说法。这种泛化能力仍可能出错，尤其是在识别文字不准确或背景不足时。
RL 是强化学习：根据模型输出得到的评分继续调整行为。三合一模型采用 SFT 加 RL 有工程记录，但流式拒识具体怎样设置奖励、怎样权衡过早接话与过晚接话，需要按对应训练方案确认，不能仅凭采用 RL 就推断它已经学会了最合适的打断时机。
模型训练完成后，还需要检验它是否判对、在第几个片段才判定、是否误接人人对话，以及识别错字会不会改变结果。这些问题对应不同体验：最终判对但接话太晚，用户仍会觉得豆包打不断；接话很快但频繁误接，又会干扰车内聊天。判断准确率和接话时机需要分别观察。
回到“帮我把副驾座椅加热打开”这句话：麦克风先采到声音，本地或在线 ASR 把声音逐步转换成文字；过程文字进入对应判断链路，模型依据当前文字和实际提供的背景决定是否提前上云或停止旧播报；用户说完后，完整文字再进入最终交互判断和指令理解；端云采信规则决定采用哪个处理结果，执行系统最后才改变车辆状态。
