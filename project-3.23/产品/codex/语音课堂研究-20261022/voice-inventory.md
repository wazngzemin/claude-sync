## 3. 课堂顺序：先讲用户遇到的问题，再放名词

### 第一站：用户开口前，豆包是否允许接这句话？

“我们先看一个很容易误判的情况：用户喊豆包，屏幕没进入对话，你不能立刻说唤醒模型坏了。先看这个时候豆包有没有交互资格。”

P1：初始化后检测麦克风权限。未授权显示“未获取麦克风权限”及去设置按钮。P5 上汽项目版写每次开机展示系统权限申请弹窗。两篇的交互细节不同，讲图时标“通用要求 / 上汽项目要求”，不要无差别合并。

P5：蓝牙电话、三方手机语音助手、宠物模式使用中：唤醒可被检测，但不能交互；显示对应不可用提示，不播唤醒应答。已经在交互时强制退出并关掉语音界面。OTA 升级时喊唤醒词也无反馈。无麦 K 歌已删除线，2026-10-19 的删除仍待评审，不可宣称已生效。

CarPlay：豆包与 Siri 语音互斥；另一边工作时通常不响应新唤醒。但“豆包激活期间，从手机按键唤醒 Siri”是例外：强制退出豆包。要在图上画出这个例外，不能只画互斥开关。

会议问法：“这个 case 是根本没识别到唤醒词，还是识别到了，但当前场景不允许进入对话？我们能不能把权限状态、通话状态、CarPlay 状态和唤醒事件放在同一时间线上？”

### 第二站：先把人的声音从车内声音里分出来

“接下来用户说话了，但麦克风收到的不是一句干净的‘打开车窗’。里面还有空调声、路噪，以及豆包自己正在播放的声音。”

P1 将降噪与回声消除拆开：降噪处理机械和环境噪声；回声消除参考车内扬声器输出，减少音乐、导航播报、电话等被麦克风重新收到的干扰。产品目标是≤50 ms 处理耗时、信噪比≥20 dB；这些是要求，不是本轮实测。

图节点：原始声音→降噪/回声消除→较清晰的人声。音乐放得越大越容易失败，要用音乐最小到最大音量验收，不要只用安静车内。

会议问法：“我们现在看到的是识别错字，但前面那段录音是否已经有回声残留？能不能同时看原始录音、处理后的录音和最终文字，先确认是哪一层把信息弄丢了？”

### 第三站：是哪位乘员在说？这个座位开没开？

P1 音区是“说话人在哪个座位”，声纹是“这个声音像已注册的哪位用户”。两者不能混同。音区关闭应提示“该音区已关闭”。靠背躺倒也不能把主驾误判为后排。P1 按车型写 5 座支持 5 音区、6 座支持 6 音区；P2 当前需求列的是主驾/副驾/二排左/二排右 4 个音区。两者范围不同，不要擅自写全车固定 4 或固定 6。

P2：座椅传感器+人脸身份信息判断有无人，无人音区不开交互。座位确定后，音区信息跟着本轮指令进入后续理解。为什么重要：同一句“把窗户打开”，需要知道哪位用户、控制哪个区域，也影响多用户合并时的来源标注。

声纹 P1：显性录入三次“豆包豆包”，上限 5 个，仅存本地特征，录入需授权。隐性注册、识人问候、儿童操作限制等多个段落明确 TBD，不能画成已交付主链路。

会议问法：“这句识别文字没错，但音区是否错了？如果乘员躺倒，目标车窗是按识别到的音区选，还是另有明确指向？声纹只辅助身份，还是承担控制授权？”

### 第四站：需不需要喊“豆包”？没喊时是不是也要理他？

P1 基础唤醒词为“豆包豆包”，不支持自定义。车外隔玻璃叫、电子设备播唤醒词的抑制标 TBD，供应商不支持。不能因为 PRD 写了目标≥95% 就宣称已具备。

P1 “主驾免唤醒（删除）”整个旧章节不作为现行规则，尤其不能搬出“主驾无须拒识”。

P2 全时免唤醒：设置开关，默认开启为需求；支持语音开关。开启并不等于任何话都执行，仍需判断人机对话还是人人聊天。

强召回：指令前/后带配置唤醒词或泛化“豆包”，应召回为人机对话。强拒识：摄像头判某音区乘员手持电话通话，该音区任何指令不响应、识别结果不上云。这里依赖感知模块提供状态，不是 ASR 自己知道用户正在打电话。

产品词“拒识”：听到、甚至识别出文字以后，判定这句话不该作为对豆包的请求。不要讲成“完全没听见”。

会议问法：“我们先对齐，用户这句是对豆包说的，还是跟副驾聊天？如果是后者，正确表现是保持安静，不是识别得越准就越应该回答。”

### 第五站：声音变成文字后，哪些文字只是暂时的？

P1 ASR=语音识别，把声音转文字并流式上屏；第一遍追求快，第二遍侧重精度修正方言/强口音。第一遍文字可能变化，最终结果不是用户再说一遍。

原文方言数据是文档声称能力：粤语字错误率约7%，江淮/陕西等约10%，二遍整体7%–10%；没有本轮评测集证据，别包装成座舱当前实测 KPI。

P1 离在线上屏：先流式离线结果，再以在线 final 刷新；无网全程用离线。注意“两遍 ASR”和“端侧/云端两条识别结果”是不同维度，不能直接画等号。

纠错示例：用户“导航去虹煤路”，下一句“梅花的梅”，模型结合上下文理解虹梅路；这是对话理解纠错，不应讲成已经改写了上一轮历史 ASR 结果。

会议问法：“我们拿来下指令的是第一遍中间结果，还是第二遍最终结果？用户看到的字被修正后，之前的预请求有没有同步撤销或重算？”

### 第六站：免唤醒为什么先在车里拦一次？

P2 未激活时：端侧先处理明确指令/明确拒识，不确定的再上云，目的写明是用户流量和云请求消耗。激活连续对话后，后续更可能仍在与豆包说话，转端云并行以保速度准确度。

P2 上云文本和音频同时走：端侧识别文本作为 soft vad 结果提前请求，流式音频在线 ASR 作 hard vad 结果；二者一致不重新请求，不一致重新请求云端模型。预请求仅跑到拒识意图模块。这里是该 PRD 的对接口径，soft/hard VAD 的工程定义、门控细节应以用户指定 OnePager 技术原文再核。特别不能说 soft 时就可以直接车控。

版本备注：“S08 未完成通过座舱云接入在线 ASR，需要将端上获取到的在线 ASR 上云，做端云 ASR 对比。”因此图不能只有理想直连云图，要单独标历史接入差异。

### 第七站：什么时候本地做，什么时候等云？

P6 无网：离线能理解就用离线结果，不支持则说“没有网络时，我只能支持一些基础功能”。

有网正常唤醒：音频并行给本地/云端；命中端白名单立即执行，未命中等云端。2 秒无心跳走端侧非白名单内容兜底；不同云端场景另有超时，超时结果通知端侧做降级。不要把“2 秒无心跳”说成“一切请求 2 秒必失败”。

feel（感受表达，比如“我有点冷”）必须等云，因为 Planner 要结合端状态处理。原文白名单列本地拨号、媒体播控、退出语音、开关应用、地图控制/设置、倒车影像、危险警报灯等，详细以离线 FC 协议表为准。

重要：原文“为何不把常规车控放白名单”的长解释已删除线，既有总结稿仍保留，不能沿用。这正是要重读原文的原因。

会议问法：“离线识别到了‘我冷’，不代表可以直接调温度。现在这条到底属于可直接执行白名单，还是要结合窗户和空调状态的感受类意图？断网时具体降级到什么？”

### 第八站：两个人同时说，为什么不能简单谁后说就覆盖谁？

P3 同时说不是宽泛“在几秒里说”：A 已说完，系统还没下发函数/工具；B 也到 VAD end（本次说话结束），才合并。仅合并有效非拒识指令，暂定上限4条；标注“主驾驶说…副驾驶说…”；合并后直接给 Planner，无需简单复杂仲裁。

角色标注只说来源，默认不等于主驾优先，安全类特殊优先级要另有产品规则。互补可综合执行；矛盾如开大/关闭同一空调应澄清。Planner 具体决策仍由 Planner 整体定义，原文标期望体验。

已进入执行后，是另一套规则：文本/控制+控制，若新控制需语音反馈则打断后恢复，否则提示音；文本+文本，后者打断前者；控制+文本，文本排队，界面显示排队状态。不要把这一组和“尚未调用工具前合并”画成一条。

后来进来的拒识语音不得取消先前有效任务：讲笑话还没输出，听到“吧啦吧啦”仍应继续；多人天气请求也不应被第三人的无意义语音破坏。

会议问法：“插进来的时候，上一条到底还在思考，还是动作已经下发了？这决定是合并计划、暂停播报，还是排队。我们先把这个时点固定下来再谈策略。”

### 第九站：打断到底停了哪一层？为什么停后还要恢复？

P4 不能写成唯一当前规则：
1. 文档记录旧问题：非简单车控等下一条 TTS 开始才停，简单车控叮一声。
2. 短期 2.6：非拒识+非简单车控停播；非拒识后暂等1.5秒是否简单车控，超时先停。
3. 二月底演示实验：TTS正在播、ASR>2字即停，不先等拒识；拒识就播放缓存里未播音频；非拒识等新任务 TTS；有“语音打断开关”，不考虑车控静默执行。
4. 长期 SOP：流式拒识+场景+恢复，具体方案待定。

删除线旧恢复规则“从前一个标点续播”不能继续用；有效文本已换成后续音频缓存 PCM 续播。PCM 在课堂只需解释为“已经合成、还没播完的原始音频数据”。

要和 P3 区分：暂停扬声器，不代表取消 Planner 任务，更不代表撤销已执行的车控。拒识后来不能抹掉先前有效任务。

会议问法：“我们现在要暂停的是声音，还是要终止上一轮任务？比如车窗已经打开了，停掉‘已打开’的播报并不能让车窗自动关回去。这个 case 的动作和声音分别是什么状态？”

### 第十站：屏幕状态是用户理解系统的依据

P2 未激活：拒识聊天不上实时文本；有效指令召回后显示最终 ASR，进入连续对话。30 秒暂定；有效指令重计时，持续无效满30秒退回未激活免唤醒。连续对话期间显示实时文本，区分拒识/有效。指令结果需成功/失败反馈和简要卡片。

“免唤醒开关已开”和“连续对话已激活”是两个状态，不能画成同一个亮灯。用户说完后一直无反馈，不应只能从他是否被豆包回答去猜系统有没有听。

会议问法：“用户现在能不能看出我是在听、在想、在执行，还是没接受这句话？如果最后失败了，界面是否给出结果，还是任务悄悄消失？”

## 4. 车外旁支：不能用车内链路直接复制

P7 施工中：左右后视镜、车头/车尾建议双麦阵列；交互范围建议5米内。文档说前4项为必要条件，第5项仅开启声纹唤醒且至少1个已注册声纹时校验，但正文没含条件列表，应读取原图。
正文待补充写车外不支持免唤醒、不支持多音区同时，仅唤醒交互单音区，连续对话时间可设默认；控制范围车窗/车门/后备箱，详细待补充。这些是方案，不是量产承诺。
测试条件有不动、面向车辆、无遮挡、同侧无近距离人声干扰、最远5米，产品目标的适用场景要一并保留，不能单独写“5米无障碍交互已实现”。

## 5. 画板建议：按因果关系画，不把所有模块硬排一行

主线：允许交互？→收音清洗→判断音区→唤醒/免唤醒状态→语音转文字→结束判定与最终确认→是否对豆包说→本地/云端处理→多人合并/任务仲裁→Planner/工具执行→生成话术→TTS合成→实际播放与界面→等待下一句。

旁支应贴到产生分歧的节点：
- 不允许交互：权限/通话/CarPlay/OTA/宠物模式；
- 音区：无人/关闭/位置错；
- 免唤醒：端侧预拦截/激活后并行；
- 识别：一遍临时/二遍最终、离线/在线两维；
- 端云：无网/白名单/感受类/心跳异常；
- 多人：工具未发合并；已执行排队/打断；
- 输出：拒识恢复旧音频/有效新请求等待新播报；
- 车外单独支路，保留未确认图内条件。

每个节点展开卡建议固定6项：用户此刻做什么；系统输入；本步做的判断；输出交给谁；没过怎么办；开会怎么问。术语放中文后括号里，第一次讲全称和作用，不让缩写承担解释任务。
