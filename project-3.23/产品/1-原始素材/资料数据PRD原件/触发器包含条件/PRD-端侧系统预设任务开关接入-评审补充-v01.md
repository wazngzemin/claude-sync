# PRD 补充：端侧系统预设任务开关接入

## 1. 需求概述

为端侧天气路况保护接入任务中心开关，使用户能够管理本车是否继续使用该任务。任务中心展示任务、提交设置并回显结果；端侧 Trigger 侧维护启停状态并让天气规则实际采用；条件命中后，继续复用已有天气业务与即时交互卡链路。

本期重点是“查询当前状态—提交开关—端侧保存并生效—返回结果—重启恢复”，并明确关闭时对已有提醒的影响。不迁移云端任务，不重做天气条件，不让 Trigger 接管卡片确认或车辆工具。

这次不是重做天气规则和即时交互卡，主要补任务中心前面的用户开关。用户点关闭以后，需要真正控制这辆车的天气任务，再把实际结果返回页面。
这次要达到三个结果：用户关得掉、页面看得准、普通重启记得住。今天请一起确认操作谁接、端侧怎样保存并生效、结果怎样回显，以及关闭时已有卡片怎么处理。后面的天气业务和车辆执行继续复用现有链路。”

## 3. 背景与现状

当前产品负责人确认端侧已做到 Trigger 到即时交互卡。该进度不能直接推出任务中心启停、状态恢复、语音和车辆执行均已完成验收。

用户在任务中心点关闭，是希望天气服务停止产生新的提醒，而不是只把一个按钮变灰。若没有将用户选择接入端侧实际运行，会出现“页面已关、仍然提醒”“重启后选择丢失”或“再次进入页面状态不同”等问题。

9 月 14 日外审明确讨论了按车维护、Trigger 侧承接任务启停，以及任务列表不应写死在车机；操作如何传到端侧、怎样反馈结果尚未落实。9 月 15 日主要明确三个云端任务的主动推荐与 DT 链路，天气仍为端侧自闭环。本期补齐端侧接入，不照搬云端下发方案。


## 6. 产品价值与状态维护选择

### 6.1 为什么要做

1. **用户关得掉：**用户关闭服务以后，不再因为新的天气条件被提醒，建立对开关的信任。
2. **用户看得准：**任务中心显示的是实际处理结果，而不是仅在页面上改变按钮。
3. **用户不用反复设置：**日常重启保留选择，不因刷新列表或同一任务更新重新开启。
4. **研发有明确的复用边界：**新增端侧任务可以复用查询、设置、反馈的接入方式，不把每个页面按钮与每条规则临时拼接。

上述是本次能力的目标收益，不宣称已有节省工时或性能数据。

### 6.2 为什么由端侧 Trigger 侧维护，而不以任务中心页面状态为准

任务中心解决“用户在哪里管理任务”；端侧任务运行解决“用户选择怎样真正执行”。用户离开任务中心页面以后，天气规则仍会收到本地数据，因此实际运行不能依赖页面是否打开，也不能只读取一个未确认生效的页面按钮值。

沿用前次评审的责任分工，端侧 Trigger 侧负责让本车启停状态保存、恢复并被规则采用；任务中心读取其实际结果，提交用户意图并展示反馈。设置是否经过任务服务，由现有接入方案确定。

**这不是说任务中心在技术上绝对不能保存数据。** 它可以缓存展示状态或复用统一设置能力；也不要求端侧将所有数据物理写入 Trigger 进程。这里选择的是责任边界：不能只改页面，不通知运行方；不能分别保存互相冲突的状态却没有一致的生效结果。若研发提出由统一设置服务持久保存、端侧负责应用的方案，只要能够实现查询、保存、运行生效和反馈一致，可以在此分工下复用。

### 6.3 四种信息必须分开

| 信息 | 决定什么 | 不能混同什么 |
|---|---|---|
| 任务列表及平台适用范围 | 本车有哪些任务、具备什么能力 | 不代表用户已经开启 |
| 用户保存的开关选择 | 用户是否希望使用这项任务 | 不代表当前版本、服务已经就绪 |
| 本车当前运行状态 | 对应规则是否已经采用选择、当前是否可工作 | 暂不可用不能伪装成用户主动关闭 |
| 即时卡本次选择 | 是否接受这一条建议 | 取消本次不关闭长期任务 |

例如用户保留开启选择，但当前能力暂不可用，应保留选择并标明“暂不可用”，不能静默改成用户关闭，也不能显示为可正常工作。

## 7. 需求方案

### 7.1 页面与任务接入

天气任务接入方提供名称、简短说明、图标、适用范围、对应任务及其子规则。任务中心展示一项长期任务和开关，不用即时卡的确认／取消替代长期开关。

列表内容与用户设置分别读取。任务改名或同一任务规则更新，应继续对应原任务，保留用户选择；若新增任务或改变控制范围，需单独明确初始化和用户告知，不直接复用旧选择。前次接受“新增任务列表下次上电可见”，不意味着已存在任务的用户关闭也要等下次上电。

任务中心至少区分：状态加载中、已确认开启／关闭、设置处理中、设置失败、结果待确认、能力暂不可用。样式复用现有规范；图标或缓存不能独立决定运行状态。

### 7.2 开关设置与结果

1. 用户进入页面，任务中心取得适用列表，并查询本车对应任务状态。
2. 用户设置开启／关闭，页面提交目标状态并显示处理中。本次建议处理中暂不接受同一任务的重复设置；如现有 UI 支持连续操作，须约定处理顺序和旧结果淘汰方式。
3. 端侧操作接收方定位任务，保存选择并使关联规则采用。关闭只影响本车该任务，不修改平台全局场景，也不关闭其他业务共用的感知能力。
4. 状态保存和运行生效均达到本次要求后，才返回完整成功。若只完成其中一部分，不得宣告完整成功；须反馈当前已知状态及处理结果，按一致性恢复方案继续处理或报错。
5. 任务中心按结果回显。明确失败时提示失败并确认当前状态；结果丢失或超时不等于操作一定失败，应查询，不能盲目恢复旧按钮值。
6. 用户离开页面后任务继续遵循端侧状态；普通重启后恢复已保存选择。实际运行不以页面收到回执作为启停前提。

### 7.3 开启、关闭与运行

- 开启只允许任务继续按原规则工作，不直接出卡、不直接切换驾驶模式。开启时是否立即检查现有条件，由本次评审结合脚本检查机制明确。
- 关闭完成后，不产生该任务新的业务事件。任务与所有关联天气分支必须列全，不能只关闭其中一条。
- 数据检查、连续条件判断、优先级及防重复沿用已有策略。反复切换开关是否清除提醒历史，需要明确；不能默认通过开关绕过防重复。
- 恢复未完成时，本次建议暂不产生新提醒，并保留未知／待恢复状态；读取错误不能当作无记录而初始化为开启。
- 原会提出首次默认开启；已有用户选择优先。按车管理、退出账号不删除预设任务是既有口径；本次要求同车普通账号切换不擅自重置选择，入口访问权限和恢复出厂行为另行确认。
- 已保存的状态应供本地任务使用。任务中心离线时能否访问、查询和设置需分别确认，不因任务端侧运行就宣称离线操作已可用。

### 7.4 事件、卡片与本次选择

Trigger 在任务允许、原条件满足且未被原策略抑制时，只发出业务事件。事件须让天气业务知道对应任务、这次提醒及场景；具体事件字段由双方约定，不要求模型处理。

天气业务按已有卡片接入规范提供文案、按钮、播报和回调；如支持本地语音，绑定当前卡片的按钮表达。卡片负责排队、展示及生命周期反馈，天气业务消费这些反馈。排队不等于已展示；失败、超时和拒绝不得被当作用户同意。

手动点击与已接入的本地语音进入同一原业务选择处理。重复回应只忽略，不重复提交动作，也不取消第一次正在进行的执行。有效确认后，执行业务按已确认的车辆限制执行并处理真实结果；不回 Trigger 重跑天气条件。卡片侧不独立决定车辆执行成功。

本文不新增单独的卡片模板平台，不规定任意等待时长，不照搬云端正文与 TTS 同文或建议 Query 的约束。卡片能力、语音和车控以本场景实际接入结果为准。

### 7.5 关闭与在途处理：本次提交评审的建议

| 关闭时的阶段 | 本次建议 | 承接边界 |
|---|---|---|
| 尚未发事件 | 停止后续新事件 | 端侧任务状态与规则运行 |
| 事件已发／卡片排队 | 取消这次未展示提醒 | 天气接入业务与卡片能力 |
| 卡片已显示、未确认 | 撤下或使本次询问失效；处理相关本地按钮绑定 | 天气业务、卡片与语音接入 |
| 确认与关闭交错，动作未提交 | 明确哪个处理完成点决定是否继续；建议关闭已生效后不接受旧询问启动新动作 | 天气业务和状态维护共同确认 |
| 动作已提交／已完成 | 不承诺撤回或自动反向车控；继续处理实际结果，停止后续新提醒 | 原执行业务 |

“停止新事件”和“结束已发提醒”是两项能力。若一期无法撤卡，应明确实际保证范围并由产品会签，不可对用户笼统承诺当前询问立即失效。关闭联动不是用户确认后回 Trigger 的二次条件判断。
