# 核心概念：从 Planner PM 到物理世界 Agent 的系统闭环 Owner

## 一句话结论

13 篇文章放在王泽民身上，指向同一个职业迁移：通用写作、常规需求和单点 Prompt 会越来越便宜；真正值钱的是进入真实现场，把私有数据、物理状态、模型规则、执行工具和评测连接成一条能持续变好的闭环。

## 为什么这次不能只讲 Planner 和 Trigger

王泽民的真实工作横跨场景知识、Selector、Skill、Planner badcase、动态示例、Trigger、Condition、信号、Task、Advisor、VLM 语义匹配、原子能力、Context 依赖和评测。

模块名在不断变化：动态 Advisor 被 Task 吸收，独立 Trigger 进入统一编排。真正稳定的能力是把一个模糊场景变成可执行、可判错、可回归、可复用的系统。

## 13 篇文章对王泽民最有用的一刀

1. AI 硬件避坑：Demo 跑通离量产很远，车端可靠性、权限、成本和供应链会决定结果。
2. 梁文锋：克制意味着只押一条主线。对王泽民来说，是用一个指标闭环替代不断增加文档版本。
3. 具身投资文章：真实部署和数据回流比融资 Demo 更硬。车上任务每多运行一天，才会产生真正资产。
4. 夏勇峰：硬件应服务 AI 进入现实。汽车已经是带传感器和执行器的身体。
5. 心力文章：有价值的部分是行动勇气；对人的道德分类缺少证据。评审中要用结论和数据，不靠猜测谁心力强。
6. 需求爆兵：代码变快不会自动让上线变快。责任、接口、历史系统和人心才是瓶颈。
7. 复杂、边界清晰、端到端：复杂只有配清晰边界和评测才有价值。场景知识误召回就是最真实例子。
8. 白领大逃杀：Harness 需要持续运营。动态示例、知识、信号规则和评测就是王泽民的 Harness。
9. 车企疯狂星期四：车型越多越需要统一底座。7 月统一编排原子能力正对应这个方向。
10. 大逃杀补充：FDE 红利来自懂 AI 与懂业务的交叉。王泽民已经在内部承担这种翻译工作。
11. FDE 五篇：与外包的分界线在学习是否回到平台。每个车企定制都必须沉淀成通用原子、评测和模板。
12. 产品经理悲观论：用户数不是企业和物理世界产品的唯一价值尺子。应看单次价值、频率、成功率提升和复用率。
13. Jeff Dean：选择裸模型几乎不会的问题，用上下文工程和评估器把它做成。车内私有状态与物理行动正属于这个区域。

## 独立判断

### 对纯银

他看到了组织迁移很慢，也看到了局部提效无法自动变成整体结果。但他把产品经理价值过度绑定到用户规模，低估了企业流程、工业风险和物理任务的单次价值。

### 对黄钊

他看到了 FDE 的早期红利和业务翻译价值。但只强调认知差和低枝果实还不够。没有数据权限、工程配合、稳定评估和产品回流，FDE 很容易变成高价救火外包。

### 对 Jeff Dean 的 1% 法则

模型成功率低不自动等于机会。还需要用户痛、可取得的私有信息、可执行动作、清晰评估和复用空间。五项缺一，可能只是很难的无底洞。

## 下一阶段主线

未来 90 天只做一件大事：把当前散落的工作收敛为“座舱 AI 能力闭环台账”，选三条已有事实基础的链路运营，并产生周度指标。

第一优先级是场景知识 60 条回归，原因是它已有基线、错误清单、目标值和发布阻断定义，最容易在短期形成硬证据。

第二优先级是动态示例运营，原因是它能证明持续运营 Harness 的能力。

第三优先级是 804 原子能力闭环，原因是它能证明从具体场景抽象到统一底座的能力。

## 王泽民专用 SOP

### 步骤 1：先选一条能判分的闭环

输入可以是线上 badcase、评测失败或明确场景需求。先判断它有没有用户价值、私有现场、行动能力、边界、评估和复用空间。缺少三项以上时，不直接立大项目。

### 步骤 2：画出从输入到结果的完整链

模板如下：

用户或事件 → 状态与 Context → Trigger → Condition → Task → Planner → Tool → feedback → Eval。

每一个箭头都写清输入、输出、owner 和失败分支。资料没有定义的部分标为待确认。

### 步骤 3：把失败分到正确层

检查清单：

1. 链路是否走错模块。
2. 工具描述或能力边界是否不清。
3. Context 是否缺少车况、人物、记忆、视觉或任务状态。
4. 下游是否无法执行。
5. 评测 query 或标签是否有问题。
6. 信息都正确时，模型是否仍推理失败。
7. 是否缺日志，导致无法归因。

### 步骤 4：选择最小修复方式

- 共性稳定规则进入静态知识、Skill 或场景卡。
- 孤立长尾且模型有能力但走错路，可以使用动态示例。
- 缺状态先推动端状态、Context 或 VLM 字段。
- 工具能力缺失先补 Tool 或原子能力。
- 规则和数据都完整仍失败，再考虑 SFT 或模型训练。

### 步骤 5：用同一把尺子回归

修改前保留基线，修改后用相同 case 重跑。记录准确率、任务成功率、误触发、漏触发、发布阻断、延迟和成本。禁止只用“体验更好”作为结论。

### 步骤 6：把项目经验回流平台

每个需求结束前必须回答：这次学习进入了哪一种可复用资产？候选包括原子能力、通用接口、场景模板、静态知识、动态示例、评测集、数据字段或排查手册。

## 判断标准与衡量指标

### 场景知识闭环

- 成功信号：同一 60 条评测准确率达到 95% 以上，发布阻断为 0，错误类型持续减少。
- 失败信号：只增加知识文本，没有同卷回归；修好一个 case 又破坏相邻场景；已删除场景仍被召回。

### 动态示例闭环

- 成功信号：每个 case 有唯一 ID，重写后回归通过率按周提高，应删除旧例能被识别。
- 失败信号：只汇报累计条数；114、86、74、63 多套口径并存；新增示例造成互相干扰却无人检查。

### 804 原子能力闭环

- 成功信号：每个补点能回到具体场景，字段、异常、owner 和验收记录齐全，并能被第二个场景复用。
- 失败信号：能力名写进表格后就算完成；端云两套重复实现；项目差异永久硬编码。

### 个人成长闭环

- 成功信号：评审前三分钟说出推荐方案、代价和验收值；每周至少完成一次修前修后对照；90 天内独立搭出一个带 Eval 的小原型。
- 失败信号：继续用更多文档替代决策；只参与会议却说不清个人判断；职业叙事仍停留在“负责某个会被合并的模块”。

## 失败模式与风险

1. 过度文档化：材料不断增加，关键结果不变。
2. 模块身份锁死：Trigger 或动态 Advisor 被架构吸收后，个人价值叙事随之消失。
3. 参与等于主责：把依赖模块写成个人业绩，降低可信度。
4. 只做一次修复：没有评测和回流，经验无法复用。
5. 过早谈 Soul 和关系：基础执行失败率尚高，长期概念掩盖可靠性问题。
6. 低代码焦虑：因为不会传统后端开发而停止入局，忽略产品型 FDE 先需要 L3 原型和评测能力。
7. 只按用户量看价值：忽略安全、成本、频率和企业复用。

## 90 天检查清单

- 第 30 天：场景知识达到 95% 以上，阻断为 0；三条闭环台账有人和日期。
- 第 60 天：形成一份车载 AI FDE Playbook，至少包含三个真实失败、修复和复用案例。
- 第 90 天：完成三个外部行业访谈，搭出一个跨行业小原型，具有私有 Context、Tool 调用和 Eval。
- 任一阶段没有数字结果时，停止扩写职业叙事，先回到当前项目补闭环。

## 评审用一页模板

以后每个复杂场景只先写一页，正文顺序固定：

1. 用户要完成什么，失败造成什么损失。
2. 推荐方案是什么，用一句话先说结论。
3. 当前链路从哪里开始，到哪里结束。
4. 需要哪些私有状态、VLM 观察、记忆和任务历史。
5. Trigger 在什么事件唤醒，Condition 还要检查什么。
6. Planner 能做的决定有哪些，禁止做的事情有哪些。
7. Tool 如何执行，失败时谁接管。
8. 用哪一批 case 验收，目标值是多少。
9. 哪些内容资料明确，哪些仍待确认。
10. 本次需要谁拍板，最晚日期是什么。

推荐开场 Prompt 模板：

“我的建议是采用方案 A。它能在本期满足 X 个关键场景，代价是 Y 暂时不支持。今天需要确认三个点：信号来源、执行 owner、验收值。确认后我会用同一批评测在某日给出结果。”

## FDE 暗线访谈模板

进入一个新行业时，不先问“你想做什么 Agent”。先问五个暗线问题：

1. 这件事今天是谁在做，他每天最烦的三个步骤是什么。
2. 发生错误时，真正承担损失的人是谁，损失用什么数字衡量。
3. 老员工靠什么经验判断，哪些信息从来没有写进 SOP。
4. 任务要调用哪些系统、设备、权限和人，哪一步最容易卡死。
5. 做完一个项目后，哪些学习能进入平台，哪些只能留在客户现场。

将答案做四次翻译：

- 第一次，把抱怨翻译成用户任务。
- 第二次，把任务翻译成 Context、规则和 Tool。
- 第三次，把系统限制翻译成产品边界和异常分支。
- 第四次，把一次交付翻译成可复用资产和 Eval。

如果四次翻译都能完成，这个方向更接近产品型 FDE；如果只能按客户要求堆人和定制，商业形态更接近外包。

## 场景边界模板

每个场景至少写四类样本：

- 正例：应该进入该场景的典型表达和状态。
- 反例：看起来相似，但绝不能进入该场景。
- 边界例：只差一个字段或阈值，结果会变化。
- 缺失例：关键信号不存在时，系统应该追问、降级或放弃。

以极速温控为例：

- 正例：用户明确说“最快降到 20 度”，当前温度明显偏高。
- 反例：用户只说“有点热”，应走普通舒适调节。
- 边界例：当前已接近目标温度，不应继续最大风量。
- 缺失例：车内温度信号不可用时，不应假装知道当前温度。

这个模板可以直接解决“复杂、边界清晰、端到端”文章里最抽象的部分。

## 个人时间分配模板

未来一个月建议按以下比例分配：

- 40% 用于评测、回归和错误趋势。
- 25% 用于跨 owner 决策和接口确认。
- 20% 用于小原型、配置、API 和自动化工具。
- 15% 用于 PRD、汇报和知识整理。

这不是永久制度。它用于纠正当前“材料投入过多、结果曝光不足”的偏差。若某周进入正式评审或上线，比例可以临时调整，但评测和回归不能归零。

## 最终成功信号

90 天后，别人介绍王泽民时，不再只说“他做过 Trigger 和 Planner 材料”，而能说：“他把一个车载复杂场景从 88.3% 做到 95% 以上，建立了动态示例周度运营，并把多个车企差异抽成可复用原子能力。”

这句话能被数据和产物证明时，职业迁移才真正发生。
