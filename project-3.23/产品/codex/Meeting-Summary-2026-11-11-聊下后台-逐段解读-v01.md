这场会从三个具体麻烦开始。**调模型判断时，车况等信息要手填。做不同车型时，同一套规则要各改一遍。查已经发生的问题时，能导出数据的人和需要看现场的人，用的页面又各有一套。** 张弛逐一提出改法，文涛演示手里已有的回放，最后你们把这些需求带回到更大的项目里讨论。哪些工具接到火山，哪些给车企用，哪些先做，都需要产品先拿一张表把现状和依赖摆出来。

可以带着同一条车窗问题读完整场会。假设某车型上，用户说「关一下车窗」，结果和预期不同。调试工具让同学补上当时的车况，**重跑一次判断**。日志与回放帮助同学找到历史记录，**看当时实际发生了什么**。提示词标准化确保切换车型时，**模型能读到这一款车正确的可用动作和限制**。这是用会议思路构造的串联例子，三个工具在这条问题里各有用途。

## 一 为什么现有 Fornax 调起来费劲

### 00:34–03:55 张弛从实际改提示词的工作开始讲

张弛此前问过明骏、晓伟，也和左晨聊过。开场后，他先讲改 Planner 系统提示词的人遇到了什么。Planner 是根据用户说的话和当前情况决定下一步做什么的模块。系统提示词（SP）是模型判断时读到的一套规则。Fornax 在这段讨论里承担两项工作。大家在那里维护提示词，也在右侧调试区输入一句话看 Planner 的输出。

难处在于，同一套规则在每次使用时还会读到一些变化中的信息。比如上一次发生过什么、车辆现在上报了什么状态、这款车型有哪些能力、有没有命中的动态示例。**占位符就是提示词中预留的位置，运行时才填入这次真实要用的值。** 直接打开一份提示词，看到的可能只是一个待填的位置。现在同学在 Fornax 调试，就得自己拼这些值，费时，也容易少带一项。

张弛想借用旧 ToB 座舱工具的对话体验，让调试者也能在类似对话框里输入一句话，由 AI 汽车后台补上约定的信息，再显示 Planner 的判断。会上还提到可切换模型，用同一套输入比较效果。模型列表和第一版具体自动带入哪些信息，当场留在方向讨论里。

### 03:56–05:22 两步走以及模拟器的例子

张弛把**先补齐提示词调试需要的信息**当作第一步。接着，他提出可以把现有模拟器接进来，在后台主动设定车速、车窗状态等，再让调试页读到刚刚设好的值。他用超过 120 公里时速的场景举例，想说明一些车况在线下很难复现，可以用模拟值在调试里构造。

模拟值（会上说的 Mock）就是测试者给定的车况。设定之后，页面需要把这个值交给 Planner 使用，调试者才知道自己在验证什么。仅在界面上填一个车速数字，和模型这轮实际读取到了这个数字，是两个需要对上的动作。会上讨论到模拟器联动的方向，具体由页面传哪些值、如何关联一次调试，还留待设计。

### 05:23–07:31 文涛问能否只跑某一段，张弛讲清快测的限制

樊文涛先确认 Fornax 右侧返回什么。张弛说，选择相应模块的提示词调试时，当前这一页看的是 **Planner 的输出**。文涛接着问，新的后台能否让人选择跑链路中的一段。张弛提到已经有一个快速测试入口，输入一句话会跑 Planner 加 Agent。Agent 是收到规划后执行具体任务的模块。张弛还提到这个入口理想上应能选择 Agent，具体能选哪些，会里没有现场逐项验证。

张弛以导航举例。云端发出一部分数据后，后续执行还有车机侧的程序及弋途服务参与。网页上看到 Planner 选到了导航，和车机真的开始导航，中间还有车端执行。旧 ToB 产品的相关能力主要在云端，页面更容易把这条链路完整展示出来。AI 汽车的首步调试因此更适合聚焦 Planner 的判断，再讨论哪些执行环节也能在网页验证。张弛也提到以后可给记忆、Context 召回等模块做提示词调试。Context 召回是从已有对话或状态里取这次判断所需的信息。

### 07:32–08:20 西钺追问为什么要单独做

陈西钺看到对话框和切模型的设想后，追问已有 Fornax 的情况下，新页面具体能带来什么。张弛把话题拉回占位符，举了端状态、记忆、用户画像的例子。陈西钺听懂以后继续问，新平台打算怎么把这些变量补进去。

这轮问答把新工具的价值定在了一件看得见的事上。调试者发一句话之后，能在同一轮里看到**平台带进了哪份车况或项目数据，Planner 根据这份输入作了什么判断**。这也是评估一版调试工具有没有用时，最容易演示给双方看的环节。

### 08:21–10:23 按车辆 ID 取最近上报，或者用模拟器故意造一个状态

第一种设想是**选指定车辆**。张弛说，调试时带上车辆 ID，平台据此查车辆上报的信息。西钺问，以端状态为例，是不是相当于按这辆车检索再拼进去。张弛回答，车辆运行时会上报，平台取**最后一次上报的端状态**加载到提示词里。这里的取数点是最近一次上报，和问题当时的历史状态要分别看。车辆多久未上报时如何提醒，本次没有展开。

第二种设想是**选定一个人为设置的场景**。测试者先在模拟器设定车窗是否打开、车速是多少，调试页再读这份配置来跑。选车辆可以减少手工抄状态，模拟器适合构造难遇到的状态。陈西钺认可手工拼动态信息的痛点，张弛也转述明骏、晓伟遇到的重复操作。

### 10:24–10:48 为什么工具信息曾经切过去，又改回来了

张弛补了一件已经发生的事。之前团队把工具信息迁到 Agent 平台，让它能动态加载。产品同学仍在 Fornax 调提示词，但这个调试页面不能从汽车侧系统自动取回工具信息，于是那次改法又退回去了。两边都有入口，人的日常动作接不上，方案就难在实际调试里用起来。

所以会上提出的分工是由 Fornax 继续承载提示词内容，汽车自己的后台负责把汽车业务的数据带进来，供产品、研发一起调。会议已经把这个痛点说透，页面细节、最先做哪些变量和实际接入方式仍需设计。 [逐字稿 00:34–10:48](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)

## 二 为什么不同项目的提示词要做成可复用

### 10:48–12:16 新车型一多，整份复制会重复维护

张弛转到第二个问题。上汽和赛力斯有各自的项目，同一家车企也可能有不同车型或场景。各自维护一整份 SP 时，团队改一条通用规则，就可能在多份文件里分别修改和核查。明年项目增多，这个维护成本还会上升。

他的设想是拆两块。**通用规则只维护一个共用版本，每个项目带入自己有差异的内容。** 会上提到 Agent 能力、动态示例、动态场景等可以按项目放。这里说的租户，可以先理解成平台上要区分的一份项目或客户配置。张弛举例，某个上汽车型能用这一组 Agent，换赛力斯项目就可能是另一组。具体按车企、渠道、项目还是车型切分，要等方案再定。

### 12:17–13:31 切换项目后，要能看见最终拼出来的一整份

张弛提出查看效果。选中一个项目，后台把通用模板和当前项目允许的内容拼起来，让人看到模型这次实际会读到的 SP。再切一个项目，就能看另一本完整结果。这样产品核对时可以直接找「这个车型是否带进了该有的工具、示例和能力说明」，不用自己在好几处查完再拼。

陈西钺认可这个方向，补充说各项目的能力边界、能用的工具本来就不同，适合跟着项目切换。这里的「标准化」是**把共用和车型专有的内容按同一种方法管理**。调试段落里的车速可能每次变化，这里的车型能力边界和工具清单通常随项目、车型或版本选择而变化。两者最后都可能进入一次模型判断，维护它们的人和切换条件各不相同。 [逐字稿 10:48–13:31](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)

## 三 日志查看与回放各已有些什么

### 13:38–14:43 芮婷现在为什么用一张导出表

张弛说以前已经为芮婷做了一版页面，因为她在 Fornax 上导出不方便。旧版每行是一条问题案例，展示她关心的项，可以下载、导出，用来做问题标注或反馈。数据同学还能结合 Fornax Trace 上报相关信息。Trace 是一条请求经过各个处理环节后留下的记录。

产品同学排查问题时，有时想从一句用户指令一路追到工具执行。芮婷则要按既有格式取数和标注。张弛看到的是两边有机会共用相同的案例数据和入口。合并讨论需要同时让人看得懂、让现有工作能继续做。

### 14:44–16:39 哪些字段当时已有，哪些要研发重新核

张弛说旧表查的是历史存储的数据，字段相对有限。Fornax Trace 的记录更丰富，因此提议更好地呈现用户原声、系统播报（TTS）、对话决策环节的推理过程和工具执行结果等。

陈西钺说早期提过日志字段需求，当时服务端没有人力继续做，提出把原需求拿出来重新看。张弛请她和李兆乾核对旧字段能否覆盖现在的业务，再找芮婷确认调整页面或字段会不会影响标注。陈西钺回应由产品再对需求，请研发从数据上检查当前取不到哪些字段，并准备把相关同学拉到已有群。这里定的是**拿旧需求与当前数据对照**，具体必看字段和页面当场没有锁定。

### 16:42–17:50 张弛打开旧 ToB 日志详情，想借它的逐轮查看

旧 ToB 的交互参考是先看对话列表，再选其中一轮看上下文。张弛说那边相对容易，主要看用户意图和调用的工具。汽车版如果用同样的逐轮切换，大家想在一轮里对齐更多现场信息，比如当时的上下文、记忆、端状态、Planner 输出和 Agent 执行结果。

举个会议设想能解决的问题。用户第二轮说「再高一档」，同学想知道模型是不是把前一轮的「副驾座椅加热」接对了，还想看这一轮最后调到哪一档。切到第二轮时，除了听录音，他需要把这轮用了哪段历史、最后选了哪个工具、执行返回什么，都对在同一轮上。上述信息是张弛提的汽车详情页方向。

### 17:51–19:49 文涛在 PPE 演示了什么，页面当时缺什么

文涛现场演示了已有的一版回放，部署在 PPE，也就是发布前的预览测试环境。入口当时是单独的回放入口。选一个时间范围，页面拉出这段时间的历史对话。用户说的话和助手播报都能听，可以听单轮，也能按顺序播放。张弛随后还提到呈现主驾、副驾等音区的效果。

张弛问能否看到端状态。文涛说回放目前查询原日志接口，**返回的数据里面没有端状态**，因此那一版无法展示。这里缺的是页面拿到的值。能听见「关一下车窗」，也还需要单独的数据提供那时车窗的状态，才可能拿来解释模型为什么那么判。文涛的演示确认的是已有回放交互和当时的数据范围，版本在 PPE。

### 19:53–20:43 换成 Fornax Trace 有条件可行

张弛提出考虑把回放查询改到 Fornax Trace 这边，争取读到更全的记录。文涛请兆乾看数据源。兆乾说此前跟伟晨聊过，技术上可以切。然后他把问题落回数据展示。改动以后怎么呈现、芮婷的反馈标注能否继续，需要和芮婷再对一遍。

这段讨论有两个可以分开的判断。工程同学找过数据侧，认为可以切源。产品和数据使用者还要确认字段与日常工作能不能接上。例如能多看几项推理状态是一件事，芮婷批量导出时能否拿到原来那几个字段，是另一件事。逐字稿明确的是技术可行性意见，实际切换尚待后续安排。

### 20:43–22:18 想把日志列表里的第 N 条接到对应回放

张弛问，能否从日志列表选中一条，请页面直接定位到这一轮回放，同时让前后轮也能查看。文涛先复述了一遍，认为可以拿被选中记录的时间往前后筛，再在回放里定位。他用的是「应该」，这是会上的做法设想。现场演示的回放从固定入口打开。

张弛希望产品按实际使用场景看看文涛这版，提应该改的地方。陈西钺回应先把已有工具汇总，再由你统一出方案，让产品先看后找研发详细对。日志段落最后留了三个接下来需要确认的问题。**用户从哪里进入、回放使用哪份数据、如何保住已有导出和标注方式。** [逐字稿 13:38–22:18](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)

## 四 你投盘点表时，大家怎么谈优先级和平台方向

### 22:21–22:59 张弛建议先解决内部调试和维护的痛点

张弛说这只是他的个人想法。提示词调优和标准化可能更能解决眼前的问题，因为有人正在反复改 SP、手工注入动态变量，明年的车型项目也会增加。日志方向有现成工具可以参考和利用。他提议先和明骏、晓伟或实际处理 Planner 问题的人再过一遍，弄清他们卡在什么动作，再出需求请研发支持。

陈西钺接下来明确会后一起排全体工具接入的优先级，并说你已有一张表。会里有人说了「哪项更解眼前的事」，最终首批和各项排期还需要回到这张表一起确认。

### 23:17–25:25 你提出统一到火山，第一件急事是已在对客用的权限

你投屏展示已有平台工具的盘点，提议逐步接到火山后台，再盘清楚客户用哪些、内部团队用哪些、不同使用者拿什么权限。你还提到和高龙聊过，部分场景可能直接走产品开白，具体流程还在研究。**开白就是让指定账号通过产品入口的访问限制。** 客户进去之后能用哪些模块，同样是这段讨论的产品问题。

你明确说自动化评测、线上数据分析看板等现状自己没接触过，需要负责人讲清楚。DT 调试也需要请改提示词、排问题的人补实际需求。你把当前正在推进的事情点出来，触发器已经在对客使用，当时还没走产品开白流程，所以文涛在做的权限管理优先级高。张弛也回应说权限应该已在做。

张弛看的是**内部调试效率和多项目复用**。你说的权限优先看的是**客户已经在用，现有入口和能做的操作要尽快有清楚的管理办法**。两个判断有不同的理由，最后需要把它们放进同一张表定先后。

### 25:41–28:04 ToB 权限是拿来参考，豆包运营后台是远期样子

你说自己还没看过 ToB 平台，问能否给访问权限。张弛请文涛帮忙，文涛明确可以。张弛随后分享豆包的做法，一个平台里集中管理策略、音色、提示词、评测等，让运营、产品、研发在日常迭代中都能操作。你顺着他的意思说，这样现在的配置平台可能逐步做成运营平台。

这段讨论解释了术语「平台化」怎么来的。一个入口下除了能找工具，以后还可以完成一些运营配置和检查结果的动作。会末确认的是你先盘目前各工具做到哪，再拉产品和研发排先后。ToB 和豆包平台用来参考形态，音色、评测等能力具体哪批进车载后台，需要按工具再确认。 [逐字稿 22:21–28:04](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)

## 五 左晨为什么说能力边界和动态示例像

### 28:14–30:19 从按渠道手工配一段说明，到能按车型发布

你问左晨之前提的是哪个平台。左晨说的是**车型能力边界**。当时由服务端同学分渠道手工配置。他希望有云端入口，让对应同学维护一段说明，然后发布到不同车型，这样模型知道眼前这辆车支持哪些功能。

你问它是不是 QA 对，也就是一条样例问题和一条对应答案。左晨接着用座椅加热、通风、按摩和播报音色解释，他说的是**一段用自然语言写的车型事实**。例如，会上的示意是座椅有几档、按摩可选哪些模式。动态示例更像给模型一条示范，某种情况下遇到一句话时，应该如何处理。张弛说这两类内容的相似之处在于，都能作为 SP 的一部分随项目加载。

把这个问题放回第二段就能看出价值。一个共用规则可以写「执行前按本车支持的能力选择动作」，再按实际车型填入各自的能力说明。**左晨答应发说明文档，西钺让他发到平台群供研发看。** 云端配置的粒度、发布操作、使用权限和排期当时都没展开。 [逐字稿 28:14–30:19](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)

## 六 散会后西钺单独留下你，明确了什么

### 30:25–31:29 先让人认领，再验证每一行的优先级

其他人下会以后，陈西钺单独留下你。她觉得已有盘点表可以作为起点，只在群里发过可能有人没仔细看，因此建议这周去私信各产品并找张航确认工具负责人。真找不到人，你和她先顶起来。把人找齐之后，再问负责人那一项为什么要现在做。

她给了一个供大家修订的排法。**P0 是与当年年底量产交付直接相关，要考虑上汽和赛力斯。P1 是内部运维，例如暂时不影响处理客户问题的工具。P2 更偏日常内部使用。** 她当场说明是自己先估的，需要实际负责人确认。会里的依据是量产节点和使用场景，哪一项最终放 P0 由产品和研发再看。

### 31:30–31:55 你补了两个必须写进盘点的问题

你补的第一件事是**要核现在到哪一步**。问清工具已经上线、正在开发、还是只有规划，因为它们的工作量和能交给客户的时间不同。第二件事是**要核客户是否确实需要**。如果年底某个项目要让车企自行使用，优先级可能更高。

换成一个具体的盘点问法就是，某工具即使已有内部入口，还要确认谁在用、客户用它做什么、入口内还差什么才能交付。会议整体收口就是让这些信息先表格化，再约产品和研发一起定。

### 31:56–33:04 项目经理、周会和开白是怎么聊的

西钺建议问坤姐是否有专项项目经理，再考虑每周盘进度。她举了对接方舟的例子，项目经理能帮忙把卡点、需要的研发支持、各产品要交的动作理清楚。你说已拉坤姐，提到浩然以前跟后台，人选还要确认。你表示先确认负责人，并提到产品开白先推进。这段定的是下一步找人和推进方向，专项项目经理、周会时间、首批交付项都留待后续确认。 [逐字稿 30:25–33:04](https://bytedance.larkoffice.com/docx/MzqSd1t5zoUDbIxHzyVcvUStnAh)
