教程 v1 · 2026-08-11真实案例：距离终点 1km 提醒适用：Planner / Trigger / Task / Context / Eval

把一句人话，写成 Agent 真能执行的业务语义

这不是教你画一个宏大架构。你要练的是一项每天都会用到的能力：有人说“到终点前 1km 提醒我”，你能把它拆成工程、测试、车企版本和评审都听得懂的定义。

← 回到文章解析

业务语义层，就是把“大家以为自己懂”的业务规则写成同一份可执行说明，让模型、Trigger、Task、工具、测试和现场的人都按同一份定义工作。

先记住这条链

第一步：找出业务对象

先问“这句话在说谁”。用户的“终点”不是一个抽象词，它至少要绑定当前导航任务、目的地和路线。

字段本案例填写为什么要填
业务对象当前导航防止把“终点”误当成车辆位置、历史目的地或地图搜索结果。
关联对象车辆、用户、当前 Task、目的地后续要知道哪个任务在等、谁发起、哪个车企渠道提供数据。
对象主键navigation_id / task_id，字段名以当前协议为准没有主键，歌曲、导航、任务容易串。
当前未知真实导航距离字段名、单位和渠道枚举待确认不允许为了让表完整而假装知道。
你在评审中要说：“先确认这个‘距离’属于哪个导航对象，来自哪个渠道，单位是什么。对象和来源没定，先不要说触发器支持。”

第二步：分清状态、事件、条件

这一步是你触发器工作里最重要的基础。三者不是同一个词。

词大白话本案例系统用途
状态现在是什么样。当前剩余距离 1200m。Context 或端状态查询。
事件刚刚发生了一个变化。剩余距离从 1100m 进入 1000m 以内。让 Trigger 知道这一刻可能要判断。
条件满足什么标准才算命中。remaining_distance ≤ 1000m。过滤事件，避免每次上报都重复提醒。
动作命中后做什么。通知用户，写回 Run，关闭一次性 Task。调用 Planner、HMI 或工具。
“每 5 秒上报一次距离”是状态上报频率；“第一次进入 1000m 内”才是一次触发事件。两者混在一起，就会出现重复提醒或完全不触发。

第三步：把条件写成可检查的规则

条件不能只写“快到的时候”。至少要写四件事：比较对象、运算符、阈值、触发频率。

condition: field: navigation.remaining_distance operator: <= value: 1000 unit: m event_mode: enter_threshold repeat: once_per_navigation valid_when: navigation.status == navigating cancel_when: navigation.status in [cancelled, arrived] 注意：上面字段名和枚举是示意，正式填写前必须拿渠道真值确认。
正向 case

距离从 1100m 变成 1000m，导航仍在进行，当前 Task 未完成，应该提醒一次。

边界 case

距离正好 1000m，运算符是小于等于，应该触发。距离 1001m，不应触发。

反向 case

导航已经取消，之后距离又变成 900m，不应触发原任务。

重复 case

距离在 900m、800m、700m 连续上报，不应重复提醒，除非产品明确要求周期提醒。

第四步：决定每一层谁负责

把规则写好以后，再把它放进系统。不要让 Planner、Trigger、Task 和工具互相猜责任。

工具 / HMIEval
层它要做什么它不能越界做什么
Planner / Director理解“提醒我”的意图，创建条件 Task，确定动作。不能假设端侧已经上报距离，也不能凭语言宣布条件已满足。
Task Service保存目标、TaskSpec、Run、状态、结束和取消。不能替代 Trigger 监听实时距离。
Trigger订阅事件、比较条件、处理一次性和频率规则、回调 Task。不能决定用户要不要收到长句回复，也不能自行改用户目标。
端状态 / VLM提供当前车况或观察结果。不能把未上报的事实假装成已发生。
执行通知、车控、导航等动作，返回成功或失败。不能吞掉错误，让上游只看到“没反应”。
验证三类 case 和第一次偏离层。不能只看最终是否说了一句话。

第五步：把车企和版本写进语义

你现在已经确认上汽和赛力斯的端状态要分开维护。原因很简单：同一句“剩余距离”，底层字段、单位、枚举或上报时机可能不一样。

维度必须记录不记录的后果
车企渠道上汽 / 赛力斯 / 其他拿 A 车企字段去判断 B 车企，测试结果虚假通过。
车型具体车型与座舱版本同一车企不同车型能力被误认为一致。
软件版本端、云、SP、PE/SFT、Trigger 版本旧结果和新结果混在一起，无法解释回归。
字段真值字段名、单位、枚举、上报周期、是否可订阅“设计支持”被误写成“实车支持”。
来源和 Owner文档链接、群消息、负责人、确认日期下一次继续找人问同样的问题。

第六步：把“模型能理解”与“系统能证明”分开

模型适合：理解用户的自然语言，判断用户是否在创建条件任务，发现“到终点”存在多个口径，生成需要确认的问题。
系统适合：保存任务，比较数字，判断时间到没到，监听媒体结束，处理权限和频率，记录真实执行结果。
失败示例

如果你只给 Planner 增加一条例子：“用户说到终点前 1km 提醒，创建 distance 条件”，模型可能会学会写出条件。但如果渠道根本没有稳定的 distance 字段，或者单位不是米，实车依然失败。示例解决了理解问题，解决不了事实不存在的问题。

第七步：用同一张表验收

交给产品：

一句用户话是否有唯一业务含义？如果有多个口径，默认规则和追问策略是什么？

交给研发：

每个字段从哪里来，TaskSpec 长什么样，Trigger 订阅什么，成功失败如何回调，日志看哪里？

交给测试：

正向、边界、反向、重复、取消、下电、跨车企和跨版本是否有 case？

交给现场：

车上出现失败时，能不能从同一张表找到当前版本、责任人和第一次偏离的位置？

你可以直接使用这句收口：
“我今天不先扩场景。我们先把这条能力的业务对象、状态、事件、条件、动作、渠道版本、结束条件和日志入口固定下来。表里没有证据的地方写未知，等真实 payload，不用口头补。”

练习：你自己填三条

练习要填的关键内容完成标准
距离终点 1km 提醒导航对象、剩余距离字段、单位、阈值、一次性、取消条件。能写出 900/1000/1001m 和取消导航四个 case。
歌曲结束后停止当前媒体 ID、结束事件、停止/暂停动作、工具返回、Task 结束。能证明事件确实上报，不能只证明 Planner 识别了话。
P→D 进入事件记忆原始信号、统一事件、时间戳、短期 Context、长期记忆、消费日志。拿到两个真实 payload，并确认记忆模块是否消费。
这三个练习做完，你对 Ontology 的理解就从“听过一个英文词”变成了“能把座舱一条能力写到可交付”。
