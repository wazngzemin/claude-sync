# Jeff Dean「1% 法则」对谈 Source 深读

## 一句话主旨

Jeff Dean 真正给出的是一套完整闭环：先挑通用模型几乎不会、但一旦解决就很有价值的问题；再用专有数据、上下文、工具和清晰规格把模型变成系统；让任务通过状态与检查点跨时间运行；最后靠快速评估器持续淘汰错误路径。

## 文章类型与 Fork 判断

- 类型：技术领袖访谈，兼具创业选题、Agent 系统设计和职业判断。
- 是否值得 fork：高价值。它同时回答了「做什么」「怎么做」「怎么越做越强」三个问题。
- 可复用代码：1% 机会筛选器、上下文闭环、长时任务状态机、脱轨诊断、评估器设计、12 个月品味复盘。
- 对用户的最高关联：用户当前负责车载 Planner、Context、工具调用、动态示例、任务与触发器。这些正好处于 Jeff 所说的模型周围系统层。未来转向具身智能时，1% 法则也可用来筛选具体方向。

## 逐段深度拆解

### 1. 「1% 法则」承担的是选题过滤器

- 原文定位：「去找模型成功率是 0% 或者 1% 的问题，而不是 20% 的。」
- 论证功能：为小团队划出与通用模型错位竞争的空间。
- 核心主张：当基础模型已经能做出 20%，通常意味着相关能力已经进入训练分布，后续模型升级可能迅速补齐剩余部分。小团队若只给这项能力包一层界面，很容易被下一代基础模型覆盖。模型接近完全失败的任务，说明关键能力、数据或环境仍在模型之外，小团队才可能通过垂直积累形成优势。
- 隐含假设：这项任务确实有客户价值；失败原因能够被专有数据、工具或系统工程补齐；团队有办法判断成功与失败。
- 精彩或破绽：精彩在于它把「模型现在很差」重新解释为潜在空间。破绽在于 0% 也可能代表伪需求、无法获取数据、无法评估或物理上不可行。低成功率只是第一道门，不是投资结论。
- 与你的直接关联：你不应把整个「智能座舱」或「具身智能」标成 1% 机会，要把它拆到任务级。直接车控指令可能已经属于高成功率能力；跨行程记忆、连续视觉观察、条件触发、长期任务闭环更接近基础模型单独无法完成的区域。

### 2. 两条护城河路径，私有数据与专用系统

- 原文定位：「组织你个人的信息」与「AlphaFold 式的专用模型」。
- 论证功能：回答小团队如何把基础模型的 0% 变成产品的高成功率。
- 核心主张：第一条路是拿到通用模型没有权限看见的数据，例如个人信息、企业流程、现场状态。第二条路是在窄问题上训练专用模型或构建专用系统，把小范围准确率做到很高。两条路的共同点是让竞争焦点离开通用语言能力，转向专属环境和闭环数据。
- 隐含假设：团队拥有合法、稳定的数据权限；数据质量足够；产品能在使用过程中持续得到反馈。
- 精彩或破绽：黄钊把它简化成「私有数据」和「小众模型」，方向正确，但容易让人误以为拥有数据文件就等于护城河。真正有价值的是数据能否持续进入决策、行动、反馈和再评估。
- 与你的直接关联：车内端状态、用户记忆、VLM 描述、任务进度、工具返回都属于通用模型看不到的现场信息。你的价值不在于把这些字段塞进 Prompt，而在于决定何时加载、怎样表达、缺失时怎么降级，以及如何验证它们真的提升了任务成功率。

### 3. 「Agent 跑几周」说的是任务寿命，不等于一条对话跑几周

- 原文定位：「可以让它们连续跑上几天甚至几周，去完成真正非常复杂的任务。」
- 论证功能：打破人们对 Agent 只能做短任务的想象。
- 核心主张：只要任务可拆解、环境可访问、结果可检查，Agent 可以在很长时间内持续推进复杂目标。文中软件跨语言重写之所以适合，是因为旧软件、测试和行为对比共同构成了清晰规格。
- 隐含假设：运行环境稳定；任务可以保存状态；失败后可以恢复；每个阶段有验证方式；成本和权限受到控制。
- 最容易的误读：把长时 Agent 理解为让同一个模型维持超长上下文并不停思考。更可靠的系统会把目标、进度、快照、检查点和结果持久化，每次唤醒只进行一次短推理。
- 与你的直接关联：「宝宝哭了告诉我」可以持续两小时，但模型无需连续推理两小时。更合理的链路是创建 task_id、订阅视觉或状态事件、等待、被事件唤醒、读取最新快照、判断、执行、验收，然后继续等待或关闭任务。这与 Task、Trigger、Context 的分工天然一致。

### 4. 上下文工程是文章对你当前工作的直接命中

- 原文定位：「把作为人类会采用的方法，以模型能用的形式交给模型。」
- 论证功能：把 AI 竞争从单纯训练模型扩展到模型周围的整体系统。
- 核心主张：训练数据被压进参数后很模糊，当前上下文是模型此刻直接看到的信息，因此它更容易被工程化控制。上下文工程包含检索、工具、记忆、历史、任务分解和相关经验。提升方法也很朴素：让模型做真实任务，观察失败，把人的解题方法写成它能执行的规则或 skill，再用同一问题验证。
- 隐含假设：失败主要来自信息、方法或工具缺口；基础模型仍具备执行这些方法的能力。
- 精彩或破绽：黄钊说这是普通团队「唯一能和大厂同桌的战场」，这比 Jeff 原话更强。Jeff 的原意接近「任何团队都能参与」。普通团队确实有机会，但大厂在工具链、分发、数据和算力上仍有优势。
- 与你的直接关联：SP 是总体规则，Context 是当前世界，动态示例和 skills 是解题方法，工具是行动能力，Task 与 Trigger 负责跨时间唤醒，eval 是裁判。你的岗位价值在于把通用模型组装成能在车里可靠工作的系统，远不止模型外层的零碎配置。

### 5. Agent 第 30 步脱轨，是分布外加开环

- 原文定位：「一旦稍微偏离它知道怎么做的那个分布，性能会突然开始劣化。」
- 论证功能：解释长链路为什么会从局部小错变成整体失败。
- 核心主张：模型在熟悉任务上表现好，进入陌生状态后错误率会上升。若系统没有阶段性反馈，小错会继续写入后续上下文，形成越走越偏的开环。Jeff 提出两类补救：用 skill 和提示限制行动范围；让多个 Agent 探索，再由评估器选择更有希望的路径。
- 隐含假设：评估器比执行者更可靠，或至少能过滤明显错误；并行探索的收益高于额外成本。
- 边界：在车控等安全场景，运行时并行生成多个方案再投票未必合适。高风险动作需要确定性边界、权限检查和明确回执。多路径搜索更适合离线方案探索或低风险规划。
- 与你的直接关联：动态示例可以照亮局部路径，工具反馈提供闭环，A-F 分诊避免把链路问题误判成模型问题。下一步应补「失败发生在哪一步」的轨迹评估，单看最终答案很难知道是 Context 缺失、工具选择错误、下游失败还是模型推理错误。

### 6. 能量账告诉产品经理，体验瓶颈可能不在模型聪明度

- 原文定位：「把数据从 HBM 搬进处理器，能量上差一千倍。」
- 论证功能：展示底层系统约束如何决定上层产品形态。
- 核心主张：计算硬件里，搬运数据可能远比做一次数学运算昂贵，因此 batching、内存层级和专用硬件会直接影响成本与延迟。低延迟产品很难依赖大批量摊薄成本，所以需要在硬件、精度、缓存与数据路径上做专门设计。
- 隐含假设：文中的量级针对芯片内部数据移动，不能直接套成「云端传输一定比推理贵一千倍」。
- 与你的直接关联：车内体验受端云往返、VLM 上报频率、上下文体积、缓存命中、工具回调和模型推理共同影响。产品经理应先画完整延迟账，再判断问题来自模型、网络、数据组织还是下游执行。文章的「延迟好 50 倍」适合用来做产品想象，但不能当排期承诺。

### 7. 自动化科学方法的发动机是评估器

- 原文定位：「瓶颈常常在评估器」与「每单位算力换来的发现数量」。
- 论证功能：把 Agent 从自动执行升级为自动试验和自我改进系统。
- 核心主张：自动系统可以提出候选、运行实验、评估结果、保留有效路径，再进入下一轮。循环速度取决于评估器是否足够快、足够接近真实目标。量子化学案例中，用近似模型替代极慢模拟器，改变了可尝试候选的数量级。
- 隐含假设：评价目标能够形式化；近似评估与真实结果高度一致；优化指标没有被投机利用。
- 边界：人类满意度、主动服务是否打扰、长期信任等指标很难被单一自动评分器覆盖。需要规则、模型评审、人工抽检和线上反馈组合。
- 与你的直接关联：评测集不能只做版本验收，它应该驱动 SP、Context、工具描述和动态示例的每次改动。现有材料中曾记录一次从 79.38% 到 88.38% 的优化，这正是闭环证据。更进一步，要记录每个增益由哪条规则或上下文改动造成，避免只看到总分变化。

### 8. 规格与品味，分别解决「怎么做」和「做什么」

- 原文定位：「说清楚你要什么的重要性反而上升」与「大半场仗打的是把时间花在哪个问题上」。
- 论证功能：在 Agent 能力变强后重新定义人的稀缺价值。
- 核心主张：规格越清楚，Agent 越容易稳定执行；软件翻译效果好，是因为原实现和测试本身就是详细规格。品味则负责选择值得写规格的问题。Jeff 给出的训练方法是写下未来 12 个月的重要判断，事后逐条对账，用真实结果给自己的判断力积累样本。
- 隐含假设：人类在选题上长期领先模型。这个判断尚未被证明，至少今天仍有现实价值。
- 与你的直接关联：你擅长把任务拆细并大量产出，但容易把「写得多」当成「判断得准」。这篇文章要求你先选一个值得承担的目标，再写清成功标准。动态示例数量增加不自动等于系统更强，只有召回正确、行为改善且没有副作用才算有效。

### 9. 黄钊「把事情想大」需要再加一层闭环判断

- 原文定位：黄钊把 1% 法则列为「大事」的检查标准，并提出新品类、builder/owner、FDE 等判断。
- 论证功能：把 Jeff 的创业建议转成个人职业选择。
- 核心主张：新品类和模型低成功率确实能帮助寻找长期机会，但它们仍不足以证明方向成立。一个值得投入的大问题至少同时满足三点：结果很有价值，通用模型单独做不到，团队能通过专有数据与快速评估持续提高成功率。
- 独立判断：FDE 不应被看成 AI PM 转型失败后的退路。对需要现场数据、业务翻译和部署反馈的 1% 问题，FDE 可能正是形成专有闭环的核心岗位。用户未来转具身智能时，更适合寻找能同时拥有客户现场、评估标准和产品回流权的岗位。
- 与你的直接关联：不要用「2030 年以后才普及」作为等待理由。这类年份缺乏可验证依据。更稳妥的做法是现在积累可迁移闭环，每 6 到 12 个月根据模型能力和岗位市场重新判断。

## 完整论证链

通用模型会持续扩张能力边界
→ 已经能做出 20% 的浅层产品容易被覆盖
→ 小团队应寻找基础模型几乎失败但结果很有价值的问题
→ 通过私有数据、专用模型、工具和清晰规格把通用能力嵌入垂直系统
→ 通过 Task 状态、检查点和反馈让 Agent 跨更长时间工作
→ 用 skills 限制错误路径，用评估器筛选候选与发现失败
→ 把「提出、执行、评估、修正」循环自动化
→ 最终人的稀缺价值向选题品味、规格定义和目标判断集中。

## 全文隐含假设

- 基础模型在未来 6 到 12 个月仍会快速增强，且增强方向可由今天的部分能力判断。
- 任务成功率能够被可靠测量，至少有可接受的近似评估器。
- 团队能持续访问专有数据，并合法用于系统改进。
- Agent 的执行环境、工具权限和状态持久化足够稳定。
- 人类仍比模型更擅长决定哪些问题值得做。
- 推理成本和延迟会继续下降，使长时 Agent 的经济账成立。

## 误读警告与边界条件

1. 「0% 就值得做」是错的。伪需求、无法评估、无数据权限的问题同样是 0%。
2. 「20% 就应该放弃」过于绝对。若产品要求 99.9% 可靠性，且剩余差距来自私有现场、合规、工具执行和服务网络，系统公司仍可创造价值。
3. 「Agent 连跑几周」不等于维持一条几周长的对话。长期任务依赖持久状态、事件唤醒、检查点和恢复。
4. 「上下文工程只要一个 API」低估了工程难度。API 是入场券，数据权限、工具稳定性、评测和分发仍然昂贵。
5. 「多 Agent 投票更可靠」没有普遍成立。在相同偏差下，多个 Agent 可能一起犯错。
6. 「品味是最后壁垒」也可能随模型持续学习而衰减，因此要把品味落实为数据、关系、评估和产品闭环。

## 对黄钊七条认知的优先级判断

| 黄钊观点 | 对你的优先级 | 判断 |
|---|---:|---|
| 把事情想大、新品类 | 高 | 加上价值、1% 缺口、闭环能力三道门后可用 |
| AI PM 要变成 builder/owner | 高 | 你需要能亲手搭评测与原型，不要求转成算法工程师 |
| FDE 是转型方向 | 高 | 适合把你的现场落地能力迁移到具身智能，但要看经验能否回流产品 |
| 世界模型缺少动机和场景数据 | 中 | 指出了数据缺口，但「不可能」说得过满 |
| Token 爆发利好存储 | 低 | 与你当前产品和职业决策距离较远 |
| 疾病趋势 | 低 | 与本文论证无关，需要独立医学证据 |
| 2030 后才长期普及 | 低 | 是时间预测，不宜用来决定是否现在行动 |

- 与《复杂、边界清晰、端到端》连接：1% 问题往往复杂，但必须能写出清晰规格和评估边界。
- 与《白领大逃杀》连接：harness 持续运营的价值，在本文被进一步解释为上下文工程和评估闭环。
- 与《FDE 专题》连接：FDE 的长期价值来自获得现场私有数据、挖出隐性需求，并把部署反馈沉淀回产品。
- 与《需求爆兵》连接：代码变便宜只解决执行成本，1% 法则与品味负责决定哪些需求值得爆兵。
