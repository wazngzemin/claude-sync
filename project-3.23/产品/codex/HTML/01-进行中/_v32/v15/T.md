## 12｜任务生命周期

导航出发之后，主驾又补一句“快到时提醒我拿泳镜”。这句话和前面所有请求都不一样，它要的不是现在做什么，而是将来某个时刻到点替我提醒一声。这一章讲这条提醒怎么被接住、存好、登记，再等到条件命中、重新回到主对话执行，最后把结果记到正确的那一轮上。即时任务这一轮当场办完，长期任务则跨越本次同步会话，可以等待未来时间、等待某个条件、按周期重复触发，也可以跨多个步骤持续推进；“现在关一下座椅加热”仍然走即时车控，不进任务系统。

任务系统的规矩是：创建受理不等于目标完成。先把任务存下来、把叫醒规则登记好，然后耐心等待；条件命中后再由 Director 重新规划、执行、回写状态。到点是谁判断“快到了”，归云端触发器那一章讲。本章还要分清两条车型渠道：赛力斯走自建 Task Service，上汽走 Extour Goal 托管，两条线保存对象、创建回调和取消方式都不同，不能当成同一套实现。Director 怎样理解和规划每一轮归第 05 章，触发器怎样判断条件归第 13 章，本章只讲任务从出生到结束的完整生命周期。

## 先选渠道：谁拥有这条长期任务

**T13（渠道路由：谁拥有长期任务）**先选这辆车由哪一套系统托管长期任务。这一步要解决的问题是：不同车型接入的后端任务服务不一样，如果不先定归属，同一条提醒可能被两套系统各自存一份、各自到点触发，用户就会收到重复提醒，两边状态也对不上。赛力斯渠道由自研 Task Service 统一管理时间、条件、周期目标和 GUI（图形用户界面任务，区别于语音创建）多步任务；上汽 saic-dna 渠道由 Extour Goal 目标引擎托管。两条线保存对象、创建通知和取消方式都不同，这一步是按车型二选一，不是所有渠道都已经迁移到同一套服务。

为什么要按渠道分开，而不是先做一套统一服务再切流，是因为两条车型线的后端已经各自落地：赛力斯沿用自研 Task Service，规则匹配复用现有触发器，具体动作仍由 Planner、Agent 或 Tool 承担；上汽的目标、触发条件判断由 Extour 维护，AIDV 只处理回调并下发车端。强行在一期合并，会同时改动两套已经联调的链路，风险高于先按渠道隔离。同一个任务不能被两个系统同时接管，渠道判断在任务入口完成，后续创建、等待、触发、回写都沿选定渠道走。任务服务的模块定位、对象划分和创建触发回写主流程见[Task Service One-pager](https://bytedance.larkoffice.com/wiki/A60Zwzy9eiiCtwkY8k2c0LKKnoc)，赛力斯一侧的内部模块分工见[Task 任务管理设计技术方案](https://bytedance.larkoffice.com/wiki/B2WYwXFOIigKzbk7aSYcJWmZn2E)。

## 接住诉求，先认出是新增、修改、取消还是查询

沿赛力斯这条主路往下。**T01（接住未来或持续的诉求）**接住这条诉求，让系统记住时间、对象和动作；此刻不能做任何车控，用户得到的只是“安排被接住”，十分钟后的真实提醒还要经过另一轮触发。这一步解决的问题是把“将来做”和“现在做”分开：如果创建阶段就去执行动作，定时提醒会在说出口的瞬间立刻触发，条件任务也等不到条件命中。Director 只负责把任务文本和类型标识透传给任务入口，自己不判断创建、修改、取消还是查询，也不生成任务规格。这样分工的原因是任务语义结构化、生命周期管理属于任务服务的职责，Director 保持单轮推理职责单一；如果让 Director 直接生成任务规格，跨轮状态、规则注册和结果回写都要挤进主对话链路，主链会被长期任务拖住。即时车控仍然走即时链路，比如“现在关一下座椅加热”不进任务系统。

**T02（弄清要办哪一件事）**先辨认用户这次是在新增、修改、取消还是查询。赛力斯一侧先查询现有 TaskView 任务视图，再由规格构建器决定增、改、删、查四种操作中的哪一种。四种操作分别是 create 新增、update 修改、cancel 取消、query 查询。“改成二十分钟后”要结合现有任务找到刚才那条；“取消刚才那个”走 T11；“还有什么提醒”走查询。修改和取消必须先定位到原任务，不能凭一句“刚才那个”新建一条，否则旧任务留在后台继续触发，用户以为已经取消，到点却又被叫醒。定位依据是任务视图里的任务 ID、创建时间和当前上下文，多任务并存时定位不到就要澄清，而不是猜一条执行。

## 关口：条件能被看见，动作能被执行

**T03（条件能看见，动作能执行吗）**是金底关卡，依次检查对象、观察条件、动作和结束策略，核对实际信号、工具、开关和配额能不能支撑。这道关口解决的问题是避免系统答应一件自己做不到的事：条件感知不到、动作工具不存在、任务数量已经到上限，硬注册成功只会在到点时失败，用户体验比当场拒绝更差。“到那里提醒我拿泳镜”还缺目的地，要先补问；项目拿不到可靠的导航进度信号，就不能先答应“快到”。条件感知不到的目标必须拒绝或澄清，例如“副驾吃没吃饭”系统无法感知。条件任务本质是 If-Then 结构，即满足某个条件时再执行某个动作，触发器的执行动作固定为“通知 Planner 条件任务触发”，真正的条件任务动作由 Planner 推理和工具调度，触发器本身不直接执行车控。

注册规则上，条件任务注册时如果 query 里包含任意一个不存在的条件，整个任务无法注册成功，而不是只丢掉那个条件；可解析范围限于已接入的端状态、VLM（视觉语言模型）、时间和编排条件。注册结果要回报 Planner，失败必须带原因，条件任务的注册、修改、取消和触发口径见[触发器条件任务需求](https://bytedance.larkoffice.com/wiki/GCfiwlJJei6fY7kYIOhcBXcxnlc)。信息齐备才建立可靠安排；这一步不卡住，后面存任务、登记规则都会建立在错误前提上。

## 先存任务，再登记叫醒规则

条件和动作都成立，进 **T05（先保存 Task，再登记触发）**。这里要分清三类核心对象，二期再扩展步骤对象。Task 保存用户目标和生命周期，TaskSpec 描述触发方式、约束、执行内容与结束条件；Run 保存某一次实际执行，周期任务每次触发产生一轮独立 Run；Event 留下状态变化事实，比如触发命中、执行成功、执行失败、用户取消、端状态变化，用于审计和状态推进。此外 Binding 保存外部请求与任务的关联，TaskView 是供 Planner、车端和其他服务查询的结构化只读视图，TaskMessage 是状态通知协议；二期才引入 Script 执行计划、Step 步骤和 Action 调用。整条长期目标、它某一次执行、状态变化记录三者各管各的，不要混在一起：一次 GUI 多步操作共享同一个 Run，GUI Agent 管理内部步骤，任务服务只管理外层 Run 状态。

保存成功和注册成功是两件事，任务记录写进数据库不等于叫醒规则已经交到触发器。先存 Task 再登记触发的顺序，是为了保证规则回调回来时一定能找到任务对象；如果先注册规则再存任务，规则先命中时任务记录可能还没落库，回调就找不到归属。

存完进 **T04（登记什么时候再叫醒任务）**，按时间、条件、周期或视觉把规则注册给触发器，由 Trigger Adapter 适配层把任务规则转成现有触发器协议，并补齐回调、作用域、来源等传输字段，保存任务与回调的关联；视觉类任务还要把整份观察目标交给视觉观察通道。任务侧不维护第二套规则描述语言，直接复用触发器统一的规则类型，避免两套条件口径漂移。注册失败不能宣告任务已经进入正常等待，必须把失败结果回报给主对话；规则没注册成功，任务记录只是一条数据库里的孤儿记录，永远不会被叫醒。

## 等待期间不占用 Director

规则注册成功才进 **T06（等待下一次触发）**。用户继续正常聊天，Director 不需要一直占着推理等车开到地方，任务系统自己托管等待；周期任务每次有效激活产生一轮独立 Run。定时、条件、视觉等待都在这一阶段挂起，车辆下电等强信号会作为事件进入任务服务，影响整条任务的生命周期。Task 的生命周期状态只有 waiting 等待激活、running 执行中、closed 已关闭三档；一轮 Run 内部还有执行中、等待用户确认、等待客户端、等待外部结果等阶段。把等待状态放在任务服务而不是 Director 上，是因为一次等待可能持续几分钟、几小时甚至跨多天，Director 每轮推理都要占用模型和上下文，长期挂在主链上既浪费算力也会干扰新请求。

这里有一个状态命名陷阱：技术方案里的 waiting 指等待激活，界面早期版本的 waiting 却写成创建中，两者不是同一个状态，后面 T22 专门讲这个映射问题。车辆下电属于强状态事件，和普通端状态不同，直接进入任务接入入口影响生命周期，而不是只作为普通背景供触发判断。

## 触发回调：任务还有效吗

等车辆真正接近目的地，触发命中回调交到 **T07（触发来了，任务还有效吗）**。触发器已经完成原条件判断，任务服务不重复判断原条件，先恢复任务、再创建本轮 Run；随后查三件事：原任务还有效吗、回调是不是重复的、执行前有没有额外限制。用户刚取消了提醒，迟到的旧回调不能让任务重新启动；存在额外执行前约束时才读取 Context 决定执行或跳过，例如座椅无人就把本轮记为跳过。无人等待的情况可以直接跳过本轮，不强行唤起主对话。

这一步要做三重校验的原因，对应三类真实故障：任务已取消或过期，迟到回调复活旧目标；同一事件重试产生重复回调，导致一轮任务被执行两次；执行前提已经变化，任务在不满足条件时仍然执行。回调事件携带任务 ID 和回调 ID，任务服务据此做幂等去重；执行前约束按规则或模型判断，需要车辆、端、乘员、用户状态时再读取 Context。Guard 跳过本轮时，周期任务回到等待，一次性任务按结束策略处理。

## 建议交回 Director，本轮再规划

允许执行后走 **T08（把本次建议交回 Director）**。这一轮先把 Task、Run 和推荐标识绑定，再经 Recommend 推荐通道、Frontier（AIDV 内的主动消息下发通道与协议）主动消息通道通知车端，客户端携带推荐标识回流到输入管理，Director 结合当前情境决定这一轮怎么说、做什么。技术上任务服务先生成推荐 ID 并持久化绑定关系，再调用推荐和通道下发；回流时凭车辆 ID 加推荐 ID 恢复 Task 和 Run 关联，客户端不需要新增任务 ID 或 Run ID。

这样设计是因为触发器只负责通知“条件命中”，真正的动作仍然由 Director 收到通知后推理调度，触发器不直接执行车控。把执行权留在 Director，才能结合当下情境决定话术、合并已有任务、判断是否需要澄清；如果触发器直接下发车控，就会绕过记忆、上下文和冲突管理，在多任务并行时容易发出互相矛盾的指令。

## 拿到真实执行结果再记账

**T09（拿到真实执行结果再记账）**要等执行结果回来才入账，不是建议一生成就办完。Flow 汇总真实的 Agent 和 Tool 结果，由独立的 Result Hook 结果钩子更新 Task 和 Run；成功、失败、跳过分别记到正确的那一次执行上。这里要解决的可靠性问题是：原有主链路收尾是异步、尽力而为的通用流程，不保证任务状态一定可靠写入，因此任务系统单独增加结果钩子，基于结构化的工具或智能体反馈，以幂等事务更新 Run、Task 和 Event，写入失败要支持重试或补偿。

Run 的终止状态分为 succeeded 成功、failed 失败、skipped 跳过、canceled 取消、running 进行中；Task 的关闭原因分为 finished 完成、canceled 用户取消、expired 过期、failed 失败、vehicle_offline 车辆下电。“正在处理”、工具已受理、语音播完三者不能互相顶替：TTS 播完不等于任务成功，受理回执不等于车辆真实状态已经改变。一轮 Run 的结果写入之后，才允许判断整条任务下一步走向；事件用于审计和状态推进，Run 表示执行轮次，两者不重复记录。

## 继续等，还是结束整条任务

入完账沿 **T10（继续等，还是结束整条任务）**判断后续。结束策略 EndPolicy 包含成功后是否关闭、车辆下电是否关闭、过期时间、最大执行轮次、最大失败次数几项配置。单次提醒按结束条件关掉整条目标；周期任务回到 T06 等待下一次触发接着等；失败或跳过时要不要续跑，按该任务自己的结束策略单独定义，一轮失败不必然关闭周期任务。外部结果和任务走向的对应关系是：执行成功后按策略关闭整条任务或回到等待；执行失败达到失败策略才关闭，否则回到等待；守卫条件跳过本轮时周期任务继续等，一次性任务按策略结束；用户取消或车辆下电直接关闭整条任务。满足结束条件后同步清理规则和任务视图。

**T18（终止后截断迟到回调与旧目标）**处理任务结束后的收尾：取消、下电、过期都按各类策略关闭，停掉规则、更新有效视觉观察目标，避免车端继续盯着已经失效的旧目标。直接 GUI 任务在途停止的处理仍待验证；迟到回调不应再推进旧任务，已经执行过的动作也不会因为删除任务卡片被自动撤回。属于主动服务子目标的任务被删时，还要通知主动服务侧同步状态。

## 用户中途改主意：修改、取消、暂停

等待期间用户也可以主动改主意，走 **T11（用户修改、取消或暂停）**回到原任务处理。修改要更新任务规格与原规则，重新回到 T03 核对条件；修改条件走触发器更新规则，修改动作时触发器只改写任务原文，真正动作仍由触发后的 Director 重新推理。取消要关闭目标、清理规则、停止后续触发。当前一期普通取消链路尚未覆盖直接创建的 GUI 任务，删除和系统预设暂停在一期支持，循环任务暂停属于二期；多用户并发、重试和用户取消场景仍待验证。修改和取消都必须先定位原任务，定位失败要澄清；修改条件和修改动作走不同处理路径，是因为条件由触发器维护，动作由触发后的 Director 推理，不能把动作改动写进规则。

## 任务中心视图与语音边界

**T12（TaskView查询与任务中心展示）**让用户在任务中心看到这件事。创建事实形成可查询视图，任务结束时同步终态；只有本轮是语音查询，才把查询结果回给主对话，查到一条任务不等于它已经执行完成。任务中心分“我的任务”“AI 服务”“场景预设”三个分区：我的任务来自任务管理模块的定时、条件和长时任务，AI 服务来自主动服务静态 Advisor 子目标，场景预设来自系统预设任务。任务全量状态包括创建中、进行中、暂停中、已结束，我的任务分区只展示进行中和暂停中的任务，AI 服务和场景预设展示全部。

数量与排序上，我的任务上限 46 条，即定时 20 条、条件 20 条、通用长时 6 条，AI 服务和场景预设不设上限；分区排序固定为我的任务在前、AI 服务居中、场景预设在后，我的任务内部按创建时间由新到旧排列，单行展示三个任务单元。任务更新由云端主动推送一次，车辆上电时客户端主动拉取一次；界面状态必须和后台真实事实保持映射，任务中心入口有 AI Bar 暂态入口和 Applist 固定入口两处，持续任务超过两个时 AI Bar 才出现更多任务浮窗。展示策略与分区数量见[任务中心 PRD](https://bytedance.larkoffice.com/wiki/LUKKwMTNaiAd53kdmpkc5oILn5e)。

**T21（任务中心不支持语音点屏）**和可见即可说例外是同一条规则：多个任务并排时用户说“第二个”，系统不知道指哪一条，任务中心页面暂不支持语音点屏；可见即可说不是全屏承诺，具体控件可点范围归第 09 章，该口径已落地。

**T22（waiting 字段要做业务映射）**记录一处状态命名冲突：技术方案里的 waiting 是“等触发”，任务中心界面里的 waiting 却写成“创建中”，同两个字不是一个状态，端侧对接前必须先做业务映射，不能直接照搬字段名显示。

**T23（三处展示数据未同步）**是仍在梳理的问题：任务岛、AI Bar、任务中心三处数据还没对齐，用户在不同位置看到的条数可能不一致【待核】，验收时要分别核对三处数据源。

## 上汽平行分支：Extour Goal 的创建、回流与状态

右边上汽那条平行分支只做对照。**T14（上汽：提交并创建）**通过 add_goal 接口把目标和上下文交给 Extour 托管，Extour 负责维护目标和触发条件；creating 状态只表示请求已经受理，不代表目标建成。静态 Advisor 仍然另行运行，不在这条 Goal 链路内。创建工具只给出类型和目标文本，AIDV 从主对话补齐 query、历史和车辆身份，上汽请求使用 saic-dna 渠道标识，回调时校验设备当前登录账号。

**T15（上汽：创建成功直出 Goal 卡）**区分创建前后话术：创建前可以播报铺垫话术，creating 受理中和创建成功后都不播报成功，只同步状态；创建成功直接显示 Goal 卡，创建失败才回流 Planner 说明原因。创建卡不等于触发，更不等于实际执行完成。创建结果分 create_success 直接下发创建卡、create_failed 把原因转成推荐回流播报两类；回调成功不代表用户已经听到播报。

**T16（上汽：触发建议经客户端回流）**规定触发后的回流路径：条件命中先发出 Recommend 执行建议卡，首跳不播报；用户操作或系统默认后二次上行回到 Director。7 月 1 日方案约定无操作默认执行；同一时刻多条建议按当时最新一条生效，不排队等待。标识缓存上，request_id 关联创建、缓存 60 秒，recommend_id 关联推荐回流、缓存 10 分钟；不同触发应使用不同幂等键，同一次事件重试复用原键，不能只按 Goal ID 去重。建议回流的接口与状态口径见[动态 Advisor One-pager](https://bytedance.larkoffice.com/wiki/VvAMwHbxei6BSEkzoxjc9AbynNh)。

**T17（上汽：消费、关闭和 done 分开）**把三个状态拆开：consumed 表示建议进入 Planner，不等于目标完成；close 是关闭目标；finish 只同步端侧 done。循环开关 switch 把循环目标设为开或关，关闭含对话删除目标，关闭后另发端侧完成通知；Goal 状态和 Task 状态需要按渠道分别映射，update 修改入口和消费回报路径目前仍待补齐，重新开启后的补触发、关闭生效时点和在途推荐处理需要与 Extour 联调确认。

## 任务分类、数量上限与双云清理

**T19（任务四类与数量上限）**把任务分成常识跟进、条件触发、AI 主动、系统预设四类；画板登记常识跟进不超过 6 条、条件触发不超过 40 条，AI 主动和系统预设各是有限集，排序按常识优先于条件固定排列，该口径为赛力斯 9 月 8 日外审结论，状态已落地。任务中心 PRD 对“我的任务”给出的上限是 46 条，即定时 20 条、条件 20 条、通用长时 6 条，两套分类和数字口径存在渠道与版本差异，对外引用前先确认车型采用哪一版【待核】。

**T20（双云分工与退登清理）**登记两侧云端分工：常识跟进和条件触发存在字节云端，AI 主动服务和系统预设存在另一云端，两侧由统一入口封装对接、拉取组装；账号退登只清空当前账号关联的前两类，和车辆绑定的后两类保留；车辆上电时主动拉取全量任务。事件日志客观按时间轴记录车辆行驶和停留过程中的各类事件以及事件与任务关系，不加工、不总结，供其他模块取用作为背景素材，事件记录与任务的归属边界见[事件日志产品需求文档](https://bytedance.larkoffice.com/wiki/Gt9qwfzlHiIKLgkWKCfcqYsYngg)。

## 验收要点与待核边界

评审这一章首先要分清创建受理、规则注册、触发执行、真实结果四个状态，不能混用，受理成功不能对外说成任务已经完成。修改和取消必须先定位原任务，定位不到要澄清而不是新建。触发回调要做任务有效性和去重校验，迟到的旧回调不能复活已取消任务。结果回写依赖独立结果钩子，不能指望通用异步收尾保证状态可靠写入，失败要支持重试或补偿。三个界面位置的任务条数以后台真实事实为准，展示层状态先完成业务映射再上线。

从工程保障看，任务定义、运行结果和状态变化持久化保存，支持沿触发与执行链路定位问题；已有回调去重、修改与回写校验、异常记录和部分状态修复能力；状态变化通过消息通知车端，通知失败不回滚已保存状态，展示需要结合查询更新。二期独立 Task Agent、通用长时复杂任务、Script 执行计划、步骤记录和断线恢复属于方案规划，尚未实施；GUI 多步任务的多用户并发、重试和用户取消仍需验证；赛事播报、视觉情绪判断、导航行程事件等场景依赖真实数据源和感知能力接入，交付范围以实际联调结果为准。到这里，一句“快到时提醒我拿泳镜”从被接住、被存好、被登记，到等车快到被叫醒，前台这一段就走完了；谁在云端站岗、怎样判断条件命中，是第 13 章云端触发器要讲的事。
