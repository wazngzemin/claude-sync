# 专家知识\-现状及后续规划思路讨论

## **一、当前的专家知识**

[赛力斯knowhow知识](https://bytedance.larkoffice.com/wiki/Ew67wKzi3ihf8WkpwsTcFAO9ncd?sheet=a52561&range=MTox)

截取了一部分之前写的专家知识，这个知识按照场景分级（一般到第三级或第四级）



**存在的问题**

**（1）专家知识质量低**

1. 知识本身没有比较统一的结构，可以看到三个“场景要点”完全对不上

2. 知识本身质量良莠不齐，比如这个已经是一个具体case的怎么分析思考的了，没有通用性

执行逻辑上也有很多先入为主的东西，比如默认会跨省

3. 很多知识里的内容根本无法使用，条件是完全不具备的



**（2）专家知识的使用时机不佳**

知识是按照场景来组织的，但检索主要考虑的是query，虽然也考虑了其他context，所以很多场景是不一定能对得上的。因为当前其实没有一个专门的模块来判定场景。

# 筛选知识时的原则
## 原则1：场景绑定推理
- 知识高度依赖于场景。需结合用户Query、对话历史、车辆状态、舱内视觉等信息，推理当前所处的**具体场景**（如"展厅看车"、"地库泊车"、"通勤堵车"、"晕车不适"），再匹配对应的知识ID。
- 场景判断应优先参考表格中的三级场景粒度，四级场景提供更细分的场景定位。

## 原则2：关注环境变化
- **趋势比绝对值更具决策价值**
  - 温度急剧变化 → `COM-01-01-01`（调温度）
  - 车内人数增加 → `EMO-01-01-01`（迎宾打招呼）
  - 车辆进入地下停车场 → `DRV-01-02-02`（知晓停车位置）

## 原则3：目标持续关联
- 关注进行中的目标。**只要目标存在，支撑该目标的知识应持续保留**，除非当前用户query表示明确终止。
- 目标变更时，及时移除旧目标相关的知识，加载新目标所需知识。

## 原则4：增量更新原则
- 对比已加载的知识，仅输出**变化部分**。
- 已加载知识在当前场景失效则应删除。

## 原则5：信息不足时不虚构
- 若需求模糊且无法从输入中推断具体场景，`add_knowledge_ids` 保持为空，在理由中说明需下游进一步确认。

## **二、回顾我们对于专家知识的期待**

- **在各类任务上能表现得更好，真正像一个专家能满足好人的需求期待，要真正达到这个专家的感觉**

    - 对什么是“好”和“差”有认知有判断能力

    - 为达成“好”的任务结果，会持续review主动发现问题，主动持续地行动来靠近“好”的结果

    - 能关注到细节context，做出正确的行动决策

- **在特定时机再使用加载，聚焦注意力的同时，节省token（省成本）**

- **对于用户来说，感受就是豆包做很多事儿都很专业：**

    - 操心更少（大部分思考可以放心交给AI）

    - 收获更多（比如更多情绪价值、实际物理价值）

    - 表现具有稳定性（再做类似的事情/任务或处于相似的情景时能不能依然表现良好）

### 3\.1 专家知识放在哪

- DT里保留一些

    - 弱领域特性的一些专家知识（比如怎么聊天更有趣、更能安慰到人\.\.\.）

    - 复杂任务澄清和拆分的专家知识（能让DT比较好地理解用户需求转化为任务）

- 长时目标类的知识可以考虑下放到task\-agent里

### 
3\.2 专家知识的形态

#### 3\.2\.1 专家知识的整体结构形态

（1）按照情景类别来组织是没问题的，覆盖的场景类型是比较完整的

- 但问题可能在于这些知识到底如何能顺利被检索、有效运行，通过什么方式运行

（2）知识其实可以考虑分成“点、面、体”三个层次，不同层次的知识的形态和承载落地这些知识的架构也不同

- 点（某个特定任务的体验）

- 面（某类情景、长程任务的体验）

- 体（完整的一种行程的体验，比如一次自驾游，综合的体验，覆盖了多个情景面）







#### 3\.2\.2 单条专家知识的形态

单条知识的形态上其实也取决于是用dt还是其他模块，跟agent本身的设计强相关，但范式上如果能有统一性会更好。

（1）有文字化的精炼知识陈述

（2）有ReAct式的示例，每步中带思考过程，用以强化思维范式和泛化性





### 3\.3 专家知识的检索

（1）根据query检索

（2）根据维持中的task/goal来匹配检索

（3）根据当前的情景类型和context来检索和维持
