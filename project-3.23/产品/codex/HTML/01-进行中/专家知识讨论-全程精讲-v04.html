第 2 章 逐段精讲

场景 1｜开场先“翻旧账”：3 月那版知识为什么不行（05:54–07:25）

会上在说什么。 最早二三月份让赛力斯写了一版专家知识，结构是按照嘉锋那边整理的“专家测试集”来的：把场景分成一、二、三、四级，覆盖各种出行领域。结论是问题很多——结构本身是当时比较赶想出来的，不一定好；内容质量也非常差。

具体差在哪。 举的例子是“周末游”：里面写了“哪里有 EVA 的地方”“小众潮的地方”“几点钟去吃饭”。这些是某一次测试的具体要求，应该和那条 case 挂钩，却被当成通用知识写了进去。会上还翻出另一条：“这个其实是当时我写的（看病的知识），它是通用性的，不是针对某一个具体 case 的——一旦针对具体 case，它就不通用了。”

还有更麻烦的一层。 很多知识里写了“感知条件”“执行条件”，但这些条件当时根本还不具备，被写成了任务的触发条件和判断条件。本质判断是：他们把 knowhow（怎么做才对的经验）和考察点（这道题考什么）搞混了。因为在专家任务集里，这两样是混在一起写的，结果 knowhow 没写清楚，考察点也没写清楚。

这一段的方法。 他们不是直接说“重写一版”，而是先分对象：这是知识、是案例、是考察点，还是用户偏好？对象没分清，后面存哪、怎么取、怎么验收都会乱。

如果你在现场，可以接。 “我先确认口径：这条是所有类似场景都成立的原则，还是这个 case 的条件？如果以后进知识库，适用范围要不要单独写出来？”

场景 2｜知识不是写在本子上就行：什么时候取出来（09:24–10:59）

会上在说什么。 现在的使用时机是“以 query 来检索为主”，同时参考一些其他 context；提示词之前写过一版。知识按目录树组织：体验官、司机、导游、管家等几个大板块（和嘉锋设计的一致）。系统根据当前 query 和 context 判断“这一次该加载哪些知识”。单次加载是可以的，但多轮遵循效果不好。

用“龙虾”做对照。 会上拿另一个 agent 产品（“龙虾”）类比：它的 skill 都有缺陷——步骤一多就容易丢；而且如果知识放在 director 里，中间还有各种各样的打断，会极大干扰 skill 的运行。所以结论是：我们的知识不能完全做成龙虾那种 skill 形态。

补一句背景：这里的“龙虾”就是你在 8 月那份《豆包上车 vs 龙虾类车载 Agent 方案》里对比过的 OpenClaw 一类通用智能体框架（见 HTML/01-进行中/豆包上车-vs-龙虾类车载Agent方案-v08.html）。所以这场会上出现“龙虾”时，你不用当成新名词——你已经有它的完整架构图了。

为什么表现不佳，会上给了四层。 ① 内容质量本身差；② DT 里的内容已经挺多，再插一份知识进去会稀释；③ 多步骤、长流程的任务，遵循能力显著打折；④ 后来加了“打断恢复”，干扰更多，成功率更低。

这一段的方法。 从“内容对不对”追到“运行时会发生什么”：读一次能不能记住、被打断后还能不能继续、多轮之后还在不在。这正是后来整场会反复回到的问题。

如果你在现场，可以接。 “用户中途插问一句天气，原目标还在，但当前 query 变了——这时候是谁保证‘接人’的知识没被丢掉？提示词里写了要保留，和运行时真做到，是两件事。”

场景 3｜什么才叫“专家”（11:56–16:33）

会上在说什么。 看嘉锋写的那些“专家体验”，很多其实只是常识。真正的专家表现是：必须为了这个目标持续追踪、review，发现哪里不足，然后做得更好。

一个完整的例子（氛围营造）。 当前车内氛围不够活跃 → 不够活跃的原因是什么 → 分析出原因之后采取行动 → 再观察是不是真的达到了 → 持续做这件事 → 达到标准。再进一步：不同的问题要有不同的预案——如果分析出原因是“大家在吵架”，那重点可能是缓和矛盾；也可能判断成“我自己不够搞笑”，换一种做法。

对专家级的另外两条期待。 一是只在需要的时候加载，节省成本，整套要和自学习统一考虑；二是要对应车的品牌调性——赛力斯有赛力斯的风格，上汽可能更朴实。会上设想：每个车型/品牌装载自己的一套专家级。有人追问“哪些任务跟品牌调性完全相关”，举的例子是迎宾；讨论也没有完全想透。

一个很好懂的比喻。 出厂的是一个豆包（一个通识的人）；他“入职”上汽，学了一套服务标准；去赛力斯，又学了一套服务标准。所谓专家级，就是给这个人做的岗前培训——在这些场景下，按照这家的服务标准服务用户。用户自己教给他的东西，优先级更高。

这一段的方法。 先定义“什么叫好”，再倒推需要什么能力；用“新人培训”这类生活类比把抽象结构讲清楚。

如果你在现场，可以接。 “这个目标‘做好了’的可观察标准是什么？系统现在拿得到这个证据吗？拿不到的话，缺的是哪个信号？”

场景 4｜标准必须是模型能判断的（16:33–21:31）

会上在说什么。 什么是好、什么是差，要能拆成几个指标——比如“氛围营造”的好，是“大家都在笑”？是“符合当前的意境”？这个标准的作用是给模型 review 的时候用来判断的。所以标准必须满足两条：模型好理解；能通过调用工具或数据客观判断、衡量。

一个关键澄清。 有人问：“你是说 knowhow 也是让模型判断自己执行得好不好的标准？”回答是：对，它觉得不好就要调、要改、要行动。行动这一块的知识可以先不给——只给标准，让它自己想办法（弱一点的做法）；也可以给——告诉它“你可以这样做”，可能一次就做对（好一点的做法）。

这里翻出一段历史。 前几个月还争论过一个更大的问题：颗粒度——“一个工具的使用技巧，算不算专家知识？”当时没有结论。

这一段的方法。 把形容词变成可判断的指标。写不出“怎么判断好坏”，知识就是文学，不是工程产物。

如果你在现场，可以接。 “这个标准现在靠什么数据判断？端上有没有这个信号？没有的话，是不是应该先记成一条‘能力缺口’？”

场景 5｜点、面、体：知识该多细、放在哪一层（21:31–27:16）

会上在说什么。 他们提出知识分三层：

  • • 点：单个工具的使用技巧，或者某个任务的小细节。例子：“搜音乐的时候什么时候该用联网工具、什么时候不用。”它是很明确的技巧，对应一个原子执行；但它不涉及 review，也没有完整标准——它只是告诉你“接到这件事时可以考虑哪些点”，不能让你把一整件事做完整。
  • • 面：面向某一个情景，或者某一类长程任务。它一定有阶段和步骤，每一步有检查点或标准，而且标准是 AI 能自己判断“达成没达成”的。例子：带人看病——知道这个情景有哪些特性、整体思路是什么、阶段性 todo 和检查点是什么、注意事项有哪些；接人——和用户确认会合点、帮忙规划路线、甚至可以教你怎么给被接的人发消息让他更好找、接近目的地时做提醒。多步、每步有标准，AI 可以持续 review、一步一步做。
  • • 体：更宏观的体验标准。例子：一个好的长途游——大场景里有无数小情景，更宏观的标准是“这趟旅行是不是给大家创造了好的回忆”“整个过程是不是足够轻松”；不满足时可以自己创建小任务再跟着追。

本质和分歧。 本质上是分而治之：从大场景到小场景再到点状知识。但会上也承认：“体的知识长什么样、面的知识到底长什么样，我现在还没想清楚”，因为它强依赖后面动态 Advisor 的设计。

谁来写？ 有人追问“游戏不算一个场景吗”，讨论到：游戏要变成“面”，还得补上它有哪些环节、每个环节的评判标准。而这些标准“得非常非常资深、非常会玩、经验丰富、还得有抽象能力和通用性的人才写得出来”——“所以就叫专家知识呀”。之前想让赛力斯的人写，他们也不一定写得出来。

落地的策略。 先从碎的知识做起，慢慢连成面，逐步迭代。例子：车很大，找停车场时不要给我找立体停车场——这就是一条非常“点”的知识。

如果你在现场，可以接。 “这条是点还是面？如果只是点，是不是不用强行上升到面？”

场景 6｜点面体的真正争论：分层到底值不值（27:16–34:49）

争论 1：面是点的集合，还是另有东西？ 回答是：面有阶段性——分阶段、分步骤，每个小环节有对应标准，而且标准是 AI 能理解的；点没有审核标准，就是“这样做挺好”，不分阶段，是碎的。

争论 2：用“人”来类比。 有人是按点吸收知识的，有人是按体抽象知识的。按点积累：不稳定（今天想到、明天没想到）、做不出更好的体验、不能举一反三，但可能更快；按体：相当于有一张网、有 SOP，但要一直思考。信息压缩得好的人也能很快——本质上是一种信息压缩方式。结论还是：得从点里再抽象出来，因为面是有结构的。

争论 3：最尖锐的一问。 如果上层 knowhow 只用写“A 和 B 这两条底层知识之间关系”的那部分，那值得分层；如果上层还得把“A 是什么、B 是什么、A 和 B 是什么”重写一遍——“那我不如平铺算了，我还要分级别干啥？”

分不分层的判断标准。 会上给了一个可操作的：看步骤长不长。步骤长的需要结构；短的场景一个点程序就够——比如过收费站，有 ETC 就开 ETC 车道，这件事不需要任何复杂的知识和思考。

检索逻辑也不同。 面类知识严格按场景覆盖、独立穷尽，主要用给动态 Advisor；Director 只需要知道“怎么创建好这个任务/要求”。点类知识游离在场景之外（比如音乐搜索的知识、聊天的技巧），给的是原子能力/行为。会上还留了一个开放问题：“场景库解决这个场景，有没有串场分支？”

这一段的方法。 用反例和成本检验漂亮概念。分层如果带不来复用，就只是好看。

如果你在现场，可以接。 “分层以后，上层会不会还要重复写底层内容？如果重复，维护收益是什么？谁来维护两份？”

场景 7｜别人的系统怎么存知识（34:49–38:20）

会上在说什么。 大家看了“龙虾”的两个结构：散的知识走 memory 的向量检索——有点相关就放进来参考，做对做错都参考；skill 是官方给的，memory 跟用户需求有关。memory 里可以有大的知识点，平时看不到细节，需要组合时再索引别的文件，可以套娃、自由组合。结论：龙虾架构更通用（想怎么存都行），但容易存乱。

这一段对照的正是你那份对比报告里写过的“便签本（任务流）＋双手（技能）”结构。你可以把它当成一次现场验证：别人系统的灵活性和混乱是同一个来源。

那我们呢。 会上判断不需要那么复杂：两种形态就够了——一种是散的知识（没有层级关系），另一种是有步骤、有每一步评判标准、有问题解决思路的“完整 skill 式”知识。

这一段的方法。 借鉴外部架构，但按自己的约束裁剪。不是照抄最强的方案，而是选最匹配的复杂度。

如果你在现场，可以接。 “我们是要一个什么都能装的容器，还是先把两种形态用起来、把检索和验收跑通？”

场景 8｜先停一下：我们到底为谁解决什么（38:20–43:38）

会上在说什么。 前面点面体、龙虾、检索聊得很散，这时有人打断：“我们先不说这些逻辑的，我们是要解决解决什么问题？”接着把话题拉回到两个价值。

价值一，对用户（to C）：越用越好用。 原话大意：“用户在很多时候表达你做得不好的那些事情的时候，你是能把他的指导沉淀下来，下一次做这件事情的时候能做好。他教了你很久之后，理论上他关心的那些事情，你应该都能做好。”

价值二，对车企和场景产品（to B）：把“最佳体验”变成可注入的标准。 原话大意：“赛力斯的宣发，或者说他们的产品，或者我们场景的产品认为，有一些场景下，他觉得我们这个模型自身调工具表现得不够、没有达到他想要的那种更好的体验，他想要让我们这个模型整的这个链路能达到他认为的那种最好的体验的样子。那就得让他能把他这个最好的体验的那个样子的、不管是知识还是 skill，能让他注入进来。”到今年年底，至少应该解决这两个问题。

嘉锋的追问和回答。 嘉锋问：如果最基础这些点都已经给他了，那一个合格的自学习是不是他能够利用这些点？回答大意：“自学习本身，它本质上就是因为你这一套知识的沉淀和注入。”——意思是自学习不是独立于知识体系的新东西，它靠的就是这套知识结构能不能被用起来。

两个方向的构想（42:32 那段，值得单独记）。 会上提出应该做两件事：

  • • 第一件：让模型基于大家每天上车 run 看到的信息，提炼出一些知识和沉淀；
  • • 第二件：再让一个模型去看沉淀出来的知识——哪些是有共性的，哪些是这个模型本身应该做的但它出错了。它的角色像一个“系统的不健康的检查器”，同时 review 哪些知识可以升级成公共知识，然后人工再去 check。

这两个方向，一个相当于 to C（优化这台车、优化用户的服务体验），一个相当于 to B（优化我们造车的知识逻辑）。

一句提纲挈领的话。 “本质上……所谓自学习，就是一个有人帮你去写知识、代替你一些。”后面又补：“专家级是有人去 review 的一个值给你注进来；自学习是我自己通过不断被教育、通过沉淀，自己挖掘出这个知识，再把它送进。”结论：“结构上知识肯定就是一套结构，但是可能生产的方式不一样。”

另一个观察。 有人分享用 agent 的体验：提问之后它总结出来的知识“已经挺好了”，比如“我要跟某个人发消息，它会先看这个人跟我之前的对话记录是什么关系，然后决定用什么口吻说，再看上下文双方有什么共同目标”——这类比较抽象的知识是有价值的。这说明系统总结不是完全不可用，但要管好“哪些留下来、留给谁”。

评测的定位。 “未来的话，评测可能只是一个引导器。因为你有一些主观设计的东西，但真实的环境运转起来，肯定跟你评测是不同的。你肯定是通过大家去体验的时候挖掘出来的问题，然后沉淀为那个知识。”

这一段的方法。 ① 当讨论发散到名词（点面体、skill、结构）时，往后退一层重新问“谁、看到什么变化”；② 把“专家级”和“自学习”当成同一套结构的两种生产方式，而不是两个系统。

如果你在现场，可以接。 “我复述一下这两个价值：用户教一遍下次做好；车企能注入他们的服务标准。那这轮的验收，是看到‘用户被纠正过一次的相似表达下次召回并生效’，还是看到‘车企提供的某条标准改变了模型行为’？”

场景 9｜模板先行、分阶段验证：先证明“教得会”（43:38–50:57）

这一段是整场会最实操的一段，值得拆到最细。

（1）怎么想到用“模板”。 思路是：只要把“面类知识”的结构——大概的字段、要包含哪些要点、哪些核心内容——想清楚，就等于有了一个模板。有了模板之后可以干两件事：第一，先让 AI 按模板把嘉锋写的那批情景自己生产一遍，看看能不能产出；第二，做一个专门的工具干这件事：在 DT 里教它怎么跟用户沟通、理解用户想要什么技能，自己尝试写出来，再 check，觉得 OK 就沉淀。

（2）模板长什么样（会上给的雏形）。 一个情景可能包含好几个阶段和步骤；这些阶段、步骤分别有哪些标准；要产出这些标准的判断方法；以及标准不满足时可能有哪些原因；以及这些原因对应的解决方案。“大的架构可能是现在也可以拆得出来一个很模糊的，我现在先产出一个。”

（3）难度排序（一句很关键的话）。 “自学习的难度都没有你定这套模板的难度难。定一个面的知识太难了。”——意思是，真正难的不是让模型学，而是人类自己都没写出“什么叫好、怎么判断、为什么不达标、怎么修”这套结构。嘉锋的想法是“我不管了，你给我提取出来，塞进去看看”；明骏的态度是“这个太乱了，一定会足够混乱的”。这两个态度的差别是：一个想先跑量再看效果，一个要先定结构再量产。

（4）自学习要分阶段。 第一阶段不是让模型自己学新知识，而是：先确保既有的知识模型能遵循得很好；再把知识换一换，看它是不是也能遵循得很好；这两步都做到了，才去谈“自动生成新知识”。对照动态示例：“你先做到让模型基于这些 bug，我给它讲了这个 bug，应该这样做，然后你自己生成一条动态示例，然后这个动态示例生成出来之后，可以被检索、像现在一样被应用。”

（5）用动态示例的现有流程当参照。 现在的流程是：“我们自己发现了 bug，我们理了理逻辑，然后泽民、晓伟、明明他们写了一条动态示例，然后上线了，然后验证发现解了。”未来的目标是把这条流水线的第一步搬到车上：“我在车上遇到这个 bug，我就跟它讲——你的问题错在这里，你应该这样做就能对了——你记一下，然后它记下来了，下次它就能做对了。”

（6）歌词全屏的真实 case（现场用来演示“可调教”的例子）。

  • • 现象：打开歌词的时候每次都打开全屏；用户想一边看导航一边看歌词就不行。
  • • 用户给的解法：跟它说“当我跟你说打开歌词的时候，第一步先打开 QQ 音乐的歌词，第二步返回桌面，第三步打开分屏模式。”
  • • 会上点评：“如果它能检索到这件事情，它还是能做到的。”也就是说模型该有的能力是有的，缺的是记住、下次检索到、按步骤执行。

（7）调试模式与“公共动态示例变量”。 想法是：在调试模式里跟它讲的东西，沉淀成一种通用类型的记忆／动态示例变量，上线时所有用户都装载这部分；“我解 bug 就口述就行了，找一些有品位的人，上车上体验体验，把好的给他讲一讲，也能解很多问题。”“不用先跟他讲那些高级的场景，至少基础用车的一些习惯，我觉得可以先解掉。”目标是：“我一直想先把动态示例变成让人在车上说，不要再让我天天在下面写。”

（8）但要承认动态示例的边界。 “这个还是聚焦的是一个……因为动态示例现在也确实只能解基本上单轮、或者说很简短的东西。”所以它是第一层的。

（9）长程的面／体知识还是要做，两条路并行。 “面或体类的知识肯定是非常重要的。面类的东西，它应该是常态、用户日常会用到的这种场景的凝练，尤其是出行类的或舒适服务类的。”比如赛力斯可能主打的场景——“真的我想让你做个导游，那怎么做好一个导游？”这一类需要“有一个很糙的东西，大家试着去打磨它，然后我能把大家吐槽的东西记下来”。

（10）验收锚点：至少一个面／体类知识在 Dynamic Advisor 跑通。 “里面的这类知识，至少有一个能在 Dynamic Advisor 跑通，然后它真的能表现得很好——是真的有这种一步一步去 review，然后发现问题，自己尝试分析原因，然后去找解决方案，然后解决之后一步一步把它做好。”跑通以后，才能往后跑。

这一段的方法。 ① 先定结构（模板）再批量生产；② 拆阶段：既有知识能被遵循 → 换知识也能被遵循 → 自动生成；③ 用现成流程（动态示例）当参照系，把“未来能力”翻译成“现有流程的哪一步变了”；④ 两条路并行但各有一个最小验收锚点（单轮可调教；一个长程场景跑通 review 闭环）。

如果你在现场，可以接。 “这个模板里‘怎么判断标准达成’这一栏，是不是就是刚才说的、必须模型能判断的指标？如果某条知识这一栏写不出来，是不是说明它还不具备进入知识库的条件？”

场景 10｜巧妇难为无米之炊：为什么感知和触发器反而更急（50:57–53:38）

会上在说什么。 有人说调教这件事别着急，但马上被反驳：“但你巧妇难为无米之炊啊。就你现在依赖的那些感知啊，依赖的那些工具……”因为每一个情景要判断好坏，“他那些好坏都得有一些对应的那些数据啊、传感器啊什么的”。

“触发器首先全”是什么意思。 会上把两件事分得很清楚：

  • • 能力层：传感器／信号／触发器要“全”——都能拿到、都能触发。
  • • 运行层：要不要用、用多少、频次多高，是另一回事——“我要真想限这个流量频次，我去限那个，我让那个主动服务不订阅这个”。

原话：“你触发器不能没有，你漏了你要了就来不及了。你后面再要，真的想要的时候又搞不上。”“源头上我不接这个信号……我可以控制我的动态的 value 或静态的 value，我不订阅这种嘛，我为了降频也行啊，但是你不能说触发器没接这个信号，等到将来想接接不了了。”

一句可以直接背下来的结论。 “有没有和用不用是两个。”

背景原因。 知识的闭环依赖：判断好坏需要数据／端状态；执行需要工具／原子能力被接进来。如果哪一条依赖接不进来，知识写得再好也做不成。所以基础能力接入这件事比知识模板更急。

一句旁白。 “而且我觉得大家最近真的被成本吓坏了。”——这句解释了为什么后面马上要谈成本怎么分。

这一段的方法。 把“能力是否具备（有没有）”和“运行时是否使用（用不用）”分开讨论。混在一起谈，会得出错误的结论：因为“这个场景现在不用”，就砍掉“以后可能需要的接入”。

如果你在现场，可以接。 “这一条是能力没接入，还是已经接入、但我们选择不订阅？如果是前者，排期要往前放；如果是后者，我们只需要定频次和成本归谁。”

场景 11｜Leading car 和走量车：不同产品的账不一样（53:04–53:38）

会上在说什么。 “不同阶段要看不同的事情。你的 Leading car 和你走量的车，后面延展的车也不是一样的定位。”第一辆 Leading car 的目标是“有影响力”“让人看到你的上限”“让人相信这个事情”。原话：“你转后面的那么多车的规模化，那我觉得我那些车全上 SMT，我根本不在乎……你上面是走量，那些你端状态，你少接几个，我都无所谓。你成本给我压下来走量，我觉得那是另一个商业模式。”

成本怎么算。 “不是说我们不 care 钱，但你那个 Leading car 上去可能也就是 SOP 到第一个 OTA 之间这段时间，到下一个时间你又可以降级，都可以降的呀。”“亏也就亏个三个月嘛，就当广告了嘛，就当广告费了。”

这一段的方法。 按产品使命分账：同一个技术决策，在不同车型、不同阶段、不同商业模式下，成本答案不同。把“贵不贵”变成“谁承担、为什么要承担、承担多久、什么时候能降级”。

如果你在现场，可以接。 “我们现在讨论的这套东西，是先在 Leading car 上验证上限，还是直接按走量车的成本约束来设计？这决定触发器接多少、端状态接多少。”

场景 12｜什么时候该记下来：一次成功 vs 明确要求（55:06–58:18）

会上在说什么。 从“动态示例能不能口述生成”展开，讨论“什么样的经历值得沉淀成规则”。

米其林三星餐厅的例子。 用户说“帮我在附近找个米其林三星餐厅”，模型先调 POI 类工具，工具说没有，然后尝试联网，联网找到了。问题：“等用户下次再问的时候，能不能直接找联网？我觉得现在做不到。”

两种沉淀时机（会上明确分开）。

  • • 第一种：用户明确表示“以后搜这个，你应该这样做”——“我觉得它会立马产生一个”，马上生成一条。
  • • 第二种：它一次做错，然后马上找了一个方法帮你做出来，就马上记——“可能会产生很大量的（噪音）”。所以更适合先放着，下次再遇到这种类型，经常地总结，再生成。“那个我觉得是更长远一点的目标，短期……”

这里的方法论就是前面说的：明确纠正（证据强）与一次补救成功（证据弱）要分开。

记忆现在稳不稳定。 “我们上次之前测音乐 case，有些让他放专辑……你现在的记忆很多时候都会达到这种效果的，但只是说不是很稳定。”——能力已经有了，稳定性是问题。

先用“嘴”调教（车企打磨体验阶段）。 “至少我们先做到，比如我们可以让赛力斯到时候打磨体验的时候，一群人用嘴，天天用嘴跟他讲，这样做一做、改一改。”这里需要一个账号设计：“得有个内部账号，上的时候是能记到全局的（公共）；以后开放给用户，用户这个账号就是单独个人的。”

调试／研发模式。 “到时候打开一个模式，比如说赛力斯我现在是一个调试模式，或者是研发模式。他记的这种类型的 skill，我全部作为一种公共类型的动态示例变量，全部全量放；等到用户上线的时候，那就变成他自己的那种类型。”

再次回到依赖。 “你要为了做到这些事情，你的端状态、你的触发器就要全。”“比如你这首歌放完，我就再回去还是什么的，比如每首歌放完我都要加讲的什么，他其实都需要音乐播放的那个切歌的那个状态。”“各种原子能力，你自己可以组合搭。”

为什么强调“全”。 “我们一直想做的东西，不是说为一个场景，所以我要接这个信号，我们就是要足够的自由。”“就是要全了才能有宽泛的（满足）。”

这一段的方法。 ① 按证据强度分流：明确要求立即沉淀，偶发成功先观察；② 用账号／模式区分公共知识与个人偏好；③ 能力建设按“组合自由度”而不是按单场景立项。

如果你在现场，可以接。 “这条如果是用户明确要求的，进个人知识；如果是全局都能用的，进公共库。公共库的审核人是谁？还有，我们怎么区分‘这次工具没覆盖’和‘这个类型永远该走联网’？”

场景 13｜收尾：定目标、约下一场、他们的学习方式（58:18–1:02:09）

通用框架满足个性化（理念句）。 “我们的理念一直是要用通用框架满足个性化需求。以前你无论怎么做都不可能做到个性化，你只有现在这样子才能真正做到个性化。因为你说啥我反正都能做，我可能就不存在什么长尾需求……个性化全是长尾。那以前做长尾需求的成本太高了，所以我不能做，我要聚焦。那现在我们的方法不就是通用框架，然后我们在高频的场景下让它稳定，然后用通用框架把我那些长尾全都能满足。”

下一场会：自学习专项。 “关于自学习的，我们可能还要再聊一次，专门聊一次。我到时候写一下，我看下周一吧，拉大家再聊一个。”议题是“自学习在今年赛力斯 SOP 的时候、12 月底的时候到底能上到什么程度”。会上还抱怨“拉了好几次会，没有一次聊上”。

先定目标。 “最近很多课题，首先你得把目标定下来，不能还是以前——自学习一句话。你到年底，自学习能学啥？学到什么程度？能达到什么样的效果？”

“像人”是顶层维度。 “你像人之后，说不定你抽象的标准里面可能就有自学习，有他打断的这些策略，他是互相嵌套的。像人是顶层维度。”“我们还是需要有一个从哲学层面给我们支撑，让我们做这些事情要有一定的理论支撑。”

还没聊清的边界（会上自己点出来的）。 “自学习里面，其实这些沉淀和记忆关系很大。到底哪些走记忆，哪些走（知识）……我觉得还要再聊。”“S6 跟……还有条件任务。”“哪些是在一个（流程）里面影响他的，哪些又是激励你的？他的激励我觉得要专门聊。”

年底的期待。 “我觉得我们到年底，我希望我们那个记忆一定要做到连续。记忆是连续的，人设是连续的，都是连续的。”

工作方式。 “很多东西互相勾连，但还是得一个一个话题聊。先聊，大家组织，谁组织都行，先聊起来，聊透了，然后再去说谁去负责去把它给落地。”

他们的学习方式（这段特别值得学）。 收尾时聊到组织大家一起看电影：“最近我们要组织让如水带我们看次电影，把一些好的内容（看一看）。”“上次我们食堂排队的时候，已经整理出了一个例子了。”“我看的时候会暂停，我掐个表……到时候谁当主持人，负责掐一下，然后引导大家讨论。”“我就先第一遍畅快地看完一遍，然后下面一帧一帧地、一帧一帧地分析。”

这个方法和他们讨论产品的方式一模一样：第一遍完整感受（相当于用户体验），第二遍逐帧拆解（相当于机制分析），有人主持掐表（控制节奏），集体讨论（对齐认知）。这不是娱乐，是他们训练“看懂好内容为什么好”的方法。

这一段的方法。 ① 先定目标（可验收的程度、效果）再谈方案；② 顶层维度（像人／理论支撑）给所有子策略提供一致性；③ 学习一个东西要“先整体体验、再逐帧拆解”。

如果你在现场，可以接。 “年底这个目标能不能拆成两个可验收的点：一个是‘歌词全屏’这类明确纠正能被记住、下次生效；另一个是至少一个面类知识在 Dynamic Advisor 里跑通 review 闭环？”

第 3 章 补课：他们说的“检索”到底是什么

你在会后追问过“文本相似度匹配 RAG”，也提过后视镜的 badcase。这一章把检索用产品语言讲清楚——因为会上反复出现的“使用时机”“多轮遵循效果不好”“动态示例能被检索、被应用”，说的都是这套水管。一句话：知识写得再好，检索不到，就等于不存在。

3.1 先看它在整条链路的哪个位置

用户说话
  → ASR 转成文字
  → 系统把这句话（可能还做一次改写）变成一个“查询向量”
  → 检索：从知识库里挑出这一次该参考的几条知识（Top-K + 阈值）
  → 注入：把挑中的知识正文拼进发给 Planner（云端大模型）的输入里
  → Planner 决定说什么、调用哪些工具（action_list）
  → 下游工具/端侧执行，返回 tool_feedback
  → 下一轮判断

最关键的一句话：模型不会自己去翻整个知识库。 它每次“看到”的，只有被检索程序挑出来、拼进输入里的那几条知识。所以：

  • • 检索没选中 → 模型根本看不到正确知识，表现得像“没学过”；
  • • 检索选中了但模型没照做 → 是遵循问题，不是检索问题；
  • • 模型照做了但端上没生效 → 是工具/端侧执行问题。

这三种情况的修法完全不同。辨不清是哪一种，讨论就会变成互相甩锅。

3.2 “文本相似度匹配”七步拆开

  1. 1. 编码（向量化）。 把一段文字转成一串数字（向量）。语义越接近的两段文字，向量在空间里的方向越接近。注意它不是关键词匹配：“副驾的镜子看不到”和“后视镜调节”没有一个共同的关键词，但意思接近，向量也接近——这是它比“搜索框找关键词”聪明的地方。
  2. 2. 建库。 知识库里每条知识（标题、正文、适用条件等）预先算好向量存起来。
  3. 3. 查询。 当前用户这句话也算一个向量。这一步可能不是直接用原话——系统可能先做一次改写或补全，再用改写后的版本去编码。
  4. 4. 比较。 拿查询向量跟知识库里每一条的向量算相似度分数（可以理解为“意思有多接近”，通常是 0～1 的分数）。
  5. 5. 排序取前 K。 按分数从高到低，取前 K 条（俗称 Top-K）。K 是人工设的。
  6. 6. 阈值过滤。 分数低于某条线的直接丢掉。阈值高＝谨慎，容易漏；阈值低＝宽松，容易混进无关知识。
  7. 7. 注入。 留下来的知识正文被拼进发给模型的输入（系统提示词或当前轮输入的一部分），模型才能参考。拼几条、拼多长，还要受上下文长度和成本限制。

3.3 六个必须问清楚的产品问题（每一个都决定 badcase 修哪层）

决策点是什么意思选错了会怎样你可以怎么问

比哪些字段只比标题，还是标题＋正文＋场景标签＋适用条件只比标题可能漏；把无关字段都算进去可能噪声多“知识表里哪些字段进入了检索？”

3.4 两种 badcase，修法完全不同（最实用的一条）

情况 A：没检索到——该拿的知识没进来。

症状：用户说“副驾的镜子看不到”，知识库里写的是“后视镜调节”。两个说法在“意思空间”里不够接近，分数没过阈值，知识没被选中。

修法：改知识的表述（把用户可能说的多种说法写进去）、补近义说法或标签、入库时做扩写、必要时加一层场景识别。不是去改模型提示词。

情况 B：检索到了但没做对。

症状：日志里能看到知识被注入，但用户结果还是错的。往下再分四种：

  1. 1. 模型看到了但没遵循（提示词写法、模型能力问题）；
  2. 2. 知识本身写错了（内容问题）；
  3. 3. 需要的端状态缺失，模型判断不了（数据依赖问题）；
  4. 4. 工具调用了但端上没生效（下游执行问题）。

修法：哪层错修哪层。如果团队不先分这两类，就会出现经典拉扯：做检索的说“我召回了”，做模型的说“我没收到”，做端侧的说“我按要求执行了”。

3.5 这件事和你手上的工作直接相连

你写动态示例的时候，其实就是在给知识库加一条“临时知识”，然后等它被检索、被注入、被模型使用。所以以后遇到“写了没生效”的 case，可以按这个顺序查：

  • • 先看有没有被检索到（命中列表、分数、阈值）——没检索到，先改表述/补说法；
  • • 再看注入位置（拼在提示词的哪里、有没有被截断、和别的知识冲突）；
  • • 再看模型是否遵循（换个说法再试，看是不是“只认一种表达”）；
  • • 最后看端上是否真的执行（工具反馈 vs 用户看到的结果）。

一次修复解了、换个表达又不行，往往是检索的泛化问题：不是知识错了，而是只有那一种说法能命中。这份判断可以直接用在你的 badcase 提报里。

3.6 为什么这跟这场会有关

会上说“使用时机以 query 来检索为主”“理论上可以多轮，但多轮遵循效果不好”“打断会极大干扰 skill 运行”——本质都是检索与注入的时机问题：知识被选中一次、模型读一次，之后还记不记得？目标还在不在？用户插一句话之后会不会被挤掉？歌词全屏的 case 能修好，说明“能被检索到”确实是这套体系的关键一环。

如果你在现场，可以接。 “这个 case 是没检索到，还是检索到了但没被遵循？我们能不能先看日志里的命中列表和分数，再决定是修知识表述还是修模型？”

第 4 章 他们是怎么一步步想到这些的：把 11 步推理链展开

这一章是整份文件最重要的一章。他们不是各自抛出观点，而是沿着一条固定的追问链往下走。每得到一个结论，这个结论就暴露出下一个必须回答的问题——这就是“能讨论得深”的技术原因。你学会这条链，就能跟着会议的节奏走，知道现在讨论到了哪一步。

第 1 步：先问事实。 现在到底发生了什么？——赛力斯二三月写的那版知识质量差，结构是赶出来的；周末游里写了“有 EVA 的地方”“小众潮的地方”“几点吃饭”。

第 2 步：再问运行。 写下来的东西，运行时会发生什么？——多轮遵循效果不好；步骤一长遵循打折；加了打断恢复之后干扰更多。结论：知识不能完全做成龙虾那种 skill 形态。

第 3 步：再问能力定义。 什么叫“专家”？——不是“做过动作”，而是：知道好坏标准 → 观察现状 → 发现差距 → 分析原因 → 采取行动 → 再观察 → 达到标准。

第 4 步：再问表达标准。 好东西怎么写成模型能用的？——标准必须模型能理解，并且能通过调用工具或数据客观判断。“大家都笑了”只是举例，不是充分的判断标准。

第 5 步：再问组织结构。 知识分几层？——点（局部技巧）／面（有阶段、有检查点的场景）／体（跨场景的整体体验）。接着争论：分层到底有没有复用价值？如果上层还要重写底层内容，“那我平铺算了，还要分级别干啥？”

第 6 步：再问使用方。 不同模块需要什么知识？——Director（Planner，负责当前交互与任务拆解）需要“怎么拆任务、怎么持续”；Advisor（顾问模块，负责持续观察和建议）需要完整的场景知识和 review 能力；两者的检索逻辑不一样。

第 7 步：再问目的。 这一切为谁解决什么？——to C：用户教一遍，下次做好；to B：车企能把“最佳体验”的标准注进来。这一步把发散的名词之争拉回产品价值。

第 8 步：再问路径。 先做什么？——先有模板；先证明既有知识能被遵循、换知识也能被遵循；先做单轮动态示例的口述化；再谈自动生成。两条路并行，各有最小验收锚点。

第 9 步：再问依赖。 还缺什么？——感知、端状态、触发器、原子能力。“巧妇难为无米之炊”；判断好坏需要数据，执行需要工具。

第 10 步：再问成本/策略。 都要吗？谁承担？——“有没有”和“用不用”是两个问题；Leading car 可以亏三个月当广告费，走量车要压成本。

第 11 步：再问收口。 今天能定什么、不能定的约什么会？——自学习专项会（暂定下周一）；年底目标要写清“能学啥、到什么程度、什么效果”；记忆、条件任务、S6 的边界另开话题。

观察他们的节奏： 每当讨论开始飘（点面体名词之争），就有人拉回目标；每当有人提出方案（自学习），就有人问“那它依赖什么”；每当有人说“这个很重要”，就有人问“那成本谁付”。这种“发散—锚定—再发散—再锚定”的循环，就是深度讨论的发动机。

第 6 章 为什么“我都不知道”——六个结构性原因（不是能力问题）

把这场会读到这里，你应该已经发现：你说的“我怎么不知道”，答案并不在“我笨”或者“我不够努力”。下面六条，是我从材料里能看到的真实原因。

原因 1：连续剧效应。 这是第 N 集。2–3 月写第一版、4 月 13 日《专家任务集完善》会、6 月动态示例讨论、7 月验证表——这些前情分散在不同人的工作里，没有人专门给你对过一次。会上说“之前讨论过好多次”，说的就是这些集。

原因 2：现场省略背景。 会上大量使用缩写、代号和历史名词：DT（Director/Planner）、Dynamic Advisor、专家任务集、基础体验集、点面体、SMT、龙虾……他们彼此都知道，所以不解释。新人缺的不是智力，是一张“名词→它背后的历史和含义”的对照表（本文件第 0 章、第 3 章、附录 B 就是给你补这个的）。

原因 3：颗粒度不匹配。 他们讨论的是机制（检索、遵循、闭环、成本），你日常处理的是case（一条 badcase、一条动态示例、一次验证）。两边都对，但中间缺了一层翻译——“我这条 case 属于哪个机制问题”。第 3.5 节就是这层翻译。

原因 4：分工视角不同。 你负责 Planner 方向里的一部分；这场会横跨知识生产、Advisor 设计、端侧感知、评测、成本、商业模式。不是你“应该”知道全部，而是没有人给你画过全图。这不是你的问题，是信息传递的问题。

原因 5：把探索当结论。 会上很多人是“边说边想”，听感上像已经定论，其实大量是假设和设想。逐字稿里“我也没想特别明白”“我现在还没想清楚”“我只是举例”“先产出一个很模糊的”出现了多次。如果你以为必须等自己想出一套完整答案才能开口，就会永远错过讨论阶段。

原因 6：你不是空白，是没连起来。 你做过动态示例的撰写与验证，提报过 badcase，跟过下游工具确认，7 月验证表里有你的条目。这些和会上讨论的是同一件事的不同侧面——只是没人帮你连成“生产 → 检索 → 决策 → 执行 → 结果 → 学习”这条链。你现在要做的是把已有的碎片串起来，而不是从零学一套新知识。

第 7 章 插嘴手册（可以照着做）

先接受一个前提：插嘴不需要你先懂全部。 观察这场会的有效发言，几乎都不是“大方案”，而是五类小贡献：定义一个词、提供一个反例、补一条历史证据、指出一个链路缺口、把讨论变成可验收动作。这五类的共同点是——它们都只需要你手上的一两条真实材料。

7.1 会前只带三样东西

  1. 1. 一个你亲手验证过的 case：从用户说了什么 → 系统做了什么 → 结果对不对，一条能讲完的完整链路（比如歌词全屏、后视镜、路线没展示）。
  2. 2. 一个反例：方案在什么条件下会失效（换个用户、换个地点、换个说法）。
  3. 3. 一条验收建议：怎么证明这件事真的做成了（到哪一层算成）。

再带一张纸画三列：他们的观点 | 我手上的例子 | 我想问的一句。听会时随听随填，你会发现自己其实能填很多行。

7.2 30 秒发言结构：事实 → 影响 → 问题 → 建议

这是最不容易翻车、又最容易被记住的结构。范例：

  1. 1. 事实：“7 月验证表里有一条：Director 逻辑正确，但路线没有展示出来。”
  2. 2. 影响：“所以只看上游输出，可能会把‘没完成’当成‘成功’。”
  3. 3. 问题：“这次专家知识的验收，准备卡到哪一层？”
  4. 4. 建议：“建议同时记录 Planner 结果、工具反馈和端上结果，三层分开看。”

注意：这四句里没有一句是“我反对你”。你补的是一条证据和一个决策缺口，对方几乎不会和你冲突，而且现场会立刻需要你这条信息。

7.3 12 句可以直接照抄的话术

澄清定义类（听到新名词、感觉大家口径不一致时）

  1. 1. “我先确认一下口径：这条是通用知识、当前 case 的要求，还是测试考察点？”
  2. 2. “这个词我们现在的定义是什么？是它决定模型怎么拆任务，还是决定它怎么判断做完？”
  3. 3. “这是能力已经接入了，还是先当作目标能力来设计？”

补边界/反例类（有人提出方案、大家开始点头时）

  1. 4. “这个方向我理解。我补一个边界：用户中途插问天气以后，原目标还在，但当前 query 变了——这里谁保证相关知识继续保留？”
  2. 5. “换一个条件：如果用户不是年轻人，而是带父母出行，这条默认行为还成立吗？”
  3. 6. “如果这条知识没被检索到，是改知识的说法，还是要改检索？我想确认修哪一层。”

拆链路类（有人说“已经成功/已经解了”、或问题被统一归到模型头上时）

  1. 7. “这里的成功是 Director 决策正确、工具返回成功，还是用户端结果已经出现？”
  2. 8. “能不能先按链路排一下：输入状态有没有、知识有没有召回、模型有没有遵循、下游有没有执行？现在的证据能定位到哪一层？”
  3. 9. “这个是一次成功，还是稳定规律？它只适用于这个用户，还是应该推广到全局？”

收口确定类（会议快结束、话题开始重复时）

  1. 10. “我复述一下：今天已对齐的是哪几点，还没定的是哪几点？”
  2. 11. “下一步每个 case 的 Owner 和验收人分别是谁？什么时候对一次？”
  3. 12. “我的理解是：先在 Leading car 上验证上限，验收锚点是一个单轮可调教 case＋一个长程 review 闭环。这个理解对吗？”

7.4 四个安全的开口时机

  1. 1. 有人抛出名词但没定义时——用第 1、2 句，帮大家统一口径，这是最快被接受的发言。
  2. 2. 有人说“已经成功了/已经解了”时——用第 7 句，把“成功”拆成三层，你手上往往正好有反例。
  3. 3. 方案越谈越大、没人管落地时——用第 8、11 句，把讨论拉回收口。
  4. 4. 会议准备收口时——用第 10、11、12 句，帮大家总结，收口的人天然存在感最强。

7.5 会后 10 分钟动作（这个动作的性价比最高）

会后在群里发三行：

  1. 1. 已对齐的：今天我们确认了什么（写 2–3 条，用大家说过的原话）。
  2. 2. 仍未定的：哪几个问题还没结论（列出来，不用有答案）。
  3. 3. 下一步：谁在什么时候做什么（哪怕是“下周自学习专项会上再谈”）。

这个动作不需要你在会上说得多好，但它让你从“参会者”变成“会议产出的人”。坚持做几次，大家会开始等你这份总结，你在会上的话语权也会自然上升。

7.6 如果你还没听懂：一句救场话

“我可能漏了一段历史背景，我先用一个实际 case 确认一下边界。”

这句话既诚实、又不把自己放在被动位置——它把“没听懂”转成“我需要一条证据来对齐”。会上没有人会因为这句话扣分，反而会有人愿意给你补背景。

7.7 下一场会你可以练习的三次发言（按出现顺序排好）

第一次（在旧知识质量问题被提起时）：
“这里是不是先要分开通用 knowhow 和 case 考察点？我建议拿同一条知识换一个用户、地点和同行人做反例，看哪些字段必须变量化。”

第二次（在 Dynamic Advisor 出现时）：
“如果 Advisor 负责持续 review，Goal 的进展由谁唯一更新？用户插入新任务以后，Director 和 Advisor 会不会分别判断完成、产生冲突？”

第三次（在自学习收口时）：
“第一阶段我建议只验用户明确纠正的 case，不把模型自动归纳混进来。验收要到下次相似表达能召回，而且端上结果真的改变。”

这三句分别贡献了：内容标准、模块边界、验证方案——都不需要你提出整套架构。
