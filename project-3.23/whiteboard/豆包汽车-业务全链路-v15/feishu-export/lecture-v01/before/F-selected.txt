按图逐步读懂
F01 · 先有业务定义，再找具体实现
英文名/中文名/能力描述给 D 看；同一定义可绑定多个实现；不是一张工具名表就能调用；定义、实现和版本各自维护。
Agent 管理平台把“这个工具干什么”和“它在哪个项目怎么执行”拆成两层。定义包含英文标识、中文名、界面名和能力描述；实现包含渠道、参数、接入点和版本。比如同为 music_search，历史表出现豆包版与函数调用版两行，不代表模型有两个不同名称。绘图必须先定位当前实现，不能看到业务定义就宣称所有车型都拥有此功能。
F02 · 选择渠道、环境和启用发布版本
channel＋应用ID隔离实现；已发布且启用才进入可用集合；车端/云端与提供方分开看；是否参与 D 推理是独立配置。
实现选择受渠道、应用、环境和发布启用状态约束，同一定义可以保留多个草稿用于测试。车端或云端是集成位置，内部、DPFM、豆包或生态是提供方，两者不能混为一个分类。管理台还有是否参与 Director 推理的开关，未参与不代表底层永远不存在。验收要看当前运行请求实际使用哪个版本，而不只是后台里曾创建过一份草稿。
F03 · 检查用户权限与车辆能力
可信账号角色在调用前检查；车型设备、音区、驾驶状态约束；可见工具不保证每次可执行；拒绝原因要反馈，不伪造成功。
工具可见只是模型知道有此能力，当前用户是否有权使用、车辆状态是否允许，还要在调用前校验。比如修改账号、操作某些车辆功能需要角色与项目策略，不能由模型自己推断一个“应该允许”。权限从可信账号链路取得；设备没有、语音不支持和当前不满足执行条件要分开。被拒绝时给出真实原因，方便 Director 解释或提供安全的手动替代。
F04 · 检查动态工具的运行条件
每轮推理前批量检查条件；一期只读请求参数 param；存在/不存在/集合条件可组合；状态/Trigger扩展是后续方案。
动态工具不是常驻把所有能力都塞进提示词，而是在本轮条件满足时才展示。技术方案一期只从请求参数判断，支持字段存在与否、在不在集合以及与或组合。比如只有实时卡片信息存在才给当前页面操作工具。文档提出以后接车端状态和 Trigger，但不能把这个未来方向写成已支持任意复杂条件。条件失败时不加载，原因和配置版本应能检查。
F05 · 实时卡片提供可操作按钮语义
card_id、标题、内容、按钮名；当前界面字段来自端侧请求；无卡片不能假造当前页面操作；实时卡片归 Context 为未来方向。
端侧把当前卡片的标识、标题、内容、按钮名和原因放入请求，动态工具才知道这个页面实际能做什么。用户说“就选第二个”时，应对应当前卡片真实按钮而不是凭旧历史猜测。当前方案用 real_time_card 请求参数，后续统一到 Context 只是规划；如果卡片已经换了，仍需要版本或有效性核对。表面按钮能点不等于所有 GUI 操作都受这个工具支持。
F06 · 把符合条件的工具描述注入 D
tool_info按项目动态加载；静态工具与条件工具槽位区分；current_page_specific按需出现；提示词调试与管理台发布同步。
可用工具定义和实现参数转换成 Director 提示词中的 tool_info，动态条件成立的工具放进对应槽位。产品在提示词平台调通一段描述后，还要把参数、notice、tips 同步到实际 Agent 管理配置并发布，否则线上仍可能使用旧描述。当前页面工具 current_page_specific 不是所有车型永远都有的第41个能力；它是一项有条件加载的设计，具体 agent_id 仍待确定。
F07 · 模型选中后校验明确参数
名字、必填项、类型和范围；卡片工具输出 select_button；业务许可满足才发布副作用；校验失败交回模型说明/澄清。
Director 选择工具后，执行层仍需检查参数合同。卡片工具要选真实按钮并关联正确卡片；普通车控要有明确设备、动作和范围，不能仅凭工具存在就发不完整指令。动态工具方案的具体 agent_id 尚未确定，应保留接口确认项。参数错误与用户表达含糊也要分开：前者是系统输出问题，后者可请用户补充，均不能擅自填一个默认值造成不可逆操作。
F08 · 单 Agent：取依赖、填请求、选执行器
元信息→Context依赖→请求参数；绑定业务后处理钩子；豆包/DPFM/HTTP/内部执行器；AgentServer不编排整套工具计划。
根代理核验的 AgentServer 原图给出明确流程：先读 Agent 元信息，再获取所需历史、长记忆、端状态和提示词依赖，填充请求并绑定后处理，然后按类型选择执行器。这里负责把一个 Agent 调通，而不是重新理解用户全部目标。不同提供方协议差异由适配处理，Director 的多步规划仍在 D 区；一个 Agent 内有子流程，也不能因此绕过外层权限和结果回传。
F09 · 流式响应先做通用协议归一
关联 chat/问题/会话/Agent/trace；POST＋SSE按标准接流；终包必须明确 is_finish；错误码与结束原因保留。
第三方协议用会话、问题、Agent 和 trace 标识关联一次请求，流式响应由通用层归一成统一格式。is_finish=true 标识这次 Agent 响应流已经结束，缺终包就不能静默当结束。错误码、消息与结束原因要保留给后续判断。它并不是车窗已关闭、商家已接单或用户已付款的统一完成字段；这些要继续看业务内容，不可只抓终包就对外报喜。
F10 · 业务后处理把三路内容分开
content：用户界面内容；tts_content：可供语音的内容；model_content：给 D 的决策事实；Widget/透传指令另有类型。
通用协议之后还有特殊业务处理，例如音乐返回一份结构化歌曲列表，需要转换成模型能理解的事实，同时保留界面展示结构。content、tts_content、model_content 分别面向界面、声音和 Director，不能全当一段最终回答。协议允许 tts_content 为空时退到展示内容，但不代表当前 Director 主链路赋予下游自主播报权；话语权仍受项目统一交互规则约束。
F11 · 正常结束：记 Agent 历史并回传
完整结果进入对应历史；is_finish终包结束本Agent请求；业务状态交回 E5核对；依赖动作由 D 下一轮发起。
正常流结束时保存该 Agent 已生成的内容和结构化观察，供后续多轮使用，再把业务结果交回执行层。比如导航返回候选路线，下一句“选红绿灯少的”需要依赖这份真实列表；不能只保留一段播报概括。保存成功和终包结束都不自动触发下一动作，目标还差一步仍由 Director 根据反馈规划。历史保存范围也应服从身份、隐私与会话隔离要求。
F12 · 历史直返：仅在明确配置下走
direct_return 是项目配置例外；可能结束该轮而不再经 D 总结；界面透传不等于语音自播；与新统一播报规则按版本区分。
历史 Planner 和 Agent 链路存在 direct_return 工具配置，有些返回会结束本轮而不再交 Director 总结。新 PRD 又要求统一话语权，两者必须按渠道和实际发布版本区分，不能写成所有工具永远直返，也不能宣称历史配置不存在。产品需要核对直返内容是什么、是否含语音以及如何保证说做一致。没有运行证据时，将它画为条件例外，不纳入默认主线。
F13 · Fallback：回 Director 重新规划
下游无法承接，给回退原因；由 Planner/D决定换工具或结束；不是默认同工具自动重试；已有副作用必须一并说明。
原图中的 Fallback 是下游无法继续时把原因交给 Planner，由它重新规划其他工具或结束话题，不是无脑重试原动作。比如工具不支持当前请求，应保留能力边界与已经做过的部分；若此前已提交订单，更不能换工具再下一个相同订单。标准协议有这个能力，不代表每个 Agent 都实现了同样回退条件，具体支持要按注册配置和测试用例确认。
F14 · Redirect：指定下个 Agent，调用方调度
下游明确指出要转交的Agent；调用方校验并调度目标实现；保留原问题、状态和关联身份；转交不等于目标已经完成。
Redirect 与 Fallback 不同：返回中明确指定下一 Agent，由调用方按协议调度，而不是让 Director 任意再想一个方案。转交之前仍需检查目标实现和权限，保留原会话、查询与已经发生的事实。不能把收到重定向当成目标 Agent 已执行，也不能无限绕圈。实际哪些 Agent 支持转交、最大跳转和超时边界，本轮未取得统一合同，应留待接口验收。
F15 · 取消与异常：结束连接不撤销业务
先发 cancel，再断开下游连接；记录已经生成的响应内容；预请求默认关闭需额外约定；超时/重试按具体工具，不统一猜。
Agent 协议区分正常、预请求和取消请求，预请求默认不启用，需要双方约定。取消时先通知下游再断连，并保留已生成内容；已经发生的车辆动作、订单或文件生成不会因此自动回滚。标准协议给出错误字段，但没有所有工具通用的超时秒数和重试次数。验收要模拟取消与结果同时到达，确认不会丢真实状态，也不会因新轮恢复再次执行旧副作用。
