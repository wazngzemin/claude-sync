# v15 业务含义与主链连通审阅

日期：2026-10-23。审阅对象：parts/voice.json、director.json、async.json、presentation.mjs、tools.json，以及 build-v15.mjs 的跨模块边。全图快照含 20 模块、288 节点、363 条模块内定义边；工具表 40 行已逐项审阅。未修改 JSON、构建器或其他人的文件。

这是根代理调整 23 条新 crossModuleEdges 前的独立快照审阅，不代表修复后验收已通过。下列最多 10 项均会改变业务理解或阻止完整交付；不是纯视觉偏好。

## 结论

先修数据装配和真实业务交接，再排节点。当前不是“模块不够”，而是部分箭头把准备、受理或问题输入接成了执行成功；另有前置授权/能力条件被旁路。普通已激活语音不应强制经过流式拒识，免唤醒和播报插话才按各自条件进入流式分支。

## 1. P1 — tools 合同与构建器不一致，来源也有覆盖/悬空

位置：build-v15.mjs 第 9 行来源组装及 meta；parts/tools.json；presentation.mjs 的 sources/sourceIds。

- tools.json 没有 sources 字段，构建器却展开 ...td.sources；这是确定的 undefined 不可迭代错误，当前产物无法构建。只读审阅没有执行构建，以免生成文件。
- tools.json 给的是 supplementalDefinitions、criticalUnknowns，构建器只读 additionalInventoryFindings/coverageNote，且只把 40 行 tools 放进 meta。新增 Task Agent、行程规划、节目编排、动态页面工具等补充合同与明确缺口会丢失。
- VOICE-TTS 在 voice 中指 10 月离在线 TTS PRD，在 presentation 中指 Sami 历史技术方案；后者按 Map 覆盖前者，I18 的优先级证据会错链。
- B/U 仍引用 ASY-EDGE、ASY-PLATFORM、ASY-CENTER、ASY-PRESET-PRD，但本次 async.sources 使用 ASY-Axx，现有 5 处模块引用缺来源。

建议：适配真实 tools 数据结构；补充定义另呈现、不计入 40 行；缺口保留可见。来源按事实文档分 ID 并校验全引用，不能悄悄用后出现的 URL 覆盖同名证据。DT-MEETING 两处来源若已确认是同一逐字稿可明确合并，但 TTS 两份不是同一文档。

验收：构建前 JSON/模块结构检查通过；所有 sourceIds 可解析且无异文同 ID；40 行、39 ID、6 弃用与补充定义分别可见。

## 2. P1 — presentation 新增 15 个节点参数错位，机制内容直接丢失

位置：parts/presentation.mjs 的 O10–O18、B10–B12、U10–U12。

辅助函数 N 接受 (id,title,lines,detail,kind)，这些调用却将多行说明拆成独立位置参数。结果每节点 lines 仅 1 行，第二条短语进入 detail，第三条进入 kind；完整解释没有进入节点。例如 O13 的 kind 是“方言/耳语等特定风格要求在线”，不是节点类型，detail 仅“系统警告可强制离线”。

这不是样式小问题：TTS 选路、缓存、真实播放、总开关与任务取消等新增机制恰好被吃掉，用户又会只看到一句话。

建议：按 N 的真实签名将 3–5 行用分隔符放到一个参数，完整业务解释单独传入；增加 kind 枚举、lines 数量、detail 长度校验，不靠渲染时默认 process 掩盖错误。

验收：上述 15 节点展开后均有完整业务机制；无自然语言 kind，图面说明与 detail 不再互串。

## 3. P1 — 动态能力准入被接在副作用发布之后

位置：director.json E3→F01、F04/F06；build 中缺 C8 与 F 的前置供给连接。

E3 的含义是获得输出许可后登记并发出动作；F01→F04→F06 却是在本轮推理前选择实现、核权限、检查动态条件、将 tool_info 注入 Director。现有 E3→F01 把“先知道有哪些合法工具”画成“动作发布后再检查”。F06 也没有明确回 C11/D1 的供给边，构成只有说明没有主链入口的能力岛。

建议分两段：推理前 C8/当前能力请求 → F01–F06 → C11/D1；模型选中后 E1/E2 → F07 参数校验 → 输出许可 → F08 单 Agent 执行。若 E3→F01 只是展开注释，必须用 reference 虚线，不应承担运行时箭头。

验收：沿任意产生副作用的路径走，权限、可用实现、参数与输出许可均先于实际下发；动态卡片不存在时不会先产生其工具调用再补检查。

## 4. P1 — 记忆与全渠道配置的授权节点存在可绕行箭头

位置：director.json C7→K07、C12→K09；build 的 C2→K02；async.json P02→P03 与 P02→P10。

预取路径可以沿 C1→C7→K07→K08→K10 返回，不经过 K01/K03；显式查记忆直接进 K09，同样从拓扑绕过授权。虽然 detail 写“先授权”，图面没有必经门禁。可信账号 K01 也没有实际跨模块入口。全渠道配置一支经过 P10，但 P02→P03 没标“非全渠道”，看上去可直接绕过 P10。

建议：记忆请求先到 K03，并确保 K01/K02 的可信身份已满足，按预取/显式模式再进 K07/K09；若只是展开引用，则明确标注“已授权请求”，不要混作真实调用。P02 的两出口标成互斥条件：普通范围直行，全渠道必须 P10 通过。

验收：未知身份、授权关闭、同名乘客、全渠道越权配置不能绕行进入读取/发布；拒绝不是空记忆或默认全范围。

## 5. P1 — 任务仅保存就返回“创建成功”，跳过 Trigger 注册结果

位置：build 的 T05→E6；async.json T05→T04→T06。

T05 明确只是保存 Task 事实；T04 才注册触发规则，T06 才进入正常等待。现有跨边在 T05 就写“任务创建结果返回调用方，成功才等待”，会让用户把存库成功当成提醒已安排，掩盖“Task 已保存但注册失败”。

建议：保存阶段可以返回 creating/已受理，但必须以阶段名标明；最终安排成功从 T04 成功出口或 T06 返回。注册失败应回明确失败/待补偿状态。上汽 Extour 的 creating、create_success 仍走自己的 T14/T15 分支，不与 Seres 共用一个成功节点。

验收：“10 分钟后关加热”在任务保存成功而 Trigger 注册失败时，不播已安排，不展示正常等待；恢复/补偿仍可追踪原任务。

## 6. P1 — VQA 问题刚提出就被当成结果回流，且跳过视觉准入

位置：build 的 E4→A10、A10→E6；async.json A01、A10→A15/A16→A11。

A10 是解析视觉问题和选择舱内/舱外通路，尚未拿到任何视觉答案；A10→E6 却写“视觉问答结果返回”，把请求当结果。E4 直接进 A10，也没有显示 A01 的隐私/资源前置门槛。

建议：显式请求先通过 A01/A02 的对应准入，或给 A10 标“已完成该调用权限/资源检查”的明确来源；实际文本/识别结果从 A11 或 A15/A16 成功出口回 E6。A18 的失败也必须回同一工具请求，不应只留视觉区内的死端。

验收：相机无权、AIBox 失败、图上传失败、结果不可判断都能沿同一调用回到 E6→M→D；拿到问题不等于看过画面。Seres 舱内失败不自动转云端。

## 7. P1 — 播放反馈回路缺源，插话又误接到首 token 合并节点

位置：build 的 O06→ids.get('I').nodes[0].id；M10 无输入；O04/O18 未连回 M10。

I 的首节点已变为 I13“有效新话到来：看旧推理到哪一步”，所以数组首项引用把播报中插话错误导向首 token 合并，而非 I1→I2 的流式停播判断。M10 的 STARTED/PROGRESS/FINISHED/ABORTED 负责释放输出许可，却没有来自真正播放器状态的边，M10→M9 成为无来源许可。

建议：写死 O06→I1，不以显示排序决定业务入口。真实播放 STARTED/PROGRESS/终态从 O04/O18 接 M10，再由 M10/M11 决定许可；首 token 不能冒充已播完。I13 作为 M 旁的输入时机说明，需标 10/19 口径与新 Input Manager 差异，不能覆盖新方案的真实播放/副作用许可。

验收：正在播时新有效语音能先按流式规则停声，不必等最终拒识；播放被抢占或无终态时也有准确的异常释放，不伪造播完。

## 8. P1 — 可见即可说把“注册界面”误作“本轮匹配入口”，无命中也没有回主线

位置：build 的 R3→W01；缺 W05 无候选出口、W03→V16 供给边。

W01 是页面/卡片先出现时由业务解析并注册控件，不是每个 Query 都重新开始的语义匹配。用户 final 应进 W04，再到 W05。当前无候选分支没有接回常规路由，用户说了一句普通车控或问答后可能在图上没有出口。热词配置与识别也断开。

建议：页面或卡片生命周期事件 → W01；W03→V16 为热词配置支路；有效 final/当前入口按配置 → W04；W05 无候选 → 普通入口 R1 或已通过门禁的对应节点，避免绕过拒识。W09 的真实结果交统一输出，W11→C5 保留历史，卡片退场→W12。

验收：匹配成功、多个候选、无候选、卡片过期四例都能串回对应业务；不得把此图改成 VLM 读屏或任意 GUI Agent。

## 9. P1 — 免唤醒早召回被放到 final 后，修复时也不能让全链必经 partial 拒识

位置：build 只有 V12→R1；voice.json R3→R13；缺 V3→R13 的条件支路。

R13 描述的是 ASR 过程文字出现 attend 后可提前放行音频，但当前总图只能从最终文字 V12 进入 R，意味着已等 final 才走“提前上传”。这会消掉免唤醒流式设计的实际意义。

建议：V3→R13 明确标“仅未激活免唤醒：过程文字驱动本地流式召回”，R14 上传后去云端最终判断；普通已激活路径保留 V12→R1/R15→R7/R8，不强制经过 R13。播报中的流式拒识是 I2 的另一组触发条件，不要合并成所有请求的唯一门。

验收：“未激活叫助手”可在 final 前上云；“已激活普通指令”无需多过一个流式拒识前置；“旁人聊天”最终拒识不能撤回已经上传的在途云端请求，也不能取消原有效工作。

## 10. P1 — PHUD 输出错接到可点击卡片，破坏静默/无按钮语义

位置：build 的 H10→U06 标签“静默文字”；H11→O18 标签“PHUD 动效回执”。

H10 实际是 PHUD 终端仲裁与渲染，不是静默文本下行；U06 定义为可见且可操作的卡片，后面自然接 U07 用户确认。这会让无按钮、无回调的闪念/动效在图上变成需要点击的业务卡片。H11 是两支真实曝光汇总，O18 是实际音频播放验收，把它连过去也容易将动效曝光误当播音证据。

建议：静默文字仍走 H09→H11，PHUD 走 H08→H10→H11；如需接 U，使用明确“静默无操作展示”节点/端口，不接 U06 的确认链。H11→H12 保留独立曝光验收；跨 O 仅可为 reference，标签明确与音频播放独立，不推进播放终态。

验收：PHUD 不显示但文字显示、文字失败但 PHUD 显示、二者被抑制三种情况可独立记录；任何一种都不生成用户确认或车辆执行成功。

## 已核正确、应保留的边界

- V 中 ASR/VAD 并行；Soft/Hard 从同次停顿起算；预请求不执行；编号及前轮精确文字匹配后才复用。
- 当前 R 正常激活路径没有把 partial 拒识列为必经门；应在补早召回边时保住这个区别。
- Task 与 Goal 按渠道分叉，不是串行双系统；G 的条件命中不直接控车。
- 40 行/39 ID/6 弃用与 PRD 33 业务行/34 ID 分开说明正确，不能显示“当前就有 40 个可调用工具”。
- M 新 Input Manager、F 动态工具、G Workflow、H 静默改造均已有设计/一期/待核限定。正式渲染仍要保留这些状态，不能仅在来源 note 中隐藏；尤其新设计不应因在蓝色主链上就被解读为全部线上。

## 回归顺序

先完成 1–2 的数据与内容校验，再修 3–10 的真实交接。然后用同一份全图跑：明确车控、缺记忆再导航、未激活免唤醒、播报插话、断网兜底、创建提醒注册失败、VQA 失败、可见即可说无命中、PHUD 单支失败。每例应能指出谁产生信息、谁检查、谁执行、谁回结果，以及用户最终看到或听到什么。
