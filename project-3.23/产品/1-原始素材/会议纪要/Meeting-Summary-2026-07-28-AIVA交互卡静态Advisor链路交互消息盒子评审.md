## 一句话结论

这次会议定的不是“一条统一后端链路”，而是“一个统一即时交互卡容器，支持三种不同调用模式”：

1. 字节云端 Static Advisor：云端理解与编排，端侧呈现。
2. 字节端侧触发器：完全端侧闭环，离线也要可用，通过“可见即可说”确认。
3. 赛力斯消息盒子：赛力斯先直接调端侧卡片；需要泛化语音时，再上云动态注册“选择工具”。

因此，卡片端在拉卡时必须知道“是哪种业务来源 / 是哪种交互模式”，否则无法决定用户说“好的”时是在本地处理，还是交给 Planner / Director。

## 三种链路的明确区别

| 链路 | 谁先产生任务 | 卡片在哪里出 | 语音由谁理解 | 是否依赖云端 | 真实动作谁执行 |
|---|---|---|---|---|---|
| Static Advisor | 云端 Trigger / Advisor | AI Bar 或即时交互卡 | Planner / Director | 是 | 端侧工具 / 赛力斯车控 |
| 端侧规则主动服务 | 端侧 Trigger | 即时交互卡 | 本地“可见即可说” | 否，要支持离线 | 端侧业务 / 赛力斯车控 |
| 赛力斯消息盒子 | 赛力斯自闭环业务 | 先在端侧即时交互卡呈现 | 手点本地；泛化语音拟由 Planner 临时选择工具理解 | 卡片本身不一定；泛化语音依赖云端 | 赛力斯业务 / 车控 |

> Planner 和 Director 在本项目里是同一决策职能的不同叫法，不应在流程图中画成前后两个决策模块。

## 会上明确的产品结论

### 1. 主动服务有两个来源

- `00:00:41–00:02:28`：一类是模型 / Static Advisor 输出，一类是规则配置主动服务。
- 赛力斯当时明确的端侧规则主动服务只有“天气 / 路况保护”。
- 端侧规则不经过模型推理，本质是 `if 条件命中 → 产生动作或询问`。

### 2. 不同执行等级决定出什么交互

| 执行等级 | 是否先问用户 | 是否 TTS | 结果展示 |
|---|---:|---:|---|
| 静默执行 | 否 | 否 | Static Advisor 在 AI Bar；端侧规则在即时交互卡 |
| AI Bar 按钮确认 | 是，手动点击 | 否 | 仅 Static Advisor 适用；点击后进 Director |
| 告知执行 | 否 | 是 | TTS + 即时交互卡 |
| 明确确认 | 是 | 是 | 先文本+确认/取消，确认后展示真实执行结果 |

### 3. 即时交互卡是统一容器，不是统一业务链路

- `00:03:00–00:04:01`：主动服务卡要有专用标识，与用户 Query 卡区分；车控、导航、媒体等业务组件复用现有基础样式。
- `00:18:50–00:20:23`：询问卡的基本结构是文本，可选确认/取消按钮；如果业务有图片、视频需求，需另行输入。
- `01:02:01–01:06:22`：用户 Query、云端主动服务、端侧主动服务和外部消息盒子都使用同一个即时交互卡容器，但各自输入、语音和执行回路不同。

### 4. 端侧触发器卡片明确不走 Planner

- `00:20:38–00:21:34`：云端主动服务的语音确认走 Director；端侧离线主动服务因为不经过 Director，只能靠注册“可见即可说”完成确认。
- `00:25:05–00:25:55`：规则配置链路是端侧自闭环，产品要求无网也能出卡和执行。
- `01:01:01–01:01:31`：汪帅再次确认，端侧触发器调卡时，确认/取消应直接在本地可见即可说闭环。

### 5. 卡片调用时要带“业务类型”

- `00:30:24–00:32:21`：客户端在拉起卡片时必须知道主动服务的类型，才能知道语音后续走 Planner 还是本地处理。
- 因此建议正式协议至少包含：`source_type`、`interaction_mode`、`card_id`、`action_id`、`need_tts`、`voice_route`、`lifecycle`。
- 上述字段名是产品建议，会议并未确认最终 Schema。

### 6. 工具执行结果是“按工具分组”呈现

- `00:09:55–00:10:47`：车控工具会一次下发 FC 列表，端侧执行成功后才展示对应卡片；执行失败不应伪装成成功控件。
- `00:13:09–00:17:36`：产品和设计希望按工具类型分组输出：车控一组、媒体一组、导航一组；工具组之间可以分批呈现，不需要等所有慢工具都结束。
- 这是产品期望，研发仍需评估；不能直接写成已实现。

### 7. 消息盒子是赛力斯的技术模块

- `00:33:48–00:39:13`：赛力斯消息盒子会透传外部业务消息。只有需要 TTS，或 TTS+二次确认的部分，才调字节即时交互卡。
- 纯系统弹窗可以由赛力斯自行实现，不需要进语音链路。
- `00:49:31–00:50:22`：消息盒子不是用户 Query，也不是主动推荐 Query，它是一种新的外部调用来源。

### 8. 消息盒子到卡片有两种技术方案，尚未拍板

- `00:45:19–00:46:39`：原倾向“赛力斯直接把消息给车端客户端”。
- 字节客户端要求云端—端侧协议统一，只认字节标准协议。
- 后续技术评审需二选一：
  1. 字节提供标准协议，赛力斯直接按标准协议调端侧；
  2. 赛力斯消息先进字节云，转换后再下发车端。

### 9. “动态选择工具”是消息盒子语音泛化的候选方案

- `00:35:45–00:36:38`：需二次交互的外部卡片，将卡片内容和按钮上报 Planner，动态注册选择工具。
- 工具生命周期与卡片绑定：卡片被关闭、消失或过期时，工具必须删除。
- `00:56:01–00:57:24`：语音走 Planner 命中动态选择工具；手动点击可本地直接执行，但要把卡片行为同步给 Planner 上下文。
- `00:57:57–01:00:58`：研发对是否应走 Planner / FC 存在争论。会上只确定了“需要语音泛化”，最终技术协议由晓伟相关团队在技术评审中收口。
- 产品倾向不让 Planner 理解具体车控功能，只将“帮我开 / 去开启 / 好的”归一到某个选项或 Yes/No，真实业务动作仍由赛力斯处理。

### 10. 手点卡片也必须同步 Planner 上下文

- `00:28:53–00:30:10`：用户手动点击卡片需通过事件上报，让 Planner 知道用户已经做了什么。
- `00:52:24–00:55:52`：卡片信息如何进 Planner，以及是否通过“模拟 Query”还没定。时间和事件的关联是主要风险。
- 因此产品必须定义 `card_id / event_id / action_id / timestamp`等关联键，但最终字段由技术方案评审确认。

### 11. 优先级是需求结论，“如何排队”还没有技术结论

- `00:27:03–00:28:14`：主动服务优先级低于用户 Query；用户 Query 过程中触发的主动服务应合并或等待，不应直接抢占。
- `00:36:38–00:44:35`：消息盒子同样不能打断用户 Query。现状是端侧没有排队，云端更像“新任务打断旧任务”。
- 研发提出可以用“实时抢占 / 非实时抢占 / 恢复”或统一任务管理实现，但没有拍板。
- `00:48:07–00:49:10`、`01:06:39–01:07:49`：需要建立统一优先级 / 仲裁表，至少覆盖系统安全、用户 Query、字节主动服务、端侧触发器和赛力斯外部消息。晓伟任务管理模块是候选承载点。

### 12. 语音和卡片生命周期

- 有 TTS 的主动服务 / 消息盒子：先进播报态，播完进全音区强聆听。
- 消息盒子复用通用对话策略：延时聆听 30 秒，有有效交互时刷新。
- 卡片通用生命周期：延时展示 10 秒，相关活跃事件刷新。
- 静默执行 / 静默展示不拉起语音，用户后续需要额外唤醒。

## 会上没有拍板的问题

1. 消息盒子是直连字节端侧标准协议，还是先经字节云转换。
2. 卡片信息如何上报 Planner：事件、Context 输入、模拟 Query，或新链路。
3. 动态选择工具的正式协议、选项形式、FC 边界、失败和超时。
4. 多来源卡片和语音的优先级、排队、打断、恢复、丢弃及超时策略。
5. 多轮 Query 什么时候算结束，后面排队的主动服务何时可以恢复。
6. 车控、导航、媒体等工具组是否能按产品期望分组流式呈现。
7. 车控卡是否能呈现执行前→执行后的数值变化，以及外部车控后实时刷新。
8. 可见即可说词条由通用卡片团队注册，还是由各业务研发注册。
9. 语音禁用是由字节逐个识别赛力斯场景，还是赛力斯只给一个全局 `can_voice_interact`状态。

## 对《系统预设任务端云一体架构-v02》的影响

### 需要修正

1. 将“无网出卡”从简单的文档冲突，改成分范围结论：端侧规则主动服务的产品要求已明确为“离线可出卡、可执行”；任务中心 PRD 的无网异常需确认是否只针对云下发卡。
2. 补上卡片调用的业务类型 / 语音路由字段，明确客户端为什么能区分本地语义和 Planner 语义。
3. 把消息盒子的两种接入方案画成分叉，不再把“赛力斯直接到端”画成唯一方案。
4. 把动态选择工具改成“产品要求确定，技术方案未定”，不应写成已经落地的 Planner 工具。
5. 补上统一仲裁节点，明确“用户 Query 高于主动服务 / 消息盒子”是已定体验，但队列 / 抢占 / 恢复的技术实现待定。
6. 补上卡片和临时工具的生命周期、用户点击事件上报、工具组分批结果展示。
7. 更新卡片容器、消息盒子、任务管理和车控组件的对齐对象，但对会议只给了称呼、没给全名的人保留待确认标记。

### 不需要推翻

1. 任务中心开关是运行门禁，不是触发条件和执行器。
2. 天气 / 路况保护是端侧 Trigger 自闭环。
3. 云端卡片仍在车机端渲染，云端只负责决策、上下文和工具编排。
4. 手动点击不能只停留在 UI，必须产生可关联的事件，用于业务执行和云端上下文同步。
