## 问题 1 · VLM/AI Service 返回的是 caption，不是 Yes/No

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 韩杰："我拿'是否雨雪天气'去请求 VLM/AI service，它能直接告诉我 Yes/No 吗？" 丁彬："LLM 没有……输入是 caption，输出也是 caption，无限级，不可枚举。" 王泽民："对，它会是一个描述。"
</callout>

**🔵 白话解释（Why）**

说白了，VLM 干的活儿是**"看图说话"**——你给它一个画面或状态，它吐一段自然语言描述，不是吐一个"是/否"。你问"宝宝睡了吗"，它可能回"睡着呢""睡了一会又醒了""醒了"，什么都可能。它天生就是个描述生成模型，不是给你下判断的分类器。

举个你们的真实例子：你问"是否雨雪天气"，你期望它回 `true`；但它实际回的是一段话——"车外有雨滴、路面湿滑、能见度中等"。这段话你端侧根本没法直接 `if`。

**🔴 为啥这事儿很烦（Impact）**

你在需求里如果写"VLM 判断是否雨雪 → 返回 Yes/No"，研发会当场说做不了——**你的需求就基于了一个不存在的能力**。而且它输出是"无限级"的自然语言，你没法穷举它会说啥，也就没法在端侧写死判断规则。更坑的是：**舱内能问"宝宝睡了吗"，舱外问"雨雪天气"却做不到**——这不是原理不同，是舱外场景现在还没训，能力没覆盖到。你要是不知道这条边界，评审时会被"为什么舱内能舱外不能"直接问懵。

<whiteboard token="LW1HwrZgJhl8JcbKGOgcslMpn1b" align="left"/>

**🟢 搞清楚了之后怎么说（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**产品的正确表达**："我要一个'是否雨雪天气'的**布尔条件**。至于是让 VLM 出 caption、再过一层模型/规则整形成 Yes/No，还是直接用能枚举的舱外感知信号——这是实现问题，你们研发定。但目前舱外这块 VLM 没训过，能枚举的值才能做条件，超出枚举的现阶段做不了，这个我认。"
</callout>

关键分野：**感知（VLM 描述）≠ 判断（布尔）**。中间永远缺一层"把描述收敛成结论"的东西。

**🟡 去找谁确认什么（Next Steps）**

1. **找丁彬**：确认舱外 VLM 现在能枚举出哪些值（雨/雪/晴？还是只有更粗的标签）——本周内要一份清单，这决定你能配哪些触发条件。
1. **找丁彬 + 元戎(Advisor侧)**：把"舱外雨雪判断"列进需要重训的能力清单，明确现阶段做不了、后续排期，别在需求里当已有能力写。
1. **你自己**：把"感知 caption → 二次整形 → 布尔条件"这条链路，作为你写触发器需求的默认模板，任何"判断类"条件都按这个套。

## 问题 2 · 端侧触发器是规则引擎，只认有限枚举

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 韩杰："端侧如果拿着字符串，其实没办法解析。" 丁彬："这个 string 不可控、没训过，需要把它再过一次模型，问问它有没有这个动作——已经在云端又经过了一次二次整形。" 王泽民："那这二次整形谁来做？"
</callout>

**🔵 白话解释（Why）**

端侧触发器本质就是一个**轻量规则引擎（if 条件判断）**，它靠精确匹配枚举值来干活，脑子里没有"理解自然语言"这套东西。你塞给它一个字符串"睡了一会又醒了"，它不知道这到底算不算"醒了"——因为它没有 NLU 能力。

类比：端侧就像一个只认工牌号刷卡的闸机，你给它一句"我是三楼那个新来的小王"，它根本刷不进去。它只认 `{醒, 睡}` 这种预定义的卡号。

**🔴 为啥这事儿很烦（Impact）**

这中间凭空多出一个**"二次整形/映射"**的活儿——把 VLM 的开放描述，再过一次模型或规则，收敛成有限枚举，端侧才能用。这个活儿现在没人做（就是丁彬说的昨晚那个"081"需求要干的事），而且它有归属：放端侧还是云端？谁负责？如果你需求里不点破这一层，就会出现"VLM 有输出、端侧却跑不通"的断点，最后甩锅到产品身上说"你需求没说清楚"。

<whiteboard token="UvqWwHUsrhbNkZbGFwocoS6Ench" align="left"/>

**🟢 搞清楚了之后怎么说（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**产品的正确表达**："端侧触发条件我只用**有限枚举值**。VLM 出的开放描述，中间需要一层'二次整形'把它映射成枚举——这层现在放在云端做。我需要研发明确：这层归谁、放哪、覆盖哪些动作/状态的映射表。"
</callout>

一句话钉死：**开放描述进不了端侧，必须先经过映射层变成有限枚举**。

**🟡 去找谁确认什么（Next Steps）**

1. **找丁彬**：确认"二次整形/映射层"的归属和位置（现在是云端），以及"081"那个需求是不是就在做这件事、覆盖范围多大——今天/明天就问，别拖到评审。
1. **你自己 → 丁彬**：把你手里那张动作/状态映射表输出给丁彬（会上你已答应），他拿去找西钺(元戎)问舱内能不能把这些动作都输出出来。
1. **找赵岩、汪帅(端侧研发)**：确认端侧触发器支持的枚举字段格式（结构化文本长啥样），保证你配的条件端侧能解。

## 问题 3 · 「车端状态信息」和「云端 context 整体」是两个东西

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 王泽民："不应该是'端侧是云端的子集'吗？为什么现在成了'云端是端侧的子集'？" 韩杰："因为云端(车端状态信息)来源于端侧，云端不可能比端侧更多……但整个云端 context 会比 AI service 多，因为有些不来源于车端信号。"
</callout>

**🔵 白话解释（Why）**

你俩其实没矛盾，是在说两个不同层级的东西，一个词套了两个概念，所以绕晕了：

- ① **「车端状态信息」**（context 里那个具体字段，比如车内成员/位置/身份）——它源头在端侧上传，所以**云端的这份 ⊂ 端侧原始信号**。云端不可能凭空比端侧的原始信号更多。
- ② **「云端 context 整体」**——它除了车端上来的信号，还叠加了后台日志、外部 API 这些非车端来源的东西，所以**端侧信号 ⊂ 云端整体**。

说白了：你说的"云端"是那个大箩筐（整体 context，啥都往里装）；韩杰说的"云端"是箩筐里的一格（车端状态信息）。一格当然比端侧小，箩筐当然比端侧大。

**🔴 为啥这事儿很烦（Impact）**

你判断"某个条件到底能不能拿到"时，得先分清它属于哪一类。如果它是车端状态信息，那"云端有没有"取决于"端侧有没有上传"——端侧没传，云端就是空的。如果你误以为"云端啥都有"，就会把一个端侧根本没上传的信号当成云端可用，需求评审时被研发一句"这个端侧没上报，云端拿不到"当场打脸。

<whiteboard token="CCt7w3Jl5h7vkhbwydSc6pRknR0" align="left"/>

**🟢 搞清楚了之后怎么说（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**产品的正确表达**："先对齐术语：我说的'云端'指整个 context（含日志/API），端侧是它的子集；但如果具体到'车端状态信息'这个字段，它源头在端、靠上传，那这份是端侧的子集，端侧没传云端就没有。我们讨论的这个条件，到底属于哪一类？"
</callout>

记住这条判断链：**看这个信息的源头在哪** → 源头在端且靠上传 = 云端⊂端侧；源头在云端叠加 = 端侧⊂云端。

**🟡 去找谁确认什么（Next Steps）**

1. **找韩杰**：要一份「车端状态信息」的字段清单（context 里那个名字），明确哪些是端侧上传来的、哪些是云端自己叠加的——这是你判断"条件可不可得"的底表。
1. **找端侧研发(赵岩/汪帅)**：对你要用的每个条件，确认端侧到底上报不上报这个信号，别默认云端一定有。
1. **你自己**：以后写条件需求时，每个条件旁边标一列"信息源头(端/云)"，从源头上避免子集搞反。

## 问题 4 · 产品定义 What，研发定义 How

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 韩杰："我不会告诉研发这个条件是端侧有还是云端有，而是提需求，研发来看端侧/云端哪有数据、怎么获取最好最准最快。这是研发去定的事。" 王泽民："农历节日这种需要 API 的，我去哪获取？"
</callout>

**🔵 白话解释（Why）**

边界就一条：**产品说"我要什么信息/什么条件"，不说"你去哪拿、放哪一侧"**。产品负责 What（哪个场景、以什么方式触发、中间要判断哪些条件、要不要离线可用、车机上的体验）；研发负责 How（这个数据端侧有还是云端有、怎么取最准最快、端云怎么配合）。

农历节日的正确表达：产品说"我要一个'是否农历端午节'的条件"，句号。至于研发是"触发器上电去请求云端节日 API"，还是"客户端本地提前写好时间推理"——那是研发内部的事，你不用管。

**🔴 为啥这事儿很烦（Impact）**

这正是你今天被暴露的根子——**之前产品把研发的技术方案拆进了产品逻辑**，结果就是韩杰说的："产品要输出的东西暴增，还容易漏洞百出"。你一旦替研发决定"从端侧判断"，就得懂端侧的所有实现细节，一个接不上就露馅。而且大家都在奇怪"为什么技术协议还要产品去定"——因为之前产品对过，研发就顺势甩给产品了。**越界不是勤快，是给自己刨坑。**

<whiteboard token="IQBVwh9LUhkMOIbzfYhc4ApCnic" align="left"/>

**🟢 搞清楚了之后怎么说（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**产品的正确表达**："我只声明我要哪些条件和信息，比如'是否农历端午''是否雨雪''是否高速'。这些信息你放端侧还是云端、怎么取，是你们研发内部端云配合的事，你们自己聊。我保证把要的东西说清楚；你保证按'最准最快、满足离线要求'把信息给我。不对的地方我们上升让老板拍板。"
</callout>

钉死这句：**产品不写"从哪拿"，只写"要什么" + "要不要离线"**。

**🟡 去找谁确认什么（Next Steps）**

1. **你自己**：把现有触发器需求过一遍，删掉所有"从端侧/云端判断"的实现描述，只留"要什么条件 + 离线要求"——本周内改完。
1. **找韩杰对齐**：把"产品定 What / 研发定 How"这条边界拉齐成团队共识，下次研发再问"端侧触发器搞不搞"，统一口径回"我们提条件，实现你们定"。
1. **找汇文(或老板)**：对"技术协议为什么要产品定"这个历史遗留，把边界上升拍板，避免研发继续甩锅。

## 问题 5 · 通用触发平台 / 原子能力库

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 韩杰："我想做一个原子能力的剥离……将来配置的就是一个一个脚本/剧本。第一需要一个平台，第二需要端云同步逻辑，第三在云端定义触发器、动作、条件……各业务自己创建脚本、订阅结果。" 丁彬："断网的时候这个功能要不要保证执行？"
</callout>

**🔵 白话解释（Why）**

这东西要做的根本原因就一个：**别再重复造轮子**。现在每个业务、每个场景都要单独开发一套"触发 + 条件判断"逻辑，成本高还没法复用。韩杰想把它抽象成原子能力库（触发/条件/动作三类原子能力）+ 可配置剧本——业务方以后只配置、不开发，director 的条件任务、定时任务、主动服务都能共用这一套。

类比：以前每盖一栋楼都从烧砖开始；现在做一个标准砖厂（原子能力库）+ 图纸系统（剧本配置），各业务照图纸搭就行。

**🔴 为啥这事儿很烦（尤其断网这条 · Impact）**

断网离线为什么能牵动整个架构选择？因为——**只要要求"断网也能跑"，这套能力就必须下沉到端侧**。你不能指望它每次都去请求云端。这一下就把"端云同步机制"从"可选优化"变成了"平台必备件"：云端配好剧本，得能下发给端侧、端侧能独立执行。所以离线需求不是个小细节，它**反向决定了哪些能力放端、哪些放云**。你需求里"哪些场景要离线可用"没说清，整个架构就没法定。

<whiteboard token="LPTPw9ofVhiwiGb4DF4cTc2rnnb" align="left"/>

**🟢 现在还是以后做（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**会上明确结论——并行推进，不是二选一**："两条腿走路：短期先用最简单、能实现的方案（端侧代码逻辑闭环）怼一批场景出来落地；同时同步设计通用平台架构（原子能力库 + 端云同步 + 剧本配置）。涉及端云配合的部分，拉小杰、赵衍单独聊。我需求里会明确每个场景'要不要离线可用'，因为这决定能力放端还是放云。"
</callout>

**🟡 去找谁确认什么（Next Steps）**

1. **你自己**：本周先输出一批"简单方案就能落地"的触发场景（端侧代码闭环那种），配合韩杰说的"先怼一批"节奏，别等平台。
1. **找韩杰**：确认通用平台的三块拆解（平台升级 / 端云同步 / 原子能力库）各自的负责方和时间线，明确产品在其中只提场景剧本。
1. **找小杰、赵衍**：把端云配合 + 离线执行这块单独拉会，逐场景标"离线必需/可在线"，这份标注就是架构分端云的输入。

## 问题 6 · 执行动作 ≠ Function Call

<callout emoji="speech_balloon" background-color="light-blue" border-color="light-blue">

**会上原话** — 韩杰："执行动作，比如驾驶模式切换，和 function call 有关系吗？我理解不相关。下雨切泥泞模式，理论上是不是直接调车端车控接口？" 王泽民："对。"
</callout>

**🔵 白话解释（Why）**

两个东西的本质区别就一句话：**触发器动作 = 规则决定调什么，Function Call = 模型运行时决定调什么**。触发器场景是"条件命中 → 执行一个写死的固定动作"，中间没有 LLM 在临场做选择，所以它就是直接调车控接口，跟 Function Call 不相关。

对比：

- **触发器动作**："下雨 + 非泥泞模式 → 调 `setDriveMode(泥泞)`"，规则写死，闭眼执行。
- **Function Call**："用户说'我有点冷' → LLM 自己从一堆工具里挑出 `setACTemp()` 并填参数"，有推理、有不确定性。

**🔴 为啥这事儿很烦（Impact）**

如果你把"执行动作"和"Function Call"混为一谈，就会在需求里给一个本该简单直调接口的动作，套上一整套 LLM 工具调用的复杂链路——**该简单的搞复杂，性能、时延、成本全上去了**，研发还得反过来纠正你。反过来，真正需要 LLM 自主决策的场景（开放意图），你又可能误用规则写死，覆盖不全。分不清这条线，需求粒度就永远拿捏不准。

<whiteboard token="MO7TwHi65hTh7YbAvNqcZNWEngc" align="left"/>

**🟢 搞清楚了之后怎么说（How）**

<callout emoji="⭐" background-color="light-green" border-color="light-green">

**产品的正确表达**："触发器的执行动作分两类：一类是确定性动作（切驾驶模式、开空调这种），规则命中就**直接调车控接口**，和 Function Call 无关；另一类才是开放意图，需要 LLM 用 Function Call 临场选工具。我们现在这批触发场景绝大多数是第一类，别套 FC。"
</callout>

判断口诀：**"调哪个"是写死的 → 直调接口**；**"调哪个"要模型临场决定 → Function Call**。

**🟡 去找谁确认什么（Next Steps）**

1. **你自己**：把这批触发场景的动作标成两类（确定性直调 / 需 LLM 决策），确定性那批明确写"直接调车控接口"。
1. **找韩杰**：对齐"确定性动作不走 Function Call"的口径，避免需求里给简单动作套复杂链路。
1. **找丁彬/研发**：对确实需要外部 API 的动作（如农历节日），确认走"触发器请求云端"还是"端侧本地推理"，但只声明要信息、不指定实现（呼应问题 4）。
