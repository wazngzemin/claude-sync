## 这份文件怎么读

这不是“每天三句话”的日报压缩版，而是一份逐日证据账。每一天固定回答四件事：

1. 当天具体聊了什么、推进了什么。
2. 信息来自哪条消息、哪场会议或哪份文档。
3. 会议有没有可读纪要；没有纪要时，哪些话只能算日报转述。
4. 当天留下什么问题，后来有没有发生变化。

### 证据等级

| 标记 | 来源 | 怎么使用 |
|---|---|---|
| A | 群聊或单聊原文 | 可信度最高，可证明对方当时具体说了什么 |
| B | 会议文字记录或智能纪要正文 | 可证明会上讨论过什么；AI 智能纪要仍需用逐字稿或后续消息校准 |
| C | Aime 工作日报 | 二次摘要，只能作为当天主线索引，不能替代原始聊天和纪要 |
| D | 关联 PRD、跟踪表、评测文档 | 可证明正式方案、版本和指标，但要看更新时间 |
| E | 会议元数据 | 只能证明会议存在或日历有安排；`current_user_participation` 为空时，不能单凭它证明你实际入会 |

6. 当时只覆盖舱内 VLM；舱外 VQA 和定时任务不在本次范围。

- 跟晓伟确认 Task 中心 804 是否有风险。

会议把链路拆得比较清楚：

1. Task 生成自己的 `task_id`，带场景名、Cron、调度类型向 Trigger 注册。
2. Trigger 返回 `scene_id`，Task 保存 `task_id ↔ scene_id` 关联。
3. 到点后 Trigger 通过 RPC 回调 Task，并带回 `task_id` 和公共参数。
4. 一次性任务触发后由 Trigger 自动删除场景。
5. 用户主动取消时，Task 根据关联找到 `scene_id`，调用 Trigger 删除。
6. 车辆下电先进入 Trigger，再由 Trigger 回调 Task；Task 判断哪些任务要删，然后走标准删除流程。
7. 更新定时任务采用“删除旧场景，再注册新场景”，不单独做 update 接口。
8. 新增 RPC 的同时保留弋途已有 HTTP GET 回调。
9. 定时器暂选 Asynq+Redis，只有默认队列；Dispatcher 投递，Worker 执行，Stopper 停止；并发暂设 100。
10. 需要补投递失败、续投失败、RPC 回调失败三类告警。
